```
## EC-NNN: <one-line name>  (YYYY-MM-DD, module: Mx, status: open | specced | tested)
- Scenario:
- Correct behavior (with the deciding rule and comparison operators spelled out):
- Golden scenario ref:
```

Seed sources: constitution M1 edge-case list, Appendix B4 battery (22 scenarios), Appendix A adversary taxonomy. **Seeded in Wave 3 by [M01](plans/M01-rules-engine.md).** `status: specced` means the behavior is decided and written down; it becomes `tested` when the golden file exists and passes in CI, which cannot happen before FREEZE.

Numbering blocks: EC-001 to EC-011 are the constitution's own M1 list, EC-012 to EC-033 are the B4 battery in order (`EC-(011 + n)` is B4 item `n`), EC-034 upward are discovered during the build. **EC-083 to EC-138 were added by Wave 3 batch 2 (M09 through M20)** and carry those plans' `review` status. **EC-139 and EC-140 were added by [ADR-025](DECISIONS.md#adr-025-progressive-cap-release-is-rejected-for-v1-and-replaced-with-cross-account-loyalty--2026-08-14-status-accepted) at the pre-Wave-4 fold**, taking the registry to **140**.

## EC-001: Rounding and comparison operators are per rule, never implied  (2026-08-13, module: M1, status: specced)
- Scenario: A threshold expressed as a percentage is compared against a money value, and the engine and the published rules page round differently by one cent.
- Correct behavior: Every threshold is materialized to integer cents at plan publish into `plan_version_sizes` and never recomputed at runtime. Every comparison operator is stated per rule in [M01 section 3.5](plans/M01-rules-engine.md) and mirrored verbatim in the plan's `copy_blocks`. Ratios are compared by integer cross-multiplication, never by division. There is no float anywhere in the engine, at any width.
- Golden scenario ref: GS-023, GS-029, and the boundary pair on every rule.

## EC-002: Consistency with a zero or negative denominator  (2026-08-13, module: M1, status: specced)
- Scenario: A funded account has a best day of 40,000c and a period profit of 0c or less. The ratio is undefined or meaningless.
- Correct behavior: The [consistency denominator rule](GLOSSARY.md#consistency-denominator-rule) applies. The gate is **skipped entirely** unless `period_profit_cents > 0` (strict `>`), and a skipped gate reports `pass: true, skipped: true`. No division is ever attempted, so there is no path to a divide-by-zero.
- Golden scenario ref: GS-021, GS-022.

## EC-003: Win day exactly at the floor  (2026-08-13, module: M1, status: specced)
- Scenario: A day closes at realized P&L of exactly the win-day floor.
- Correct behavior: Counts. The operator is `realized_pnl_cents >= win_day_floor_cents`, and the published copy says "at least". One cent below does not count.
- Golden scenario ref: GS-006, GS-007.

## EC-004: Breach and pass signals on the same day  (2026-08-13, module: M1, status: specced)
- Scenario: A day's low is below the floor and the same day's close is at or above the profit target.
- Correct behavior: **Breach wins.** Day ordering is binding and is a single ordered pipeline: mark ingest, then breach check, then progression. The breach check uses the floor **at the open of the day**, so a new closing high cannot retroactively rescue a day that already broke the floor. No `phase.passed` is emitted and no funded state is written.
- Golden scenario ref: GS-012, GS-063, GS-064.

## EC-005: Trading-calendar half days  (2026-08-13, module: M1, status: specced)
- Scenario: A shortened session, for example the day after Thanksgiving.
- Correct behavior: A half day is a full trading day for every counter: minimum days, cadence gap, and win-day eligibility. It is published as such so nobody is surprised.
- Golden scenario ref: GS-003, GS-032.

## EC-006: Account with fills but flat P&L  (2026-08-13, module: M1, status: specced)
- Scenario: A trader opens and closes a position for exactly zero realized P&L.
- Correct behavior: `traded_day = true` because `fill_count > 0` (strict `>`). `win_day = false` because `0 >= win_day_floor_cents` is false for any positive floor. The two flags use different operators on different inputs and both are asserted.
- Golden scenario ref: GS-005.

## EC-007: Payout request landing mid nightly batch  (2026-08-13, module: M1 + M5, status: specced)
- Scenario: A request arrives at 23:59:59 while the batch that closes the next day starts at 00:05.
- Correct behavior: Every evaluation is against the [last closed day](GLOSSARY.md#last-closed-day) and nothing more recent. The request pins `basis_trading_day` into an immutable snapshot, so the answer does not depend on whether the batch had started, finished, or crashed.
- Golden scenario ref: GS-035.

## EC-008: Cap greater than withdrawable  (2026-08-13, module: M1, status: specced)
- Scenario: The plan cap is 150,000c and the account's withdrawable is 120,000c.
- Correct behavior: Auto-clamp. `approved_cents = min(effective_request, cap_cents_for_ordinal, withdrawable_cents)`, `clamp_reason: withdrawable`. The clamped amount is shown before submission so the number never changes underneath the trader.
- Golden scenario ref: GS-026, GS-027, GS-028.

## EC-009: Multiple accounts, same identity, requesting the same day  (2026-08-13, module: M1 + M5 + M6, status: specced)
- Scenario: One [trader identity](GLOSSARY.md#trader-identity) holds ten funded accounts and several become eligible on the same trading day.
- Correct behavior: Each account is evaluated independently and each request is individually correct and individually capped. There is no cross-account state in the engine, by design. The aggregate exposure surfaces at identity level in admin, and the Eligible-Next-7-Days forecast is identity-aware so a correlated wave is visible before it lands.
- Golden scenario ref: GS-036, GS-062.

## EC-010: Config migration never touches existing accounts  (2026-08-13, module: M1 + M3, status: specced)
- Scenario: Plan version 2 is published while accounts exist on version 1.
- Correct behavior: An account's `plan_version_id` is pinned at purchase and never changes, enforced by an update trigger. A published version is immutable, enforced by a second trigger. The engine reads the account's pinned version as an input and has no concept of a "current" version.
- Golden scenario ref: GS-041.

## EC-011: Replay determinism  (2026-08-13, module: M1, status: specced)
- Scenario: Re-running every mark from day one must reproduce the stored `rule_states`.
- Correct behavior: Byte-identical, compared by canonical state hash first and then field by field on mismatch. This runs as a nightly self-audit job in production, not only in CI. Any divergence halts payout eligibility for the affected account and pages. The full design, including the engine-upgrade protocol that stops a bugfix from paging on every historical row, is [M01 Appendix B](plans/M01-rules-engine.md).
- Golden scenario ref: GS-071 to GS-075.

## EC-034: A settled payout looks like a catastrophic loss  (2026-08-13, module: M1 + M2, status: specced)
- Scenario: A 150,000c payout settles and the platform reduces the simulated account balance. The next mark's closing balance is 150,000c lower with no losing trade behind it. Under a naive breach check, a trader who just earned a payout can be breached by receiving it.
- Correct behavior: **Amended by [ADR-014](DECISIONS.md), which removed the middle of the three original mechanisms.** Non-trading balance movements are carried in `daily_marks.adjustment_cents` (schema delta SD-01) and are applied **between sessions**, at the open of the payout's effective trading day, never inside a session (dependency D-M2-2, and a vendor-confirmation item). The floor is **not** recomputed at settlement and does not need to be: config validation guarantees the post-payout balance clears the floor before any account is ever sold on that config. `buffer_cents` must exceed the locked-floor offset when the lock is enabled (CV-11), and every cap must be below the drawdown when it is not (CV-17), which together bound the floor above by `size + lock_offset` or below the post-payout balance in every reachable configuration. The mark identities `opening == prior_balance + adjustment` and `closing == opening + realized_pnl` are asserted on every mark, and a violation raises reconciliation rather than being computed on. The result is unchanged, INV-21: a settled payout can never breach the account that earned it. What changed is **where** it is enforced, and publish time is the better place, because a config that could break it never reaches an account rather than being compensated for on every settlement forever.
- Golden scenario ref: GS-065, GS-081, GS-083.

## EC-035: Comparing the day's low against the floor after trailing it  (2026-08-13, module: M1, status: specced)
- Scenario: A day dips below the floor at 10:00 and then rallies to a new closing high. If the engine trails the floor to the new high before checking the breach, the day is compared against a floor that did not exist while the trader was below it. In the other direction, if a naive implementation trails first on a losing day, nothing happens, so the bug hides until exactly the volatile day that matters.
- Correct behavior: The breach comparison uses `floor_at_open`, which is the floor carried by the previous closed day's rule state. Trailing happens strictly after the breach check, within the same day evaluation. Stated as rule R-18 and stored explicitly as `rule_states.floor_open_cents` (schema delta SD-04) so the evidence pack can show which number the decision used.
- Golden scenario ref: GS-012.

## EC-036: Eligibility is not monotone in profit  (2026-08-13, module: M1, status: specced)
- Scenario: An account is eligible with best day 30,000c and period profit 100,000c, exactly at a 3000bp threshold. The trader has one more good day of 20,000c on what was already their best day. Best day is now 50,000c, profit 120,000c, share 4166bp, and eligibility is **lost** by making money.
- Correct behavior: This is correct and intended, and the constitution's section 5.1 phrasing "eligibility is monotone in its inputs" is imprecise. The precise property, and the one the property suite asserts, is: eligibility is monotone non-decreasing in profit added on **any day other than the current best day**, monotone in elapsed trading days, and monotone in win-day count. It is **not** monotone in profit added to the best day. The trader-facing consequence is handled by reporting `profit_needed_to_dilute_cents` on the eligibility endpoint so the path forward is always visible.
- Golden scenario ref: GS-069.

## EC-037: A failed transfer consumes a ladder rung  (2026-08-13, module: M1 + M5, status: specced)
- Scenario: Payout ordinal 3 is approved, the transfer exhausts its retry budget, and the request ends `failed`. Under `unique (account_id, payout_ordinal)` the retry must take ordinal 4, which advances the trader up the cap schedule and toward graduation for a payout they never received.
- Correct behavior: The ordinal is defined as `payouts_settled_count + 1`, so a failed attempt does not consume a rung, and the uniqueness constraint becomes partial: `unique (account_id, payout_ordinal) where status <> 'failed'` (schema delta SD-05). Graduation and the cap schedule both key on settled count, never on attempt count.
- Golden scenario ref: GS-066.

## EC-038: Split rounding direction  (2026-08-13, module: M1 + M5, status: specced)
- Scenario: An approved amount of 100,001c at a 9000bp split. Naive integer division yields trader 90,000c and firm 10,000c, and one cent vanishes.
- Correct behavior: `trader_cents = ceil(approved_cents * split_bp / 10000)` computed as `(approved * split_bp + 9999) / 10000` in integer arithmetic, and `firm_cents = approved_cents - trader_cents`. The remainder always goes to the trader, the legs always sum exactly to the approved amount, and the published copy says the rounding favors the trader. It costs at most one cent per payout and it is a free trust signal.
- Golden scenario ref: GS-029.

## EC-039: The cadence anchor changes the published extraction ceiling  (2026-08-13, module: M1, status: specced)
- Scenario: The [cadence gap](GLOSSARY.md#cadence-gap) can be counted from the payout's basis day or from its settlement day. On CORE-50K the choice moves the steady-state extraction ceiling from 19,300c per trading day (settlement anchored, a roughly 7 trading day cycle) to 27,000c per trading day (basis anchored, a 5 trading day cycle), a 40% difference in the per-account liability rate.
- Correct behavior: **Ruled at the M1 gate, [ADR-013](DECISIONS.md): settlement anchored.** `cadence_anchor_day` is the settled payout's **effective** trading day and the gap counts trading days strictly after it (R-37). Win days and the consistency period reset on the **basis** day of that same payout (R-47), so progress earned during the transfer window is not confiscated. Two anchors, each with a stated reason, both stored on the payout row and both deterministic under replay. The founder's lifecycle simulation was basis anchored, so realized liability is at most the modeled figure. The same ruling renamed Rapid Daily to **Merit Rapid** and requires its cadence to be published honestly rather than as daily.
- Golden scenario ref: GS-055, GS-059, GS-068, GS-082.

## EC-040: Payout stacking inside the settlement window  (2026-08-13, module: M1 + M5, status: specced)
- Scenario: Win days and the consistency period reset on settlement. A trader who is eligible fires a second and third request during the two to three business day transfer window, before any reset has happened, and converts one qualifying stretch into three capped extractions.
- Correct behavior: G-NO-IN-FLIGHT is part of eligibility: no request may be created while another for the same account is `approved`, `transferring`, or `frozen`. Enforced by a partial unique index, not only by the engine, because the engine is not the only writer. This is a liability control and is documented as one wherever the `conflict` error appears.
- Golden scenario ref: GS-052, GS-053.

## EC-041: The funded account does not start at the account size  (2026-08-13, module: M1 + M2, status: specced)
- Scenario: On eval pass, the platform fails to reset the simulated account and the first funded mark opens at the eval closing balance. The trader begins the funded phase already in profit, clears the buffer immediately, and can extract before any funded gate has had time to work.
- Correct behavior: The funded phase begins at `size_cents` and eval profit is never carried. The engine asserts `first funded mark.opening_balance_cents == size_cents` and refuses the day with a reconciliation error rather than computing on it. Whether M2 achieves the reset by resetting the platform account or provisioning a new one is M2's choice; the assertion is M1's contract either way.
- Golden scenario ref: GS-070, GS-019.

## EC-042: Minimum trading days is dominated by the win-day gate  (2026-08-13, module: M1, status: specced)
- Scenario: CORE-50K was proposed with 5 win days and 5 minimum trading days. Since every win day is a traded day, the minimum-days gate can never be the binding constraint and provides no protection whatsoever.
- Correct behavior: **Resolved at the M1 gate by [ADR-015](DECISIONS.md): funded `min_trading_days` is 0 on all three plans.** The field stays, because it is the binding gate on any future plan where `required_win_days < min_trading_days` and it is what stops a one-day funded account on a future config, but at 0 the gate is **explicitly disabled** and reports `pass: true, skipped: true` rather than sitting in the eligibility breakdown reading as satisfied (CV-19). The publish-time warning also stays and now fires on all three plans by design, so the domination is a thing the founder sees in every publish diff rather than a thing the corpus remembers. Marketing copy must not present a dominated gate as a separate protection.
- Golden scenario ref: GS-060, GS-080.

## EC-043: Zero-risk day farming  (2026-08-13, module: M1 + M7, status: specced)
- Scenario: A [traded day](GLOSSARY.md#traded-day) requires only one fill. One micro round trip per day advances the traded-day counter at commission cost, so minimum-trading-day requirements are a fee rather than a constraint. Across a rented fleet this keeps every account's counters advancing while a single directional account carries the ring's risk.
- Correct behavior: The engine's definition does not change: a fill is a fill, and inventing a minimum-size or minimum-duration test invites arguments Merit will lose in public. The answer is that the real gates are win days, the buffer, and consistency, and that the pattern (fleets of accounts with exactly one round trip per day) is a detector signal for M7 rather than a rule.
- Golden scenario ref: GS-060.

## EC-044: An engine upgrade pages on every historical row  (2026-08-13, module: M1, status: specced)
- Scenario: A legitimate engine bugfix changes a computed value on historical days. The nightly replay self-audit compares stored against recomputed and raises `replay.divergence_detected` for thousands of accounts at once, burying the one real divergence.
- Correct behavior: Divergence detection compares only rows whose `engine_version` equals the running version. Changing the version requires the documented upgrade protocol in [M01 Appendix B](plans/M01-rules-engine.md): a dry-run replay that produces a full diff report, founder approval of that report, an audited rewrite of historical states under the new version, and a hard rule that **no settled payout's `eligibility_snapshot` is ever rewritten**, because the snapshot is what was true when the money moved.
- Golden scenario ref: GS-075.

## EC-045: Consistency period off-by-one at the settlement boundary  (2026-08-13, module: M1, status: specced)
- Scenario: The consistency period is "profit since the last payout". If the basis day is included in the new period, the day that funded the payout also counts against the next one, and a single good day silently blocks the following cycle.
- Correct behavior: The period is trading days **strictly after** the anchor day: `d > payout_anchor_day`. On a fresh funded account with no settled payout, the period is trading days `d > funded_on`, which excludes the eval pass day for the same reason. Both boundaries are pinned by fixtures because a one-day error here moves real eligibility and is invisible in aggregate.
- Golden scenario ref: GS-068.

## EC-046: Holiday clusters stretch and compress the gap in calendar time  (2026-08-13, module: M1, status: specced)
- Scenario: A 5 trading day cadence gap is 7 calendar days in June and 9 or more across the Christmas cluster. Traders experience this as the rules changing.
- Correct behavior: The gap is counted in [trading days](GLOSSARY.md#trading-day) and always was. The engine reports `next_eligible_trading_day` as a concrete date resolved through the calendar, so the trader sees the actual date rather than doing the arithmetic, and the published copy states the unit explicitly.
- Golden scenario ref: GS-059.

## EC-047: A trading day with no mark at all  (2026-08-13, module: M1 + M2, status: specced)
- Scenario: The vendor report omits an account entirely for a session. This is different from a day with no fills, which produces a mark with `fill_count = 0`.
- Correct behavior: A missing mark is never treated as a flat day. The engine's fold advances only on marks it is given, so a gap in the mark stream leaves the account's counters where they were, and the batch raises a completeness check: every `active` account must have exactly one live mark per trading day it was open. A missing mark is a reconciliation alarm, and the account is `recon_blocked` until it is resolved, which excludes it from payout eligibility.
- Golden scenario ref: GS-033, GS-047.

## Entries discovered at the M1 gate (2026-08-13)

The three below were produced by the founder's rulings rather than by drafting. Per the constitution's working agreements, a discovered gap becomes an entry here even when the gap was created by a decision that was correct.

## EC-048: Removing the post-payout floor reset creates a config that pays an account into a breach  (2026-08-13, module: M1, status: specced)
- Scenario: [ADR-014](DECISIONS.md) removed the post-payout floor recompute. On a trailing-EOD plan with the floor lock **disabled**, the floor sits `drawdown_cents` below the account's high-water balance and stays there. A trader who requests a payout on a new closing high has their balance reduced by up to `cap_cents` against a floor that does not move. If `cap_cents >= drawdown_cents`, the account opens the next session at or below its own floor and breaches on the day it was paid, which is precisely the failure INV-21 exists to make impossible.
- Correct behavior: A publish-time rejection, not a runtime compensation. **CV-17**: when `drawdown.type = "trailing_eod"` and `drawdown.lock.enabled` is false, every `cap_cents` in the schedule must be strictly less than `drawdown_cents`. When the lock is enabled, CV-11 already covers it by a different route: the floor can never exceed `size_cents + lock_offset`, and the post-payout balance is at least `size_cents + buffer_cents`, so `buffer_cents > lock_offset` is sufficient. No v1 plan can reach the unlocked case, since all three enable the lock, which is exactly why it is validated rather than trusted to stay true. INV-21 is now a property of the config rather than of the settlement code path, which is the stronger arrangement: it fails at publish, once, instead of needing to be right on every settlement forever.
- Golden scenario ref: GS-083, GS-065.

## EC-049: The cadence gap can be dominated by the win-day gate, and the two gates use different anchors  (2026-08-13, module: M1 + M9, status: specced)
- Scenario: Merit Rapid publishes a 1 trading day cadence gap and requires 5 win days. Win days reset to the settled payout's **basis** day and each one needs its own trading day, so no second request can qualify until 5 trading days after the basis day. The 1 day gap never binds. The plan's real cadence is 5 trading days, roughly weekly, and the number a trader would compute from the published gap is wrong by a factor of five. This also invalidated M01 OQ-1's own estimate of 3 to 4 trading days, which was made before the win-day count was fixed.
- Correct behavior: The engine is correct and does not change; the failure is a marketing-versus-implementation gap, which constitution section 0.5 treats as the thing the corpus exists to prevent. Three responses. **Published copy states the real cycle** (about 5 trading days for Merit Rapid) and may not attribute the plan's speed to its 1 day gap. **A publish-time warning fires** when `cadence_gap_trading_days + min_settlement_lag_trading_days <= win_days.required_count`, where `min_settlement_lag_trading_days` is a published config constant with v1 value 2, because the two gates measure from different anchors (gap from the effective day, win days from the basis day) and a naive comparison would wrongly flag Core EOD, where the gap genuinely binds at 7 to 8 trading days. And **the portal's `next_eligible_trading_day` resolves through the calendar**, so no trader ever has to do this arithmetic themselves. Whether Merit Rapid's win-day count should change is [OQ-12](plans/M01-rules-engine.md), a plan-economics decision and a config edit, not an engine change.
- Golden scenario ref: GS-082, GS-059.

## EC-050: A gate configured to zero is indistinguishable from a gate that passed  (2026-08-13, module: M1 + M4, status: specced)
- Scenario: [ADR-015](DECISIONS.md) sets funded `min_trading_days` to 0 on all three plans. Evaluated naively, `traded_days_count >= 0` is true on day zero and forever, so the eligibility breakdown shows a green gate that was never a constraint. A trader reads it as a hurdle they cleared; a support agent reads it as evidence the account met a requirement; a future config author reads it as a protection that exists. All three are wrong in the same way, and it is the same failure as EC-042 wearing different clothes.
- Correct behavior: A gate whose configured threshold makes it unconditionally true reports `pass: true, skipped: true`, the identical shape the [consistency denominator rule](GLOSSARY.md#consistency-denominator-rule) already uses for a skipped comparison, and the portal renders `skipped` as visibly disabled rather than as satisfied (CV-19). `engineEligible` is unaffected, because the conjunction of gates treats a skipped gate as true, which it is. The general rule this establishes and which every later module inherits: **a gate that cannot fail must say so.**
- Golden scenario ref: GS-080, GS-060.

## Entries from M02 (Rithmic bridge)

## EC-051: A balance movement that is neither trading nor a known settlement  (2026-08-13, module: M2 + M5, status: specced)
- Scenario: The vendor's EOD report shows an account's balance changed by an amount that does not match the day's fills and does not match any settlement Merit knows about. Candidate causes: a vendor-side adjustment, a fee Merit did not model, a manual correction by platform support, or a payout Merit's own records have not caught up with.
- Correct behavior: **The normalizer refuses to guess.** Every balance delta is classified as trading (explained by fills) or non-trading (explained by a settlement Merit issued, which becomes `adjustment_cents` under SD-01). A delta that fits neither quarantines that account's day, sets `recon_blocked`, and alarms. It is never absorbed into `realized_pnl_cents`, because doing so would make a vendor fee look like a trading loss and could breach an account (INV-M2-12). The correct resolution is a human matching it against M5's settlement record or the vendor's own explanation, then a corrected mark.
- Golden scenario ref: GS-092.

## EC-052: A redelivered file that is not byte-identical and carries no correction markers  (2026-08-13, module: M2, status: specced)
- Scenario: The vendor re-exports a day already applied. The bytes differ so the `sha256` duplicate guard does not fire, and the rows carry no `correction_of` reference. Processing it as new either collides on the live-mark unique index or doubles every account's realized P&L for that day.
- Correct behavior: Ingest file disposition is an explicit four-way decision recorded on the row (SD-M2-03): `new`, `duplicate_ignored`, `full_replacement`, `correction_set`. A row touching an already-applied trading day without a correction reference **quarantines the whole file** and pages. A deliberate `full_replacement` is a human decision that supersedes the prior marks rather than deleting them, emits `ingest.file_replaced`, and triggers replay forward with settled snapshots untouched.
- Golden scenario ref: GS-086.

## EC-053: A recycled platform account reference  (2026-08-13, module: M2, status: specced)
- Scenario: The platform reissues a User ID or account reference that a closed Merit account previously held. Historical files or late corrections for the old account then route onto the new one. Two accounts are corrupted, the fills are internally consistent so reconciliation may not catch it, and replay diverges on an account that did nothing wrong.
- Correct behavior: A platform reference is **burned permanently** on account close. `platform_account_refs` (SD-M2-02) records assignment and retirement, `platform.account_ref_retired` announces it, and any inbound row citing a retired reference quarantines the whole file rather than being routed anywhere at all. Losing a day of data is the correct trade against silently corrupting two accounts. Whether the vendor's identifier space forces reuse is V-M2-10 and, if it does, the answer is a Merit-side surrogate with an explicit epoch rather than an assumption.
- Golden scenario ref: GS-089.

## EC-054: A risk setpoint that was delivered but never applied  (2026-08-13, module: M2 + M6, status: specced)
- Scenario: Merit's entire intraday risk posture is one number pushed to the platform: the auto-liquidation setpoint at the account's floor. SFTP delivery confirms transport, not effect. An account whose setpoint never applied has no intraday enforcement, looks identical to a well-behaved account, and carries unbounded loss for the firm under an EOD rule model that explicitly assumes the platform stops the trader.
- Correct behavior: Transport success is **not** confirmation for `set_risk`, which is the one provisioning operation that may never reach `confirmed_inferred`. Confirmation is either an acknowledgement artifact (V-M2-06) or, where the report exposes it, a nightly comparison of the platform's stated setting against our floor (V-M2-08). Failing both, the fallback is behavioral: a day whose low went below the floor **without** an accompanying liquidation record is evidence the setpoint is not working and is a page. Unconfirmed setpoints appear as a named number on the admin liability dashboard, because an unenforced funded account is carried liability whether or not anyone noticed.
- Golden scenario ref: GS-087.

## EC-055: Entitlement hygiene disabling an account that is still trading  (2026-08-13, module: M2, status: specced)
- Scenario: The nightly job that disables billable platform entitlements for closed accounts disables one belonging to a live funded trader, taking them offline mid-session. The inverse failure, a job that silently stops running and leaks real money monthly, is the same job's other direction.
- Correct behavior: The two directions get deliberately asymmetric controls, because their costs are asymmetric. Disable fires **only** on a terminal account status with `closed_on` set, never on inactivity, never on a heuristic, never on a missing mark, and a disable targeting an `active` account is a hard error rather than a warning. The leak direction is caught by evaluating the alarm on the **query** ("any closed account entitled more than 24 hours") rather than on the job's own success signal, plus a monthly reconciliation of the vendor invoice against `platform_entitlements`, which requires knowing the vendor's billing unit (SD-M2-05).
- Golden scenario ref: GS-088.

## EC-056: The vendor's session date disagrees with our calendar  (2026-08-13, module: M2, status: specced)
- Scenario: A fill executed near the session boundary is assigned to one trading day by the platform's stated session date and to another by Merit's calendar containment. Silently taking our own answer hides the disagreement; silently taking theirs breaks replay determinism, since our calendar is what every counter is defined against.
- Correct behavior: Store both (SD-M2-04, `trading_day_vendor` plus `trading_day_source`) and **alarm on divergence**. Merit's calendar decides `fills.trading_day`, because every rule in the engine is defined against it, but the disagreement is the most valuable ingest signal available and must never be discarded. Systematic clustering of a trader's fills within seconds of the boundary is an M7 detector input rather than a rule, because trading into the close is entirely legitimate and a rule against it would be indefensible.
- Golden scenario ref: GS-090, and it shares the calendar fixtures GS-030 and GS-032.

## Entries from M03 (billing and checkout)

## EC-057: A refund taken before any trade, repeatedly, as free optionality  (2026-08-13, module: M3 + M7, status: specced)
- Scenario: The refund policy is pre-first-trade only. A buyer purchases an evaluation, watches the market, and refunds when conditions look poor, repeating until a good setup appears. "No trades placed" reads as "nothing consumed", but the account cost real entitlement money from provisioning, occupied a slot against the entity cap, and delivered something of value: the option to start on a day of the buyer's choosing.
- Correct behavior: The policy needs a fact to hang on, so `purchases.first_trade_at` is recorded by M2 on the account's first fill (SD-M3-02) and the window is enforced against it rather than against a support judgment. Refund **velocity per identity** is a risk signal routed to M7, never a checkout block, because a first-time buyer's refund is a support win and blocking it costs more brand than the pattern costs money. Entitlements are not provisioned before the account opens, which bounds the cost of the pattern to PSP fees. Stated honestly: this cannot be fully closed without charging for the option, and charging for the option is a worse product.
- Golden scenario ref: none owned; covered by the refund-window unit suite and M7's velocity detector.

## EC-058: Failover double-charges one purchase across two MIDs  (2026-08-13, module: M3, status: specced)
- Scenario: PSP-A goes slow, health checks mark it degraded, and a retry routes the same purchase to PSP-B. PSP-A then confirms. One buyer, two charges, two accounts, and a chargeback that damages exactly the MID health the failover existed to protect. Every individual step is reasonable and the bug only appears under the provider slowness that triggers failover, so it never shows up in testing.
- Correct behavior: **Failover is per-attempt routing and never mid-transaction.** Once a payment session exists at a provider, that purchase completes there or fails there; Merit never retries the same purchase elsewhere, because the card may already be charged and the provider may simply be slow to say so. A new attempt is a new purchase row with a new idempotency key, linked to the first so support can see the pair. Detection: an alarm on any identity holding two `paid` purchases for the same plan and size inside five minutes, which is the fingerprint of both this bug and a genuine double-click.
- Golden scenario ref: GS-095.

## EC-059: A leaked coupon code silently reprices resets forever  (2026-08-13, module: M3, status: specced)
- Scenario: A launch discount code leaks, as launch codes always do. The visible exposure is discounted evaluations. The real exposure is that resets are the highest-volume repeat purchase in the business, so a code with no purchase-kind restriction discounts every reset indefinitely and permanently reprices the revenue line that funds payout liability. Nobody notices, because per-transaction revenue looks normal and only slightly lower.
- Correct behavior: `applies_to_kind` (`new`, `reset`, `any`) and `first_purchase_only` on every coupon (SD-M3-04), with `applies_to_kind` **required at creation** rather than silently defaulted, plus `max_redemptions` as launch-code policy and the existing `per_identity_limit`. The detection that actually works is **realized discount rate per plan per week**, because absolute revenue hides a leaked code and realized discount rate does not.
- Golden scenario ref: GS-097.

## EC-060: A reset silently moves a trader onto rules they never agreed to  (2026-08-13, module: M3 + M4, status: specced)
- Scenario: Existing accounts are pinned to their plan version and are safe. Resets are not: a reset resolves the plan version current at reset time. A trader who breaches on Tuesday and rebuys on Wednesday, after a version publishing a lower cap or a longer gap, gets the new rules. Every mechanism behaved as designed, there is no bug anywhere, and the trader is still right to be angry.
- Correct behavior: The reset flow **renders the diff** between the parent account's plan version and the version being purchased whenever they differ, and requires explicit acknowledgement before payment. `copy_blocks` keyed by rule path is what makes the diff renderable at all, which is the same mechanism that keeps marketing equal to implementation, applied at the one moment a trader is most likely to be surprised. Dual control on cap, split, and gap edits ([ADR-010](DECISIONS.md)) means the publish that would trigger this cannot come from a single compromised session.
- Golden scenario ref: GS-098.

## EC-061: A payment event that Merit never originated  (2026-08-13, module: M3, status: specced)
- Scenario: A forged or replayed webhook, or a PSP that reports success optimistically, mints accounts at zero cost. On Direct plans that is a **funded** account, so the attacker is in the money with no evaluation to pass, and unlike a chargeback attack there is no cardholder left to complain, so the only possible detection is Merit's own books.
- Correct behavior: Three layers. Signature verification **throws** before the payload is parsed, with timestamp and nonce replay protection and the key in the platform vault on a 90 day rotation. `purchase.paid` requires a `purchases` row Merit itself created at checkout, matched on `(psp, psp_reference)`; a webhook citing an unknown reference is rejected and alarmed and may never create one. And a **daily reconciliation of accounts created against payments settled** at each provider, compared to the provider's own settlement report, with any discrepancy paging. That third layer is the money-in mirror of the platform balance reconciliation in M2 and exists for the same reason: a pipeline is only known to be honest when it is compared against an independent record.
- Golden scenario ref: GS-099.

## Entries from M04 (trader portal)

## EC-062: The payable amount changes between the dashboard render and the tap  (2026-08-13, module: M4 + M5, status: specced)
- Scenario: A trader opens the payout screen at 23:58 showing a maximum of 150,000c. The nightly batch closes a losing day at 00:05. The trader taps Request at 00:07. Naively the client sends 150,000c, the server clamps to 90,000c, and the trader receives an amount they never agreed to. Every component behaved correctly and the failure lives entirely in the seam.
- Correct behavior: The confirm step **re-fetches eligibility** and displays the amount that will actually be sent; when it has moved, the screen says so explicitly and requires a fresh confirmation. The request body carries the displayed amount rather than omitting it, so that the server-side clamp ([ADR-009](DECISIONS.md)) can only ever reduce the figure and the trader's screenshot and their payout can never disagree. A 422 is worded as "not yet, here is what is left", never as a denial, because the zero-denial policy is a copy obligation as well as a system one.
- Golden scenario ref: GS-101.

## EC-063: A share certificate the firm cannot verify  (2026-08-13, module: M4 + M11, status: specced)
- Scenario: Payout share cards are cheap virality and every competitor has them, so adversaries already know the format. A forged card claiming a Merit payout that never happened damages Merit in two directions: outward, when a scam signal service uses fake Merit proof, and inward, when a trader forges a card and the dispute becomes Merit's word against an image.
- Correct behavior: The image is a rendering and the **certificate is the signed row** (SD-M4-01). Every card carries a short code resolving to a public verification page that reports, from that row, exactly what Merit issued. Three rules make it defensible: the verification page is the authority and the image never is; an unknown code returns "no certificate with this code" rather than "this is fake", because the honest claim is the defensible one; and certificates are **revocable**, so a card on an account later closed for chargeback or enforcement says so instead of outliving the fact it proved. Claims are minimal by construction (plan, size, trading day, amount) with no identity and no cumulative totals.
- Golden scenario ref: GS-102.

## EC-064: The breach screen is the highest-yield dark-pattern surface in the product  (2026-08-13, module: M4, status: specced)
- Scenario: A trader has just lost an account, is emotional, and a reset purchase is one tap away. Countdown discounts, pre-checked upgrades, an obscured floor number, and "you were so close" framing all convert better here than anywhere else in the funnel. The revenue is immediate and measurable; the cost is invisible for months and then arrives as a review-page theme. The adversary in this entry is Merit's own future incentive under revenue pressure.
- Correct behavior: The breach screen shows the **arithmetic first**, rendered from the `breach.detected` payload: the floor, the day's low, the shortfall in cents, and which rule fired. The reset offer sits below that explanation, honestly priced, with no countdown, no pre-selection, and no comparative framing. The **ordering is the control**, so it is asserted by a layout test at every breakpoint rather than left to a review checklist that erodes.
- Golden scenario ref: GS-103.

## EC-065: An eligibility notification that was true yesterday and is not true today  (2026-08-13, module: M4 + M10 + M16, status: specced)
- Scenario: A "you are now eligible" notification is generated from a `day.closed` event. The trader reads it the following evening, after another day has closed, and the account is no longer eligible because a losing day moved the buffer or a new best day broke consistency (EC-036). The trader experiences a firm that invited them to request money and then refused. This is the highest-volume support wave available and it is entirely self-inflicted.
- Correct behavior: Three cheap rules. Every notification **carries the trading day it was true on** in the body, not in metadata, so the claim stays permanently true and is reconcilable by the reader. The eligibility notification links to the **eligibility screen, never to a request action**, because a notification that deep-links to a Request button is a notification promising an outcome. And no "you became ineligible" notification is sent, because that is technically transparent and practically cruel; the current state is always one tap away for anyone who wants it.
- Golden scenario ref: GS-105.

## Entries from M05 (payout system)

## EC-066: A settled payout that never reduces the platform balance  (2026-08-13, module: M5 + M2, status: specced)
- Scenario: Merit pays 150,000c through the settlement rail. The platform is supposed to reduce the simulated account's balance by the same amount, appearing as `adjustment_cents` on the next mark. If it does not, the account's balance still contains money already paid, the engine computes `withdrawable` from a figure that is too high, and the trader is legitimately eligible to withdraw the same cents again. Every rule passes, nothing is broken, and the ladder does not stop it because each payout is a separate correct ordinal. Reconciliation does not catch it either: our balance and the vendor's **agree**, since both believe the money is still there.
- Correct behavior: The reflection is a tracked fact, not an assumption. Every settled payout enters `balance_reflection_status = 'pending'` (SD-M5-04) and must be observed as an `adjustment_cents` matching amount and account within a window (proposed 3 trading days, OQ-M5-03). Past the window it emits `payout.balance_reflection_missing`, pages, and sets `recon_blocked`, removing the account from eligibility until a human resolves it. **The payout is never reversed.** The fix is a platform-side adjustment recorded as an admin action referencing the settlement, because reversing a settled payout to correct a firm-side error is the worst possible reason to break the never-claw-back promise.
- Golden scenario ref: GS-106.

## EC-067: The payout name match freezes real traders and catches no mules  (2026-08-13, module: M5 + M19, status: specced)
- Scenario: The settlement rail's payout name must match the verified identity, and a mismatch freezes and flags. Two problems. Mules pass it perfectly, because the mule **is** the verified person, so the check does not address the threat it is named for. And names are weak identifiers: transliteration, married and maiden names, hyphenation, middle-name ordering, and diacritics all produce mismatches on entirely legitimate traders, disproportionately those with non-Anglophone names. Under a zero-denial policy, freezing a real trader's payout on a string comparison is the most damaging false positive available.
- Correct behavior: Two separate answers, because they are two separate problems. For the check: a **score with a recorded method** rather than a boolean (SD-M5-02), a configured distance threshold, review inside the bounded freeze window, and a tracked false-positive rate so the threshold is tuned against recorded data rather than guessed before launch. For mules, which the name check does not address: biometric dedupe across all applicants (M19), the device and payment graph (M7), and the strongest signal of the three, **one settlement destination receiving payouts from several unrelated identities**, which is a query rather than an inference and therefore belongs in this module's data as a first-class flag input.
- Golden scenario ref: GS-107.

## EC-068: Instant approval commits the firm before the wallet can react  (2026-08-13, module: M5 + M6, status: specced)
- Scenario: Approval is instant and irrevocable. One identity holding ten copy-traded accounts crosses the win-day gate on the same day and produces up to 1,350,000c to the trader in individually correct, individually capped payouts. The payout wallet is funded weekly and manually ([ADR-011](DECISIONS.md)). The circuit breaker cannot help, because by design it pauses sales and never payouts, and that asymmetry is correct and must not be weakened. The commitment is made before anyone can react, and late settlement is the exact failure the constitution names as fatal.
- Correct behavior: A forecasting and liquidity problem, never a rule. The Eligible-Next-7-Days forecast is a **launch requirement** and aggregates at identity level as well as account level, since a correlated wave is invisible in an account-level sum until it lands. [ADR-011](DECISIONS.md)'s same-day top-up trigger fires on that forecast and emits `treasury.coverage_changed`, so it is an event rather than a dashboard someone remembers to open. The reserve coverage ratio is computed against a **live rail balance** (SD-M5-03), because a ratio derived from our own ledger is one that agrees with itself. And CVaR99 must model request timing as a strategy and correlated identity waves as a scenario, or the reserve is sized for a world where traders request at random. Residual, stated: with no identity ceiling (OQ-7) the one-day exposure is bounded only by cap times account maximum, and the whole mitigation is visibility plus liquidity.
- Golden scenario ref: GS-108, GS-062.

## EC-069: A freeze with no expiry is a denial nobody had to authorize  (2026-08-13, module: M5, status: specced)
- Scenario: A freeze requires a cited open flag, which is a real constraint. Nothing bounds its **duration**. A flag can sit in `investigating` indefinitely, and an indefinitely frozen payout has been denied without anyone typing the word. Every step is individually defensible, which is precisely the problem: the zero-denial policy is enforced against explicit denial and is silent about the implicit kind.
- Correct behavior: `freeze_expires_at` (SD-M5-01), where **expiry releases the payout** rather than extending the hold. `payout.freeze_expiring` fires two business days out so the decision is forced while there is still time to make it properly. Extension is a second, separately audited admin action requiring its own written reason, so an indefinite freeze remains possible but leaves a numbered trail of deliberate decisions rather than a silence. The trader sees the expiry date, because a review with no visible end is indistinguishable from a refusal to the person waiting.
- Golden scenario ref: GS-109.

## EC-070: The ledger zero-sum halt as a cheap denial-of-payouts trigger  (2026-08-13, module: M5, status: specced, founder ruling requested)
- Scenario: `ledger.invariant_violated` is the one event permitted to change system behavior automatically, and what it does is halt payouts. That is correct, because a ledger that does not sum to zero means we do not know what we owe. Viewed from outside it is also an outage switch with a very small activation energy: anyone who can cause a one cent imbalance anywhere halts every payout for every trader until a human intervenes. Candidate levers include a refund and chargeback race on one purchase, a partial refund with an odd amount interacting with a split, and an affiliate commission reversal timed against a statement boundary. The attack never has to move money; it only has to make the books disagree, and the safety control does the damage.
- Correct behavior: **Scope the halt.** A per-transaction imbalance halts payouts for the implicated identity and its accounts; only a **global** sum mismatch halts everything, because only a global mismatch means the aggregate is unknown. Make imbalance structurally hard: the per-transaction zero-sum check is a deferred constraint trigger at commit, so an unbalanced transaction cannot be written at all, which means a global mismatch implies corruption or a direct write and genuinely warrants a global halt. And make the global halt loud and short: page immediately, state the implicated transaction range, and open with the reconciliation query rather than a search for the cause. **This scoping amends the approved EVENTS wording and is OQ-M5-01, pending a founder ruling.**
- Golden scenario ref: GS-110.

## Entries from M06 (admin and ops console)

## EC-071: An evidence pack sent to a trader discloses the detection thresholds  (2026-08-13, module: M6 + M7, status: specced)
- Scenario: Evidence packs exist because adversaries contest enforcement publicly and the firm that cannot show its work loses the argument, so packs get sent to traders during disputes. A pack contains flags with their `evidence` JSON, and that JSON contains the numbers behind the accusation: the correlation coefficient that tripped the inverse-pair detector, the millisecond window that tripped fill clustering, the exact velocity threshold. A ring member who triggers a flag deliberately, contests it, and receives a pack has bought the detection parameters of the whole firm for the price of one burned evaluation, and these groups coordinate, so the disclosure does not stay with one person.
- Correct behavior: Audience is a **declared, audited property of the export** with a redaction profile that follows from it (SD-M6-04), not a judgment made under pressure mid-dispute. A `trader` pack carries every fill, mark, rule state, gate result, the plan version and its rule text, the computation trace, and the fact and ToS clause of any flag; it carries no detector parameter, no threshold, no population comparison, and no other identity. `internal`, `counsel`, and `regulator` profiles carry full detail. Every export records the profile used. The tension is real and the answer that holds up publicly is that the pack contains everything about the trader's account and every rule applied to it, which is the entire basis of the outcome, while a detector parameter is not a rule that was applied.
- Golden scenario ref: GS-112.

## EC-072: The circuit breaker fires on a sample of one and is never trusted again  (2026-08-13, module: M6, status: specced)
- Scenario: The breaker pauses a plan's new sales when its trailing 30 day loss ratio exceeds 6000bp. In a new plan's first weeks the denominator is tiny: one trader buys a $99 evaluation, passes, and extracts a 150,000c payout, giving a ratio of roughly 13,500bp and auto-pausing the firm's newest product during its launch week on a sample of one. The pause is recoverable in minutes. What is not recoverable is that the breaker was wrong on its first firing, was overridden, and is now a thing that gets overridden, including later when it is right.
- Correct behavior: Record the denominator and a `min_sample`, and make `insufficient_data` a first-class state that is neither armed nor paused (SD-M6-02). Below the minimum the breaker **states it has no opinion** rather than manufacturing one. Above it, the ratio appears next to its sample size everywhere it is shown, and `breaker.state_changed` carries the sample size into the alert itself, since an alert omitting it invites exactly the override that destroys the control. Proposed minimum: 20 purchases and 3 settled payouts in the window (OQ-M6-02); the specific number is a judgment, having one is not.
- Golden scenario ref: GS-113.

## EC-073: A muted alarm outlives the reason it was muted  (2026-08-13, module: M6, status: specced)
- Scenario: An alarm is noisy during an incident, so the person with the most context mutes it for a genuinely good reason. The reason expires long before the mute does. Nothing about the moment feels like a decision. This is the general form of the failure the constitution already names for the replay self-audit: it gets slow, someone disables it "temporarily", and the firm has a silent rules engine.
- Correct behavior: Suppression is a row with a **mandatory expiry**, an author, and a written reason (SD-M6-03), announced by `alarm.suppressed` on the feed, and it restores automatically when the clock runs out without anyone acting. A weekly digest lists every active suppression with its age, so a mute renewed three times is visibly a decision not to fix something rather than an accident. A small set is **unsuppressible**: ledger global imbalance, replay divergence, and payout balance-reflection missing. Each means Merit no longer knows something it must know before paying anyone, so they may be acknowledged and never silenced.
- Golden scenario ref: GS-114.

## EC-074: "Open liability" is wrong in both directions at once  (2026-08-13, module: M6 + M5, status: specced)
- Scenario: The obvious definition, the sum of withdrawable across funded accounts, feels right and is wrong twice. It **overstates** near-term cash need, because a trader with 500,000c withdrawable cannot extract it: the cap is 150,000c per request, one payout is in flight at a time, and the cadence gap enforces days between cycles. It **understates** total exposure, because withdrawable is today's snapshot while the real commitment is the remaining ladder, up to eight caps over an account's life regardless of what it is worth this morning. Funding the wallet against the overstatement starves operations; reasoning about total exposure from the same figure is blind to the ladder. Either way a number gets quoted in a decision it does not fit, which is what liability blindness looks like from the inside.
- Correct behavior: **Three named numbers, never one**, each printed with its own definition (SD-M6-01). Open liability, the sum of withdrawable, is the accounting claim. Bounded near-term liability, the sum of `min(withdrawable, cap_for_next_ordinal)` over accounts eligible now or inside 7 trading days, is the figure the payout wallet is funded against and the one [ADR-011](DECISIONS.md)'s trigger reads. Remaining ladder exposure, the sum of `(ladder - payouts_settled) * cap`, is the upper bound on lifetime commitment and is what INV-17 asserts. Showing all three is cheap; showing one and calling it "liability" is how the FTT quote happens.
- Golden scenario ref: GS-115.

## Entries from M07 (risk and abuse)

## EC-075: The flagship correlation detector does not defend the first extraction cycle  (2026-08-13, module: M7, status: specced)
- Scenario: The B4 ring rehearsal requires a six-account hedged syndicate to be flagged by day 3, and that number was never checked against how fast money can actually leave. The minimum-variance path to a first full-cap payout is 5 trading days, plus 2 to 3 business days of settlement, so the earliest cash leaves is roughly trading day 7 to 8. Detection at day 3 wins, but the margin is thinner than it appears: the inverse-P&L pair detector needs a 20 trading day rolling window, so on a 5 day account life it has almost no data. A ring that funds, extracts once, and abandons every account never generates enough history for the detector the constitution names as the answer to the number one industry threat.
- Correct behavior: Split the detector set by what it needs. Fill clustering and group exposure are **pattern** detectors that operate from day 1 on short windows, and fill clustering runs **on ingest** rather than only nightly, because same-second clustering is computable the moment fills land. The inverse-pair detector keeps its long window and is explicitly labelled a **second-cycle** detector that catches persistence rather than entry. The strongest early control is not a detector at all: it is biometric dedupe at funding, which fires before the first trade, plus the identity-level eligibility forecast, which makes a correlated cluster visible before it is eligible. Honest bound to carry: a single-cycle abandon-after-extraction ring on Direct plans is bounded by the cap and the buffer rather than by detection, and the counter is entry cost plus verification.
- Golden scenario ref: GS-118, GS-050.

## EC-076: Rotating a third leg defeats pairwise correlation entirely  (2026-08-13, module: M7, status: specced)
- Scenario: The hedged-pair detector looks for rolling correlation below -0.8 between two accounts, and that threshold is industry folklore, so assume rings know it. Three accounts rotating which two carry the hedge produce pairwise correlations around -0.5, comfortably inside the threshold, while the group remains flat. A -0.9 two-account signature becomes roughly -0.45 across three legs and -0.3 across four. Each extra leg costs one evaluation fee and defeats the pairwise detector completely.
- Correct behavior: Detect at **group** level. For a candidate group, compare the variance of the summed daily P&L against the sum of the members' variances: an independent group's summed variance sits near the sum of the parts, a hedged group's sits far below it, and that ratio is invariant to how the ring rotates its legs. Candidate groups come from identity-link clusters and from accounts sharing any signal, with a bounded search size. Group findings need their own home (SD-M7-05) because a schema built around pairwise edges cannot express them, and a finding that cannot be stored cannot be reviewed or replayed. Residual, stated: a ring with no shared signal at all produces no candidate group and is invisible, which is the same residual as cross-firm hedging and takes the same answer, bounded by caps and priced into the reserve.
- Golden scenario ref: GS-119.

## EC-077: Poisoning the flag queue with true positives about innocent people  (2026-08-13, module: M7 + M6, status: specced)
- Scenario: Detection's scarce resource is the operator's attention. An adversary who understands the detector set manufactures benign traffic that trips it on strangers: trading a popular public signal service from a widely used VPN exit clusters dozens of unrelated accounts, and a free-copy-signals offer in a Discord produces genuine same-second fills between people who have never met. Every flag is technically correct, the detector did its job, the operator learns that clustering means nothing, and the real ring runs underneath.
- Correct behavior: Three parts. **Per-detector precision** is computed from admin dispositions and a detector whose precision collapses is **auto-demoted to digest severity** as a data change through the detector registry, with no deploy and no human deciding to ignore it. **Severity is contextual rather than per-detector**: clustering across evaluations is low, the same pattern with a funded member eligible this week is top severity, and manufactured noise lands almost entirely in the low bands because an adversary cannot easily push strangers into funded eligibility. And **corroboration outranks any single detector**: the queue sorts by the number of independent detector families implicated on an identity, so poisoning one detector does not move anyone up the queue.
- Golden scenario ref: GS-120.

## EC-078: Entity resolution merges a family and punishes them for each other  (2026-08-13, module: M7, status: specced)
- Scenario: A father funds his son's evaluation with his card. A married couple share a laptop. Two students share a dorm IP and ASN. Each produces exactly the signals the adversary dossier lists for a fleet. An over-eager resolver merges them, aggregates their caps, and eventually enforces against all of them for one member's behavior. The cost falls on people who did nothing wrong, and unlike a ring, the wronged trader is sympathetic, articulate, and telling the truth, which is precisely the review-page content that kills firms.
- Correct behavior: **Two tiers.** Only a biometric dedupe hit or an explicit admin merge with evidence performs a hard merge that aggregates caps. Shared device, IP, ASN, and payment produce **soft links** that make the cluster visible and change nothing a trader may do. `confidence_bp` is never 10000 on an inferred edge, so the schema itself refuses to express certainty it does not have. A **dispute path** (SD-M7-04) lets a trader contest a link, renders the dispute on the graph, and puts it in front of the admin **before** they act rather than after. And enforcement is always per behavior and never per edge: an edge is a reason to look, never the evidence.
- Golden scenario ref: GS-121.

## EC-079: Commission is cash paid before the sale is final  (2026-08-13, module: M8 + M3, status: specced)
- Scenario: Commission becomes payable after the refund window, measured in days, while chargebacks arrive on the card networks clock, commonly up to 120 days. Merit pays real money on purchases that were never real, then pays chargeback fees on the same purchases, then absorbs a chargeback ratio spike that threatens the processor relationship. At a $99 evaluation and a 30 percent commission each fraudulent purchase yields about $30 of clean cash and costs Merit more than the purchase price. It is more attractive than plain card fraud because it converts a stolen card directly into cash with no trading at all.
- Correct behavior: The two clocks are separated (SD-M8-01), and the commercial choice to pay before the chargeback window closes is made explicitly rather than by omission, because waiting 120 days is not commercially available in this market. Three controls carry the accepted risk. A **carried negative balance** so a clawback always lands and nets against future commission. A **per-affiliate reserve holdback** for the first 90 days of a relationship, so new affiliates carry the risk they introduce (OQ-M8-01). And **chargeback rate as a payment gate**, holding the statement pending review rather than only appearing on a dashboard, which is what catches the attack in its first month rather than its fourth.

## EC-094: A pass rate is a choice of denominator, and every choice is defensible  (2026-08-14, module: M12, status: specced)

## EC-095: Publishing on-chain payout proof publishes the treasury  (2026-08-14, module: M12, status: specced)

## EC-096: An auto-review-request on payout settlement is review gating  (2026-08-14, module: M12, status: specced)

Suppression is for genuine conflict only (open dispute, open severity 4+ flag, opt-out, recent invitation), and **"the outcome was bad" is never a suppression reason**. Silently recomputing makes the published series editable, which destroys the evidentiary value of publishing it and is undetectable to anyone who did not save the old page. Never correcting leaves a known-wrong number. Correcting only when it helps is indefensible and is what everyone will assume happened unless the policy is fixed in advance. The version that will actually occur is subtler: most corrections are immaterial, and "sensible standard applied case by case, after seeing the delta" is exactly how a materiality policy becomes a selection mechanism, with the first hard case arriving under pressure.
- Correct behavior: Published values are **immutable**; a correction produces a new row with `restatement_of` set and the superseded value stays visible with a restatement note naming the cause. **Materiality is a published threshold per statistic, fixed in advance** (proposed 0.5 percentage points for rates, 1 percent of value for money figures), so restating is arithmetic rather than judgment; below the threshold the recomputation is still recorded in the method changelog, so nothing is invisible even when nothing is restated. Recomputation uses the **definition version in force when the original was published**, never the current one, or a restatement would silently mix a data correction with a methodology change. Every restatement alerts, because a rising restatement rate means the ingest pipeline has a problem the statistics surface noticed first.
- Golden scenario ref: GS-167.

## EC-099: The analytics page becomes a second implementation of a gate  (2026-08-14, module: M13, status: specced)
- Scenario: The adversary is a reasonable engineer with a deadline. The analytics surface needs "profit this consistency period"; `rule_states` has it, the join is awkward, and the fills are right there, so the page sums them. The result differs from the engine's by fee treatment, by a partial fill on a period boundary, or by a correction the mark absorbed and the raw fills did not. Nobody notices for months. Then a trader reads their consistency share as 29.4 percent on Merit's own page, requests a payout, and the engine computes 30.2 percent and fails the gate. TOP10_FIRMS records this class as Topstep's dominant complaint theme, "a rule-implementation gap between what traders expect and what the engine enforces", and the instructive part is that in that case the engine was right too.
- Correct behavior: Make the second computation impossible rather than merely incorrect, because a code review catches the obvious version and a unit test written by the same engineer tests the same misunderstanding. **The analytics service's database role cannot read `plan_versions` or `plan_version_sizes`**, so no gate can be evaluated here at all; this is the same shape as SECURITY C-26's write-grant absence and is chosen for the same reason, that a permission is a control and a guideline is not. Every engine value is read from `rule_states` and every money value from `daily_marks`, to the cent, with round trips presentational and labeled as such wherever they sit beside a money figure. A **nightly parity assertion** recomputes every rendered engine value from stored rows across every account and fails loudly, running alongside the replay self-audit that already exists. And every metric carries its definition including fee treatment, because the second most common version of this failure is the trader and the engine both being right about different questions.
- Golden scenario ref: GS-172.

## EC-100: A trader's own history changes overnight with no explanation  (2026-08-14, module: M13, status: specced)
- Scenario: A backdated fill correction (B4 #5) arrives for a day three weeks ago. The engine replays forward correctly and never claws back, but the trader's analytics now show a different win rate, largest loss, and equity curve than yesterday, with no event and no notice. The more insidious variant needs no data change at all: altering the round-trip grouping rule regroups the same fills into a different trade count and a different win rate. A trader who screenshotted their stats has, from their side, watched the firm edit their history, in a market whose dossier describes a community primed to believe exactly that, at a firm whose brand is that numbers do not move. It is guaranteed to happen, because corrections are a designed-for part of the pipeline rather than an exception.
- Correct behavior: Store an `inputs_digest` on every analytics snapshot, so a change to an already-computed day is detected without anybody checking. Emit `analytics.history_changed` and **notify the trader** with the cause (`correction` or `regrouping`) and the affected date range, because told first by Merit is a completely different experience from noticed later by them. Stamp `derivation_version` on every round-trip row and every API page, and when a grouping rule changes, announce it and apply it to everyone at once rather than silently to new data only, which would leave a discontinuity inside one account's own history. The definitions page carries version history in the same shape M12 uses, since the discipline that makes a public statistic defensible makes a private one defensible for the same reason.
- Golden scenario ref: GS-173.

## EC-101: The trading journal is a confession the firm holds  (2026-08-14, module: M13, status: specced)
- Scenario: A trader writes, privately, "hedged this one against my other account, worked out". Merit now holds a written admission of conduct the copy-trading clause makes a violation. The temptation escalates in three steps: let support see notes when investigating a ticket, include them in the internal evidence tier because they are highly probative, and finally run a keyword detector over them, which would be cheap, effective, and would find real rings.
- Correct behavior: Refuse all three, and the argument is practical before it is ethical. **A journal that can be used against its author is a journal nobody writes in honestly**, and the module's retention value comes entirely from candid writing. The enforcement value is illusory for the same reason: it would catch the careless and miss the organized rings who coordinate on Discord and read rulebooks forensically, which is the worst possible selectivity for an enforcement mechanism. The evidence is weak on its own terms, since a note saying "hedged" is ambiguous, unverified, and self-reported, while M7's detectors work on conduct and the batch 1 gate ruled the trader-facing pack shows conduct, rule text, and the trader's own trades, none of which a journal note is. And "Merit reads your journal" is a headline that costs more than any ring it could catch and is unanswerable once true. The control is an **absence**: no code path reads journal content except to show it to its author or export it to them, enforced by database grant and asserted by a negative test in the D5 family. Journal content enters an evidence pack only on the trader's own request or on lawful compulsion. The promise is **published on the journal surface itself**, because a privacy property nobody knows about buys none of the candour it was built to protect.
- Golden scenario ref: GS-174.

## EC-102: A metric that looks rigorous and is definitionally circular  (2026-08-14, module: M13, status: specced)
- Scenario: Every competitor ships R-multiples and PROP_TECH_LANDSCAPE records them as a standard portal feature. An R-multiple expresses a result in units of **intended risk**, which Merit does not know: it has fills, not stop orders, and even with order data a stop that was moved or never placed makes intent unknowable. The available shortcut defines R as the realized loss on losing trades, which makes every loss exactly -1R by construction and turns the metric into a restatement of the win/loss ratio wearing risk-management vocabulary. It is worse than useless because it looks rigorous, and a trader optimizing against a circular metric makes real decisions from false precision the firm supplied. The same trap sits behind Sharpe ratios on fewer than thirty observations, expectancy across mixed instruments without tick-value normalization, and profit factors over a handful of trades.
- Correct behavior: **A metric with no valid definition on the available data is absent and explained, never approximated.** The analytics response carries an `absent_metrics` list with a one-line reason each, so the absence is visibly a choice rather than an oversight. R-multiples ship only if intended risk is **captured as a trader-supplied journal field**, never inferred, which makes the metric meaningful and makes its dependence on the trader's own input obvious on the surface. Every ratio states its minimum sample and renders "not enough trades yet, n of m", borrowing M12's suppression discipline wholesale because the failure is identical at individual scale. Tick values come from `contract_specs` and never from a multiplier in analytics code (B4 #14).
- Golden scenario ref: GS-176.

## EC-103: The retention feature contends with the payout path for one database  (2026-08-14, module: M13, status: specced)
- Scenario: Analytics is by a wide margin the heaviest read workload in the estate: a funded trader with a year of history pulls tens of thousands of fills and the interesting queries aggregate across all of them. ADR-006 and ADR-007 deliberately put jobs, marks, fills, and the ledger in one Postgres instance so restore and backup are one procedure, which means an analytics query and a payout request contend for the same resources. The timing is the attack even with no attacker: traders open analytics after the session closes and around the daily reset, which is when the nightly batch runs and when M05 FM-M5-12's promo-day payout spike lands. The constitution's target is payout request p95 under 500ms, and the module most likely to break it is the one nobody classified as a money path. A trader with ten accounts refreshing during a wave is a denial of service with an innocent explanation, and a competitor who works this out has a very cheap way to make Merit's payouts slow on the day it hurts most.
- Correct behavior: **Precompute** the expensive shapes once per account per closed day in the nightly batch, so the common page load is a single-row read rather than an aggregation. Run analytics reads against the read replica or a role with hard connection and statement-timeout caps, so the worst case is slow analytics rather than slow payouts. Cursor paginate everywhere with a hard cap on the widest window a single request may ask for. And make it a **named gate**: load test analytics at realistic concurrency **while** the payout load test runs, asserting the payout p95 target still holds, because testing them separately proves nothing about the only interaction that matters.
- Golden scenario ref: GS-178.

## EC-104: Progressive cap release moves the lifetime bound for the cohort best able to reach it  (2026-08-14, module: M14, status: specced)
- **RULED 2026-08-14 ([ADR-025](DECISIONS.md#adr-025-progressive-cap-release-is-rejected-for-v1-and-replaced-with-cross-account-loyalty--2026-08-14-status-accepted)): the mechanic is REJECTED for v1, not deferred.** The correct behavior below is superseded by a prohibition rather than a process, and the scenario is retained because the arithmetic is what the rejection rests on. The replacement is **cross-account loyalty** ([EC-139](#ec-139-cross-account-loyalty-rewards-the-population-that-completes-ladders-reliably--2026-08-14-module-m14-status-specced)). **Every option, tabulated:** the market's own shape (release after ordinal 5) is **structurally impossible on a 5-rung ladder** because five payouts is the whole ladder; release at ordinal 5 costs **+20 percent** of the lifetime bound and delivers one raised payout at the very end of an account's life; release from ordinal 4 costs **+40 percent**. A shorter ladder did not make the mechanic safer. It made the cheap version impossible and left only the expensive ones. **INV-M14-11 now states the outcome directly**: no loyalty mechanic moves a per-account bound, asserted by GS-243 as an equality to the cent.
- Scenario: "After five payouts your cap goes up" sounds like pure goodwill and actually moves the lifetime bound INV-17 establishes, selectively, for accounts that have already demonstrated repeated extraction. At Core EOD 50K the ladder is **5 payouts** at a 150,000c cap ([ADR-024](DECISIONS.md)), so lifetime extraction is bounded at **750,000c gross and 675,000c to the trader**; doubling the cap at ordinal 5 gives four at 150,000c and one at 300,000c, a **20 percent increase**, and doubling from ordinal 4 gives a **40 percent increase**. **The market mechanic this models, "after five payouts your cap goes up", cannot be copied at all on a 5-rung ladder, because five payouts is the whole ladder**; re-keying it earlier is what makes it expensive. ADR-018's defense of Merit Rapid's headline rate names the 5-payout ladder as the second of three protections, and this mechanic attacks it directly. The cohort reaching ordinal 5 is also not a random sample of good traders: it disproportionately includes hedged pairs and rings for whom repeated extraction is the designed outcome, so a cap release pays the residual undetected fraction more.
- Correct behavior: The mechanic is genuinely good for genuine traders, so the answer is process rather than prohibition. It is **always a plan-version publish**, carrying ADR-010's dual control, the delay window, and the full publish diff including CV-10, CV-11, CV-17, and the INV-21 post-payout-versus-floor check. The proposal event carries `projected_lifetime_delta_cents` and the founder never sees the proposal without it, with the reserve model rerun at the new schedule before publish because a cap change is a CVaR99 input. It is **published in the plan's rules page from the beginning rather than granted per trader**, so a buyer sees the second step before purchase and no per-trader state exists. The ladder's length stays structural and does not move.
- Golden scenario ref: GS-179.

## EC-105: A streak reward pays for the behavior the cadence gap exists to slow  (2026-08-14, module: M14, status: specced)
- Scenario: A streak of consecutive payout cycles is the obvious loyalty metric, and earning one means extracting at the maximum rate the rules permit without interruption: 5 trading days on Core EOD, 3 on Merit Rapid under ADR-019. Rewarding it is Merit paying a bonus for maximum-rate extraction, which every liability control in the corpus is arranged to discourage. The adversarial half is worse: a hedged pair produces a perfect streak by construction, since one side wins every cycle mechanically. D-02 needs 20 trading days at the population threshold and the young-account fast path needs 5 at much tighter thresholds, so a streak reward pays out on a cadence the ring hits **before** the detector's window closes, making the program's most reliable earners the accounts not yet detected.
- Correct behavior: **Streaks are recognition, not economics.** A badge, a portal milestone, an M11 certificate; no credit, discount, cap change, or fee reduction. If an economic streak reward is ever wanted, its criteria must be uncorrelated with extraction rate: tenure, total trading days, or accounts held without breach, all of which reward durability, which is what loyalty is supposed to buy. Streak-holder cohorts are an M7 **input**, never a trust signal, because a perfect streak is genuinely more likely under a hedge than under skill. The live test is the payout-frequency distribution of streak holders against the population; a shift toward the ceiling means the mechanic is doing exactly this.
- Golden scenario ref: GS-180.

## EC-106: A free earned spin that resolves into a purchase is still a purchased loot box  (2026-08-14, module: M14, status: specced)
- Scenario: ADR-019a's two clauses can each be satisfied while their composition is violated. A trader earns a spin through activity, the spin is free, its odds are published, and it awards a **discount of randomized size on a reset they then buy**. Nothing was purchased randomly and the product is a paid random outcome, because the randomized result determines what the subsequent payment yields. The same composition appears as a "mystery bundle" of evaluation credits earned through a milestone and redeemed at a fixed price for unknown contents, and as a randomized promotional-credit grant spendable only on a purchase. A separate but related failure: promotional credit that becomes withdrawable converts a marketing instrument into cash, which is an unpriced and possibly regulated liability and hands an attacker a laundering path.
- Correct behavior: State the composition as a rule rather than relying on the two clauses: **a randomized outcome that determines what a subsequent purchase yields is a purchased loot box regardless of how the randomization was obtained.** A mechanic that needs this explained has already failed, which is ADR-019a's own test. v1 randomizes nothing at all and every benefit is deterministic against published criteria; this is a position rather than a limitation to work around. `promotional_credit` has **no path to `trader_wallet` and no path to a withdrawal**, asserted by a ledger test rather than inferred from the absence of a feature. Every discount is a stated amount on a stated product before payment.
- Golden scenario ref: GS-181.

## EC-107: The highest-scoring win-back target is the worst one to win back  (2026-08-14, module: M14, status: specced)
- Scenario: Any sensible win-back score ranks candidates by repurchase likelihood, and the trader most likely to buy another evaluation after a breach is the one who has already done so many times. The model therefore selects serial resetters, and retention becomes a system for finding people who repeatedly lose money on evaluations and encouraging them to continue, at a discount, when they are most susceptible. Three things make it worse than an ordinary marketing concern: it converges on dossier item 8's martingale eval brute-forcers, whose signature is exactly high reset velocity and whom D-05 and D-06 are already investigating, so the program subsidizes the population risk is examining; a discounted reset landing minutes after a breach is the mechanic behind the review themes TOP10_FIRMS catalogues, and the constitution's M4 tone directive forbids dark patterns in as many words; and it is bad economics, because a trader on their eighth reset is not becoming funded and a successful funded trader is worth more than the fee stream from one who never will.
- Correct behavior: **Invert the design rather than moderating it.** A reset-velocity ceiling **excludes** an identity from win-back and discount targeting rather than promoting it, which must be stated plainly because every off-the-shelf retention tool defaults to the opposite. Exclusions bind at computation and again at send, alongside open severity 4+ flags, active restrictions, and chargebacks in the window. Timing is deliberate, with M10's hold window applying so no offer arrives in the emotional minute after a loss. And the targeting principle is **published**: Merit does not send discount offers to traders who reset frequently, which is checkable by any heavy resetter who notices the silence and costs less revenue than it appears to.
- Golden scenario ref: GS-182.

## EC-108: A loyalty service is a config editor with less scrutiny  (2026-08-14, module: M14, status: specced)
- Scenario: The adversary is a reasonable feature request under time pressure. Progressive cap release needs the cap to differ for some accounts; the plan-version path carries dual control, a delay window, a publish diff, and a validation suite, while a loyalty override column on `accounts` takes an afternoon. Nobody intends to bypass ADR-010; they intend to ship a benefit. ADR-010 names cap, split, and gap precisely because they are the parameters through which economic sabotage is silent, and a per-account cap override is that surface with less scrutiny, reachable by a service whose job is to be generous. An attacker compromising the loyalty service would find a supported path to raise payout caps whose audit trail reads as a marketing action. Meanwhile the engine stays pure and the rules pages stay honest, so the account's **published rules and its actual cap differ**, which is constitution 0.5's marketing-versus-implementation gap arriving from the one direction nobody watches.
- Correct behavior: The loyalty service holds **no write grant** on `plan_versions`, `plan_version_sizes`, or `accounts.plan_version_id`, as a permission rather than a policy. **No per-account parameter override exists anywhere in the data model**, so adding one is a schema change that surfaces in a migration review; an account's parameters come from its pinned plan version and nowhere else, which is the property every replay, evidence pack, and rules page depends on. A cap release is a plan version, published, visible in the rules page from the start, applying by pinning rather than by grant. And a canary in CI attempts a cap write outside the publish path and asserts it fails on the grant, in the same family as SECURITY C-19's tripwires.
- Golden scenario ref: GS-184.

## EC-109: A loyalty streak broken by the exchange calendar  (2026-08-14, module: M14, status: specced)
- Scenario: A trader holds a 12 cycle streak. Thanksgiving brings a half day, a limit-locked session the following month leaves them unable to trade at all, and the streak window elapses. The streak breaks; the trader did nothing and could do nothing. B4 items 1 through 3 already require calendar handling to follow the exchange session rather than the wall clock, and the constitution's own answer to the halted-session question is that calendar trading days advance while win days do not, **published publicly**. A streak that ignores that contradicts a rule Merit has already published about a nearly identical situation, which reads less like an oversight and more like a mechanic designed to expire, in a market whose watchlist includes a firm destroyed by a retroactive rule change.
- Correct behavior: A streak **pauses rather than breaks** on any day the trader could not trade: halts, materially curtailed half days, holidays, and exchange closures, all read from the trading calendar as data rather than from a second calendar understanding built inside this module. `breaks_on` is enumerated in the published criteria so the question is answerable before the break rather than after, and `loyalty.streak_broken` names which enumerated cause applied, because "your streak ended" with no reason is the shape of a mechanic nobody trusts. Fixtures cover the DST transition, the half day, and the limit-locked session, reusing M01's existing calendar fixtures.
- Golden scenario ref: GS-185.

## EC-110: A Discord role broadcasts a trader's financial state  (2026-08-14, module: M15, status: specced)
- Scenario: A "Funded" role tells everyone in a public server which members hold live simulated capital; a "Recently Paid" role names who received money this week; tiered roles publish account size. The trader agreed to join a server, not to have their financial state broadcast in it, and in the usual implementation they were never asked. The dossier records that paid passing services and copy-ring rentals recruit on exactly these platforms, so a funded-role list is a **pre-qualified prospect list delivered by Merit and refreshed automatically**, and a payout-role list is better still because it identifies people with money moving right now, which is the population worth targeting for account takeover and social engineering. This is M11's leaderboard problem with two aggravating factors: automatic rather than opt in, and real time.
- Correct behavior: **Opt in per role**, with the role's exact meaning shown at the moment of choosing, because consent to be in a room is not consent to be labeled in it and a single global sync toggle hides the distinction that matters, which is that traders feel very differently about "Funded" and "Paid this week". **Coarse roles only**: no amount, size, count, rank, or tier, so a role says a trader reached a stage and nothing about how much. The payout-visible role is recommended not to exist at all (OQ-M15-02), since its only benefit is community texture a trader can produce themselves with an M11 certificate, consented per instance rather than standing. Opt-out is immediate and its role removal goes through the same batch window, so leaving is not itself an event.
- Golden scenario ref: GS-186.

## EC-111: A linked chat account becomes a trading credential  (2026-08-14, module: M15, status: specced)
- Scenario: Once a Discord identity maps to a Merit identity, the mapping starts looking like proof, in three small steps: a support agent accepts "I am @handle, the linked account" as verification; a recovery flow offers "confirm through Discord" as a convenience; and a bot command returns account state to whoever controls the Discord account. SECURITY C-01 makes Merit passwordless precisely so there is no credential to stuff, and D1 names trader sessions a crown jewel because takeover leads to payout redirection. Discord accounts are compromised constantly, are password protected by default, and sit outside Merit's control, so making one a factor imports the entire threat model Merit designed itself out of, through a community feature nobody classified as security relevant. Direction matters equally: if a Discord user can initiate the link, possession of a Discord account becomes evidence about a Merit account.
- Correct behavior: The link is **initiated from the authenticated portal only**, with a single-use nonce confirmed in Discord, so possession of the Discord account proves only that the holder of the Merit session also holds it. The link table is unreachable from the auth and support-verification services **by grant**, with a negative test in the D5 family. **No bot command returns account state** of any kind, and the bot's reply to such a request is a portal link; this costs a genuinely nice feature and removes an entire attack surface, which is the right trade because the feature is one click away somewhere actually authenticated. Support's verification runbook does not list Discord, and dossier item 9's prohibition on support-initiated identity changes applies unchanged.
- Golden scenario ref: GS-187.

## EC-112: A stolen bot token can announce a rule change in the firm's own voice  (2026-08-14, module: M15, status: specced)
- Scenario: A Discord bot token is a bearer credential living in a deploy environment, granting the ability to post as Merit in Merit's own community. An attacker holding it needs to touch no database: they post a **retroactive rule change**. TOP10_FIRMS carries FundingTicks as "the live case study in how one announcement destroys a brand" after exactly that, and Merit's whole market position is that rules never change retroactively and every parameter has a version history. A convincing fake, in the official channel from the official bot, is screenshotted within seconds and spreads faster than any correction, and the damage lands at the screenshot rather than at the correction. Adjacent versions: a fake payout suspension, a fake "verify your wallet here" link during a real incident, or a fake status update contradicting the status page.
- Correct behavior: Bound what a **valid** credential can say rather than relying on protecting it. **Template-only posting with no free-text send path**: every message resolves from an allowlisted `template_code` with values drawn from the triggering event, so a stolen token can replay a legitimate announcement and cannot compose a new claim. Assert the channel allowlist per post. Record every post in `discord_announcements` with its causing event, so a disputed announcement resolves against a table rather than a memory. Require every announcement to link to the authoritative surface, so a message with no corresponding rules-page version or status entry is self-evidently wrong to anyone who checks and the community can be told once that this is the rule. Rotate the token on the 90 day calendar, and pre-write the incident template for "our Discord bot posted something we did not author", because this is a communications incident before it is a technical one.
- Golden scenario ref: GS-188.

## EC-113: Hosting the community creates both a recruitment venue and a surveillance temptation  (2026-08-14, module: M15, status: specced)
- Scenario: The dossier is explicit that hedging syndicates, paid passing services, and copy-ring rentals coordinate on Discord and Telegram. Running an official Merit server makes Merit the host of a venue where its adversaries find each other, with the funded-role list as the recruiter's best targeting signal. The tempting response is to mine moderator-visible content for enforcement signals, which is cheap and would find real violations, since people do post "anyone want to run the other side". It creates four problems at once: it makes community content an evidence source, which is M13's journal failure with an audience; it catches the careless and misses the organized, who move to a private server the moment they suspect it; it makes the community a place members assume is surveilled, destroying the retention value the server exists for; and it imports soft, unverified, self-reported evidence into an enforcement process M07 deliberately built on conduct.
- Correct behavior: Separate two things that look alike. **Community content is never a detector, enforcement, or evidence input**: no storage, no ingestion, no grant. **Moderation is a different act with a different record**: soliciting a prohibited arrangement violates the server rules and is moderated as such, removed and banned from the server, which is a hosting decision made on hosting grounds and does not touch the trader's account, produce a flag, or enter an evidence pack. Publish the separation in the server rules, because the outcome that proves it real is a member banned from Discord who keeps their funded account. And narrow the recruitment surface at its source through the per-role consent and coarseness rules, which is the intervention that actually reduces harm: no funded-role list means no pre-qualified prospect list.
- Golden scenario ref: GS-189.

## EC-114: The freeze notice a trader is owed is also an investigation tip-off  (2026-08-14, module: M16, status: specced)
- Scenario: M05 requires a frozen payout to be visible to the trader with its reason class and expiry date, because a review the trader cannot see the end of is indistinguishable from a refusal. The unpriced cost is that the notice tells the subject of an active investigation that it exists, when it started, and roughly what class of conduct triggered it. For a coordinated ring, one member's freeze notice is an early warning for the whole group, who then stop, unwind, or accelerate extraction on the accounts not yet frozen before M07 has finished building the case.
- Correct behavior: The obvious mitigations are refused: delaying or vaguing the notice produces the "under review" pattern TOP10_FIRMS documents as the most damaging complaint theme at the largest firm in the market, and Merit cannot adopt the anti-pattern it defined itself against to make an investigation slightly easier. Resolve the tension by changing **what the notice contains** rather than whether it is sent. The notice goes promptly and always, carrying the ToS clause and the expiry date, and contains **no detector, threshold, other identity, or pattern description**, so it tells the trader everything they need and a ring almost nothing about how they were found. The real answer is upstream: M07's detection-time doctrine and M05's requirement of a cited open flag mean a freeze happens when a case already exists rather than while one is being built, and the scenario's damage comes from freezing early, which the architecture already discourages for independent reasons. Group-scoped timing is an M7 decision: when a clique is actioned the decisions are taken together and notices follow decisions, rather than being staggered to buy investigation time.
- Golden scenario ref: GS-192.

## EC-115: An attacker mutes the alarm before redirecting the money  (2026-08-14, module: M16, status: specced)
- Scenario: C-11 and Appendix D4 make a payout destination change trigger 48 hour cooling and re-verification, and the notice to the contact on file is what makes the trader aware in time. An attacker with a valid session reorders the steps: change the email or add a new primary, turn off notification preferences, and only then change the destination. Every notice about the last two steps arrives at an address the attacker controls, so the cooling window runs and protects nobody, because its whole function is to give the real owner time to notice. SECURITY §4.7 distinguishes contained internal wallet spend from external theft on the grounds that external theft "stays slow and detectable", and the unstated assumption in "detectable" is that a human is told.
- Correct behavior: Four parts, of which the third is the one usually missing. **Contact changes are a ceremony, not a settings edit**: the existing contact is notified immediately and unmutably, and the new contact must verify before becoming usable. **Preference changes are themselves security class** and confirm to the existing contact before taking effect, so step two raises the alarm it was meant to silence. **Prior contacts keep receiving security-class messages for a configured window after any change**, which is what defeats the reordering, since even a fully successful step one does not stop the destination notice reaching the real owner; this requires the previous contact to survive as a row rather than being overwritten, which is why `contact_channels` exists. And the sequence itself, contact change then preference change then destination change inside a short window, is a rare and specific pattern that belongs in M7's flags queue at high severity rather than only in an email.
- Golden scenario ref: GS-193.

## EC-116: A read receipt is not proof of notice  (2026-08-14, module: M16, status: specced)
- Scenario: A trader disputes that they were told a payout was frozen, that the ToS changed, or that a destination change was accepted. Merit checks `notifications` and finds `read_at` null, or set. Both answers are traps: a null `read_at` does not mean no notification, because an email can be delivered and read in a preview pane without generating any read event, and a set `read_at` does not prove a person read anything, because an image proxy, a security scanner, or a shared inbox can produce it. Building either inference into a support script, or worse into a ToS-acceptance argument, means asserting something the data does not support in the one context where being wrong is expensive.
- Correct behavior: Keep **three fields with three meanings**: `sent_at` is dispatch, `delivered_at` is the provider's confirmation, and `read_at` is a convenience for the in-app unread badge. **Proof of notice is dispatch plus delivery**, stated in those words in the support runbook and in any dispute template, with `read_at` explicitly excluded. Anything requiring genuine acknowledgement uses a positive act instead: ToS acceptance is a click recorded with version, IP, and timestamp per constitution section 6; a destination change requires verification; and a freeze notice is informational precisely because M05's bounded freeze expires regardless of whether anyone read it, which is why the bound is a better control than the notice. The admin query answers a dispute with "sent at T, delivered at T+2s", which is both honest and sufficient.
- Golden scenario ref: GS-196.

## EC-117: A rule change marketed as a promotion  (2026-08-14, module: M17, status: specced)
- Scenario: The adversary is a good marketing idea. Every lever that would actually move conversion is a rule rather than a price: a bigger payout cap this weekend, consistency waived for October signups, a shorter cadence gap for Black Friday buyers, a ninth rung on the ladder for the anniversary. Each is more compelling than any discount and each is trivially expressible as a config value. Three harms follow, and the third persists. It breaks the rules page, because M09 renders `copy_blocks` from the pinned plan version, so a promotionally-capped account either shows a rules page disagreeing with its engine behavior or forces a per-account override, which is M14's config-bypass failure from a second direction. It bypasses ADR-010, since cap, split, and gap are dual controlled precisely because they are the parameters through which economic sabotage is silent, and a campaign flag moving one substitutes a marketing approval for a second hardware key. And it makes every future rule negotiable: once a cap has been raised for a weekend it is a number Merit chose rather than computed, and every subsequent support conversation about a cap has a precedent in it.
- Correct behavior: The offers service holds **no write grant** on plan config, so the temptation cannot be acted on. The legitimate version of every one of those campaigns is a **plan version**: published through M3 with dual control, validated by the CV suite, visible on the rules page before purchase, and pinned to the accounts that bought it, which is the same mechanism M14 specifies for progressive cap release and is a better product honestly marketed. ## EC-118: A free trial deletes the identity signal it most needs  (2026-08-14, module: M17, status: specced)
- Scenario: Free-trial accounts are a recorded brochure input and an obvious funnel improvement, and they remove Merit's strongest identity signal exactly where it matters most. D-08 watches payment velocity and the dossier names the payment fingerprint as a primary entity-resolution input, with constitution B1 making the identity graph the system's spine. A free account has **no payment fingerprint at all**, so entity resolution on a trial cohort falls back to email normalization, device fingerprint, and IP or ASN, each cheap to defeat with disposable domains, browser profiles, and residential proxies. Dossier item 6 describes one operator running 20 to 30 accounts under different names to beat per-entity caps, and free trials drive the marginal cost of an additional identity to approximately zero, which is the one condition under which the account cap stops being a real constraint.

Trials are capped per identity and per resolved entity and count against `max_accounts_per_entity` rather than sitting outside it. ## EC-119: Stacked instruments sell a funded account for nothing  (2026-08-14, module: M17, status: specced)
- Scenario: B4 #11 pins the coupon race and says nothing about arithmetic once several instruments coexist, and by launch there are at least five: a campaign coupon, a contextual reset discount, promotional credit from a loyalty grant, an affiliate code, and a bundle price. `stackable=false` on coupons prevents two coupons combining and says nothing about a coupon plus credit plus a bundle. On **Direct**, which funds immediately with no evaluation, a 40 percent coupon over a bundle already 25 percent below list, plus enough promotional credit to cover the remainder, approaches a zero-price purchase that issues live simulated capital with real payout liability and effectively no fee behind it: at 25K Direct with a 75,000c cap and a 6 payout ladder that is up to 405,000c of trader-side lifetime exposure created by a transaction collecting almost nothing. Floor edits are **dual controlled** on the same footing as cap, split, and gap, since a control anybody can lower is not a control. `offer.floor_applied` alerts, because the floor firing means a live configuration would otherwise have sold below it, which is a bug to find rather than a clamp to be grateful for. ## EC-120: Promotional credit funded by a payment that came back  (2026-08-14, module: M17, status: specced)
- Scenario: A promotion grants $100 of promotional credit on a purchase. The trader spends it on a reset the following week. Three weeks later the original purchase is charged back, reversing through M3's LT-04 and closing the account per B4 #10. **The credit does not reverse**, because nothing linked it to the payment that funded it, and it was already consumed on a different product that was delivered. It is repeatable and cheap: buy with a stolen card, receive credit, spend it immediately on something else, let the chargeback land. Dossier item 7 names stolen-card evaluation purchases and the MID health damage they cause; this variant adds a second extraction on top, funded by Merit.
- Correct behavior: Record `funding_purchase_id` on every grant, so a credit knows what paid for it. A chargeback or refund **revokes the grant**, and revocation **may drive the promotional balance negative**, which blocks further credit spend and is honest about the position rather than an error state to swallow. The negative balance settles through the existing chargeback path, where the identity is already net negative and the ledger already shows the firm's loss honestly, so no new mechanism is introduced. **Credit granted against a purchase does not become spendable until that purchase's refund window closes**, which costs a little immediacy and removes the fast version of the attack entirely, reusing M3's existing window rather than inventing a second timer. And chargeback-in-window is already an exclusion for further offers.
- Golden scenario ref: GS-203.

## EC-122: The payout ladder is only a ladder while the trader is winning  (2026-08-14, module: M18, status: specced)

- Scenario: The constitution calls M18 "the marketing face of the payout cap", which honestly describes a slightly uncomfortable fact: the ladder bounds lifetime extraction (INV-17), and presenting it as a progression makes a limit feel like a goal. From where they sit the firm stopped paying an account that was working at the moment it worked best, and every previous instance of reliability now reads as setup. ADR-018 makes the ladder one of three named defenses of Merit Rapid's headline rate, and a defense the customer does not know about is one that feels like a trap when it fires.

Open another anytime."**, with the lifetime figure spelled out in money. The continuation clause is load bearing. **The tracker counts down rather than up**, because "2 remaining" and "3 of 5 taken" are the same fact and only one cannot be misread. Publish the lifetime number, **$6,750 on Core EOD at 50K and $4,500 on Merit Rapid** at the 9000bp split, which ADR-018 already uses internally as a defense and which publishing converts into a feature, since it is a large and honest number. And keep a public graduation page linked from every rules page so what happens at the end is readable before the beginning.

## EC-123: Completing the ladder is exactly what a successful undetected ring produces  (2026-08-14, module: M18, status: specced)
- Scenario: A graduation benefit rewards completing the ladder, and completing the ladder means eight successful payout cycles, which is precisely the bounded extraction a hedged pair or ring is engineered to achieve. M07's detectors are good and imperfect, so the population reaching the final ordinal is enriched for whatever they missed: a genuinely skilled trader and an undetected ring look identical in the tracker, because the ladder measures extraction rather than skill. The problem is the discontinuity. Everything else bounds the adversary smoothly, with caps bounding the payout and the ladder bounding the lifetime, and ADR-018 leans on that boundedness explicitly. A benefit adds a **step function at exactly the point the ladder was supposed to end**, so a ring's payoff for surviving detection jumps rather than stopping, and if the benefit is real capital the step is enormous and the adversary's optimal strategy becomes a plannable "survive eight cycles undetected".
- Correct behavior: Treat the graduating cohort as a **risk cohort reviewed before conferral**, which is affordable because the population is small by construction. The review touches the **benefit only, never the money**: the final payout and the terminal settlement proceed regardless on M05's zero-denial logic, and what can be held is a discretionary reward, whose hold inherits the bounded-freeze discipline of a cited flag, a stated reason class, and an expiry. Take the second look with more data, since a graduating account has a complete history of every fill, every mark, and eight settlements, over which D-02, D-03, and D-14 are far more powerful than over the five days D-13 has. And **keep the step small**: the strongest structural answer is that graduation confers recognition and continuation rather than a windfall, and a design with no step function needs no review at all.
- Golden scenario ref: GS-207.

## EC-124: A graduated account can still owe the trader money  (2026-08-14, module: M18, status: specced)
- Scenario: The ladder ends at the eighth payout, and withdrawable balance is not a function of ordinals: an account can hold buffer, retained profit above the buffer, and profit earned between the final request and its settlement. So an account can graduate while still holding money that is the trader's under every rule in the engine, and the mechanism that would pay it, a payout request, is exactly the mechanism that just ended. M05 INV-M5-01 says no code path denies an eligible request and the absence of a `denied` status is the control, so an account holding withdrawable balance that can no longer request produces the same outcome as a denial, by an accounting boundary rather than by a decision. The trader's complaint is unanswerable: the number is visible in their own dashboard and the button is gone.
- Correct behavior: A **terminal settlement is a required state**. On graduation, remaining withdrawable is paid to the wallet automatically as one final settlement, with no request and no gate, recorded by `graduation.terminal_settlement`. It **is not an ordinal** and does not extend the ladder, and it should carry a distinct word on the trader's timeline so nobody reads it as a ninth rung. It is capped by what the account actually holds rather than by the payout cap, because with no ordinal there is no cap-schedule entry to apply. The same close-out applies at every other terminal state, including an account closed by the trader or closed by Merit for a non-enforcement reason; **enforcement closure follows M07's process and is the one case where the balance question is decided by the enforcement**, a distinction named here so it is never quietly generalized.
- Golden scenario ref: GS-209.

## EC-125: KYC placement silently sets the size of the biometric dedupe corpus  (2026-08-14, module: M19, status: specced)
- Scenario: Constitution section 10 prices the placement tradeoff on cost and conversion: pre-eval costs roughly $1.50 to $2 on 100 percent of buyers and suppresses conversion on an impulse purchase, while pre-funded verifies about 15 percent for an 85 percent saving with friction landing on people already invested. That analysis omits a variable the same section gestures at without following through, when it says fleets are caught by biometric dedupe before liability exists. **Dedupe is a cross-applicant face match and its power is a function of corpus coverage, and under pre-funded 85 percent of buyers never enter the corpus.** An operator running dossier item 6's 20 to 30 accounts buys 30 evaluations, has 4 or 5 pass and get verified, and **25 faces are never seen**. They have bought reconnaissance: they learn which synthetic identities survive verification at a cost of four checks, and can iterate in batches reusing the winners. Pre-eval would have matched all 30 faces against each other on day one.

That claim is smaller than it appears, because the operator still gains tolerance intelligence and funded accounts caught only if dedupe fires across a small set, and the constitution is explicit that the business dies from liability rather than foregone fees. Launch `pre_funded` as directed and **extend the (g) telemetry to capture corpus coverage**: the share of purchasing identities ever verified, and dedupe matches per 1,000 verifications at that coverage. Recognize that under pre-funded **the device and payment graph carries the whole first line of defense** for 85 percent of buyers and resource it as a primary control rather than as corroboration for a face match that will never be taken. ## EC-126: The verification provider becomes a payout dependency  (2026-08-14, module: M19, status: specced)
- Scenario: M19 sits upstream of provisioning, funded trading, and the wallet's external withdrawal leg, so a provider outage has a blast radius that looks from outside exactly like the failure constitution 0 calls fatal. The dangerous part is not the outage but the naive gate: "verify KYC is current before paying" reads naturally as a provider call, and under a re-verification regime there is already a code path that talks to the provider on a sensitive action, so an outage would stop payouts for identities verified months ago. The second-order version is a multi-day outage under pre-funded leaving passers unable to be funded, which is a queue of people who did the hard part, and is the moment somebody suggests "let them trade and verify later".

Provisioning queues honestly with a visible state, a pre-written comms template naming the dependency, and a next-update time rather than a slipping ETA. **"Trade now, verify later" is refused in advance, in writing**, because it is exactly what an outage produces and it converts a bounded delay into an unverified funded account. ## EC-127: The geo-consistency triangle fires on cross-border lives  (2026-08-14, module: M19, status: specced)
- Scenario: Constitution (d) requires consistency checks across the IP, document, and payment country triangle, and a mismatch is a real signal: dossier item 6 names VPNs and synthetic identities and item 3 names login geography versus KYC mismatch as a paid-passing-service signal. It is also, far more often, the ordinary condition of legitimate customers: expatriates with a home-country passport and a local card, migrant workers, dual nationals, students abroad, anyone travelling, and anyone whose bank issues cards from another country. Under a zero-denial brand, refusing or freezing on a mismatch reproduces M05 AS-M5-02's name-matching failure **on the same population**, so the trader whose name transliterates inconsistently is disproportionately the same trader whose passport and card disagree, and Merit would have built two independent controls that fail on the same people twice.

Score it rather than treating it as boolean, since the pairs differ in weight: document-versus-payment is weaker than IP-versus-both, and a stable long-term IP country differing from the document is close to meaningless alone. Monitor disparate impact as a named metric: mismatch rate by document country, and downstream flag and enforcement rates for mismatched identities against everyone else, because a control nobody measures for skew will have it. Keep restricted-jurisdiction enforcement a **separate mechanism**, so a fraud heuristic never quietly becomes a jurisdiction policy. And the trader-facing consequence of a mismatch alone is **nothing**: no message, no extra step, with any eventual action coming from M7 on its own evidence.

## EC-128: A sanctions match is the one refusal Merit must be able to make  (2026-08-14, module: M19, status: specced)
- Scenario: Two failures point in opposite directions. Treating a confirmed sanctions match like any other gate collides with M05 INV-M5-01's no-denial-path architecture, and if that has not been settled in advance it gets resolved under pressure, probably by adding a general-purpose refusal capability, which is the thing the whole zero-denial architecture exists not to have. Treating a *possible* match as confirmed is the opposite error: name-and-DOB screening produces false positives at a rate that surprises people, especially on common and transliterated names, which is the same fairness axis as the geo triangle and M05's name matching for the third time, and auto-refusing a relationship to a legitimate person on a name collision is among the most damaging and least reversible errors available.
- Correct behavior: State the distinction as the deliverable. **A confirmed sanctions match is a legal prohibition on the relationship, not a denial of a request**: Merit is not judging their trading, Merit is prohibited from transacting, it is scoped to the relationship, it is the only exception in the corpus, and it is written down precisely so it is never cited as precedent for a general refusal power. Possible matches **never auto-refuse**; they enter a review queue with `match_strength` recorded and a disposition recorded either way with a reviewer and reason. **Confirmation is dual controlled**, on the same footing as ADR-010's set, because it is the single irreversible refusal in the system. Confirmation triggers a **legal runbook rather than an automated action**, since freezing funds, reporting obligations, and what a trader may be told are jurisdiction-specific legal questions and confirmed matches are rare enough that a human process is affordable. And the screening event payload **carries no name**, because an alert channel carrying names is a PII channel with a wide audience.
- Golden scenario ref: GS-215.

## EC-129: The fleet-killer is also a false-accusation engine  (2026-08-14, module: M19, status: specced)
- Scenario: Biometric dedupe is the constitution's named counter to one-face-many-names fleets and is genuinely the strongest available. Face matching also produces false matches on siblings, identical twins, poor captures, and at rates that vary by demographic group in documented and asymmetric ways, so Merit will at some volume be told two unrelated legitimate traders are the same person. The corpus has a clear posture for detection generally, with flags queued, humans deciding, and evidence packs, and no guidance for this specific case: the evidence is a **biometric assertion Merit cannot inspect**, about **two people who may be strangers**, where confirming means telling somebody they are running a fleet and denying means overriding the firm's strongest control on the say-so of the accused. Inside it sits a disclosure trap: telling trader A their face matched trader B discloses B's existence and participation, and telling A nothing produces the unexplained restriction that is the documented anti-pattern.
- Correct behavior: **A hit changes no state** and both identities remain fully operational while it is open. Model a match as a **relationship with a disposition**: open, confirmed same person, distinct persons, or inconclusive, each recorded with a reason, and **`inconclusive` is a permitted and expected outcome** so a reviewer is never forced to choose between two wrong answers. **A dedupe hit alone never enforces**: it is a strong prior requiring corroboration by conduct, whether shared devices, shared payment fingerprints, correlated trading, or the day-0 graph priors, which is the same standard the batch 1 gate applied to copy trading. **Neither trader is told about the other, ever**, and if enforcement follows, its stated grounds are the corroborating conduct and the ToS clause, both concerning the trader's own account, because a control that cannot be explained without disclosing a third party must rest on something else. And the false-match rate is tracked and broken down enough to notice demographic skew.
- Golden scenario ref: GS-216.

## EC-130: A re-verification that reads a cached status verifies nothing  (2026-08-14, module: M19, status: specced)
- Scenario: Appendix D4 pairs 48 hour destination cooling with re-verification, and that pairing is the primary control against the account-takeover cash-out. The failing implementation is easy and looks correct: on a destination change, call the provider with the stored applicant id, receive "this applicant is verified", proceed. Nothing has been verified, because the stored status was true yesterday and says nothing about who holds the session today, which is the only question. The genuinely hard version is that even a real re-check, if document-only, proves possession of a document image a compromised account may well contain, so the control must be a **liveness** check tied to the moment, and liveness is a moving target with injection attacks against camera streams and synthetic face generation both live threat classes. SECURITY_LANDSCAPE's finding that credential stuffing against trader dashboards is the sector's most documented attack is why the chain matters: the session is the cheap part.
- Correct behavior: **Re-verification is a new row with its own liveness result**, linked by `supersedes` and carrying a `verification_purpose`, so reading a cached status cannot satisfy the trigger because the trigger requires a row that does not yet exist. Record `liveness_method` on every verification, so an enforcement or dispute decided years later knows which technique produced the evidence and can re-evaluate it rather than excavate it. **Block the gated action rather than the identity**, so a pending re-check stops the destination change while ordinary payouts to the existing destination continue. Run the **48 hour cooling regardless of the re-verification result**, so neither control can short-circuit the other. And notify **both the old and the new contact**, which is the control that survives even if liveness is defeated, on the explicit assumption that it eventually will be.
- Golden scenario ref: GS-217.

## EC-131: Data minimization creates an evidence dependency on the provider  (2026-08-14, module: M19, status: specced)
- Scenario: Appendix D2 and VG-10 are emphatic and correct that documents and biometrics never touch Merit's storage. The untraced consequence is that **the evidence for Merit's strongest fraud finding lives entirely at the provider**. Three ways that hurts, none requiring bad behavior: the provider's retention expires the applicant record while Merit's `kyc_verifications` retention is forever for AML reasons, so Merit holds a conclusion whose basis is deleted; Merit changes providers and every historical dedupe match becomes an assertion referencing an applicant id at a company Merit no longer contracts with; or a trader disputes an enforcement two years later in a forum with discovery and Merit's evidence pack contains a boolean. The batch 1 gate made evidence packs two tier with detector detail in the internal tier, and M07's posture rests on court-grade packs, so an enforcement grounded in a dedupe hit with no retrievable basis is the weakest link under the strongest-sounding claim.
- Correct behavior: Thread the minimization requirement rather than weakening it. Store an **`evidence_snapshot` of decision metadata at the time**: match score, method identifier, model or technique version, provider decision id, and timestamps, with **no images, no templates, no document data**, which is fully compatible with D2 because a score and a method are not biometric data. Rest enforcement on **corroborating conduct**, so the pack's spine is fills, marks, devices, and payments that Merit holds forever, with the dedupe hit supporting rather than load bearing. Put **retention and export commitments in the provider contract** aligned with Merit's AML retention, including export of decision metadata for historical matches on a provider change, as a procurement requirement settled before the first verification rather than after the first dispute. And run a payload scanner plus canary in CI, because the counter to this scenario adds a field and the risk of a field is that it grows.
- Golden scenario ref: GS-218.

## EC-132: Bonus-credit farming converts promotional credit to cash through a funded account  (2026-08-14, module: M20, status: specced)
- Scenario: ADR-019, M14, and M17 all separate `promotional_credit` from `trader_wallet` with no path between them, which closes the direct route and leaves the product open as an indirect one. Accumulate credit; spend it on an evaluation, which is what credit is for; pass, or buy Direct which funds immediately; take a payout, which credits the **wallet**, which is real money; withdraw. Promotional credit has become cash through five legitimate steps with every ledger entry correct. The separation of ledger classes was necessary and is not sufficient, because the product is the converter. The economics decide the severity: at a 15 percent pass rate the conversion is poor for a lone trader and **excellent for a hedged pair**, since a hedge turns a probabilistic pass into a near-certain one, so a ring that can reliably pass evaluations holds a machine that turns promotional budget into withdrawable cash. M14 AS-M14-02 compounds it, because a hedged pair earns loyalty streaks by construction, partly automating the credit supply.
- Correct behavior: A hold rather than a block, because most of this population is honest. Record `provenance` on every wallet entry and record the funding method of every account from `offer.redeemed`. **P-1**: a withdrawal composed FIFO whose contents include payout credits from accounts purchased with promotional credit is **held for review on first occurrence**, not confiscated, so a genuine winner is paid after a look and a farm is visible before cash leaves. **Spending that value inside Merit is unaffected**, keeping the honest case frictionless where traders actually feel it. Watch the pattern rather than the instance, since many credit-funded accounts under linked identities converting far above the population rate is an M7 input composing with D-02 and D-03. Cap the promotional budget per identity and per resolved entity upstream, which bounds this regardless of conversion rate. Residual stated: a skilled trader who wins on a promotional evaluation converts credit to cash legitimately and should, and preventing that would mean promotions nobody can win with.
- Golden scenario ref: GS-222.

## EC-133: A freeze that covers the cash door and not the product door is not a freeze  (2026-08-14, module: M20, status: specced)
- Scenario: M05's freeze path and Appendix D4's destination controls all guard the external leg, and the wallet has a second exit none of them touch. An identity whose withdrawals are frozen, whose destination is inside its 48 hour cooling window, or whose KYC has expired simply **spends** the balance at checkout. The value does not sit still: spending converts a frozen balance into accounts, accounts produce payouts, and those payouts credit the wallet again in a position that may by then be unfrozen, on an account carrying no freeze of its own. SECURITY §4.7 reasons that internal spend is contained because it never leaves Merit's books and is reversible by ledger entry, which is true of the spend and **not true of what the spend buys**: a frozen $5,000 becomes five evaluations, then funded accounts, then fresh unfrozen credits. The freeze bought a delay and a change of clothes.
- Correct behavior: **A payouts-frozen identity cannot spend either.** The freeze covers both exits, because a freeze that covers one is not a freeze, and this is the module's most important single line. The same applies to every context gate blocking the external leg: expired KYC, `recon_blocked`, and an active restriction all block spend as well as withdrawal, so the wallet's two doors share their context gates even though their mechanical gates differ. The velocity limit is a rate control and **not a freeze substitute**, since conflating them leaves a frozen identity draining slowly, which is the same attack with patience. And accounts purchased while an identity was under any hold are marked, so their eventual payouts carry that provenance into the review path and the chain does not launder the provenance along with the value.
- Golden scenario ref: GS-223.

## EC-134: Refunding a card purchase to the wallet is a rail crossing  (2026-08-14, module: M20, status: specced)
- Scenario: Refunding to the wallet is instant, avoids card-network delay, and traders like it, and it builds a rail crossing that is the attack. Buy an evaluation with a card, request a refund inside the pre-first-trade window, receive it as **wallet balance**, withdraw to a bank. Card money has become bank money through Merit with none of the card network's protections and none of the checks a processor applies to a cash-out. For a stolen card this is a clean extraction that leaves Merit holding the chargeback, and it is materially more attractive than dossier item 7's existing pattern because it does not require passing an evaluation first; in substance it is also unlicensed money movement. The non-fraud version is bad too: a legitimate refund-and-withdraw means a card payment and a bank payout with no product delivered, which is exactly the pattern a processor's risk team looks for, against M3's 0.65 percent MID health threshold.
- Correct behavior: **A refund returns to the payment method that funded the purchase, always.** A card purchase refunds to the card; a wallet-funded purchase refunds to the wallet; the rails never cross in either direction. Assert this by test on **every** refund path including partial refunds, chargeback reversals, and admin-initiated corrections, because the exception will be requested for a sympathetic support case and the answer must already exist. Answer the convenience argument honestly: refunds are rare because the window is pre-first-trade only, the delay belongs to the card network, and trading a rare inconvenience for a laundering path is not a close call. Cover the residual by flagging identities whose purchase-and-refund rate is far above the population, regardless of where the refund went.
- Golden scenario ref: GS-224.

## EC-135: The wallet becomes a deposit account by accretion  (2026-08-14, module: M20, status: specced)
- Scenario: Nobody proposes operating a payment institution. What gets proposed, each reasonably, is: let traders top up so they can buy faster; let a backer fund a trader's wallet; let a balance be sent to another trader as a gift or a split; pay a small return on idle balances. ADR-019 already rejected interest and peer-to-peer transfer outright and did not reject top-ups, because nobody had proposed them yet. The line matters enormously: a balance that only receives money the customer already earned and only pays it back or spends it on the issuer's own products is a **payable**, while a balance accepting inbound funds from the customer or a third party, holding them, and paying them out is **stored value**, which depending on jurisdiction is money transmission or e-money with licensing, safeguarding, and reporting obligations no corpus document contemplates. Merit's whole compliance posture assumes the first, and a top-up would arrive as a checkout convenience with an engineering ticket rather than as a regulatory decision, which is exactly how firms end up operating unlicensed.
- Correct behavior: **No deposit, no top-up, no third-party funding, ever**, enforced by the absence of an endpoint, a payment method, and an admin path. The only credits are payouts, refunds of wallet-funded purchases, and corrections; that list is **closed**, asserted by the `provenance` check constraint, and adding a value to it is a schema change surfacing in a money-path migration review. No interest and no peer-to-peer, per ADR-019, with the reason now recorded alongside the rest of the boundary. And file a counsel item confirming, **before launch**, that a payable of this shape avoids regulated stored-value characterization in Merit's operating jurisdictions, since the answer may add a condition rather than a prohibition and conditions are cheap in advance.
- Golden scenario ref: GS-225.

## EC-136: The wallet compresses the attacker's cycle as much as the trader's  (2026-08-14, module: M20, status: specced)
- Scenario: B4 #10 pins the chargeback landing after a settled payout, with the identity netting negative and the ledger showing the loss honestly. The wallet adds a timing dimension that pin does not cover: buy with a stolen card, pass quickly, take a payout to the wallet, withdraw to a bank, and weeks later the chargeback lands, so Merit has already sent real cash out on an account funded by a reversed payment and B4 #10's honest accounting records a loss rather than preventing one. The wallet makes this sharper rather than softer, because ADR-019 deliberately compressed the cycle to 3 trading days on Merit Rapid with instant wallet credit, and that compression applies equally to the attacker, whose cycle is the one racing the chargeback window. On Direct no evaluation is needed at all, so a $99 stolen-card purchase against a dispute window measured in weeks is a favorable trade, and at volume it is also a MID health event against M3's 0.65 percent threshold.
- Correct behavior: **P-3**: payout credits from an account whose funding purchase is still inside the chargeback window are **spendable inside Merit but not withdrawable** until that window closes, computed from the credit's age and the funding purchase's status. State the cost honestly, since this delays cash for legitimate fast winners on newly purchased accounts, landing hardest on the plan whose selling point is speed; it is bounded, disclosed at purchase, and the trader can still spend immediately, so the promise that they were paid stays true and only the bank leg waits. The window is the card network's rather than one Merit invents, and a purchase whose payment has aged past the practical dispute rate for its method releases early. M19's `direct_purchase` placement, already mandatory for Direct, is the strongest single mitigation and is required for independent reasons. AVS and CVV strictness, per-BIN velocity, and D-08 remain the upstream controls; P-3 is the last line rather than the first.
- Golden scenario ref: GS-226.

## EC-137: Checkout is a transfer endpoint nobody labelled as one  (2026-08-14, module: M20, status: specced)
- Scenario: M05 INV-M5-14 forbids transferring a wallet balance to another identity, enforced by there being no transfer endpoint. Checkout is one. If wallet value can pay for a purchase whose resulting account belongs to a different identity, A can fund B and the wallet is transferable through the product. Three uses follow, and the third makes it urgent: a ring pools value into a designated operator's accounts, solving dossier item 6's fleet funding problem; a paid-passing service is paid in wallet value, untraceable through card rails and invisible to M8's attribution; and **an account takeover becomes profitable without ever touching the external leg**, because SECURITY §4.7's containment argument rests on internal spend staying inside Merit's books and being reversible, and if the attacker spends the victim's balance on **their own** accounts the value has moved to an identity Merit does not control, where reversing a ledger entry does not bring it back once those accounts have traded.
- Correct behavior: **Wallet value may only buy products for the spending identity's own accounts**, with the target account's ownership resolved server side and compared to the paying identity inside the same transaction as the debit. A cross-identity spend attempt is a **high-severity flag rather than a validation error**, because there is no legitimate reason to make one and a trader cannot construct the request accidentally through the UI, so an attempt is evidence. Gifting is not a feature and will be requested; the answer is recorded in advance, that a gift is a transfer, transfers are prohibited by INV-M5-14, and the reason is legal as well as anti-abuse. This is also what tightens SECURITY §4.7's containment claim into something true: internal spend is contained **because** it can only buy the victim's own products, which are recoverable by ledger entry and by closing the accounts.
- Golden scenario ref: GS-227.

## EC-138: A dormant wallet balance may be neither kept nor held forever  (2026-08-14, module: M20, status: specced)
- Scenario: A trader breaches, gets discouraged, and stops logging in with $420 in their wallet; multiply by an attrition rate over years. Merit holds money it owes to people who have stopped asking. Expiring it is the worst option available to this firm specifically: a forfeiture clause on money already earned, already through every gate, which Merit's own product describes as already theirs, would be the most brand-destroying term Merit could write, would appear in every review next to the transparency page, and would be indistinguishable from the payout-denial behavior the firm defines itself against. Holding it forever is also wrong, and this is the half that gets missed: unclaimed-property law in most US states and its equivalents elsewhere requires holders of abandoned property to attempt contact and then **remit to the state** after a dormancy period, as a real, audited, penalty-bearing obligation that applies to exactly this kind of payable and varies by the trader's jurisdiction.
- Correct behavior: **Never forfeited to Merit**; the balance is payable on demand forever and no expiry mechanism exists to misuse. Run a dormancy state machine with escalating contact starting well before any jurisdictional deadline, through M16's security-class channels **including prior contacts**, because a dormant trader is by definition one whose current contact may be stale. Track escheatment as a legal calendar item with a jurisdiction hint recorded per trader rather than discovered in an audit, with a counsel item filed. **Publish the policy** in plain words: Merit never takes a wallet balance, contacts the trader repeatedly, and where the law requires it remits to the state where the trader can still claim it, which is a good story that costs nothing to tell. And report dormant balances separately within the float, because they are its most stable part and therefore the most tempting to treat as capital.
- Golden scenario ref: GS-228.

## EC-139: Cross-account loyalty rewards the population that completes ladders reliably  (2026-08-14, module: M14, status: specced)
- Scenario: [ADR-025](DECISIONS.md#adr-025-progressive-cap-release-is-rejected-for-v1-and-replaced-with-cross-account-loyalty--2026-08-14-status-accepted) replaces progressive cap release with perks earned by completing the **Nth ladder** across an identity's accounts. A completed ladder is five settled payouts on one account, which is a bounded, gated, detected achievement and therefore a defensible thing to reward. It is also exactly what a hedged pair or a small ring is engineered to produce. [EC-105](#ec-105-a-streak-reward-pays-for-the-behavior-the-cadence-gap-exists-to-slow--2026-08-14-module-m14-status-specced) establishes that a hedge earns streaks mechanically and [EC-123](#ec-123-completing-the-ladder-is-exactly-what-a-successful-undetected-ring-produces--2026-08-14-module-m18-status-specced) establishes that the graduating population is enriched for whatever M07 missed, so the identity reaching a third or fourth completed ladder fastest is not reliably the durable retail trader the program exists to keep. Three harms, ascending: a discount spent on somebody who was buying anyway, which is a bounded marketing loss; **bonus credit funding the next evaluation in the rotation**, which is [EC-132](#ec-132-bonus-credit-farming-converts-promotional-credit-to-cash-through-a-funded-account--2026-08-14-module-m20-status-specced)'s conversion machine fed by a rule a ring can satisfy on purpose rather than by a campaign somebody targeted; and **review-pool priority ordering M18's discretionary queue by the metric a ring optimizes**, which would hand the adversary the one thing [ADR-024](DECISIONS.md)'s discretion exists to withhold. What this is emphatically **not** is a liability finding: INV-M14-11 holds, INV-17's bound is identical for every identity at every tier, and the worst case is a bounded marketing loss plus a mis-ordered queue rather than a 40 percent increase in what an undetected ring may extract. Recording that comparison is half the point of the entry, because at review "rings can farm this too" reads like the same finding as [EC-104](#ec-104-progressive-cap-release-moves-the-lifetime-bound-for-the-cohort-best-able-to-reach-it--2026-08-14-module-m14-status-specced) and is a different order of magnitude.
- Correct behavior: Perk issuance inherits **every exclusion win-backs already carry** (INV-M14-08), evaluated at computation **and again at issuance**: open severity 4+ flag, active restriction, chargeback in the window, reset-velocity ceiling. An identity under review **earns the milestone and receives nothing** until the review closes, and the milestone is **not revoked** when it closes, because the fact is true (INV-M14-09). Completed-ladder cohorts are an M07 input and never a trust signal (INV-M14-05, INV-M14-12). Bonus credit is **`promotional_credit`, never `trader_wallet`** (INV-M14-10), so value derived from it meets M20's P-1 hold on first withdrawal exactly as [EC-132](#ec-132-bonus-credit-farming-converts-promotional-credit-to-cash-through-a-funded-account--2026-08-14-module-m20-status-specced) already requires: loyalty is a new **source** of promotional credit and deliberately not a new **class** of it, so it inherits an existing control rather than needing one. Review-pool priority is an **ordering key with no trader-facing rendering** in v1; it never gates entry to the pool and it never implies an invitation. And the **perk budget is a configured ceiling** reported per cohort, so the failure mode is a budget alarm rather than a liability discovery.
- Golden scenario ref: GS-244, GS-245, and GS-243 for the bound invariance.

## EC-140: A rejected mechanic returns as a roadmap item nobody re-prices  (2026-08-14, module: M14, status: specced)
- Scenario: [ADR-025](DECISIONS.md#adr-025-progressive-cap-release-is-rejected-for-v1-and-replaced-with-cross-account-loyalty--2026-08-14-status-accepted) rejects progressive cap release, and the `payout_cap_schedule` array survives it because the shape costs nothing and the publish-time validations should stay exercised. That combination is a trap with a long fuse. Some months from now a competitor ships a cap-release program, somebody looks at the schema, finds an array that already supports multiple steps and a publish path that already validates them, and concludes the feature is a config change that was simply never turned on. The arithmetic that made it a bad trade lives in an ADR nobody in that conversation is reading, the cohort argument lives in an adversarial scenario in a module plan, and the decision gets reversed by an afternoon rather than by an argument. The same shape applies to the retired `loyalty.cap_release_proposed` event and the retired `M14-P-nn` suite: a name that once existed in a design document is a name somebody re-implements from an old branch. **The general failure is that a rejection is invisible in the artifact while a deferral is visible in the backlog, so rejections decay faster than deferrals do.**
- Correct behavior: Three defenses, and they are cheap because they are all documentation with a test attached. **A publish-validation alarm**: a `payout_cap_schedule` with more than one step reaching publish validation **pages**, not because it is an error but because it is a decision that must not happen by accident, and the alarm text names ADR-025. **The rejected path stays documented as a negative flow** ([M14](plans/M14-loyalty-retention.md) section 3.5) rather than being deleted, so the route a reversal would have to take is written down and the negative tests can assert against it by name. And **the golden file keeps the price**: GS-179 is rewritten to pin that no v1 plan version carries a second step, and it carries the full option arithmetic as a superseded counterfactual, which is the same discipline [GS-055](testing/GOLDEN_SCENARIOS.md) uses for the cadence anchor. A reversal then costs an ADR arguing against a number that is sitting in the test suite, which is the correct price.
- Golden scenario ref: GS-179.
