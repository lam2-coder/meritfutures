**Objective.** Rule where an identity comes into existence, and land `ADR-196` at `status: proposed` with an UNSIGNED approval line.

### Done

**[ADR-196](../decisions/ADR-196.md) landed**, `status: proposed`, approval line UNSIGNED, with a `What a founder read adds` block. It rules three things and refuses a fourth.

1. **The moment.** An identity comes into existence at `POST /auth/verify`, on a code that verifies, when the address resolves to no existing `users` row.
2. **The unit of work.** The identity and its first `users` row are written together. A committed `identities` row with no login is not a state this system creates.
3. **The contents.** The row is written with defaults only, and the emptiness is a control rather than an accident.
4. **Refused:** creation at OTP request, at first purchase, or by an explicit registration route, each on its own cost rather than on preference.

**`0060` returned to the pool unspent**, and the allocation row records the A/B that decided it rather than the argument that would have.

**The absence was re-derived before it was ruled on**, per the dispatch's instruction, and it holds.

### The finding that made this entry smaller than its dispatch expected

**The timing was already ruled, in a document that has been frozen since 2026-08-14.**

[`API_CONTRACT:117-121`](../architecture/API_CONTRACT.md)'s `VerifyResponse` carries `is_new: boolean` beside `identity_id` and `user_id`. **A boolean saying "this call created the row" is meaningless at an endpoint that does not create the row.** Its only other occurrence in this workspace is `is_new: false` in the auth suite's fixture, so the field has been in the contract since FREEZE and nothing has ever been able to answer it `true`.

Three more sentences agree with it and none of them is in the dispatch:

- [`API_CONTRACT:104`](../architecture/API_CONTRACT.md)'s `OtpResponse` carries no identity at all, and [`:91`](../architecture/API_CONTRACT.md) says the endpoint deliberately does not reveal whether the destination exists. **A creation there would be a row the caller is never told about, for an address nobody has proven they hold.**
- [`SECURITY:297`](../architecture/SECURITY.md) prices the tripped cost breaker and names the residual: *"during a degraded window, identities exist that have not proven they hold their number"*. **So the identity row precedes phone verification**, and [ADR-039](../decisions/ADR-039.md)'s *"mandatory at registration"* is a gate inside the registered state rather than a precondition of entering it.
- [`0002:305-307`](../../packages/db/migrations/0002_identity.sql) explains that `otp_challenges` keys off the normalized address *"before a user may exist"*. **A creation at OTP request makes that sentence false in a merged migration.**

**What was left to rule is the shape of the write, what the row carries, and the refusals stated as refusals rather than left as silence.** That is what the entry does.

### At first purchase is not late. It is unreachable

Both checkout endpoints declare `required: 'session'` ([`checkout.ts:2437`](../../apps/api/src/routes/checkout.ts) and [`:2501`](../../apps/api/src/routes/checkout.ts)), and a session is a `sessions` row referencing `users` referencing `identities`. **By the time checkout runs the identity must already exist, or the caller could not have reached the endpoint.**

**That discharges [ADR-183](../decisions/ADR-183.md)'s own "where this entry is most likely wrong" paragraph**, which said: *"If the right trigger is the first purchase rather than the first sighting, this entry has put provisioning one step too early."* It did not. The instant it chose is the only instant reachable, and `0054` is correct as merged.

---

### The `sms` channel cannot register anybody, and nothing says so

[`0002:248`](../../packages/db/migrations/0002_identity.sql) declares `users.email citext NOT NULL UNIQUE`. `VerifyRequest` presents two symmetric channels. **A verification arriving on `sms` for an unknown number has no value to write into `users.email`**, so it cannot create the login the ruling's unit of work requires, and `is_new` is always false there.

The channel is a **login** channel, resolving through `identity_phones.identity_id` to an identity that must already exist. That is coherent with [ADR-039](../decisions/ADR-039.md) making a verified phone a signal rather than a contact field, **but an implementer reading the contract's symmetric shape would build a symmetric handler and learn the asymmetry from a `NOT NULL` violation on a money path.** Recorded as a clause of the entry rather than deferred.

### `LT-01` posted end to end, which no session had done

Against the 58-file schema on a real PostgreSQL 16, in one transaction: an identity created the ruled way, then the **shipped** `lt01` builder from [`payouts.ts:785`](../../apps/api/src/routes/payouts.ts) and the **shipped** `postTransaction` from [`packages/ledger/src/post.ts`](../../packages/ledger/src/post.ts), over a `LedgerTx` bound to a live connection.

`0054`'s trigger opened all three positions, `resolve` found them instead of throwing, four entries posted, and the split landed: 40,000c to the wallet, 10,000c recognized as fee revenue at approval, withdrawable drained to exactly zero, global sum zero.

**So the path from a person typing an email to `LT-01` posting is blocked at exactly the four items the entry prices and at nothing else in the money layer.**

---

### Why `0060` was refused after being built

The ruling's unit-of-work clause is a cross-row assertion no row-local `CHECK` can make, and a `DEFERRABLE INITIALLY DEFERRED` constraint trigger makes it exactly. **It was written and executed rather than reasoned about**: it accepts the ruled shape and refuses the OTP-time shape at COMMIT.

**It was refused anyway, and the first ground is a clean A/B.** All 15 `probe_*.sql` scripts in `scripts/db/` were run against a fresh schema with the guard absent and again with it installed: **15 of 15 pass without it, 14 with it**, and the casualty is [`probe_ledger_constraints.sql`](../../scripts/db/probe_ledger_constraints.sql), the acceptance script for `0054`'s own trigger. It also has no caller, which is the rule [ADR-126](../decisions/ADR-126.md) section 7 applied to this very construction, and an `AFTER INSERT` trigger never sees the `UPDATE` a merge uses, so the invariant it advertises stops holding after the first merge.

### Landmines

It tells an operator that a pre-identity read has no door and that the repair is widening `SystemReason`; [ADR-126](../decisions/ADR-126.md) built the door as `resolutionDb` and ruled expressly that the vocabulary that moves is the TABLE and never the REASON. Outside this fence, one string, owed by whoever next holds that file.
- **`resolutionDb` has no caller anywhere in `apps/`.** Its only workspace references are inside `packages/db` and its own suite. A door built for a named endpoint that the endpoint does not open decays into a door nobody remembers the reason for.

A handler that reads then writes rather than writing and catching the unique violation creates a second identity, with three ledger accounts, that nothing can delete.
- **The dispatch's pool count is off by one** against its own `0060` row, which names three precedents as the fourth, fifth and sixth. This return is the seventh.
