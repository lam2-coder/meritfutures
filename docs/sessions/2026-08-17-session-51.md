### `accounts.expires_on` is ruled out as an input, and three mechanisms already make that structural

`ADR-051` rules that **`phase_eval.max_days` binds and `accounts.expires_on` is a derived materialisation that is never an input to `R-32`**. Nothing written this session makes that mechanically true: it is true because the column was not read. **A ruling whose enforcement is "we did not do the wrong thing" reads as unenforced to the next person**, so the enforcement is worth naming, because this one is genuinely enforced and by four separate things.

**The engine cannot reach a database at all.** [`RI-01`](../../packages/tooling/checks/repo-invariants.mjs) is "packages/rules-engine declares no workspace dependencies, in any dependency field", so `@merit/db` is unreachable by construction rather than by convention. [`RI-07`](../../packages/tooling/checks/repo-invariants.mjs) is "packages/rules-engine's transitive module graph reaches no Node builtin", which removes `node:fs` and `node:net` and with them every path to a socket or a file. **`types: []`** in [the package's tsconfig](../../packages/rules-engine/tsconfig.json) withholds the ambient Node typings, so a call to one would not compile even if the module resolved. And **`merit/engine-purity`**, attached at `error` in [`eslint.config.js`](../../eslint.config.js), is the lint-level statement of the same rule.

So a future session cannot quietly make `expires_on` authoritative by reading it: there is no query to write, no client to import, and three of the four mechanisms fail the build before the fourth is consulted. **What remains genuinely conventional is only that the value is not passed IN on `DayInput`** -- and that is visible in one interface, which is where ADR-051 put the amendment.
