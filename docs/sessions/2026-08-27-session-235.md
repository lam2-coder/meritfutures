### 3. HALF ONE: the refusal moves into the audit

**The change in `replay.ts` is one guard and its argument.** `runReplayAudit` gains, beside the existing `OI-14` guard and before it:

```
if (report.accountsAudited === 0) throw new ReplayAuditRefusal(...)
```

`ReplayAuditRefusal` already exists and already carries both instances the file documents (the empty in-scope set and the history that is not one account life). A third instance is the same failure at a third scale and needs no new class.

**THE ORDER OF THE TWO GUARDS IS DECIDED AND NOT INCIDENTAL.** The zero-accounts guard runs FIRST. Over an empty book the `OI-14` guard is false anyway, so the order changes no outcome today; it is fixed so that the message a reader gets names the wider failure ("nothing to audit") rather than the narrower one ("nothing in scope"), which is the diagnosis that is true.

**WHAT THIS CHANGES ABOUT WHAT THE AUDIT PROMISES, STATED BEFORE IT IS DONE.** [`apps/worker/test/replay.test.ts`](../../apps/worker/test/replay.test.ts) carries `it('does not refuse when there is genuinely nothing stored')`, which asserts the opposite of the new behaviour and passes today. **That assertion is INVERTED, not deleted**, and the inversion is the whole reason `ADR-123` was reserved. See section 6.

**The cost, stated rather than discovered later.** On a genuinely empty production book (before the first nightly batch has ever written a row) the audit refuses instead of reporting clean. That is deliberate: an audit is a control, and a control with no subject must say so. The alternative is the sentence [ADR-073](../decisions/ADR-073.md) section 5 refused to ship: *"a nightly built today reports `accountsAudited: 0, diverged: 0`, green, every night, over nothing."*

**Files.** [`apps/worker/src/batch/replay.ts`](../../apps/worker/src/batch/replay.ts), [`apps/worker/test/replay.test.ts`](../../apps/worker/test/replay.test.ts), [`scripts/demo/world.ts`](../../scripts/demo/world.ts) (guard removed), [`scripts/demo/test/world.test.ts`](../../scripts/demo/test/world.test.ts) (assertion follows the class).

### 4. HALF TWO: the enrichment call site

**One call, at the end of `completePurchase`, after the attribution write and before the response is built.** Placing it last keeps `checkout.ts`'s own sentence true ("THE ATTRIBUTION WRITE IS THE LAST THING AND IT IS NOT GUARDED") and makes "nothing downstream reads this" a fact about position as well as about types.

| Piece | Source | Why not somewhere else |
|---|---|---|
| `EnrichmentTx` | A new `readonly enrichment: EnrichmentTx \| null` on `CheckoutTx` | It must be **the open transaction**, which in this file is only ever `CheckoutTx`. `packages/enrichment` declares no `@merit/db` and cannot open a connection ([`tx.ts`](../../packages/enrichment/src/tx.ts)), which is what makes an observation commit with the purchase that caused it or not at all |

| `subject` | `{ ip }` and nothing else | Checkout knows the request IP. It does not hold an email, a phone, a device fingerprint or a BIN: `CheckoutRequest` carries `plan_id`, `size_cents`, `coupon_code`, `affiliate_click_token`, `accept_tos_version_ids`, and `AuthSession` carries ids. **Four of the five facets are absent rather than empty**, which is what `EnrichmentSubject` being a `Partial` under `exactOptionalPropertyTypes` already requires |

**Either `null` means NO CALL AT ALL**, which is clause 4's posture reached one step earlier than the contract row: no vendor wired, no disclosure, and a checkout that commits exactly as it would have.

#### 4.1 The two places, and the assertion against each

[ADR-115](../decisions/ADR-115.md)'s title is *"the two places observe mode could quietly become enforcement are closed by shape rather than by discipline"*, and clause 2 is both of them.

| Place | The shape that closes it | What this session asserts AT THE CALL SITE |
|---|---|---|
| **1. A return value a call site could branch on** | `observeEnrichment` returns `Promise<void>`. Seed `S-1` in [ADR-115](../decisions/ADR-115.md) section 4 is this shape reopened | **A source-reading case**: the call in `checkout.ts` is `await observeEnrichment(` with its result bound to nothing, and the file contains no enrichment decision word. A behavioural case cannot see this one, because a call site that ignored a returned decision looks identical from outside until the day somebody reads it |
| **2. A throw that propagates into checkout's transaction** | `observeEnrichment`'s `try`/`catch` makes it total. A throw inside the transaction is a `ROLLBACK`, so a propagating enrichment failure is **enforcement by exception**, which is a silent decline. Seed `S-7` | **Three behavioural cases, all through Fastify's real router and the fixture's real staging transaction**: a vendor that hangs past the 800ms budget, a vendor that throws, and a reporter that throws. Each asserts the response is byte-identical to the no-enrichment response and `fixture.committed.purchases` holds exactly one row |

**AND THE DIRECTION IS ASSERTED POSITIVELY AS WELL AS NEGATIVELY.** A vendor answering with a **maximal risk score** (every `reputationBp: 0`, every `footprintPresent: false`) commits the same purchase with the same `amount_cents`, `discount_cents`, `psp` and `payment_session` as a checkout with no enrichment at all. A suite that only ever seeded failures would pass against a call site that ignores enrichment entirely, which is the [DELTA_MANIFEST](../../packages/db/DELTA_MANIFEST.md) section 13 trap this repository catches most often, so a case also asserts the observation **was** recorded: `signalsInserted` on the reported outcome, so "non-blocking" is distinguishable from "not wired".

#### 4.2 What the fixture cannot model, said here rather than implied

[ADR-115](../decisions/ADR-115.md) clause 2 states that when a write **this package issues** fails, the caller's transaction is **already** aborted before the `catch` runs, so the swallow hides nothing. **A JavaScript staging-store fixture cannot reproduce that**, because nothing in it puts the transaction into Postgres's aborted state. So the write-failure case asserts what is true of the fixture (the throw does not escape `observeEnrichment`, and the outcome is reported as `record_failed`) and says in its own comment that the real rollback is Postgres's and is not observable here. **A test that claimed otherwise would be asserting a fact about a database this suite never opens.**

**MONEY.** Nothing added to the checkout path carries money. The subject is an IP; `FacetFinding.reputationBp` is integer basis points and never reaches a money column; every expectation in the new cases is derived from `SIZE` in `bigint` cents, as the file already requires.
