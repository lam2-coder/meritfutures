### 4. Half two: the call site, and the two places asserted separately

[ADR-115](../decisions/ADR-115.md)'s title is *"the two places observe mode could quietly become enforcement are closed by shape rather than by discipline"*, and **both are properties of the CALL SITE rather than of the package**. A package that decides nothing becomes enforcement at the site that calls it.

| Place | Closed by | Asserted here as |
|---|---|---|
| **1. A return value a call site could branch on** | `observeEnrichment` returns `Promise<void>` | **A source-reading case.** Exactly one call site; its text is `await observeEnrichment(tx.enrichment, {`; no binding, no `void`, no chained `then` or `catch`; and no score, band, `severity` or `FootprintScore` word anywhere in the route. **A behavioural case cannot see this one**, because a call site that ignored a returned decision looks identical from outside until somebody reads it |
| **2. A throw that propagates into checkout's transaction** | `observeEnrichment`'s `try` makes it total, including over the reporter's own throw | **Three behavioural cases through Fastify's real router and the fixture's real staging transaction.** A hanging vendor, a throwing vendor and a throwing reporter each commit the purchase with a response byte-identical to the unwired baseline |

**A VENDOR TIMEOUT DOES NOT ROLL BACK A PURCHASE, and the slow case is measured rather than reasoned about.** `hangingVendor()` returns a promise that never settles and ignores the abort signal deliberately, so what runs is the route's own 800ms budget: `ENRICHMENT_TIMEOUT_MS` is a package constant and the route does not pass `timeoutMs`, which `ObserveDeps` documents as *"for suites, not for routes"*. The outcome is reported as `timed_out`, **the `integration_dispatches` row is still written because the subject left Merit either way**, and the purchase commits.

**Three seeds watched failing and all three removed:**

| Seed | What it changed | Red |
|---|---|---|
| `S-1` | The call site binds the result and branches on it | 1, place 1 |
| `S-7` | The call site reaches the vendor ITSELF, uncaught, which is the naive transcription | 2, both of place 2 |
| `S-0` | The call site never calls enrichment at all | 5, the negative control among them |

**`S-0` is why the negative control exists.** Without it the four failure cases would pass against a route that never calls enrichment, so the `answeringVendor('maximal')` case asserts both halves: the worst reading on every facet returns the same response, **and** the observation was recorded (`signalsInserted: 1`, one `identity_signals` row, and a score in integer basis points on the 0 to 10000 scale that is stored nowhere, per [ADR-115](../decisions/ADR-115.md) clause 1).

**WHAT THE FIXTURE CANNOT MODEL, said in the test rather than implied.** [ADR-115](../decisions/ADR-115.md) clause 2 states that when a write the package issues fails, the caller's transaction is ALREADY aborted before the catch runs. A JavaScript staging store does not enter an aborted state. So the write-failure case asserts the half that is true here, that the throw does not escape and the outcome is reported as `record_failed`, and its own comment says the rollback is Postgres's and is not observable in this suite. **A test that claimed otherwise would be asserting a fact about a database this file never opens.**

**Money.** Nothing added to the checkout path carries money. The subject is the request IP: `CheckoutRequest` carries a plan, a size, a coupon code, a click token and TOS ids, and `AuthSession` carries ids, so **four of `EnrichmentSubject`'s five facets are absent rather than empty**. Every expectation in the new cases is derived from the file's one `bigint` price seed.
