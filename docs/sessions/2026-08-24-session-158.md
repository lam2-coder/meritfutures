**THE CLAIM ROW THIS SESSION WAS TOLD TO STRIKE DID NOT EXIST WHEN IT OPENED, AND LANDED WHILE IT RAN.** The brief says *"Session 158 is already CLAIMED for you"*. At the session's start commit (`ef4cccc`) the table's live rows were **147, 148 and 156**, with **no row for 157 through 171** — checked with a numeric grep over the whole file rather than only the table. So the row was **written here already struck**, on [session 143](2026-08-23-session-143.md)'s `ADR-082` precedent: *"a deleted row is indistinguishable from a number nobody ever claimed, which is the state this table exists to end"*.

**Then `#199` merged, reserving 157 to 170, and the two rows collided on one key.** `CI-06u` failed the merge-result run and named it exactly: *"the first cell `158` already heads the row at line 61 of the same table. Two rows for one key is the keep-both merge"*. Resolved by **striking the dispatcher's row IN PLACE and deleting the stand-in**, per [ADR-065](../decisions/ADR-065.md) T3 and the table's own rule that a row leaves by being written and never by being deleted: the dispatcher's row is the real claim and carries the real dispatch text, and the stand-in existed only to stand in for its absence.
