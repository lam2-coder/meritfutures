#### 1.2 The CHECK, read at source before either handler was written

[`0031:62`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql), quoted rather than paraphrased:

```sql
ALTER TABLE payout_requests
  ADD CONSTRAINT payout_requests_hold_is_complete CHECK (
    (status <> 'held_pending_review'
       AND held_at IS NULL AND hold_flag_id IS NULL
       AND hold_expires_at IS NULL AND hold_tos_clause IS NULL
       AND hold_reason IS NULL)
    OR
    (status = 'held_pending_review'
       AND held_at IS NOT NULL AND hold_flag_id IS NOT NULL
       AND hold_expires_at IS NOT NULL AND hold_tos_clause IS NOT NULL
       AND hold_reason IS NOT NULL)
  );
```

**It is a BICONDITIONAL and [ADR-158](../decisions/ADR-158.md) finding 9 is confirmed at the source.** Both of this session's endpoints move `status` off `held_pending_review`, so **both must NULL all five hold columns in the same statement**, and a release or an enforcement that left one populated is refused by Postgres rather than by anything in the handler. **These two endpoints are the only things that will ever perform that transition**, so the erasure is this session's to name.

#### 1.3 The order inside each transaction, which is the control

1. `lockAt('payoutRequests', { id })` -- **`rowAt` plus `FOR UPDATE`**, [ADR-157](../decisions/ADR-157.md). Two operators resolving one hold concurrently is the case it exists for. `undefined` is `not_found`.
2. `status === 'held_pending_review'` or `conflict`, per both contract rows' error lists.
3. **CAPTURE ALL FIVE HOLD COLUMNS OFF THE LOCKED ROW.** After step 5 the row cannot say it was ever held.
4. `INSERT admin_actions` with `before` carrying the whole hold. **FIRST, before the mutation**, on [`admin-writes.ts`](../../apps/api/src/routes/admin-writes.ts)'s rule and [`0017:82`](../../packages/db/migrations/0017_events_and_audit.sql)'s: `reason text NOT NULL` is the control and it is only a precondition if it is written first.
5. `updateAt('payoutRequests', { id }, ...)`: the new status plus **five explicit nulls**.
6. **Release only: post `LT-01`.** See 1.5.
7. Respond, from the hold captured at step 3.

#### 1.4 `INV-M5-23`'s shape: an authorization refusal is never a gate result

The `401` and the `403` are decided **before `operator()` opens a transaction**, so a refused caller writes **no `admin_actions` row, no snapshot and no `payout_requests` change**. That is [M05](../plans/M05-payout-system.md) `INV-M5-23` in its own words carried one endpoint over, and it is a property of the handler's ORDER rather than of a comment.

#### 1.5 The release POSTS `LT-01`, and this is the one non-obvious call in the session

[ADR-040](../decisions/ADR-040.md)'s own table: a held request has **nothing posted, no wallet credit, nothing owed**; `approved` is the state *after* `LT-01`. [`payouts.ts:991`](../../apps/api/src/routes/payouts.ts) says it in terms -- *"The ledger is the discriminator between `held_pending_review` and `frozen`, and it is what makes release mean 'approve and pay' on a hold"* -- and does not post when the hold stands. **So the deferred posting has exactly one home and it is this endpoint.** A release that moved `status` to `approved` and posted nothing would mark a payout paid that never paid.

Three things follow, each of which is a refusal to invent:

- **The posting is built by [`payouts.ts`](../../apps/api/src/routes/payouts.ts)'s own `lt01()`, imported.** A second transcription of `debit trader_withdrawable / credit trader_wallet / credit fees_revenue` is the two-statements-of-one-fact hazard on the money path, and `lt01` already asserts `INV-M5-03` internally. **This module contains no ledger arithmetic and names no ledger account.**
- **The money comes off the stored row and is never recomputed.** `INV-M5-02`: the number shown is the number sent. The contract's own comment on `PayoutReleaseResponse` says a release producing a different number would mean the hold cost the trader money.
- **The `LedgerTx` is a port the wiring supplies**, exactly as [`payouts.ts`](../../apps/api/src/routes/payouts.ts)'s `PayoutTx.ledger` is. `SqlExecutorReason` gains no member, `SystemReason` gains no member, nothing imports `pg`, and no key type is cast past.

#### 1.6 What is LOST, stated here and in the code rather than worked around

**The `hold_reason` does not survive.** It is one of the five columns the CHECK NULLs, and neither `released_hold` nor `enforced_hold` has a field for it: the contract's blocks are `{ held_at, resolves_by, tos_clause, flag_id }`. So the operator's written justification for the hold survives **only in `admin_actions.before`**, and only because this session writes it there.

**And the row keeps no mark that it was ever held at all.** After a release, `payout_requests` cannot distinguish a request that was held for 47 hours from one that was never flagged; `GET /payouts` correctly returns `hold: null` for both. The whole record is the `admin_actions` row, which is `firm`-class, append-only under [`0026`](../../packages/db/migrations/0026_roles_and_grants.sql), and reachable only by an operator.

**This is NOT repaired here.** A migration is sacred once merged -- superseded, never edited (constitution `E2`) -- so the constraint cannot be fixed in this fence, and a shadow column added beside it to dodge the CHECK would be a second record of the hold that the database does not constrain, which is worse than the hole. **The honest thing is built and the loss is named.**

#### 1.7 The fence, and what this session refuses to take

- **NO ADR NUMBER AND NO MIGRATION NUMBER.** The contract already defines both rows; this is transcription against it.
- **`packages/db` is untouched**, and so are [`admin-reads.ts`](../../apps/api/src/routes/admin-reads.ts) (session 280), `wallet.ts` (session 275) and [API_CONTRACT](../architecture/API_CONTRACT.md).
- **The other three unregistered admin rows are not built**: `POST /admin/wallet/:identityId/correct`, `POST /admin/wallet/:identityId/spend-limit` and `GET /admin/wallet/reconciliation` are wallet work.
- **The route registry needs no edit at all.** [`registry.ts`](../../apps/api/src/registry.ts)'s module list **is the directory listing** and is never written down, so the new file registers itself and collides with nothing session 275, 280 or 284 is writing.

### 4. Landmines

**THE LEDGER IDEMPOTENCY KEY IS SHARED WITH `payouts.ts` ON PURPOSE AND IT LOOKS LIKE A BUG.** `releaseLedgerKey` returns `POST /accounts/:accountId/payout <stored key>` from an endpoint whose path is `/admin/payouts/:id/release`. A reader who "corrects" it to name this endpoint removes the only thing stopping two doors from posting two `LT-01`s for one approval, and both would commit. The reason is in the function's own doc comment and pinned by two assertions.

**A SIXTH HOLD COLUMN ADDED LATER AND NOT BLANKED HERE IS A `23514` IN PRODUCTION.** `payout_requests_hold_is_complete` is a CHECK on the table and this module's `SET` clause is the only place that satisfies it. The suite therefore derives the column set FROM the migration and compares, in both directions, rather than pinning a literal list that would silently keep passing.

**`hold_reason` HAS EXACTLY ONE SURVIVING WRITE AND IT IS ONE LINE.** `holdBefore` copies it into `admin_actions.before`. Delete that line and the operator's written justification for every hold in the system's history stops existing the moment the hold resolves, with nothing failing.

**THE MODULE IMPORTS FROM THREE SIBLING ROUTE FILES AND THAT IS DELIBERATE.** `ACCOUNT_ACTION_ROLES` and `AdminPrincipal` from [`admin-writes.ts`](../../apps/api/src/routes/admin-writes.ts) so two admin modules cannot answer "who may act" two ways; `lt01` and `PAYOUT_ENDPOINT` from [`payouts.ts`](../../apps/api/src/routes/payouts.ts) for decisions 1 and 2; `centsToJson` from [`checkout.ts`](../../apps/api/src/routes/checkout.ts). `accounts.ts` and `catalog.ts` already import from `auth.ts`, so the idiom is precedented, but **a session that moves any of those four exports breaks this module** and `RI-10` is what will say so.

**THE UNWIRED DEFAULT ANSWERS 503 AND MUST NOT BE MADE PLAUSIBLE.** `UNWIRED_ADMIN_PAYOUT_BACKEND` rejects every method. The value it would otherwise have to invent is whether a held payout was released.
