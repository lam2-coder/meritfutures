### 5. Finding 2: the package boundary, and the reason `RI-08` gives for its scope

**The dispatch's anticipated answer holds in the direction it asked about.** `packages/tooling` cannot import `apps/api`: a probe placed in `packages/tooling/checks/` importing `@merit/api` fails `ERR_MODULE_NOT_FOUND`, and `packages/tooling/node_modules/@merit` does not exist. Declaring it would make a shared package depend on a deployable, which is `RI-04`'s argument pointed the other way. So a real `compose()` is unreachable from a `packages/tooling` check, exactly as the dispatch predicted, and the reader this session built therefore takes markdown as a STRING and reads nothing from disk.

**The other direction does not hold, and that is the finding.** A probe in `apps/api/test/` importing `@merit/tooling/checks/repo-invariants` **RESOLVED**, to `packages/tooling/checks/repo-invariants.mjs`, though `apps/api/package.json` declares no such dependency and `apps/api/node_modules/@merit` does not contain it. The mechanism is that [`package.json:30`](../../package.json) declares `@merit/tooling` in the workspace ROOT `devDependencies`, so it is linked at `<repo>/node_modules/@merit/tooling`, and Node's resolution walks up the directory tree from the importer.

`RI-08`'s `covers` line states the opposite as its reason for not following transitive edges:

> `.npmrc` sets `node-linker=isolated`, so an undeclared specifier resolves neither at run time nor at build time (TS2307, measured from apps/site and apps/api both, with no `paths` mapping in the tree)

Both halves were measured here and both are false for a root-declared package. Run time: **RESOLVED**. Build time: `tsc --noEmit -p apps/api/tsconfig.json` over the same import reports **`TS7016`**, *"Could not find a declaration file for module ... `packages/tooling/checks/repo-invariants.mjs` implicitly has an 'any' type"*, which is resolution SUCCEEDING and only typing failing. `TS2307` is what an unresolvable specifier produces, and this is not one. The same sentence appears three times in [`apps/api/package.json`](../../apps/api/package.json)'s `//dependencies` note and once in [`.npmrc`](../../.npmrc)'s comment on `node-linker`.

**The hole is bounded and it is nine names wide**: the root manifest's `devDependencies` are `@merit/tooling`, `@playwright/test`, `@types/node`, `eslint`, `fast-check`, `eslint-plugin-merit`, `prettier`, `typescript`, `vitest`. **`@merit/db` is not among them**, and `node_modules/@merit` holds `tooling` alone. So `RI-08`'s CONCLUSION about the accessor is unaffected: the acquisition point for `@merit/db` really is the direct field, because the accessor is not root-declared. **What is wrong is the reason, not the ruling**, and a reason that is wrong in the permissive direction is the kind a later slice leans on.

**REGISTERED AND NOT REPAIRED.** `repo-invariants.mjs` may gain no invariant this slice and its `covers` line is a `RI-08` change; the root manifest is nobody's fence this wave.
