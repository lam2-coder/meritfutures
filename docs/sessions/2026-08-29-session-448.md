### 2. The first ruling: which `ok`

The row called this the trap with a wrong answer available on both sides, and it is.

**The engine's, carried through untouched.** `ValidationResult.ok` is
`errors.length === 0 && materialization.length === 0`, and the primary source that puts the second
term at publish is a migration rather than a plan: [`0004_catalog.sql:188`](../../packages/db/migrations/0004_catalog.sql),
inside the block declaring the materialized column, reads *"The publish path writes both, and
CV-publish validation asserts the materialized flag matches the parent's jsonb."* `FM-07` names the
cost: a size row that disagrees with its rules is a plan whose published text and executed arithmetic
are two different plans, and `copy_blocks` publishes the first.

**The other direction is checked rather than assumed.** [API_CONTRACT](../architecture/API_CONTRACT.md)'s
publish row says the endpoint *"Materializes `plan_version_sizes` in the same transaction"*, so the
contract's own sentence about this endpoint is that the two agree. Nothing in the corpus makes a
disagreement publishable.

---

### 3. The consequence nobody had named

The publish handler maps `validation.errors` straight into the problem document. So a projection that
carried the engine's `ok` and only the nineteen `CV-nn` rules would answer `validation_failed` with an
**empty `errors[]`** on a plan refused for materialization alone: a refusal an operator cannot act on,
on the one endpoint where the remedy is editing the refused thing.

**Measured**, on a plan whose eval and funded daily loss limits differ: `errors` empty,
`materialization` one finding, `ok` false. The MZ findings are folded into `errors` for that reason.
`diffs` are not folded, because `PW-` values fire on plans that publish.

### 4. The finding, and why it is about a frozen document

`sizeCents` is the **only** address a violation carries for the `plan_version_sizes` row it was found
on. No ordinal, no index, no primary key. Two rows with the same defect:

```
{ id: 'CV-02', path: 'drawdown_cents', detail: 'drawdown_cents is 0', sizeCents:  5000000n }
{ id: 'CV-02', path: 'drawdown_cents', detail: 'drawdown_cents is 0', sizeCents: 10000000n }
```

project to two entries that are **equal**. Not degraded: equal.

**And widening `PlanValidation` would move the loss one line later rather than remove it.**
[API_CONTRACT](../architecture/API_CONTRACT.md) section 2 freezes the envelope at
`errors?: Array<{ path: string; message: string }>`, and this refusal travels inside it. So the
finding is about that document and it is **reported at [ADR-257](../decisions/ADR-257.md) section 5
rather than repaired**, along with two others: the `path` slot on this endpoint carries a rule id
because the wire has one addressing slot and the engine produces two addressing facts, and the publish
row names two errors while its handler raises a third that may be the wrong code for the condition.

**The projection ships anyway because the loss FAILS CLOSED.** `ok` survives, so every plan the engine
refuses is still refused. What is lost is an operator's ability to tell which size row to repair. That
is the direction of the loss, and it is the whole argument for building rather than refusing.

### 6. Where this session is most likely wrong

**THE `ok` RULING RESTS ON A MIGRATION COMMENT AND A FAILURE-MODE NAME, NOT ON AN ENDPOINT RULING.**
No approved document says in one place that a materialization finding refuses a publish. The engine
says it and this session takes the engine at its word. A founder who reads `0004`'s sentence as
describing the materialization STEP of the same transaction rather than a gate before it would rule
the other way, and one line of the projection would change.

**AND "FAILS CLOSED" IS ARGUED ACROSS THE WHOLE PUBLISH PATH RATHER THAN EXECUTED.** It rests on `ok`
being the only value the handler branches on, which is read from the handler and is true today. It
stops being true the moment anything downstream reads `errors` to decide something, and nothing
mechanical in this tree would notice.

**THE PROJECTION IS NEVER CALLED IN THIS TREE.** No wiring slice exists. What is not executed is the
composition a deployment would write, and in particular how `rules: unknown` and
`sizes: readonly unknown[]` are narrowed at the wiring site without a cast that hides a shape error.
