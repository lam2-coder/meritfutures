### 1. The distinction this session existed to render, and why one test date is the whole assertion

[API_CONTRACT](../architecture/API_CONTRACT.md) section 1: *"`*_at` are RFC 3339 UTC strings. `*_day` and `*_on` are `YYYY-MM-DD` **exchange trading days**, never UTC dates."*

`EconomicCalendarOccurrence` carries `scheduled_release_at` and `release_trading_day` side by side. [`0039`](../../packages/db/migrations/0039_economic_calendar.sql) header item 5 made the second a COLUMN precisely so nothing would derive it, and [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql) supplies the mechanism that makes them differ: *"The next session opens at 17:00 CT regardless."*

| | |
|---|---|
| `2026-03-03T23:30:00Z` | the stored instant. UTC calendar date `2026-03-03` |
| `2026-03-03 17:30 CT` | the same instant, CST (`UTC-6`); US daylight time begins `2026-03-08` |
| `2026-03-04` | **the trading day**, because 17:30 CT is inside the session that opened at 17:00 CT and that session's trading day is the next date |

**The suite asserts the divergence before it asserts the rendering.** A test on a date where the two agree passes against a route that derives the day from the instant, so it asserts nothing at all. A morning row where they DO agree is kept beside it, because a suite holding only the evening row cannot tell *"renders the stored day"* from *"renders the day after the instant"*.

### 2. What the calendar route does NOT do, and each refusal it does

| Does not | Why |
|---|---|
| **Compute the calendar** | It is maintained as data and the engine already reads it. The route holds no slice and calls nothing in [`calendar.ts`](../../packages/rules-engine/src/calendar.ts) |
| **Read a clock** | [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md)'s threshold compares `coverage_end_day` against *"today"*, and that column is in the CT trading-day domain. A route reaching for `new Date()` would have produced a UTC date and compared two vocabularies. `freshness` arrives as data |
| **Sort** | Lexicographic order over RFC 3339 is chronological only at a fixed precision, which section 1 does not fix. `economic_calendar_release_idx` is where ordering lives |
| **Filter `tier`** | `0039` header item 3 makes the tier a column rather than an import filter. A route that rendered only tier 1 would make the field a constant |

**And it refuses**: a `*_at` that is not `Z`-spelled RFC 3339; a `*_day` that is not a bare day; `stale: false` beside `covered_through_day: null` (`DEP-M4-09`, *"the dangerous failure is not the empty panel, it is the confident one"*); two rows for one occurrence, which `economic_calendar_current`'s `DISTINCT ON` makes impossible and which would be two release times for one release; a tier outside `1..3`; and `economic_calendar_revision_states_its_reason`'s equivalence in both directions.

**Auth is `session` and the handler reads nothing out of it**, which is [ADR-111](../decisions/ADR-111.md) clause 3 as the contract states it: *"widening later is a decision and narrowing later is a break."* `economic_calendar` is classified `firm` in [`scope.ts`](../../packages/db/src/scope.ts), so there is no identity filter for a session to supply either way.

### 4. The webhook clause, watched in both directions on one payload

[ADR-109](../decisions/ADR-109.md) clause 7 is that entry's only prohibition. The suite watches both halves in one test on one payload:

1. **The correctly signed bytes VERIFY.** `200`, the applier called once.
2. **The SAME payload re-serialised is REFUSED.** `401`, `signature_mismatch`, the applier not called again.

Before either, the test asserts the two texts **parse equal** and are **different bytes**, so the premise cannot silently stop being true. A key-reordering re-serialisation of **identical length** is refused too, which is the version a length check would have missed.

**Neither assertion alone proves anything**, and that is why both are in one test: a verifier that refuses everything satisfies the second, and a verifier that checks nothing satisfies the first.
