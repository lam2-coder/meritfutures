### 1. The objective, and what it turned out to be about

**Row `281` asked one question: is `usePayoutBackend`'s `state` clause still true?**

The clause reads that `state` *"waits on NO CAPABILITY EITHER. It waits on a DEPLOYMENT that has run the job, and on a way to read the calendar on the transaction that reads the state."* The row said the second half looked discharged, supplied the citations it had verified, and instructed that they be re-derived rather than trusted. It then framed the honest question as a ruling: does a port refuse because a table is empty, or does it wire and answer honestly that there is no state for the day?

**Both halves of the row were right and the question was the wrong one, which is a better outcome than either arm it named.**

### 2. What was checked, in order

The row's citations were re-derived first, because a session that starts from a dispatch is a session that inherits its errors.

1. **The door exists and is on the transaction.** `lastClosedTradingDay(): Promise<string>` on `ScopedTx`, implemented over `source`, which is the payout transaction. Its statement reads `trading_calendar` and `trading_calendar_loads` and throws three ways: an empty calendar, an exhausted one, and a coverage gap. No fourth outcome.
2. **The route names it.** `PayoutSubject.state`'s docblock instructs a backend to call that method and not to fold a calendar in the route.
3. **`CATALOG_TABLE_KEYS` is five.** No sixth key was needed and none was admitted.
4. **The stale sentence is stale.** `readLastClosedTradingDay` is gone from `apps/worker`'s exported surface; `anchorLastClosedDay` reads both tables in one transaction. [ADR-277](../decisions/ADR-277.md) section 7 item 2 registered it and was fenced out of the file.

**Then the entry's own summary was checked, because the row's instruction was to distrust the entry's reading of itself.** The summary names three fields and says two wait on nothing. `gates` holds: `ExternalGateFacts` takes raw scalars and two row lists, and every table is `root` or `owned` on this transaction. **`plan` does not.**

### 3. The finding

`PayoutSubject.plan` is a `ResolvedPlan`, not a row. [ADR-233](../decisions/ADR-233.md) gave `ScopedTx` a catalogue **read** over `planVersions` and `planVersionSizes`; `plan_versions.rules` is a `jsonb` column, so what a catalogue read hands back is a blob. `resolvePlan` takes a decoded `PlanRulesJson`.

The census, over `apps/*/src` and `packages/*/src` with comments stripped:

- **Two files call `resolvePlan(`**, and one of them is the declaration. Neither is under `apps/api/src`.
- **Two files declare a decoder returning the published shape**, in `apps/worker` and `apps/site`. `apps/api` can import neither deployable.
- **The engine declares none.** `PlanRulesJson` leaves that package through `export type`.

The same blocker is already live one port over, on the same value, in `EligibleFoldUnwired`'s own message ([ADR-269](../decisions/ADR-269.md)). **Two ports in one deployable wait on one decoding and only one of them said so.**

### 4. Why the empty table is not the question

The row's second arm, wire and answer honestly, needs a refusal path this route does not have. `subject()` returns `PayoutSubject | null` where `null` is the 404 for a resource the caller does not own, so an absent `rule_states` row cannot be expressed in the return type and leaves as a throw. `unwiredOrThrow` is the route's one funnel and it rethrows anything that is not a `PayoutBackendUnwired`. **The trader is answered 500.**

[ADR-256](../decisions/ADR-256.md) ruling 12 is the standing rule and it is quoted in `wiring.test.ts`'s own header: wiring is permitted when the last gap is a thing the deployment sets, and a composition that does not exist is not such a gap. An unrun nightly job is a thing a deployment does. **A refusal arm is not; it is code somebody writes here.**

### 5. What was not done

- **No sixth catalogue key.** The row forbade it and [ADR-268](../decisions/ADR-268.md) refused it in writing; nothing in this diff needed one.
- **No decoder written in `apps/api`.** That is the shorter diff and it is `FM-16` on the money path.
- **No move of the decoder into `packages/rules-engine`.** That is the correct repair and it is out of this row's fence.
- **No wiring.** `start.ts` is untouched and the route still answers 503.
- **`RI-31` not minted.** The number is returned.

### 6. What the next session should know

**The payout path's critical purchase is not the nightly schedule.** It is a move of one decoding into `packages/rules-engine`, and it unblocks `usePayoutBackend` and `setAdminReadSource` together. Behind it sits a smaller purchase, a refusal arm in `routes/payouts.ts` mapping an absent `rule_states` row to a problem document the contract permits. **Neither alone wires this port, and the order is decoding first.**

**And two refusals in `apps/api` are right for reasons that are no longer true** ([ADR-281](../decisions/ADR-281.md) section 7 item 1). They were left because the fence reaches them and ADR-003 does not, and each belongs to a different port's reason.
