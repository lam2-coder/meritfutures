### 1. The re-derivation, and why it was done against a running database

The brief said not to trust session 164's sentence. It was not trusted, and the check that mattered turned out to be one no session had run: **PostgreSQL 16 server binaries are present in this environment**, so the grants could be measured instead of argued about.

A cluster was initialised, all 47 files in [`packages/db/migrations/`](../../packages/db/migrations) applied in order under `ON_ERROR_STOP=1` exactly as [`corpus.yml:154-160`](../../.github/workflows/corpus.yml) applies them, giving **111 tables**, and the privileges read out of `has_table_privilege`.

**So session 164's conclusion stands and both of its forks are real.** What follows is where it does not stand.

### 2. Three findings this session added, in the order they change the remedy

**1. The revoke is declaratory. The omission is what does it.** Session 164's title names [`0026:157`](../../packages/db/migrations/0026_roles_and_grants.sql) as the cause. `0026` builds the analytics surface **by enumeration** and says so at `:124-126`, so `merit_analytics` never held anything on `rule_states` and `:157` revokes a privilege that was never granted. **A second database was built from the same 47 files with line 157 deleted and read back: still `false`.** The remedy is therefore an **addition**, and a later `GRANT SELECT ON rule_states TO merit_analytics` was executed against that database and flips it to `true`. A session that had inherited the sentence would have gone looking for a line to delete.

**2. `engine_gates` carries eight plan thresholds, so two of M13's own sentences were never true.** `INV-M13-01`'s enforcement cell says *"no access to plan config **at all**"* and `AS-M13-01` counter 1 says *"the thresholds are **unreachable**"*. [`hash.ts:421-476`](../../packages/rules-engine/src/hash.ts) declares the twenty-five leaves of `engine_gates` and **eight of them are plan parameters**: `tradedDays.need`, `winDays.need`, `winDays.floorCents`, `buffer.needCents`, `consistency.maxDayShareBp` ([`types.ts:322`](../../packages/rules-engine/src/types.ts)), `cadenceGap.need`, `minimumAmount.capCents`, `minimumAmount.minPayoutCents`. **Those two sentences and `AN-M13-04` were never jointly satisfiable**, whichever way the grant goes, which is why ADR-091 amends the invariant's text as well as ruling the grant.

**3. The revoke's stated reason argues against a threat M13 does not have, and guarantees the one it does.** [`0026:150-152`](../../packages/db/migrations/0026_roles_and_grants.sql) excludes `rule_states` because *"an analytics surface that reads verdicts will eventually be asked to explain them."* `AS-M13-01`'s attack ([M13:187](../plans/M13-trader-analytics-journal.md)) is *"`rule_states` has it, but joining is awkward, and the fills are right there. So the page sums them."* **The attack is what happens when `rule_states` is hard to reach.** And `0015:121-122`, in the migration that created the column, states its purpose as *"so the portal renders truth rather than recomputing it."* **`0026` revoked the table whose job is to make recomputation unnecessary.**

### 3. The ruling, in one line each

`merit_analytics` is granted `SELECT` on `rule_states`; it is a **new migration and never an edit to `0026`** (E2); the **plan-config revoke stays and is what makes the grant safe**; `SELECT` only and `rule_states` only; and `INV-M13-01`'s enforcement cell plus `AS-M13-01`'s counter 1 are **amended** to say what the schema actually delivers. **Clause 5 is the one a reader should be slowest to accept and is the reason this is a ruling rather than a migration.**

**The alternative was priced rather than dismissed.** *"The invariant is wrong, not the grant"* was the brief's own suggested answer and it loses on its own terms: it deletes `AN-M13-04`, it deletes **`AN-M13-01`'s floor** (`floor_cents` and `withdrawable_cents` are in `rule_states` and nowhere else, measured), it deletes `GS-172`, it deletes `OQ-M13-02`'s launch scope, **and it does not buy safety**, because `fills` stays granted and the demand for the number stays. **The column-level grant is a real third option**, measured with `has_column_privilege`, and is left open as a named foreclosure priced at `AN-M13-04`'s buffer progress and two missing targets.

---

- **Landmines:**

  - **`VG-8`'s GRANTS LEG IS NOT THIS SUBJECT, AND NOTHING ANYWHERE CHECKS A GRANT.** The brief asked whether anything asserts the grants. **Nothing does, in both directions.** [STRATEGY:214](../testing/STRATEGY.md)'s `VG-8` row says it itself -- *"**Grants:** [data-model](../architecture/data-model/README.md)'s append-only set and the four migrations that revoke on it; **no probe asserts it**"* -- and its scope is the **append-only set**, `merit_app` holding no `UPDATE` and no `DELETE`. **The `merit_analytics` READ surface is in no `VG` row at all**, so a session reading `VG-8` for this subject reads a row about a different one. `grep -rln 'has_table_privilege|pg_roles|information_schema.table_privileges|aclexplode'` over `scripts/`, `packages/` and `apps/` returns **two files and both are migrations that WRITE grants**. **Fifteen probes sit in [`scripts/db/`](../../scripts/db) and not one reads a privilege catalogue**, so every grant in this schema is currently asserted by reading the file that wrote it, which is the shape [ADR-034](../decisions/ADR-034.md) exists to end.

  - **A PROBE WRITTEN ON `has_table_privilege` WILL REPORT `false` ON A CORRECTLY COLUMN-GRANTED DATABASE, AND THAT IS MEASURED RATHER THAN WARNED ABOUT.** `GRANT SELECT (col, ...)` was executed on the second database: `has_table_privilege(...,'rule_states','SELECT')` stays **`false`** while `has_column_privilege(...,'floor_cents',...)` is **`true`**. **ADR-091's checkable clause is written on `has_column_privilege` for exactly this reason**, and so must the eventual probe be, or section 4's foreclosure becomes unimplementable the day someone takes it.

  - **THE POSTGRES SERVER IS AVAILABLE IN THIS ENVIRONMENT AND NO SESSION HAD USED IT.** `/usr/lib/postgresql/16/bin` carries `initdb` and `pg_ctl`, and the full 47-file set applies in well under a minute. Every session that has reasoned about a constraint, a grant or a trigger by reading SQL could have executed it instead. **Two of this session's three findings are things reading could not have produced**: that deleting `0026:157` changes nothing needed a second database, and the column-level behaviour needed a `GRANT` run and read back. **`initdb` refuses to run as root and the cluster directory must sit somewhere the `postgres` user can traverse**, which is the only friction; `/var/lib/postgresql/` works and the scratchpad does not.

  - **`NOT GRANTED` READS AS `GRANTED` TO `CI-06r`, AND THE CORPUS'S WORD FOR UNSIGNED IS `PENDING`.** The approval line was first written *"Founder approval: **NOT GRANTED**"* and `CI-06r` failed at 28 of 29, correctly: [`gates.mjs:3664`](../../scripts/corpus/gates.mjs)'s `ACCEPTING_VERDICTS` is a **closed uppercase vocabulary** matched by `line.includes`, so a negated accepting token is an accepting token. **The gate is right and the wording was outside its vocabulary**, which the gate's own comment says is deliberate. **`PENDING` is in `OPEN_VERDICTS` and is the form to use.** Worth naming because the failure mode is silent in the other direction: an entry that had headed itself `accepted` while writing *"NOT GRANTED"* would have passed.

  - **THE COLLISION WITH SESSION 174 IS CONFIRMED, AND NEITHER BRANCH CAN RESOLVE IT FROM THE INSIDE. MEASURED, NOT ARGUED.** `lam2-coder/meritfutures#223` was read directly and **creates the same path**, `docs/decisions/ADR-091.md`, touching the same five shared files. **Both pull requests report `mergeable_state: clean`, which is the trap**: git computes mergeability against the base and **never against a sibling**, so neither shows a conflict and the second to merge produces an add/add conflict plus two `090` rows. **The renumber to `091` was then ATTEMPTED on this branch and reverted.** `CI-06f` fails outright -- *"ADR-091 is neither present nor reserved (a hole)"* -- at 27 of 29, because gaplessness is asserted over allocated **plus reserved** and a branch that vacates a number reserves nothing. **Taking `091` therefore requires writing a `090` row on 174's behalf, which is out of fence and is exactly [session 164](2026-08-24-session-164.md)'s landmine 8 repeated**: the invented row becomes a duplicate key the moment the sibling's real row lands. **So the merge resolves this or nothing does.**

  - **A RENUMBER'S BLAST RADIUS IS NOT ENUMERABLE BY ANY GATE IN THIS CORPUS, AND THIS SESSION BELIEVED THE OPPOSITE FOR ONE COMMIT.** While `090` was vacant, the reverted experiment failed `CI-06a` with **six** dangling citations, and this log claimed the corpus therefore had a mechanical instrument for the problem. **The real renumber refuted that.** Once [session 174](2026-08-24-session-174.md)'s `ADR-090` occupied the number, all fifteen stale citations in this log and the four in the [STATE](../STATE.md) append **resolved**, to the wrong entry, and `CI-06a` passed at **30 of 30 with every one of them still wrong**. **`CI-06a` catches a link to a MISSING file, never a link to a WRONG one**, and a colliding renumber is exactly the case where the old number is occupied.

  - **SO [ADR-089](../decisions/ADR-089.md)'s INCOMPLETE RENUMBER WAS NEVER A GATE THAT WENT UNRUN.** Its five stale [INFRA](../architecture/INFRA.md) citations pointed at `ADR-088`, **which exists**, so no link check could have flagged them either. **That defect is invisible to every gate here**, which makes it worse than the record has been treating it. The nineteen sites in this session were repaired by grepping the old identifier and judging each one, and **[STATE](../STATE.md) is the file that proves a blind `sed` would have been wrong**: it carries both entries' appends and only four of its five `ADR-090` mentions were this session's. **A renumber is read by a human or it is not read.**

  - **HOW `090` WAS CHOSEN, KEPT FOR THE RECORD.** [ALLOCATION](../decisions/ALLOCATION.md) was read on a `git fetch origin main` taken in this session at `c1acfa7`: `089` is the highest row and nothing claims `090`. **Session 174 was dispatched from the same table in the same wave under the same *"lowest free number"* sentence**, so it is claiming this number too. The brief said to take the lowest free number that is not 174's; **174's number is not knowable from the tree, and `CI-06f` asserts gaplessness over allocated plus reserved**, so reserving `091` and leaving `090` empty fails the gate on this branch rather than avoiding the collision. **Taken and reported**, on the precedent [ADR-089](../decisions/ADR-089.md) records in its own approval section, where sessions 152 and 154 both took `088`. **If 174 lands first this entry renumbers, and the renumber's scope is every document that CITES it** -- the part that went wrong last time.

  - **THE CLAIM ROW FOR `175` WAS PRESENT AT THIS BRANCH'S BASE, WHICH IS SESSION 164's LANDMINE 8 NOT RECURRING.** [`README.md`](README.md):78 carried it at `c1acfa7`, so it is **struck in place** per [ADR-065](../decisions/ADR-065.md) T3 and no row was invented. Session 164 paid a CI cycle for the opposite case; the cheap check it named -- `git fetch origin main` before writing a row rather than after CI reports one -- was run at the start of this session and again before the ADR number was taken.

  - **`0048` IS NOT CLAIMED AND [`packages/db/`](../../packages/db) IS NOT TOUCHED.** ADR-091 rules the **shape** of the superseding migration and writes none of it, which is [ADR-087](../decisions/ADR-087.md)'s own sentence from today. **The temptation here was real and is worth recording**: the remedy is a single `GRANT` statement, it was already executed against a scratch database to prove it works, and copying that one line into `0048_*.sql` would have looked like finishing the job. **It would have been a money-path migration written in the same session that decided it needed to exist**, with no separate `E2` read, which is exactly how a schema acquires rules nobody decided.
