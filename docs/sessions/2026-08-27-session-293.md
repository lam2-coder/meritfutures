### 2. The recommendation was checked before it was taken, and one of the three checks changed what could be built

`OI-06`'s recommendation is [DELTA_MANIFEST](../../packages/db/DELTA_MANIFEST.md)'s own and the dispatch made refusal available. **It is taken, and not out of deference.** Three things had to hold.

**One: the key spans both rails only because an affiliate is an identity.** `C-24` requires affiliate destination changes to carry the same window. `affiliates.identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT` at [`0005:31`](../../packages/db/migrations/0005_affiliate_program.sql), with that file's own comment _"An affiliate is an identity"_, is what makes `(identity_id, destination_ref)` sufficient. Had it been otherwise the recommendation would have needed a discriminator, a second table or a nullable second column, and all three put [ADR-017](../decisions/ADR-017.md)'s _"one rail, one destination table, one detector"_ back to being a convention.

**Two, and this is the one that decided the schema: ONE ROW PER PAIR IS WHAT THE ACCESSOR CAN READ.** The natural reading of _"no table records that a destination changed or when"_ is an event log -- one row per registration, keyed `(identity_id, destination_ref, first_seen_at)` -- and it is a better historical record. **It is also unreadable through the one door.** `G-DESTINATION-COOLING` asks _"is this destination cooling for this identity right now"_, which over an event log is `max(cooling_until)`, and [ADR-157](../decisions/ADR-157.md) **refused the scalar aggregate on the accessor** two slices earlier in this same wave, on grounds this session does not reopen. An append-only registry would therefore have left `P5-h`'s gate outside `scopedDb` and blocked the slice the table exists to unblock, and the only ways out are the reach-arounds [P5 rule 10](../plans/P5-payouts-and-wallet.md) forecloses by name.

**That is the session's finding and it is worth more than the table.** A refusal ruled for one slice's reasons, in a file this session may not touch, determined another slice's DDL -- and it did so **before** the migration was written rather than after it merged. That is the whole return on the one-door design, and it is the first time in this tree that the return is visible as a decision rather than as a cost.

**Three: the two columns are different kinds of fact.** `first_seen_at` is when the destination appeared; `cooling_until` is the window that was applied. Section 4 is why the second is not derived from the first.

### 3. The amendment, and why it is one word rather than a redesign

**The recommendation names `cooling_until` and says nothing about nullability.** Read literally as `timestamptz NULL`, the gate's predicate `cooling_until > now()` is not true for a NULL, so a row missing the value is a destination **usable the instant it exists**. And the row is not a hypothetical: it is the row written when a destination is registered, which is exactly the moment `C-11` exists to slow down. Watched failing under `NOT NULL`:

```
INSERT INTO payout_destinations (identity_id, destination_ref) VALUES (...);
ERROR:  null value in column "cooling_until" of relation "payout_destinations"
        violates not-null constraint
```

**It is [SECURITY](../architecture/SECURITY.md) section 4 item 9's own lesson applied before rather than after.** That item was written about `wallet_withdrawals` carrying `frozen_at`, `freeze_flag_id` and `freeze_expires_at` from `0011` while a halted withdrawal still matched the open index and nothing refused settlement -- _"representable and unenforced, in a shipped control, for the whole life of the table"_, repaired by `0031` twenty migrations later. A nullable `cooling_until` is that shape one table over, and one word now is cheaper than a superseding migration then.

**It also settles the first-destination question, fail-closed, without a second constraint.** `C-11` says a _change_ triggers cooling and a first destination is not a change -- but on an identity that has never withdrawn there is nothing to change from, so a first-destination exemption opens a hole on every account that has not yet used the rail, which at launch is all of them. `NOT NULL` means every row carries a window because no row can be written without one, so _"is this a change?"_ is never a question a handler gets to answer wrongly.

### 4. The one derivable-looking value this table accepts, argued rather than assumed

`0049`'s objection is the right question and its answer comes out the other way here. That header says _"a ratio stored beside its own numerator invites recomputation drift ... a ratio the database computes cannot disagree with its own inputs"_, and bought its way out with a `GENERATED` column.

**A cooling window is not a ratio, it is a promise made at a moment.** The duration is a launch candidate in config ([ADR-037](../decisions/ADR-037.md)), so a derived `cooling_until` would move whenever the config moved: 48 hours to 72 **retroactively re-cools every destination ever registered**, and the reverse retroactively releases the ones cooling right now. Neither is a recomputation of one fact; each is a different fact replacing the stored one. And `0049`'s remedy is structurally unavailable for [session 281](2026-08-27-session-281.md)'s reason on a different table: **a `GENERATED` column is a row-local expression and the duration is not in the row.**

What the database asserts instead is the **ordering**, `payout_destinations_cooling_follows_first_seen`, which is `0029`'s split applied to the destination ceremony: the duration is config's, the fact that there is one is the database's.
