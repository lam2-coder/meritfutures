### 2. The pair, and its two classes disagree because the two tables record different things

[`0004_catalog.sql`](../../packages/db/migrations/0004_catalog.sql) declares `tos_versions` and `tos_acceptances` twenty lines apart. **They take different classes and that is the correct answer rather than an inconsistency**, which is why the dispatch grouped M09 and M16 into one session: reading either without the other is how a version table and its acceptances end up sharing a rule.

| | `tos_versions` | `tos_acceptances` |
|---|---|---|
| What the row is | what the FIRM published | what a PERSON did |
| Identity column | none, and there is no correct one | `identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT` |
| Class | **`firm`** | **`owned`**, NOT NULL |

**`tos_versions` is `plan_versions`' reason applied to the legal catalogue instead of the commercial one.** Every identity is shown the same version, and the link runs the other way: `tos_acceptances.tos_version_id` names the version a person accepted, so ownership flows FROM the published document rather than to it. [M09](../plans/M09-marketing-site.md) section 1.2 draws the same line in the corpus's own words, that the site *"renders versioned legal documents and records nothing about acceptance"*. A public read of `body_md` is not a leak, and a superseded version stays readable forever because the version a trader accepted has to remain quotable (`FM-M9-06`, `INV-M9-11`).

**`tos_acceptances` is `owned` and the `ON DELETE RESTRICT` is the DDL saying so out loud**: an acceptance outlives every convenience, the identity cannot be deleted out from under the signature, and there is no way to write an unowned acceptance. A scoped read returns EVERY version this person ever accepted rather than the current one, which is what `DEP-M16-06` means by keeping acceptance a positive act, and it is the record `FM-M9-06`'s pinned-version argument is settled from.

**A shared class fails in one direction or the other, and both directions were checked before the two rules were written.** Firm for both leaves a person unable to read their own signature and makes an acceptance record that no party owns. Owned for both is worse: `tos_versions` has no identity column, so the rule would have to be `derived` through the acceptances, and a version is accepted by MANY people -- the traversal would be a semi-join returning every published document to everyone who accepted any of them, which is not a scoped read of a public document but a scoped read that happens to return the same rows for a different reason, and it would silently drop every version nobody has accepted yet.

**And the pair carries this file's named trap in its most plausible dress.** `tos_acceptances.tos_version_id` is `uuid NOT NULL REFERENCES tos_versions(id)`, single-valued and declared inline in the `CREATE TABLE` body: it reads exactly like `daily_marks`' hop to `accounts` and it is not one, because the parent is FIRM. `DerivedRule.via` is typed `TableKey` and includes every firm key, so the wrong rule compiles at every call site and throws the first time anybody reads the table. **Seeded, and the bounded chain assertion failed by name** -- see section 6.

### 3. `certificate_verifications` is `firm`, and the hop that would make it otherwise does not exist

[`0025_reserved_sequence.sql`](../../packages/db/migrations/0025_reserved_sequence.sql) gives it seven columns and **not one foreign key**. `GET /verify/:code` is public, unauthenticated and rate limited ([M11](../plans/M11-certificates-social-proof.md) section 6), so whoever produced a row here is an outsider Merit has no identity for and never will.

**The trap is worth naming because `certificates` IS registered and would make a plausible `via`.** The column is `code_hash bytea`, a DIGEST of the attempted code, and 0025's own comment gives the reason: storing the codes in the clear would make this table a list of valid tokens for anyone who reached it. **A hash addresses no row**, `unknown` is one of the four `result` values so most attempts resolve to no certificate at all, and a rule cannot be written through a join the schema refuses to declare.

**The class would still be wrong if the join existed**, and that is the stronger half. The signal this table carries is the RATE of `unknown` across all verifiers, which is an enumeration campaign in progress (`AS-M11-04`, `FM-M11-04`). That is estate-wide security telemetry; a per-certificate slice of it is not a smaller version of it, and handing a holder the list of who looked their card up would publish the verifiers instead of the certificate.

**`bytea` was declared as the custom type this file already carries and never approximated as `text`**, on both `code_hash` and the nullable `ip_hash`. `ip` on `tos_acceptances` is `inet NOT NULL` and is stored in the clear, unlike `ip_hash` here, and the difference is the tables': one is a party's own record of their own act, the other is telemetry about strangers.

### 4. `geo_restrictions` is `firm` on `price_floors`' shape

The primary key is `country_code char(2)` and **the table has no `uuid` of its own**, so there is no surrogate id for anything to point at and no foreign key in the tree points here. A restriction is a statement about a JURISDICTION and is identical for every person in it, which is precisely the property `DEP-M9-04` depends on when it makes this one table the source for checkout enforcement, campaign targeting and the public notice at once. A per-identity slice of a country's rule is not a smaller version of it.

`reason` is counsel's rationale in 0004's own words and `effective_from` is a `date` rather than a timestamp. The row's history is versioned in `events`, which lives in another table and is not a second path to a person here.
