### 3. Why `detector.run_completed` is not a row, which is this session's finding

**THE DISPATCH ASKED FOR TWO ROWS AND THE DOCUMENT SUPPORTS ONE.** Both names were
verified at their line numbers and both spellings were verified before anything was
copied. The difference between them is not effort, it is that one payload can fill
`events`' NOT NULL columns and the other cannot.

| | `flag.raised` (`EVENTS:354`) | `detector.run_completed` (`EVENTS:358`) |
| --- | --- | --- |
| a payload field for `subject_id` (`uuid NOT NULL`) | `flag_id` | **none. the payload declares no `_id` field at all** |
| a payload field for a tenancy leg | `identity_id`, and `account_id?` | **neither** |
| consumers | FEED, ALERT (sev >= 4), EVID | BI, ALERT on failure |
| disposition | **a row in the producer** | **blocked twice over, and both repairs are EVENTS'** |

**THE FIRST BLOCKER IS THE SUBJECT AND IT IS THE ONE THAT MATTERS FOR THIS FENCE.**
`CatalogueRow.subjectField` names the payload field `events.subject_id` is read from, and
`{ detector, detector_version, trading_day, rows_scanned, flags_raised, duration_ms }`
contains nothing that names a row. Choosing a field here would be the producer inventing
what the registry does not carry, which is `ADR-159` clause 1's refusal and is the same
class of move as the omission this session was dispatched to repair.

**THE SECOND IS TENANCY AND IT IS INDEPENDENT.** Given a subject, the row would still be
refused by `assertTenanted`, for `payout.freeze_expiring`'s reason and by its argument. It
is not the same case, though: `payout.freeze_expiring` is a fact about ONE TRADER's frozen
payout whose payload happens to name neither column, which `ADR-191` section 9 calls a
producer defect. A detector run is a fact about the DETECTOR. Its consumers are BI and
ALERT and it carries no `TL`, so it is firm-level by content, and `assertTenanted`'s
message already names the repair for exactly that case: *"where the event genuinely
belongs to the firm rather than to a trader, say so on its row in EVENTS. No row says that
today."* Still no row says it.

**THE SUBSTRATE FOR THE FIRST HALF EXISTS, WHICH MAKES THE AMENDMENT SMALL AND DOES NOT
MAKE IT THIS SESSION'S.** `detector_runs.id` is a `uuid` primary key, and
[`runner.ts`](../../apps/worker/src/detectors/runner.ts) already holds it as `runId` in
the same function that emits the event. So an EVENTS amendment adding `detector_run_id` to
that payload has a real column to point at and a producer already holding the value. It is
still an amendment to a frozen document, so it is an ADR and a report and never a commit.

**AND IT DOES NOT HELP THE OTHER TWO.** `detector.run_degraded` and
`breaker.state_changed` have no EVENTS row at all, which sessions 300 and 320 registered.
What has changed is that the three remaining refusals are now ONE kind of gap rather than
two: every one of them needs `EVENTS` to move first.
