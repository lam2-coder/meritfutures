### 1. The eight rows, and where each one's shape came from

**The dispatch's instruction was to write the row from the CONSTRAINTS rather than from a plan's sentence, on [ADR-113](../decisions/ADR-113.md)'s and [ADR-139](../decisions/ADR-139.md)'s precedent. It paid on six of the eight.**

| Row | Section | The constraint that decided its shape |
|---|---|---|
| `GET /wallet` | `6.2` | `balance_after_cents CHECK (>= 0)`, so no response carries a negative wallet figure. `available_at` is `null` under `chargeback_window` because no landed column carries the window's end |
| `GET /wallet/entries` | `6.2` | `provenance NOT NULL` whose members are the credit list, and `amount_cents CHECK (> 0)` with `direction` carrying the sign. The wire is a union on `direction` and the amount is a magnitude |
| `POST /wallet/withdrawals` | `6.2` | `idempotency_key NOT NULL` under a unique index; `wallet_withdrawals_approved_has_provenance` permitting `'{}'` at `requested`; `wallet_withdrawals_freeze_is_complete` making the halt all-or-nothing |
| `POST /admin/payouts/:id/release` | `8` | `payout_requests_hold_is_complete`, the biconditional. `released_hold` exists because the row cannot keep it |
| `POST /admin/payouts/:id/enforce` | `8` | The same biconditional, plus `payout_requests_account_ordinal_uq` being partial on `status <> 'failed'`, which is why `ordinal_released` is a field |
| `POST /admin/wallet/:identityId/correct` | `8` | `REVOKE UPDATE, DELETE ON wallet_entries`, so "no update path" is a grant. `balance_after_cents >= 0` makes an over-correcting debit `insufficient_funds` |
| `POST /admin/wallet/:identityId/spend-limit` | `8` | The primary key `(identity_id, effective_from)`, which makes the write an APPEND, and `wallet_spend_limits_weekly_exceeds_daily` |
| `GET /admin/wallet/reconciliation` | `8` | The stored `balance_after_cents` as a tamper indicator, which `INV-M20-10` does not name, so the row reports two divergences rather than one |
