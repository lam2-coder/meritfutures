**Objective.** Make the worker deployable actually run its job, so that something
in this system finally evaluates a trader.

**Outcome.** **It runs, and it fails loudly.** The three things the row named all
landed. What it does not yet do is write a `rule_states` row, and the reason is
two named slices with homes outside this fence rather than anything undiscovered.

### 1. The defect, reproduced first-hand before a line changed

The dispatch supplied the measurement and required it to be re-derived. It was
run against `origin/main` at `6e8891c`, in a worktree, rather than taken.

```
$ grep -c "^main();\|^await main();\|void main()" apps/worker/src/index.ts
0

$ pnpm --filter @merit/worker start
> @merit/worker@0.0.0 start .../apps/worker
> node --experimental-strip-types src/index.ts

BASELINE_EXIT=0
```

The same command on this branch exits **1**.

**The row understated nothing and the dispatcher's independent derivation was
right in both halves.** `package.json` started the deployable on `src/index.ts`,
which is the package's `exports` target; that module declared
`export function main(): void` whose body was a `console.log` listing everything
the module does not do; and nothing called it.

### 3. The trap, met head on

**"A JOB THAT CANNOT FAIL LOUDLY IS THE DEFECT YOU ARE FIXING, IN A NEW
COSTUME."** The row said so and it was the easiest thing in this session to get
wrong, because every instinct on a job that can fail is to wrap it.

**The answer is that nothing between `runNightlyBatch` and the process catches**,
and the answer to "how would anybody know" is that a test spawns a process and
reads its status:

| case | status |
|---|---|
| the real entry point, `DATABASE_URL` unset | **non-zero**, stderr names `DATABASE_URL` |
| a job that cannot resolve its day | **non-zero**, `WorkerJobRefusal` |
| **a port that refuses mid-batch** | **non-zero**, `BatchPortUnwired`, `loadAccountDay` |
| a completed run over an empty book | **0**, and it prints its report |

**SEEDED AND WATCHED, ON THE REAL TREE, EACH RESTORED BEFORE THE NEXT.**

| seed | what went red |
|---|---|
| a `catch` in `start.ts` that logs and falls through | **1.2 and 2.1**, the textual check and the spawned process |
| `package.json` `start` pointed back at the barrel | 1.1 |
| `loadAccountDay` returning a plausible `null` instead of refusing | 2.3 |

**The first seed is the trap itself and it is caught twice**, which is the point:
the textual check would survive a rename of the entry point and the spawned
process would survive a rewording of the comment, and neither survives on its
own.

**AND THE SUITE ALREADY CARRIED THE DEFECT AS A GREEN TEST.**
`test/service.test.ts` read `expect(() => main()).not.toThrow()` under the name
*"the deployable starts"*. It passed every day of the period in which the
deployable started and did nothing. It is replaced rather than repaired, and the
replacement asserts the concurrency ruling instead.

### 4. The schedule, ruled

**EXTERNAL. One process per run.** The argument is in
[ADR-241](../decisions/ADR-241.md) section 3 and it is one sentence long: **a
long-lived process has no exit code to fail with.** This whole session exists
because a status of 0 from a process that did nothing is unreadable, and an
in-process timer makes every future run unreadable the same way, because the
only status such a process leaves is the status of its last moment.

The second reason is that the register already works this way: every dead-man
switch in `CRON_INVENTORY` is phrased as the ABSENCE of a completion signal by an
expected-by time, and that phrasing presumes discrete runs with discrete
completions.

**What is NOT ruled is the setting.** Which scheduler and which cron expression
are deployment facts, in this repository's own sense ([ADR-012](../decisions/ADR-012.md)),
exactly as a `DATABASE_URL` is.

### 5. The adapter, and what it refuses

| served | refusing |
|---|---|
| `calendarWatermark`, `calendarSlice`, `accountsWithLiveMark`, `accountsWithStoredState` | `loadAccountDay`, `accountDaysFrom`, `storedRuleStates`, `raiseReconciliation`, `raiseDivergence`, and the encoder leg of `writeRuleState` |

**Four of ten is the house shape and not a shortcut.** `databaseAccountReads`
serves one of four and `databaseAuthBackend` four of sixteen, and the reason is
the same everywhere: a fixture serving real traffic is worse than a refusal.
Here it is worse than that, because `runNightlyBatch` counts a `written` outcome
per account that did not throw, so a port returning a plausible value produces a
report saying the book gained rows on a night it gained none.

**THE CODEC WAS NOT WRITTEN AND THAT IS THE ONE DECISION IN THIS SESSION MOST
LIKELY TO READ AS A GAP.** [ADR-239](../decisions/ADR-239.md) slice A homes the
`engine_gates` codec in `packages/rules-engine`, because `readLiability` in
`apps/api` needs the same decoder and cannot import `apps/worker`, and an encoder
in one place with a decoder in another is `FM-16`. That package is not in row
`241`'s fence. **Writing it here would have been widening a fence to finish**,
which the settled rulings put beside weakening a gate to pass it.

**Two properties of the calendar read are decisions rather than transcription**
and are argued at their own site: a holiday is inside `coverage` and is not in
`days`, and `sequence` is dense over sessions rather than over calendar rows.

### 6. Citation repair, using the rights the row granted

Four sites in `apps/api` asserted the defect as a live fact and would have gone
red or, worse, stayed green while saying something false.

| site | what went false |
|---|---|
| `test/rule-state-producibility.test.ts` link 1 | named "no scheduler, and the worker deployable starts, runs nothing and exits 0" |
| the same file's link 2 | named "no `BatchPorts` value is constructed under any `src/`", and its needle could not see the one that now is |
| `test/wiring.test.ts`, `usePayoutBackend` | led with an unscheduled job |
| `src/routes/account-reads.ts`, `ELIGIBILITY_BLOCKER` clause 1 | said no adapter implements `BatchPorts` and the batch is exported without being scheduled |

**LANDMINE, MET AND RECORDED.** The first repair of the `usePayoutBackend` entry
QUOTED its own retired sentence, and the predicate asserting that sentence is
gone matched the quotation. **A reason that reproduces its own retired wording
reads as live to every grep and to the check that says it is dead.** The wording
is paraphrased instead, which is the same move `rule-state-producibility.test.ts`
already makes by assembling its needle from two string literals.

**Link 2's needle was widened as well as repointed.** It matched
`': BatchPorts = '`, which finds a value assigned to an annotated const and does
not find one returned from an annotated function. Both spellings are swept now,
so a second constructor in either shape is a named failure.

### 9. Next, and blockers

**Next.** ADR-241 section 6 sizes three slices and none is claimed.

1. **The `engine_gates` codec**, in `packages/rules-engine`, both directions. It
   clears `storedRuleStates`, the write port's last leg and `readLiability` at
   once. Unchanged from ADR-239 and now the cheapest thing standing between this
   deployment and a written row.
2. **The `AccountDay` loader.** The largest, and **it should be planned before it
   is written**: two of its six fields are readings no primary source in this
   tree states end to end, so a session that writes it without ruling them first
   will invent them.
3. **The event sink**, and the manifest line that lets this deployable reach a
   writer.

**Blockers.** None for this row. The two above are fences rather than unknowns.

**Landmines for whoever holds this next.**

- **A `catch` anywhere between `runNightlyBatch` and the process undoes this
  session**, and `test/entrypoint.test.ts` case 1.2 is the thing that says so.
- **`apps/worker/src/index.ts` may not import `./db.ts`.** `digests.test.ts` case
  9.2 reads every `from './...'` clause in the barrel and requires each to be a
  declared leg, so the live default for `main`'s io lives in `job.ts` and not in
  the barrel.
- **`breaker.test.ts`'s leg count cannot see a top-level module.** Section 7.
- **The adapter reads whole tables** because the three `FilterTerm` constructors
  live in `@merit/db`, which only `src/db.ts` may name here. It is right for the
  calendar and wrong for `accountsWithStoredState`, which is stated at its own
  site and which nothing calls yet.
