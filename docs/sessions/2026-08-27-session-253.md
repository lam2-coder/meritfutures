It is bounded in practice by the account cap and by nothing the database enforces, and it is a performance ruling owed to a later slice rather than a tenancy hazard. **The response is composed from TWO transactions**, and it survives that on `plans.code` and `plan_versions.version` only because `0028`'s published-row guard pins them; a later crossing on `status` or `retired_at` -- the two columns that guard deliberately leaves movable -- inherits none of that argument. **`renderPlans` throws rather than dropping a plan** whose `code` is outside the contract's closed set, and `plans.code` carries no CHECK, so seeding a fourth plan code takes the pricing page down loudly. ### 1. The three routes, and the one thing that made them non-trivial

| Route | Auth | Door | Why it is that door |
|---|---|---|---|
| `GET /plans` | none | `firmDb()` | The catalogue belongs to nobody. `scope.ts` on `plans`: *"the link runs the other way ... ownership flows FROM the catalogue rather than to it"* |
| `GET /plans/:planId/versions/:version` | none | `firmDb()` | Same, and it serves RETIRED versions on purpose, which is section 4's own stated reason: *"so a trader can always retrieve the contract they bought"* |
| `GET /purchases` | session | `scopedDb(identityId)` **then** `firmDb()` | `purchases` is `owned` on `identity_id`; `plan: { plan_id, code, version }` is three catalogue facts a purchase row does not carry |

**The two public reads are BARE handlers rather than `EndpointSpec`s, and that is a finding rather than a style choice.** `endpointHandler` reads the session cookie and calls `sessionByToken` BEFORE it consults the declared factor, so a route declared `required: 'none'` still resolves a session whenever a request happens to carry a cookie. On the most cacheable public path in the contract that buys nothing and costs an auth transaction per request plus a `503` for a stale cookie whenever the auth backend is unwired. [`public-methods.ts`](../../apps/api/src/routes/public-methods.ts) is the precedent and [ADR-141](../decisions/ADR-141.md) clause 4 of section 5 makes it the rule for the class.

### 2. The correction this session made to its own work, recorded because it is the useful part

The route file's header, as first written, said this about the crossing:

> *"The reverse direction ... is an estate-wide read wearing a trader surface, and NOTHING IN THE TYPE SYSTEM REFUSES IT."*

**It was measured before the commit and it is wrong.** Replacing `db.scoped(identityId, ...)` with `db.firm(...)`:

```
src/routes/catalog.ts(1341,37): error TS2345: Argument of type '"purchases"'
  is not assignable to parameter of type 'FirmTableKey'.
src/routes/catalog.ts(1342,36): error TS2345: Argument of type '"accounts"'
  is not assignable to parameter of type 'FirmTableKey'.
```

That is [ADR-106](../decisions/ADR-106.md) clause 3's key-type partition holding at a call site in a different package, which is exactly what ADR-106 section 9 case H measured for `pair` tables and never had an `owned` instance of.

**The header now carries the error text and states the narrower thing that is actually left**: which identity the scoped door is opened with (`scoped` takes a `string`, so a session field and a path parameter are the same type, and the control is that there is one call site), and whether the firm read was keyed by the scoped result (both reads are legal alone; `plansOfVersions(ids)` takes the ids as a parameter so the wrong side has nowhere to put a filter).

**A header that overstates a hazard is the same defect class as one that understates it**, because the next reader budgets against it. This is the tree's own rule about checking a claim against the primary source, applied to a claim this session wrote.

### 3. The hunt the dispatch pointed at, and its negative result

The dispatch said: *"`firmDb()` takes no reason, on the claim that a `firm` row endangers nobody. That claim is exactly as true as the `firm` classification is, and `ADR-102` section 7 records a live blind spot in the only thing that checks it. If a `plans` read looks like it is returning something identity-specific, that is a finding worth more than the route."*

**The citation is correct and the hunt came back negative.** [ADR-102](../decisions/ADR-102.md) section 7 records that the assertion *"no firm table carries a column referencing identities"* reads the `CREATE TABLE` body and misses a column added later by `ALTER`. `plan_versions` has three such columns:

| Column | Migration | Reaches |
|---|---|---|
| `fee_back_repeats` | `0044` | a boolean, locked to `false` by its own CHECK |
| `decided_on_simulation_run_id` | `0045` | `simulation_runs`, which is itself `firm` |
| `simulation_waiver_reason` | `0045` | free text |

**None reaches `identities`**, so the classification is correct and correct for a reason the blind check happens not to cover.

**WHAT IS THERE IS SMALLER AND POINTS THE SAME WAY.** `simulation_waiver_reason` is text an operator wrote about MERIT'S OWN publish decision, sitting on a table `GET /plans/:planId/versions/:version` serves to anybody with a socket. It is firm-internal rather than identity-shaped, so **no scope class would ever have withheld it** -- and [ADR-106](../decisions/ADR-106.md) section 4 says why in advance: *"a scoped read is a FILTER and not a PROJECTION"*. The only control is [API_CONTRACT section 1](../architecture/API_CONTRACT.md)'s allowlist, which `renderPlanVersion` is. Seeded with real operator text in the live fixture and asserted absent from the response.

### 4. Verification, including the half a recorder cannot do

`db-recorder.ts` says of itself that it proves *"which door was opened, whose identity was handed to it"* and **nothing** about whether a composed predicate reaches one row or many, because a case claiming that *"would be agreeing with its own fake"*. That rule was kept, and the other half was obtained rather than skipped.

**A PostgreSQL 16 cluster was created, all 47 migrations applied in order, and a two-identity fixture seeded**: two `identities`, two `users`, three `plans` (one delisted), three `plan_versions` (one retired, two on sale), four `plan_version_sizes`, three `purchases` split across the two identities, two `accounts`, and two `sessions` rows carrying real `sha256` digests of real tokens. `apps/api` was then started against it with `MERIT_API_SURFACE=public PORT=8899` and hit over a socket.

| Check | Result |
|---|---|
| `GET /plans` | `200`. Two plans, ordered by `sort_order`; the delisted `direct` plan absent; `payout_cap_cents` and `min_payout_cents` derived correctly per size |
| `GET /plans/.../versions/1` (RETIRED) | `200`, `status: "retired"`, with `retired_at` |
| The allowlist against real rows | `simulation_waiver_reason`, `public_slug`, `created_by` and `decided_on_simulation_run_id`: **zero occurrences** in the response body |
| `GET /purchases` as A | A's two rows, newest first, `account_id` resolved. **Zero of B's** |
| `GET /purchases` as B | B's one row. **Zero of A's.** Both directions, because a read that refused everything passes the first half alone |
| Cursor, `limit=1` | Page 1, then page 2 from `next_cursor`, then `next_cursor: null`. No repeat, no skip |
| **B replays A's cursor** | **B's own row only.** The cursor is opaque rather than secret: it seeks into a set the accessor had already narrowed |
| Bad cursor / `limit=101` | `400 validation_failed`, `errors[]` naming the path |

**Before the database was seeded, the same process was started without `DATABASE_URL`**, and the resulting `500` is worth keeping because of what its stack proves:

```

  at transaction  (packages/db/src/scoped-db.ts:1392)
  at Object.firm  (apps/api/src/db.ts:143)

```

`GET /plans` reaches the database through `db.ts`'s **firm** door and through nothing else, in a running process rather than in a test.

### 5. Three of the dispatch's citations did not reproduce

Recorded in full in [ADR-141](../decisions/ADR-141.md) section 9. In short:

1. **`GET /plans/:plan` is not a contract row.** [API_CONTRACT](../architecture/API_CONTRACT.md) spells it `GET /plans/:planId/versions/:version`, and both segments are load bearing because `(plan_id, version)` is the pair that addresses one version. The contract's spelling landed and the [ALLOCATION](../decisions/ALLOCATION.md) row is corrected.
2. **"names 53, implements 20" reproduces as neither.** A repeatable count of `###`/`####` headings with comma lists split gives **52**, plus five more named in sections 9 and 10's tables. `discoverRouteModules()` composed **23** before this branch, printed by the process's own startup line, and **26** after.
3. **THE FENCE'S REGISTRY WARNING IS WRONG FOR THIS TREE, AND THAT IS A RULING RATHER THAN AN ACCIDENT.** The dispatch said the route registry would conflict and to keep both sides of an append. [ADR-100](../decisions/ADR-100.md)'s registry IS the directory listing: `discoverRouteModules` reads `src/routes/`, there is no array and no path roster, and [`registry.ts`](../../apps/api/src/registry.ts)'s own header explains that a hand-written array *"makes the file it lives in a write collision for every slice that adds a route"*. **Seven concurrent route slices collide on nothing.** Registration here was creating one file.

### 6. The one thing taken outside the letter of the fence

The fence read *"`catalog.ts` (new) + registration + `catalog.test.ts`"*, and registration in this registry is the file existing. **One line was appended to [`start.ts`](../../apps/api/src/start.ts)**, beside the identical line [ADR-120](../decisions/ADR-120.md) added for the auth backend, because that file is the deployable's declared wiring slice by its own header and without it three complete routes answer `503` in every deployment.

**It is named rather than buried, and it is the file the other seven route sessions may also append to.** An append ordered beside its neighbour is what that costs, and it is a smaller cost than the registry conflict the dispatch predicted and this registry cannot have.
