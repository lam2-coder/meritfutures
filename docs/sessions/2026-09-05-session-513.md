### 5. The ruling, in one paragraph

**The schema is what was wrong.** `provenance` is what value is MADE of; a withdrawal is composed FIFO out of many credits, so a debit consumes a MIXTURE and a scalar column cannot hold one. The corpus already carries the plural answer on the other table. [`EVENTS.md`](../architecture/EVENTS.md) is therefore upheld and **not edited**, though the fence permitted it.

**The one thing the dispatch had wrong is the thing that shaped the migration.** Its framing was *"three values that are all credits"*. Two of them are. `correction` is not: [`0011:64`](../../packages/db/migrations/0011_wallet.sql) defines it as *"a compensating entry, never an update"*, which says nothing about direction, and `0038` merged a constraint trigger that REQUIRES it on a wallet debit. So the constraint is not the biconditional the row's own suggestion implies. It is:

```sql
CASE direction
  WHEN 'credit' THEN provenance IS NOT NULL
  WHEN 'debit'  THEN provenance IS NULL OR provenance = 'correction'
  ELSE false
END
```

`0011`'s CHECK is left in place and carries the vocabulary; this one carries the direction rule and names one literal.
