### 2. The blind spot, which is bigger than the record and smaller than it looks

**`CI-06i` requires a `### <table>` design record for every `CREATE TABLE` and a `CREATE TABLE` for every design record. It never compares the two records' columns**, and its own header gives the reason: *"Column-level drift is caught by the generated diff against a live catalogue, which needs a database."*

**That premise is false for existence and true for type.** The migrations declare the column set in the tree, forward-only from empty, and `grep -rn 'DROP COLUMN\|RENAME COLUMN' packages/db/migrations/*.sql` returns nothing, so an accumulating catalogue **is** the schema. `CI-06j` already builds that catalogue for trigger bodies and `CI-06l` already spends it on `*_expires_at`. **The catalogue that answers this question existed and nothing asked it this question.**

**The reconciliation was run before the repair was claimed complete, which is what the brief asked for and is the reason this section exists.** Four design records disagreed with their schema at the moment of measurement. One was `admin_actions`.

| [`contact_channels`](../architecture/data-model/contact_channels.md) | missing `complained_at` | [`0041`](../../packages/db/migrations/0041_contact_channel_complaints.sql):87. **Open, outside this fence** |

**The other direction produced exactly one hit and it is a false one, which is the finding that shaped the check.** [`kyc_verifications`](../architecture/data-model/kyc_verifications.md) keeps a struck-through row for `dedupe_matched_identity_id` reading *"never created, by [ADR-029](../decisions/ADR-029.md)"*. **That row is the record earning its keep**: it answers the reader who arrives holding the approved design and goes looking for the column. A parse that counted it as a claim would have reported the best design record in the corpus as one of the worst, so **a struck-through row is a tombstone and not a claim**, and a tombstone the schema contradicts is its own finding. [ADR-134](../decisions/ADR-134.md) clause 2.

**In all four cases the RECORD was wrong and the SCHEMA was right. No migration is owed and none was written**, which is the outcome the brief reserved a hand-off for.

### 3. Why the check is not registered, stated as a decision rather than discovered later

**Three records fail it and all three are outside this fence.** Registering it would put `pnpm run verify` at non-zero, and the only remedy reachable from inside this fence would be to narrow the check until it passed. **Working agreements section 9: never weaken a gate to pass it.** So it landed at full strength and outside the runner, with the registration condition written into [ADR-134](../decisions/ADR-134.md) clause 3 rather than left to a future reader's judgement.

**The id is a slug and not a letter**, so no letter allocation and no `STRATEGY` section 4.4 row is owed. `CI-06p`'s own `covers` line states that it *"does not require an implemented gate to HAVE a STRATEGY row"*, so registration moves an `import`, one `GATES` entry and one `SEEDS` entry, and nothing else.

### 4. Findings reported rather than resolved quietly

1. **The three sibling records are named and NOT numbered.** This fence carries the `OI-15` row in [DELTA_MANIFEST section 16](../../packages/db/DELTA_MANIFEST.md) and that row is closed here; it does not carry the right to MINT `OI-nn` rows for three findings nobody dispatched, and an identifier claimed from outside a fence is the collision [ADR-034](../decisions/ADR-034.md) exists to end. They are in the pull request body for the dispatcher.
2. **[`gates.mjs`](../../scripts/corpus/gates.mjs) is not importable.** It ends in `process.exit(main())` at module scope with no direct-invocation guard, unlike [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs). **That is why the new file parses the migrations a second time**, against `OQ-P1-04`'s one-parser ruling. The duplication fails in the safe direction (a narrower parse yields a loud false finding, never a silent pass) and the remedy is to delete the copy at registration, since a gate inside `gates.mjs` reaches `columnCatalogue()` directly. Adding the guard was refused here: it is a behavioural edit to a file sessions **243** and **244** are both live in.
3. **The check went into `scripts/corpus/` and not `packages/tooling/checks/`, and that was decided rather than defaulted.** `repo-invariants.mjs` states its own boundary, *"these do not check the corpus"*, and a design-record reconciliation is plainly corpus. **The mechanical half of that argument is that its test fixture would refuse the check anyway**: [`repo-invariants.test.ts`](../../packages/tooling/test/repo-invariants.test.ts)'s `cleanTree()` builds a synthetic tree with no `docs/` and no `packages/db/migrations`, and asserts *every* member of `CHECKS` holds against it, so an `RI-11` reading either directory would ERROR there and the repair would be an edit to a file outside this fence.
4. **The `admin_actions` index row in [DATA_MODEL](../architecture/data-model/README.md) was a bare link**, as most rows below `0040` still are. It now carries the one-line description the rows added since `0040` carry. **The other bare rows are left alone**: that is a wave of its own and not a repair to slip into this one.
