#### 3. THE HEADLINE FINDING, WHICH TWO EARLIER SESSIONS HANDED TO THIS ONE AND WHICH THIS FENCE CANNOT CLOSE

[Session 216](2026-08-25-session-216.md) reported that **"only `SystemTx` can write a two-party posting and a checkout handler is neither of its two reasons"** and named it as blocking session 220. **[ADR-112](../decisions/ADR-112.md) DID NOT CLOSE THIS AND SAYS SO.** Its section 10 lists what it does not decide and `SystemReason` is on that list: *"`sqlExecutor`'s vocabulary does not move"*, and the ruling that gave the accessor an address deliberately left the AUTHORITY question where ADR-102 section 7 left it. So the wall the dispatch calls gone is gone **for addressing a row** and is standing **for a request handler reaching a two-party table**.

**THIS SLICE DOES NOT RESOLVE IT AND DOES NOT NEED TO, BECAUSE THE SEAM IS A PORT.** `apps/api` declares no `@merit/db` ([`apps/api/package.json`](../../apps/api/package.json), and [ADR-112](../decisions/ADR-112.md) section 10 restates it), so `checkout.ts` cannot import the accessor at all under this fence. It therefore declares a `CheckoutTx` port, exactly as [`routes/webhooks-psp.ts`](../../apps/api/src/routes/webhooks-psp.ts) declares `PspWebhookTx` and [`routes/auth.ts`](../../apps/api/src/routes/auth.ts) declares `AuthBackend`. **The wiring session that binds that port to a real handle is the one that meets this wall**, and it is reported in ADR-113, in `STATE` and in the pull-request body rather than resolved quietly.

#### 4. `IdempotencyStore` IS THE NEXT SESSION'S, AND THE REASON IS THE FENCE RATHER THAN A PREFERENCE

The dispatch asks this session to decide and to say which. **It is the next session's.**

[ADR-109](../decisions/ADR-109.md) clause 3 left `IdempotencyStore` a port because nothing could stamp one row, and [ADR-112](../decisions/ADR-112.md) removed that obstacle. What it did not remove is that an implementation of that interface must import `@merit/db`, and `idempotency.ts` lives in `apps/api`, whose manifest declares no such dependency and **is not in this fence**. Adding `@merit/db` to `apps/api` is an authority change on the deployable that serves the whole public surface, and it drags in the `pair`-table question in section 3 the moment the first caller writes `attributions`. **A one-line manifest edit that makes the API deployable able to reach a pool is not a side effect of a checkout slice.**

So `ADR-109` clause 3's claim stands unchanged after this session and the pull-request body says so.
