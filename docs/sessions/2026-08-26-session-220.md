#### 3. THE HEADLINE FINDING, WHICH TWO EARLIER SESSIONS HANDED TO THIS ONE AND WHICH THIS FENCE CANNOT CLOSE

[Session 216](2026-08-25-session-216.md) reported that **"only `SystemTx` can write a two-party posting and a checkout handler is neither of its two reasons"** and named it as blocking session 220. [Session 215](2026-08-25-session-215.md) attached a second table to the same shape: **"A `pair` TABLE IS UNREACHABLE TO EVERY `apps/api` REQUEST HANDLER ... and `attributions` is written inside checkout, so it is session 220's problem in a concrete shape."**

Re-derived at source this session rather than accepted:

| # | Claim | Verified at |
|---|---|---|
| 1 | `attributions` is class **`pair`** on `buyer_identity_id` and `affiliate_identity_id` | [`scope.ts:1067`](../../packages/db/src/scope.ts) |
| 2 | A `pair` key is in **neither** `ScopedTableKey` nor `FirmTableKey`, so `scopedDb` and `firmDb` both refuse it at `tsc` | [`scope.ts`](../../packages/db/src/scope.ts)'s `PairRule` docblock, [ADR-106](../decisions/ADR-106.md) |
| 3 | The only remaining door is `systemDb(reason)`, whose vocabulary is **`'nightly-batch' \| 'operator-console'`** | [`scoped-db.ts:176`](../../packages/db/src/scoped-db.ts) |
| 4 | A checkout request handler is neither | The dispatch's own framing, and [`idempotency.ts`](../../apps/api/src/idempotency.ts)'s header states it about the same two reasons |

**[ADR-112](../decisions/ADR-112.md) DID NOT CLOSE THIS AND SAYS SO.** Its section 10 lists what it does not decide and `SystemReason` is on that list: *"`sqlExecutor`'s vocabulary does not move"*, and the ruling that gave the accessor an address deliberately left the AUTHORITY question where ADR-102 section 7 left it. So the wall the dispatch calls gone is gone **for addressing a row** and is standing **for a request handler reaching a two-party table**.

**THIS SLICE DOES NOT RESOLVE IT AND DOES NOT NEED TO, BECAUSE THE SEAM IS A PORT.** `apps/api` declares no `@merit/db` ([`apps/api/package.json`](../../apps/api/package.json), and [ADR-112](../decisions/ADR-112.md) section 10 restates it), so `checkout.ts` cannot import the accessor at all under this fence. It therefore declares a `CheckoutTx` port, exactly as [`routes/webhooks-psp.ts`](../../apps/api/src/routes/webhooks-psp.ts) declares `PspWebhookTx` and [`routes/auth.ts`](../../apps/api/src/routes/auth.ts) declares `AuthBackend`. **The wiring session that binds that port to a real handle is the one that meets this wall**, and it is reported in ADR-113, in `STATE` and in the pull-request body rather than resolved quietly.

#### 4. `IdempotencyStore` IS THE NEXT SESSION'S, AND THE REASON IS THE FENCE RATHER THAN A PREFERENCE

The dispatch asks this session to decide and to say which. **It is the next session's.**

[ADR-109](../decisions/ADR-109.md) clause 3 left `IdempotencyStore` a port because nothing could stamp one row, and [ADR-112](../decisions/ADR-112.md) removed that obstacle. What it did not remove is that an implementation of that interface must import `@merit/db`, and `idempotency.ts` lives in `apps/api`, whose manifest declares no such dependency and **is not in this fence**. Adding `@merit/db` to `apps/api` is an authority change on the deployable that serves the whole public surface, and it drags in the `pair`-table question in section 3 the moment the first caller writes `attributions`. **A one-line manifest edit that makes the API deployable able to reach a pool is not a side effect of a checkout slice.**

So `ADR-109` clause 3's claim stands unchanged after this session and the pull-request body says so.

#### 6. The approval line, unsigned, one checkable clause

> **A checkout whose attribution write fails leaves NO purchase row**, watched by seeding a failure in the attribution fold and asserting the purchase absent, **and a checkout carrying a client-supplied price is charged the server's price**, watched in both directions: the tampered price is refused and the honest path produces the price the server computed.

**Cost if wrong:** an affiliate's referral is lost while the purchase stands, or a customer sets their own price.
