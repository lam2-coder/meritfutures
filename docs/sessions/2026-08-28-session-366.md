**Objective.** Compose a writer for the event sink, so that emitting an event writes a row instead of rejecting.

**Done:** two commits.

1. **The writer**, [`events.ts`](../../apps/api/src/events.ts)'s `TRANSACTION_EVENT_WRITER`, `EventInsertTx`, `EVENT_WRITE_TABLE` and the brand guard, plus eleven cases.
2. **The serialisation refusal**, `assertSerialisablePayload`, plus nine cases and the header paragraph recording what the live write found.
3. [STATE](../STATE.md) append, this log and its generated `README` row.

**Next:** the sink has no INSTALL and nothing to install it into. `apps/api` holds no
handle that can carry an event; `apps/worker` holds the seven producers and a `SystemTx`
door, and its three event ports are unwired. The money payload needs a ruling on EVENTS
before three of the eight names can ever be written.

**Blockers:** one ruling reported and left, per the dispatch. See section 5.

**Landmines:**

1. **A ROW WRITTEN THROUGH `systemDb('nightly-batch')` IS ATTRIBUTED TO THE NIGHTLY BATCH
   IN NOTHING BUT THE READER'S HEAD.** `events` carries `actor_kind` and `actor_id` from
   the producer and nothing from the handle, so the reason the transaction was opened at
   is invisible in the row. That is correct and it means the door's vocabulary is not an
   audit trail.
2. **THE BRAND GUARD IS A VALUE COMPARISON ACROSS A PACKAGE BOUNDARY.** If `packages/db`
   renamed its brands, every handle would be refused at run time. The suite binds all

### 2. Where the writer is composed, and why it is not `db.ts`

**IT TAKES NO HANDLE, WHICH IS THE WHOLE OF THE ARGUMENT.** `db.ts`'s header claims to be
*"THE ONE FILE IN THIS DEPLOYABLE THAT NAMES `@merit/db`"* and then corrects itself in its
own next paragraph: the property that is actually true and actually checked is that **one
file TAKES A HANDLE from it**, and [`db.test.ts`](../../apps/api/test/db.test.ts) asserts
exactly that over `src/` alone, naming `firmDb`, `scopedDb`, `systemDb` and `transaction`.
`TRANSACTION_EVENT_WRITER` calls none of them. It receives a transaction the caller
already opened.

**SO IT FOLLOWS `admin-source/events.ts` AND NOT THE DOOR FILE.** That module declares
`EVENT_READ_TABLES = ['accounts', 'events'] as const` and an `EventsTx` naming only the
methods it uses, holds no import of `@merit/db`, and its suite binds both halves where the
package is reachable. The writer is that shape inverted: `EVENT_WRITE_TABLE = 'events'`,
an `EventInsertTx` naming only `insert`, and
[`events.test.ts`](../../apps/api/test/events.test.ts) holding the one import
`src/events.ts` cannot.

**THE FOUR ADMIN READ ADAPTERS' SHAPE WAS THE OTHER CANDIDATE AND IT DOES NOT FIT.** Those
are `(tx, query) => Promise<result>` free functions serving `AdminReadSource`, installed
through a setter. A writer serves `EventWriter`, which `makeEventSink` already takes as a
constructor parameter, so there is nothing for a setter to do.

| Candidate | Why not |
| --- | --- |
| `src/db.ts` | It is the file that ACQUIRES handles. A writer acquires none, and putting it there would suggest this deployable can open the door it needs |
| a new `src/event-writer.ts` | One exported const and one guard, and the port it fills is twenty lines above it |
| `src/admin-source/` | That directory serves `AdminReadSource` and is session 363's fence besides |
| **`src/events.ts`** | **Taken.** Beside the port, beside the composition, and the file still imports nothing |

### 3. The door is narrower than the read, and that is the finding

**ADR-191 CLAUSE 5 MADE `events` READABLE FROM THE SCOPED HANDLE AND DID NOT MAKE IT
WRITABLE FROM ONE.** `ScopedTableKey` is what `rows` and `rowsWhere` are generic over.
`insert` is a different generic on every handle, and the three were read out of
[`scoped-db.ts`](../../packages/db/src/scoped-db.ts) rather than assumed.

| Handle | `insert` is generic over | Reaches `events`? |
| --- | --- | --- |
| `ScopedTx` | `OwnedTableKey` | **no.** `events` is `either` |
| `FirmTx` | `FirmTableKey` | **no.** `events` is not firm |
| `SystemTx` | `TableKey` | **yes** |

**THE REASON IS NOT AN OVERSIGHT.** A scoped insert STAMPS the tenancy column from the
handle, and an `either` row has TWO tenancy columns and may carry neither, so there is
nothing to stamp. `insertUnder` is not a fourth door and was checked rather than assumed:
`ParentedTableKey` is `Extract<DerivedTableKey, 'sessions'>`, and `insertUnderStatement`
refuses a non-`derived` class in words that name this one, *"an either row has one
[parent] through a NULLABLE edge, so proving it establishes tenancy for the rows that have
a parent and nothing about the rows that reach an identity the other way"*.

**SO `apps/api` CANNOT RECORD AN EVENT AT ALL.** `ApiDb` opens `scoped` and `firm` and
there is no third door, deliberately: `SystemReason` is `'nightly-batch' |
'operator-console'`, a request handler is neither, and ADR-165 refused to widen it. **That
is reported and not worked around.** No `SystemReason` member was added, no door was
opened, and the writer's refusal names the door rather than the payload.

**THE GUARD IS A BRAND CHECK AND NOT A SHAPE CHECK.** All three handles carry
`insert(key, values)` at run time and the difference between them is a type parameter that
is gone by the time a value arrives. A duck-typed guard therefore ADMITS a `ScopedTx`,
and `refuseTenancyColumn` then throws *"`identityId` is events' tenancy column ... and a
scoped write never takes it from the caller"* at somebody who was never permitted a scoped
write, so the reader repairs the payload instead of the door. **An unbranded object is
refused too**, rather than admitted as not `packages/db`'s to judge: a sink is installed
once per deployment and the thing behind it is an append-only money record.

### 5. The money payload no `jsonb` column can take, which is the ruling this entry reports and leaves

**TWO RULES, EACH CORRECT, WHOSE CONJUNCTION IS EMPTY.**

| | |
| --- | --- |
| `events.payload` is `jsonb` | [`schema.ts`](../../packages/db/src/schema.ts), `payload: jsonb('payload').notNull()` |
| drizzle's jsonb driver mapping | `JSON.stringify(value)` |
| `JSON.stringify` on a `bigint` | `TypeError: Do not know how to serialize a BigInt` |
| `assertPayloadRules` on a `_cents` that is not a `bigint` | **refuses**, because `Cents` is `bigint` and a `number` reaching here may already have lost digits |

**SO EVERY `_cents` VALUE IS REFUSED BY ONE RULE OR THE OTHER, AND 33 OF THE 102 READABLE
CATALOGUE ROWS CARRY A `_cents` FIELD.**

**NO SUITE COULD SEE IT AND THAT IS THE INTERESTING HALF.** Every writer double in this
repository is a function that records what it was handed. None of them serialises. The
producer, its eight fixtures and its hundred-odd cases were green over a payload the
storage layer cannot take, and the only thing that found it was writing a row.

**THE REPAIR IS A RULING AND IT IS NOT THIS FENCE'S.** What a `_cents` value IS inside a
`jsonb` payload is [EVENTS](../architecture/EVENTS.md)' to say, and that document is
frozen, so it moves by an ADR and not by a commit. A JSON number loses digits above 2^53,
which is the constitution's no-floats rule arriving in a financial path. A JSON string is
exact but is a wire format no document states and every consumer would have to know.
**Neither is invented here**, on ADR-159 clause 1's rule that a format in a
forever-retained column is not a producer's to choose.

**WHAT WAS DONE INSTEAD.** `assertSerialisablePayload` refuses the payload at the writer,
names the field by path, and states the question. It **breaks no caller**: all three names
already failed at the driver, so this changes the message and not the outcome. It sits in
the WRITER rather than in `buildEvent`, because the limit belongs to the `jsonb` column
and not to the event: a sink over a writer that does not serialise still receives the
envelope, and a case asserts exactly that.

### 6. The three questions the dispatch asked, answered with derivations

**6.1 How many producers would now be refused. ONE, and it already throws.**

The 34 is a measurement over the **catalogue**, and it was re-derived independently here
rather than inherited: **105 rows, 3 whose payload is given by reference and excluded, 34
of the remaining 102 naming neither tenancy column, and exactly one of the 34 carrying the
`TL` consumer, which is `payout.settled`.** All four are unmoved from session 358.

**But a catalogue row is not a producer.** Only **eight** of the 105 have a producer in
this tree, and exactly **one** of those eight declares neither column:
`payout.freeze_expiring`. So wiring the sink makes **one** producible name throw, not 34.
**And it already throws**, because `UNWIRED_EVENT_SINK.emit` rejects before `buildEvent`
ever runs, so the failure moves from `EventSinkUnwired` to `assertTenanted`'s message and
nothing that works today stops working. **The guard was not loosened and the wiring did
not wait behind it.**

**6.2 Whether anything calls `emit` today. NOTHING IN `apps/api/src`. ZERO, measured.**

| `apps/api/src/**` | **0** |
| `apps/worker/src/breaker/evaluate.ts` | 1 |
| `apps/worker/src/detectors/runner.ts` | 3 |
| `apps/worker/src/sweeps/expiry.ts` | 3 |

All seven are `io.events.emit` against a port that is independently unwired in its own
