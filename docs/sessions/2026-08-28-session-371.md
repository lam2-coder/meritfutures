### 2. The six terms, and the one type check that is not a subject check

Every term is an equality on a declared column, and `ADR-157`'s `LIKE` refusal is untouched.

| Term | Reads |
| --- | --- |
| account id | `accounts.id` |
| platform ref | `accounts.platform_account_ref` **and** `platform_account_refs.platform_account_ref` |
| email | `users.email` **and** `users.email_normalized` |
| identity id | `accounts.identity_id` |
| coupon | `coupons.code`, then `coupon_redemptions.coupon_id` |
| payout id | `payout_requests.id` |

**The platform ref reads two tables because one of them is the history.** `ADR-194` section 3 records
that the live index is partial and that the burn history is `platform_account_refs`; reading only
`accounts` loses the retired ref an operator is holding precisely because something went wrong on it.
**A ref reaching more than one account is a PAGE and not an error**, which is the choice that entry's
section 9 left here, taken for the reason its clause 3 admits a coupon: `M06:435` rules that naming a
signal and listing what shares it IS a specific-subject query, and an error would refuse real work on
the exact input an incident is run from.

**The email term takes both columns and `ADR-194` section 12 left that here in terms.** `users.email`
is what the person typed and is `UNIQUE`; `email_normalized` is `0002_identity.sql:254`'s
entity-resolution key, *"deliberately NOT unique"*, and it is the only one that reaches an account
opened as `A.lice+news@Example.com` from the plain address an operator holds. Watched doing exactly
that against a live cluster.

**A term that is not a uuid is not offered to a `uuid` column, and that is not the check clause 5
refuses.** Postgres answers `invalid input syntax for type uuid` to `id = 'jo'`, confirmed at `psql`,
so without the guard every coupon search is a 500 -- watched, live, with the guard removed. What is
tested is whether the VALUE can address the COLUMN. What is not tested is whether the term names a
subject, which clause 5 says only a lookup answers, and `jo` reaches the coupon term untouched.

### 3. `ADR-194` section 9 is wrong about the price, and the ordering is the repair

That section is the reason this slice exists: *"what changed is that the remaining work is affordable
in the runner"*. **Its measurement of the affordability is wrong for one term of the six.**

> Under an exact subject that price is bounded by the page limit `INV-M6-10` already caps.

**The page limit caps what is RETURNED and caps nothing that is READ.** A coupon is the term where
those two diverge without bound: the same entry's clause 3 defends a coupon *because* many accounts
share one, `coupons.redemption_count` is a counter over every identity that ever used the code, and
`ADR-157` keeps `OR` and `IN` refused, so a naive expansion of a launch code with five thousand
redemptions is five thousand round trips to serve twenty-five rows.

**The repair is the ordering rather than a cap.** The page is ordered `(identity_id, account_id)`
ascending, identities are walked ascending, and every identity not yet walked sorts strictly after
every row already collected. Once more than `limit` eligible rows sit at or before the identity just
walked, the window and its successor are fixed and nothing unread can reach either. A cursor skips
whole identities below it for the same reason.

**Nothing is truncated, and the suite asserts that rather than asserting the saving.** Forty
identities on one coupon: **six expanded on page one, seven on page two** (the extra is the identity
the cursor sits on, which yields nothing after it), and paging the whole set returns all forty
accounts, each exactly once, in the same order the unstopped answer gives. `graph.ts` refuses a silent
truncation by name and so does this; `AccountSearchCost` reports `identitiesResolved` beside
`identitiesExpanded` so the saving is a number rather than a claim.

**Both cursor components are immutable, which `readFlagQueue`'s cursor cannot be.** That header prices
its own hazard: depth moves between requests, so a flag already returned can appear again, and it
argues that repeating beats dropping. Here both components are primary keys, so a page boundary cannot
move under a concurrent write at all and neither failure is available.

### 5. An account the engine has not evaluated, and why zero rather than a throw

`balance_cents` and `withdrawable_cents` are ONE row of `rule_states`, the account's latest trading
day, taken from one row because taking them from two days would report a withdrawable the balance
beside it never produced. **Nothing in this tree writes a `rule_states` row yet**, so an account with
none is not hypothetical, and `API_CONTRACT` types both members `number` with no null. Three answers
were available:

| | Refused because |
| --- | --- |
| a throw | `FM-17`'s shape arriving on a console, and `0015_rule_states.sql`'s own header is where that failure mode is written down. An account provisioned this morning is an ordinary state, and a search that 500s on it loses every OTHER account of the same person on the same page |
| `accounts.size_cents` | a rules-engine claim this module may not make. `M06` section 3.2 refuses a recomputation on the drill-down for the same reason: a recomputation is an assertion and the stored row is a record |
| **zero** | taken. `withdrawable_cents` at zero is exactly right, since `0015` CHECKs it `>= 0` and no gate has passed. `balance_cents` at zero is the weaker half and is the honest reading of an absent record rather than a number this module invented |

**It is pinned with a stated clearing condition and its own non-vacuity read**, so the day a row is
written at account open, or the contract admits a null, the case goes red and names the choice instead
of the next session re-deriving it.

### 6. A finding nobody went looking for: a UNIQUE the transcription does not carry

[`0006_commerce.sql:38`](../../packages/db/migrations/0006_commerce.sql) declares
`code citext NOT NULL UNIQUE`. [`schema.ts`](../../packages/db/src/schema.ts) transcribes the column
as `citext('code').notNull()` with **no `.unique()`**, and `refuseUnaddressed`
([`scoped-db.ts`](../../packages/db/src/scoped-db.ts)) reads uniqueness out of `schema.ts` through
Drizzle's own table config. **So `rowAt('coupons', { code })` throws at run time on an address the
database would have honoured**, and the coupon term reads through `rowsWhere` because of it.

`packages/db` is session 372's fence, so this is registered rather than repaired, with a
clearing-condition case that asserts its own non-vacuity first (the reader can see a `.unique()` where
one exists, on the same file) and goes red on the repair. **The neighbouring transcription comment
already predicted this class**: `accounts`' header says *"the COLUMN is transcribed, which is what the
drift assertion compares; the constraint is the database's"*, so nothing in this tree compares
constraints and this gap was invisible.

### Landmines

- **`AccountSearchCost.ruleStateRows` GROWS WITH THE AGE OF THE ACCOUNT AND WITH NOTHING A CALLER
  CHOSE.** `0015_rule_states.sql` is *"roughly 250 rows per funded account per year"*, and the latest
  state is found by pulling the account's rows and taking the greatest day, because the accessor has no
  aggregate and this module does not widen one to get it. A page of twenty-five two-year-old accounts
  is roughly twelve thousand rows crossing the boundary. **It is reported and not capped**, because a
  cap the contract does not state is a ruling.
- **The early stop's correctness rests entirely on `identity_id` being the ordering's FIRST key.** A
  later slice that reorders this page by anything mutable, or by anything that is not identity-first,
  breaks the stop silently and the suite's whole-set comparison is what catches it.
- **`balance_cents` at zero is a decision and not a default**, and its case is written to expire.
- **The census in the suite is a parse over two files and its non-vacuity guard is asserted first**,
  because a reader that stopped matching would make the absence pass for the wrong reason.
- **`citext` is what makes the email and coupon terms case-free, and no unit case can assert it.**
  The fake compares with `===`. Both were re-checked by hand against a real cluster and section 4 is
  that evidence; a session that moves either column off `citext` will find this suite green.
