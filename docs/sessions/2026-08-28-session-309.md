### 2. The finding: a canary that reads a column the table does not have

`canary.ts`'s `martingaleSequence` mints `fills` rows carrying `realizedPnlCents` and `sequenceOrdinal`. Neither is a column of `fills`:

| Field | Where it actually lives |
|---|---|
| `realized_pnl_cents` | [`daily_marks`](../../packages/db/src/schema.ts), `schema.ts:652`. `fills` has no P&L column of any kind |
| `sequence_ordinal` | nowhere. No table in `schema.ts` declares it |

**Why it matters more than a wrong column name usually does.** `D-05`'s statistic is "size-after-loss regression", so the obvious implementation fits a regression to the loss field on a fill row. Written that way, `D-05` **finds its canary on every run and can never fire on real data**, because no real fill row carries either field. `detector_runs` would read `status: ok`, `synthetic_found: 1`, `flags_raised: 0` every night forever, which is `AS-M7-05`'s opening sentence with a battery in front of it: *"indistinguishable from a genuinely quiet night, and quiet nights are the normal case, so nobody looks."*

**The disposition is REPORT AND WORK AROUND, not repair.** `canary.ts` is `P7-e`'s file and outside this fence. `D-05` builds its own battery from `mint.subject`, which `canary.ts`'s own header sanctions -- *"A detector needing a fifth builds one from `CanaryMint.subject` and states why"* -- over `fills.quantity` and `daily_marks.realized_pnl_cents`, both of which exist. The suite asserts the property in the durable direction: **every canary row this file builds uses only column names `schema.ts` gives the table its stream claims to be.** It deliberately does not assert the defect in `canary.ts`, because a suite that goes red when another slice repairs its own file is a suite nobody may fix.

### 3. What `fills` not having an identity column does to all three

`risk_flags.identity_id` is `NOT NULL` and is who enforcement acts against, and `fills` carries only `account_id`. So the account-to-identity edge is a second table, and `ADR-157` refused the join. Every one of these three therefore declares an `accounts` stream and does the join in the runner, which is what that entry granted in as many words.

**The narrowing is `openedOn <= tradingDay` and it is exact rather than convenient.** An account cannot have a fill before it was opened, so nothing this detector needs is dropped. **The alternative was refused by the accessor rather than by taste**: [`scoped-db.ts:830`](../../packages/db/src/scoped-db.ts) throws on a filter that renders no conjunct, so "read the whole table" is not expressible at all, and a sentinel range term dressed up as one would have been a reach with extra steps.

**What it costs is stated in the file rather than discovered at 02:00.** The account book crosses whole on every run of all three detectors. If that stops being affordable the remedy is `ADR-157` section 5's named entry against `scoped-db.ts`, whose question is already written down: *"a joined read has two tables and the tenancy narrowing has to hold on BOTH of them, or the accessor is a BOLA hole with an extra table in it."* This session did not reach for it and did not need to.

### 4. `D-01` on ingest, and the thing the narrow window cannot buy

`AS-M7-01` counter 2 requires on-ingest detection for `D-01`. `fillClustering({at})` returns the same detector with one extra stream: `fills` for the day **and** `executed_at >= at - window_seconds`, one range term beside one equality, which is `ADR-157`'s grant used exactly as written. A two-sided range is not expressible -- a filter is one narrowing per column -- and is not needed, because a fill later than the one that just landed has not been ingested yet.

**The non-obvious half: the ingest run still reads the whole trading day.** `D-01`'s statistic is *"more than a configured share of BOTH ACCOUNTS' FILLS"*, and the share's denominator is the account's fills for the day. A detector taking its denominator from the two second window would compute a share near 10000bp for every coincidence and fire on all of them. So the ingest mode buys **detection latency and not read cost**, which is what `AS-M7-01` actually asks for: that scenario's margin is thin because *"the detector runs nightly, so day 3 is really the night after day 3"*.

**The canary sits in both streams for the same reason a real fill does.** A battery present only in the day's population would never pair inside the window, so every ingest run would report `degraded` and page, which is how a canary battery gets switched off.

### 5. The near-miss fixtures, which are the deliverable

Every threshold is asserted twice, and the two fixtures differ by one unit.

| Detector | Just inside | Just outside | Why the pair is one unit apart |
|---|---|---|---|
| `D-01` share | 3 of 4 shared fills, at a 5000bp floor: **fires** | 2 of 4, which is exactly 5000bp: **does not fire** | `M07:108` is "MORE THAN a configured share", so the boundary belongs to the trader. `shared * 10000 > floor * total` as integers, never a division |
| `D-01` window | fills 2s apart, at a 2 second window: **fires** | fills 3s apart: **does not fire** | the window is inclusive at its edge, which is `ADR-157` clause 6's foreclosure of a half-open interval read one layer up |
| `D-01` identity | two identities: **fires** | the identical fixture with ONE field changed, both accounts on one identity: **no flag and no row of any kind** | `M07` section 3.4. It is a filter at the detector, not a dismissal in the queue |
| `D-04` events | entries near 3 distinct releases, at a minimum of 3: **fires** | entries near 2 releases, and separately **twenty entries around ONE release**: **does not fire** | the count that matters is of RELEASES and never of fills, which is the case a reader would get wrong |
| `D-04` window | entries on the release instant, 60s window: **fires** | the same entries moved 61s: **does not fire** | one second |
| `D-05` slope | 100 -> 200 contracts after a loss, at a 10000bp floor: **fires** | 100 -> 199: **does not fire** | `199 * 10000` is 1,990,000 and `100 * 20000` is 2,000,000. One contract |
| `D-05` sequences | three sequences, at a minimum of three: **fires** | two: **does not fire** | one sequence |
| `D-05` loss | the firing series after LOSING days: **fires** | the identical series after WINNING days: **does not fire** | the "after loss" qualifier asserted rather than assumed |

Two registries are refused rather than obeyed: a `min_events_in_pattern` below 2 (`M07:111`, *"never a single event"*, and the same row's stated `fires_on_single_event: false`) and a `min_sequences` below 2 (`M07:112`, *"never a single sequence"*). A share floor at or above 10000bp is refused too: it can never be exceeded, so it is a detector that cannot fire, including on its own canary.

### 6. All three decline against the registry as `P7-d` seeded it, and that is the honest state

`INV-M7-04` makes the registry the only source of a threshold. Eleven of the seventeen numbers these three need are `unstated` in [`m07-detectors-v1.rows.json`](../../packages/db/src/seed/detectors/m07-detectors-v1.rows.json), because that seed writes no number it cannot cite to `M07` and `OQ-M7-02` is the founder's on all of them.

| Detector | Stated today | Unstated today |
|---|---|---|
| `D-01` | `window_seconds: 2`, `same_identity_pairs_filtered_at_query`, `runs_on_ingest` | `min_shared_fill_share_bp` |
| `D-04` | `fires_on_single_event: false` | `release_window_seconds`, `min_events_in_pattern`, `lookback_days` |
| `D-05` | `scope: strategy` | `size_after_loss_slope_bp`, `min_sequences`, `severity`, `lookback_days` |

So each raises `DetectorDeclined`, the runner records the run as `failed`, and `detector_runs_unhealthy_idx` and `CRON_INVENTORY`'s dead-man switch both see it on the morning it happens. **A detector that ran anyway would either invent a threshold or match nothing, and matching nothing is `FM-M7-01` exactly.** The suite asserts the decline against the real seed file rather than against a fixture, so the day a number is seeded the assertion is the thing that notices.

### 7. Severity: the band that holds a payout is not written here

`M07` section 3.3: moving a detector from 3 to 4 changes who gets held, because 4 and 5 is the band `G-HOLD-REQUIRED` reads to hold a payout for 48 hours under [ADR-040](../decisions/ADR-040.md), and `risk_flags_high_severity_has_sla` makes `sla_due_at` mandatory there.

**Nothing in the corpus states a duration for that clock.** `OQ-M7-03` is open, proposes *"4 hours to first touch during business hours, 24 hours otherwise"* for severity **5** and nothing at all for severity 4, and records that `ADR-040` moved the footing the question was answered against. No seed row carries an `sla_hours` parameter.

So the file reads `sla_hours` from the registry and computes the clock from the run's own `now` when it is there, and **caps a finding that would score 4 or 5 at 3 when it is not**, recording `severity_capped_from` and the reason on the flag. Both alternatives are worse: an invented clock holds a real trader's money on a number nobody chose, and dropping the finding loses the detection. **The cap lifts with a seed row and not with a deploy**, which is `SD-M7-03`'s whole point.

Two cited severity cases are unreachable and both are reported rather than approximated:

- **`D-01` severity 5** is *"the same pattern with a funded member ELIGIBLE THIS WEEK"*. Payout eligibility has no read in `DETECTOR_READ_TABLES`, and a funded account is not a funded account eligible this week. The flag carries `funded_member_present` and says in its own evidence which case it could not evaluate.
- **`D-04`'s only cited case is severity 1 for "single-window observations"**, and this detector never produces one: it fires only on a pattern across many events. Severity 1 is taken because it is the only number the registry carries for `D-04` and because `FM-M7-04` puts severity 1 in a digest rather than the queue, which is right for straddle farming. **The founder may want a distinct value for the pattern case**, and choosing one here would be the author of a detector scoring his own detector, which `M07` section 3.3 calls a money decision.

### 8. The evidence carries the conduct and discloses no threshold

`M07` section 3.4, on `D-01` and generalising: *"the evidence is the conduct: these fills, on these accounts, held by these two identities, at these timestamps, against this ToS clause. That is exactly the form `AS-M7-07` says survives a public argument, and it discloses no threshold."* The seed says the same from the other side, in its own `is_sensitive_reason`: *"A ring told the window is 2 seconds spaces its entries by 3."*

So every `evidence` object carries observations -- the accounts, the identities, the symbols, the shared and total counts, the first and last instants, the release keys, the escalating days -- and **carries no parameter at all**. The suite asserts it over every flag all three detectors can raise, by name, for all six thresholds. The parameters remain one join away through `detector_runs.(detector, detector_version)` for anything entitled to them, which is `INV-M7-04`'s chain and `P7-j`'s redaction problem rather than this file's.

### 10. Six things reported and not repaired

1. **`canary.ts`'s martingale rows carry two fields that are not `fills` columns.** Section 2. `canary.ts` is outside this fence.
2. **[P7](../plans/P7-risk-and-abuse.md)'s `P7-f` row cites "section 3.4's ruling" and `P7` has no section 3.4.** The ruling is `M07` section 3.4, which is what this slice implemented. A citation to repair in `P7`, not a ruling to seek.
3. **`lookback_days` is a parameter no document names and two of these three detectors cannot run without.** *"A pattern across many events"* and *"over a minimum number of sequences"* both need history and neither states how much. It is asked of the registry, it is absent from the seed, and both detectors decline. It is **calendar** days rather than trading days because the trading calendar is not a member of `DETECTOR_READ_TABLES` and minting a member to convert one to the other is a wider reach than the number is worth.
4. **No SLA duration exists for severity 4 or 5.** Section 7. `OQ-M7-03` is the founder's and until it is answered no detector in this phase can write the band that holds a payout.
5. **The on-ingest CALL SITE is outside this fence.** `fillClustering({at})` is built, exported and asserted; `apps/worker/src/live/ingest.ts` is the file that would call it and `P7-f` does not hold it.
6. **`DEP-M7-01` is a residual and the assumption is stated.** All three read `fills`, which `M02` supplies contingent on `V-M2-11`, and `M02` holds at `review`. **What is assumed is that a fill row arrives with `account_id`, `symbol`, `side`, `quantity` and `executed_at` populated**, which is what the landed `fills` declares `NOT NULL` today. If the vendor cannot supply fill-level data at all, these three read empty windows, raise nothing, and still find their canaries -- which is `AS-M7-05`'s opening sentence again and the reason the battery is not the whole control.
