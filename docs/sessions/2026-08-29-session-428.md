### 2. The cap: the finding is the home rather than the absence

**Two halves that are each settled and do not fit together.** The enforcement is
identity-level: constitution B1 lists *"total accounts (cap enforcement)"* among
the identity-level aggregations, `INV-M3-08` says per resolved identity,
`GS-094` pins the eleventh purchase, and `AccountCapRow.liveAccounts` is declared
*"Live accounts this IDENTITY holds"*. The parameter is per plan version, inside
`plan_versions.rules`, with no `CV-nn` and no database constraint, which the
[plan-config audit](../reviews/2026-08-20-plan-config-audit.md) records as
finding C and calls deliberate.

**So one number per published version is compared against one count that spans
every plan, and the three ways to read it are each refused for a reason that is
not the others'.** The purchased version hands the choice to the adversary. The
pinned version, on the reset path, reads a row that was retired years ago and is
never revisited, because pinning is what makes `B4 #12` provable. Agreement
across versions cannot be a `CHECK`, because a `CHECK` cannot read another row,
which `0004_catalog.sql` already records about a different leaf of the same blob.

**The third is the one worth rejecting slowly, because it almost works.** Enforce
agreement at publish and read any version. It fails on the reset path in the
direction that costs money, and it concedes the point: a parameter every version
must agree on is not a plan parameter.

### 3. Where it goes, and why it did not go there today

**`price_floors` is the precedent and it is exact.** Its registry rule says the
number is the firm's, that the table carries no identity column *"because a floor
that differed per trader would not be a floor"*, that its grain is
`(product_ref, effective_from)` so a change is a new row, and that `approved_by`
records who authorised it. **A cap that decides who is refused a purchase is the
same class of number as a floor that decides what a price may not go below.**

**It is not built here and the reason is a fence rather than a difficulty.** A
`firm` parameter row is a migration plus a declaration in
[`schema.ts`](../../packages/db/src/schema.ts) plus a classification in
[`scope.ts`](../../packages/db/src/scope.ts), and both files are session 427's
this wave. **No migration number was taken**, because a number reserved for a
file this session cannot write is a hole in [ALLOCATION](../decisions/ALLOCATION.md)
with nobody to fill it.

### 4. The cross-identity read, refused again and on different ground

**ADR-233's argument is unavailable here and the row said so in advance.** That
entry admitted a `firm` read because the row belongs to nobody. These rows belong
to somebody.

**What IS different was worth finding and does not carry.** A buyer presenting a
coupon code or a click token holds something the affiliate gave them, which is
the premise [ADR-230](../decisions/ADR-230.md) leaned on when it declined to
validate `insertAsParty`'s counterparty. It loses to three objections that do not
depend on each other: a token is picked up by following a link and is not an
authorisation; every door in `packages/db` returns whole rows, so the grant would
be the widest answer to the narrowest question; and `OwnedRule` has no field for
a per-table exception.

**The remedy is a stamp rather than a read, and it is the part ADR-233 registered
without naming.** `packages/db` resolves the affiliate inside the transaction,
stamps `attributions.affiliate_identity_id` exactly as `insertAsParty` already
stamps the buyer, and hands the handler a boolean for the literal self-deal void.
**That closes the contradiction ADR-233 section 5 recorded**, which is that
`insertAsParty` on `attributions` has had no possible caller since it was built.
Not taken here: `AffiliateRef` carries `identityId` and `packages/affiliate` was
outside the fence.

### 5. The ledger arm, which is not ours, with the argument ADR-165 never had to make

**ADR-165's ground holds and was re-derived rather than cited.** `SystemReason`
is two members, `ApiDb` declares six doors and none yields a `SystemTx`, both
ledger tables are `derived` so `FirmTx` cannot serve them, and ADR-233's
catalogue door reads `firm` rows and has no write verb at all.

**And a session reading only ADR-165 would reach for ADR-176's remedy, which is
foreclosed.** That entry deleted `PayoutTx.ledger` and moved the `LT-01` posting
to a system authority. `LT-08` cannot follow: [M20](../plans/M20-wallet.md) says
*"LT-08 posted in the same transaction as the purchase"* and `DEP-M20-02`'s
consequence column says the wallet becomes a transfer instrument.

### 8. Next, blockers, landmines

- **Next.** The firm parameter row that ruling 3 names, which needs `schema.ts`
  and `scope.ts` and **unblocks `readMe` on `GET /me` at the same time**. Then the
  stamped counterparty, which gives `insertAsParty` its first possible caller.
  Then the two-party posting from a request path, which is the largest.
- **Blockers.** `useCheckoutBackend` keeps all three clauses. Nothing became
  installable and `start.ts` is untouched.
- **Landmine, registered rather than repaired.** `auth-backend.ts`'s `readMe`
  reason says the base cap appears in no table in any of the *47* migrations and
  the directory holds more than that. The file is outside this fence, the numeral
  is prose rather than a citation, and `RI-20` does not reach a bare count.
- **Landmine, registered rather than ruled.** `gateIdentity` refuses a RESET when
  `liveAccounts >= maxAccounts`, and a reset creates no account. An identity at
  its cap therefore cannot reset an account it already holds. It is a behaviour
  question about a live handler and it was not this entry's subject.
