**Objective.** Give `rule_states.phase` a vocabulary, so the engine's own record
cannot admit a string that is not a phase, and rule whether the fix is the
existing `account_phase` type or a `CHECK`.

**Outcome.** Landed. [ADR-216](../decisions/ADR-216.md) ships `proposed` with an

### 2. Which of `ADR-207`'s reasons transfer

| Reason | Verdict |
|---|---|
| **1.** All thirteen enums are in `0001`, so a new one is a ruling nobody took | **DOES NOT TRANSFER.** A reason against CREATING a type. 13 before, 13 after |
| **2.** This table already stores an engine union as bare `text` | **INVERTS.** Its premise is this defect. A reason citing a gap cannot survive the gap's repair unchanged |
| **3.** A `CHECK` narrows; an enum value can never be removed | **FACT TRANSFERS, REASON FAILS.** `DROP VALUE` is a syntax error and `ADD VALUE` costs two migrations -- both executed -- but `accounts.phase` has borne both since `0001`, so the marginal cost here is **zero** |

**And the reason `ADR-207` could not reach**: the copy count. `breach_kind` had
two copies and paid for the second with a comparator. `Phase` has six and none.

**The one objection on the other side, answered at its source.** One enum now
serves two columns, and the worry is that an account's phase and the engine's
`Phase` are only incidentally the same. **They are the same by design**:
[`0007:8`](../../packages/db/migrations/0007_accounts.sql) says in its own `E2`
header that *"`phase` is the lifecycle the rules engine executes; `status` is the
operational state. They are separate columns on purpose."* The account-side state
that can move independently already has its own type, `account_status`. **And
under a `CHECK` the widening this objection fears would be silent in the other
direction, with nothing shared to compare**: the shared type is what makes the
divergence checkable, which is what REJECTION 5 and the comparator assert.

### Landmines

- **The enum's declaration order is now this column's sort order.** Nothing in
  the estate orders `rule_states.phase` today, so the change is invisible; the
  first `ORDER BY phase` anybody writes will silently mean lifecycle order rather
  than alphabetical. REJECTION 5 of the probe asserts the order from the
  catalogue for that reason, and `accounts.phase` has behaved this way since
  `0001`, which makes the two agreeing the thing that hides it.
- **Widening `Phase` now costs two migrations and narrowing it costs a rewrite.**
  `ALTER TYPE ... ADD VALUE` cannot be used in the transaction that adds it, and
  `DROP VALUE` does not exist. Both were already true for `accounts.phase`.
- **A `text` variable does not implicitly cast to an enum in PL/pgSQL.** Every
  future probe writing this column through a helper must pass the phase as a
  literal or it will report a failure on a phase the column accepts.
- **The fold's `ALTER COLUMN` vocabulary is closed at THREE members now and its
  default is still FAIL.** A `SET NOT NULL` or either `DEFAULT` shape still turns
  `scoped-db.test.ts` red, and the inventory assertion pins the statement count
  at four and the carrier tables at three.
