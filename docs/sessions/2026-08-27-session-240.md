#### 2. Two migrations, not one, and why

The dispatch says to decide honestly and to split with a reason if one item is a different
change. **One item is.**

`OI-03`, `OI-04`, `OI-12` and `OI-13` are one idea stated four ways: **a write that changes
what the database already said goes through a path that records who and why.** `OI-04` and
`OI-13` are the paths; `OI-12` is the write that had no path; `OI-03` is the assertion that
the set of tables holding to it is the set the document names. They go in `0048`.

`OI-01` is a missing table, and the ruling it waits on is **a founder choice between two
named designs**. Folding it into `0048` means a founder who prefers the other design rejects
four guards along with it. [`0033`'s header](../../packages/db/migrations/0033_trading_calendar_revision_required.sql)
already designs for exactly this ("Reject this half if the founder reads the ruling narrowly"),
and a separate file is the stronger form of the same courtesy. It goes in `0049`.

**Both numbers are claimed in the same commit as `ADR-128`.** `OI-03` takes no migration
number, because it needs no DDL.

#### 3. `0048_audited_writes_on_append_only_tables.sql`

`E2 READ: MONEY PATH`. Four parts, each separately rejectable and each headed as such.

| Part | What it installs |
|---|---|
| **`OI-04` a** | `supersede_daily_mark(...)`, `SECURITY DEFINER`, owned by `merit_migrator`, writing `daily_marks.superseded_by` and nothing else |
| **`OI-04` b** | `suppress_identity_link(...)`, same shape, writing the four `SD-M7-04` dispute columns |
| **`OI-13`** | `rewrite_rule_state(...)`, same shape, requiring an `admin_actions` row (B.4 step 3) and refusing to move `id`, `account_id` or `trading_day` |
| **`OI-12`** | `CALENDAR-C3`, a deferred constraint trigger refusing a **retroactive** `trading_calendar` INSERT that leaves no revision row |

**The assignment list in `rewrite_rule_state` is DERIVED, not listed.** It is built from
`pg_attribute` and executed with the new row bound as `$1`, so a column a later migration adds
to `rule_states` is rewritten without anybody remembering. That is `0032`'s `to_jsonb(OLD)`
argument ("a hand-written column list is the same object as a hand-maintained count") applied
to the write side. The three identity columns are excluded from the list, which is what stops
a rewrite from moving a state row to a different account or a different day.

**`CALENDAR-C3`'s retroactivity test is the fold extent, not the coverage window**, and that
is the part to read first. The obvious test, "is the day inside an existing
`trading_calendar_loads` window", is **wrong**: loading the 2027 calendar writes a load row
covering 2027 and inserts 250 days that are all inside it, so the obvious test demands 250
revision rows for the one case `OI-12` says is already correct. The test that expresses the
actual harm is `NEW.trading_day <= greatest(max(trading_day))` over `fills`, `daily_marks` and
`rule_states`, which is **P1 S-E section 4's ruled partition, the same three tables
`CALENDAR-C1` counts over**. A day beyond everything the engine has folded changes no computed
state. A day at or before it changes the day sequence retroactively.

**The revision row `CALENDAR-C3` requires carries the ABSENCE image**, `is_holiday` JSON null,
which is what a day that did not exist looked like and is the only honest prior image for an
INSERT. It is also what stops the guard being satisfied by pointing at some unrelated
correction's revision row. And **`incident_ref` is required unconditionally**, because a
retroactive day insertion is an incident by construction: `dependent_row_count` counts rows on
the day itself, which for a day that was never a trading day is legitimately zero, so the
existing `incident_named_when_dependent` CHECK would not fire.

**The trigger asserts and does not write**, which is `0027` and `0033`'s idiom rather than a
preference. It cannot invent an actor or a reason.

#### 4. `0049_reserve_coverage_snapshots.sql`

### The three things a reading would not have found

1. **The ruled mark correction has never been executable.** `0014` and `0026` both state the order and the database refuses both directions: inserting the replacement first trips `daily_marks_live_per_account_day_uq` (two live marks for an instant), and pointing the old row first trips the `superseded_by` foreign key. There is no third order. **Found by writing the fixture for `SUCCESS 4`.** The repair is a `DEFERRABLE` `EXCLUDE` constraint over the identical btree under the identical name.
2. **`CALENDAR-C3` refused its own fixtures as first written.** A deferred constraint trigger asks its question at commit, so a transaction that seeds a calendar and then folds over it refuses itself. **Found by running every existing probe against the new schema**, which is DELTA_MANIFEST section 18's rule, on the first run. It is now immediate, and `0032`'s revisions foreign key is superseded as `DEFERRABLE` so a backfill can record an absence before the day it is about.
3. **`OI-03` had already happened, three times.** DATA_MODEL section 1 carried three copies of its Mutability bullet claiming twenty-three, twenty-two and twenty-two tables over three different migration lists, while the installed set was twenty-five, with every gate green.

### Two register rows were wrong

`OI-04` calls the `identity_links` write "a single-column update" and it is four columns. `OI-01` lists `per_plan` among the fields with no home and [`plan_breaker_state`](../architecture/data-model/plan_breaker_state.md) has carried it since `0016`. Both rows are corrected in place. **The register calling its own entry stale is the blind spot [ADR-117](../decisions/ADR-117.md) names**, and this is two instances of it in one wave.
