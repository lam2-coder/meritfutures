**`POST /auth/elevate`'S CELL DISAGREES WITH SECTION 12'S AND THE DISAGREEMENT IS NOT AN ERROR.**
Section 12's row for it reads `passkey or dual_channel`, which names **the factor the elevation
admits** rather than the authority needed to CALL the endpoint; section 3 says "Auth: session" and
"It does not re-establish the session and it never issues a new one", so a caller with no session
has nothing to elevate. The declaration table therefore carries `session` for the call and the
`ElevationFactor` union carries the other half. `CI-06k` reads the DOCUMENT and not this table, so
there is no gate conflict, and this paragraph exists so that a later gate comparing the two finds
the reason rather than a defect.

**`POST /phone/change/:id/cancel` HAS NO REQUIRED FACTOR IN THE CORPUS AND IT IS DECLARED
`session` ON THE CONTRACT'S OWN ARGUMENT.** Section 3.1 declares the factor for opening a change
and for reading one, and says nothing about cancelling one. `session` is taken because cancelling
an in-flight change is the same shape as reading the session list: requiring elevation to STOP an
attacker's ceremony would lock the real owner out of the one control that helps them, which is the
argument the contract itself makes one paragraph earlier. **This is a debt against section 12 and
not a ruling**: API_CONTRACT is outside this fence, so the row is owed rather than written.

#### 3. `C-27` is a TYPE and the seed is `@ts-expect-error`

```
type AuthFactor      = 'email_otp' | 'sms_otp' | 'passkey';   // sessions.auth_factor,        0029:565
type ElevationFactor = 'passkey' | 'dual_channel';            // sessions.elevated_by_factor, 0029:581
```

`ElevateRequest` is a discriminated union over `ElevationFactor` and over nothing else, so
`{ factor: 'sms_otp', ... }` is **not constructible**, which is section 12's "there is no such
value to send" expressed as a type. **The refusal is watched by `@ts-expect-error` in the suite**
rather than by a runtime assertion, because `tsc` reports an unused `@ts-expect-error` as an error
of its own: the day the union widens, `pnpm run typecheck` goes red on the line that says it must
not. `apps/api/tsconfig.json` includes `test/**/*.ts`, so the seed is inside the typechecked set.
This is the approval line's second clause, and it is the reason it is a compile failure rather than
a test failure.

#### 5. Rate limits are data, and no handler holds a number

Section 11 puts the SMS branch's velocity in `otp_send_budget` rows carrying `send_limit` and
`budget_cents` (integer cents, `0029:388`). The email branch's limits are stated as prose numbers
in the same table, and **both branches go through the same port** so that no numeric literal
appears in any handler in this diff: a `5` written into the email path is the same defect as a `5`
written into the SMS path, arriving one row earlier. `notification_kinds.rate_limit_exempt` is
`GENERATED ALWAYS AS (class IN ('security','money')) STORED` at `0029:695`, so `pre_identity_auth`
is non-exempt by construction and the handler asserts nothing about it.

#### 6. The ports, why they are fail-closed, and the finding that blocks them

Every handler resolves a session, applies its DECLARED factor, and performs its effect through one
`AuthBackend` port. **The port's default implementation is absent and every method throws**, which
the handlers answer as 503 `service_unavailable`. The suite substitutes an in-memory backend, so
section 12's 200s are real 200s through Fastify's own router and its 403s are genuine authority
refusals rather than an unwired port failing by accident.

**THE PORT IS BLOCKED ON ITS OWN DECLARATION AND THE REASON IS THE ACCESSOR.** Three writes this
surface needs are **not expressible through `packages/db` as it stands today**, and none of the
three is a missing handler:

| Write | Why nothing can express it |
|---|---|
| revoke ONE session | `ScopedTx.update` renders `scopePredicate('sessions', identityId)` and takes no second predicate, so it writes every session that identity holds. `SystemTx.update` and `FirmTx.update` render **no `WHERE` clause at all** ([`scoped-db.ts:701`](../../packages/db/src/scoped-db.ts), `:718`), so they write every row in the table |
| mark ONE otp challenge consumed | `otp_challenges` is `firm`, so `scopedTx` refuses it at compile time and `firmTx.update` is the defect above |
| stamp `elevated_at` on ONE session | as the first row |

`sqlExecutor` is the deliberate door out and **its reason vocabulary is closed to `'job-enqueue'`**
([`scoped-db.ts:567`](../../packages/db/src/scoped-db.ts)), and it throws on any other word; widening
it edits `scoped-db.ts`, which is outside this fence and whose fix is the founder's pending ruling.
**So the ports are declared, the refusal is named on each of them, and the persistence half of this
surface is reported rather than routed around.** [Session 222](2026-08-26-session-222.md) found the
same wall from `apps/worker` and stopped at it for the same reason.

#### 7. No dependency, and the lockfile is not taken

The fence admits `pnpm-workspace.yaml` (`catalog:` only) and `pnpm-lock.yaml`, anticipating a
WebAuthn library. **Neither file is touched and the reason is that the library would have no
caller.** A passkey assertion cannot be VERIFIED without the credential store, `passkeys` lives in
`packages/db`, and that package is outside this fence, so a verifier admitted here would sit behind
a port that throws. `registry.ts`'s own header states the rule this follows: "a primitive admitted
before a caller exists is a primitive nobody can remove". The lockfile is also rowed **SERIAL**
across `P3-j`, `P3-m` and `P4-i` in [P3 wave 3](../plans/P3-wave3-modules.md) section 9, so taking
it for an unusable dependency would cost a sibling slice its scheduling for nothing. Request
validation is hand-written and total over the shapes section 3 declares.
