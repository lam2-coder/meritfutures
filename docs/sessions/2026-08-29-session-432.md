**Objective.** Work out which of `setInternalOpsSource`'s four methods are
database reads this deployable can serve and which are live calls to another
process, and build the ones that are reads.

**Outcome.** **One of the four is a read. The port stays blocked, and saying
which method refuses for which reason is the deliverable.** The number is spent
because four rulings were made with evidence and one of the entry's own
sentences was refuted, not because a port moved.

that covers four methods covers whichever of them it happens to fit.

### 2. Why `readReconStatus` is a read, and why that does not wire anything

Every field it needs is a column. `reconciliations` is
[`0014_marks.sql`](../../packages/db/migrations/0014_marks.sql)'s table, a
process writes it, and the identical filter is already written in this
deployable at [`liability.ts:1193`](../../apps/api/src/admin-source/liability.ts)
over a handle narrowed AT THE PORT, which is the narrowing
[ADR-171](../decisions/ADR-171.md) section 5 ruled belongs there.

**SO THE MISSING THING IS NOT A SHAPE AND NOT A VOCABULARY. IT IS THE DOOR.**
`reconciliations` is scope class `derived`, so `FirmTx.rowsWhere` will not take
the key and `scoped` has no identity on the operator surface. `SystemTx` at
`systemDb('operator-console')` serves it, `apps/api/src/db.ts` declares no such
door, and ADR-171 clause 1 refuses one until an installable `AdminSessionSource`
exists. [ADR-237](../decisions/ADR-237.md) built the operator directory last
session and wired no port, so that condition is unmet.

**A NARROW DOOR OVER THIS ONE TABLE WOULD SURVIVE ADR-171 SECTION 5's TEST AND
IS STILL NOT TAKEN.** Section 9 of that entry names a door narrowed at the door
as one of two admissible answers, and a door reading only `reconciliations`
leaves `databaseAuthBackend` with no `users` row and `B1` refused. It is not
taken because **its only caller cannot be constructed**: the other three methods
reject, the port is one port, and a door with no call site is the
primitive-before-a-caller `job-queue.ts` names and ADR-120 clause 3 cites for
this exact door. Recorded as available to whoever holds a slice that can compose
the source, and neither endorsed nor refused on its merits.

### 3. Why `runBatch`'s stated reason was false

`ApiDb.firm(fn)` hands its callback a `FirmTx`; `FirmTx extends TxCommon`
carries `sqlExecutor(reason)`; `SqlExecutorReason` is `'job-enqueue'` and
nothing else; and the `SqlExecutor` it returns declares `executeSql` and
nothing else, which is the whole of `packages/queue`'s `JobTransaction`. **The
transactional enqueue ADR-006 requires is expressible with the doors this
deployable holds today.**

The module's own header said so when it was written and named the real blocker
in the same paragraph: *"`apps/api` DECLARES NO `@merit/queue` ... the manifest
is the only place that capability can be acquired."* **That sentence was always
the true blocker and the `BLOCKED` entry did not carry it.** A future session
reading the old entry would have gone looking for a shape and found one, which
is the worst possible outcome of a wrong reason: it retires the question toward
"impossible" when the true statement is "needs an authority somebody grants".

**AND THE SHARPEST VERSION OF THAT BLOCKER IS WORKSPACE-WIDE: `@merit/queue` is
declared as a dependency by ZERO packages.** The only manifest naming the string
is the package's own `name` field.

### 7. Landmines

- **`packages/db`'s `systemDb('operator-console')` EXISTS AND IS EXPORTED**, and
  the only thing between it and this route is `apps/api/src/db.ts` not opening a
  door onto it. A session that reads "the shape does not exist" from any summary
  of this port will find that it does. What does not exist is the ruling that
  lets `apps/api` hold it, and `db.test.ts` asserts the absence so the door
  cannot arrive quietly.
- **`readJobs`' partition assumes pg-boss stays the backend.** ADR-006 chose it
  and ADR-086 contained it behind `JobQueue`; a move to Redis makes the depth
  half unambiguously a live call and the ruling would be reached by a different
  argument to the same place.
- **The `last_completed_at` fragment may be more than a fragment.** It is counted
  as one row of twenty because CRON_INVENTORY's dead-man predicates are
  heterogeneous. A reader who thinks the other nineteen reduce to event lookups
  would rule `readJobs` differently, and would still meet the missing depth
  reader and `renderJobs`' refusal.
- **Nothing here has met a database.** Every case executes over source, over the
  scope registry and over rendering functions handed fixtures. That a `SystemTx`
  read would return the rows this response needs is untested and untestable until
  a door exists.
