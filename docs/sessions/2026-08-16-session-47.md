- **Landmines:**
  - **THE PER-ACCOUNT READING OF `INV-06` IS THE ONE R-31 VIOLATES, AND `D-M2-1` IS NOT ABOUT THE MERIT ACCOUNT.** The hypothesis was that "or provisioning a new one" makes the funded account a **new account**, so nothing decreases within one and "no phase qualifier" holds exactly. **Five independent sources refuse it.** [M02](../plans/M02-rithmic-bridge.md)'s **`DEP-M2-01` is the same dependency from the owning side and names the subject outright**: "on `phase.passed`, **the platform account** is reset to `size_cents` (or a new account provisioned at `size_cents`)". `INV-M2-07` restates it as "a funded account's first **mark** opens at exactly `size_cents`" and `FM-M2-07`'s remedy is "refuse, page, **re-provision**". [STATE_MACHINES](../architecture/STATE_MACHINES.md) draws `eval_phase --> funded_phase` **inside one account's `active` state**, and its universal rule 3 reserves "a new one is created instead" for **terminal** states. [`0007`](../../packages/db/migrations/0007_accounts.sql) makes `phase` one column on one row with `funded_on` set on that same row, and `account_status_history` logs `from_phase`/`to_phase` **per `account_id`**. `accounts.purchase_id` is **`NOT NULL UNIQUE`**, so a pass cannot mint a second row. [`0015`](../../packages/db/migrations/0015_rule_states.sql) is unique on `(account_id, trading_day)` carrying `phase` per day, which under a new-account reading would be constant. **The mechanism the hypothesis wanted is `platform_account_refs`**: `account_id` with `assigned_at`/`retired_at`, so one Merit account holds successive **platform** refs. **So per account is already the corpus's meaning, which is exactly why it cannot rescue R-31.**
  - **`DEP-M2-03`'s SAFETY ARGUMENT HAS EXACTLY ONE V1 COUNTEREXAMPLE AND IT IS EVERY EVAL PASS.** The dependency is "M1 emits a floor change (via `day.closed`, `rule.floor_locked`) that M2 turns into a `set_risk` push", justified by "**since [ADR-014](../decisions/ADR-014.md) the floor only moves up, so drift is always permissive, which is safe for the trader**". On the pass day the floor moves **down**: the event carries `locked_floor_cents` of **5,050,000c** and the account leaves the day on **4,750,000c**. The drift is **restrictive**, so `D-M2-3`'s other branch is live: "the platform liquidates before the floor (**traders lose accounts early**)". **The payload sits above the funded account's opening balance of `size_cents`**, so a setpoint pushed from it liquidates the account on its **first funded mark**. Session 45 recorded this event as timeline noise; **the noise is the smaller half**. The engine is faithful and this is not a defect in it: it is a hazard for whoever writes M2's setpoint push, and `RE-U-031` now pins the sequence and the payload so a change to either fails a test rather than a funded account.
  - **"IT IS NOT DERIVABLE FROM `RuleState`" IS TRUE; "SO IT IS A SCHEMA DELTA" IS THE STEP THAT DID NOT HOLD.** The datum R-32 needs is already stored **twice**: **`accounts.opened_on date NOT NULL`**, declared `**Unit: trading day**`, never moves, and is exactly R-02's `sequence` anchor; and **`accounts.expires_on date NULL`**, "eval expiry when configured", which is `max_days` already materialised as a date. **And [M01](../plans/M01-rules-engine.md)'s own public surface already treats the open day as an engine input**: section 1.3 is `initialState(plan: ResolvedPlan, openedOn: TradingDay)`. The engine is **handed** the open day and drops it, because `initialState` writes it to `tradingDay` and the next fold overwrites it. **So R-32 needs one field on `DayInput`, an M01 section 2.1 amendment, not a `rule_states` column.** Still an ADR, because `DayInput` is in a frozen document. **No migration number was reserved, and that restraint is the point**: a number claimed against a migration that should not be written is worse than no number, because a migration is sacred once merged and can only be superseded (constitution E2).
  - **THE REFUSAL SURVIVES THE CORRECTION, AND NOW STANDS ON BETTER GROUND.** R-32 still refuses, and no longer because the schema is missing something. Two things are **genuinely unruled**. The **anchor**: R-32 and `G-EXPIRED` both say "elapsed trading days" and **neither names the day they elapse from**, while an account sits `provisioning_pending` before it is `active`, so a clock anchored at `opened_on` can burn days the trader could not trade. And **which column binds**: R-32 and `G-EXPIRED` describe a **count** against `max_days`, `accounts.expires_on` is a stored **date** for the same fact, and the corpus does not say which is authoritative. **A refusal resting on an unruled anchor is honest; one resting on a schema gap that does not exist is not.**
