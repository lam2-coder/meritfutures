### 3. `payout_requests` is `owned` by `identity_id`, and this is where a wrong rule returns another identity's money

The row carries **two** columns that reach an identity:

```
account_id   uuid NOT NULL REFERENCES accounts(id)    ON DELETE RESTRICT,
identity_id  uuid NOT NULL REFERENCES identities(id)  ON DELETE RESTRICT,
```

Both terminate at the same identity, `accounts` being `owned` by `identity_id` itself. **The direct column is the rule**, which is `certificates`' reading one table over, and [`0010`](../../packages/db/migrations/0010_payouts.sql)'s own comment says why the column is on the row at all:

> DENORMALIZED DELIBERATELY (Wave 2 gate ruling 4). Aggregate exposure queries and race-safety checks are identity-level: the question "how much is this human extracting right now" cannot be a join if it is being asked inside the race it is protecting against.

**A `derived` rule through `accounts` would make the payout table's tenancy depend on a join** rather than on a column the database declares against `identities(id)`, on the one table where a wrong answer returns another identity's payout history and, through `eligibility_snapshot` and `hold_flag_id`, the reasons Merit paid or held them.

**Seeded and caught.** `column: 'account_id'` in place of `identity_id`, nothing else changed, is **1 failed / 79 passed**, and the failure quotes the DDL back:

```
payout_requests.account_id must reference identities(id), and its DDL is:
  account_id uuid NOT NULL REFERENCES accounts(id) ON DELETE RESTRICT
```

That is [session 145](2026-08-23-session-145.md)'s seed, on the money table, arriving red where its ancestor arrived green.

### 4. `wallet_entries`, where the trap points at a table that IS registered

`ledger_transaction_id uuid NOT NULL REFERENCES ledger_transactions(id) ON DELETE RESTRICT`. It is NOT NULL, it is single-valued, and its target is in the registry, so `via: 'ledgerTransactions'` **compiles, terminates, and is not refused by any assertion in the suite**. It is still wrong, and the reason is arithmetic rather than taste: `ledger_transactions` carries no identity column and reaches one by a `semi-join` through `ledger_entries`, which is the double-entry pair of a trader leg and a firm leg. Deriving a wallet statement through it replaces a direct NOT NULL identity column with a three-step chain that traverses the firm leg of the posting and can only ever answer the question the row's own column already answers.

**`reference_id uuid NOT NULL` is the second thing that reads like a hop and is not one.** It is polymorphic -- a payout request, a purchase, or the corrected entry -- and declares no foreign key, so there is nothing a `derived` rule could name even if the rows belonged to somebody else.

**The firm-parent trap was seeded anyway**, on `payout_transfers`, because it is the shape [ADR-092](../decisions/ADR-092.md) warns about and the one [session 188](2026-08-25-session-188.md) built the bounded chain assertion for: `via: 'planVersions'`, `localColumn: 'plan_version_id'`, which is a real NOT NULL foreign key on a real column of a real table. **3 failed / 77 passed**, at *every column a rule names exists on the table it names it for*, *every derived rule names a foreign key the DDL actually declares*, and *every derivation chain ends at an identity, so none of them ends at a firm table*. The assertion was let catch it rather than worked around.

### 5. `wallet_dormancy` is `owned` and not `root`, and the distinction is the vocabulary's

`identity_id uuid PRIMARY KEY REFERENCES identities(id) ON DELETE RESTRICT`. One row per identity, keyed by the identity, NOT NULL by the key. **`root` is still wrong.** `RootRule.column` is typed `'id'` and the suite asserts `SQL_NAME[key] === 'identities'` for every `root` rule, so the class is reserved for the table whose row **is** the identity; this row is a fact **about** an identity that happens to be keyed by it. `owned` on `identity_id` is the same predicate and the honest class.

**[`0028`](../../packages/db/migrations/0028_supersede_plan_version_immutability.sql) alters this table and it is not a drift.** `DROP CONSTRAINT wallet_dormancy_review_was_noticed` followed by `ADD CONSTRAINT` of the same name, swapping `array_length(notified_at, 1) >= 1` for `cardinality(notified_at) >= 1` so an empty array can no longer reach `escheat_review`. The fold's shape test matches `ADD|DROP|ALTER COLUMN` and `RENAME`, none of which appears, so the statement is read and discarded and the column set is unchanged. **A same-name re-add is also why `CI-06/retired-constraints` stays green with the constraint named in a comment**: 16 `DROP CONSTRAINT` statements less 9 same-name re-adds leave 7 retired names, and this is not one of them.

### 7. `hold_flag_id` carries no `.references()` and `freeze_flag_id` does

Both columns are `uuid NULL REFERENCES risk_flags(id) ON DELETE RESTRICT`, `risk_flags` is registered, and the two are transcribed differently on purpose. [`schema.ts`](../../packages/db/src/schema.ts)'s own header is the rule:

> A COLUMN CARRIES `.references()` HERE ONLY WHEN ITS `CREATE TABLE` BODY DECLARES THE FK INLINE AND THE TARGET IS ONE OF THIS FILE'S TABLES.

`freeze_flag_id` is in [`0010`](../../packages/db/migrations/0010_payouts.sql)'s `CREATE TABLE` body. `hold_flag_id` is declared inside [`0031`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)'s `ADD COLUMN`, and **the fold reads that statement for its column NAME alone** -- `topLevelParts` matches `^ADD COLUMN "?name` and discards the rest of the clause -- so a `.references()` written for it would be a claim nothing in this package checks. That is the header's own stated reason applied to a case it does not name by example, and it is recorded here rather than left for a reader to infer.

**The existing precedent does not settle it and is not being leaned on.** `rule_states.calendar_revision_id` is also an ALTER-added FK column with no `.references()`, but its stated reason is that the target is not one of this file's tables, which is a different clause of the same sentence.
