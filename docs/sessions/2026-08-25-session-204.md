### 2. The resolution was structural, and one lift was REFUSED rather than truncated

**Every `pgTable` declaration ends with the same `createdAt` / `updatedAt` / `});` tail, so git aligns the conflict hunk on lines two unrelated tables merely happen to share.** Each side of the hunk then ends MID-DECLARATION with the shared tail after the closing marker, and a hunk-level keep-both splices one table's columns into another's object literal. Four of the five merges conflicted textually in all five files; the first was a fast-forward and conflicted in none.

**The resolution used on all four was the one [sessions 198](2026-08-25-session-198.md), [203](2026-08-25-session-203.md) and 197 each describe having used:** rebuild each of the three code files from the **CURRENT TREE's** copy, then re-append the incoming branch's **WHOLE declarations**, lifted intact and appended at the end, with nothing reordered and no existing line's content edited. The branch was asserted **byte-identical to its base from its first declaration to its last** before anything was lifted, so the only thing that differed was the header count sentence.

**ONE LIFT WAS REFUSED AND THAT REFUSAL IS THE REASON THE DECLARATION IS WHOLE.** [Session 199](2026-08-25-session-199.md)'s `analytics_snapshots` uses the three-argument `pgTable(name, columns, (t) => [primaryKey(...)])` form for its composite primary key, so it closes on a bare `);` where every other declaration in the file closes on `});`. The splitter, which terminates a unit at a top-level `});`, ran off the end of the appended text and **threw rather than ending the declaration at the wrong line**. Widened to both top-level closings and re-run. **A resolver that had silently taken the last `});` it found would have produced exactly the splice this session was dispatched to avoid**, and it would have compiled, because what follows a truncated declaration is another valid one.

### 6. `CI-06u` caught the keep-both hazard in the place this session was not warned about

The dispatch named the hazard on **code** and the resolution used on the three code files was structural throughout. **The documents were resolved keep-both, which is right for a section that is appended and WRONG for a registry table whose rows are keyed**, and `CI-06u` is what said so: **four duplicate keys in [`README`](README.md)'s claim table**, sessions 198, 199, 200 and 201 each present twice.

**The duplicate is not two copies of one row.** Each of those sessions **struck its own claim row in place** on its branch, `**198**` becoming `~~**198**~~` and `CLAIMED` becoming `WRITTEN`, so the two sides of the hunk held the same key in two different states. A keep-both keeps both states, and the register then answers *has 198 been written* with **both yes and no**. The struck row was kept in each of the four and the stale `CLAIMED` duplicate dropped; the numeric ordering of 200 and 201, which the merge had inverted, was restored. **No row's text was edited and no session's own wording was touched** -- session 201's row says *"its entry row is generated below"* where the others say *"its entry is below"*, and it still does.

**IT THEN HAPPENED A FIFTH TIME ON THE TRANCHE A MERGE, ON 202**, whose row this branch carried unstruck while `main` carried it struck. Resolved the same way and by the same rule: **take the STRUCK row for every key, whichever side carries it**. All of 194 to 203 now read struck, once each, in numeric order, and no row's text was edited -- session 201's still says *"its entry row is generated below"* where the others say *"its entry is below"*.

**The lesson is the narrow one and it is worth the line: keep-both is safe for an APPENDED section and unsafe for a KEYED row, and the two live in the same file.** [`STATE`](../STATE.md) and this file's entry table are the first kind; the claim table three headings above is the second. `CI-06u` exists because that distinction is invisible at the hunk.
