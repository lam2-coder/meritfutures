### 2. What the page IS, and the two decisions inside it

**The liability home is at `/` and not at `/liability`.** [M06 section 3.1](../plans/M06-admin-ops-console.md) names it the liability home PAGE, `OQ-M6-04`'s recommended answer is *"yes, daily, one screen, and it is the first thing built in this module, because the habit is the control"*, and [WAVE-06 section 10](../plans/WAVE-06-admin-console-transport.md) item 4 records this wave building it first as a transcription of that recommendation. [`apps/portal/src/app/page.tsx`](../../apps/portal/src/app/page.tsx) put that app's first screen at its root. The alternative costs something an operator meets on day one: with the home one path down, the console's origin answers the framework's own 404 and no slice in this wave holds a root index to put there.

**The document is built from the page VALUE and its leaves are the value's own strings.** `PanelRendering.lines` already carries the label, the amount through `formatCents`, the definition, the as-of, the source, the age at render and the `SUSPECT` prefix. Reading `panel.readings` and formatting them in the document would be a SECOND renderer of a `Figure` in the package whose whole subject is that a number carries its definition and its provenance. What the document adds is structure: sections, headings, lists and `data-` attributes.

**That is not the same as rendering `renderLiabilityHome`'s array**, which is [WAVE-06 section 5.2](../plans/WAVE-06-admin-console-transport.md)'s distinction. That function flattens the whole page into one list of strings and it is untouched: `page.test.ts` reads it, and a flat transcript is the right shape for an assertion over words.

**The banner is printed once.** `page.banner` and the trust panel's own statement are the same string by construction, so the document filters a panel line equal to the banner. The filter is on VALUE rather than on an index, so if the two ever stop being the same string both are printed rather than one silently lost.

### 3. The re-point, and why it is not cosmetic

**The measurement that makes it load bearing.** `buildLiabilityHome` applies `assertNamesNoSubject` to `panels.flatMap((rendered) => rendered.lines)`. The live figure is not a panel and the pending list is not a panel, so neither is in that array. And the live figure's `asOf.source` is built from `movement.feed`, a string a FEED supplies, in [`live-liability.ts`](../../apps/admin/src/live-liability.ts).

So a subject name can reach an operator through a supplier-controlled string while the builder's own INV-M6-10 call reports nothing. `page.test.ts`'s new case asserts exactly that scope: the panels do not carry the name, `renderLiabilityHome` does, and the assertion applied to the array throws. `render.test.ts` then asserts the served side refuses it.

**The shipped guard walks the element tree, and that is the framework's ruling.** The first shape written here rendered the tree with `renderToStaticMarkup` and swept the string. `next build` exits 1 on it:

> You're importing a component that imports react-dom/server. To fix it, render or return the content directly as a Server Component instead for perf and security.

naming `liability-home.tsx` and the import trace through `page.tsx`. So `servedLiabilityHomeStrings` collects every text node and every attribute value from the tree the route returns, one step before it becomes bytes.

**`M6-A-42` is what stops that being a claim.** The suite is in no route graph, so it renders the real markup and asserts that every string the shipped walk collects is in it, that the walk collects attribute values (`liability-home`, the trust verdict) and not only text, and that it THROWS on a node it cannot resolve rather than skipping it. A walk that silently ignored an unfamiliar node would stop covering a screen on the day that screen grew one, while staying green.
