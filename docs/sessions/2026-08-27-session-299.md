#### 1.2 The interesting line, and it is not the line `0050` sketched

[`0050`](../../packages/db/migrations/0050_live_cache_and_role.sql)'s header refuses a monotonicity
trigger and names this slice as the owner of the guard, sketching it as
`ON CONFLICT ... DO UPDATE ... WHERE excluded.sequence > live_account_state.sequence`.

**That predicate freezes the surface at the day boundary, and the migration's own column comment is
why.** `LiveAccountTick.sequence` is 1-based **per account per day**, so the first tick of a new
trading day carries `sequence = 1`. Against a row left over from yesterday at `sequence = 400`,
`1 > 400` is false, the row never moves, and the trader's dashboard shows yesterday's number through
the whole of today. That is [ADR-020](../decisions/ADR-020.md) rule 3's named failure exactly: *"a
live surface that silently freezes at its last value ... looks exactly like a quiet market"*.

`0050` supplies the correction in the comment above the column it added for it: *"The tick's trading
day. Carried because `LiveAccountTick.sequence` is 1-based PER ACCOUNT PER DAY, so a sequence without
its day is not an ordinal at all, and because a row left over from yesterday must be distinguishable
from a quiet market today."*

**So the ordinal is the PAIR `(trading_day, sequence)`, compared lexicographically**, and the guard is
that pair strictly increasing. This is a widening of the sketch in the direction the sketch's own file
argues for, not a departure from it.

### 2. THE PREDICATE, WHICH IS THE ONE INTERESTING LINE, AND IT IS WRONG IN BOTH DIRECTIONS AS SKETCHED

[`0050`](../../packages/db/migrations/0050_live_cache_and_role.sql)'s header refuses a monotonicity
trigger and hands the guard here:

> "the guard belongs in the ingest's `ON CONFLICT ... DO UPDATE ... WHERE excluded.sequence >
> live_account_state.sequence` predicate. It is `P6-f`'s and is recorded as owed rather than added to a
> migration that cannot be edited."

**The sketch loses the day.** `LiveAccountTick.sequence` is 1-based **per account per day**, which
`stream.ts` states in the field's own docstring and `0050` restates on the column it added for it.

| Case | Sketched, `sequence` alone | Shipped, `(trading_day, sequence)` | What the sketch costs |
|---|---|---|---|
| same day, higher sequence | WRITE | WRITE | nothing, and the suite asserts the two agree everywhere inside one day |
| same day, same or lower | REFUSE | REFUSE | nothing |
| **later day, `sequence` back to 1** | **REFUSE** | WRITE | **the surface freezes at yesterday's equity for the whole session.** [ADR-020](../decisions/ADR-020.md) rule 3: *"a live surface that silently freezes at its last value ... looks exactly like a quiet market"* |
| **earlier day, high sequence** | **WRITE** | REFUSE | **yesterday's straggler rewinds the row by a whole session** |

**The correction is in the migration rather than invented here.** `0050`'s comment on `trading_day`:
*"Carried because `LiveAccountTick.sequence` is 1-based PER ACCOUNT PER DAY, so a sequence without its
day is not an ordinal at all, and because a row left over from yesterday must be distinguishable from a
quiet market today."* So this is the sketch widened in the direction its own file argues for, not a
departure from it.

**It is not a money defect and it is still a defect.** ADR-164 `F3` and `INV-M2-14` keep the figure off
every eligibility, breach and money decision, so the loss is a labeled indicative number that is wrong
on the surface a trader watches.

**Two renderings stand and neither is removable.** `supersedes` is where the suite can execute it and
where a fake applies it; the SQL `WHERE` is where the guard actually runs, because two ingest processes
and a restarted one share no memory and only the database can order their writes. They are adjacent in
[`ports.ts`](../../apps/worker/src/live/ports.ts) so a change to one is a diff beside the other, and the
suite asserts the SQL carries both of `supersedes`' comparisons.

### 3. THE EXPECTATION ROW IS A GRANT ARGUMENT, AND IT IS THE FINDING RATHER THAN THE OMISSION

[P6 section 3.4](../plans/P6-live-tier.md) makes the expectation row this slice's, on
`report_deliveries.due_at`'s shape, whose own data-model row states the sentence: *"Without a stored
window, 'nothing arrived' and 'not due yet' are the same empty result set."* **Three facts, each read at
its source, make it unbuildable inside this fence.**

1. **The producer is the sweep and not this ingest.** [EVENTS](../architecture/EVENTS.md) section 5.4 and
   [ADR-161](../decisions/ADR-161.md) clause 7: *"nothing below is produced by the streaming ingest"*,
   because a feed that stops opens no transaction and because `INV-M2-14` makes this path write one
   table. So the ingest emits nothing and holds no event port at all.
2. **A sweep that writes `events` runs as `merit_app`, and `merit_app` cannot read the live cache.**
   `0050`'s `REVOKE ALL ON live_account_state FROM merit_app, PUBLIC` is `FM-M12-08` and `FM-M13-07`
   written as permissions. **So the sweep cannot see the absence it exists to alarm on by looking at the
   cache.** The cheap escape is `0050`'s `F1`, granting `merit_app` `SELECT`, which the migration names
   as the one that will be reached for because it *"makes `FM-M12-08` and `DEP-M12-08` false
   **silently**: nothing fails, the read works"*. **NOT TAKEN.**
3. **So the expectation must live in a table both roles reach, and `merit_live` cannot write one today.**
   ADR-164 clause 2 gives it three verbs on one table and `SELECT` on one more, **with no default
   privileges by design** (`0050` header item 5), so a table a later migration creates is invisible to
   the live tier until somebody grants it deliberately.

**A table plus a grant is a migration, and no migration number is allocated to this fence.** P6 rule 5
says to stop and report rather than reach. So [`ports.ts`](../../apps/worker/src/live/ports.ts) declares
`FeedExpectation` and `FeedExpectationPort`, the ingest records a heartbeat through the port on every
accepted write, and the unwired default refuses. **That is `sweeps/ports.ts`' disposition for the event
sink one directory over, taken for the same reason.**

**What the migration session needs, written where it will read it.**

| Question | The answer this slice argues |
|---|---|
| **Grain** | `(feed, trading_day, account_id)`. Two of the three `feed.*` payloads are per feed and one is per account, so the finer grain serves all three and `accounts_expected` becomes a count of rows rather than a stored number that can disagree with them |
| **Who writes what** | `merit_live` writes `last_tick_at` and `last_sequence`, which is the heartbeat this ingest already produces. `expected_by` is the `due_at` analogue and is a CALENDAR fact, so it is not this ingest's: no trading calendar exists in the tree, which [session 291](2026-08-27-session-291.md) measured independently for a different clock |
| **Why `merit_app` reading it is not `F1`** | `F1` forbids a grant on `live_account_state`. This row carries a heartbeat and an ordinal and **no equity, no movement and no money of any kind**, and the suite asserts that over the declared field list. What makes it safe is the absence of any figure `FM-M12-08` is about, not its name, and the migration should say so in those terms |
| **The atomicity it cannot have** | ADR-164 clause 4 rules that no process holds both roles, so the cache write and the heartbeat cannot be one transaction and [ADR-006](../decisions/ADR-006.md)'s criterion does not reach. The cost is bounded and stated: a heartbeat lagging its cache row by one tick makes the sweep alarm a moment early, and EVENTS section 5.4 already rules that *"tier 2 failing is not a money incident"* |
| **The aggregate** | The feed-wide roll-up is a `GROUP BY`, and [ADR-157](../decisions/ADR-157.md) section 5 refused an aggregate on the read path. That is the sweep's problem rather than this module's and is named so the session that meets it does not read it as new |

### 4. THE ABSENCE TEST, AND THE EIGHT SEEDS

**`INV-M2-14` is a claim about what this code CANNOT reach, so it is asserted mechanically.** The four
table names are **derived from `0050`'s own closing `REVOKE`** and never retyped, so a fifth appended to
that list arrives in the suite without anybody editing it. The regex is anchored on the newline after
`ON`, because a looser one matches `REVOKE ALL ON live_account_state FROM merit_app, PUBLIC;` first and
captures everything between.

Each name is asserted **PRESENT** in the raw text of both module files, which is the foreclosure the
slice is required to carry in its header, and **ABSENT** from the same files with every comment
stripped. The stripper tracks quotes rather than matching a regex, because
[`ports.ts`](../../apps/worker/src/live/ports.ts) holds a multi-line SQL template literal and a naive
stripper meeting a `//` inside one would remove code and pass by deleting what it is looking for. Both
spellings are checked: `tx.insert('dailyMarks', ...)` passes a snake-case check untouched.

**The import graph is walked and is closed at two nodes.** `ingest.ts` imports `./ports.ts` and nothing
else; `ports.ts` imports nothing at all. So there is no path from here to any table in the estate **by
any name**, and not merely by these four.

| # | Seeded | Caught by |
|---|---|---|
| 1 | `import { systemDb } from '@merit/db'` in `ingest.ts` | the closed-graph case and the forbidden-specifier case, both |
| 2 | `export const BASELINE_TABLE = 'daily_marks'` in `ports.ts` | *"names none of them in code, which is the claim"*, naming the file and the table |
| 3 | a local named `ruleStates` in `ingest.ts` | the Drizzle-spelling case, which the snake-case one would have missed |
| 4 | `supersedes` reduced to `0050`'s sketch | four cases, including both seeded-hole cases and the behavioural day-rollover run |
| 5 | the SQL `WHERE` reduced to the same sketch | the SQL fragment case |
| 6 | `as_of_instant = excluded.as_of_instant` deleted from the `DO UPDATE SET` | the UPDATE-arm case |
| 7 | the `opening_equity_cents` `CASE` replaced with `excluded.opening_equity_cents` | the preservation case |
| 8 | the FAKE cache's transcription of the same `CASE` removed | four behavioural cases, including the day's opening and the coalescing run |

**All eight were watched failing and every file was restored from `git checkout --`**, with
`git diff --quiet` confirming a byte-identical tree before the next seed.

**One thing the suite deliberately does not claim.** Nothing here reaches a database: `ci.yml`'s
`integration` job runs on bare `ubuntu-latest` with no services block. The `ON CONFLICT` predicate is
asserted as TEXT against `0050` and as BEHAVIOUR against a fake that transcribes it. **Whether
PostgreSQL executes it as written is not asserted anywhere in this repository**, and the assertion that
could is `P6-k`'s, which P6 rows against the batch's input assembly and `P6-c`'s grant boundary.
