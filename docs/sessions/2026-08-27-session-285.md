### 1. The measurement, and it is the finding

`discoverRouteModules()` then `buildServer({ surface: 'public', modules })`, reading `CompositionReport.registered` on the dispatch SHA:

| Endpoint | The dispatch said | The server says |
|---|---|---|
| `GET /accounts` | named, registered | **REGISTERED** |
| `GET /plans/:planId/versions/:version` | named, registered | **REGISTERED** |
| `GET /accounts/:accountId` | not named at all | **REGISTERED** |
| `GET /accounts/:accountId/marks` | not named at all | **NOT REGISTERED. Nothing serves it** |

The dispatch rowed this segment as `WIRABLE NOW  accounts  all endpoints registered`. It is not: SC-M4-03 needs four reads and one of them has no route. **`GET /accounts/:accountId/marks` is session 284's**, and this session did not wait for it and did not reach for it.

### 2. Why the detail screen fetches anyway

The marks endpoint is absent, so `loadDetail` cannot return `ready` from a browser whatever it does. It performs `GET /accounts/:accountId` and `GET /plans/:planId/versions/:version` regardless, and the two reasons are the difference between a screen and a placeholder:

- **A refusal on a registered endpoint would otherwise never be reported as a refusal.** `INV-M4-07`'s 404 is the case that matters: a cross-trader read must reach the trader as *"not found"*, and a screen that short-circuited would tell them the portal was still being built.
- **The wired path would first run in production on the day the marks route lands**, which is the worst possible day to discover a misconfigured origin.

[`payouts/source.ts`](../../apps/portal/src/app/payouts/source.ts) made the same choice for the same reason: it fetches `GET /payouts` although its screen cannot reach `ready` without an eligibility endpoint nothing registers.

### 3. The third arm, and why it is a decline rather than a repair

[ADR-162](../decisions/ADR-162.md) section 5 item 1 reports that `PayoutCenterLoad` has no error arm, so a 500 renders exactly as a missing endpoint does, and says the repair *"needs `./sections.ts` to render it and `./page.ts` to branch on it, and this session's fence holds neither"*.

**This segment's fence holds both, and this segment had no load type at all yet.** So the two-arm union is not a thing being repaired here; it is a thing being declined at the moment of authorship. Writing `ready | unavailable` and reporting the hole would have been reproducing a known defect on purpose in the one segment positioned to avoid it.

The three arms are three different facts and the screen says a different sentence for each: `ready` (the data arrived), `unavailable` (**nothing failed**: no API configured, or an endpoint nobody serves yet), `error` (**a registered endpoint refused or failed**, carrying the `PortalErrorKind` the client mapped and the status it was mapped from).

### 4. What was refused

| Move | Why refused |
|---|---|
| **Touching `http/client.ts`** | [ADR-162](../decisions/ADR-162.md)'s, and a second segment editing it is what that entry exists to prevent. The one thing it did not give this segment, a status on a successful read, is reported rather than added |
| **Registering `GET /accounts/:accountId/marks`** | `apps/api` is outside this fence and it is session 284's |

| **Importing `KYC_CONTENT_COPY`** | A segment reaching into another segment's copy catalogue couples two screens' wording to one edit, and `app/kyc/` is being wired concurrently. The shared catalogue belongs under `src/shell/`, which this fence does not hold |
| **Deleting the `accountsSource()` fence test** | Narrowed instead, into a stronger claim: it now proves all three screens are distinct rather than that one of them was unreachable |
| **An export in `src/index.ts`** | Nothing new here is a read surface a builder reaches through the package entry point. `payouts/source.ts` is not exported either |
