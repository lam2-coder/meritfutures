### 1. The finding was reproduced before anything was built

Both greps were run on the tree as received, and the second one is the one that matters, because the dispatch supplied only the first.

```
$ grep -oE '^\s*(use|set)[A-Za-z]+\(' apps/api/src/start.ts | sort -u | wc -l
4
$ grep -ohE 'export function (use|set)[A-Za-z]+' apps/api/src/routes/*.ts | sort -u | wc -l
20
```

The sixteen names matched the dispatch's list exactly. The 503 was read out of the ports rather than assumed: `wallet.ts:758-765` maps `WalletBackendUnwired` to `503` and never `500`, and every other port carries the same shape with its own message.

### 2. The count that decides whether this is mechanical, which the dispatch asked for by name

Of the sixteen unwired ports, **one** had a usable `databaseX` factory beside it, **one** had a factory that cannot be called, and **fourteen** had none at all.

| Port | Adapter | State |
|---|---|---|
| `useWalletBackend` | `databaseWalletBackend`, `wallet.ts:496` | **WIRED.** One line |
| `useCertificateBackend` | `databaseCertificateBackend`, `certificates.ts:646` | Exists and **cannot be called**: its `links` parameter has no supplier |
| `setMethodDefinitionSource` | none | **BUILT AND WIRED** here |
| the other thirteen | none | Reported, each with what it waits on |

So `4 of 20` becoming `6 of 20` is the honest number, and **the ratio is the finding**: wiring an existing adapter is a line, and fourteen of these are slices with rulings in front of some of them.

### 3. The money ports are blocked, not merely unbuilt, and that is stronger than "ready to wire"

The dispatch offered leaving the money ports as ready-to-wire and saying so. The reading is that they are **not** in that state, and the distinction is load bearing for whoever takes them next.

| Port | The thing in the way |
|---|---|
| `usePayoutBackend` | `PayoutTx.ledger` (`payouts.ts:395`) is `LedgerTx` and **not nullable**. No live deployment can construct a `PayoutBackend` at all |
| `useCheckoutBackend` | `insertAttribution` (`checkout.ts:878`) writes `attributions`, scope class `pair`, which no `packages/db` authority admits a request handler writing. The wallet arm's `ledger` is the same `LedgerTx` |
| `useAdminPayoutBackend`, `useAdminWalletBackend` | `operator()` at `systemDb('operator-console')` |

`LedgerTx` is satisfied only by `SystemTx`, opened at a `SystemReason`, which is `'nightly-batch' | 'operator-console'` (`packages/db/src/scoped-db.ts:197`). **`ADR-165` ruled this evening that it gains no member.** Nothing here widened it, imported `pg`, or cast past a key type.

### 4. Three ports already hold their production value, which the dispatch's grep could not see

`useAffiliateDeps`, `useKycDeps` and `useCheckoutAdapters` are not `null` and not a fail-closed sentinel at module scope. They hold `productionAffiliateDeps` (`affiliate.ts:478`), `productionKycDeps` (`kyc.ts:284`) and `PRODUCTION_CHECKOUT_ADAPTERS` (`checkout.ts:1005`).

**Calling those three setters from `start.ts` would have raised the reported count from 6 to 9 and changed nothing any request sees.** It would also have passed the test written in this session. That is recorded in the blocked reasons themselves rather than only here, so the next reader tempted by it meets the sentence before the green tick.
