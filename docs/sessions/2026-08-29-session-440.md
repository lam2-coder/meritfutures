### 2. Why the round trip is the assertion and an encode is not

**AN ENCODER WATCHED ALONE IS GREEN ON A BAG NO DECODER CAN REBUILD**, which is the exact failure
[ADR-206](../decisions/ADR-206.md) section 5 measured: Postgres holds `9007199254740993` exactly and
`JSON.parse` hands back `9007199254740992`. So every case that matters goes out through
`JSON.stringify` and back through `JSON.parse` before it is compared. **An object copy would have
carried the `bigint` this codec exists to keep out of the column**, and a suite that skipped that leg
would have been green on the one encoding the ruling refuses.

**THE ENCODER IS TOTAL AND EVERY REFUSAL IS ON THE DECODE SIDE.** A write path that refused a legal
state would leave the account-day with no row at all, which is `DO-3`. The decoder's input is
`unknown` and it means it.

**THE CENTS CHECK IS A ROUND TRIP AGAINST THE RENDERING RATHER THAN A PATTERN**, and this is the one
place the implementation is cleverer than the ruling required. `BigInt(text).toString(10) === text`
admits exactly the strings the encoder can emit, so the two directions are bound to one rendering
instead of to two descriptions of one. A regular expression would have been `FM-16` at the leaf.

### 6. Where this session is most likely wrong

**THE ROUND TRIP IS THROUGH `JSON.parse` AND NOT THROUGH POSTGRES.** No database was reachable from
this session, and inventing one would have been a worse claim than a stated absence. What is
executed is the leg the ruling identified as lossy; what is NOT executed is that `jsonb` accepts
this bag and that the table's `CHECK` constraints admit the row it sits in.
[ADR-206](../decisions/ADR-206.md) section 6 measured both on a real row and this session relies on
that rather than repeating it.

**THE DECODER IS STRICTER THAN ANY DOCUMENT REQUIRES.** Nothing approved says a decoder must refuse
a leading zero or a padded string. The case for it is a silently wrong `bigint` on a money path; the
case against it is that a strict decoder can leave a merely untidy row unreadable and answer 503 on
it. That is a judgement and it is flagged for the `E2` read rather than buried.

**AND ONE FENCE EXTENSION RESTS ON A TOOL'S CONFIGURATION.** The suite is in
`packages/rules-engine/test/` because Stryker mutates that package's `src/` against that package's
own vitest config. That is measured from the two config files and not from a run: `CI-09` is nightly
and was not executed here.

### 8. Landmines for the next session

- **`ENGINE_GATE_LEAVES` IS A LIST OF DOTTED PATHS AND IT IS NOT A CODEC.** Building a bag by
  walking it means splitting each path and indexing back into the value, which is the key iteration
  `M01` section 1.4 bans and which no type checker sees through. The array is for COMPARING against,
  and the suite is where that comparison belongs.
- **THE STRICT TS FLAGS BITE THIS PACKAGE HARD.** `noPropertyAccessFromIndexSignature` and
  `noUncheckedIndexedAccess` are both on, so a decoder written against `Record<string, unknown>`
  needs bracket access everywhere and a suite that reaches into a bag by index does not compile.
  Typing the round-trip helper as the stored type is what makes the suite readable.
- **`adapter.ts` NO LONGER IMPORTS `UNWIRED_RULE_STATE_WRITER_IO` AND A TEST ASSERTS THAT.** A future
  session restoring that import to compose something else will go red in
  `apps/api/test/rule-state-producibility.test.ts` rather than in the worker.
