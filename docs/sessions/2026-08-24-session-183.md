- **Landmines:**

  - **A DEPENDENCY'S OPTIONAL PEER IS IN YOUR LOCKFILE, AND A PROBE THAT GREPS FOR A NAME WILL FIND IT.** This is the sharpest thing in the session and it was not in scope. `CI-08` waits on *"`@playwright/test` present in the lockfile"*; `next@16.3.2` declares `@playwright/test` at `peerDependencies` with `optional: true`; pnpm lockfile v9 records a package's peer block **verbatim**, so installing Next.js wrote `      '@playwright/test': ^1.51.1` into the file. The gate failed at **29 of 30** with *"the artifact HAS ARRIVED"* on a row whose artifact is absent, and it failed on a row **`P4-c`'s fence does not hold**. The old needle was anchored so `@vitest/browser-playwright` could not trip it, which bounds the **name**; nothing bounded the **context**. A lockfile v9 entry key is `name@version:` at exactly two spaces, a peer declaration is deeper and carries no `@version`, and a catalog line is four spaces and carries neither. **`VG_PROBES`' `fastify` needle has the identical shape and is one dependency away from the identical failure** -- it is `P4-d`'s register and is reported rather than touched.

  - **REPAIRING A PROBE CAN MAKE AN EXISTING FALSIFY CASE VACUOUS, AND THIS ONE ALREADY WAS.** `playwright-near-miss` seeded `  '@vitest/browser-playwright': 4.1.10` and its control seeded `  '@playwright/test': 1.56.0`. **Neither is a shape pnpm's lockfile has anywhere**: an entry key carries `@version` and a catalog line carries a `specifier:` beneath it. The control stopped firing under the repaired probe, which is how it was found; and had only the seed been left, the case would have passed **because no entry key existed** rather than because the name anchor held. **A near-miss seed must be a real instance of the thing that MUST NOT fire**, or the case reads as coverage and asserts nothing. Both seeds are entry keys now.

  - **THE PLAN PREDICTED `VG-2` WOULD EXPIRE AND IT DID NOT, BECAUSE THE FENCE FORBADE THE THING THAT WOULD HAVE EXPIRED IT.** [P4 section 4.1](../plans/P4-portal-and-site.md) says `VG-2` *"expires the moment `CI-07` acquires an implemented leg"*, and the dispatch says both rows *"fail on good news"*. **`VG-2` does not fail on good news**: `CI-06/vg-inventory` checks a chained leg against whether the named 4.1 row carries an **implemented** leg, and `CI-07` cannot acquire one from inside `P4-c` because [`ci.yml`](../../.github/workflows/ci.yml) is `P4-i`'s fence. So the row moved by **gaining a sentence and keeping its disposition**, which is the honest edit, and [ADR-080](../decisions/ADR-080.md) had already ruled this exact day in advance.

  - **A GATE IS A BAD PLACE TO KEEP ANOTHER DECISION'S PREMISE.** [ADR-083](../decisions/ADR-083.md) section 5 makes *"the framework had to be one that needs no build step at all"* a condition *"from a gate rather than from taste"*, and its foreclosure table hedges it exactly right: NestJS is *"not merely rejected but unavailable **while that gate stands as written**"*. **This session is when that gate stopped standing as written.** ADR-083's ruling survives on its three measured properties and on the back-door argument; **its enforcement does not exist any more**, and `apps/api` keeping no build step is now a convention. Signed entry, out of fence, reported.

  - **[ADR-096](../decisions/ADR-096.md) FOUND `F4` INDEPENDENTLY, ON THE SAME DAY, FROM THE OPPOSITE END OF THE QUESTION, AND IT MERGED WHILE THIS BRANCH WAS OPEN.** Session 185 asked what `apps/site`'s adapter reads through; this one asked what a framework forecloses; **both landed on `merit/no-raw-db-client` having nothing to say about `@merit/db`**, which is not a `CLIENT_FAMILIES` entry and is not meant to be. Neither session could see the other. ADR-096 goes further and **names the remedy**, an `RI-08` over `apps/site`'s four dependency fields, unwritten and assigned to `P4-e`. **It does not close `F4`**: it reads `apps/site` where `F4`'s subject is `apps/portal`, and it reads a **manifest** where a route handler declares no dependency at all. **The overlap is the diagnosis and not the repair**, and `ADR-095` section 9 item 5b says so rather than leaving a founder to notice that two entries in one wave describe one gap.

  - **THE APPROVAL CLAUSE WAS TAKEN UP BEFORE THIS BRANCH MERGED, AND THE ROW THAT TOOK IT UP CORRECTS ONE WORD OF THE ENTRY.** Session **189** is CLAIMED against `ADR-098` to rule the gap and, if the ruling calls for it, build the mechanism. Its row says *"it is true on `main` TODAY ... the gap predates the framework"*, and that is **more precise than `ADR-095` section 10's *"from this commit"***: what predates this commit is the **absence of a mechanism**, which holds on a tree with no framework at all because nothing stops `apps/portal/src/index.ts` opening a socket; what this commit changes is that serving an operator path becomes **one file in a conventional location** rather than a server somebody has to write. **The gap is older than the framework and the framework is what makes it cheap.** Section 10 is amended to say so. **A clause is worth writing when a later session can scope a slice off it without asking you what you meant.**

  - **THE APPROVAL CLAUSE WAS TRUE WHEN WRITTEN AND IS FALSE ON THIS BRANCH NOW, WHICH IS THE OUTCOME A CLAUSE IS FOR.** [ADR-098](../decisions/ADR-098.md) is **signed** and [`RI-09`](../../packages/tooling/checks/repo-invariants.mjs) is on `main`; merging them here closes the hole. **Re-executed with this session's own seed verbatim on the merged tree**, `check:invariants` exits **1** at **7 of 8** with `RI-09` naming the file. `ADR-098` also settles the *"predates the framework"* correction by execution: it reproduced the clause on a tree with **no `next`, no `react`, no `build` script and no server outside `apps/api`**, and **generalised one seed file into five**. **`F4`'s import half is still open and `RI-09` says so itself**, naming `ADR-095` section 9 item 5: *"that defect is an import and this one is a path."* **`ADR-095` section 10 is amended to read as a record rather than a live finding**, because an entry whose clause a founder would act on when the action is already taken is worse than one that never made the claim.

  - **`CI-05` FAILED ONCE ON A NETWORK RESET AND ITS DIAGNOSTIC BLAMED THE PIN, WHICH IS A FALSE LESSON WAITING TO BE LEARNED.** On head `fc434f4` the job died at *`curl: (35) Recv failure: Connection reset by peer`* while fetching the pinned `gitleaks` tarball, and printed **`the pin is stale or the asset name changed`** followed by **`upstream currently publishes v8.30.1. Pin that version in .github/workflows/ci.yml`**. **The pin already IS `8.30.1`**, the asset it asked for is in the list the error itself prints, and the job's own later step reports *`gitleaks/gitleaks: pinned at 8.30.1, current`*. **A transport error is being reported as a stale pin, with a remedy that is a no-op edit.** The trap is that a session which makes that no-op edit and re-pushes will see green, because the flake has cleared, and will write down that the edit fixed it. **No re-run was spent proving this**: GitHub had started two runs on the same commit and **the sibling `CI-05` PASSED** (`97665619447`), same head, same pins, so the failure did not reproduce and nothing was pushed for it. [`ci.yml`](../../.github/workflows/ci.yml) is outside this fence; reported, not touched.
