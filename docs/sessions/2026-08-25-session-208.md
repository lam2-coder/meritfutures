### 2. `identity_merges`, and why the argument FOR registering it is in this log

The DDL, [`0002_identity.sql`](../../packages/db/migrations/0002_identity.sql):

```
surviving_identity_id  uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT,
merged_identity_id     uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT,
...
CONSTRAINT identity_merges_distinct CHECK (
  surviving_identity_id <> merged_identity_id
)
```

with `identity_merges_surviving_idx` **and** `identity_merges_merged_idx`, so both columns are queried.

`OwnedRule.column` is one column and [`scopePredicate`](../../packages/db/src/scoped-db.ts) renders one `eq`. **Naming the survivor** drops the row from the merged identity, which [`INV-M7-06`](../plans/M07-risk-abuse.md) and `0002`'s own comment keep alive on purpose: *"the pre-merge history is what a dispute about a grandfathered cap is argued from"*, and the dispute is argued from `accounts_at_merge`, a fact about the merged side. **Naming the merged identity** drops it from the survivor, whom the cap now binds. **Both return rows and neither raises**, which is the BOLA class [ADR-008](../decisions/ADR-008.md) scoped the accessor to bound. `firm` is refused mechanically by the suite's *"no firm table carries a column referencing identities"* assertion.

**THE COUNTER-ARGUMENT IS WRITTEN DOWN BECAUSE IT IS GENUINELY STRONGER THAN THE ONE `identity_links` FACES, AND A FUTURE READER SHOULD NOT HAVE TO RECONSTRUCT IT.** `identity_links` carries a canonical-order CHECK, so its two columns are **symmetric by construction** and the choice is arbitrary. These two are **asymmetric**: a hard merge *"repoints ownership into the surviving `identities` row"* ([`plan_size_unlocks.md`](../architecture/data-model/plan_size_unlocks.md), [ADR-070](../decisions/ADR-070.md) section 3), `identities.id` **is** the hard-merged grain, and [`users.md`](../architecture/data-model/users.md) says *"one identity may own several users only through a merge"*. Read together those say the merged identity holds no login after the merge and therefore never holds a scoped session, which would make `surviving_identity_id` cover every read that can actually occur.

**It was not taken, for two reasons stated in the order they weigh.**

1. **It is an inference about application behaviour drawn from prose, against a DDL that says the opposite twice.** Nothing in any migration says a merge repoints `users.identity_id`; the closest statement is a sentence in a data-model page describing the survivor's post-state. The DDL declares two `NOT NULL` identity foreign keys and indexes each. [CLAUDE.md](../../CLAUDE.md) records that the reconciliation session's three worst errors were *"a failure to check a claim against the primary source"*, and the primary source here is the `CREATE TABLE`.
2. **`identity_merges_distinct` guarantees the disclosure that refused `events`.** [Session 195](2026-08-25-session-195.md)'s second reason for refusing `events` is that `identity.merged`'s `jsonb` payload *"names a DIFFERENT identity inside `jsonb`, which no scope rule can express and which `INV-M4-06` forbids the portal to receive"*. **Here that property is a `NOT NULL` COLUMN and a CHECK enforces it on every row**, beside `evidence jsonb` written by a detector -- and `INV-M4-06` is *"the portal never receives detector internals or other identities' ids"*. A scope rule states which rows reach an identity and says nothing about what is inside one, which is the position [ADR-008](../decisions/ADR-008.md) scoped the accessor to stop relying on.

**[ADR-092](../decisions/ADR-092.md) section 3 names this class as a per-TABLE ruling and takes neither column. A transcription rules nothing, so this session took neither either, and wanting a number for it was the stop signal.** On [session 192](2026-08-25-session-192.md)'s stronger model the table carries **no `pgTable` declaration at all**: a declared-but-unregistered table is a `pgTable` that no drift assertion compares, `DDL_NAMES` being derived from `TABLE_KEYS`.

**This is the FOURTH table of one shape**, after `identity_links`, `attributions` and `dedupe_matches`. Four instances is an argument for one entry that rules the shape, and that entry is named in **Next** rather than written here.

### 4. The three rules

**`idempotency_keys` -- `owned` on `identity_id`, NULLABLE.** It is the only column in the body that reaches a person; `key` is the client's own token, `endpoint` a route, `request_hash` a digest, `response_body` a stored response. **This is `ledger_accounts`' shape and NOT `offers`'**, and the difference is a CHECK: `offers_identity_scope_matches` makes `offers`' null biconditional against `scope`, and **this table has no CHECK of any kind**, so `identity_id IS NULL` means *no identity was recorded* and never *the firm owns it*. The DDL already separates the two populations in its own index -- `idempotency_keys_identity_idx (identity_id)` is declared `WHERE NOT NULL` -- and SQL does the excluding, because NULL never equals anything. **What the rule does NOT bound is said out loud in the `why`**: `0017`'s own comment is that replaying a key returns the stored response **verbatim**, and a scope rule states which ROWS reach an identity and nothing about what is inside one.

**`trading_calendar_loads` -- `firm`.** The exchange's calendar belongs to no trader and this row is the provenance of one load of it ([ADR-042](../decisions/ADR-042.md) F-4). No foreign key at all, no identity or account column, and no correct one: a coverage window that differed per trader would not be a coverage window. **`actor text NOT NULL` is a free-text operator string on `0002`'s idiom rather than a `users` reference**, which is the shape [`scope.ts`](../../packages/db/src/scope.ts)'s own header refuses `treasury_balances.recorded_by` for being.

**`trading_calendar_revisions` -- `firm`.** A correction to the exchange calendar is a statement about a DAY. `trading_day` is a date, `prior_row` is `to_jsonb(OLD)` of a `trading_calendar` row, `source_digest` is a SHA-256, `incident_ref` is an incident label, `actor` is the same operator string. **`dependent_row_count` is the column most likely to be misread as tenancy and it is a count**: rows in [`fills`](../architecture/data-model/fills.md), [`daily_marks`](../architecture/data-model/daily_marks.md) and [`rule_states`](../architecture/data-model/rule_states.md) that depend on the day, asserted a second time by [`0033`](../../packages/db/migrations/0033_trading_calendar_revision_required.sql)'s trigger under [ADR-045](../decisions/ADR-045.md). Those three tables are each identity-scoped and this number is not, **because a count across every account is a property of the DAY**.

**`trading_day` carries no `.references()` and the reason is this file's own rule.** The FK is declared inline against `trading_calendar(trading_day)`, but `trading_calendar` is not one of `schema.ts`'s tables **and cannot become one**, so the column alone is transcribed and the constraint is left to the database. A `derived` rule through it is not merely wrong, it **cannot be written**: `DerivedRule.via` is `TableKey` and `trading_calendar` is not a member.
