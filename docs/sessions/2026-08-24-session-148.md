### The database CAN hash it, so the refusal is a ruling rather than a limitation

`pgcrypto` is installed at [`0001:22`](../../packages/db/migrations/0001_extensions_and_enums.sql) for `gen_random_uuid()`, so `digest(rules::text, 'sha256')` runs today. **A trigger comparing that against `rules_digest` would define the canonical serialization of the rule contract to be PostgreSQL's `jsonb::text`**, in passing, on the money path, binding on a TypeScript writer that does not exist yet.

Measured on the same cluster rather than reasoned about:

```
SELECT digest('{"a":1.0}'::jsonb::text,'sha256') = digest('{"a":1}'::jsonb::text,'sha256');  -->  f

'{"a":1.0}'::jsonb::text     -->  {"a": 1.0}
'{"a":1.00}'::jsonb::text    -->  {"a": 1.00}
'{"a":1e2}'::jsonb::text     -->  {"a": 100}
'{"a":1,"a":2}'::jsonb::text -->  {"a": 2}
```

`jsonb::text` sorts keys and normalizes whitespace and **is not canonical over numbers**. So the check would **refuse a legitimate publish**: a draft re-saved with `5.0` where it held `5` is the same rule contract and a different digest. **That is the failure direction a money path cannot take**, and it is why `hash.ts` carries explicit `money()` and `count()` renderers while `jsonb::text` decides the question by accident.

**No temporal fallback exists either.** `plan_versions` carries `created_at`, `published_at` and `retired_at` and **no `updated_at`** ([`0004:52-135`](../../packages/db/migrations/0004_catalog.sql)), so a draft edit leaves nothing for a run to be dated against.

### The ruling: the trigger wins here, and the loser is the only thing that can ever win later

[`0004:183`](../../packages/db/migrations/0004_catalog.sql) states the trigger's cost and **`0047` hedges neither limb**: it can be disabled and it fires per row. It wins on a fact.

```
$ grep -rn 'plan_versions' apps/ --include='*.ts'
apps/site/src/catalog/types.ts:136 ... (read-side types)
apps/worker/src/batch/ports.ts:42  ... (a comment)
```

**Nothing in `apps/` writes a `plan_version`.** A control that would run in a code path nobody has written is not a control, and it would stay absent for `psql`, for a migration and for an admin console.

**What the loser gives up is the part that matters later, and the entry says it rather than only saying why the winner won.** The application path is **the only mechanism that could ever close the staleness state**, because it can call the TypeScript that would produce a digest and a trigger cannot. **So the two are ORDERED, not one refused.** When a publish path is written it should carry the digest comparison and this trigger should stay, because the trigger covers the paths the application is not.

### Two directions nobody would have thought to assert, and both are about the guard NOT firing

**A `BEFORE ROW` trigger fires before the table's `CHECK` constraints.** So the two rows `plan_versions_publish_decision_recorded` exists to refuse reach `0047`'s guard first. **A guard scoped one clause wider would take those refusals over silently**: both rows would still be refused, no probe would fail, and every caller resolving publish failures by constraint name would stop working. Cases `0045 A` and `0045 B` watch them arrive by name with the trigger installed.

**Two `BEFORE ROW` triggers on one table fire in NAME ORDER**, and `plan_versions_publish_decision_is_sound` sorts before `plan_versions_published_immutable` because `'_' < 'e'`. Left unscoped, `0047` would answer first on an already-published row and an **immutability** refusal would arrive worded as a soundness failure. That is why there are two attachments with explicit `WHEN` clauses rather than one, and the probe's `0028` case asserts `0028` still answers in its own words.
