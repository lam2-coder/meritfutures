### 3. THE 503, AND IT IS THE LARGEST FINDING

**[WAVE-06 section 8.1](../plans/WAVE-06-admin-console-transport.md):** _"Every one of the 26 operator routes above answers 503 today."_
**[`src/app/page.tsx`](../../apps/admin/src/app/page.tsx), shipped by `W6-d`:** `const NOT_YET: AdminErrorKind = toAdminErrorKind(503);`

Measured here over a real `compose()` of the modules on disk and Fastify's own `inject`, on the operator surface, **28 registered and 45 withheld**:

| Request | Answer |
|---|---|
| `GET /api/v1/admin/flags`, no cookie | **401** `unauthenticated` |
| `GET /api/v1/admin/liability`, no cookie | **401** `unauthenticated` |
| `GET /api/v1/admin/identities/id-1/graph`, no cookie | **401** `unauthenticated` |
| the same three with `merit_admin_session=any-token` | **500** `internal_error` |

**Both branches are the code saying what it already documented.** With no cookie, `adminHandler` computes `lookup` as `{ kind: 'unknown' }` **without calling `currentSessionSource()` at all**, and `authorizeAdmin` answers 401 on `auth.ts`'s stated order. With a cookie, `currentSessionSource()` throws `AdminReadError`, whose own declaration at [`admin-reads.ts:109`](../../apps/api/src/routes/admin-reads.ts) reads _"IT IS A 500 AND NEVER A 404 OR A 503, on ADR-110's precedent for the same shape one route over: an unwired port is a deployment that has not been finished, and answering ... 'try again shortly' would be this file describing an operational gap as a fact about the estate"_, and [`server.ts:155`](../../apps/api/src/server.ts) maps an unmapped throw to `problem('internal_error', 500, ...)`.

**So the console's one `unavailable` is a status its own API has argued against producing.** The two routes this session adds name **no error kind at all** and carry both real answers in their blocker prose, where an operator reads them. `src/app/page.tsx` is `W6-d`'s file and section 8.1 is the plan's, so neither is repaired here.

**What it is not.** It is not an argument for deleting `unavailable` from [`http/client.ts`](../../apps/admin/src/http/client.ts). That member exists so the console can tell _"not built yet"_ from _"broke just now"_, and the finding is that **no route says 503 today**, not that none ever will.

### 4. THE TWO INV-M6-10 SHAPES, AND THEY ARE OPPOSITE ON PURPOSE

`INV-M6-10` is one sentence: the console renders trader-identifying data **only when the query names a specific subject**. Four screens name none and one names one, so the same invariant produces two different controls.

| | flags queue (`W6-f`) | identity drill-down (`W6-g`) |
|---|---|---|
| the query | names no subject | names one, in the path |
| the rule | **no subject identifier in the served bytes at all** | **every id served is one the query reached** |
| leg one | `assertNamesNoSubject`, the package's own assertion | the closure: subject, root, nodes, both ends of every edge |
| leg two | the three identifiers the document declines to render, asserted absent by VALUE | the root the server answered with **is** the subject the path named, checked first |
| what is rendered instead | position, type, detector, date, and a SCOPE where `account_id` was | the ids, the statuses, the account counts, the link kinds and the confidences |

**`assertNamesNoSubject` is deliberately NOT called on the drill-down, and that is the finding a reviewer should test hardest.** It refuses any uuid in a rendered string, so calling it there would refuse the identity the operator asked about, which is the one thing that screen exists to render. The invariant is not "never render an id"; it is "render one only when the query names one". The closure is **narrower than the licence** rather than a relaxation of the other screens' rule.

### 5. Four findings, none of them in the dispatch, none repaired here

#### 5.1 The 503. Section 3. `WAVE-06` section 8.1 and `apps/admin/src/app/page.tsx`, both outside this fence

#### 5.2 `assertNamesNoSubject` misses a uuid glued to a word character

[`page.ts:184`](../../apps/admin/src/page.ts)'s pattern is `\b[0-9a-f]{8}-...-[0-9a-f]{12}\b`. A word character on either side removes the boundary, so the token is not a match.

| String | `assertNamesNoSubject` |
|---|---|
| `see <uuid>` | **throws** |
| `manual-review-<uuid>` | **throws** |
| `ref:<uuid>` | **throws** |
| `linked_to_<uuid>` | **passes** |
| `x<uuid>` | **passes** |
| `<uuid>y` | **passes** |

**Found by a seed failing to fire.** The first shape of `M6-A-45` asserted that a subject id in `flag_type` was refused; it was not, and the measurement above is why. `page.ts` is `P5-l`'s file, so the flags queue grew its **value leg** instead, which refuses the three identifiers of every row it renders however they are spelled. What survives both legs is a subject id that is in **no field of the response** and is glued to a word character, and that residue is this finding exactly.

**The liability home is covered by neither leg**, and it is the screen whose supplier-controlled string is `movement.feed`, which is the field `M6-A-40` exists for.

#### 5.3 `GET /admin/identities/:identityId/graph` carries three money fields and no as-of

`IdentityGraph` declares `nodes[].total_withdrawable_cents`, `aggregate.open_liability_cents` and `aggregate.payouts_lifetime_cents`, and **no `as_of` and no source anywhere on the response**. `GET /admin/liability` declares `as_of` as its first field, and `LiabilityResponse`'s own header says why: _"a number without its as-of and its source is a number this console may not render"_ (`INV-M6-04`).

**A second, independent mechanism refuses the same render.** [`figure.ts:70`](../../apps/admin/src/figure.ts)'s `ORIGIN_ID` is `/^(P-M6-(0[1-9]|10)|AS-M6-04)$/`, and `figure()` and `absent()` both check it, so a reading raised on M06 section 3.2a has **no origin it may declare** whatever its as-of. Neither repair is inside any WAVE-06 fence: one is an API_CONTRACT field addition and the other widens `figure.ts`'s roster, which is a decision about what M06 section 3.1 fixed.

So the drill-down states all three as a named absence in `PendingPanel`'s shape, beside a second entry naming what section 3.2a asks for that the response has no field for at all: **flags, restriction episodes, admin actions and per-account state.** `IdentityGraph` carries a status, an account count and the edges.

#### 5.4 Every view of the drill-down is supposed to be logged and nothing logs it

M06 section 3.2a: _"every view is logged as an access to the underlying identities, in section 7.9's terms."_ Nothing in this repository writes that row, and it cannot be written before ADR-171 supplies an actor. **The route names the obligation on its own face**, inside the ADR-171 entry, rather than shipping a screen that quietly does not keep it. `M6-A-54` asserts the sentence reaches the served bytes.
