### 2. `required_factor`, read against session 218's branch as the dispatch required

`#290` (UNLANDED) declares `required_factor` **twice, in two registers, and only one of them is a wire field**:

| What it declares | Where | Wire field |
|---|---|---|
| `requiredFactorTable(specs)`, keyed `METHOD /path` | `apps/api/src/routes/auth.ts:889`, applied at `:1109` and `me.ts:126` | **no.** Server-side bookkeeping derived from the route array |

| `RequiredFactor`, six tokens | `auth.ts:154` | section 12's vocabulary verbatim, space included |

**AND THAT BRANCH DOES NOT EDIT [API_CONTRACT](../architecture/API_CONTRACT.md).** `git diff --name-only` over it gives six files: two route modules, one test, [STATE](../STATE.md), its own session log, and the sessions README. **So a field is on the wire and undeclared in an `approved` contract**, which is not a contradiction between two branches but a gap between a branch and the document it implements. Clause 4 closes it, and closes it by transcribing what that branch already sends, so the merge is a no-op for session 218 and nothing of theirs was edited.

**[ADR-093:166](../decisions/ADR-093.md) had already handed the field here in those words**: *"It is `P4-h`'s, listed there, and moving auth's service does not move it."*

**THE PART THAT IS STILL MISSING IS THE PART `INV-M4-14` NEEDS, AND IT IS SAID PLAINLY RATHER THAN COUNTED AS DONE.** `DEP-M4-07` is a sentence with two halves:

> *"Every sensitive endpoint **declares** its required factor, **and the session endpoint reports the session's own factor and elevation**."*

The second half exists: `Me.session` carries `auth_factor`, `elevated` and `elevated_by_factor` at [API_CONTRACT:139](../architecture/API_CONTRACT.md). **The first half, as something a client can read before acting, does not.** A `403`'s extension member is a declaration the client reads AFTER acting, and `INV-M4-14`'s component takes `required_factor` as a required prop it must hold BEFORE rendering. [M04 section 3.7](../plans/M04-trader-portal.md) is written against precisely the difference: *"A boundary that is only ever discovered by hitting it is indistinguishable from a bug, and users route around bugs."*

**Three ways to close it and this slice takes none.** A static table in the portal is refused by `DEP-M4-07`'s own last clause and needs no session to rule. The other two are edits to `GET /me` or to the sensitive endpoints' success responses, and both are the auth surface: `#290` holds section 3's implementation open, and [P4](../plans/P4-portal-and-site.md) section 4.4 says inventing a phase for auth "is not a plan's to do". **A read-screen slice writing a requirement into an approved contract for a branch in review and a phase that does not exist would be the fence widening the dispatch named.**

### 3. Why the banner's shape lands and its endpoint does not

**The shape was never in doubt.** [M04 section 3.9](../plans/M04-trader-portal.md) tabulates the banner field by field against columns and says the quiet part outright: every field is a column *"rather than a string the portal composes"*. All five have been in [`0042`](../../packages/db/migrations/0042_impersonation_sessions.sql) since it landed. **The row that was missing was never a design question.**

**The carrier is the whole ruling.** [M04 section 3.9](../plans/M04-trader-portal.md): the banner *"renders from the session the server resolved, never from client state"*, and *"it survives reload and deep link"*.

| Candidate | What it costs |
|---|---|
| `Me.impersonation` on `GET /me` | **Correct, and not this slice's to write.** That endpoint is *"the trader portal's first call on every page load"* (`#290`'s own header), so the banner and the session it describes arrive together and cannot disagree |
| `GET /impersonation/session` | **Reintroduces `GS-301`**: two resolutions, one page, and a banner that can render from a session the page is no longer served under |
| Client state in the shell | Refused by section 3.9: *"A banner held in memory is gone on the first hard refresh, which is the ordinary way an operator works"* |

**`IMPERSONATION-C1` IS WHAT MAKES THE CARRIER A QUESTION RATHER THAN AN OBVIOUS ANSWER, AND IT IS PASSED FORWARD RATHER THAN GUESSED AT.** An impersonation token can never be the token a trader session carries, in both directions, enforced at [`0042:183`](../../packages/db/migrations/0042_impersonation_sessions.sql). So `GET /me` under an impersonation token resolves something structurally different from `GET /me` under a trader token. **That is an auth-path ruling and not a view ruling**, and the slice that takes it should inherit the question rather than discover it.

**The portal loses nothing today.** [`impersonation-banner.ts`](../../apps/portal/src/shell/impersonation-banner.ts) already renders the type and [`app-shell.ts`](../../apps/portal/src/shell/app-shell.ts) already carries the band. What changed is that the type is now a declared contract shape instead of an undeclared local one, which is what session 158 asked for on this row.

### 4. The five screens

**Seven of [M04 section 3.1](../plans/M04-trader-portal.md)'s eleven now exist**, against three at [session 158](2026-08-24-session-158.md). The four that do not are `SC-M4-01` and `SC-M4-11` (one auth surface, money path), `SC-M4-04` and `SC-M4-10` (P5's, per [P4](../plans/P4-portal-and-site.md) section 6). **None was taken and the seam is reported instead**, which is what `P4-h`'s own cell asked for.

| Screen | File | The one thing it gets right, and how it is enforced |
|---|---|---|
| `SC-M4-05` | [`view/rules.ts`](../../apps/portal/src/view/rules.ts) | Every clause is a `CopyBlock`, so a rule sentence typed in the portal does not compile. Reads **every key the version published** rather than a list of its own, because a portal-side key list fails silently on a new clause. **A version with no copy throws** and names the version, since a rules page rendering nothing is `INV-M4-08`'s failure by omission |
| `SC-M4-06` | [`view/purchases.ts`](../../apps/portal/src/view/purchases.ts) | The diff renders `was` and `now` and **has no field a delta could go in**. The walk is structural over opaque JSON, arrays are leaves, and a key on one side only is a change rather than a skip. `settled` is read off the status union and never off an amount, because a refunded purchase still carries what was paid |
| `SC-M4-07` | [`view/kyc.ts`](../../apps/portal/src/view/kyc.ts) | Five states, an unknown one refused rather than rendered as `pending`, and **section 7.9's vocabulary enforced as a refusal on the wire string** |
| `SC-M4-08` | [`view/certificates.ts`](../../apps/portal/src/view/certificates.ts) | `verify_url` required and a card without one refused, because the page is the authority and the image is what gets forged. An absent amount stays absent. The claims list is asserted to carry no identity |
| `SC-M4-09` | [`view/referrals.ts`](../../apps/portal/src/view/referrals.ts) | The NFA disclosure is a required `DisclosureBlock` field. Earned, payable and paid are never combined: they are three server answers with a clawback window between them, and the subtraction that looks like it reconciles them is also wrong |

**Section 7.9's check is the one worth explaining, because it is not the lint that section asks for.** That section asks for *"a lint over the portal's string catalogue"*. **There is no string catalogue here and the string is not this module's**: `action_required` arrives on the wire, written by whoever wrote the handler, and a lint over portal source would never have read it. So the check is a refusal at the point the server's string enters the trader's screen, which is the only place a check can be made about the string that will actually render. **It is not a substitute for 7.9's lint and does not claim to be**: a lint covers strings this module authors, this covers the one string it renders and did not author, and both are owed.
