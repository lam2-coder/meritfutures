### 2. `INV-M7-10`: what makes the strip list COMPUTED, and how that is proved

`INV-M7-10` reads *"Detector parameters never appear in a trader-audience evidence pack"*, and its own
source column reads *"using SD-M7-03's registry as the strip list"*. `FM-M7-06` calls it **a cross-module
control and neither half works alone**.

**A hand-written strip list is a list that drifts from the thing it mirrors.** `P7-d` seeded eighteen
`detector_definitions` rows and the seed IS the registry; a nineteenth detector added there and forgotten
in `apps/api` would leak on the first export after it shipped, and nothing in this tree would say so. So
`sensitiveParameterNames(registry)` reads the rows THIS EXPORT RAN AGAINST, and the answer changes when
the registry changes.

**The proof that it is computed is not the seed, and [session 282](2026-08-27-session-282.md) is why.**
That session recorded the consequence of a uniformly `true` column in its own words: a pack that computes
its strip list and one that strips every detector unconditionally *"produce byte-identical output, so
`GS-112` passes either way and `INV-M7-10`'s mechanism is untested"*, and the distinguishing row *"cannot
come from this seed"* because there is no `M07` line to cite for an `is_sensitive: false`.

**The distinguishing fixture is a REGISTRY and not a seed row**, which is the move that was available and
was not taken before: `sensitiveParameterNames` is a pure function of rows, so the suite drives it with a
two-row registry, one sensitive and one not, and asserts

- a name the non-sensitive row alone claims is **released**;
- a name a still-sensitive row **shares** is not, because the list is a UNION;
- the computed set and the unconditional set are **different sets**;
- a nineteenth detector appended to the seed is covered **with no edit to the module**.

**And the seed's uniformity is pinned in its own case**, so the day the column acquires its first `false`
the suite goes red and sends the reader to the mechanism cases rather than absorbing the change silently.

**The `_meta` block is not a parameter and its keys are deliberately out of the list.** `P7-d`'s rows carry
`_meta` holding `name`, `input`, `quote` and `is_sensitive_reason`; those are prose keys that collide with
ordinary column names, and sweeping them would strip real trader facts while reading as a redaction
working. The strip list is the TOP-LEVEL parameter names, which is what a threshold is named by.

### 3. THE DEFECT THE SUITE FOUND, IN THIS SESSION'S OWN CONTROL

The "no other identity" check tested each string against an ANCHORED uuid pattern, start of string to end of string. **That reads a value that IS an
identifier and is blind to one that CONTAINS an identifier.**

`tos_clause` is free text an operator writes during a dispute, and **`GS-112` REQUIRES a `trader` pack to
carry it**. An investigator who wrote *"ToS 9.3, coordinated with account `<uuid>`"* has put another
identity into a trader pack **through a field the pack must not drop**, and the anchored check saw nothing
at all: the string is not a uuid, it contains one.

The case that found it was written to drive the end-to-end refusal and **passed against the anchored
version, which is the shape of a test that proves nothing**. Repaired to a scan within strings, pinned by
its own case at `foreignIdentifiers`, and the export-level refusal is watched firing on exactly that
clause while the same clause at a `counsel` audience exports normally.

**It is a property of every free-text column a pack carries**, and there is more than one.

### 9. A LATENT DEFECT IN `gates.mjs` FOUND BY WRITING THIS LOG, REPORTED AND NOT REPAIRED

**Writing this file corrupted [`docs/sessions/README.md`](README.md), and `CI-06g` is what caught it.**

The span writer at [`scripts/corpus/gates.mjs:1219`](../../scripts/corpus/gates.mjs) interpolates the
generated text into the **replacement** argument of `String.prototype.replace`:

```js
next = next.replace(full, `<!--gen:${name}-->${actual}<!--/gen-->`);
```

**A replacement string is not literal text.** JavaScript gives it a substitution vocabulary, and two of
its members insert the parts of the subject the match did not cover. This log's index line contained a
dollar sign immediately followed by a backtick, from a sentence quoting an anchored regular expression,
and the generator therefore wrote **the entire text preceding the span back into the span**: `README.md`
went from 549 lines to 743, with its own frontmatter and its own opening section appearing inside the
generated table.

**Three things about it are worth carrying.**

- **It is silent at write time and loud at check time.** `generate` exited 0 and reported *"1 span(s)
  rewritten"*. `CI-06g` failed on the next run, which is the gate doing exactly its job: the span no
  longer matched its query.
- **`generate` is NOT idempotent under this defect and re-running it does not heal.** Each run rewrites
  the corruption, so the repair is to restore the file and regenerate once from a clean copy.
- **Any generated span is reachable, not only this one.** The vulnerable value is the GENERATED CONTENT,
  so a count span carrying a plain integer is safe by luck rather than by construction, and the next span
  whose query returns prose has the same exposure.

**Not repaired here.** `scripts/corpus/gates.mjs` is outside this slice's fence and the repair is a
one-line change to a runner every gate in the repository depends on: pass a **function** as the
replacement, which suppresses the substitution vocabulary entirely. **The prose in this file was changed
instead**, which fixes this occurrence and not the class.
