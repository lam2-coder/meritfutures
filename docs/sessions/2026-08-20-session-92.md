### `0041` was spent on neither thing it was reserved for, and that is the finding

[ALLOCATION](../decisions/ALLOCATION.md) reserved it as *"widening M16's delivery status to carry `bounced` and `spam_complaint`"*. **Read against [`0019`](../../packages/db/migrations/0019_notifications_and_community.sql), neither half survived.**

| Reserved | What is true |
|---|---|
| add `bounced` | **Already legal.** `0019`'s check is `delivery_status IN ('pending', 'delivered', 'bounced', 'suppressed', 'failed')`. What was missing was the **specification**: M16's lifecycle machine had no `bounced` state, so the schema could store an outcome no document described |
| add `spam_complaint` | **Refused**, on three grounds in M16 section 3.4. A complaint arrives **after** delivery, so writing it into `delivery_status` overwrites `delivered` and destroys the proof of notice `INV-M16-09` rests on. **A trader who complains about a freeze notice would erase Merit's evidence that it arrived, by complaining about it** |

So the number buys **one nullable column**, `contact_channels.complained_at`, because a complaint is a fact about the **destination** and the send path needs something to ask. `notifications` is not touched. Both refusals were **executed, not argued**:

```
NOTICE:  SUCCESS 4  delivery_status ACCEPTS bounced, so 0041 did not need to add it
NOTICE:  REJECTION 1  delivery_status REFUSES spam_complaint, by check constraint
```

### The assertion that matters is the one that keeps the trader logged in

`GS-293` is a bounced security-class message alarming; `GS-295` is a complaint suppressing marketing and leaving security alone. **The way to fail both at once is to make a complaint take the channel away**, so the probe leads with the success case that says it does not:

```
NOTICE:  SUCCESS 1  complained_at exists, nullable, unset by default
NOTICE:  SUCCESS 2  complaint recorded and the channel is STILL LIVE (1 live email channel)
NOTICE:  SUCCESS 3  the grain is the DESTINATION: email complained, push untouched
NOTICE:  REJECTION 2  contact_channels_live_uq still refuses a second live email channel
```

Supersession was considered for the same job and refused for exactly this: `contact_channels_live_uq` is partial on `superseded_at IS NULL`, so superseding the channel leaves the identity with **no live channel of that kind** and the security class with nowhere to go. That is `GS-293`'s lock-out arriving through the remedy.

### Two controls disagreed about migration numbering, and the test was the stricter one

`packages/db/test/migrations.integration.test.ts` asserted **strict contiguity over the files on disk**. `CI-06h` asserts gaplessness over **on disk plus reserved**, and [ALLOCATION](../decisions/ALLOCATION.md) says in terms that "an unspent reservation costs nothing". Writing `0041` while `0038` to `0040` stay reserved-and-unwritten **failed the test and passed the gate on the same tree.**

**The test's own header called it "the weaker half" of `CI-06h`, and that description is what hid the incompatibility.** It was the stronger half. [ADR-066](../decisions/ADR-066.md) reserves `0038` to `0042` for five sessions that land in whatever order they finish, so **the first of them to land was always going to break it**, and F4 was first. Renumbering is not available: the lower numbers are claimed by other sessions and `E2` makes a merged migration unrenumberable.

Now two assertions, **each watched failing on its own before being trusted**: a duplicate `0041` turns the uniqueness half red (`expected 38 to be 39`) and a stray `0050` turns the reservation half red naming `0046` to `0049`. A hole ALLOCATION does not explain still fails, which is the control the file was actually protecting.

### Reported, not touched

- **A same-kind channel rotation is expressible only through a three-step dance, and this predates the branch.** Measured rather than asserted: insert-then-supersede is refused by `contact_channels_live_uq`, supersede-first is refused by the `superseded_by` FK, and a single-statement CTE doing both is refused by the unique index. **It does work** if the replacement is inserted as already-superseded pointing back at the row it will replace, then the old row superseded, then the new one revived. Awkward, undocumented, and not a defect; noted because the next reader of `0019` will hit it.
- **No probe file under `scripts/db/`.** The six assertions above ran by hand. A probe there would be the durable form, and it costs three more out-of-fence files: the workflow step, `CI-06h`'s needle list, and `CI-06s` is the gate that checks both.
- **No `notification.bounced` or `contact.complaint_received` event.** [EVENTS](../architecture/EVENTS.md) is outside this fence and **no gate binds a module plan's event table to it**, so inventing a name here would have been silent drift. The alarm fires on the **delivery record** instead, which is what [ADR-066](../decisions/ADR-066.md) requires of the digest alarm for the same reason.
- **`GS-270` and `GS-271` were owned by M16 from [ADR-039](../decisions/ADR-039.md) and section 8.2 never listed them.** The ownership index said eleven while 8.1 said six. Both added rather than reported, because a corrected count with no rows behind it is the same defect one line on.
- **No E2 header on `0041`.** The regime is non-money by the brief and by M16's own classification, and the column suppresses the marketing class only. The adjacency is real enough to name in the file header: [`0034`](../../packages/db/migrations/0034_reversible_contact_addresses.sql) carries an E2 header for work on this same table because auth is a money path. **If the desk wants the founder's read on it, that is a one-line change and it moves `gen:e2_files` from 27 to 28.**
- **Admin resend and download are `M06`'s and were not touched.** `GS-294` is registered to M16 because the snapshot it re-sends is M16's; the surface is not.
