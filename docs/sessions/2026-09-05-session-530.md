### 3. What was found, and why nothing was wired

**THE VALUE IS FOUNDER-OWED.** The corpus states three numbers and every one of them belongs to a plan: Core EOD 10, Merit Rapid 5, Direct 5, in constitution 0.4 and again per size in [M01](../plans/M01-rules-engine.md) appendix A. [ADR-238](../decisions/ADR-238.md) ruling 1 refuses all three ways of reading a per-plan number as the per-identity base, and the trap is sharper than it looks: **`GS-094` says "cap of 10" and 10 is Core EOD's number**, so the value a hurried session would copy is precisely the maximum-over-versions reading the ruling names first. `0074`'s own header had already written the sentence: *"a number written here today would be a number this session invented"*.

**AND THE ROW IS NOT LANDABLE HERE AT ALL, WHICH THE DISPATCH COULD NOT HAVE KNOWN.** [ADR-284](../decisions/ADR-284.md) added `0076_firm_parameter_write_control.sql` after the blocker text was last touched. A `firm_parameters` row now needs a `dual_control_approvals` row whose digest matches, **two distinct `owner` operators**, and an `admin_actions` row; `0076` refuses to seed an operator because *"a real operator's identifiers are not this repository's to hold"*, and it deliberately FAILS on a deployment that wrote a cap by hand. **So the founder owes two things rather than one: the number, and the operator directory the approval names.** No migration number is taken, because there is no migration this repository is allowed to write.

**`Me.kyc.placement` HAS NO READER.** API_CONTRACT section 3 types it as a bare `string` while `verified_at` beside it is nullable, so an unverified trader still needs one. The settled fill is `pendingTrigger` in `routes/kyc.ts`, the earliest UNREACHED member of the trader's own pinned trigger set, computed from the seven `KycGateFacts` a `KycBackend` measures, and **this deployable holds `UNWIRED_KYC_BACKEND` with no `databaseKyc` factory for a wiring slice to install.** A second fill written in `auth-backend.ts` would be a second statement of [ADR-021](../decisions/ADR-021.md)'s trigger ruling, in the file least likely to be read beside the first.

**`Me.accounts_count` HAS ONE READER AND NO PRODUCER.** It is projected in `routes/me.ts` and computed nowhere. `AccountCapRow.liveAccounts` is declared in `routes/checkout.ts` on a port that is itself blocked and **nothing in the tree produces the number**; [ADR-238](../decisions/ADR-238.md)'s own approval block registered exactly this and it is still true. `account_status` declares **seven** members and the corpus never says which are live; `graduated` and `provisioning_pending` are the two a reader would disagree about, and [ADR-260](../decisions/ADR-260.md) already refused to decide a comparable question inside a narrowing function nobody reads twice.

**SO `readMe` IS NOT IMPLEMENTED.** An implementation would call a door that throws on every deployment this tree can produce, turning an honest 503 into a 500, and it would still owe two fields.

### 6. Blockers and landmines

- **THE FOUNDER OWES THE NUMBER AND THE OPERATORS TOGETHER.** `0076` will not accept a cap approved by a name in no directory and refuses to seed one, so a future row dispatched to "write the cap once the number is ruled" will find no migration it may write. **The act is a deploy, through the dual-control path.**
- **A DISCHARGED BLOCKER IS THE HAZARD HERE, NOT AN UNDISCHARGED ONE.** The day the cap row lands, `readMe` is still two fields short. `me-blockers.test.ts` is what says so; without it the next reader meets a satisfied cap clause beside a 503.
- **`Me.kyc.placement` MAY BE A CONTRACT BUG RATHER THAN AN ABSENT ADAPTER.** A founder may rule the field nullable, which discharges that finding entirely. This row is not entitled to take that ruling and says so in its approval block.
- **THE `firm_parameters` WRITER SEARCH IS A REGEX OVER TWO `src` TREES AT ONE INSTANT.** A writer built out of a computed table key would pass it. Every call site in this tree passes the key as a literal, but that is not proven and it is the weakest assertion in the new file.
- **ROW `340` IS RESERVED WITH NO HOLDER NAMED** and the dispatcher resolves it by hand at merge.
