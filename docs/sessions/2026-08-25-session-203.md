**The prediction that M21's slice would be almost entirely `firm` holds, and it holds for the six that were already there as well**: five of the six pre-registered tables and both new ones are firm, and `accounts` and `rule_states` are the only two of the eight a trader can reach at all.

### 2. `plans` is `firm` because there is no identity column and no correct one

Three rows: `core_eod`, `merit_rapid`, `direct`. [`0004_catalog.sql`](../../packages/db/migrations/0004_catalog.sql) gives it `id`, `code`, `name`, `is_active`, `sort_order`, `created_at`, `updated_at`, and **not one of the seven is an identity or reaches one**.

**It is `plan_versions`' reason one hop further up.** Every identity is offered the same three plans, and the link runs the other way: a version names its plan, an account names its version. A `derived` rule through `plan_versions` would be the refused shape twice over, because that parent is firm too.

**`is_active` DELISTS AND NEVER DELETES**, in the table's own words: a plan nobody can buy still has to explain the accounts sold under it. So a retired row is firm for exactly as long as a live one, and there is no state in which this table acquires an owner.

### 3. `simulation_runs` is `firm`, and the trap is weaker than the one this file already names

[`0045_simulation_runs.sql`](../../packages/db/migrations/0045_simulation_runs.sql), nineteen columns. The subject of a run is a **parameter set**, its population is synthetic, and no person's rows are read to produce it: `INV-M21-02` makes the designer's simulation read-only compute holding no grant on any account, ledger or engine-verdict table, so there is no identity whose data went in.

**`requested_by` is the available mistake and it is smaller than `treasury_balances.recorded_by`, not larger.** It is `text NOT NULL` with **no foreign key at all**, written on `dual_control_approvals.requested_by`'s precedent, so it does not even name a `users` row to derive through. Had it been one, the reading it would produce is this file's own named failure: the firm's plan economics scoped to whichever operator pressed the button.

**`plan_version_id` is the one that compiles.** It is a foreign key to `plan_versions` and reads exactly like the `hop` that `daily_marks` and `rule_states` make to `accounts`. It is not one, because `plan_versions` is firm and a chain terminates at `owned` or at `root` or it does not terminate. It is **nullable** besides, deliberately, because the run is over a DRAFT that may not yet be a row -- which is why `rules_digest` and `sizes_digest` sit beside it rather than instead of it.

### 5. [ADR-094](../decisions/ADR-094.md)'s fold applies nothing to either table

Re-derived over all 47 migrations with the multiline `ALTER TABLE ... ;` match the suite itself uses: **no `ALTER TABLE` statement in the tree names `plans` or `simulation_runs` in any shape.** No `ADD COLUMN`, no `DROP COLUMN`, no `ALTER COLUMN`, no `RENAME`, and no `ADD CONSTRAINT` either.

So both are among ADR-094's 99 undrifted tables, `refused` is empty for both, and neither contributes to the non-vacuity assertion, which still passes on the eight drifted tables sessions 182, 191 and 193 registered. **A session registering an undrifted table writes no less than one registering a drifted one; the fold is in the suite and not in the transcription.**

### 6. Two tables named by the module and deliberately not registered

**`competitor_plan_models`, `SD-M21-03`. **`plan_size_unlocks`, and this one was a judgement rather than a fact.** [`0044`](../../packages/db/migrations/0044_fee_back_and_ladder_unlock.sql) landed it and [session 170](2026-08-24-session-170.md) counts it as `DEP-M21-06` half met, which is what makes it reachable for M21's parameter form at all. It is left, for three reasons that agree:

- **`0044` attributes it to `SD-M18-04`**, `M18` names it **four** times and M21 names it **zero**; M21 section 1.3 says of the four absent parameters that *"this plan does not draw fields for them"*.
- **It is `owned`, not firm.** `identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT`, with the DDL's own note that `identities.id` is the hard-merged grain because a merge repoints ownership into the row. **An `owned` rule is where a wrong column is a BOLA failure that returns rows**, and the argument for the right one is made in [M18](../plans/M18-graduation-track.md), which this session does not hold.
- **[ADR-092](../decisions/ADR-092.md)'s reason for making the owner the table is that the `why` states the TABLE's tenancy**, and a session that has not read the module owning the behaviour is not in a position to write it. Session 201 holds M18 and is running concurrently.

### 7. One non-edit, reported rather than made

`plan_versions.plan_id` is `uuid NOT NULL REFERENCES plans(id) ON DELETE RESTRICT`, declared **inline** in `0004`. [`schema.ts`](../../packages/db/src/schema.ts)'s header rules that a column carries `.references()` *"ONLY WHEN its `CREATE TABLE` body declares the FK inline AND the target is one of this file's tables"*, and registering `plans` makes the second half true for the first time.

**The line is not edited and the reason is not laziness.** The rule is a necessary condition and not a requirement; `.references()` is compared by nothing in this package, because the fold reads `ADD COLUMN` and deliberately ignores `ADD CONSTRAINT`; and the line belongs to session 182's `planVersions` object literal, which is exactly the shape [P4 section 11](../plans/P4-portal-and-site.md)'s tranche-1 landmine describes -- git aligns conflicts on the shared `createdAt` / `});` tail, so a careless resolution splices one table's fields into another's. **Whoever wants the reference makes it a one-line change on a quiet tree.**

### 9. The merge, and why the figures above are the base rather than the result

**[Session 197](2026-08-25-session-197.md) merged while this branch was open**, moving `main` from `3c9c2d3` to `92ea3d9` with M08's three affiliate tables. **Every figure in sections 1 to 8 is true at this session's base and the merge result is different**, which is [ADR-092](../decisions/ADR-092.md)'s *"a session cannot know its own slice size before it runs"* arriving on the count rather than on the slice: the slice was unaffected, because M08's three and M21's two are disjoint.

**All five files conflicted textually, which is [ADR-092](../decisions/ADR-092.md) section 4's fourth row and the loud outcome it predicts.** Every resolution was keep-both and every one was done STRUCTURALLY: [`schema.ts`](../../packages/db/src/schema.ts) was rebuilt from `main`'s copy and diffed against it to prove nothing but the header count differed, and only then were the two whole declarations re-appended. **Two of the four code hunks were aligned on a shared tail exactly as [P4 section 11](../plans/P4-portal-and-site.md) warns** -- `plans` against `affiliates` on `createdAt` / `updatedAt` / `});`, and `simulation_runs` against `affiliate_clicks` on `});` -- so a keep-both of the hunk rather than of the declarations would have spliced this session's columns into session 197's object literal.

| Figure | Base `3c9c2d3` | `main` `92ea3d9` | Merged |
|---|---|---|---|
| `TABLE_KEYS.length` | 53 | 56 | **58** |

**ONE LINE THAT WAS NOT THIS SESSION'S WAS CORRECTED, AND IT IS NAMED RATHER THAN QUIET.** [`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts)'s comment above the totality test states the unreachable figure twice, and on `92ea3d9` the two disagreed: *"the other 55"* beside *"`identity_links` IS ONE OF THE 58"*, the second left at its pre-197 value. **Both now read 53**, which is 111 minus 58, because they are one derived number and the merge is where it was recomputed. **Session 197's own STATE section and log were not edited.**

### 10. The second merge, where first-writer-wins actually decided something

**Integration batch A merged sessions 195, 196 and 202**, moving `main` from `92ea3d9` to `9cf3feb` at **64 of 111**. [Session 195](2026-08-25-session-195.md) registered **`plans`** on the way through, so [ADR-092](../decisions/ADR-092.md)'s first-writer-wins decides it: **session 195 merged first, `plans` is session 195's, and this session's row rebases out.**

**Nothing was re-argued, which is what the ruling is for.** Both `why` fields reach the same answer in different words -- no identity column, no correct one, the link runs the other way from the catalogue with a version naming its plan and an account naming its version. Session 195's transcription is taken as it stands, and it is better than this session's draft in one place: `code: text('code').notNull().unique()` against `code: text('code').notNull()`, where `0004` declares `code text NOT NULL UNIQUE`. **The first writer's row was not edited to match this one's prose.**

**So the count moves twice and the honest form is the last one.** The slice was two at the base and is **ONE at the merge**: `simulation_runs`, with seven of M21's eight already registered. That is [ADR-092](../decisions/ADR-092.md) section 9's *"a session cannot know its own slice size before it runs"* in the direction it names -- a sibling registering a shared table first -- after section 3's *"the other rebases four rows out"* had already been demonstrated on the wallet tables by sessions 196 and 202.

**ONE AUTO-MERGE ARTIFACT IS WORTH RECORDING BECAUSE THE COMPILER WAS NOT THE THING THAT CAUGHT IT.** Git produced a **duplicate `plans,` in [`scope.ts`](../../packages/db/src/scope.ts)'s import list**, outside any conflict hunk, because both sides added the specifier at different sorted positions.
