### 2. The registration was built rather than believed, and the dispatch was right this time

`discoverRouteModules()` then `buildServer({ surface, modules })` for `public` and `operator`, reading `CompositionReport.registered`:

```
public:    45 registered, 23 withheld

GET /purchases                        REGISTERED, public
GET /plans/:planId/versions/:version   REGISTERED, public
GET /accounts/:accountId/certificate   REGISTERED, public
GET /certificates                      REGISTERED, public

```

**All five, including the two the dispatch said session 297 landed.** A dispatch has been wrong about a registration twice in this repository and this one was not; the measurement was still run, because the alternative is trusting the class of statement that has already been wrong.

**AND THE MEASUREMENT DOES NOT END AT THE REGISTRATION, WHICH IS THE FINDING THIS SESSION ADDS.** [`account-reads.ts`](../../apps/api/src/routes/account-reads.ts)'s `readCertificate` rejects with a stated blocker -- section 6 types `image_url` as a signed URL and *"nothing in this tree can produce one"* -- and [`certificates.ts`](../../apps/api/src/routes/certificates.ts) ships `UNWIRED_CERTIFICATE_BACKEND` as its default, on its own argument that *"an empty list is a trader being told they have no certificates"*. **So both certificate rows answer 503 for every caller today.**

That is a REGISTERED ENDPOINT FAILING, which is the `error` arm, and it is emphatically not `unavailable`. The portal learns it from the status line it was given and never from a table of what this repository happens to have wired, because a client that special-cased a 503 into "waiting on an endpoint" would report every real outage as a screen still being built. **The 503 is in the test's refusal list beside the 401, the 404, the 429, the 500 and the 403 for exactly that reason.**

### 3. What SC-M4-08 could not reach, and why it is a measurement rather than a shrug

The certificates screen assembles per account and per kind. Two documents already written into this segment decide where those account ids may come from, and neither of them is this session's:

> `apps/portal/src/app/(purchases)/fixtures.ts`, on `CERTIFICATE_REQUESTS`: *"The accounts a trader holds are `GET /accounts`, which is SC-M4-02's read and session 259's segment; asking for it here would be this page reaching into that one."*

> `apps/portal/src/app/(purchases)/ports.ts`, on the list endpoint: *"The day a handler exists, this port gains a method and the assembly above is what it replaces."*

**The handler exists and the port still gains no method, and the reason MOVED rather than disappearing.** `GET /certificates` answers section 6.3's `CertificateListResponse`, whose item carries `state`, `code`, `deferred` and `revoked`. [`api/types.ts`](../../apps/portal/src/api/types.ts) transcribes `CertificateResponse` and no list item; `model.ts` and `view/certificates.ts` consume the singular row's shape. Reading the list is a transcription in the contract's file plus a second shape through two rendering files, which is a restructuring of this segment rather than a `load` and a guard.

So `loadCertificates()` passes `requests: null`, which is `app/accounts/source.ts`'s `marks` and `app/referrals/data.ts`'s `disclosureText` exactly, and `loadCertificatesFrom` is exported so the wired path runs today through the real client rather than first running in production on the day the list lands.

### 4. The third `why`, and why it is measured rather than invented

Session 290 gave a LATE read and a REFUSED read different types so that a refusal could not be rendered to a trader as something Merit is still building, and gave `PendingRead` two reasons: `no_api_origin` and `nothing_serves_it`. **This segment measured a third fact that is neither.**

`GET /certificates` is in `CompositionReport.registered`. Saying nothing serves it would be false about a row session 297 landed; saying the origin is unset would be false about a configured deployment. **`no_transcription` names what is actually missing**, and it is not new here either: `app/accounts/source.ts` refused `GET /accounts/:accountId/marks` on precisely this fact an hour before session 290 wrote the other two reasons -- *"`../../api/types.ts` declares `MarkListItem` and NO envelope type at all"* -- and had no word for it.

**`RefusedRead` IS NOT DECLARED IN THIS SEGMENT.** [ADR-168](../decisions/ADR-168.md) clause 3's refusal is `GET /affiliate/creatives` and it is `referrals`'; this segment has no refused read, and an empty second copy of a type is not the vocabulary being kept, it is a shape waiting to be filled by whatever the next author has to hand.

### 5. The `.png` row, demonstrated rather than described

[ADR-168](../decisions/ADR-168.md) clause 2 admitted `GET /certificates/:code/image.png` and its finding 5 records that an earlier draft dropped the extension. It is API_CONTRACT section 1's first non-JSON success response and section 1's conventions presume a JSON body. **This segment does not call it, for two reasons and either alone is enough:**

1. **The screen holds no `code`.** The row is served off `certificates.code` and `CertificateResponse` does not carry it, which `model.ts` states in its own field comment on `image_url`. What this screen renders is the response's own signed, time-limited URL.
2. **The client reads JSON.** `get` performs `await response.json()` on every 2xx and maps a body that is not JSON to `server_error` with the status it did have. So a PNG through this client is an error, correctly, and the repair is a second method on ADR-162's file.

The second is asserted rather than asserted-about: a 200 carrying image bytes comes back `{ ok: false, error: 'server_error', status: 200 }`. The path is named once in code, as a constant, and is handed to no request.

### 6. The disclosure boundary, asserted over the bytes of all three arms

[`page-certificates.test.ts`](../../apps/portal/test/page-certificates.test.ts) already asserts INV-M11-01's absences over the rendered fixture page. **A state component is a second way onto the same screen**, and an endpoint path carrying an account id, or an error sentence quoting a response, would be a value arriving past every assertion written about a card.

So the new suite renders all three arms -- `ready` from the wire, `unavailable` from the page with no origin configured, `error` from the component -- and asserts over each that no `certificate_id`, no account identifier and none of `@`, `identity`, `lifetime`, `cumulative`, `balance` or `total` appears in the bytes. **Nothing in `states.ts` interpolates a response, a route parameter or an identifier**: the pending list renders the read as its own document spells it, `:accountId` and all, and the error arm renders one of five fixed sentences with no status number.

The repair is one line in [`app/payouts/page.ts`](../../apps/portal/src/app/payouts/page.ts), which this fence did not hold.
2. **THE PURCHASE HISTORY CAN BE A PAGE AND CANNOT SAY SO.** `app/calendar/load.ts`'s paging decision is three parts and this segment keeps two: one page, at the contract's maximum. The third -- *"THE SCREEN SAYS WHICH IT GOT, AND IT CANNOT COMPILE WITHOUT SAYING"* -- needs a required prop on `purchases-screen.ts` and a field on `model.ts`, both read-only here. `model.ts`'s `unpairable` reset panel is the half that was already there and it is the half that matters most.
3. **ONE 404 CARRIES TWO FACTS.** `GET /accounts/:accountId/certificate` answers `problemNotFound` for an account with no certificate of that kind, and INV-M4-07 gives an account that is not the caller's the same 404 so existence is not confirmed to a stranger. The segment renders the common one -- no certificate -- because the requests are built from the trader's own accounts. Distinguishing them needs a field the response does not carry.
4. **`GET /certificates` NEEDS A TRANSCRIPTION AND TWO RENDERING FILES.** Section 3.
