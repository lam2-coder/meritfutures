### The finding set, re-measured before anything was written

**Exactly one orphan run of two or more rows existed under `docs/`**, and it is the one the brief named: **[STRATEGY](../testing/STRATEGY.md):238-243, six rows**, holding `CI-06p`, `q`, `r`, `t`, `s` and `u`. `S6` had already repaired ALLOCATION's four. The set matched, so the session proceeded.

**The cause was three lines at `:235-:237`:** a re-inserted header row, a re-inserted delimiter row and a blank line, which is the review desk merge script's keep-both resolution landing mid-table. Deleting the three rejoined the six rows to the table starting at `:218`.

### Landmines

- **THE GATE INVENTORY DID NOT RENDER SIX OF ITS OWN GATES, AND `CI-06u`'s ROW WAS ONE OF THE SIX.** A section whose purpose is to say what each gate checks was, for six of twenty-two, saying it as prose that no parser read and no renderer drew as a table.

- **BE EXACT ABOUT WHAT WAS BLIND, BECAUSE THE SATISFYING VERSION IS FALSE.** It reads better to say the fragment hid six gates from the runner. **It did not.** `strategyGateLetters()` ([gates.mjs:2890](../../scripts/corpus/gates.mjs)) is a **line-level regex** over lines starting with `|` and requires no delimiter row, so **`CI-06p` parsed all six letters throughout** and its uniqueness and gaplessness assertions held the whole time. The damage was to **rendering** and to **`CI-06u`**, which builds tables from maximal pipe runs and keeps only those carrying a delimiter. Overclaiming here would have put a false sentence into the inventory that exists to describe the gates truthfully.

- **A NUMBER IN THE FIRST COMMIT MESSAGE WAS INFERRED RATHER THAN MEASURED, AND IT WAS WRONG.** The message claimed `CI-06u`'s in-scope table count moves **918 -> 924**. Measured both sides, it is **924 both times**. `:234` and `:235` are consecutive pipe lines, so the re-inserted header and delimiter joined the run above them rather than starting a second table; the table count could not move. What moves is **six rows from unread to read**: `STRATEGY.md` goes from *13 parsed tables, 125 parsed lines, 1 discarded run of 6 lines* to *13 parsed tables, 129 parsed lines, 0 discarded runs*. The commit was amended with the measurement before the branch had a pull request. **This is the corpus's own recorded failure mode arriving again: a correct observation followed by one unchecked inferential step.**

- **`CI-06p` DOES NOT ASSERT THAT AN IMPLEMENTED LETTER HAS A ROW IN THE INVENTORY, AND NOTHING ELSE DOES EITHER.** Its three assertions are uniqueness over the rowed letters, **implemented against [ALLOCATION](../decisions/ALLOCATION.md)'s letter table**, and gaplessness. **None of them is "implemented against STRATEGY."** So a gate can be implemented, reserved and entirely absent from section 4.4 with the runner green. Verified on this ref: rowed `a`-`u`, implemented `a`-`v`, and `v` was the only implemented-but-unrowed letter, which is exactly the state this session repaired. **Named rather than fixed**: it is one line and it is a second objective.

- **THE RUN-LENGTH MINIMUM IS A CHOICE AND IT IS MEASURED, NOT ASSUMED.** `ORPHAN_MIN_ROWS = 2`. A single isolated pipe line claims nothing, because a sentence starting with a pipe is prose and a gate calling it a fragment reports on English. **Counted over `docs/`: zero single isolated pipe lines exist**, so the concession costs nothing today and is made against tomorrow. **The cost is stated in the gate's own comment: a genuine one-row orphan is invisible to `CI-06v`.**

- **THE GATE REUSES THE RUN SPLITTER RATHER THAN CARRYING A SECOND ONE.** `markdownTables` already computed every maximal pipe run and **threw away exactly the set this gate needs**, so it is now `markdownRuns(body).filter(has delimiter)`. Writing a second splitter is the defect [session 20](2026-08-15-session-20.md) removed from this runner when `CI-06b` and `CI-06c` carried two regexes for one document set, ten lines apart, agreeing until they did not. **The refactor was verified behaviour-preserving at 22 of 22 before the gate was added.**

- **A COMMENT IN THE RUNNER WENT STALE THE MOMENT THE REPAIR LANDED.** The block above `isDelimiterRow` said a second delimiter row inside a table "is a keep-both artifact in its own right, and STRATEGY section 4.4 carries one today". The repair removed it. Corrected in the same session rather than left for a reader to trip over.
