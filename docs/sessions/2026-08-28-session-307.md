### The plan, written before the ruling, per ADR-003 strict

The dispatch reserved ADR-172 for two findings and asked whether they are one
ruling or two. **They are two, and only one of them is a ruling.** Both premises
were checked at the primary source before anything was written.

**Finding 1, `usePayoutBackend`, CONFIRMED.** `PayoutTx.ledger` is a
non-nullable `LedgerTx`; `LedgerTx` needs `insert` on `ledgerTransactions` and
`ledgerEntries`; both are scope class `derived`; `ScopedTx.insert` takes
`OwnedTableKey` and `insertUnder` takes `ParentedTableKey`, which is
`Extract<DerivedTableKey, 'sessions'>` and a closed list of one. Only `SystemTx`
satisfies it, at a `SystemReason` that ADR-165 ruled gains no member. No live
deployment can construct a `PayoutBackend`. **This is the load-bearing ruling and
it takes the number.**

**Finding 2, `IdempotencyStore`, REFUTED as stated.**
[`apps/api/src/idempotency-store.ts`](../../apps/api/src/idempotency-store.ts)
exists and implements all three methods. The dispatch's own fence asked whether
`updateAt` "may already be exactly that" addressed update, and **it is**: the
store's `complete` is `tx.updateAt(TABLE, { key }, ...)`, which renders
`WHERE identity_id = $1 AND key = $2`. The `systemTx`/`firmTx` hardcoded
`undefined` is a true fact about doors this store does not use.

**But `useWithdrawalBackend` stays blocked, for a truer reason.** Wiring it would
not be safe, and the reason is not the store. Written up in the ADR.

**The plan.** ADR-172 rules finding 1 and disposes of finding 2. The stale
premise is corrected where it is written down inside the fence. No port is
wired, so the `{declared, wired, blocked}` triple does not move. No migration is
needed and none is taken.
