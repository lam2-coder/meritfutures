### 2. Why a new module, and not `accounts.ts`

**`accounts.ts` had already thought about this and declined in writing.** Its header lists all four of these paths as belonging to the contract's account section, and its `RuleStateRow` note says of `engine_gates` and `context_gates` that they *"are `/eligibility`'s and are somebody else's endpoint"*. This session is that somebody. Three reasons it is right rather than merely inherited:

1. **[ADR-100](../decisions/ADR-100.md)'s registry makes a new file free and an edit expensive.** The module list is the directory listing and is never written down, so a new `routes/*.ts` collides with nothing, while four more endpoints inside `accounts.ts` would put this diff in the same file as every later edit to `GET /accounts`.
2. **The ports are disjoint and the tables are different.** `AccountsBackend`'s three methods all render `AccountListItem`/`AccountDetail` off `accounts`, `rule_states`, `plan_versions` and `kyc_verifications`. Of the four here, one reads `daily_marks`, one needs `events`, one needs the rules engine and one reads `certificates`. Merging them would give `start.ts`'s single `useAccountsBackend(...)` line a backend most of which refuses, and would make `resetAccountsBackend()` a shared fixture for two unrelated slices in one suite file.
3. **The paths are disjoint, which is what ADR-100 actually requires.** None of the four is declared anywhere else, so `compose`'s duplicate `METHOD /path` refusal has nothing to catch.

**The four are ONE module rather than four** because they are one path family, they share one tenancy resolution and one 404 shape, and they land on one branch in one session: four files would be four copies of the same port scaffolding bought with no concurrency at all.

### 4. The two things the contract underdetermines, ruled here and reported

**Neither is a decision this session claims authority for.** Both are stated beside the code that makes them and both are in the pull-request body.

**`corrected`, on a day that carries two marks.** Section 6 says it is *"true when this day has a superseding mark"*, and `daily_marks` makes a correction a NEW row pointing the old one at it, so a corrected day holds two rows and the sentence reads two ways. **(a)** every row is an item, `corrected = superseded_by IS NOT NULL`: the day appears twice, the chart draws two balances at one x, and the flagged one is the SUPERSEDED row, a balance Merit no longer asserts, plotted as if it did. **(b)** the current row is the item and `corrected` says the day was corrected. **(b) is taken, on the money rule rather than on taste**: [`apps/portal/src/view/marks.ts`](../../apps/portal/src/view/marks.ts) plots the series with no deduplication and no gap filling by design, so under (a) the equity chart states a superseded balance as a fact about somebody's money. (b) also makes the field non-trivial, because the current row of a corrected day has no superseding mark of its own.

**The list envelope.** Section 6 types the ITEM and does not write the envelope; section 1 does, generically -- *"Responses carry `{ data, next_cursor }`"* -- and section 6's own `GET /wallet/entries` row writes the pair out longhand for a list whose item type it declares the same way. So the envelope is transcription rather than invention, and a bare array would be the one list response on this surface that does not carry a cursor.

**One thing that is NOT ambiguous and is ruled anyway: a day with a mark and no `rule_states` row is OMITTED.** `floor_cents` and `withdrawable_cents` are not columns of `daily_marks`; both are `rule_states`'. `accounts.ts`'s ruling applies to the same two columns: *"a zero balance beside a zero floor is a readable, false statement about somebody's money"*, and a floor of zero on an equity chart is a breach line drawn where no breach line is.

### 5. Reported and not repaired

**`accounts.ts`'s header states that `apps/api/package.json` does not declare `@merit/rules-engine`, and it does.** The sentence is the load-bearing half of that file's argument for refusing `readProgress`, and the package was added by session 252 for `routes/payouts.ts`. **The refusal survives the correction on the other half** -- `0004_catalog.sql`'s *"there is no plan parameter anywhere in application code"* and `trading_calendar` being unreachable through every door -- so nothing about that 503 changes. `accounts.ts` is outside this fence and the sentence is reported rather than edited, on the precedent that file itself set when it corrected `package.json`'s stale `//` key rather than leaving it beside a tree that refuted it.

**`GET /admin/wallet/reconciliation` and the four admin writes are still unregistered.** They are money-path admin work with their own sessions and were not touched.
