**The five checks, and none of them mints an identifier.** [ADR-074](../decisions/ADR-074.md) makes a definition site a row inside a **declared** register, so a `<PREFIX>-nn` series invented in a CI script would be a claim on a namespace with no allocation table. Each check is named by the corpus row it enforces: `ADR-073` section 5 (the funnel is non-empty), `RE-S-06`/`INV-17` (the lifetime bound), `FM-05` with `ADR-049` (refusal kinds), `INV-M21-04` (provenance and sample size, in both directions), and `SIMULATION_HARNESS` section 7.2 (one seed, one result).

### The check that would have been left out, and why it is first

**ADR-073 section 5 rejected `CI-09`'s replay leg because with zero stored rows `runReplayAudit`'s `OI-14` refusal does not fire**, so a nightly "would report `accountsAudited: 0`, `diverged: 0` and exit green, every night, over nothing". The ruling carries the obligation forward rather than losing it with the condition: "a leg whose activation condition is a seeded world must assert that the world is there."

**That failure is reachable in the leg that WAS built, and the falsification case demonstrates it rather than describing it.** Under a one-session window no account passes an evaluation, so nothing reaches funded. `RE-S-06`'s bound is then compared against an empty set, **holds, and reports `pass`** with the detail `the largest lifetime extraction over 0 funded account(s) is 0c`. A nightly carrying only the hard assertion would have been green on a run that simulated nothing. The funnel check is what refuses it, and `CI-09/empty-funnel` demands that exact string in the output so a future edit cannot quietly stop asserting it.

### No calibration band is supplied, and that is the session's one judgement call

[SIMULATION_HARNESS](../testing/SIMULATION_HARNESS.md) section 5 states eleven `RE-S-nn` bands and says "the nightly run asserts each band and fails the build on a breach". **This run asserts none and supplies no band at all.** Three artifacts are missing and each was checked rather than argued:

| | What is missing | Checked how |
|---|---|---|
| **The real lineup** | Section 5's bands are stated "lineup blended". The scenario's plan is synthetic | The transcription of the real lineup is `packages/rules-engine/fixtures/plans/`, whose records are the `rules`/`size` shape rather than `resolvePlan`'s `PlanRulesJson`. Reaching them needs a resolution path outside this fence |
| **The skill mixture** | `PP-01` to `PP-04`. `RE-S-01`'s pass rate is a function of a **drift range this file picked** | [`packages/harness/README.md`](../../packages/harness/README.md) lists the mixture under what the package does not do: "the day model draws a per-account drift and volatility from caller ranges" |
| **The trading calendar** | `DEP-M21-08`. The sessions are consecutive weekdays | Section 4: a synthetic calendar "would silently remove the most calendar-sensitive rules from the run". There is not one calendar row in this repository (P2 section 6) |

**The choice was between a band that fails on arrival and no band.** [ADR-073](../decisions/ADR-073.md) section 1 rejects the first in its own words, about a rule applied to a table it cannot satisfy: it "produces a gate that FAILS ON ARRIVAL". The other repair, widening a band until the run fits inside it, is `TR-03` and section 5 names it as "the exact failure this harness exists to catch". So the run asserts what is true at any calibration and **says on every run, in its own output, that it is doing so** rather than leaving the limit in a pull-request body nobody reads on run 200.

### The three findings, each a one-line repair outside this fence

1. **`test-results/` has no `.gitignore` entry and this is its first producer.** [INFRA](../architecture/INFRA.md) section 9 names it: "simulation output ... writes to `test-results/` artifacts, never to the production database and never into an agent's context", and [SIMULATION_HARNESS](../testing/SIMULATION_HARNESS.md) section 4 carries it. Nothing else in the tree writes there, verified by grep. So a local run of `CI-09` leaves an untracked file, and the end ritual's clean-tree check is one `git add -A` away from committing a report. **The falsification cases route around it** by writing into a throwaway tree, which is why the harness's own "this changed nothing" assertion still passes.

2. **`CRON_INVENTORY` already carries this job's row and its dead-man switch is not implemented.** The row reads *"Simulation harness | nightly | expected by 10:00 CT | run absent | S3"*, under that document's own first rule: *"a job in this table without a dead-man switch is a job that does not exist."* Nothing here alerts on **non-run**, and GitHub disables scheduled workflows in a repository after 60 days of inactivity, which is exactly the "stops being scheduled" failure the register was written for. `CRON_INVENTORY`'s own ruling is that the switch runs **outside the estate**, so it is not a thing a workflow file can close for itself.

3. **`SIMULATION_HARNESS` section 7.2's channel does not exist.** "A failed band pages the same channel a nightly batch failure does." There is no page, no channel and no on-call in this repository. **The honest answer to who sees a red run is the Actions tab plus GitHub's own email for a failed scheduled workflow**, and both the workflow header and the report say that in those words rather than implying more.

### Landmines

- **A REPORT THAT SAYS `5 of 5 checks passed` IS NOT A REPORT THAT SAYS THE HARNESS IS CALIBRATED.** The population is drawn with a **positive** drift, which is not a book: `PP-02` finds a negative experience coefficient and roughly 93 percent of the funded book at zero or negative true edge. It is drawn that way for `canonical.ts`'s stated reason, so that settlement, the ladder and the cycle arithmetic are reached at all. **Quoting `evaluation_pass_rate` off this report is quoting a drift range chosen in a CI script**, and the report says so under its own results.

- **THE SCENARIO IS IN THE RUNNER AND NOT IMPORTED FROM `packages/harness/test/canonical.ts`, DELIBERATELY.** Importing it would have been shorter. That fixture's calibration bands are "wide enough that a fixture population lands inside them, which is exactly what SIMULATION_HARNESS section 5 forbids a real band from being", and a gate whose inputs are shaped to pass a unit suite moves whenever that suite is edited, by an author not thinking about the nightly. The cost is that the synthetic plan now exists in two places and neither is plan configuration.

- **THE DETERMINISM CHECK IS TWO CALLS IN ONE PROCESS AND THE REPORT SAYS SO.** It catches a module-level counter, an unkeyed `Math.random` and any iteration whose order depends on insertion. It does **not** prove reproducibility across processes, Node versions or machines. What carries that is the run digest printed in the report: two nights differing on it, at one seed and one harness version, is a finding a reader can see without re-running anything.

- **`refused` IS NOT ASSERTED AT ZERO AND MUST NOT BE.** `AssertionKind` has eight members and they are two populations. Seven are arithmetic identities (`INV-18` to `INV-20`) or DO-1 preconditions the trial loop controls entirely, and any of those is a defect. The eighth, `calendar_coverage_miss`, is `ADR-049`'s "the answer is UNKNOWN": an account passing its evaluation on the last session has an `R-31` consistency period starting on a day the slice cannot answer for, which is a property of a **finite window**. The 10,000-trial run produces exactly one. The check is scoped to the kind rather than to the count, and the funnel check above is what stops coverage misses from quietly becoming the whole run.

- **`CI-07` AND `CI-08` WERE NOT BUILT AND MUST NOT BE BUILT BY THE NEXT SESSION EITHER.** ADR-073 section 3 rules `CI-07` out on `repo-invariants.mjs` rule 2, which forbids the skip branch by name, and STRATEGY section 1, which forbids the fail-forever branch. Both are disposition (b) with dated artifacts: a `build` script in any `apps/*/package.json`, and `@playwright/test` in the lockfile.
