- **Objective:** make [`apps/worker/src/batch/replay.ts`](../../apps/worker/src/batch/replay.ts)'s `auditAccount` call the engine's `replay` instead of folding `advanceDay` in its own loop, and close the second code path [M01 section 3.7](../plans/M01-rules-engine.md) forbids and [ADR-078](../decisions/ADR-078.md) recorded as owed.

- **Done:** `auditAccount` folds through `replay`. **Four restatements are gone**: the arrival order, the settlement grouping, the assertion handling and the terminal break. `diffStoredAgainstRecomputed`'s second parameter is a `StateHashSubject` rather than a second `RuleStateRow`. **No ADR**: `078` ruled the export and this implements the consequence it recorded as owed.

- **The four restatements, and what each was a place for two implementations to disagree about.** The old loop folded the port's order and trusted it, where `replay` sorts by trading day then `sourceHash`, **a total order with no stable-sort dependence**, which is what `PT-06` permutes. It folded whatever settlement bucket the port had attached to each day, where `replay` buckets by `effectiveTradingDay`, which is **SD-03's own rule** and what `DayInput.settlements` is documented to mean. It restated `if (fold.kind === 'refused') break`. And its terminal break was **absent rather than restated**: `advanceDay` refuses every day after `closed` or `graduated` ([`day/advance.ts:188`](../../packages/rules-engine/src/day/advance.ts)), so the loop broke one day LATER on that refusal and **the set of folded days is identical either way**. Three needed reconciling; the fourth needed deleting.

- **Next:** `P2-h` was the last claimed P2 build session. `OI-14`'s row in [`DELTA_MANIFEST`](../../packages/db/DELTA_MANIFEST.md) is still `open` and this file still SATISFIES it rather than closing it, which is a documentation edit in a directory no P2 session held. `OI-29`'s enforcement half is session 148's.

- **Blockers:** **this branch waits on the founder's `E2` read and must not be merged before it.** `134` and `135` merged on delegated authority without one, which [P2 section 9](../plans/P2-rules-engine-build.md) records. **This one changes what the nightly compares stored money state against**, which is the whole of INV-04's right-hand side.

- **Landmines:**

  - **A SESSION WHOSE PURPOSE IS ELIMINATING A SECOND FOLD RECONCILES A REFUSAL BY FOLDING TWICE, AND THE ANSWER IS ON THE PAGE RATHER THAN ARRIVED AT DEFENSIVELY.** `replay`'s contract is that *"the array it returns is a contiguous history or there is no array at all"*, so it THROWS on the first refused day and **discards the prefix it had already folded**. The audit wants that prefix: a refused day ends the chain for the account and the days after it are reported as stored rows the replay never reproduced, which is what the old `break` produced. So a `ReplayAssertionError` is caught once and the marks strictly before `error.tradingDay` are folded again. **What 3.7 forbids is a second EXPRESSION of the fold, not a second CALL to it.** Calling one implementation twice cannot drift from itself; restating the sort order, the settlement grouping, the assertion handling and the terminal break in a second place can, and did.

  - **THE SECOND CALL CANNOT REFUSE, AND THE REASON IS STRUCTURAL RATHER THAN PROBABILISTIC.** [`replay.ts:139`](../../packages/rules-engine/src/replay.ts) documents *"@throws ReplayAssertionError on the first day that refuses"* and `:164` throws INSIDE the loop, so **every day strictly before `error.tradingDay` has already folded**, from the identical prior chain over the identical settlement buckets. If it refuses anyway the throw propagates: an engine that refuses a day it has just folded is non-determinism, which is INV-04's own subject and must be loud rather than absorbed.

  - **THE CHEAPER OPTION IS NAMED AS REFUSED RATHER THAN LEFT UNSEEN.** Widening `replay` to hand back the contiguous prefix alongside the error would remove the second call entirely. It is refused for **two** reasons and both are needed: `packages/rules-engine` is outside this fence, **AND** it would reopen a contract `ADR-078` ruled and the founder signed. An entry recording only what was done leaves the next reader unable to tell whether the cheaper option was considered.

  - **`replay`'s SIGNATURE IS NARROWER THAN THE LOOP IT REPLACES AND THE NARROWING IS CHECKED RATHER THAN APPLIED SILENTLY.** The old fold accepted a different plan, opening anchor and calendar on **every day**; `replay` takes one of each, because that is what an account life is. So `lifeOf` asserts four equalities across the history and refuses on any of them: `account_id`, `plan_version_id` (INV-16, and it names the SQL column), `opened_on` ([ADR-051](../decisions/ADR-051.md)'s required anchor), and **the calendar slice BY IDENTITY**, because `runReplayAudit` reads it ONCE before the fold on [`0035`](../../packages/db/migrations)'s ordering and hands that same value to every day. All four are unreachable on well-formed port output, which is exactly what makes them cheap. **A report built from day one's facts over a history that carried two would describe a life the account did not have, and would read exactly like an audit that found nothing** (FM-17). `ReplayAuditRefusal` widens from `OI-14` alone to *"the audit cannot honestly report"*.

  - **THE ASYMMETRY B.2 DEPENDS ON IS NOW STRUCTURAL AND NOT ONLY DOCUMENTED.** `diffStoredAgainstRecomputed` used to call `subjectOf` on **both** sides, which meant both sides were rows and both carried a hash field. The stored side is still a `RuleStateRow` carrying the bytes storage returned; the recomputed side is a `StateHashSubject`, which **has no hash field at all** and is hashed inside the function. There is nowhere left to pass a re-hash of the stored row in, which is the simplification [`ports.ts:122`](../../apps/worker/src/batch/ports.ts) warns would *"disagree with every hash this batch wrote"* and diverge the whole book on its first run.

  - **TWO THINGS STOPPED BEING COMPUTED PER AUDITED DAY AND NOTHING EVER COMPARED EITHER.** `context_gates` is INV-23's never-replayed half and ADR-026 C-07 excludes it from the hash, so building the recomputed row meant calling `evaluatePayout` to fill a column this file never reads. `calendar_revision_id` is excluded for the same reason, and scoping reads it off the **stored** row, which is the only side where it means anything. Building a `RuleStateRow` for the recomputed side would have replaced one restatement with another: eighteen field names re-listed in a second place.

  - **THE REFUSAL PATH HAD NO TEST, AND IT IS THE ONE WHOSE EXPRESSION CHANGED.** So it was written FIRST, against the loop-and-break, watched passing there, committed on its own, and only then re-run against the engine fold: a **differential against the implementation being replaced** rather than a description of the replacement. **A test that passes on both implementations may pass on both because it asserts nothing**, so both halves were watched REJECTING a perturbation before being trusted: `matched` 2 to 3 gives *"expected 2 to be 3"*, and the boundary shifted back one day gives *"expected [ '2026-08-12', '2026-08-13' ] to deeply equal [ '2026-08-11', '2026-08-12' ]"*. **Both reject identically on the loop and on the engine fold**, which is the equivalence claim itself. The fixture is the clean four-day chain in storage against inputs whose day 3 opens one cent above the prior close: `opening_mismatch`, *"INV-18: opening balance is not the prior balance plus the adjustment"*, with the closing balance moved with it so INV-18 is the only thing wrong with the mark.

  - **`GS-071`'s 250-DAY CASE GAINS THE ENGINE'S OWN FOLD, ASSERTED IN B.2's ORDER, AND `stored` IS STILL WHAT `foldAccountDay` PRODUCED.** That is what makes it a differential: the implementation being replaced is still on the page, still folding, and the engine's `replay` is compared against it over 250 days -- **250 identical digests first, then 43 fields a day**. Watched rejecting: dropping the four settlements from the engine fold gives *"expected [ ...(250) ] to deeply equal [ ...(250) ]"*. The count is asserted before both, because `replay` breaks at `closed` and at `graduated` and **a stream that graduated early would fold fewer days and make both comparisons pass over a prefix** (FM-17).

  - **`HASHED_FIELDS` NOW READS A `StateHashSubject` AND THAT IS THE STRONGER TRANSCRIPTION, NOT A CONVENIENCE.** The list is transcribed from ADR-026 C-07 rather than imported, on the rule block 2 states: *"a fixture derived from the implementation proves only that the code agrees with itself."* `StateHashSubject` is the shape C-07 actually covers -- the account id, which is column 1 and is **not** on `RuleState`, plus the eighteen state fields -- so the one list now reads both carriers: storage's `RuleStateRow` and the engine's `RuleState`. The twenty-five gate leaves stay IMPORTED, because that is a coverage question and not a question about SQL.

It is left: [`state-hash.ts`](../../apps/worker/src/batch/state-hash.ts) is the `Buffer` boundary and `stateHash` returns a `Buffer` that `:161`'s `.equals()` needs, so the import is not a stale path but the boundary itself. Repointing the type-only names while keeping `stateHash` would put two import sources in one file for no gain.
