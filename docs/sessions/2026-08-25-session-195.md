### 1. The slice, and why the method decides the answer

**M04 owns no endpoint.** Its section 4 opens *"M4 owns no endpoint. It consumes [API_CONTRACT](../architecture/API_CONTRACT.md) sections 3, 5, 6, and 7 verbatim"* and then records one obligation per endpoint it CONSUMES. So the module's table set is **what those endpoints read**, not what the module writes, and a slice computed any other way is a different slice.

**A whole-word grep of the plan alone returns six unregistered names and four of them are not tables at all**, which is worth writing down because it is the cheap method and it is wrong here:

| Grep hit | Line | What it actually is |
|---|---|---|
| `events` | 273, 287, 289 | *"M4 emits no domain events"*. **Prose.** The `events` TABLE is reached through the timeline endpoint and not through this sentence |
| `offers` | 175, 240, 263 | *"the UI offers actions its API refuses"*. **A verb** |
| `plans` | 261 | `GET /plans/:id/versions/:v`. **A URL path segment**, and the table behind it IS read |
| `fills` | 56 | *"cannot be joined to `fills`"*, which is [M07](../plans/M07-risk-abuse.md)'s join in `INV-M4-16`'s argument. **Not M04's read** |
| `passkeys` | 25 | *"passkeys plus email OTP plus SMS OTP"*. An auth-factor list, and the table IS read through section 3's ceremonies |
| `payout_requests` | 447 | `portal.eligibility_views` versus `payout_requests`. **A metric name** in section 9 |

**Taken from section 4's thirteen rows plus sections 3.8 and 3.9, M04's table set is 22.** Eighteen were registered before this session opened:

`accounts`, `identities`, `users`, `sessions`, `daily_marks`, `rule_states`, `plan_versions`, `purchases`, `certificates`, `kyc_verifications`, `kyc_funnel_events`, `identity_phones`, `contact_channels`, `phone_change_requests`, `economic_calendar`, `economic_calendar_loads`, `impersonation_sessions`, `impersonation_page_views`.

**Not one of the eighteen `why` fields was opened.** [ADR-092](../decisions/ADR-092.md)'s ruling is that a registration is never re-argued, and eighteen of twenty-two is what that rule looks like from inside the module that reads the most and owns the least.

**Four tables M04 also consumes are deliberately left to the sessions dispatched for them** and are named so the absence is a record: `payout_requests` and `payout_transfers` (`POST /accounts/:id/payout`, `GET /payouts`) are session 196's M05 slice, the wallet four are the [ADR-092](../decisions/ADR-092.md) section 8 item 4 intersecting pair between 196 and 202, and the affiliate tables behind `SC-M4-09` are session 197's M08. **First-writer-wins would have permitted taking them.** They were not taken because M04's plan argues none of their tenancies, and a `why` states the TABLE's tenancy: writing four of them from a plan this session did not read is how a rule gets asserted against itself.

### 2. `main` did not move while the slice was computed, and then it did

So **the slice this session computed is the slice it registered**: nothing was taken by a sibling first, and nothing was forced into the slice by the registry's own totality, which is the direction [session 182](2026-08-24-session-182.md) reported four-of-three from and [ADR-094](../decisions/ADR-094.md) section 6 names.

**Then it moved, which is exactly what [P4](../plans/P4-portal-and-site.md) section 11 rule 3 says an absence cannot promise.** [Session 197](2026-08-25-session-197.md) merged as `92ea3d9`, carrying M08's `affiliates`, `affiliate_creatives` and `affiliate_clicks` and taking `main` to **56**. **[ADR-092](../decisions/ADR-092.md) section 4's fourth row happened as written: a textual conflict in all five files** -- [`schema.ts`](../../packages/db/src/schema.ts), [`scope.ts`](../../packages/db/src/scope.ts), [`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts), [STATE](../STATE.md) and [sessions/README](README.md).

**The resolution was structural rather than a keep-both of the hunks**, because the hunk boundary is the hazard: every `pgTable` ends with the same `createdAt` / `});` tail, so git aligns the conflict on lines two unrelated tables happen to share and a careless resolution splices one table's fields into another's object literal. **Each of the three code files was rebuilt from `origin/main`'s copy plus this session's WHOLE declarations lifted out of its own commit `f5c58d2`**, never by editing around a marker; `pnpm run typecheck` was then run to **exit 0 with zero `error TS`** before anything else, and `TABLE_KEYS`, `SCOPE_RULES` and `SQL_NAME` were checked on the merged file for **key-set equality and duplicate keys** rather than trusted because it compiled.

### 3. The two that landed

| Table | Class | The rule, in one line |
|---|---|---|
| [`plans`](../../packages/db/migrations/0004_catalog.sql) | **firm** | Every identity is offered the SAME plan and the link runs the other way, so ownership flows FROM the catalogue |
| [`passkeys`](../../packages/db/migrations/0002_identity.sql) | **derived** via `users`, `user_id` -> `id`, hop | A credential belongs to a LOGIN and not to a person ([ADR-041](../decisions/ADR-041.md)) |

**`plans` is `plan_versions`' argument one level up.** `plan_versions` has been firm since [ADR-084](../decisions/ADR-084.md)'s original seven on the reasoning that an account names the version it was bought under, so ownership flows from the catalogue; the plan is that catalogue's root and the same sentence holds without amendment. **`is_active` delists and never deletes**, on [`0004`](../../packages/db/migrations/0004_catalog.sql)'s own records reason -- *"a plan nobody can buy still has to explain the accounts sold under it"* -- so a delisted row stays readable and stays firm.

**`passkeys` is `sessions`' hop for `sessions`' reason.** `user_id uuid NOT NULL REFERENCES users(id)` is single-valued so the hop cannot multiply rows, and there is **no second candidate column on the row to choose wrongly** -- which is the one respect in which it is easier than `sessions`, whose `device_fingerprint_id` is [`scope.ts`](../../packages/db/src/scope.ts)'s own named trap.

**`credential_id` is UNIQUE across the whole table rather than per user, and the `why` says so explicitly.** That is WebAuthn's rule and not a scope. It is written down because it is exactly the kind of fact that reads like a reason to skip the hop: a globally unique column looks addressable, and addressable is not the same as owned.

**`bytea` and `text[]` are transcribed and not approximated.** `credential_id` and `public_key` are the file's `bytea` custom type; `transports` is `text('transports').array()`, the file's first array column. Writing any of the three as a plain `text()` would compile and would satisfy the column-name comparison the suite runs, which is precisely why it would be the wrong thing to do: **[ADR-094](../decisions/ADR-094.md) section 3 records that column type and nullability are asserted nowhere**, so on that axis a transcription that lies is indistinguishable from one that does not.

**Neither carries a later column change**, re-derived over all 47 migrations with the suite's own multiline `ALTER TABLE ... ;` match rather than inherited from any document: no `ADD`, `DROP` or `ALTER COLUMN` and no `RENAME` touches either. **The fold applies nothing to either**, so both per-table comparisons are byte-identical to a `CREATE TABLE` read, and the eight drifted tables already registered are unaffected.

### 4. `events`, which is the finding

**`GET /accounts/:accountId/timeline` is M04 section 4's own row**, and [API_CONTRACT:375](../architecture/API_CONTRACT.md) types its `TimelineItem.kind` as `// event_name, trader-safe subset only`. `event_name` is a column of [`events`](../../packages/db/migrations/0017_events_and_audit.sql). **So the portal reads this table, it is in M04's slice, and it is left unregistered.**

**It is not declared in [`schema.ts`](../../packages/db/src/schema.ts) at all**, which is [session 192](2026-08-25-session-192.md)'s handling and not merely its conclusion: a declared-but-unregistered `pgTable` compiles, changes no test, and sits there as a table **no drift assertion compares**, `DDL_NAMES` being derived from `TABLE_KEYS`. Leaving it out of `SCOPE_RULES` alone would have been half the refusal.

**No column can be chosen, and both halves are genuinely read.**

```
identity_id  uuid NULL REFERENCES identities(id) ON DELETE RESTRICT
account_id   uuid NULL REFERENCES accounts(id)   ON DELETE RESTRICT
```

Neither is required. **There is no CHECK on this table at all**, so nothing declares that a row carrying one carries the other. An `owned` rule on `identity_id` therefore drops every account-level row written without one; a `derived` hop through `account_id` drops every identity-level row. And **both kinds are on the same screen**: [EVENTS](../architecture/EVENTS.md) section 2 rows the `TL` consumer as *"Account timeline (M6 drill-down, M4 portal), per-account chronological view"*, while M04 section 5 and [`SC-M4-11`](../plans/M04-trader-portal.md) consume `phone.verified` and `phone.change_requested`, whose payloads are keyed on `identity_id` and which have no account at all.

**The payload is the second reason and it is the one no scope rule can reach.** [EVENTS](../architecture/EVENTS.md) section 3 gives `kyc.dedupe_hit` the payload `{ identity_id, matched_identity_id, provider }` and `identity.merged` the payload `{ surviving_identity_id, merged_identity_id, ... }`. **A row whose own tenancy column is correct still names a DIFFERENT identity inside `jsonb`**, and `INV-M4-06` is that the portal *"never receives detector internals or other identities' ids, so it cannot leak them"*. A scope rule states which rows reach an identity; it says nothing about what is inside one. Registering the table would make those rows readable and leave the projection as the only control, which is the position [ADR-008](../decisions/ADR-008.md) scoped the accessor to stop relying on.

**This is a FOURTH shape of [ADR-092](../decisions/ADR-092.md) section 3's named-and-unruled class and the first that is not two identity columns.** `identity_links` ([session 192](2026-08-25-session-192.md)), `dedupe_matches` ([session 194](2026-08-25-session-194.md)) and `attributions` each carry two columns against `identities(id)`; `events` carries one identity column beside one ACCOUNT column, which reads like an easier case and is not, because the second column reaches an identity too and reaches a different set.

**A transcription rules nothing, and wanting an ADR number for this was taken as the stop signal rather than as a reason to allocate one.** Unregistered is unreachable and unreachable is safe; the call site is refused with `TS2345` naming `ScopedTableKey`, which is the property [ADR-084](../decisions/ADR-084.md) installed and [ADR-092](../decisions/ADR-092.md) section 6 preserved.

### 5. `otp_challenges`, refused for a reason already ruled

M04 consumes `POST /auth/otp` (section 4, the channel row), so the table is in this slice. [`0029`](../../packages/db/migrations/0029_phone_identity_and_auth.sql) writes `ALTER COLUMN email_normalized DROP NOT NULL`, and [ADR-094](../decisions/ADR-094.md) closes the fold's vocabulary **at one member with a default of FAIL**. **[Session 193](2026-08-25-session-193.md) already executed this refusal** -- declared, registered, ruled and named, `tsc --noEmit` exit 0, the drift assertion RED quoting the statement verbatim -- and it was not re-executed here, because re-running a landed session's seed proves nothing this tree does not already record.

**Widening the fold to fit it would be weakening a gate to pass it**, and `ALTER COLUMN` is refused as a stated proxy for a comparison this suite does not have rather than because the fold cannot parse it ([ADR-094](../decisions/ADR-094.md) section 3).

### 6. Registering `plans` falsified a comment on a table this session does not own

[`schema.ts`](../../packages/db/src/schema.ts)'s `plan_breaker_state` block read:

> `plan_id` CARRIES NO `.references()` because `plans` is not one of this file's tables.

**It is one now.** The file's header rule is that a column carries a reference **only when** its `CREATE TABLE` body declares the FK inline **and** the target is one of this file's tables. [`0004:59`](../../packages/db/migrations/0004_catalog.sql) and [`0016:127`](../../packages/db/migrations/0016_treasury_controls.sql) both always declared theirs inline, so **the second half of the condition changed and the first never did**. `plan_versions.plan_id` and `plan_breaker_state.plan_id` now claim the reference the rule permits, and the comment states what actually happened rather than being deleted.

**This is [ADR-092](../decisions/ADR-092.md)'s "a session cannot know its own slice size before it runs" arriving as PROSE rather than as a table.** The registry's totality did not force a table into this slice; a registration made a sentence elsewhere in the file untrue. **Leaving it would have been the cheaper move on a file eight sessions are editing, and it would have been the wrong one**, because [ADR-042](../decisions/ADR-042.md)'s "prose is not a control" cuts both ways: a comment that is not a control is still a claim a later reader acts on.

**The third row is [ADR-084](../decisions/ADR-084.md) section 7's lesson in place.** The expectation comes from the MIGRATIONS and not from the rule, so a rule cannot pass by being asserted against itself.
