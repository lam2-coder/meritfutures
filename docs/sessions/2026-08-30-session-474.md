### 1. The objective, and the question under it

**Row `283` asked whether a plan-rules codec is the same move [ADR-250](../decisions/ADR-250.md) already made or a different one, and it said the real open question is what a decoder at READ does about validation that lives at PUBLISH: re-run it, trust the publish gate, or refuse. Rule which, and say what happens to a row published before a validation rule existed.**

It is the same move, in the same home, differing in exactly two properties. **And the trilemma has only two arms**, which was not visible from the dispatch and is the finding the rest of this ruling rests on.

### 2. What was checked, in order

The row's citations were re-derived first, because a session that starts from a dispatch inherits its errors.

1. **`apps/api` imports `@merit/rules-engine`.** Both cited lines sit inside live imports from that specifier, and the manifest declares it `workspace:*`. **Two sentences in the deployable still denied it**, which [ADR-281](../decisions/ADR-281.md) section 7 item 1 registered.
2. **`gates-codec.ts` exists** and its section 2 argument is the one this module lands on.
3. **`CATALOG_TABLE_KEYS` is five.** No sixth was needed and none was asked for.
4. **`resolvePlan(rules: PlanRulesJson, size: PlanVersionSizeRow)`** at `plan/resolve.ts:184`, and the pre-diff census returned two decoders, neither reachable.
5. **Then `validatePlan`'s signature was read**, which is the step the dispatch did not require and which decided the whole shape of the answer.

### 3. Why the first arm does not exist

`validatePlan` takes `PlanRulesJson`. A decoder cannot re-run a validator that requires the value the decoder produces; decoding is strictly prior. **A session that read the three arms as three designs would have spent its budget looking for a way to call a function that needs its own output.**

And it cannot be run at read even after decoding, because it takes `sizes: readonly PlanVersionSizeRow[]` and a payout read holds one pinned size. `validate.ts`'s own header says what that costs: *"A VALIDATOR HANDED ONE SIZE AT A TIME COULD NOT SEE THE PLAN."*

### 4. What the port waits on now, said in the order it should be bought

**The refusal arm is the cheapest, the size row is next, and the missing `PayoutTx` implementation is the whole purchase.** That ordering is in the entry, because the habit this file keeps catching in itself is leading with the second-cheapest blocker.

### 5. Landmines

- **The three-statement position is real and is on a money path.** Until `toPublishedRules` and `decodeRules` collapse onto the engine's, this repository states one payout-basis predicate three times. Link 7's census is the only thing that will notice if the retirement never gets rowed.
- **`CV-13` is unchecked at read and it is a money number.** A stale `plan_versions` row carrying `split_bp: 20000` decodes, resolves, and pays double. The suite asserts that as a PASSING case on purpose.
- **`min_settlement_lag_trading_days` is now enforced by a third module** and the corpus disagreement behind it is still open after sessions 49, 98, 449 and this one. One line in one of two approved documents closes it, and it is free while `plan_versions` is empty.
- **`packages/rules-engine`'s test project cannot read the filesystem.** Its tsconfig declares no `node` types, which is `M01`'s purity boundary reaching the tests. Three cases were written there first and the typecheck refused them by name; they live in `apps/api/test` link 8 instead.
- **A docblock added to `routes/payouts.ts` moved two cited lines by fourteen.** `RI-15` caught both. Any diff that adds prose to that file should expect the same and repoint rather than be surprised.
