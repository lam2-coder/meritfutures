### 1. The absence, re-derived at its source

The dispatch required this before anything was built on it, and it required a database rather than a grep.

| Query, against the installed 59-migration schema | Result |
| --- | --- |
| Tables carrying **both** `started_at` and `finished_at` | **one**: `detector_runs` |
| Columns matching `%run_at%`, `%run_id%`, `last_%` | twelve, none a reconciliation clock |
| `last_run_at` among the schema's distinct column names | **absent**, over **705** |
| Tables matching `%recon%`, `%run%`, `%load%`, `%job%`, `%sweep%` | five, listed below |
| `reconciliations.account_id` | `NOT NULL`, unique on `(account_id, trading_day)` |

**The last row is the finding rather than a detail.** Every row of `reconciliations` is about one account on one day, so the only fold across them is `max(reconciliations.created_at)` -- the fold ADR-199 section 5 refuses one field to the left, because OVERVIEW section 5.2 leaves the run *"resumable at the account boundary"* and a fold over per-account clocks reports a success for a run that crashed.

### 2. The four refusals, which are why the number is spent

The conditional reservation said the number returns unspent if an existing table can carry the record under its own rules. Four could plausibly have, and each is refused on its DDL rather than on taste.

| Table | Why not |
| --- | --- |
| `reconciliations` | `account_id NOT NULL` and `reconciliations_account_day_uq`. The batch-level fact has no row shape here at all |
| `detector_runs` | The closest shape in the schema and the wrong subject. It keys on `(detector, detector_version)`, and `synthetic_expected` / `synthetic_found` is `INV-M7-07`'s control; writing a sweep here means inventing a detector name with no `detector_definitions` row behind it |
| `ingest_files` | `applied_at` is the **ingest** stage's clock, two stages earlier in OVERVIEW section 5.2's sequence. A file applied at 05:12 whose reconciliation then crashed reports a reconciliation that never finished, which is the same defect one stage over |
| `simulation_runs` | A run of the simulation harness over a draft plan version |

### 3. What the row answers, ruled rather than assumed

The dispatch named four questions a useful record must answer, and warned that a row saying only "a job ran" makes `last_run_at` truthful and the panel useless.

| Question | Column | Ruling |
| --- | --- | --- |
| When | `started_at`, `finished_at` | `started_at` is `NOT NULL` where `detector_runs`' pair is nullable: the row is created BY the start of the sweep |
| What it covered | `trading_day`, `accounts_total`, `accounts_done` | The two counter names are transcribed from EVENTS section 5.3's `batch.completed` payload rather than invented, so the stage and the batch describe coverage in one vocabulary |
| Found or merely completed | `mismatches_found` beside `status` | Two columns and never one. A run that found three mismatches **succeeded**; conflating the finding with a failure of the check makes them indistinguishable |
| What next | `trading_day` and the count | `reconciliations_open_mismatch_idx (trading_day) WHERE status = 'mismatch'` resolves the finding set through an index `0014` already built for it, which is what an operator opens RB-02 with |

**`mismatches_found` is not a copy of `mismatches_open` and the probe proves they come apart.** One is what this run saw and nothing may change it; the other is a count of the current state of `reconciliations` and moves the moment a human resolves a mismatch. SUCCESS 3 resolves one and asserts the two numbers disagree afterwards. If they could not, one would be a copy of the other and this table would carry a number `reconciliations` already answers.

### 4. Three things refused, each with the reason in the file

**No `duration_ms`**, although `batch.completed`'s payload carries one: `finished_at - started_at` is the same number and a stored copy can disagree with the two instants beside it ([ADR-047](../decisions/ADR-047.md)).

**No column on `reconciliations`.** The symmetric design -- `risk_flags.detector_run_id`, one table over -- is refused on the DDL: that works because a flag is raised once and never re-raised, while `reconciliations_account_day_uq` makes a re-run **update** the existing row, so a `reconciliation_run_id` there would name the LAST run that touched the row rather than the run that found it. A column whose meaning changes under a redelivery is worse than no column.

**No cross-table constraint.** `mismatches_found` is bounded (`0 <= mismatches_found <= accounts_done`) and not verified against `reconciliations`; verifying it needs a trigger, which is the class `0060` refused on evidence. The limit is named in the file rather than left to be discovered.

### 7. The registration, executed rather than asserted

`TABLE_KEYS` is **110** and the class is `firm` on ADR-199's own predicate: no column of the row is declared against `identities(id)` or `accounts(id)`. `batch_run_id` is the available mistake and it is not an edge at all -- no foreign key, because EVENTS section 5.3 declares that `run_id` in three payloads and no table stores it.

Through the package's own accessor against a live database:

```
TABLE_KEYS includes reconciliationRuns: true      TABLE_KEYS length: 110
system read rows: 1  { startedAt: 2026-08-28T06:00:00.000Z, createdAt: 2026-08-28T21:38:00.100Z, ... }
firm read rows: 1
scoped read refused: reconciliationRuns belongs to no identity (ONE ROW PER RECONCILIATION SWEEP, ...)
```

The two clocks on that row are the injected `started_at` and the database's `created_at`, fifteen hours apart, which is why both columns exist.

**The suite verifies the transcription independently.** Registering the table adds two per-table cases -- the column set and the type-and-nullability set, each compared against the DDL as of the last migration -- so `schema.ts` is checked against `0064` by a machine rather than by this session's reading.

### 8. What did not clear

`B4`'s clearing condition was *"a `recon.completed` event or a run record"*. This is the record. Two things stand and neither is a migration:

1. **A producer and a reader.** `apps/worker` writes the row and `apps/api`'s adapter folds it; both are other fences and neither was opened.
2. **The event.** The data-model README section 1 says a mutable table *"emits an event on every meaningful transition"*, and EVENTS section 5.3 carries `recon.mismatch_detected` and `recon.resolved` and no `recon.completed`. That is an amendment to a frozen document and therefore an ADR, which this fence does not hold -- session 382's finding about `detector.run_completed` at the same boundary, arriving from the other side.

### Next

- **`recon.completed` needs an EVENTS amendment**, and unlike `detector.run_completed` its subject now exists: `reconciliation_runs.id` is a `uuid` primary key the producer holds before it writes anything. **That is not permission to take it**, on session 382's landmine 1: the field goes into EVENTS first or it does not go in.
- **`batch.completed`'s `run_id` has no table**, which is `B4`'s shape one level up and is now the only thing `reconciliation_runs.batch_run_id` cannot be a foreign key to.
- **`readLiability` is still blocked on four**, and `B4` is now the only one whose remaining work is a producer rather than a ruling or a registration.

### Blockers

None encountered. The conditional number was taken and the condition was tested rather than assumed.

### Landmines

- **The two absent objects are decisions and the seeds are the only thing saying so.** A UNIQUE index on `trading_day` and a `REVOKE UPDATE` are each what the nearest precedent suggests, and each breaks an acceptance case. A session that adds either has undone a ruling by writing code.
- **`mismatches_found` is bounded and not verified.** A producer that writes the wrong number is not caught by the database, and closing that gap is a cross-table trigger, which is `0060`'s refused class. Do not close it by widening the constraint.
- **`batch_run_id` has no referent to validate against.** `NOT NULL` is the whole of what the database can hold, and a producer writing a random uuid there passes every check in this file.
- **`RI-15` claims a RANGE citation as nothing.** `wiring.test.ts` carried a `file:line-line` citation that was thirty-one lines stale at `main` and no invariant could see it. Any count of "citations verified" derived from `RI-15` is a count of single-line citations only.
- **A clearing condition fires once.** Session 374's `B4` case is spent here. The next session on this read path should read section 8 rather than expect a red.
