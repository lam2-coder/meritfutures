### 1. The objective

**[ALLOCATION](../decisions/ALLOCATION.md) row `292`: every push to a pull request branch runs all three workflows twice, concurrently, on the identical commit.** Fix it without removing a trigger or narrowing a branch list, prove it rather than asserting it, and mint `RI-33` if the work needs an invariant. One objective, non-money.

### 2. What was read before anything was written

Row `292` in full, then `CLAUDE.md` and [STATE](../STATE.md), then the `on:` and `concurrency:` blocks of all four workflows, then `RI-05` as the existing workflow-reading invariant and `RI-29`, `RI-30` and `RI-31` as the house shape for a new check, then the two derived cases in [`repo-invariants.test.ts`](../../packages/tooling/test/repo-invariants.test.ts) that a new member of `CHECKS` must satisfy, then the live Actions API for the runs the row cited and the ones it did not.

### 5. Blockers

**None that stopped work.** One that bounded it: no pull request exists anywhere in this repository and this session was told to open none, so the `pull_request` half of the observation was unreachable. It is reported as unreachable rather than substituted for.

### 6. Landmines

- **THE MOST-COPIED ANSWER TO THIS QUESTION DOES NOT ANSWER IT.** `${{ github.event.pull_request.number || github.ref }}` looks like the fix, is what the dispatching row supplied, passes every gate, and leaves the duplication running. So does `${{ github.head_ref || github.ref }}`. **Only the `ref_name` fallback collapses the two events**, and the difference is `B` against `refs/heads/B`.
- **A DEFECT WHOSE ONLY SYMPTOM IS THAT THE CORRECT ANSWER IS COMPUTED TWICE IS INVISIBLE TO EVERY GATE THAT ASKS WHETHER THE ANSWER IS CORRECT.** Nothing was ever red. Both runs passed. The cost was wall-clock, runner minutes and queue depth, and this tree reads none of them.
- **`git checkout -- <path>` REVERTS TO HEAD AND TAKES UNCOMMITTED WORK WITH IT.** Used mid-session to remove a seed from a file whose real fix was also uncommitted, it silently restored the defect in all three workflows. Caught by `sha256sum -c` against a hash taken before seeding, which is why that hash was taken. **Seed and restore with an explicit inverse edit, and verify the restore rather than assuming it.**
- **THE FIX LOSES THE `push`-EVENT RUN ON A PULL REQUEST BRANCH.** The surviving run is the `pull_request` one, which tests the MERGE COMMIT rather than the branch head, so while a pull request is open nothing tests the branch head in isolation. Argued as the better of the two in ADR-292 section 2 and put to the founder in section 10.
