### Why three of the four are `firm`, stated per table

Each `why` in [`scope.ts`](../../packages/db/src/scope.ts) states the TABLE's tenancy and never this module's use of it, which is [ADR-092](../decisions/ADR-092.md)'s requirement and the reason it does not matter which module's session writes the rule.

**`coupons`.** A discount code is an OFFER Merit makes. There is no identity column and there is no correct one: the thing a buyer holds is the REDEMPTION, which is the next table and carries `identity_id NOT NULL`. **The trap is `affiliate_id`**, which references `affiliates`: a rule through it would scope a launch code to whoever is CREDITED for it, which says who gets paid when the code is used and nothing about whose row it is. It is also `NULL`able, so most codes name no affiliate and would reach nobody. `redemption_count` and `max_redemptions` are counters over every identity, so a per-identity slice of the row is not a smaller version of it.

**`psp_webhook_events`.** The table's own DDL comment decides the class: these are **third-party assertions rather than facts Merit generated**, kept separately from `events` for exactly that reason, *"and the distinction matters the day one of them turns out to be wrong."* No identity owns a processor's statement about a payment; the buyer's row is `purchases`. **The trap is `purchase_id`, and it differs in kind from `coupons`'.** It points at the right table. It is nullable and it is written by the processing path, so a derived rule would make a row's tenancy a function of whether a job has run yet: the same event belonging to nobody while it is `out_of_order_deferred` and to somebody once it is `applied`. A `rejected_signature` row belongs to nobody permanently, because it is stored precisely on the fact that its signature did not verify. **A class that answers "whose row is this" differently before and after a re-drive is not an answer.**

**`mid_health`.** One row per PSP per window: attempts, declines, chargebacks and the two basis-point rates the failover decision is read from. No identity column and no correct one -- the row is about a PROCESSOR and its counters are aggregates over every identity's card volume. The denominator rule the column names carry (both rates against CARD volume, never total volume, because wallet purchases carry no chargeback exposure and a healthy shift toward wallet funding would otherwise look like a deteriorating ratio, AS-M3-02) is a property of the published row rather than of any reader.

**`coupon_redemptions` is the one scoped table and its rule is the direct column.** `identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT`, and the DDL states why the column is the identity rather than the email: **limits are per identity, because an email limit is a limit on typing and not on people**. `purchase_id` is present and is NOT the scope: it is null while the claim is HELD and the payment is in flight, so a derivation through `purchases` would return only the redemptions that were paid for, and **the rows it would drop are exactly the claim-and-abandon ones this table keeps on purpose** -- a release writes `released_at` rather than deleting the row, which is what makes the pattern visible instead of erased.
