### 1. The objective, and what the row already knew

**Row `285` is the cheapest of the three things [ADR-283](../decisions/ADR-283.md) left standing on `usePayoutBackend`, and it is the one that entry deliberately did not lead with.** Row `281` asked whether the port refuses on an empty `rule_states` table or wires and answers honestly that there is no state for the day, and ADR-283 answered that **the second arm did not exist**. The row's instruction was to build it or to rule that it should not be built, with the second option carrying a high bar: it would have to argue why a 500 on the money door is acceptable.

It is not acceptable and no argument was found.

### 2. The citations, re-derived first, and the defect reproduced

A session that starts from a dispatch inherits its errors, and this entry's own history is the argument: the reason on this port has named its second-cheapest blocker three times.

| Claim | Read |
|---|---|
| `unwiredOrThrow` reads `if (!(err instanceof PayoutBackendUnwired)) throw err;` | HELD, verbatim, at `payouts.ts:1387`. The row cited `:1386`, which is the function's own declaration line; `RI-16` then found the same citation drifted by five across this diff and it is repointed |
| `ruleStateOn` throws `RuleStateAbsent` | HELD, `rule-state-reader.ts:355` |
| So a wired backend meeting an unfolded day answers **500** | HELD, and EXECUTED rather than read |

**The third was reproduced on the route rather than argued from the source.** Three cases were written against a backend whose `subject()` rejects, with an insert that writes STRAIGHT THROUGH rather than staging, so an empty `payout_requests` afterwards is a fact about the route and not about the fake. Two measured `expected 500 to be 503`. The third, an UNREADABLE row at 500, passed then and passes now.

### 3. The finding, and it is a status before it is a function

**`service_unavailable` is the row of API_CONTRACT section 2's closed table this answer belongs to**, on that row's own two halves: a dependency that is down, and safe to retry. The nightly fold is a dependency that lives outside this repository exactly as the two vendors named in that row do, [ADR-241](../decisions/ADR-241.md) having ruled its schedule EXTERNAL, and retrying is exactly right once the day is folded.

**The alternative that had to be refused carefully is `payout_not_eligible`**, because it is the code a reader reaches for first. Section 6 requires it to carry the FULL gate breakdown, and there is no evaluation here, so every cell would read pass. That is [ADR-140](../decisions/ADR-140.md)'s own finding one door up in this same file, and it is why the identity-status term is a named refusal rather than a gate result.

**The `detail` is generic and the operator's discriminator goes to the log**, on `AuthBackendUnwired`'s ruling for the two absences that already share this status: different facts to an operator, and the reason never reaches the response. WARN rather than ERROR, on the reader's own sentence that an absence is not an error in the estate at all.

### 4. What the arm does not do, which is most of what makes it correct

- **It synthesises nothing.** No `RuleState` is constructed, zeroed or carried forward. Link 7 asserts it rather than promising it.
- **It does not catch `RuleStateUnreadable`.** A malformed row is an internal error and a retryable status would tell a trader to retry what no retry can fix.
- **It is not folded into `unwiredOrThrow`.** The idempotency store cannot raise a `RuleStateAbsent`, so a shared helper would claim a path that does not exist.
- **The rethrow is unchanged.** An `unwiredOrThrow` that stopped rethrowing would answer every internal fault on this route with a retryable 503, which is the larger defect.

### 5. Two things found by building rather than by reading

**A 503 AND A 404 ARE DISTINGUISHABLE, SO THE ORDER A BACKEND READS IN IS NOW LOAD BEARING.** A scoped read of a foreign account's rows is EMPTY, and an empty list is `RuleStateAbsent`, so a state-first `subject()` would answer a prober 503 for every account of every other identity. Before this diff both answers were the same 500 and the hazard was invisible. It is written into two docblocks and the entry and it is **not enforced**, because nothing implements `PayoutTx` and a route cannot observe the order of reads inside a port it does not own.

**AN UNSTAMPED REFUSAL LEAVES THE IDEMPOTENCY KEY CLAIMED FOREVER.** The case originally read *"a retry after the fold gets a real answer"* and expected 200; it measured 409. `beginIdempotent` claims before the handler runs, a refusal is deliberately never stamped, and `classify` calls a claimed row with a null response `in_flight`. **This is true of every refusal this route makes and matters most here**, because this is the only one that is Merit's rather than the caller's, so the caller's instinct is to resend exactly what they sent. The contract is not moved: `apps/api/src/idempotency.ts` is out of fence and the rule reaches every endpoint that claims a key. The `detail` names the header instead.
