| Endpoint | Public surface |
|---|---|
| `GET /kyc/status` | **REGISTERED** |
| `POST /kyc/session` | **REGISTERED** |

### 3. Fail closed, which on this screen is a compliance statement

[`apps/api/src/routes/accounts.ts:824`](../../apps/api/src/routes/accounts.ts) states the posture on the identical question one deployable over:

> A chain whose head cannot be named "**fails closed, because the alternative is reporting somebody verified on the strength of an ordering this table does not declare**."

**The screen half of that sentence has two wrong answers rather than one.** Rendering `verified` for a trader who is not is a statement Merit makes about an identity check that did not happen. Rendering NOTHING is the blank [`screen.ts`](../../apps/portal/src/app/kyc/screen.ts) and [`view/kyc.ts`](../../apps/portal/src/view/kyc.ts) each already refuse, because it reads as neither and leaves the trader unable to tell a passed check from a broken page.

**IT DOES NOT SUBSTITUTE `kyc_required` EITHER, AND THAT IS WHERE IT DIVERGES FROM `accounts.ts` ON PURPOSE.** That function computes a value the API will state; this one renders a value the API stated. Falling back to `kyc_required` here would put *"you need to verify"* in the server's mouth and tell an already-verified trader to do it again.

**Fifteen failure modes, every payload claiming `verified`, asserted on the bytes the page emitted.** 401, 403, 404, 429, 500, 503, no response at all, a body that is not an object, an array of one, a missing field, a non-string state, a state the enum cannot produce, a placement the `0003_kyc.sql` CHECK cannot produce, a document on the wire, and an internal-tier sentence. Each renders no `data-badge="verified"`, no `data-state=` at all, not the word, **and a named content state carrying copy a trader can read**.

**WATCHED FAILING ON A REAL SEEDED DEFECT.** `statusFrom` was made to return a fabricated verified status on a refused read, and the assertion reported:

```
AssertionError: 401 renders no verified badge: expected '<article data-screen="SC-M4-07"><h1>I...' not to contain 'data-badge="verified"'
Received: <article data-screen="SC-M4-07"><h1>Identity verification</h1><section data-state="verified">
          <p data-field="state">Verified</p><p data-badge="verified">Verified</p>...
```

**That is the screen this assertion exists to prevent, printed.** The seed was reverted and the suite is green.

### 4. The constant that became a measurement

[`page.ts`](../../apps/portal/src/app/kyc/page.ts) rendered `toPortalErrorKind(503)` for every failure. That was the only honest answer while nothing here could fail for a reason: with no transport, every refusal was the same refusal.

| What the API said | Before | Now | What the trader reads |
|---|---|---|---|
| 401 | `server_error` | `unauthenticated` | *Please sign in again to see this.* |
| 404 | `server_error` | `not_found` | *We could not find that.* |
| 429 | `server_error` | `rate_limited` | *That was a lot of requests at once.* |
| 500, 503 | `server_error` | `server_error` | unchanged |
| 403 | `server_error` | `unexpected` | [`app-shell.ts`](../../apps/portal/src/shell/app-shell.ts)'s deliberately unmapped case |
| a screened key, a malformed payload, an internal-tier sentence | `server_error` | `server_error` | unchanged, and each is a defect upstream |

**No member was added to `PortalErrorKind`**, which is [ADR-162](../decisions/ADR-162.md) clause 3.
