### 1. What `OI-25` actually was, and what had already been done about it

[WAVE-04 section 6](../plans/WAVE-04-fixture-backlog-and-gate-inventory.md) opened the item because the backlog is arrived at **by subtraction**: a population somebody counted once, written above the rows it counts, owed an edit by every session that moves a row. **One thing had already been built against it and the dispatch's premise needed correcting on it**, so it is stated first rather than discovered by a later reader.

**`CI-06/fixture-inventory` assertion 5 already COMPARED both summary tables to the rows, in both directions, and had since it landed.** Its own finding text named exactly what it could not do:

> *"This is a hand-maintained count over hand-maintained rows (`ADR-034`) and `CI-06g` cannot reach it, because it is not a generated span"*

**So the number was CHECKED and still STATED, and the gap between those two is what this session closed.** A checked-but-stated number still has to be retyped by hand every time a row moves, and the gate that refuses the wrong value is also the gate that tells the typist which value will pass. **Under a check, session 237's diff shows a human editing a summary number and a reader cannot tell "moved by the right amount" from "typed until green". Under a span the summary is machine output and the dispositions are the only thing a human touched.**

### 3. The dispatch's question answered: three reasons, and only the third is a hole

**`CI-06/derivable-counts` did not catch this and could not have.** The reasons apply in this order, and the first two are properties of the number rather than defects.

| # | Reason | Is it a hole? |
|---|---|---|
| **1** | **No vocabulary entry.** `DERIVABLE_NOUNS` is eight populations and *"how many registered scenarios are blocked"* is not among them. Before this session no `SPAN_QUERIES` key derived it either | **No.** The gate's `covers` line declares this limit: a derivable population with no entry is unpoliced, and the remedy is an argued entry |
| **2** | **Value-anchored.** The cardinal must EQUAL what its bound query returns. The eight queries give 122, 18, 47, 111, 32, 157, 316 and 117, and no backlog count is any of those, so the match fails before any exclusion is reached | **No.** It is the property the gate was chosen for, against alternatives that gave 206 sites and five false findings |
| **3** | **A summary table row is excluded BY SHAPE** | **YES** |

**Measured with a probe rather than argued.** One file under `docs/`, a heading carrying no date and no session number, one number at a value the runner derives, governed by a noun already in the vocabulary, written twice: once as prose and once as a summary table row.

```
The corpus registers 316 golden scenarios.

| Term | Rows | |
|---|---|---|
| **registered** | 316 golden scenarios | a summary row |
```

**One finding on the prose line and silence on the table row.** The table-row counter moved from 13 to 14 and the finding count was 1. **Identical text, identical value, identical noun, and the shape decides.** The exclusion's stated argument is that a table row is *"a per-row datum whose number belongs to that row rather than to the document"*. **That is true of a DATA row and false of a SUMMARY row**, whose number is a population over the document's own rows, restated above them and maintained by hand, which is `ADR-034`'s subject exactly.

**It is NOT narrowed here, and [ADR-133](../decisions/ADR-133.md) section 2.2 gives the three reasons.** The narrowing is an edit to `gates.mjs`, where sessions **243** and **244** are live; it is not free, because a noun entry for `written` would now fire on section 39's own *"43 are written"* where the number is a SUBSET that happens to equal the whole; and it is `OI-26`-shaped rather than `OI-25`-shaped, a gate that does not exist rather than a count that is stated.

**A live instance is already in the tree.** [ALLOCATION](../decisions/ALLOCATION.md) row 125, session **237**'s own reservation, states its population in a table row, and it will be wrong the moment 237 lands. It is left standing because that row is 237's and not this session's, and it is named so the class has something to point at.

### 4. The one thing a later reader will get wrong, so it is written down

**`CI-06/fixture-inventory` assertion 5 changed what it asserts and stayed green through the change.** It existed to compare a hand-maintained summary against the rows. Nobody types the number now, so **it catches no typist**. It cross-checks **two independent readers of the same rows**: [`fixture-backlog.mjs`](../../scripts/corpus/fixture-backlog.mjs) writes the span, and the runner's own loop re-derives it with its own parser. That is the `sql_tables` against `tables` arrangement, and it is exactly what a span alone does not buy, in `ADR-034`'s own words: *"a generated span can still be generated from the wrong query, and CI-06g cannot tell a right query from a wrong one."*

**Both halves of the runner's prose had to move with it**, because both said something that is now false: assertion 5's header bullet and its finding text each described the summary as hand-maintained and unreachable by `CI-06g`. **A gate whose `covers` line says something untrue is the defect this corpus hunts**, so they moved in the same commit as the spans rather than being left for somebody to find.

**The merge hazard is that somebody makes the two readers one.** They look like duplication. They are the assertion.

**Five was already wrong and the last two merges added twelve.** It is invisible to every gate: `CI-06u` reads TABLE ROWS and this is a paragraph, `CI-06g` checks that each span matches its query and all seventeen do, and `CI-06/derivable-counts` excludes a generated span because a span is the remedy. **A count can be derived, correct, gated, and present seventeen times.**

**THIS SESSION BRIEFLY MADE IT WORSE AND THE MECHANISM IS WORTH NAMING.** The merge at `1ad60e0d` took a branch carrying 5 into a `main` carrying 13 and produced **17**. The correct result was 13. The four extra came from resolving STATE's conflict hunk as **keep-both**, which is right for two genuinely new appended sections and wrong for the lines BOTH SIDES INHERITED FROM THE BASE, which a keep-both writes twice. **`main` then reached 17 on its own**, so the current branch adds none: `git diff origin/main HEAD -- docs/STATE.md` is this session's two sections and the regenerated `adr_count`, and nothing else. **Neither is repaired here.** The seventeen are `main`'s, they predate this branch, [STATE](../STATE.md) is not in this session's fence, and another session has already escalated the same finding. **The transferable rule, which is the same one `CI-06u` taught in 7.4 one level up:** keep-both is correct for what a side ADDED and never for what both sides already had. A merge resolution that cannot tell those apart duplicates the corpus a little on every merge, and this file is what that looks like after a wave.
