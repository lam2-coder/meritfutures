**`requestOtp` ANSWERS AND `NO_DELIVERY` IS GONE.** [`auth-backend.ts`](../../apps/api/src/auth-backend.ts) refused it with *"nothing in this deployable delivers a code"* while `verifyOtp` had been wired since [ADR-200](../decisions/ADR-200.md), so this tree could verify a code it had no way to send. Re-run before a line changed, `git grep -I -i "postmark\|sendgrid\|mailgun\|twilio\|ses\.amazonaws"` over `apps packages e2e scripts .github` at `21afc5d` returned **nothing, exit 1**. [`apps/api/src/otp-delivery.ts`](../../apps/api/src/otp-delivery.ts) is the send and `requestOtp` writes the `otp_challenges` row `verifyOtp` reads, so **the email half of sign-in is end to end at the API and what is owed is a CREDENTIAL rather than a construction.**

**THE VENDOR IS POSTMARK AND IT IS ARGUED AGAINST AMAZON SES RATHER THAN DEFAULTED.** Four criteria and the dependency decides it: SES authenticates with SigV4, so it is either `@aws-sdk/client-ses` -- which is the `VG-12` sentence `NO_WEBAUTHN` already uses to refuse a dependency on this exact path -- or a hand-rolled request signer on the sign-in path, where a signing bug fails as a vendor 403 rather than as a compile error. A Postmark send is **one `fetch`**, which is `turnstile.ts`'s call shape with a different body; its SERVER token sends from one server and cannot manage the account, the domains or the other servers; and its pools are transactional-only, so a sign-in code does not share IP reputation with anybody's newsletter. **NO PRICE FROM EITHER VENDOR'S TABLE IS WRITTEN INTO THIS REPOSITORY** and the entry says so rather than quoting a figure it cannot cite.

**THE PRICE HALF IS RULED AND IT BELONGS TO THE SMS BRANCH ALONE, WHICH IS THE ROW'S OWN FRAMING NOT SURVIVING.** `otp_send_budget` admits `scope_kind IN ('phone','ip','country','global')` and **no `email`** ([`0029:392`](../../packages/db/migrations/0029_phone_identity_and_auth.sql)), its cost breaker is `global` *"because Merit's SMS bill is one number"* ([`:390`](../../packages/db/migrations/0029_phone_identity_and_auth.sql)), and [API_CONTRACT `:1462`](../architecture/API_CONTRACT.md) rows the email channel as prose velocity with no cost half at all. **So the email branch discharges without a price**, and the half that blocked delivery is the half that always belonged to SMS. The value is `MERIT_OTP_SMS_PRICE_CENTS`, **integer cents**, and a decimal point is **REFUSED rather than rounded**: `Number('0.79')` succeeds and truncating it to zero is a cost breaker that counts every send as free while every gate reports green. **The rounding direction is UP**, because `otp_send_budget` DEGRADES rather than stopping, so an early trip defers a verification and a late one pays an unbounded bill.

**FAIL CLOSED ON [ADR-226](../decisions/ADR-226.md)'s SHAPE, TRANSCRIBED RATHER THAN RE-INVENTED.** Four outcomes and three of them refuse; an absent credential is `unconfigured` and never a pretend send; a `switch` over `Exclude<OtpDeliveryOutcome, { outcome: 'sent' }>` turns a fifth member into a `tsc` error; one deadline and **no retry**, which is a stronger rule here than there because a repeated send is a second billed message and **a request that timed out may well have been accepted**. **All three refusals arrive as one 503**, and that is the single place this departs from that entry: API_CONTRACT says the endpoint *"deliberately does not reveal whether the destination exists"*, so a refused DESTINATION told apart from a broken deployment would disclose through the status what the body withholds.

**`NO_DELIVERY` IS QUOTED RATHER THAN DELETED AND `NO_SMS_DELIVERY` NAMES WHAT SURVIVES, WHICH IS TWO THINGS AND NEITHER IS DELIVERY.** A code sent to a phone cannot be verified anywhere in this tree, because `verifyOtp` refuses the `sms` channel for want of a phone resolution, **so an SMS send is money spent on a code no handler here can answer** -- which is why no SMS vendor was taken, rather than one being taken and left unreachable. And the per-send price still has a name and no value. [ADR-197](../decisions/ADR-197.md) section 7's rule is that a refusal replaced by a softer version of itself is the failure mode; this replacement names what is left.

**THE LANDMINE THIS SLICE ALMOST WALKED INTO IS THE PER-IP LIMIT, AND IT IS ADR-226's `remoteip` REFUSAL WEARING A DIFFERENT HAT.** API_CONTRACT rows the email channel *"5/hour/IP, 5/hour/email"* and **only the second half is enforced here**: [`server.ts:170`](../../apps/api/src/server.ts) builds the instance as `Fastify({ logger: options.logger ?? false })` and configures no `trustProxy`, so `request.ip` is the IMMEDIATE PEER and five per hour counted on it is **five per hour for the whole product** behind Cloudflare. [INFRA `:27`](../architecture/INFRA.md) puts rate limiting at the edge, which is the one place the address is the trader's. It would have passed every test in this repository while locking out production.

**EVERY NUMBER IN THE HANDLER IS TRANSCRIBED WITH ITS CITATION, ON `OTP_MAX_ATTEMPTS`' PRECEDENT IN THE SAME FILE.** Six digits from `otpCodeDigest`'s own arithmetic and [ADR-197](../decisions/ADR-197.md) section 3; ten minutes from [`0002:313`](../../packages/db/migrations/0002_identity.sql)'s *"short TTL, 10 minutes"*; five per hour from API_CONTRACT section 11. **And the velocity is counted off `otp_challenges` because the schema says so rather than because this session decided it**: [`0029:539`](../../packages/db/migrations/0029_phone_identity_and_auth.sql) calls its SMS index *"the per-number velocity read"* and declares it the sibling of `otp_challenges_email_created_idx` from `0002`.

**THE FENCE WAS EXTENDED TWICE AND BOTH EXTENSIONS WERE FORCED BY A CHECK RATHER THAN CHOSEN.** [`apps/portal/src/app/sign-in/availability.ts`](../../apps/portal/src/app/sign-in/availability.ts)'s cross-check went **RED in both directions**, and that table's own docblock had named this session as the case it exists to catch: *"a session that wires `requestOtp` over there cannot leave this screen quietly claiming it is still blocked."* And six `file:line` pointers in [`client.ts`](../../apps/portal/src/http/client.ts) were shifted by eight after `RI-15` found one of them; **no claim changed, only the numbers**, which is [session 416](2026-08-29-session-416.md)'s repair on the same file for the same reason.

**THE SCREEN IS STILL NOT WIRED AND THE REASON IS NO LONGER THIS ONE.** [ADR-219](../decisions/ADR-219.md) section 6.2's cookie refusal was always the independent second half: `next@16.3.2` permits a cookie write only in a Server Action or a Route Handler and [ADR-138](../decisions/ADR-138.md) section 3 refuses the first outright. So a trader still cannot sign in through the portal, and **after this entry that is a portal defect rather than an API one.** `AVAILABILITY.email_otp` stays `served: false` and its sentence stops telling a trader a code cannot be sent, now that one can.

**WHAT A GREEN SUITE DOES NOT PROVE, SAID HERE RATHER THAN LEFT TO BE ASSUMED.** Nothing in this repository has ever sent a message: every case injects a `fetch` or a fake sender, deliberately, because **a suite that could reach a vendor is a suite that can spend money.** No deployment holds the token, so `POST /auth/otp` answers 503 today and no end-to-end sign-in has been observed by anybody. What IS proved is the round trip that matters: the digest written into `otp_challenges.code_hash` is checked against the code handed to the sender, through `otpCodeMatches` itself, so a handler that stored one code and sent another is a red case rather than a support ticket.

**`SESSION_LIFETIME_DAYS` WAS NOT TAKEN**, `turnstile.ts` and `csrf.ts` are unedited, no migration was written or edited, no `SD-nn`, no `GS-nnn`, no `CI-06` letter, no `RI-nn`, no new enum type or label, no new canonical error code, no dependency admitted, no `pg` import, no float on a money path, `MERIT_BUILD_MASTER_PROMPT.md` untouched, and no gate weakened. The approval line is **UNSIGNED**.
