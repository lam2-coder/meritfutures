### 2. What the `.png` costs, stated once so nobody re-derives it

Section 1 opens with *"`application/json` for requests and successful responses"*. Four of its conventions are not about a body and survive on this row unchanged: the error model, which section 6.3 restates explicitly; the base path; the surface partition; and the rate limit, which section 11 gives this row its own line for.

**The one that cannot survive is the response-shape allowlist**, and it is the one that carries the disclosure guarantee everywhere else in the contract. There is no projection inside a PNG. So on this row the boundary moves out of a projection function and into a renderer that is not in this repository, and the suite says so rather than implying otherwise by checking something adjacent. What it does assert is every part of the response this file controls: the status, the content type, the `Cache-Control` value and its bound, the problem shape on every refusal, and that the body is byte-for-byte the bytes the source handed over.

**`assertPng` is a FORMAT check and never a disclosure check.** The path ends in `.png` and the response declares `image/png`, so this route makes a claim about the bytes that section 1's allowlist would have made about fields; the eight-byte signature is the smallest version of that claim being true. It says nothing about what is drawn.

### 3. The negative assertion, and the four mutations that were watched failing

Every seeded `certificates` row carries the five things section 6.3 says a certificate never names, plus `revoked_reason`'s internal free text and the account uuid. Half are columns and half are inside the `jsonb` claim. The case reads the **serialized** response, so a value nested at any depth under any key is caught by the same assertion.

Each mutation was applied alone to a byte-identical copy and reverted:

| Seeded mutation | Caught by |
|---|---|
| `narrowClaims` spreads the stored claim | the allowlist case |
| ...and `projectCertificate` passes the claim through unrebuilt | the wire case, and the four-key case |
| the deferred branch stops withholding the token | the withholding case, and the never-signed case |
| a rejected `certificate_verifications` write is swallowed and the bytes served | the fail-closed case |

**The two claim layers are independent and the middle row of that table is why the distinction is worth keeping.** With only the first mutation applied the response is still clean, because `projectCertificate` rebuilds the claim field by field; the wire case reddens only when both layers are careless, which is the correct behaviour of a test over composed behaviour, and each layer has its own case besides.

### 4. Where the security posture came from, in the order it was read

Every item below was read at its source before it was implemented, which is what [ADR-168](../decisions/ADR-168.md) asked of this slice.

| Ruled | Source | Implemented as |
|---|---|---|
| The claim is minimal | `INV-M11-01`, section 6.3 | `narrowClaims`, four keys by name over `jsonb` |
| `revoked_reason` never enters a response | `INV-M11-07`, `AS-M11-05`, `certificates_revocation_is_complete` | no field on `CertificateRow` |
| A revoked row renders as revoked | `INV-M11-08`, `AS-M11-02` | the `revoked` result renders; a `revoked` with no card is refused |
| `state` is derived, three members | `0020`, `ADR-040` | `deriveState`; `withheld` is not typed |
| The token is withheld while deferred | section 6.3, `certificates_code_uq` | the deferred branch never calls the signer |
| No timing defence | `INV-M11-05`, `FM-M11-05` | none written and none claimed |
| Every fetch is recorded | `SD-M11-04`, `AS-M11-04`, `FM-M11-04` | recorded before the response; a rejected write fails the fetch |

**Two of these are enforced by SHAPE rather than by a check, and that is deliberate.** A conditional that withholds a deferred token can be removed by an edit that did not understand it; a function with no path from a deferred row to the signer cannot. The same is true of `revoked_reason`: an allowlist that omits it is one line away from including it, and a row type with no field for it is a compile error away.

### 5. Two things reported rather than taken

**The deferred-and-revoked overlap.** `certificates_deferral_is_explained` and `certificates_revocation_is_complete` each constrain their own half and neither forbids both columns being set, so a deferral that was later revoked is representable. No approved document says which state that row is in. This file gives **revocation precedence**, because revocation is terminal where a deferral is a wait and because the CHECK guarantees a revoked row carries a class to publish; the `deferred` and `revoked` blocks track the columns, so the fact the row holds is not discarded. **That is a reading and it is recorded as one.**

**`user_agent_class` is not sent.** `0025`'s column comment is *"a class, never the string"* and no approved document enumerates the classes, so a taxonomy invented here would be a vocabulary nothing else shares. The column is nullable and the observation omits the field. **The digest is likewise the sink's**: `code_hash` and `ip_hash` are required to be digests and no approved document fixes the algorithm, so this route names what it observed and the writer hashes. Choosing SHA-256 here would be a constant the detector then has to match by coincidence.
