#### 2.1 `approved_at` is the one column that can lie, and the rule for it is already written

[ADR-290](../decisions/ADR-290.md) finding `F6` states it and this session confirmed it at the DDL rather than carrying it. The column is `NOT NULL DEFAULT now()` ([`0010:89`](../../packages/db/migrations/0010_payouts.sql)) and `0031` relaxed nothing, by its own stated design ([`0031:40-44`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)). **So a held row carries a non-null `approved_at` whose value is the insert time and not an approval time**, while [API_CONTRACT:515](../architecture/API_CONTRACT.md) types it `string | null` and says *"null while held: the hold is PRE-approval"*, which the declaration's own docblock repeats. **`listPayouts` suppresses `approved_at` to `null` when `status = 'held_pending_review'`, and a straight column read publishes a false approval time on the one state that most needs to render correctly.** The suppression is a rule already ruled, not a value invented.

#### 2.2 `failure_note` is served as the ruled absence, and the ruling says so in the contract's own words

The row's trap is that a field with no source is where a build session invents one. **There is nothing to invent here, because the corpus already states what the route serves.** [ADR-290](../decisions/ADR-290.md) section 2.5: *"`failure_note` IS SERVED AS `null` BY v1's `listPayouts`, ON EVERY ROW, AND THE CONTRACT SAYS SO."* [API_CONTRACT](../architecture/API_CONTRACT.md) section 6 carries the paragraph: *"`failure_note` IS `null` ON EVERY ROW v1 SERVES, AND THAT IS A RULING RATHER THAN AN OMISSION."*

**It is `null` by construction and not by omission.** The field describes `status = 'failed'` and nothing else, both edges into `failed` are enforcement acts, and no `payout_requests` row on this tree can reach that status. **Two things are owed before it carries a value and neither is `GET /payouts`'s**: the column [ADR-290](../decisions/ADR-290.md) section 2.4 specifies in full and refuses to write, and a field on `PayoutEnforceRequest` to supply it. **So the row's question, what the route serves in the meantime, is answered rather than open, and this is not a finding.**

### 3. The conflict, stated exactly

**Building `listPayouts` deletes a string another file asserts is present.**

[`apps/api/test/rule-state-producibility.test.ts`](../../apps/api/test/rule-state-producibility.test.ts), in the case `ONE file implements PayoutTx now, and it is still not installed`, reads `payout-backend.ts` as text and asserts, at [`:1243-1244`](../../apps/api/test/rule-state-producibility.test.ts):

```
for (const member of ['holdFlag', 'listPayouts'])
  expect(backend).toContain(`new PayoutBackendUnwired('${member}')`);
```

The stop condition requires `listPayouts` to answer. A member that answers does not construct `new PayoutBackendUnwired('listPayouts')`, so that case goes red. **The file is not in the fence and it is not `payout-backend.ts`'s suite**: it is a census over every deployable's `src/`, and [`wiring.test.ts`](../../apps/api/test/wiring.test.ts) cites it by name as where its own clauses are made predicates.

**The three ways out and why each is refused.**

| Way out | Refused because |
|---|---|
| Edit the assertion | The file is outside the fence the row states, and the row forbids widening it |
| Leave the case red | A session never ends on a red suite, and the row's verification block requires the counts reported at the moment of reporting |
| Keep the literal in a comment so the `toContain` still passes | **That is weakening a gate to pass it**, which the constitution's working agreements forbid in terms, and it would leave a census asserting a refusal that no longer exists |

**AND IT IS A RULING RATHER THAN A LINE, WHICH IS THE PART THAT MAKES THIS THE DISPATCHER'S AND NOT A SESSION'S.** The assertion is not incidental; it encodes `usePayoutBackend`'s own closing ruling, quoted in the case's comment: *"`listPayouts` and `idempotency` are both constructible today, and installing them beside a `transact` whose `subject` rejects is what `usePayoutBackend`'s entry refuses in its own closing sentence."* [`payout-backend.ts:44-48`](../../apps/api/src/payout-backend.ts) states the same rule from inside the module: *"A partial backend refuses AS A WHOLE or it is a fixture serving real traffic."*

**The condition that ruling names has already stopped being true.** `subject` no longer rejects: [ADR-308](../decisions/ADR-308.md) built its last two legs and the module's own header now reads *"`subject()` ANSWERS WHOLE"*. So the sentence protecting `listPayouts` rests on a premise the tree has moved past, while the members that still refuse, `holdFlag` and the hold branch, are slice 8's and cannot be scheduled at all because `HoldFlag.tosClause` has no value space and `DEP-M7-05` owes the clauses to counsel.

**Deciding whether the whole-refusal ruling still binds, and rewriting it where it lives, reaches [`wiring.test.ts`](../../apps/api/test/wiring.test.ts)'s `usePayoutBackend` entry.** [ADR-287](../decisions/ADR-287.md) section 8 already recorded that entry as owed to a later row: *"the next row that touches that entry should carry F1, F2 and F4 into it."* **That is a ruling this row's fence does not reach and this session did not make.**

**What the dispatcher can answer with.** Either widen row `311`'s fence to `rule-state-producibility.test.ts` and `wiring.test.ts` and say what becomes of the whole-refusal ruling, or rule that slice 7 lands only with slice 9 and leave `listPayouts` refusing until then. **This session took neither.**

**FINDING 2. NO ORDERING IS RULED FOR `GET /payouts` ANYWHERE, AND THREE THINGS DEPEND ON ONE.** [API_CONTRACT](../architecture/API_CONTRACT.md) section 6 declares `PayoutListItem` and states no order. The accessor cannot supply one: [ADR-112](../decisions/ADR-112.md) foreclosure 3 records that `ORDER BY` and `LIMIT` have no shape in it, and `rows()` takes a table key and nothing else. **And the portal declares that it renders in server order and deliberately does not sort**, [`view.ts:117-122`](../../apps/portal/src/app/payouts/view.ts): *"The history, in the order the server sent it. NOT SORTED HERE. The ordinal is the server's and a client that re-sorts a list of payouts has produced a second answer to 'which one was third'."*

**So a client that must not sort is reading a list nobody ordered.** The nearest precedent serves it unordered: [`certificates.ts`](../../apps/api/src/routes/certificates.ts)'s `readCertificates` is `(await tx.rows('certificates')).map(toCertificateRow)` on the same accessor with no sort. **Recorded rather than settled**, because choosing a sort key and a tie-break inside this adapter would be the route deciding an ordering the frozen contract does not state, and `PayoutListItem` carries no `payout_ordinal` to sort on even if it did.
