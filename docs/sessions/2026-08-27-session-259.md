`view/accounts.ts` and `view/marks.ts` are **unchanged**. The dispatch's fence allowed editing them if rendering forced a change and rendering forced none: every field the screens needed was already on the view models, in the right shape, with the invariants already expressed as required properties.

**Three decisions are worth their own line.**

**THE SEGMENT IS `.ts` AND NOT `.tsx`, AND THAT IS A FENCE RATHER THAN A STYLE.** A `.tsx` file needs `jsx` and a `dom` lib in [`apps/portal/tsconfig.json`](../../apps/portal/tsconfig.json), which [ADR-095](../decisions/ADR-095.md) `F7` assigns to whoever writes the first page and the root layout. `next@16.3.2`'s default `pageExtensions` is `["tsx","ts","jsx","js"]`, read out of the installed package's own `defaultConfig` rather than remembered, so a `page.ts` is a page and this segment changes no shared file at all. Measured after the build: `git diff apps/portal/tsconfig.json` is empty.

**THE CHART IS HAND BUILT BECAUSE THE REFUSALS ARE THE RENDERER'S.** [`view/marks.ts`](../../apps/portal/src/view/marks.ts) states NO GAP FILLING, NO SMOOTHING and NO DOWNSAMPLING and explains why each would invent a balance the ledger never held. A view model can state those and only a renderer can keep them, and each is one prop away in every charting library. `scale()` is the single `bigint` to pixel seam that module designed the `plot` fields for, and it is the only `Number(` in the file; it rounds, so the markup carries no floating point literal.

**THE AXIS LABELS ARE POINT STRINGS AND NEVER ROUND NUMBERS.** A chart normally picks round values for its axis and formats them, which would be this application computing a money value for display (`INV-M4-01`) and putting a figure on screen that no ledger row holds. The two labels are the highest and lowest figures actually present, rendered from the `EquityPointView` strings that produced them.

### 7. `VG-1` SCANS THE OBJECT GRAPH, SO ONE BRANCH'S TEST FIXTURE REDS EVERY OPEN PULL REQUEST

`CI-05 security static` failed on this branch and **not one of its four findings is in a commit this branch contains.** Reproduced with the workflow's own pinned binary, `gitleaks 8.30.1`, verified against `ci.yml`'s `GITLEAKS_SHA256` before it was run.

| Scope | Commits | Result |
|---|---|---|
| `--log-opts="origin/main..HEAD"`, this session's own commits | 9 | **no leaks**, exit 0 |
| `--log-opts="origin/main"`, main's whole history | 1,341 | **no leaks**, exit 0 |
| the whole object graph, which is what `gitleaks git .` reads | 1,481 | **4 leaks**, exit 1 |

The four sit in three commits on two OTHER branches, `claude/routes-affiliate` and `claude/routes-internal`, and `git merge-base --is-ancestor` says in both directions that none is an ancestor of `main` or of this head.

**THE MECHANISM IS THE FINDING AND IT IS NOT A DEFECT IN `VG-1`'s INTENT.** [`ci.yml`](../../.github/workflows/ci.yml)'s own comment is right that *"`VG-1` is gitleaks on the diff AND THE FULL HISTORY and a shallow clone has no history to scan"*, so `CI-05` takes the full fetch on purpose. What follows from it had never been met before today: `gitleaks git .` reads **every commit the clone holds**, so an unmerged sibling branch's blob turns `CI-05` red **for every open pull request at once**, including ones sharing no file with it. **23 pull requests were open when this was measured**, and this clears by no rebase, no re-run and no merge of `main`. The figure is a fact about a moment rather than a transcription target, which is [ADR-074](../decisions/ADR-074.md) section 3's own rule about counting identifiers; what does not move with it is that the blast radius is EVERY open branch rather than the two holding the finding.

**AND THERE IS NOTHING PORTABLE, WHICH IS A FACT ABOUT THE MECHANISM RATHER THAN A JUDGEMENT.** `gitleaks git` reads HISTORY, so a commit added anywhere cannot remove a blob from a commit already in the graph. Even the owning sessions cannot clear it with a follow-up commit.

**THE FLAGGED VALUE IS A UUID TEST FIXTURE**, a hardcoded literal on a `click_token` field in an `apps/api` test double, and `generic-api-key` fires on a high-entropy string beside a `token`-shaped key. It is a false positive on a constant, not a credential.

**AND DOCUMENTING IT IS WHAT PRODUCED TWO OF THE FOUR.** Session 255's log records the `CI-05` finding, session 254's log records the same line, and quoting the flagged bytes carried them into two more commits. **The natural response to a secret-scanner finding is to write it down, and writing it down propagated it.** That is why the paragraphs above name the field and the shape and quote no literal.

**Three repairs, all outside this fence and none of them this session's**: the fixture stops being UUID shaped (session 254); the two session logs stop quoting it (sessions 254 and 255); and because history is what is scanned, neither takes effect unless those branches' commits are rewritten before merge, **which is a decision about somebody else's branch**. A `.gitleaksignore` entry would also clear it and is deliberately not proposed: `VG-1` blocks merge, and an allowlist added by a session that does not hold the finding is a gate weakened from outside.
