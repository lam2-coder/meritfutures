## 2026-08-17 - Session 49: the nightly batch and `state_hash`, with the comparison deliberately not wired (non-money)

- **Done:** **The nightly batch exists and it folds through the engine's published interface only.** [`apps/worker/src/batch/`](../../apps/worker/src/batch/) carries three files: [`state-hash.ts`](../../apps/worker/src/batch/state-hash.ts) (SD-08, SHA-256 over ADR-026 C-07's nineteen columns in the declared order), [`ports.ts`](../../apps/worker/src/batch/ports.ts) (the I/O boundary, declared before its client exists), and [`nightly.ts`](../../apps/worker/src/batch/nightly.ts) (read ingest, fold `advanceDay` over the trading day, write `rule_states`). **`packages/rules-engine/src`, `test/` and `fixtures/` are untouched**, per the session fence, and the module resolver enforces it rather than a convention: `@merit/rules-engine`'s `exports` map publishes `.` and nothing else, so no path into the engine's internals exists from `apps/worker` at all. **`pnpm run verify` green: 6 of 6 invariants, 571 tests over 45 files, 15 gates clean and dirty, 16 scope cases.** Seventy-nine of those tests are this session's.
- **Next:** **The replay self-audit's COMPARISON, and it is deliberately not this session's.** `state_hash` is computed and written on every row; nothing yet re-derives a stored row and compares the two. It waits until more rules exist, because an audit run against six of eight rule groups would report agreement about the two it can fold and silence about the rest, which reads exactly like an audit that found nothing (FM-17). The other two next items are the adapter (blocked on a database client that does not exist) and the event sink (blocked on `0017`'s vocabulary mapping).
- **Blockers:** **The batch cannot run against anything.** There is no Drizzle client, no `pg` in any manifest, and [`packages/db`](../../packages/db/src/index.ts)'s `ScopedDb` carries one field. That is why the ports are declared and not implemented, and it is the same restraint `packages/db`'s own header states: "neither the client nor the accessor exists yet, and the scaffold does not invent them." The calendar transcription still blocks a batch run over real days, unchanged and a founder item.
- **Landmines:**

  - **THE HASH'S FRAMING IS A DECISION THE SOURCES DO NOT MAKE, AND IT FIXES EVERY STORED HASH FOREVER.** ADR-026 C-07 and M01 Appendix B.2 give three rendering rules and **no separator**: declared order, `bigint` base-10, `null` as an explicit sentinel, no whitespace. **Plain concatenation is not injective and the collision is one column pair away**: `traded_days_count = 1, win_days_count = 23` and `12, 3` both render `123`, so two genuinely different states carry one hash and INV-04 asserts nothing on exactly the counters R-33 and R-34 gate on. Each field is now length-prefixed `<utf8 byte length>:<utf8 bytes>`, which is injective **with no argument about the value domains**, because a separator character is injective only while no field can contain it and that is a claim a future column can falsify quietly. **It is settled now because `rule_states` has zero rows** (`0035`'s header says so in its own words), and this is the only moment at which choosing costs nothing. **Changing it after the first row lands invalidates every hash in the table and no migration repairs it, only a full audited rewrite under B.4.** Founder read wanted on this line specifically.

  - **`engine_gates` CANNOT BE `JSON.stringify` AND THE REASON IS NOT STYLE.** `JSON.stringify` **throws on a bigint** and four of the twenty-five leaves are `Cents`, so the obvious rendering does not merely drift, it does not run. Underneath that, M01 section 1.4 bans "iteration over an object's keys where the result affects output" and names "canonical serialization in `hash.ts`" as the replacement, so hashing today's insertion order would diverge every row in the book the day someone reorders two fields in `EngineGateResults` with no rule changed. The leaves are an explicit ordered list. **And the hash is over the ENGINE'S value, never over Postgres's `jsonb`**, which stores keys sorted by length then bytewise: a hash recomputed from a round-trip is a **different serializer** and would disagree with every hash the batch wrote. `RuleStateRow` says so on the column.

  - **`account_id` IS COLUMN 1 AND IT IS NOT ON `RuleState`.** `DayInput` carries no account id by design ("the fold is per account by construction and the caller that supplied the marks is the one that knows whose they are"), so the batch supplies it and nothing else can. It is **asserted** as a canonical lowercase UUID rather than normalized: a caller that started sending upper case would otherwise keep working while every hash it produced changed, and that divergence is invisible in a field diff because the field is not on the state.

  - **THE WATERMARK IS READ BEFORE THE SLICE, AND REVERSING TWO LINES IS A SILENT LIE.** If a correction commits between the two reads, the slice carries it and the stamp does not, so the row claims an **older** calendar than the one it read: replay finds it out of scope and B.4 step 4 rewrites it, which is the protocol working. Reversed, the row claims a calendar it never saw and, in [`0035`](../../packages/db/migrations/0035_rule_states_calendar_revision.sql)'s own words, "replay would then believe a stale row was current". **This is the code half of the trigger `0035` refused to write**, and it is asserted on call order rather than left to a comment.

  - **`context_gates` IS `NOT NULL` AND THE DAY FOLD DOES NOT PRODUCE IT.** SD-06 splits the gates precisely so the context half never enters the replayed state, so `advanceDay` returns none, and a `rule_states` row cannot be written without them. The batch asks **`evaluatePayout`** rather than re-deriving R-40 in a worker, which would be a second implementation of a money gate outside the engine. R-06 is satisfied rather than strained: the state passed is the day the batch just closed. **`requestedCents: null` is ADR-009's "pay the maximum I am eligible for"**, which is the right argument for a question that is not a request.

  - **`0015` NAMES FOUR CONTEXT GATES AND THE ENGINE PUBLISHES FIVE.** The column comment says "freeze, recon_blocked, KYC, in-flight"; `ContextGateResults` carries those plus **`accountActive`**, which R-40 states and API_CONTRACT's eligibility shape renders, and R-38's in-flight verdict is reported on its own field because API_CONTRACT has no slot for it. The engine's shape is what gets stored, so the column and the endpoint speak one vocabulary. **`0015` is merged and only an ADR moves it**, so this is flagged rather than reconciled.

  - **M01 SECTION 1.3 PUTS `hash.ts` IN THE ENGINE AND THE LINT RULE WOULD REFUSE IT THERE TODAY.** `merit/engine-purity` reports **every non-relative import** inside `packages/rules-engine/src/**`, so `import { createHash } from 'node:crypto'` is an error, while M01 section 1.4's own banned-constructs table permits "`crypto` **beyond a pure hash**". **The prose allows the import the rule refuses.** Building in `apps/worker` sidesteps it and does not resolve it: whoever writes `hash.ts` must take a scoped lint exception or hand-roll SHA-256, and neither is a decision to make in passing. Carried as `OI-15`. The module is written so that resolving it is a **file move**: it imports published types and `node:crypto` and nothing else.

  - **A TYPECHECK FAILURE LANDED BECAUSE A PIPE ATE ITS EXIT STATUS.** `pnpm run typecheck 2>&1 | tail -8 && git commit ...` continues past a red compile, because a pipeline exits with the status of its **last** command. The branded `BasisPoints` literals in the batch test were pushed broken and fixed one commit later. **This is not a new lesson and that is the point**: `falsify-ci.mjs` already refuses to trust a run it cannot bound. A check whose failure cannot reach the shell is a check that passed.

  - **EVENTS ARE RETURNED AND NOT PERSISTED, AND THE REPORT SAYS SO RATHER THAN THE MEMORY.** `advanceDay` emits M01 section 5's facts; writing them needs `0017`'s tables and EVENTS.md's vocabulary mapping. They are carried on each outcome so the gap is visible in the type.

  - **THE ADAPTER OWES A PER-ACCOUNT ADVISORY LOCK AND NO LOCK API WAS INVENTED.** FM-10: "settlement webhook and nightly batch race on the same account", answered by "`applySettlement` is the only writer of anchors, is idempotent on `payout_request_id`, and the batch takes a per-account advisory lock". The lock belongs with the connection and the connection does not exist, so it is named in `runNightlyBatch`'s contract instead of stubbed.

### What `0033` and `0035` bought, and why the computation lands before the comparison

**`INV-04` is "replaying every mark from day one reproduces stored state byte-identically", and this session builds the left-hand side of that sentence.** The right-hand side is the audit, and it is not wired.

Saying that plainly is the point. A green suite over a batch that computes `state_hash` looks exactly like a green suite over a batch whose hashes are being **checked**, and the difference is the whole of `INV-04`. The [PR](../../apps/worker/src/batch/nightly.ts) says it, `nightly.ts`'s header says it, and this entry says it, because the failure mode is not that somebody lies about it: it is that six weeks from now nobody remembers which half exists.

**What makes the computation worth landing early is what the two migrations already installed.** [`0033`](../../packages/db/migrations/0033_trading_calendar_revision_required.sql) made the calendar's prior image **mandatory**, so every correction leaves an unforgeable record of what the calendar said before it moved; it exists because ADR-042 F-2 "landed as a table nobody is required to use", and its own header names the consequence exactly: replay was "unable to tell a calendar correction from an engine regression, on the nightly self-audit, at the moment somebody is paging". [`0035`](../../packages/db/migrations/0035_rule_states_calendar_revision.sql) then **joined that record to a state row**, because `0033` left replay holding the evidence with no way to scope by it.

Together they are what makes a calendar correction **distinguishable** from an engine regression. Before them, a holiday correction fell into Appendix B.3's "anything else: page", and since a calendar correction changes the day sequence for **every account at once**, the first one diverged the whole book: 5,000 pages on one morning, which is how B.5's warning comes true. **The alarm does not fail by being wrong. It fails by being right five thousand times.**

**The half those two migrations could not install is the one this session wrote.** `0035`'s header refuses a trigger asserting the stamp is current, and refusing is the ruling rather than an omission: a correction committing between the fold and the write leaves a row that genuinely read the older calendar, and stamping it with the newer watermark "records a calendar it never saw". No per-row constraint can tell "not yet written" from "pristine calendar" without fabricating, which is `OI-14`. So the honest stamp is the one the fold read, and **only the batch is in a position to write it** because only the batch knows when the fold ran. That is now two lines in `runNightlyBatch`, in the order that makes them true.
