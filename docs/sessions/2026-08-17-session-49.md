### What `RE-C-oracle` is, and why it is worth more than nineteen more assertions

`test/generators/validate-plan.ts` transcribed the same nineteen rules from the same table in **session 40**, before any engine code existed, and its own header explains why it is deliberately not the generator: "If one module did both, the counterfactual would prove only that the code agrees with itself."

`plan/validate.ts` was written from M01's table and the two were compared **afterwards**. `RE-C-oracle` is that comparison as an executable check: each of the nineteen seeded violations is built in both stored shapes and both validators must name the same id. That is constitution C10's writer/reviewer split arriving as a test rather than as a process claim.

**The two differ in three places and none is a rule**, each documented at its site:

1. **The oracle calls `isInt` on money and this file cannot.** Its money is `number`, so half a cent is constructible and has to be rejected; here money is `Cents`, which is `bigint`.
2. **The oracle reads one merged `MaterializedPlan` and this file reads two stored shapes.** Where the merged view has one field, the tree has a jsonb key and a materialized column that can disagree, so `CV-09`, `CV-11`, `CV-12`, `CV-16` and `CV-17` name which of the two they read. The three `MZ-` findings are what make that choice safe instead of arbitrary.
3. **The oracle stops at the nineteen.** `PW-01` to `PW-04` and the materialization findings are here because this is the publish path.
