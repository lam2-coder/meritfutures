### 4. Two findings, both pre-existing, both tree wide, neither repaired

**A `:code` over 100 characters answers `414` in Fastify's own shape.** Fastify's `maxParamLength`
defaults to 100 and `buildServer` does not set it, so the response is `application/json` carrying
`{"error":"Bad Request","code":"FST_ERR_MAX_PARAM_LENGTH", ...}` **with the request path echoed
back**. It costs two things the corpus asks for. It is a **length oracle**, and ADR-170 foreclosure 3
refuses a shape check precisely because it "would hand an attacker the token's alphabet and length
for free"; it arrives **before the floor**, so it is a faster path as well. And it escapes
[`server.ts`](../../apps/api/src/server.ts)'s error model, whose own header says a status it has no
canonical code for becomes a logged `internal_error` and whose 404 handler exists so the framework's
shape and the path never reach a caller. **Measured identically on
`GET /certificates/:code/image.png` and `GET /accounts/:accountId/purchases`**, so it is not this
slice's and the fix is a Fastify option in a shared file or a ruling on what a long path parameter
answers. The case asserts the real behaviour and the boundary at 100, so the day it is fixed the case
goes red and names the ruling that fixed it.

**A `:code` of `..` or `%2E%2E` is normalized by the router and answers the router's 404.** That 404
is contract shaped, produced by `server.ts`'s not-found handler, and it discloses nothing about the
book: no `certificates.code` can be `..`, since a code that is not routable is a code that was never
issued to anybody. Named because "a malformed token answers `unknown`" is otherwise read as total.

### 5. Two things this session could not close and did not paper over

**The floor has no upper bound.** `readPresentation` refuses a `floor_ms` that is not a positive
whole number of milliseconds and refuses nothing about its size. No approved document bounds it, and
a bound invented here would be this route choosing a latency budget the corpus has not chosen, which
is `certificates.ts`' refusal to invent a digest constant applied to a clock. A misconfigured
deployment can therefore hold every public verification for an hour, and the case asserting that is
labelled as the gap rather than as the behaviour.

**The revoke's preview is rendered with the operator process's copy.** ADR-170 section 6.2 makes the
response "exactly what `GET /verify/:code` will return for that code", and the two surfaces are two
deployments. Sharing the FUNCTION is what the file can guarantee, and it does: `renderVerify` is
imported from `verify.ts` and is the same code path, so the shape and the branching cannot drift.
Sharing the CONFIGURATION is the deployment's, and a check written in this file would compare this
process's copy against itself.

### 6. What the E2 read is owed on

**Neither handler moves cash and neither opens a ledger transaction**, and ADR-170 says the same
about itself. What the read is owed on is the disclosure boundary and the audit:

1. **`VerifyRow`'s field list**, because it is the disclosure control. `id`, `payout_request_id`,
   `revoked_reason`, `identity_id`, `account_id` and `deferred_reason` have no field on it, so no
   projection in `verify.ts` can reach one. That is the property seed 8 had to defeat in three edits.
2. **`narrowClaims` reused rather than re-written.** The `jsonb` allowlist is `certificates.ts`' and
   there is one of it, not two.
3. **The derived initiative table**, `INITIATIVE_BY_CLASS`, against ADR-170 section 6.2's own table
   and `admin_actions_on_behalf_matches_initiative`.
4. **The order of the two writes in the revoke**, audit first, and `before` carrying all three
   columns of `certificates_revocation_is_complete`.
5. **The floor's placement**: every response after the presentation resolves, the log write inside
   it, the overrun logged rather than failed.
