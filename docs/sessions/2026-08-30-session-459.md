**Objective.** Rule the choice [ADR-264](../decisions/ADR-264.md) section 5 named and declined: `ADR-211` clause 2's two-transaction remedy on the calendar half, or a sixth `CATALOG_TABLE_KEYS` member.

**Outcome.** Both refused. The day is a named door on the scoped transaction, and the payout port is not wired.

---

### 1. The choice, ruled in one sentence

**The day is `ScopedTx.lastClosedTradingDay()`, a named door, because a catalogue read would hand the payout route `R-06`'s own selection and a second transaction would compute a verdict from a calendar snapshot the transaction recording it never read.**

**The losing option is the sixth key**, and it lost on **what it hands out** rather than on what it costs. It is the shorter diff, `refuseUncatalogued`'s admission test is met by the table, and the argument [ADR-233](../decisions/ADR-233.md) requires of a member was available.

### 2. Why each option lost, at source

| Option | Why it lost |
|---|---|
| **A sixth catalogued key** | A catalogue read hands out ROWS. The fold the caller then holds is not a lookup, it is **`R-06`**: which of every trading day the exchange has ever had is the last closed one. **That fold exists twice in this tree and the two disagree** (below). And the answer needs TWO tables, because coverage lives in `trading_calendar_loads` and the registry says a reader must consult both, so the admission would be two keys and the caller would still be the thing joining them |
| **[ADR-211](../decisions/ADR-211.md) clause 2's crossing** | **That entry's own clause 4 states the precondition**: a migration pinning the readable rows, after which *"nothing readable can move, and the transaction count stops mattering entirely"*. `0028` and `0066` are that pin. **`trading_calendar` is the one table the corpus built a correction mechanism FOR**, so no such pin exists or should |

**THE TWO EXISTING STATEMENTS OF `R-06`, MEASURED.**

| Statement | What it folds on | Coverage |
|---|---|---|
| `readLastClosedTradingDay`, [`apps/worker/src/batch/adapter.ts`](../../apps/worker/src/batch/adapter.ts) | the maximum `trading_day` | **not consulted.** `calendarCarriesDay` guards only the `MERIT_BATCH_TRADING_DAY` override path, and reads `trading_calendar` rather than the loads table |
| `lastClosedDay`, [`apps/api/src/admin-source/liability.ts`](../../apps/api/src/admin-source/liability.ts) | the maximum close INSTANT, day tiebreak | **consulted**, by `anchorCalendar`, which can answer `uncovered` |

**Under a well-formed calendar the two agree, which is exactly why the divergence is dangerous rather than obvious: they differ only where the answer matters.**

### 3. What the two-transaction crossing would have cost, established rather than asserted

The row required this before the choice, and the answer is that **the calendar can move between the two reads**.

| Fact | Where |
|---|---|
| `merit_app` holds `SELECT, INSERT, UPDATE, DELETE` on every table in `public` | `0026`'s `GRANT ... ON ALL TABLES` |
| `0032` revokes `UPDATE, DELETE` **only on `trading_calendar_revisions` and `trading_calendar_loads`** | `0032`'s revoke block |
| CALENDAR-C1, C2 and C3 **record** a correction rather than preventing one | `0033`, `0048` |
| The table carries an `updated_at` and its satellites do not, **because a correction is an `UPDATE`** | [`schema.ts`](../../packages/db/src/schema.ts), in its own words |
| A calendar correction triggers the same replay protocol an engine upgrade does | [M01](../plans/M01-rules-engine.md) section on `INV-22`, [ADR-047](../decisions/ADR-047.md) |

So a correction landing between the two transactions produces a verdict whose **basis day the recording transaction never read**, stored in `payout_requests.basis_trading_day` and in an `eligibility_snapshot` that `INV-22` says is never rewritten.

**`databaseEconomicCalendar` is not a counter-example.** It reads the same table on `ApiDb.firm` and is correct there: it counts sessions still **ahead** for a freshness panel, selects no day and writes nothing. **The same table on the same door answering a different question is not the same read.**

### 5. The finding that is larger than the door

**Two cases were written to assert that a `Date` on a calendar row THROWS. Both passed green-side-up, and measuring why produced this.**

| Step | Measured |
|---|---|
| `pg`'s type parser for OID 1082 (`date`) | returns a JS `Date` **at the process's LOCAL midnight**. `grep -rn setTypeParser packages/db/src` returns nothing |
| Drizzle's `PgDateString.mapFromDriverValue` | renders that `Date` with **`toISOString()`**, which is UTC |
| The database day `2026-08-28`, read at `TZ=Europe/Berlin` | arrives in Merit code as **`'2026-08-27'`** |

**That is [ADR-146](../decisions/ADR-146.md) clause 4's forbidden failure performed by two libraries, on every `date` column in the estate**, with nothing between the database and the consumer that raises. `0032`'s own DDL comment calls the bound *"the exchange's CT trading day, never a UTC calendar date derived from a timestamp"*.

**REPORTED AND NOT REPAIRED, ON THE FENCE.** The repair is one `setTypeParser` call in `packages/db/src/client.ts`, which row `268` does not fence, and it changes the reading of every `date` column at once. **What is paid here is the observation**: three cases assert the measured behaviour, one of them saying in its own comment that it is a bug report rather than a control, and one asserting that no `setTypeParser` call exists. The door's guard is neither loosened nor deleted; it still catches a malformed string, and a non-string dies in the mapper, so the door fails closed either way.

**A process at `TZ=UTC` is unaffected, and `INFRA` names no timezone. That is the point: the correctness of every trading day in the estate rests on an environment variable nobody has written down.**
