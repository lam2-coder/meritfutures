Row `353`: write the adapter for `apps/worker/src/digests/alarm.ts`'s `findUndeliveredWindows`, and rule on its clock.

### 3. Ruling one: all three members, and no refusal

`read` is `WorkerDb.batch` narrowed to a handle carrying `rowsWhere` and nothing else. `terms` is `atLeast`, passed through untouched because `packages/db` recognises a term by `WeakSet` IDENTITY and a wrapper would hand back something the accessor refuses at the first live scan. `now` is the injected process clock, which `job.ts` already spends at the wiring for the nightly fold.

**The three rows this wave that refused a fifth port each refused a capability this repository does not contain**: an event sink that `RI-04` puts out of reach, or a fact this estate cannot produce. **There is no analogue here.** The alarm writes nothing, emits nothing, reads no trader-bearing table, and its two tables are `firm`, so no identity cast, no second door and no scope predicate is in play. Manufacturing a refusal to look rigorous was the one outcome the dispatch put a burden of proof on, and nothing met it.

**The narrowing is the one real decision in the file.** `ports.ts` section 3 says `SystemTx` satisfies `DigestReadTx` structurally, and it was tested and it does. **It is a claim about the type.** A pass-through leaves `insert`, `updateAt`, `deleteAt` and `sqlExecutor` on the object the alarm is holding, and `alarm.ts` rests its whole construction on the alarm being unable to discharge the window it complains about, so the adapter builds an object with one method and the suite counts KEYS.

### 4. Ruling two: not scheduled, and the reason is its own

[ADR-345](../decisions/ADR-345.md) was read before this ruling was taken, as the dispatch required, and **its reasoning does not carry over.** That row refused a clock for a control that finds missing money, because `recon_blocked` is a payout veto with no clearing path and because its cron row named a different check. **Neither applies here and both run the other way**: this job cannot write, so it cannot block anybody, and the inventory row it answers to states this alarm's finding in its own words.

**So the reason had to be its own, and it is that the alarm has no subject.** Nothing writes a `report_schedules` row: no `.insert('reportSchedules', ...)` under three `src/` trees, no `INSERT INTO report_schedules` in any migration, no seed. A scheduled run returns zero findings over zero schedules and publishes a green metric an operator is entitled to read as evidence. **That is worse than silence, because silence does not claim anything.**

**And a finding would reach nobody even with a subject.** The report type has no consumer, the two metric names appear in no `src/` file outside the alarm's own comments, no event sink is reachable, and this job IS the dead-man switch rather than a job one watches, so there is no completion signal whose absence would page.

**No number was invented.** Which finding kinds should fail the process is the founder's, recorded with its three options.
