### The finding: the sixth view is not a signal, and it reads two tables

**The brief lists "shared payout destination" beside five signal kinds, which reads as though all six are one query with a different `kind` in it. They are not.**

The approved model's **settlement-rail identity** is `identity_signals.kind = 'rise_identity'`: **who the rail says the payee is.** `D-09` reads `payout_transfers.destination_ref`: **where the money actually went.** Those are different facts about different objects, and a view that answered the first while claiming the second would look right and mean something else. A destination is not an attribute of an identity at all; it is an attribute of a transfer, which is why no `kind` for it exists and why none should be invented.

**And it reads both legs, which is the half that would have been missed.** [ADR-028](../decisions/ADR-028.md) retired `transferring` from `payout_requests` and moved the external leg to `wallet_withdrawals` (`SD-M5-06`), so `destination_ref` now lives on two tables. `D-09` names only `payout_transfers`, because `D-09` was written before the split. **A view reading `payout_transfers` alone shows a clean board while one destination collects wallet withdrawals from four identities**, which is [M07](../plans/M07-risk-abuse.md)'s own *"strongest mule detector available"* going blind on precisely the leg [ADR-019](../decisions/ADR-019.md) created. Reading both columns is not new detection and not a widened scope: it is the same query over both places one fact is now stored.

**This is stated in section 7.10 rather than absorbed**, and a test pins it, because the cheap simplification a later session reaches for is to collapse the sixth view onto `identity_signals` so that all six look alike.

### What section 7.10 argues rather than asserts

1. **The sort is the ruling, and the sort key is `P-M6-01` with four constraints on it.** Sorting by signal count ranks the coffee shop first, which [M07:94](../plans/M07-risk-abuse.md) says is not a person. Sorting by liability makes it a risk tool. But the figure has to be the right one: it **includes wallet balances** (`INV-M6-11`), it is the **authoritative as-of-last-closed number and never section 3.5's live one** (`INV-M6-12`), it **names its as-of** (`INV-M6-04`), and it is **suppressed when data trust is red** (`P-M6-09`). The second of those is the one worth arguing: [ADR-020](../decisions/ADR-020.md)'s rule is that the live figure decides nothing automatically, and **a sort order is a decision about what a human looks at first.** A live number in that column makes the ordering of a risk surface a function of an intraday vendor feed.
2. **Summing liability across a soft-linked group is not cap aggregation.** This is the paragraph the section most needed and the brief did not ask for. [M07](../plans/M07-risk-abuse.md) section 3.1 says caps do not aggregate across a soft link, which is a statement about **what a trader may buy**. The column adds up **what Merit already owes**, which is true whether or not the identities are one person. A reader who conflated them would either delete the sort key or enforce a merge nobody decided. The row is evidence of exposure; only the merge is a decision.
3. **Suppressed edges leave the aggregate and stay visible as history.** `SD-M7-04` exists because housemates, married couples and a father funding a son's evaluation all produce genuine edges between genuinely different humans. A sort key is exactly where a disputed edge would quietly go on contributing.
4. **The jump to section 7.9 cannot be the only destination.** [ADR-022](../decisions/ADR-022.md) tiers the explorer to **v1.x** and these views are **SHOULD**, so a row whose only exit was the explorer would be a surface that does nothing until a post-launch module lands. Every row also opens the identity drill-down at section 3.2a, which is v1. **This is [ADR-041](../decisions/ADR-041.md)'s argument applied one surface over**, and section 7.9 already carries it in its own restriction row.
5. **`INV-M6-10` holds because the subject is the signal.** Naming a signal and listing the identities that share it is a specific-subject query. The list of signals is not a list of humans, no view offers an all-identities browse, and there is no export affordance on any of the six.

### Landmines

**The test's own first draft carried two defects, both found by its own guards rather than by review, and both are the class [CLAUDE.md](../../CLAUDE.md) says a bigger model does not fix.**

**The first is a regex that matched the wrong table.** The kind cross-check parsed `identity_signals`' allowed values with `/CHECK\s*\(\s*kind IN \(/`, which found the **notification-channel** kinds further down [`0029`](../../packages/db/migrations/0029_phone_identity_and_auth.sql) and produced the three-value set `'email', 'push', 'sms'`. Every view would then have been asserted against a vocabulary from a different module. **It was caught by the `kinds.size >= 10` guard**, which existed only because this repository's runners already require a parser to prove it parsed something. The expression is now anchored on the constraint name, and the guard is now documented as the thing that caught it rather than as decoration.

**The second is that two migration comments quoted as primary sources are hard-wrapped at 79 columns.** `toContain` against the raw file was therefore asserting on **where the original author pressed return**, and both quotations failed despite being accurate. A `prose()` helper joins comment text before matching. Same class as [session 89](2026-08-20-session-89.md)'s `/\btime_?zone\b/`, which could not match `display_timezone`: an assertion that reads a file as bytes when it means to read it as prose.

**A third, which is a coordination hazard rather than a defect.** [M06](../plans/M06-admin-ops-console.md) section 8.2's named-scenario table is being appended to by `F2` in this same fold, which owns `GS-288` to `GS-290`. **This session cites `GS-291` and `GS-292` inside its own section and does not touch 8.2.** The ownership index is what `CI-06d` actually reads and it already assigns both to M6, so the gate is satisfied without a second writer in one table. **Section 8.2 is now a table that two concurrent sessions have reason to edit and neither should**, and it is named here so the merge does not discover it.
