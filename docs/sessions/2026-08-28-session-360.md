### 1. THE RULING, AND IT IS THE EXTENT RATHER THAN THE SHAPE

**The question was whether a name-shape rule that reads `_day` as "trading day" is the wrong SHAPE,
the wrong EXTENT, or right with an exemption. It is the wrong extent, and the primary source that
says so is the frozen contract rather than the schema.**

Parsing every `ts` block of [API_CONTRACT](../architecture/API_CONTRACT.md) for a member whose name
ends `_day` or `_on` returns **22 declarations over 14 distinct keys**, and they fall in four forms:

| Form | Distinct keys | The keys |
| --- | --- | --- |
| `YYYY-MM-DD` string | 7 | `as_of_trading_day`, `basis_trading_day`, `closed_through_day`, `first_detected_on`, `opened_on`, `release_trading_day`, `trading_day` |
| `string \| null` | 5 | `closed_on`, `covered_through_day`, `funded_on`, `next_eligible_trading_day`, `trading_day` in `TimelineItem` |
| container | 1 | `by_day` |
| **`boolean`** | **2** | **`traded_day`, `win_day`** |

`trading_day` appears in two forms, which is why 7 + 5 + 2 + 1 exceeds 14.

**The two booleans are one line of the contract**, [`API_CONTRACT:418`](../architecture/API_CONTRACT.md):
`traded_day: boolean; win_day: boolean;`, inside section 6's `MarkListItem`. Section 1's Time rule,
which the sweep was enforcing, is nineteen lines away in the same document at `:33`. **So the sweep
refused a form its own primary source declares, and it was not close to the edge of the document: it
was two sections away.**

**Session 356's sentence is true and it is not the whole document.** It reads *"which is correct for
every typed response in section 8"*, and it is; the collision is with **section 6**, which that
session had no reason to read because the drill-down is a section 8 route. **The cheapest available
check would have found it**: [`account-reads.ts:170-171`](../../apps/api/src/routes/account-reads.ts)
declares `readonly traded_day: boolean; readonly win_day: boolean;` and `:643-644` puts both on the
wire for `GET /accounts/:accountId/marks`. **A live trader route in this tree has been shipping the
two fields the admin sweep calls impossible.** That route does not run the sweep, which is the only
reason the contradiction has been quiet.

**WHY BY TYPE AND NOT BY AN EXEMPTED LIST.** The dispatch named the hazard and it is real: `RI-05`'s
`covers` line calls two files holding one number *"a hand-maintained count in a different costume,
and it drifts the same way"*. **A list of `traded_day` and `win_day` would have been stale before it
was committed.** Sweeping the migrations for a column whose name ends `_day` or `_on` returns **29
distinct columns**: 3 are `boolean`, 1 is `text` (`breaks_on text[]`, [`0023:58`](../../packages/db/migrations/0023_loyalty_and_graduation.sql)),
and the rest are `date`. **The third boolean is [`0004_catalog.sql:323`](../../packages/db/migrations/0004_catalog.sql)'s
`is_half_day boolean NOT NULL`, on `trading_calendar`** -- the table the whole trading-day concept
lives in carries a boolean whose name ends `_day`. A case reads that column out of the migration and
admits it, so the staleness argument is asserted rather than asserted-in-prose.

**WHAT ADMITTING A BOOLEAN COSTS, WHICH A CONTROL HAS TO ANSWER BEFORE IT LOOSENS.** The rule exists
to catch a value that COULD be a day and is the wrong FORM of one. **A boolean is not a failed day.
No date rendering path in any language produces `true`.** The forms a wrong trading day actually
takes are a UTC instant, an epoch second, a `Date`, and a date missing its zero padding, and **all
four are still refused, on every one of the 14 declared names**, which is the second new case.

### 2. THE HALF THAT TIGHTENS, AND IT WAS NOT IN THE DISPATCH

**A `Date` under a day-shaped name PASSED the sweep, and that is the exact defect the sweep exists
to catch reaching the wire through the sweep.**

The container exemption was written for a real shape: `LiabilityResponse.eligible_next_7d.by_day` is
an array whose elements each carry a `trading_day`, so an object or an array under a day-shaped name
has to be walked rather than string-matched. It was written as
`typeof member === 'object' && member !== null`, and **`Object.entries(new Date())` is `[]`**. A
`Date` is an object, is not null, is walked, carries no own enumerable property, and is admitted.
Measured before the repair, `{ trading_day: new Date('2026-08-27T00:00:00Z') }` was **ADMITTED**, and
`JSON.stringify` renders it `{"trading_day":"2026-08-27T00:00:00.000Z"}`. **That is section 1's
forbidden UTC instant, standing where the contract types an exchange trading day, delivered to an
operator by the control.**

`isWalkableContainer` now descends into an array or a plain object (`Object.prototype` or a null
prototype) and nothing else. **No projector in this tree hands the sweep a `Date` under such a name
today**, because each converts one to `YYYY-MM-DD` through its UTC parts first, but that is a
property of every writer rather than of this reader, which is exactly the kind of thing that is
remembered until it is not.

### 3. WHAT A NULLABLE TRADING DAY SERVES, AND THE CONTRACT HAD ALREADY ANSWERED IT

**An explicit `null`, under a key that is always present.** The contract writes `string | null` five
times under day-shaped names, twice on one line of `AccountDetail`
(`funded_on: string | null; closed_on: string | null`). **An absent key is a wire shape the document
never declares anywhere**, so session 356's landmine 2 was not a choice between two defensible
answers: it was the only shape the broken sweep admitted.

Nine `optionalDay` call sites across three projectors (`account`, `rule_states`, `payouts`) change
what they put on the wire. **Not one of them is edited**: the spread stays at the call site, which is
where a reader sees which columns are nullable, and the helper's return type moves from
`Record<string, string>` to `Record<string, string | null>`.

### 4. THE BOOLEANS ARE CARRIED, AND UNDER WHAT AUTHORITY

**No contract moved, so there is no ADR.** The question the dispatch posed was whether
`GET /admin/accounts/:accountId` declares them, and it declares nothing field by field: its
field-level schema is the DEBT [`admin-reads.ts:672`](../../apps/api/src/routes/admin-reads.ts)
records, because section 8 describes the route in prose and section 1's allowlist policy has no
schema to apply.

**What the drill-down's own module header already ruled is what carries them**: *"every field is the
DDL's own column, in the DDL's own name, snake_cased"*. Under that rule the two columns were always
in scope, and the only thing keeping them off the wire was a control that refused them. **The repair
removes the obstacle rather than adding a field**, and the two names it puts on the wire are the
same two names section 6 declares for the same two columns of the same table.

**Nothing was renamed and no field this schema does not have was invented**, which was the answer
session 356 correctly refused.
