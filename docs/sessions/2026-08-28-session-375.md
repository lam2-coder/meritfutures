**Objective, as performed.** The liability dashboard has a route. It is `/`, the build prints it, and its renderers are wired to it. So this session measured that, built the one screen that genuinely does not exist, and repaired the stale port count the measurement exposed in five files.

### 1. The refutation, derived rather than assumed


**The dispatch's count is exactly right and its inference from it is not.** `/` is the liability dashboard. [`src/app/page.tsx`](../../apps/admin/src/app/page.tsx)'s first line of header is *"THE CONSOLE'S ROOT ROUTE, AND IT IS M06 SECTION 3.1's LIABILITY HOME"*, and the next paragraph is titled *"WHY THE LIABILITY HOME IS `/` AND NOT `/liability`"*. There is no `/liability` in that list because there was never meant to be one.

The chain from session 364's arithmetic to the served bytes is unbroken, checked link by link rather than assumed:

### 2. `/search`, and the term is the whole precondition

[`src/app/search/account-search.tsx`](../../apps/admin/src/app/search/account-search.tsx) is the document and [`src/app/search/page.tsx`](../../apps/admin/src/app/search/page.tsx) is the route. The build now prints **seven** routes and `/search` carries the **dynamic** marker.

**`FM-M6-10` is refused rather than described.** That failure mode is *"search returns a result set that enumerates identities"*, whose control M06 section 6 writes as *"search requires a specific subject term"*. Three things follow and each is a behaviour rather than a sentence:

- A page value with a blank term **throws**, in `assertQueryNamesASubject`, before a byte is built. The server already refuses the same input on the wire; this refuses it on the DOCUMENT, and the two fail at different times, because a document handed rows by a supplier that never consulted the route would render them and the endpoint's guard cannot see that.
- The route's **no-term arm renders the box and no row**. An operator arriving at `/search` with nothing typed has not made a mistake, so there is no refusal message there either; what is refused is a page VALUE with no term, which is a defect a supplier would have to commit.
- **A repeated parameter is refused rather than resolved.** `?query=a&query=b` arrives as an array and picking either half would be the route deciding which subject the operator meant.

**It is its own segment and not `src/app/accounts/page.tsx`.** `M6-A-66` asserts that directory holds exactly `['[accountId]/', 'account-detail.tsx']`, and it gave two reasons with a note that the second outlives the first. **The first has expired and the second has not**, which is the whole value of having kept them apart: the fence read *"`AdminReadSource.searchAccounts` is owned by no plan at all"* and both halves of that are now false, while *"an index with no query behind it is FM-M6-10"* is an invariant. That reason is corrected where it is written rather than worked around, and the case itself is unchanged.

### 3. Three controls the screen carries, and why each is a control rather than a comment

**`INV-M6-10` is a CLOSURE here and not a refusal.** [`assertNamesNoSubject`](../../apps/admin/src/page.ts) is deliberately not called: it would refuse the accounts the operator asked about, which is the one thing this screen exists to render. The rule is [`identity-graph.tsx`](../../apps/admin/src/app/identities/identity-graph.tsx)'s applied to a different closure -- every subject-shaped id served must be the TERM or an `account_id` or `identity_id` of a row this page carries -- and the width is the point: `email`, `plan_code`, `phase` and `status` are server-supplied strings, so an id written into any of them reaches the screen through a field nobody classified as one. Three seeds prove it, one per field.

**A result set spanning several humans is inside the licence and that is ruled rather than assumed.** M06 section 7.10: *"naming a signal and listing the identities that share it is a specific-subject query: the subject is the signal"*, and `ADR-194` clause 3 admits a coupon for exactly that reason. **The fixture is three rows over TWO humans**, so the row count and the human count differ and a closure keyed on the wrong one is caught by them disagreeing.

**The cursor is never served, which removes a class of leak rather than guarding it.** Session 371 records both cursor components as primary keys, `(identity_id, account_id)`, so the token is a subject identifier in an encoding no closure can read. What an operator needs from it is the FACT rather than the token, and `next_cursor === null` is that fact: the difference between an exhausted query and a full page, which is the pair `ADR-157` leaves in place of a `total` nothing in this system can compute.

**`INV-M6-04` withholds the three amounts, on two independent mechanisms.** `AdminAccountSearchItem` carries `size_cents`, `balance_cents` and `withdrawable_cents` with no `as_of` and no source, and [`figure.ts`](../../apps/admin/src/figure.ts)'s `ORIGIN_ID` closes the admissible roster at `P-M6-01` to `P-M6-10` and `AS-M6-04`, which are section 3.1's panels. Either alone would refuse a figure here. This is the third screen to meet that pair -- `W6-g` met it on section 3.2a and `W6-j` on section 3.2 -- and **both are REPORTED again rather than repaired**, because widening the roster is an edit to `figure.ts` and adding an `as_of` is an edit to API_CONTRACT, and this fence holds neither. **`open_flags` renders**, because a count carries no `Cents`, reaches no `figure()` and cannot be misread as a liability, which is the licence `identity-graph.tsx` already takes for `aggregate.accounts`.

**And `INV-M6-10`'s second half is made a type obligation rather than a promise.** M06 section 7.9 requires that *"every view is logged as an access to the underlying identities"*, with the reason *"an investigator browsing the graph is reading personal data across many people"*, which is this screen's fact pattern on a coupon term. `ADR-171` finding 4 measured that no table in the registry holds an operator, so there is no actor to record. **So `accessRecord` is a required field, refused blank**: a slice filling the read arm cannot construct the page value without stating what was recorded, and the audit lands with the read instead of after it. It is `AbsentFigure.reason`'s idiom applied where the same silence would otherwise be invisible.

**What the screen deliberately has none of is a mutating control.** `ADMIN_READ_ROLES` is the whole closed set, so every role may perform this read and no row is visible to one role and not another; the four writes section 8 declares against an account are named nowhere in either file, and the only form is a `GET` form. A freeze button here would be disabled for `readonly` and broken for all three.

### 4. The finding nobody went looking for: a count five files were quoting into a panel an operator reads

Every screen in this console states its blockers as prose an operator reads. Five of them state the same sentence, and it is wrong:

> `exportEvidence`, `readLiability` and `searchAccounts` have no module

**Derived at this edit rather than carried forward:** `AdminReadSource` declares **seven** methods; `IMPLEMENTED_ADMIN_READS` names **five**; and `adminReadSourceParts` supplies `exportEvidence` as a **sixth**, through the other producer in the same composition file. **So `readLiability` is the one method left**, and the count on those panels was three.

**The shape of the failure is session 371's own Next item arriving as a live defect.** That entry warned that *"a reader counting implemented methods off the array undercounts by one"*, because pull request #490 landed `exportEvidence` through the `Partial` rather than through the compile-checked `Pick`. Nothing goes red when a comment says three: prose is not type checked, and a panel is only read by an operator who has no way to check it.

Corrected in [`index.ts`](../../apps/admin/src/index.ts), [`app/page.tsx`](../../apps/admin/src/app/page.tsx), [`app/feed/page.tsx`](../../apps/admin/src/app/feed/page.tsx), [`app/flags/page.tsx`](../../apps/admin/src/app/flags/page.tsx), [`app/accounts/account-detail.tsx`](../../apps/admin/src/app/accounts/account-detail.tsx) and [`app/accounts/[accountId]/page.tsx`](../../apps/admin/src/app/accounts/[accountId]/page.tsx), each with the measurement beside it rather than a new number on its own.

**AND THE LIABILITY HOME'S THIRD BLOCKER IS RETIRED ON A MEASUREMENT RATHER THAN REWORDED.** It read *"four of the five figures `buildLiabilityHome` reads have no field on the response"*. `LiabilityResponse` in [`api/types.ts`](../../apps/admin/src/api/types.ts) declares **twelve** top-level fields and `wallet_balances_cents`, `bounded_near_term_cents`, `remaining_ladder_exposure_cents` and `absorbed_corrections_cents` are all among them; `RI-18` binds all three declarations of that shape to one field set, so the wire cannot carry a field in one place and not another. Every column `LiabilitySnapshot` reads is reachable.

**What survived that entry is not a blocker, and it is now served in its own section.** `ADR-195`'s third component of `P-M6-01`, the firm-scoped `withdrawals_in_flight` obligation, has no column and therefore no field, and [`liability.ts`](../../apps/admin/src/liability.ts) already renders it ABSENT with that reason and marks the total INCOMPLETE. **A term the page renders honestly is not a term the page is waiting for**, and filing it as one tells an operator the screen is broken when it is being careful. The two sections are kept apart in the bytes so the reader can tell which is which.

`M6-A-61` in [`test/render.test.ts`](../../apps/admin/test/render.test.ts) is updated to the measurement rather than weakened. It now derives the four field names out of the console's own transcription, **asserts its parser is not vacuous before it asserts anything about the fields**, and asserts that the `ADR-195` entry is NOT in the blocked list.

### What was reported and not repaired

- **[`figure.ts`](../../apps/admin/src/figure.ts)'s origin roster still admits only section 3.1's panels**, so no screen outside the liability home can raise a figure. Three screens have now met this and none holds that file.
- **`AdminAccountSearchItem` carries no `as_of`**, exactly as `IdentityGraph`'s three money fields do not. API_CONTRACT is not this fence.
- **`GET /admin/accounts?query=` types its ITEM and not its envelope.** Derived by reading the contract: of the three cursor-paginated admin reads, `GET /admin/accounts` and `GET /admin/flags` declare an item apiece and `GET /admin/events` is the one that declares `EventFeedResponse`. So this screen holds the shape of its own page, as [`flags-queue.tsx`](../../apps/admin/src/app/flags/flags-queue.tsx) already does, and no `AccountSearchResponse` is invented in `api/types.ts`.
- **`/`, `/feed` and `/flags` PRERENDER STATIC.** This is session 368's landmine -- *"any App Router segment whose data load throws before touching a request-scoped API prerenders its failure screen, silently, with the build exiting 0"* -- **measured on this application for the first time**. It is harmless today for a reason worth stating: [`http/client.ts`](../../apps/admin/src/http/client.ts) is a BROWSER client that throws in a Node process by design, so no admin route performs a server-side read at all, and prerendering a constant is correct. **It stops being harmless on the day the first read lands.** A derived gate of the portal's shape would select zero routes here and would therefore be vacuous, so the guard is put where it cannot be: `/search` declares `force-dynamic` with its argument, and `M6-A-73` asserts it.
- **`wiring.test.ts`'s `setAdminReadSource` entry** is still wrong in the two ways session 371 recorded. That suite is `apps/api`'s and this wave holds none of it.

### Landmines

- **A COUNT QUOTED INTO PROSE ON FIVE SCREENS DRIFTED FOR TWO SESSIONS AND NOTHING COULD GO RED.** The panels an operator reads are string literals; `RI-14` catches a reason claiming a named thing does not exist while the tree exports it, and *"three of the port's seven methods"* names no thing. This is the same class as session 368's stale barrel: correct-looking prose with no reader.
- **`apps/admin` has no route-rendering gate and the portal does.** Building one today would be vacuous here, for the stated reason, and the day the first server-side read lands in this console that reason evaporates. The next slice to add a read to `apps/admin` inherits the hazard with no control.
- **The `accessRecord` obligation is enforced by a required field and not by an audit.** Nothing checks that the string describes a record that exists. It forces the next slice past the question; it cannot answer it.
- **The search screen's closure cannot see an identifier that is not uuid shaped.** The contract types `account_id` and `identity_id` as plain strings, so a server spelling one differently would serve it past the pattern. `flags-queue.tsx` carries a second, value-based leg for exactly that residue; this screen has no such leg, because every id it renders is one it is licensed to render and the value leg would have nothing to refuse.
