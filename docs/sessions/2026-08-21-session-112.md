### The findings, and the first two are corpus findings rather than code ones

**`SD-M6-01`'s identity-max columns did not land, and [DELTA_MANIFEST](../../packages/db/DELTA_MANIFEST.md) records `SD-M6-01` as landed.** The delta asks [`liability_snapshots`](../../packages/db/migrations/0009_ledger.sql) for four additions and [`0009`](../../packages/db/migrations/0009_ledger.sql) carries two of them. `absorbed_corrections_cents` is there and the bounded figure is there under the name `bounded_near_term_cents`; **`eligible_next_7d_identity_max_cents` and `eligible_next_7d_identity_max_id` are in no migration in the tree**, verified by grep across `packages/db/migrations`. So P-M6-03's identity-level maximum, which [M05](../plans/M05-payout-system.md) `AS-M5-03` needs and an account-level total hides, **has no column to read**. It renders absent with the missing column names in the reason, never as zero, because a zero there reads as "no identity is concentrated" on exactly the panel that exists to say one is. **The manifest row is the thing to repair**: a disposition of `landed` against a delta that half landed is the drift `ADR-034` exists to end, and it is a one-line disagreement between a registry and a migration that a session reading only the registry would carry forward.

**AS-M6-04 requires three numbers and section 3.1's panel table names two of them.** Open liability is P-M6-01 and bounded near-term is P-M6-02. **Remaining ladder exposure has no panel id anywhere in [M06](../plans/M06-admin-ops-console.md)**, and `0009` stores it as `remaining_ladder_exposure_cents NOT NULL`. **`P-M6-11` was not minted**: a `P-M6-nn` written in application code is a claim on a series with no allocation table, made from a fence that cannot add the row to the document that owns it, which is `ADR-034`'s condition exactly. The figure cites `AS-M6-04` instead, which is an identifier that already exists, and the roster in `figure.ts` carries the eleventh member with the reason beside it. **Whoever holds M06 next owns deciding whether the panel table gains a row or the third number is declared to live inside P-M6-01's block.**

**`0009.open_liability_cents` is not the panel called Open Liability, and the two share a name.** The migration documents the column as "the sum of withdrawable across funded accounts" and carries `wallet_balances_cents` separately; P-M6-01 is the two summed and INV-M6-11 makes that not optional. **The reading is stated here because the batch that WRITES the row has the same trap pointed the other way**: a writer that puts the panel figure into the column named after the panel double counts wallet balances the moment this page adds them, and nothing in the schema would say so. The input record in `liability.ts` is named `withdrawableAcrossFundedCents` for that reason, so INV-M6-11 cannot be broken by a name.

**One ordering between the three is derivable, and it is now asserted.** `min(withdrawable, cap) <= withdrawable` termwise and the eligible set is a subset of the funded set, so **bounded near-term can never exceed the sum of withdrawable across funded accounts**. A row that violates it had the wrong number written to a column, and the page refuses to render it. The other pair has no ordering and none is asserted: GS-115's own book is the counterexample, at 500,000c open against 900,000c remaining ladder.
