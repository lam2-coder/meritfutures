### 4. The type edge, and why it is a run-time validation rather than a declaration

A static import of `packages/tooling/checks/api-contract-endpoints.mjs` from `apps/api`'s project is `error TS7016: Could not find a declaration file`, measured. Three ways out, and the third is taken.

| Way | Disposition |
|---|---|
| `allowJs` in `apps/api/tsconfig.json` | outside this fence, and it widens a deployable's compiler settings to buy one test file a type |
| a hand-written `api-contract-endpoints.d.mts` | INSIDE this fence and refused anyway: a second copy of the reader's type surface that nothing checks against the reader, which is the class of defect this check exists to remove, and every later consumer would trust the copy |
| load it by path, validate the shape at run time | taken |

The trade is stated rather than hidden: the static edge is gone, so a renamed export is a red test here and not a compile error. It buys the property that the check validates what it actually received, and the check has to do that anyway, because asserting the reader's coverage IS its second half. `registry.ts` loads its own route modules by computed specifier and validates them against a type that no longer exists at run time, and says so in its own words; this is that pattern one directory over.
