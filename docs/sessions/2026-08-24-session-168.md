### 4. Five divergences between M19 and its own primary sources

Each was found by checking M19's citation against the cited file, and each is stated with the line that refutes it.

**D1. `kyc.pending` is in no catalogue.** [M19:260](../plans/M19-kyc-identity.md) lists *"`kyc.required`, `kyc.pending`, `kyc.verified`, `kyc.rejected`, `kyc.expired`"* and says **"Already in the approved [EVENTS](../architecture/EVENTS.md) catalogue."** [EVENTS:56](../architecture/EVENTS.md) carries **`kyc.submitted`**, and `kyc.pending` appears nowhere in `docs/` outside M19's own line. Four of the five are catalogued and the fifth is a name only M19 uses. The `kyc_status` **enum** value is `pending` ([`0001:29`](../../packages/db/migrations/0001_extensions_and_enums.sql)), which is what makes the wrong one look right.

**D2. `kyc.dedupe_hit`'s payload is the shape [ADR-029](../decisions/ADR-029.md) refused.** [EVENTS:60](../architecture/EVENTS.md) reads `{ identity_id, matched_identity_id, provider }`. `SD-M19-04` exists because a single matched identity *"cannot express a face matching three identities"*, ADR-029 ruled `dedupe_matches` authoritative, and [M19:261](../plans/M19-kyc-identity.md) says the payload adds `match_strength` and `dedupe_match_id`. **The catalogue carries neither and still names a singular match.** No ADR moves it. The column was dropped and the event that carried the same assumption was not.

**D3. `pre_eval` is unwritable and four approved documents still key behaviour on it.** [`0003:61`](../../packages/db/migrations/0003_kyc.sql): *"'pre_eval' is retired into 'first_purchase' ... The value is not carried forward"*, and the CHECK refuses it. Still live: [API_CONTRACT:286](../architecture/API_CONTRACT.md) makes `kyc_required` an error *"only when placement is `pre_eval` or the plan is Direct"*; [GLOSSARY:324](../GLOSSARY.md) defines placement as *"`pre_eval` (at purchase) or `pre_funded`"*, with no trigger set at all; [STATE_MACHINES:317](../architecture/STATE_MACHINES.md) the same; [M03:283](../plans/M03-billing-checkout.md) and `DEP-M3-05` at `:508` gate checkout on it. **A checkout implementer reading API_CONTRACT would compare against a value the database refuses to store.** M19's own sections 1.2 and 3.1 keep the word deliberately as vocabulary, which is why this reads as prose rather than as a defect until the CHECK is opened.

**D4. `INV-M19-02`'s enforcement has no number.** The invariant's enforcement column says *"Publish-time validation (a new CV rule)"*. [M01](../plans/M01-rules-engine.md) defines **`CV-01` to `CV-19` and no more**, and all nineteen are implemented in [`validate.ts`](../../packages/rules-engine/src/plan/validate.ts) and [`resolve.ts`](../../packages/rules-engine/src/plan/resolve.ts). **The series stops at nineteen and no twentieth number is minted anywhere in the corpus** (deliberately not written out here: `CI-06/identifier-series` reads a citation of an unminted member as a finding, which is this gate catching the exact defect the invariant describes). So `GS-220`, whose whole assertion is *"publish validation fails"*, names a rule with no identifier to fail under.

**D5. `kyc.triggers` has no typed home.** [ADR-030](../decisions/ADR-030.md) ruled the key `kyc.triggers`, an array. [`types.ts:555`](../../packages/rules-engine/src/types.ts) says *"`limits` and `kyc` are in the stored jsonb and are NOT here"*, by M01 section 1.2's boundary. That is correct and it means `INV-M19-01`'s *"read from the account's pinned plan version"* has **no reader and no type** anywhere in the workspace.
