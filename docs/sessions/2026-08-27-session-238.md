### 2. The ruling this session intends to write, in five clauses

> **1. [ADR-109](../decisions/ADR-109.md) CLAUSE 1's FINDING IS DISCHARGED AND NOT SUPERSEDED, AND ITS DISPOSITION IS UPHELD ON AN ARGUMENT THAT IS NOT ITS OWN.** The two cases ARE distinguishable and the distinction is checkable: ADR-109's caller HELD a door (`idempotency_keys` is `owned`, so `scopedDb` reached it) and lacked a predicate, which [ADR-112](../decisions/ADR-112.md) then supplied and [ADR-120](../decisions/ADR-120.md) wired. This session's callers hold the predicate and lack a door. **What does NOT survive is clause 1's REASON** -- *"admitting `'request-handler'` would buy a door that still writes the whole table"* -- which stopped being true the day ADR-112 merged. It is retired by name so nobody cites it again.
>
> **2. `SystemReason` STAYS AT TWO MEMBERS FOR THE THIRD TIME, AND THE ARGUMENT IS BOLA SURFACE RATHER THAN PREDICATE ARITHMETIC.** A `SystemReason` member grants all 104 registered tables at six verbs. The two constructions need one table each at one verb each. **The vocabulary that moves is the TABLE and never the REASON**, and that is finding 6 made into a rule rather than a preference.
>
> **3. MINT IS NOT AN AUTHORITY PROBLEM. It is a SCOPED write whose parent must be PROVED rather than stamped.** `ScopedTx.insertUnder` takes a closed table vocabulary, requires the caller to name the local column, and READS the parent through `scopePredicate(via, identityId)` inside the same transaction before writing. The caller must name WHICH parent because an identity may hold more than one user ([ADR-041](../decisions/ADR-041.md)), which is [ADR-112](../decisions/ADR-112.md) section 5 draft 2's own finding about `analytics_snapshots` one class along.
>
> **4. RESOLVE IS AN AUTHORITY PROBLEM AND IT IS A FOURTH DOOR, NOT A THIRD REASON.** `resolutionDb()` is READ ONLY, NON-TRANSACTIONAL, addresses AT MOST ONE ROW, and reaches a closed set of one table by a closed set of one column. It has no `transaction()` overload, so it cannot participate in a write at all. This is [ADR-102](../decisions/ADR-102.md) clause 3's move exactly: `firmDb()` was carved as a narrower door rather than admitted as a third reason, and [`scoped-db.ts:939`](../../packages/db/src/scoped-db.ts) says so in its own words.
>
> **5. THE THIRD CONSTRUCTION IS NAMED AND NOT BUILT.** Establishing an identity (`identities`, `class: 'root'`) has no door and no caller, and building it would be the primitive [`job-queue.ts`](../../packages/queue/src/job-queue.ts) rules against.

### 3. Why building is correct here and `mintSessionToken` was not

[ADR-120](../decisions/ADR-120.md) section 4 refused to write `mintSessionToken` on [`job-queue.ts`](../../packages/queue/src/job-queue.ts)'s rule that *"a primitive admitted before a caller exists is a primitive nobody can remove"*, and that refusal was right. **The distinction is which end of the stack the gap is at.** `mintSessionToken` sat ABOVE a gap: nothing could insert the row it would mint for, so it was building on air. These two constructions ARE the gap, named by a signed-pending entry as the blockers on specific methods. [ADR-112](../decisions/ADR-112.md) is the precedent in the same direction: it built `updateAt` for four callers, none of which existed in the tree, and its section 12 said so.

**AND THE HONEST CONSEQUENCE IS STATED IN THE PLAN RATHER THAN DISCOVERED IN THE PR.** This ruling unblocks NO endpoint on its own. `verifyOtp` carries three independent blockers ([`auth-backend.ts`](../../apps/api/src/auth-backend.ts)'s `NO_PRE_IDENTITY_READ`, `NO_DERIVED_INSERT` and `NO_OTP_DIGEST`); this removes the two that are `packages/db`'s and leaves the one that is a deployment secret or a migration.

### 7. Two findings the dispatch did not predict, reported at the site

1. **BOTH CONSTRUCTIONS ARE ALREADY EXPRESSIBLE AT `systemTx`.** `SystemTx.insert` is generic over `TableKey` and reaches `sessions`, `unscopedInsertStatement` runs no `refuseTenancyColumn`, and `SystemTx.rowAt` reaches `users` by `email`. **So the gap is a VOCABULARY gap and not a construction gap**, which is what makes it the offer [ADR-109](../decisions/ADR-109.md) declined rather than a new question, and it is why the ruling is about which vocabulary moves.
2. **`ledger_entries` IS `derived` WITH A `hop`.** The first draft of `insertUnder` was generic over the class, which reads correctly. It would have handed a scoped request handler one leg of a double-entry posting under its own ledger account. **It was caught by enumerating the class rather than trusting it**, which is this project's own stated lesson about checking a claim against the primary source.
