**All five classes were tried against the table by the slice dispatched to register it**, and
[`scope.ts`](../../packages/db/src/scope.ts) records each refusal: `owned` on `identity_id` compiles and
drops every account-level row; `derived` through `account_id` is refused by

second is an ACCOUNT; `firm` is refused by the suite's own assertion because the row declares a column
against `identities(id)`; `root` is `identities`' alone. *"WHAT THE TABLE NEEDS IS A SIXTH CLASS, and
ADR-106 is the precedent for what adding one costs."*

**So the writer is a port and the reason is reported.** `EventWriter.insert(tx, row)` is one method whose
whole body would be `tx.insert('events', row)`, except that `'events'` is not a `TableKey`. Writing it
would need [`packages/db`](../../packages/db/src/scope.ts), which this fence excludes, and an ADR, which
this session was allocated none of. It is not faked either: `UNWIRED_EVENT_SINK` **refuses**, and its
message names the sixth class, on `UNWIRED_EXPIRY_SWEEP_IO`'s argument one deployable over that a silent
no-op is indistinguishable from a working sink.

#### `payout.freeze_expiring` is that blocker in one catalogue row, and it is not this session's example

Its payload, as [ADR-159](../decisions/ADR-159.md) folded it, is
`{ payout_request_id, flag_id, expires_at, lead_hours }`. **An event about one trader's frozen payout
that carries neither `identity_id` nor `account_id`.** Both columns are nullable, so the row is legal;
a rule naming either column drops it. The producer records that absence explicitly rather than deriving
a tenancy column from somewhere, and the suite asserts it, because **a sixth class has to answer this row
and the answer is not derivable from the DDL.**

### 3. THE PORT `P5-j` DECLARED IS SATISFIED, AND THE TWO THIN PLACES ARE ARGUED RATHER THAN WORKED AROUND

The dispatch's instruction was *"build the producer that satisfies it, and if its declared shape is wrong,
say so with an argument rather than building a second one beside it."*

**THE SHAPE IS NOT WRONG AND IT IS SATISFIED.** `ExpiryEventPort.emit(tx: ExpiryTx, event: ExpiryEvent)`
is met by `EventSink.emit(tx: object, event: EmitSpec)`: `ExpiryTx` is assignable to `object` and
`ExpiryEvent` is assignable to `EmitSpec`, so an `EventSink` **is** an `ExpiryEventPort` with no adapter
between them. The suite asserts it by assignment -- narrowing either parameter is `TS2322` -- and binds
the two files by reading `ports.ts` as text, because [`RI-04`](../../packages/tooling/checks/repo-invariants.mjs)
forbids one app depending on another and `.npmrc`'s `node-linker=isolated` makes it unresolvable besides.

**Two fields are absent from `ExpiryEvent` and each costs something. Neither is a defect and neither is
repaired here**, because that file is outside this fence:

1. **`occurredAt`.** [EVENTS](../architecture/EVENTS.md) section 1 separates when a fact happened from
   when we learned it, and *"analytics that confuse them will silently lie"*. With no field for it, a
   sweep's events take the recording instant as their occurrence instant. **That is admissible here and
   only here**, because a release occurs inside the transaction that records it, and the producer names
   the default rather than hiding it: `EmitSpec.occurredAt` exists, is optional only so the port is
   satisfiable, and its docblock says which emitters must pass it.
2. **`correlationId`.** Section 1: *"Every multi-step flow carries a `correlation_id` so a saga reads as
   one thread ... request through settlement."* A hold release is a step in exactly that saga, and with
   no field for it every sweep-emitted event is unthreadable **forever**, on a table whose retention is
   forever.

**Both are one optional field on a shape a session holding that file can add in a line**, and the suite
asserts their absence, so the day either arrives the assertion is what tells the next reader here that
the report was acted on rather than forgotten.

### 5. `INV-M6-10` IS THE FEED'S SUBJECT, AND IT IS NOT THE LIABILITY PAGE'S PROBLEM

*"The admin console renders trader-identifying data only when the query names a specific subject"*, enforced
by *"no bulk export of identities exists as a UI affordance. Bulk is an audited export, not a screen."*

[`page.ts`](../../apps/admin/src/page.ts) satisfies that by having nothing to withhold, and
`assertNamesNoSubject` refuses any uuid outright. **The feed cannot do that.** `events` carries
`identity_id` and `account_id` on most rows, so an unfiltered page of it **is** the affordance
`INV-M6-10` says does not exist, and it is the read-side risk `AS-M6-05` names: *"a read-only admin
session and no write capability can still take the identity graph and a pack per account."*

**So the surface has two modes.** With no subject named, every identity and account uuid is withheld
**visibly** -- the word in the line, on `FM-M6-01`'s argument that a style does not survive a screenshot,
and visibly rather than dropped because a row showing no identity must not read as a row with no identity
involved. With a subject named, `INV-M6-10`'s condition is met **for that subject** and its ids render.

#### The hardest case is the one `scope.ts` says no scope rule can express

That file records it as one of the two reasons `events` is unregistrable: *"`kyc.dedupe_hit` carries
`matched_identity_id` and `identity.merged` carries `merged_identity_id`, so a row whose own tenancy column
is correct still names a DIFFERENT identity inside `jsonb`, **which no scope rule can express**."*

**A scope rule cannot express it and a renderer can**, which is the one thing this layer is better placed
to do than the accessor. So the rule is on the **shape of the key** -- any payload key ending
`identity_id` or `account_id` -- rather than on a list of columns, and both of those keys are covered by
construction rather than by having been thought of. In subject-named mode the named subject's own id
renders and a different identity's does not, because the query named one subject and the licence is for
that one. **That is the sharpest test in the file and it is the one seed A turns red.**

#### The aggregate is refused on evidence, which is `ADR-157`'s ruling arriving at a surface

[ADR-157](../decisions/ADR-157.md) admitted a RANGE term, an `IS NULL` term and a ROW lock and refused the
aggregate. So `shown` is `rows.length`, **there is no `total` field to reach for**, and `complete` is
what keeps `shown` honest: a full page is indistinguishable from an exhausted query unless the reader is
told, and an operator who reads a truncated page as the whole story during an incident is the failure that
field exists against.

#### Two orders, and one refusal that is deliberately NOT `liability.ts`'s

The feed orders by `recordedAt`, because it is the operational timeline and a late vendor webhook about
Tuesday's fact must appear at the top on Thursday rather than buried in Tuesday. `thread()` orders by
`occurredAt`, because a saga is a sequence of facts. **Both are stated rather than one of them assumed**,
and seed C turns two tests red when they are made to agree.

A row claiming we learned a fact before it happened is **flagged and rendered**, not refused.
[`liability.ts`](../../apps/admin/src/liability.ts) refuses an incoherent snapshot because *"a dashboard
that renders an incoherent book is the confident wrong answer with a source citation attached"* -- right
for an AGGREGATE, where one bad input corrupts the answer. **Wrong for a LIST**, where one bad row is one
bad row and blanking the timeline during the incident that row is evidence of is the worse failure.
