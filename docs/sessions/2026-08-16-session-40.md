## 2026-08-16 - Session 40: the fast-check plan generator, and the counterfactual that caught itself

- **Done:** [P2](../plans/P2-rules-engine.md) section 5's plan generator, which that section calls "the expensive half" and the one thing genuinely buildable before the engine exists. Three files in `packages/rules-engine/test/generators/`: [`plan-config.ts`](../../packages/rules-engine/test/generators/plan-config.ts) (the materialized shape a published plan has at `validatePlan` time), [`validate-plan.ts`](../../packages/rules-engine/test/generators/validate-plan.ts) (**CV-01 to CV-19 transcribed from M01's table and from nowhere else**, the oracle), and [`plan.ts`](../../packages/rules-engine/test/generators/plan.ts) (the `fast-check` arbitrary, valid **by construction**). **33 assertions in [`plan.property.test.ts`](../../packages/rules-engine/test/generators/plan.property.test.ts)**, and the full `pnpm run verify` is green: 241 tests pass, 15 of 15 gates pass clean and fail dirty, 14 scope cases hold.
- **Next:** The `PT-nn` suites consume `planArbitrary()` as-is. **The arbitrary day-sequence and settlement-sequence generators are NOT built**, per the session fence: they depend on `DayInput`'s shape, which `OQ-P2-01` is about to widen, and building them now means building them twice.
- **Blockers:** None.
- **Landmines:**
  - **THE COUNTERFACTUAL CAUGHT ITS OWN GENERATOR ON THE FIRST RUN, and this is the finding of the session.** Two of the nineteen cases failed: `CV-03` and `CV-17`. Both for the same reason, and it is general. **Six of the nineteen rules are CONDITIONAL, and inverting the consequent of a conditional rule proves nothing while its precondition is false.** The first version forced the lock branch for `CV-11`, `CV-12` and `CV-17` and left `phase_eval.enabled` and the funded drawdown type free, so those two cases drew a disabled eval phase and a `static` drawdown about half the time and emitted a plan the oracle **correctly accepted**. Had the counterfactual not been built, the generator would have shipped with two rules it never actually enforced and a green suite saying otherwise.
  - **The precondition guard is now mechanical rather than remembered.** `PRECONDITIONS` in the test file lists all six conditional rules with an executable predicate each, asserted over every omitted sample. A seventh conditional rule that nobody wires up fails there by name, rather than surfacing as "the generator stopped inverting", which is the same failure with the opposite fix.
  - **The oracle and the generator share no code, deliberately.** One builds by construction, the other checks by reading. Folding them would make direction 1 prove only that the code agrees with itself, which is the shape this repository has now caught in a `CHECK` that evaluated to `NULL` ([ADR-035](../decisions/ADR-035.md)), a `DO` block that read a prefix of the schema (`OI-08`), a probe whose successes were rolled back before its deferred trigger fired, a harness that read `tee`'s exit status instead of `psql`'s, and `CI-06k`'s first run reading a legend as data.
  - **A DERIVED CONSTRAINT THE CV TABLE DOES NOT STATE, and it is load bearing in the generator.** With the funded lock **disabled** and the drawdown **trailing**, `CV-17` requires every cap strictly **below** the drawdown while `CV-10` requires every cap **at or above** `min_payout_cents`. Both hold only if **`drawdown_cents > min_payout_cents`**. A generator drawing the drawdown freely in that branch produces unsatisfiable cap constraints. No v1 plan reaches it (all three enable the lock), which is exactly why nothing had noticed.
  - **`CV-14`'s text is stale and this session followed the ADR rather than the table.** M01 spells it `ladder.payouts_to_graduate >= 1`; **[ADR-030](../decisions/ADR-030.md) ruled the canonical name is `max_payouts`**, DATA_MODEL section 11 carries it, and that section's own note says "the zod schema and the CV publish validations key off this name". The generator and the oracle both use `max_payouts`. **The CV-14 row in M01 was not edited**, because M01 is approved and the correction is a one-line documentation change that belongs to whoever owns the next M01 fold rather than to a test-infrastructure session.
  - **`CV-01`, `CV-02`, `CV-06` and `CV-16` are checked on BOTH phases.** A plan declares two drawdowns, two loss limits and two consistency gates. Checking only the funded ones would leave an eval phase publishable with `intraday_trailing`, which is the value `CV-01` exists to refuse.
  - **The size arbitrary draws Appendix A's four ruled sizes AND arbitrary sizes**, and a test asserts both are reachable. A generator emitting only the four shipped sizes would pass every property while proving nothing about `CV-11` and `CV-12`, which are inequalities in `size_cents` that the shipped four satisfy comfortably.
  - **`payout_cap_schedule` is generated multi-step even though v1 ships one step.** `CV-09`'s "ordinals strictly increase" clause is unreachable with a single-element schedule and would never have been exercised.
- **Files touched:** `packages/rules-engine/test/generators/{plan-config,validate-plan,plan}.ts` (new), `packages/rules-engine/test/generators/plan.property.test.ts` (new), `docs/sessions/`.

### One thing this session got wrong about itself, recorded because the class matters

The comment introducing the conditional-rule list read **"FIVE of the nineteen rules are CONDITIONAL"** above a list of **six**, written into the file whose entire subject is that unverified claims are worthless. It survived one commit. It is corrected, and the correction points at `PRECONDITIONS` as the executable copy, because a prose count with no query behind it is the defect [ADR-034](../decisions/ADR-034.md) exists to end and this corpus has now found wrong on every occasion it has been checked.

### What the generator does not do, named rather than implied

It emits a **materialized** plan: `plan_versions.rules` structure and `plan_version_sizes` cents in one object, because `CV-11` is an inequality across both. It does **not** model the bp-to-cents materialization itself, so it cannot catch a publish that materializes `amount_bp` incorrectly. That belongs to the publish path and to `plan_version_sizes`' own tests, and stating it here stops a later reader assuming this file covers it.
