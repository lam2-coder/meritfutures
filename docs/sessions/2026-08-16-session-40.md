- **Landmines:**
  - **A REVOKE THIS SESSION CALLED DECORATION IS A CONTROL, AND ONLY EXECUTION SAID SO.** The trailing `REVOKE DELETE ... FROM merit_dispatcher` was written with a comment reading "a statement rather than a mechanism", reasoning that nothing above it grants `DELETE`. The seeded run then added `DELETE` to the grant list above it, expecting `R12` to catch it, and **all 27 assertions passed**: the `REVOKE` had already taken it back. A privilege granted earlier in the file cannot survive to `COMMIT`. The comment now says what the run showed and the seed adds the grant **after** the statement, which is how the defect actually arrives. **This is the third comment in three days found wrong in the direction of understating a control, and the second found by executing rather than by reading.**
  - **`IS DISTINCT FROM`, NOT `<>`, AND THE NULLABLE COLUMN IS THE WHOLE REASON.** `integration_dispatches.identity_id` is nullable because `0018` rules that not every dispatch is about a person. Written the obvious way, the identity-match trigger compares `NULL` to a uuid, gets `NULL`, and **waves through the least attributed row in the table**, which is the one an attacker would cite. Seeded, `R9` is the **only** assertion that fails: `R7` and `R8` both still pass, so a probe without `R9` would have scored the naive version as working.
  - **THE PLAN WAS ONE LAYER SHORT AND [EC-146](../edge-cases/EC-146.md) HAD ALREADY SAID SO.** M10 §7.9.4's recommendation is about the address only. The address makes a send **possible**; `phone_change_requests_applied_is_complete` was still accepting a timestamp from a handler that sent nothing, which is the defect that made this invisible in the first place. EC-146 ruled the remedy in words **nine days before** that section was written and §7.9.4 does not cite it. **Read the edge case that owns the finding, not only the plan that raises it.**
  - **THE SMS LEG CANNOT BE A `notifications` ROW**, and a session "completing the pair" by adding an `sms` channel would be adding a value no row can legally carry. `notifications.identity_id` is `NOT NULL` and `0029` already recorded that reasoning for the pre-identity class. Two legs, two tables, deliberately.
  - **`ON DELETE RESTRICT` MEANS A CITED NOTIFICATION CAN NEVER BE DELETED.** That is correct, because it is evidence. **It collides with any future retention sweep on `notifications`**, which will find rows it cannot delete. `R10` and `R11` watch it on every push so the sweep's author meets it in a CI log rather than in an incident.
  - **`merit_app` CAN READ EVERY CIPHERTEXT AND POSTGRESQL CANNOT STOP IT.** A table-level `SELECT` implies every column and `REVOKE SELECT (col)` against it is a **no-op that looks like a control**. Scoping it means a hand-maintained column list, which is the object `0026`'s revoke list already cost us. **The key is the control, not the grant**; the sidecar table that would make the grant the control is named in ADR-046 and is not built.
  - **THE COLUMN-SCOPED `UPDATE` IS NARROWER THAN THE AMENDMENT'S WORDS**, and that is a departure even though it is in the same direction. "UPDATE stays for rotation" is implemented as `GRANT UPDATE (three columns)`. Table-wide would let the send path blank a `value_hash` and disarm `INV-M16-03` without deleting anything, which `R14` proves by seeding it. **Widening it back is one word per line if the founder meant the broader reading.**
  - **A BARE FIXTURE `INSERT` IN A PROBE IS A FAILURE MESSAGE NOBODY CAN ACT ON.** Seeding a guard that refuses everything made the unlabelled `phone_change_requests` insert fail with a raw constraint error eight assertions in, which reads as a broken fixture and gets "fixed" by loosening the fixture. It is `S5pre` now and the same seed reports that the ceremony can no longer be opened.
