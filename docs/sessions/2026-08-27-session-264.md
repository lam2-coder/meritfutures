### The calendar clause: a date where the two answers actually differ

A renderer that slices the ISO string is wrong on some days and right on most, which is why the fixture is chosen rather than convenient. `2026-03-12T22:30:00Z` is **17:30 CT** on 12 March 2026, US daylight time having begun on 8 March. [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql) records the open as *"session opens at 17:00 CT regardless"* beside its governing rule, *"session calendar (CT) is authoritative; storage is UTC"*, and [GLOSSARY](../GLOSSARY.md)'s `session` entry closes it: *"A fill belongs to the trading day whose session CONTAINS its execution timestamp."*

**One instant, three answers, and only one of them is the trading day.**

| | |
|---|---|
| trading day, the server's stored column | **2026-03-13** |
| UTC calendar date, what a naive slice gives | 2026-03-12 |
| the viewer's date in `America/New_York` (18:30 EDT) | 2026-03-12 |

Rendered, with the heading and the row disagreeing on purpose:

```html
<h2 data-group-trading-day="2026-03-13">
  <span class="merit-trading-day" data-trading-day="2026-03-13"><time>2026-03-13</time>
  <span class="merit-trading-day__unit"> (trading day)</span></span></h2>
<article class="merit-release"><h3>us_cpi</h3>
  <p><span class="merit-local-clock" data-local-day="2026-03-12"><time>2026-03-12 18:30</time> EDT
    <span class="merit-local-clock__unit"> (your local time)</span></span></p>
  <dl class="merit-detail">
    <dt>Merit&rsquo;s stored instant</dt><dd><time>2026-03-12T22:30:00.000Z</time></dd>
    <dt>Trading day</dt><dd>...<time>2026-03-13</time>...</dd></dl>
  <span class="merit-release__revised" data-revised="true">This release time has been revised.
    Reason given: source publisher moved the release window</span></article>
```

**The suite asserts the premise before it asserts the render**, because a fixture where the two agree would pass against the wrong renderer. It then asserts the heading is the trading day, that **no** heading is the calendar day, and that the calendar day is still on the page labelled as the viewer's clock, which is `GS-285` intact.

**Watched failing.** Grouping by `local_day` instead:

```
× groups by the trading day on a date where the trading day and the calendar day differ
× puts both same-day releases under one heading and keeps the stored order
  Tests  2 failed | 24 passed (26)
```

**The mechanism is the absence of an input.** `TradingDay` takes a string and has no instant on its props, so a caller holding only a timestamp cannot render a trading day at all. That is the same idiom [`view/economic-calendar.ts`](../../apps/portal/src/view/economic-calendar.ts) uses for `INV-M4-16` and [`app-shell.ts`](../../apps/portal/src/shell/app-shell.ts) uses for `INV-M4-07`.

Rendered from a timeline whose account speaks for `2026-03-09` against a firm that has closed through `2026-03-13`:

**Watched failing**, on the exact defect the clause exists to catch, a behind day rendered as current:


The ruling behind both renders is [ADR-152](../decisions/ADR-152.md) and the finding that produced it is that `INV-M4-02` is satisfied exactly as well by a stale value as by a fresh one. The entry declines to close the gap by inventing a field in the portal's type file and puts the sentence on the screen instead, which is the cheapest pressure toward the repair: a gap in a document is one nobody is reminded of.

### The build-configuration edit, which is arguably 250's file

[`apps/portal/tsconfig.json`](../../apps/portal/tsconfig.json) gains `jsx: "react-jsx"`, `lib: ["ES2023", "DOM"]` and the `.tsx` include patterns. All three are what **any** rendered file needs and this session landed the first one; 250's layout will need the identical three. The edit is additive in every key, so a 250 branch writing the same options merges as a duplicate rather than as a behavioural conflict, and the file says so in a `//fence` note rather than leaving a reader to derive it from the blame.

**`DOM` is added to this package and to no other, and the narrowness is the argument.** [`tsconfig.base.json`](../../tsconfig.base.json) withholds it from every package deliberately and the root manifest records why: the four non-UI deployables run under `node --experimental-strip-types` and a DOM global there is a type that exists at compile time and not at run time. `@types/react` references `Element`, `HTMLElement` and `Event` from its own declarations, so a React component cannot be type-checked without them, and this application renders in a browser under [ADR-095](../decisions/ADR-095.md).

**The suite file is `.ts` and the components are `.tsx`, deliberately.** [`vitest.config.ts`](../../vitest.config.ts)'s `unit` project includes `apps/*/test/**/*.test.ts` and nothing else, so a `.test.tsx` would be a suite that never runs and reports nothing, which is the failure that file's own header is about. A server component is a function, so `createElement` reaches it from a `.ts` file with no JSX and no second project.
