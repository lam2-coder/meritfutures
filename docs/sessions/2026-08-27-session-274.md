#### 1.1 `wallet_spend_limits` is REGISTERED and the registration is NOT re-argued

[Session 202](2026-08-25-session-202.md) registered all four M20 wallet tables, this one among them,
`owned` on `identity_id` with `nullable: false`, and its `why` already cites `INV-M20-07` and states
the `(identity_id, effective_from)` grain and the supersession-is-a-new-row reading.

**[ADR-092](../decisions/ADR-092.md) section 2 clause 1 decides what this session does about it:**
*"A table is registered ONCE, by the first session that needs it, and **the registration is not
re-argued**."* So the plan does not touch the declaration, the rule, or the `why`. **What it does add is
the tenancy assertion the dispatch asks for**, because an assertion is not a re-argument and
`scoped-db.test.ts` is inside this session's fence.

#### 1.2 `payment_disputes` is the one table this session registers

`derived` through `purchases`, `purchase_id` to `id`, `traversal: 'hop'`. Checked against the three
mechanical refusals before it was written rather than after:

| Refusal | Source | This table |
|---|---|---|
| [ADR-101](../decisions/ADR-101.md) clause 1: no `derived` rule on a row carrying its own identity column | `no derived rule stands on a row that carries its own identity column` | **PASSES.** The DDL declares no `REFERENCES identities(id)` at all |
| [ADR-101](../decisions/ADR-101.md) clause 2: no `derived` rule traverses a nullable edge | `no derived rule traverses a nullable edge` | **PASSES.** `purchase_id uuid NOT NULL REFERENCES purchases(id) ON DELETE RESTRICT` |
| A `hop` must name the via table's primary key | [`scoped-db.ts:136`](../../packages/db/src/scoped-db.ts) | **PASSES.** `purchases.id uuid PRIMARY KEY` |
| The chain terminates at `owned` or `root` | `scopePredicate` recursion | **PASSES.** `purchases` is `owned` on `identity_id`, `nullable: false` |
| [ADR-094](../decisions/ADR-094.md)'s fold | every `ALTER TABLE` over all 49 migrations | **Nothing applies.** `0012` creates it and no later migration names it |

**`ledger_transaction_id` is the available mistake and it is refused here rather than in review.** It is
`uuid NULL REFERENCES ledger_transactions(id)`, and `ledger_transactions` is registered `derived`, so a
rule through it **terminates and compiles** -- which is [session 202](2026-08-25-session-202.md)'s named
trap exactly. It is refused twice over: the column is NULLABLE, so it returns a person only the disputes
that already moved money and silently drops every open one; and it answers a different question, whose
ledger accounts appear on the reversal rather than whose purchase was disputed.

#### 1.3 `events` IS REFUSED, and the refusal is a STOP rather than a choice

The dispatch says *"`events` is the one to think hardest about ... Argue the one you pick at the file."*
**The answer this session reaches is that no member of the vocabulary may be picked without a ruling,
and this session is forbidden one.**

`0017` gives it `identity_id uuid NULL REFERENCES identities(id)` **and** `account_id uuid NULL
REFERENCES accounts(id)`, **no CHECK tying them, neither required**, and no later migration alters the
table. Every class in the five-member vocabulary was tried against that shape:

| Class | Result |
|---|---|
| `owned` on `identity_id` | Compiles. Drops **every account-level row**, silently. `EVENTS` section 2 rows the portal timeline `TL` as a **per-account** view |
| `derived` through `account_id` | Refused mechanically by [ADR-101](../decisions/ADR-101.md) clause 1 (the row carries its own identity column) **and** clause 2 (the edge is nullable) |
| `pair` | Not applicable. `pair` is **two identity columns**; this is one identity column beside one **account** column, so `PairRule.columnB` has nothing to name and the DDL assertion refuses it |
| `firm` | Refused. The row declares a column against `identities(id)`, and the suite refuses `firm` on such a table by assertion rather than by taste |
| `root` | Not applicable |

**A sixth class is what the table actually needs, and adding one is an ADR.** [ADR-106](../decisions/ADR-106.md)
is the precedent and it is a whole entry that exists to add exactly one class.

**This is not a new finding and that is the strongest part of the argument.** [Session 195](2026-08-25-session-195.md)
reached it, [session 207](2026-08-25-session-207.md) met it and left it, [session 208](2026-08-25-session-208.md)
recorded that M01 is the corpus's heaviest reader of `events` and still could not have it, and
[`scope.ts`](../../packages/db/src/scope.ts)'s own `TABLES` docblock carries the refusal in the file.
Its closing sentence is the ruling this session obeys: ***"A transcription rules nothing, so this is
reported and not allocated."***

**The payload is the second reason and it is the weaker one, which is said here rather than leaned on.**
`kyc.dedupe_hit` carries `{ identity_id, matched_identity_id, provider }` and `identity.merged` carries
`merged_identity_id`, so a row whose own tenancy column is correct still names a **different identity
inside `jsonb`**, which [M04](../plans/M04-trader-portal.md) section 4 says `GET /accounts/:id/timeline`
must never return and `INV-M4-06` forbids. **It is the weaker reason because the corpus already ruled the
adjacent question the other way**: `idempotency_keys`, registered out of the **same migration**, says in
its own `why` that *"a scope rule states which ROWS reach an identity and nothing about what is inside
one."* The distinction that survives is that `response_body` holds **this person's** stored response and
an `events` payload holds **a third party's uuid** -- but that distinction is a ruling too, and this
session takes it no further than recording it.

**So `events` is left unregistered and, on [session 192](2026-08-25-session-192.md)'s model, NOT DECLARED
IN `schema.ts` AT ALL**, because a declared-but-unregistered `pgTable` is one no drift assertion compares.
Unregistered is unreachable through both accessors, and unreachable is safe.
