**Objective.** Make the sign-in page call the auth endpoints that are served,
refuse the ones that are not, and say which is which.

**Outcome.** **The served set admits no complete sign-in, so nothing is wired
and the page says that.** Which is the outcome the reservation named in advance
as a successful session, and it is a derivation rather than a deferral.
`ADR-218` is **not taken** and the number returns to the
pool unspent.

### 1. Which of the four, by method, derived rather than assumed

The port declares **16** methods. `databaseAuthBackend` implements **5** and
refuses **11**, each with its own blocker.

| Route | `AuthBackend` method | This deployment |
|---|---|---|
| `POST /auth/otp` | `requestOtp` | **BLOCKED** on `NO_DELIVERY` |
| `POST /auth/verify` | `verifyOtp` | **WIRED**, by [ADR-200](../decisions/ADR-200.md) |
| `POST /auth/passkey/login/options` | `passkeyLoginOptions` | **BLOCKED** on `NO_WEBAUTHN` |
| `POST /auth/passkey/login/verify` | `passkeyLoginVerify` | **BLOCKED** on `NO_WEBAUTHN` |

The other four implemented methods are `sessionByToken`, `logout`,
`listSessions` and `revokeSession`, none of which stands behind this screen.

**The reservation forbade a guess and the guess is wrong in both halves.** The
four read as an OTP pair and a passkey pair, so the free reading is "OTP works,
passkeys do not". The passkey pair is indeed both blocked. **The OTP pair is
split down the middle**, and it is split in the direction that matters: the
route that ISSUES a code is blocked and the route that CONSUMES one is wired.

### 2. Why nothing is wired, which is the finding

**The one served route cannot be reached.** `POST /auth/verify` consumes an
`otp_challenges` row. The only method in the port that WRITES one is
`requestOtp`, and `requestOtp` is blocked on `NO_DELIVERY`. `auth-backend.ts`'s
own header says it in one sentence: "a trader cannot sign up today, because
nobody can send them a code."

**And there is no third door, which is what makes this total rather than
partial.** Merit is passwordless ([ADR-039](../decisions/ADR-039.md)), and
[`0002_identity.sql`](../../packages/db/migrations/0002_identity.sql) records it
on the table where a password would have to live: there is no password table
anywhere in the schema, by design. Both passkey ceremonies are blocked. So the
three factors on this screen are the whole of trader authentication and
**nobody can sign in to this deployment by any route**.

**So "call what is served" resolves to a single route that would answer a code
no trader could have been sent.** `verifyOtp` returns the deliberately
indistinguishable failure for a bad or expired code, so a button posting to it
has exactly one reachable outcome and it is that failure: a wrong answer dressed
as a working control. [ADR-190](../decisions/ADR-190.md) rules a wrong answer
worse than an honest refusal, and this is that distinction on the surface a
trader meets first.

**A second refusal would stop it anyway, independently.** All four routes are
`POST` and [`http/client.ts`](../../apps/portal/src/http/client.ts) declares an
`ApiClient` with `get` and nothing else, so this application cannot express any
of the four even for the one that answers. The portal's first write verb is a
transport ruling with a CSRF posture, an unsafe-method cookie policy and an
idempotency question attached; `app/security/source.ts` declined exactly that
widening one screen over for `POST /sessions/:id/revoke`, and this screen's
write is heavier still because `POST /auth/verify` sets the session cookie. That
file is outside this fence either way. The two refusals would lift on different
days, which is why `view/sign-in.ts` keeps `submits_to` a separate field from
`served` rather than a second spelling of it.

### 3. The finding that was inside the file the reservation points at

`availability.ts` carried a **correct** per-method wiring measurement and, six
lines above it, a summary reading *"all four routes behind SC-M4-01 are
REGISTERED, and NOT ONE of them is wired"*. That has been false since `ADR-200`
wired `verifyOtp`, and **the measurement six lines below it already said so**.
`page.ts` repeated the false half.

**Both were prose, so both were out of reach of every gate in this repository,
and the summary is the half a reader trusts.** A file whose own summary and own
measurement disagreed is the frontend shape of the defect class this corpus
keeps finding, and it was caught only because the session derived the split at
the backend instead of reading the paragraph.

### 4. What now holds it

`ENDPOINT_WIRING` carries the measurement as data -- `endpoint` (API_CONTRACT's
spelling), `method` (the port's, which is the join key), `served`, and `blocker`
(the operator's constant, which reaches no screen per
[ADR-120](../decisions/ADR-120.md) ruling 4). `REQUIRED_ENDPOINTS` is **derived**
from it, so the flat list the other five segments also export cannot disagree
with the table above it.

[`sign-in.test.ts`](../../apps/portal/test/sign-in.test.ts) reads the split back
off `apps/api/src/auth-backend.ts` and `apps/api/src/routes/auth.ts` and **fails
in both directions**. It reads text, which is narrower than it looks: dispatch
protocol section 5 rules a grep unreliable for **which routes exist**, and this
is the **wiring** question, answered off the one object literal that answers it.

**The partition assertion is the negative control.** Blocked plus implemented
must equal the port exactly, so a regex that silently stopped matching fails the
count rather than letting every per-row check pass by comparing empty sets.
That is `falsify`'s own 36-rows-to-13 lesson applied to a new reader.

### Landmines

- **`served` is not a licence to call.** A row reading `served: true` is a
  statement about `apps/api` and nothing else; `submits_to` is the portal's
  half and is the literal `null`, so wiring it is a type change a reviewer
  reads. A later session that sees `POST /auth/verify` served and draws a form
  has reintroduced exactly the button this session refused to draw.
- **The new gate reads `apps/api` source as TEXT.** It is sound for the wiring
  question and is guarded by a partition assertion, but a refactor that
  respells `blocked('name'` or `async name(` fails the count rather than the
  claim, and the fix is the regex and not the data.
- **Delivery landing does not unblock SMS.** `verifyOtp`'s `sms` arm raises
  separately because a phone has no address in `RESOLUTION_ADDRESS`
  ([ADR-200](../decisions/ADR-200.md) section 4.4), so that factor has two
  independent blockers and the second outlives the first.
