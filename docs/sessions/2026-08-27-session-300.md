### 2. THE MEASUREMENT THAT DECIDED THE DESIGN

`AS-M7-05`'s counter says the synthetic subjects are *"flagged `is_synthetic`"*, and cites
the discipline [M02](../plans/M02-rithmic-bridge.md) `OQ-M2-01` proposes for simulator
accounts. **That question is open and the column is not there.**

```
grep -rn 'is_synthetic' packages/db/migrations/   -> no matches
grep -rn 'synthetic'    packages/db/src/schema.ts -> detector_runs.synthetic_expected
                                                     detector_runs.synthetic_found
```

Two counters about a **run**, and no marker on a **subject**, anywhere in 51 migrations.
`OQ-M2-01`'s own wording is a recommendation rather than a ruling: *"Recommendation: yes,
with a hard `is_synthetic` flag on the identity and a CI test asserting every aggregate query
excludes it."*

**So the column reading needs a migration, and this slice holds no migration number and may
not take one.** What it takes instead is the reading that makes the same assertion
unconditionally true:

| Reading | What "excluded from every aggregate" means |
|---|---|
| **A marker column** | a property every present **and future** query must honour, watched by a CI test over the queries somebody remembered to audit |
| **Never persisted** | true by construction, of every query, including the ones nobody has written yet |

The second is strictly stronger and it is also cheaper: no column, no query audit, and no day
on which somebody adds the nineteenth aggregate and forgets.

**AND ITS COST IS NAMED RATHER THAN WAVED AT, BECAUSE IT IS THE PART A LATER SESSION WOULD
OTHERWISE ASSUME.** A canary that never travelled through `rowsWhere` proves the detector's
PREDICATE still matches and proves **nothing** about whether the READ still returns the rows
it used to. A schema change renaming `fills.executed_at` breaks the read and the battery is
still found, because it arrives through the same in-memory door on either side of the rename.
That case is a test rather than a caveat:

> `it('rows_scanned is ZERO when the read returns nothing, even though the canaries were found')`

which is `AS-M7-05`'s own opening sentence, still reachable, pinned so nobody claims otherwise.

### 3. The cheap implementation the DDL cannot see

[`0008_risk.sql:96`](../../packages/db/migrations/0008_risk.sql):

```sql
CONSTRAINT detector_runs_synthetics_match_status CHECK (
  status <> 'ok' OR synthetic_found >= synthetic_expected
)
```

**A detector that seeds NO canaries satisfies it at `0 >= 0` and reports `ok` every night
forever.** No constraint in the database can tell that run from a working one, and
`SD-M7-01`'s whole design rests on the counters being non-zero. So `mintBattery` refuses an
empty battery in code, on [M07 section 8](../plans/M07-risk-abuse.md)'s own row: the
synthetic-canary suite is one per detector, every run, in prod.

### 5. The four findings, reported and not repaired

1. **`detector.run_degraded` has no row in [EVENTS](../architecture/EVENTS.md).**
   [M07 section 5](../plans/M07-risk-abuse.md) carries it as one of three NEW events, with the
   payload `{ detector, detector_version, trading_day, synthetic_expected, synthetic_found,
   rows_scanned }` and consumers *"ALERT (page), FEED"*. The catalogue's section 8 carries
   only `detector.run_completed`. [session 161](2026-08-24-session-161.md) already recorded
   that all three appear in no `.ts` or `.mjs`. `EVENTS.md` is outside this fence and
   [ADR-159](../decisions/ADR-159.md) clause 1 makes the authority for a name the registry
   rather than a producer, so the payload is transcribed from `M07` field for field and **the
   suite asserts the ABSENCE**, which goes red the day somebody adds the row -- at which point
   the payload should be re-derived from the catalogue rather than from `M07`.
2. **`flag.raised`'s `evidence_summary` is undefined in the corpus.** `EVENTS` section 8 gives
   the field and defines it nowhere, and its consumers include FEED. This runner sends the
   evidence object's **keys** rather than its values: `INV-M7-03` keeps the numbers ON the
   flag where the admin console reads them, `INV-M7-10` keeps detector parameters away from a
   trader audience, and the keys carry what kind of accusation it is without carrying a
   threshold into a consumer nobody has written yet. **The definition is owed.**
3. **`detector_definitions_current_idx` is NOT UNIQUE.**
   [`0008_risk.sql:52`](../../packages/db/migrations/0008_risk.sql) creates it as a plain
   index, so two overlapping current rows are insertable. The runner refuses them; a
   `UNIQUE INDEX` would put `INV-M7-04`'s provenance on the schema instead of on a code path.
   That is a migration and this slice holds no number.
4. **[`apps/worker/src/batch/statistics.ts`](../../apps/worker/src/batch/statistics.ts) has
   never been exported from [`src/index.ts`](../../apps/worker/src/index.ts).** Found by
   re-reading the whole barrel after the merge, which `P7` section 9 asks for. It is reached
   only by its own test through a relative import. **A leg that was never added rather than
   one a merge dropped**, and adding it here would be widening a fence to finish.
