### 4. What was not done, and why

- **NO SCHEDULE.** The job stays `unscheduled`. Writing an adapter makes it RUNNABLE and scheduling makes it RUN, and the second has a blocker the first does not: there is no event sink, and there cannot be one from this deployable. **Never schedule a money-path sweep to make a checklist look complete.**
- **NO REFUSING DEFAULT FOR THE SINK**, which was the tempting shape and is refused in [ADR-344](../decisions/ADR-344.md) section 4. A live io over a rejecting sink is worse for a trader than the unswept estate, because today the alarm rings.
- **NO EVENT SINK BUILT HERE.** It is a package both deployables can declare, which is `P5-n`'s slice and a MOVE rather than a wiring.
- **NO MIGRATION AND NO SQL.** `git diff --stat origin/main -- packages/db/migrations scripts/db` is EMPTY.
- **NO `pnpm run verify` AND NO `falsify.mjs`.** Both forbidden by the row.
- **NO RENAME OF `sweeps/ledger.ts`**, whose name is narrower than its contents and which that file registered as owed in session 516.

### 5. Blockers and landmines

- **THE EVENT SINK IS THE ONLY THING BETWEEN THIS JOB AND A CLOCK, AND IT IS NOT A WIRING.** The producer is in `apps/api` and the only handle that can write `events` is in `apps/worker`. Neither may import the other and neither should. A session that tries to close this with an import will meet `RI-04`, `node-linker=isolated`, `test/db.test.ts` section 4 and `test/event-sink.test.ts` section 3, in that order.
- **AND THE SINK IS NOT THE LAST BLOCKER.** `payout.freeze_expiring`'s payload names neither tenancy column, so `assertTenanted` refuses it even with a sink installed. That is [ADR-191](../decisions/ADR-191.md) section 9's open item and `EVENTS.md` owes the repair.
- **THE ADAPTER'S FILENAME IS LOAD-BEARING.** `expiry-adapter.ts` falls inside `merit/no-calendar-in-expiry-path`'s `apps/**/*expiry*.ts` glob and `adapter.ts` would not have. A future rename moves the file out of the one rule written for this exact mistake.
- **`terms` NOW REACHES THIS DEPLOYABLE.** `src/db.ts` re-exports two constructors that reach no table. The argument that they are not a door is [ADR-344](../decisions/ADR-344.md) section 3's and it is an argument rather than a measurement; a third narrowing arriving there is a decision somebody should take deliberately.
- **FIVE RESERVATION ROWS WERE WRITTEN ON SIBLINGS' BEHALF (`339` to `343`) AND EACH CLAIMS NOTHING.** Only `339` could be traced to a pushed branch; `340` to `343` are on branches nobody has pushed, so those cells name no branch and quote the search that found none instead. **`ALLOCATION.md` will conflict at merge and it is a resolve-by-hand, never a keep-both.** **THAT PREDICTION WAS RIGHT AND IT WAS INCOMPLETE, WHICH IS RECORDED RATHER THAN QUIETLY WIDENED.** It named the `ALLOCATION` cells and did NOT anticipate that the SESSION LOG would collide add/add, which is the conflict a keep-both would actually have destroyed: two different logs at one path. Section 5a is what happened. **THE NEXT ROW IN A PARALLEL WAVE SHOULD DERIVE ITS SESSION NUMBER AGAINST `origin/main` IMMEDIATELY BEFORE PUSHING, NOT AT THE START OF THE SESSION**, because maximum-plus-one is a fact about a moment and fourteen branches took the same answer from it.
