### 2. The seven writes, and what the database said

`pg_ctlcluster 16 main start`, then `0001` through `0051` applied forward-only under `ON_ERROR_STOP`
with no failure. One fixture: one identity, the two ledger accounts an adjustment posts to
(`trader_wallet` at identity scope, `fees_revenue` at firm scope), one posted transaction and one prior
wallet CREDIT of `50000` cents from a settled payout, which lands as `wallet_entries.id = 1`.
**The fixture is ADR-173's, rebuilt rather than reused, so the writes below are a reproduction and not a
citation.**

| | The write | What the database said |
|---|---|---|
| **A** | The correction **exactly as the OLD contract instructed**: the corrected entry's id into `reference_id` | `ERROR: invalid input syntax for type uuid: "1"` |
| **B** | The same correction through [`0038`](../../packages/db/migrations/0038_account_adjustments.sql)'s door: `reference_id` is the ADJUSTMENT's id | **`COMMIT`.** `wallet_entries.id = 2`, `provenance = 'correction'`, `balance_after_cents = 60000`, and `w.reference_id = a.id` reads back `t` |
| **F** | `reference_id` is a WELL-FORMED uuid that is not the adjustment's id | `ERROR: ADJ-C3: adjustment 99999999-... has 0 matching wallet_entries row(s) and must have exactly one ... and this adjustment's id as reference_id` |
| **C** | The correcting DEBIT the contract's body admits, with no `reverses_adjustment_id` | `ERROR: ... violates check constraint "account_adjustments_debit_is_a_reversal"` |
| **E** | A `goodwill` credit with a NULL `account_id`, which **corrects no entry at all** | **`COMMIT`.** `wallet_entries.id = 4`, `provenance = 'correction'`, `reason_code = 'goodwill'` |
| **G** | An amount AT the row's own `dual_control_threshold_cents` with no approval named | `ERROR: ... violates check constraint "account_adjustments_dual_control_above_threshold"` |
| **H** | The grant, read at `information_schema.role_table_grants` rather than off the DDL | `merit_app` holds exactly `INSERT, SELECT` on `admin_actions`, on `wallet_entries` and on `account_adjustments`. PUBLIC holds nothing |

**Write F is this session's own and it is the one the deliverable rests on.** ADR-173 proved the
contract's referent was not expressible; write F proves the binding is exclusive, which is a different
claim. A wiring slice that put the ledger transaction's id or the identity's id in that column would be
well typed, would pass every type in the workspace, and would raise `ADJ-C3` by name at `COMMIT`. That is
why the port states the binding and why `1a` asserts it at the trigger rather than at the two types.

**The threshold used in writes B, E and G is `100000` cents and it is ARBITRARY.** It appears in no
assertion and in no committed file. Its real value has no source anywhere in this tree and is the
founder's, so no number was chosen for the code and none is proposed here.

### 4. Findings reported and not repaired

**1. THE DISPATCH'S PREMISE IS WRONG ABOUT SCOPE AND THE ENTRY IT CITES SAYS SO IN TERMS.** The dispatch
opened *"ADR-173 has now ruled and the blocker is gone"* and asked for the append to be finished. ADR-173
clause 6 is titled *"THE STOPPED APPEND STAYS STOPPED, and this entry unblocks nothing"* and its table
marks three of session 298's four findings **STANDS**. The dispatch's own list of what must be true when
the session is done contains no item that requires the append to write, and all four of them are
satisfied. **The entry governs and the session followed it**; had the two been reconciled by widening
instead, the widening would have been a `reason_code` this repository chose on a trader's behalf and a
dual-control threshold it invented on the cash door.

**2. THE THRESHOLD HAS NO SOURCE ROW TO READ FROM, NOT MERELY NO VALUE IN THE TREE.** The dispatch said
to read the threshold from the row. A sweep of the live catalog for every column in `public` whose name
mentions a threshold or a dual control returns four: `account_adjustments.dual_control_threshold_cents`,
`account_adjustments.dual_control_approval_id`, `correlation_groups.threshold` and
`plan_breaker_state.threshold_bp`. **The last two are not this control and the first is the column being
written.** `0038` calls it *"The threshold IN FORCE when this row was written"*, which is a SNAPSHOT of a
policy value, and no table in this schema holds the policy. So the first correction ever written has
nowhere to read its threshold from, and every later one could only read the last row's snapshot, which is
a policy that changes by being written rather than by being set. **This is session 298's finding 3
sharpened, and it still cannot be ruled from any document in this tree.**

**3. NOTHING IN THE DATABASE REFUSES A CORRECTION COMPOSED WITHOUT ITS AUDIT ROW.** ADR-173 section 6
item 1 priced this and the price is now paid in code: the record of which entry a correction corrects is
written by this handler, in the same transaction as the append, and by nothing else. A future writer who
composes an `account_adjustments` row and its wallet entry directly gets a correction whose occasion is
`reason_note` alone. **The repair named in that item is an [`0048`](../../packages/db/migrations/0048_audited_writes_on_append_only_tables.sql)-shaped
`SECURITY DEFINER` function taking an `admin_actions.id` as a PRECONDITION**, it is a migration, it is
`E2`, and it is not this session's.

**4. THE CONTRACT ROW STILL CARRIES THREE STATEMENTS THE DATABASE REFUSES**, which ADR-173 section 6 item
6 also says. A reader of the repaired row now finds `corrects_entry_id` truthful and `direction: "debit"`,
`second_approver` and the absent `reason_code` still wrong. **The route is made honest about one field
tonight and the row is not made honest**, and saying so is cheaper than a later session rediscovering the
other three inside a money-path diff.
