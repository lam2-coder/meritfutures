### The measurement is what decides the ruling, and P4 took it without classifying it

[P4 section 5.4](../plans/P4-portal-and-site.md) found twelve drifted tables and named the three that are P4's. **Re-derived here with the drift assertion's own algorithm and then CLASSIFIED BY SHAPE, which P4 did not do:**

| Later column-change shape | Tables |
|---|---|
| **`ADD COLUMN`** | **11** |
| **`ALTER COLUMN`** | **2** (`otp_challenges`, `trading_calendar`) |
| **`DROP COLUMN`** | **0** |
| **`RENAME`** | **0** |
| Distinct tables | **12 of 111** |

**Ten of the twelve are `ADD COLUMN` and nothing else**, one carries both (`otp_challenges`), one carries `ALTER COLUMN` alone (`trading_calendar`). **The two zeroes are the most important numbers in the entry**: a fold for `DROP COLUMN` and `RENAME` would be written against nothing, so the ruling refuses them and lets the first instance turn the suite red and buy its own ADR.

**`ALTER COLUMN` is refused although folding it would be a NO-OP**, because it cannot change a column-name set at all. Both instances are `DROP NOT NULL`, which moves **nullability** -- an axis [`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts) has never compared on any of the seven since [ADR-084](../decisions/ADR-084.md). **So the refusal stays as a stated PROXY, and the gap it stands in for is named rather than quietly inherited.**

### The slice was four tables and the type checker is what said so

`sessions.user_id` is `uuid NOT NULL REFERENCES users(id)`, not `identities(id)`. `DerivedRule.via` is typed `TableKey`, so a rule reaching an identity through `users` cannot name `users` unless `users` is registered. **`users` entered the registry because the registry's own totality forced it, not because a plan asked for it.**

This is [ADR-092](../decisions/ADR-092.md)'s *"a session cannot know its own slice size before it runs"* arriving from the direction that entry did not name: not a table a sibling already registered, but a table pulled IN by a rule. **Reported as four of three rather than three of three.**

| Table | Class | Reaches an identity by |
|---|---|---|
| `users` | `owned` | `identity_id NOT NULL REFERENCES identities(id)` |
| `sessions` | `derived` | a hop through `users`. **NOT through `device_fingerprint_id`**, which reaches whoever shares a device |
| `plan_versions` | `firm` | nothing. Every identity is sold the same version and the link runs the other way |
| `rule_states` | `derived` | a hop through `accounts`, one row per account per trading day |

### ADR-094's clause, executed in the direction it fails in

**The failure direction is SILENCE and the silence available to a replay is doing nothing.**

| Seeded | Result |
|---|---|
| fold intact, `fee_back_repeats` deleted from the transcription | **`plan_versions` per-table assertion RED**, 1 failed / 30 passed, the column named |
| **fold made vacuous AND the same seven later columns deleted from the transcription**, so both sides are wrong the same way | **every per-table comparison GREEN**, and only **`the fold is not vacuous`** RED. 1 failed / 30 passed |

**The second row is the whole reason that assertion exists.** Without it a replay that returned each `CREATE TABLE` set unchanged would leave the suite green for every table whose transcription also omitted its later columns, which is [ADR-084](../decisions/ADR-084.md) section 7's failure at estate scale.

- **Landmines:**
  - **`otp_challenges` AND `trading_calendar` REMAIN UNREGISTRABLE** and no ruling in this session changes that. Their `ALTER COLUMN` refusal is a **proxy** for a comparison that does not exist: **column TYPE and NULLABILITY are transcribed into [`schema.ts`](../../packages/db/src/schema.ts) and asserted nowhere**, on all eleven registered tables, and that was already true before this session. Deleting the refusal before writing the comparison trades a real control for nothing. **Writing the comparison turns the suite red on whatever it finds across eight already-merged money-path files, and measuring that is its own session.**
  - **`users` IS NOW REGISTERED AND NO PLAN ASKED FOR IT.** Under [ADR-092](../decisions/ADR-092.md) the registration is never re-argued and the first writer wins, so any concurrent slice that intended to register `users` now rebases its rows out rather than merging them. `users` is named by many module plans; this is the collision that entry predicted, arriving on the first slice after it.
  - **`plan_versions` IS `firm`, WHICH MEANS `P4-e` READS IT THROUGH `systemDb`, AND `SystemReason` STILL HAS NO MEMBER FOR A MARKETING PAGE.** `'nightly-batch'` and `'operator-console'` are the closed vocabulary and neither is a public rules page. **That is [P4](../plans/P4-portal-and-site.md) section 10 item 6, dispatched as session 185's `ADR-096`, and it is untouched here.** Registering the table does not unblock `P4-e`; it removes one of `P4-e`'s two blockers.
  - **THE FOLD READS `ALTER TABLE ... ;` WITH A NON-GREEDY MATCH TO THE FIRST SEMICOLON, INHERITED FROM THE ASSERTION IT REPLACES.** A semicolon inside parentheses would truncate a statement and the fold would read a partial clause list as a complete one, so the fold now **throws on an unbalanced statement** rather than trusting the match. No such statement exists in the 47 migrations today; the guard is there because the fold's correctness now depends on the regex where the old assertion only needed its detection.
  - **`ADD CONSTRAINT` NO LONGER EXEMPTS A WHOLE STATEMENT.** The old assertion skipped any statement containing `ADD CONSTRAINT`, so a statement mixing `ADD CONSTRAINT` with `ADD COLUMN` would have been skipped entirely and its column missed. The fold checks the column-changing shape FIRST. **No such mixed statement exists today**, and the reordering is stated here so it is not read later as an unexplained difference.
