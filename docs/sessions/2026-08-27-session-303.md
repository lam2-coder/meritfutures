### 2. What was measured, and what was refused

#### 2.1 The route, and the one step it does not take

The ordered behavior is section 1.5's, built and asserted end to end. What is NOT here is `LT-06`,
and section 1.3 is the argument. **Two mechanical facts back it up rather than the prose alone.**

1. **`WithdrawalTx` carries no ledger handle.** [`payouts.ts`](../../apps/api/src/routes/payouts.ts)'s
   `PayoutTx` declares `readonly ledger: LedgerTx` and this port declares nothing of the kind, so a
   later edit that wanted to post here has to widen the port in a diff a reviewer reads.
2. **The suite asserts it.** The adapter case reads back every accessor call the route made and
   asserts that none of them names a `ledger*` key.

**The key this route WOULD have used is recorded in the module header rather than left for a later
session to re-derive.** `payouts.ts`, `admin-payouts.ts` and
[`apps/worker/src/sweeps/expiry.ts`](../../apps/worker/src/sweeps/expiry.ts) were all read: each builds
the identical string `` `${PAYOUT_ENDPOINT} ${idempotencyKey}` `` for `LT-01`, so one approval is one
posting whichever of the three doors reaches it, and `expiry.ts` states in its own header that using the
identical string **is the fail-closed direction**. `LT-06`'s equivalent is the string derived from
`wallet_withdrawals.idempotency_key`, which the trader supplied and the schema already makes unique per
identity, and **not** one naming this endpoint: the approval edge is reachable from a sweep and an
operator console as well as from here. **And the sign is not a caller's to write.**
[`packages/ledger/src/posting.ts`](../../packages/ledger/src/posting.ts) applies it in exactly one place,
`+amountCents` on the debit and `-amountCents` on the credit; a caller names a debit account, a credit
account and a POSITIVE amount. `LT-06` debits `trader_wallet` (identity) and credits `firm_treasury`.

#### 2.2 The lock, and why it is `lockScope` rather than `lockAt`

The dispatch says *"`lockAt(key, at)` = `rowAt` plus `FOR UPDATE` ... 'one in flight' is exactly the case
that lock exists for"*. **`lockAt` locks a row that exists and the row a concurrent second request would
create does not**, so there is no address to point it at. [ADR-157](../decisions/ADR-157.md) clause 4
names the other half in the same sentence: *"`lockScope()` locks the handle's own `identities` row and
takes NO argument"*, and clause 4's own gloss calls it *"`INV-M20-01`'s per-identity lock"*. Its section 9
rows 15 to 17 watch a second A-scoped transaction BLOCK while a B-scoped one does not, which is exactly
the mutex this gate needs. **An advisory lock is refused by name** and nothing here adds a
`SqlExecutorReason` member, a `SystemReason` member, a `pg` import or a cast past a key type.

#### 2.3 The aggregate was NOT wanted, which the plan asked to be told either way

[P5](../plans/P5-payouts-and-wallet.md) rule 10 says the aggregate is refused on evidence and that if FIFO
composition wants one, *"that is a finding and a stop, not a widening"*. **It does not want one.** The
composition is a fold over the identity's whole `wallet_entries` set, which `tx.rows` already returns, and
the balance cross-check is a second fold over the same array. What the read costs is
[`wallet.ts`](../../apps/api/src/routes/wallet.ts)'s recorded cost, *"the rows crossing the boundary are
the window's rather than the match's"*, and it is paid the same way. **`G-NO-IN-FLIGHT` is the one place a
predicate would have helped and it is a four-value `OR`**, which is one of the two terms `ADR-157` still
refuses on the argument that a disjunction can ADD rows; so the four statuses are filtered in memory and
the list is written out as `wallet_withdrawals_open_idx`'s own.

#### 2.4 THE FENCE EXCEPTION, stated plainly

[`apps/api/test/registry.test.ts`](../../apps/api/test/registry.test.ts) is **not** in this slice's fence
and **one line of it changed**.

Its expected order was derived by stripping `.ts` and THEN sorting, while `discoverRouteModules` sorts
`readdir`'s output and strips per file. `'-'` is `0x2D` and `'.'` is `0x2E`, so **`wallet-withdrawals`
sorts BEFORE `wallet` by filename and AFTER it by stem**, and the two derivations disagree for the first
time in this repository's history the moment a module stem is a prefix of another's. The sort was moved
above the strip. **The assertion is unchanged**: it is still an equality against the directory, and the
directory is still the module list.

**The three available answers and why this one.** Leaving the suite red contradicts the dispatch's
*"END MERGEABLE"* and hands the founder a branch that cannot merge. Renaming the module breaks
[P5](../plans/P5-payouts-and-wallet.md) section 8's fence, which names
`apps/api/src/routes/wallet-withdrawals.ts` explicitly, and severs the correspondence between the module
name and the contract path. Repairing a test's derivation of its own expectation changes no behavior and
removes a defect that would have bitten the next slice whose name prefixes another's. **It is reported
here, in [STATE](../STATE.md), in the module's own commit message and in the pull-request body rather
than being left for a reviewer to notice in a diff.**

**It also qualifies one sentence of the plan.** [P5](../plans/P5-payouts-and-wallet.md) section 9 says the
routes directory is *"NOT A COLLISION, and that is [ADR-100](../decisions/ADR-100.md)'s whole return"*.
That is true of the SOURCE, where the module list really is the directory listing, and it was not true of
this test's derivation of it.
