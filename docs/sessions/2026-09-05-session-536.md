### 4. Ruling one: RECORD, BLOCK, ALARM, and never CORRECT

The dispatch asked whether the sweep records, alarms or corrects, and warned that a job that silently corrects hides the defect it exists to find. **The corpus answers it in one line and the session did not have to invent a policy.**

`ST-M2-8`: *"Mismatch sets `recon_blocked`, alarms, excludes from eligibility."* `0014_marks.sql`: a mismatch *"sets accounts.recon_blocked = true and blocks eligibility until a HUMAN resolves it"*. [RB-02](../ops/runbooks/RB-02-recon-mismatch.md) ends every one of its four shapes at a person: request redelivery rather than repairing the file, because *"a repaired vendor file is a file Merit wrote"*; a correction SUPERSEDES and replay recomputes forward; an unattributable delta is *"Quarantine. Never classify as realized P&L, never guess"*.

**SO THREE OF THE FOUR, AND CORRECTION IS NOT ONE OF THEM.** Two of the three are built. The third is finding 1 below.

**THE ASYMMETRY IS THE CONTROL AND IT HELD AGAINST A REAL DATABASE.** The sweep may SET the block and never CLEAR it, implemented by writing no `accounts` value at all on a match; section 6's second transcript shows an account still blocked after a clean night, with its `updated_at` still at the instant of the mismatch.

### 5. Ruling two: wired, and deliberately not scheduled

**THE ADAPTER MAKES THE JOB RUNNABLE. A CALLER MAKES IT RUN.** `test/schedule.test.ts` case 3.1 derives disposition from a caller census over `src/`, so this is not a label somebody typed. Nothing in this row calls the sweep.

1. **THE BLOCK HAS NO RELEASE.** `recon_blocked` is a payout-eligibility veto through `R-40` (`packages/rules-engine/src/payout/evaluate.ts:104`). The only write of that column under any `src/` is `sweep.ts:614`, and it writes `true`. **Nothing writes `false` anywhere, in code or in a route.**
2. **THE RUN NEEDS A `batch_run_id` NOBODY IS MINTING.** `OVERVIEW` 5.2 puts the stage inside the nightly batch, and the sweep refuses a non-uuid rather than generating one.
3. **THE DEAD-MAN SWITCH WOULD BE SATISFIED BY THE WRONG CHECK.** Finding 2.

**THIS IS THE ONE I WOULD MOST LIKE OVERRULED IN WRITING RATHER THAN IN A DIFF.** Refusing to schedule the control that finds missing money means nobody is comparing the books, and every night it stays off a clock is a night a discrepancy goes unfound. I chose the reversible harm over the irreversible one, and a founder who says "block them, we will clear them by hand in SQL" is making a different and defensible call.

### 7. Findings

1. **THE ALARM THIRD OF `ST-M2-8` IS NOT BUILT.** `recon.mismatch_detected` exists in [EVENTS](../architecture/EVENTS.md):188 with exactly the payload `ReconOutcome` carries, and nothing emits it. `ports.ts` excludes `events` from the write union on the ground that EVENTS has no `recon.completed`, which is true and is about the RUN event; the MISMATCH event does exist. The real blocker is that this deployable has no event writer, which `batch/adapter.ts`'s `EVENT_SINK_BLOCKER` already says for two other channels. **A mismatch is recorded and blocks, and nobody is paged.**
2. **THE CRON REGISTRATION NAMES THE WRONG CHECK.** `schedule.ts` binds this entry point to the `CRON_INVENTORY` row "per-identity ledger reconciliation", which is `INV-M20-10`'s wallet-against-ledger assertion (`GS-231`, S1). This sweep is `ST-M2-8`'s per-account-day comparison. Left as registered, because case 4.1 requires an existing inventory row and there is no `ST-M2-8` row to move it to; creating one is an edit to a frozen document.
3. **THE CLEARING PATH DOES NOT EXIST ANYWHERE**, raised from an observation `sweep.ts` already made to a **precondition of scheduling**.
4. **`0064` REFUSED `'degraded'` FOR WANT OF A PRODUCER AND THE PRODUCER IS NOW RUNNABLE.** One uncomparable account closes the whole night `failed`, the same word a sweep that died at account three gets. Not taken: the member is a `CHECK` on a merged migration and only a superseding one moves it.

### 8. Landmines for the next session

- **DO NOT SCHEDULE THIS SWEEP UNTIL SOMETHING CAN CLEAR `recon_blocked`.** The adapter existing makes it one line to wire, and that line would be the harm section 5 refused.
- **`RECON_READ_FILTERS` IS TRANSCRIBED FROM THREE CALL SITES.** A fourth read added to `sweep.ts` gets a run-time throw and not a compile error. That is the weakest structure in this row.
- **THE SEEDED FIXTURE NEEDED `ingest_files.kind = 'eod_report'` AND `status = 'applied'` WITH BOTH `applied_at` AND `disposition`.** `ingest_files_applied_has_disposition` refuses otherwise, and `'daily_marks'` is not a member of `ingest_files_kind_check`.
- **`merit_app` IS `NOLOGIN`**, so a live probe needs a login role granted into it. A run as the owner proves nothing about the deployed role's grants.
- **THE SESSION NUMBER IS 536 AND IT SKIPS FIVE.** `origin/main` ends at 529, `530` is on the branch holding `339`, and `531` through `535` are on no ref, matching the five reservation rows above.
