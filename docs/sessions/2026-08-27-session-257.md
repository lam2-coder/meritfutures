### 1. THE PLAN, committed before a source file was touched

[ADR-003](../decisions/ADR-003.md)'s money-path regime requires the plan to exist before the diff does, and plan mode wedges a remote session, so the discipline is discharged here: **this section was committed on its own, ahead of `admin-writes.ts`.** Everything below it is what the session then did.

#### 1.1 What "the four writes" resolves to, against the contract

The dispatch names **`POST /admin/accounts/:account`, `POST /admin/flags/:flag`, `POST /admin/plans/:plan`, `POST /admin/plans/versions/:version`**. None of those four is a row in [API_CONTRACT](../architecture/API_CONTRACT.md) section 8. **Each is the PATH PREFIX of one or more rows that are**, with the action segment cut off and the parameter abbreviated:

| The dispatch's name                   | API_CONTRACT section 8's rows under it                              |
| ------------------------------------- | ------------------------------------------------------------------- |
| `POST /admin/accounts/:account`       | `/admin/accounts/:accountId/freeze`, `/unfreeze`, `/close`, `/note` |
| `POST /admin/flags/:flag`             | `/admin/flags/:flagId/status`                                       |
| `POST /admin/plans/:plan`             | `/admin/plans/:planId/versions`                                     |
| `POST /admin/plans/versions/:version` | `/admin/plans/versions/:versionId/publish`                          |

**The corpus is the specification, so the rows are what get written: seven routes under four prefixes.** Writing four collapsed endpoints, each taking an action discriminator, would be a shape the contract does not carry, and writing only four of the seven would leave three admin writes with no owner: session **256** holds the reads and this session holds the writes.

#### 1.2 THE RULING THAT SHAPES ALL SEVEN

`admin_actions.reason` is `text NOT NULL` under a comment reading **"NO UNEXPLAINED ADMIN ACTION, EVER. NOT NULL is the whole control."** Verified at [`0017_events_and_audit.sql:82`](../../packages/db/migrations/0017_events_and_audit.sql), the line the dispatch cited, which is correct.

So the ruling is a shape and not a check:

> **The audit row is written FIRST, in the same transaction, and the mutation is downstream of it. The route never supplies `reason`, never defaults it, and never substitutes a neighbouring field for it. An operator write carrying no reason is refused by the DATABASE, and the route's job is to report that refusal rather than to pre-empt it.**

Ordering is the half that makes this structural. If the target row moved first and the audit row were appended afterwards, "no unexplained admin action" would depend on both statements running. Inserting the audit row first makes the explanation a **precondition of the mutation** in the only place that cannot be forgotten: the transaction itself.

#### 1.3 The door, and why it is `systemDb('operator-console')`

Two of the four subject tables are `owned` and two are `firm`:

| Table                                          | `SCOPE_RULES` class      | Reachable by           |
| ---------------------------------------------- | ------------------------ | ---------------------- |
| `accounts`                                     | `owned` on `identity_id` | `scopedTx`, `systemTx` |
| `risk_flags`                                   | `owned` on `identity_id` | `scopedTx`, `systemTx` |
| `identities`                                   | `root`                   | `scopedTx`, `systemTx` |
| `plans`, `plan_versions`, `plan_version_sizes` | `firm`                   | `firmTx`, `systemTx`   |
| `admin_actions`                                | `firm`                   | `firmTx`, `systemTx`   |

**`firmTx` cannot reach `accounts` or `risk_flags`** (`FirmTableKey` excludes every `owned` table, by construction), and an operator write reaches across identities by definition. **One door serves all seven and it is `systemDb('operator-console')`**, which is the reason [ADR-084](../decisions/ADR-084.md) accepted that word for and the one [ADR-102](../decisions/ADR-102.md) section 10 is least comfortable with. **`SystemReason` is not widened and `SqlExecutorReason` is not touched.**

The accessor is [ADR-112](../decisions/ADR-112.md)'s keyed one: **`rowAt`, `updateAt`, `deleteAt`.** `update` and `delete` are not methods on any transaction handle in this workspace, which ADR-112 section 6 states in exactly those words and which the tree confirms.

#### 1.4 Roles

[M06](../plans/M06-admin-ops-console.md)'s `INV-M6-09` is the ruling and it is one line: **"`readonly` cannot mutate anything, and `ops` cannot change config, roles, or plan versions."**

| Route                                                | Roles                              |
| ---------------------------------------------------- | ---------------------------------- |
| `freeze`, `unfreeze`, `close`, `note`, flag `status` | `owner`, `ops`                     |
| `POST /admin/plans/:planId/versions`                 | `owner` only. It is a plan version |
| `POST /admin/plans/versions/:versionId/publish`      | `owner` only. It is a plan version |

`readonly` is refused all seven, which is [API_CONTRACT section 12](../architecture/API_CONTRACT.md)'s row _"`readonly` role calls any admin mutation | `admin_sso` | 403"_.

#### 1.5 The surface

`/admin` is one of `OPERATOR_PREFIXES`, so [`registry.ts`](../../apps/api/src/registry.ts)'s `compose` **never registers this module on the public deployment** and the public 404 is the router's. That is [ADR-083](../decisions/ADR-083.md) section 4 and it is not a permission check.

### 2. What was built

Seven routes in one module, [`apps/api/src/routes/admin-writes.ts`](../../apps/api/src/routes/admin-writes.ts), registered by the directory listing rather than by a list ([`registry.ts`](../../apps/api/src/registry.ts) discovers `routes/`, so registration cost no edit to a shared file and collided with nothing).

| Route                                           | Roles          | What it writes, after the audit row                                                                                                                                    |
| ----------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /admin/accounts/:accountId/freeze`        | `owner`, `ops` | `accounts.payouts_frozen = true`. Every cited flag must exist, belong to this account's identity, and at least one must still be `open`                                |
| `POST /admin/accounts/:accountId/unfreeze`      | `owner`, `ops` | `accounts.payouts_frozen = false`. `resolution_note` is recorded as the note and is **never** used as the reason                                                       |
| `POST /admin/accounts/:accountId/close`         | `owner`, `ops` | `accounts.status`, `phase`, `closed_on`, `close_reason`, plus an `account_status_history` row. `kind` **is** `admin_actions.initiative`, which is `0043`'s own wording |
| `POST /admin/accounts/:accountId/note`          | `owner`, `ops` | The audit row and nothing else, because `events` is unreachable. Finding 3                                                                                             |
| `POST /admin/flags/:flagId/status`              | `owner`, `ops` | `risk_flags.status` plus the resolution trio, and on `investigating` the identity's `payouts_frozen`, which the response states explicitly                             |
| `POST /admin/plans/:planId/versions`            | `owner`        | A draft `plan_versions` row and its `plan_version_sizes` grid                                                                                                          |
| `POST /admin/plans/versions/:versionId/publish` | `owner`        | `plan_versions.status`, behind three gates: already-published, `validatePlan`, and dual control                                                                        |

**The ruling, in one shape:** read the target row, INSERT `admin_actions`, then mutate. **Nothing supplies a `reason`, defaults one, or substitutes a neighbouring field for one**, and the same rule covers `initiative`, `public_slug`, the five `plan_version_sizes` money columns `CreateVersionRequest` omits, and the publish-decision pair: carried from the request or refused by the database, never invented.

### 3. THE CLAUSE, both directions, against a real PostgreSQL 16.13

All <!--gen:migration_files-->63<!--/gen--> migrations applied from empty, `111` tables installed, `systemDb('operator-console')` opened against it. **The refusal and the pass are one test each and neither is worth anything without the other**, which is [`DELTA_MANIFEST`](../../packages/db/DELTA_MANIFEST.md) section 13's lesson.

```

 ✓ the reason, at the database > SUCCEEDS on the same call carrying a reason, and both rows land
 ✓ the reason, at the database > is refused by the database when the initiative is absent too
 ✓ the reason, at the database > is refused by 0043's biconditional when trader_request names no identity

 Test Files  1 passed (1)
```

The refusal, at source, executed by hand before it was written into a test:

```
$ psql -c "insert into admin_actions (actor, action, subject_kind, subject_id, before, after, initiative)
           values ('ops:a','account.freeze','account',gen_random_uuid(),'{}','{}','operational');"
ERROR:  null value in column "reason" of relation "admin_actions" violates not-null constraint

$ psql -c "insert into admin_actions (..., reason, ...) values (..., '', ...) returning id, quote_literal(reason);"
2|''
$ psql -c "insert into admin_actions (..., reason, ...) values (..., '   ', ...) returning id, quote_literal(reason);"
3|'   '
```

**`NOT NULL` refuses an OMITTED reason and ADMITS an empty one.** [API_CONTRACT section 8](../architecture/API_CONTRACT.md) requires a non-empty one, so the route refuses a blank reason and says in its own message that it is standing in for a `CHECK` the table does not carry. `plan_versions_simulation_waiver_not_blank` is that idiom, one table over.

**Nothing moved on the refusal**: zero `admin_actions` rows and `accounts.payouts_frozen` still `false`, asserted after the 400. That is the audit-first order working, not a second guard.

### 5. The role check is not vacuous, pasted

```
--- ADMIN_WRITE_ROLES (INV-M6-09, as data) ---
  POST /admin/accounts/:accountId/freeze           owner, ops
  POST /admin/accounts/:accountId/unfreeze         owner, ops
  POST /admin/accounts/:accountId/close            owner, ops
  POST /admin/accounts/:accountId/note             owner, ops
  POST /admin/flags/:flagId/status                 owner, ops
  POST /admin/plans/:planId/versions               owner
  POST /admin/plans/versions/:versionId/publish    owner
```

Three assertions, and the second and third are what stop the first from being a guard that refuses everybody: **`readonly` is refused all seven and writes nothing at all**; **`ops` is refused exactly the two plan rows and allowed the other five**; **`owner` passes the role gate on all seven**. The last one asserts `412` on publish rather than `200`, because an owner then meets dual control, and asserting `200` across the board would have been a test that could only pass with the dual-control gate absent.

### 6. The two greps, at ZERO

**Domain-shaped strings in the whole diff.** Every dotted token in every added line was listed, not just the ones matching a TLD list. What came back was property access (`ctx.request`, `account.freeze`, `admin_actions.reason`), file names, and **one address, `seed-${stamp}@example.test`**, which is [RFC 6761](https://www.rfc-editor.org/rfc/rfc6761)'s reserved test domain in a seed row. **No hostname, no apex, nothing `ADMIN_ORIGIN`-shaped, in code, comments, fixtures, docs or the PR body.** A scan of the whole tree returned vendor, competitor and research domains only.

**Floats in the money path.** Every `*_cents` value in the diff is an integer literal or a `bigint`: `5_000_000n`, `16_500n`, `250_000`, `12_500`. The only decimals anywhere in the added lines are a timestamp's `.000Z`, a ToS clause string `'4.2'`, and `16.13` in a comment about a Postgres version. **No `parseFloat`, no `toFixed`, no `Math.round` on money, no `/ 100`, no `* 100`.** The two conversions are `centsField`, which refuses a value that is not a safe integer rather than rounding it, and `centsToJson`, which refuses a `bigint` that does not fit a JSON integer.
