#### 1.3 THE ORDERING RULE, WHICH IS THE THING MOST LIKELY TO BE GOT WRONG

[M20](../plans/M20-wallet.md) section 3.7. The two refusals **fire at different moments against
different subjects** and are kept apart on purpose:

| | Subject | When | Where in this file |
|---|---|---|---|
| The hard limit (`INV-M3-15`, `identities.status`) | the IDENTITY | at the resolved-identity step | `gateIdentity`, **BEFORE the payment-method branch**, on all three methods |
| `INV-M20-06`'s enumerated gate set | the IDENTITY | inside the spend transaction | the wallet arm of the branch |
| The impersonation refusal (`INV-M20-16`, `M6-N-02`) | the SESSION | at authorization | **NOT IMPLEMENTABLE.** Section 1.7 |

`gateIdentity` is already at the top of both handlers' transactions and it stays there. The
branch is added BELOW it, so a `restricted` or `closed` identity is refused identically whether
it asked for `psp`, `wallet` or `mixed`, **and the suite asserts it against all three** rather
than against the one the slice is about. A refusal written inside the wallet arm passes a
careless test and is wrong for the other two, which is the defect
[M03](../plans/M03-billing-checkout.md) section 3.5.1 already paid for once.

`INV-M20-06` is re-asserted in the wallet arm **including its `identities.status` member**, even
though `gateIdentity` has already refused that case. The set is enumerated rather than
described, and a set that drops a member because another control happens to cover it is a set
that silently loses the member the day that control moves. That is `GS-302`'s own note read in
the direction it points.

#### 1.4 THE WALLET ARM, IN [M20](../plans/M20-wallet.md) SECTION 3.2's ORDER AND NOT ONE OF MY OWN

Section 3.2's diagram orders the refusals, and the order is followed literally, including that
**the position check comes BEFORE the velocity delay**: an insufficient balance is refused
rather than delayed, because telling a trader to come back in six hours and then refusing them
is worse than refusing them now.

```
1  INV-M20-06   the enumerated set: identities.status, identity payouts_frozen,
                account payouts_frozen, account recon_blocked, KYC not verified
2  INV-M20-02   own accounts only, RESOLVED SERVER SIDE: the target account is
                the one the SCOPED handle returned, never one the body named
3  ADR-157      tx.lockScope(), which takes NO argument, then
4  INV-M20-01   the position read UNDER that lock, refused if short
5  INV-M20-07   the velocity limit, which DELAYS
6  LT-08        posted through packages/ledger, in this transaction
```

**`INV-M20-07` DELAYS AND DOES NOT REFUSE, AND THE DIFFERENCE IS WHAT THE TRADER IS TOLD.** A
refusal is terminal and carries no way back; a delay names the instant the window has rolled off
enough spend to admit this purchase, and the trader retries then. It answers `rate_limited` 429
with `Retry-After`, which is [API_CONTRACT](../architecture/API_CONTRACT.md) section 2's own code
for a velocity throttle, and `retry_at` is COMPUTED from the debits that will age out rather
than guessed. **A limit of `daily_cents: 0` is the one case with no such instant**: the contract
says that value "means no wallet spend at all", so no amount of window rolling admits a positive
spend, and the delay is returned with no `Retry-After` rather than with a fabricated one.

**No row in `wallet_spend_limits` is UNLIMITED**, on the contract's own sentence: "the absence of
any row for an identity is what unlimited looks like".

#### 1.5 THE ACCESSOR IS THE ONE DOOR

member, no `SystemReason` member, no `pg` import and no cast past a key type**, and touches no

#### 1.7 FOUR THINGS THIS SLICE CANNOT WRITE, REPORTED RATHER THAN REACHED AROUND

Each is named at the site as well as here, and each is fail-closed rather than guessed.

**1. `purchases.psp` AND `purchases.psp_reference` ARE BOTH `NOT NULL` AND A WALLET ROW HAS
NEITHER.** [`0006_commerce.sql`](../../packages/db/migrations/0006_commerce.sql):
`psp text NOT NULL CHECK (psp IN ('psp_a','psp_b'))` and `psp_reference text NOT NULL`.
`SD-M3-06` added `payment_method`, `wallet_debit_cents` and `wallet_ledger_transaction_id` to
this table and **relaxed neither**, and the only two `ALTER TABLE purchases` in the tree
([`0007`](../../packages/db/migrations/0007_accounts.sql),
[`0011`](../../packages/db/migrations/0011_wallet.sql)) add foreign keys. So a `payment_method =
'wallet'` row is unwritable without naming a processor that was never called and a reference that
references nothing. **`PurchaseInsert.psp` and `.pspReference` are therefore `| null` and the
wallet path sets both to `null`**, which is the schema reported honestly rather than a field
forgotten, on [ADR-158](../decisions/ADR-158.md) clause 2's precedent. The repair is a superseding
migration and [P5](../plans/P5-payouts-and-wallet.md) section 7 forbids this slice a number.

**2. `wallet_entries.provenance` HAS NO MEMBER THAT DESCRIBES A DEBIT.**
[ADR-158](../decisions/ADR-158.md) finding 3, already recorded and already unrepaired: the column
is `NOT NULL` and its three members are the CREDIT list by the DDL's own heading, so
"every wallet debit in this schema is written carrying a class that does not describe it".
**`WalletDebitInsert` declares no `provenance` field**, exactly as `ADR-158`'s `WalletDebit` does
on the wire, and what the debit MEANS is `cause` and `reference_id`, whose own declaration
enumerates `purchase` among its referents. The repair is a direction-conditional CHECK or a debit
vocabulary, and it is a migration.

**3. `payment_method` IS NOT ON [API_CONTRACT](../architecture/API_CONTRACT.md)'s
`CheckoutRequest`, AND `CheckoutResponse` REQUIRES TWO FIELDS A WALLET PURCHASE DOES NOT HAVE.**
Section 5's `CheckoutRequest` has five members and no sixth;
[M03](../plans/M03-billing-checkout.md) section 4 says `POST /checkout`
**"Accepts `payment_method` of `psp`, `wallet`, or `mixed`"**. [ADR-158](../decisions/ADR-158.md)
took eight contract rows and none of them is this one. The contract is `approved`, it is **outside
this fence**, and no ADR number is allocated to this session. **The code is written as a strict
superset that no contract-conformant request can reach**: `payment_method` is OPTIONAL and
defaults to `'psp'`, so a five-member body behaves byte for byte as it does today and receives
today's response shape; the wallet response is a second member of a union reachable only through a
field the contract does not declare. The contract owes both rows and this session does not write
them.

**4. THE IMPERSONATION REFUSAL (`INV-M20-16`, `M6-N-02`) CANNOT BE IMPLEMENTED.** `AuthSession`
has six fields and none of them is a session type, so there is nothing to refuse on. This is
[`payouts.ts`](../../apps/api/src/routes/payouts.ts)'s finding about `INV-M5-23` arriving on the
second money route, and [M05](../plans/M05-payout-system.md) section 3.6's corollary applies here
too: a refusal nothing asserts disappears silently. It is reported and not invented.

#### 1.8 `mixed` NEEDS A RULING, SO IT IS REPORTED AND REFUSED RATHER THAN HALF-BUILT

The fence admits an ADR **only if `mixed` needs a ruling**, and says to stop and report rather
than take a number if it does. **It does**, and the argument is three lines against the landed
tree:

1. [M03](../plans/M03-billing-checkout.md) section 3.4 specifies the wallet leg of a `mixed`
   purchase as **"held pending the PSP result"**. There is no held representation.
   `wallet_entries` is append-only, `purchases_wallet_debit_is_posted` requires
   `wallet_ledger_transaction_id` the instant `wallet_debit_cents > 0`, and `ledger_entries` is
   append-only with no UPDATE or DELETE grant ([`0026`](../../packages/db/migrations/0026_roles_and_grants.sql)).
   So the leg is POSTED and not held, from the moment the row exists.
2. The release is therefore a **compensating credit** days later, and
   `wallet_entries.provenance` has no member for it either: `refund_wallet_funded` describes a
   refund of a purchase **the wallet itself funded**, and a `mixed` purchase is funded partly by
   card; `correction` is [M20](../plans/M20-wallet.md)'s `WF-M20-05`, "Admin, dual controlled",
   and a PSP webhook is not an admin. That is finding 2 above arriving on a second row.
3. The compensation site is [`webhooks-psp.ts`](../../apps/api/src/routes/webhooks-psp.ts), which
   is not in this fence.

So `payment_method = 'mixed'` is refused with a named refusal that states the reason.
**The refusal sits AFTER `gateIdentity` and not at the wire**, because putting it in validation
would answer `validation_failed` 400 to a restricted identity asking for `mixed` where
[M20](../plans/M20-wallet.md) section 3.7 requires the hard limit to answer first. That is the
ordering rule tested from the direction that catches it.

**Refusing it forecloses nothing and weakens nothing**: nothing in the tree sends
`payment_method` at all today, so `mixed` is unreachable either way, and a `mixed` that posted a
debit it cannot release is a real loss rather than a missing feature.

#### 1.9 A DEFECT IN THE FILE I HOLD, REPORTED WITH ITS PATCH AND NOT TAKEN

`gateIdentity` refuses a non-`active` identity with **`forbidden` 403**.
[API_CONTRACT](../architecture/API_CONTRACT.md) section 2 defines **`identity_restricted` 422**
for exactly this, in these words: "Refused **server side** at the resolved-identity step, on
**every** payment method"; [M03](../plans/M03-billing-checkout.md) section 3.5 says "`422`, in
`geo_restricted`'s and `account_cap_reached`'s shape"; and
[`payouts.ts`](../../apps/api/src/routes/payouts.ts) already answers `identity_restricted` 422 on
the sibling route.

**It is left as it is and reported.** The refusal's PLACEMENT is this slice's; its CODE is a
wire-visible change to the card leg, which [P5](../plans/P5-payouts-and-wallet.md) section 6 says
this slice "touches neither other branch" of. The suite pins today's behaviour with the finding
named beside the assertion, so the day somebody takes the patch the test says why it moved.
The patch is two lines in `gateIdentity`:

```
-    return refuse(
-      'forbidden',
-      'Forbidden',
-      403,
+    return refuse(
+      'identity_restricted',
+      'Identity restricted',
+      422,
```
