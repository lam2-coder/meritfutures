### 1. THE ADAPTER, AND WHY IT IS NOT HERE

**The dispatch's first sentence is "write the admin event feed's ADAPTER so `listEvents`
resolves". It cannot be written, and the reason is not a fence and not a missing file.**

`admin-source/flags.ts` and `admin-source/graph.ts` are the two adapters this directory
has, and both have the same shape: a module declares the TABLES it reads as a closed
tuple, declares a `Tx` interface whose `rows`, `rowsWhere` and `rowAt` are keyed by that
tuple, and `SystemTx` satisfies it structurally. Two assertions hold that shape together
in `test/admin-source-flags.test.ts`: every key those tuples name is in `TABLE_KEYS`, and
`const handle: AdminSourceTx = null as unknown as SystemTx` compiles.

**`events` fails the first and a feed adapter would fail the second.** Derived at
reporting time rather than read out of a document:

| Claim | How it was produced | Result |
| --- | --- | --- |
| `TABLE_KEYS` does not hold `events` | imported `packages/db/src/scope.ts` and read the array | **106 keys**, and the only event-ish members are `pspWebhookEvents` and `kycFunnelEvents` |
| `packages/db/src/schema.ts` declares no `events` table | `grep` for `pgTable('events'` | **no match.** 106 `pgTable` declarations and none is this one |
| A `Tx` naming `'events'` is not satisfied by `SystemTx` | seeded a `FeedTx` under `src/admin-source/` and ran `tsc` | **`TS2322`**: *"Types of parameters 'key' and 'key' are incompatible. Type `"events"` is not assignable to type `"identities" \| ... \| 91 more`"* |

**THE REFUSAL IS ARGUED AND IS NOT AN OVERSIGHT, WHICH IS WHY THIS SLICE DOES NOT REACH
FOR IT.** [`scope.ts`](../../packages/db/src/scope.ts) spends a paragraph on this table
by name: `identity_id uuid NULL` and `account_id uuid NULL` with no CHECK tying them, so
`owned` drops every account-level row, `derived` is refused by `ADR-101` twice, `pair`
needs a second IDENTITY column and this row's second column is an ACCOUNT, `firm` is
refused by a mechanical assertion, and `root` is `identities`' alone. Its conclusion is
that **the table needs a SIXTH CLASS**, and `ADR-106` is the precedent for what adding
one costs. `P5-b` was dispatched to register it, tried all five members, and stopped.

**So the three ways to land an adapter today are each a refusal this corpus already
made.** Registering `events` is `packages/**`, is session 347's fence this wave, and is
an entry rather than a commit. Reaching `sqlExecutor` needs a second
`SqlExecutorReason` member, which the dispatch forbids and `ADR-157` closed. Declaring a
second port in `admin-feed.ts` is the shape `ADR-184` section 5 refused **by name** as
weakening a gate to pass it. **The fourth option is to report, and it is the one taken.**

### 2. `ADR-184` SECTION 3's NARROWING DOES NOT REACH `listEvents`, AND THE ENTRY SAYS THE OPPOSITE

**This is the one claim in a merged entry that this session found false, and it is load
bearing rather than cosmetic.**

`test/wiring.test.ts`'s `BLOCKED` reason for `setAdminReadSource` reads *"None of the six
methods is a projection of one table ... A live adapter today would have to reach
`sqlExecutor`"*. `ADR-184` section 3 argues that **the reason is false for the feed**,
because it is "a keyed range read over ONE table", and that `listEvents` is therefore the
**third** instance after `listFlags` and `readIdentityGraph` where the narrowing applies.
`admin-source/index.ts` and the port's own doc comment both record it that way.

**The first half of that sentence is true and the conclusion is false.** `AdminEventRow`
is a projection of one table. That table is not reachable through the accessor at all, so
"a live adapter today would have to reach `sqlExecutor`" is **correct for `listEvents`**,
where it was measured false for the other two. The narrowing has two instances and not
three.

**The difference is not bookkeeping.** `listFlags` and `readIdentityGraph` were unblocked
by ORDINARY CODE over keyed reads, which is what `P7-i` demonstrated. `listEvents` is
blocked by a **registration decision in another package**, which no amount of ordinary
code reaches. A reader who takes the recorded narrowing at face value will schedule the
feed adapter as a slice like `P7-i`'s and discover a `packages/db` ruling instead.

**Reported and not repaired, in three places, each with its owner.** `ADR-184` is merged
and a change to it is an entry. `admin-source/index.ts` and `routes/admin-reads.ts` are
`apps/api` files this fence does not hold and this session touched neither.
`test/wiring.test.ts` already owed two repairs from session 341 and this is a third.

### 3. `WAVE-06` SECTION 5.2, DISCHARGED WITHOUT EDITING `src/feed.ts`

**Section 5.2 predicted that a React page would leave `assertWithheld` reading a line
array nothing serves, with both suites green. The repair it named is a case asserting the
SERVED BODY.**

`assertWithheld(feed, lines)` takes `readonly string[]`. `collectServedStrings` walks a

matters beyond convenience: `src/feed.ts` is a barrel leg and is named by neither the
`W6-h` plan row nor this dispatch's fence, so a repair requiring it would have been a
fence widening for a control that was already available.

**`ADR-184` SECTION 6's SECOND SHAPE IS NOT TAKEN AND THE REASON IS THE SAME FENCE.** That
entry names two ways to close its own duplication and calls the second "already `W6-h`'s
shape": the console re-points at the served body and DROPS its own copy of the redaction
rule. **The re-pointing landed and the dropping did not**, because dropping it is an edit
to `src/feed.ts`. The console's copy is therefore still a second statement of one rule,
and it is now a defence-in-depth statement rather than a competing one, which is the half
of that shape this fence could take.

### 4. Two legs, and each catches what the other cannot

| Leg | Catches | Cannot see |
| --- | --- | --- |
| **The closure**, over the served bytes | any subject-shaped id the query did not name, arriving through ANY field including `event_name` and `subject_kind`, and one **glued to a word character**, which `assertNamesNoSubject`'s `\b`-anchored pattern misses | an identifier that is not uuid-shaped |
| **`assertWithheld`**, over the same bytes | any value **this package** would have withheld, by value however it is spelled, including a non-uuid string in an identifying field | an id in a field nobody classified, because `buildFeed` would not have withheld it either |

**`assertNamesNoSubject` is deliberately not called**, which is
`../identities/identity-graph.tsx`'s reason arriving on a screen that holds the licence
only SOMETIMES: it refuses ANY subject identifier and is exactly wrong on this screen's
two named arms. **The closure is strictly wider than it would have been on the
`operational` arm**, and the glued-uuid case is that difference exercised.
