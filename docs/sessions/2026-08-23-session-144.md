## 2026-08-23 - Session 144: the `API` container gets a deployable, and the argument that decides it is not the one the brief pointed at

- **Objective:** `P3-a`. [OVERVIEW](../architecture/OVERVIEW.md) section 2's C4 diagram declares `API [/api/v1]` inside the Merit boundary and section 3's container table does not row it, so every endpoint [API_CONTRACT](../architecture/API_CONTRACT.md) specifies has no deployable to live in. Write `ADR-083`, create the deployable, and row it.

- **Done:** **[ADR-083](../decisions/ADR-083.md), `status: proposed`, approval line UNSIGNED.** Three rulings. **(1)** The API is its own deployable, [`apps/api`](../../apps/api), and not a server inside `apps/portal`. **(2)** It is **one codebase deployed twice**, the surface chosen at startup: `public` serves API_CONTRACT sections 3 to 7 and 10, `operator` serves sections 8 and 9 on `ADMIN_ORIGIN`, and neither registers the other's routes. **(3)** **Fastify 5**, under `node --experimental-strip-types`, **no build step ever**. The deployable is `package.json`, `tsconfig.json`, `src/index.ts`, [`src/surface.ts`](../../apps/api/src/surface.ts) and [`test/surface.test.ts`](../../apps/api/test/surface.test.ts). [OVERVIEW](../architecture/OVERVIEW.md) section 3 rows it, [ALLOCATION](../decisions/ALLOCATION.md)'s `083` row is amended in place, and [STATE](../STATE.md) carries the entry.

Two one-line repairs are owed by sessions holding files this fence did not: `RI-04`'s `DEPLOYABLES` literal and [INFRA](../architecture/INFRA.md) section 2's Railway service table, both below. **P3's wave 3 was deliberately not dispatched because its fences were paths inside a deployable that did not exist**; `apps/api/src/**` is nameable now, and a second P3 planning session can dispatch the six module slices.

- **Blockers:** **nothing is signed.** `ADR-083` amends a frozen `approved` document and picks a framework the project lives with for years.

- **Landmines:**

  - **THE BRIEF POINTED AT THE ORIGIN ARGUMENT AND THE ORIGIN ARGUMENT DOES NOT DECIDE THIS.** It quotes [P1 section 2.1](../plans/P1-monorepo-scaffold.md)'s *"the tempting scaffold is one application with three route groups"* and asks whether it reaches the API surface. **That sentence is about the admin console's SEPARATE ORIGIN**, and [INFRA section 13.2](../architecture/INFRA.md) puts the portal and the API on the **same** origin, `app.meritfutures.com`. Carried across unexamined it argues for nothing, or worse, for folding the API into the portal because they share an origin anyway. **The sentence that decides it is [API_CONTRACT section 1](../architecture/API_CONTRACT.md)**: the three UI surfaces are the API's clients and have *"no privileged back door"*. A surface that CONTAINS the API has one by construction, because a handler in the same package is an import away and no lint can distinguish a legitimate internal call from a route bypass. **The P1 argument's SHAPE reaches this seam and its subject does not**, and writing that down is the whole of section 3 of the entry.

  - **THREE DOCUMENTS READ THE OTHER WAY AND ALL THREE ARE STILL TRUE.** [INFRA section 2](../architecture/INFRA.md) names the Railway service **`portal-api`**; INFRA section 13.2 puts *"portal and API"* on one origin; [OVERVIEW section 7](../architecture/OVERVIEW.md)'s application zone reads **`API + portal + site`**. Every one is about deployment topology and none is about ownership. **Sharing an origin and sharing an edge zone are not sharing a process**, and a session that reads those three and stops has folded the API into `apps/portal` with three citations behind it.

  - **403 AND 404 ARE THE MECHANISM, AND THEY ARE ONE ROW APART IN THE SAME TABLE.** [API_CONTRACT section 12](../architecture/API_CONTRACT.md) requires **403** for a trader session on `/admin/*` and **404** for `/internal/*` from the public origin. **403 is what a permission check returns; 404 is what an ABSENT ROUTE returns.** A process that registered the route and then refused it can be made to answer 404, and every future handler, middleware ordering and error mapper is another chance to get it wrong. A process that never registered it cannot answer anything else. **That is why the route set is chosen at startup rather than per request**, and it is the difference between the ruling being structural and being a preference.

  - **A PARTITION BY API_CONTRACT'S SECTION NUMBERS PUTS THE LIVENESS PROBE ON THE ADMIN ORIGIN.** Section 9 is headed *"Ops and internal (admin origin only)"* and its first row is **`GET /health`, marked Public**, beside `GET /internal/health/deep`, marked admin-origin only. The obvious reading of the heading leaves the public deployment with nothing for the platform to poll. **The partition is over the `/admin` and `/internal` path prefixes**, which gets both rows right with no special case, because the contract had already drawn the distinction where it belongs.

  - **A BARE `startsWith` MATCHES `/administration`, AND A HELPFULLY PREFIXED BASE PATH IS WORSE.** `/api/v1/internal/jobs` passes a leading-slash check and then matches **neither** operator prefix, so a classifier that only checked the slash calls an operator route **public** and reports nothing. Both are refused in [`surface.ts`](../../apps/api/src/surface.ts) rather than documented, and [`surface.test.ts`](../../apps/api/test/surface.test.ts) asserts the refusal **and** that `/apiary` survives it, or the guard has become the substring match it exists to prevent.

  - **THE BRIEF'S CANDIDATE APPROVAL CLAUSE IS FALSE AND STAYS FALSE AFTER THE FIX.** It reads *"OVERVIEW section 2's container list and section 3's container table name the same set"*. **They do not.** `packages/rules-engine` and `packages/rithmic` are rows in section 3 with no box in section 2, and that is **correct**: section 2 is a C4 **context** diagram, which draws deployables and datastores, and a library that ships inside a deployable is not one. **The clause is asserted in the one direction that was actually false** -- every container section 2 draws has a row in section 3 -- and the reverse is refused in writing. A clause signed in the direction that reads well would have been signed and would have been wrong.

  - **`MERIT_API_SURFACE` HAS NO DEFAULT AND THERE IS NO SAFE ONE TO PICK.** Defaulting to `public` fails closed and is still wrong, because it turns a misconfigured admin deployment into a silently useless one; defaulting to `operator` fails open. The refusal follows [`apps/admin/src/origin.ts`](../../apps/admin/src/origin.ts)'s precedent for `ADMIN_ORIGIN`: a deployment that has not been configured is a deployment that has not been configured.

  - **THE FRAMEWORK'S FOUR PROPERTIES WERE MEASURED IN A SCRATCH DIRECTORY OUTSIDE THIS REPOSITORY, AND ONE OF THEM RULES A WHOLE FAMILY OUT.** Against `fastify@5.12.1` on Node `v22.22.2`: a `.ts` entry point served a registered route (**200**) and answered an unregistered one (**404**) under `node --experimental-strip-types` with no build; `addContentTypeParser(..., { parseAs: 'buffer' })` returned the raw 7 bytes and the parsed object from one request, which is what *"HMAC signature verified **before** parsing"* needs; and the 49-package install tree declares **zero** `preinstall`, `install` or `postinstall` scripts, which is what `onlyBuiltDependencies: []` turns into an admission decision. **NestJS and every decorator-first framework are not merely rejected, they are unavailable** while `CI-06/gate-inventory` requires the `build` key absent: decorators need a transform and `--experimental-strip-types` transforms nothing.

  - **THE COST OF FASTIFY OVER HONO IS NAMED RATHER THAN GLOSSED.** Hono is runtime-agnostic and would have kept a Cloudflare Workers deployment open for free. Fastify targets Node's `http`, and reopening that is a rewrite of every route registration and every hook. It is accepted because Merit is on Railway ([ADR-007](../decisions/ADR-007.md)) with Cloudflare as edge only, and the API holds a pooled Postgres connection per request, which is the workload edge runtimes are worst at. **An entry that recorded only the winner would have left the next reader unable to tell whether Hono was considered or never seen.**

  - **ONE FORCED FENCE EXTENSION, NAMED RATHER THAN DISCOVERED, AND IT IS THE SAME ONE [SESSION 142](2026-08-23-session-142.md) HIT.** [`docs/decisions/README.md`](../decisions/README.md) gains one row: an ADR entry file is a registry **fragment**, not a corpus document, so it takes no `docs/INDEX.md` row and `CI-06n` fails on an entry with no README row. INDEX's role here was the generated `adr_count` span, 82 to 83, which is `CI-06g`'s and moved under `gates.mjs generate` in the same commit. **The fence's `docs/INDEX.md (your row only)` clause anticipated a row that the registry rules mean does not exist.**

- **Reported, not touched:**

  - **`RI-04` DOES NOT SEE THE FIFTH DEPLOYABLE, AND THIS IS THE HIGHEST-VALUE ONE-LINE FOLLOW-UP THIS SESSION CREATES.** Its `DEPLOYABLES` list in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs) is the literal `['site', 'portal', 'admin', 'worker']`, so `apps/api` gets none of its three assertions: own directory, distinct package name, and **no app depending on an app**. **The invariant passes and is now narrower than the tree it names**, which is the quiet failure mode rather than the loud one. It matters more than it looks: `ADR-083`'s placement argument rests on section 2's three arrows into `API` being unimplementable if an app may import an app, which is exactly the assertion `RI-04` makes and now makes about four fifths of the apps.

  - **[INFRA section 2](../architecture/INFRA.md)'s RAILWAY SERVICE TABLE NAMES FOUR SERVICES AND THIS RULING NEEDS SIX.** `api` and `api-admin` join `site`, `portal-api`, `admin` and `worker`. **It is the same defect this session closed, one document over**: a topology table that does not row a container the architecture requires. `SERVICE_BY_SURFACE` in `surface.ts` names both services and cites the consequence.

  - **`portal-api` IS A SERVICE NAME THAT DESCRIBES ONE THING AND IS NAMED FOR TWO.** `apps/portal` exports `SERVICE = 'portal-api'`. Renaming it is not free -- it is a Railway service identity -- so it is recorded for the INFRA session to decide rather than inherit.

  - **NOTHING IS INSTALLED AND THE RULING NAMES A FRAMEWORK THE MANIFEST DOES NOT DECLARE.** Every version in this workspace lives in `pnpm-workspace.yaml`'s `catalog:` block, which [the P3 plan section 6](../plans/P3-ledger-billing-identity.md) gives to sessions 145 and 147, and a manifest declaring `"fastify": "catalog:"` against an absent catalog entry does not install. So `pnpm-lock.yaml` gains **one importer entry and no package**, the workspace still declares **zero runtime dependencies**, and the VG-12 admission with its exact pinned version is the next holder's. **The gap between a named framework and an installed one is a real state and it is stated rather than left to be found.**
