### 2. The two halves, and neither deployable holds both

**THE DISPATCH ASKED WHAT DOOR `apps/worker` HAS. IT HAS THE ONE.**

[`apps/worker/src/db.ts:150`](../../apps/worker/src/db.ts) exports `LIVE_DB`, whose single
method `batch` is `transaction(systemDb('nightly-batch'), fn)` and hands the caller a
`SystemTx`. [`scoped-db.ts:2167`](../../packages/db/src/scoped-db.ts) declares
`SystemTx.insert<K extends TableKey>`, which is session 366's finding read from the other
end: `events` is registered `either` under ADR-191, `ScopedTx.insert` is generic over
`OwnedTableKey` and `FirmTx.insert` over `FirmTableKey`, so the system handle is the only
one that reaches the table. **`apps/worker` has held that handle since ADR-165 and it is
the only deployable in the workspace that does.**

| | `apps/api` | `apps/worker` |
| --- | --- | --- |
| `emit` call sites in `src` | **0**, measured | **7**, measured |
| a handle whose `insert` reaches `events` | **no** (`scoped` and `firm` only, ADR-165) | **yes**, `SystemTx` |
| the producer (`buildEvent`, the catalogue, the writer) | **yes**, `src/events.ts` | **no** |

**SO THE SYSTEM HAS BOTH HALVES AND NO DEPLOYABLE HAS TWO.** That is not a defect either
file introduced. [`P5:393`](../plans/P5-payouts-and-wallet.md)'s `P5-n` row names
`apps/api/src/events.ts` as the producer's file and it was written before this deployable
had a door at all; the arrangement became impossible when ADR-165 gave the door to the
worker rather than to the API, and nothing since has re-read the plan row against it.

**THE FENCE IS `RI-04` AND IT IS AN INVARIANT RATHER THAN A CONVENTION.**
[`repo-invariants.mjs:389`](../../packages/tooling/checks/repo-invariants.mjs) iterates
`DEPLOYABLES` at `:385` and reports *"a deployable that imports a deployable is one
deployable"* for any dependency field naming another app. `apps/worker/package.json`
declares `@merit/db` and `@merit/rules-engine` and nothing else, and under
`node-linker=isolated` an undeclared bare specifier resolves at neither run time nor build
time (ADR-117 section 5, measured there).

**BUT `RI-04` READS MANIFESTS AND NOT SOURCE, AND `db.test.ts` PINS BARE SPECIFIERS AND
NOT RELATIVE ONES.** So `import { makeEventSink } from '../../api/src/events.ts'` is
refused by neither, resolves at both run time and build time, and is exactly the move a
session that has read this entry's section 6 and decided the ruling can wait would reach
for. **Section 3 of the new suite refuses it**, comment-stripped first so a header
discussing `apps/api` in prose cannot fire it.

TABLES, AND `events` EMPTY BEFORE THE RUN.** One identity, one user, one plan, one plan

`ExpiryTx` structurally, so no adapter stands between the sweep and the real handle.

### 5. What `ADR-198` unblocked, and it is none of these seven

**THE DISPATCH SAYS `ADR-198` IS "WHAT MADE THIS SLICE POSSIBLE AT ALL". IT IS NOT, AND

`payout.hold_released` carries three timestamps and three identifiers.
`wallet.withdrawal_halt_released` carries a rail status. `payout.freeze_expiring` carries a

`breaker.state_changed` carries `ratio_bp`, `threshold_bp`, `sample_size` and `min_sample`,

**WHAT THE RULING DID UNBLOCK IS `payout.requested`, `payout.approved` AND `payout.held`**,

is not a criticism of it: a format for a forever-retained column is better ruled before

### 6. The ruling that is owed, with the four candidates priced

| Candidate | Disposition |

| **`apps/worker` grows its own producer** | **REFUSED HERE.** A second implementation of a format in an append-only column retained forever, which ADR-159 clause 1 refuses one level up and `ADR-198` clause 4 refuses by name: *"the corpus holds exactly one implementation of each direction"*.
