### The refutation, derived rather than assumed

The dispatch says the portal serves **four** routes and asks for two screens it does not have. Both halves are false at `63b73fcc`, before a line of this session's work.

`pnpm --filter @merit/portal build` prints **twelve** routes, and the count is the same on both sides of this session's diff because no route was added:

```
/  /_not-found  /accounts  /accounts/[account]  /calendar
/calendar/[accountId]/rules  /calendar/[accountId]/timeline
/certificates  /kyc  /payouts  /purchases  /referrals
```

`/accounts` is `SC-M4-02` and `/accounts/[account]` is `SC-M4-03`. Both landed in **pull request #434**, and [ADR-147](../decisions/ADR-147.md) is session 259's entry recording what building them found. So the dispatch asked for work that was done, and asked for it against a route count that was stale by eight.

**Every requirement the dispatch named as binding was already satisfied**, checked one at a time against the shipped source rather than against the dispatch's summary of it:

| `SC-M4-03`: every gate, gate by gate, never a single progress bar | [`account-detail.ts:185`](../../apps/portal/src/app/accounts/account-detail.ts)'s `FundedProgress`. No bar, no ring, no percentage, no aggregate |

### Finding 1: the barrel was at 18 of 21, and the omission could not go red

The dispatch's one pointed instruction was *"re-read it after you touch it and count its legs"*. Counted: [`api/types.ts`](../../apps/portal/src/api/types.ts) exports **21** names and [`index.ts`](../../apps/portal/src/index.ts) re-exported **18**.

The three missing are `CursorPage`, section 1's list envelope, and `PAGE_LIMIT_DEFAULT` and `PAGE_LIMIT_MAX`, the contract's own stated bounds.

**The shape of the failure is why it survived a year of sessions.** A name absent from a barrel type checks, lints and tests green, because it is simply a name nobody outside the package can write. Nothing goes red anywhere. `CursorPage` was used by **three** modules inside this application -- `app/(purchases)/source.ts`, [`calendar/load.ts`](../../apps/portal/src/app/calendar/load.ts) and that segment's suite -- and was nameable from nowhere outside it. So a consumer could import `MarkListItem` and could not import the envelope it arrives in, and the only way to type the response was to redeclare the envelope, **which is a second transcription of a contract shape and is the exact defect [`test/api-types.test.ts`](../../apps/portal/test/api-types.test.ts) exists at the top to prevent**.

**The repair is the gate and not the three names.** That file now derives both lists from the two sources and asserts set equality. [`test/surface.test.ts`](../../apps/portal/test/surface.test.ts) already asserted reachability and does it against a transcribed list of twenty names, so it drifts the same way the barrel does and for the same reason; this one cannot.

**Three seeded defects fired and were watched:** dropping `CursorPage`, re-exporting a name that does not exist, and dropping the two bounds. Both parsers assert a non-empty result first, so a regex that matched nothing cannot pass the test by comparing two empty lists.

### Finding 2: the payout centre was prerendering static, and the build exits 0 either way

`/payouts` printed with the **static** marker. Nine of the ten data-reading routes declare `export const dynamic = 'force-dynamic'`; the tenth was **the payout centre**, which [M04 section 3.6](../plans/M04-trader-portal.md)'s own table rows as *"authoritative, always"* (`INV-M4-13`).

**The mechanism is an ordering inside the transport.** What marks an App Router route dynamic is a request-scoped API, and this application's only one is `cookies()`. [`serverApiClient`](../../apps/portal/src/http/client.ts) reaches it in its last line; [`resolveApiOrigin`](../../apps/portal/src/http/client.ts) runs first and throws `ApiConfigError` when `MERIT_API_ORIGIN` is unset. **A build environment without that variable never reaches the cookie**, [`payouts/source.ts`](../../apps/portal/src/app/payouts/source.ts) correctly returns `unavailable`, and Next successfully bakes *that* screen into an artifact and serves it to every trader afterwards.

**So the render mode of the payout centre was decided by whether an environment variable happened to be set in the build environment.** That is not a property any screen should have, and least of all this one.

[`accounts/page.ts`](../../apps/portal/src/app/accounts/page.ts) had already written the argument this segment was missing, in its own words: `M04` section 1.2's *"no client-side cache of a money number survives a navigation"*, and a statically rendered money screen is *"`FM-M4-03`'s shape arriving through a build step rather than through a query"*. **The same paragraph that justified the declaration on `/accounts` condemns its absence on `/payouts`, and nothing connected the two.**

After the change the build prints `/payouts` dynamic. **The route count is twelve on both sides.**

**[`test/route-rendering.test.ts`](../../apps/portal/test/route-rendering.test.ts) makes it mechanical, and the predicate is derived rather than an allowlist**: a page must be dynamic exactly when its transitive relative-import closure inside `src/` reaches [`src/http/client.ts`](../../apps/portal/src/http/client.ts). That exempts [`app/page.tsx`](../../apps/portal/src/app/page.tsx), which reads no trader data, **on a measurement rather than on a name in a list where the next static money screen could be added quietly**.

**Three seeds fired.** Dropping the declaration from `/payouts`, dropping it from `/accounts`, and **blinding the closure walk**. The third is the one worth having: it is the vacuous pass, where a walk that resolved nothing would make every page look like it reads nothing and assert nothing at all, and the acceptance assertion on the count of routes reaching the client is what catches it. The protocol asks for exactly that and it was the seed that justified writing one.
