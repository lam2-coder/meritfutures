### 3. The three legs, and the two refusals

`gates` is `resolveExternalGates` over the **raw** columns, on `gatesOf`'s shape in [`eligible-next-7d.ts`](../../apps/api/src/admin-source/eligible-next-7d.ts): the whole kyc chain rather than a head, every payout status rather than a filtered set, and `accounts.status` un-narrowed so the seven-versus-six question stays answered in one file. `plan` reads the account's own pinned version on the catalogue door and decodes `rules` with the engine's decoder; **the decoded value is discarded and the decode is still the point**, because what it buys is the refusal of a document this build cannot read.

`state` refuses because a backend must call `ruleStateOn` and must not fold a state in the request path, and because where `RuleStateAbsent` may escape from is [ADR-285](../decisions/ADR-285.md) ruling 4's ordering, which is slice 5's stop condition. `subject.plan.size` refuses because nothing in this repository decodes a `PlanVersionSizeRow` and **no cast stands in for one**.

### 5. The one file outside the fence, reported rather than buried

[`rule-state-producibility.test.ts`](../../apps/api/test/rule-state-producibility.test.ts) looped over `['subject', 'holdFlag', 'listPayouts']` requiring `payout-backend.ts` to contain `new PayoutBackendUnwired('<member>')` for each. **That assertion and this row's stop condition cannot both hold**: the stop condition is that the two legs refuse by name *and not through the member's blanket rejection*, and the assertion requires the blanket rejection's exact text.

The row says STOP AND REPORT where the fence and the stop condition conflict. **This session made the minimal edit and reported it**: the plain refusal asserted absent, the two leg names asserted present, on the precedent `insertPayoutRequest.hold` set ten lines below in the same case, recorded here, in the ALLOCATION row and in [ADR-306](../decisions/ADR-306.md) section 6.

**THE DISPATCHER GRANTED THE EXTENSION AND NAMED THE FENCE AS ITS OWN ERROR.** It read both primary sources first rather than this log's account of them: that the retired assertion required the blanket refusal PRESENT while the stop condition requires it ABSENT, and that the replacement transcribes the precedent below it. One assertion became three; the property strengthened. `rule-state-producibility.test.ts` is inside row `306`'s fence for that assertion and should have been from the start. **Whether these three lines were allowed is settled and is not a founder's question.**

**LANDMINE FOR SLICES 5 AND 9: CARRY THIS FILE INSIDE THE FENCE UP FRONT.** Its needles are by construction whatever `subject()` cannot yet answer, so **every row that shrinks the remainder moves that assertion**, and by slice 9 every needle it asserts is gone. A dispatch that omits it repeats this conflict and puts the next session in the position this one was. What remains genuinely open, and [ADR-306](../decisions/ADR-306.md) section 8 states it, is whether the case should keep tracking the remainder this way at all or be rewritten as an assertion about the refusal SET.

[`db-recorder.ts`](../../apps/api/test/db-recorder.ts) was the second file and it was **not** touched: it carries one `rows` array for every table and no catalogue verb, so the payout suite got its own per-table fixture instead of a diff on five suites' shared one. Consolidating them is a declared debt.
