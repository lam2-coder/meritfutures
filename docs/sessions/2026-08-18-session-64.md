- **Landmines:**

  - **THE PROPERTY PASSED WITH THE MUTANT SEEDED, AND FINDING THAT OUT IS THE ENTIRE VALUE OF THE TRAP.** The seeded violation is `falsify-ci.mjs`'s own named `R-43` case, the clamp losing its cap term, and the first version of this suite did not notice. **`CME_WINDOW` is five days**: `fundedPrior` opens on its first, leaving four foldable ones, so the directed run's profit topped out at `4 x 50,000c` and the withdrawable reached **exactly** MERIT-RAPID's `100,000c` cap and never passed it. `approved <= cap` held **by equality on every case**, and a clamp with no cap term is indistinguishable from one that has it. **A bound only ever met at equality is a bound no test can watch being removed**, and a suite that never crosses it reports green forever. Widening to twenty-four days fixed it and fast-check shrank the case to the cent: withdrawable `100,001c`, request `100,001c`, both one cent over the cap.

  - **HAD THE MUTANT NOT BEEN RUN, THIS FILE WOULD HAVE SHIPPED AS A PASSING TEST OF NOTHING.** It type-checked, it was green, its counters were non-zero, and the three clauses read correctly. **Every signal available without seeding a violation said it worked.** That is the argument for the trap being a required step rather than a diligence flourish, and it is the same argument [ADR-038](../decisions/ADR-038.md) makes about `CI-03`'s polarity.

  - **THE FREE GENERATOR REACHES ELIGIBILITY ZERO TIMES, AND THAT WAS MEASURED RATHER THAN ASSUMED.** Across 240 runs over two plans, `daySequenceArbitrary` produced **no** eligible state. Reaching eligibility needs win days, the buffer, consistency and the minimum to pass at once, which random P&L does not stumble into. The directed profitable run supplies **the entire eligible side**, so a suite built only on the free generator would assert clause 3's antecedent-false branch forever. The counters are asserted `> 0` inside the suite, which turns "both sides are covered" from a claim in a log into a thing that goes red when it stops being true.

  - **CLAUSE 3 PROVES LESS THAN ITS WORDING AND THE TEST SAYS SO IN ITS OWN COMMENT.** Over `approvedCents` it is a **tautology**: `clamp.meetsMinimum` is *defined* as `approvedCents >= minPayoutCents`, so a disjunction phrased over it can never fail. Asserted over `maxPayoutCents` instead, where it is a **duplication-drift detector** and not an independent check of `R-39` against the clamp -- the two are the same arithmetic written twice. Writing that down was not optional: [ADR-038](../decisions/ADR-038.md) exists because a merge-blocking stage claimed more than it proved, and a property overstating its reach is that defect wearing a different hat.

  - **`GS-042` SETTLED THE READING AND STOPPED THIS SESSION PROPOSING AN `EC-nnn` IT DID NOT NEED.** STRATEGY line 67's "the result is `>= min_payout_cents` **or the request is not eligible**" looks false of this engine over `approvedCents`: a 1-cent request on a fully eligible account approves 1 cent. `GS-042` states that exact case in the corpus's own words -- "a supplied `1` clamps to 1 and **fails the minimum gate** rather than paying 1 cent" -- so "not eligible" means the **request** is refused, the line is true as written, and there is **no doc-versus-code disagreement to escalate**. The reading was about to be recorded as a proposed edge case; **the primary source dissolved it instead**, which is cheaper than a registry entry and did not spend an identifier the registries owe to sessions 66 and 70.

  - **REPORTED AND DELIBERATELY NOT FIXED: `payable` IS COMPUTED TWICE ON THE MONEY PATH.** [`gates.ts`](../../packages/rules-engine/src/payout/gates.ts) builds `capForOrdinal(funded, ordinalForNextPayout(state))` then `withdrawable < cap ? withdrawable : cap` to feed `minimumAmount.pass`; [`evaluate.ts`](../../packages/rules-engine/src/payout/evaluate.ts) builds `clamp.capCents`, the **same call**, then the **identical ternary** to feed `maxPayoutCents`. **Two expressions of one concept, agreeing until they do not.** That is the class `OQ-P1-04` ruled, and the transferable half of that ruling was **one predicate both callers use**, not two kept in sync. Nothing in the tree records it and no gate can see it. **Not fixed here**: `src/` is outside this session's fence and a shared predicate on the payout path is its own money-path session.

  - **THREE HELPERS ARE COPIED AND THE FENCE IS WHY.** `materializedFrom`, `toEngineMark` and `sliceOf` are duplicated from [`floor-monotonicity.property.test.ts`](../../packages/rules-engine/test/floor-monotonicity.property.test.ts) because this session may create files under `test/` and may not edit them while sessions 62 and 63 fold concurrently, and lifting them into a shared module means editing that file to import it. **Recorded in the new file itself**, so the duplication reads as a fence cost rather than as an oversight by whoever next opens it.
