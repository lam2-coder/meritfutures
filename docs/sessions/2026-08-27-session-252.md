### 2. So what does `ADR-140` rule, given the question it was reserved for is answered

**The residue, and it is what actually stops the route being writable.** `G-ELIGIBLE` names eleven terms. Two of them can be evaluated by nothing in this tree, and the corpus already routes one of the two to its own error code:

| Term | An `ExternalGates` field? | A cell in `EligibilityResponse.gates`? | Its refusal today |
|---|---|---|---|
| `identities.status = 'active'` | **NO.** Five fields at [types.ts:905](../../packages/rules-engine/src/types.ts) and none is it | **NO.** Ten keys at [API_CONTRACT:445](../architecture/API_CONTRACT.md) and none is it | **UNRULED. This is `ADR-140`** |
| `G-NO-IN-FLIGHT` | Yes, `hasPayoutInFlight` | **NO** | Already ruled: `PayoutEvaluation.noPayoutInFlight`, *"reported separately because API_CONTRACT's `gates` has no slot"* |

**The second row is the precedent the first one needs.** The engine already met this exact shape, for a different term, and answered it by reporting the verdict beside the breakdown rather than inside it. The identity-status term has no evaluator at all, so it cannot even be reported beside one.

> **THE RULING `ADR-140` WILL CARRY.** The identity-status term of `G-ELIGIBLE` is enforced by the route as a **named refusal evaluated before the account is read**, answered `identity_restricted` **422**, and it is **never expressed as a gate result**: no eligibility snapshot, no gate breakdown, no `payout.blocked`. It refuses **`closed` as well as `restricted`**, because the ruled predicate is `= 'active'` and not an enumeration of what is refused.

**Four supports, each a primary source rather than a preference:**

1. **The engine cannot evaluate it.** `ExternalGates` is `accountStatus`, `kycState`, `payoutsFrozen`, `reconBlocked`, `hasPayoutInFlight`. Handing `evaluatePayout` an identity status is a widening of a money-path contract three modules render, and it is not this session's.
2. **The contract has nowhere to report it.** A refusal shaped as `payout_not_eligible` carries *"the full gate breakdown"* ([API_CONTRACT:490](../architecture/API_CONTRACT.md)), and the breakdown has no cell that could carry this one. The client would render a refusal with every gate passing.
3. **`INV-M5-23` is the same placement argument one refusal over.** [M05](../plans/M05-payout-system.md) rules that the impersonation refusal sits *"before section 1.1's first step ... Nothing about the account is read, because reading it is the act being refused"*, on the ground that routing a non-eligibility refusal down the eligibility path *"would put a false eligibility story on a real account"*. A restricted human is not a trader who did not qualify either.
4. **The code already exists.** [API_CONTRACT:86](../architecture/API_CONTRACT.md): *"checkout, payouts, wallet spend, external withdrawal and affiliate settlement all refuse with this one code rather than with five near-synonyms."* The canonical code table is closed, so inventing a sixth spelling is a ruling nobody took.

**What I leave to session 247 and say so.** `ADR-067`'s eligibility question (`OI-18`, `OQ-F3-01`, `OQ-F3-02`) is whether a manual adjustment enters the payout-eligibility computation. **Nothing in `ADR-140` touches it.** This route calls `evaluatePayout` and reports what it returns; whatever 247 rules changes what that function is handed, not where this refusal sits.

**The residual imprecision, recorded rather than smoothed.** `identity_restricted`'s own name says *restricted* and a `closed` identity is not restricted. The `detail` string carries the fact; the code cannot, because the table is closed. `ADR-140` will carry an `OQ` for whether the contract should gain a distinct code, owned by whoever holds [API_CONTRACT](../architecture/API_CONTRACT.md).

### 3. The ordered behavior, which is [API_CONTRACT:496](../architecture/API_CONTRACT.md)'s sentence with the gates put where section 2 puts them

| # | Step | Refusal it can produce |
|---|---|---|
| 1 | Declared factor, applied by `auth.ts`'s `endpointHandler` | `401 unauthenticated` |
| 2 | `Idempotency-Key` present | `400 validation_failed` |
| 3 | Body validated: `amount_cents` optional, integer, positive | `400 validation_failed` |
| 4 | `beginIdempotent` over the RAW bytes | `409 idempotency_key_reuse`, `409 conflict`, or a verbatim **replay** |
| 5 | **`identities.status = 'active'`. The account is not read** | `422 identity_restricted`. **`ADR-140`** |
| 6 | The account resolves through the caller's own scoped handle | `404 not_found` |
| 7 | `evaluatePayout(state, plan, {gates, requestedCents})` | |
| 8 | `noPayoutInFlight` | `409 conflict` |
| 9 | `eligible`, and `approvedCents >= minPayoutCents` | `422 payout_not_eligible` + the breakdown |
| 10 | `G-HOLD-REQUIRED`: an unresolved severity `>= 4` flag | **`200 held_pending_review`. Not an error** |
| 11 | Otherwise: persist, post `LT-01`, respond `approved` | |
| 12 | `completeIdempotent` | |

**Step 9's second clause is the route's and not the engine's.** `MinimumAmountGate` is an ENGINE gate computed at day advance over `min(withdrawable, cap)`; it has never seen the caller's `amount_cents`. [API_CONTRACT:496](../architecture/API_CONTRACT.md) requires that *"a supplied amount that clamps below the minimum returns `payout_not_eligible` with `minimum_amount` failing, never a partial payment and never a denial"*, so the route conjoins `approvedCents >= minPayoutCents` onto that cell and the conjunction is written at the projection.

**Step 10 posts NOTHING**, which is `INV-M5-21`: *"A held request has posted nothing. No ledger transaction, no wallet credit, no anchor advance, no win-day reset."* Every money field is still populated, per [API_CONTRACT:492](../architecture/API_CONTRACT.md), because the decision is computed and frozen at request time.

**Step 11 posts `LT-01` through [`packages/ledger`](../../packages/ledger/src/index.ts) and this route contains no ledger arithmetic.** `LT-01` is debit `trader_withdrawable` `approved_cents`, credit `trader_wallet` `trader_cents`, credit `fees_revenue` `firm_cents` ([M05 section 2.1](../plans/M05-payout-system.md)). It is built with `transfer()` and `posting()` and written with `postTransaction`, so the imbalance is unrepresentable by construction ([ADR-104](../decisions/ADR-104.md)).

### 4. `SECURITY:45` `C-27`, and which of its three actions this route is

**`C-27` names three sensitive actions: payout destination change, contact change, external withdrawal.** A payout REQUEST is **none of them**, and the answer is checkable rather than argued:

- [API_CONTRACT:797](../architecture/API_CONTRACT.md) rows a destination change at `passkey or dual_channel`, and [M05 section 3.6](../plans/M05-payout-system.md) records that **no destination route exists**: *"`grep destination` over API_CONTRACT returns three hits and none of them is a route."* Mine is not that route.
- [API_CONTRACT:800](../architecture/API_CONTRACT.md) rows external withdrawal at `passkey or dual_channel` and names **both** legs it covers: *"the payout external leg and the wallet withdrawal"*. The external leg is `POST /wallet/withdrawals`, `SD-M5-06`'s separate object. Mine is the INTERNAL leg.
- [API_CONTRACT:490](../architecture/API_CONTRACT.md) states this endpoint's own factor in terms: **`Auth: session, owner`**.

So `required: 'session'`, `c27` unset, and **the money does not leave Merit on this route**: `LT-01` moves the trader's claim into the trader's own wallet position. Cash derecognizes at `LT-02`/`LT-07`, behind `C-27`.

### 7. The refusal tests, which are the deliverable

**A guard that refuses everything passes every refusal test** ([`DELTA_MANIFEST`](../../packages/db/DELTA_MANIFEST.md) section 13). So every refusal below is paired with the one case that ADMITS, from the same fixture, and the pair is what is asserted.

| # | Refusal | Its paired admission |
|---|---|---|
| 1 | A `restricted` identity is refused `identity_restricted` | The same request on `active` returns `approved` and posts `LT-01` |
| 2 | A **`closed`** identity is refused the same way | as above. **This is the witness `ADR-140` turns on** |
| 3 | An identity naming ANOTHER identity's account gets **404**, and `GET /payouts` returns **zero rows** | The owner gets the account and a non-empty list from the same store |
| 4 | An ineligible account is refused `payout_not_eligible` with the breakdown | An eligible one is approved |
| 5 | A supplied `amount_cents` clamping below the minimum is refused with `minimum_amount` failing | A supplied amount above it is approved AT THE SUPPLIED AMOUNT |
| 6 | A second request while one is in flight is `409 conflict` | The first one succeeded |
| 7 | A replayed key returns the first response **verbatim**; a changed body is `409 idempotency_key_reuse` | The fresh key ran and stamped |
| 8 | A severity-4 flag holds the request | Without the flag the same request approves and posts |

**And the negative control on the refusals themselves**: the identity-status door is asserted to be evaluated BEFORE the account is read, by refusing a `restricted` identity naming an account that does not exist and getting `identity_restricted` rather than `404`.

**No float appears anywhere in this path**, including in a fixture. Money is `bigint` inside the file and a JSON integer on the wire, and the two conversions refuse rather than round.
