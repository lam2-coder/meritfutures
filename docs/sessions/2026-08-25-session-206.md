### 2. `events` is the hit both plans share and it was refused in both

Both plans read `events` heavily -- M14 derives loyalty state from the event stream (INV-M14-03) and M15 sources every announcement from one (INV-M15-04) -- and it is the table most likely to look available to a session holding either plan.

**Its refusal already stands at [`scope.ts:157`](../../packages/db/src/scope.ts) and nothing here reopens it.** `identity_id uuid NULL` and `account_id uuid NULL`, no CHECK tying them and neither required, so an `owned` rule on the first drops every account-level row and a `derived` hop through the second drops every identity-level one; the `jsonb` payload names a DIFFERENT identity inside `kyc.dedupe_hit` and `identity.merged`, which no scope rule can express.

**Registering it would have made this seven of seven rather than five of five**, and it would have been the wrong answer twice. **The count that is smaller because a refusal held is the count worth reporting.**

### 3. `loyalty_criteria` is `firm` because the promise belongs to nobody until it is earned

[`0023_loyalty_and_graduation.sql`](../../packages/db/migrations/0023_loyalty_and_graduation.sql) gives it `benefit_code`, `version`, `title`, `criteria_spec`, `terms_body_mdx`, `expiry_rule`, `breaks_on`, `effective_from`, `superseded_by` and `created_at`, and **not one of the ten is an identity or reaches one**.

**THE DIRECTION OF THE EDGE IS WHAT DECIDES IT.** `loyalty_benefit_grants` cites `(benefit_code, criteria_version)` and carries `identity_id` itself, so ownership flows FROM the grant. A `derived` rule the other way would hand every trader the whole published catalogue, which is not a smaller version of the catalogue.

**It is `statistic_definitions`' reason applied to promises rather than to statistics**, and 0023's own `COMMENT ON TABLE` says so. A superseded row stays firm for exactly as long as a live one, because INV-M14-07 and INV-M14-09 exist to keep what a past trader was promised readable after the criteria move.

**Two shapes transcribed rather than repaired.** The grain is `(benefit_code, version)` and is the whole primary key, so the table has no `uuid` of its own -- which is `price_floors`' shape and has the same consequence: `offers.criteria_version` is a bare `integer` that cannot address a row here. And `superseded_by text NULL` names a successor CODE with no foreign key at all, so it cannot address the pair either.

### 4. `loyalty_states` is `owned` on `identity_id`, and the identity grain is a ruling rather than a convenience

`identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT` is on the row and **it is the only column that reaches a person**. Every other column is a counter.

**INV-M14-12 is why there is no account column here to be tempted by**: cross-account loyalty is computed at the identity grain, from completed ladders. So this table has no `accounts` hop available and needs none, which is the opposite of `graduation_benefits`, where two paths exist and the direct column is chosen over the join.

**The composite primary key `(identity_id, as_of_trading_day)` is a history and not a second owner**, which is `analytics_snapshots`' and `daily_marks`' shape: one state per identity per closed day, and the day contributes nothing to who may read it.

**`inputs_digest bytea NOT NULL` is the tamper indication** and is transcribed as the custom `bytea`. Recompute, compare, and a mismatch is a finding -- which is what INV-M14-03 buys, and it is why the table stores a derivation rather than a balance: an admin cannot grant a tier, only correct the inputs, which is an audited act with a different name.

### 5. `loyalty_benefit_grants` is `owned`, and its composite foreign key is this session's trap

`identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT` is on the row, which is `promotional_credit_grants`' shape and its reason: a grant is a named person's entitlement from the moment it exists.

**THE TRAP IS `loyalty_benefit_grants_criteria_fk`.** It points at `loyalty_criteria (benefit_code, version)`, `loyalty_criteria` is FIRM, and `DerivedRule.via` is typed `TableKey` and includes every firm key -- so a `derived` rule through it compiles at every call site and throws the first time anybody reads the table. **It is the sharper form of the trap because the foreign key is real**: unlike `simulation_runs.requested_by`, which is bare text naming nothing, this is a declared constraint that a reader can verify exists.

**It is also a TWO-COLUMN edge against a `DerivedRule` that names one column**, so the rule could not have been written truthfully even had the parent carried an identity.

**`consumed_ref uuid NULL` is the second trap and it is polymorphic.** 0023 declares it as an M17 offer id OR an M03 purchase id with no foreign key, because it is two kinds; the single-spend guarantee is `loyalty_benefit_grants_consumed_ref_uq`, a partial unique index, rather than a reference. A bare `uuid` naming two possible parents reaches neither.

**A revoked grant is still this identity's row.** `loyalty_benefit_grants_revocation_is_explained` ties `revoked_at` to a reason and `loyalty_benefit_grants_not_both_consumed_and_revoked` refuses the row that was both spent and withdrawn. INV-M14-09 forbids retroactive withdrawal in both directions, and a disappearance is how that promise gets broken quietly.

### 6. `discord_links` is `owned`, and the second half of its primary key is a foreign platform's key

`identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT` is the table's only reference. **A LINK IS A CONSENT AND CONSENT IS THE PERSON'S.**

**The primary key is the pair `(identity_id, discord_user_id)` and the second half names no row here.** `discord_user_id text NOT NULL` is Discord's key, not Merit's: it is not a hop, not an owner, and not a grain the way a trading day is on `loyalty_states`.

**`role_opt_ins text[]` is per-role consent** (INV-M15-01) rather than a boolean, because a role is a public statement about a person and consent to be in a server is not consent to be labeled in it. **`link_nonce_hash bytea NOT NULL`** is stored hashed so a stolen database yields no live link tokens, and it is declared as the custom `bytea` rather than approximated.

**`revoked_at` is the end state and the row survives it.** `discord_links_live_discord_user_uq` is partial on `revoked_at IS NULL`, so revocation frees the Discord account rather than deleting the record, and a scoped read returns revoked links as the trader's own history.

**One sentence in the rule exists to be read as a boundary rather than as an implementation.** INV-M15-03 forbids this link from ever being an authentication factor, a recovery path or a support-verification method, and **its enforcement is structural, by grant, outside this package entirely**. Registering the table makes it readable and nothing else ([ADR-092](../decisions/ADR-092.md) section 9), and the `why` says so rather than letting a later reader take the registration for the control.

### 7. `discord_announcements` is `firm` because the row is Merit speaking to a room

[`0019_notifications_and_community.sql`](../../packages/db/migrations/0019_notifications_and_community.sql) gives it `id`, `event_id`, `template_code`, `channel_id`, `rendered_body`, `posted_at`, `provider_message_ref` and `created_at`. **No identity column, and no correct one**: a post to a public channel is addressed to the ROOM, so a per-identity slice of it is not a smaller version of it. The trader-facing row for the same fact is the `notifications` row, which carries the identity and is already registered.

**`event_id bigint NULL REFERENCES events(id) ON DELETE RESTRICT` is the one column that looks like a path and it is not one, twice over.** `events` is unregistered and deliberately so, and this column is NULLABLE besides -- a status post has no causing event -- so a derivation through it would drop exactly the announcements nobody's event caused. **`integration_dispatches.event_id` is the same column with the same treatment one migration earlier**, and it carries no `.references()` either.

**Announcements are template-only.** `template_code text NOT NULL` means there is no free-text send path using the bot credential (INV-M15-04), and `rendered_body` is STORED rather than re-rendered, so what was said stays a fact about the past after the template moves.
