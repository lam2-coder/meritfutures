### 1. Both dispatch premises were re-derived, and the measurement is the reason the screen looks like this

**The dispatch said to measure twice and named the two sessions that had been dispatched at screens which already existed.** Both premises held.

`pnpm --filter @merit/portal build` printed fourteen routes before a line changed, which is the number the dispatch gives. **Then every page file behind every one of those routes was read**, because session 375's finding was not that a count was wrong but that a path named `/` rendered something other than what the dispatch assumed. `app/page.tsx` is the error-vocabulary screen and says so in its own first line; `app/security/page.ts` is `SC-M4-11` and `app/wallet/page.ts` is `SC-M4-10`. **No route rendered an auth surface**, and the root page said in rendered copy that "Sign-in is not built here yet".

**What decided the shape of the screen was the second measurement, and it is the one the dispatch asked for by name.** All four routes behind `SC-M4-01` are REGISTERED, read from `CompositionReport.registered` over a real `compose()` on the `public` surface:

| Route | Registered | Wired |
|---|---|---|
| `POST /auth/otp` | yes | **no**, `requestOtp` is blocked on `NO_DELIVERY` |
| `POST /auth/verify` | yes | the email arm only; the `sms` arm raises |
| `POST /auth/passkey/login/options` | yes | **no**, `NO_WEBAUTHN` |
| `POST /auth/passkey/login/verify` | yes | **no**, `NO_WEBAUTHN` |

**A ROUTE TABLE OR A GREP WOULD HAVE REPORTED THIS SCREEN AS FULLY SERVED**, which is the dispatch protocol's section 5 in its sharpest form so far: registration and wiring are different questions, and here the difference is the whole answer.

`NO_DELIVERY` is the one that decides the screen: *"nothing in this deployable delivers a code. A handler that writes an `otp_challenges` row and answers `sent: true` having sent nothing is a worse answer than 503."* So the honest state of the screen is that the code cannot be sent yet, and the screen says that rather than drawing a flow around a 503.

### 2. Three things the screen must not do, each asserted rather than intended

**No password field, no reset link, no recovery step.** `0002` states it on the table where a password would have to live: *"Merit is passwordless only, so THERE IS NO PASSWORD TABLE ANYWHERE IN THIS SCHEMA, by design"*, and `M04:80` states the consequence for this screen. **The screen says so BY ITS SHAPE and carries no sentence about it**, which is a decision worth naming: a screen carrying "Merit does not use passwords" is a screen where the next builder adds the field and edits the sentence, it puts the word on the page that every phishing template is built around, and it would put the word out of reach of the blunt assertion. The suite fails on the word itself.

**`sms` is never offered as a way to sign up.** `ADR-196` clause 5 rules `is_new` always false on that channel and says the ruling is *"derived, not chosen"*: `0002` declares `users.email citext NOT NULL UNIQUE`, so an SMS verification for an unknown number has no value to write. **Email is therefore the only door into Merit**, `passkey` is refused for a different reason -- API_CONTRACT section 3 says registration *"requires a session"*, so it presupposes the account it might otherwise have made -- and the flag lives in the view model with a suite tying the copy to it, because two places stating one fact is where `M04:265`'s drift starts.

**No separate create-account control.** `ADR-196` section 3 refuses that surface in its own words: *"the sign-up is a branch inside a handler that already exists in the contract, not a surface of its own."* Drawing two controls would draw the refused surface, and it would also DISCLOSE: a person choosing between "sign in" and "create account" learns from the outcome which one applied to their address.

### 3. The disclosure posture is structural rather than a property of today's copy

API_CONTRACT section 3 says `POST /auth/otp` *"deliberately does not reveal whether the destination exists"*, and `ADR-200` section 4 extends it to the verify route.

**`toSignInView` TAKES NO ADDRESS AND NO SUBMITTED VALUE OF ANY KIND.** There is no branch an existence check could be smuggled into, no copy that can vary with a destination, and no work whose duration could differ between a known address and an unknown one. **A test that checked two addresses produce the same copy would pass over a function that could still tell them apart**, so the property is taken structurally and the suite guards the shape instead: an exact key-set assertion over the view and over every factor, so a later `email` or `submitted` field is a red suite rather than a line nobody notices.

The screen also states the posture to the person it protects: *"The answer is the same whether or not you already have one."* A uniform answer that is never explained reads to the next builder as a bug worth fixing.

### 4. Two absences, kept independent, and the acceptance case is what proves they are

`served` is a property of `apps/api` and `submits_to` is a property of `apps/portal`, which has no verb but GET. **Both are false for all three factors today and they would stop being false on different days**, so collapsing them into one sentence would make the screen go quiet on the second the day the first landed. `submits_to` is typed as the literal `null` on the payout centre's and the session list's precedent, so wiring it is a type change a reviewer reads.

**The acceptance half drives the measurement to `served: true` for all three and watches the per-factor sentences disappear while the inert one survives**, with a negative control asserting the shipped screen and the driven one differ. A suite that only ever rendered the shipped constant would pass against a fixed page of apologies.

### 5. The route is STATIC, and the omission of `force-dynamic` is argued rather than left to look forgotten

Every other screen in this application carries `export const dynamic = 'force-dynamic'`. This one must not: `test/route-rendering.test.ts` derives the requirement from whether a page's transitive import closure reaches `src/http/client.ts`, and this page's does not. **`SC-M4-01` is PRE-IDENTITY**, so there is no session to read anything with and no trader datum to bake into an artifact, which is `app/page.tsx`'s position exactly.

**The exemption is only safe while it stays true**, so the suite walks this page's closure from this side too and fails on a client import. That is redundant with the acceptance count in `route-rendering.test.ts`, deliberately: the count fails on the arithmetic and this one names the file.
