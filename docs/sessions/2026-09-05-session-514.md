### 5. The discrepancy the row said to resolve rather than inherit

The row named a disagreement between [`schema.ts:521-522`](../../packages/db/src/schema.ts)'s `.notNull()` and [`checkout.ts`](../../apps/api/src/routes/checkout.ts)'s claim that `PurchaseInsert` types both `| null`.

**There is no disagreement, and finding it out took one `grep`.** `PurchaseInsert` is a hand-written interface declared once inside `checkout.ts`, used by one port method and one call, and it is not `typeof purchases.$inferInsert` or anything derived from the drizzle table. `schema.ts` transcribes the DDL, which is what `scoped-db.test.ts` compares it against, and the DDL said `NOT NULL`. **So the comment was accurate about `PurchaseInsert`, `schema.ts` was accurate about the DDL, and the two types never met.** Neither was stale; the row's suspicion that one of them was is the reason it was checked, which is the process working.

### 6. The ruling, in one paragraph

**A wallet-funded purchase is a purchase with no processor.** `psp` is *"which MID took it"* and no MID took it; `psp_reference` is a processor's own reference and no processor issued one. Both columns are ABSENT rather than unknown, and absent is what NULL means. The alternative, `'psp_a'` and a minted string on a row that reached no processor, is the state `FM-M3-01` pages on wearing a wallet purchase's clothes, and it is exactly what `SD-M3-06` exists to make unrepresentable.

```sql
ALTER TABLE purchases
  ALTER COLUMN psp DROP NOT NULL,
  ALTER COLUMN psp_reference DROP NOT NULL;

ALTER TABLE purchases
  ADD CONSTRAINT purchases_processor_columns_follow_method CHECK (
    CASE payment_method
      WHEN 'psp'    THEN psp IS NOT NULL AND psp_reference IS NOT NULL
      WHEN 'mixed'  THEN psp IS NOT NULL AND psp_reference IS NOT NULL
      WHEN 'wallet' THEN psp IS NULL     AND psp_reference IS NULL
      ELSE false
    END
  );
```

`0006`'s CHECK is left in place and carries the processor vocabulary; this one carries the method rule and restates nothing.

### 7. The three questions the row asked that are not the migration

| Question | Answer |
|---|---|
| **What happens to the idempotency anchor** | Nothing. It is not dropped, not recreated and not made partial; the only change is a `COMMENT ON INDEX`. Over nullable columns a btree unique index treats NULLs as DISTINCT, so wallet rows collide with nothing, **and that is correct because a row with no processor has no webhook to be duplicated.** [M03 section 6](../plans/M03-billing-checkout.md)'s matcher looks a row up by `(psp, psp_reference)` with a `psp` from the closed vocabulary, and SQL equality with NULL is never true, so wallet rows are invisible to it BY CONSTRUCTION. Their own idempotency is `INV-M3-13`: the row is `paid` in the transaction that creates it |
| **Whether a partial index states it better** | **No, and the reason is that it states exactly the same thing.** `WHERE psp IS NOT NULL` admits and refuses precisely the same rows as the index already on the table, so it is a restatement of the CHECK in a second vocabulary with nothing keeping the two in step, and its cost is dropping and recreating the object `0006` calls the anchor. The one thing it WOULD buy, immunity from a `NULLS NOT DISTINCT` rebuild, is bought by `ACCEPTANCE 2` instead, and an assertion also catches the `NOT NULL` coming back, which a partial index would not |
| **Whether `payment_method` is the discriminator** | **Yes, and the alternative is strictly weaker rather than merely different.** `CHECK ((psp IS NULL) = (psp_reference IS NULL))` states only the agreement and admits both the wallet row naming `psp_a` measured ACCEPTED in section 4 and a `'psp'` row naming no processor. Keying on the method refuses both AND implies the agreement, because every branch names both columns |
