#### 1.2 THE THREE CLOCKS ARE THREE DIFFERENT ACTS, AND THE THIRD IS NOT WRITABLE

`payout_requests_freeze_is_complete`, [`0031:62`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)'s
`payout_requests_hold_is_complete`, [`0011:176`](../../packages/db/migrations/0011_wallet.sql)'s
`wallet_withdrawals_freeze_is_complete`, and
[`0031:183`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)'s
`wallet_withdrawals_live_freeze_blocks_settlement`.

| Clock | What release MEANS | Ledger | Writable here |
|---|---|---|---|
| `payout_requests.hold_expires_at` | `held_pending_review` -> `approved`, ALL FIVE hold columns NULLed in the same statement, **and `LT-01` posts** | **POSTS.** `INV-M5-17`, `ADR-040`: a held request has posted nothing, so release means approve **and pay** | **YES** |
| `wallet_withdrawals.freeze_expires_at` | the three freeze columns NULLed, **`status` untouched** | **NOTHING.** `INV-M20-14`: the money is already the trader's, so release resumes the rail and never re-pays | **YES** |
| `payout_requests.freeze_expires_at` | `frozen` -> **`settled`** ([STATE_MACHINES:86](../architecture/STATE_MACHINES.md), `G-FREEZE-CLEARED`) | already posted at approval | **NO, and section 1.3 is why** |

**A sweep that treated the three identically would be wrong in the direction that looks correct**, which is
the sentence the suite exists to make false: it would either re-pay a withdrawal, or fail to pay a hold, or
collapse an orthogonal halt into a rail status, which is `SD-M5-06`'s named mistake.

#### 1.3 THE FREEZE LEG'S RELEASE TARGET IS `settled` AND `settled` IS UNWRITABLE BY ANY CODE IN THIS TREE

Not a fence problem. A tree problem, measured rather than assumed:

1. [STATE_MACHINES:86 and :150](../architecture/STATE_MACHINES.md) draw `frozen --> settled` under
   `G-FREEZE-CLEARED`, and [ADR-040](../decisions/ADR-040.md) states it in terms: *"`frozen` releases to
   `settled`, which is what a released freeze does under the wallet."* There is no `frozen --> approved`
   edge; writing one would be redrawing a machine, which is outside this fence and is the widening
   [ADR-159](../decisions/ADR-159.md) clause 4 refused for the same reason.
2. [`0010:151`](../../packages/db/migrations/0010_payouts.sql)'s `payout_requests_settled_has_days` makes
   `settled` require `settled_at`, `settled_trading_day` AND `effective_trading_day`, all three NOT NULL.
3. `effective_trading_day` is *"the FIRST TRADING DAY WHOSE OPENING BALANCE REFLECTS THE WITHDRAWAL"*
   ([`0010:96`](../../packages/db/migrations/0010_payouts.sql)). It is the exchange session calendar applied
   to an instant. **No trading calendar exists in this workspace** and `CLAUDE.md` keeps it as data.
4. [STATE_MACHINES:155](../architecture/STATE_MACHINES.md): *"Win-day reset and floor recompute happen on
   settlement."* That is `applySettlement`, `INV-M5-07`. **THIS SESSION CLAIMED NO SUCH FUNCTION
   EXISTS AND THAT WAS WRONG**: it is exported from
   [`packages/rules-engine/src/payout/settle.ts`](../../packages/rules-engine/src/payout/settle.ts).
   **The correction strengthens the conclusion rather than overturning it.** Its signature takes a
   `calendar: CalendarSlice`, and
   [`merit/no-calendar-in-expiry-path`](../../packages/eslint-plugin-merit/rules/no-calendar-in-expiry-path.js)
   bans that import in this path by glob under [ADR-042](../decisions/ADR-042.md) -- a rule whose own
   header names THIS SWEEP as the failure it was written for. So the leg is blocked by a checkable
   control rather than by an absence, which is the better reason. **The error class is the one
   [CLAUDE.md](../../CLAUDE.md) names: a failure to check a claim against the primary source.**
5. **Nothing in the application writes `frozen` at all.** `payouts.ts:963` writes `approved` or
   `held_pending_review` and no third value; `'frozen'` appears in `packages/db/src/schema.ts` as an enum
   member and nowhere else in `apps/` or `packages/` source. `G-FREEZE-DURING-FLIGHT`'s own row
   ([STATE_MACHINES:412](../architecture/STATE_MACHINES.md)) says why: under
   [ADR-019](../decisions/ADR-019.md) the internal leg is one transaction, so **`ADR-040` routed both
   remaining cases elsewhere** -- a flag at request time to the hold, a flag after wallet credit to the
   external leg's halt -- and the edge *"stays drawn because the state is reachable"*.

**So the third leg is SWEPT and REPORTED and not written.** The job scans it, counts it, and emits
`payout.freeze_expiring` for a freeze inside its twelve-hour warning lead, which is a producer
[EVENTS:255](../architecture/EVENTS.md) names for this exact job and which needs none of the four missing
things. A row actually PAST `freeze_expires_at` is returned as an `unreleasable` finding naming the three
columns and the two functions that do not exist. **Inventing a settlement instant, a trading day and a
win-day reset inside a sweep would be the sweep deciding what settlement is**, on the money path, in the
file whose whole purpose is that a clock binds Merit rather than the trader.

**This does not weaken `CI-06l`.** That gate asks that every `*_expires_at` column name a release job in
CRON_INVENTORY. All three still name this one job, the row is not edited to say otherwise, and the honest
count goes in the pull-request body: **three clocks swept, two released, one reported.**

#### 1.4 The read: `ADR-157`'s RANGE term, its `IS NULL` term, and its ROW lock

[ADR-157](../decisions/ADR-157.md) is why this slice is dispatchable at all. Two phases, deliberately:

```
SCAN  (one read per clock, at the sweep's own instant)
  rowsWhere('payoutRequests',    { status: 'held_pending_review', holdExpiresAt: atMost(at) })
  rowsWhere('payoutRequests',    { status: 'frozen',              freezeExpiresAt: atMost(at) })
  rowsWhere('walletWithdrawals', { freezeExpiresAt: atMost(at), settledAt: isNull() })

RELEASE (one transaction PER ROW)
  lockAt(key, { id })            <- ADR-157's rowAt + FOR UPDATE, tenancy conjunct attached
  re-read the precondition UNDER the lock
  write
```

- **`atMost` is INCLUSIVE and the bound is the SWEEP'S CLOCK, never the database's.** `ADR-157`'s own
  paragraph: rendering `now()` would put the database's clock in a money path and make every expiry test
  unwritable. The instant is a parameter, so a fixture pins it.
- **`isNull()` earns its place on the withdrawal read and nowhere else.** `atMost` already excludes a NULL
  clock, because `NULL <= x` is NULL and never matches, so `IS NULL` is not needed to find a live halt.
  `settledAt: isNull()` is `wallet_withdrawals_live_freeze_blocks_settlement`'s other half asserted on the
  READ, so the scan cannot even see a settled row. **`IS NOT NULL` does not exist and is not reached for**;
  `ADR-157` refuses it by name and the range term makes it unnecessary.
- **ONE TRANSACTION PER ROW, and that is `FM-M5-13` taken seriously.** The failure this job exists against
  is the sweep stalling and every hold silently becoming indefinite at once. A single transaction over the
  whole estate makes one bad row stall every other row; per-row transactions make it stall one.
- **The lock is a ROW lock and no advisory lock is taken.** `ADR-157` clause 4 and [P5](../plans/P5-payouts-and-wallet.md)
  and [P7](../plans/P7-risk-and-abuse.md) rule 10 refuse `pg_advisory_xact_lock` through `sqlExecutor` by
  name, because it carries no tenancy narrowing at all. **This sweep is the third door onto the hold
  transition and the operator's two are `admin-payouts.ts`'s**; the lock plus the re-read is what makes an
  operator releasing at 12:59:59 and the sweep firing at 13:00:00 produce one release rather than two.

#### 1.5 THE KEY DISCIPLINE, WHICH IS THE ONE THING THIS SESSION IS MOST LIKELY TO GET WRONG

`ledger_transactions.idempotency_key` is `text NOT NULL UNIQUE`. `payouts.ts:1010` posts under
`` `${PAYOUT_ENDPOINT} ${idempotencyKey}` `` and `admin-payouts.ts`'s `releaseLedgerKey` builds **the
identical string** rather than one naming its own endpoint, so `LT-01` for one payout request is ONE posting
whichever door reaches it and the database refuses the second.

**This sweep is the third door and it builds the same string.** `apps/worker` cannot import it:
`apps/worker/package.json` declares `@merit/rules-engine` and nothing else, and under `node-linker=isolated`
an undeclared import does not resolve at all; the manifest is not in this fence. So the constant is declared
here and **the suite BINDS it by reading `apps/api/src/routes/payouts.ts` and `admin-payouts.ts` as text**,
which is `packages/db`'s own idiom for binding `SqlExecutor` to `packages/queue`'s `JobTransaction` without
an import. A retyped constant that drifts is how one approval mints two postings, and the assertion is
mechanical rather than a comment asking a reader to check.

#### 1.6 The ports, and the two gaps they name rather than close

`apps/worker/src/sweeps/ports.ts` declares the boundary structurally, importing nothing, which is
`batch/ports.ts` and `provisioning/ports.ts`'s established idiom in this app.

1. **`ExpiryTx` is narrowed to two table keys**, not `TableKey`. `SystemTx.updateAt` reaches every table in
   the estate with one word; a sweep that accepted the same reach would spend `ADR-102`'s widening again for
   nothing, and a `SystemTx` is assignable to the narrower shape.
2. **`postLt01` is a PORT the wiring supplies**, exactly as `PayoutTx.ledger` and `AdminPayoutTx.ledger` are.
   Nothing here names a ledger account, writes a transfer or does ledger arithmetic: a second transcription
   of `debit trader_withdrawable / credit trader_wallet / credit fees_revenue` is `ADR-092` section 5's
   two-statements-of-one-fact hazard arriving on the money path. **NOTHING HERE ADDS A `SqlExecutorReason`
   MEMBER, ADDS A `SystemReason` MEMBER, IMPORTS `pg`, OR CASTS PAST A KEY TYPE.**
3. **`SystemReason` HAS NO WORD FOR AN HOURLY SWEEP, AND THAT IS REPORTED RATHER THAN FIXED.** It is
   `'nightly-batch' | 'operator-console'` and this job is neither. `P5` rule 10 says report it and stop
   rather than reach, and the reach here would be one word in a file this fence does not hold. So
   `ExpirySweepIo.transact` takes the unit of work and the WIRING decides the authority, which is
   `AdminPayoutBackend.operator`'s shape and its reason. **The sweep is unwired and refuses rather than
   inventing a handle**, on `UNWIRED_ADMIN_PAYOUT_BACKEND`'s stated ground: a backend returning plausible
   values would be a fixture paying real traders.
4. **The event sink is a port too, and it takes the transaction.** `ADR-006`'s criterion: the event commits
   with the release or not at all. Nothing in `apps/` writes an event yet and `P5-n` builds the producer;
   this file declares what it emits and does not invent a sink.
