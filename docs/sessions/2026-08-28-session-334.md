### 3. The three shapes, priced

**(a) TAKEN.** A trigger makes provisioning coextensive with the identity's existence: there is no path that creates an identity and skips it, because there is no path at all.

**(b) REFUSED ON A MEASUREMENT.** `grep -rni "insert into[[:space:]]*identities" --include='*.ts'` over `apps/`, `packages/` and `scripts/` returns **zero**. Every TypeScript reference to that table is a read, a lock, a scope predicate or a schema declaration. **A ruling placed there would be written against an absence** and section 2's defect would still be live the day it landed. Not refused forever: when the path exists it may take provisioning, and superseding a trigger is a later migration.

**(c) REFUSED TWICE, AND THE SECOND REFUSAL WAS NOT IN THE DISPATCH.** [`chart.ts:46`](../../packages/ledger/src/chart.ts) refuses it in shipped source with its reason stated, so taking it overturns a shipped design rather than filling a silence. **And [`tx.ts:64`](../../packages/ledger/src/tx.ts) declares `LedgerWriteKey` as `ledgerTransactions` and `ledgerEntries` only**, so `ledgerAccounts` is read-only on the handle a posting is written through and `postTransaction` **cannot** open an account at all. [`tx.ts:59-61`](../../packages/ledger/src/tx.ts) states the narrowing is the point. Lazy provisioning is not a small change to `chart.ts`; it is a widening of the one boundary that package holds against itself.

**The cost of (a), read from the catalog rather than from a grep.** Over `0001` through `0053` applied from empty: **21 non-internal triggers, 19 distinct functions, and not one function body contains an `INSERT`, an `UPDATE` or a `DELETE`.** Two bodies match the word `UPDATE`; both matches are inside error-message strings. **The dispatch's claim holds and the entry does not soften it.**

### 6. Two armed assertions fired, and neither was weakened

**6.1 [`chart-of-accounts-kinds.test.ts`](../../packages/ledger/test/chart-of-accounts-kinds.test.ts).** It asserted that every chart write is firm scoped and that no write carries `ON CONFLICT`. Its own comment gave the reason: *"A migration has no identity to seed against, so the three per-identity classes still have no writer at all, anywhere in this tree."* **`0054` needs no identity to seed against because it does not seed**, and that sentence is the finding this session exists to falsify.

The file now partitions **firm seeds** from **identity writes** on the `scope` literal the statement itself carries. Every original property is kept on the firm half unchanged, and the identity half gets the property the original was really holding: **no write names a literal identity**, the uuid comes from `NEW.id` or from a join to `identities`. A case asserting the partition is **total** is added, because a statement naming neither scope would otherwise escape both sets while the block stayed green.

**6.2 [`lt-07.test.ts`](../../packages/rail/test/lt-07.test.ts), and this session had to edit `packages/rail`.** That case *"asserted an empty list, ADR-177 filled it and ADR-180 extended it"*; this is the third step in the sequence [ADR-174](../decisions/ADR-174.md) section 7 built it for. Its probe assertions moved from naming two seeded fixtures to asserting the probe writes **no `ledger_accounts` row for an identity at all**, which is strictly stronger. **[ADR-181](../decisions/ADR-181.md) recorded leaving that package untouched as a result rather than an accident; this session cannot, and the fence question is in ADR-183 section 9 and its approval block on [ADR-177](../decisions/ADR-177.md)'s and [ADR-180](../decisions/ADR-180.md)'s precedent.**

### 7. The finding that came from running the probe rather than reading it

**`0054` reproduced [ADR-177](../decisions/ADR-177.md)'s defect one code down.** [`probe_ledger_constraints.sql`](../../scripts/db/probe_ledger_constraints.sql) seeded its two per-identity fixtures with **pinned uuids under `ON CONFLICT DO NOTHING`**. With `0054` applied, the probe's own `INSERT INTO identities` fires the trigger, the rows already exist, the clause skips, and the pinned uuid names nothing. The `LEDGER-C1` block then raised

```
LEDGER-C2: ledger_account aaaaaaaa-0000-0000-0000-000000000002 does not exist
```

**instead of probing `LEDGER-C1` at all**, which is what that file's own next paragraph describes happening to `fees_revenue`. **The zero-sum block had the identical defect on its own pinned row.** Both are repaired the way ADR-177 repaired `fees_revenue`: the ids are resolved from the chart through a temp view, with a `DO` block that raises if the row is missing. **And the provisioning itself is now probed**, because a mechanism nobody has watched run is a mechanism nobody knows is wired up, which is that file's first line. All three probes fire as expected on two independently built databases.
