### 1. Does a reconciliation run anywhere in this tree? No, and neither does the comparison

The dispatch required this before a line was written and required it measured. Every `.ts` under each app's and package's `src` was walked, at this commit, and the walk is [section 1 of the suite](../../apps/worker/test/recon-sweep.test.ts) so it is re-derived on every run rather than copied forward.

| Question | Answer |
| --- | --- |
| Modules writing `reconciliations` | **none** |
| Modules writing `reconciliation_runs` | **none** |
| Modules setting `accounts.recon_blocked`, in either direction | **none** |
| Adapters implementing `BatchWritePort` | **none** |

Every occurrence of the two tables in application code is a READ ([`admin-source/liability.ts`](../../apps/api/src/admin-source/liability.ts) folds open mismatches, [`routes/internal.ts`](../../apps/api/src/routes/internal.ts) renders them) or a REGISTRATION ([`scope.ts`](../../packages/db/src/scope.ts), [`schema.ts`](../../packages/db/src/schema.ts)).

**`BatchWritePort.raiseReconciliation` is the mistake this slice was most likely to make**, and it is not this. [`batch/ports.ts`](../../apps/worker/src/batch/ports.ts) declares it for `DO-3` -- *"A failure does not throw: it returns an `AssertionFailure`, the batch raises reconciliation, and NO STATE IS WRITTEN FOR THE DAY"* -- which is the fold REFUSING TO RUN. This file is the comparison that runs after a fold succeeded and then disagrees with it. That file draws the identical line one register over between reconciliation and replay divergence, and its header says of the sibling port that no adapter implements it yet.

**So a producer that wrote only the run row would have made `integrations.recon.last_run_at` truthful and the panel useless**, which is the shape the dispatch named. The honest slice was both halves and the entry says which is which: the run record is `0064`'s and was owed; the comparison is new.

### 3. The two sides, and why the pair is not a tautology

`our_source` is **`'rule_state'`**, the only one of `SD-M2-06`'s two this deployable can reach; `@merit/ledger` is not in `apps/worker/package.json` and under `node-linker=isolated` an undeclared specifier does not resolve, which is the wall session 379 met in front of `ExpirySweepIo.ledger`. The type is the single literal rather than the union, so the slice that acquires the ledger meets a compile error rather than a field it can leave alone.

The platform's side is the LIVE `daily_marks` row's `closing_balance_cents`, and **only** when that mark's `source` is `report` or `api`.

**The circularity objection is real and it is answered by the supersession rule.** `packages/rules-engine/src/day/advance.ts` sets `balanceCents: mark.closingBalanceCents`, so on the day the fold ran the two sides agree by construction. They come apart exactly when a correction has landed: `0014` ruling 2 makes a correction a NEW ROW pointing the old one at it, never an UPDATE, and `daily_marks_live_per_account_day_uq` is `WHERE superseded_by IS NULL`. A stored state folded from a superseded mark disagrees with the live one by exactly the correction, which is `FM-M2-08` arriving through the mechanism `0014` built for it.

**What the pair cannot see is named rather than left to be discovered**: a vendor number that was wrong when it arrived, was ingested and was folded agrees with itself here and always will, and catching that needs the ledger derivation. `INV-M2-08`'s setpoint reconciliation, which `ST-M2-8` names in the same breath as this one, is a different subject and is not built.

### 4. Three outcomes, and the two controls that are the producer's rather than the database's

**`uncomparable` is the arm that keeps the panel honest.** A `recomputed` mark is Merit's own number, so comparing it would compare Merit with Merit and write a `match` that means nothing whatever -- a clean bill of health for exactly the accounts whose vendor number never arrived. An account with no rule state has no number to offer. Neither writes a row, neither counts toward `accounts_done`, and `reconciliation_runs_completed_is_whole` then does the rest by itself.

**An empty population closes `failed`, and this is the hole the database cannot close.** The completion control is `status <> 'completed' OR accounts_done = accounts_total`, and **at `0 of 0` it is satisfied vacuously**. A night whose ingest never landed produces no live marks, and a producer that closed that run `completed` would write the row `0064`'s own reasoning warns about one column to the left: *"a sweep over zero accounts is indistinguishable from a sweep that never looked"*. `accounts_total > 0` is not a constraint `0064` carries and adding one is a superseding migration this fence does not hold, so the producer refuses instead. The run row still exists, and `reconciliation_runs_unhealthy_idx` puts it in front of the morning read.

**The block is set and is never cleared.** `0014_marks.sql`: a mismatch *"sets accounts.recon_blocked = true and blocks eligibility until a HUMAN resolves it"*, which `M01`'s `FM-04` and `M02`'s `ST-M2-8` both state as the response. The finding and the block commit in ONE transaction, because a mismatch row without the block is an account excluded from nothing and a block without the row is an account nobody can explain. The second half is implemented by writing no `accounts` value at all on a match, so a sweep can never lift a block an operator has not looked at; the type cannot forbid it and the suite walks every committed value instead.

### 5. Executed, and the execution found a blocker the plan did not have

PostgreSQL 16.13, all **60** migrations under `ON_ERROR_STOP=1`, **115** tables, **401** indexes, **25** triggers. Run through `LIVE_DB.batch` with `isNull` from the real accessor behind `ReconTerms`, over a seeded book of five accounts.

| Sweep | Result | Row |
| --- | --- | --- |
| `2026-08-26`, four accounts, one of each outcome | `2/4` | **`failed`** |
| `2026-08-27`, one agreeing account | `1/1` | **`completed`** |
| `2026-08-28`, empty population | `0/0` | **`failed`** |
| `2026-08-26` again, the `RB-02` redelivery | `2/4` | `failed`, and the comparisons **UPDATED** |

Four sweeps, **four run rows and three `reconciliations` rows**. The mismatch reads back `our_balance_cents 5000000`, `platform_balance_cents 4999950`, GENERATED `delta_cents 50`, `status mismatch`, `our_source rule_state`, naming its ingest file. **Exactly one account carries `recon_blocked = true`**; the two uncomparable ones carry `false` and have no row at all.

**A fifth run was killed before its close** and left `status running` with a null `finished_at` and `accounts_done 0`, which is `0064`'s mutability claim executed rather than quoted.

**THE BLOCKER.** The natural address for the redelivery UPDATE is `{accountId, tradingDay}` and the accessor REFUSES it, verbatim:

```
a write to reconciliations must name a row. [account_id, trading_day] contains
no unique key reconciliations declares, so this predicate can match more than
one row. Declared: (id).
```

`uniqueKeys` in [`scoped-db.ts`](../../packages/db/src/scoped-db.ts) derives its roster from the Drizzle declaration -- inline and table-level primary keys, inline `.unique()`, table-level unique constraints -- and `reconciliations_account_day_uq` is a `CREATE UNIQUE INDEX`, which is none of the four. **This is not that table's gap.** `schema.ts` carries **no `uniqueIndex` declaration at all**, and the migrations create **61 unique indexes, of which 33 are unconditional**. So no unique index in this estate is addressable. The update is addressed by the primary key instead, which costs nothing and is stronger -- the row was read on the same transaction -- and the finding is **reported rather than repaired**, because that file is `P5-a`'s and no slice here moves it.

A case now pins both window predicates and the transaction each is read in, and the seed goes red.

### 7. Found and not in the dispatch

1. **`degraded` is the vocabulary member this producer wants.** `0064` refused it because *"a state with no producer is a vocabulary member nobody can write"*, and this file is that producer. One uncomparable account out of five thousand now closes a whole night with the same word a sweep that died at account three gets, which is exactly what `SD-M7-01` splits for `detector_runs`: *"a single failure state hides one inside the other"*. **Reported and not taken**: the member is a `CHECK` on a merged migration and only a superseding one moves it.
2. **No unique INDEX in this estate is addressable.** Section 5.
3. **`apps/api` holds four doors, not two.** `resolution` and `establishment` arrived with `ADR-200` and neither reaches `reconciliations` either, so the conclusion is unchanged and the count in the suite is derived from that file rather than written here.
4. **The clearing path does not exist anywhere.** Nothing in this tree sets `recon_blocked` in either direction, so the first account this sweep blocks stays blocked until somebody writes the operator's endpoint. That is not a reason to weaken the block: a sweep that cleared its own findings is the control deleting itself.

### Blockers

**One, and it was found by executing rather than by planning**: the accessor refuses `(account_id, trading_day)` as an address for `reconciliations`. Routed around correctly rather than widened -- the primary key is the better address anyway -- and reported in section 5 as the workspace-wide property it is.

### Landmines

- **A crashed run's counters read zero however much it compared.** The run row is written at the start and updated at the end, so `accounts_done` on a `running` row is `0` no matter how many `reconciliations` rows the sweep committed before it died. **The truth is in `reconciliations`**, and a reader that trusts `accounts_done` on an unfinished run will understate what happened.
- **`batch_run_id` still has no referent.** The producer refuses a value that is not a uuid and that is the ONLY check there is; a well-formed uuid naming no batch run passes everything.
- **A recorder cannot see a predicate it does not assert.** Seed 12 is the general case, not a one-off: any narrowing this sweep makes is invisible to the suite unless a case reads the `where` off the recorded call.
- **The empty-population rule lives in the producer and not in the database.** A second producer, or a reader that computes its own verdict from the columns, gets `0 of 0 completed` back and nothing stops it.
- **A barrel leg check sees specifiers and not names.** A single export dropped from a surviving leg is invisible to both `breaker.test.ts` and `digests.test.ts`.
