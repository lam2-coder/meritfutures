## ADR-354: the digest producer gets four of its six ports, the transport's two channels are shown to block differently and only one of them is unwritten, and the job stays off a clock on a third blocker that a transport would not discharge (2026-09-05, status: proposed)

**THE DISPATCH SAID `runDigestDeliveries` IS BUILT, TESTED AND NOTHING RUNS IT, AND THAT THE TRANSPORT IS THE BLOCKER. THE FIRST HALF REPRODUCES EXACTLY. THE SECOND IS ONE OF THREE, AND THE TRANSPORT ITSELF IS TWO FINDINGS RATHER THAN ONE.**

[`DigestIo`](../../apps/worker/src/digests/ports.ts) has **six** members. [`apps/worker/src/digests/adapter.ts`](../../apps/worker/src/digests/adapter.ts) serves **four** of them over [ADR-165](ADR-165.md)'s one door. `content` and `transport` refuse, and **the transport's two channels do not block for the same kind of reason**: `sftp` is **unreachable** behind an OPEN founder question that both `M06` and [ADR-066](ADR-066.md) call a **second credential surface**; `email` is **unwritten**, and what it waits on is a **vendor ruling** rather than an adapter, because the one working mail sender in this workspace is `apps/api`'s and [ADR-229](ADR-229.md)'s own argument for it is that the credential scopes to sending from ONE server.

### 2. THE HEADLINE: the transport is two findings and only one of them is a missing file

`DigestTransport.send` is one method and `report_schedules.channel` admits two values. **THE TWO CHANNELS ARE HELD APART IN `DIGEST_TRANSPORT_BLOCKERS` BECAUSE COLLAPSING THEM INTO "unwritten" WOULD LOSE THE ONE THAT IS A RULING.**

**`sftp` IS UNREACHABLE, AND WHAT FENCES IT IS AN OPEN FOUNDER QUESTION RATHER THAN AN EMPTY DIRECTORY.** `OQ-F3-04` stands: [`M06` section 3.6](../plans/M06-admin-ops-console.md) and [ADR-066](ADR-066.md) section 3 each admit SFTP push as **SHOULD** and each call it **a second credential surface**, "which makes *is email alone acceptable for v1* a security question rather than a convenience one". ADR-066 adds that it **reuses no `M02` code path**, so the vendor SFTP one directory over is not a shortcut into it either: "coupling them would make a reporting change a provisioning incident". **A row that shipped an SFTP transport would answer an open founder question by writing a file**, which is the move this wave exists to refuse.

**`email` IS UNWRITTEN, AND THE PLACE IT COULD LEGALLY LIVE IS NOT WHERE THE INTERESTING PART IS.** A new module under `apps/worker/src/digests/` violates nothing and this row could have written one. It did not, and the reason is one register in from the import graph.

1. **A WORKING SENDER ALREADY EXISTS AND IS ONE DEPLOYABLE AWAY.** [`apps/api/src/otp-delivery.ts`](../../apps/api/src/otp-delivery.ts)'s `postmarkOtpSender` is a credential-holding mail sender: one `fetch`, a token in a header, a refusal when unconfigured. `RI-04` forbids the import and `node-linker=isolated` makes the specifier unresolvable at run time and at build time. That is [ADR-348](ADR-348.md)'s shape exactly, and on its own it would make this an `unwritten` waiting on a relocation.
2. **THE DECIDING FACT IS THE CREDENTIAL, AND `DigestEnvelope` SAYS SO IN THE FILE'S OWN WORDS.** It "carries bytes and a destination **and no credential**", so the credential is the TRANSPORT's, held by the process. [`packages/db/src/scope.ts:1199`](../../packages/db/src/scope.ts) closes the other door from the schema side: `report_schedules` holds recipients and **"NO CREDENTIAL IS STORED HERE and there is deliberately no column that could hold one, so this table is not a fifth credential surface arriving without a ruling."**
3. **SO NAMING THE CREDENTIAL IS NAMING A VENDOR, AND NO APPROVED DOCUMENT HAS NAMED ONE FOR THIS CHANNEL.** [ADR-229](ADR-229.md) chose Postmark for the **sign-in** path on the sign-in path's criteria, and `otp-delivery.ts`'s own second criterion is that **"a Postmark server token sends from one server and cannot manage the account, the domains or the other servers"**. Handing the digest run that same token widens a credential admitted narrow, on the argument that made it admissible. Minting a different one is a vendor decision, and this row does not take it.

**THAT DISTINCTION CHANGED WHAT IS OWED, WHICH IS THE TEST [ADR-349](ADR-349.md) SET FOR MAKING IT.** An `unwritten` transport is a slice somebody schedules. An `unreachable` one is a question on the founder's list. **This port has one of each behind a single method**, so the delivery job is not one slice away from working and is not one ruling away either: it needs the ruling AND the slice, in that order, and only for the channel `M06` sizes as the MUST.

### 3. `content` refuses on both reads and NEITHER blocker is an adapter

`ports.ts` states the boundary before either read is reached: both bodies are **INPUTS** and neither is queried through this handle, because "a producer that could read `identities`, `risk_flags` or `accounts` directly is a producer one line away from putting a trader in an email" (`INV-M6-10`, `M06:54`).

**`lossRatioCusum` CARRIES THE BREAKER'S TWO BLOCKERS AND ADDS NONE.** The body is `P7-k`'s `BreakerEvaluationReport` folded by `lossRatioBodyFrom`, and this deployment can produce no such report. `UNWIRED_BREAKER_IO` is the only `BreakerIo` in the tree, **and the evaluator would DECLINE even wired**, because `OQ-M6-02`'s minimum sample is the founder's and is unanswered. `schedule.ts`'s breaker row states both and this file does not restate them differently.

**`flagQueue` IS `P7-i`'s QUEUE AND IT LIVES IN THE OTHER DEPLOYABLE.** `readFlagQueue` is in [`apps/api/src/admin-source/flags.ts`](../../apps/api/src/admin-source/flags.ts); `apps/worker/package.json` declares neither `@merit/api` nor any path into it, which is `RI-04`, and `ports.ts` already names the consequence: the flag queue "crosses as a SUMMARY the deployment supplies rather than as a call this deployable makes".

**AND THE SECOND ONE IS WHERE THE PLAUSIBLE REPAIR IS THE WRONG MOVE, WHICH IS RECORDED BECAUSE IT IS TEMPTING.** Nothing stops this deployable opening its own door onto `risk_flags` and folding counts by severity. The result would carry no trader, would satisfy `INV-M6-10`, and would type-check. **It is refused anyway**: it would be a SECOND independent fold of one corpus figure, in a different deployable from `readFlagQueue`, with nothing making the two agree. Two implementations of one number that may silently disagree is the drift [ADR-034](ADR-034.md) exists to end, and **a digest is where a wrong number gets mailed rather than merely displayed.**

### 4. Ruling 1: four members served, and `tradingDayOf` is served by being PINNED

`transact` is `LIVE_DB.batch`, which `ports.ts` had already argued satisfies it. `terms` is the accessor's `atLeast`, passed through untouched because `isFilterTerm` reads identity rather than shape ([ADR-157](ADR-157.md) clause 2). `now` is an argument, on `job.ts`'s rule that "THE CLOCK IS AN ARGUMENT AND NOT A CALL".

**THE FOURTH IS THE ONE WORTH ARGUING WITH.** `DigestIo.tradingDayOf(at: Date): string` is **synchronous and total**. The only last-closed-trading-day fact in this workspace is `anchorLastClosedDay(db, at)` in `batch/adapter.ts`: **asynchronous, database-backed, and able to refuse three ways** (an empty calendar, an EXHAUSTED calendar, a coverage gap). There is no way to await the second from inside the first, and `ports.ts` forbids the alternative in its own words: "a job deriving one from a UTC instant would be inventing a calendar."

**SO THE RESOLUTION IS HOISTED ABOVE THE RUN AND THE PORT IS PINNED TO THE INSTANT IT WAS RESOLVED FOR.** `resolveDigestTradingDay(db, at)` is the async half and delegates to `anchorLastClosedDay` rather than folding the calendar a second time; `tradingDayAnchoredAt(resolvedFor, day)` is the pin. `job.ts`'s `resolveTradingDay` is the same shape one file over and for the same reason: every refusal that can be made ABOUT a run is made above the work, so a run that cannot say which day it is reporting never opens a transaction.

**THE PIN REFUSES ANY OTHER INSTANT AND THAT REFUSAL IS THE POINT, NOT A LIMITATION.** An adapter answering one day for every instant handed to it would stamp a day resolved for one window onto a different window's row, and `report_deliveries.covers_through_trading_day` is `INV-M6-04`'s as-of column: "every number names its as-of moment and its source". That is [ADR-273](ADR-273.md) finding 1's harm, a confident `YYYY-MM-DD` written for a night nobody resolved against, moved off `rule_states` and onto the digest's evidence table. **Case 2.3 proves the refusal lands ABOVE the transaction**: the door records zero transactions and zero calls.

### 5. Ruling 2: the job is WIRED and deliberately NOT SCHEDULED, on three blockers

**WIRING AND SCHEDULING ARE TWO DECISIONS**, which is `schedule.ts`'s own standing rule. The adapter lands and `disposition: 'unscheduled'` does not move.

**BLOCKER 1 AND 2 ARE SECTIONS 2 AND 3.** A run today writes no digest to anybody.

**BLOCKER 3 IS THE ONE A TRANSPORT WOULD NOT DISCHARGE, AND IT IS THIS ROW'S OWN FINDING.** `DIGEST_WINDOW_ANCHOR` ships `weekdayOfWeeklyWindow` and `hourOfWindowClose` `unstated` with their citations, because `CRON_INVENTORY`'s Expected-by cell for this row reads "the schedule's own window", `M06` section 3.6 names no time, and `WEEKLY_RISK_RITUAL` says "same time every week" without saying which. `produce.ts` states the consequence for a scheduler in one sentence: `due_at` is the CALLER's, "because the anchor is unstated and **whatever schedules this job is what knows when it fired**". **`schedule.ts` is that caller.** An interval typed there is the weekday and the hour, chosen, and `report_deliveries_window_attempt_uq` would then key the whole delivery history on a window nobody agreed to. `ADR-345` left the reconciliation sweep off a clock because its consequence had no release; **the reasoning transfers in form and not in substance, and the difference is stated rather than borrowed**: nothing this job writes blocks a payout, so the harm here is not an unreleasable block but a permanent record keyed on an invented anchor.

**AND A CLOCK TODAY WOULD ARM `DigestUnwired`'s OWN HAZARD WITH THE SIGN FLIPPED, WHICH IS MEASURED RATHER THAN FEARED.** `DigestUnwired`'s message says a `delivered` from an unwired producer is indistinguishable from one from a wired producer. **The composed value cannot produce that.** What it CAN produce is the mirror: `deliverOne` **CATCHES** a refusing `content` and **CATCHES** a refusing `transport` and writes `outcome: 'failed'` in both cases rather than crashing, and `0040` **REVOKES `UPDATE` and `DELETE`** on `report_deliveries`. So a scheduled run appends one **uncorrectable** `failed` row per enabled schedule per window, at climbing `attempt` ordinals, and on the day a transport lands every window before it reads as a transport that existed and could not send. **Case 5.1 RUNS this**: one enabled schedule in, `delivered: 0`, `failed: 1`, one `insert` on `reportDeliveries` carrying `outcome: 'failed'`, and no path reaching `delivered`.

**THE CRON ROW'S OWN CLAUSE IS WHY NONE OF THIS IS URGENT AND IT SURVIVES UNCHANGED.** `CRON_INVENTORY`'s scheduled-digest row asserts the QUERY rather than the job, so the dead-man switch is correct with nothing running: an enabled `report_schedules` row whose window has closed with no `delivered` row is the finding, evaluated independently of whether any run reported success.

### 6. Ruling 3: the alarm's reads are REFUSED by this adapter, which is a boundary and not a gap

`DigestTx` extends `DigestReadTx`, so the handle this row builds is assignable to the one `findUndeliveredWindows` takes. **It still refuses the alarm's filter shapes.** `alarm.ts` reads `reportDeliveries` by `{scheduleId}` alone, optionally with a `dueAt` TERM; `produce.ts` reads it by `{scheduleId, dueAt}` as an equality. `DIGEST_READ_FILTERS` is transcribed from the producer's two call sites and from nothing else, and a missing column is a THROW for a measured reason rather than a general one: `{scheduleId}` without `dueAt` is a syntactically perfect read of **every window that schedule has ever had**, and `nextAttempt` folds whatever it is handed into an ordinal, so a dropped column does not fail, it returns a NUMBER over the wrong population, and `report_deliveries_window_attempt_uq` accepts a too-high ordinal because it collides with nothing.

**THE ALARM IS ROW `353`'s AND ITS DOOR IS ITS OWN TO ARGUE FOR.** `ports.ts` section 1 is why the two runs are wired independently: a deployment that wired the producer and not the alarm is exactly the deployment where "the job reported success" is the only thing anybody has. An adapter quietly serving both would be one value carrying both halves, which is the coupling that file refuses as text.
