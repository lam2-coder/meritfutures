## ADR-145: `admin_actions.reason` is a PRECONDITION, so the audit row is written first and the route never supplies one (2026-08-27, status: proposed)

**[`0017_events_and_audit.sql:82`](../../packages/db/migrations/0017_events_and_audit.sql) carries one line of DDL and one sentence about it: `reason text NOT NULL`, under _"NO UNEXPLAINED ADMIN ACTION, EVER. NOT NULL is the whole control."_ Read as a log line it is a column somebody has to remember to fill. Read as the design it is a PRECONDITION, and this entry rules the second reading and makes it structural: in all seven admin writes the `admin_actions` INSERT runs BEFORE the mutation, on the same transaction, so an operator write that records no reason is refused by POSTGRES and the account is never touched.**

- **Origin:** session **257**, [ALLOCATION](ALLOCATION.md) row 145, **RESERVED BEFORE DISPATCH, REQUIRED, UNLINKED**. The reservation's own words are the objective: _"an admin write that records no reason is refused by the database ... the write path must carry the reason rather than default one."_

- **MONEY PATH.** `POST /admin/plans/versions/:versionId/publish` decides what a trader is sold and what the firm owes, and `POST /admin/accounts/:accountId/close` and `/freeze` reach an account's status and its payout gate. **The `E2` line-by-line read is owed on every line this lands and is the founder's.** The approval line below is UNSIGNED.

- **Session 256 owns the surface-selection ruling, `ADR-144`, and it governs.** Nothing here invents a second answer to how an operator principal is resolved: `admin-writes.ts` declares an `AdminWriteBackend.principal` port and the resolution is 256's. Cited unlinked under `CI-06a` because that entry has not landed.

- **`ADMIN_ORIGIN` appears nowhere.** [ADR-012](ADR-012.md) keeps the admin apex domain out of the corpus, the repository and every public artifact. There is no hostname in the diff, no origin comparison against a literal, and no comment naming one. A grep of the whole diff for a domain-shaped string returns **zero**.

### 2. THE RULING

#### Clause 1. The audit row is written FIRST and the mutation is downstream of it

In all seven handlers the order inside the transaction is: read the target row, INSERT `admin_actions`, apply the mutation. **The explanation is a precondition of the write in the one place that cannot be forgotten, which is the transaction itself.** Mutating first and appending the audit row afterwards would make "no unexplained admin action" depend on both statements running; this way the second statement is unreachable when the first is refused.

Proved in both directions against a real database. The refusal: `23502` on `admin_actions.reason`, zero `admin_actions` rows, `accounts.payouts_frozen` still `false`. The pass: the identical call carrying a reason returns `200`, one `admin_actions` row with the reason verbatim, and `payouts_frozen` `true`. **A guard that refused everything would pass the first case and fail the second**, which is [`DELTA_MANIFEST`](../../packages/db/DELTA_MANIFEST.md) section 13's lesson.

#### Clause 2. THIS MODULE TRANSCRIBES AND NEVER SUPPLIES

> **A value a handler cannot derive is carried from the request or it is absent, and an absent one is the database's refusal to report rather than the handler's to fill.**

`reason` is the case the dispatch named and it is not the only one. Findings 5, 6 and 7 put `public_slug`, five money columns of `plan_version_sizes` and the publish-decision pair in exactly the same position, and the answer is the same in all of them: the route writes what the body carried, the `NOT NULL` or the `CHECK` refuses what it did not, and the problem document names the column the database refused on.

**The alternative was a handler inventing a drawdown**, and a drawdown is what a trader is sold and what the firm owes. Between a route that refuses until the contract is amended and a route that guesses a money value, this entry takes the refusal.

`initiative` is carried the same way, and `0043`'s biconditional CHECK is what refuses a `trader_request` that names no identity. **That is a better control than a line in a handler and this module does not duplicate it.**

#### Clause 3. The empty reason is refused HERE, and the CHECK that should refuse it is OWED

Finding 1 is a gap and it is stated as one. `NOT NULL` refuses omission and admits `''`, API_CONTRACT requires non-empty, so `readEnvelope` refuses a blank reason with `validation_failed` and its message says why it is doing the database's job.

**The repair is one CHECK and this session may not write it.** Session **240** owns the migration numbers, and a merged migration is never edited, only superseded (constitution E2), so the need is named and stopped at:

> `admin_actions` wants `CHECK (btrim(reason) <> '')`, on `plan_versions_simulation_waiver_not_blank`'s precedent (finding 2). Until it exists the non-empty half of the contract's requirement lives in a route rather than in the schema, and a second admin route written later inherits nothing.

#### Clause 4. "The four writes" are four PATH PREFIXES and the contract carries seven rows under them

None of `POST /admin/accounts/:account`, `/admin/flags/:flag`, `/admin/plans/:plan` or `/admin/plans/versions/:version` is a row in API_CONTRACT section 8. Each is the prefix of rows that are: `/freeze`, `/unfreeze`, `/close` and `/note`; `/status`; `/versions`; `/publish`. **The corpus is the specification, so the rows are what was written.** Collapsing seven into four behind an action discriminator would be a shape the contract does not carry, and writing four of the seven would leave three admin writes with no owner.

#### Clause 5. One door, and the vocabulary is not widened

`accounts` and `risk_flags` are `owned` and `identities` is `root`, so `firmDb()` cannot reach any of them; an operator write reaches across identities by definition. **All seven rows run at `systemDb('operator-console')`, which is what [ADR-084](ADR-084.md) accepted that word for.** `SystemReason` stays at two members and `SqlExecutorReason` is untouched. [ADR-102](ADR-102.md) section 10 already records that an operator handle "reaches every row in the estate"; this entry adds callers to that reach and adds nothing to the vocabulary.

The door arrives as a PORT rather than being opened in the route, because finding 9's third door in `db.ts` is outside this fence. **Until somebody installs a backend every route here answers 503**, which is `auth.ts`'s `UNWIRED_AUTH_BACKEND` precedent: fail closed and honest for a deployment that installed no backend at all.

#### Clause 6. Roles are DATA, and they are `INV-M6-09`'s

[M06](../plans/M06-admin-ops-console.md)'s `INV-M6-09` decides all seven in one line: _"`readonly` cannot mutate anything, and `ops` cannot change config, roles, or plan versions."_

| Route                                                                       | Roles          |
| --------------------------------------------------------------------------- | -------------- |
| `/freeze`, `/unfreeze`, `/close`, `/note`, `/status`                        | `owner`, `ops` |
| `/admin/plans/:planId/versions`, `/admin/plans/versions/:versionId/publish` | `owner`        |

The declaration is an exported table derived from the same array the routes are derived from, so `FM-M6-09`'s negative-authz matrix reads a table rather than seven `if` statements. **`FM-M6-09` is a merge blocker and its control column is a matrix "across every role and every mutating endpoint"; a matrix cannot read a handler body.**

#### Clause 7. Dual control is resolved at PUBLISH, over three named fields, bound by a payload hash

[M06](../plans/M06-admin-ops-console.md) section 8 rows it on publish and API_CONTRACT's publish row lists `precondition_failed` for it. "Cap, split, or cadence gap" resolves against `PlanRulesJson` exactly:

| The contract's word | The key                                 | The `CV-nn`               |
| ------------------- | --------------------------------------- | ------------------------- |
| cap                 | `phase_funded.payout_cap_schedule`      | `CV-09`, `CV-10`, `CV-17` |
| split               | `phase_funded.split_bp`                 | `CV-13`                   |
| cadence gap         | `phase_funded.cadence_gap_trading_days` | `CV-08`                   |

**A PLAN'S FIRST PUBLISHED VERSION IS SENSITIVE.** It establishes all three from nothing, and a comparison against a predecessor that does not exist would let the very first cap and split reach production on one approval. Fail closed.

The approval must name THIS payload: `payload_hash` is checked against `sha256` of a canonical JSON of the plan version id and the three fields, which is `SD-M6-05`'s own sentence about the column, _"pins WHAT is being approved, so an approval cannot travel"_. The window is ADR-010's twenty-four hours and it is checked in both directions: an approval opened with a longer window does not satisfy, and one whose window has passed does not either. **The database already carries the structural half** (`_second_person`, `_approval_is_complete`, `_within_window`) and this module does not restate it.

#### Clause 8. `validatePlan` gates publish, and an unwired deployment publishes nothing

`CV-01` to `CV-19` are publish-time checks and a publish that skipped them would put a version in front of buyers that the engine refuses to resolve. `apps/api` declares no `@merit/rules-engine` and a manifest is not in this session's fence, so it is a port on `AdminWriteBackend` and an unwired deployment answers 503 instead of publishing unvalidated.

#### Clause 9. The trading day is INJECTED, because finding 10 says nothing here can derive it

`accounts.closed_on` is a `date` on the CT session calendar and `new Date().toISOString()` is wrong for the hours the two calendars disagree. `AdminWriteBackend.tradingDay()` is a port for that reason. **This is a real gap and the port is where it is visible** rather than a UTC date that looks right most of the day.

### 3. What this entry PROPOSES to API_CONTRACT, and does not perform

Findings 4 to 8 are gaps in a **frozen** document. Changing one requires an ADR and not a commit, API_CONTRACT is outside this session's fence, and the corresponding amendment is proposed here for the founder rather than folded:

1. **Section 8's preamble governs the per-row bodies.** `reason` and `initiative` are carried on every mutating admin endpoint, including the three rows whose TS type omits them. `resolution_note` and `note` are recorded as themselves and are **never** used as a reason.
2. **`CreateVersionRequest.sizes` carries every `NOT NULL` column of `plan_version_sizes`**, and `CreateVersionRequest` gains `public_slug`. Until it does, a body short of them is refused by the database.
3. **`PublishRequest` gains `decided_on_simulation_run_id` and `simulation_waiver_reason`**, exactly one of which a published row requires.
4. **The size grid is written at CREATE.** `CreateVersionResponse.computed_sizes` is the evidence: the grid exists once the draft does, so the publish row's "materializes" clause is already satisfied when publish runs.

**None of these is applied to API_CONTRACT by this session.** The routes are written against the reading above and the reading is stated here so the founder's read is a read of a proposal rather than an archaeology of a diff.

### 4. Consequences

- **A second admin write inherits the shape.** The audit-first order, the envelope, the role table and the database-refusal mapping are one runner in one file, so the eighteenth parity route `0043` anticipates gets them by declaring a spec rather than by remembering a convention.
- **A blank reason is refused by a route and not by the schema** until clause 3's CHECK lands. That is the weakest thing in this entry and it is why it is a clause rather than a footnote.
- **The event half of every admin action is not written.** `0017` calls the duplication the point and this module supplies one side of it. Registering `events` in `SCOPE_RULES` is a diff on `packages/db`, which is outside this fence; **named and stopped at**, per finding 3.
- **Nothing here can serve in production yet.** No backend is installed, so the operator deployment answers 503 on all seven. The third door in `db.ts`, the `@merit/rules-engine` admission and the SSO principal are three named debts and each belongs to a session that holds the file.
- **SESSION 256's `ADR-144` GOVERNS THE SURFACE AND THE PRINCIPAL, AND WHERE THIS MODULE DIFFERS FROM IT, IT LOSES.** `ADR-144` had not landed on `main` when this was written (`PR #338`, open), so this module built against its own best reading and the two agree on the shape: `AdminRole` closed at three, an endpoint declaring the roles it admits as data, `INV-M6-09` as the ruling, and the operator session as a PORT nothing in this tree wires. **Three differences are named so the merge resolves them rather than discovers them**: `AdminPrincipal.actor` here against `actorId` there; a `principal(): AdminPrincipal | null` here against `AdminSessionLookup`'s three arms there, of which **theirs is the correct one** because API_CONTRACT section 12 wants **403** for a real trader session on `/admin/*` and 401 only for a token nobody recognises; and the cookie, which 256 owns. **On merge this module takes 256's `AdminSessionSource`, `AdminPrincipal` and `resolveAdminRole` and drops its own `principal` port.**
- **`apps/api/test/server.test.ts` was widened, and the widening is a STRENGTHENING.** Its `expect(report.withheld).toStrictEqual(['GET /internal/jobs'])` was true only while one synthetic operator route existed in the workspace, and seven real ones made it red. **Session 256 hit the same line and repaired it the same way**, so this branch carries 256's text VERBATIM rather than a second correct answer: the assertion is now that what the public deployment withholds is exactly what `classifyPath` calls operator, in both directions, which cannot go stale as operator modules land. **The fence named one test file and could not produce a green tree**, which the stop condition requires, so the widening is named here rather than performed silently.
- **An operator handle now writes to seven more tables.** That is the reach ADR-102 section 10 priced and this entry spends some of it. It is stated rather than left to be discovered.

### 5. Alternatives considered

- **Validating `reason` in the route and never letting the database see its absence.** Refused, and refusing it is the whole entry. It converts the one control the schema enforces on operators into a convention that the next route may not follow, and `0017:82` calls the `NOT NULL` "the whole control" precisely to stop that.
- **Defaulting `reason` from `resolution_note` or `note`.** Refused. It is defaulting with extra steps, and it makes the audit record a sentence the operator did not write as their justification.
- **Writing a placeholder to get past the constraint.** Refused. It would make every row satisfy the constraint and no row satisfy the control.
- **Computing the five missing `plan_version_sizes` columns from `rules`.** Refused on finding 5: nothing in this workspace does it, so the computation would be invented here, and it is money.
- **Deriving `public_slug` from the plan code and the version number.** Refused. `SD-M9-01` makes it a permanent public URL; choosing one is a product decision and not a transcription.
- **Widening `SystemReason` with an `'admin-write'` member.** Refused by the dispatch and by [ADR-096](ADR-096.md) clause 3's own argument: a list nobody has to justify joining is not a control. `'operator-console'` is what an operator console is.
- **Collapsing the seven rows into the four endpoints the dispatch names.** Refused on clause 4.
- **Proving the refusal against a recorder.** Refused. A fake cannot refuse a `NOT NULL`, and a suite that asserted the refusal against its own fake would be agreeing with itself. It is also how finding 11 was found: the recorder half of this suite was green while every real database refusal answered 500.
