### 3. Construction time, defined mechanically and defended

**THE DEFINITION.** A node is at CONSTRUCTION TIME of a function `f` when it lies inside `f` and its **nearest enclosing function-like ancestor is `f` itself**. Function-like means `FunctionDeclaration`, `FunctionExpression`, `ArrowFunction`, `MethodDeclaration`, `GetAccessor`, `SetAccessor` or `Constructor`. **Parameter default initializers are included**, because a call that omits the argument evaluates them.

**WHY THAT IS THE RIGHT LINE, AND NOT AN APPROXIMATION OF ONE.** Calling `f` runs everything in that region and nothing outside it. A `throw` in the region is a `throw` the INSTALL LINE takes, and an install line that throws aborts module evaluation. A `throw` inside a closure `f` merely RETURNS is taken by a request, per method, which is the fail-closed refusal every adapter in this tree is built out of and is not a failed install. **The two look identical to a grep for `throw` and they are opposite things.**

**THE PARAMETER-DEFAULT CLAUSE IS NOT DECORATION.** `postmarkOtpSender` is reachable ONLY as the default value of `databaseAuthBackend`'s fourth parameter, and `start.ts` writes `databaseAuthBackend(LIVE_DB)`, omitting it. **The default IS what a deployment constructs.** This is the one hop ADR-372 followed by hand and it is the hop a reader that skipped parameters would lose silently.

**WHERE THE DEFINITION IS UNSOUND, NAMED RATHER THAN LEFT TO BE FOUND.** A function-like node in the region is skipped, so a `throw` inside one is invisible even if something in the region CALLS it. Two shapes do that: an immediately invoked function expression, and a callback handed to a construction-time call that invokes it.

**BOTH ARE CLOSED BY ASSERTION.** The guard pins two lists rather than filtering them:

- **every construction-time callee must be a plain name the walk resolved**, and the set it could not follow is pinned at exactly one entry, `Map`, a global. An IIFE has a callee that is not a name and enters that set, so it reddens the bar.
- **no construction-time call may be handed a function.** There is no such call on this tree and the day there is one, the bar is red and the definition is re-opened rather than quietly outrun.

**THIS IS THE PART OF THE ROW MOST LIKELY TO AGE BADLY AND IT IS BUILT TO FAIL LOUDLY WHEN IT DOES.** A guard whose analysis is outrun by the code it reads is worse than no guard, because it is read as protection. Neither list is a filter; both are equalities.

### 4. The two guards, and how each is falsifiable

**`apps/api/test/start-construction.test.ts`, four cases.**

| guard | what it derives | how it fails |
|---|---|---|
| **no factory a run constructs can throw at construction** | a transitive walk from the 11 roots to a fixed point, 13 functions | a `throw` at construction level anywhere in the closure |
| **every construction-time call is resolved, and none is handed a function** | the opaque set and the function-argument set over the same walk | a callee the walk cannot follow, or a callback passed at construction |
| **the reader tells a body throw from a closure throw** | six synthetic fixtures, both directions | the reader stops drawing the line the definition draws |
| **`app.listen` is reached only inside `main`** | every member call named `listen` under `apps/api/src`, recursively, tagged by its enclosing function | a `listen` anywhere but `main` |

**NOT ONE OF THEM IS ALLOWED TO PASS VACUOUSLY, AND THE ANTI-VACUITY DEVICES ARE FOUR SEPARATE CLAIMS RATHER THAN A GESTURE.** Three of the four cases assert a list is EMPTY, which is what a reader that read nothing would also report. So:

1. **The eleven roots are NAMED**, not counted. A factory leaving the list is a named regression, and a factory joining it forces a person to edit that line and thereby be asked whether the new adapter can throw while it is built.
2. **Every named root must have resolved to a body the case actually read.** A resolver that silently returned nothing would report zero throws forever.
3. **The walk must reach PAST the roots.** It reaches 13 from 11. A walk that stopped at the roots would still report zero throws and would be reading a fifth less than it claims to.
4. **`postmarkOtpSender` must be in the walked set**, named at the one function that proves the parameter-default clause runs. Removing that clause leaves claims 1 through 3 green while an entire construction-time path goes unread. **This hole was found in this row's own first draft and closed before the guard was committed.**

**AND THE DETECTOR HAS NO POSITIVE ON THIS TREE**, which is [ADR-369](ADR-369.md) section 10's lesson and ADR-372 seed 6's: a clause defended by a case that does not run it is a claim rather than a control. So the definition is exercised over six synthetic fixtures in BOTH directions, three that must be detected and three that must not, and the case asserts both directions are populated so the fixture list cannot decay into one a gutted reader still satisfies.

**THE `listen` GUARD DERIVES ITS ANSWER AND PINS NO LINE NUMBER.** It reports `index.ts::main`, a file and an enclosing function name. **This row's own first draft pinned `index.ts:168` and that was wrong**: it would have gone red on any edit above line 168 in a file this row does not own, which is a control that cries wolf and gets deleted. It was corrected before the guard was committed.

### 5. ADR-372 section 5's four shapes, and whether these guards catch them too

**THE DISPATCH ASKED, AND THE ANSWER IS YES, ON A MECHANISM DIFFERENT FROM THE ONE THAT ALREADY CATCHES THEM.** The four are the shapes a line pattern counts as wired while a run installs nothing: a BLOCK comment, a call after `main()`, dead code after a top-level `throw`, and a call inside a template literal.

**ALL FOUR REMOVE A NAME FROM THE PINNED ROOT LIST**, and that is why they are caught here at all:

| shape | why this file sees it |
|---|---|
| a BLOCK comment | the reader is a syntax tree, so a commented call is not a call. The name vanishes from the roots. **Seeded and watched red** |
| a call after `main()` | the walk collects installs BEFORE `main()`, because that is the set whose failure could half-install. The name vanishes. **Seeded and watched red, in this file AND in `start-program.test.ts`** |
| dead code after a top-level `throw` | `start-program.test.ts`' straight-line case reddens first; the walk also stops and the name vanishes |
| a call inside a template literal | not a statement, so not a call. The name vanishes |

**THE PIN IS WHAT DOES THE WORK, AND IT IS NAMES RATHER THAN A CARDINAL.** A count would go from eleven to ten and say nothing about which. **This is deliberately not a second copy of the census `start-program.test.ts` owns**: that file measures the SCANNER against a run, this file measures the CLOSURE against a run, and the four shapes fall out of the second measurement as a consequence rather than as its subject.

### 9. Where this entry is most likely wrong

- **THE OPAQUE PIN IS A MAINTENANCE TAX AND IT MAY BE PAID BADLY.** A legitimate new construction-time call to a package function reddens a money-path bar, and the tempting repair is to add it to the list without reading it. **The list is the review trigger and it only works if the reading happens.**
- **THE ROOT PIN HAS THE SAME SHAPE.** A new adapter forces an edit to a named list. That is intended, and a session in a hurry can satisfy it without asking whether the new factory can throw.
- **THE WALK RESOLVES NAMES SYNTACTICALLY AND IS NOT A TYPE CHECKER.** It follows named imports through relative specifiers and function declarations. A factory exported as a `const` arrow, or re-exported through a barrel, would not resolve and would enter the opaque set rather than being silently skipped, which is the safe direction but is a red bar somebody has to read correctly.
- **NOTHING HERE MODELS A TOP-LEVEL `await` THAT NEVER SETTLES**, which would leave everything below unreached. `start-program.test.ts`' straight-line case forecloses the shapes that would need it, and this row inherits that rather than re-deriving it.
