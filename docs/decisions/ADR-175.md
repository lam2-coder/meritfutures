## ADR-175: the two ledger idempotency conventions are one rule under two spellings, and the rule is that a key names the EVENT and never the DOOR  (2026-08-28, status: proposed)

**`LT-01`'s key is `` `${PAYOUT_ENDPOINT} ${idempotencyKey}` `` and `LT-06`'s is the withdrawal's own stored key with nothing prefixed, and they were recorded as pointing opposite ways.** They do not. **Both were written to stop ONE event becoming TWO postings when more than one door reaches it**, and `admin-payouts.ts` says so in terms about the first while `wallet-withdrawals.ts` says so in terms about the second. What differs is the spelling, and neither spelling generalises to `LT-07`: bare is the string `LT-06` already claims under a globally UNIQUE column, and endpoint-prefixed is the thing `LT-06` refused. **The spelling that satisfies the shared rule is the transaction's own `kind` against the reference it posts**, which is two columns `ledger_transactions` already carries.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `175`, session **315**, reserved CONDITIONALLY beside `174` so that the session could split rather than fold. **It splits**, and [ADR-174](ADR-174.md) section 5 argues why: finding (A) is about `ledger_accounts` and `ledger_entries` and is BLOCKED on an absence, finding (B) is about one column on `ledger_transactions` and is not.

- **MONEY PATH.** The subject is what makes a money posting idempotent. **No migration lands and no code changes**, so no [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) read is owed by this entry; the read is owed on the caller that first mints a key under this convention.

- **This entry rules a CONVENTION and re-spells nothing that has already landed.** Clause 4 is the half that matters most and it is a refusal.

### 2. THE RULING

> **1. A `ledger_transactions.idempotency_key` NAMES THE EVENT IT POSTS AND NEVER THE DOOR THAT REACHED IT.** This is not new: it is what [`wallet-withdrawals.ts:69-71`](../../apps/api/src/routes/wallet-withdrawals.ts) states in its own words and what [`admin-payouts.ts:909`](../../apps/api/src/routes/admin-payouts.ts) enforces by importing the constant instead of retyping it. **What is new is that it is written down once, where a third posting can find it.**
>
> **2. AN EVENT IS `(kind, reference)`, AND BOTH ARE COLUMNS ON THE ROW.** A ledger transaction records one event about one referent, and `ledger_transactions` already carries `kind`, `reference_kind` and `reference_id`. **The key is therefore derivable from the row's own header and never from the call stack that produced it**, which is the property that makes it survive a second door being added later.
>
> **3. `LT-07`'s KEY IS `` `${kind} ${wallet_withdrawals.idempotency_key}` ``**, that is, `wallet_withdrawal_settlement <the withdrawal's stored key>`. It does not collide with `LT-06`'s bare key (finding 9, EXECUTED), it names no endpoint, and a replay of the settlement is refused by the database rather than by the handler.
>
> **4. `LT-01`'s THREE DOORS ARE NOT RE-SPELLED, AND THIS IS A REFUSAL RATHER THAN AN OVERSIGHT.** Their string is already one-per-event-per-reference and already satisfies clause 1. **Changing it would change the key of postings that may already be committed under the old one**, and `ledger_entries` is append-only with no `UPDATE` and no `DELETE` grant ([`0026`](../../packages/db/migrations/0026_roles_and_grants.sql)), so the reconciliation would be a compensating posting rather than an edit. **A convention that costs a ledger correction to adopt is a convention that should apply forward only.** `payouts.ts`, `admin-payouts.ts` and `expiry.ts` are unchanged by this entry.
>
> **5. `LT-02` AND `LT-08` ARE NOT RULED HERE.** Clause 1 covers them and clause 3 does not: `LT-02`'s posting is entangled with [ADR-174](ADR-174.md)'s open question and `LT-08` belongs to [M3](../plans/M03-billing-checkout.md), which has its own reference and its own idempotency story. **A key spelled for a posting whose slice has not been read is a key somebody will have to argue with later.**

### 3. What this entry deliberately does NOT rule

> **Whether the column should have been `UNIQUE (kind, reference_kind, reference_id)` instead.**

**It is the shape finding 6 makes tempting.** A composite unique would have let both postings carry the withdrawal's bare key and would have made the prefix unnecessary. It is refused here for three reasons and only the first is about cost.

- **`0009` is merged and a merged migration is superseded, never edited** (constitution [E2](../../MERIT_BUILD_MASTER_PROMPT.md)). Replacing the constraint is a money-path migration on the ledger's header table, and this entry lands none.
- **The current constraint is STRICTER, and strictness on this column is the control.** A globally unique key refuses a collision even between two postings that got their reference wrong; a composite one trusts `reference_id` to have been resolved correctly before the insert. **`S-2` resolves the transfer by `provider_transfer_id`** ([M05 section 3.1](../plans/M05-payout-system.md)), which is a lookup that can return the wrong row, and the global constraint is the check that does not depend on it.
- **It would not remove the need for clause 2.** With a composite key, `kind` becomes load bearing on the constraint instead of on the string, so the same fact has to be right either way. **Moving a discipline from a value into a schema is only worth a migration when the schema can enforce something the value cannot**, and here it cannot.

**A later session may still want it.** If it does, the argument it owes is against the second bullet, not against the first.

### 4. Alternatives considered

- **Rule that `LT-01` is the convention and prefix everything with an endpoint.** **Rejected on finding 7, EXECUTED.** Two doors reaching one settlement produced two accepted postings for one withdrawal against a live schema. This is the failure `wallet-withdrawals.ts` predicted in a comment and this entry watched happen.
- **Rule that `LT-06` is the convention and use the bare stored key.** **Rejected on finding 5, EXECUTED.** `LT-06` and `LT-07` are two events about one withdrawal and there is one stored key between them, so the second posting is refused by the database. **The convention is not wrong; it is under-specified**, because it was written by a route that posts one transaction and never met the second.
- **Prefix with the transaction's `reference_kind` instead of its `kind`.** **Rejected.** `wallet_withdrawal` is the same for both postings, so it discriminates nothing. `kind` is the only column on the header that distinguishes `LT-06` from `LT-07`.
- **Mint a fresh key per posting, from `gen_random_uuid()` or a counter.** **Rejected, and it is the option that looks cleanest.** An idempotency key that is fresh per attempt is not an idempotency key: the column exists so that a REPLAY of one event finds the row already there, and `S-2`'s whole design is a replayed webhook returning 200 and stopping. A generated key makes every replay a new posting.
- **Report the contradiction again and let the slice that posts `LT-07` decide.** **Rejected.** That slice does not exist and cannot until [ADR-174](ADR-174.md)'s open question is answered, and the convention is needed by `LT-02` and by anything else that posts twice about one referent. **A convention decided inside the first caller is a convention the second caller finds by reading a route.**

---

### 5. Consequences

- **A third posting has a rule to follow and one place to read it.** The rule was already correct in two files and stated in neither as a rule.
- **`LT-07`'s key is settled while `LT-07`'s legs are not**, which is section 5 of [ADR-174](ADR-174.md)'s point made concrete: the header and the entries are decided by different facts.
- **No code changes in this session.** `payouts.ts`, `admin-payouts.ts`, `expiry.ts` and `wallet-withdrawals.ts` are untouched, and clause 4 is why.
- **[`packages/rail`](../../packages/rail/src/settlement.ts) still mints no key**, and its finding B now records that the key is ruled rather than open. The package's refusal to mint one is unchanged, because the caller that mints it is the receiver and this package is the port.
- **`wallet-withdrawals.ts`'s comment becomes the second statement of a ruled convention rather than the only statement of an unruled one.** It is not edited; a later session touching that file may cite this entry beside it.

---

### 6. Approval

- **Approval line: PENDING, UNSIGNED.** **MONEY PATH.** No key is minted by this entry, so the [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) line-by-line read is owed on the first caller that mints one under clause 3.

**What a founder read adds and this entry cannot.** Two of the decisions here are judgements. **That the two conventions AGREE** (finding 3) reads `PAYOUT_ENDPOINT` as a constant that names an event and happens to be spelled as a route, and the coherent opposite reading is that it names a route and the three doors merely share one: on that reading `LT-01` is already wrong and clause 4's refusal to re-spell it is preserving a defect rather than respecting an append-only ledger. **That `LT-01` is not re-spelled** (clause 4) leaves this system with two spellings of one rule in production, and the cost of that is a reader who has to be told they are the same, which is what this entry is. The alternative is a compensating posting against `ledger_entries`, and that is a founder's call rather than a session's.
