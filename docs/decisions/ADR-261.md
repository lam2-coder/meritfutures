## ADR-261: the composition ADR-256 named is written and the image port is wired, its refusal is moved in front of the door so a deferral cannot decide it, and the list port turns out to wait on a guard rather than on a variable (2026-08-30, status: proposed)

**[ADR-256](ADR-256.md) built the card and then drew a distinction: [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md) permit wiring when the only remaining gap is a thing the deployment sets, and *"a composition that does not exist is not such a gap"*, so `useCertificateImageSource` was ONE SLICE from wireable rather than one VARIABLE from wired. THIS ENTRY IS THAT SLICE.** [`apps/api/src/certificate-image-source.ts`](../../apps/api/src/certificate-image-source.ts) composes `db.publicLookup` for the row, `databaseVerifySource`'s `certificate_verifications` append and `renderCertificateCard` into one `CertificateImageSource`, [`start.ts`](../../apps/api/src/start.ts) installs it, and the wired count moves from **8** to **9**.

**AND THE ROW'S NAMED TRAP TURNED OUT TO HAVE A SECOND FACE, ONE PORT OVER FROM THE ONE IT NAMES.** [ADR-246](ADR-246.md) clause 8 refused a half-wired `useCertificateBackend` because `projectCertificate` never calls `links` for a deferred row, so a live read beside a refusing signer answers by the state of the caller's own rows. **A deferred code never RENDERS either** ([ADR-168](ADR-168.md) foreclosure 4), so every refusal the render makes is a refusal only a code whose row issued can reach. `assertCopy` is one of them. A deployment whose `MERIT_VERIFY_DISCLOSURE` carried a character the typeface cannot draw would have answered **404 for a deferred code and 500 for an issued one**, and that pair is `INV-M11-02`'s authority read out of a status code by whoever holds a token. **The whole configuration is therefore read and refused BEFORE the door is opened**, `assertCopy` and `cacheControl` lifted out of the render and run on every path, so a misconfigured deployment answers **503 for every code alike**. That is the case this entry was written around and it was watched RED.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `261`, session **452**, dispatched as `claude/the-composition-that-does-not-exist`. The row is **RESERVED, REQUIRED**, and it is taken.

- **NOT THE MONEY PATH.** No ledger account, no balance, no payout. `E2` is not owed. **NO MIGRATION IS RESERVED, TAKEN OR SPENT**, which is [ADR-249](ADR-249.md) section 4's ruling applied rather than re-derived: every value the card draws is already a column. **The next free number is still `0075`.** Ships `proposed` with an **UNSIGNED** approval line.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That a misconfigured deployment refuses identically for an unknown code, a deferred code, an issued row and a revoked row, and that the database is not reached on any of them; that the read opens `publicLookup` and never `scoped` and carries no identity; that all four revocation classes render and that retuning one class's sentence moves exactly that card; that a deferred row resolves with NO card and the route answers 404; that the route serves a revoked card end to end at 200 with the configured `Cache-Control`; that two rows differing only in `signature` and `signing_key_id` render byte-identical cards; and that this port's `record` writes bytes identical to `databaseVerifySource`'s, is **MEASURED**, by executing it. That the composition closes `useCertificateImageSource` and not `useCertificateBackend` is **DERIVED** from [ADR-256](ADR-256.md) ruling 13 at the clause it names. What is **JUDGED** is where the module lives (section 1), that closing one port without the other is legitimate (section 3), and that `useCertificateBackend`'s remaining gap is a GUARD and therefore still not a deployment fact (section 5).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every clause the row quotes was re-read in [ADR-256](ADR-256.md), [ADR-249](ADR-249.md) and [ADR-246](ADR-246.md) themselves, and every line citation was opened before anything was built on it.

### 3. Whether closing one without the other is legitimate, which the row asked to be established first

**YES, AND [ADR-256](ADR-256.md) RULING 13 IS THE RULING RATHER THAN THIS ENTRY.** [ADR-246](ADR-246.md) section 2 clause 2 held that the bytes `useCertificateImageSource` owes and the `image_url` `useCertificateBackend` owes are **ONE deliverable**, so the two entries *"expire together or not at all"*. [ADR-256](ADR-256.md) narrowed that in its own words: the deliverable *"has turned out to be three"* -- the renderer, the adapter and the origin -- and *"the two entries no longer expire together, they expire in ORDER"*, with `useCertificateBackend` **downstream** of `useCertificateImageSource`.

**SO THIS ENTRY IS NOT WEAKENING [ADR-246](ADR-246.md); IT IS THE FIRST ENTRY IN A POSITION TO EXERCISE THE ORDER [ADR-256](ADR-256.md) PUT IN ITS PLACE.** And the order runs the right way round, which is the half worth checking rather than assuming: the sentence that kept `useCertificateBackend` shut for three entries was *"publishing a link to a trader is publishing a promise that bytes are there"*, and it is the IMAGE port answering that discharges it. Wiring the list port first would have published the promise before the bytes; wiring the image port first publishes nothing at all, because the field that would address it is still refused.

**AND [ADR-246](ADR-246.md)'s FOUNDER BLOCK ALREADY NAMED THIS AS ITS OWN MOST LIKELY ERROR**, in its own words: *"The claim that the two ports are ONE deliverable rests on the card being one artefact, and nothing here proves that the bytes `useCertificateImageSource` serves and the object `image_url` addresses are the same object."* They are the same object -- [ADR-249](ADR-249.md) section 2.4 ruled the address is this deployable's own path -- and the entry still falls, on the other half: one object, three pieces of work.

### 4. The trap, and the four things that shut it

**THE ROW NAMED A TRAP ON `useCertificateBackend` AND THE ANSWER IS IN TWO PARTS.** Part one is section 5: this slice does not wire that port, so it does not have to fix it, and saying so is the correct outcome the row asked for. **Part two is that the same trap was available on the port this slice DOES wire, and it is shut here.**

> **6. A DEFERRED CODE NEVER RENDERS, SO EVERY REFUSAL THE RENDER MAKES IS STATE-DEPENDENT AT THE ADAPTER EVEN THOUGH [ADR-256](ADR-256.md) MADE IT STATE-INDEPENDENT AT THE RENDERER.** That entry's section 3 clause 4 checks all five published sentences and the disclosure on EVERY render, *"including the four sentences this card will not draw"*, so a broken `fact_untrue` fails an ISSUED card too. **That is the half a renderer can shut alone.** It cannot shut the other half, because a renderer never sees a code no row carries and never sees a deferral. Left inside the render, one curly quote in `MERIT_VERIFY_DISCLOSURE` answers **404** for a deferred code and **500** for an issued one, and the difference between those two answers is a fact about Merit's book.
>
> **7. SO THE CONFIGURATION IS READ AND REFUSED IN FULL BEFORE THE DATABASE IS TOUCHED**, which is [`routes/verify.ts`](../../apps/api/src/routes/verify.ts)' own timing control transcribed: *"read before the lookup and validated in full"*. `readCertificateImageConfig` runs `readPresentation`, then `assertCopy`, then `cacheControl`, and the suite asserts on the **recorder's call list** that it is EMPTY on every refusal. That is the assertion that makes the property state-INDEPENDENT rather than merely uniform today: a check that ran after the read would satisfy "the answers are all 503" and still be an oracle the moment a branch was added below it.
>
> **8. THE REFUSAL IS A 503 AND IT REQUIRED A SECOND ERROR CLASS.** `CertificateImageUnconfigured` sits beside `CertificateImageUnwired` in [`routes/certificates.ts`](../../apps/api/src/routes/certificates.ts) and `unwiredOrThrow` answers both, which is [`routes/verify.ts`](../../apps/api/src/routes/verify.ts)' two-classes-one-answer shape and [ADR-240](ADR-240.md) section 4's standing ruling: a deployment nobody finished is not a defect, and a 500 sends an operator hunting for a bug when what is missing is a variable. **`CertificateImageError` is deliberately not in that arm**: those are defects and a defect is a 500.
>
> **9. AND A DEFERRED ROW CANNOT BE HANDED A CARD AT ALL.** `imageHandler` throws if one arrives, in words that call it *"that claim published"*, and the adapter branches on `logResult` before it can build one. That is [ADR-168](ADR-168.md) foreclosure 4 obtained at a second site, the same way `projectCertificate` obtains it.

**AND ONE WRITER OF `certificate_verifications`, NOT TWO.** The append arm is `databaseVerifySource(db, env).record` delegated to rather than reimplemented, and the reason is stronger than tidiness: `code_hash` is a **pseudonym**, so a second digest written here would make one code hash two ways depending on which row observed it, and a detector reading that table for a rate across sources would count two callers where there was one. [ADR-235](ADR-235.md) section 6.3 settled which digest and why. **The suite asserts the two arms produce identical recorder calls for one observation**, and a seeded SHA-512 was watched failing it.

### 9. Consequences

- **The trader's public proof is served by a real deployment line.** A pass card and a payout card render from the live row on every fetch, and `INV-M11-08`'s re-render is a code path in a running process rather than a port declaration.
- **A revocation reaching a circulating image is executed end to end.** [ADR-256](ADR-256.md) executed it against a fake source; this entry executes it against the composition that a deployment actually installs.
- **A misconfigured deployment fails identically for every code**, so the image row carries no information about Merit's book in its failures. That property is asserted on the recorder rather than on the status codes, so it survives a branch being added below it.
- **`certificate_verifications` still has exactly ONE writer in this deployable**, and a second digest is a failing test rather than a comment.
- **The `BLOCKED` list shrank on a COMPOSITION rather than on a door**, for the first time, and `wiring.test.ts`' header records what that means: the last thing a port waits on is not always an authority.
- **`useCertificateBackend`'s reason has stopped being about missing pieces and is now about a property**, which is a smaller and sharper entry for the next reader and a harder one to close by accident.
- **The rate limit is now overdue in a running process.** Consequence and liability at once, and section 8's block is where it is put to a founder.

  **What a founder read adds and this entry cannot.**

  **THE FIRST IS THE ORDERING QUESTION [ADR-256](ADR-256.md) PUT TO YOU AND THIS ENTRY HAS NOW ANSWERED IN ONE DIRECTION.** That entry's block reads: *"the honest statement is that wiring the image port before the rate limit exists puts `FM-M11-05` on a surface anybody can drive"*, and *"the ordering question is a founder's"*. **This entry wired it.** The reasoning is that the row dispatched this slice and permitted `start.ts` *"only if the slice genuinely closes a port"*, that `GET /verify/:code` already serves an unauthenticated public read with a digest and no rate limit, and that the addition is a PNG encode on top of that rather than a new class of exposure. **That is a degree argument and a degree argument is exactly the kind that is wrong when it is wrong.** If you would rather the port stayed at 503 until `INV-M11-05`'s limit exists, **the revert is one line in [`start.ts`](../../apps/api/src/start.ts)** and everything else in this entry stands: the composition, its refusals and its suite are all still there, one line from live.

The alternative is a second parser over the same six copy variables, and two parsers of one copy table is precisely the drift [ADR-256](ADR-256.md)'s key-set assertion exists to refuse. **The reasoning taken is that both rows are served by one deployable from one route table, so a deployment holding one without the other is not a shape anything in this estate builds** -- and that is a claim about deployments, which is yours rather than this session's.

  **THE THIRD IS THAT THE ROW-LEVEL REFUSALS ARE STILL STATE-DEPENDENT AND THIS ENTRY DOES NOT FIX THEM.** `assertRow` refuses a `claims_schema_version` this template cannot draw, and `toVerifyRow` refuses a row whose `revoked_at` and `revocation_class` disagree. **Both answer 500 for the one code whose row is malformed and 200 for the code beside it.** The reasoning is that these are DEFECTS -- a row this deployable genuinely cannot draw -- rather than configuration, and that [`routes/certificates.ts`](../../apps/api/src/routes/certificates.ts) already treats a `CertificateRowError` the same way. **The counter-argument is real**: a `claims_schema_version` of `2` is not a defect, it is a schema this deployable has not been taught yet, and `SD-M11-01` exists so the shape can evolve. **The first row written at version 2 takes its own card down and nothing else.** Whether that should be a 500, a 404 or a card drawn at the version it knows is a decision about `SD-M11-01`'s evolution rather than about a renderer, and no approved document makes it.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **Section 5's distinction between an origin and a guard is doing a great deal of work and it is a JUDGEMENT.** A reader could say: the guard is four lines, the shape is settled in two files, and calling that "a slice" rather than "a variable and some obvious plumbing" is a session finding a reason not to finish. **The answer this entry gives is that the same sentence was available to the session that wrote [ADR-256](ADR-256.md) about the adapter, and it refused it**, and that the property at stake is not the size of the code but whether a DEPLOYMENT can close the gap -- a deployment cannot write a guard. **But if you read that as a distinction being stretched to hold a line, section 5 is the paragraph to strike, and the port beneath it is one small slice from wired either way.**
