## ADR-213: a published plan version's size grid is immutable, and the `INSERT` is refused on the same evidence as the `UPDATE` -- because `validatePlan` runs at the publish transition and takes the whole grid  (2026-08-29, status: proposed)

**The defect was live in the merged schema and it is closed by [`0066`](../../packages/db/migrations/0066_published_size_grid_immutable.sql).** [`0027:260`](../../packages/db/migrations/0027_triggers_invariants.sql) creates `plan_versions_published_immutable` and [`0028`](../../packages/db/migrations/0028_supersede_plan_version_immutability.sql) replaces its body, so a published `plan_versions` row is pinned to the byte and a retired one is frozen absolutely. **`plan_version_sizes` carried ZERO triggers.** Read from `pg_trigger` against the merged set rather than from a grep, and re-derived on this branch rather than taken from the dispatch: the only non-internal triggers on any plan table were `plan_versions_published_immutable`, `plan_versions_publish_decision_is_sound`, `plan_versions_publish_decision_is_sound_on_publish` and `accounts_plan_version_pinned`.

**So `0028`'s guarantee was true of the row and false of the money.** Executed against `0001`..`0065` applied forward-only from empty to PostgreSQL 16, inside a rolled-back transaction: `buffer_cents` moved from `100000` to `777777` on a **published** version, that version's whole size grid `DELETE`d, and a fourth size `INSERT`ed into it. **All three committed.** [`packages/rules-engine/src/types.ts:408`](../../packages/rules-engine/src/types.ts) states the dependency in the tree's own words -- *"`plan_versions.rules` for STRUCTURE and `plan_version_sizes` for EVERY CENTS"* -- and the approval those numbers feed writes an append-only `eligibility_snapshot` (`INV-22`). The failure was never a stale response. It was **an approval the catalogue no longer supports, recorded as though it did.**

**And the design record has claimed the missing guard since the day the table landed.** [`plan_version_sizes.md`](../architecture/data-model/plan_version_sizes.md) reads *"Immutable once the parent version is published (same trigger)."* There was no such trigger, in `0004` or anywhere after it. **That sentence is why sixty-two migrations went by without anybody looking**, and it is finding 1.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `213`, session **403**, dispatched as `claude/published-size-grid-immutable`. The row's substance holds in full and was re-derived at its sources before a line was written. **Migration `0066` was reserved REQUIRED and is TAKEN**; nothing returns to the pool.

- **MONEY PATH. `E2` READ IS OWED AND NOTHING HERE DISCHARGES IT.** [`0066`](../../packages/db/migrations/0066_published_size_grid_immutable.sql) carries an `E2 READ: MONEY PATH` header. This entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **`0027` AND `0028` ARE UNTOUCHED ON DISK.** `git diff` against `origin/main` reports no change to either. A merged migration is never edited, only superseded (constitution `E2`), and `0066` adds beside them rather than replacing anything they installed.

- **`apps/**` AND `packages/tooling` WERE NOT TAKEN.** No door, no port, no adapter, no interface member, no scope class. `usePayoutBackend` is **not** wired and section 8 says what still blocks it, re-derived rather than copied from [ADR-211](ADR-211.md).

### 1. THE RULING

1. **A `plan_version_sizes` row may be written only while its parent `plan_versions` row is `draft`.** `UPDATE` refused, `DELETE` refused, **`INSERT` refused**. Once a version leaves `draft` its grid is fixed **as a set**.

2. **The refused set is derived from the status vocabulary and not listed.** The guard permits `draft` and refuses everything else, so a fourth label added to `plan_version_status` by a later migration is refused by default and the migration adding it must say otherwise on purpose. This is `0028`'s own instinct -- *"THE PINNED SET IS DERIVED, NOT LISTED"* -- applied to the status vocabulary instead of to a column list.

3. **Both ends of an `UPDATE` are checked.** Moving a size row from a draft version onto a published one is an `INSERT` into the published grid under another name; moving one off a published version is a `DELETE` from it. A guard reading only `NEW` admits the second and a guard reading only `OLD` admits the first. **Both were seeded and both fire** (section 7, seeds 1 and 2).

4. **A retired version's grid is frozen for the same reason its row is.** `0028` freezes a retired `plan_versions` row absolutely on [STATE_MACHINES section 9](../architecture/STATE_MACHINES.md)'s `retired --> [*]`. Retirement stops new sales and never touches live accounts, so the grid a retired version was published with is still the contract some live account is held to.

5. **The instrument is a trigger and the cost is `0004:184-185`'s, restated rather than hidden.** It can be disabled and it fires per row. **A `CHECK` cannot express this predicate at all**, because the status that decides it lives on the parent, which is [`0004:183`](../../packages/db/migrations/0004_catalog.sql)'s own argument for materialising `floor_lock_enabled` rather than checking it.

### 2. The `INSERT` is the clause that needed an argument, and it is refused on evidence

**The dispatch was right to insist this be decided rather than assumed.** Adding a size to a published version takes nothing away from an account that already exists: `accounts` pins `plan_version_id` at purchase ([`0027`](../../packages/db/migrations/0027_triggers_invariants.sql)'s `accounts_plan_version_pinned`) and resolves exactly one grid row through `plan_version_sizes_version_size_uq (plan_version_id, size_cents)`. **No existing account's numbers move.** The easy symmetry is therefore not the argument, and if it were the only one this clause would be wrong.

**It is refused because nothing validates such a row, and four of the five things that should have are not in the database.**

| What governs a size row | Where it runs | Reaches a post-publish `INSERT`? |
|---|---|---|
| `CV-02`, `CV-03`, `CV-05` (second half), `CV-07`, `CV-11`, `CV-12`, `CV-16` (second half), `CV-17` -- the eight evaluated **once per size** | `validatePlan(rules, sizes)`, at the publish transition | **No.** The transition already happened |
| `CV-09`, `CV-10` | same | **No**, and neither has any constraint on this table |
| the `floor_lock_enabled` materialization check | same | **No.** [`0004:188`](../../packages/db/migrations/0004_catalog.sql): *"CV-publish validation asserts the materialized flag matches the parent's jsonb"* |
| `plan_version_sizes_buffer_clears_lock` (`CV-11`) and `plan_version_sizes_floor_lock_complete` | the database, per row | **Yes.** These two, and the seven `> 0` column checks |

**The split is `validate.ts`'s own and is quoted rather than inferred.** [`packages/rules-engine/src/plan/validate.ts:45`](../../packages/rules-engine/src/plan/validate.ts): *"Nine of the nineteen read only `plan_versions.rules` and are therefore true or false for the whole version; eight read `plan_version_sizes` and are evaluated once per size."* And it takes the **array**, not a row: *"A VALIDATOR HANDED ONE SIZE AT A TIME COULD NOT SEE THE PLAN."*

**So a row inserted after publication is a row `validatePlan` was never given, and `validate.ts:463` already names what that is:** *"A size row that disagrees with its own rules is two plans wearing one version number, and which of the two an account gets depends on which field a rule happens to read."* That is `FM-07`'s blast radius arriving through a door the publish gate does not watch.

**The corpus already has a mechanism for offering a new size and it is publishing a version.** [`0044:243`](../../packages/db/migrations/0044_fee_back_and_ladder_unlock.sql) says so from the other side, about `plan_size_unlocks.unlocked_size_cents`: it names a `size_cents` rather than a row id *"because the entitlement is to the SIZE, and a version publishing the same size again should honour an unlock earned against it."* **An entitlement designed to survive a republish is an entitlement written by somebody who expected new sizes to arrive by republish.**

**And the only publish path the corpus has designed already writes in the order this guard requires.** [`apps/api/src/routes/admin-writes.ts:1465`](../../apps/api/src/routes/admin-writes.ts) creates the version with `status: 'draft'`, `:1476` inserts every size row into that draft, and the publish route at `:1548` reads the grid back with `rowsWhere` and hands **the array** to `backend.validatePlan`. **Nothing in `apps/` is broken by this guard**, and that is measured rather than hoped: that module is the only writer of this table in the tree, and every route in it answers 503 today.

### 3. What this entry does NOT rule, stated so the gap is a decision rather than an oversight

- **How a published version's grid is corrected when it is found wrong.** The answer this ruling implies is *publish a new version*, which is `0004:54`'s promise (*"Publishing a change means creating a NEW VERSION"*) and is what `0028` already forces one table up. **No migration path, admin route or runbook for it exists**, and this entry does not write one.
- **`plans`.** Session 401 finding 5, re-derived on this branch and it holds: `plans` carries **zero** triggers and `plans.code` moved on a live database, while [ADR-141](ADR-141.md) clause 3 credits `0028` with pinning it and `0028` does not name that table. `plans` feeds no cents value into `ResolvedPlan`, so it is not this ruling's subject; it is **registered and open**.
- **Whether the resolved grid should be denormalised onto `accounts` at purchase instead.** [ADR-211](ADR-211.md) section 7's live alternative, which removes the crossing rather than protecting it. **This entry does not foreclose it**: a guard is cheap and reversible where a denormalisation is neither, so protecting the crossing now costs a denormalisation nothing later.

### 4. The mechanism is `0027`/`0028`'s, and the one place it is extended is named

**The shape is theirs.** A `BEFORE ... FOR EACH ROW` PL/pgSQL trigger raising `check_violation` with a message naming the row and what was attempted. It is deliberately **not** a `CONSTRAINT TRIGGER`: deferring would let the write land and fail at `COMMIT`, which is weaker for no gain, and `0027` defers only the assertions that must see a whole transaction.

**The extension, said plainly because the dispatch asked whether one was needed.** `0027` and `0028`'s predicate is **row-local**: `OLD` against `NEW` on the guarded table. This one is not. The status that decides the refusal lives on the parent, so the body issues one `SELECT status FROM plan_versions`. **That is a widening of the predicate and not of the mechanism**, and it is the only shape `0027`/`0028` could not supply. It did not require bending theirs.

**A missing parent is not this guard's refusal.** A `BEFORE ROW` trigger fires before the foreign key's own `AFTER` check, so a `plan_version_id` naming no row reaches the guard first. The body falls through on a parent it cannot find and lets `plan_version_sizes_plan_version_id_fkey` answer **by name**. **Seed 5 is what makes that load bearing**: with the `FOUND` test dropped, a genuine dangling reference is reported as `plan_version <uuid> is <NULL> and its size grid is immutable`, which sends a reader to the wrong file -- precisely what `0027`'s `undefined_column` did.

### 5. Four things the guard does not do

1. **`TRUNCATE`.** A row-level trigger does not fire on it. Not reachable by the application role: `information_schema.role_table_grants` gives `merit_app` exactly `SELECT`, `INSERT`, `UPDATE`, `DELETE` on this table and no `TRUNCATE`, so the hole is the owner's, which is item 2.
2. **A superuser or the owner can `DISABLE TRIGGER`.** `0004:184-185`'s stated cost. It won because the alternative does not exist.
3. **It does not pin `plans`.** Section 3.
4. **It does not wire `usePayoutBackend`.** Section 8.

### 6. The counterfactual, in both directions, and the A/B is clean

**[`scripts/db/probe_published_size_grid_immutable.sql`](../../scripts/db/probe_published_size_grid_immutable.sql), seventeen cases, six of them acceptances and they lead.** Both installs are from empty, forward-only, under `ON_ERROR_STOP=1`, and every object count is read from `pg_tables`, `pg_indexes`, `pg_constraint`, `pg_proc` and `pg_trigger`.

| | `0001`..`0065` | `0001`..`0066` |
|---|---|---|
| triggers on `plan_version_sizes` (`pg_trigger`) | **0** | **1** |
| the probe | **11 of 17 RED** | **17 of 17 PASS** |
| `buffer_cents` `100000` -> `777777` on a published version | **COMMITTED** | **REFUSED**, `check_violation` |
| that version's whole grid `DELETE` | **COMMITTED**, 0 rows remain | **REFUSED**, 2 rows remain |
| a fourth size `INSERT`ed into it | **COMMITTED** | **REFUSED** |
| non-internal triggers, whole schema | 25 | **26** |
| functions in `public` | 111 | **112** |
| tables / indexes / constraints | 115 / 401 / 797 | **115 / 401 / 797**, unchanged |

**THE SIX CASES THAT PASS ON BOTH SIDES ARE THE POINT OF THE ACCEPTANCE HALF.** A draft grid takes an `INSERT`, an `UPDATE` and a `DELETE`; a version carrying a grid still publishes; it still retires; and a dangling parent is still the foreign key's refusal. **The dangerous over-correction on this table is not a missing guard, it is a total one**: a guard refusing every write to `plan_version_sizes` passes all eleven refusals and makes plan authoring impossible, and since nothing in `apps/` writes this table today, nobody would find out.

**The transcripts are in [`DELTA_MANIFEST` section 31](../../packages/db/DELTA_MANIFEST.md).**

### 7. The seeds, seven of them, six red and one green

| # | Seed | Result |
|---|---|---|
| 1 | the landing check removed, so only `OLD` is read | **RED, 4 cases.** The published and retired `INSERT`s and the move-onto |
| 2 | the leaving check removed, so only `NEW` is read | **RED, 5 cases.** The published and retired `DELETE`s, the move-off, and the retired `UPDATE` |
| 3 | the refused set listed as `= 'published'` rather than derived as `<> 'draft'` | **RED, 3 cases.** All three retired ones. **This is `0028` item 3's exact defect one table out**, reproduced on purpose |
| 4 | `BEFORE` changed to `AFTER` | **GREEN, and it is a measurement rather than a pass.** The exception aborts the statement either way, so the probe cannot see the timing. Written into the probe's header so a reader does not take green here as proof of `BEFORE` |
| 5 | the `FOUND` test dropped, so a missing parent becomes this guard's refusal | **RED, 1 case.** The dangling-parent case, and the message it produced is quoted in section 4 |
| 6 | the refusal message reworded | **RED, 5 cases.** The refusals are asserted by TEXT and not only by SQLSTATE |
| 7 | one case deleted from the probe | **RED**, on the row-count sentinel: *"expected 17 probe rows and found 16"* |

**Each was applied to the committed shape and restored from a byte copy taken before it, with the SHA-256 checked both ways and `git status --porcelain` empty after every one.**

**SEED 1 IS THE MOST VALUABLE RESULT AND IT DID NOT FIRE THE FIRST TIME.** With the landing check neutered, the retired-`INSERT` case collided with the now-committed row of the published-`INSERT` case on `plan_version_sizes_version_size_uq`. `unique_violation` is not `check_violation`, the exception escaped its block and took the whole `DO` with it, and **the run reported ZERO failing rows while four cases were broken.** The probe was loud and it was loud about the wrong thing, three cases downstream. Repaired in a commit of its own: the retired `INSERT` takes a size of its own, and every one of the eight rejection blocks gained a `WHEN OTHERS` leg recording `FAIL: wrong error class <sqlstate>` rather than letting an exception escape.

**AND THE COUNTERFACTUAL FOUND A SECOND DEFECT IN THE PROBE'S OWN COUNTER.** Running against `0001`..`0065`, the move-onto rejection commits, which empties the draft sibling the per-version acceptance then looks for; the value came back `NULL`, `b = 123456` evaluated to `NULL`, the `CASE` returned `NULL`, and `verdict <> 'PASS'` is `NULL` for that row and does not count. **Ten failures were reported where there were eleven.** The three value comparisons are total now, the counter reads `IS DISTINCT FROM`, and a row-count sentinel refuses a run producing fewer than seventeen cases, because a case that did not run looks exactly like a pass. **Neither defect was reachable from the green side**; both were found by running the counterfactual, which is the direction nobody looks.

### 8. What still blocks `usePayoutBackend`, re-derived on this tree rather than copied

**This entry clears one of [ADR-211](ADR-211.md)'s grounds and NOT the port.** The port is not wired, `apps/**` was not opened, and the wiring triple does not move: **`{ declared: 23, wired: 6, blocked: 17 }`**, asserted green by `apps/api/test/wiring.test.ts` before and after.

**What `0066` clears.** ADR-211 refused on *"nothing in this database pins the numbers `ResolvedPlan` is built from."* `ResolvedPlan` is built from `plan_versions.rules` plus one `plan_version_sizes` row ([`resolve.ts:4`](../../packages/rules-engine/src/plan/resolve.ts)). **Both halves are now pinned**: the parent by `0028`, the grid by `0066`. That ground is spent.

**What still refuses, measured on this branch:**

1. **`PayoutTx` runs every method on ONE transaction and `subject()` needs a `firm` read.** `PayoutSubject.plan` (`routes/payouts.ts:331`) is a `ResolvedPlan`; `plan_versions` and `plan_version_sizes` are both scope class `firm`, and `ScopedTableKey` excludes `FirmTableKey`, so no `ScopedTx` read reaches either. **[ADR-211](ADR-211.md) ruled the remedy and it has not been applied**: two transactions, scoped first, the catalogue read a **second port** beside `PayoutTx` rather than a member of it. That is a change to `routes/payouts.ts` and this session did not hold it.
2. **The state half is now a CODE blocker rather than a schema one, and the entry recording it has not caught up.** `wiring.test.ts`'s `BLOCKED` entry still reads *"`grep -rn lifetime_settled packages/db/migrations` returns nothing at all"*. **That is false on this tree**: [`0065:101`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql) declares `lifetime_settled_cents` and the file declares `breached` and `breach_kind` beside it. `databaseAccountReads.readEligibility` still rejects on `ELIGIBILITY_BLOCKER` (`routes/account-reads.ts:925`), and `INV-M5-02` binds the two endpoints to identical inputs, so the refusal is real -- **its stated reason is not.** `apps/**` is not this fence: **registered, not repaired.**
3. **`routes/payouts.ts:438` still states a property `PayoutTx` does not have** -- *"no member of this interface that a scoped door cannot serve"* -- while `subject()` returns a `ResolvedPlan` no scoped door reaches. Session 401 registered it; it is unrepaired and it is a false claim rather than a drifted line.
4. **No adapter exists.** Nothing in the tree implements `PayoutTx`.

**So the honest statement is: one of four grounds is cleared, and the port stays at 503.**

### 9. Findings this session made that were not in the dispatch

1. **THE DESIGN RECORD CLAIMED THE GUARD FOR SIXTY-TWO MIGRATIONS.** [`plan_version_sizes.md`](../architecture/data-model/plan_version_sizes.md): *"Immutable once the parent version is published (same trigger)."* **No such trigger existed.** The sentence is true from `0066` forward and the record now names the trigger and the file. **This is the reason the defect survived**: a reader checking whether the grid was protected found a document saying it was.
2. **AND NO GATE CAN SEE THAT CLASS.** `CI-06i` reconciles the TABLE set in both directions, [`data-model-columns.mjs`](../../scripts/corpus/data-model-columns.mjs) reconciles COLUMNS, and **nothing reconciles a record's `Triggers:` or immutability prose against the `CREATE TRIGGER` statements in the migrations.** `plan_versions.md:27` already records the neighbouring half of this -- *"constraint and trigger names cited in prose are not yet checked by any gate"* -- about a trigger whose NAME was wrong. This is the stronger case: a trigger that did not exist. **Registered, not built**: the gate is cheap and it is not this session's stop condition.
3. **`probe_plan_version_immutability.sql:227` carries the same `verdict <> 'PASS'` counter that lost a failure here.** Its six `CASE` expressions are total in practice, since `msg` is set by `GET STACKED DIAGNOSTICS` and cannot be `NULL`, so nothing is wrong today. **The counter is one edit away from the defect anyway** and it is the only other probe in `scripts/db/` using the idiom. Reported rather than repaired: it is another session's control.

### 10. Consequences

- **A payout approval's basis can no longer move under it.** Every cents value in `ResolvedPlan` now comes from a row that is pinned once its version is published.
- **The publish path gains an obligation it did not have.** A version's grid must be complete before the status moves, because after it the grid cannot be added to. `admin-writes.ts` already writes in that order; anything else that publishes must.
- **A correction to a published grid is now a republish**, and no route performs one. Section 3.
- **`0066` is spent.** The migration pool is unchanged otherwise, no `SD-nn`, no `U-nn`, no `OI-nn`, no `CI-06` letter, no `RI-nn`, no gate id.
- **`ADR-213` is `proposed` and UNSIGNED.** `0066` is a money-path file and the `E2` read is owed on it.

### 11. Approval

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS CLAUSE 1's `INSERT`, BECAUSE IT IS THE ONLY CLAUSE THAT FORECLOSES A COMMERCIAL MOVE.** Refusing `UPDATE` and `DELETE` costs nothing anybody wants: no one argues for editing a published price. **Refusing `INSERT` says that adding a 150K tier to a plan already on sale requires publishing a new version**, which republishes the whole rule contract, mints a new `public_slug`, and leaves every account on the old version pinned there. Section 2 is the argument and it is a validation argument: the row would be one nothing checked. **The honest counter is that the publish path could simply re-run `validatePlan` over the widened grid and the guard could permit an `INSERT` that carried proof of it.** This entry refuses that because **no such proof exists in the schema** -- there is no publish-validation record a trigger could read, `simulation_runs` is anchored to a version rather than to a grid, and a guard that trusted a flag written by the same statement is not a guard. **If a founder wants added sizes, the thing to ask for is that record, not a weaker trigger.**

  **THE SECOND IS THAT THIS ENTRY ANSWERS THE QUESTION [ADR-211](ADR-211.md) LEFT OPEN AND THE PUBLISH PATH IS STILL UNBUILT.** ADR-211's approval block names it: *"A guard written before that question is answered will either break a publish nobody has built or admit a row that changes a live account's basis."* **This guard takes the first horn deliberately**, on the evidence that the only publish path the corpus has designed (`admin-writes.ts`) already writes drafts first. **If M01's publish path is going to differ from that module, this is the moment to say so**, because after the merge `0066` is superseded rather than edited.

  **THE THIRD IS WHETHER A TRIGGER IS ENOUGH, GIVEN WHAT IT PROTECTS.** Section 5 lists what it cannot reach, and item 2 is the real one: the owner can switch it off. The alternative controls are a `REVOKE` and a `SECURITY DEFINER` write path, which is `0048`'s shape for `rule_states`. **This entry did not take that road** because `merit_app` legitimately writes this table while a version is a draft, so a `REVOKE` needs a definer function for ordinary authoring, and that is a bigger change than the defect warrants today. **A founder who thinks the grid deserves `0048`'s treatment should say so**, because the trigger becomes the weaker half of a pair rather than something to undo.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **Clause 2 derives the refused set from the status vocabulary, and that is a bet on future migrations.** Every status but `draft` is refused, so a later migration adding, say, a `staged` status between draft and published gets a guard that refuses its grid writes and a confusing error, rather than a clean compile-time signal. **The alternative -- listing `published` and `retired` -- fails in the other direction and worse**: a new status would be silently unguarded, which is exactly `0027` item 3's defect (a retired row completely unprotected because the guard named only `published`), and seed 3 reproduces it. **The bet is deliberate and the direction is the safe one**, but a reader who expects the vocabulary to grow should know the first migration to grow it will have to touch this guard.
