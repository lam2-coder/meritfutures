### 3. THE RULING, part one: where the check lives, and why it is an invariant

**THERE ARE 33 GATES AND 33 INVARIANTS TODAY**, both derived off their own runners' last lines before the first edit and neither taken from the dispatch. The check lands as **`RI-36`**, written **inline in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs)**, so invariants become 34 and gates stay 33.

#### 3.1 Three arguments for the invariant runner, and the one argument against it

The subject is a DOCUMENT, and `CI-06i` already compares that exact directory to the migrations. **That is the argument for a corpus gate and it is a real one.** Three things beat it.

1. **THIS FILE ALREADY READS THIS MIGRATION SET AND `gates.mjs` DOES NOT READ IT THE WAY THIS CHECK NEEDS.** `RI-26` ([ADR-272](ADR-272.md), [ADR-278](ADR-278.md)) folds `packages/db/migrations` with `stripSqlComments`, `topLevelSegments`, a balanced-paren `CREATE TABLE` body scan, an `ADD COLUMN` reader, a `RENAME COLUMN` fold and a `DROP COLUMN` throw. `RI-36` **reuses the first two verbatim** and would have had to copy both into any module outside this file. `gates.mjs`'s `columnCatalogue()` returns a NAME SET and carries no definition text, so a gate there would have needed a new reader in a file that already holds two SQL parsers, and `data-model-columns.mjs` next to it holds a third by its own admission.
2. **THE LETTER IS NOT AVAILABLE AND THE SLUG WOULD HAVE BEEN A THIRD PARSER.** Finding 5: `CI-06x` is refused by `CI-06/closed-letter-series`. A slug gate is still possible, and it would have been either a new block inside `gates.mjs` or a module beside it; **no registered gate lives in a module beside `gates.mjs` today**, and the one module that tried, `data-model-columns.mjs`, is deliberately unregistered and duplicated the parser to exist.
3. **`scripts/corpus/tsconfig.json` SETS `checkJs: false` IN WRITING, AND `packages/tooling/tsconfig.json` SETS IT TRUE.** That is not an accident: `scripts/corpus`'s config says `gates.mjs` *"is nine thousand lines of JavaScript that no `tsc` has ever read"* and that type-checking it would move every line a live document cites. So the same check is TYPE-CHECKED here and UNCHECKED there, and this one carries a `Map<string, Map<string, FoldedColumn>>` through four functions.

**THE COST OF CHOOSING THIS RUNNER IS STATED RATHER THAN HIDDEN.** One docs-to-migrations comparison is now split across two runners: `CI-06i` and `data-model-columns.mjs` own the NAME axis in `scripts/corpus`, and `RI-36` owns the NULLABILITY axis in `packages/tooling`. A reader chasing "what checks my design record" has two places to look. The alternative was one place to look and a third copy of a DDL parser, and this corpus has recorded the cost of a second parser more often than the cost of a second directory.

#### 3.2 Why the answer is NOT to import `scoped-db.test.ts`'s fold, and what binds the two instead

[ADR-323](ADR-323.md)'s landmine says the gate is cheap because `packages/db/test/scoped-db.test.ts` **already** runs a fold that computes the answer. It does: `foldTableDefs` plus `declaredNotNull`, and this row read all of it before designing anything. **It cannot be the reader here.** It is a `.ts` file that declares vitest suites at module scope, exports nothing, and importing it from a check that CI runs as `node repo-invariants.mjs` would run a test file inside a check.

**SO THERE ARE TWO FOLDS, AND THEY ARE BOUND BY AN ASSERTION RATHER THAN BY CARE.** That is not an invention: it is the rule the estate already wrote for exactly this hazard. `scoped-db.test.ts` carries `foldTable` AND `foldTableDefs` over the same migrations, and its own comment says *"THE TWO FOLDS ARE BOUND BY AN ASSERTION RATHER THAN BY CARE. A second reader of the same migrations that could disagree with the first is the hazard [ADR-092](ADR-092.md) section 5 names"*, and it compares their key sets.

**THE BINDING HERE RUNS THROUGH `schema.ts`, WHICH BOTH FOLDS ARE ALREADY COMPARED AGAINST.** `scoped-db.test.ts` asserts, for every column of every registered table, `column.notNull === declaredNotNull(foldTableDefs(...))`. [`data-model-nullability.test.ts`](../../packages/db/test/data-model-nullability.test.ts) asserts, over the same population, `column.notNull === foldColumnNullability(...).notNull`. **The two readers can therefore disagree with each other only by one of the two files going RED**, and the binding needs no cross-import of a test file and no circular module. The case also asserts that both dispositions appear over more columns than there are tables, because two readers that both returned `false` for everything would agree on every row.

### 4. THE RULING, part two: how `ALTER` is folded over `CREATE TABLE`

**A COLUMN IS ITS `CREATE TABLE` DECLARATION AS AMENDED BY THE SET, AND THE AMENDMENT IS THE WHOLE POINT.** Finding 2: both stale records agree with their `CREATE TABLE` bodies, and `E2` makes those bodies permanent. A gate that read the `CREATE` would have reported a clean estate over the two defects it was written for.

`foldColumnNullability` walks the migration files in filename order and applies five shapes.

| Shape | What it does | Instances in this set |
|---|---|---|
| `CREATE TABLE t (...)` | seeds each column's definition; NOT NULL is a **top-level** `NOT NULL` or `PRIMARY KEY` in that definition | 118 unqualified tables |
| table-level `PRIMARY KEY (a, b)` | marks those columns NOT NULL, because the column definitions do not | **16 tables**, `firm_parameters` and `wallet_spend_limits` among them |
| `ALTER TABLE t ADD COLUMN c ...` | replaces the definition | many |
| `ALTER TABLE t ALTER COLUMN c DROP/SET NOT NULL` | moves the flag and records the file | **six** `DROP`, **zero** `SET` |
| `ALTER TABLE t RENAME COLUMN a TO b` | moves the folded column | **one**, `0075` |

**THE `NOT NULL` SCAN IS AT PAREN DEPTH ZERO AND THAT IS NOT A DETAIL.** `wallet_entries.balance_after_cents` is `bigint NOT NULL CHECK (balance_after_cents >= 0)`, and this corpus writes `CHECK (... IS NOT NULL)` in several places; a textual scan would read a constraint as the column's own nullability. `scoped-db.test.ts`'s `withoutNotNull` scans at depth zero for the same reason, and a case seeds `a text CHECK (a IS NOT NULL)` and requires the fold to call it nullable. **`PRIMARY KEY` counts as NOT NULL even where the words are absent**, which is `declaredNotNull`'s own ruling one file over: `wallet_dormancy.identity_id` is `uuid PRIMARY KEY REFERENCES identities(id)` with no `NOT NULL` text at all.

**`SET NOT NULL` IS READ ON A TREE THAT HAS NONE, AND THAT IS DELIBERATE.** A replay that models one direction of a statement pair is a replay with a hole in it, and the hole would be invisible until the day somebody re-tightened a column. A case seeds one and watches the fold move.

**EVERY SHAPE THE FOLD CANNOT REPLAY IS A THROW AND NEVER A SKIP.** `DROP COLUMN`, a table `RENAME TO`, a `LIKE` body and any statement that adds or drops a `PRIMARY KEY` each raise, with the file and the statement in the message. That is this runner's rule 1 rather than rule 2: it is not an input the check cannot reach, it is a migration set whose shape the fold does not model, and reporting on it would be claiming to have checked something that was not checked. `data-model-columns.mjs` refuses the same statements for the same reason and says so; `RI-26` throws on `DROP COLUMN` for the same reason again.

**SCHEMA-QUALIFIED RELATIONS ARE NOT READ AT ALL, WHICH IS WHAT KEEPS `0079` OUT.** pg-boss installs twelve relations and every statement naming them is `pgboss.`-qualified, including three `ALTER TABLE pgboss.job ADD PRIMARY KEY` that the throw above would otherwise fire on, two of them inside dollar-quoted function bodies. `docs/architecture/data-model/` records no relation outside `public`. A case asserts `tables.has('job')` and `tables.has('pgboss')` are both false and that `unmodelled` is empty on this tree.

**THE COMMENT STRIPPER IS `RI-26`'s AND THE REUSE WAS MEASURED RATHER THAN ASSUMED.** That stripper is the naive two-replacement idiom, admitted by `RI-30` under its SQL window; `gates.mjs` carries a careful one that preserves string and dollar-quote bodies. The prototype of this fold was run with BOTH over this migration set and they produce identical output: **118 tables, 1,374 record columns compared, 5 silent, 3 findings**, either way. Reusing the reader beside the check therefore costs nothing measurable and saves a sixth SQL stripper, which is a class [ADR-279](ADR-279.md) already reports as unrepaired.

### 5. THE RULING, part three: what `wallet_entries.provenance` should say, and what the check demands about the CHECK

#### 5.1 The line, and why `null` alone would have been a worse record than `not null`

After `0080`, `provenance` is **not simply nullable**. `wallet_entries_provenance_follows_direction` makes it **required on a credit** and **null-or-`correction` on a debit**, and `0011`'s vocabulary CHECK still closes the member list at three. A record reading only `` null `` would have dropped the requirement entirely, and a reader building the first writer of a wallet row off that line would write a credit with no class and meet the constraint at run time. **That is a less true page than the one that said `not null`**, which at least asserted that the value is required.

**THE REPAIRED CELL STATES THE COLUMN'S OWN NULLABILITY FIRST AND THE CONDITIONAL REQUIREMENT BESIDE IT**, naming the constraint and the migration:

> `` null, **required on a credit** and null-or-`correction` on a debit (`wallet_entries_provenance_follows_direction`, `0080`), check in (`payout`,`refund_wallet_funded`,`correction`) ``

and the `Why` cell carries [ADR-322](ADR-322.md)'s reasoning at the line it applies to: the requirement did not go away, it became conditional on `direction`; a debit CONSUMES a composition rather than having one, so what a withdrawal destroys is the FIFO mixture in `wallet_withdrawals.source_provenance_summary` and not a scalar; and `correction` stays admissible on a debit because `0038`'s `ADJ-C3` REQUIRES exactly that row for a reversing adjustment. **The two purchases cells are repaired the same way**, keyed on `payment_method` because that is what `purchases_processor_columns_follow_method` keys on.

**NOTHING TRUE WAS DELETED FROM EITHER RECORD.** Both repairs are strictly longer than what they replace, and `purchases.md`'s `Constraints:` line gains `purchases_processor_columns_follow_method`, which `0081` added and the record never learned about.

#### 5.2 The check demands NOTHING about the CHECK, and here is the limit that buys

`RI-36` reads the column's own `NOT NULL` and nothing else. **After the repair, a cell reading merely `null` would pass it**, and the conditional requirement above is prose no check in this repository reads. That is stated here rather than left for a reader to discover from green.

**THE CONSTRAINT IS NOT UNGUARDED, IT IS GUARDED SOMEWHERE A TEXT COMPARISON CANNOT REACH.** [`probe_wallet_debit_provenance.sql`](../../scripts/db/probe_wallet_debit_provenance.sql) executes its semantics against PostgreSQL, five acceptances and five rejections, and was watched FAILING against `0001`..`0079` ([ADR-322](ADR-322.md) section 4); [`probe_purchase_processor_columns.sql`](../../scripts/db/probe_purchase_processor_columns.sql) does the same for `0081`, four acceptances and eight rejections, each matched by constraint NAME. `RI-24` requires every `scripts/db` assertion to be run by `corpus.yml` and pinned by `CI-06h`, and both are.

**THE THREE REASONS FOR STOPPING AT `NOT NULL`, in order of weight.** A CHECK's meaning is an EXPRESSION, and reading one out of the tree is an expression parser, which is a second hard thing to keep true for an assertion the probes already make better. The probes read a real database and this check reads the tree, so they fail in different directions and the tree-side one is the one that runs on every push. And the dispatch's own fence says nullability only. **The wider check is named as OWED and not attempted**: a record's declared TYPE, DEFAULT and constraint list against the DDL. Two of those three are cheap now that the fold carries the whole definition text, and the third is the expression parser. Whoever takes it should read section 4 first.

### 7. The directory sweep: what else it found, which was one class and not a third page

**RUN OVER THE WHOLE DIRECTORY: 1,374 columns compared across 118 design records against 118 tables folded from 75 migrations.** Findings: **three**, all of them the two records the row named. **There is no third stale page.**

**WHAT THE SWEEP DID FIND IS A READER DEFECT, AND IT IS THE MOST USEFUL THING IN THIS SECTION.** The first reader written for the document side tested the whole `Constraints` cell for `not null`. It produced **six** findings: the three real ones and **three against records that are TRUE**.

| Cell | Why it is true | What the naive reader saw |
|---|---|---|
| `account_adjustments.promotional_credit_grant_id`: `` null, unique where not null, fk `promotional_credit_grants` `` | the phrase belongs to an INDEX PREDICATE | `not null` |

**THOSE ARE THE TWO BEST-MAINTAINED NULLABILITY LINES IN THE DIRECTORY.** The `trading_calendar` cell is a record that already did, by hand, exactly what this row exists to make mechanical, and it cites `0032` while doing it. Working agreements section 9: never weaken a gate to pass it, and **if a true line trips the gate, the gate is wrong, not the line**. Both cells stand byte for byte and the reader moved: it splits the cell on TOP-LEVEL commas and reads the first term that speaks, so `fk identities, not null, on delete restrict` is NOT NULL and `null, unique where not null, fk ...` is nullable. Both cells are cases in the suite, and two more cases assert that they are the LIVE text of their own records so the argument is about this repository rather than about two strings.

**THE SECOND THING THE SWEEP FOUND IS SILENCE, AND IT IS A LEG RATHER THAN A REPORT.** **Five of 1,374 record rows state no nullability at all**, and all five are `GENERATED ALWAYS AS (...) STORED` columns whose cell spends itself on the expression: `live_account_state.intraday_movement_cents`, `notification_kinds.mutable`, `notification_kinds.rate_limit_exempt`, `reconciliations.delta_cents`, `reserve_coverage_snapshots.rcr_bp`. The sixth generated column, `report_schedules.cadence`, is `NOT NULL GENERATED` and its record says `not null`, so it is compared like any other.

**SO SILENCE IS A FINDING UNLESS THE DDL MAKES THE COLUMN GENERATED, AND THAT ADMISSION IS KEYED ON THE DDL RATHER THAN ON A WRITTEN LIST.** Without leg 2 this check is satisfied by **deleting two words from a row**, which is the repair a session under deadline reaches for and is exactly the failure [ADR-328](ADR-328.md)'s approval block worries about one control over.
