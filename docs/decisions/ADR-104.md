## ADR-104: the imbalance is unrepresentable, the posting path is a library both deployables call, and a halt is only a halt because this code path honours it  (2026-08-25, status: proposed)

**A ledger that can write an unbalanced transaction silently stops being a ledger, and the failure is discovered when a reconciliation cannot explain a balance, months later, with no record of which statement did it.** This entry rules the double-entry posting path: where it lives, what it guarantees that the database does not, what it relies on the database for, and the one thing it needs from [ADR-102](ADR-102.md)'s accessor that ADR-102 does not offer.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-i` row and section 15's prompt, session **216**. It is P3's first content and every other money content in the phase posts through it.

- **Context:** `0009_ledger.sql` has declared the chart of accounts, `ledger_transactions` and `ledger_entries` since the schema-delta fold, and `0027` has carried the deferred zero-sum trigger, `LEDGER-C1` and `LEDGER-C2` beside them. **Nothing in this workspace has ever written a ledger entry.** `packages/ledger` did not exist; `ledger_halts` was created by `0016` and was one of the four tables [ADR-092](ADR-092.md) section 9 said no session would reach.

---

### 1. THE RULING

> **1. THE IMBALANCE IS UNREPRESENTABLE AND NOT MERELY REFUSED.** An entry is never constructed. A `Transfer` is, and every transfer yields exactly two entries -- `+a` against the debit and `-a` against the credit -- so the legs of any posting sum to zero **arithmetically**, with no assertion doing the work. The guard is kept beside it and fires before the first `INSERT`, for the failure the claim depends on rather than for a caller.
>
> **2. IT IS A PACKAGE, AND `postTransaction` TAKES THE CALLER'S OPEN TRANSACTION AS ITS FIRST ARGUMENT WITH NO OVERLOAD THAT OMITS IT.** `packages/ledger` declares no dependency, cannot import a client, and therefore cannot open a pool. That is `job-queue.ts`'s ruling and [ADR-102](ADR-102.md)'s applied a third time, and here it carries [ADR-006](ADR-006.md)'s central consequence: the movement commits with the state change that caused it.
>
> **3. THE POSTING PATH DOES NOT RE-IMPLEMENT WHAT THE DATABASE ENFORCES.** It posts what the database will accept and it fails loudly when the database refuses. Section 4 is the line-by-line partition of which invariant belongs to which, and it is the section a reviewer should read first.
>
> **4. A LIVE `ledger_halts` ROW REFUSES THE POSTING, AND THE CHECK IS INSIDE `postTransaction` RATHER THAN BESIDE IT.** Nothing in the database honours that table. The override is a word from a closed one-member vocabulary, `'halt-remediation'`, on `sqlExecutor`'s precedent, because a halt that refused its own remediation is a halt somebody turns off.
>
> **5. MONEY IS INTEGER CENTS AS `bigint`, AND A `number` IS REFUSED AT RUNTIME AS WELL AS AT COMPILE TIME.** JSON has no other numeric type and `5.5` is exactly the value the constitution bans. Every generated value in `PT-03` is a `bigint` from `fc.bigInt`, so no `number` exists on this path at any point.
>
> **6. `ledger_halts` IS REGISTERED `owned` ON `identity_id`,** closing the first of [ADR-092](ADR-092.md) section 9's four orphans. Its class was never in doubt; what it lacked was a session whose fence contained it.
>
> **7. THE POSTING PATH NEVER OPENS A LEDGER ACCOUNT.** A reference that the chart does not hold is a refusal naming it. `0009`'s own argument decides it: "a class appearing first in a migration is a class nobody defined", and an account appearing first inside a posting is an account nobody opened.

### 3. Clause 1: what "unrepresentable" means here, stated precisely enough to be falsified

**The claim is narrow and it is exact.** `entriesOf` is the only function in this package that produces an `EntryDraft`, and its whole body is:

```
for (const t of post.transfers) {
  entries.push({ account: t.debit,  amountCents:  t.amountCents, memo: t.memo });
  entries.push({ account: t.credit, amountCents: -t.amountCents, memo: t.memo });
}
```

For any `transfers`, the sum is `Σ (a - a) = 0`. **There is no `Transfer` value for which that is false, including one assembled past both brands by a cast**, because the cast still goes through the same fold. The suite proves that over the worst forgery it can write: a `Posting` built as an object literal with two hand-written `__brand: 'Transfer'` legs still nets `0n`.

**SO THE GUARD IS NOT PROTECTING AGAINST A CALLER, AND SAYING OTHERWISE WOULD BE THE KIND OF CLAIM THIS CORPUS EXISTS TO CATCH.** `assertBalanced` is exported and runs immediately before the first `INSERT`, and what it protects against is a **later session that changes `entriesOf`**: a third leg shape, a netted amount, an adjustment entry with no counter-leg. Every type still compiles through that change and the arithmetic claim above silently stops being true. The guard turns that into a refusal at the last moment, and the suite drives it directly with a credit that has no debit so that it is watched refusing rather than assumed to.

**WHICH IS ACHIEVED, IN THE DISPATCH'S OWN TERMS: UNREPRESENTABLE, with a refusal kept for the failure that unrepresentability depends on.** Section 9's first mutation is that failure seeded, and it takes 26 of 57 tests with it.

**NETTING IS REFUSED AND THAT IS A DECISION.** Collapsing `A -> B` and `B -> C` into `A -> C` balances, satisfies `LEDGER-C1`, and erases the middle position's movement from the books. `0009`'s C-01 reversal is exactly that class of error surviving because the arithmetic still worked: "the ledger reconciles perfectly and the balance is wrong."

### 5. Clause 4: the halt, and the finding that it has never been enforced by anything

**`0016` creates `ledger_halts` under [ADR-016](ADR-016.md) and `INV-M5-16` and argues the design in its own comment:** a single identity's position failing a check "is not" a stop-the-world event, "halting the firm for it is an outage; ignoring it is a leak", so the ruling is a scoped halt with a subject, a start and a deadline.

**WHAT IT CARRIES IS NO ENFORCEMENT AT ALL.** `grep -n 'TRIGGER' packages/db/migrations/0016_treasury_controls.sql` returns nothing. A halted identity's accounts can be posted against all day and every constraint stays green. **The table's own escalation index calls itself "the read every payout and withdrawal path makes before it moves money for this identity" -- a read, made by a code path, and until this entry no code path made it.** Section 10's round trip executes both halves: the path refuses, and the same posting with the path bypassed commits with the halt still live.

**THE CHECK IS INSIDE `postTransaction` AND NOT BESIDE IT**, because a separate `assertNotHalted` a caller is asked to remember is the shape [ADR-008](ADR-008.md) rejects for scoping and [ADR-102](ADR-102.md) rejects for the write path: a control that is a convention at each call site.

**THE OVERRIDE IS A WORD AND NOT A BOOLEAN.** Releasing a halt frequently requires posting a compensating entry, because `SD-M5-05` rules that a correction is a new transaction and never an update, so a halt that refused its own remediation is a halt somebody turns off. `{ despiteHalt: 'halt-remediation' }` is a closed one-member vocabulary on `sqlExecutor`'s and `systemDb`'s precedent, so "posted through a live halt" is a diff a reviewer reads. **It closes the accidental door and not the deliberate one**, which is the limit `job-queue.ts` and `VG-4` both state about themselves.

**A FIRM-ONLY POSTING IS NEVER BLOCKED**, which is `0016`'s own partition kept: a halt names a subject and the firm-wide stop is an incident rather than a row.

### 6. THE FINDING THIS SESSION DID NOT EXPECT: a `ledger_transactions` row with no entries commits clean

**`ledger_entries_zero_sum` is `AFTER INSERT ON ledger_entries`. A transaction with zero entries fires it zero times.** Nothing else requires a transaction to have entries. So the following is accepted by this database today, executed and confirmed in section 10 case 5:

```sql
INSERT INTO ledger_transactions (kind, reference_kind, reference_id, idempotency_key)
VALUES ('empty','purchase',$1,'rt-empty');   -- COMMITS. One row, no entries, no error.
```

**THIS IS [ADR-101](ADR-101.md) SECTION 7's OPEN FAILURE CLASS WITH A PRODUCER RATHER THAN A HYPOTHESIS.** That entry says the `semi-join` on `ledgerTransactions` "rests on the same unstated property" -- that every parent has a child -- and that "SQL declares the first and has no way to declare the second". Here is a shape the database accepts that makes the property false, reachable by any raw statement, and the round trip left one such row standing on purpose so the count could be reported: **1**.

**`posting()` REFUSES IT AND THE DATABASE DOES NOT.** That is the one shape of the open class this entry can close, and it closes it only for callers who use this path.

**THE REMEDY IS NAMED AND NOT BUILT.** A `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED AFTER INSERT ON ledger_transactions` asserting `EXISTS (SELECT 1 FROM ledger_entries WHERE transaction_id = NEW.id)` would refuse it at commit, in the database, for every writer. **That is a migration, `0048` is the lowest free number, and [P3 wave 3](../plans/P3-wave3-modules.md) section 15 says no slice in this wave is dispatched with one.** So it is reported and not taken, which is that instruction honoured rather than argued with.

### 7. Which of ADR-101's failure classes this path can suffer, asked because the dispatch asked it

| Class | On this posting path |
|---|---|
| **1. A rule answering a different question from the row's own identity column** | **CANNOT ARISE.** This path evaluates no scope predicate at all: `SystemTx.insert` renders an `INSERT` with no `WHERE` |
| **2. A nullable edge** | **CANNOT ARISE**, for the same reason |
| **3. A `semi-join` on a non-total reverse edge** | **THE PATH CANNOT SUFFER IT AND IT IS THE PATH'S POPULATION THAT SUFFERS IT.** `LedgerTx` names no `UPDATE` and no `DELETE`, so the statement that could return or destroy a subset does not exist here whatever authority the injected handle carries. But the rows this path writes are exactly the rows a scoped read of `ledger_transactions` traverses, and ADR-102 records that a `DELETE` through that rule "deletes a subset and leaves the rest". **This entry is the producer of that population and it does not close the class.** What it does close is the extreme case, section 6's zero-entry transaction, and only for its own callers |
| **4. Re-parenting** | **CANNOT ARISE.** A re-parent is a `SET` on a tenancy column and this path issues no `UPDATE` |

**So the honest answer is: three of four cannot arise because this path only inserts, and the fourth is inherited in the direction ADR-102 already named as the one that destroys.** The uncovered one is [ADR-101](ADR-101.md)'s and the remedy that entry prices -- an attestation on reverse-edge rules -- edits `ledgerTransactions`' row in [`scope.ts`](../../packages/db/src/scope.ts), which is outside this fence.

### 8. What ADR-102 does not offer, reported rather than routed around

**The dispatch said: if the posting path needs something the accessor does not offer, that is a finding for the pull-request body and possibly a superseding entry, never a second door. It needed two things.**

#### 8.1 THE REASON PROBLEM, AND IT IS THE ONE THAT BLOCKS A LATER SLICE

A double-entry posting touches two parties' accounts by construction, so no single-identity handle can write it, and [ADR-102](ADR-102.md) section 8 foreclosure 2 says so about this slice by name. **`firmDb()` cannot serve it either**: `FirmTx.insert` accepts `FirmTableKey` and both `ledgerTransactions` and `ledgerEntries` are `derived`. That leaves `SystemTx`, whose vocabulary is exactly `'nightly-batch' | 'operator-console'`.

**A CHECKOUT POSTING FROM `apps/api` IS NEITHER OF THOSE WORDS.** ADR-102 clause 3 found the identical gap on the READ side -- "a request handler is neither `SystemReason`" -- and answered it with `firmDb()`, a door that does not reach these tables. **On the write side the gap is open and this entry does not close it**, because a `packages/ledger` that invented its own door would be the accessor routed around by the one library every money movement goes through.

**IT BLOCKS NOTHING TODAY AND IT BLOCKS `P3-n` (session 220).** The reason is chosen by whoever opens the transaction, which is the caller: `apps/worker`'s nightly batch writes `'nightly-batch'` honestly, and checkout has no honest word. The three readings and their prices, so that the session that hits it does not re-derive them:

- **A third `SystemReason` member.** Refused by ADR-102 section 7 on ADR-096's own argument, **and on a finding that entry adds**: the reason names the CALLER and the key type names the REACH, and they are not connected, so `systemDb('request-handler')` reads and now writes `accounts` and `wallet_entries` firm-wide.
- **A fourth door**, `postingDb()`, narrowed to the three ledger keys. It is the shape `firmDb()` already set and it is the reading this session would take if the decision were its to take. It is a diff on [`scoped-db.ts`](../../packages/db/src/scoped-db.ts).
- **`INSERT ... SELECT ... WHERE EXISTS`,** the construction ADR-102 section 4 names, priced and did not build. It does not help here: the two legs belong to two different identities, so there is no single parent predicate to check.

**`accessor-bind.test.ts` WATCHES THE VOCABULARY.** It asserts `SystemReason` is still exactly two members, so the day a third lands, this finding is closed by whoever added it rather than rediscovered.

#### 8.2 THERE IS NO READ THAT CARRIES A PREDICATE

`rows(key)` renders `SELECT * FROM t` with no `WHERE`. Resolving one posting's four references therefore reads **the whole chart of accounts**, which is four firm rows plus up to three per identity and grows with the trader population rather than with the posting; the halt check reads **every halt row ever written**, and released halts accumulate without bound.

**THE PATH DOES NOT REACH AROUND IT AND IT DOES NOT PRETEND THE COST IS NOTHING.** `readChart` is separated from `postTransaction` and returns a value, so the read happens once per caller-chosen window: the nightly batch reads the chart once and posts thousands of transactions against it. **The cost is stated in [`chart.ts`](../../packages/ledger/src/chart.ts)'s own header, at the call site, rather than only here.** The remedy is a predicate-carrying read on ADR-102's handles, which is a diff on `packages/db` and outside this fence.

### 11. `PT-03`, and what makes the aggregate half not a restatement of the per-transaction one

**[STRATEGY](../testing/STRATEGY.md) section 3.1 rows `PT-03` as "ledger zero-sum, per transaction and in aggregate" and says why the second half is the subject: "per-transaction is a deferred constraint in the database, so this property tests the aggregate the constraint cannot see."**

`0027`'s trigger reads `WHERE transaction_id = NEW.transaction_id`. It knows nothing about any other transaction, so **a database in which every individual transaction balances and the ledger as a whole does not is one that trigger reports as healthy**. The property is asserted over the `ledger_entries` rows the writer **was asked to insert** rather than over `entriesOf`'s output, so a path that dropped a leg between the value and the `INSERT` fails here and a property over the value type alone would not.

**THE PROPERTY IS WATCHED NOT BEING VACUOUS.** A generator that produced nothing, or a fold that emitted no entries, would leave every assertion green. One test counts what actually ran and requires more than 100 postings, more than 200 entries and more than 20 multi-leg postings across the run.

**`GS-231` STAYS `blocked / no-fixture-format`.** It is `PT-03`'s golden pair and carries the per-identity assertion; a property and a fixture are not the same artifact and [section 39](../testing/golden-scenarios/39-fixture-status-and-blockers.md) is untouched.

### 13. What this FORECLOSES

1. **A posting outside a transaction is unavailable, permanently.** ADR-102's foreclosure 1 inherited and made concrete for the path every money movement takes.
2. **The posting path never opens a ledger account**, so an identity's `trader_wallet` must exist before anything can be posted to it. The first caller that needs one must open it under a `scopedTx` bound to that person, in its own act, and that act does not exist yet.
3. **A posting cannot be netted**, and a caller that wants `A -> C` for a movement that really passed through `B` has to write both legs.
4. **`LedgerTx` names no `UPDATE` and no `DELETE`**, so a correction is a compensating entry forever. That is `SD-M5-05` and `0009`'s append-only rule made structural rather than conventional, and undoing it is a diff on the port.
5. **The halt override is one word wide.** A second legitimate reason to post through a live halt is a diff on [`halts.ts`](../../packages/ledger/src/halts.ts), which is `sqlExecutor`'s cost accepted for the same benefit.
6. **`LedgerTx` restates `SystemTx`**, so a rename in `packages/db` fails a test in `packages/ledger` and the two must move together. The alternative was a dependency edge and clause 2 rules against having one.
7. **The chart is read whole, and every caller now has a window to choose.** A caller that reads it once per posting is correct and slow; one that reads it once per batch is fast and can miss an account opened during the run. **That choice did not exist before this entry and now every caller makes it, including by not thinking about it.**
8. **`ledger_halts` is registered, so it is now reachable through a scoped read** -- which is what a trader-facing "why is my payout frozen" surface would read, and this entry rules nothing about whether it should.
