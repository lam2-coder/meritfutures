### 2. The scope decision, argued rather than assumed

The dispatch put two readings and leaned to the first. **The first is taken, and the argument below is narrower than the dispatch's framing because measuring the tree made it narrower.**

**(a) THE ENQUEUE HALF. TAKEN.** The saga's `ProvisioningJobQueue` gets one live implementation over `LIVE_QUEUE`, and `PROVISIONING_QUEUE_NAME` gets a way to be declared.

**(b) THE ENQUEUE HALF PLUS A CONSUMER. REFUSED, AND NOT ON SIZE.** It is refused because taking it here would mean overturning two rulings from a third one's chair:

1. **THE DOOR'S NARROWING IS [ADR-241](ADR-241.md) AND NOT A SIMPLIFICATION.** This deployable is a ONE-SHOT JOB: `src/start.ts` awaits `main()` and exits, and the exit code is the only signal. `start()` installs pg-boss's sixty-second supervise interval and holds the event loop open, so a one-shot process that started one would either exit before the first pass fired or HANG, which is the defect `closeWorkerDb`'s docblock names in its own words. `consume` is the same refusal one method over: a consumer is a process that stays up.
2. **A CONSUMER MEETS THE EMITTER GAP BEFORE IT MEETS ANYTHING ELSE.** pg-boss reports a supervise failure on an `EventEmitter` that `pgBossQueue` does not expose, so a process that starts one and hits a failure gets an unhandled rejection naming a line in a vendor's `dist` with nothing naming the queue. [ADR-331](ADR-331.md) section 10 item 3 recorded it, [ADR-332](ADR-332.md) section 10 item 2 recorded it again, and surfacing it is a **SIXTH method on `JobQueue`**. [ADR-165](ADR-165.md) clause 5 and [ADR-331](ADR-331.md) section 4 clause 4 both rule that an interface change is taken by a row whose OBJECT it is; taking it here would be taking it as a MEANS.

**AND `test/queue.test.ts:146` IS NOT EDITED.** That `Object.keys` assertion exists so that widening the door is a decision somebody records rather than a diff that passes. Nothing in this row widens it, so nothing in this row touches it.

**WHAT MEASURING THE TREE CHANGED ABOUT (a).** The dispatch describes (a) as *"pass the door to the saga in production"*. There is no production run of the saga to pass it to, and there cannot be one this row could reach. `runProvisioningSaga` takes FOUR ports:

| `PlatformProvisioningPort` | absent | `packages/rithmic/src/index.ts` *"declares it and implements none of it"*, and its two signatures disagree with M02's |
| `ProvisioningAdvancePort` | **BLOCKED** | `SystemTx.update` renders `update "provisioning_queue" set "status" = $1` with **no `WHERE` clause** and no argument gives it one ([ADR-102](ADR-102.md)) |

So (a) is **one port of four**, and the other three are named in `src/index.ts`, in `provisioning/ports.ts` on their own declarations, and in `schedule.ts`'s registry row. ### 3. What the adapter is, and why it is not an assignment

**`export const LIVE_PROVISIONING_QUEUE = LIVE_QUEUE` WOULD HAVE TYPE-CHECKED.** `JobTransaction` and `ProvisioningSqlExecutor` are the same one-method shape, `JobPayload` is `Record<string, unknown>`, and `JobId` is a branded `string` that widens on the way out. It is refused for two reasons that outlive the compiler.

1. **IT WOULD HAND THE SAGA `declareQueue`.** The saga's port names ONE method. `declareQueue` runs on the CONSTRUCTOR's executor, which is the pool, and the saga runs inside a caller's open transaction; a value carrying both lets a step inside the pipeline reach the wrong one. The narrowing is an **object literal and not a cast**, which is `workerQueue()`'s own stated reason: the value HAS one property rather than merely being typed as having one, and `Object.keys` is asserted.
2. **IT WOULD BE INVISIBLE TO THE CHECK THAT WATCHES FOR IT.** See section 5.

**`declareProvisioningQueue` IS PART OF THE ENQUEUE HALF AND NOT AN EXTRA.** pg-boss **refuses an undeclared queue**, which is why `JobQueue` carries `declareQueue` at all, and `0079_pgboss_job_store.sql` section 3 says in its own words *"IT CREATES NO QUEUE AND ENQUEUES NOTHING. `pgboss.queue` ships empty"*. So `PROVISIONING_QUEUE_NAME` names a queue that exists in no database this repository can build, and an adapter shipped without a way to declare it would be an enqueue path whose first live call fails. It takes the door as an argument with **no default**, and it is a separate function rather than a lazy declare inside `enqueue`, because folding one into the other would put a pg-boss `locked()` plan carrying its own `BEGIN ... COMMIT` in front of a money-path transaction, which [ADR-331](ADR-331.md) section 5 measured.

**IT MINTS NO QUEUE NAME AND IT REACHES NO SECOND DOOR.** `PROVISIONING_QUEUE_NAME` is declared once, in `saga.ts`. The adapter imports `../queue.ts` and no workspace package, so `test/queue.test.ts`'s *"exactly one file under src imports `@merit/queue`"* and `test/db.test.ts`'s *"exactly one file imports the accessor"* both still read one-element lists. **`WORKER_BARREL_LEGS` does not move**: the adapter rides the `./provisioning/index.ts` leg, and the count is **31 legs, 8 modules behind a leg, 4 not re-exported, 43 accounted against 44 `.ts` files under `src/` plus the barrel itself**, derived at the moment this line was written.

### 4. What stops the job store growing, stated plainly because the answer is thin

**NOTHING DRAINS `pgboss.job`, AND NOTHING IN THIS DEPLOYABLE MAY.** The door withholds `consume`, `start` and `stop`, and `test/queue.test.ts` asserts over the tree that no module here calls the first two.

**WHAT STOPS THE STORE GROWING TODAY IS THAT NOTHING ENQUEUES.** No module under any `src/` calls the adapter or the saga: `test/queue.test.ts`'s last case reads that off the tree, excluding the adapter's own module and the two barrels that re-export its names, and it is written so that **the day a caller lands this case goes red**.

**THAT IS A FACT ABOUT THE TREE AND NOT A CONTROL, AND IT EXPIRES.** Stated in the words the row was asked to state it in: **there is no mechanism in this repository that would bound `pgboss.job` if a caller landed tomorrow.** No retention job, no archive pass, no maintenance schedule, and no `deleteAfter` that runs, because every one of those is pg-boss's maintenance and pg-boss's maintenance runs under `start()`.

**SO THE ROW THAT GIVES THE SAGA A CALLER OWES A DRAIN, OR OWES THE ARGUMENT FOR RUNNING WITHOUT ONE**, and it meets the failure channel first. That obligation is written into `queue-adapter.ts`'s header, into `src/index.ts`, into `queue.ts`'s amended paragraph and into `schedule.ts`'s registry row, so a session reading any of the four finds it.

### 5. THE HEADLINE FINDING: the invariant written to fail on good news could not see the good news, and could see a sentence about it

`RI-35`'s `worker-queue-door-caller` probe was written by [ADR-333](ADR-333.md) to flip the day somebody wired the door. **It was wrong in both directions at once, and both were measured rather than reasoned.**

An adapter takes a door as an **ARGUMENT** -- `provisioningJobQueue(LIVE_QUEUE)` -- which is `postgresBatchPorts(io.db)`'s arrangement one capability over and the ordinary way a door reaches an adapter in this estate. **Written as it stood, the probe would have reported `absent` over the very row that falsified its claim**, holding a `live` claim true past its own falsification, which is the defect `RI-35` exists to prevent arriving inside `RI-35`. **FALSE POSITIVE, FOUND BY FALSIFYING THE WIRING, AND IT IS THE WORSE HALF.** The probe read **RAW text**. `queue-adapter.ts`'s header names `workerQueue(` in order to explain what the file does not do. So with the **wiring deleted by hand** -- the `LIVE_QUEUE` import removed and the live constant built over a stub -- the probe still reported `present` and **`RI-35` still passed at 35 of 35**. That transcript is in section 7. An absence check going green over an emptied file is the worst direction a defect can fail in, in `strip-comments.mjs`'s own words, and it had arrived inside the check written to prevent it.

**THE REPAIR IS `RI-30`'s OWN RULE APPLIED TO THIS FILE.** `RI-30` bans a second comment stripper and requires that every file which parses source import the shared one; `absence-claims.mjs` parses source in two probes, so it was on the wrong side of that rule rather than exempt from it. The header sentence that said no stripper is written or imported is amended with its correction beside it.

### 9. The open question this row did not reach

**THE DRAIN, AND IT IS ONE QUESTION WITH AN ORDER INSIDE IT.** Somebody must consume `provisioning` jobs and run pg-boss's maintenance. That row cannot start at the consumer, because:

1. **THE FAILURE CHANNEL COMES FIRST.** A supervise pass reports its failures on an emitter `pgBossQueue` does not forward, so a consumer built today fails into a vendor's `dist`. That is a sixth method on `JobQueue` and it is `packages/queue`'s row.
2. **THE PROCESS SHAPE COMES SECOND.** A consumer stays up; `apps/worker` is one-shot by [ADR-241](ADR-241.md), and its exit code is the only signal a supervisor reads. A drain is either a second deployable or a ruling that reopens `ADR-241` for this one.
3. **AND THE SAGA'S OTHER THREE PORTS ARE INDEPENDENT OF BOTH.** The platform adapter is `packages/rithmic`'s; `ProvisioningAdvancePort` and `ProvisioningReadPort` need a write path that can name a row, which is [ADR-102](ADR-102.md)'s open `semi-join` class seen from the other side and is a `packages/db` row.

**IT IS NOT REACHED HERE BECAUSE REACHING IT MEANS TAKING THREE OTHER ROWS' SUBJECTS AS A MEANS**, which is the rule this row's own subject was created by.
