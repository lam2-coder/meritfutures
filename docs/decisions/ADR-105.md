## ADR-105: the PSP port is the ORDER and the vendor is the mechanics, and two fakes are what told them apart  (2026-08-25, status: proposed)

**[M03](../plans/M03-billing-checkout.md) section 2.1 sketched a five-method interface and stated three rules for it. This entry implements the interface, and reports that one of the three rules cannot be honoured as written, that a second is honoured by a mechanism the sketch does not contain, and that the third moved three times while a SECOND implementation was being written against it.** The vendor is unselected, no network is opened, no dependency is added and no row is written.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-m` row and section 15's prompt, session **217**. That row cites [session 157](../sessions/2026-08-24-session-157.md)'s `M3-h` verbatim. **MONEY PATH by subject**, and it opens no network and writes no row.

- **Context:** `packages/psp` did not exist. `POST /webhooks/psp/:provider` (session 219), `POST /checkout` (session 220) and the dispute path do not exist either, and all three program against this port, which is the entire reason it is written before any of them.

### 2. THE RULING

> **1. THE PORT OWNS THE ORDER. THE ADAPTER OWNS THE MECHANICS.** `verifyHmacWebhook` runs digest, then freshness window, then parse, once, for every provider. What a provider supplies is an `HmacWebhookScheme`: which headers carry what, how the MAC is encoded, what bytes go into the digest, and which body fields are the event id and type. **No adapter re-implements the ordering and no adapter can reach the parse without the digest having agreed.**
>
> **2. `verifyWebhook` THROWS, AND THE THROW CARRIES THE PROVIDER AND THE RAW BYTES.** M03's rule that a boolean gets ignored is kept exactly. Finding 4 is why the error is not bare: `WebhookVerificationError` carries `psp`, a `refusal` from a CLOSED set, and `raw`, so the catch block can write the `signature_verified = false` row the schema requires. **Carrying them softens nothing: nothing is parsed, nothing is trusted, and `raw` is the bytes that arrived.**
>
> **3. THE PARSE IS INSIDE THE VERIFIER AND THERE IS NO OTHER PARSE.** `verifyWebhook` is the only exported function in this package that returns a parsed webhook body. API_CONTRACT section 10's ordering is therefore a MODULE BOUNDARY rather than a convention a handler could get wrong: there is no parsed body to be had without it.
>
> **4. THE NONCE MUST BE COVERED BY THE SIGNATURE. IT NEED NOT BE A HEADER.** It is resolved with the event identity, after the digest, and may come from a header or from the verified body. Section 5 is the finding this clause came out of.
>
> **5. NO ADAPTER METHOD TAKES A PRICE, AND THE MECHANISM IS A BRAND.** `CardAmountCents` is a branded `bigint` with exactly one producer, `cardLegOf`, which takes a `purchases` row and returns `amount_paid_cents - wallet_debit_cents`. **A wallet-funded row is REFUSED rather than returned as zero**, which is `INV-M3-13` kept: a wallet purchase commits with its debit and reaches no processor at all.
>
> **6. AN ADAPTER REPORTS AND NEVER DECIDES.** `health()` returns `{ reachable, latencyMs }` and never a `mid_health.state`. `RefundResult.providerStatus` is `'pending' | 'succeeded'` and is deliberately NOT `payment_disputes.outcome`'s `'lost' | 'won' | 'refunded'`, so nothing can pass one where the other is meant.
>
> **7. THE ONLY ROUTING FUNCTION IS NAMED FOR THE ONLY LEGITIMATE MOMENT.** `chooseMidForNewAttempt` reads the decision record and never probes. **There is no function that moves a live session between providers**, which is AS-M3-02 expressed as an absence rather than as a warning.
>
> **8. THE PACKAGE OPENS NO SOCKET AND NAMES NO VENDOR.** The two implementations of the I/O methods are fakes and say so. `psp_a` and `psp_b` are the schema's words for the two MIDs, and M03 section 7.9.1 already rules the procurement criterion, so this entry neither chooses a vendor nor forecloses one.

### 3. The three deviations from M03 section 2.1's sketch, each with its reason

**The sketch is a specification of the SHAPE and this entry follows it. Three signatures differ, and each difference is reported rather than absorbed.**

| Sketch ([M03:87-92](../plans/M03-billing-checkout.md)) | Implemented | Why |
|---|---|---|
| `verifyWebhook(raw: Buffer, ...)` | `raw: Uint8Array` | `Buffer extends Uint8Array`, so every `Buffer` a caller holds is accepted and nothing narrows. The wider type keeps a Node-only class out of a port's public surface, which matters because a port is what a second runtime would be ported to. **No caller loses anything and none has to convert** |
| `verifyWebhook(..., headers: Headers)` | `headers: WebhookHeaders`, a readonly record | `Headers` is the web class; a Node HTTP server hands a handler `IncomingHttpHeaders`, which is `Record<string, string \| string[] \| undefined>`. Requiring the web class would put a conversion at every call site, and **the conversion that picks `[0]` out of a repeated signature header is the header-smuggling hole this package refuses by name** (`signature_header_repeated`) |
| `PurchaseIntent` carries a `purchase_id` and "the amount is read from the purchase row" | `PurchaseIntent` carries `purchaseId` AND a branded `cardAmountCents` | **The sketch's literal reading cannot be implemented.** An adapter that read the purchase row would need a database dependency and a money read inside the package whose whole job is to isolate a vendor. What is honoured is the rule's REASON: `INV-M3-02`'s enforcement is "the Zod schema has no price field at all. **The absence is the control**", and the failure it names is a number travelling from a request body to a processor. The brand makes that number unspellable |

**The third row is a genuine gap in an approved document and is reported as one.** It is not proposed as an amendment here, because the rule's intent is met and an ADR that edits a frozen plan to match an implementation is the wrong direction of travel.

### 4. What writing the SECOND fake changed, which is the whole argument for writing it

**A port with one fake is a port shaped like that fake.** The brief for this session put it as a test: *"if the second fake is uncomfortable to write against your port, the port is wrong and that discomfort is the finding."* It was uncomfortable three times.

| # | What the port said after one fake | What the second fake could not do | What it says now |
|---|---|---|---|
| **1** | `PresentedSignature` carried a `nonce`, read from a header beside the timestamp, which is how API_CONTRACT section 10 reads if you read it quickly | **One of the two real shapes has no nonce channel at all.** Forcing that shape to supply a nonce before the digest means inventing one, and an invented nonce is a replay control that protects nothing | The nonce is resolved WITH the event identity, after the digest, from a header or from the verified body. **What is required is that it be covered by the signature**, and both shapes satisfy that for different reasons: one because the MAC spans the nonce header, the other because the MAC spans the body the nonce is read out of |
| **2** | `RefundResult` had no status. A refund returned meant a refund done | **One provider acknowledges and settles on a later webhook.** It would have had to report `succeeded` for something that had not happened | `providerStatus: 'pending' \| 'succeeded'`, and nothing in the port treats a returned refund as money moved |
| **3** | The port built the signed byte run from the headers, because one provider joins timestamp to body with a `.` | **The other joins timestamp, nonce and body with newlines.** A shared builder would have had a provider-shaped branch inside it, which is the drift M03's second rule exists to prevent | `signedBytes` is the adapter's. Only the ORDER of the checks is Merit's |

**What did NOT move is the other half of the result and is the part worth signing.** `verifyWebhook` still throws rather than returning a boolean, still refuses before parsing, and still returns nothing the digest did not cover. **Two providers with no mechanical detail in common agree on all three**, so those three are the port rather than one vendor's habit.

**The two fakes are asserted to be different, so the shared table is not proving something vacuous.** They share no header name (one against three), share no body field name, neither can verify the other's webhook, and they disagree about whether a refund has settled. Every port case in `port.test.ts` runs over both from one table; a third adapter is one line, and the day it is a real one that file is its acceptance suite.

### 6. What this entry FORECLOSES

**Section 13 rule 8 of the dispatching plan asks for this half explicitly, and these are decisions this project lives with for years.**

1. **A THIRD PSP IS A MIGRATION.** `PspId` is a closed union and `purchases.psp` is a CHECK constraint. Adding `psp_c` requires a migration, and a migration is `E2`. **That is the intended cost**: `RB-03`'s MID-freeze runbook is written for two, and a third MID is a commercial decision rather than a type edit.
2. **NO CALLER WILL EVER HOLD AN UNVERIFIED PARSED BODY FROM THIS PACKAGE.** Adding a `parseWebhook` export later would be adding the exact door API_CONTRACT section 10 exists to close, and `port.test.ts` fails by name if one appears.
3. **NO SECOND PRODUCER OF A `CardAmountCents`.** A future path that needs a partial refund, or an amount from somewhere other than a purchase row, has to add a producer, and that addition is a visible diff on the money path rather than an argument at a call site. **Partial refunds have no producer today and that is deliberate**: `payment_disputes.amount_cents` exists, the dispute path does not, and a primitive admitted before a caller exists is a primitive nobody can remove ([`job-queue.ts`](../../packages/queue/src/job-queue.ts)'s own rule).
4. **MERIT CANNOT MOVE A LIVE SESSION BETWEEN PROVIDERS.** There is no function for it. A caller that wants one finds a compile error rather than an incident, which is AS-M3-02 priced at the interface.
5. **AN ADAPTER CAN NEVER DECLARE ITSELF UNHEALTHY.** `health()` returns a probe. Failover therefore cannot be driven from a live call, which means it also cannot be driven from inside checkout's transaction, and `mid_health` stays the record SD-M3-03 requires it to be.
6. **THE FRESHNESS WINDOW IS CHECKED IN BOTH DIRECTIONS, PERMANENTLY.** A future-stamped capture that never expires is refused. A provider whose clock runs ahead will therefore fail rather than degrade quietly, and that is the trade this entry takes.

**Nine mutations were seeded into [`webhook.ts`](../../packages/psp/src/webhook.ts) and watched. SIX WERE CAUGHT ON THE FIRST PASS AND THREE SURVIVED, and the three are reported as findings rather than rounded up.**

| Mutation | Caught, of 69 |
|---|---|
| The MAC comparison is removed | **7** |
| The MAC length guard is dropped | 1, **after a case was written for it** |
| The freshness window is not checked | 2 |
| A repeated signature header resolves to `[0]` | 2, **after a case was written for it** |
| The window is checked in one direction only | 1 |

| A non-object top-level JSON value is accepted | 1 |

**The three survivors, and why each mattered.**

- **The MAC length guard.** No case presented a well-formed MAC of the wrong size. `timingSafeEqual` THROWS on a length mismatch rather than returning `false`, so without the guard this path raises a bare `TypeError`: the route's catch block sees something that is not a `WebhookVerificationError`, cannot tell it is a signature refusal, and returns **500 where the contract requires 401 and a security event**.
- **The repeated header.** The existing case seeded `[good, bad]`; a `found[0]` implementation is only refused for the right reason if `[bad, good]` is seeded too. Both are now.
- **The tolerant decoder.** The obvious invalid-UTF-8 body also fails `JSON.parse`, so it refused for the second reason and the mutation hid behind it. **The case that separates them is a body whose bytes are invalid UTF-8 and which still parses once U+FFFD is substituted**: that event verifies under a tolerant decoder, and `payload` then holds a replacement character where `raw` holds `0xFF`. Two representations of one signed event disagreeing is the shape a dispute is argued from, and the raw bytes are the ones the schema stores.

**`webhook.ts` was diffed byte-for-byte against a pre-seed copy after every mutation and restored. `falsify:ci` was not run.**

### 9. What this entry does NOT do, named rather than implied

**No route, no network, no vendor SDK, no dependency, no migration, no migration number, no `CI-06` letter, no gate register row, no `VG` row, no `RI-nn`, no `SD-nn`, no `OI-nn`, no fixture and no edge-case entry.** Nothing under [`apps/`](../../apps/api/src/server.ts) is touched and nothing in [`packages/db`](../../packages/db/src/schema.ts) is touched, which is why this ran beside sessions 214, 215 and 216 with no shared file.

**`scripts/corpus/gates.mjs` IS NOT EDITED, AND THAT IS A FENCE DECISION WITH A REPORTED CONSEQUENCE.** [Session 157](../sessions/2026-08-24-session-157.md)'s `M3-h` row put `gates.mjs` (`CI06O_SCOPE` only) inside this slice's fence and [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-m` row does not. **The plan wins by its own instruction and by the dispatch's, and the consequence is measured rather than assumed:** `CI06O_SCOPE` is `['packages/rules-engine']` and `CI-06o`'s discovery half recognises a money path by directory name against `MONEY_PATH_WORDS`, which is `['rules-engine', 'payout', 'ledger', 'auth']`. **`psp` is in neither**, so the gate neither covers this package nor reports that it is missing, and `gates.mjs check` is 30 of 30 unchanged. **`packages/psp` is money path by subject and is scanned by nothing for a model-SDK import.** The remedy is one array element in a file this fence excludes.

**`payment_disputes` IS READ AND NOTHING IS BUILT AGAINST IT.** The dispute path is not this slice, `RefundResult.providerStatus` is deliberately spelled in a different vocabulary from `payment_disputes.outcome` so the two cannot be confused, and partial refunds are foreclosed rather than implemented (section 6 item 3).

**`mid_health` IS READ AND NO ROW IS WRITTEN OR PROPOSED.** `chooseMidForNewAttempt` takes the state as an argument. Who computes the state, on what window, and who writes the transition is SD-M3-03's and belongs to whichever slice builds it.

**NO REPLAY STORE.** The nonce is surfaced and recorded by the caller. `psp_webhook_events` and its `(psp, provider_event_id)` unique index are session 219's, and a replay store inside a port would be a port that holds state across requests.
