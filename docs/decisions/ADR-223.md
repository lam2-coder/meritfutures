## ADR-223: the constitution's `strict CSP/HSTS/frame-deny`, taken at the origin on all four surfaces, with `script-src`'s one weakness named and priced rather than papered over  (2026-08-29, status: proposed)

**`MERIT_BUILD_MASTER_PROMPT.md` Appendix D section D2 rules `strict CSP/HSTS/frame-deny` among the binding application controls, and nothing in this repository set any of the three on any surface.** [The D2 controls audit](../reviews/2026-08-29-d2-controls-audit.md) row `D2-8` measured that and measured the half that makes it worse: **no test anywhere asserted any security header**, so none of it would have failed if it had been added and later removed. **This entry discharges both halves.** Three `next.config.mjs` gain a `headers()`, `apps/api` gains a hook beside [ADR-221](ADR-221.md)'s, and four test files assert every header on every surface.

**WHAT MADE THIS THE HIGHEST-VALUE ROW ON THE BOARD RATHER THAN A MISSING FORMALITY.** [`M06:46`](../plans/M06-admin-ops-console.md) is `INV-M6-02`, a **BINDING MODULE INVARIANT**: *"The admin origin shares no cookie, no CORS policy, and no CSP with any public surface"*. [`INFRA:71`](../architecture/INFRA.md) draws the conclusion the whole admin separation rests on: *"Cookie scope, CORS, and the CSP never span the two origins, so an XSS on the portal cannot reach the admin surface **even in principle**."* Four shipped `.ts` files restate it. **A separation that holds "even in principle" is a claim about a header, and there was no header.** The audit ranked this above `zod` for exactly that reason and this entry agrees.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `223`, session **413**, dispatched as `claude/security-headers-are-set-by-nothing`. The row is **RESERVED, REQUIRED** and the number is spent.

- **NOT THE MONEY PATH BY FILE, AND ONE FILE IN IT IS ON THE MONEY PATH'S ROAD.** No migration, no ledger account, no rule. But [`apps/api/src/server.ts`](../../apps/api/src/server.ts) is the file every money route passes through and this entry registers a hook **ahead of** ADR-221's CSRF check in it. **The `E2` read is owed on [`apps/api/src/security-headers.ts`](../../apps/api/src/security-headers.ts) and on the two `addHook` calls and their ORDER.** This entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** Every census in sections 1 and 4, every count in section 7, and the browser results in section 7 are **MEASURED** on this tree at the moment of writing, most of them through a real `next build` and a real Chromium. That a nonce cannot reach a prerendered document is **MEASURED** rather than reasoned, in section 4. What is **JUDGED** is that the origin and not the edge is the layer (section 2), that `'unsafe-inline'` on `script-src` is worth shipping the rest of the policy for (section 4.1), that the three policies differ in one derived directive (section 5), and that nine candidate additions or edits are refused (section 6).

### 2. THE LAYER. **THE ORIGIN, AND CLOUDFLARE IS RULED AGAINST AS THE ONLY ONE**

[`INFRA:27`](../architecture/INFRA.md) puts *"Cloudflare in front of every origin"* with *"WAF, bot rules, rate limiting, DDoS, and the admin-origin IP allowlist all land in one place"*, and a response-header transform is the most ordinary thing an edge does. The row asked for the ruling and it is the same ruling [ADR-221](ADR-221.md) section 6 made about the CSRF check, on the same two grounds.

**THE FIRST IS THAT NOTHING MAKES A REQUEST GO THROUGH THE EDGE.** `INFRA` rules **no origin lock anywhere**: no authenticated origin pull, no origin firewall rule, no allowlist between Cloudflare and Railway, in any section of that document. Railway serves each service on its own hostname by default. **A response fetched direct from the origin would carry no policy at all**, and unlike the CSRF check, whose absence a caller notices, a missing CSP is invisible to everyone including the person it was supposed to protect.

**THE SECOND IS THAT AN EDGE RULE IS INVISIBLE TO EVERYTHING THAT READS THIS REPOSITORY.** No gate reads it, `pnpm vitest` cannot exercise it, and the founder's `E2` read cannot see it. That matters more here than it did for the CSRF control, because **the specific defect this row exists to end is a control cited in six places and installed in none**, and installing it where nothing can cite it is that defect with the halves swapped. The audit's section 0 already established the hard version of this: **the repository holds no infrastructure-as-code of any kind**, so an edge rule is not merely unverified from here but permanently unverifiable.

**THE EDGE IS STILL THE RIGHT LAYER FOR WHAT IT ALREADY HOLDS AND THIS ENTRY WEAKENS NONE OF IT.** `INFRA` section 3 hard rule 3's IP allowlist and the Cloudflare rules on `ADMIN_ORIGIN` are ORIGIN-scoped controls on an origin. **A duplicate of these headers at the edge would be defensible as an operational backstop and is not proposed here**, because section 6's count applies to it and because the edge configuration is nobody's fence in this repository.

**AND THE ORIGIN IS WHERE THE POLICY CAN BE DERIVED AT ALL.** The content of a CSP is a function of what the application emits. Section 4 derives eleven directives from a form census, a style census and a client-component census, all of which live here. An edge rule would be a transcription of those facts into a place that cannot read them.

### 3. THE `apps/api` HALF, AND THE HOOK ORDER IS THE RULING IN IT

**A JSON SURFACE NEEDS A DIFFERENT POLICY AND NOT A SHRUNKEN COPY OF A DOCUMENT ONE.** `API_CONTRACT` section 1 makes every response of this deployable JSON and section 2 makes every error `application/problem+json`. Nothing it emits is a document, so `script-src`, `style-src` and `img-src` have no subject. [`security-headers.ts`](../../apps/api/src/security-headers.ts) declares four directives and three headers:

| Header | Value | Why |
|---|---|---|
| `Content-Security-Policy` | `default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` | `default-src 'none'` refuses every fetch type at once, **including the ones a later CSP level adds**. The other three are spelled out because **no CSP level falls them back to `default-src`**, so a policy naming only `default-src 'none'` permits framing and D2's `frame-deny` is undone by an omission that reads as tidy |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | An HSTS header names no host, it binds the host that served it, so it is compatible with [ADR-012](ADR-012.md) by construction and needs no environment variable |
| `X-Content-Type-Options` | `nosniff` | Not one of D2's three words, declared as an addition in section 6. It belongs on this surface above the others: a browser free to re-sniff `application/json` as HTML is a browser that can be made to execute a reflected value out of a response whose own Content-Type said it was data |

**IT IS ONE `onRequest` HOOK BESIDE ADR-221's, AND IT IS REGISTERED BEFORE IT.** That order is the ruling rather than a detail. ADR-221's hook can **END** a request with `403` before any handler runs, so a header hook registered after it would leave **the one response class produced by a deliberate attack as the one class with no policy on it**. Registering first puts the three headers on every response this instance produces: every route on both surfaces, the CSRF refusal, the not-found path and the error handler, **with no list of what it covers anywhere**. [`security-headers.test.ts`](../../apps/api/test/security-headers.test.ts) asserts all five of those response classes and the registration order in the source, and both go red when the two `addHook` calls swap (section 7).

**ADR-221 IS NOT WEAKENED AND ITS COMMENT IS CORRECTED RATHER THAN LEFT STANDING.** `server.ts`'s CSRF hook carried the word *"FIRST, because everything after it costs more than it does"*. It is now second, and the sentence is rewritten to say what is true and why: what runs before it writes three response headers and decides nothing, and it is the header set that hook's own refusal has to carry. **The claim moved with the shape rather than being left behind as a sentence about a shape that changed.**

**`onRequest` AND NOT `onSend`.** Both would cover the same set. `onRequest` runs before a body is parsed, so a request the parser refuses has already been answered under the policy.

#### 4.1 THE NONCE ALTERNATIVE, PRICED BY RUNNING IT RATHER THAN BY READING ABOUT IT

The installed framework's own guide, `next/dist/docs/01-app/02-guides/content-security-policy.md`, is unambiguous: *"you **must use dynamic rendering** to add nonces"*, and *"Static pages are generated at build time, when no request or response headers exist, so no nonce can be injected."* **That was taken as a claim to test rather than as an answer.**

**THE EXPERIMENT, RUN ON `apps/site` AND THEN REVERSED.** A `src/proxy.ts` was written from that guide verbatim, minting a nonce per request and sending `script-src 'self' 'nonce-<value>' 'strict-dynamic'`. It registered: the build printed `ƒ Proxy (Middleware)`. **And every one of the site's eleven route entries stayed prerendered**, `○` and `●`, because Next does not opt a page into dynamic rendering merely because a proxy set a nonce. The served document then carried the fresh nonce **in the header** and **zero `nonce=` attributes in the markup**. Loaded in Chromium:

| Under the nonce policy, `apps/site` `/` | Result |
|---|---|
| CSP violations | **8.** Six external `/_next/static/chunks/*.js` refused, because `'strict-dynamic'` disables host allowlisting, and both inline scripts refused |
| `self.__next_f` after load | **undefined** |
| The page | **completely dead** |

**THAT IS THE TRAP THE ROW NAMED, AND IT IS THE DIRECTION A CARELESS SESSION WOULD HAVE SHIPPED IN**: a policy that reads as strict, a header that looks exemplary, and a product that does not run. Making it work needs a `proxy.ts` per app **and** an explicit `connection()` in every page file to force dynamic rendering. That is not one file outside this fence, it is **one file per page** outside it.

**AND THE COST IS DIFFERENT ON EACH APP, WHICH IS WHY THIS IS NOT ONE DECISION.**

| App | Route entries | Prerendered today | What the nonce would cost |
|---|---|---|---|
| `apps/site` | 11 | **11, all of them** | Every document. And [`M09:23`](../plans/M09-marketing-site.md) calls this app *"a fast statically generated Next.js application, served from the edge"*, which is an approved corpus document: **turning it dynamic is an M09 amendment and not a code change** |
| `apps/portal` | 14 | 3 (`/`, `/sign-in`, `/_not-found`) | Three routes forced dynamic. **Cheap** |
| `apps/admin` | 7 | 3 (`/`, `/feed`, `/flags`) | Three routes forced dynamic. **Cheap** |

**SO `script-src 'self' 'unsafe-inline'` SHIPS, ON ALL THREE, AND IT IS THE ONE DIRECTIVE IN THIS ENTRY THAT IS NOT A CONTROL.** It is named here rather than left for a reader to notice, because a CSP with `'unsafe-inline'` on scripts does not stop the classic injected-script payload from running.

**WHAT IT DOES STOP IS NOT NOTHING, AND THE DIFFERENCE MATTERS FOR `INV-M6-02` SPECIFICALLY.** `'unsafe-inline'` lets an injected script RUN; it does not let it REACH anywhere. `connect-src 'self'` refuses its `fetch`, `form-action` refuses its form submission, `img-src 'self'` refuses the one-pixel exfiltration, `base-uri 'none'` refuses the relative-URL hijack, `object-src 'none'` refuses the plugin, and `script-src 'self'` still refuses `<script src="https://attacker">`. **`INFRA:71`'s conclusion is that an XSS on the portal cannot REACH the admin surface, and reaching is exactly the half that holds.** The half that does not hold is that the XSS runs at all, and nothing in this fence could have changed that.

#### 4.2 WHAT WOULD END `'unsafe-inline'`, STATED SO A LATER SESSION DOES NOT HAVE TO RE-DERIVE IT

**Any ONE of these ends it, and until one of them lands the directive stays.**

1. **`next` stops writing the Flight payload inline**, or grows a build-time hash manifest. This costs nothing and is not in Merit's hands.
2. **`apps/portal` and `apps/admin` take a `proxy.ts` and a `connection()` on three routes each.** Both are cheap and neither needs a corpus amendment. **This is the one worth doing first**, and it is worth doing on the admin console before anywhere else, because `INV-M6-02` is about that origin. **It is a fence of its own and is registered as owed rather than taken here.**
3. **`apps/site` follows**, and that one needs an **M09 amendment** first, because `M09:23` rules the app statically generated and served from the edge.

**A REPORT-ONLY PHASE IS REFUSED AND THE REASON IS NOT CAUTION.** `Content-Security-Policy-Report-Only` carrying the strict `script-src` would report to a collector, and **there is no collector**: the audit's section 0 established that this repository holds no infrastructure-as-code of any kind, so `report-to` has nowhere to point and no session could configure one inside a fence. A report-only header with no endpoint reports to a browser console nobody is reading, which is a fourth header that looks like a control and is not. **The end condition above is the substitute, and it is written down rather than deployed.**

### 5. WHETHER THE THREE APPS GET THE SAME POLICY. **`INV-M6-02`, MADE MECHANICAL**

**THE PUBLIC SURFACES' POLICY**, `apps/site` and `apps/portal`:

```
default-src 'self'; base-uri 'none'; object-src 'none'; frame-src 'none'; frame-ancestors 'none';
form-action 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self'; font-src 'self'; connect-src 'self'
```

**THE ADMIN CONSOLE'S**, differing in exactly one directive:

```
... form-action 'self' ...
```

**THE DIFFERENCE IS DERIVED AND NOT CHOSEN.** `account-search.tsx:416` renders the only `<form>` element in the three deployables, and `form-action` governs a `GET` submission as much as a `POST` one, so the console needs `'self'` and the public surfaces do not. **The public surfaces' `'none'` is strictly tighter**, and it is the directive that denies a script injected into the portal a form submission to any origin at all, the admin origin included.

**A DIFFERENCE THAT WAS MERELY PRESENT WOULD BE SATISFIED BY A STRAY SPACE, SO THE SUITE ASSERTS WHICH DIRECTIVE DIFFERS.** [`apps/admin/test/security-headers.test.ts`](../../apps/admin/test/security-headers.test.ts) reads the two sibling configs **as text**, parses all three policies into directive maps, and asserts that the differing key set is exactly `['form-action']` against each public surface. A future edit that made the policies diverge somewhere unconsidered turns it red rather than passing on a technicality.

**AND THE ASSERTION THAT ACTUALLY DISCHARGES "EVEN IN PRINCIPLE" IS NOT THE COMPARISON.** It is this: **no source expression in any of the four policies names a host or a scheme.** Every one is a quoted keyword, `'self'`, `'none'` or `'unsafe-inline'`, asserted by regex in all four suites. A policy built only from keywords **grants no origin but the one that served it, whatever that origin turns out to be**, so:

- **`INV-M6-02` holds structurally rather than by inspection.** No policy CAN span two origins, so the admin origin cannot share one with a public surface even if somebody later made the strings identical.
- **[ADR-012](ADR-012.md) is satisfied by construction rather than by care.** There is no hostname anywhere in this diff, and there is no shape of edit to these files that could add one without turning a test red. That is stronger than asserting the absence of one particular hostname, which a rename would defeat.

**THE SIBLINGS ARE READ AS TEXT AND NEVER IMPORTED**, on [ADR-221](ADR-221.md)'s precedent for reading `routes/auth.ts`'s cookie templates from `apps/api/test/csrf.test.ts`: `RI-04` refuses one deployable depending on another, and a cross-app import in a test is that dependency wearing a test's costume. Each app's OWN config is **executed**, not read, so the assertion covers the wiring and not only the constant.

**THE FORM CENSUS IS RE-READ ON EVERY RUN, WHICH IS WHAT MAKES THIS A DERIVATION RATHER THAN A SNAPSHOT.** All three suites walk their own `src/` and count form elements. A form landing in the portal turns the portal's suite red on the directive that would then be wrong; the console losing its form turns the admin suite red on a directive that would then be wider than it needs to be.

### 6. What is refused, and why each one is a ruling rather than an omission

| Refused | Why |
|---|---|
| **`X-Frame-Options: DENY`** | `frame-ancestors 'none'` refuses **exactly** the set it would refuse, and a browser that reads `frame-ancestors` ignores `X-Frame-Options` when both are present. The callers here are three Next 16 applications and three server-to-server webhook senders; there is no legacy browser in the set. **[ADR-221](ADR-221.md) section 3.1's count is the precedent and it is applied against a header rather than a token**: a second mechanism that refuses the same set is a second copy of a control rather than defence in depth. D2's word is `frame-deny` and `frame-ancestors 'none'` is what discharges it |
| **`Content-Security-Policy-Report-Only`** | Section 4.2. No collector exists and none can be configured from this repository |
| **`preload` on HSTS** | A preload-list entry ships inside browser binaries, binds every subdomain of the apex and takes months to leave once a subdomain cannot serve HTTPS. It is irreversible on Merit's clock, so it is on the approval line rather than in the header. The suites assert its ABSENCE so that it stays a decision |
| **`upgrade-insecure-requests`** | Nothing measured needs it. Every URL in every built document is relative and no external host appears in any of them, so it would carry no traffic. An unmeasured directive is a line a later reader has to disprove |
| **`sandbox` on the API's policy** | Defensible on a pure JSON surface and **unmeasured**: this session could not construct a case where it changes an outcome, and section 4.1's whole argument is that an unexercised directive is how a policy becomes decorative |
| **`Cross-Origin-Resource-Policy` and `Cross-Origin-Opener-Policy`** | Genuinely valuable on the API and **outside D2's sentence**. Widening the ruling to a fourth and fifth header because they were nearby is the move the corpus calls widening a fence to finish. **Registered as owed** |
| **`poweredByHeader: false`** | `next start` sends `X-Powered-By: Next.js` on every document, measured. Removing it is one key in each config and it is a **removal** rather than one of D2's three. **Registered as owed** rather than taken, on the same ground as the row above |
| **`SECURITY.md` and `INFRA.md`** | The row admits them **only if the ruling is a contract fact**, and this one is not. ADR-221 took `C-29` on the opposite finding: a caller that sends a mismatched `Origin` gets `403` and no handler runs, which a client could learn from no other sentence in the corpus. **A response header the caller satisfies nothing to receive is not a contract fact.** And the six citations the audit flagged do not need repairing: they were false because the thing they named did not exist, and **they become true with no edit**. A catalogue row is a reasonable thing to want and is on the approval line |
| **`MERIT_BUILD_MASTER_PROMPT.md`** | Frozen |
| **Any migration, environment variable or hostname** | The control holds no state and names no origin. **No migration number was minted and none is owed** |

**`X-Content-Type-Options` IS THE ONE ADDITION THIS ENTRY DOES TAKE**, and it is declared here rather than smuggled in under D2's three words. It ships on all four surfaces so the set is uniform and assertable, its cost is zero on a tree that serves no user-uploaded content, and on the API it answers the sniffing case named in section 3.

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS WHETHER `'unsafe-inline'` ON `script-src` IS ACCEPTABLE AS A SHIPPING STATE, BECAUSE IT IS THE ONE DIRECTIVE HERE THAT IS NOT A CONTROL.** Section 4 measured why it is forced and section 4.1 measured what the alternative does when it is done carelessly, which is kill the product silently. **The honest position is that this entry ships nine directives that are controls and one that is a placeholder**, and a reader who thinks a CSP is worth having only if `script-src` is strict should say so now rather than after three apps depend on it. **The cheap next step is real and is named**: `apps/portal` and `apps/admin` need a `proxy.ts` and three `connection()` calls each, no corpus amendment, and `INV-M6-02`'s own origin is the one that gets the benefit. **If that is wanted, the thing to say is that it is a session of its own**, because it is a file per page in two packages this fence does not hold.

  **THE SECOND IS THE HSTS COMMITMENT, BECAUSE IT IS THE ONE LINE HERE THAT IS HARD TO TAKE BACK.** `max-age=31536000; includeSubDomains` tells every browser that touched a Merit hostname to refuse plain HTTP to it and to every subdomain of it for a year. **That is correct and it is also a year during which a subdomain that cannot serve HTTPS is unreachable rather than degraded**, and Merit has no subdomain inventory in this repository to check against. The `preload` upgrade, and the two-year `max-age` it requires, is deliberately not taken and is a separate yes.

  **THE THIRD IS WHETHER `SECURITY.md` SHOULD HAVE GAINED A CONTROL-CATALOGUE ROW FOR THIS.** This entry says no, on the ground that a response header is not a contract fact a caller satisfies, which is the exact condition the dispatch put on that file. **The argument on the other side is good**: `SECURITY.md` section 1 is the control catalogue, three of its own sentences cite these headers, and a control the catalogue does not carry is a control the next audit measures from source instead of from the register. **If that is the right call, the correction is a row in that file and not a change to this entry**, and it is five minutes.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **The policies were derived from what these apps emit TODAY, and these apps are three months from finished.** No client component exists yet, so `connect-src 'self'` has never been exercised by a browser-initiated `fetch`; no image exists yet, so `img-src 'self'` has never refused anything; no design-system stylesheet exists yet, so `style-src` has never seen a `<link rel="stylesheet">`. **Every one of those is permitted by the policy and none has been observed under it.** The suites re-read the form and style censuses on every run, which catches the two changes that would make a directive WRONG, and **nothing catches the change that would make one INSUFFICIENT** except a page breaking. That is the failure mode to expect and it is loud rather than silent, which is the direction this corpus asks a control to fail in.

  **AND ONE OBJECTION WORTH TWO MINUTES, because it is the strongest thing on the other side.** A reader could reasonably say that section 2 rules against the edge too quickly, and that HSTS in particular is a header the edge is unusually good at: Cloudflare will send it on every response including ones the origin never saw, such as its own error pages and redirects. **That is true and this entry does not refuse it.** What it refuses is the edge as **the only** layer, on the ground that a direct-to-origin request bypasses it and that nothing here can read it. **A Cloudflare transform duplicating these three headers is compatible with everything above** and would be strictly better than either layer alone; it is not proposed here because the edge configuration is nobody's fence in this repository, which is itself the finding the audit's section 0 recorded and nobody has yet taken.
