### 8. What a GREEN comparison still leaves unproven

**[ADR-112](ADR-112.md) FORECLOSURE 4 AND [ADR-299](ADR-299.md) SECTION 5.1 ITEM 5 BOTH SURVIVE THIS ROW INTACT, AND THIS SECTION IS WHY.** [`ADR-299:5.1`](ADR-299.md)'s ruling is *"the runtime guards must not be dropped on the strength of the declared type"*. **Nothing here retires a single runtime check.**

1. **A GENERATED EXPRESSION COMPARING EQUAL AS TEXT IS NOT THE SAME CLAIM AS IT COMPUTING THE SAME VALUE, AND THAT IS THIS ROW'S CENTRAL LIMIT.** Both sides are STRINGS and neither is evaluated. Two spellings that differ only in whitespace or in a quoted identifier are made equal here by a deliberate canonicaliser; two spellings that are semantically identical and textually different, `a - b` against `-(b - a)` or `x*10000/y` against `x*100*100/y`, would be reported as a DISAGREEMENT by this check even though Postgres computes the same number. **The comparison is therefore STRICTER than semantics in one direction and no stronger in the other**: it cannot tell that `our_balance_cents - platform_balance_cents` computes a difference, only that both documents say the same words. **A row that wanted the semantic claim would have to execute the expression against PostgreSQL**, and section 8 item 2 is why nothing here does.
2. **IT IS COMPARED AGAINST THE MIGRATIONS AS TEXT, NOT AGAINST A DATABASE.** The fold is a second transcription. A generated column that exists in a live database and in no migration is invisible to both sides, and so is the reverse. **No leg of this check connects to Postgres**, so nothing here proves the expression is even VALID SQL, that `NULLIF(cvar99_cents, 0)` protects the division it is written to protect, or that `integer` can hold the result. [`0049:188`](../../packages/db/migrations/0049_reserve_coverage_snapshots.sql) states the overflow bound in a comment and this row does not check it.
3. **IT IS COMPARED OVER THE REGISTERED POPULATION, WHICH IS NOT THE DATABASE.** The sixth generated column is the instance and section 6 is its report. `live_account_state` carries **three** `*_cents` columns plus the generated one and no leg of any comparison in this file reads any of them.
4. **IT DOES NOT PROVE THE GENERATED COLUMN IS NEVER WRITTEN, ONLY THAT BOTH DOCUMENTS AGREE IT CANNOT BE.** `$inferInsert` omitting a column is a TYPE fact. **Nothing in this tree asserts that no accessor and no raw statement names one of these five columns in an `INSERT` or `UPDATE`**, and a raw `sql` fragment could. That is a different check on a different population and this row did not widen into it.
5. **IT DOES NOT MAKE A WRITE PATH SAFE AND IT DOES NOT AUTHORISE ONE.** [ADR-437](ADR-437.md) section 7 lists four reasons the write path is refused; [ADR-438](ADR-438.md) discharged reason 4 and **this row discharges none of the remaining three.** It closes the last uncompared leg of the transcription and that is all. **A row reading this entry as clearance to narrow a write is reading a completed comparison as a ruling.**
6. **AND THE FACT THE TYPE STILL DOES NOT CARRY IS THE VOCABULARY.** [ADR-437](ADR-437.md) section 6.2's `state: string` observation is unchanged. **A compared generation clause does not make a `CHECK` into a type**, and `report_schedules.cadence` is the sharpest instance in the five: [`0040:185`](../../packages/db/migrations/0040_report_schedules.sql) explains that the `CASE` and a `CHECK` are a deliberate pair, and this row compares one of them.
