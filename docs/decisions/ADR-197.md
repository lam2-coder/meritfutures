## ADR-197: the OTP key is a deployment secret, the digest binds the address as typed, and the establishment door is one verb  (2026-08-28, status: proposed)

**[ADR-196](ADR-196.md) ruled where an identity comes from and could execute none of it, because the code that verifies had no digest and the establishment had no door.** This entry builds both. It is 2 and 3 of that entry's honestly-priced four.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `197`, session **367**, dispatched as `claude/otp-digest-and-door`. **Migration `0061` was reserved CONDITIONALLY and the condition is NOT met: the number RETURNS TO THE POOL UNSPENT.** Section 8.

- **MONEY PATH (auth). [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) READ IS OWED.** The entry ships `proposed` with an UNSIGNED approval line. **Merging is not signing.**

- **NO MERGED MIGRATION IS EDITED AND NO NEW ONE IS WRITTEN.** [`0002`](../../packages/db/migrations/0002_identity.sql), [`0029`](../../packages/db/migrations/0029_phone_identity_and_auth.sql), [`0034`](../../packages/db/migrations/0034_reversible_contact_addresses.sql) and [`0054`](../../packages/db/migrations/0054_identity_ledger_accounts.sql) are byte for byte unchanged. The set is still 58 files.

- **WHAT IS DERIVED AND WHAT IS JUDGED, separated before the argument starts.** That an in-database key grants no separation is **DERIVED**, from one `GRANT` in a merged migration (section 2). That the rotation cost which argues for a column is bounded to ten minutes is **DERIVED**, from a merged `expires_at` comment. That `users.email_normalized` cannot separate two people is **DERIVED**, from the column's own comment and a non-unique index. That the one-unit-of-work write refunds a racing loser's four rows is **EXECUTED** (section 6). What is **JUDGED** is that the deployment secret's residual is the better one to hold (section 2), and that the door should be one verb rather than a table vocabulary (section 5).

### 2. RULING 1: THE KEY IS A DEPLOYMENT SECRET, AND THE ARGUMENT IS ONE `GRANT`

**The dispatch said neither answer is obviously right and priced both honestly. One of them is refuted mechanically rather than on judgement.**

#### The threat the digest exists for

`otp_challenges.code_hash bytea NOT NULL` ([`0002:311`](../../packages/db/migrations/0002_identity.sql)) says only *"NEVER store the code itself"*. The adversary is somebody with a **READ** of that table -- a dump, a backup, a replica, an injected `SELECT`, a compromised read-only role. A six-digit code is **10^6 candidates**, `email_normalized` sits in the clear in the same row, and a live challenge is a session as that person. So the digest's whole job is to make an offline search over that table useless.

#### Candidate (a): the key in a table. **REFUSED, and the refusal is a merged `GRANT` rather than an opinion.**

[`0026:75`](../../packages/db/migrations/0026_roles_and_grants.sql) is `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO merit_app`. **The role that verifies an OTP must read the key, and it is the same role that reads `otp_challenges`.** A key table is therefore readable by exactly the principal the key is meant to be withheld from, and **one dump yields the digests and the key that opens them together**. That is not weaker defence in depth; it is none: the key and the thing it protects fail to the same capability.

**A column-scoped revoke cannot rescue it and [ADR-046](ADR-046.md) already measured why.** A table-level SELECT implies every column and `REVOKE SELECT (col)` against it is a no-op that *"looks like a control"*. Scoping it means revoking the table grant and re-granting column by column, which is a hand-maintained column list.

**AND THE CORPUS HAS ALREADY RULED THIS EXACT SHAPE ONE TABLE OVER.** [ADR-046](ADR-046.md), on the contact ciphertext: *"The key identifier references no table here, on purpose. A key registry in the same database as the ciphertext is one dump away from being a key ceremony."* Putting the OTP key in a row would make this estate hold two contradictory positions about where a key lives, decided three migrations apart.

#### Candidate (b): a deployment secret. **TAKEN.**

[INFRA section 7](../architecture/INFRA.md) is the surface and it already exists: secrets *"stored only in the platform vault, injected as environment variables at runtime, scoped per service"*, a **90 day rotation calendar**, and rotation as a runbook with *"a delay window before the old credential is revoked, so a rotation cannot itself become an outage"*.

**THE COST THE DISPATCH NAMED IS REAL AND IT IS BOUNDED TO TEN MINUTES.** *"Unrotatable without a deploy and unauditable after one"* is the honest objection, and the second half is the sharp one: `otp_challenges` carries **no `key_id` and no salt column**, so after a rotation nothing records which key sealed which row.

**THAT AUDIT QUESTION IS ONLY MEANINGFUL FOR A ROW THAT CAN STILL VERIFY, AND [`0002:313`](../../packages/db/migrations/0002_identity.sql) BOUNDS THAT SET:** `expires_at timestamptz NOT NULL, -- short TTL, 10 minutes`. A challenge past its TTL cannot verify under **any** key. **So a rotation admits two keys for one TTL, issues under the newest, and retires the old one -- which is INFRA section 7's own delay window with an upper bound the schema states rather than an operator chooses.** `resolveOtpMacKeys` at [`auth-backend.ts:388`](../../apps/api/src/auth-backend.ts) returns a **list** for exactly that reason, and it is why **no column is needed and `0061` is returned**.

**THE RESIDUAL, STATED RATHER THAN ARGUED AWAY.** The key sits in the environment of every API process, so a memory disclosure or an SSRF that reads the environment yields it. **That is a different capability from a table read, and that is the entire point**: the two must not fail to the same attack.

#### Candidate (c): no key at all, a slow KDF. **REFUSED ON A MEASUREMENT, and it was not in the dispatch.**

The obvious key-free answer is to make each guess expensive. **Priced rather than reasoned about**, `scrypt` at `N=16384, r=8, p=1` on the machine this session ran on:

| Figure | Value |
|---|---|
| Cost per guess | **49.0 ms** |
| Exhausting 10^6 candidates, one core | **13.6 core-hours** |
| Cores needed to exhaust inside ONE TTL | **82** |
| Cost paid on every honest verification | **49.0 ms** |
| HMAC-SHA-256 on the same path | **5.16 microseconds** |

**Eighty-two cores is an hour of a rented machine.** A work factor that made 10^6 infeasible would be paid by every person logging in, on the only route into the product, and it would still be a *large* space rather than an unreachable one. **A key the attacker does not have makes the space infinite instead of large, which is the only answer that scales to a secret this short.**

### 3. RULING 2: WHAT THE DIGEST IS TAKEN OVER, AND THE FINDING THAT MADE IT LOAD BEARING

`otpCodeDigest` at [`auth-backend.ts:299`](../../apps/api/src/auth-backend.ts) is **HMAC-SHA-256** over a domain-separated, length-prefixed `(channel, destination, code)`.

**THE DESTINATION IS THE ADDRESS AS TYPED AND NOT THE NORMALIZED FORM, AND THAT IS A SECURITY PROPERTY RATHER THAN A PREFERENCE.**

| Merged decision | What it says |
|---|---|
| [`0002:306-308`](../../packages/db/migrations/0002_identity.sql) | `otp_challenges` keys off `email_normalized`, *"Issued before a user may exist, so this keys off the normalized email rather than a user_id"* |
| [`0002:250-253`](../../packages/db/migrations/0002_identity.sql) | `users.email_normalized` is *"Indexed but deliberately NOT unique. **Two people can legitimately share a normalized form**, so it is a SIGNAL, not a constraint, and making it unique would refuse service to the second of them"* |
| [`0002:248`](../../packages/db/migrations/0002_identity.sql) | `users.email citext NOT NULL UNIQUE` -- and `RESOLUTION_ADDRESS` addresses **this** column |

**BOTH DECISIONS ARE CORRECT AND TOGETHER THEY LEAVE A HOLE.** The challenge row is keyed on a column that **cannot tell two people apart**, and the row carries no copy of the address the code was actually mailed to. So a handler that finds the newest unconsumed challenge for a normalized address and compares an unbound digest would let **`bob.smith@gmail.com`'s code answer a challenge presented as `bobsmith@gmail.com`**: one human authenticating as another, produced by two individually correct merged migrations and by no defect in either.

**THE DIGEST IS THE ONLY PLACE THAT SEPARATION CAN LIVE, and it costs no column**, because the address arrives in the request body at verify time and never has to be stored. Executed in section 6: same code, same challenge row, the other spelling -> **`false`**.

**THREE SMALLER BINDINGS, EACH WITH ITS OWN REASON.**

- **Case is folded, ASCII only.** `users.email` is `citext` *"so casing never creates a duplicate human"* ([`0002:247`](../../packages/db/migrations/0002_identity.sql)), so a digest that did not fold would refuse a person who typed `Bob@` on Tuesday and `bob@` on Wednesday. `citext` folds with `lower()`, which is **locale dependent above ASCII**, and a MAC must be reproducible byte for byte in every process; so the fold covers the range where every locale agrees and leaves the rest, which diverges in the **fail-closed** direction.
- **The channel is in the input**, because `otp_challenges_exactly_one_destination` ([`0029:532`](../../packages/db/migrations/0029_phone_identity_and_auth.sql)) admits two destination shapes on one table.
- **Every field is length-prefixed**, because otherwise `('ab', 'c')` and `('a', 'bc')` hash identically and a destination can be extended into a code.

### 4. RULING 3: THE DOOR IS ONE VERB, AND THAT IS CLAUSE 2 WITH ENFORCEMENT BEHIND IT

`establishmentDb()` at [`scoped-db.ts:1830`](../../packages/db/src/scoped-db.ts), `EstablishmentTx` at [`:1818`](../../packages/db/src/scoped-db.ts), reached through the existing `transaction(handle, fn)`.

**ADR-196's APPROVAL LINE SAYS CLAUSE 2 IS "the only clause with no enforcement behind it... prose that the first implementer of `verifyOtp` can violate with a green test suite".** Section 8 of that entry wrote the `DEFERRABLE INITIALLY DEFERRED` constraint trigger that would enforce it, measured that it works, and refused it -- the first ground being that it breaks `probe_ledger_constraints.sql`, the acceptance script for `0054`'s own trigger.

**THIS DOOR ENFORCES CLAUSE 2 AND COSTS NO DDL.** `establish` is **one method that issues both inserts**, and `EstablishmentTx` carries **no other verb**: no `insert`, no `updateAt`, no `deleteAt`, no `rowAt`, no `sqlExecutor`. The statement that writes the identity **is** the statement that writes the login. A caller has no seam to violate the clause through, so the invariant moved out of a constraint nobody could remove and into a construction nobody can misuse.

**CLAUSE 3 IS STRUCTURAL FOR THE SAME REASON.** `establish` takes no `identities` values and there is no parameter through which one could arrive, so the statement names **every column `default`** -- asserted mechanically against the registry's own column count rather than against a written list. `display_name`, `max_accounts_override` and `support_contact_ref` stay NULL because nothing in the file can say otherwise.

**THE VOCABULARY IS THE RESOLUTION DOOR'S, DELIBERATELY.** `establish` is addressed by `{ email }` and refused by the same `refuseUnresolvableAddress` guard, in both directions. The handler's branch is *"resolve, and if that answered nothing, establish AT THE SAME ADDRESS"*, and two vocabularies for one address is how the two halves of one `if` come to disagree about what they are keyed on.

**WHAT THE DOOR DOES NOT DO, NAMED RATHER THAN LEFT TO BE FOUND.** It does not mint the session. `sessions` is served by `insertUnder` at a **scoped** handle, so the mint is a second unit of work, and a crash between the two leaves an established identity with no session -- the person logs in again and gets `is_new: false`. **Nothing is orphaned**, because the four rows that would exist either way are exactly the four that exist. That is the price [ADR-126](ADR-126.md) already stated for `resolutionDb` -- *"paid in an inconvenience rather than in a row"* -- and it is the same price here.

### 5. WHAT MAKES THE WRITE IDEMPOTENT, IN ONE SENTENCE

> **The unique violation is ALLOWED TO RAISE, and because the two inserts are one unit of work, the rollback takes the identity row and the three `ledger_accounts` rows with it.**

**So the loser of a race pays ZERO permanent rows rather than four, and clause 2 is not merely tidy: it is the mechanism.** `users_email_key` is the arbiter, exactly as `ADR-196` said, and what this entry adds is that the arbiter's verdict is free.

**`ON CONFLICT (email) DO NOTHING` IS REFUSED BY NAME AND A CASE READS THE SOURCE FOR IT.** It does not raise, so the transaction **commits** with an `identities` row and no `users` row: clause 2's forbidden state, permanent under `ON DELETE RESTRICT`, retained *"forever (financial counterparty record)"* ([`0002:82-85`](../../packages/db/migrations/0002_identity.sql)). **The lenient spelling costs the four rows the strict one refunds.**

**A DEFECT FOUND BY MEASURING RATHER THAN BY REVIEWING, RECORDED BECAUSE IT FAILED IN THE DIRECTION THAT LOOKS FINE.** The first draft of `isEmailAlreadyTaken` read `code` and `constraint` off the top-level error. **Drizzle does not re-raise the driver's error**: it throws its own with the driver's in `cause`, so the translator matched **nothing**. Every row count was still correct -- the rollback happens whatever the error's type is -- and only the TYPE was wrong, which would have made a handler answer **500 to every second verification of a racing address** where clause 4 requires `is_new: false`. **The suite that would have caught it did not exist until the end-to-end run produced the wrong error name.**

- **Approval:** `___________________________` (UNSIGNED. `E2` read owed. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO READ IS SECTION 2, BECAUSE IT COMMITS THE ESTATE TO A KEY MANAGEMENT POSTURE AND NOT ONLY TO A DIGEST.** The mechanical half is settled -- a key in a table is readable by the role that reads the digests, and that is a `GRANT` rather than an opinion. **The half a founder owns is the residual**: the key sits in the environment of every API process, so an SSRF or a memory disclosure yields it, and this entry accepts that trade because it is a *different* attack from the one the digest exists for. **A founder who wants the key out of the process as well is asking for a key manager the dispatcher already has under [ADR-046](ADR-046.md)**, and reusing it for the OTP MAC is a coherent, larger entry that should be raised **before the handler is written**, because after it the key's shape is load bearing on a live path.

  **THE SECOND IS SECTION 3, WHICH IS A SECURITY FINDING RATHER THAN A DESIGN CHOICE.** Two merged migrations are each right and together they let one person answer another's challenge, and **the digest is the only thing standing in the way**. This entry closes it in `apps/api` with no schema change. **A founder who would rather the schema carried the binding is proposing that `otp_challenges` hold the address it was actually sent to**, which is a plaintext address at rest on a table [`0034`](../../packages/db/migrations/0034_reversible_contact_addresses.sql) deliberately left alone, and a very different entry. **What must not happen is that the finding is read as closed because this one is committed**: nothing in the database enforces it, and a later handler that digests `email_normalized` instead re-opens it silently.
