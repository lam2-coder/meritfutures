## ADR-206: `engine_gates` stores the engine's own value in the engine's own names, with cents as base-10 strings, because the storage constrains nothing and the three shapes already in this tree disagree  (2026-08-29, status: proposed)

**[Session 392](../sessions/2026-08-29-session-392.md) established that `B5`'s clearing condition has three terms and that all three lay outside its fence. THIS ENTRY RULES TERM 2: the stored encoding of `rule_states.engine_gates`.** The dispatch's instruction was to read the rows before ruling, and reading them is the finding. **The column is `jsonb NOT NULL` and that is the whole of what the database says about it**: measured live over every migration in the tree, `rule_states` carries fourteen `CHECK` constraints and **not one of them touches this column**, no index reads into it, no trigger inspects it, and the table holds **zero rows**. So there was never an encoding to discover. There is an encoding to **rule**, and the reason it must be ruled now rather than by whoever writes the adapter is that **three different shapes for these same six gate groups already exist in this tree, they disagree, and each one is individually defensible from where it sits.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `206`, session **394**, dispatched as `claude/engine-gates-encoding`. **The row exists because the dispatcher withheld an ADR number from session 392 and recorded that this was wrong.** **NO MIGRATION NUMBER WAS RESERVED, none is needed for the ruling, and none is taken.** Section 8 states what a `CHECK` would buy and why it is a separate decision rather than a silent one.

- **MONEY PATH.** `engine_gates` is column 19 of `SD-08`'s state hash, it is the bag `projectPayout` reaches through its own input type, and one of its leaves is the only forward-knowable input [ADR-204](ADR-204.md) found for the figure the payout wallet is funded against. [**`E2`**](../../MERIT_BUILD_MASTER_PROMPT.md) **READ IS OWED** on this ruling. The entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **WHY A SECOND RULING WAS NEEDED, said plainly rather than left to be inferred.** [ADR-204](ADR-204.md) ruled the **meaning** of the per-account projection: of the eleven conditions that decide eligibility, exactly one has an input a stored row fixes for the whole horizon, and that one is `R-37`'s cadence gap. **Its entire ruling therefore rests on reading one leaf out of this bag**, `cadenceGap.nextEligibleTradingDay`, and it declared nothing about the bag. That is why three sessions have now recorded that `ADR-204` moves nothing: **a projection whose sole input is a path no primary source declares is a projection nobody can write.** `ADR-204` ruled what the number means; this entry rules what the row says.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED**, separated before the argument starts. That the storage constrains nothing and holds no rows is **MEASURED**, live, in section 2. That the wire shape is lossy against the hash's own leaf list is **DERIVED**, leaf by leaf, in section 3. That a JSON number cannot round-trip a `Cents` through the read port is **MEASURED**, in section 5, against a value stored in and read back from a real row. What is **JUDGED** is the choice of the engine's names over the contract's (ruling 2) and of strings over numbers (ruling 3).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim below was read at its own file before it was relied on, and the one that came back different from the tree is section 9's first finding.

### 3. The three shapes already in this tree, and why two of them are not it

**A. The engine's value.** [`types.ts:961`](../../packages/rules-engine/src/types.ts) declares `EngineGateResults` as six groups, and [`hash.ts:422`](../../packages/rules-engine/src/hash.ts) enumerates their twenty-five leaves as `ENGINE_GATE_LEAVES`, an explicit ordered array of dotted paths. That array is not a convenience: `M01` section 1.4 bans iteration over an object's keys where the result affects output, so the hash's input set **had** to become a list, and the list it became is the leaf set of this bag.

**B. The wire shape.** [`payouts.ts:674`](../../apps/api/src/routes/payouts.ts)'s `projectGates` renders these same gates in `API_CONTRACT`'s snake case, and [`payouts.ts:922`](../../apps/api/src/routes/payouts.ts)'s `snapshotOf` writes the result into `payout_requests.eligibility_snapshot`, **a `jsonb` column, today**. That makes it the tempting answer: a landed serializer of these gates into `jsonb` already exists, and reusing it would look like consistency.

**It is the wrong answer and the arithmetic says so.** `projectGates` is an allowlist for a published contract and its own comment says so: a spread "would ship `capCents` on `minimum_amount`, which the contract does not declare". Against the hash's twenty-five leaves it is lossy in three distinct ways.

| Leaf of the hash's twenty-five | What the wire shape does with it |
|---|---|
| `tradedDays.skipped` | **ABSENT.** Not carried |
| `cadenceGap.skipped` | **ABSENT.** Not carried |
| `minimumAmount.capCents` | **ABSENT**, and deliberately: the comment names this field as the one a spread would wrongly ship |
| `consistency.maxDayShareBp` | **RENAMED** beyond casing, to `max_bp` |
| `cadenceGap.tradingDaysSinceLastPayout` | **RENAMED** beyond casing, to `days_since_last_payout` |
| `minimumAmount.pass` | **A DIFFERENT FACT.** `minimum_amount.pass` carries `minimumAmountHolds`, the route's conjunction of the engine's gate with `G-CLAMP`'s approved amount, which the engine never computed and the hash never hashed |
| the four `R-40` context gates | **ADDED**, and barred from the replayed state by `INV-23`, which is the whole reason `SD-06` split the column in two |

**Twenty-two of twenty-five leaves survive and one of the twenty-two is a different fact.** A row written in the wire shape would hash-mismatch on day one against a `state_hash` computed over all twenty-five, and the divergence report would name a field the reader cannot find in the row. **The wire may be lossy because a contract is an allowlist; the store may not, because the store is the audit's left-hand side.**

**C. The fixture shape.** The golden fixtures write `engine_gates.traded_days.skipped` in snake case, and it is easy to read that as evidence about storage. It is not. [`compare.ts:134`](../../packages/golden-loader/src/compare.ts) states the reason in its own words: the path is in the fixture's spelling and not the engine's, and `diffEndState` translates one to the other with `snakeToCamel` before comparing. **The fixtures compare against the engine's returned value and have never seen a stored row.**

### 4. THE RULING

1. **`rule_states.engine_gates` stores the engine's `EngineGateResults` value, group for group and leaf for leaf: six groups, twenty-five leaves, no more and no fewer.** The leaf set is exactly `ENGINE_GATE_LEAVES`' dotted paths. It is not the wire shape, it is not the fixture shape, and it carries no context gate.

2. **The names are the engine's, not `API_CONTRACT`'s.** The read port is typed to return an `EngineGateResults`, so a snake-case bag would need a rename map maintained beside the interface it renames. **That is a second statement of one predicate with nothing comparing the two**, which is `FM-16`'s shape, and it is the exact defect session 392 found sitting on `B5`'s clearing condition. The camel-case names already have an executable declaration in `ENGINE_GATE_LEAVES`; the snake-case names would have none, because `projectGates` is a different and lossy list.

3. **Every `*Cents` leaf is a JSON string holding the base-10 integer.** Seven leaves take this form: `winDays.floorCents`, `buffer.haveCents`, `buffer.needCents`, `consistency.profitNeededToDiluteCents`, `minimumAmount.withdrawableCents`, `minimumAmount.capCents` and `minimumAmount.minPayoutCents`. Section 5 is why.

4. **Every other leaf is its JSON primitive.** `pass` and `skipped` are booleans. `have`, `need`, `bestDayShareBp` and `maxDayShareBp` are JSON integers, and the two basis-point leaves are nullable. `tradingDaysSinceLastPayout` is a nullable JSON integer. `nextEligibleTradingDay` is a nullable `YYYY-MM-DD` string. **`null` is written as JSON `null` and never as the hash's `~null` sentinel**, which belongs to the serializer and not to the bag.

5. **`skipped` appears on `tradedDays`, `consistency` and `cadenceGap` and on no other group.** That is the interface's shape and not an omission: `CV-19` fixed that a gate which was not evaluated reports `pass: true, skipped: true`, and the other three groups are always evaluated. A bag that grew a fourth `skipped` would carry a fact the engine never produced.

6. **Key order is not part of the encoding and no reader may depend on it**, because `jsonb` does not preserve it. The consequence is already written at [`hash.ts:408`](../../packages/rules-engine/src/hash.ts) and is restated here as a ruling rather than a comment: **the hash is taken over the engine's in-memory value and never over a round trip**, and the column and the hash are written from one value in one step.

7. **The declaration lands in [`rule_states.md`](../architecture/data-model/rule_states.md)**, beside the `state_hash` input list, for that list's own stated reason: a shape whose input set is implicit is a shape that changes meaning when a field is added. An ADR records a decision; the design record is where a reader checking a row looks.

8. **`0015`'s eight-gate column comment and the design record's copy of it are both wrong and the design record is corrected here.** "Profit target, drawdown, win days, minimum days, consistency, cadence, cap, minimum payout" names no group `EngineGateResults` declares, splits `minimumAmount` into two, and carries a "profit target" gate the payout path does not have. [ADR-060](ADR-060.md) had already closed the enumeration at the six `R-33`, `R-34`, `R-35`, `R-36`, `R-37` and `R-39`. **The migration is merged and is superseded rather than edited** (constitution E2), so its comment stands and this entry is the record that it does not describe the bag.

### 5. Why cents are strings, decided on a round trip rather than on taste

**The write path may not be able to refuse.** `Cents` is [`types.ts:38`](../../packages/rules-engine/src/types.ts)'s `bigint` and the columns beside this one are `bigint`, so a state the engine computed legally can hold a value no JSON integer expresses. [`payouts.ts:548`](../../apps/api/src/routes/payouts.ts)'s `centsToJson` **throws** past `Number.MAX_SAFE_INTEGER`, which is right on a wire that `API_CONTRACT` says carries JSON integers and wrong in a store: a write that threw would leave the account-day with no `rule_states` row, which is `DO-3`, and the nightly batch would raise a reconciliation against a value the engine got right.

**And the loss is not where it looks.** The obvious argument is that `jsonb` cannot hold the number, and that argument is false. Stored in a real row and read back:

```
stored           {"capCents": "9007199254740993", "capNumber": 9007199254740993}
jsonb_typeof     string                            number
postgres keeps   9007199254740993                  9007199254740993   <- exact, jsonb numbers are numeric

read into JS through JSON.parse
  as a number    typeof number   9007199254740992   BigInt(...) -> 9007199254740992   WRONG
  as a string    typeof string   9007199254740993   BigInt(...) -> 9007199254740993   exact
```

**Postgres is not the lossy leg. The read port is.** `storedRuleStates` at [`ports.ts:285`](../../apps/worker/src/batch/ports.ts) is typed to return `RuleStateRow`s whose `engineGates` is an `EngineGateResults`, so the adapter has to rebuild a `bigint` from what `JSON.parse` gives it, and from a JSON number it cannot. That read is the left-hand side of `INV-04`'s replay audit, so the failure mode is a nightly divergence on a row that was written correctly.

**A string also costs nothing at the hash.** [`hash.ts:355`](../../packages/rules-engine/src/hash.ts)'s `money()` renders a `Cents` as `toString(10)`, which is the same base-10 text, so the column and the hash speak one representation of money instead of two.

**The runner-up, named because it is reasonable.** A JSON integer with a documented bound is simpler to read in `psql` and is what `eligibility_snapshot` already does. It is refused because the bound would have to be enforced on a write path that has no acceptable refusal, and because a bound that holds today at ninety trillion dollars is exactly the kind of assumption this corpus keeps finding written down nowhere.

### 7. The check, and three seeds that made it fire

**The declaration is checkable because the leaf set already has an executable copy.** Walking a stored row two levels deep gives its dotted paths, and comparing that set against `ENGINE_GATE_LEAVES` is the whole check:

```sql
select g.key || '.' || l.key
  from rule_states r, jsonb_each(r.engine_gates) g, jsonb_each(g.value) l
```

Against the specimen this returns twenty-five paths and they are **identical, set for set**, to the paths `ENGINE_GATE_LEAVES` declares. A check nobody has watched fire is not a check, so it was seeded against the live row and restored between seeds:

| Seed | Shape it imitates | Result |
|---|---|---|
| control, unmutated | the ruling | **GREEN**, twenty-five leaves |
| drop `minimumAmount.capCents` | the leaf the wire shape omits | **RED**, names the missing path |
| rename `consistency.maxDayShareBp` to `max_bp` | the wire shape's spelling | **RED**, names both paths |
| add `accountActive` | the context gates `INV-23` bars | **RED**, names the added path |
| control, restored | the ruling | **GREEN**, twenty-five leaves |

**The three seeds are the three ways the wire shape differs from the store**, which is what makes them worth applying rather than arbitrary mutations: each one is a defect a session that reused `projectGates` would have introduced.

### 8. No migration number, and what a `CHECK` would buy

**No number was reserved and none is taken.** The ruling needs no column: `engine_gates` exists, it is `jsonb NOT NULL`, and the declaration is about what goes in it.

**A `CHECK` is the one thing that would make the database itself enforce this, and it is reported rather than taken.** A constraint asserting the six top-level keys are present and no seventh exists is expressible today, and it would move the check from a suite into the store. It is not taken here for three reasons, each of which a founder may overrule. **It needs a migration number nobody reserved**, and section 7 of the dispatch protocol is explicit that a number is claimed before the file is written. **It would be the first constraint in this table that encodes engine vocabulary in DDL**, so a group renamed in `types.ts` would fail at the write rather than at a gate, which is a good failure in production and an expensive one during the build. And **it cannot reach the leaves cheaply**: the useful assertion is the twenty-five-path one in section 7, and expressing that in SQL duplicates `ENGINE_GATE_LEAVES` into a migration that can never be edited afterwards. **The recommendation is the suite-side check over the executable list, and a `CHECK` on the six group keys only if a founder wants the store to refuse.**

### 9. Registered rather than repaired, each with the fence that owns it

1. **[`hash.ts:391`](../../packages/rules-engine/src/hash.ts) says "four of the twenty-five leaf fields below are `Cents`" and seven of them are.** Derived by reading the array: `winDays.floorCents`, `buffer.haveCents`, `buffer.needCents`, `consistency.profitNeededToDiluteCents`, `minimumAmount.withdrawableCents`, `minimumAmount.capCents`, `minimumAmount.minPayoutCents`. **The argument it supports survives** -- `JSON.stringify` throws on a `bigint`, which was confirmed rather than assumed, and seven is worse than four, not better. **Reported and not repaired: `packages/**` is session 395's this wave**, and the count sits inside the comment that this entry's section 5 relies on, so a reader of both should know which number is right.

2. **[`identity.ts:1469`](../../apps/worker/src/detectors/identity.ts)'s `failingGates` is the only live reader of this bag, and it depends on the nesting rather than on the names.** It walks `Object.entries` at the top level and looks for `pass === false` with `skipped !== true`, then compares the group name to `CONSISTENCY_GATE`, whose own comment says `ENGINE_GATE_LEAVES` is its source. **Under this ruling it is correct.** Under the wire shape it would still find six groups and still match `consistency`, because that one name is identical in both casings, **but the group names it publishes into `risk_flags` would change spelling** and `D-11`'s `tradedDays.skipped` and `cadenceGap.skipped` reads would silently see `undefined`, which its `skipped !== true` test treats as not-skipped. **Reported: `apps/worker/**` is session 395's.** It is named here because it is the one place where an encoding chosen from the read side would have produced a wrong flag rather than a type error.

3. **`DISPATCH_PROTOCOL:49` says 16 of 16 invariants and the tree reports seventeen**, for the fifth session running.
