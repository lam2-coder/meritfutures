## ADR-098: the operator path's absence from every UI deployable is a PROPERTY of this repository, and `RI-09` is that property  (2026-08-25, status: accepted)

**[ADR-083](ADR-083.md) section 4 closes the operator path with two status codes one row apart, and until this entry the door had no hinge.** Its argument is that **403 is what a permission check returns and 404 is what an ABSENT ROUTE returns**, so `apps/api` chooses its route set at startup and the public deployment answers 404 for `/internal/*` by having nothing there. That is true of `apps/api` and it was never true of anywhere else. **A file at `apps/portal/src/app/api/v1/admin/payouts/route.ts` makes the path exist on the public origin without `apps/api` registering anything**, and nothing in this estate says a word. **RULED: the absence is a property, and this entry writes the mechanism** as `RI-09` in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs).

- **Origin:** the approval clause of `ADR-095` (session 183, unlinked here because it is not on `main` until [#240](https://github.com/lam2-coder/meritfutures/pull/240) merges and `CI-06a` fails on a link to an absent document), which states the hole as a path and four green commands. Dispatched as session **189**, with the instruction to reproduce it before ruling on it rather than to inherit it.

- **Context:** `ADR-095` measured the hole on a tree with **Next.js installed**. That tree is on an unmerged branch, so the first question this entry had to answer was whether the framework is the cause. **It is not.** Section 1 re-derives every figure on `origin/main` at `38e420b`, with no framework anywhere in the workspace, and finds the hole **wider than reported** rather than narrower.

- **NOT MONEY PATH.** No ledger, no payout, no engine, no migration, no `SD-nn`, no route. It writes one check and one ruling. **It touches a money-path property from outside**, which is the same shape [ADR-096](ADR-096.md) has: the operator surface is where payout runs, batch jobs and the admin console live, and the direction this fails in is silence.

### 2. The ruling

> **1. The absence of `/api/v1` and of every operator path from every deployable but `apps/api` is a PROPERTY of this repository and not an assumption that has held because nobody wrote the file.**
>
> **2. `RI-09` is that property. It reads `BASE_PATH` and `OPERATOR_PREFIXES` out of [`apps/api/src/surface.ts`](../../apps/api/src/surface.ts) and refuses three path shapes in every deployable in `DEPLOYABLES` except the one that owns the surface.**
>
> **3. It asserts a SPELLING and never a served route, it says so in its own `covers` line, and a green `RI-09` must never be read as "no UI deployable serves an operator path".**

### 3. Why it must be a property, and the argument is `ADR-083`'s own

**`ADR-083` section 3 refuses the API-inside-a-UI-surface placement on a sentence about mechanisms rather than about tidiness.** Quoting it:

> **A surface that CONTAINS the API has a privileged back door by construction**, because a handler in the same package is an import away, and **no lint can tell the difference** between a legitimate internal call and a route bypass in a codebase where both are the same kind of function call. **The guarantee degrades from a boundary into a habit, and it degrades silently.**

**That paragraph is an argument that the boundary must be structural, and the entry then rests it on a check that does not assert it.** Section 3 continues: *"`RI-04` in `repo-invariants.mjs` refuses an app that depends on an app... An API living inside any one of the three makes the other two arrows unimplementable."* **`RI-04` does refuse that, and refusing it does not produce the boundary**, because the cheapest way to put the API inside `apps/portal` is not to depend on `apps/api` -- it is to write the handler.

**This is `RI-04`'s own recorded failure mode, one axis over.** [Session 153](../sessions/2026-08-24-session-153.md) found `RI-04` *"PASSING while asserting nothing whatsoever about the deployable it was cited to protect"*, its `DEPLOYABLES` literal naming four apps when `ADR-083` had ruled a fifth, and `ADR-083` section 3 leaning on the check **by name**. The literal was widened and the shape was not: **`RI-04` now iterates five deployables and still never asks what any of them serves.** `ADR-083`'s consequence list called the fix *"the highest-value single-line follow-up this ruling creates, because the arrow argument in section 3 rests on exactly the assertion `RI-04` makes"*. **It rests on more than `RI-04` makes, and this entry is the remainder.**

**And the generalisation the dispatch asked to be decided rather than assumed.** [ADR-096](ADR-096.md) section 9 names its own remedy as *"`RI-01`'s shape pointed one directory over"* and states the class: a control that is *"an ABSENT dependency declaration ... announces nothing when it stops holding"*. **The class generalises and the SHAPE does not.** `RI-08` as `ADR-096` scopes it reads four dependency fields of one manifest, and `ADR-095` section 9 item 5b already records why that does not reach here, in the entry that found this hole: *"it reads a **manifest**, where a route handler serving an operator path declares no dependency at all."* **Two entries, two silent-absence controls, and two different instruments** -- which is the answer to whether it generalises: the diagnosis does, the repair does not, and writing `RI-09` on `RI-01`'s literal shape would have produced a check that cannot see its own subject.

### 4. The mechanism, and the three shapes

**`RI-09` walks every file under each deployable in `DEPLOYABLES` except `apps/api` and classifies its PATH.** Three shapes, ordered so the sharpest message wins, each carrying the ruling it violates:

| Shape | Example | What it cites |
|---|---|---|
| **The base path followed by an operator prefix** | `apps/portal/src/app/api/v1/admin/payouts/route.ts` | `ADR-083` section 4 and API_CONTRACT section 12's 404 |
| **The base path's segments anywhere in the path** | `apps/portal/src/app/api/v1/checkout/route.ts` | `ADR-083` ruling 1 and *"no privileged back door"* |
| **An operator prefix, or the base path's first segment, directly below a routing root** | `apps/site/src/app/internal/jobs/route.ts`, `apps/portal/src/pages/api/hello.ts` | `ADR-083` ruling 2, `ADR-095` ruling 3 |

**The two lists are read out of `surface.ts` and never written here.** `BASE_PATH` and `OPERATOR_PREFIXES` are the contract's vocabulary and they live in one file; `RI-06` already established the relationship, parsing the ESLint plugin's `rules` map rather than keeping a copy. **A second `['/admin', '/internal']` in the checker would drift the day the contract grows a third prefix, and it would drift silently**, which is the exact failure this check exists inside. **Watched, not asserted:** adding `'/ops'` to `OPERATOR_PREFIXES` in a scratch copy made `apps/portal/src/app/ops/route.ts` a finding **with no edit to the checker**, and removing `OPERATOR_PREFIXES` made `RI-09` **ERROR** rather than pass -- the runner's second rule, *"a check that cannot run is not a check that passed"*.

**Two decisions inside the shapes are worth naming because a careless version gets them wrong.**

- **Route groups and parallel routes are skipped, and private `_folders` are not.** `app/(ops)/admin/route.ts` serves `/admin`, so reading the literal segment below the routing root would find `(ops)` and miss it. **The skip runs in the direction that catches MORE and never less.** Private folders go the other way: `RI-09` asserts a **spelling**, not a prediction about what one framework version happens to route, so it does not model the exclusion and reports the path.
- **`ROUTING_ROOTS` is `['app', 'pages']` and no more.** Adding SvelteKit's `routes` would have refused [`apps/site/src/routes/`](../../apps/site/src/routes/page.ts), which exists on `main` today and is seven pure render functions rather than a router. **A guessed convention is a false refusal a human has to argue with**, and the base-path shape is framework-independent and catches SvelteKit's `routes/api/v1/...` anyway.

**Ten cases in [`repo-invariants.test.ts`](../../packages/tooling/test/repo-invariants.test.ts), each watched failing on its own seed, and the second is the one that matters most:**

| Case | Direction |
|---|---|
| `ADR-095`'s exact path under `apps/portal` | **must be refused** |
| the same path under `apps/api`, plus `apps/api/src/routes/admin/payouts.ts` | **must PASS.** A check that refused both would be unusable the day `P4-d` writes the first handler, and nobody would find out until then |
| `apps/portal/src/api/types.ts` | **must PASS.** It exists on `main` and `ADR-083` section 3 cites it as evidence the portal is on the far side of the boundary |
| `app/internal/jobs/route.ts` with no base path | must be refused |
| `app/(ops)/admin/payouts/route.ts` | must be refused |
| `pages/api/hello.ts` with no version segment | must be refused |
| a third `OPERATOR_PREFIXES` entry in the fixture's own `surface.ts` | the finding must FOLLOW it |
| `surface.ts` gone, and `OPERATOR_PREFIXES` gone | must **throw**, not pass |

**The suite was mutation-checked rather than trusted.** Deleting the route-group skip fails exactly one case; deleting the owner exemption fails exactly one case; disabling the operator branch fails exactly one case. **A suite that stays green under a mutation of the thing it tests is a suite that is asserting something else.**

### 5. What a repo invariant cannot see, stated against itself

**`ADR-096` records that a manifest-level control is *"shorter, less obviously about the database, and reviewed by whoever reviews manifests"* and books a control that never has to fire as a COST. The same scepticism is owed here and it is not softened.**

- **`RI-09` reads PATHS.** A route reached by a catch-all `[...slug]/route.ts`, a `next.config` rewrite, a middleware, or a hand-written router table in a file called anything at all **declares nothing this check can find**. It catches the convention a filesystem-routing framework makes load-bearing, which is the cheap and likely spelling, and not the only one.
- **Nothing in this repository can see what a process SERVES**, and on `main` today no deployable but `apps/api` has a server. **So `RI-09` refuses a shape rather than a served route, and that is the point rather than an excuse**: the shape is what the framework [ADR-095](https://github.com/lam2-coder/meritfutures/pull/240) admits turns into a served route, and a check written after the framework has to grandfather whatever it finds. `ADR-042` wired `merit/no-calendar-in-expiry-path` to a glob matching zero files for the same reason, and `RI-06` exists because that rule is indistinguishable from an unplugged one.
- **It does not read `apps/api`**, which owns the surface. That half is `surface.ts` and `surface.test.ts`, and pointing `RI-09` at it would refuse the deployable the ruling exists to protect.
- **It does not read `packages/`.** A package routes nothing on its own and reaches an origin only through a deployable that depends on it, which is `RI-04`'s question rather than this one's.
- **It is not `ADR-095` section 9 item 5's owed mechanism.** `F4` is a server component importing `packages/db` directly; that defect is an **import** and this one is a **path**, and neither check substitutes for the other. **Both remain owed** after this entry: `F4`'s rule, and `ADR-096`'s `RI-08`.

**The cost, stated in the direction that costs something.** If [#240](https://github.com/lam2-coder/meritfutures/pull/240) never merges and this workspace never adopts a filesystem-routing framework, **`RI-09` is a check that never has to fire**, and `ADR-096` books that as a cost rather than a strengthening. **What separates it from a speculative control is that its subject is dated and named**: `apps/portal` and `apps/site` acquire Next.js App Router on an open pull request awaiting the founder, and the window in which this check can be added against a clean tree is now.

### 6. What this forecloses

| Foreclosed | What it costs to reopen |
|---|---|
| **An ESLint rule as the primary mechanism** | `RI-07`'s header states the rule: *"the defect is a PATH and not a line."* A filesystem-routing framework turns a directory name into a URL, so the violation is complete before any statement is written and an exported `GET` is a consequence rather than the cause. ESLint is attached to globs and reads one file at a time. **A rule is still welcome as the SOURCE half** -- the same division `RI-01` and `merit/engine-purity` already have -- and this entry does not write one |
| **Widening `RI-04` instead of adding a check** | `RI-04`'s subject is *"each deployable is its own package"*. Folding a second property into it would give one id two `covers` lines and make a failure ambiguous about which property broke. `RI-07` was added beside `RI-01` for exactly this reason rather than folded into it |
| **A route-file allowlist per deployable** | The rule is `apps/api` and nothing else, and an allowlist is the shape that converts that into a list somebody edits. `ADR-083` section 4 refuses the equivalent for routes: *"a process that registered it cannot be relied on to answer 404"* |
| **Reading `apps/api`'s route set as data and comparing it to the UI deployables'** | There is no route set to read: `apps/api` registers nothing, by `ADR-083` section 7. A check that needed one would be unrunnable today, which is a check that does not exist |
| **Refusing the whole `api` word anywhere under a deployable** | It would refuse [`apps/portal/src/api/types.ts`](../../apps/portal/src/api/types.ts), which `ADR-083` section 3 cites as evidence the portal is a CLIENT. A check that refuses the corpus's own example of correct behaviour gets deleted rather than obeyed |

### 7. The number is `RI-09` and not `RI-08`, and there is no register to have checked

**And the reason the collision was even possible is a finding.** [ALLOCATION](ALLOCATION.md) carries four tables -- ADR numbers, migration numbers, CI gate identifiers, `OI-nn` -- **and no `RI-nn` table.** `RI-08` was claimed **in prose, in an ADR**, which is the one place a `grep` for the next free number does not look.
