### 2. THE RULING

> **1. A ROUTE DECLARES THAT ITS BODY IS BYTES, AND NOTHING ELSE MAY.** `RouteDefinition` carries `rawBody`, and it is the ONLY way into the raw context. There is no list of raw paths anywhere: a list restating a property the route already states is the hand-maintained list `registry.ts` was built to refuse.
>
> **2. THE SCOPE IS ONE ENCAPSULATION CONTEXT AND NEVER THE PROCESS, AND THE REFUSAL OF THE ALTERNATIVE IS MEASURED.** `compose` opens one child context, installs the buffer parser on it, and registers every raw route inside it. **Registering on the root instance is refused**, and section 3 is the measurement rather than the reasoning.
>
> **3. `rawBody` ON A VERB THAT CARRIES NO BODY IS REFUSED AT THE DEFINITION.** Fastify reaches a content-type parser only when there is a body, so `rawBody` on a `GET` would be reported by `CompositionReport` and ignored at request time. `defineRoutes` throws, in the module's own file, on `BODY_METHODS` being `POST | PATCH | PUT`.
>
> **4. THE REPORT NAMES WHAT IS SERVED RAW.** `CompositionReport.raw` is a list, a subset of `registered`, and it exists so the blast radius is a thing a test asserts rather than a thing a reviewer reasons about. A fourth route declaring `rawBody` turns a case red and somebody decides rather than discovers.
>
> **5. THE PARSER INSTALLER MOVES TO `registry.ts` AND IS NOT COPIED.** `compose` is its only production caller. `routes/webhooks-psp.ts` re-exports that one definition under its historical name, because three suites import it by that name and renaming their call sites is churn in files concurrent rows hold. **A second copy would be a second thing to keep true**, which is that file's own rule.
>
> **6. THE INHERITED JSON PARSER IS REMOVED BEFORE THE RAW ONE IS ADDED.** Not tidiness: without it, any instance whose parent already carries a raw parser fails at `ready()` with `FST_ERR_CTP_ALREADY_PRESENT`. Section 4 is the measurement.
>
> **7. NO RECEIVER'S LOGIC IS TOUCHED AND NO DEPENDENCY IS WIRED.** This row makes the three receivers' existing answers reachable. It does not give any of them a store, an adapter or an applier, and the answers it exposes are 503, 404 and 404 rather than 200.

### 3. Clause 2, measured rather than argued

[ADR-109](ADR-109.md) clause 6 already refused a root registration, in a sentence: *"a Fastify content-type parser is per encapsulation context, so a root registration takes JSON parsing away from every route that lands later."* **That sentence was written before there were forty-seven registered routes to take it away from, and it was never run.** It is run here.

**THE COUNTERFACTUAL WAS BUILT AND EXECUTED.** `compose` was changed to install the parser on `app` and register the raw routes on `app`, which is the shape the sentence refuses, and `pnpm vitest run apps/api` was run against it:

| Composition | `apps/api` result |
|---|---|
| The child context, as this row ships it | **76 files, 2,511 passed, 5 skipped, 0 failed** |
| The parser on the root instance | **7 files failed, 136 tests failed**, 2,375 passed, 5 skipped |

The seven files are `checkout.test.ts` (67 failed), `wallet-withdrawals.test.ts` (39), `auth.test.ts` (15), `affiliate.test.ts` (9), `payouts.test.ts` (4), `webhooks-rise.test.ts` (1) and the new `raw-body-scope.test.ts` (1). **Every one of them is a route that reads fields off `request.body` and was handed a `Buffer` instead.** `POST /checkout` is on the money path.

**AND THE FAILURE MODE IS THE ONE THAT WOULD NOT HAVE BEEN CAUGHT BY READING THE DIFF.** A root registration is one line and looks local. What it does is change how forty-odd routes parse, at a distance, in a file whose subject is webhooks.

**SO THE SCOPE IS VISIBLE IN THE DIFF IN TWO PLACES RATHER THAN ONE**: `compose` registers raw routes on `scope` and everything else on `app`, and `CompositionReport.raw` states the resulting set so a case can pin it.

### 4. Clause 6, which is a defect this row created and then met

**THE CHILD CONTEXT ALONE BREAKS THE THREE SUITES THAT INSTALL THE PARSER ON THE ROOT.** `webhooks-psp.test.ts`, `webhooks-rise.test.ts` and `kyc.test.ts` each build an app and call `installRawWebhookBodyParser(app)` on it, because until this row that was the only way to reach a receiver.

Fastify 5.12.1's `ContentTypeParser.prototype.existingParser` special-cases `application/json`: it reports the parser as already present when it is **not** the default JSON parse function. A child context clones its parent's parser map at boot. So a root that already carries a raw parser gives the child a map in which `application/json` is non-default, and the child's `add` throws `FST_ERR_CTP_ALREADY_PRESENT` **at `ready()`**, which surfaces as a boot error naming a vendor file.

**MEASURED, NOT REASONED.** A minimal Fastify program with a root install and a child install throws `FST_ERR_CTP_ALREADY_PRESENT`; the same program with `removeContentTypeParser('application/json')` before the add answers `200` with the bytes. The remove is scoped to the same context as the add, so it takes nothing from the parent.

**IT IS WATCHED RATHER THAN COMMENTED.** `raw-body-scope.test.ts` composes a raw route AND installs on the root, and asserts the app boots and serves bytes. With the remove line deleted, that case fails with the Fastify error by name; the transcript is section 7.

### 6. Two sentences that could not be checked while everything answered 500, and are wrong now that they can be

**A `500` THAT PRECEDES EVERY RECEIVER MAKES EVERY CLAIM ABOUT A RECEIVER'S ANSWER UNFALSIFIABLE.** Three files carry such claims. Making them reachable made them checkable, and two of the three do not survive.

| Claim | Where | Measured on a live process |
|---|---|---|
| The Rise row answers **503**, section 2's code for a dependency that is not there | `webhooks-rise.ts` header | **HOLDS.** `503 service_unavailable` |
| The KYC row answers **404**, because an unselected vendor names no resource | `webhooks-kyc.ts` header | **HOLDS.** `404 not_found` |
| *"`productionAdapters` resolves nothing and a live deployment answers `503 service_unavailable`"* | `webhooks-psp.ts` header | **WRONG.** `404 not_found` |
| *"this resolves `null` and the route answers 503"* | `webhooks-psp.ts`, `productionDeps` docblock | **WRONG.** `404 not_found` |

**THE REASON IS ORDER AND IT IS IN THE RECEIVER'S OWN NUMBERED STEPS.** `receivePspWebhook` step 1 resolves the `:provider` path parameter before step 2 looks at `store` and `applier`. `productionDeps.adapters` returns `null` for every name, so every provider name is unknown, so step 1's `not_found` is reached and step 2's `service_unavailable` is not. **The PSP row answers 404 for the KYC row's reason and not for its own**, and the only row that genuinely reaches 503 is the Rise row, which carries no path parameter and so names no resource that could be absent.

**AND THE HEADER NAMED A SYMBOL THAT IS NOT IN THE FILE.** `productionAdapters` does not exist; the value is `productionDeps.adapters`. Corrected beside the original.

**NEITHER IS A DEFECT IN THE RECEIVER.** 404 is the right answer for an unknown provider and step 1 is in the right place. What was wrong is a sentence about it, written when nothing could check it.

### 10. A landmine this entry names and does not repair

**THE RAW CONTEXT'S ROUTES ARE REGISTERED AT `ready()` AND NOT INSIDE `compose`.** A Fastify plugin body runs on boot, which `listen` and `inject` both await, so nothing observable changes for a deployment or for the suite. But it means `app.hasRoute` for a raw path is false between `compose` returning and the app booting, where it was true before. **Nothing in this tree reads it in that window**, checked by grep, and `compose` still refuses every duplicate and every malformed module synchronously, so the registry's own checks did not move into the boot. A future caller that inspects the router before `ready()` would see three fewer routes than the report names, and would be right to be surprised.

  **What a founder read adds and this entry cannot.**

  **THE FIRST QUESTION IS WHETHER `rawBody` ON `RouteDefinition` IS THE RIGHT PLACE FOR THIS DECISION.** I put it on the route because the route is what knows it must verify a signature over bytes, and because the alternative I can see, a list of raw paths read by `compose`, is the hand-maintained list this registry exists to refuse. The argument against is that `RouteDefinition` has been three fields since it was written and every future body-parsing question now has a precedent for landing here as a fourth, fifth and sixth flag. I think a boolean whose only value is `true` on three routes is cheap; I am aware that is what the first flag always looks like.

  **THE SECOND IS THE ALIAS.** `installRawBodyParser` in `registry.ts` is re-exported from `routes/webhooks-psp.ts` as `installRawWebhookBodyParser`, so one function answers to two names. I chose it to keep three suites held by concurrent rows out of this diff. The honest alternative is to rename the four call sites and have one name; it is a better tree and a worse merge this week. **If the answer is that two names is not acceptable, the repair is four import lines and I would rather be told than guess.**

A session that made a false sentence measurable and left it standing would be leaving a worse trap than it found.
