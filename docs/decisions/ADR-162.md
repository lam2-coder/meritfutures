## ADR-162: the portal's HTTP client is one server-side file that forwards one cookie, stores nothing, and asserts no wire shape  (2026-08-27, status: proposed)

**[`162`](ALLOCATION.md) was reserved REQUIRED rather than conditionally, and the requirement held for the reason the row gives.** [`surface.test.ts`](../../apps/portal/test/surface.test.ts) has asserted since session 111 that NO file under `apps/portal/src` contains `fetch(`, `XMLHttpRequest`, `WebSocket` or `EventSource`, with a stated reason: *"the fetch layer arrives with the framework. Asserting it now means THE FIRST `fetch` WRITTEN HERE IS A DECISION SOMEBODY MAKES ON PURPOSE rather than one that appears in a diff."* **Narrowing a landed assertion from *no transport* to *transport in one named file* is a ruling whichever way it goes**, and the alternative to a ruling is six segments each inventing an origin, a cookie policy and a cache window in a diff nobody read as a transport decision.

**The five decisions were enumerated by the file that refused to take them.** [`app/payouts/source.ts`](../../apps/portal/src/app/payouts/source.ts) read, until this entry: *"A client for `/api/v1` needs a base URL, a session cookie policy, an error mapping onto ../../shell/app-shell.ts's `PortalErrorKind`, and a decision about caching that INV-M4-04's re-fetch depends on. Five other segments land in this same app in this same wave and every one of them needs the same client. A transport invented inside `app/payouts/` would be the sixth copy or the one everybody else has to adopt unread, and neither is this segment's to choose."*

- **Origin:** [P4](../plans/P4-portal-and-site.md)'s remaining transport work as [P6 section 6](../plans/P6-live-tier.md) rows it, branch `claude/portal-http-client`, session **273**. The number was **RESERVED BEFORE DISPATCH and REQUIRED** ([ALLOCATION](ALLOCATION.md)), so none was chosen here; the `162` row is amended **in place** per [ADR-065](ADR-065.md) T3.

- **NOT MONEY BY FILE AND MONEY-ADJACENT BY CONTENT.** No migration, no `SD-nn`, no ledger, no engine, no payout write, no auth surface. **The one clause worth a founder's eye is clause 4**, because the failure it forecloses is `FM-M4-03` and the corpus calls that *"the single most common vibe-code fatality"*.

### 2. THE RULING

> **1. THE BASE URL IS AN ORIGIN IN `MERIT_API_ORIGIN`, IT HAS NO DEFAULT, AND THE CONTRACT'S BASE PATH IS NOT AN OPERATOR'S TO SET.** Findings 6 and 15. The variable carries scheme, host and optional port and is refused if it carries a path, a query or a fragment; `/api/v1` is appended by [`client.ts`](../../apps/portal/src/http/client.ts) and is a second copy of finding 6's constant **asserted against its source** rather than imported, because `apps/portal` does not declare `@merit/api` and admitting it would pull Fastify, `@merit/db` and `@merit/ledger` into a UI deployable to read one string. **`http` is refused outside `localhost`**: finding 5 marks the cookie `Secure`, so a plaintext origin produces a 401 on every read that looks exactly like an expired session.
>
> **2. THE REQUEST IS MADE BY THE PORTAL'S SERVER AND CARRIES EXACTLY ONE COOKIE. THE BROWSER NEVER CALLS THE API.** Findings 3, 4 and 5, in that order and none of them a preference. The API sets no `Access-Control-Allow-Origin`, so a browser fetch across the origin boundary is refused before the cookie question is reached; the cookie is `httpOnly`, so page script could not attach it by hand either; what remains is a server holding the inbound `Cookie` header. **It forwards `merit_session` and nothing else, never the whole header**, because the portal's own origin may accumulate cookies that are nobody else's business and relaying them wholesale would hand every one of them to another deployable on every read.
>
> **3. A STATUS MAPS THROUGH `toPortalErrorKind` AND THIS FILE ADDS NO MEMBER TO THAT UNION. A FAILURE WITH NO STATUS IS `server_error` AND CARRIES `status: null`.** Finding 7. A request that never reached a status line has no number, and inventing one -- `503` is the tempting one -- puts a sentence in the server's mouth that no server said. **`server_error` rather than `unexpected` is the argument**: [`app-shell.ts`](../../apps/portal/src/shell/app-shell.ts) reserves `unexpected` for a case it names a rendering bug, and an unreachable API is an outage rather than a defect in the page. `status: null` is what keeps the two distinguishable without a second vocabulary. **A `2xx` whose body is not JSON is the same answer with the status it did have.**
>
> **4. EVERY READ IS `no-store`, THE CLIENT OFFERS NO WAY TO SAY OTHERWISE, AND THE REASON IS NOT STALENESS.** Findings 8, 9 and 10. The first two require it. **The third is why it is not negotiable per screen**: a cache is a key and a value, every response here is identity-scoped, and a key that omits the session serves one trader's payouts to another. That is `FM-M4-03`, and it is reached not by writing a bad key but by not writing one. **The safe design is the one with no store to leak**, and it is stated in source rather than inherited from a framework default, because a default is a thing that changes in a minor version with no diff in this repository.
>
> **5. THE CLIENT RETURNS `unknown` AND ASSERTS NO WIRE SHAPE. NARROWING IS THE SEGMENT'S AND IS FORCED.** A generic `get<T>` is a cast the compiler cannot check: `get<AccountDetail>` reads as a guarantee and is a claim about bytes nobody inspected. A transport that validated shapes would have to know all of them, and this application already keeps its shapes honest by transcription in [`api/types.ts`](../../apps/portal/src/api/types.ts). **`unknown` cannot be read without a check**, so the check lands beside the transcription, where a reviewer looking at the screen can see it.
>
> **6. THE ASSERTION IS NARROWED PER NEEDLE, NOT PER FILE, AND THREE OF THE FOUR NEEDLES DO NOT MOVE.** Finding 2. `fetch(` moves from *no file* to `src/http/client.ts`. `XMLHttpRequest`, `WebSocket` and `EventSource` are still permitted in **zero** files, so a client that reached for `EventSource` fails the same test, which a bare "this file may do transport" allowlist would not have caught. **A companion assertion fails if a permitted file stops existing or stops performing the call it was permitted**, because a stale exception is the control quietly back at *none* while looking narrowed.
>
> **7. `P6-h` MOVES `WebSocket` FROM ZERO FILES TO ONE AND INHERITS CLAUSES 1 AND 2 WHOLE.** Finding 16. That slice adds one entry to one row of the transport table and writes no second origin resolution and no second cookie policy; if the socket needs something clauses 1 and 2 cannot give it, that is an amendment to this entry rather than a second answer inside `src/live/`. **This clause binds another slice without taking its ruling**: what the socket's frame shape is, where it connects and how it degrades are [ADR-161](ADR-161.md)'s and `P6-g`'s, and nothing here touches them.
>
> **8. `app/payouts/` IS THE ONE SEGMENT WIRED, AND IT ASKS ONLY FOR THE ENDPOINT THAT EXISTS.** Finding 12. `load` performs `GET /payouts` and asks nothing of `GET /accounts/:accountId/eligibility`, because a request to an unregistered path returns 404, clause 3 correctly maps that to `not_found`, and **a screen rendering it would tell the trader their ACCOUNT was not found.** The other five segments are not wired here; each is one `load` and one guard.

### 3. WHAT THIS FORECLOSES

**1. NO OTHER FILE IN `apps/portal/src` MAY CALL `fetch(`.** Clause 6, and it is a test rather than a convention. A second segment that writes its own transport fails `surface.test.ts` by name and line.

**2. NO SERVER ACTION, EVER, AND NO ROUTE HANDLER ON THE API SURFACE.** Finding 11. This entry does not soften either refusal and does not rely on softening one: the client is an ordinary module, it declares no directive, and it serves no path. **The portal never re-serves what it reads**, so API_CONTRACT section 1's *"no privileged back door"* stays a property of there being no door.

**3. NO BROWSER-SIDE CLIENT AND NO `credentials` OPTION.** Clause 2. A segment that wants data fetches it where the session already is, which is the server component. **This forecloses client-side polling, optimistic re-fetch on focus, and any interactive control that reads the API without a navigation**, and that cost is accepted here rather than argued per screen. Reopening it is a change to `apps/api` first (finding 4) and an entry second.

**4. NO CACHING OF ANY KIND, WHICH FORECLOSES STATIC RENDERING OF EVERY AUTHENTICATED SCREEN.** Clause 4. No `revalidate`, no cache tag, no `force-cache`, so every navigation pays a round trip. **The one surface in [M04](../plans/M04-trader-portal.md) with a real claim to caching is the public certificate verification page**, `SC-M4-08`, because it is the one read with no session; it does not relax this constant when it lands, it is a different function with its own entry.

**5. NO SHAPE ASSERTION IN THE TRANSPORT, WHICH MEANS A NEW SEGMENT OWES A GUARD.** Clause 5. `app/payouts/source.ts` is the worked example and its guard checks **every field the view reads, not a subset**: a partial guard reads as a complete one at the call site and crashes on the field it skipped, which is worse than none because it looks like a control.

**6. THE ORIGIN IS REFUSED RATHER THAN DEFAULTED, AND THE REFUSAL IS PER READ.** Clause 1. Nothing in this application runs at start, so an unconfigured deployment is discovered by a screen rather than by a process that failed to boot. **`source.ts` converts `ApiConfigError` AND NOTHING ELSE** into the screen's existing *waiting on an endpoint* state, on the ground that a deployment with no API genuinely cannot reach either endpoint; a transport failure or a bug in a path propagates, because converting those would make every fault in the application look like a pending endpoint.

### 4. THE ALTERNATIVES, AND WHY EACH IS REFUSED

| Alternative | Why refused |
|---|---|
| **A browser-side client with `credentials: 'include'`** | Finding 4. `apps/api` sends no `Access-Control-Allow-Origin` and no `Access-Control-Allow-Credentials`, so it does not work today, and making it work is a change to the deployable that serves the whole public surface. **It is also the wrong direction**: `httpOnly` exists so that page script cannot hold the session, and a design whose happy path is the browser presenting it spends that property for a round trip |
| **A Next.js Route Handler in `apps/portal` proxying `/api/v1`** | [ADR-095](ADR-095.md) ruling 3 and `RI-09`. It is the shape that makes CORS go away and it is exactly the *"privileged back door"* [ADR-083](ADR-083.md) section 3 refuses; the check would fail the directory before the reviewer read the file |
| **A Server Action per segment** | Finding 11. Refused TOTALLY rather than by path, because an action has no path: *"the endpoint is real, runs with this deployable's credentials, and nothing in the tree describes what it answers"* |
| **`get<T>(path)`, generic on the caller's expected shape** | Clause 5. It reads as a guarantee and is an unchecked cast. The failure it produces is a `TypeError` deep inside a view function, on a screen that renders money, attributed to the view rather than to the response |
| **`get(path, decode)`, a required decoder argument** | Genuinely better than the generic and still refused, on cost: it forces a decoder for shapes nothing can fetch yet, and `EligibilityResponse` alone is ten nested gate objects behind an endpoint no route registers (finding 12). `unknown` obtains the same discipline -- the field cannot be read without a check -- and lets each guard land with the segment that needs it |
| **Reading `document.cookie` or a bearer token** | Finding 5. There is nothing to read: the cookie is `httpOnly` and API_CONTRACT states there are *"no bearer tokens in local storage"* |
| **A short cache keyed on the session token** | Clause 4. It is the design that is correct and still refused: it puts a money number in a store that must be invalidated correctly forever, to save a round trip on a screen a trader opens a few times a month. `INV-M4-04` would then need a bypass, and a bypass is a thing a later screen forgets |
| **Deleting the four needles from `surface.test.ts`** | Finding 2, and [P6 section 8](../plans/P6-live-tier.md) forbids the same move to `P6-h` by name. It removes the control while appearing to satisfy it |

### 5. WHAT IS REPORTED RATHER THAN RESOLVED

**1. THE PAYOUT CENTRE CANNOT SAY "THIS FAILED", AND THE REPAIR IS NOT ONE FILE.** `PayoutCenterLoad` has two arms, `ready` and `unavailable`, and a `GET /payouts` that returns 500 renders exactly as a missing endpoint does. **That is [`source.ts`](../../apps/portal/src/app/payouts/source.ts)'s own argument -- *"`unavailable` IS NOT AN ERROR STATE"* -- cutting the other way now that a request can fail.** An error arm needs `./sections.ts` to render it and `./page.ts` to branch on it, and this session's fence holds neither, so it is reported here rather than reached for. **The client already carries what the arm would need**: `ApiFailure` has the `PortalErrorKind` and the status.

**2. `GET /accounts/:accountId/eligibility` IS DEFINED BY THE CONTRACT AND REGISTERED BY NOTHING**, and this session did not register it: `apps/api` is outside the fence. Finding 13 shows it has been on the record since session 272. **This screen additionally has no account to ask about** even once the route exists, because `GET /payouts` is account-less and nothing in this segment selects an account; that is P5's payout-centre routing.

**3. THE OTHER FIVE SEGMENTS ARE NOT WIRED.** `accounts`, `calendar`, `kyc`, `referrals` and `(purchases)` still render from fixtures. Each is one `load` function and one guard against the client this entry lands, and none of them needs a ruling.

**4. `next/headers.js` IS AN IMPORT SPECIFIER SHAPED BY A RESOLUTION MODE, AND THE NEXT AUTHOR WILL MEET IT.** Finding 14. It is recorded in the file rather than only here, because the failure mode is an error message that reads like a missing dependency.

### 6. Founder approval

**One checkable clause, and it names the property rather than a file count.**

> **Exactly one file under `apps/portal/src` contains `fetch(`, and it is `src/http/client.ts`; `XMLHttpRequest`, `WebSocket` and `EventSource` appear in none.** Checked by [`surface.test.ts`](../../apps/portal/test/surface.test.ts), which walks the tree rather than reading a list, and **watched failing on a real seeded second file** -- `src/app/accounts/seeded-transport.ts` calling `fetch` -- reporting `app/accounts/seeded-transport.ts: fetch(` before the seed was removed.
>
> **The direction it fails in is the one that matters.** A second segment that writes its own client type-checks, lints clean, passes every other assertion in this application and renders correctly. This clause fails on it immediately, and it fails identically for `EventSource` inside the permitted file, which is the case an allowlist keyed on the file would have missed.

**What a founder read adds and this entry cannot.** Every fact in section 1 is a file's own words or a command's output. **Clauses 2 and 4 are not.** Clause 2 decides that this application's data path runs through the server on every navigation, which is a shape the whole frontend inherits and which costs interactivity the corpus has not priced. Clause 4 spends a round trip per screen to make a cross-identity leak structurally impossible rather than defended, which is `C-26`'s standard applied to a surface with no store; the alternative that spends less is section 4's second-to-last row, and it is refused on a judgement about what a later screen forgets rather than on a citation.

**Approval line: UNSIGNED.**
