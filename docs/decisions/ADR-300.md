## ADR-300: the resolver's keep-both branch duplicates a generated line, and `RI-31` is the whole control. The repository ships a landmine entry and no code (2026-08-30, status: proposed)

**The subject of this row is a defect in the dispatcher's own merge tool rather than in this tree, so the first question is not how to fix it. It is whether there is anything in this repository to fix at all.** A scratchpad markdown conflict resolver's ADDITIVE branch keeps both sides of a `docs/STATE.md` conflict without deduping a line that carries a `<!--gen:` span, so a wave merge reintroduces a duplicated generated line. `RI-31` has caught it on four consecutive merges and is the only check that ever sees it.

**THE ANSWER IS THAT THERE IS NOTHING TO FIX, AND IT IS A MEASUREMENT RATHER THAN A PREFERENCE.** The resolver is untracked and is not in this tree. The two things a repository could ship in its place, a committed merge helper and a committed merge driver, were each built and run on this tree, and both fail for reasons that are properties of `git` rather than of the helper anybody would write. Meanwhile `RI-31` was measured against sixty commits of `main` and has not let one duplicate through since the day it landed, where the ten commits before it did.

**THE FOUR FIRINGS ARE THE CONTROL WORKING, AND THE HISTORY SAYS SO IN A WAY NOBODY HAD LOOKED AT.** Before `RI-31` existed, a duplicated generated line reached `main` itself: `9f4a8f4a`, a first-parent merge commit on `main`, carries thirteen duplicated generated lines over three files at fifty excess copies. Since `RI-31` landed, across sixty commits of `main` and five consecutive registry merges, the count is zero. **A control that has fired four times on a defect that used to land is a control that is now catching what it used to miss.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `300`, session **491**, branch `claude/the-resolver-duplicates-a-generated-line`. **NON-MONEY. NO CODE.** `apps/**`, `packages/**`, `scripts/**`, `.github/workflows/**`, `.gitignore` and `.claude/**` are untouched, and `git diff origin/main --stat` outside `docs/` is EMPTY.

- **`RI-31` IS NOT WEAKENED, NOT RETIRED, NOT NARROWED AND NOT TOUCHED.** `packages/tooling/checks/repo-invariants.mjs` has no diff against `origin/main`. `RI-12` is likewise untouched and stays for the reason its own header gives.

- **NO `RI-nn` IS MINTED AND ROW `300` RESERVED NONE.** The next-free note is not moved.

- **THE COUNT OF CHECKS DOES NOT MOVE.** `31 of 31 invariants hold.` and `33 of 33 gates pass.` before this change and after it.

### 1. The honest question, answered first and in writing

The resolver is a scratchpad script. It is not tracked, it is not present in this checkout, and no gate in this repository can see it. So the repository change this row could make is one of exactly three things, and each was tested rather than argued:

| Candidate | Verdict |
| --- | --- |
| A committed merge helper, a script a session runs to resolve a markdown conflict | **REFUSED.** Section 3. It is inert unless every clone runs an untracked local step, and the fifth data point proves sessions vary their resolution method, so a helper nobody must run is not a control |
| A committed merge driver, `merge=union` in a tracked `.gitattributes` | **REFUSED.** Section 3. It is the defect, institutionalized, and it removes the conflict the session would otherwise have seen |
| Nothing, because `RI-31` is already the correct and sufficient control | **THIS IS THE RULING.** Sections 2 and 4 |

**The outcome is a documented landmine entry and no code.** That is [EC-158](../edge-cases/EC-158.md), and this entry.

### 2. The defect reproduces, and all three claims about which checks see it hold

Reproduced on this tree in a throwaway worktree, then removed. Two branches off `origin/main` each append a session section to the end of `docs/STATE.md`. The headings differ, the closing sentences differ, and **the middle line is byte-identical on both sides**, which is the formulaic "position" line `docs/STATE.md` session sections carry and which holds two `gate_count` spans. `git merge` puts the whole block in one conflict hunk with the shared line on both sides. The additive keep-both resolution is then applied literally: delete the three marker lines, keep every other line.

Three commands on the resolved tree, each run separately, each exit code read without a pipe:

| Check | Result |
| --- | --- |
| `node packages/tooling/checks/repo-invariants.mjs RI-31` | **FAIL, exit 1.** *"docs/STATE.md:11071,11076 carries one generated line 2 times where a generated line is written once ... Keep the first and delete the rest"* |
| `node packages/tooling/checks/repo-invariants.mjs RI-12` | **PASS, exit 0.** Its ceiling is 8 and the duplicate sits at 2 |
| `node scripts/corpus/gates.mjs generate` then `check` | **exit 0 then `33 of 33 gates pass.`** `generate` rewrote every span in the file and the duplicate came out the other side intact, still at two copies |

**Three for three, exactly as the row stated.** The `CI-06g` leg is the one worth stating twice: the count gate does not merely fail to notice the duplicate, it **runs over it and leaves it correct**, because it rewrites every copy it finds and compares each to its own query. Two correct copies of one correct span is what a count gate looks like on a broken file.

### 3. The repository has no committable merge-time lever, and the one git gives away free is the defect

Both candidates were built as commits in the same worktree and merged against the same conflicting branch.

**A committed `.gitattributes` naming a custom driver is INERT AND SILENT.** With `docs/STATE.md merge=meritmd` committed and no `merge.meritmd.driver` defined anywhere, `git merge` fell straight back to the default text merge and produced the ordinary conflict. **No warning, no error, no diagnostic of any kind.** The driver definition lives in git config, which is per-clone and untracked, so a committed merge helper is not in force until every clone runs a local setup step that nothing in this repository can require. **A control that depends on a per-clone setup step is a control that depends on being remembered**, which is the property that puts it in the same class as the resolver bug it would be fixing.

**`merge=union`, the only driver that is built into git and needs no config, is the defect rather than the fix.** With `docs/STATE.md merge=union` committed, the same merge reported *"Merge made by the 'ort' strategy"* and **exited 0 with no conflict at all**. The shared generated line landed twice, and `RI-31` went red on the result. So the single fully committable merge-time lever available to this repository does not prevent the duplicate. It **produces** the duplicate automatically, on every merge, and it takes away the conflict marker that is the only reason a session looks at the hunk. Adopting it would convert a defect that requires a careless resolution into one that requires nothing at all.

**This is why the right control for this defect is a check on the tool's OUTPUT rather than a replacement for the tool.** The output is in this repository. The tool is not.

### 4. `RI-31` is holding the line, and the before and after is in git history

Nobody had measured this. The row reports four firings; the firings are the visible half. The measurable half is what reached `main`.

Every commit reachable from `origin/main` but not from `RI-31`'s landing commit `ce168690` was scanned for a whole line carrying a `<!--gen:` span that appears twice, across the nine files in this tree that carry generated spans and are amended by merges: `docs/INDEX.md`, `docs/STATE.md`, `docs/decisions/ALLOCATION.md`, `docs/decisions/README.md`, `docs/edge-cases/README.md`, `docs/sessions/README.md`, `docs/architecture/data-model/README.md`, `docs/testing/golden-scenarios/README.md` and `packages/db/DELTA_MANIFEST.md`.

| Population | Result |
| --- | --- |
| **Sixty commits in which `RI-31` EXISTS** (`ce168690` is an ancestor) | **ZERO carry a duplicated generated line.** This population contains the four merges the row names and the fifth it cites |
| **Ten commits in which `RI-31` DOES NOT YET EXIST** | **All ten carry them.** Confirmed by running the live runner against those trees, which answers `no such check: RI-31` |
| **`9f4a8f4a`, a FIRST-PARENT merge commit on `main`** (*"Merge pull request #629"*) | **Thirteen duplicated generated lines over three files, fifty excess copies.** A duplicated generated line reached `main` itself |

The tail is clean by the same measurement. Whole-tree scans of every tracked `.md` at `e812e5ae`, `290521f7`, `3a1e1aa6` and `8b4920fa` each report zero, and `RI-31` PASSES on the checkout this entry was written on.

**This is the measurement that reads the sign the right way round.** The accumulated pre-`RI-31` damage is the fifteen instances [ADR-282](ADR-282.md) repaired in fifty-one deletions on the day it minted the check. `9f4a8f4a` is a snapshot of that damage still on `main`. Four firings since are four occasions on which the same thing was stopped at the branch instead. **A session that reads four failures as a false-positive rate is comparing them against a zero that `RI-31` is the cause of.**

### 5. The fifth data point, confirmed, and what it narrows

`3a1e1aa6`, *"merge: main into ADR-299's branch, keeping both registry rows"*, the fifth consecutive registry merge, resolved three markdown conflicts by hand. It carries **zero** duplicated generated lines, by whole-tree scan and by `RI-31` on the merged content.

**So the defect is specific to the resolver's keep-both branch and not to registry merging in general**, which is what the row said and which is confirmed here. It narrows the target correctly and, combined with section 3, it closes the case for a helper: **a hand resolution and a helper resolution are both things a session chooses**, and one session in five already chose neither the resolver nor a helper. Any control that sits at the moment of resolution is a control the session can decline. `RI-31` sits at the moment of verification, which is in the mandated pre-push set and in `CI-01` on every push and every pull request, and cannot be declined.

### 6. What is refused, and why

- **Weakening, retiring, narrowing or re-scoping `RI-31`.** Refused. Section 4 is the reason and it is arithmetic, not judgement.
- **A committed merge helper.** Refused on section 3, and on the fifth data point.
- **`merge=union` in `.gitattributes`.** Refused on section 3. It is the defect.
- **A `.claude/settings.json` hook that blocks a commit carrying a duplicated generated line.** Refused on three grounds. It is a **second statement of one property in two places**, the shape session 472 refused when it returned `RI-31`'s own number for exactly that reason. It protects only harness-launched sessions, so it is **narrower** than `RI-31` rather than wider, while costing a tree walk on every intercepted call. And `RI-31` already runs in `CI-01` on every push and every pull request, so it adds no coverage, only an earlier copy of the same red.
- **Adding a `docs/edge-cases/` golden scenario for this entry.** Refused. [EC-158](../edge-cases/EC-158.md) declares `none owned`, which the `CI-06e` gate accepts and reports. This is a defect in a tool outside the tree and owns no product behavior.

### 7. Found and reported, not fixed, out of fence

**`scratchpad/` is neither tracked nor ignored.** `git check-ignore -v scratchpad/resolve.mjs` exits 1 and prints nothing, and `.gitignore` has no entry for the directory. So the resolver that carries this defect appears in `git status` as untracked, and a `git add -A` would commit it. That matters more than it looks: the standing rule against `git add -A` in this repository exists for `falsify.mjs`'s tree mutations, and a session that observes the rule for that reason has no reason to expect an untracked tool sitting in the same tree.

**`.gitignore` is outside this row's fence and was not edited.** It is named here as a follow-up row.

**The ideal home for this landmine is `RI-31`'s own header comment**, because a session that has just watched `RI-31` go red on a merge is already reading that file, and that is the moment it decides whether the check is noisy. `packages/tooling/checks/**` is outside this row's fence, and editing the control's own file under a row about that control is the move the row forbids. **One sentence in that header pointing at [EC-158](../edge-cases/EC-158.md) and this entry is a follow-up row**, and it is the one worth dispatching.

### 8. What this row did not do

No `src/` line moved. No migration was written or reserved. No schema, no gate runner, no workflow and no check was edited. No `RI-nn` was minted and none was returned, because row `300` reserved none. The registry READMEs and `INDEX.md` in this diff are **generated** by `node scripts/corpus/gates.mjs generate` and are not hand-written.

### 9. Consequences

**The operating instruction for every future merge is unchanged and is now written down.** Resolve the conflict, run the mandated verification set, and if `RI-31` is red, collapse the duplicate it names. That is what the last five merges did and it is why `main` is clean.

**One caveat on `RI-31`'s own remediation sentence, recorded because it is a heuristic and reads as a rule.** The message says *"Keep the first and delete the rest"*, which is right whenever the copies are a merge artifact. It was NOT right for at least one of the fifteen [ADR-282](ADR-282.md) repaired, where one sentence had been splattered into five session sections of `docs/STATE.md` and its home was a specific session rather than the earliest occurrence. **A session collapsing a duplicate should confirm which copy belongs where before deleting**, and on a keep-both merge artifact that confirmation is immediate because the two copies are the two sides of one hunk.

### 10. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

**What a founder read adds and this entry cannot.**

**THE FIRST IS WHETHER "NO CODE" IS THE RIGHT DISPOSITION FOR A DEFECT THAT HAS NOW FIRED FIVE TIMES.** This entry argues it is, on the ground that every repository-side preventive lever is either inert without a per-clone step or is the defect itself, and that a detective control with a perfect record over sixty commits is not improved by a preventive one that can be declined. **A founder who weighs the recurring cost of the hand collapse more heavily would dispatch the merge helper anyway and accept that it works only when it is remembered.** That is a judgement about how much a repeated small cost is worth, and it is the part of this entry most worth overruling.

**THE SECOND IS THE FENCE.** Two repairs were found and left: `.gitignore` has no `scratchpad/` entry, and `RI-31`'s header does not point at this landmine. **Both are outside the fence, both are cheap, and both are in the file a session would actually read.** Leaving them is correct under the standing rule and it leaves the landmine recorded in the registry a merging session does not open. Whether those become one follow-up row or are folded into the next tooling wave is a scheduling decision this session cannot take.

**THE THIRD IS WHETHER THIS BELONGS IN `docs/edge-cases/` AT ALL.** That registry is seeded from the constitution's M1 list and the B4 battery, and every entry in it before this one carries a product module. [EC-158](../edge-cases/EC-158.md) carries none, because the defect is in a tool this repository does not contain. The row's fence named `docs/edge-cases/` as the home for a landmine entry and this entry took it at its word. **A founder may prefer that process and tooling landmines get a register of their own** rather than a module-shaped entry with the module field answered "none".
