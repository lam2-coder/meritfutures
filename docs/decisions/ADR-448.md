`updateStatementOn` at [`scoped-db.ts:1211`](../../packages/db/src/scoped-db.ts) reached `.set(values)` at `:1221` with the caller's keys unfiltered. **Both line numbers were confirmed by opening the file before anything was written**, along with `refuseTenancyColumn` at `:473` and `refuseTermInValues` at `:946`.

**NO POINTER INTO `node_modules` IS WRITTEN ANYWHERE IN THIS DIFF, AND THE SCAFFOLD HAD TO SAY SO TWICE.** The guard's first draft cited a line inside the installed `drizzle-orm` package and **`RI-15` caught it in the code**: *"... and NO FILE IN THIS TREE has that path. ### 5. What the guard refuses, and the one thing it must never touch

`refuseGeneratedColumn` refuses a values key naming a column `schema.ts` declares `GENERATED ALWAYS AS (...) STORED`. **BOTH SPELLINGS**, property and SQL name, on `refuseTenancyColumn`'s own stated reasoning: the values object is keyed by Drizzle property names and the DDL names the column, so `delta_cents` is reachable as `deltaCents` and only one of those looks like the migration's word.

**IT GUARDS `values` AND NEVER AN ADDRESS, AND THE DISTINCTION IS THE ONE THING THAT COULD HAVE BROKEN A LIVE MONEY PATH.** [`apps/worker/src/recon/sweep.ts`](../../apps/worker/src/recon/sweep.ts) addresses `reconciliations` by its identity `id` at `:615` and must keep working. An address is a predicate that READS a column; `SET id = ...` WRITES it. They arrive through different parameters and only one is checked.

**THE LIVE WRITER WAS OPENED BEFORE THE GUARD WAS WRITTEN, NOT AFTER.** `recordComparison` at [`sweep.ts:577`](../../apps/worker/src/recon/sweep.ts) builds its values object from six fields and `deltaCents` is deliberately not among them; the comment at `:352` already records that the database re-derives it. **So no live caller names a member of the set, the guard changes no behaviour any caller relies on, and the dispatch's STOP condition is not reached for the half that landed.**

### 6. The identity half, seeded and measured rather than argued

[ADR-445](ADR-445.md) section 8 item 2 asks for the guard "widened" to identity columns, and the dispatch instructed this row to take it. **It is not taken, and the reason is a measurement.**

**THE CAUSE IS ONE SHAPE IN TWO HELPERS.** `someOtherColumn` at [`write-accessor.test.ts:180`](../../packages/db/test/write-accessor.test.ts) and `setFor` at [`keyed-accessor.test.ts:196`](../../packages/db/test/keyed-accessor.test.ts) both skip the TENANCY columns and return the first column left. **SO FOUR CASES IN THIS SUITE ASSERT THAT THE ACCESSOR ACCEPTS AN UPDATE POSTGRESQL ANSWERS `428C9` TO.** That is a finding in its own right and it is worth more than the widening: the tests are green because no database is involved, and they encode a write that could never succeed. **NEITHER FILE IS IN THIS ROW'S FENCE.** The dispatch names `schema.ts` and `scoped-db.test.ts` as row 449's and names neither of these. Editing a test in a file whose owner this row cannot see is exactly the collision the wave-branch instruction exists to prevent, and **the alternative, pushing a money-path branch with four red cases, is worse than both.** The seed was reverted and `packages/db/src/scoped-db.ts` verified byte-identical with `git hash-object`.

**THE GATE IS NOT WEAKENED AND NO TEST IS SKIPPED, DISABLED OR QUARANTINED.** The identity columns are still REACHED and COUNTED by leg D, and the count is asserted against the DDL fold, so the population cannot drift unobserved while the refusal is owed. Section 8 item 2 carries the price.
