## ADR-183: an identity's three ledger positions are opened by the database when the identity is created, and `0054` is spent  (2026-08-28, status: proposed)

**Nothing in this tree has ever created a ledger account for an identity. [ADR-181](ADR-181.md) section 4's third ground rests on that absence, in its own words: minting the eighth code *"today unblocks nothing"*, because `LT-06`'s debit leg is per identity and no such row can exist. THIS ENTRY MAKES THAT GROUND FALSE.** The mechanism is ruled EAGER AND IN THE DATABASE, a trigger on `identities`; the codes are ruled ALL THREE, derived from the vocabulary's own identity partition rather than from which module ships first. Migration `0054` is TAKEN AND SPENT.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `183`, session **334**, dispatched as `claude/identity-ledger-accounts`. **`0054` was CONDITIONAL on the ruled mechanism needing one.** It does: the ruling is the shape whose whole content is a migration, and section 3 is why the two shapes that would have returned the number unspent are refused.

- **MONEY PATH. A MIGRATION LANDS, SO AN [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) LINE-BY-LINE READ IS OWED ON IT AND IS NOT DISCHARGED HERE.** The entry ships `proposed` with an UNSIGNED approval line. `0009`, `0027`, `0038`, `0052` and `0053` are byte for byte unchanged, the vocabulary stays closed at seven, and **no eighth code is minted**.

- **WHAT IS DERIVED AND WHAT IS JUDGED, separated before the argument starts.** That every per-identity posting in this corpus is unpostable is DERIVED and is executed in section 7. That the three codes are the right set is DERIVED, from `LEDGER_ACCOUNT_SCOPE`. **That a trigger is the right home is JUDGED**, and section 9 states that question for the founder rather than burying it.

### 3. RULING 1: THE MECHANISM. Eager, in the database

**Three shapes were named in advance and each is answered.**

**(a) EAGER, IN THE DATABASE. TAKEN.** A trigger on `identities` writes the per-identity rows. Provisioning becomes coextensive with the identity's existence: there is no path that creates an identity and skips it, because the row is what fires it, whatever writes the row. **It needs no wiring, which matters more here than it usually would, because there is nothing to wire it into.**

**(b) EAGER, IN APPLICATION CODE. REFUSED, AND NOT ON PREFERENCE.** This is where every other control in this corpus lives and that is a real argument. **The path does not exist.** `grep -rni "insert into[[:space:]]*identities" --include='*.ts'` over `apps/`, `packages/` and `scripts/` returns **zero**, re-measured here; every reference to the table in TypeScript is a read, a lock, a scope predicate or a schema declaration. **A ruling placed on that path would be a ruling written against an absence, and on the day it was written the defect in section 2 would still be live.** The shape is not refused forever: when the identity-creation path is built it may take provisioning, and superseding a trigger is a later migration. What it cannot do is close this today.

**(c) LAZY, AT FIRST POSTING. REFUSED TWICE, AND THE SECOND REFUSAL IS MECHANICAL.** [`chart.ts:46`](../../packages/ledger/src/chart.ts) already refuses it in shipped source with its reason stated, so taking it means OVERTURNING A SHIPPED DESIGN rather than filling a silence, and this entry declines to read a stated refusal as an omission. **The second is not in the dispatch and is the harder one**: [`tx.ts:64`](../../packages/ledger/src/tx.ts) declares `LedgerWriteKey = 'ledgerTransactions' | 'ledgerEntries'`, so `ledgerAccounts` is READ-ONLY on the handle a posting is written through. `postTransaction` **cannot** open an account without widening that union, and [`tx.ts:59-61`](../../packages/ledger/src/tx.ts) states the narrowing is the point: *"a posting library that accepted the same range could write anywhere ... a widening is a diff on this union."* Lazy provisioning is therefore not a small change to `chart.ts`. It is a widening of the one boundary that package holds against itself.

**THE COST OF (a), MEASURED RATHER THAN ASSUMED.** The dispatch asked for the trigger claim to be checked before it was relied on. Read from the catalog rather than from a grep, over `0001` through `0053` applied from empty: **21 non-internal triggers over 19 distinct functions, and NOT ONE function body contains an `INSERT`, an `UPDATE` or a `DELETE`.** Two match the word `UPDATE` and both matches are inside an error-message string. **So this is the first trigger in this schema that WRITES rather than asserts, exactly as the dispatch predicted, and the entry does not soften it.** What the ruling rests on is that the alternative is not the same guarantee somewhere safer; it is no guarantee at all until a file that does not exist is written.

**THE SECOND COST OF (a) IS NOT IN THE DISPATCH EITHER: IT MINTS A FOURTH STATEMENT OF THE PER-IDENTITY VOCABULARY.** [`0009:49-58`](../../packages/db/migrations/0009_ledger.sql) states the seven, [`0027:118-120`](../../packages/db/migrations/0027_triggers_invariants.sql) states them again, [`accounts.ts:51-60`](../../packages/ledger/src/accounts.ts) states which three are per identity, and its header rules when a copy is allowed: it earns its place *"only because it is CHECKED against both of the others."* **A merged migration is never edited, so a fourth copy nobody checks is wrong forever.** [`identity-provisioning.test.ts`](../../packages/ledger/test/identity-provisioning.test.ts) reads the code list out of `0054` and holds it against `LEDGER_ACCOUNT_SCOPE` in both directions. That is the condition on which this shape was taken.

### 4. RULING 2: THE CODES. All three, at identity creation

**`ledger_accounts_identity_code_uq` is `(code, identity_id) WHERE scope = 'identity'` ([`0009:74-75`](../../packages/db/migrations/0009_ledger.sql)), so the schema permits either answer and this is a ruling rather than a constraint.**

**THE MECHANISM DOES NOT SETTLE IT, WHICH IS WORTH SAYING BECAUSE IT NEARLY DOES.** A trigger fires once and cannot know which code a future posting will name, so "the one a posting needs when it needs it" is unavailable in its literal form under shape (a). **What remains available is a smaller set**, and the tree contains a precedent for exactly that: the CI probe seeded TWO of the three, `trader_withdrawable` and `trader_wallet`, and not `promotional_credit`. That is the real form of the second question and it is answered rather than dissolved.

**TWO OF THE THREE ARE NAMED BY SHIPPED CODE AND THE THIRD IS NOT.** Section 2's sites name `trader_withdrawable` and `trader_wallet`. No TypeScript file constructs a `promotional_credit` reference; it is granted by [M14](../plans/M14-loyalty-retention.md), [M17](../plans/M17-offers-engine.md) and [M20](../plans/M20-wallet.md), none of which is built.

**IT IS PROVISIONED ANYWAY, ON THREE GROUNDS.**

- **Provisioning two leaves a second provisioning mechanism to be designed later, for one code, in a module that is not the ledger's.** That is this same ruling made a second time, and the second time it would be made by whoever happens to build the loyalty grant path. **The question of where a ledger account comes from is this entry's, and answering it for two thirds of the vocabulary answers it for none of it.**
- **The set written is DERIVED rather than chosen.** It is the identity partition of `LEDGER_ACCOUNT_SCOPE`, whole. A set of two would have to be derived from module ship order, which is not a property of the ledger and changes without anything noticing.
- **The type and the database agree.** `identityAccount` is typed over `IdentityAccountCode` ([`accounts.ts:71-74`](../../packages/ledger/src/accounts.ts)), which is all three. A caller can construct a `promotional_credit` reference today and it compiles; under a set of two it would compile and throw.

**AN ACCOUNT IS NOT A GRANT, AND THIS IS THE OBJECTION THAT DESERVES AN ANSWER RATHER THAN A DISMISSAL.** `INV-M14-10` and `INV-M17-08` require `promotional_credit` to have **no path to `trader_wallet` and no path to a withdrawal**, and `FM-M14-06` names promotional credit becoming withdrawable as a failure mode. **Those invariants are about ENTRIES, and this ruling writes none.** A zero-balance account crosses no boundary; what would cross one is a posting, and no posting is added here. The separation the two modules depend on is the separation of CLASSES, which `0009`'s vocabulary and `accounts.ts`'s partition already carry and this entry does not touch.

**THE COST IS A READ, IT IS ALREADY WRITTEN DOWN, AND THIS RULING MAKES IT MAXIMAL.** [`chart.ts:12-16`](../../packages/ledger/src/chart.ts) records that resolving one posting's references reads THE WHOLE CHART, *"four firm rows plus up to three per identity, which grows with the trader population and not with the posting."* **That comment anticipated this shape and priced nothing.** All three makes it exactly three per identity, and the chart read is 3n + 2 rows today. The remedy is named in the same header and is not reachable from that file: `rowsWhere` exists on the other three handles and the diff that would let `chart.ts` use it is on [`tx.ts`](../../packages/ledger/src/tx.ts). **This ruling makes that diff worth more and does not take it**, because widening `LedgerReadKey`'s handle is section 3's refused (c) arriving by the other door.

### 5. What `0054` does, and what it deliberately is not

[`0054_identity_ledger_accounts.sql`](../../packages/db/migrations/0054_identity_ledger_accounts.sql) is a function, a trigger and a backfill.

- **`provision_identity_ledger_accounts()` writes the three rows on `AFTER INSERT ON identities FOR EACH ROW`**, under `ON CONFLICT DO NOTHING` with no conflict target, so that `ledger_accounts_identity_code_uq` decides what already exists rather than the function holding a second opinion about it.
- **The `kind` literals are DERIVED AND SELF-CHECKING.** `ledger_accounts_kind_matches_code` as [`0053`](../../packages/db/migrations/0053_firm_treasury_kind.sql) left it rules all three per-identity codes `liability`, read out of the constraint in force rather than out of a file by name. **A wrong `kind` is refused by the database and every identity creation fails loudly.**
- **The `code` literals are NEITHER, and the hole was executed rather than reasoned about.** A row reading `('reserve','liability','identity', <uuid>)` satisfies `ledger_accounts_code_is_declared`, satisfies `ledger_accounts_scope_identity`, and falls through the kind constraint's `ELSE true`. **It was ACCEPTED.** The DDL never ties `code` to `scope`, which [`accounts.ts:17-23`](../../packages/ledger/src/accounts.ts) states from the other direction. **So the code half gets a test and cannot get a constraint.**
- **THE BACKFILL IS THE HALF THAT IS RIGHT IN AN ENVIRONMENT THAT IS NOT EMPTY.** A trigger repairs the future only, and an identity created before `0054` would keep the defect forever, which is a migration that looks like it worked. **This tree has no such row** and the statement writes nothing on a fresh install; it was nonetheless executed against a database with two pre-existing identities and filled both, and re-running it wrote nothing more.
- **IT SUPERSEDES NOTHING.** No `DROP CONSTRAINT`, no `CREATE OR REPLACE FUNCTION`, no `ALTER TABLE`, no `DROP TRIGGER`. **This is the diff [`0027:97-100`](../../packages/db/migrations/0027_triggers_invariants.sql) warns about NOT being**: it moves neither of the two guards, because it widens no vocabulary.
- **NO MANIFEST SECTION IS OWED AND THAT WAS CHECKED RATHER THAN ASSUMED.** `grep -c "0052\|0053" packages/db/DELTA_MANIFEST.md` returns **0**: neither predecessor took a section, `0054` introduces no `SD-` delta id, and the gate that reads that file binds delta ids rather than migration numbers.

### 6. `0054` DOES NOT MAKE `LT-06` OR `LT-07` POSTABLE, AND CONFLATING THE TWO ABSENCES WOULD BE THE EASY ERROR

**`LT-06`'s credit slot and `LT-07`'s debit slot are a firm-scoped `liability` with no code to hold it ([ADR-181](ADR-181.md) sections 1 and 2), and that is a different absence which this entry does not touch.** What changes is the ground [ADR-181](ADR-181.md) section 4 gave for returning `0054` unspent: *"minting it today unblocks nothing ... `LT-06` is unpostable on an absence this entry does not touch, whatever code sits in its credit slot."* **`LT-06`'s debit leg is `trader_wallet`, per identity, and it now resolves.** The eighth code's remaining price is the transcription set that entry measured, and its three grounds are now two.

**The other two grounds are untouched and are not weakened by this entry.** [GLOSSARY](../GLOSSARY.md) still says seven and [`0027:102-104`](../../packages/db/migrations/0027_triggers_invariants.sql) still records that list as the control that caught `firm_payable`; the two-guard design is still one that a single migration defeats by construction. **This entry mints no code precisely so that those two stay live.**

### 8. TWO MORE FINDINGS THAT WERE NOT IN THE DISPATCH

**8.1 `0054` REPRODUCED [ADR-177](ADR-177.md)'s DEFECT ONE CODE DOWN, IN THE CI PROBE, AND IT WAS FOUND BY RUNNING THE PROBE RATHER THAN BY READING IT.**

[`probe_ledger_constraints.sql`](../../scripts/db/probe_ledger_constraints.sql) seeded its two per-identity fixtures with **pinned uuids under `ON CONFLICT DO NOTHING`**. With `0054` applied, the probe's own `INSERT INTO identities` fires the trigger, the three rows already exist, the clause SKIPS the pinned rows, and the pinned uuid names nothing. **The `LEDGER-C1` block then raised**

```
LEDGER-C2: ledger_account aaaaaaaa-0000-0000-0000-000000000002 does not exist
```

**instead of probing `LEDGER-C1` at all.** That is precisely what that file's own next paragraph describes happening to `fees_revenue`: *"once that seed exists the clause SKIPS the row, the pinned uuid names nothing, and the LEDGER-C1 block below raises LEDGER-C2 on a dangling account instead of probing C1 at all."* **The zero-sum block had the identical defect on its own pinned row.** Both are repaired the way [ADR-177](ADR-177.md) repaired `fees_revenue`: the ids are RESOLVED from the chart through a temp view, with a `DO` block that raises if the row is missing, so a fixture that stops existing is loud rather than silent. **And the provisioning itself is now probed**, because a mechanism nobody has watched run is a mechanism nobody knows is wired up, which is that file's first line.

**8.2 AN IDENTITY THAT HAS BEEN PROVISIONED CAN NEVER BE DELETED, AND THAT IS ALIGNED RATHER THAN ACCIDENTAL.** `ledger_accounts.identity_id REFERENCES identities(id)` with no `ON DELETE`, so after `0054` every identity is permanently referenced. **This was checked against the corpus rather than left as a surprise**: `identity_status` is an enum of `active`, `restricted`, `closed`, closure is a STATUS and not a deletion, and nothing in `apps/`, `packages/` or `scripts/` deletes an identity. **A financial record whose subject can be deleted is the worse arrangement**, so this is reported as a consequence rather than a cost. It is stated here because a later session meeting a foreign-key error on `identities` should find the reason in the entry that created it.

### 9. Consequences

- **Two armed assertions fired and each was AMENDED rather than weakened**, which is what both were built for. [`chart-of-accounts-kinds.test.ts`](../../packages/ledger/test/chart-of-accounts-kinds.test.ts) asserted that every chart write is firm scoped and that no write carries `ON CONFLICT`; its own comment gave the reason, *"A migration has no identity to seed against"*, and `0054` needs none because it does not seed. **The file now partitions firm seeds from identity writes on the `scope` literal the statement itself carries**, keeps every original property on the firm half unchanged, and adds to the identity half the property the original was really holding: **no write names a literal identity**, the uuid comes from `NEW.id` or from a join. A case asserting the partition is TOTAL is added, because a statement naming neither scope would otherwise escape both sets while the block stayed green.
- **[`lt-07.test.ts`](../../packages/rail/test/lt-07.test.ts) TAKES ITS THIRD EXTENSION and this entry had to edit `packages/rail`.** That case *"asserted an empty list, ADR-177 filled it and ADR-180 extended it"*, and this is the next step in the sequence [ADR-174](ADR-174.md) section 7 built it for. ### 10. Approval

- **Approval line: PENDING, UNSIGNED.** **MONEY PATH. A MIGRATION LANDS.** The [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) line-by-line read is owed on [`0054`](../../packages/db/migrations/0054_identity_ledger_accounts.sql) and is NOT discharged by this entry, by the ruling being derived, or by the shape having been executed. **Merging is not signing.**

**What a founder read adds and this entry cannot.**

**THE QUESTION, PLAINLY. A WRITING TRIGGER IS A PRECEDENT AND THE PRECEDENT IS THE COST.** Twenty-one triggers in this schema assert and refuse; this is the twenty-second and the first that makes a row appear. **A founder who holds that rows in a financial schema should only ever be written by a statement somebody can read overturns ruling 1 in a sentence**, and the entry would rather be overturned there than have the alternative go unstated: shape (b) is that position, it is where every other control lives, and its whole cost is that the file it belongs in does not exist. **The honest form of the disagreement is a question about time, not about architecture.** If the identity-creation path is weeks away, (b) is the better ruling and section 2's two handlers keep throwing until it lands. If it is not scheduled, (a) is the only shape that closes anything.

**THE SECOND JUDGEMENT IS `promotional_credit`, AND TWO IS A DEFENSIBLE ANSWER.** Nothing constructs that reference today, the CI probe seeded two and not three, and a founder who reads a per-identity account as a thing the trader can be SHOWN may not want one opened for a promotional instrument nobody has granted. **The case for three is that the alternative is a second provisioning mechanism designed later by whoever builds the loyalty path**, and that the set of three is derivable from a shipped constant while the set of two is derivable only from module ship order. **If that is wrong, it is wrong in the cheap direction**: removing a code from the trigger is a later migration and no entry has posted against it.

**THE THIRD IS THAT THIS ENTRY MINTS A FOURTH COPY OF THE VOCABULARY INTO A FILE THAT CAN NEVER BE EDITED.** [ADR-181](ADR-181.md) refused to widen the vocabulary partly because [`0027:104`](../../packages/db/migrations/0027_triggers_invariants.sql) records GLOSSARY's class list as the control that caught the last invented class. **This entry does not widen the vocabulary, and it does copy part of it into a merged migration.** The mitigation is a test that reads the migration and holds it against `accounts.ts` in both directions; the mitigation is a test, and a test is a weaker thing than a constraint. **A founder who wants the code list read out of `ledger_accounts_code_is_declared` at trigger time rather than written into the function body is asking for something better than what shipped**, and it was not taken because a trigger that queries the constraint's own text to decide what to write is harder to read than the four literals it would replace. That trade is worth a second opinion.

**WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** It assumes that an identity's ledger positions should exist from the moment the identity does, rather than from the moment the identity has any financial relationship with Merit. **Those are not the same instant.** [`0002:32-62`](../../packages/db/migrations/0002_identity.sql) creates an identity with a `first_seen_at` and a default `active` status, and nothing there says money is involved; an identity that browses and never purchases would carry three ledger accounts under this ruling. **If the right trigger is the first purchase rather than the first sighting, this entry has put provisioning one step too early**, and the shape that follows is a trigger on a different table. This entry judges that wrong because `readChart` is the only reader and it filters by identity anyway, so the cost of an early row is 3 rows and no entries, while the cost of a late one is section 2's throw returning for whichever path runs first. **That is an argument about cost, and a founder who reads a ledger account as a statement that a financial relationship exists is reading it as a fact rather than as a slot, in which case the instant is wrong.**
