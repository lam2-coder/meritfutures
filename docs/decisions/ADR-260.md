### 2. RULING 1: the resolver is PURE and the caller reads the rows

**THE SPLIT IS THE DESIGN AND EVERYTHING ELSE FOLLOWS FROM IT.** [`resolveExternalGates`](../../packages/rules-engine/src/external-gates.ts) takes the RAW column values and returns the record or refuses. It opens nothing, reads no file and takes no transaction. The caller performs the reads; what the caller gets back is the NARROWING.

**THIS IS `types.ts`'s OWN SENTENCE HONOURED RATHER THAN CONTRADICTED.** That file has always said of `ExternalGates` that "every field is resolved by the CALLER", and a resolver that read rows would make that false. Reading is still the caller's. **What was never the caller's, and what two callers would otherwise each answer separately, is what `accounts.status = 'provisioning_pending'` means to the engine.**

**AND IT IS WHY THE PACKAGE CAN HOST IT AT ALL.** [`packages/rules-engine/tsconfig.json`](../../packages/rules-engine/tsconfig.json) sets `types: []`, so `readFileSync`, `fetch` and `process` do not exist inside it: "an I/O call inside this package is a COMPILE ERROR before it is a lint finding". A pure function is admissible there and a reader is not. [`apps/api/test/external-gates.test.ts`](../../apps/api/test/external-gates.test.ts) case 4.1 asserts the resolver's ONLY import is a type import, so the shortcut of having it read the rows itself is a named failure rather than a future temptation.

### 3. RULING 2: its home is `packages/rules-engine`, and the row asked why

**THE ROW SAID "if both deployables need it, `packages/` and say why". BOTH DO, AND THE WHY IS `ADR-239` SLICE A's ARGUMENT UNCHANGED.**

- [`apps/worker/src/batch/ports.ts`](../../apps/worker/src/batch/ports.ts) declares `readonly external: ExternalGates` on `AccountDay` and the field is required.
- [`apps/api/src/routes/payouts.ts`](../../apps/api/src/routes/payouts.ts) declares `readonly gates: ExternalGates` on `PayoutSubject`.
- **`apps/api` cannot import `apps/worker`**, and this package declares NO workspace dependency at all (`RI-01`), so it is the only place both arrows already point.

**A RESOLVER IN EACH IS NOT TWO SMALL RESOLVERS. IT IS `FM-16`**: two statements of one predicate with nothing comparing them, which is the defect [ADR-206](ADR-206.md) and [ADR-250](ADR-250.md) moved the gates codec here to close rather than to relocate. **The specific thing that would drift is the seven-versus-six question**, and it would drift silently, because both answers type-check.

**AND THE COST OF THE OTHER CHOICE IS ALREADY PAID ONE LEG DOWN, MEASURED RATHER THAN PREDICTED.** `currentKycState` is written out TWICE under `apps/api/src/routes/` -- once in [`accounts.ts:813`](../../apps/api/src/routes/accounts.ts) and once in [`wallet-withdrawals.ts:462`](../../apps/api/src/routes/wallet-withdrawals.ts) -- and the second one says why: "a route module importing another route module is an edge the registry does not have and the directory listing cannot express". **That is a real constraint and it is why the third copy could not go in a route.** `ADR-248` section 4 predicted a resolver would CALL `currentKycState`; section 12 of that entry named this as its most likely error, and it was: the function is unreachable from either place that needs it.

**THE ROW'S NARROWER PERMISSION IS ALSO SATISFIED AND IS NOT THE WHOLE JUSTIFICATION.** The fence admits `packages/rules-engine/src/**` "only if the refusal belongs beside the type". `AccountStatus` and `KycState` are declared in [`types.ts`](../../packages/rules-engine/src/types.ts); the refusal of `provisioning_pending` is exactly a statement about `AccountStatus`, and it is one file away from it.

**WHAT THE EXPORT COSTS, AGAINST `M01` SECTION 1.3.** That section's rationale is "every additional export is a way for a caller to reimplement a rule slightly differently", and it is the only thing that decides an export here. **`resolveExternalGates` REIMPLEMENTS NO RULE**: `R-40` and `R-41` are `evaluatePayout`'s and nothing in this module decides whether a gate passes. Withholding it produces two narrowings rather than none. The engine's public surface goes from twenty-eight names to **thirty-one**, seventeen functions to **eighteen**, and five error classes to **six**; [`evaluate.golden.test.ts`](../../packages/rules-engine/test/evaluate.golden.test.ts) caught the addition rather than being updated alongside it, which is what that gate is for.

### 4. RULING 3: the seventh `account_status` member is REFUSED, and the union is not widened

**THE TRAP THE ROW NAMED, AND IT IS A TYPE ERROR WAITING TO BE PAPERED OVER.** [`0001:47-50`](../../packages/db/migrations/0001_extensions_and_enums.sql) declares `account_status` with **SEVEN** members and [`types.ts`](../../packages/rules-engine/src/types.ts) declares `AccountStatus` with **SIX**. The difference is `provisioning_pending`, in that direction only, and `M01:203` carries the same six, **so the engine transcribed its source correctly and the gap is the corpus's.**

> **A resolver meeting `provisioning_pending` REFUSES. It does not widen the union, it does not map the member onto one of the six, and it does not return a value at all.**

**THE ARGUMENT.** Widening `AccountStatus` would amend a frozen plan through a type, and it would do so by deciding -- in a narrowing function nobody reads twice -- what a half-provisioned account is worth to `R-40`'s first gate. Mapping it onto `active` pays a trader on an account that is not open; mapping it onto `closed_admin` denies one with a gate that reads as working. **An account still being provisioned is not an account whose payout verdict is meaningful, and the resolver says so out loud.**

**THE PRECEDENT IS ONE FILE OVER AND IS THIS REPOSITORY'S OWN.** `IdentityStatus` in [`routes/payouts.ts`](../../apps/api/src/routes/payouts.ts) is read against `= 'active'` "precisely so that a fourth arriving later fails CLOSED on this door rather than open".

**AND THE RESOLVER HOLDS THE COLUMN'S SEVEN RATHER THAN THE ENGINE'S SIX**, which is a smaller point that matters at three in the morning: an unrecognised status and a recognised-and-refused one are different findings with different remedies, and a resolver holding only six could not tell them apart. The first says the enum grew and nobody swept this file; the second says one known account is not foldable today.

**WHAT IS NOT DECIDED HERE.** This entry does **not** rule what `provisioning_pending` means to the engine, and it does not propose adding it. It rules that a resolver may not answer the question. **Closing the gap for real is an amendment to `M01` section 2.1 and is an ADR somebody else writes.**

### 5. RULING 4: there is no permissive default on any leg, and the KYC leg is where this entry goes further than the estate does

**`R-41` CONJOINS ALL FIVE, SO A FACT DEFAULTED TO THE PERMISSIVE VALUE IS A VETO THAT NEVER FIRES.** `payoutsFrozen: false` on a row nobody could read pays a trader an investigation had frozen. `hasPayoutInFlight: false` on a status this resolver does not recognise pays a second time. **And the refusing default is not safe either**, which [ADR-248](ADR-248.md) section 8 ruled first: it "would deny every eligible trader while reading as a working gate". So an underivable value is a THROW, because a refusal is visible and a conservative value is a silent denial with a plausible shape.

**THE KYC LEG IS A JUDGEMENT AND IT DIVERGES FROM TWO SHIPPED READERS ON PURPOSE.** `currentKycState`, in both of its copies, answers `kyc_required` when the live set is not a singleton, and [ADR-248](ADR-248.md) section 4 praised that as failing closed. **This resolver REFUSES instead**, and the distinction is what the value is FOR:

**THE PRECEDENT IS [ADR-258](ADR-258.md) SECTION 6, ONE FIELD OVER**: the absent `min_settlement_lag_trading_days` key is READ and a row without it is refused, "because a default here would be a plan parameter in application code, and it would be invisible". Same shape, same choice.

**WHAT IS NOT A REFUSAL, AND THE TWO CASES ARE STATED SO NOBODY READS THIS AS MAXIMALISM.** An EMPTY chain resolves to `kyc_required`, because that is the enum's own word for an identity that has never been verified and it is a fact about the rows rather than a value chosen when they could not be read. **EVERY FAILING LEG IS REPORTED AT ONCE.** A resolver throwing on the first bad column sends an operator back three times for three columns of one account. `ExternalGatesRefusal` carries the account id and every leg, which is [ADR-258](ADR-258.md) section 5's "the refusal is a MEASUREMENT rather than a claim" applied one level down.

### 6. THE CONSEQUENCE THE ROW ASKED TO BE SAID OUT LOUD: the nightly fold now completes

**IT IS INSIDE THE ROW'S FENCE AND IT IS NOT A PORT WIRING.** The fence names [`apps/worker/src/batch/adapter.ts`](../../apps/worker/src/batch/adapter.ts) "for the sixth field only" and that is exactly what moved: no `use*Backend` is called, `apps/worker/src/batch/ports.ts` is untouched, and no type widened (`AccountDayInputs` is DELETED rather than widened, because `Omit<AccountDay, 'external'>` has nothing left to omit).

**THE PER-ACCOUNT REFUSAL STOPS THE BATCH, AND THAT IS CORRECT RATHER THAN UNFORTUNATE.** An account whose status is `provisioning_pending` and which has a live daily mark is an anomaly: a mark arrived for an account still being provisioned. `nightly.ts` does not catch, `main` does not catch, and the process leaves a non-zero status. **[`entrypoint.test.ts`](../../apps/worker/test/entrypoint.test.ts) case 2.3 SPAWNS a real process over that path and asserts it**, which a unit test cannot do: only a process can show that the throw is not swallowed between the resolver and the supervisor.

**AND IT IS NOT ANSWERED `null`.** That arm means "no live mark" and `nightly.ts` counts it `absent`; reusing it for an unfoldable account would hide the anomaly inside a count of accounts that had no data.

### 9. Findings reported rather than repaired, and the one fence widened

**FINDING 1, AND IT IS THE ONE A FUTURE SESSION SHOULD ACT ON. `currentKycState` NOW EXISTS IN THREE PLACES AND THIS DIFF ADDED THE THIRD.** [`accounts.ts:813`](../../apps/api/src/routes/accounts.ts) and [`wallet-withdrawals.ts:462`](../../apps/api/src/routes/wallet-withdrawals.ts) are byte-similar copies, and the head-of-chain reading in this resolver is a fourth reader of the same table. **It is not a fourth COPY**, because its ambiguous branch is deliberately different (section 5), but the head-selection logic is the same three lines in three files with nothing comparing them. **The repair is that both routes call the engine's**, and it is outside this fence twice over: `wallet-withdrawals.ts` is session 454's and both are live money doors. **Named here so the next reader of either is not the first to notice.**

**FINDING 2, AND IT WAS ALREADY FALSE ON `origin/main`.** `ELIGIBILITY_BLOCKER` in [`account-reads.ts`](../../apps/api/src/routes/account-reads.ts) carries three clauses and TWO of them are stale independently of this diff: clause 2 says `RuleStateWriterIo.encodeEngineGates` "has no implementation under any `src/`" and clause 3 says a reader "would still have to INVENT a decoding" for `engine_gates`. **[ADR-250](ADR-250.md) made both false** and [`adapter.ts`](../../apps/worker/src/batch/adapter.ts) imports that codec. They are registered rather than repaired: they are `ADR-250`'s remainder and not this ruling's blast radius, and the case that guards clause 2 measures a different predicate (`RuleStateWriterIo` VALUES declared under a `src/`), so it is green on a false sentence. **That is the more useful half of this finding: the gate cannot see the defect.**

**THE ONE FENCE WIDENED, DECLARED RATHER THAN BURIED.** Row `260`'s fence names `apps/api/src/routes/payouts.ts` and no other route. **[`account-reads.ts`](../../apps/api/src/routes/account-reads.ts) is edited anyway, in one clause**, because this diff is what falsified it: it read that the adapter "rejects `loadAccountDay` by name" and that "this deployment resolves none of" an `AccountDay`'s six fields. **That sentence is shipped inside a live 503 on a money-adjacent endpoint and it now sends an operator to build a port that is built.** The alternative was to repair only the test that reads it, which would leave a control asserting that a shipped reason still says something false. **The retired wording is PARAPHRASED rather than quoted**, on the rule `wiring.test.ts` states for exactly this, and the replacement says the smaller true thing: the fold completes, no run has written against this database, and a verdict off an empty table is a wrong answer where a 503 is honest. **A founder who thinks the fence should have held instead should say where that sentence belongs, because leaving it was the only other option.**
