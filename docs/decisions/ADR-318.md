## ADR-318: the queue has no schema, so the migration is a transcript. `0079` quotes pg-boss's own `getConstructionPlans('pgboss')` byte for byte at a pinned version, a catalog bump to that library is a schema change and is now asserted as one, and the schema ships with NO GRANT because making it usable by `merit_app` means granting CREATE inside the ledger's restore boundary  (2026-09-04, status: proposed)

**Row `318` is [ADR-305](ADR-305.md) section 7 slice 4, absence 3, and it owes one thing: the job store as a numbered migration.** It is [`0079_pgboss_job_store.sql`](../../packages/db/migrations/0079_pgboss_job_store.sql). **`migrate: false` stays false**, no deployable is wired, no queue is created and nothing is enqueued.

**IT IS MONEY BY WHAT IT GOVERNS AND NOT BY WHAT IT TOUCHES.** Not one cent moves through any object below and no ledger column changes. What lands is a schema in the same database, inside the same restore, which is [ADR-165](ADR-165.md)'s precedent and is `packages/queue`'s own stated reason for refusing a boot-time install. **`E2` READ OWED, and it is owed on a body this session did not write.**

**THE THING A READER SHOULD KNOW BEFORE READING THE FILE IS THAT ITS BODY IS A TRANSCRIPT.** Everything between the two `VERBATIM` markers is the exact string `getConstructionPlans(QUEUE_SCHEMA)` returned from the installed pg-boss: indentation, blank lines, doubled statement terminators, the vendor's own inline comments, and one line of trailing whitespace. Nothing was transcribed from pg-boss's documentation, its changelog or its git history, and nothing was typed. **Reviewing it is therefore not reviewing a design. It is checking that the quote is a quote and that the decisions AROUND it are right**, and section 6 is the list of decisions around it.

### 3. THE RULING, part 1: the body is emitted, not written

**`packages/queue` states the whole argument and this entry does not re-derive it.** pg-boss defaults `migrate` to true, which runs DDL against the money database at `start()`, from a library, outside the migration set. [ADR-008](ADR-008.md) makes migrations *"plain SQL files that can be reviewed line by line"* and constitution `E2` makes them sacred once merged. **A queue that installs its own schema at boot puts tables inside the PITR boundary that protects the ledger with no review and no migration number.**

So the body was produced by running the library, not by reading about it:

```
node scripts/db/assert_pgboss_schema_matches_library.mjs --emit
```

which resolves pg-boss **the way `@merit/queue` itself resolves it**, through `packages/queue/package.json` rather than through the script's own directory, reads `QUEUE_SCHEMA` out of [`pg-boss-queue.ts:66`](../../packages/queue/src/pg-boss-queue.ts) and refuses to run if that file carries anything other than exactly one declaration of it, and prints `getConstructionPlans(schema)` to stdout. **It reported `pg-boss@12.28.0`, schema version `38`, `QUEUE_SCHEMA = "pgboss"`, and 416 lines.**

**THE SPELLING IS NOT REPEATED IN THE MIGRATION.** `QUEUE_SCHEMA`'s docblock says it is named in one place *"so the migration that installs it and the runtime that reads it cannot disagree by a spelling"*, and a migration that hardcoded `pgboss` would be a second statement of it. `0079` instead quotes output GENERATED FROM that constant, and the assertion script re-reads the constant on every run. That matters more than it looks: Postgres folds a bare identifier to lower case and stores a quoted one verbatim, so `pgboss` and `"PgBoss"` are two schemas whose configs differ by two characters, are indistinguishable in logs, and produce a second empty schema rather than an error.

### 4. THE RULING, part 2: a catalog bump to pg-boss is a schema change, and it is now asserted as one

**This is the finding that turned a transcription task into a ruling, and it was read out of the installed library rather than assumed.**

Under `migrate: false` pg-boss branches at `start()` and runs `Contractor.check()` instead of `Contractor.start()`. `check()` throws `pg-boss is not installed` when the version table is absent, and `pg-boss database requires migrations` unless the row in `<schema>.version` equals the schema version compiled into the library, its manifest's `pgboss.schema` key. The last statement of the quoted body is `INSERT INTO pgboss.version(version) VALUES ('38')`.

**SO `0079` IS CORRECT AGAINST EXACTLY ONE LIBRARY VERSION, AND A LINE IN `pnpm-workspace.yaml` CAN INVALIDATE IT.** Constitution `E2` makes the remedy a new numbered migration carrying `getMigrationPlans(schema, version)`'s output at the same standard of transcription, never an edit to `0079`. **What was missing was anything that would make somebody write it.** The failure without a check is not loud, it is misplaced: green CI, a merged bump, and `pg-boss database requires migrations` thrown at boot in a deployable.

**[`scripts/db/assert_pgboss_schema_matches_library.mjs`](../../scripts/db/assert_pgboss_schema_matches_library.mjs) is that check**, and it is the mechanical assertion `CLAUDE.md` asks for in place of a bigger model. It asserts three things: that `0079`'s `EMITTED-BY` header line names the version, the schema and the pg-boss schema version the INSTALLED library reports; that the region between the markers is byte-identical to what that library emits, reporting the first differing line of the quoted region when it is not; and that `QUEUE_SCHEMA` still has exactly one declaration site. **`--falsify` runs first in CI**, on the rule an assertion only ever run against a tree that satisfies it reports `PASS` in the same way as one narrowed until it reads nothing: a seeded line inside the quoted region must change the comparison, and the unseeded tree must be green, or the falsification itself fails.

**WHAT IT CANNOT SEE, STATED RATHER THAN LEFT TO BE FOUND.** It compares text and never runs a statement, so it says nothing about whether the body applies. A pg-boss upgrade whose construction plans are unchanged is a `PASS` here and correctly so, because the installed schema and the library still agree.

### 5. THE RULING, part 3: `0079` GRANTS NOTHING, and that is the decision in this file most likely to surprise

**Measured, on the applied set:**

| Query | Result |
|---|---|
| `has_schema_privilege('merit_app', 'pgboss', 'USAGE')` | **false** |
| `has_schema_privilege('merit_app', 'pgboss', 'CREATE')` | **false** |
| `SET LOCAL ROLE merit_app; SELECT count(*) FROM pgboss.queue` | `insufficient_privilege` |

[`0026`](../../packages/db/migrations/0026_roles_and_grants.sql) grants `USAGE ON SCHEMA public`, table and sequence privileges `IN SCHEMA public`, and `ALTER DEFAULT PRIVILEGES IN SCHEMA public`. **Every one of those terms is scoped to `public`, so a new schema inherits none of them.**

**THE GRANT IS REFUSED HERE RATHER THAN OVERLOOKED, AND THE REASON IS NOT TIDINESS.** pg-boss's `create_queue` executes `CREATE TABLE pgboss.%I` and `ALTER TABLE pgboss.job ATTACH PARTITION`, so a runtime that can declare a queue is a runtime with **CREATE on the schema**. `0026` explicitly runs `REVOKE CREATE ON SCHEMA public FROM merit_app`. Granting CREATE to that same role on a schema **inside the boundary that protects the ledger** is a privilege ruling on the money database, and it is the kind of ruling [`0074`](../../packages/db/migrations/0074_firm_parameters.sql) and [ADR-284](ADR-284.md) both refused to make on behalf of a slice that had not been dispatched. **It belongs to [ADR-305](ADR-305.md) slice 8**, which is the row that gives the queue a clock and a deployable.

**IT IS ASSERTED AND NOT COMMENTED.** `REJECTION 5` of [`probe_pgboss_job_store.sql`](../../scripts/db/probe_pgboss_job_store.sql) fails the day `merit_app` holds `USAGE` or `CREATE` on this schema. **That is deliberate and it is not a trap**: it turns a silent widening into a red gate whose message names the control being changed and the row that owes the ruling. It was falsified rather than assumed: `GRANT USAGE ON SCHEMA pgboss TO merit_app` against the applied set turns the case red, and the `REVOKE` restores the green run.

**THE CONSEQUENCE, STATED PLAINLY: `0079` ALONE DOES NOT MAKE THE QUEUE USABLE BY THE APPLICATION ROLE.** Whether that is a defect depends on which role the executor `pgBossQueue` is handed actually runs as, and no deployable hands it one today because none declares `@merit/queue` at all. Slice 8 answers both together, which is the right place for both.

### 6. What the founder is reading, because it is NOT the DDL

**Four decisions, and none of them is a line of SQL.**

1. **That the transcript is a transcript.** Checkable in one command, and the CI step that checks it is described above.
2. **That `38` is a contract with a library version**, and that the remedy for an upgrade is a new migration rather than an edit (section 4).
3. **That the schema ships with no grant** and that the privilege ruling is slice 8's (section 5).
4. **That two gates were corrected rather than relaxed** (section 7).

**AND TWO PROPERTIES OF THE QUOTED BODY THAT A READER WILL WANT NAMED.**

**IT IS NOT DETERMINISTIC IN THE OBJECTS IT CREATES.** The `DO` block over `pgboss.queue_stats` creates one partition for today and one for tomorrow, named `queue_stats_YYYYMMDD` off `now() AT TIME ZONE 'UTC'`. This session's apply produced `queue_stats_20260904` and `queue_stats_20260905`. **Applying `0079` on a different day installs differently named tables**, so a table count over the `pgboss` schema is a fact about the day it was read, and **no gate in this repository states one**. That is why section 8's counts are given per schema and why only the `public` figures are compared against anything.

**IT OPENS AND CLOSES ITS OWN TRANSACTION** and takes an advisory lock keyed on the database and schema name. Nothing wraps it, because wrapping it would be editing the transcript.

### 7. Two gates were corrected, and neither was relaxed

**`CI-06i`'s TABLE PARSER READ A SCHEMA NAME AS A TABLE NAME.** `tablesInMigrations()` matched `CREATE TABLE ([a-z_]+)`, which was the table name for seventy-eight migrations because **every table in this estate was in `public`**, so the two were the same string. Against `CREATE TABLE pgboss.job` it captured `pgboss`, nine times, and reported nine duplicate definitions of one imaginary table plus a missing design record for it. The parser is now schema-aware and scoped to `public`.

**THE SCOPE IS DERIVED AND NOT PREFERRED.** That function feeds `CI-06i`, whose subject is [DATA_MODEL](../architecture/data-model/README.md)'s `### <table>` design records, and the `tables` span. Both describe **Merit's** schema. `CI-06h` has read the installed truth as `pg_tables where schemaname='public'` since it was written, so scoping the parser makes the two agree rather than making either wrong, and **a vendor's job store has no Merit design record and is not owed one**. The `tables` span is unchanged at 118 across this diff, which is the check that the correction did not move a number it should not have moved.

**`sql_tables` IS DELIBERATELY NOT CHANGED.** It is the `^CREATE TABLE ` grep the workflow itself runs, kept identical on both sides on purpose, and pg-boss's emitted DDL is indented so that grep never saw it. Changing it here would desynchronise the two halves of `CI-06h`'s count comparison to fix a problem neither half has.

**THE `CI-06h` JOB NOW INSTALLS DEPENDENCIES, AND IT DID NOT BEFORE.** The transcript assertion has to import the **installed** pg-boss, because the version in the catalog is the whole subject of the check and a copy of the DDL in this repository would be a second statement of the thing being compared. The step could not degrade to a skip on a missing tree, on this repository's own rule that a check which cannot run is not a check that passed. The install is `--frozen-lockfile`, on `VG-12`'s first part and for a second reason here: an install allowed to move the lockfile is an install that could move pg-boss out from under the assertion.

**`CI-06s` AND `RI-24` FORCED THE WIRING AND IT IS COMPLETE IN BOTH DIRECTIONS.** The new `probe_*.sql` and the new `assert_*.mjs` each appear as a step in [`corpus.yml`](../../.github/workflows/corpus.yml) and as a needle in `CI-06h`'s required list, which is why [`gates.mjs`](../../scripts/corpus/gates.mjs) is in this diff at all.

### Approval

**Status: `proposed`. The approval line is UNSIGNED and merging is not signing.** No `status` field anywhere moves and nothing is marked `accepted`. **`E2` READ OWED**, and it is inherited as well as owed here: [ADR-305](ADR-305.md), [ADR-304](ADR-304.md) and [ADR-297](ADR-297.md) are all `proposed` and UNSIGNED, and this entry rests on the first of the three.

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO CHECK IS THE ONE A GATE CANNOT: THAT QUOTING A VENDOR'S DDL INTO A SACRED FILE IS THE RIGHT TRADE AT ALL.** Every gate in this diff can tell you the quote is faithful. **None of them can tell you that pg-boss's job store is a schema Merit wants inside the ledger's PITR boundary**, and that is the question `0079` actually settles: twelve tables, five functions, an enum, a `LIST` partition tree and a `DO` block that creates dated partitions off `now()`, all landing in the same restore as `ledger_entries`. The alternative is not "write it by hand", which is strictly worse. It is a SEPARATE DATABASE for the job store, which costs [ADR-006](ADR-006.md)'s transactional enqueue outright, because an enqueue in the caller's transaction is only possible while the queue is in the caller's database. **That trade was made by [ADR-006](ADR-006.md) and this file is the first time it is visible as DDL.** A founder reading the emitted body decides whether it still looks like the right one.

  **THE SECOND IS SECTION 5, AND IT IS THE ONE WHERE A READ CHANGES THE ANSWER.** `0079` grants nothing, so the schema is installed and unreachable by the application role. Two readings are defensible. One says an unusable schema is an incomplete migration and the grants belong here, where the person who understands `create_queue`'s DDL is writing. The other, which this entry takes, says CREATE on a schema inside the ledger's restore boundary for the role `0026` explicitly revokes CREATE from is a control, not a detail, and a control invented by the session that needed it is how controls get weaker. **If you rule the first way, the grant is a new migration and not an edit to `0079`, and `REJECTION 5` of the probe is rewritten in the same commit that grants**, so the assertion and the ruling move together.

  **THE THIRD IS THE ONE A LINE-BY-LINE READ CATCHES AND NOTHING ELSE DOES: WHAT THE QUOTED DDL DOES THAT A COUNT CANNOT SEE.** Three candidates are named so the read has somewhere to start. `pgboss.job` is `PARTITION BY LIST (name)` with a DEFAULT partition, so every queue that is not explicitly partitioned shares one physical table with every other, and that table is in the ledger's database and its vacuum budget. `queue_stats` accumulates a partition per day and **the quoted body creates only today's and tomorrow's**, which means retention and partition creation are a RUNTIME responsibility this migration does not discharge; nothing in this repository schedules pg-boss's maintenance today, and slice 8 is where that stops being true or is recorded as not. And `create_queue` is `SECURITY INVOKER` DDL reachable by anybody who can call it, which is the mechanism behind section 5's whole argument rather than a separate point.

  **THE ONE OBJECTION WORTH CHECKING IN A MINUTE.** `0079` is only correct against `pg-boss@12.28.0` and the assertion that says so runs in `CI-06h`, which needs a database. **A reviewer might reasonably want that check in a job that runs on every pull request rather than in the migrations job.** It is here because `RI-24` and `CI-06s` both read `corpus.yml` for `scripts/db/*` wiring and would report the file unpinned anywhere else; moving it means moving what those two invariants read, which is a wider change than this row.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The claim that the public object counts are unchanged is a claim about this apply, on this day, and one of the objects the body creates is dated.** The counts in section 8 are read per schema for exactly that reason, and the `public` figures are the ones compared. If a future reader finds a `pgboss` table count in a document, it was written by somebody who did not read this paragraph, and it is wrong on any day but the one it was measured.
