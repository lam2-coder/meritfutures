## ADR-292: every CI run happens twice, the fix is one line per workflow, and the one line the row supplied does not work  (2026-08-30, status: proposed)

**Every push to a branch with an open pull request has built this repository TWICE, concurrently, on the identical commit, for the whole life of the tree, with every gate green.** `ci.yml`, `corpus.yml` and `golden.yml` each declare `on: push` **and** `on: pull_request`, and each keyed `concurrency.group` on `${{ github.ref }}`. That context is **not the same value for the two events**: `refs/heads/<branch>` on `push` and `refs/pull/<n>/merge` on `pull_request`. Two values are two groups, two groups are two runs, and `cancel-in-progress: true` never saw them as siblings.

**THE DEFECT IS REPAIRED IN THREE LINES AND HELD BY A NEW INVARIANT.** The group is now `${{ github.head_ref || github.ref_name }}`, which renders **one string on both events**. `RI-33` renders every dual-triggered workflow's group under a push context and a pull-request context and requires the two to be equal.

**AND THE IDIOM [ALLOCATION](ALLOCATION.md) ROW `292` SUPPLIED DOES NOT FIX THIS.** The row named `${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}` as "the standard idiom" and told this session to satisfy itself before writing it. Satisfied: it renders `7` on the pull request and `refs/heads/<branch>` on the push. **It is the most-copied answer to this question and it leaves the defect exactly where it was.** Section 2 is the table both were read off, and `RI-33` refuses it by name in section 4.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `292`, session **483**, branch `claude/every-ci-run-happens-twice`. **NON-MONEY.** No migration number is taken or reserved and `packages/db/**` is untouched; `apps/**` is untouched. **`RI-33` IS MINTED**, which row `292` reserved to this session by name. **`RI-32` IS NOT TOUCHED AND STAYS FREE**, as row `292` required and [ADR-291](ADR-291.md) section 8 left it.

- **Ships `proposed` with an UNSIGNED approval line.** Merging is not signing.

- **NO TRIGGER IS REMOVED AND NO `branches` LIST IS NARROWED.** `main` still runs on push, which is what [`CI-08`](../testing/STRATEGY.md)'s own `Runs on` cell requires. Deleting a trigger to stop a duplicate is weakening a gate to pass it, and the row forbade it in those words.

- **ONE HALF OF THE PROOF WAS WATCHED AND THE OTHER HALF COULD NOT BE. SECTION 5 SAYS SO IN ITS OWN WORDS AND DOES NOT ROUND IT UP.** The before-state is measured off the live Actions API, run by run. The after-state on a pull request **was not observed**, because no pull request exists for this branch and this session was instructed to open none.

### 2. The four candidate expressions, rendered

**Every row below is the value GitHub substitutes, for ONE commit on ONE branch, under each event.** `B` is the branch name, `7` is the pull request number.

| `concurrency.group` expression | renders on `push` | renders on `pull_request` | one group? |
| --- | --- | --- | --- |
| `${{ github.ref }}` (what the tree had) | `refs/heads/B` | `refs/pull/7/merge` | **NO** |
| `${{ github.event.pull_request.number \|\| github.ref }}` (**what row `292` supplied**) | `refs/heads/B` | `7` | **NO** |
| `${{ github.head_ref \|\| github.ref }}` (the near-miss) | `refs/heads/B` | `B` | **NO** |
| `${{ github.head_ref \|\| github.ref_name }}` (**what landed**) | `B` | `B` | **YES** |

**THE THREE FACTS THE TABLE RESTS ON, EACH A DOCUMENTED PROPERTY OF THE EVENT AND NOT A CHOICE MADE HERE.**

1. **`github.head_ref` is set ONLY on `pull_request` and `pull_request_target`**, and holds the **source branch name**. On every other event it is the empty string, which is falsy to `||`.
2. **`github.ref_name` is the short ref name.** On a push to a branch it is the branch name; on a `pull_request` it is `<n>/merge`. So it is unusable alone and correct as the *fallback*, where `head_ref` has already answered.
3. **`github.ref` is the full ref.** On a push it is `refs/heads/<branch>`, which is why row 3 of the table fails: `B` and `refs/heads/B` are different strings.

**ROW 2 IS THE ONE WORTH DWELLING ON.** `github.event.pull_request.number` is a perfectly good discriminator *within* the pull-request event: it makes successive pushes to one pull request cancel each other. It says nothing at all about the push-event run, which falls through to `github.ref`. The idiom collapses **pull-request runs against pull-request runs**, which the tree already had, and never touches the duplication. It is right about the wrong problem.

**WHAT THE LANDED EXPRESSION COSTS, STATED RATHER THAN LEFT TO BE FOUND.** The two runs are now siblings, so one cancels the other. The `push` run is created first (three seconds first, measured above), so **the run that survives is the `pull_request` one**, which checks out the **merge commit** rather than the branch head. That is the better of the two to keep: it is the state that would exist after merge. The cancelled `push` run's check runs conclude within seconds and the surviving run's conclude ~50 minutes later, so the latest check run for each job name on that SHA is the surviving one.

**One line each, and the comment above it.**

| File | Was | Is |
| --- | --- | --- |
| [`ci.yml`](../../.github/workflows/ci.yml) | `group: ci-${{ github.ref }}` | `group: ci-${{ github.head_ref \|\| github.ref_name }}` |

**THE LITERAL PREFIX IS KEPT AND `${{ github.workflow }}` IS NOT ADDED.** Concurrency groups are scoped per repository rather than per workflow, so the three names must differ, and `ci-`, `corpus-` and `golden-` already differ. Substituting `github.workflow` would render the same three strings from the `name:` field and change nothing except making the group harder to read in the Actions UI. **This is the one place this session declined a piece of the row's idiom for a reason that is taste rather than correctness**, and it is recorded so a later reader can overrule it cheaply.

**[`nightly.yml`](../../.github/workflows/nightly.yml) IS UNTOUCHED AND THAT IS A FINDING RATHER THAN AN OVERSIGHT.** It keys `nightly-${{ github.ref }}` with `cancel-in-progress: false`, and its triggers are `schedule` and `workflow_dispatch` only. **It declares neither `push` nor `pull_request`, so it has never run twice for one commit**, and `RI-33` correctly holds it out of subject. Changing it would be a change to a workflow with no defect.

**`cancel-in-progress: true` IS UNCHANGED ON ALL THREE**, and it is load-bearing in a way it was not before: one shared group that only *queues* would still run both halves, one behind the other. `RI-33` leg 3 asserts it for exactly that reason.

### 4. `RI-33`, and why it renders the group instead of matching it

**`RI-33`: _"A workflow on both push and pull_request renders one concurrency group for both"_**, in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs). Its register row is in [ALLOCATION](ALLOCATION.md), written in the same commit, with its title copied out of the live `CHECKS` array. `check:invariants` reports **31** where it reported 30.

**THE DESIGN DECISION IS THAT IT EVALUATES RATHER THAN PATTERN-MATCHES, AND SECTION 2's TABLE IS THE ARGUMENT FOR IT.** A denylist of forbidden context paths would have to encode four separate rulings, three of them counter-intuitive: that `github.ref` diverges, that `github.head_ref` **alone** diverges, that `github.head_ref || github.ref` **still** diverges, and that `github.head_ref || github.ref_name` does not. That is a table of exceptions inside a check, maintained by whoever remembers it, which is the shape this repository has now written four ADRs against.

Instead the check holds **two `github` contexts**, one per event, differing only where the events differ, renders the group string under each, and requires the two to be **equal**. The finding it emits is the two group names it computed, which is the defect stating itself:

```
.github/workflows/ci.yml:89 keys `concurrency.group` on `ci-${{ github.ref }}`, which renders
"ci-refs/heads/merit-branch" on `push` and "ci-refs/pull/7/merge" on `pull_request` for one
commit on one branch. Two groups is two runs, and `cancel-in-progress` never sees them as
siblings.
```

**THREE LEGS.**

1. **No `concurrency` block at all** on a dual-triggered workflow. The same defect in its worst form: two runs per commit and nothing that could ever cancel either.
2. **Divergent renderings.** The leg the check is named for.
3. **`cancel-in-progress` that is not `true`.** Necessary and not sufficient: collapsing the groups without cancelling merely queues the second run.

**THREE SENTINELS THAT THROW, ON [ADR-274](ADR-274.md)'s RULE THAT AN ABSENCE CHECK OVER AN EMPTY SCOPE IS WORSE THAN NONE.** No workflow file walked. A tree whose workflows name `pull_request` while the reader classified **none** as dual-triggered, which is the one that matters because this check's scope is computed by a line reader over YAML. And **an operand inside a group that the renderer does not model**, which is subtler than the other two: an unmodelled path renders as empty *on both sides*, compares equal, and turns leg 2 into a check that always passes.

**WHAT IT CANNOT SEE, stated rather than left to be discovered.** It is a line reader and not a YAML parser, so an anchor, a merge key or a flow mapping spanning lines is beyond it; the second sentinel is what stops that from being silent. It says **nothing** about whether a workflow *should* carry both triggers, which is [STRATEGY](../testing/STRATEGY.md)'s call and not a check's. It cannot see a duplicate arising from two different workflows or via `workflow_run`. And it models a **same-repository** pull request; section 6 finding `F1` records the fork case.

### 7. Findings this row was not sent for

**F1. A pull request from a FORK whose head branch shares a name with a branch of this repository renders the same group as a push to that branch.** `github.head_ref` on a fork pull request is the **fork's** branch name, unqualified. A fork pull request from a branch called `main` would therefore share `ci-main` with pushes to this repository's `main` and could cancel one. **Accepted and bounded rather than fixed**: this repository has no forks and every pull request in its history comes from a `claude/*` branch in the repository itself. **The one-line hardening, if forks are ever enabled, is to prefix the group with `${{ github.event.pull_request.head.repo.full_name || github.repository }}`**, which renders identically for a same-repository pull request and its push and differs for a fork. It is written here so the next session does not have to derive it, and `RI-33` would need both operands added to its context tables.

**F2. `RI-33` LANDS WITH NO CASE IN [`repo-invariants.test.ts`](../../packages/tooling/test/repo-invariants.test.ts), WHICH EVERY OTHER CHECK HAS.** That file is **outside row `292`'s fence** and was not touched. The two derived cases in it (`clean tree: every invariant holds` over `CHECKS`, and the synthetic fixture over `CHECKS`) **do** cover `RI-33` automatically and both were run green; what is missing is a seeded case in the dirty direction. The row substituted hand-watched RED transcripts for it and section 6 is that substitution discharged in full, including both directions and all three sentinels. **The owed follow-up is one `describe` block over `packages/tooling/test/repo-invariants.test.ts`**, seeding a workflow fixture per leg. It is named rather than taken, because narrowing the check to fit the fence or widening the fence to fit the check are both refused ([ADR-282](ADR-282.md)'s precedent one wave ago).

**F3. THE FIXTURE IN THAT TEST FILE CARRIES A WORKFLOW WITH NO `on:` BLOCK, AND `RI-33` PASSES OVER IT CORRECTLY BUT VACUOUSLY.** `cleanTree()` writes `.github/workflows/ci.yml` as four lines of `jobs:` with a `node-version-file:` line, for `RI-05`'s benefit. It declares no triggers, so it is out of `RI-33`'s subject and sentinel 2 does not fire because the file never says `pull_request`. **The fixture therefore proves nothing about `RI-33` beyond that it does not crash**, and the follow-up in `F2` should give the fixture a dual-triggered workflow with a correct group.

**F4. THE DUPLICATION COST IS NOT MEASURABLE FROM INSIDE THIS REPOSITORY AND NOTHING HERE WILL NOTICE IF IT RETURNS IN ANOTHER FORM.** `RI-33` asserts a property of the YAML. It cannot count runs. A duplicate arising from two workflows that both do the same work, or from a `workflow_run` chain, would be invisible to it exactly as this one was invisible to every other gate. **The measurement lives in the Actions API and this tree reads it never.**

**F5. ROW `292`'s OWN PRESCRIBED FIX WAS WRONG, AND THAT IS A DISPATCH FINDING RATHER THAN A CODE ONE.** The row supplied a specific expression, called it "the standard idiom", and hedged it with *"satisfy yourself that is right ... do not copy it blindly"*. A session that took the first clause at face value would have shipped a change that looked like a fix, passed every gate, and left the duplication running. **The hedge is what saved it, and a hedge is a convention held by whoever reads carefully.** `RI-33` is the durable form of that hedge: from now on the expression is checked rather than trusted, whoever writes it.

### 10. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

This is a **non-money tooling row**. What is owed is a read of one expression and one check, not of a money path.

- **Decision:** the three dual-triggered workflows key `concurrency.group` on `${{ github.head_ref || github.ref_name }}`, which renders one string on both the `push` and `pull_request` events, so the two runs of one commit become siblings and the later cancels the earlier. **Both triggers stay and no branch list is narrowed.** `RI-33` holds the property by rendering every dual-triggered workflow's group under both event contexts and requiring equality, with three legs and three throwing sentinels.
- **Consequences:** a commit on a branch with an open pull request builds **once** rather than twice. The surviving run is the `pull_request` one, which tests the **merge result** rather than the branch head, which is the better of the two. Wave dispatch arithmetic that counted jobs was low by a factor of two and can now be taken at face value. **`RI-32` remains free and `RI-34` is the next number after it.**

**What a founder read adds and this entry cannot.**

**THE FIRST THING TO DECIDE IS WHETHER LOSING THE `push`-EVENT RUN ON A PULL REQUEST BRANCH IS ACCEPTABLE.** It is the direct consequence of the fix and it is not free: the surviving run tests the merge commit, so **nothing tests the branch head in isolation any more** while a pull request is open. Section 2 argues the merge result is the more useful of the two and that is a judgement. A founder who wants both would keep the duplication deliberately, and the honest way to want that is to say so rather than to leave it as an accident of `github.ref`.

**THE SECOND IS `F1`, THE FORK CASE.** It is accepted here on the ground that this repository has no forks. That is true today and it is a fact about the repository's configuration rather than about its code, which is exactly the class of assumption this tree has been burned by. The hardening is one line and is written out in `F1`; taking it now costs a longer group name and closes the hazard permanently.

**THE THIRD IS `F5`, AND IT IS ABOUT DISPATCH RATHER THAN ABOUT CODE.** The row prescribed an expression that does not work. This session caught it because the row also said not to copy it blindly. **A prescribed fix inside a dispatched row reads as settled and is not**, and the general repair is that a row states the property to achieve and leaves the expression to the session, or states both and marks which is which.
