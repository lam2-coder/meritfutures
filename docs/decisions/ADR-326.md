### 2. The three counts that disagreed, and the number that is actually true

**THE SENTENCE.** [`index.ts`](../../apps/worker/src/index.ts)'s `./job.ts` docblock read *"the five other jobs this deployable has built (detector runs, the expiry sweep, the two digest producers, the breaker evaluation and the statistics run) are still unscheduled, each with its own row in `CRON_INVENTORY` saying so."*

**IT SAID FIVE AND LISTED SIX.** Detector runs, the expiry sweep, digest producer one, digest producer two, the breaker evaluation, the statistics run. The word *"two"* is inside the parenthetical, so the enumeration disagrees with its own head.

**THE INVENTORY IT CITED MARKED THREE.** `detector runs`, `plan breaker evaluation` and `freeze expiry sweep` carried `NOT YET WIRED OR SCHEDULED`; the statistics run said the same thing **in different words** (*"Nothing schedules it yet"*), which no grep can count, and the two digest producers said nothing at all. So the clause *"each with its own row in `CRON_INVENTORY` saying so"* was false for three of the six it listed.

**AND [ADR-325](ADR-325.md) THEN BUILT A SEVENTH THE SENTENCE PREDATED**, which is the failure mode a typed count has by construction: it does not go stale loudly, it goes stale in silence and stays green.

**THE RECONCILIATION IS THAT NONE OF THE THREE NUMBERS WAS COUNTING THE SAME THING, AND THE FIX IS TO COUNT ENTRY POINTS AND ROWS SEPARATELY BECAUSE THEY ARE DIFFERENT QUESTIONS.**

- **Job ENTRY POINTS under `apps/worker/src`: thirteen.** Derived by census of exported job-shaped functions, registered in [`WORKER_JOB_ENTRY_POINTS`](../../apps/worker/src/schedule.ts) and asserted against the tree in both directions by `test/schedule.test.ts` cases 2.1 and 2.2.
- **Of those, two are SCHEDULED and eleven are not.** The two are `runNightlyBatch` and `main`, which are the fold and its process wrapper and are **one job**.
- **Distinct `CRON_INVENTORY` rows those eleven answer to: ten.** Two entry points share the digest row.
- **So the marker belongs on ten rows and it was on three.** It is on ten now, and case 4.2 asserts the marked set and the unscheduled set are EQUAL rather than merely overlapping, so a job that gets wired and a row that loses its marker are each a failure.

**THE OLD SENTENCE'S REAL ERROR WAS NOT ARITHMETIC.** It counted "the two digest producers" as one item in a list of five while writing them out as two, which is what happens when a count of ROWS and a count of ENTRY POINTS are written as one sentence. The register keys on the entry point and carries the row beside it, so both numbers are readable and neither is typed into prose.

### 3. THE MANIFEST LINE, AND THE GRANT UNDER IT THAT SLICE 8 ACTUALLY OWES

#### 3.1 The measurement

**`merit_app` CANNOT REACH THE `pgboss` SCHEMA AT ALL.** [`0026_roles_and_grants.sql:60`](../../packages/db/migrations/0026_roles_and_grants.sql) is `GRANT USAGE ON SCHEMA public TO merit_app, merit_analytics;` and [`:64`](../../packages/db/migrations/0026_roles_and_grants.sql) is `REVOKE CREATE ON SCHEMA public FROM merit_app, merit_analytics;`. Every grant in that file is scoped `IN SCHEMA public`. [`0079`](../../packages/db/migrations/0079_pgboss_job_store.sql) adds none.

**THAT IS NOT THIS ROW'S INFERENCE, IT IS AN ASSERTION ALREADY RUNNING IN CI.** [`probe_pgboss_job_store.sql`](../../scripts/db/probe_pgboss_job_store.sql) REJECTION 5 fails if `has_schema_privilege('merit_app', 'pgboss', 'USAGE')`, and its own failure message reads: *"a later migration granted it and ADR-305 slice 8 owes the ruling that says why"*. [ALLOCATION](ALLOCATION.md) row `318` says the same thing from the other side: *"That privilege ruling is slice 8's and so is the `@merit/queue` manifest line."*

**SO EVERY METHOD OF `JobQueue` THROWS FOR THIS DEPLOYABLE TODAY.** `start()` reads `pgboss.version`, `declareQueue` calls `pgboss.create_queue`, `enqueue` inserts into `pgboss.job`, `consume` polls it. All four need `USAGE` on a schema this role has no privilege on.

#### 3.2 What the line would buy, and why it is not added

**A MANIFEST LINE WITH NO WORKING CALL IS NOT THE REPAIR THE BARREL ASKED FOR.** That header says the wiring is *"one manifest line **and one call**"*. There is no call that can succeed, so adding the line alone would leave the header's own sentence half-true in a new way, and constitution `E3` admits no dependency without a caller. **The sentence is repaired instead by replacing an unfalsifiable deferral with a measured blocker**: *"owed by a different session than this one"* is true on every tree, before and after any work, so nothing can ever make it false. `test/schedule.test.ts` case 5.1 now asserts the manifest has no `@merit/queue` **and** that the barrel names the blocker, and case 5.2 asserts at the migration directory that no grant on `pgboss` exists, so the day one lands both halves go red together.

#### 3.3 THE RULING, WHICH IS THE PART OF SLICE 8 THAT IS THIS ENTRY'S TO MAKE

**`0079` AND ITS PROBE BOTH STATE THAT THE GRANT MEANS `CREATE` ON THE SCHEMA, AND THAT IS TRUE OF A PARTITIONED QUEUE AND FALSE OF THE ONE THIS TREE DECLARES.** [`0079`](../../packages/db/migrations/0079_pgboss_job_store.sql)'s finding 1 reads *"pg-boss's `create_queue` runs `CREATE TABLE pgboss.%I`, so making the queue usable by the application role means granting CREATE on a schema inside the ledger's restore boundary"*. **Read at the function body in that same file**, `create_queue` computes `tablename` as `'job_common'` unless `options->>'partition' = 'true'`, inserts one row into `pgboss.queue`, and then:

> `IF queue_created_on IS NULL OR options->>'partition' IS DISTINCT FROM 'true' THEN RETURN; END IF;`

**The `EXECUTE format('CREATE TABLE pgboss.%I ...')` is below that `RETURN` and is unreachable for a non-partitioned queue.** [`pg-boss-queue.ts:103`](../../packages/queue/src/pg-boss-queue.ts) calls `boss.createQueue(queue)` with no options, so this workspace declares no partitioned queue and asks for no `CREATE TABLE`. The probe's own SUCCESS 2 measures it: `create_queue('probe-plain', '{"policy":"standard"}')` leaves `table_name = 'job_common'`.

**RULED. The grant slice 8's migration should write is `USAGE` on `pgboss` plus table privileges on the queue's own tables, and it must NOT include `CREATE` on the schema.** `CREATE` inside the ledger's restore boundary is exactly the privilege [`0026`](../../packages/db/migrations/0026_roles_and_grants.sql) revokes from this role on `public` and exactly what `DATA_MODEL` section 14's "the application role has no DDL" forbids; granting it to make a queue work would undo one of the four things `0026`'s own header puts to the founder for a line-by-line read.

**AND THE RULING NAMES ITS OWN RESIDUE RATHER THAN CLAIMING TO BE COMPLETE.** What is ruled here is that `CREATE` is refused and that a non-partitioned queue does not need it. **What is NOT ruled is the exact privilege set**: pg-boss's maintenance path writes `pgboss.bam`, `pgboss.warning` and the `queue_stats` partitions, and the honest way to enumerate that is to run `start()` against the applied schema under the role and read what it refuses, which needs an estate this row does not have. **The migration that writes the grant owes that measurement**, in the idiom `0079` itself set by emitting its body from the installed library rather than transcribing it. A row that guessed the set would be inventing a control on the money database, which is the thing `0079` declined to do and named this slice for.

#### 3.4 `migrate: false` STANDS, AND THE MIGRATION IS THE REASON IT STILL SHOULD

**The setting was chosen so an ABSENT store failed loudly** ([`pg-boss-queue.ts:28-44`](../../packages/queue/src/pg-boss-queue.ts)): *"A queue that installs its own schema at boot puts tables inside the PITR boundary that protects the ledger with no review and no migration number."* That reason expired when `0079` merged, and **the setting is still right for a second reason that only exists now**. Under `migrate: false` pg-boss runs `Contractor.check()` at `start()`, which refuses any `pgboss.version` other than the one the library was compiled with, and `0079` was emitted at that version and pins it. So a catalog bump to `pg-boss` is a **red boot** and a new migration rather than a silent in-place upgrade of a schema inside the ledger's restore boundary. **Flipping it to `true` today would convert the one loud failure this arrangement still has into a library quietly re-running DDL there.** No line of `packages/queue` was edited; this is a reading of it and the file is outside this row's fence.

### 4. THE DRIVER'S CLOCK, AND WHY IT IS A ROW AND A SWITCH RATHER THAN A SCHEDULE

**THE STOP CONDITION IS *"a clock and a `CRON_INVENTORY` row WITH A DEAD-MAN SWITCH"*, AND WHAT A CLOCK MEANS HERE IS ALREADY RULED.** [ADR-241](ADR-241.md) and the nightly-batch row: the schedule is **EXTERNAL**, one process per run, and *"a timer inside a long-lived process is refused because a long-lived process has no exit code to fail with"*. Which scheduler and which cron expression are deployment facts and are not written in this repository ([ADR-012](ADR-012.md)). **So the repository's half of a clock is a row, an expected-by time, a switch and an entry point a scheduler can start**, and this entry adds no second shape.

**AND THE DRIVER MUST NOT GET A LIVE ONE, WHICH IS THIS ROW'S ONE REFUSAL.** [ADR-305](ADR-305.md) section 5 measures the trap past approval: the only arrow out of `approved` is `transferring`, `packages/rail` opens no socket and has no importer, and `WD-C2` at [`0072:211-218`](../../packages/db/migrations/0072_terminal_withdrawal_transitions.sql) refuses `approved --> cancelled` at the database. **A schedule that starts `runWithdrawalApprovals` against a live adapter posts `LT-06`, extinguishes the trader's wallet claim and leaves the money in a state with no exit and no cancel.** That entry forbids slice 9 for exactly that reason and its own words are *"THIS SLICE MUST NOT BE DISPATCHED BEFORE THE RAIL EXISTS"*. **A clock is a slower door, not a different one.** So the row lands, the switch lands, and the schedule does not.

**THE ROW'S SWITCH ASSERTS THE QUERY AND NOT THE JOB**, which is the idiom four rows of that page already use and this entry transcribes rather than invents: *an approvable `wallet_withdrawals` row whose destination cooling window has elapsed, that carries no standing hold, and that is still not `approved`.* **The clock in the query is the DESTINATION's window and not the row's expected-by time**, because [`approval-sweep.ts:543`](../../apps/worker/src/withdrawals/approval-sweep.ts) reads `destination.coolingUntil` and a window that has not started has not elapsed. The switch fires today, on every approvable row, and **that is correct rather than noisy**: nothing drives the arrow.

### 5. THE REGISTER, AND WHY THE DISPOSITION IS A FACT RATHER THAN A LABEL

[`apps/worker/src/schedule.ts`](../../apps/worker/src/schedule.ts) carries one row per job entry point: its module, its exported name, the `CRON_INVENTORY` row it answers to, its disposition, and for an unscheduled one the blocker. **The disposition is tied to the tree and not to somebody's intention**: `test/schedule.test.ts` case 3.1 runs a caller census over `apps/worker/src` with comments stripped and asserts that an entry point has a caller **if and only if** it is registered `scheduled`. A job marked scheduled that nothing calls, and a job marked unscheduled that something calls, are both red.

**THE CENSUS IS THE SECOND FINDING OF THIS ROW AND IT IS LARGER THAN THE COUNT.** `runNightlyBatch` is called by `main` and `main` by `src/start.ts`. **Every other job entry point in this deployable has zero callers under any `src/` in this workspace**, and nine `UNWIRED_*_IO` values stand as the only inhabitant of their own port type. So the reason eleven entry points are unscheduled is not that nobody wrote a cron line: **it is that they have no live adapter, and the clock is downstream of the adapter.** The register says that per job rather than as a generality, because the blockers are not all the same one: the breaker declines even wired (`OQ-M6-02`'s minimum sample is unanswered), the live-feed sweep is blocked by [`0050`](../../packages/db/migrations/0050_live_cache_and_role.sql)'s `REVOKE ALL` rather than by an adapter, the provisioning saga additionally needs the job store, and the withdrawal driver is blocked by a rail.

### 9. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

**What a founder read adds and this entry cannot.**

**THE FIRST THING TO DECIDE IS SECTION 3.3, BECAUSE IT IS A PRIVILEGE RULING ON THE MONEY DATABASE AND IT IS THE ONLY THING HERE THAT NO CITATION SETTLES.** The finding under it is checkable by opening one function body: `create_queue` returns before its `CREATE TABLE` for a non-partitioned queue, and this workspace declares none. **The ruling on top of the finding is a judgement**, and it is that the application role must never hold `CREATE` on `pgboss` even though granting it would be the shortest path to a working queue. **A founder who disagrees is not disagreeing with the finding**, they are deciding that DDL inside the ledger's restore boundary is an acceptable price for a partitioned queue, and that is a `0026` question rather than a slice's. The residue is stated in the same section and is real: the exact privilege set needs a live `start()` and this row could not run one.

**THE SECOND IS SECTION 3.2, BECAUSE IT IS THE ONE PLACE THIS ROW DID LESS THAN ITS DISPATCH ASKED FOR.** The row asked for the manifest line and for the barrel sentence repaired in the same commit. **The sentence is repaired and the line is not**, on the argument that a dependency whose only call throws is not the wiring the header asked for. **A founder who reads that as over-caution should say so**, and the cost of the other choice is one line in a manifest and one in the lockfile, plus a barrel paragraph that would then have to explain why an installed dependency is unusable. What this entry can say is that the line was refused for a blocker it measured rather than for a preference, and that the blocker is asserted by two cases so it cannot be forgotten.

**THE THIRD IS SECTION 4, WHICH IS A REFUSAL DRESSED AS A DELIVERABLE.** Slice 8's stop condition asks for a clock and this row gives the driver a row, a switch and no schedule. **The argument is that a live clock in front of that job IS slice 9**, whose harm [ADR-305](ADR-305.md) section 5 measures and whose dispatch it forbids until a rail exists. **A founder who wants the driver scheduled behind a feature flag, or run in a dry mode that decides and posts nothing, is describing a design this entry did not build**, and either would be a real answer. The one this entry refuses is the unqualified one, and the reason is that a trader whose wallet claim is extinguished into a state with no exit is worse off than a trader who gets a 503.

**THE FOURTH IS WHETHER THE REGISTER BELONGS IN `apps/worker/src` AT ALL.** It is data about the deployable rather than behaviour of it, so it could have been a document. **It is code because the assertions that keep it honest read the tree**, and a document would have put the register and its derivation in two languages a session apart, which is the drift this whole row exists about. **The cost is that a barrel leg now exists whose runtime value nothing executes**, and a founder is entitled to call that a document in the wrong place.

**AND ONE THING THIS ENTRY IS NOT A JUDGEMENT ABOUT.** Sections 1, 2, 3.1, 5, 6 and 8 are **FINDINGS**: every claim is a path and a line and any of them is refuted by opening the file rather than by disagreeing. **Section 3.3's ruling, section 3.2's refusal and section 4's refusal are the judgements**, and they move if and only if one of those findings is wrong.
