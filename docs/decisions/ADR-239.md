## ADR-239: The API reads a rule state the worker wrote, and the reason this deployment can produce none is that nothing runs the worker at all  (2026-08-29, status: proposed)

**[ALLOCATION](ALLOCATION.md) row `239` dispatched this session to find out why `usePayoutBackend`'s last clause is true, and its own first instruction was to check whether the answer is that `runNightlyBatch` is exported and called by nothing. It is, and there is a link under that one.** The worker deployable's `start` script loads a barrel of exports, declares `main` and never invokes it. **Measured live rather than read: `pnpm --filter @merit/worker start` prints nothing and exits 0**, which is what a healthy service looks like to a supervisor.

**So the payout port is not blocked by a door. It is blocked by a deployable that runs no job**, and that is a larger finding than the wiring the row was willing to settle for.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `239`, session **429**, dispatched as `claude/a-rule-state-this-deployment-cannot-produce`. **No migration is reserved, taken or spent**: nothing here changes the schema, and section 6 states why the next slice needs one and this one does not.

- **MONEY PATH.** `usePayoutBackend` is the arm that approves payouts, and ruling 1 decides where the payout verdict is computed for every deployment after it. [**`E2`**](../../MERIT_BUILD_MASTER_PROMPT.md) **READ IS OWED.** The entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED**, separated before the argument starts. That the worker starts and exits 0 is **MEASURED**, by running it, in section 2. That the chain has four links and that no `src/` file supplies any of them is **DERIVED**, by census, in sections 2 and 3. That the API reads rather than folds is **JUDGED**, in ruling 1, and section 4 is the argument.

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim was read at its own file before it was relied on, and the two that came back different from the dispatch are in section 7.

### 1. The question the row asked, and the four links under it

The row's clause is *"a `RuleState` THIS DEPLOYMENT CANNOT PRODUCE"*. Four things stand between this tree and one row of `rule_states`, and they fail in order:

| Link | What it needs | State on this tree |
|---|---|---|
| **1. A scheduler** | something that CALLS `runNightlyBatch` | **ABSENT, and the deployable that would hold it runs nothing** |
| **2. A `BatchPorts` adapter over Postgres** | a value satisfying seven read methods and three write methods | **ABSENT under every `src/`** |
| **3. An `engine_gates` codec** | an `encodeEngineGates`, and its inverse for the read | **ABSENT. The ENCODING is ruled ([ADR-206](ADR-206.md)); the CODEC is not written** |
| **4. Rows** | a `rule_states` row for the account-day | **NONE, which is links 1 to 3 restated as a fact about the table** |

**Only link 3 had ever been named on this port, and it is the only one of the four that got cheaper this week.** `usePayoutBackend`'s entry and `ELIGIBILITY_BLOCKER` both carried links 3 and 4. **Neither carried link 1 in the form it actually takes**, which is not "the batch has no caller" but "the process that would call it does not run".

### 2. Link 1, measured rather than asserted

Both deployables start the same way, and they differ by one statement.

```
$ pnpm --filter @merit/worker start
> @merit/worker@0.0.0 start /home/user/meritfutures/apps/worker
> node --experimental-strip-types src/index.ts

EXIT=0
```

**No output, no listener, no timer, no exit code.** [`apps/worker/package.json`](../../apps/worker/package.json) declares `"start": "node --experimental-strip-types src/index.ts"`, and [`apps/worker/src/index.ts:1268`](../../apps/worker/src/index.ts) is `export function main(): void {`, whose body is a `console.log` describing everything the module does not do. **The only occurrence of `main(` anywhere under `apps/worker/src` is that declaration.** [`apps/api/src/start.ts:149`](../../apps/api/src/start.ts) is `await main();`, on a manifest whose `start` names that same shape of module.

**THIS IS WHY THE ABSENCE HAS NEVER PAGED ANYBODY.** [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md)'s own opening states the failure it exists for: *"A scheduled job that fails loudly is a job somebody fixes. A scheduled job that stops being scheduled is invisible."* A process that exits 0 having done nothing is the same shape one layer down, and it is worse, because a supervisor reads it as success rather than as absence.

**AND THE COST IS NOT THE RULE STATE ALONE.** Four rows of that inventory record their job as *"BUILT ... AGAINST PORTS AND NOT YET WIRED OR SCHEDULED"*: the statistics run, the detector runs, the freeze expiry sweep and the plan breaker evaluation. **The nightly batch's row records no such thing**, and it is the `S2` row every one of the others sits downstream of. Section 7 finding 1 states what that row is owed and why this session did not write it.

**Link 1's census, over all 281 `.ts` files under every `apps/*/src` and `packages/*/src`:** three name `runNightlyBatch`. They are the module that declares it, the barrel that exports it, and [`routes/account-reads.ts`](../../apps/api/src/routes/account-reads.ts), which names it **inside a string literal** in the reason that refuses `/eligibility`. **A fourth would be a scheduler or an adapter.**

### 4. RULING 1: the API READS a rule state the worker WROTE

**The two deployables meet at `rule_states`. The API never folds a day.**

The row required this ruled with its reasoning, and the reasoning is four things, of which the first is the only one that would matter on its own:

1. **`INV-M5-02` is a claim about the number of evaluators, not about the number of call sites.** [M05:81](../plans/M05-payout-system.md) states it and states its own control in five words: *"A second evaluator would be a second rule."* An API that folded its own `RuleState` would satisfy the letter of that row, both endpoints still calling `evaluatePayout`, while producing the input from a code path the worker's audit has never seen.

2. **`ADR-026` C-07's `state_hash` is the detector for exactly this defect, and a request-path fold is invisible to it.** That hash exists so a replay can compare a stored row against a recomputation. **A state computed in the request path is never stored and never hashed**, so the one mechanism this corpus built to catch two disagreeing producers would be looking at one of them. **Both answers would look authoritative, and only one would be in the ledger.**

3. **`R-06` makes the intraday answer a different question rather than a fresher one.** [M01:470](../plans/M01-rules-engine.md): *"Every evaluation is against the last closed day and nothing more recent."* The engine's own gloss at [M01:785](../plans/M01-rules-engine.md) already worked this out for the forecast endpoint: a `RuleState` for a day that has not closed comes only from `advanceDay`, whose `DayInput.mark` is a `DailyMark` **R-06 guarantees does not exist**. So the request path has no legal input to fold from, and inventing one would be inventing a mark.

4. **The layering says so and the manifests enforce it.** [`ports.ts`](../../apps/worker/src/batch/ports.ts)'s header records M01 section 1.2 putting *"reading or writing the database"* outside the engine, and the fold's inputs are six per-account fields plus a calendar slice and a watermark. **Doing that per request is not a cheaper version of a nightly job; it is the nightly job with no batch and no advisory lock**, and `FM-10` names the race the lock exists for.

**RULING 2. This port is not wireable and its entry is NARROWED rather than deleted.** `listPayouts` and `idempotency` are constructible today. Installing them beside a `transact` whose `subject` rejects would put a live-looking route in front of the arm that approves payouts, so a **partial** backend is refused rather than overlooked. The route answers 503 before it reaches a transaction.

**RULING 3. NOTHING IN A REQUEST PATH MAY COMPUTE A RULE STATE TO GET A PORT WIRED**, and this is stated as a standing rule rather than as this session's choice, because the temptation recurs every time a session is dispatched at a blocked port with a fold in scope.

### 6. The next slice, sized

**Three slices, and they are strictly ordered, because each one's tests need the one before it.**

**SLICE A: the `engine_gates` codec. The cheapest, and the only one with no open question in it.**

- **Home: `packages/rules-engine`.** Both consumers declare it: `apps/worker`'s manifest lists `@merit/db` and `@merit/rules-engine`, `apps/api`'s lists both among eight, and the engine declares **no workspace dependency at all**, so the arrow cannot point back (`RI-01`). **Putting the encoder in `apps/worker` and the decoder in `apps/api` is `FM-16`**, two statements of one predicate with nothing comparing them, and `readLiability` cannot import `apps/worker` anyway.
- **Content:** `encodeEngineGates` and `decodeEngineGates` over ADR-206's twenty-five leaves. Seven cents leaves render base-10 through the same path `hash.ts:355`'s `money()` uses. Three `skipped` leaves and no fourth. Two nullable basis-point leaves. One nullable `YYYY-MM-DD`.
- **Its own control:** a round trip against [ADR-206](ADR-206.md) section 6's specimen, which was written into a real row and read back, plus a case pinning the leaf set against `ENGINE_GATE_LEAVES` so a bag that grew a leaf goes red rather than hashing differently.
- **Size:** one module, one suite, no migration, no schema change, no new dependency. **It also clears `B5` term 2's implementation and is the term `readLiability` waits on.**
- **It inherits an `E2` debt:** ADR-206 is `proposed` and UNSIGNED, so the slice that writes this codec is transcribing a ruling the founder has not yet read.

**SLICE B: `BatchPorts` over Postgres.** Ten methods on `apps/worker`'s one door, `LIVE_DB.batch` at `systemDb('nightly-batch')`. `writeRuleState` is already built as `writeRuleStateVia` and needs only a `RuleStateWriterIo` whose `transact` is that door and whose `encodeEngineGates` is slice A. **The costs the type does not show:** `loadAccountDay` assembles six fields beyond the account id (`plan`, `prior`, `mark`, `settlements`, `openedOn`, `external`) and its `prior` needs slice A's decoder; `FM-10`'s **per-account advisory lock** is owed by the adapter in writing and by nothing else; and `raiseReconciliation` and `raiseDivergence` need an event sink this deployable cannot reach. **A composed writer exists and it is in the wrong app**: `TRANSACTION_EVENT_WRITER` in [`apps/api/src/events.ts`](../../apps/api/src/events.ts) is the only one in the tree, `apps/worker`'s manifest declares `@merit/db` and `@merit/rules-engine` and nothing else, and under `node-linker=isolated` an undeclared import does not resolve at all. **So the two loudest events in the estate, `replay.divergence_detected` among them, have a writer the worker cannot import.** Size: the largest of the three, and the one that should be planned before it is written.

**SLICE C: the scheduler.** This is where the migration is. [`index.ts`](../../apps/worker/src/index.ts)'s header records that **pg-boss's schema is not in `packages/db/migrations`**, confirmed here by a search of every migration for the string, so there is nothing to enqueue into; `@merit/queue` is not in `apps/worker/package.json` and under `node-linker=isolated` an undeclared import does not resolve; `main()` must be called; and `batch.completed` must be emitted or [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md)'s dead-man switch has nothing to watch. **Size: one migration, one manifest line, one call, and one event.**

**A cheaper first move exists and is named so nobody has to invent it.** Slice A is independently valuable, has no open question, and turns three live refusal messages from "waiting on a decision" into "waiting on a module". **A session that lands only slice A has moved link 3 and left links 1 and 2 exactly where they are**, which is honest progress rather than the appearance of it.

### 10. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS WHETHER SLICE C MOVES UP.** You have been told for many sessions that jobs are *"built against ports and not yet wired"*, and that reads as one missing adapter per job. **It is not.** There is no process. The provisioning saga, the expiry sweep, the detector runner, the breaker evaluator, the digests and the nightly batch are all downstream of one uncalled function, and every dead-man switch that would page on their absence is downstream of a deployment that reports success. **If the estate has ever been thought of as partly running, it is not.**

  **THE SECOND IS RULING 1**, which is the one thing here that binds every session after it. It says the payout verdict is computed in exactly one place, by the worker, and that the API only ever reads. **The cost of that ruling is that the payout port stays at 503 until three slices land.** The cost of the other answer is a second evaluator, and section 4 argues that the corpus already spent a hash column on making that answer detectable.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The four links are ordered as a chain and the ordering is an argument rather than a measurement.** It is possible that a `BatchPorts` adapter and a codec could land and be exercised end to end by a manual invocation, with the scheduler last, and that would be a defensible build order that this entry's framing discourages. **What is measured is that all four are absent; that link 1 must be repaired FIRST is a judgement about sequencing, not a finding.**
