## ADR-047: `rule_states` carries the calendar revision, and Appendix B.4's protocol governs a calendar correction  (2026-08-16, status: accepted)

**[P2 section 4](../plans/P2-rules-engine.md) is the analysis and this ADR records the ruling. `OQ-P2-02`, closed. The migration is NOT this session: it is money path and gets its own, and its number is claimed in [ALLOCATION](ALLOCATION.md) here so a sibling branch can read it.**

- **Context:** **[M01 Appendix B.3](../plans/M01-rules-engine.md) has no row for a calendar correction, and the default it falls into is the wrong one.** Its table names three legitimate divergence causes — a superseded mark, a backdated mark, an engine upgrade — and everything else is **"no. Page."**

  **Verified on the tree: `rule_states` carries no calendar reference of any kind.** So replay cannot scope by calendar revision even if it wanted to. [`trading_calendar_revisions`](../architecture/data-model/trading_calendar_revisions.md) exists in [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql) and holds the prior image `INV-04` needs, and [`0033`](../../packages/db/migrations/0033_trading_calendar_revision_required.sql) makes writing one mandatory under [ADR-045](ADR-045.md), **but nothing joins either to a state row.**

### Why the gap is not small, which is the part a reader will underestimate

**A mark correction changes one account's inputs. A calendar correction changes the day sequence for every account at once.** Every counter that advances per trading day, every cadence gap computed by sequence subtraction, every `nextTradingDayAfter`.

**The first holiday correction diverges the whole book and pages once per account.** At 5,000 accounts that is 5,000 pages, which is exactly how [Appendix B.5](../plans/M01-rules-engine.md)'s own warning comes true: *"a self-audit that becomes slow becomes a self-audit that gets disabled."* The alarm does not fail by being wrong. It fails by being right five thousand times on one morning.

### The ruling

> **The calendar revision is the engine's SECOND version-like input, and Appendix B.4's protocol already fits it without amendment.**

`engine_version` is **the code the fold runs**; the calendar revision is **the data it folds over**. B.4 step 1 already scopes divergence detection to rows whose stored `engine_version` matches the running version, and the same scoping is the right answer for the same reason.

1. **`rule_states` carries the calendar revision it was computed under.** A migration, therefore **money path**: its own session, plan mode, fresh context. **[`0034`](ALLOCATION.md) is claimed for it here and is not written in this session.**
2. **Replay compares only rows computed under the current revision.** Older rows are out of scope until step 4, exactly as for an engine upgrade.
3. **A revision triggers the dry run**: accounts affected, fields changed, and **whether any changed day underlies a settled payout**.
4. **Founder approval as an `admin_actions` row carrying the report digest**, so what was approved is provable later.
5. **Audited rewrite. `INV-22` holds: no settled payout's `eligibility_snapshot` is ever rewritten.**

**B.3 gains the row it was missing**, so a calendar correction is a named legitimate cause rather than falling into "no. Page."

### The wrinkle, stated so nobody re-derives it under pressure

**A calendar correction can insert or remove a day *between* two settled payouts**, and so change a cadence-gap count retroactively, **which can make a settled payout retroactively ineligible.**

The corpus already rules this case in a different costume. B.3 and `AS-05` say a correction under a settled payout is **absorbed, flagged, reported, never clawed back**, and B4 #5 is the constitution's form of the same sentence. **Nothing new is decided here**, and it is written down precisely because the arithmetic looks novel enough that somebody would rule it again, differently, at speed.

- **Consequences:** **`0034` is claimed and unwritten**: `rule_states` gains the calendar revision it was computed under, and that migration is money path with its own session under [ADR-003](ADR-003.md)'s strict regime. Until it lands, **replay cannot scope by revision and a calendar correction remains the 5,000-page event** — which is a stated exposure rather than a solved one, and it is why the number is claimed now. [M01 Appendix B.3](../plans/M01-rules-engine.md) gains a fourth legitimate divergence cause. **The revision is a reference to a `trading_calendar_revisions` row rather than a copied value**, because ADR-045 already makes that row mandatory and unforgeable, and a second copy of a fact the database owns is the drift this corpus has spent five ADRs ending. **This ruling adds no clawback and no new absorption rule**; it points at the ones already ruled.

- **Alternatives considered:** **Paging on every calendar-caused divergence** (rejected: it is the current behavior, it is 5,000 pages, and B.5 already names what happens to an alarm that behaves that way); **suppressing calendar-caused divergences** (rejected outright: it is the same silence with a nicer name, and it would hide a genuine engine regression that happened to coincide); **a global "calendar revision" counter compared per run rather than stored per row** (rejected: it cannot tell a row computed before the correction from one computed after, which is the entire question); **recomputing the whole book on every correction without the dry run** (rejected: it writes before a human has seen whether a settled payout is under a changed day, and step 3 exists for exactly that); **inventing a new protocol** (rejected: B.4 exists, it was written for a version-like input, and a second protocol for the same shape is two expressions of one concept).
