## ADR-148: `G-ELIGIBLE` conjoins two terms the eligibility response declares no gate for, so the differentiator screen can render ten passing gates beside a refusal  (2026-08-27, status: proposed)

**[`STATE_MACHINES:403`](../architecture/STATE_MACHINES.md)'s `G-ELIGIBLE` is a conjunction of twelve terms. [`API_CONTRACT:446`](../architecture/API_CONTRACT.md)'s `GET /accounts/:accountId/eligibility` declares TEN gates. Two of the twelve have no member in the response at all: `identities.status = 'active'`, which is [ADR-062](ADR-062.md) section 1's own ruling, and `G-NO-IN-FLIGHT`. So a trader whose identity is `restricted` or `closed`, or who already has a payout in flight, receives `eligible: false` with every rendered gate passing.** The endpoint's own header calls itself *"the differentiator identified in TOP10_FIRMS: competitors show progress bars, THIS SHOWS THE WHOLE RULE"*. On the two inputs above it shows ten green rows and a no. **This entry rules the display half, which is the half rendering forced, and refuses the contract half, which is not this session's.**

- **Origin:** session **260**, `claude/portal-payouts`, building `apps/portal/src/app/payouts/`. The number was **RESERVED BEFORE DISPATCH and CONDITIONAL** ([ALLOCATION](ALLOCATION.md) row 148): *"the eligibility view is the one screen where ADR-067's open question becomes visible to a trader"*. **The condition fired on a different question than the reservation predicted**, and section 4 reports that rather than filing the finding under the heading it was expected in.

- **NOT MONEY PATH BY FILE AND MONEY PATH BY CONSEQUENCE.** Nothing here reads, writes or computes a money value; `apps/portal` performs no arithmetic on money at all (`INV-M4-01`). What it does is decide what a trader is told about their own payout, and a wrong render is a wrong promise.

- **It amends no frozen document.** [API_CONTRACT](../architecture/API_CONTRACT.md), [STATE_MACHINES](../architecture/STATE_MACHINES.md), [M04](../plans/M04-trader-portal.md) and [M05](../plans/M05-payout-system.md) are untouched by this entry. Section 3 is why: the repair that would touch them is a ruling this session declines to take alone.

### 2. THE RULING, which is the display half and only the display half

#### Clause 1. The payout screen renders the disagreement between the verdict and the gate list, rather than the gate list alone

`apps/portal/src/app/payouts/view.ts` carries a three-valued `Verdict`. `eligible` and `blocked` are the ordinary answers. **The third, `unexplained`, is entered when the server answered `eligible: false` AND reported no failing gate**, and it renders a sentence saying that this response does not name what is holding, that this is a gap in what the endpoint reports rather than a rule the trader missed, and that support should be contacted with the account and the day.

#### Clause 2. That comparison is not a client-side gate evaluation and `INV-M4-03` is not weakened

`INV-M4-03` is *"the payout request button is enabled **only** when the server said `eligible: true` ... no client-side gate evaluation exists"*. The comparison reads two fields the server sent, `eligible` and the `pass` booleans, and decides no rule, reads no threshold and computes no number. **A client noticing that a response did not explain itself is not a client deciding whether a rule was met**, and a screen that could not notice is a screen that renders the ten green rows.

#### Clause 3. The screen states no reason, and stating one would be the ruling this entry refuses

`unexplained` does not say "your identity is restricted" and must never say it. The response does not carry that fact, and a client that guessed it would be inventing a cause, which is `FM-M4-05`'s failure aimed at a verdict instead of at a rule. **What it says is what is true: the answer arrived without its reason.**

### 3. WHAT THIS ENTRY DOES NOT RULE, AND WHOSE IT IS

**The contract question is: does `EligibilityResponse.gates` gain members for the two terms?** Three answers are available and this session takes none of them.

| Candidate | What it costs | Whose |
|---|---|---|
| **A. Add `identity_active` and `no_request_in_flight` to `gates`** | An addition to a **frozen** contract, and `INV-M4-06`'s neighbour has to be weighed: an identity-level state surfaced on an account-scoped endpoint. It is the answer that makes the screen honest with no client change at all, since the portal renders every gate the response declares | A ruling on [API_CONTRACT](../architecture/API_CONTRACT.md). Session **252** is writing `GET /payouts` and `POST /accounts/:id/payout` and ruling the gate |
| **B. Leave `gates` at ten and require `eligible` to be true whenever all ten pass** | Moves the problem into the engine: the endpoint would have to refuse to answer `false` without a gate to point at, which is a real constraint and a testable one | The engine's, and `G-ELIGIBLE`'s. Not a display decision |
| **C. Add a separate reason field beside `gates`** | A second vocabulary for refusal beside the gate list, which is two answers to "why not yet" on one screen | A ruling on [API_CONTRACT](../architecture/API_CONTRACT.md) |

**Why this session does not choose.** Changing a frozen document requires an ADR **and the ruling** ([CLAUDE.md](../../CLAUDE.md)), the money-path regime gives the payout gate its own session with its own fresh context ([ADR-003](ADR-003.md)), and session 252 is live on exactly this route while this branch runs. **A display session ruling the payout gate's contract is the shape of error this corpus keeps finding**, and clause 3 above is the version of it that was available here and was declined.

**What is owed either way.** Whichever candidate lands, `apps/portal/src/app/payouts/view.ts`'s `unexplained` branch becomes unreachable under A and B and stays reachable under C. **It should not be deleted on the day the contract changes.** A branch that renders "the answer arrived without its reason" is worth keeping for as long as an answer can arrive that way, and the test that proves it is reachable is the thing to read before removing it.

### 5. Alternatives considered

- **Render the ten passing gates and the `false` verdict, with no third state.** **Rejected, and it is the option this entry exists to refuse.** It is the literal truth of the payload and it reads as a firm that refuses without a reason, which is the single most damaging thing this screen can say. [M04:83](../plans/M04-trader-portal.md)'s differentiator is that the trader can check the firm's work, and ten green rows beside a no is work that cannot be checked.
- **Guess the reason from the failing write-route error codes.** **Rejected.** The read route never returns them and the screen has not called the write route. It would be a cause invented in the client on the one screen where a number becomes a money decision.
- **Add the two gates to `apps/portal/src/api/types.ts` and render them optimistically.** **Rejected twice over.** The contract does not declare them, so the app would believe in data the server does not send, which that file's own header forbids in those words; and it would pre-empt candidate A on a frozen document.
- **Hide the request control entirely when the verdict is unexplained.** **Rejected.** `INV-M4-03` already disables it, and hiding a control removes the trader's evidence that the screen understood the question.
- **Skip the entry and put the finding in the session log only.** **Rejected on the reservation's own terms.** [ALLOCATION](ALLOCATION.md) row 148 reserved a number against exactly this class of discovery, and a finding about a frozen money-path contract that lives only in a session log is a finding the next session will re-derive.
- **Rule candidate A here, since it is the obvious repair.** **Rejected.** It is obvious and it is not this session's, and section 3 is the argument at length.
