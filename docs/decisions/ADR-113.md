## ADR-113: the creative-submission endpoint enters the contract, and the row is written from the CONSTRAINTS rather than from the plan's sentence  (2026-08-26, status: proposed)

**[M08](../plans/M08-affiliate-system.md) section 4 rows `POST /affiliate/creatives` as **NEW** and owned by M08, and [API_CONTRACT](../architecture/API_CONTRACT.md) has never carried it. API_CONTRACT is `approved`, so the row is an ADR and not a commit.** This entry adds it, and it rules that the response shape is derived from `affiliate_creatives`' own CHECK constraints rather than from M08's one-line description of the endpoint, because the plan's sentence and the schema disagree about when the disclosure is known.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-n` row, session **220**. The number was RESERVED before dispatch and the fence names it REQUIRED. **`POST /affiliate/creatives` IS THE ONLY ROW THIS SESSION MAY ADD** to a file [P4 section 9](../plans/P4-portal-and-site.md) calls the hottest cross-phase file in the corpus.

- **Context:** [session 162](../sessions/2026-08-24-session-162.md) measured the gap and the measurement was re-taken at this session's base: `grep -n "creatives" docs/architecture/API_CONTRACT.md` returns **nothing**. The table exists ([`0005_affiliate_program.sql:104`](../../packages/db/migrations/0005_affiliate_program.sql)), the invariant exists (`INV-M8-08`), the delta exists (`SD-M8-03`), and the endpoint that writes the row has no contract.

### 2. THE RULING

> **1. THE ROW IS ADDED TO API_CONTRACT SECTION 7, BESIDE `POST /affiliate/links`, AND NOWHERE ELSE.** Section 7 is headed *"KYC and affiliate"* and already holds `GET /affiliate/stats`, `GET /affiliate/statements` and `POST /affiliate/links`. A creative submission is an affiliate write and belongs with them.
>
> **2. THE RESPONSE CARRIES THE CREATIVE AT `pending` AND THE REQUIRED DISCLOSURE BESIDE IT, AND THE TWO ARE SEPARATE FIELDS BECAUSE THE SCHEMA MAKES THEM SEPARATE FACTS.** M08 says the endpoint *"returns the current required disclosure text so the affiliate can attach it before submitting rather than after being rejected"*, which reads as though the disclosure is pinned on submission. **It is not, and the constraint says so**: `affiliate_creatives_approved_has_disclosure` binds the disclosure to APPROVAL and `disclosure_version_id` is nullable at `pending`. So `disclosure` in the response is **THE DISCLOSURE THE REVIEW WILL REQUIRE** rather than one this row already carries, and it is named `required_disclosure` so nobody reads it as a pin.
>
> **3. `kind` ON THE WIRE IS THE SCHEMA'S FIVE MEMBERS AND A SIXTH IS A MIGRATION BEFORE IT IS A CONTRACT CHANGE.** The union is written out in the contract rather than typed `string`, on `psp` in section 5's own precedent.
>
> **4. THE ENDPOINT REQUIRES `session` AND NOT ELEVATION, AND IT IS NOT A `C-27:` ROW.** [ADR-039](ADR-039.md) amendment 4's closed vocabulary is the input and C-27's sensitive actions are payout destination change, contact change and external withdrawal. Submitting a creative moves no money and changes no credential surface; what it does is put a document in front of a human reviewer, and the reviewer is the control.
>
> **5. NO REVIEW ENDPOINT IS ADDED AND THE ASYMMETRY IS DELIBERATE.** Approval, rejection and the automatic withdrawal M08 section 3.3 describes are OPERATOR acts on the admin origin, and section 8 is where an admin row goes. **This entry adds ONE row**, which is the fence, and the operator half is named in section 5 below as owed rather than left to be discovered.

---

### 3. Clause 2, which is the only place this entry disagrees with the plan

**The plan's sentence and the schema's constraint are both right about different moments and a contract row has to pick one.**

M08 wants an affiliate to see the disclosure BEFORE submitting, which is a real product argument: NFA I-26-12 requires the disclosure to accompany the claim, and an affiliate who learns the requirement at rejection has already published. The schema pins the disclosure at APPROVAL, which is also right: `affiliate_creatives_approved_has_disclosure` exists so that a 2027 review of a 2026 post can answer which disclosure was in force, and a disclosure recorded at submission would record the one the affiliate saw rather than the one the reviewer applied.

**A single field would have collapsed the two.** `disclosure_version_id` in the response would have read as the pin and would have been null on every fresh submission, which is the shape that makes a client render an empty disclosure box on the one screen it matters. So the response carries `creative` (the row as written, disclosure absent) and `required_disclosure` (the version in force now, with its text), and **the client is told which is which by the field names rather than by a comment**.

**WHAT THIS COSTS is one honest ambiguity, stated here rather than hidden**: `required_disclosure` is read at submission time and the review may happen after a new version supersedes it. M08 section 3.3's automatic withdrawal is the mechanism that handles that and it is not this endpoint's.

---

### 4. Alternatives considered

- **Putting the row in section 8 as an admin endpoint.** Refused: the affiliate submits, the operator reviews. `POST /affiliate/links` sets the precedent one row up.
- **Returning `disclosure_version_id` alone.** Refused on section 3: null on every fresh submission, and an id is not text an affiliate can attach.
- **Typing `kind` as `string`.** Refused on section 5's own `psp` precedent. A closed CHECK list that reaches the wire as `string` is a contract that admits a value the database refuses.
- **Adding the review endpoints in the same row.** Refused: the fence is one row, and the operator surface has its own RBAC, its own `admin_actions` requirement and its own origin.
- **Requiring elevation.** Refused on clause 4. C-27 names three actions and this is none of them; a factor requirement invented here would be a fourth sensitive action added without the ruling that creates one.
- **Amending [M08](../plans/M08-affiliate-system.md) to match the schema instead.** Refused, and it is the tempting one: M08 is `approved` and frozen, so moving its sentence is a second ADR against a second document, and the sentence is not wrong. It is about a different moment, which is what section 3 says.

### 5. What this entry does NOT decide

- **THE OPERATOR HALF IS OWED AND IS NAMED HERE RATHER THAN DISCOVERED LATER.** Approve, reject and withdraw have no contract row, and neither does M08 section 3.3's automatic withdrawal when a disclosure version is superseded. `affiliate_creatives_decision_has_author` requires `reviewed_by` and `reviewed_at` on both decided states, so the operator row cannot be written from the trader surface at all.
- **No route is implemented.** This entry adds a contract row and no code. `apps/api/src/routes/` gains no `affiliate.ts` in this session.
- **No migration and no migration number.** `affiliate_creatives` exists in `0005` and needs nothing. **`0048` stays free.**
- **No schema delta, no `SD-nn`.** `SD-M8-03` already created the table and this row does not widen it.
- **No `CI-06` letter, no gate register row, no `VG` row, no `RI-nn`, no `OI-nn`, no fixture, no edge case.**
- **Nothing about commission.** [P3 section 12](../plans/P3-wave3-modules.md): *"`P3-n` writes the attribution and no commission."*

### 6. Two things this session found and did not rule, recorded here because the entry is where a reader will look

**A `pair` TABLE IS UNREACHABLE TO EVERY `apps/api` REQUEST HANDLER, AND `attributions` IS WRITTEN INSIDE CHECKOUT.** [Session 216](../sessions/2026-08-25-session-216.md) reported it from the ledger posting path and [session 215](../sessions/2026-08-25-session-215.md) attached this table to it in its own words: *"`attributions` is written inside checkout, so it is session 220's problem in a concrete shape."* Re-derived here: [`scope.ts:1067`](../../packages/db/src/scope.ts) classes the table `pair`; [ADR-106](ADR-106.md) excludes a `pair` key from both narrow key sets; [`scoped-db.ts:176`](../../packages/db/src/scoped-db.ts) declares `SystemReason = 'nightly-batch' | 'operator-console'`. **[ADR-112](ADR-112.md) did not close it and says so**: its section 10 moved the ADDRESS and left the AUTHORITY where [ADR-102](ADR-102.md) section 7 left it. `apps/api/src/routes/checkout.ts` declares `CheckoutTx.insertAttribution` as a PORT, which is where that decision lands. **It is reported and not taken here, because a third door on the money path is not a checkout slice's to open.**

**`IdempotencyStore` IS STILL UNIMPLEMENTED AND [ADR-109](ADR-109.md) CLAUSE 3's CLAIM STANDS UNCHANGED.** ADR-112 removed the obstacle that clause named. What remains is that an implementation must import `@merit/db` into `apps/api`, whose manifest declares no such dependency and was not in this session's fence, and that admission is an authority change on the deployable serving the whole public surface rather than a side effect of a checkout slice.

### 7. Consequences

- **API_CONTRACT gains one row and M08's section 4 stops naming an endpoint no contract carries.** That closes the measurement [session 162](../sessions/2026-08-24-session-162.md) took and P3's `P3-n` row was dispatched with.
- **The operator surface's debt is now written down.** Three verbs and one automatic transition have a table, an invariant and no contract, which is the same shape this entry just closed one door of.
- **The contract now states a field whose value can go stale between submission and review**, and the mechanism that resolves it lives in a plan rather than in the contract. Section 3 names that rather than implying it.
