## ADR-237: Authentication and the operator directory are two different things, so the directory is built, `admin_actions.actor` gains a referent, and what is left of the SSO blocker is one named function and three named variables  (2026-08-29, status: proposed)

**Six ports in `apps/api` refuse to be wired, and every one of them reduces to `setAdminSessionSource`.** That port's own BLOCKED entry named two obstructions in one breath: *"THE OPERATOR DIRECTORY IS NOT IN THIS DATABASE: `admin_actions.actor` is `text NOT NULL` with no foreign key ([`0017_events_and_audit.sql:77`](../../packages/db/migrations/0017_events_and_audit.sql)) and no table in the registry holds an operator, a role or an operator session"*, and behind that, `SECURITY` `C-08`'s hardware-key SSO. **THE TWO ARE NOT ONE THING AND TREATING THEM AS ONE IS WHY BOTH WAITED ON A PURCHASE.**

**Proving WHO someone is needs the identity provider `C-08` requires, and that is a purchase the founder has not made.** **Recording WHICH operators exist and WHAT ROLE each holds is a table**, and [API_CONTRACT](../architecture/API_CONTRACT.md) section 8 closed the role set at `owner`, `ops` and `readonly` long before any of this was written. This entry builds the second and leaves the first as a **named seam**.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `237`, session **427**, dispatched as `claude/the-operator-directory`. **Migration `0073` is reserved and spent**, in the same commit that writes it.

- **NOT THE MONEY PATH BY FILE, AND IT SITS UNDER EVERY MONEY-PATH ADMIN ROUTE.** Nothing here moves a cent, declares a ledger class or touches a payout branch. What it does is give `admin_actions.actor` a referent, and `admin_actions` is the row `POST /admin/payouts/:id/release` and `POST /admin/wallet/:identityId/correct` both write. **It ships `proposed` with an UNSIGNED approval line.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That `admin_actions.actor` carried no foreign key, that no table held an operator, a role or an operator session, that `0002:280` states there is no password table in this schema by design, that `impersonation_sessions.admin_user_id` references `users(id)`, that `otp_challenges` keys off `email_normalized`, and that the role set is stated in **four** places rather than three, are all **MEASURED**, each against the primary source and each named below at its file. That an operator modelled as a `users` row is authenticable by an emailed OTP is **DERIVED**, by following three declarations in section 6. What is **JUDGED** is that `C-08` covers two questions rather than one (section 2), that no port is wired out of this (section 8), and that a session-lifetime ceiling is owed rather than invented (section 7).

- **A DISPATCH PROMPT IS NOT A SOURCE, AND THIS ROW'S ONE CITATION DOES NOT HOLD.** The row cites `API_CONTRACT:516` for the closed role set. **The role set is at [`API_CONTRACT:896`](../architecture/API_CONTRACT.md)**; `:516` is a field of `PayoutListItem`. The quoted words hold exactly at `:896` and the pointer is wrong by 380 lines. **It is wrong in five other live documents besides**, which is section 9 finding 3.

### 1. THE RULING

> **1. `C-08` COVERS TWO QUESTIONS AND ONLY ONE OF THEM IS THE PROVIDER'S.** *Who is this person* is the identity provider's, is phishing-resistant hardware-key SSO, and is a purchase. *Which operators exist, and what role does each hold* was never the provider's: it is Merit's authorization model, it is read by `admin_actions`, and it belongs in Merit's own database. **`SECURITY` `C-08` is amended in terms and section 3 carries the exact replacement text.**
>
> **2. THE DIRECTORY IS BUILT.** [`0073_operator_directory.sql`](../../packages/db/migrations/0073_operator_directory.sql) creates `operators` and `operator_sessions`, closes `operators.role` over API_CONTRACT section 8's three with a `CHECK`, and both relations are registered in [`scope.ts`](../../packages/db/src/scope.ts) as `firm`.
>
> **3. `admin_actions.actor` GAINS A REAL REFERENT, AND THAT IS `0017`'s OWN CONTROL ENFORCED RATHER THAN ASSERTED.** `0017` writes *"NO UNEXPLAINED ADMIN ACTION, EVER. NOT NULL is the whole control"* over `reason`, one column away from an `actor` that any string satisfied. `admin_actions_actor_is_an_operator` makes an audit row naming an actor in no directory **unwritable** rather than merely undesirable. `0017` is merged and is superseded **by addition** (constitution `E2`).
>
> **4. NO LOGIN IS BUILT, AND THIS IS THE CLAUSE THAT MATTERS MOST.** No password column, no local credential, and no session a human can mint by knowing a secret this deployable holds. Merit is passwordless by [ADR-039](ADR-039.md) and `0002:280` states it for the whole schema. **An admin password would be that rule broken at the highest-privilege door in the system, and it would be worse than the 503 this entry narrows**: a 503 refuses everybody and a local credential admits whoever learns it.
>
> **5. THE SEAM IS A FUNCTION AND IT STAYS BLOCKED.** `OperatorAssertionVerifier` ([`operator-identity.ts`](../../apps/api/src/operator-identity.ts)) takes a presented assertion and returns an `AssertionOutcome`. **No implementation of it exists in this repository.** A deployment closes it by supplying `MERIT_ADMIN_IDP_ISSUER`, `MERIT_ADMIN_IDP_AUDIENCE` and `MERIT_ADMIN_IDP_JWKS_URL` **and** by the slice that writes the verifier. **Absent means `unconfigured`, `unconfigured` is a 503, and the configuration is necessary and not sufficient**, which section 4 states as a property a suite asserts.
>
> **6. THE ROLE IS MERIT'S AND IS NEVER ASSERTED BY THE PROVIDER.** `OperatorAssertion` carries an issuer, a subject and an assertion id, and no role. A role asserted by a provider would put Merit's authorization model in a vendor console, where it is unversioned, invisible to `admin_actions`, and changeable by whoever administers the tenant.
>
> **7. AN OPERATOR IS NOT A `users` ROW, AND `0042` ALREADY SAID OTHERWISE.** `operators` declares no column against `users` or `identities`. The reason is a credential rather than a taste and section 6 derives it in three steps. **`0042` is merged, is not edited, and the collision it creates is reported rather than repaired here.**
>
> **8. NO PORT IS WIRED OUT OF THIS AND THAT IS A REFUSAL RATHER THAN AN OMISSION.** Nothing can write an `operator_sessions` row, so an installed `AdminSessionSource` would answer 401 to every operator on a door that is not shut against them. `admin-reads.ts` says so in its own refusal: answering 401 *"would report it as the caller being logged out"* when what is true is that the deployment is unfinished. `usePayoutBackend`'s rule is the general one: **a live-looking route in front of an arm that cannot answer is worse than an honest 503.**
>
> **9. THE BLOCKED ENTRIES ARE NARROWED TO WHAT STILL REFUSES.** `setAdminSessionSource` no longer waits on a directory. It waits on **one function and three variables**, both named in the entry, and the other five ports still reduce to it.

### 2. Why the two questions were one sentence for so long

**The sentence was never wrong, it was short.** `C-08` reads *"RBAC on admin, admin on a separate origin, IP allowlist, hardware-key SSO"*, four controls in one row of a table whose purpose is to be scannable. **Three of the four are edge controls on `ADMIN_ORIGIN` and the fourth, RBAC, is not**, and nothing in the row says which is which. `admin-reads.ts` read all four as the provider's and wrote it down: *"the mapping from a session to an actor and a role is the admin identity provider's"*. `admin-writes.ts` read the same thing and wrote a second copy: *"the operator directory is the SSO provider's and not this database's"*. `wiring.test.ts` quoted the first. The ALLOCATION row quoted the entry. **Four restatements of one compression, and every one of them was reasonable given the one above it.**

**What separates RBAC from the other three is who a control is ABOUT.** An origin, an allowlist and a factor are all statements about the request. A role is a statement about a **person Merit employs**, and Merit is the only party that knows it. A provider can be told a role and can assert it back, which is the design this entry refuses in ruling 6, and the cost of that design shows up the first time somebody asks *"who was `owner` on the day this payout was released"* and the answer is in a vendor's audit log rather than in `admin_actions`.

### 4. What a deployment must supply, and why configuration alone is not enough

**Three variables, NAMED here and VALUED nowhere in this repository** ([ADR-012](ADR-012.md)), on `MERIT_TURNSTILE_SECRET`'s and `MERIT_OTP_MAC_KEY`'s precedent ([ADR-226](ADR-226.md), [ADR-197](ADR-197.md), INFRA section 7).

| Variable | What it is | Why it is separate |
|---|---|---|
| `MERIT_ADMIN_IDP_ISSUER` | The issuer this deployment expects | An assertion whose issuer is not this value is another provider's. **Configuration and not a constant**, which is the opposite of `TURNSTILE_SITEVERIFY_URL`'s ruling and for its stated reason: that URL is a fact about a vendor's API, an issuer is a fact about which provider Merit bought |
| `MERIT_ADMIN_IDP_AUDIENCE` | Who the provider vouched **to** | The issuer says who vouched. Without the audience, an assertion the same provider minted for a different relying party is accepted here, which is the confused-deputy shape and needs no attacker inside Merit |
| `MERIT_ADMIN_IDP_JWKS_URL` | Where the signing keys are fetched from | **A URL rather than a key.** A pinned public key is a rotation that takes a deploy, and a provider rotating on its own schedule then locks every operator out at a moment nobody chose |

**ABSENT IS `unconfigured` AND `unconfigured` IS NEVER A PASS.** The failure this control exists to remove is a check that silently does nothing, so the one answer it may not give when it cannot run is *"fine"*. **A blank counts as absent**: an empty string is what a platform writes when a secret was declared and never filled in, and reading it as configured points the control at nothing while reporting that it is armed.

**PRESENT IS NOT ENOUGH, AND THAT IS THE DIFFERENCE FROM `turnstile.ts`.** There, the secret was the only missing thing and the verifier existed. Here the verifier does not, so a fully configured deployment receives `unavailable` rather than a pass. **`test/operator-identity.test.ts` asserts it over all eight subsets of the three variables and `verified` appears in none of them**, so a future edit that lets an environment file open this door turns that case red.

### 6. The finding on `0042`, derived in three steps

**[`0042_impersonation_sessions.sql:57`](../../packages/db/migrations/0042_impersonation_sessions.sql) declares `admin_user_id uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT`**, with the comment *"An admin user under hardware-key SSO at ADMIN_ORIGIN"*. So the estate already contains one modelling of an operator, and it is a trader-side `users` row.

1. **A `users` row is reachable by an emailed OTP.** [`0002`](../../packages/db/migrations/0002_identity.sql) declares `otp_challenges.email_normalized citext NOT NULL` and says why in its own comment: the challenge is *"Issued before a user may exist, so this keys off the normalized email rather than a user_id"*.
2. **Answering one mints a `sessions` row.** `sessions.user_id` references `users(id)`, and `routes/auth.ts` is the path.
3. **Therefore an operator holding a `users` row already holds a login this deployable can mint**, over a factor `SECURITY` forbids on this surface in terms: *"Admin auth stays hardware-key SSO (C-08) with no SMS path, ever"* ([`SECURITY.md:134`](../architecture/SECURITY.md)).

**THE COLLISION IS LATENT RATHER THAN LIVE**, and the entry says so rather than overstating it: nothing in this tree writes an `impersonation_sessions` row, `useImpersonationBackend` is not wired, and no route initiates a session. **`0042` is merged and is not edited** (constitution `E2`). `operators` refuses the edge, so the directory this entry builds does not inherit the problem, and the repair belongs to the slice that builds impersonation, which must either supersede `admin_user_id` onto `operators(id)` or state why an operator needs a trader row.

**THIS IS ALSO WHY `scope.ts` REGISTERS `operators` AS `firm` WITH THE TRAP NAMED.** `derived via users` is the rule a reader arriving from `0042` would expect, it would compile, and there is nothing for it to traverse because `0073` declares no such column.

### 7. What is owed and is deliberately not taken

1. **A CEILING ON `operator_sessions.expires_at`.** `impersonation_box_is_bounded` carries two hours because [M06](../plans/M06-admin-ops-console.md) `SD-M6-10` states one, and that plan's own sentence is the argument: *"a configurable duration with no ceiling is a setting, not a bound"*. **The corpus states no ceiling for an operator session** and `sessions` carries none either, so a number invented here would be the setting that sentence warns about. **It is ruled by whichever slice lands the minter, because that is the first slice with a number to defend.** `0073` carries the floor (`expires_at > issued_at`) and the revocation ordering.
2. **A FOREIGN KEY ON THE OTHER FOUR FREE-TEXT ACTOR COLUMNS.** `evidence_packs.requested_by`, `dual_control_approvals.requested_by` and `.approved_by`, and `treasury_balances.recorded_by` are all `text` actor strings this directory could now constrain. **They are a different question from the one this row was dispatched to rule** and each carries its own: `dual_control_approvals_second_person` compares two of them, so constraining them changes what that control compares against.
3. **A PROVISIONING PATH.** Creating an operator is a write, no admin write backend is wired, and **a route that mints the first `owner` is precisely the shape a login takes when it is written by accident.** The first `owner` row is a deployment act, and the slice that rules how it is taken should rule it deliberately.
4. **A RETENTION JOB.** Both design records state a retention and no job exists for either table, which is true of `sessions` as well and is [`CRON_INVENTORY`](../ops/runbooks/CRON_INVENTORY.md)'s standing gap rather than this entry's.

### 11. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS WHETHER THE SPLIT IS RIGHT.** This entry says `C-08`'s RBAC belongs in Merit's database and the identity belongs at the provider. **The alternative is real and some firms take it**: put groups in the provider, assert them as a claim, and have no `operators` table at all. It is less to build and it costs the property that a role change is an `admin_actions` row with a before and an after. **If you would rather the roles live in the vendor console, ruling 6 is the one to overturn and `0073` shrinks to a session table.**

  **THE SECOND IS THE FIRST `owner` ROW.** Nothing in this repository can create an operator, which is section 7 item 3 and is deliberate. Somebody has to decide whether the first one is a seed migration, a runbook step against the database, or a route that exists only while a deployment is being stood up. **All three have been used at other firms and only the third can be left behind by accident.**

  **WHERE THIS ENTRY WAS MOST LIKELY WRONG, AND THE PREDICTION WAS PAID OUT WITHIN THE HOUR.** This paragraph read *"`0073` has never been applied to a live PostgreSQL by this session ... the first real proof of it is the forward-only apply from empty in the `migrations` job"*. **`CI-06h` went RED on the first push and the constraint is what failed.** Two probe fixtures write `admin_actions (actor) VALUES ('founder', ...)` against a database holding no `operators` row, so the foreign key refused them, which is the control doing exactly what section 1 ruling 3 says it does. **The fixtures were repaired and the constraint was not weakened**: each probe now inserts the operator it names. Section 12 carries the measurement.

  **What that leaves genuinely unproven is narrower and is still worth your eye.** The DDL now applies forward-only from empty on PostgreSQL 16.13 with **67 migrations, 117 base tables and 29 triggers**, all eighteen probes green, the append-only grant assertion green in both directions, and a re-apply rejected. **What no run has exercised is a `0073` estate with rows in it that outlive a session**, because every probe ends in `ROLLBACK`: `ON UPDATE RESTRICT` on a renamed actor, and `ON DELETE RESTRICT` on an operator who has acted, are argued here and are not executed anywhere.

### 12. The constraint's first live proof, which arrived as a red CI run

**`CI-06h` failed on the first push and the failure is this PR's.**
`scripts/db/probe_audited_writes.sql` and
`scripts/db/probe_rule_state_phase_vocabulary.sql` each write an
`admin_actions` row with `actor = 'founder'` into a database holding no
`operators` row. **`admin_actions_actor_is_an_operator` refused both**, with
*"Key (actor)=(founder) is not present in table `operators`"*. CI reached the
first; the second was never run and fails identically.

**The repair is the fixture and never the constraint.** Each probe now inserts
the operator it names, with `idp_issuer` and `idp_subject` left NULL, which is
the state `0073` defines for an operator who cannot sign in and is the correct
one for a probe database that has no identity provider.

**Reproduced and then watched passing, locally, against PostgreSQL 16.13.** The
two probes at `HEAD` were run first and reproduced the CI error byte for byte,
including the second one CI had not reached. After the repair: **67 migrations
applied forward-only from empty under `ON_ERROR_STOP=1`, 117 base tables against
117 `CREATE TABLE` statements, 29 triggers against 29, all eighteen probes green,
`assert_no_floats` green, `assert_append_only_grants` green in both directions
over 26 append-only tables, and a re-apply of `0001` rejected.**

**THE REFUSAL IS NOW A WATCHED ONE RATHER THAN AN ACCIDENT.** A constraint whose
only demonstration was a red CI run stops being demonstrated the moment the run
goes green, so `probe_audited_writes.sql` gains **REJECTION 15**: an audit row
naming an actor in no directory is refused, and the message must name the
constraint. **It is in that file rather than in a new probe** because `CI-06s`
requires every probe on disk to be run by the workflow, a new file would widen
this diff into `.github/workflows/`, and that file already holds the table. The
case was falsified by dropping the constraint against the live database and
watching `REJECTION 15 FAILED` fire, then restoring it.

**The permit direction is exercised by the same file's own setup**, which
inserts the operator and then the audit row that names it, and the case also
asserts that a **suspended** operator's rows still write: this foreign key is a
referent check and never an authorization control, which is
`resolveOperatorSession`'s job at the door.
