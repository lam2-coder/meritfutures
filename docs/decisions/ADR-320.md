### 2. The shape, transcribed

[ADR-315](ADR-315.md)'s ruling is the specification, and its load-bearing sentence is that the handle stays in the wiring:

> SO THE ADAPTER RECOVERS THE HANDLE BY THE IDENTITY OF THE `ExpiryTx` IT IS GIVEN ... The wiring opens ONE transaction, passes it to `transact` as the `ExpiryTx` it already satisfies, records it against itself, and `postLt01` looks it up and REFUSES a handle it did not open.

**Three declarations and one expression are the whole of the file:**

| Name | Where | What it is |
|---|---|---|
| `OPENED` | [`ledger.ts:128`](../../apps/worker/src/sweeps/ledger.ts) | `const OPENED = new WeakMap<ExpiryTx, LedgerTx>();` |
| `recordExpiryTransaction` | [`ledger.ts:145`](../../apps/worker/src/sweeps/ledger.ts) | records the handle **against itself** and returns it |
| `ExpiryLedgerHandleUnknown` | [`ledger.ts:160`](../../apps/worker/src/sweeps/ledger.ts) | the refusal, naming the mechanism rather than the caller |
| `EXPIRY_LEDGER` | [`ledger.ts:196`](../../apps/worker/src/sweeps/ledger.ts) | the port: look up, refuse, or `postTransaction(ledger, await readChart(ledger), lt01(values))` |

**A `WeakMap` AND NOT A `WeakSet`, WHICH IS THE ONE PLACE THIS ENTRY DEPARTS FROM THE WORD THE RULING USED.** The ruling names `TERMS` ([`scoped-db.ts:723`](../../packages/db/src/scoped-db.ts)) as the idiom, and that is a `WeakSet` because membership is all `isFilterTerm` needs. Here membership is a boolean, and `postLt01` would still be holding an `ExpiryTx` it had to **cast** into a `LedgerTx` to post through. [`ports.ts:23-26`](../../apps/worker/src/sweeps/ports.ts) rules that nothing in this path casts past a key type and [ADR-315](ADR-315.md) section 6 refused a handle cast by name, so the map hands the value back already typed. **The key and the value are the same object**, which is what "records it against itself" means and what makes the `LedgerTx` the handle the release was written through rather than a second one opened beside it. `mintTerm` ([`scoped-db.ts:726`](../../packages/db/src/scoped-db.ts)) is the same three lines, and `recordExpiryTransaction` returns its argument for the same reason `mintTerm` does: so there is no arrangement of the wiring's one line in which the handle reaches the sweep unrecorded.

**THE HALT IS LEFT ALONE AND NO OVERRIDE IS TAKEN.** `postTransaction` ([`post.ts:126`](../../packages/ledger/src/post.ts)) asserts against `ledger_halts` unless the caller passes `despiteHalt`; this file passes no options at all, and a case asserts the word occurs in **no code** under `src/sweeps/` once comments are stripped. A refused posting rolls the release back, the hold stands, and `P5-k` reports it.

### 3. Why the file is where it is, and what it is forbidden to become

**IT IS THE ONE FILE IN THIS DEPLOYABLE THAT NAMES `@merit/ledger`**, on the pattern [ADR-165](ADR-165.md) set for `@merit/db` at [`db.ts`](../../apps/worker/src/db.ts). A manifest line grants a capability to a whole deployable at once, so the answer to "where does `apps/worker` post a ledger entry" is one path, and the suite runs that measurement rather than trusting the convention.

**IT REACHES NO DATABASE AND COULD NOT.** There is no `@merit/db` import in it, so [ADR-165](ADR-165.md)'s ONE-DOOR rule is untouched, and [`apps/worker/test/db.test.ts`](../../apps/worker/test/db.test.ts) is what runs it: that suite parses every BARE SPECIFIER under `src/` and asserts the accessor is imported by `src/db.ts` alone. `packages/ledger` declares no dependency of its own and takes the caller's open transaction as its first argument ([`tx.ts`](../../packages/ledger/src/tx.ts)), so what arrives here is always a handle somebody else opened.

**THE CLAUSE [`ports.ts:14-16`](../../apps/worker/src/sweeps/ports.ts) STATES IN GREP FORM IS NOT THAT CONTROL, AND IT WAS ALREADY FALSE AS SPELLED BEFORE THIS ROW.** It says `grep -rlE "from '@merit/db'" apps/worker/src` must print `apps/worker/src/db.ts` **AND NOTHING ELSE**. Run on this tree it prints **seven** files: `db.ts`, and six whose COMMENTS quote the clause. Six of the seven predate this row and the adapter is the seventh, for the same reason. **The property is true and that command is not the way to read it.** This entry names the specifier scan instead, and the grep sentence in `ports.ts` is **reported rather than repaired**: that file is outside this fence and the repair is a rewrite. Section 7 carries it as a landmine.

**IT IS NOT `ports.ts` AND MUST NEVER BE.** That file imports nothing, which is what makes a `ledger` member on `ExpiryTx` unreachable rather than merely unwanted: the member could only RESTATE `LedgerTx` there, and the restatement writes `LedgerWriteKey` ([`tx.ts:64`](../../packages/ledger/src/tx.ts)), exactly the two keys `EXPIRY_TABLES` ([`ports.ts:83`](../../apps/worker/src/sweeps/ports.ts)) excludes, back into the sweep's own port as an `insert` key union. **`ExpiryTx` still has three members, `EXPIRY_TABLES` is unchanged, and `ports.ts` was not edited at all in this row.**

### 5. What the suite proves that the prose cannot

[`sweep-ledger.test.ts`](../../apps/worker/test/sweep-ledger.test.ts) is nineteen cases in five sections, and the two sentences it exists to make false are named in its header.

- **"The adapter posts through whatever handle it is given."** A SECOND handle of the identical class is refused while the recorded one posts, so the check is identity and not shape. A shape test on `rows` and `insert` being present would admit the impostor, and that is exactly the defect the ruling exists against. Nothing is read and nothing is written before the refusal.
- **"The posting is a second transaction beside the release."** The whole sweep runs over the real `EXPIRY_LEDGER`, and the case asserts that the five hold NULLs and the four ledger entries landed **on one handle, in that order**, with no third handle opened. That is [ADR-006](ADR-006.md) exercised rather than described.
- **The posting is four entries and not three legs**, resolved onto `trader_withdrawable` twice and never `firm_treasury`, asserted at the account uuid. M05 section 2.1's recognition timing is the reason, and that error has been made in this repository once already.
- **A live `ledger_halts` row** makes the run report `failed` rather than `released` and `expirySweepClean` false; a RELEASED halt does not; `despiteHalt` occurs in no code under `src/sweeps/`.
- **`INV-M5-03` propagates**: a split that does not sum throws `PayoutMoneyError` and writes nothing.
- **The adapter holds no account name, no `transfer(`, no `@merit/db`, no `pg` and no `drizzle-orm`**, checked with comments stripped.

**The fake is built rather than borrowed from [`recording-tx.ts`](../../packages/ledger/test/recording-tx.ts).** What this suite needs is one object satisfying `LedgerTx` AND `ExpiryTx` at once, because that is precisely what `SystemTx` does and what the whole ruling turns on; a fake satisfying one of them would agree with the half that was never in doubt.

**What it cannot see, stated rather than left to a reader:** whether PostgreSQL accepts the rows, and whether a composed predicate reaches one row or many. Both are `packages/db`'s.

### 9. Approval

**What a founder read adds and this entry cannot.**

**THE FIRST THING TO DECIDE IS WHETHER A RUN-TIME REFUSAL IS THE RIGHT PRICE FOR A SENTENCE STAYING TRUE, NOW THAT THE PRICE IS PAID RATHER THAN PREDICTED.** [ADR-315](ADR-315.md) put this question in its own approval block and this row is where the answer becomes code: `postLt01` handed a transaction nothing recorded throws `ExpiryLedgerHandleUnknown` at run time, where a `ledger` member on `ExpiryTx` would have refused at compile time. **The failure mode is now concrete and worth reading as such.** A wiring that opens a transaction and forgets to record it does not fail a build; it fails on a clock, unattended, as a rolled-back release, a payout that stays held and a nightly assertion. This row narrowed that as far as the shape allows by making `recordExpiryTransaction` return its argument, so the wiring's one line has no correct-looking wrong arrangement, and by asserting the refusal in four cases. **It did not eliminate it, and it cannot.** A founder who reads that risk as unacceptable should send the next session to reverse [ADR-315](ADR-315.md) and amend `EXPIRY_TABLES`'s exclusion sentence, and the honest thing to say is that this row makes that reversal more expensive than it was yesterday, because there is now a file and a suite built on the other reading.

**THE SECOND IS THE MANIFEST LINE ITSELF, WHICH IS THE ONLY IRREVERSIBLE THING HERE.** `@merit/ledger` on `apps/worker` grants the whole deployable the ability to construct a posting and write a `ledger_entries` row, and nothing in the type system takes that back. What this row substitutes for a type is a measurement: exactly one file names the package, and a second one is red in two suites. **That is a control and not a convention, and it is still weaker than not having the capability at all.** [ADR-270](ADR-270.md) clause 7 already ruled that no `RI-nn` is minted over this line and `RI-08` owns the property, so a founder who wants the boundary enforced at the invariant layer rather than the suite layer is overruling that clause and should say so explicitly.

**THE THIRD IS THE COUNT, AND IT IS THE PART OF THIS ROW WORTH THE MOST ATTENTION.** [ADR-305](ADR-305.md) said two cases would go red. The dispatch corrected it to three and enumerated them at file and line, which was careful work and was still short by three. The three it missed were not obscure: one was predicted in terms by [session 506](../sessions/2026-09-04-session-506.md), and two sit in a file whose own comment predicts this exact edit and has predicted it three times before. **A count derived by reading is a count that will be wrong, and only running the suite produced the real number.** The generalisation this entry offers, and it is a recommendation rather than a ruling: **a slice that says "N cases go red" should state N as the thing to be measured on the branch and never as a fact the dispatch already knows**, because a session that trusts the dispatch's N and finds N red stops looking. This one did not stop, and the difference between three and six is the whole of what it found.

**THE FOURTH IS THE `index.ts` EDIT.** The fence did not include it and the barrel's totality check made the edit unavoidable; section 7 states the alternative that stays inside the fence and why it is worse. **A founder who reads a fence as absolute should say so**, in which case the remedy is that a row adding a module names `apps/worker/src/index.ts` in its fence from the start, rather than a session choosing between a fence and a green suite.
