### 2. What the field would have to address, and what the schema says about it

**THE SNAPSHOT HAS NO IDENTITY SEPARATE FROM ITS PARENT, AND THAT IS A RULED PROPERTY RATHER THAN AN ACCIDENT.** [`0010_payouts.sql:70-73`](../../packages/db/migrations/0010_payouts.sql) states it in the migration's own comment:

> Full gate-by-gate evaluation and inputs, immutable. A jsonb column rather than a separate table because it is written exactly once, always read with its parent, and must never drift from it. A join here would add a way for THE PROOF AND THE DECISION to disagree.

The same reasoning is in the corpus at [`data-model/payout_requests.md:36`](../architecture/data-model/payout_requests.md), and `INV-22` ([`M01:133`](../plans/M01-rules-engine.md)) is what makes the value immutable once written.

**SO THERE ARE EXACTLY TWO WAYS TO ADDRESS THE STORED PROOF: BY ITS PARENT ROW'S PRIMARY KEY, OR NOT AT ALL.** `payout_requests.id` is `uuid PRIMARY KEY DEFAULT gen_random_uuid()` ([`0010_payouts.sql:42`](../../packages/db/migrations/0010_payouts.sql)), and **the response already carries it**, as `payout_request_id` at [`payouts.ts:234`](../../apps/api/src/routes/payouts.ts) and [`API_CONTRACT.md:480`](../architecture/API_CONTRACT.md).

**AND THE ONE DOOR IN THIS SYSTEM THAT ACTUALLY SERVES AN ELIGIBILITY SNAPSHOT SERVES IT INLINE, KEYED BY THE REQUEST ID, AND CARRIES NO SNAPSHOT ID.** `GET /admin/accounts/:accountId` is the contract's *"payouts with snapshots"* screen ([`API_CONTRACT.md:1121`](../architecture/API_CONTRACT.md)) and it is built at [`admin-source/account.ts:556-572`](../../apps/api/src/admin-source/account.ts): `payout_request_id: id` at [`:557`](../../apps/api/src/admin-source/account.ts) and `eligibility_snapshot: json(row, 'eligibilitySnapshot', at)` at [`:572`](../../apps/api/src/admin-source/account.ts), under a comment quoting the contract verbatim. **That is the existing, working, shipped answer to "how does a caller reach the proof", and it has never needed a second identifier.**

**AND NO ENDPOINT IN THE CONTRACT ACCEPTS ONE.** `eligibility_snapshot_id` occurs once in [API_CONTRACT](../architecture/API_CONTRACT.md) and it is a response field. It is never a path parameter, never a query parameter, and never a request field. **A client that stored it could not send it anywhere.**

### 3. The four shapes, each taken or refused in writing

#### 3.1 REFUSED: return `payout_requests.id` under a name that says `snapshot`

**THE STRONGEST ARGUMENT AGAINST IT IS NOT THAT THE VALUE IS A DUPLICATE. IT IS THAT THE ROUTE GENERATES IT ITSELF, ONE LINE ABOVE THE CALL.**

| Line | Code |
|---|---|
| [`payouts.ts:1168`](../../apps/api/src/routes/payouts.ts) | `const payoutRequestId = randomUUID();` |
| [`payouts.ts:1172`](../../apps/api/src/routes/payouts.ts) | `id: payoutRequestId,` inside the `PayoutRequestInsert` |
| [`payouts.ts:1201`](../../apps/api/src/routes/payouts.ts) | `const { eligibilitySnapshotId } = await tx.insertPayoutRequest(row);` |
| [`payouts.ts:1238`](../../apps/api/src/routes/payouts.ts) | `payout_request_id: payoutRequestId,` |
| [`payouts.ts:1250`](../../apps/api/src/routes/payouts.ts) | `eligibility_snapshot_id: eligibilitySnapshotId,` |

`PayoutRequestInsert.id` is a declared field of the insert shape ([`payouts.ts:493`](../../apps/api/src/routes/payouts.ts)). **So under this shape the port returns its own argument to a caller that already holds the value in a local variable.** It is not a read and it is not a decode. It is an echo, and the two wire fields would be equal on every response for the life of the contract.

**THAT IS WORSE THAN REDUNDANT, AND THE REASON IS THE MONEY PATH RATHER THAN TASTE.** A field named `eligibility_snapshot_id` asserts a separately addressable proof, which is precisely the thing [`0010`](../../packages/db/migrations/0010_payouts.sql) refuses to create in writing. **If a snapshot store is ever built, the two identifiers diverge and every client that stored the request id as a snapshot id is silently wrong**, holding a receipt that resolves to the wrong proof rather than to none. A wire field that says nothing is cheap; a wire field that teaches a false distinction is not.

**IT IS ALSO THE CLOSEST THING HERE TO THE MOVE THIS ROW FORBIDS.** *"An identifier synthesised to satisfy a type is a receipt for a decision nobody recorded, on the money path."* The echo is not a fabrication, but it is a value chosen to satisfy a type rather than to address a thing, and nothing in the corpus records the decision that these two identifiers are the same.

#### 3.2 REFUSED: mint a fresh uuid

**Refused for [ADR-287](ADR-287.md)'s stated reason, re-derived: it addresses nothing.** No endpoint accepts one (section 2), so a client that stores it holds a receipt for a proof it can never fetch.

**AND IT DOES NOT EVEN SURVIVE A SECOND READ.** A minted id is not written to any column, so the same request read again through `GET /payouts` or the admin drill-down produces a different value or no value. **The moment anyone tries to use it, this shape collapses into 3.3.** It is also the fabricated id row `289` forbids by name.

#### 3.3 REFUSED: a migration. Two sub-shapes, both refused, and NEITHER NEEDS A NUMBER

**(a) A separate snapshot table.** [`0010:70-73`](../../packages/db/migrations/0010_payouts.sql) argues against it in the migration's own words, and a merged migration is superseded rather than edited (constitution `E2`), so this is a supersession argument rather than an additive one. **And it buys nothing even if won**: the snapshot is one-to-one with its parent and written exactly once, so its primary key would be a second primary key for a single row, and the join it introduces is the exact mechanism `0010` names as the way the proof and the decision come to disagree.

**(b) An `eligibility_snapshot_id uuid` column on `payout_requests` itself.** Strictly worse than (a). A uuid stored on a row, addressing that same row's own `jsonb` column, is a second name for `id` with no referential meaning at all, plus a `NOT NULL` column that every writer on the money path must populate with a value nothing reads.

**SO NO MIGRATION NUMBER IS TAKEN AND NONE IS RESERVED.** Row `289` required that a needed migration be specified and nothing reserved, on [ADR-272](ADR-272.md)'s precedent. **None is needed**, and reserving a number against a shape this ADR refuses would be the reservation that outlives its reason.

#### 3.4 TAKEN: the field comes out, of the frozen contract and of the port shape

Six facts, each derived in section 1 or 2:

1. **The snapshot has no identity of its own by design**, and two corpus sources say so.
2. **The identifier that addresses it already exists and is already on the response**, as `payout_request_id`.
3. **The only door that serves a snapshot serves it inline, keyed by that identifier**, and carries no snapshot id.
4. **No endpoint accepts an `eligibility_snapshot_id`**, so no client can use one under any shape.
5. **Nothing consumes it.** Outside `payouts.ts` and its own test, no line in `apps`, `packages` or `scripts` mentions either spelling.
6. **Its only test is a tautology.** The fixture returns `` `snap-${row.id}` `` ([`payouts.test.ts:369`](../../apps/api/test/payouts.test.ts)) and the assertion checks the body equals `` `snap-${payout_request_id}` `` ([`:499`](../../apps/api/test/payouts.test.ts)). **That test proves the route forwards what a fixture invented. It has never proved a supplier exists, because there has never been one.**

**WHAT IT COSTS, STATED RATHER THAN MINIMISED.** A document inside the corpus FROZEN on 2026-08-14 moves. [API_CONTRACT](../architecture/API_CONTRACT.md) carries `status: approved` and no document in this corpus carries `status: frozen`; the freeze is the corpus-level state [STATE](../STATE.md) declares, under which *"changing a frozen document requires an ADR, not a commit"*. **This is that ADR, and it is UNSIGNED.** A founder who disagrees overturns section 3.4 in a sentence and the contract line is restored by one edit.

**AND THE REMOVAL BREAKS NO CLIENT, WHICH IS THE FACT THAT MAKES IT CHEAP RATHER THAN EXPENSIVE.** `usePayoutBackend` is a key of `BLOCKED` ([`wiring.test.ts:147`](../../apps/api/test/wiring.test.ts), entry at [`:561`](../../apps/api/test/wiring.test.ts)) and the live count assertion reports `{ declared: 24, wired: 10, blocked: 14 }` ([`wiring.test.ts:1402-1409`](../../apps/api/test/wiring.test.ts)). **`POST /accounts/:accountId/payout` has never served this field with a value produced by anything but a test fixture**, because nothing implements `PayoutTx` ([ADR-287](ADR-287.md) section 1). **Removing a field no deployment has ever sent is not a wire break; it is the corpus ceasing to promise something it cannot deliver.**

### 8. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

**This is a ruling on the money path and what is owed is a read of the REFUSALS rather than of a diff.** The diff is one deleted contract line and one added note; the decision is section 3, and any of its four arms can be overturned in a sentence.

- **Decision:** `eligibility_snapshot_id` **is removed from `PayoutResponse` in [API_CONTRACT](../architecture/API_CONTRACT.md) section 6**, and `PayoutTx.insertPayoutRequest` **is ruled to return `Promise<void>`**. The eligibility snapshot is addressed by `payout_request_id`, which the response already carries, because the snapshot has no identity separate from its parent by [`0010`](../../packages/db/migrations/0010_payouts.sql)'s own written design.
- **Alternatives considered:** returning `payout_requests.id` under a snapshot name (**refused**, section 3.1: the route generates that id one line above the call, so the port would return its own argument, and the name asserts a resource `0010` refuses to create); minting a uuid (**refused**, 3.2: addresses nothing and does not survive a second read); a migration, as a table or as a column (**refused**, 3.3: contradicts `0010`'s stated reasoning, is an `E2` supersession, and buys a second primary key for one row).
- **Consequences:** slice 6's stop condition loses its return-value clause (4.3). Seven lines in `payouts.ts` and `payouts.test.ts` are **owed** and specified (4.2), to a row whose fence reaches them, and **that row should run before slice 3**. Nothing about the stored snapshot changes. **No migration number is reserved**, so the refusal leaves no residue.

**WHAT A FOUNDER READ ADDS AND THIS ENTRY CANNOT.**

**THE FIRST THING TO DECIDE IS WHETHER THE CONTRACT SHOULD MOVE AT ALL, BECAUSE THAT IS THE HALF THIS ENTRY CANNOT PROVE.** Sections 1 and 2 are findings and every one resolves by opening the file. **Section 3.4 is a judgement**: that a field with no supplier, no consumer, no endpoint and no test but a tautology is better deleted than satisfied. The opposite judgement is defensible and is cheaper today: shape 3.1 costs one line and nobody would notice for a year. **This entry refuses it because the year is the problem**, and because the field would then be a name in a frozen contract for a resource the schema is on record refusing to create.

**THE SECOND IS SECTION 5.1, WHICH THIS RULING DELIBERATELY DOES NOT ANSWER.** The trader can see that a payout was approved and cannot see the evaluation behind it through any endpoint in the contract. **That is a bigger question than this field and it is not made worse by this ruling**, because the identifier being removed was never fetchable. A founder who wants it answered gives it a row; it is not folded in here.

**THE THIRD IS SECTION 4.2's ORDERING.** The seven owed lines are put ahead of slice 3 rather than inside slice 6 on the argument that a declared return value nothing can supply is an invitation to invent one. **The cost of taking that advice is one extra small session.** The cost of not taking it is that slices 3, 4 and 5 all pass through a file whose port still promises this value.

**AND ONE THING THIS ENTRY IS NOT A JUDGEMENT ABOUT.** Sections 1 and 2 are citations, not preferences. **The re-derivation moved five line numbers and changed no finding**, which is the result worth recording either way: it is what the row was told to check, and checking it is what caught a repair that was applied to half of one citation.
