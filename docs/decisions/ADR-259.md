## ADR-259: the probe is run, the seed that reported it unwatched cannot be installed at all, and the gap that is real is that nothing binds scope to code (2026-08-30, status: proposed)

**Row `259` sent one session to close a gap [ADR-247](ADR-247.md) section 7 named: that *"the suite holds the TypeScript copy of the scope and not the migration's own, so the two can diverge and only one side is watched"*, with the instrument being [`probe_ledger_constraints.sql`](../../scripts/db/probe_ledger_constraints.sql)'s `LEDGER-K3` block, said to need *"a running PostgreSQL that `CI-02` does not have"*. THE ROW'S FIRST INSTRUCTION WAS TO ESTABLISH, BY READING, WHETHER `CI-02` CAN BE GIVEN A POSTGRESQL SERVICE. IT DOES NOT NEED ONE. THE PROBE IS ALREADY RUN, ON EVERY PUSH, AGAINST A REAL DATABASE, IN A DIFFERENT JOB.**

**[`corpus.yml`](../../.github/workflows/corpus.yml)'s `migrations` job is `CI-06h`. It declares a `postgres:16` service, applies every migration forward-only from empty under `ON_ERROR_STOP`, and then runs `probe_ledger_constraints.sql` against the result.** `LEDGER-K3` has therefore read the migration's own copy of the eighth code's scope on every push since [ADR-187](ADR-187.md) merged. The claim is TRUE of `CI-02` and FALSE of CI, and the inference from one to the other is the whole of the gap the row was dispatched to close.

**AND THE SEED THAT REPORTED THE COPY UNWATCHED CANNOT BE INSTALLED.** `('withdrawals_in_flight', 'liability', 'identity')` in [`0056`](../../packages/db/migrations/0056_eighth_ledger_code.sql) violates `ledger_accounts_scope_identity` and the migration set **fails to apply**. A green vitest run against that seed is not evidence that a copy is unwatched; it is evidence that vitest has no database.

> **THE TREE IS NOT DEFECTIVE, [ADR-187](ADR-187.md)'s RULING STANDS, AND [ADR-247](ADR-247.md)'s CONCLUSION DOES NOT. What is left after both halves are removed is a gap that is REAL, LARGER, and in a different place: `ledger_accounts` binds a row's KIND to its CODE and binds NOTHING about its SCOPE.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `259`, session **450**, dispatched as `claude/only-one-copy-is-watched`. **No migration number is taken, reserved or spent.** The highest on disk is `0074`. **`RI-24` IS TAKEN** and its row is written in the same commit as the check, from the check.

- **MONEY PATH BY WHAT IT GUARDS: the ledger is the record of what Merit owes whom.** The [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) read is **OWED** on this diff and nothing here discharges it. ### 2. Why [ADR-247](ADR-247.md)'s seed proves nothing, executed rather than reasoned about

[`0009:62-66`](../../packages/db/migrations/0009_ledger.sql) installs `ledger_accounts_scope_identity`, read here from `pg_get_constraintdef` on a `0074` database rather than from the DDL:

```
CHECK (((scope = 'identity' AND identity_id IS NOT NULL)
     OR (scope = 'firm'     AND identity_id IS NULL)))
```

[`0056:311-312`](../../packages/db/migrations/0056_eighth_ledger_code.sql) seeds `INSERT INTO ledger_accounts (code, kind, scope)` with **no `identity_id` column at all**. Changing that row's third value to `'identity'` therefore inserts a row with `scope = 'identity'` and `identity_id IS NULL`, which the constraint refuses.

**MEASURED.** The migration set was copied to a scratch directory, the one literal changed, and the copy applied forward-only from empty into a fresh database:

```
APPLY FAILED AT: 0056_eighth_ledger_code.sql
ERROR:  new row for relation "ledger_accounts" violates check constraint
        "ledger_accounts_scope_identity"
DETAIL:  Failing row contains (..., withdrawals_in_flight, liability, identity, null, ...)
```

**So that seed does not reach `LEDGER-K3`; it does not reach the probe at all. It fails `CI-06h`'s FIRST step**, *"Apply migrations in order"*, before any assertion runs. **A seed the schema cannot hold is not a divergence, and a suite staying green on one is not a suite failing to watch.**

### 3. The gap that is real, and it is seven codes wide

`ledger_accounts` carries `ledger_accounts_kind_matches_code`: a `CASE` over all eight codes closed with `ELSE false`, which is [ADR-186](ADR-186.md)'s work and which binds a row's **kind** to its **code** in the database.

> **THERE IS NO EQUIVALENT FOR SCOPE. `ledger_accounts_scope_identity` binds scope to whether `identity_id` is null. NOTHING binds scope to code.**

**MEASURED, one INSERT per code inside a rolled-back transaction on a `0074` database:**

```
ACCEPTED WRONG SCOPE: firm_treasury=IDENTITY  psp_clearing=IDENTITY
  fees_revenue=IDENTITY  reserve=IDENTITY  trader_withdrawable=FIRM
  trader_wallet=FIRM  promotional_credit=FIRM  withdrawals_in_flight=IDENTITY
REFUSED: (none)
```

**The database accepts a wrong-scope row for all eight codes.** `LEDGER_ACCOUNT_SCOPE` is what [`firmAccount`](../../packages/ledger/src/accounts.ts) and `identityAccount` refuse at COMPILE time; a row the database holds against it is a position the library cannot name.

**And the readers that do exist are HAND COPIES rather than comparisons.**

| Reader | What it holds | Coverage |
|---|---|---|
| `LEDGER-K3`, [`probe_ledger_constraints.sql:252-285`](../../scripts/db/probe_ledger_constraints.sql) | the literal `scope = 'firm'` for `withdrawals_in_flight`, and zero identity-scoped rows in it | **1 code of 8** |
| the provisioning block, [`probe_ledger_constraints.sql:54-69`](../../scripts/db/probe_ledger_constraints.sql) | the SQL array `ARRAY['promotional_credit','trader_wallet','trader_withdrawable']` | the trigger's output, **as a third copy** |
| [`identity-provisioning.test.ts`](../../packages/ledger/test/identity-provisioning.test.ts) | `0054`'s TEXT | the migration file, not the database |

**Each of those writes the answer out again.** [ADR-247](ADR-247.md) was worried that two copies of one fact can drift and only one is watched; the tree in fact holds **four**, and the two on the database side are as capable of drifting from `LEDGER_ACCOUNT_SCOPE` as the migration was. **The instrument this entry adds holds NO copy.**

### 9. Where this entry is most likely wrong

**THE SCOPE-PER-CODE CONSTRAINT IS THE OBVIOUS REPAIR AND IT IS NOT TAKEN.** A `CHECK (CASE code WHEN 'trader_wallet' THEN scope = 'identity' ... ELSE false END)` on `ledger_accounts` would make every finding in section 3 unrepresentable rather than merely observed, in the same shape [ADR-186](ADR-186.md) gave `kind`, and a reader who holds that a database should refuse a wrong row rather than have a script notice it afterwards is **right**. Three things are said against taking it here and none of them is that it is wrong. It is a migration, and row `259` reserves no migration number. It supersedes a merged constraint on the money path, which is an `E2` read this session cannot discharge. **And it would still leave the comparison unwritten**, because a CHECK is a fifth hand copy of the same map: it would refuse the row and it would never once read `LEDGER_ACCOUNT_SCOPE`. **The honest position is that the constraint and this check are complements and the constraint is the larger of the two.** It is named here as owed.

**AND THE COMPARISON IS ONLY AS GOOD AS THE ROWS THAT EXIST WHEN IT RUNS.** It reads `ledger_accounts` on a freshly migrated database, which holds three firm seeds and the three positions its own probe identity opens. **A wrong-scope row written by APPLICATION code at runtime is invisible to it**, because CI's database has no application traffic. `LEDGER-K3`'s second half has the same limit and states it in the same terms. The reader that would close it is a runtime invariant over the production table, which is `INV-M5-15`'s neighbourhood and is not built.

**AND SECTION 4's CLAIM THAT THIS IS `OI-07`'s FIFTH IS A COUNT OVER RECORDED OCCURRENCES**, taken from `CI-06s`'s own comment, which records four. If a session recorded an occurrence somewhere this entry did not read, the number is low rather than high. **The two files are on disk and were unpinned, and that half is measured.**
