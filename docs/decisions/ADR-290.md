## ADR-290: two fields with no column. `failure_note` is a RULED ABSENCE with its column and its writer both specified and neither written, and `timeline`'s source is NAMED as `events` and is EMPTY because that table has no producer  (2026-08-30, status: proposed)

**[ADR-287](ADR-287.md)'s finding `F4` said `PayoutListItem` declares ten fields, eight resolve off `payout_requests` columns and two do not. THE COUNT WAS RE-DERIVED HERE FROM THE DECLARATION AND THE DDL RATHER THAN RESTATED, AND IT HOLDS: TEN, EIGHT, TWO.** `payout_requests` carries **TWENTY-NINE** columns, counted mechanically off the two files that declare them, and neither `failure_note` nor any history column is among them. **Both of the two now have an outcome, and they are different outcomes for different reasons.**

**`failure_note` IS A RULED ABSENCE AND IT IS AN HONEST ONE RATHER THAN A PUNT**, because no `payout_requests` row on this tree can reach the only status the field describes. **`timeline` HAS A NAMED SOURCE, `events`, AND THE SOURCE IS EMPTY**: no `src/` file in any deployable constructs an event writer, so the correct projection of that relation is the empty array, and serving `[]` is the projection rather than a stub standing in for one.

**THE PROJECTION THIS ROW REFUSED IS THE ONE AN IMPLEMENTER WOULD HAVE REACHED FOR FIRST, AND SECTION 3.2 IS WHY.** `payout_requests` looks like it carries a history because it carries four state timestamps. **Two of the four are NULLED BY CONSTRAINT the moment the row leaves the state they record**, so a timeline folded from this table shows a settled payout that was held for forty hours with no hold in it. That is a partial history that reads as a complete one, and it is worse than an empty one.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `290`, session **481**, branch `claude/two-fields-with-no-column`. **[ADR-287](ADR-287.md) section 7, slice 2.** **RULING ONLY: NO `src/` LINE, NO MIGRATION, NO `RI-nn` MINTED**, and `RI-32` stays reserved to row `291`. `apps/api/src/**` and `packages/db/**` are untouched and were read only.

- **NOTHING IS WIRED AND NO COUNT MOVES: TEN WIRED OF TWENTY-FOUR DECLARED, FOURTEEN BLOCKED.** Derived here rather than carried: `wired` is the set of ports `start.ts` calls ([`wiring.test.ts:138`](../../apps/api/test/wiring.test.ts)) and `start.ts` makes **ten** such calls, eight `use` and two `set`; `BLOCKED` ([`wiring.test.ts:147`](../../apps/api/test/wiring.test.ts)) carries **fourteen** keys and `usePayoutBackend` is one of them. ### 2. `failure_note`. RULED ABSENT IN v1, AND THE ABSENCE IS PROVABLE RATHER THAN CONCEDED

#### 2.1 The measurement

**`grep -rn failure_note packages/db/migrations` returns ZERO lines.** So does `grep -rn 'failure' packages/db/migrations` restricted to column declarations: every hit in that file set is prose inside a `--` comment. **The corpus already knew.** [API_CONTRACT:1360](../architecture/API_CONTRACT.md): *"The trader-readable failure note is not written by this endpoint and no column holds it. `GET /payouts` types `failure_note: string | null` and `payout_requests` declares no such column; the note's storage is **unresolved** and is not this row's to decide."*

**IT IS THIS ROW'S TO DECIDE, AND THE DECIDING FACT IS THAT THE FIELD DESCRIBES ONE STATUS AND NOTHING CAN PRODUCE THAT STATUS.**

#### 2.2 The field describes `failed` and nothing else

Of the five members of `payout_status`, four are states in which nothing has failed. `failed` is the fifth, and [STATE_MACHINES:138](../architecture/STATE_MACHINES.md) defines it: *"Enforcement decided on a frozen request, with an exported evidence pack. **Rail exhaustion is not a path here**: it belongs to `wallet_withdrawals` with the rest of the external leg"*, and what the trader sees is *"honest status plus what happens next"*, which is this field.

**TWO EDGES REACH IT AND BOTH ARE ENFORCEMENT ACTS**, [STATE_MACHINES:146](../architecture/STATE_MACHINES.md) and [`:151`](../architecture/STATE_MACHINES.md): `held_pending_review --> failed` on `G-HOLD-ENFORCED`, and `frozen --> failed` on `G-FREEZE-ENFORCED`.

**SO ONE SENTENCE OF [M04:281](../plans/M04-trader-portal.md) DOES NOT REACH THIS FIELD, AND AN IMPLEMENTER WOULD HAVE ASSUMED IT DID.** That row reads *"`payout.approved`, `payout.settled`, `payout.transfer_failed` | The status timeline. `transfer_failed` gets a truthful note and a visible retry"*. **A rail exhaustion never sets `payout_requests.status = 'failed'`**; it belongs to `wallet_withdrawals`, per the line above and per [ADR-028](ADR-028.md)'s retirement of `transferring` from this table. M04's truthful note is a note on the **external leg**, and `PayoutListItem.failure_note` is a note on an **enforcement**. Reading the two as one field is how a note about a bank retry would come to be shown beside a closure for cause.

#### 2.3 Three candidate suppliers, all refused, each with its reason

| Candidate | Refused because |
|---|---|
| `admin_actions.reason` ([`0017:83`](../../packages/db/migrations/0017_events_and_audit.sql), `NOT NULL`), written by the enforce endpoint | **It is admin reasoning and the corpus excludes admin reasoning from trader projections in terms.** [API_CONTRACT:444](../architecture/API_CONTRACT.md): *"Excluded from the trader projection: detector internals, flag evidence, admin reasoning, other identities' ids."* The portal renders this field **VERBATIM** ([`view.ts:43`](../../apps/portal/src/app/payouts/view.ts): *"`not_frozen.reason` and `failure_note` are rendered VERBATIM. Both are server-composed trader-safe sentences"*), so a value composed for an audit trail would reach a trader unedited |
| `payout_requests.hold_tos_clause` and `hold_reason` ([`0031:51-52`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)) | **Both are NULL by the time the field is read.** `payout_requests_hold_is_complete` ([`0031:62-72`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)) is a biconditional on `status = 'held_pending_review'`, so all five hold columns are NULL on any row whose status is `failed`. [API_CONTRACT:1358](../architecture/API_CONTRACT.md) states the same mechanism from the other side: *"`enforced_hold` is read before the write for the same reason `released_hold` is: the same biconditional NULLs all five columns on the way to `failed`"* |
| `POST /admin/accounts/:accountId/note` ([API_CONTRACT:1144](../architecture/API_CONTRACT.md)) | Account scoped, not payout scoped, and *"attached to the timeline; audited like any other action"*. #### 2.4 What is owed, specified and NOT written

**A COLUMN IS OWED AND THIS ROW DOES NOT TAKE IT.** No migration number is claimed or reserved.

```
ALTER TABLE payout_requests
  ADD COLUMN failure_note text NULL;
```

with the completeness rule stated so the row that writes it does not have to re-derive it: **the note is permitted only on `status = 'failed'` and forbidden on every other status**, which is `payout_requests_freeze_is_complete`'s and `payout_requests_hold_is_complete`'s shape one column wide. It must **not** be made `NOT NULL` on `failed`, because that would make the enforce write unperformable until the second half below lands, which is exactly the trap `hold_tos_clause` set for the hold branch ([ADR-287](ADR-287.md) section 4).

**`failed` IS TERMINAL** ([STATE_MACHINES:89](../architecture/STATE_MACHINES.md), `failed --> [*]`), so this column is written once and never nulled on exit. It is the only one of `payout_requests`'s state annotations of which that is true, and it is why a column is the right shape here where a column was the wrong shape for `eligibility_snapshot_id` ([ADR-287](ADR-287.md) finding `F2`). **`0010`'s own argument against a second table ([`0010:70-73`](../../packages/db/migrations/0010_payouts.sql)) is an argument FOR this column**, not against it: written once, always read with its parent, must never drift from it.

**AND A SECOND THING IS OWED, WHICH IS THE HALF AN IMPLEMENTER WOULD DISCOVER AFTER WRITING THE MIGRATION.** **No endpoint accepts the value.** `PayoutEnforceRequest` ([API_CONTRACT:1341-1345](../architecture/API_CONTRACT.md)) declares `reason`, `tos_clause` and `evidence_pack_id`, and **none of the three is a trader-directed note**; `PayoutEnforceResponse` ([`:1346-1352`](../architecture/API_CONTRACT.md)) does not return one either. **The `frozen --> failed` edge has no endpoint at all**: `POST /admin/accounts/:accountId/freeze` and `/unfreeze` ([API_CONTRACT:1127](../architecture/API_CONTRACT.md), [`:1133`](../architecture/API_CONTRACT.md)) act on an account, and no `G-FREEZE-ENFORCED` endpoint exists in the contract.

**THAT SECOND HALF IS OUT OF THIS FENCE AND IS NAMED RATHER THAN TAKEN.** This row's API_CONTRACT permission is `failure_note` and `timeline` on `GET /payouts` and nothing else; adding a field to `PayoutEnforceRequest` is an edit to a different frozen section and is a fence widening. **So the gap is two gaps and not one**, and a row that writes only the column produces a column nothing can fill.

#### 2.5 The ruling

**`failure_note` IS SERVED AS `null` BY v1's `listPayouts`, ON EVERY ROW, AND THE CONTRACT SAYS SO.**

**IT IS `null` BY CONSTRUCTION AND NOT BY OMISSION, WHICH IS THE WHOLE DIFFERENCE BETWEEN THIS AND A STUB.** No `payout_requests` row can be in `failed` on this tree. Both edges into it are enforcement acts on a request that already exists, `usePayoutBackend` is `BLOCKED` and nothing writes a `payout_requests` row at all, and [ADR-287](ADR-287.md) section 7 slice 8 rules the hold branch **unschedulable** until counsel drafts a clause vocabulary. **A field that is null on every row the endpoint can return is not being withheld.** When the column and the writer land, the field carries the note and this ruling is spent.

### 3. `timeline`. THE SOURCE IS `events`, AND `events` HAS NO PRODUCER

#### 3.1 The measurement

**No column and no history table.** `grep -rn timeline packages/db/migrations` returns only prose inside `--` comments; none of the twenty-nine columns of `payout_requests` is a state history, and no `payout_request_states` or equivalent table exists.

#### 3.2 THE FOLD FROM `payout_requests` TIMESTAMPS IS REFUSED, AND THIS IS THE PART THAT IS NOT OBVIOUS

The table carries four state timestamps: `approved_at` [`0010:89`](../../packages/db/migrations/0010_payouts.sql), `settled_at` [`:90`](../../packages/db/migrations/0010_payouts.sql), `frozen_at` [`:105`](../../packages/db/migrations/0010_payouts.sql), and `held_at` [`0031:47`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql). `failed` has none: `grep -rn failed_at packages/db/migrations` returns **zero** lines. So four of the five states appear to be foldable and one is not, which is where [ADR-287](ADR-287.md) stopped.

**TWO OF THE FOUR ARE DESTROYED ON EXIT, BY CONSTRAINT, AND THAT IS A FACT ABOUT THIS TABLE RATHER THAN ABOUT ANY IMPLEMENTATION.**

- `payout_requests_hold_is_complete` ([`0031:62-72`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)) is a **biconditional**: `status <> 'held_pending_review'` requires `held_at IS NULL`. So the instant a held request is released to `approved` or enforced to `failed`, **`held_at` must be NULL**. A settled payout that was held for forty hours carries no record that it was ever held.
- `payout_requests_freeze_is_complete` ([`0010:141-149`](../../packages/db/migrations/0010_payouts.sql)) is the same shape one state over: `status <> 'frozen'` requires `frozen_at IS NULL`. A payout frozen and then cleared to `settled` on `G-FREEZE-CLEARED` ([STATE_MACHINES:150](../architecture/STATE_MACHINES.md)) carries no record that it was ever frozen.

**SO `payout_requests` IS A CURRENT-STATE TABLE BY DELIBERATE DESIGN AND NOT A HISTORY THAT HAPPENS TO BE MISSING A ROW.** Exactly two of its five states survive into a terminal row, `approved_at` because nothing nulls it and `settled_at` because `settled` is terminal ([`payout_requests_settled_has_days`, `0010:152-157`](../../packages/db/migrations/0010_payouts.sql) makes it `NOT NULL` there).

**A FOLD OVER THE SURVIVING TIMESTAMPS IS THEREFORE REFUSED IN WRITING.** It would render a two-entry timeline on a payout whose real history had four entries, and it would render it **as if it were complete**, with no field on the shape able to say otherwise. The trader most entitled to see the hold, the one who was held, is the exact trader from whom the fold hides it. **A partial history that reads as a complete one is worse than an empty one**, and this corpus has already ruled the same shape twice: a predicate that stops matching is a gate that enforces nothing and fails no test ([`0031:80-81`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql), the `C-02` defect), and a synthesised value on the money path is a basis nobody computed ([ADR-287](ADR-287.md) section 3.2).

#### 3.6 The ruling

**`timeline`'s SOURCE IS `events`, PROJECTED ON `subject_kind = 'payout_request'` AND `subject_id = payout_requests.id`. IN v1 IT IS `[]`, BECAUSE THAT PROJECTION IS EMPTY, AND THE CONTRACT SAYS SO.**

**v1's `listPayouts` DOES NOT READ `events`.** A query against a relation nothing writes, carrying a name-to-state mapping nobody ruled, is code that has never once been true and that no seeded test can exercise honestly. It returns the literal empty array, and the contract states that it does.

**THREE THINGS ARE OWED BEFORE THE FIELD CARRIES ANYTHING, AND NONE IS `listPayouts`'s:**

1. **A producer.** Some deployable must construct an event sink and write in the same transaction as the state change, which is [EVENTS](../architecture/EVENTS.md) section 1's own rule and `TRANSACTION_EVENT_WRITER`'s stated purpose ([`events.ts:1260-1263`](../../apps/api/src/events.ts)).
2. **Two catalogue gaps closed.** `payout.settled` has no entry, and the `frozen` state plus the `G-FREEZE-ENFORCED` edge have no payout-request-addressable event anywhere, in the code catalogue or in [EVENTS](../architecture/EVENTS.md). **The second is a payload defect of exactly the shape [ADR-191](ADR-191.md) already ruled** for `payout.freeze_expiring` ([EVENTS:445](../architecture/EVENTS.md)): a fact about one trader's payout whose payload merely fails to name the column that would reach it, repaired at the producer by resolving from the `payout_request_id` the producer holds.
3. **A ruled `event_name` to `state` mapping**, which is a naming decision and not a transcription: `payout.hold_released` moves a request to `approved` and `payout.approved` also does, so two names produce one state token, and a mapping that emits both would show a released hold approving twice.

**A ROW THAT SERVES `timeline` FROM `events` WITHOUT ALL THREE IS INVENTING A TRADER-VISIBLE PAYOUT HISTORY**, which is the outcome [ADR-287](ADR-287.md) finding `F4` named and this ruling exists to prevent.

### 5. Findings this row was not sent for, recorded because the failure mode is silent

**What a founder read adds and this entry cannot.**

**THE FIRST THING TO DECIDE IS SECTION 3.2's REFUSAL, BECAUSE IT IS THE ONLY PLACE HERE WHERE A CHEAPER ANSWER EXISTS AND IS REJECTED.** Folding `approved_at` and `settled_at` into a two-entry timeline is four lines of code and ships something rather than nothing. **It is refused because the two constraints that null `held_at` and `frozen_at` make the fold silently partial on exactly the requests whose history matters most.** A founder who reads that trade differently would get a timeline sooner and a trader who was held would never see it.
