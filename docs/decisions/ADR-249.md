## ADR-249: the certificate card is rendered on fetch, stored nowhere, addressed by the code and signed by nothing, so the two remaining certificate ports wait on a renderer and no migration is owed (2026-08-29, status: proposed)

**Row `249` sent one session at the single absent artefact [ADR-246](ADR-246.md) collapsed three certificate ports into, and asked four questions about it: what renders the card, when, into what store, and how a URL for it reaches the row. All four are ruled here. The fourth is ruled in the negative and that is the whole of the schema answer: NO URL REACHES THE ROW, `certificates` needs no image-location column, and NO MIGRATION NUMBER IS RESERVED OR TAKEN.**

**AND THE QUESTION THE ROW ASKED TO BE RULED EXPLICITLY RATHER THAN INHERITED IS RULED: THE CARD CARRIES NO SIGNATURE AT ALL.** A static public object addressed by a 128-bit unguessable token needs no second credential, and [`PUBLIC_LOOKUP_ADDRESS`](../../packages/db/src/scoped-db.ts) is already this estate's standing assertion that `code` alone is the entire predicate on an unauthenticated read of this row. **That does not overturn [ADR-240](ADR-240.md); it removes the thing [ADR-240](ADR-240.md) was placing.** That entry answered *where does the URL signing key go*, conditional on there being one. This one answers *is there a key*, and the answer is no. Clause 8 stands untouched and applies unchanged the day something in this estate does need a signed URL.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `249`, session **439**, dispatched as `claude/the-certificate-has-no-image`. The row is **CONDITIONAL** on ruling, and it is taken.

- **NOT THE MONEY PATH.** No ledger account, no balance, no payout. `E2` is not owed. **NO MIGRATION IS RESERVED, TAKEN OR SPENT**, and section 4 is the ruling that none is needed rather than a report that none was written. Ships `proposed` with an **UNSIGNED** approval line.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That `certificates` carries **seventeen** columns and that **no migration of the 67 alters the table**, that every value the card renders is one of those columns, that `FM-M11-05`'s cache key names a column the table has not got, that `projectCertificate` hands the address function the code and no other field, that the image row is reached with the code and nothing else even when a signature is dressed onto its URL, and that `imageHandler` refuses a live lookup that rendered nothing, is **MEASURED**, by executing it. That `INV-M11-08` and [API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3 already answer *when* is **DERIVED**, at the file and line each claim names. What is **JUDGED** is that a cache is not a store (section 2.3), that the render version is derived rather than stored (section 2.4), that the card carries no signature (section 3), and that [ADR-246](ADR-246.md) section 2 clause 5's placement of the renderer is narrowed rather than upheld (section 2.1).

- **A DISPATCH PROMPT IS NOT A SOURCE.** [ADR-246](ADR-246.md)'s measurement was re-derived before anything was built on it, mechanically and in this session: section 1.

### 2. The ruling: four questions, four answers, and what each rejected option costs

#### 2.1 What renders it: whatever answers the image row, and NOT the worker's issuer

[ADR-246](ADR-246.md) section 2 clause 5 put the renderer *"with the ISSUER, which [M11](../plans/M11-certificates-social-proof.md) section 3.2 puts in the WORKER and which already talks to a Vault for the claim signature"*. **That clause is NARROWED here, and its own ground is what narrows it.** The ground is about the CLAIM SIGNATURE: the issuer holds the Vault relationship because `signature` and `signing_key_id` are written once, at issuance, into columns. **The card is neither signed nor issued.** It is drawn from the row every time somebody looks at it, so the property that makes the worker the right home for the signer makes it the wrong home for the renderer: **an issuer runs once per certificate, and a thing that runs once per certificate cannot re-render on fetch.** Putting the renderer there is not a placement choice, it is answer 2.2(a) arriving by a different door.

> **1. THE RENDERER SITS BEHIND `CertificateImageSource.lookup` ([`certificates.ts:996`](../../apps/api/src/routes/certificates.ts)), AND THAT IS A PORT RATHER THAN A PROCESS.** Whether the bytes are produced in `apps/api` or by a render service it calls is a deployment shape, both satisfy `INV-M11-08`, and **this entry deliberately does not choose between them**: the port's own shape already makes it the deployment's, which is [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md)'s posture. What this entry rules out is the third option, a producer that writes an artefact and walks away.
>
> **2. AND `apps/api` STILL RENDERS NOTHING TODAY**, which is [ADR-240](ADR-240.md) section 6's measurement and is untouched: `CertificateCard` is named in one file and it is the port's own declaration. **This entry lands no renderer and wires no port.**

#### 2.2 When: on fetch, and this is not a preference

**`INV-M11-08` states it in its own words** ([M11:57](../plans/M11-certificates-social-proof.md)): *"A rendered image is re-generated on fetch from the live row, and its URL is short lived"*, enforced by *"The image is never a static artifact Merit keeps serving after the row changed."* [M11:156](../plans/M11-certificates-social-proof.md) and [API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3 both repeat it, and section 6.3 adds the reason: *"this is the whole reason this endpoint exists rather than a static asset."* **So the row's first question has an approved answer already and the work here is to say what the alternatives cost, so that the answer is chosen rather than inherited.**

| When | What it costs |
|---|---|
| **(a) At issue**, into an object store | **REJECTED, and the corpus rejects it in a sentence.** Every object outlives the row state that produced it, so a revocation reaches a circulating image only as a DELETE against the store, which is a second write path with its own failure mode; an object that fails to delete keeps asserting a revoked claim indefinitely. `AS-M11-02` accepts that a SCREENSHOT cannot be recalled and builds the recovery on the code printed inside it. **It does not accept that Merit's own copy is a screenshot** |
| **(b) On first request**, cached forever | **REJECTED.** The same failure with a delay: the first fetch pins the render and every later state change is invisible to every later fetch. It is (a) with the write moved and nothing else changed |
| **(c) On a schedule**, a re-render sweep | **REJECTED.** The window in which a revoked card renders as valid becomes the sweep interval, set by a cron nobody reads, rather than the cache lifetime `cacheControl` already bounds at *"minutes, never days"*. And it re-renders the whole book to catch the rows that moved |
| **(d) On fetch**, from the live row | **RULED.** Its cost is named rather than waved past: **a render on a public unauthenticated path is compute an attacker can drive**, and `FM-M11-05` is that failure mode's own row. [API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3 has already accepted the consequence in writing, putting this surface OUTSIDE `INV-M11-05`'s constant-time clause because *"a render is orders of magnitude slower than a 404"*. The controls are the entropy, the cache in 2.3, and a rate limit that **is still owed and exists nowhere in this tree** |

> **3. AND THE ROUTE ALREADY ENFORCES IT, WHICH IS WHY THIS IS A RULING AND NOT A PLAN.** `imageHandler` ([`certificates.ts:1130`](../../apps/api/src/routes/certificates.ts)) throws when a non-deferred lookup carries no card, in words that name the invariant: *"a revoked certificate that does not render is the revocation failing to arrive."* **A stored-object design arrives at that line on the fetch that matters.** It is executed in [`certificate-card-home.test.ts`](../../apps/api/test/certificate-card-home.test.ts) rather than read.

#### 2.3 Into what store: none. A CACHE, and a cache is not a store

> **4. THE CARD LIVES NOWHERE DURABLE, AND THE DIFFERENCE BETWEEN A CACHE AND A STORE IS THE ONLY THING THIS CLAUSE SAYS.** A store is addressed, is the authority for what it holds, and outlives the thing that wrote it. A cache is none of those: **it may be emptied at any moment with no loss**, because the row plus the renderer reproduce its contents exactly. `FM-M11-05`'s remedy is a cache in exactly this sense, *"cache the rendered bytes keyed by `(code, row_version)`, so a re-render only happens when the row actually changed"*, and it is a performance control rather than a place the card lives.
>
> **5. THE KEY IS WHAT MAKES THE CACHE SELF-CORRECTING, AND THAT IS THE PROPERTY WORTH BUYING.** Keyed on the code alone, a state change needs somebody to remember to invalidate, and `INV-M9-04`'s page-revalidation row one table up in [`0020`](../../packages/db/migrations/0020_public_surface.sql) exists because *"an invalidation that is fire-and-forget is a cache that is USUALLY RIGHT"*. Keyed on the code AND the render version, **a state change MISSES the cache with nobody invalidating anything**, which is the same correctness bought without a second write path.

The cost of the rejected option, named: **a durable store buys a card that survives an outage of the renderer.** That is a real benefit and it is refused, because the thing it keeps serving during that outage is precisely the thing `INV-M11-08` exists to stop it serving. A 404 or a 503 during a render outage is honest; a card that is right until the moment it is most wrong is not.

#### 2.4 How a URL for it reaches the row: IT DOES NOT

**This is the schema question, and the answer is that the address is a FUNCTION rather than a value.**

> **6. `image_url` IS `origin` PLUS THE PATH THIS REPOSITORY ALREADY SERVES, DERIVED FROM `code` AT PROJECTION TIME.** `projectCertificate` ([`certificates.ts:861`](../../apps/api/src/routes/certificates.ts)) calls `links(row.code)` at [`certificates.ts:898`](../../apps/api/src/routes/certificates.ts) and hands it nothing else, so **no other field of the row can reach the address** even by accident. `CertificateBackend.links` ([`certificates.ts:646`](../../apps/api/src/routes/certificates.ts)) takes a code and returns both URLs, which is the same shape `verify_url` has been built on since [ADR-231](ADR-231.md).
>
> **7. `0020`'s SEPARATION OF `code` FROM `id` IS THE PRECEDENT THE ROW NAMED, AND IT POINTS THIS WAY RATHER THAN AT A COLUMN.** [`0020`](../../packages/db/migrations/0020_public_surface.sql) writes that `code` is *"DISTINCT FROM id so the public token can be ROTATED AFTER AN INCIDENT without rewriting the primary key"*. **A stored address would undo exactly that.** Rotating a code would leave a stored `image_url` naming the retired token, so the incident that the separation exists to survive would need a second column rewritten in the same transaction or the card would go on answering at the address the incident burned. An address derived from `code` rotates when `code` rotates, for free.
>
> **8. AND THE VERSION THE CACHE KEY NEEDS IS DERIVED, NOT STORED.** `FM-M11-05` names `row_version` and **`certificates` has no such column, no `version` and no `updated_at`**, measured. A stored counter costs a migration, a trigger or a discipline on every writer, and it is a second source of truth for *"did the rendering inputs change"* that is derivable from the row itself, which is `FM-M7-08`'s shape. **A digest over the value handed to the template is the same answer and cannot drift from what was drawn**, because it is computed from the drawn input rather than maintained beside it. The cost is one hash of a row already read, on a path that is about to render a PNG.

**SO THE TABLE NEEDS NOTHING.** Every value the card draws is already a column: `kind`, `claims` and `claims_schema_version` for `INV-M11-01`'s claim, `code` because `SD-M11-01` says the token *"appears in the image"*, `issued_at` for `INV-M11-11`, `revoked_at` and `revocation_class` for `INV-M11-07` and `INV-M11-08`, and `deferred_until` because a deferred claim does not render at all. [`certificate-card-home.test.ts`](../../apps/api/test/certificate-card-home.test.ts) asserts that partition **TOTAL over all seventeen columns**, so a column added tomorrow has to be classified by whoever adds it.

### 3. The signature question, ruled explicitly rather than assumed

**THE CARD CARRIES NO SIGNATURE, AND `image_url` IS AN ORDINARY PUBLIC URL.** The row asked for this to be ruled rather than inherited, and it is ruled on four grounds, in the order they arrived.

> **9. THE CODE IS ALREADY THE ONLY CREDENTIAL ON THIS SURFACE AND THE ESTATE HAS RULED IT SUFFICIENT.** `PUBLIC_LOOKUP_ADDRESS` is `{ certificates: ['code'] }` ([`scoped-db.ts:1697`](../../packages/db/src/scoped-db.ts)), and [`packages/db/src/index.ts:148`](../../packages/db/src/index.ts) states what membership MEANS: *"an assertion that the named column is unguessable, because the address is the entire predicate and there is no tenancy conjunct to fall back on."* [ADR-231](ADR-231.md) built that door and [ADR-235](ADR-235.md) gave it a real 128-bit mint. **`GET /verify/:code` discloses MORE than the card does**: [API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3's `VerifyResponse` carries the claim, the disclosure, the published sentence AND `signature` with `signing_key_id` beside it, where the card renders a strict subset of that and never the signature. It runs on the code alone today. A second secret guarding the strictly smaller disclosure is a control that does not know why it is there.
>
> **10. THE SIGNATURE HAS NOWHERE TO RIDE, WHICH [ADR-240](ADR-240.md) MEASURED AND THIS ENTRY DOES NOT REDISCOVER.** [API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3: *"the path token only, no query, no body."* [`certificate-links.test.ts`](../../apps/api/test/certificate-links.test.ts) already executes that from the CALLER's side, asserting that a fetch dressed with signature-shaped query parameters is answered identically to a bare one. [`certificate-card-home.test.ts`](../../apps/api/test/certificate-card-home.test.ts) adds the PORT's side: the same dressed fetch reaches `lookup` with the bare code, so a signature that ever started travelling on this path fails a test at the boundary rather than at the response.
>
> **11. THE ONE THING A SIGNATURE WOULD BUY IS AN EXPIRY, AND AN EXPIRY BUYS NOTHING HERE.** A short-lived URL stops a shared link from working later. **The code beside it does not expire**, `GET /verify/:code` does not expire, and `certificates.code` is `text NOT NULL` under `certificates_code_uq` with no lifetime of any kind. So an expiring `image_url` inconveniences the holder of a link and stops nobody: whoever has the URL has the code, and the code opens the verify page for as long as the row lives. **The real revocation control is the re-render**, which is 2.2 and is `AS-M11-02`'s own answer.
>
> **12. AND THE PRICE DOES NOT FALL WHEN THE BENEFIT GOES TO ZERO.** [ADR-240](ADR-240.md) section 5 priced a URL signing key at key storage in a process that terminates unauthenticated public requests, a rotation calendar M11 section 3.3 wrote for a different key, and a blast radius in which an application compromise mints valid card URLs for every code in the book. **That price is unchanged. What changed is that nothing is being bought with it.**

**SO THE LINE THAT IS WRONG IS [API_CONTRACT](../architecture/API_CONTRACT.md) SECTION 6's `image_url: string; // signed, time-limited`, AND ITS ECHO IN SECTION 6.3's LIST ITEM.** It is **NOT REPAIRED HERE.** That document is `approved`, it was not in row `249`'s fence, and widening a fence to finish is the move this repository refuses. It is reported in section 7 and in the pull request, and it is the same tension [ADR-240](ADR-240.md) section 7 and [ADR-246](ADR-246.md) section 6 both reported and both declined to repair, now with a ruling behind it saying which of the two sentences should survive.

**NO REAL BUCKET NAME, NO REAL HOSTNAME, NO REAL KEY AND NO SECRET IS WRITTEN INTO THIS REPOSITORY** ([ADR-012](ADR-012.md)). The word `origin` above is a role and not a value, and no environment variable is named: section 5 says why.

### 9. Consequences

- **M11's card slice starts from an answer instead of from four questions.** Where the renderer runs, when it runs, what it writes and what addresses it are ruled, and each rejected option has its cost written down beside it.
- **The schema question [ADR-246](ADR-246.md) measured is closed in the direction that costs nothing.** `certificates` gains no column, no migration number is spent, and the reason is a property of `code` rather than an omission.
- **The second key is gone from the design rather than relocated.** Nobody has to store it, rotate it or reason about its blast radius, and [ADR-240](ADR-240.md)'s ruling about where such a key would live is left intact for the next thing that needs one.
- **A signature that ever starts travelling on the public card path fails a test**, rather than being noticed by whoever reads the route next.
- **A stored-card design now meets an executed refusal** at the route, at the cache key and at the column partition, instead of a paragraph.
- **The two `BLOCKED` entries name one absent thing between them**, which is the smallest either has been.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST IS THAT SECTION 3 REMOVES A CONTROL, AND REMOVING A CONTROL IS THE DIRECTION THAT DESERVES THE SLOW READ.** The argument is that the code is already the whole credential and an expiry buys nothing while the code beside it never expires. **The counter-argument is real and is stated here rather than left for you to construct**: a signed, short-lived `image_url` means a card URL scraped out of a Slack unfurl or a proxy log stops working, while a bare one works forever. Section 3 clause 11 answers that the same scraper has the code and the code opens the verify page anyway, so the URL's lifetime protects nothing the code does not already disclose. **If you want the image bytes to be harder to reach than the verify page**, that is a policy this entry does not have the standing to set, and it is the one input that would flip the ruling.

  **THE SECOND IS THAT SECTION 2.2 ACCEPTS A COMPUTE COST ON AN UNAUTHENTICATED PUBLIC PATH AND THE CONTROL FOR IT DOES NOT EXIST.** `INV-M11-05`'s rate limit has now been ruled owed three times, by [ADR-235](ADR-235.md), by [ADR-246](ADR-246.md) and here, and it exists nowhere in this tree. **Render-on-fetch is the approved answer and it is also the expensive one**, and the day the renderer lands without the limit, `FM-M11-05` is live on a surface anybody can drive. That ordering is a founder's to set and this entry can only report it.

  **THE THIRD IS THAT THIS ENTRY NARROWS [ADR-246](ADR-246.md) SECTION 2 CLAUSE 5, WHICH IS THREE DAYS OLD AND UNSIGNED.** That clause put the renderer in the worker with the issuer, and its own founder block named the choice as the thing a founder read would add. **This entry takes the other branch** and the ground is `INV-M11-08`.
