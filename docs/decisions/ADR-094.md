## ADR-094: a transcription reads a table AS OF THE LAST MIGRATION, and the drift assertion becomes a REPLAY whose vocabulary is one member wide and whose default is FAIL  (2026-08-24, status: proposed)

**[ADR-084](ADR-084.md) transcribes a table by comparing `schema.ts` against the table's `CREATE TABLE` body, and asserts separately that NO later migration changes a column on any registered table. Those two assertions are consistent only while the second one holds. On this tree it does not hold for 12 of the 111 tables, and three of them are [P4](../plans/P4-portal-and-site.md)'s own reads.** This entry rules how the transcription reads such a table.

**The answer is not a rule about three tables.** [ADR-092](ADR-092.md) made the owner the TABLE and the queue the TYPE CHECKER, so 91 unregistered tables will be transcribed by module sessions that never read this entry's argument and will only see its mechanism. **The mechanism is therefore the ruling, and section 4 states what it FORECLOSES rather than only what it chooses.**

- **Origin:** [P4](../plans/P4-portal-and-site.md) section 8, slice `P4-a`, dispatched as session **182**. [P4 section 5.4](../plans/P4-portal-and-site.md) is the measurement that created the slice, and it is itself a correction: P4's first pass used a single-line grep, `ALTER TABLE` statements in this set span lines, and the re-run with the suite's own algorithm found three P4 tables drifted where the first run found none.

- **Context:** [`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts) holds two assertions that together make the `CREATE TABLE` body a sound proxy for a table's current column set: the per-table set comparison, and *"no later migration changes a column on any of the seven"*. **The second is the load-bearing one and it is a REFUSAL, not a check** -- it does not verify the transcription of a drifted table, it declines to have one. [`schema.ts`](../../packages/db/src/schema.ts)'s own header says so: *"so the day one lands, the check fails rather than silently reading a stale CREATE."* **That day landed before this session, on 12 tables, and the seven registered ones are simply not among them.**

### 2. The ruling

> **1. A TRANSCRIPTION READS A TABLE AS OF THE LAST MIGRATION, NEVER AS OF ITS `CREATE TABLE`.** [`schema.ts`](../../packages/db/src/schema.ts) declares the column set the database has today, `CREATE TABLE` plus every later change, and there is no second reading of "the table" available to a transcribing session.
>
> **2. THE DRIFT ASSERTION STOPS READING ONE STATEMENT AND STARTS REPLAYING THE MIGRATION SET.** It folds each registered table's `CREATE TABLE` column set forward, in migration order, and compares the TypeScript declaration against the folded result.
>
> **3. THE FOLD'S VOCABULARY IS CLOSED, IT HAS EXACTLY ONE MEMBER, AND ITS DEFAULT IS FAIL.** `ADD COLUMN` is folded. **Every other column-changing shape -- `DROP COLUMN`, `ALTER COLUMN`, `RENAME` -- remains an offender that turns the suite RED**, exactly as all four do today. A statement the fold does not recognise is a failure and never a statement it skips.

**The refusal is not deleted, it is NARROWED, and that direction is the whole point.** Today a table with any later column change cannot be registered at all. After this entry a table with only `ADD COLUMN`s can be registered **and its full effective column set is compared**, which is a comparison that did not exist before; a table with any other shape is refused exactly as before. **No table is ever registered by being excused from the assertion.**

**Three mechanical properties come with it, because a fold that silently did nothing would leave every existing assertion green:**

- **The fold is asserted NON-VACUOUS.** The suite asserts that at least one registered table's effective column set is strictly larger than its `CREATE TABLE` set, and names them. Without this the replay could be dead code and the suite would report success.
- **The fold refuses its own mis-parse.** An `ADD COLUMN` clause that yields no column name, or one already present in the set, throws rather than being absorbed -- a mis-parse becomes red rather than a set that happens to agree.
- **Migration ORDER is checked rather than believed.** The fold applies files in `readdirSync().sort()` order and asserts that each table's `CREATE` file sorts before every `ALTER` that touches it. A statement folded onto a table that does not yet exist is a failure with the statement quoted.

---

### 3. Why `ALTER COLUMN` is NOT folded, and the reason is not that it is hard

**`ALTER COLUMN` cannot change a column-NAME set.** Folding it would be a no-op, so "the fold does not understand it" is false: the fold would understand it perfectly and have nothing to do. Both instances in the tree are `DROP NOT NULL`:

```
0029  ALTER TABLE otp_challenges ALTER COLUMN email_normalized DROP NOT NULL;
0032  ALTER TABLE trading_calendar ALTER COLUMN session_open_at  DROP NOT NULL;
0032  ALTER TABLE trading_calendar ALTER COLUMN session_close_at DROP NOT NULL;
```

**They change NULLABILITY, which [`schema.ts`](../../packages/db/src/schema.ts) transcribes as `.notNull()` and which this suite has never compared, on any of the seven, since [ADR-084](ADR-084.md).** The per-table assertion compares NAMES. So exempting `ALTER COLUMN` would register a table whose transcription is verified on every axis except the one the migration moved.

**It therefore stays a hard failure AS A PROXY REFUSAL, and this entry says so rather than letting a later reader mistake it for a parsing limit.** The cost is exactly two tables, `otp_challenges` and `trading_calendar`, and neither is P4's or any dispatched slice's.

**THE GAP THE PROXY STANDS IN FOR IS NAMED AND NOT CLOSED HERE.** Column TYPE and NULLABILITY are transcribed into `schema.ts` and asserted nowhere; that is true of all seven registered tables today and is not created by this entry. Closing it is a second comparison against `ddlColumnDefs`, it would turn the suite red on whatever it finds across seven already-merged money-path files, and **measuring that is its own session** -- which is [session 165](../sessions/2026-08-24-session-165.md)'s reasoning about a gate whose cost is unmeasured, applied to this one. **Until it exists, `ALTER COLUMN` refusing a table is the only thing standing where that comparison should be**, and deleting the refusal before writing the comparison would be trading a real control for nothing.

### 4. What this FORECLOSES

**[P4](../plans/P4-portal-and-site.md) section 11 rule 8 asks for this half, and [ADR-092](ADR-092.md) is why it matters more than the choice**: 91 tables remain unregistered and the sessions that register them will read the mechanism, not the argument.

1. **A PER-TABLE EXEMPTION LIST IS FORECLOSED PERMANENTLY.** There is no allowlist, no `skip`, no `// drifted, see ADR-NNN`. A table is registered with its full effective column set compared, or it is not registered. **This is the tempting shape and it is the one that ends with a registry of tables nobody compares**, which is [ADR-084](ADR-084.md) section 7's failure -- a transcription and an expectation agreeing because nothing else is looking -- reintroduced as a maintenance convenience.
2. **RECORDING THE DRIFT IN A COMMENT IS FORECLOSED.** [ADR-042](ADR-042.md) already ruled prose is not a control. A folded `ADD COLUMN` is compared; an unfolded shape is red. Neither outcome is a sentence.
3. **FOLDING A DESTRUCTIVE CHANGE IS FORECLOSED UNTIL AN ADR TAKES IT.** `DROP COLUMN` and `RENAME` have **zero instances in 47 migrations**, so a rule for them would be written against nothing, which is the defect [P4](../plans/P4-portal-and-site.md) section 8 names as *"a fence over files a ruling has not yet made possible"*. **The first one to arrive turns the suite RED and gets its own entry.** That is deliberate and it is the expensive-looking choice: a fold that quietly absorbed a rename would let a registered table's old column name vanish from the comparison while application code still names it, and the rename is the change most likely to have live readers.
4. **WIDENING THE FOLD BY ADDING A REGEX IS FORECLOSED.** The vocabulary is a closed set with a default of fail, the same shape as `ScopeClass`'s four classes at [`scope.ts:58`](../../packages/db/src/scope.ts): adding a member is an ADR, not a commit. **A fold whose default is skip is a fold that silently gets larger every time somebody writes a migration shape nobody anticipated.**
5. **`drizzle-kit generate` STAYS FORECLOSED**, and a replay does not reopen it. Reading the SQL to assert against it is not generating a schema from it; nothing is emitted and nothing is written back. The migrations stay the source and `schema.ts` stays the transcription, which is the inverse of the flow drizzle-kit exists to run.
6. **TAKING MIGRATION ORDER ON FAITH IS FORECLOSED.** Lexical filename order equals numeric order only while the four-digit prefix holds; the fold asserts the `CREATE`-before-`ALTER` relation per table rather than assuming it.
7. **"THE TABLE HAS DRIFTED, SO SOMEONE SHOULD SUPERSEDE THE MIGRATION" IS FORECLOSED, AND IT WAS NEVER AVAILABLE.** Migrations are sacred: once merged, never edited, only superseded (constitution `E2`). **A later `ADD COLUMN` is not a defect to be repaired into the `CREATE`; it is the table's history and the transcription reads the end of it.**

### 5. What it does NOT decide

- **Nothing about the write accessor.** Registering a table makes it readable and nothing else, unchanged from [ADR-092](ADR-092.md) section 9.
- **Nothing about which tables get registered, or by whom.** That is [ADR-092](ADR-092.md)'s and it is not re-argued.
- **Nothing about type or nullability comparison.** Section 3 names that gap, states why it is not closed inside a money-path slice that already carries a ruling and four registrations, and leaves the refusal standing in its place.
- **Nothing about the four tables no module plan names.** [ADR-092](ADR-092.md) section 9 already records them as unregistered, therefore unreachable, therefore safe.

### 6. Consequences

- **10 of the 12 drifted tables become registrable and 2 do not.** `otp_challenges` and `trading_calendar` stay refused, named here so their absence is a record rather than a gap. **Every one of the 99 undrifted tables is unaffected**: for them the fold applies nothing and the comparison is byte-identical to today's.
- **The drift assertion gets STRONGER on exactly the tables it used to refuse**, and unchanged everywhere else. A drifted registered table now has its full effective column set compared, which is a comparison that did not exist for any table before this entry.
- **`P4-a`'s registration is FOUR tables and not three, and the type checker is what says so.** `sessions.user_id` references `users(id)` and not `identities(id)`, so `sessions` reaches an identity only through `users`; `DerivedRule.via` is typed `TableKey`, so `users` cannot be named without being registered. **This is [ADR-092](ADR-092.md)'s "a session cannot know its own slice size before it runs" arriving in the direction it did not name**: not a table already registered by a sibling, but a table the registry's own totality forces into the slice. Reported as four of three rather than three of three.
- **A session registering a drifted table writes no more than one for an undrifted one.** The fold is in the suite, not in the transcription; the transcribing session declares the columns the table has and the replay is what checks it.
- **The suite's test count grows by one per registered table plus one fixed non-vacuity test**, so a registration that fails to add its per-table drift assertion still shows as a count that did not move. That signal exists only because [ADR-092](ADR-092.md) section 5's precondition landed in this same session, which is why the precondition went first.

---

### 7. Alternatives considered

- **Compare against the `CREATE TABLE` and exempt the drifted tables by name.** Rejected, and it is the cheap one: a registry whose drifted members are the ones nobody compares is the transcription-agreeing-with-itself failure with a list attached. Foreclosed by item 1 above rather than merely declined.
- **Refuse to register any drifted table and wait for a repairing migration.** Rejected on `E2`. There is no repairing migration: a `CREATE TABLE` is never edited, so the drift is permanent by construction and waiting is waiting forever. It would also leave [P4](../plans/P4-portal-and-site.md)'s central read `plan_versions` unreachable, which is the phase's second stated content.
- **Fold every shape, `DROP COLUMN` and `RENAME` and `ALTER COLUMN` included.** Rejected on the measurement rather than on caution: two of the three have no instance to rule against, and the third changes an axis the assertion does not compare. A vocabulary written for statements nobody has written is a vocabulary nobody has checked.
- **Read the effective column set from a live database instead of replaying the SQL.** Rejected. `CI-04` has no database ([P4](../plans/P4-portal-and-site.md) section 5.2: the `integration` job runs on bare `ubuntu-latest` with no `services:` block), so the check would not run in CI, and *"a check that cannot run is not a check that passed"* is already this repo's line in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs).
- **Put the fold in `schema.ts` and generate the column list.** Rejected on [ADR-084](ADR-084.md) section 4's measurement and on this file's own first line: the registry is declared and never derived. The fold verifies a human's transcription; it does not produce one.

### 8. Approval

- **Approval line: PENDING.** Left unsigned. **MONEY PATH**, and the `E2` line-by-line read is owed the four registrations this entry lands alongside it.

  **One checkable clause, carrying the direction it fails in:**

  > **The fold's failure direction is SILENCE, and the silence available to it is a replay that does nothing.** A fold that returned each table's `CREATE TABLE` set unchanged would leave every per-table assertion in [`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts) GREEN for any table whose transcription also omitted the later columns, because both sides would be wrong in the same direction -- which is [ADR-084](ADR-084.md) section 7's failure exactly. **Seed it: make the fold return the `CREATE TABLE` set and delete the three `ADD COLUMN` columns from `plan_versions` in [`schema.ts`](../../packages/db/src/schema.ts), and the per-table assertion must stay green while `the fold is not vacuous` turns RED and names the tables it expected to gain columns.** The loud direction is watched beside it: folding `ADD COLUMN` while the transcription omits `fee_back_repeats` fails the per-table assertion with the column named.

  **Cost if wrong:** every module session after this one registers drifted tables against a replay that verifies nothing, and the estate arrives at 111 transcribed tables whose later columns were never compared to any migration -- a strictly worse position than today's, because today those tables are refused registration and after a broken fold they are registered and silently unchecked.
