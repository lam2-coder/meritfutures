**THE STACK IS THE EVIDENCE AND THE EXIT CODE IS THE PROPERTY.** The frames run from the module's last statement through `main` into the adapter and out at the door, so the process is not merely exiting non-zero for some unrelated reason: it reached the first thing the job needs and refused there. `apps/worker/src/start.ts:43` is `await main().finally(closeWorkerDb)` at ES module top level, `apps/worker/package.json`'s `start` names that file, and neither `start.ts` nor `job.ts` contains a `catch`.

**A SUPERVISOR CAN NOW TELL THE TWO APART, WHICH IS THE WHOLE OF WHAT LINK 1 WAS.** [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md)'s opening is that a job that stops being scheduled is invisible; a process that exits 0 having done nothing is that failure one layer down. It does not do that any more.

### 3. Links 2, 3 and 4, re-derived

**Link 2 is real and is partial, and the adapter says so in its own header.** `postgresBatchPorts` in [`apps/worker/src/batch/adapter.ts`](../../apps/worker/src/batch/adapter.ts) is the one `BatchPorts` value under any `src/`. [`ports.ts:265`](../../apps/worker/src/batch/ports.ts) declares `BatchReadPort` with seven methods and [`:336`](../../apps/worker/src/batch/ports.ts) declares `BatchWritePort` with three; the adapter serves the calendar watermark, the calendar slice, the accounts with a live mark and the accounts with stored state, and refuses `loadAccountDay`, `accountDaysFrom`, `storedRuleStates`, `raiseReconciliation` and `raiseDivergence` by name.

**SO THE FOLD NEVER STARTS, AND THE ORDER OF CALLS IN `runNightlyBatch` IS WHY.** [`nightly.ts:293,294,296`](../../apps/worker/src/batch/nightly.ts) read the watermark, the calendar and the accounts, all served; [`:299`](../../apps/worker/src/batch/nightly.ts) is `await ports.read.loadAccountDay(...)`, inside the per-account loop, and it throws. On a database with one account carrying a live mark for the day, the run reaches the first account and stops. On a database with none, the run completes having written nothing. **Both outcomes leave `rule_states` empty**, and the second is worth naming because it is the one that exits 0.

**Link 3 did not move and the adapter is where it is visible.** [`adapter.ts:473`](../../apps/worker/src/batch/adapter.ts) composes the write port as `writeRuleStateVia({ ..., encodeEngineGates: UNWIRED_RULE_STATE_WRITER_IO.encodeEngineGates })`, and [`state-writer.ts:386`](../../apps/worker/src/batch/state-writer.ts) is `throw new RuleStateWriterUnwired('encodeEngineGates')`. **Over every `.ts` under every `apps/*/src` and `packages/*/src`, comment-stripped, the only `RuleStateWriterIo` declared is `UNWIRED_RULE_STATE_WRITER_IO`.** `ADR-239` slice A is unstarted, its home is still `packages/rules-engine`, and its price is still a module rather than a decision.

**Link 4 did not move either**, which is links 2 and 3 restated as a fact about the table.

### 5. RULING 2: `PayoutSubject` has a THIRD field, it has no producer, and the entry gains a clause for it

[`routes/payouts.ts:329`](../../apps/api/src/routes/payouts.ts) declares `PayoutSubject` with `accountId`, `state`, `plan` and `gates`. **Links 1 to 4 are the `state` field. `ADR-233` discharged the `plan` field. `gates` has been the third one the whole time and no revision of this entry has ever carried a clause about it.**

**THE CENSUS, AND ITS SCOPE STATED BEFORE ITS RESULT.** Over every `.ts` file under every `apps/*/src` and `packages/*/src`, with comment lines removed, the object key `hasPayoutInFlight:` appears in exactly two files:

| File | What it is |
|---|---|
| [`packages/rules-engine/src/types.ts`](../../packages/rules-engine/src/types.ts) | the interface DECLARING the field |
| [`packages/harness/src/trial.ts`](../../packages/harness/src/trial.ts) | raises one member on a value its own caller handed it, inside a Monte Carlo loop whose package declares the engine and the simulator and no database |

**NEITHER RESOLVES ONE FROM A ROW, SO THE ESTATE HAS NO PRODUCER.** Every constructed `ExternalGates` in the repository is a fixture or `scripts/demo/fold.ts`, and the non-vacuity half is run in the suite: the identical predicate is shown finding those.

**THE NEEDLE IS THE OBJECT KEY RATHER THAN THE TYPE NAME, AND THAT IS THE MEASUREMENT RATHER THAN A PREFERENCE.** Seven files name `ExternalGates` in code and five of them are the engine declaring, re-exporting or consuming the type, which is the opposite of producing one. A record literal must carry every member, so the key finds the construction and the annotation does not.

**THE FIVE FACTS ALL HAVE COLUMNS, SO WHAT IS MISSING IS A FUNCTION AND NOT A SCHEMA.** `payouts_frozen` is [`0002_identity.sql:50`](../../packages/db/migrations/0002_identity.sql) on the identity and [`0007_accounts.sql:83`](../../packages/db/migrations/0007_accounts.sql) on the account, resolved as the OR of the two, which [`admin-source/search.ts`](../../apps/api/src/admin-source/search.ts) already worked out and states; `recon_blocked` is [`0007_accounts.sql:87`](../../packages/db/migrations/0007_accounts.sql) and has no identity half; the KYC vocabulary is [`0001_extensions_and_enums.sql:29`](../../packages/db/migrations/0001_extensions_and_enums.sql); and R-38's in-flight leg reads `payout_requests`. **Every table involved is registered in [`scope.ts`](../../packages/db/src/scope.ts) and reachable on the payout transaction**, so this is not a second `ADR-233`.

**AND ONE LEG CANNOT BE A TOTAL MAP, WHICH IS THE PART A SLICE WOULD DISCOVER AT THE WORST MOMENT.** [`0001_extensions_and_enums.sql:47`](../../packages/db/migrations/0001_extensions_and_enums.sql) declares `account_status` with **seven** members. [`types.ts:891`](../../packages/rules-engine/src/types.ts) declares `AccountStatus` with **six**. The difference is `provisioning_pending`, in that direction only.

**THE ENGINE IS FAITHFUL AND THE GAP IS THE CORPUS'S.** [`M01:203`](../plans/M01-rules-engine.md) carries the same six, so nothing was dropped in transcription and widening the union would be a route amending a frozen plan.

**SO THE RESOLVER OWES A REFUSAL RATHER THAN A GUESS, and the precedent is in the same file.** [`routes/payouts.ts:316-317`](../../apps/api/src/routes/payouts.ts) records that `identities.status` is read against `= 'active'` "precisely so that a fourth arriving later fails CLOSED on this door rather than open". An `accountStatus` resolver that mapped `provisioning_pending` onto some nearby member would be a route deciding what a provisioning account is worth to the rules, on the money path, in a line nobody would ever read again. **It is registered here rather than ruled**, because the slice that writes the resolver is the one that should carry it, and because a ruling made now would be made without the resolver in front of it.

**BOTH HALVES ARE PREDICATES AND NOT SENTENCES**, in [`apps/api/test/rule-state-producibility.test.ts`](../../apps/api/test/rule-state-producibility.test.ts) section 5, which runs on every `CI-01` pass. Both were **measured in both directions**: a seeded `ExternalGates` literal in `routes/payouts.ts` fails the census, and `provisioning_pending` seeded into the engine's union fails the arity case. The tree was restored after each and `git status` reports it.

**AND `RI-15` CAUGHT A CITATION IN THIS SESSION'S OWN DIFF**, which is worth recording because the entry above argues that a drifting citation is worse than none. The new clause cited `0007_accounts.sql:83,87` once for two column names, and the runner correctly read the first number as the citation for the second name. It is split into two citations rather than argued with.

### 11. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS WHETHER THE `ExternalGates` RESOLVER MOVES TO THE FRONT OF THE QUEUE.** `ADR-239` sized three slices and ordered them; this entry says there are four and the new one is the cheapest, has no dependency on the other three, and is the only one whose absence would not have been noticed until a session had already spent the other three. **The argument against moving it up is that it unblocks nothing on its own**, which is true of slice A as well.

  **THE SECOND IS `provisioning_pending`.** This entry declines to rule what a provisioning account is to the engine and says the resolver's own session should carry it. **That is a judgement about sequencing and you may disagree with it.** The alternative is to rule it now, in the abstract, and the risk of ruling it now is that the answer looks obvious (refuse) right up until somebody notices that an account in provisioning has no `rule_states` row either, so the refusal may never be reachable and a refusal that cannot fire is a rule nobody tests.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The census is a search for a NAME and a KEY, and a producer that used neither would be invisible to it.** A function assembling the five facts into a value typed only by inference, at a call site that spread them, would not carry `hasPayoutInFlight:` as a literal key and would not be found. What is measured is that no such value exists in either spelling the repository has ever used; that no fifth spelling exists is a judgement about how this codebase writes records, not a finding.
