## ADR-139: the dispatch named four endpoints, `API_CONTRACT` has two of them free, and `AccountDetail.progress` is refused by the contract's own nullability  (2026-08-27, status: proposed)

**[ALLOCATION](ALLOCATION.md) row 139 reserved this number CONDITIONALLY, on the rule that *"transcription against an approved contract mints nothing until the contract and the schema disagree"*, with [ADR-113](ADR-113.md) as the precedent. The condition fired, and it fired somewhere the reservation did not look: the contract and the schema AGREE here, member for member, on every enum this session touched. What disagreed was the DISPATCH and the TREE.** Of the four endpoints session 251 was told to write, one is not in `API_CONTRACT` at all and one is already served by another module, where a second declaration would not be a merge conflict but a startup failure. This entry records both, and a third finding that is a genuine refusal rather than a subtraction: **the contract types five members of `AccountDetail.progress` as non-nullable and every one of them is a plan parameter**, which `0004_catalog.sql` forbids in application code.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `139`, session **251**, dispatched as `claude/routes-accounts`. **MONEY PATH: an account carries a balance and every field this endpoint renders is one.** The [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) line-by-line read is owed on every line this lands and is not discharged by this entry's own signature line.

- **The row's own citation is wrong and is amended in place.** It reads *"[API_CONTRACT](../architecture/API_CONTRACT.md) section 4"*. Section 4 is `## 4. Catalog (public)`; accounts is `## 6. Accounts`.

- **A DISPATCH PROMPT IS NOT A SOURCE**, and this entry exists because that instruction was followed. Every finding below is a `grep` or a run, quoted at the file it came from.

### 2. THE RULING

#### Clause 1. `POST /accounts/:accountId` is not written, and the reason is that it does not exist

STATE's operational reading of FREEZE: *"A behavior not in the corpus is not in scope. A behavior in the corpus is a commitment."* Writing this endpoint would mean inventing its request body, its response, its error set, its idempotency requirement and its rate limit, none of which any approved document states, and then having the invention read like a transcription because it sits beside two that are. **A missing row in a dispatch is a question for the founder and never a blank a session fills in.**

#### Clause 2. `POST /accounts/:accountId/reset` stays in `checkout.ts`, and this entry is the record that it was found there rather than missed

Finding 2 and finding 3. It is not one of the 33 contract endpoints that do not exist. **`accounts.ts` declares it nowhere**, and [`accounts.test.ts`](../../apps/api/test/accounts.test.ts) asserts both that the module does not declare it and that a module which did would refuse to boot.

#### Clause 3. `GET /accounts` is served end to end. `GET /accounts/:accountId` is written in full and REFUSES its `progress` block by name

The asymmetry is the finding, so the two endpoints have separate port methods rather than one. `GET /accounts` needs no plan parameter and no calendar: every field of `AccountListItem` is a column of `accounts`, a column of the latest `rule_states` row, a `plans` or `plan_versions` column through the firm door, or arithmetic over two of them.

`readProgress` raises `AccountsBackendUnwired` carrying findings 4 and 5, and the route answers **`503 service_unavailable`**. That is [`databaseAuthBackend`](../../apps/api/src/auth-backend.ts)'s shape: four of sixteen methods served, twelve refused by name, each with its own blocker. **A backend that returned plausible values would be a fixture serving real traffic**, and here the fixture would be a hardcoded `win_days.need`, which is precisely the value `0004_catalog.sql` forbids application code to hold.

#### Clause 4. The refusal is REPORTED and the fence is not widened to remove it

Two moves would serve `progress` and both were refused:

| Move | Refused because |
|---|---|
| Declare `@merit/rules-engine` in [`apps/api/package.json`](../../apps/api/package.json) | It is a `package.json` line plus a `pnpm-lock.yaml` delta, on the file this wave's eight route sessions all touch, and admitting the rules engine into the deployable that serves the whole public surface is an authority change. That is [ADR-120](ADR-120.md)'s argument about `@merit/db` and the reason sessions 218 and 220 each correctly declined to take it in passing |
| Register `trading_calendar` in `packages/db` | The dispatch's own instruction: *"If a read you need cannot be expressed through the scoped door, that is a finding: name it and stop, do not edit `packages/db` to make your route possible."* Registering it means superseding `0032`, and session **240** owns every migration number in flight |

**Neither is a large piece of work and that is not the point.** Both are somebody else's decision, and this entry is how the next session finds them already priced.

#### Clause 5. The four money fields come off ONE `rule_states` row, and `floor_open_cents` is never that row's floor

Finding 7. `balance_cents`, `floor_cents`, `withdrawable_cents` and `as_of_trading_day` are read from the row with the greatest `trading_day`, and `floor_distance_cents` is `balance - floor` in `bigint`. Section 6's own sentence is the requirement: *"the last closed day; EVERY NUMBER ABOVE IS AS OF THIS DATE."* Taking the balance from `daily_marks.closing_balance_cents` and the floor from `rule_states` would satisfy every field individually and break that sentence.

`floor_open_cents` is **not** this field. `SD-04` put two floors on the row on purpose and `0015` says why: `floor_cents` survived the day, `floor_open_cents` is the one the day was judged against, and *"a breach explanation reads 'your low was below the floor' while showing a floor the low was never compared to"*. The dashboard shows the floor that is open now.

#### Clause 6. An account with no `rule_states` row is ABSENT from the response rather than present at zero

A freshly provisioned account has no mark. The alternative to reporting absence is reporting a zero balance beside a zero floor, which renders as an account sitting exactly on its breach line. **A false statement about somebody's money is worse than a missing card**, so the list omits it and the detail is a 404.

#### Clause 7. Nothing in `accounts.ts` compares one identity with another

Section 1: *"A path parameter naming a resource the caller does not own returns 404 (not 403) on trader surfaces."* The handler holds no tenancy column, because `AccountRow` does not carry one. `scopedDb(identityId)` ANDs tenancy onto the address ([ADR-112](ADR-112.md)), so `rowAt('accounts', { id })` on a stranger's id reaches zero rows and returns `undefined`, which becomes the 404. **An ownership `if` written here would be a second control over one fact, and the failure mode of two controls is that the weaker one runs.**

#### Clause 8. The account is resolved BEFORE `progress`, and the order is a security property

Reversed, `readProgress`'s 503 would answer for every id. A real id answering 503 while a stranger's id answered 404 is the existence oracle section 1 forbids, delivered by a status code. **Resolved first, a stranger's id and a nonexistent id are both 404 and only the caller's own account reaches the refusal.**

This field is `state !== 'verified'`, which is the fail-closed direction, and the word is the enum's own |

### 4. THE APPROVAL LINE, UNSIGNED

> **A session holding identity A that names identity B's account gets ZERO ROWS and a 404, from `scopePredicate` and not from a comparison in the route, and no field of `AccountDetail.progress` is served by a number this repository invented.**

Both halves executed against a **real PostgreSQL 16** with all 47 migrations applied and two seeded identities, rather than against a fixture: identity A reading `GET /accounts` receives exactly its own account, identity A naming identity B's account id receives `404 not_found` with none of B's data in the body, identity B naming the same id receives it, and `SELECT count(*) FROM accounts WHERE identity_id = A AND id = B` returns **0**. The refusal's reason reaches the process log and no part of it reaches the wire.

**The `E2` line-by-line read is owed and is the founder's. NOT MERGED.**
