## ADR-221: the constitution's CSRF control, taken as an Origin check because the cookie the corpus trusted is scoped to a site and the attack is scoped to an origin  (2026-08-29, status: proposed)

**`MERIT_BUILD_MASTER_PROMPT.md` Appendix D section D2 rules `CSRF on cookie mutations` among the binding application controls, and nothing in this tree implemented it.** [ADR-219](ADR-219.md) found that by accident, from the other side of a fence it could not cross, and registered it as owed. **This entry discharges it.** The control is an `Origin` header check on every unsafe method, it mints no token, it needs no stored state, no migration, no environment variable and no client change, and it is watched refusing.

**THE THING THAT MADE THIS A LIVE GAP RATHER THAN A MISSING FORMALITY.** [`INFRA` section 2.1](../architecture/INFRA.md) rows `site` on **`meritfutures.com`** and rows both `portal` and `api` on **`app.meritfutures.com`**. Those hostnames share one registrable domain, so they are the **SAME SITE**. `SameSite=Lax` is a SITE control. A form `POST` issued by a page on the marketing origin to the API is therefore same-site, `Lax` permits it, and the host-only `merit_session` cookie is attached because the destination host is the host that set it. **A script on the marketing site could issue a fully authenticated write against a trader's money and nothing in this repository refused it.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `221`, session **412**, dispatched as `claude/csrf-on-cookie-mutations`. The row is **RESERVED, REQUIRED** and the number is spent.

- **MONEY PATH, and the coverage is total rather than partial.** The control runs ahead of every route on both deployments, `POST /accounts/:accountId/payout`, `POST /wallet/withdrawals` and `POST /checkout` included, and ahead of the not-found handler. **The `E2` read is owed on [`apps/api/src/csrf.ts`](../../apps/api/src/csrf.ts) and on the hook in [`apps/api/src/server.ts`](../../apps/api/src/server.ts).** This entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** The route and method counts in section 2 and every count in section 8 are **MEASURED** over the tree at the moment of writing, through a real `compose()`. That `SameSite=Lax` leaves the same-site case open is **DERIVED** from the cookie's attributes and `INFRA`'s origin table together, as [ADR-219](ADR-219.md) derived it. What is **JUDGED** is that the `Origin` check is sufficient ALONE (section 3), that the comparison is on hostname (section 4), that the check reads no cookie and no path (section 5), and that Cloudflare is the wrong layer for it (section 6).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim below was read at its own file, and section 1 records what the row said against what the tree says.

### 3. The mechanism. **THE `Origin` CHECK, AND IT IS SUFFICIENT ALONE**

**The row ordered this considered first and it is taken.** The check reads three headers, reads no body, reads no identity, and answers before any handler:

1. **A safe method passes.** `GET`, `HEAD`, `OPTIONS`, and that list is CLOSED. Membership is tested against the SAFE list, so an unsafe verb this contract does not use yet arrives **guarded** rather than exempt. [`registry.ts:106`](../../apps/api/src/registry.ts) closes the route vocabulary at five verbs; `csrf.ts` deliberately does not read that list, because the property it wants is *not a read* and not *one of ours*.
2. **No `Origin` header passes.** This is the clause that admits every legitimate caller and it is why the control needs no client change.
3. **An `Origin` this file cannot read is refused.** The literal `null` an opaque origin sends, two headers Node folded into one with a comma, a scheme that is not `http` or `https`, a value carrying a path or credentials.
4. **An unreadable `Host` is refused**, for clause 3's reason from the other side: a comparison that cannot be made must not report a match.
5. **Otherwise the `Origin`'s hostname must equal the request's own `Host` hostname.**

**WHY CLAUSE 2 IS NOT THE HOLE IT LOOKS LIKE, WHICH IS THE WHOLE ARGUMENT FOR SUFFICIENCY.** A cross-site request forgery is a request **the victim's browser is tricked into issuing with its own cookies attached**. Browsers set `Origin` on every request whose method is not `GET` or `HEAD`, form submissions included, so **a browser cannot issue a cookie-bearing unsafe request without one**. What arrives with no `Origin` is a non-browser client, and a non-browser client holds no victim's cookie jar, which is the mechanism the whole attack runs on. So clause 2 admits exactly the callers that cannot mount the attack: the portal's server-side `fetch` ([ADR-219](ADR-219.md) section 3) and every `/webhooks/*` sender.

**AND IT NEEDS NOTHING.** No token, no issuing endpoint, no storage the client can read, no migration, no environment variable, no hostname written into this repository ([ADR-012](ADR-012.md)), and no line of `apps/portal`. **A minted token would need every one of those and would refuse the same set of requests**, with one difference in the wrong direction: it cannot be reached by the portal's server-side caller at all. [ADR-219](ADR-219.md)'s standard is that a token nothing checks is not a control; the converse is this entry's, which is that **a token this check makes redundant is a second copy of a control rather than defence in depth**.

#### 3.1 One mechanism, and what the second one would have caught, which is nothing

**DEFENCE IN DEPTH IS A CHOICE AND THE CHOICE HERE IS NO.** The two candidates for a second mechanism were costed and both are strict subsets:

| Candidate | What it would catch that clause 5 does not |
|---|---|
| A minted token | **Nothing.** Both refuse exactly the requests a browser issues from a hostname that is not this one. It adds an endpoint `API_CONTRACT` does not declare, a script-readable store the `httpOnly` ruling exists to avoid, and a client contract |
| A `Sec-Fetch-Site` check | **Nothing, and it is worse than nothing for the one case that matters.** The marketing origin's forged write arrives as `same-site`, which is the value such a check would **admit**. A second mechanism that admits the gap is not depth, it is a control that reads as one |

### 4. Why hostname, and not scheme-host-port

**THE BOUNDARY THIS CONTROL DRAWS IS THE BOUNDARY THE COOKIE DRAWS, AND A COOKIE IS NEITHER PORT-SCOPED NOR SCHEME-SCOPED.** [`auth.ts:613`](../../apps/api/src/routes/auth.ts) sets `merit_session` with no `Domain` attribute, so it is host-only: it is sent to exactly one hostname and to no other, on any port and, subject to `Secure`, on any scheme. Comparing hostnames is therefore **exactly as tight as the cookie is**. A full-origin comparison would refuse nothing further, because a page that can occupy any port of this hostname already receives this cookie by the cookie's own rules.

**THAT ARGUMENT HAS ONE LEG IN ANOTHER FILE AND IT IS ASSERTED RATHER THAN TRUSTED.** A `Domain=` attribute on the session cookie would widen the cookie past the hostname this check compares, and nothing else in the repository would report it. [`apps/api/test/csrf.test.ts`](../../apps/api/test/csrf.test.ts) reads every `Set-Cookie` template in `auth.ts` and fails if one grows a `Domain`, which was watched firing (section 8).

**Both sides go through `URL`**, which lowercases, punycodes a unicode label, strips the port and brackets an IPv6 literal, so both sides are normalized identically or neither is. The `Host` header is rejected outright if it carries `/`, `?`, `#`, `@` or `\` **before** it is parsed: `new URL('http://trusted@attacker')` reads `attacker`, so a header of `trusted-host@attacker-host` would otherwise resolve to the attacker's half under a name that reads as the trusted one.

### 5. What the check does NOT read, and the less obvious half of that

**IT READS NO PATH.** A control that exempts a list of routes is a control whose list is its bypass, and [`registry.ts`](../../apps/api/src/registry.ts)'s header already establishes that a second place to say which routes are special is a second place to get it wrong.

**IT READS NO COOKIE, AND D2's WORDS ARE `cookie mutations`, SO THAT NEEDS SAYING OUT LOUD.** The narrower reading, fire only when a session cookie arrives, was considered and refused on two grounds. **The first is LOGIN FORGERY**: a forged sign-in `POST` carries no cookie at all and the RESPONSE is the mutation, so the victim's browser ends up holding the attacker's session and everything the victim does next lands in the attacker's account. The narrow reading misses it entirely. **The second is that reading the cookie to decide whether to read the origin makes the cookie's NAME the bypass**, and that name lives in one constant in a route module this file must not import. **Broader is not weaker**, which is [SECURITY](../architecture/SECURITY.md) §2.6's own sentence about C-01 in a different direction.

**WHAT IT COSTS, NAMED RATHER THAN LEFT TO BE FOUND.** A non-browser caller that sent an `Origin` would be refused. No caller does today: the portal's `fetch` runs in Node and the three webhook senders are server-to-server. If one ever did, **the failure is loud** (a `403` on a named check with the clause in the log) rather than silent, which is the direction this corpus asks a control to fail in. The alternative, exempting `/webhooks/*` by path, is the bypass list section 5 opens by refusing.

### 6. Cloudflare is the wrong layer for THIS control, and the reason is not taste

[`INFRA:27`](../architecture/INFRA.md) puts *"Cloudflare in front of every origin"*, and the row asked whether the check belongs there.

**IT DOES NOT, AND THE FIRST REASON IS THE ONE THE ROW NAMED.** `INFRA` rules **no origin lock anywhere**: there is no authenticated origin pull, no origin firewall rule and no allowlist between Cloudflare and Railway in any section of that document. Railway serves each service on its own hostname by default. **A direct-to-origin request bypasses the edge**, and a control that a request can decline to pass through is not the control for a money path.

**THE SECOND REASON IS THAT AN EDGE RULE IS INVISIBLE TO EVERYTHING THAT READS THIS REPOSITORY.** No gate reads it, `pnpm vitest` cannot exercise it, and the founder's `E2` read cannot see it. **A control cited as a reason and never installed is this corpus's oldest defect class**, and a control installed where nothing can cite it is the same defect with the halves swapped.

**THE EDGE IS STILL THE RIGHT LAYER FOR WHAT IT ALREADY HOLDS**, and this entry weakens none of it: `INFRA` section 3 hard rule 3's IP allowlist and Cloudflare rules on `ADMIN_ORIGIN` are ORIGIN-scoped controls on an origin, which is a different shape from a per-request header comparison. **A WAF rule duplicating `C-29` at the edge would be defensible as an operational tripwire and is not proposed here**, because section 3.1's argument applies to it too and because the edge configuration is nobody's fence in this repository.

### 7. What the portal owes, which is the trap the row named

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS WHETHER CLAUSE 2 IS ACCEPTABLE, BECAUSE THE WHOLE CONTROL RESTS ON IT.** A request with no `Origin` header is admitted. That is safe if and only if no browser can be made to issue a cookie-bearing unsafe request without one, which is true of every current browser and is a property of the Fetch standard rather than of Merit. **It is checkable in two minutes**: submit a cross-origin HTML form and read the request. **The alternative is to require an `Origin` and refuse its absence**, which would refuse the portal's own server-side caller and every webhook on the day it landed, so it cannot be taken without a client change this fence does not hold. **If the founder wants the stricter posture, the thing to say is that the portal must send an explicit `Origin` on every write before that check flips**, and it is much cheaper to say now than after nineteen call sites exist.

  **THE SECOND IS THE WEBHOOK EXPOSURE, BECAUSE IT IS THE ONE PLACE THIS ENTRY COULD COST MONEY IF IT IS WRONG.** The check runs on every unsafe method, including the three provider webhooks, and refuses any caller that sends a mismatched `Origin`. **No standard server-side HTTP client sends one** and none of Merit's providers is believed to, but this entry cannot prove a third party's behaviour and does not claim to. **The failure mode is payment webhooks answering 403.** The cheap insurance is a `/webhooks/*` exemption, which section 5 refuses on the ground that a path list is a bypass list; **if the founder weighs a provider outage above that, the exemption is three lines and the argument against it is stated rather than hidden.**

  **THE THIRD IS THE FENCE EXTENSION INTO `apps/portal`.** Two files, taken on rights the dispatch granted, in a commit of their own. **The argument for is that the alternative was landing a control that turns a sibling package's test suite red and calling the session complete.** The argument against is that `ADR-003` gives a money-path session one objective and a reviewer now reads two diffs. If that trade is wrong, **the correction is to the dispatch rather than to this entry**: a fence drawn around a control whose absence another package asserts is a fence drawn without reading that assertion.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **Section 4's hostname comparison has a second leg nobody has tested and it is the deployment's.** The check compares the `Origin` to the `Host` header **as it arrives at the process**. Fastify is built here with no `trustProxy`, so `Host` is the header on the wire and not an `X-Forwarded-Host`, which is the safe direction. But if Railway or Cloudflare ever rewrites `Host` to an internal name while the browser's `Origin` still says `app.meritfutures.com`, **every write in the product fails at once, loudly, on the first request after the deploy**. That is the good direction for a control to break in and it is still a production outage. **The two-minute check is to read the `Host` header the running service actually receives**, and nothing in this repository can do it.

  **AND ONE OBJECTION WORTH TWO MINUTES, because it is the strongest thing on the other side.** A reader could reasonably say that section 3.1 dismisses defence in depth too quickly, and that a token is the textbook answer precisely because origin checks have historically been got wrong. **The answer is that the historical failures are allowlist failures** -- a regex matching `evil-meritfutures.com`, a `startsWith`, a config listing a hostname that later moved -- **and this check holds no allowlist at all**: it compares the request against itself. There is no list to get wrong and no hostname anywhere in the diff. **But that argument is about THIS shape of origin check and not about origin checks in general**, and if the shape ever grows a configured allowlist, section 3.1's conclusion should be re-argued rather than inherited.
