## ADR-308: `subject()` answers whole, because `state` reads the row the worker wrote and the size row decodes on the typed door  (2026-09-03, status: proposed)

**Row `308` builds [ADR-287](ADR-287.md) slice 5, which is the last of `subject()`.** [ADR-306](ADR-306.md) built three legs and left exactly two things refusing by name in one throw, `subject.state` and `subject.plan.size`. **Both are built here.** `PayoutTx.subject(accountId)` returns a `PayoutSubject` against a seeded database, and five of the eight members of `PayoutBackend` and `PayoutTx` now answer.

**NOTHING IS SYNTHESISED, AND THE RULE IS HELD BY THE RETURN TYPES RATHER THAN BY A UNION.** `SubjectLeg<T>` existed so an unbuilt leg could refuse by name without ever carrying a partial value; with no unbuilt leg left its `ok: false` arm had no producer, so the type is retired and `stateLeg` answers a `RuleState` or throws while `planLeg` answers a `ResolvedPlan` or throws. **There is no shape in this file that can hold half of either.** The sentence that has stood on this member since it was one line of rejection stands unchanged: *a synthesised `RuleState` is a payout basis nobody computed.*

**`state` READS AND DOES NOT FOLD, AND THAT IS THE ONE PROPERTY A GREEN SUITE CANNOT OTHERWISE HOLD.** A request-path fold would answer every case in the suite correctly. It is refused because `INV-M5-02` and [ADR-239](ADR-239.md) make the API a READER of the state the worker wrote, and because a fold computed on the request path is precisely the divergence [ADR-026](ADR-026.md) `C-07`'s `state_hash` exists to detect, on the one path no replay audit reads. Section 3.

**THE SIZE DECODE WAS BOUGHT BY A DOOR AND NOT BY A RULING, WHICH IS WHY ROW `303` RAN AHEAD OF THIS ONE.** [ADR-286](ADR-286.md) ruling 4 measured that the payout path is on the DRIVER side of the two spellings and needs no rename from anybody, and its section 5 named the remedy as *"`packages/db` handing out a typed catalogue row instead of `unknown` ... whoever takes it is amending a door, not writing a decoder"*. [ADR-303](ADR-303.md) took it. Section 4.

### 2. Why the `SubjectLeg<T>` scaffolding went, and why that is not a weakening

**THE ROW'S STOP CONDITION NAMES THAT TYPE AND THE PROPERTY IT NAMES IS STRONGER WITHOUT IT.** The condition is *"`SubjectLeg<T>` has no arm carrying a partial value ... a leg that cannot answer refuses; it never returns a value it did not read"*. With both legs built there is no producer of the `ok: false` arm anywhere, so what the type would carry from this row forward is a **dead union arm on the money path**, which is an invitation to park a future half-built leg in rather than a control. The refusal-collection block below it would likewise be unreachable and unreddenable: no case could exercise it.

**SO THE SCAFFOLDING IS RETIRED AND THE RULE MOVES INTO THE SIGNATURES.** `stateLeg` returns `Promise<RuleState>` and `planLeg` returns `Promise<ResolvedPlan>`; neither has an arm that carries half a value, because neither has an arm at all. A leg that cannot answer throws, and the classes it throws are the ruled ones in section 5.

**THE DELETION IS ASSERTED RATHER THAN PERFORMED QUIETLY.** [`payout-backend.test.ts`](../../apps/api/test/payout-backend.test.ts) requires `type SubjectLeg<T> =` and `{ ok: false, member:` to be ABSENT and the two retired needles with them, so a session that restored the scaffolding to park a leg in goes red. **The needle is the DECLARATION and not the bare name**, because the member's own docblock says in prose why the scaffolding went, and a sweep for the name would be a case satisfiable only by deleting the reason. That is [ADR-286](ADR-286.md)'s own repair of two assertions applied here: ask a narrower question rather than relax a broader one.

**THIS IS THE ONE PLACE THIS ROW READ ITS OWN INSTRUCTION AGAINST ITS SUBSTANCE**, and it is section 8's first item for the founder rather than a call this entry treats as settled.

### 3. `state`, and the two constraints that are rulings rather than preferences

**THE READER IS CALLED AND NOTHING IS FOLDED.** `PayoutSubject.state`'s docblock ([`routes/payouts.ts`](../../apps/api/src/routes/payouts.ts)) requires a backend implementing `subject()` to CALL `ruleStateOn` ([`rule-state-reader.ts`](../../apps/api/src/rule-state-reader.ts)) and NOT to fold a state in the request path, on `INV-M5-02` and [ADR-239](ADR-239.md). **`INV-M5-02` is that both payout endpoints call `evaluatePayout` with the same inputs because "a second evaluator would be a second rule"**, and a fold here would make the API the second evaluator of the state itself, one level below the one that invariant is written about.

**THE DAY COMES FROM THE NAMED DOOR AND NEVER FROM A CALENDAR FOLDED HERE**, on [ADR-268](ADR-268.md). `ScopedTx.lastClosedTradingDay()` takes no argument at all, because there is no day a caller could name: naming one is the question. `R-06` permits only the last closed day *"whatever the batch is doing at the time"*, so the day is asked for FIRST and there is no arm in this file that picks a row and then names the day it came from. **A case seeds two `rule_states` rows on two days and watches the member read the one the door gave rather than the later one**, which is the shape `ruleStateOn`'s own header forbids: *"There is no `latest` function here and there must not be one."*

**THE PREDICATE IS `{ accountId }` AND THE SELECTION IS THE READER'S, WHICH IS THIS DEPLOYABLE'S EXISTING CALL UNCHANGED.** `gatesOf`'s neighbour [`eligible-next-7d.ts:817`](../../apps/api/src/admin-source/eligible-next-7d.ts) already reads `tx.rowsWhere('ruleStates', { accountId })` and hands the rows plus the anchor day to `ruleStateOn`. Narrowing on the day here as well would state one fact in two places on the money path, and the duplicate-row refusal `rule_states_account_day_uq` backstops is a property of the SET on that day, which belongs to the function that owns `R-06`.

**BOTH READS ARE ON THE PAYOUT TRANSACTION AND NEITHER IMPLIES A SECOND DOOR.** `ruleStates` is scope class `derived` via `accounts` on `account_id` ([`scope.ts:930`](../../packages/db/src/scope.ts)), so the rows are one hop out on the handle the account was already resolved on.

**AND THE ORDER IS NOW LOAD BEARING RATHER THAN TIDY.** [ADR-285](ADR-285.md) ruling 4 requires the ownership answer FIRST, because a scoped read of a foreign account's rows is EMPTY and an empty list IS `RuleStateAbsent`: a state-first implementation would hand a prober **503** for every account of another identity where API_CONTRACT section 1 requires **404**. Until this row that hazard was hypothetical, because nothing read a state. **From this row it is the read order**, and a case asserts the `null` arm is reached with the calendar door untouched and no `ruleStates` read taken.

### 4. The size row, and the door that made it buildable

**[ADR-283](ADR-283.md) SECTION 5 SAID A CANONICAL DECODER HAS TO MAKE ONE CALLER RENAME. [ADR-286](ADR-286.md) MEASURED THE MANIFESTS AND FOUND THAT FRAMING WRONG**, and what it put in its place is the ground this row stands on: `apps/site` declares no `@merit/db` at all and reads snake_case because it reads Merit's own HTTP response; `apps/worker` and `apps/api` read camelCase because Drizzle hands back property names. **The payout path is on the driver side, so it needs no rename from anybody.** What it needed was a home, and [ADR-286](ADR-286.md) section 5 named the smaller and better-aimed of the two candidates as the typed catalogue row.

**[ADR-303](ADR-303.md) LANDED IT, AND THIS IS THE FIRST PRODUCTION CALLER OF THAT DOOR.** `catalogRowAt` returns `CatalogRow<'planVersionSizes'>`, derived from `TABLES` and therefore from `schema.ts`, so every property this row reads is checked by `tsc` against the transcription of the DDL and a key that does not exist is `TS2339` rather than a runtime throw on a money read.

**THE RUNTIME CHECKS DO NOT COME OFF ON THE STRENGTH OF THAT TYPE, AND THAT IS THAT DOOR'S OWN LIMIT 1 RATHER THAN THIS FILE'S CAUTION.** `CatalogRow<K>` is derived from a TRANSCRIPTION, and [ADR-112](ADR-112.md) foreclosure 4 records that nothing in this tree compares a transcribed column TYPE against the migration that declares it. The door's docblock states the rule this row keeps: *"a caller that reads money off one of these rows still checks the value it read."* So `centsOf`, `centsOrNullOf` and `boolOf` check every column, and `INV-02` is the reason they refuse rather than coerce.

**THE MAPPING IS AN ACCEPTED `FM-16` AND IS REGISTERED HERE RATHER THAN HIDDEN.** [ADR-303](ADR-303.md) limit 2 states it in advance: the typed row *"is not a decoder. It SHRINKS one. A driver-side caller still writes a field mapping onto the engine's own row type, once per caller, which is an accepted `FM-16`."* `toSizeRow` ([`apps/worker/src/batch/adapter.ts:1296`](../../apps/worker/src/batch/adapter.ts)) is the same mapping, `apps/api` cannot import `apps/worker`, and that is the identical shape [`rule-state-reader.ts`](../../apps/api/src/rule-state-reader.ts) registers in its own header for `toRuleState`. **The finding is registered and not taken, on that file's own precedent.**

**THE ONE PART THAT IS NOT DUPLICATED IS THE `jsonb`, WHICH IS THE HALF THAT ACTUALLY DIVERGED.** [ADR-286](ADR-286.md) ruling 5 measured `payout_cap_schedule_cents` as one predicate stated THREE times with nothing comparing them, and found `apps/api`'s copy already wrong on the money in both directions. [ADR-302](ADR-302.md) collapsed the three into `decodeCapScheduleCents`, and this member is a **caller** of it. Two cases hold that: a `cap_cents` past `Number.MAX_SAFE_INTEGER` is REFUSED here rather than handed back rounded, and the base-10 string [ADR-283](ADR-283.md) ruling 5 blessed is admitted exactly.

**THE ADDRESS IS THE GRID'S OWN UNIQUE KEY.** `plan_version_sizes_version_size_uq` is `(plan_version_id, size_cents)` ([`0004_catalog.sql:220`](../../packages/db/migrations/0004_catalog.sql)), transcribed as a `unique()` at [`schema.ts:480`](../../packages/db/src/schema.ts) precisely so `refuseUnaddressed` can read it ([ADR-233](ADR-233.md)). A read filtered on the version alone would be the whole grid with the choice made in this adapter, and the choice is `accounts.size_cents`. **The size travels as a `bigint` into the predicate itself**, because a predicate is a boundary and `INV-02` is money as integer cents at every one.

**SIX COLUMNS ARE NOT READ AND THE ENGINE'S OWN RULE IS WHY.** `price_cents` and `reset_price_cents` are columns and [`types.ts:587`](../../packages/rules-engine/src/types.ts) states their absence from `PlanVersionSizeRow` as a decision: no `CV-nn` mentions either, no rule reads a price, M01 section 1.2 puts commerce outside the engine, and *"a validator that could see the price could grow a rule about it."* So could a payout adapter. A case seeds both as nonsense and watches nothing change.

### 5. The absent size row, which is the refusal rule [ADR-306](ADR-306.md) named as unwritten

**THAT ROW LEFT THE READ OUT FOR THIS REASON AND SAID SO**: `catalogRowAt` answers a row OR `undefined`, and what an absent `plan_version_sizes` row MEANS -- an account pinned to a size its own plan version does not publish -- was a rule nobody had written. **It is written here, and the ground is the DDL rather than a judgement about likelihood.**

**THERE IS NO COMPOSITE FOREIGN KEY HOLDING THE PAIR TOGETHER.** [`0007_accounts.sql`](../../packages/db/migrations/0007_accounts.sql) declares `plan_version_id uuid NOT NULL REFERENCES plan_versions(id) ON DELETE RESTRICT` at line 50 and `size_cents bigint NOT NULL CHECK (size_cents > 0)` at line 52, as two independent columns; a recursive read of the migrations finds no `REFERENCES plan_version_sizes` anywhere, and [`0044_fee_back_and_ladder_unlock.sql:241`](../../packages/db/migrations/0044_fee_back_and_ladder_unlock.sql) states the shape in its own words for a sibling column: it *"names a plan_version_sizes.size_cents; it is not a foreign key to that row"*. **So the pair can fail to resolve.**

**THE ANSWER IS A `PayoutRowError`, WHICH IS A 500, AND IT IS THE READ ABOVE IT ANSWERED THE SAME WAY.** `planLeg` already refuses an empty `plan_versions` read on exactly this ground. **A grid is not an interpolation**: an account pinned to an unpublished size has no drawdown, no buffer and no payout ceiling anywhere in this database, and resolving against a neighbouring rung would hand a trader a floor rule nobody published. A 503 would tell them to retry what no retry can fix, which is `RuleStateUnreadable`'s ruling applied one door over.

**EVERY REFUSAL THIS MEMBER CAN NOW TAKE ALREADY HAD AN ARM ON THE ROUTE, AND THAT WAS DERIVED AT SOURCE RATHER THAN ASSUMED.** This is why no route file is edited:

| Class | Where it arises | What the route does | Status |
|---|---|---|---|
| `RuleStateAbsent` | `ruleStateOn`, a day the fold has not closed | `stateNotFolded` at [`payouts.ts:1427`](../../apps/api/src/routes/payouts.ts), [ADR-285](ADR-285.md) | **503** |
| `RuleStateUnreadable` | two rows for one account-day, or a malformed one | deliberately NOT caught, and that line says so | **500** |
| `PayoutRowError` | an absent size row, a coerced money column | not a `PayoutBackendUnwired`, so `unwiredOrThrow` rethrows | **500** |
| `PlanRulesCodecError`, `CapScheduleCodecError` | the engine's codecs | same | **500** |
| `EngineInvariantError` | `resolvePlan` on a config `validatePlan` must have rejected at publish | same | **500** |
| a plain `Error` | `lastClosedTradingDay()` on an empty, exhausted or holed calendar | same, and `PayoutSubject.state`'s docblock already rules it: *"the refusal reaches this route as a throw inside the payout transaction, which rolls back"* | **500** |

**THE ONLY RETRYABLE ONE IS THE ONE THAT IS ACTUALLY A SCHEDULING QUESTION.** An unfolded day is a fold that has not run; everything else in that table is Merit's records disagreeing with Merit's schema, its engine or its own catalogue.
