## ADR-083: the API is its own deployable, one codebase deployed twice, and Fastify runs it  (2026-08-23, status: proposed)

**This rows a container [OVERVIEW](../architecture/OVERVIEW.md) has drawn since 2026-08-13 and creates the deployable that serves it.** Section 2's C4 diagram declares `API [/api/v1]` inside the Merit boundary; section 3's container table did not row it; [P1-monorepo-scaffold](../plans/P1-monorepo-scaffold.md) section 3 names four deployables and `ls apps` returned those four. So every endpoint [API_CONTRACT](../architecture/API_CONTRACT.md) specifies had no deployable to live in. **Non-money: it is a shell, it moves no money, no route implements a behaviour, no migration and no `SD-nn`.**

- **Origin:** the [P3 build plan](../plans/P3-ledger-billing-identity.md) section 3, which measured the gap and named it the one precondition standing in front of all six of P3's stated contents. Dispatched as session `P3-a` ([session 144](../sessions/2026-08-23-session-144.md)).

- **Context:** the workspace declares zero runtime dependencies, `ScopedDb` is an interface with one field whose own header states that neither the client nor the accessor exists, and the three UI surfaces are pure render functions rather than servers. **This ruling picks where the API lives and what runs it. It wires nothing**, because the session's fence holds no `packages/db` and there is nothing for a handler to read.

---

### 1. The finding, re-derived rather than inherited

Every line below was run in this session against this tree.

| Claim | How it was checked | Result |
|---|---|---|
| Section 2 draws six containers inside the Merit boundary | read [OVERVIEW](../architecture/OVERVIEW.md) section 2's `subgraph Merit` | `Site`, `Portal`, `Admin`, **`API [/api/v1]`**, `Worker`, `DB` |
| Section 3's table did not row the API | read section 3's table before this change | seven rows: `apps/site`, `apps/portal`, `apps/admin`, `packages/rules-engine`, `packages/db`, `packages/rithmic`, `worker` |
| The workspace holds four deployables | `ls apps` | `admin`, `portal`, `site`, `worker` |
| P1 names four | [P1 section 3](../plans/P1-monorepo-scaffold.md)'s **Deployables** row | `apps/site/`, `apps/portal/`, `apps/admin/`, `apps/worker/` |
| Three arrows point into the container nobody owns | section 2's edge list | `Site --> API`, `Portal --> API`, `Admin --> API` |

**The dispatching brief's candidate approval clause does not survive this reading, and that is worth more than a repeat of it would have been.** It reads *"OVERVIEW section 2's container list and section 3's container table name the same set"*. **They do not, and after this change they still do not.** `packages/rules-engine` and `packages/rithmic` are rows in section 3 with no box in section 2, and that is **correct** rather than a second finding: section 2 is a C4 **context** diagram, which draws deployables and datastores, and a library that ships inside a deployable is not one. The direction that holds, and the direction the defect ran in, is the other one:

> **Every container section 2 draws inside the Merit boundary has a row in section 3's table.**

That was false for `API` and is true now. Section 8's approval line asserts it in that direction. **A clause asserted in the direction that was never true would have been signed and would have been wrong.**

---

### 2. The ruling

> **1. The API is its own deployable, `apps/api`, and not a server inside `apps/portal`, `apps/site` or `apps/admin`.**
>
> **2. It is ONE codebase deployed TWICE. A process serves exactly one surface, chosen at startup: `public` on the portal's origin, serving [API_CONTRACT](../architecture/API_CONTRACT.md) sections 3 to 7 and 10; `operator` on `ADMIN_ORIGIN`, serving sections 8 and 9. A deployment registers no route belonging to the other surface.**
>
> **3. Fastify 5 runs it, under `node --experimental-strip-types`, with no build step and no bundler, ever.**

---

### 3. Why the API is its own deployable, and why the corpus reads the other way at first

**Three documents pull toward folding it into the portal, and every one of them is about deployment topology rather than about ownership.** [INFRA section 2](../architecture/INFRA.md) names the Railway service `portal-api`. [INFRA section 13.2](../architecture/INFRA.md) puts *"portal and API"* on `app.meritfutures.com`. [OVERVIEW section 7](../architecture/OVERVIEW.md)'s application zone reads `API + portal + site`. **All three remain true under this ruling**, because sharing an origin and sharing an edge zone are not sharing a process.

**The sentence that decides it is [API_CONTRACT section 1](../architecture/API_CONTRACT.md):**

> The portal, admin console, and site are the first clients of this API and have **no privileged back door**: anything the UI can do, it does through these endpoints, which is what makes the [Enrichlead failure](../../research/VIBE_FAILURE_POSTMORTEMS.md) untestable-by-omission impossible here.

**A surface that CONTAINS the API has a privileged back door by construction**, because a handler in the same package is an import away, and no lint can tell the difference between a legitimate internal call and a route bypass in a codebase where both are the same kind of function call. The guarantee degrades from a boundary into a habit, and it degrades silently, which is the shape [P1 section 2.1](../plans/P1-monorepo-scaffold.md) already named for the admin console: *"That choice is invisible for months, is a re-platform to undo, and it silently converts a security control into a URL convention."*

**Two more sources say the same thing from their own side and neither was recalled.** [M04 section 4](../plans/M04-trader-portal.md): *"M4 owns no endpoint. It consumes API_CONTRACT sections 3, 5, 6, and 7 verbatim, and adds no field to any of them."* And the portal already behaves as a client: [`apps/portal/src/api/types.ts`](../../apps/portal/src/api/types.ts) is a **transcription** of the wire types, checked field by field against the contract by [`api-types.test.ts`](../../apps/portal/test/api-types.test.ts). A package that transcribes an interface is on the far side of it.

**And the diagram closes it mechanically.** Section 2 draws three arrows into `API`, from `Site`, `Portal` and `Admin`. `RI-04` in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs) refuses an app that depends on an app: *"A deployable that imports a deployable is one deployable."* **An API living inside any one of the three makes the other two arrows unimplementable**, so the only placement consistent with the drawn architecture is a fifth deployable.

### 4. Why sections 8 and 9 are a second DEPLOYMENT and not a second codebase

**The constraint is sharper than "admin is separate", and it is a status code.** [API_CONTRACT section 12](../architecture/API_CONTRACT.md)'s negative-authz matrix:

| Test | Required factor | Expected |
|---|---|---|
| Trader session calls any `/admin/*` | `admin_sso` | 403 |
| Trader session calls `/internal/*` from the public origin | `admin_sso` | **404** |

**403 is what a permission check returns. 404 is what an absent route returns.** A process that registered `/internal/batch/run` and then refused it can be made to answer 404, and every future handler, middleware ordering and error mapper is another chance to get that wrong. A process that never registered it **cannot answer anything else**. So the route set is selected at startup, and the public deployment's 404 is the router's, produced by there being nothing there.

**The alternative was to put sections 8 and 9 in `apps/admin`, and it is refused on the transcription argument.** API_CONTRACT is one contract with one base path, one RFC 9457 error model, one idempotency rule, one pagination rule and one OpenAPI generator. Implementing part of it in a second codebase means a second copy of all five, and the corpus already records what a second transcription costs: [`apps/site/package.json`](../../apps/site/package.json)'s own comment refuses one on the ground that *"the marketing-versus-implementation gap constitution 0.5 names is exactly what a second transcription is"*. **One codebase, two deployments** buys the structural 404 without buying a second spelling of the contract.

**The partition is over PATH PREFIXES and never over API_CONTRACT's section numbers, and section 9 is why.** That section is headed *"Ops and internal (admin origin only)"* and its rows include `GET /health`, marked **Public**, beside `GET /internal/health/deep`, marked **Admin origin only**. **A partition that read the heading would put the liveness probe on the admin origin** and leave the public deployment with nothing for the platform to poll. `/admin` and `/internal` are the operator prefixes; `/health` is served by both deployments; everything else is public. The contract already drew the distinction in the path, and reading the path is what gets both rows right without a special case.

[`apps/api/src/surface.ts`](../../apps/api/src/surface.ts) is that partition, and [`surface.test.ts`](../../apps/api/test/surface.test.ts) asserts it in both directions plus the two edge shapes a naive implementation gets wrong: a bare `startsWith` matches `/administration`, and a caller that helpfully prefixes `/api/v1` turns `/api/v1/internal/jobs` into a path matching neither operator prefix, which classifies an operator route as public with nothing reporting it. Both are refused rather than documented.

**`MERIT_API_SURFACE` has no default, on [`apps/admin/src/origin.ts`](../../apps/admin/src/origin.ts)'s precedent for `ADMIN_ORIGIN`.** There is no safe guess available: defaulting to `public` turns a misconfigured admin deployment into a silently useless one, and defaulting to `operator` fails open. A deployment that has not been configured is refused at startup.

### 5. Fastify 5, and the three properties the choice rests on, each measured

**The hard constraint comes from a gate rather than from taste.** `CI-06/gate-inventory` probes every `apps/*/package.json` for a `build` script and requires it **ABSENT**, because `CI-07`'s whole row waits on an artifact that does not exist; the day a build script lands, that gate fails on good news. The four existing apps run TypeScript directly under `node --experimental-strip-types` and declare no build. **So the framework had to be one that needs no build step at all**, which is not a preference to be revisited later but a condition on the candidate set.

Measured in this session against `fastify@5.12.1` and Node `v22.22.2` (`.nvmrc` reads `22`), in a scratch directory outside this repository:

| Property | Why it is load-bearing | Measured |
|---|---|---|
| **Runs under `node --experimental-strip-types`, no build** | `CI-06/gate-inventory`'s absent-`build` probe, and the four apps' precedent | a `.ts` entry point importing Fastify, registering a route and serving it: **200 on the registered route** |
| **An unregistered route is a 404 from the router** | section 4's whole argument | the same process, with the operator route not registered: **404** |
| **Raw body reachable BEFORE parsing** | [API_CONTRACT section 10](../architecture/API_CONTRACT.md): every webhook's *"HMAC signature verified **before** parsing"*, and the raw payload stored | `addContentTypeParser('application/json', { parseAs: 'buffer' })` delivered the 7 raw bytes and the parsed object from one request: **200, `{"rawLength":7,"parsed":{"a":1}}`** |
| **No install scripts anywhere in its tree** | `pnpm-workspace.yaml`'s `onlyBuiltDependencies: []` makes every install script an explicit VG-12 admission | `fastify@5.12.1` plus its 48 transitive packages: **zero `preinstall`, `install` or `postinstall` declared** |

The remaining fit is contract-shaped rather than measurable here: `setErrorHandler` gives whole control of the response body, which `application/problem+json` needs; the zod type provider generates the OpenAPI document API_CONTRACT section 1 requires *"from the same zod schemas"*; and the encapsulation model expresses "a surface is a set of plugins registered at startup" without a second router.

**Nothing is installed by this change and that is the fence rather than the ruling.** Every version in this workspace lives in `pnpm-workspace.yaml`'s `catalog:` block, which [the P3 build plan section 6](../plans/P3-ledger-billing-identity.md) gives to sessions 145 and 147; a manifest declaring `"fastify": "catalog:"` against an absent catalog entry does not install. So `apps/api/package.json` declares no runtime dependency, `pnpm-lock.yaml` gains exactly one importer entry with three dev catalog references and no package, and **the admission is the next holder's**, with the exact version and the VG-12 approval that goes with it.

### 6. What this forecloses

**Named because an entry that records only the winner leaves the next reader unable to tell whether an alternative was considered or never seen.**

| Foreclosed | What it costs to reopen |
|---|---|
| **NestJS, and any decorator-first framework** | Out on the build constraint AND on the runtime. Decorators and `emitDecoratorMetadata` require a transform; `node --experimental-strip-types` erases types and transforms nothing, so a decorator framework needs `tsc` or a bundler, which is a `build` script, which fails `CI-06/gate-inventory` on the day it lands. **This is the one alternative that is not merely rejected but unavailable** while that gate stands as written |
| **Next.js API routes, or any full-stack framework serving the API beside a UI** | Same build constraint, plus section 3's argument: it puts the API back inside a UI deployable and reinstates the back door |
| **Deploying the API to an edge or Workers runtime** | **This is the real cost of Fastify over Hono, and it is the one to weigh.** Fastify targets Node's `http` module. Hono is runtime-agnostic and would have kept a Cloudflare Workers deployment open at no cost today. Merit is on Railway ([ADR-007](ADR-007.md)) with Cloudflare in front as edge, WAF and DNS only, and the API talks to Postgres over a pooled connection on every request, which is the workload edge runtimes are worst at. **Reopening it is a rewrite of every route registration and every hook**, and the reason to accept that is that no v1 requirement points at the edge |
| **tRPC, or any typed-RPC transport, as the primary interface** | API_CONTRACT specifies HTTP verbs, path parameters, RFC 9457 problem documents, `Idempotency-Key` headers, cursor pagination and a generated OpenAPI document. tRPC's shape is none of those. Reopening it means rewriting the contract, not the server |
| **A single process serving both the public and the operator surface** | The 404 in section 4 stops being structural and becomes a check somebody has to keep getting right |
| **`apps/portal` growing endpoints** | Foreclosed by ruling 1 and by M04 section 4, which already said so |

**What stays open, deliberately.** The framework is an implementation of the transport and not of the behaviour: handlers are expected to be functions over a request model with the framework as the adapter, which is the shape that keeps a future migration a re-registration rather than a rewrite. **This entry does not build that**; it names it as the constraint the module sessions inherit, because a shell that invented a handler abstraction with no handler to abstract would be guessing.

### 7. Consequences

- **[`apps/api`](../../apps/api) exists**: `package.json`, `tsconfig.json`, `src/index.ts`, `src/surface.ts`, `test/surface.test.ts`. **No `build` script**, and the manifest says why in its own `//` comment so that a later session adding one has to delete the explanation first.
- **[OVERVIEW section 3](../architecture/OVERVIEW.md)'s container table rows `apps/api`.** The diagram and the table stop disagreeing. **Section 2 is not edited**: it was right.
- **`pnpm-lock.yaml` gains one importer entry and no package.** The workspace still declares zero runtime dependencies.
- **`RI-04` does not see this deployable, and that is reported rather than repaired.** Its `DEPLOYABLES` list in [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs) is the literal `['site', 'portal', 'admin', 'worker']`, so `apps/api` gets none of its three assertions: distinct package name, own directory, and no app depending on an app. **The invariant still passes and is now narrower than the tree it names.** That file is outside this session's fence. **It is the highest-value single-line follow-up this ruling creates**, because the arrow argument in section 3 rests on exactly the assertion `RI-04` makes.
- **[INFRA section 2](../architecture/INFRA.md)'s Railway service table names four services and this ruling needs six.** `api` and `api-admin` join `site`, `portal-api`, `admin` and `worker`. **The same defect as the finding this entry closes, one document over**, and INFRA is outside this fence. `SERVICE_BY_SURFACE` in `surface.ts` names both and cites this consequence.
- **`portal-api` is now a service name that describes one thing and is named for two.** `apps/portal` exports `SERVICE = 'portal-api'`. Not this fence's to rename, and renaming it is not free: it is a Railway service identity. Recorded so the INFRA session decides it rather than inherits it.
- **`ADMIN_ORIGIN`'s value appears nowhere.** `api-admin` is a Railway service name and not a hostname, so [ADR-012](ADR-012.md)'s placeholder convention holds: the tree names the service that runs there without naming where there is.
- **No migration, no `SD-nn`, no new `CI-06` letter, no gate change and no `falsify` case.** `0047` stays free and the scope-case count does not move.
- **What P3's wave 3 was waiting for now exists.** The plan declined to dispatch the six module slices because *"every module session's fence is a path inside a deployable ADR-083 has not yet named"*. `apps/api/src/**` is nameable now.
