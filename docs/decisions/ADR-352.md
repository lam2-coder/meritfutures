### 2. THE HEADLINE: four of five, and the fifth is unreachable rather than unwritten

`BreakerIo` declares `transact`, `terms`, `events`, `now` and `tradingDayOf`. **Four are served by this row.** Here is what stands between the fifth and a run.

**THE EVENT SINK REFUSES, AND IT IS TWO REFUSALS RATHER THAN ONE.**

1. **NO SINK IS REACHABLE.** `TRANSACTION_EVENT_WRITER` in `apps/api/src/events.ts` is the workspace's only composed event writer. `RI-04` forbids one deployable depending on another; `apps/worker/package.json` declares `@merit/db`, `@merit/ledger`, `@merit/queue` and `@merit/rules-engine` and **no `apps/*` package at all**; and `node-linker=isolated` in `.npmrc` makes an undeclared bare specifier resolve at neither run time nor build time. `test/event-sink.test.ts` section 3 holds the fence. **This is not a file somebody forgot to write.**
2. **AND THE NAME WOULD BE REFUSED ANYWAY.** `EVENT_CATALOGUE` carries **ten** names, derived by counting them at the moment this line was written, and **not one of them begins `breaker.`**. [ADR-159](ADR-159.md) clause 1 makes the registry the authority for a name, so `buildEvent` would throw at the NAME before it read the payload. Amending a frozen registry is an ADR and is not inside this fence.

**AND THE REFUSAL COSTS THE WHOLE RUN, WHICH IS WORSE THAN THE DETECTOR CASE ONE DIRECTORY OVER.**

[ADR-349](ADR-349.md)'s runner opens a transaction **per detector** and `runOne` catches, so a refusing sink there costs one detector and the report names it. **`evaluateBreaker` OPENS ONE TRANSACTION FOR THE WHOLE RUN** (`ADR-006`: the alert commits with the row that changed state or neither does) **AND CATCHES NOTHING.** A single refused emit rolls back every `plan_breaker_state` row the run had written and the call rejects.

**AND THE FIRST RUN OF THIS JOB EMITS FOR EVERY ACTIVE PLAN.** `stateChangedEvent` returns `null` only when `previousState === state`. On a plan's first evaluation `previousState` is `null` while `state` is one of the four `0016` admits, and `null` is never equal to a state, so the event is built. **A deployment holding the composed value therefore writes NOTHING on its first night**, rather than writing rows that go quiet later. `test/breaker-adapter.test.ts` case 5.2 asserts the `from_state: null` that makes this true, and case 5.1 asserts the loss.

### 4. Ruling 2: the clock, and the finding that forced the factory to be `async`

**`tradingDayOf` IS SYNCHRONOUS AND THIS DEPLOYABLE HAS NO SYNCHRONOUS SOURCE FOR WHAT IT RETURNS.** That is the ruling the writing forced, and it was not in the dispatch.

`ports.ts` says the day is *"Supplied, never derived"*, and [ADR-146](ADR-146.md) clause 4 forbids meeting an exchange CT trading day with a UTC calendar date derived from an instant. The one anchored source in this deployable is `anchorLastClosedDay`, which reads `trading_calendar` **and** `trading_calendar_loads` in one transaction and comes back with a coverage verdict ([ADR-277](ADR-277.md)), **and it returns a promise**. A synchronous member cannot await it.

**THREE WAYS OUT, AND ONLY ONE OF THEM IS HONEST.**

1. **Derive the day from the instant.** Forbidden by `ADR-146` clause 4 and by `ports.ts`'s own header, which says in terms that a job doing this would be inventing a calendar. **REFUSED.**
2. **Widen the port to `Promise<string>`.** That is a change to a money-path port declaration in service of its adapter, and it would ripple into `DigestIo`, which declares the same member with the same signature. A port reshaped to suit the first thing that tried to fill it is the tail wagging the dog. **NOT TAKEN**, and recorded as an option in section 8.
3. **Anchor once, before the value exists.** **TAKEN.** The factory is `async`, resolves the day for one instant, and closes over it.

**AND THE SAME INSTANT BECOMES `now()`, WHICH IS NOT A CONVENIENCE.** `ports.ts` states that `evaluated_on`, the window's lower bound and every override-expiry comparison all derive from `now`, so a second reading of the clock would compute a thirty-day window against a day it was not anchored to. `job.ts` anchors the nightly batch the same way, from `io.now()` and once.

**`tradingDayOf` REFUSES ANY OTHER INSTANT RATHER THAN IGNORING ITS ARGUMENT.** A closure returning its one day for every input would be a function whose parameter is a lie, and the lie would be invisible: a later caller passing a different instant would receive a day anchored to something else and no test could see it. Case 3.3 asserts the refusal and case 3.2 asserts that `now()` hands back a fresh `Date`, so a caller that mutated the value it was given cannot move the anchor.

**THE CALENDAR REFUSES RATHER THAN FALLING BACK.** An empty calendar is not an unbroken holiday ([ADR-042](ADR-042.md) F-4) and a day without a coverage verdict is not a day (`ADR-277`), so the factory rejects with `BreakerCalendarRefused` instead of handing back a value whose `tradingDayOf` invents one. Cases 3.5 and 3.6 assert both refusals. **Case 3.4 is the one that matters**: `AT` is `2026-08-30` and the answer is `2026-08-28`, so a derived-from-the-clock implementation returns a different string and fails.

### 5. Ruling 3: the adapter is written and the job is NOT scheduled, on three blockers

**`unscheduled` WITH A MEASURED REASON IS A COMPLETE OUTCOME AND THIS IS ONE.** Wiring and scheduling are two decisions and this row takes only the first.

**BLOCKER 1: the event sink.** Section 2. Not an adapter, and not inside this fence.

**BLOCKER 2: `OQ-M6-02` IS UNANSWERED AND THE EVALUATOR DECLINES BEFORE IT DOES ANYTHING.** `LOSS_RATIO_POLICY.minSample` ships `state: 'unstated'` with `value: null`, and `resolvePolicy` runs **before** `io.now()` and **before** `io.transact`, so the decline costs no unit of work at all. Case 6.1 asserts that the door opened no transaction beyond the factory's own calendar read. A breaker running without a floor is `AS-M6-02` produced deliberately: **a floor of zero is refused by `min_sample > 0` at the database, and a floor of one pauses the firm's newest plan during its launch week on a sample of one.** No number is invented here. It is the founder's and it is section 8's first open question.

**BLOCKER 3, WHICH IS NEW, IS MINE, AND IS RULED NOWHERE IN THE CORPUS.**

`0016_treasury_controls.sql` keys the table `PRIMARY KEY (plan_id, evaluated_on)`. `BreakerTx` publishes a plain `insert` with **no upsert and no `onConflict`**. `CRON_INVENTORY` schedules this job **daily at 09:00 CT**. And `evaluated_on` would carry the **last closed trading day**, which is what `tradingDayOf` means where the corpus defines it: `digests/ports.ts` says so in terms, and it is the only reading `anchorLastClosedDay` can serve.

**THOSE TWO CADENCES DISAGREE ON EVERY NON-SESSION DAY.** Run daily at 09:00 CT across a weekend and Saturday, Sunday and Monday morning all anchor to Friday. The second run computes a **different** thirty-day window, because the window's lower bound is `now - 30d` in instants while the key is a day, and Postgres refuses it on the primary key. The run is lost, and `evaluateBreaker` holds one transaction for every plan, so **the whole night is lost rather than one plan's row.**

**`ports.ts` ANTICIPATES A NEIGHBOURING CASE AND NOT THIS ONE**, and the difference is the finding. Its `BreakerTx` header rules that two **concurrent** runs on the same plan-day contending on the primary key is correct, *"because both computed the same day from the same rows"*. That sentence is true of a race and **false of a weekend**: the second run computes the same day from **different** rows. So the existing ruling does not cover this and must not be read as covering it.

**WHAT `evaluated_on` MEANS IS A FOUNDER RULING AND IS NOT TAKEN HERE.** It is section 8's second open question, with its options. The dead-man switch reads *"a plan with no `plan_breaker_state` row for the day"*, and which day that is depends on the same unmade ruling.

**A clock in front of this job today is a process that declines every night, and would page every weekend if the decline were lifted.** That is [ADR-239](ADR-239.md)'s defect in its other direction and the disposition stays `unscheduled`. `schedule.ts`'s row now names all three, with its original sentence kept beside its correction per `RI-14`.

**THE FOURTH PARTY IS THE ONE WORTH ADDING: M06 CARRIES THE NAME THE CODE EMITS, WITH ITS EXACT PAYLOAD, MARKED NEW.** So `ports.ts` did not invent the name. It transcribed an approved module plan. What never happened is the fold into `EVENTS.md`, and **M06's own text shows it knew that**: three rows above, for a different gap, it declines to name an event because *"naming the event here would claim in a registry this session does not own"*. `breaker.state_changed` is marked NEW in exactly that registry-it-does-not-own sense and the claim was never made.

**AND THE TWO ARE NOT INTERCHANGEABLE, WHICH IS WHY THIS IS NOT A RENAME.**

1. **THE REGISTRY'S PAYLOAD HAS NO `sample_size` AND NO `min_sample`.** `AS-M6-02`'s whole counter is that an alert omitting the sample size *"invites exactly the override that destroys the control"*, and `M06:265` makes both fields REQUIRED for that reason. Renaming the code to `circuit_breaker.tripped` **deletes a stated safety requirement**.
2. **A `tripped`/`reset` PAIR CANNOT EXPRESS A FOUR-STATE MACHINE.** `0016`'s `CHECK` admits `armed`, `paused`, `insufficient_data` and `manually_overridden`. A transition into `insufficient_data` is neither a trip nor a reset, and `insufficient_data` is first class and **must never be alarmed** (`GS-113`). The registry pair has nowhere to put it.

**THIS ROW RULES NOTHING HERE AND SAYS SO.** [ADR-159](ADR-159.md) clause 1 makes the registry authoritative for a name, which points at `circuit_breaker.*`; `AS-M6-02` and `GS-113` point at `breaker.state_changed`; and amending a frozen registry is an ADR rather than a commit. **It is section 8's third open question, with both options and their costs.** Case 6.2 pins all four parties as assertions rather than as prose, so the divergence cannot close quietly on one side.

### 8. The open questions this row records and does not answer

**NO THRESHOLD, CAP OR INTERVAL IS INVENTED HERE.** The one number the corpus does state, the daily 09:00 CT cadence, is read from `CRON_INVENTORY` rather than chosen.

1. **`OQ-M6-02`: the minimum sample.** Unanswered since M06. **Options:** (a) state a floor, and the breaker can run; (b) leave it unstated, and the evaluator declines forever, which is what it does today. There is no third option that is not inventing a number, and both bad inventions are already ruled out at the database and by `AS-M6-02`. **The founder's.**
2. **What `evaluated_on` means.** **Options:** (a) the **calendar date of the run**, which makes a daily job idempotent under the primary key and puts a date on the row that is not a trading day, contradicting `tradingDayOf`'s type and every other use of the term in this estate; (b) the **last closed trading day**, which is what the corpus defines and what this adapter serves, and which collides on the primary key on every non-session day; (c) keep (b) and make the write an **upsert**, which needs a ruling on whether a later run may overwrite an earlier day's verdict, and interacts with the override-expiry exemption because *"the override lapses by being recomputed"*. **The founder's, and it blocks scheduling.**
3. **`breaker.state_changed` versus `circuit_breaker.tripped`/`.reset`.** **Options:** (a) fold `breaker.state_changed` into `EVENTS.md` as `M06:265` proposes, retiring the pair, which keeps `sample_size` and can express four states; (b) keep the registry pair and reshape the code, which deletes `AS-M6-02`'s required field and has nowhere to put `insufficient_data`. **The founder's**, and section 6 is the evidence. Neither is done here.
4. **`DEP-M6-05`: the CUSUM's `mu_0` and `sigma`.** Untouched by this row and still absent, so the CUSUM still renders ABSENT per [ADR-167](ADR-167.md) clause 5.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **The weakest claim is section 5's third blocker, because it rests on a reading of `evaluated_on` that no document states.** I derived "last closed trading day" from `digests/ports.ts`, which defines the term for a different column on a different table, and from the fact that `anchorLastClosedDay` is the only anchored source available. `breaker/ports.ts` itself says only "the exchange trading day". **If `evaluated_on` is meant to be the calendar date of the run, my third blocker dissolves and the adapter is serving the wrong day**, which is a defect in this file rather than an open question. That is why it is question 2 in section 8 and why the job is not scheduled either way. **The second weakest is section 6's four-way divergence**: I read `EVENTS.md` and `M06` as text and matched names, and a registry row carrying this event under a name I did not think to grep would make the "no row anywhere" half of that finding false.
