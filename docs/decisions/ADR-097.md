### 3. `no-fixture-format` IS THE WRONG TERM ON BOTH ROWS, BY ADR-072'S OWN TIE-BREAK

[ADR-072 section 2](ADR-072.md) states the rule that assigns a term when more than one condition fails:

> **When more than one condition fails, the row carries the blocker that WOULD STILL HOLD IF EVERY OTHER WERE CLEARED.** [...] a blocker naming something that can be cleared while the row stays unwritable is a promise the table cannot keep.

Two of the three conditions fail on both rows. **Run the rule in both directions**, which is the only way it answers:

| Clear this | Does the row become dischargeable? |
|---|---|
| **W2**, by giving M9 a fixture format that can state MDX input and a build expectation | **No.** There is still no build to fail. The row stays exactly where it is |
| **W1**, by [`P4-j`](../plans/P4-portal-and-site.md) landing the MDX pipeline and its lint | **Yes, immediately, and WITHOUT A FIXTURE.** [ADR-076 section 1](ADR-076.md) discharges a row when its assertion is EXECUTED wherever it runs, so the row moves to `covered-elsewhere` citing the check that runs |

**So `no-fixture-format` is precisely the defect the rule forbids, inverted.** It names the half that never binds, on rows where clearing it changes nothing, while the half that does bind sits unnamed. `P4` section 5.3 is right and this entry confirms it by running the ADR's own rule rather than by re-reading its prose.

### 4. THE TERM IS `outside-loader-boundary`, AND WHAT THE WORD "exists" IN IT WAS GUARDING

The W1 term's row-condition reads *"The code the assertion runs against **exists** and lives outside `@merit/rules-engine`"*, and that word is the whole reason a seventh term looks necessary. **It is a guard against a term ADR-072 refused, not a condition on the row**, and the entry says so itself three ways.

1. **W1's own check column is implementation-independent, in ADR-072's words:** *"Read the imports of [`golden-loader/src`](../../packages/golden-loader/README.md). A symbol in `apps/worker` or `packages/rithmic` fails W1 **whether or not it is implemented**."* [Section 39](../testing/golden-scenarios/39-fixture-status-and-blockers.md) quotes that same sentence as W1's operative reading when it explains why `writable` now holds no row. **The CONDITION does not turn on existence and never did.**

2. **A term names which condition fails and by what mechanism** ([ADR-072 section 2](ADR-072.md)). The condition is W1. The mechanism is the golden loader's import boundary. **Both are true of these two rows exactly and permanently**: no version of a loader that imports `@merit/rules-engine`'s public entry point and nothing else will ever reach an MDX pipeline in `apps/site`.

3. **"exists" separates this term from `no-module-code`, which ADR-072 refused BY NAME**, and the refusal is scoped in its own sentence to *"the 229 rows it would have covered"*. Its reason is that for those rows the code's absence *"is not the binding half"*, **because [ADR-048](ADR-048.md) lets a fixture be written before its rule exists**: a fixture citing an undeclared rule *"loads, derives inverted, and flips on its own when the rule lands."*

**ADR-048 IS THE DISCRIMINATOR AND IT DOES NOT REACH THESE TWO ROWS.** Inversion is polarity over the rule identifiers a fixture cites, against the set the engine exports. **A row whose expectation is a tool's refusal cites no rule, loads nothing, derives nothing and has no polarity.** So the artifact's absence is not the half that clears first here; **it is the only half**, and the guard was never written against a row of this shape.

**The test that separates the two terms is therefore not *"does the code exist"*, which is `no-module-code`'s test and is refused. It is one question, asked per row:**

> **Would a fixture format for this module, if one existed, discharge this row?**

**Yes for the 227, which is exactly what they are waiting for. No for these two, and no for any format anyone could write**, because the expectation is an exit code and not an end state.
