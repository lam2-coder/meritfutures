## ADR-046: `CalendarSlice` is a value, and a lookup miss is a typed refusal  (2026-08-16, status: accepted)

**[P2 section 1](../plans/P2-rules-engine.md) is the analysis and this ADR records the ruling. `OQ-P2-01`, closed.**

- **Context:** **[M01](../plans/M01-rules-engine.md)'s reference algorithm calls a function it never supplies.** `applySettlement` computes `consistencyPeriodStartDay: nextTradingDayAfter(fact.basisTradingDay)` (section 3.6, R-47), and R-37 counts the cadence gap by sequence subtraction from `cadenceAnchorDay`, **a day that may be months old**. But `DayInput.calendar` is a single `CalendarDay` and `replay` passes `calendar.get(mark.tradingDay)`, one row. **Neither rule can be computed from one row.** `CalendarSlice` appears in the `replay` signature and is defined nowhere.

  This is a gap in an approved document rather than an implementation detail, which is why it is an ADR and why it lands before `P2-1` writes a line of engine code.

### The ruling

> **`CalendarSlice` is a VALUE, not an interface.** A frozen ordered array of `CalendarDay` plus a precomputed index and a declared coverage interval, built by a pure exported constructor, with the calendar queries as free functions in `calendar.ts` over that value.

**The three purity mechanisms cannot see the alternative, and that is the whole argument.** [`merit/engine-purity`](../../packages/eslint-plugin-merit/rules/engine-purity.js) bans every non-relative import and every clock spelling; `RI-01` asserts the manifest declares no workspace dependency; the `RI-01` manifest check reads the same. **None of the three sees an interface whose implementation reads a database.** An interface carrying `get()` and `nextAfter()` is a **capability**: a caller could satisfy it with a live query, with a memoiser, or with something that consults the clock, and every mechanism would stay green while the engine's output became a function of what the caller happened to do. **A value has no behavior to smuggle.**

`merit/engine-purity`'s own header already says this in advance: it reads one file at a time with no type information, so a nondeterministic value **passed in as an argument** is invisible to it. This ruling is what keeps that gap from being the one P2 walks through.

### The fourth mechanism, and it belongs here because the other three cannot cover it

**`types.ts` already asserts `PlanConfigVersionIsClosed` with a compile assertion**, and the same idiom extends: assert that `CalendarSlice` has **no function-valued property**.

That makes "the calendar is data" a **compile error rather than a review note**, in the file that already carries the shape. It is the mechanism the existing three are missing, and it costs one type alias.

### What a lookup miss does, which is the load-bearing half

Replay **will** ask for the sequence of an anchor older than the slice. That is not an edge case; it is what a months-old `cadenceAnchorDay` means.

| Answer | Verdict |
|---|---|
| **Throw** | **Rejected.** The fold's behavior would depend on how much calendar the caller loaded, which is **a caller decision leaking into engine output**. Two callers with different windows would get different answers for the same account and the same day |
| **Return null and let the gate pass** | **Rejected outright.** It silently weakens **R-37, a money gate**. A cadence gap that cannot be computed and is scored as satisfied is a payout released early, and nothing raises |
| **A typed refusal into `DayOutput.assertions`** | **Adopted.** Identical to `DO-3`'s `INV-18` handling: **no state is written for the day, reconciliation is raised, and nothing throws** |

**The coverage interval is not an invention and this ruling does not introduce a second idiom.** The fixture calendar already declares one and the loader enforces it (`L-08`), and [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql) makes an uncovered day a **positive unknown** under [ADR-042](ADR-042.md) F-4. A day outside coverage is `unknown` rather than `not a trading day`, in the database and now in the engine, **because those two answers differ and only one of them is safe to act on.**

- **Consequences:** `DayInput` is widened in an approved document: `calendar` becomes a `CalendarSlice` rather than a `CalendarDay`. [M01 section 2.1](../plans/M01-rules-engine.md) records the widening and this ADR is the authority for it. `calendar.ts` gains the constructor and the free functions; `types.ts` gains the no-function-valued-property assertion beside `PlanConfigVersionIsClosed`. **`DayOutput.assertions` gains a calendar-miss variant**, which every consumer of the assertion channel already handles because `INV-18` put one there first. **The slice is built by the caller and the caller decides its window**, so the batch loads a window wide enough for the oldest anchor it will fold against; a window that turns out too narrow produces refusals and a reconciliation, never a wrong number.

- **Alternatives considered:** **an interface with injected implementations** (rejected above: it is a capability, and the three purity mechanisms are blind to it); **passing the whole calendar** (rejected: it makes every fold's cost a function of the calendar's age rather than of the account's history, and B.5 already budgets 1.25M day evaluations inside a 10 minute window); **a memoised lazy loader** (rejected: it is the interface with a performance argument on top, and it makes the fold's output depend on cache state); **computing the sequence arithmetically from the day** (rejected: that is B4 #1 exactly, the trading day is data and never arithmetic, and it is wrong on roughly 104 days a year); **throwing on a miss** (rejected above, and it is the option a reader will re-derive under pressure because it feels strict: it is strict about the wrong thing, since it makes the caller's window a determinant of engine behavior).
## ADR-046: A contact address is held reversibly, and the notification obligation is discharged by evidence  (2026-08-16, status: accepted)

**This closes `OQ-M10-06`, raised by the session that folded [ADR-039](ADR-039.md)'s two egresses into [M10](../plans/M10-integrations.md). It is a proven gap in a shipped control rather than a design preference: [`EC-146`](../edge-cases/EC-146.md) records it, [`GS-265`](../testing/golden-scenarios/34-gs-258-to-gs-272-phone-identity-and-the-authority-boundary.md) is written to fail against it, and the [privacy policy](../legal/PRIVACY_POLICY.md) tells counsel the question is open.**

- **Context:** `INV-M16-03` is the account-takeover countermeasure: when a contact changes, notify the **prior** contact for a window. [SECURITY section 4.8](../architecture/SECURITY.md) leg 2 is the same control one document over, and [ADR-039](ADR-039.md) (c) makes it a precondition of a phone change. **Nothing in the schema held an address any of them could send to.**

  **The claim, checked against the migrations rather than recalled.** There was no plaintext telephone number in any of the thirty-three migrations. `identity_phones.phone_hash`, `phone_change_requests.new_phone_hash`, `otp_challenges.destination_hash` and `contact_channels.value_hash` are all one-way, and `identity_phones.phone_preview` is deliberately "enough to recognise, not enough to reconstruct". `users.email` is plaintext and is one column on one row, so a change **overwrites** it and the prior address survives only as a hash.

  **Every one of those columns is one-way on purpose, and the reasoning in each comment is correct.** A second plaintext copy of every address a trader ever used buys nothing and costs a breach. **What follows from it is not what those comments assume.** Both [`0019`](../../packages/db/migrations/0019_notifications_and_community.sql) and the [`contact_channels`](../architecture/data-model/contact_channels.md) design record say the value is hashed because **"the sending path holds the address"**. The sending path is [M10](../plans/M10-integrations.md). M10 holds nothing, by `INV-M10-02` and `INV-M10-03` and by the deliberate absence of any table in that module that stores a contact value, and it may not delegate the holding to a vendor because `AS-M10-06` part 3 forbids a vendor being the system of record for content a trader must receive. **Two documents named a holder that does not exist.**

  **The sharpest version, and the one that made it invisible.** `phone_change_requests_applied_is_complete` makes `prior_notified_at` a precondition of reaching `applied`, so the database refuses a change that did not notify. **The database can only assert that a timestamp exists.** A handler with no address and a column it must fill will fill it, the constraint passes, the ceremony looks enforced, and the notification that is the entire anti-takeover control never leaves the building. `SD-M16-06` widened `contact_channels.kind` to accept `sms` and made the countermeasure **representable**; it did not make it **sendable**, and the difference is the finding.

### The ruling

**Founder ruling, 2026-08-16.** The plan in [M10 section 7.9.4](../plans/M10-integrations.md), approved as written:

> **Store the address reversibly rather than not at all**: a `value_ciphertext` beside the existing `value_hash`, envelope-encrypted under a key only the dispatcher can use, with the hash kept for matching and uniqueness. It touches `contact_channels`, `identity_phones` and `phone_change_requests`.

**With one amendment, given at the same sitting:**

> **`merit_dispatcher` gets SELECT and INSERT. Not DELETE.** Erasure is a privacy operation, not a send operation, and a compromised send-path role with DELETE can destroy the addresses the anti-takeover control depends on. **UPDATE stays for rotation.**

[`0034`](../../packages/db/migrations/0034_reversible_contact_addresses.sql) is that plan and that amendment.

| Change | What it is |
|---|---|
| Three sealed columns per table | `*_ciphertext`, `*_key_id`, `*_encrypted_at` on `contact_channels`, `identity_phones` and `phone_change_requests`, each with a completeness `CHECK`, a **plaintext floor** and a partial index serving the rotation sweep |
| `merit_dispatcher` | The fourth role. [`0026`](../../packages/db/migrations/0026_roles_and_grants.sql) created three and none of them is a sending path, and you cannot withhold DELETE from a principal the database cannot name |
| The evidence foreign keys | `prior_notified_at` may not be set without citing **both** legs: an `integration_dispatches` row and a `notifications` row, both `ON DELETE RESTRICT` |
| The identity-match trigger | The cited evidence belongs to the **same identity** as the request. Separately rejectable, see below |

### Reversible is a smaller concession than it looks, and the goal it preserves is stated exactly

**The stated goal was never "no address exists". It was that a database dump does not yield a usable address**, and envelope encryption preserves that goal exactly: the row holds ciphertext and the identifier of the key that sealed it, and **the key is not in this database**. A dump yields the same nothing it yielded before.

**What changes is who can ask.** A key manager can answer the dispatcher and refuse everybody else, which a hash can do for nobody, and the answer is auditable in a way a hash's silence is not.

**The key identifier references no table here, on purpose.** A key registry in the same database as the ciphertext is one dump away from being a key ceremony.

### The seal is asserted rather than assumed, which is `INV-M10-12` becoming a constraint

**Founder ruling, 2026-08-16, at the same sitting.** The redesign above is approved as written: ciphertext columns on the existing tables rather than a side table, the SMS evidence pointing at a dispatch record rather than a notifications row, both evidence foreign keys, the identity-matching trigger, and no `DELETE` grant on `merit_dispatcher`. **What was missing was the plan's sharpest mechanical assertion:**

> `CHECK (octet_length(<col>) >= 29)` on each of `value_ciphertext`, `phone_ciphertext` and `new_phone_ciphertext`, guarded so it applies only when the column is not null. Twelve bytes of nonce, sixteen of GCM tag, at least one of ciphertext. **A raw E.164 number is at most 16 bytes, so the constraint structurally refuses a plaintext address smuggled in as `bytea`.**

**It is the difference between `INV-M10-12` being a constraint and being a promise.** `INV-M10-12` says a telephone number exists in plaintext **in a request body and never at rest**. Nothing else in `0034` enforces that: every sealed column is `bytea`, **every byte string is a valid `bytea`**, and a handler that skips the seal and writes the number itself satisfies the completeness `CHECK`, the uniqueness indexes and the foreign keys. Nothing objects, the row reads as sealed to every reader and every catalogue query, and **the failure surfaces at decrypt time with the address sitting in the clear at rest for however long that takes.** That is precisely what the invariant forbids, and it is the failure mode a review cannot see because the schema looks right.

**The reach is stated exactly rather than rounded up**, on this ADR's own discipline about overclaiming the withheld `DELETE`. `contact_channels.kind` is `('email','push','sms')`, so that column also holds email addresses and push tokens and **a plaintext email of 29 bytes or more clears the floor**. The refusal is **total for telephone numbers**, which is the class `INV-M10-12` names and the class `OQ-M10-06` was about, and **partial on `contact_channels` for the other two kinds**. On `identity_phones` and `phone_change_requests` the column holds a telephone number and nothing else, so there it is total.

**It is a floor rather than an equality**, so a scheme with a longer nonce or a second tag stays inside it and no future change has to edit a merged migration to fit.

**It is a separate constraint rather than a clause inside the completeness `CHECK`, and the reason is the probe.** A write can violate both at once, and PostgreSQL reports one of the two in an order it does not document. [`DELTA_MANIFEST` section 18](../../packages/db/DELTA_MANIFEST.md) already records two assertions, in a probe written before `0034`, that were resting on exactly that undocumented order. Named separately, every assertion names the constraint it is actually watching.

### `merit_app` can read the ciphertext, and that is stated rather than left to be discovered

**The key is the control, not the grant.** `merit_app` holds table-level SELECT on everything ([`0026`](../../packages/db/migrations/0026_roles_and_grants.sql)) and it can read every sealed column added here. It cannot decrypt one.

**A column-scoped revoke was considered and PostgreSQL cannot express it.** A table-level SELECT implies every column, and `REVOKE SELECT (col)` against it is a no-op that **looks like a control**. Scoping `merit_app`'s read means revoking the table grant and re-granting column by column, which is a hand-maintained column list, which is the object [ADR-034](ADR-034.md), [ADR-036](ADR-036.md), `0026`'s revoke list and every hand-maintained count in this corpus have already cost us.

**The exposure it would close is also smaller than it looks.** `merit_app` is the role that already handles a number in plaintext at registration, because the trader types it into the request. **If the founder wants the grant rather than the key to carry this weight, the shape that gets it is a sidecar table keyed by the row id**, and that is a different migration and a different ADR. It is named here so the decision is visible rather than inferred from an absence.

### What the withheld DELETE buys, stated without overclaiming it

**It protects the row.** The `value_hash` `INV-M16-03` matches on, the supersession lineage that makes a **prior** contact addressable at all, and the evidence rows below.

**It does not make an address indestructible**, and saying that it does is how the next reader stops looking. UPDATE stays, because rotation needs it, and a role that can rewrite a ciphertext can blank one. **Row destruction and value destruction are different losses and only the first is closed here.**

**The grant is column-scoped to the rotation columns**, which is narrower than the amendment's words. Rotation rewrites the sealed value and the key that sealed it and touches nothing else; table-wide UPDATE would additionally let the sending path clear a `verified_at`, rewrite a supersession pointer, or blank a `value_hash`, none of which is rotation and all of which disarm `INV-M16-03` without deleting a single row. **If the founder meant table-wide UPDATE the widening is one word per line**, and it is called out because a grant narrower than its ruling is still a departure from it.

**The three tables are not append-only and must not be read as such.** When an erasure path exists it gets its own grant to its own role. **Erasure is expressible today without DELETE**, and that is what makes withholding it defensible rather than merely strict: clearing the three sealed columns leaves the hash, the lineage and the evidence standing, which is the only erasure that does not also disarm the countermeasure through the privacy path. The probe's `S4` is that assertion, and a `NOT NULL` on any of the three would have made DELETE the only way to erase, on the tables that no longer have it.

### The obligation is discharged by evidence, which is EC-146 made structural

[`EC-146`](../edge-cases/EC-146.md) already ruled the remedy in words: **a notification obligation is discharged by a dispatch record, never by a timestamp.** `0034` is that sentence as a constraint. `prior_notified_at` stops being a claim and becomes a citation, and a handler with no address produces no dispatch and therefore cannot advance the request.

**Two tables, because the two legs are different objects.** The email leg is a `notifications` row. **The SMS leg cannot be one**: `notifications.channel` is `CHECK (channel IN ('in_app','email','push'))` and [`0029`](../../packages/db/migrations/0029_phone_identity_and_auth.sql) declined to widen it, because `notifications.identity_id` is `NOT NULL` and a pre-identity message cannot be a `notifications` row at all. Its record is an `integration_dispatches` row, which is the pairing `0029`'s own comment already states for the OTP path.

**The `CHECK` is one-directional and the other direction is deliberately left open.** A claim with no evidence is refused; evidence with no claim is permitted, because the two legs do not land in the same instant and a biconditional would force a handler that has sent one to either discard the citation it holds or assert a notification it has not made. `phone_change_requests_applied_is_complete` has exactly this shape and for exactly this reason.

**`ON DELETE RESTRICT` on both, which means a cited notification can never be deleted.** That is correct: it is evidence, and evidence a retention job can remove is evidence for exactly as long as nobody needs it. **And it collides with any future retention sweep on `notifications`**, which will find rows it cannot delete and must be written to expect that rather than to treat it as a bug. It is recorded here and in the migration because the sweep does not exist yet and its author will not read either.

### The identity-match trigger, which is one assertion more than the ruling names

**Stated separately because it is separately rejectable**, on [ADR-045](ADR-045.md)'s precedent for the counted half.

**A foreign key proves a row was cited and nothing more.** Without this, the two columns can cite **any** dispatch and **any** notification in either table, and the strongest reading of the control collapses to "a message was sent to somebody". A `CHECK` cannot say otherwise, because it may not read another table. So it is a trigger, in [`0027`](../../packages/db/migrations/0027_triggers_invariants.sql)'s idiom: it asserts and it never repairs.

**It uses `IS DISTINCT FROM` and that is the whole of it.** `integration_dispatches.identity_id` is nullable, because [`0018`](../../packages/db/migrations/0018_integrations.sql) rules that not every dispatch is about a person. Written the obvious way, `evidence_identity <> NEW.identity_id` yields `NULL` against an unattributed dispatch, `NULL` is not `TRUE`, and **the one check that exists to attribute the evidence would wave through the least attributed row in the table.** The probe's `R9` is what watches that, and the seeded run confirms it is the only assertion that fails when the comparison is written the obvious way.

**Reject this half if the ruling is read narrowly.** The foreign keys and the `CHECK` stand without it.

### What is still not enforced, named rather than implied

**The database cannot assert that the notice was ADDRESSED to the prior channel**, which is the wording `GS-265` uses. `integration_dispatches` records `fields_sent` and never values (`INV-M10-03`), so **no column anywhere holds the destination of a dispatch**, and adding one would make the audit record of a disclosure into a second copy of the thing disclosed. The limit is structural and it is left standing rather than papered over. What `0034` closes is that the citation must exist and must belong to this identity.

**`otp_challenges` is deliberately untouched.** An OTP is a challenge-response flow: the trader types the number into the request, so the address is held by the request and is deliverable today. `destination_hash` stays one-way. **The exposed class is every message Merit itself initiates**, and those are the three tables `0034` changes.

**No gate can tell a storage-enforceable control from a send-enforceable one**, which `EC-146` already says and which remains true. `0034` moves this control one layer up and does not build the gate.

### Consequences

- **The privacy description moves and counsel must see it.** The [privacy policy](../legal/PRIVACY_POLICY.md) tells counsel that Merit's contact addresses are stored as one-way hashes and that whether that survives contact is this question. It does not survive contact for the three tables here, and the retention description for that category changes with it.
- **A key manager is now a launch dependency.** There is no envelope without a key encryption key that lives outside this database, and `DEP-M10-08` stops being unowned.
- **A backfill exists and is not in this migration.** Every row written before `0034` has a hash and no ciphertext, which is the state the whole corpus was in until today: a prior contact Merit can recognise and cannot reach. Sealing them requires the plaintext, which for a prior address Merit does not have, so **the backfill is forward-only by construction** and the addresses already lost stay lost.
- **A future retention sweep on `notifications` will hit rows it cannot delete.** Above.
