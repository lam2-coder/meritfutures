## ADR-342: the withdrawal backend is complete, is still not installed, and the reason it is not is moved out of a nine-times-corrected paragraph into three findings a runner executes; and the one blocker that paragraph never named turns out to be this deployable's own (2026-09-05, status: proposed)

**THE ROW WAS DISPATCHED TO INSTALL `databaseWithdrawalBackend` AND THE INSTALL IS REFUSED.** The refusal is not about the adapter. **The adapter is whole**: every one of `WithdrawalTx`'s eleven members is served, the lock is real and first, every read and write goes through `db.scoped`, and there is no float on any arm. A session reading the port and the adapter alone would conclude that one line in `start.ts` is all that separates this route from service, and would be wrong for a reason neither file states.

**WHAT SEPARATES IT IS THE ESTATE PAST THE INSERT, AND ONE THING INSIDE THIS DEPLOYABLE THAT NO ENTRY HAD EVER NAMED.** `POST /wallet/withdrawals` and `POST /wallet/withdrawals/:withdrawalId/cancel` both declare `required: 'passkey or dual_channel'`, `authorize` refuses a non-elevated session **before any handler body runs**, and `databaseAuthBackend` declares `elevate` **blocked on both arms**. So no session in a deployment can be elevated, no request reaches this port at all, and the 503 the unwired backend produces **is itself unreachable**. An install would change no response any client can observe.

**THAT IS AN ARGUMENT AGAINST INSTALLING RATHER THAN A REASON IT IS HARMLESS**, and it is this entry's own finding rather than the dispatch's.

### 2. The adversarial read of the adapter, which the dispatch asked for first

**IT IS SOUND, AND THE SPECIFIC THINGS THAT COULD HAVE BEEN WRONG WERE CHECKED RATHER THAN ASSUMED.**

1. **THE LOCK IS FIRST AND EVERY GATE IS UNDER IT.** `decideWithdrawal` calls `tx.lockScope()` before it reads anything. This is the whole control: `G-NO-IN-FLIGHT` is an application check over a **non-unique** index, so without the lock two concurrent requests both read an empty in-flight set and both insert.
2. **THE FIFO COMPOSITION CONSUMES DEBITS.** `unspentLots` walks credits and debits in `(occurred_at, id)` order and lets debits eat the oldest lots, so a wallet that spent its payout does not compose a withdrawal out of money already gone. The `id` half of the sort is load bearing: `wallet_entries` has no unique constraint on the instant.
3. **IT CROSS-CHECKS ITSELF AGAINST THE STORED RUNNING BALANCE AND REFUSES ON DIVERGENCE**, which is the fail-closed direction on the door that pays.
4. **MONEY IS `bigint` THROUGHOUT.** `parseFloat`, `toFixed`, `Math.round`, `Math.floor` and `Math.ceil` occur **zero** times as calls in this module; the sole textual match is a comment explaining why rounding is banned here. `centsFromJson` returns `null` for a non-integer and for an unsafe integer, so `5.5` is a `validation_failed` and never a round. Every `number` in the file is a JSON wire field, an HTTP status, a comparator result or a millisecond window.
5. **THE ORDER OF THE COOLING GATE IS RIGHT AND IT MATTERS IN ONE DIRECTION.** `register` writes a row and `first_seen_at` is immutable under `PAYOUT-DEST-C1`, so every other refusal is decided first and a refusal after the write is **thrown** so the transaction rolls back.
6. **AN ABSENT DESTINATION IS "REGISTER IT AND COOL IT"**, which is `0051`'s obligation on this slice by name, and the first destination an identity ever uses is cooled too.

**THE TWO WEAKNESSES THE MODULE ALREADY REPORTS ARE REAL AND ARE NOT THIS ROW'S TO FIX.** `wallet_withdrawals_approved_has_provenance` is satisfied by `'[]'::jsonb`, so the CHECK does not enforce what its name says; the module never writes an empty array, and the gap is in the DDL. And `withdrawableCents` equals the balance because **no hold in this corpus has a computable input**, which `wallet.ts` states identically on the read leg.

**SO THE HEADLINE IS NOT "THE ADAPTER IS HALF-WRITTEN".** It is that a complete adapter and an installable adapter are different things, and nothing in either file said so.

### 4. THE HEADLINE FINDING: the route is unreachable, and that is why installing is worse than not

**C-27 REFUSES EVERY CALLER BEFORE THIS FILE'S HANDLER RUNS.** `endpointHandler` calls `authorize(session, spec.required)` and returns 403 on `forbidden` **before** `spec.handle`. Both withdrawal rows declare `passkey or dual_channel`, which `authorize` admits only for an elevated session.

**AND NO SESSION CAN BE ELEVATED IN A DEPLOYMENT.** `databaseAuthBackend` is installed by `start.ts`, and it declares `elevate: blocked(...)` on **both** arms: the passkey arm for an absent WebAuthn ceremony, the `dual_channel` arm for absent SMS delivery. `ElevationFactor` refuses `sms_otp` at compile time, so these two are the only members there are.

**THE CONSEQUENCE, STATED PLAINLY.** Today the route answers **403** to every caller. The 503 this port is famous for is produced by code no request reaches.

**THE DISPATCH READ THIS AS A CAVEAT AND IT IS THE DECIDING FACT, IN THE OPPOSITE DIRECTION FROM THE ONE IT SUGGESTS.** The tempting reading is that installing is therefore free. It is the reverse:

1. **AN INSTALL NOTHING EXERCISES IS AN INSTALL NOTHING FALSIFIES.** No client, no e2e pass and no deployment could distinguish the wired port from the unwired one, so the first request it ever serves would be its first test.
2. **IT WOULD ARM ITSELF SILENTLY.** The day an unrelated row lands a WebAuthn ceremony or an SMS sender, the cash door opens as a **side effect of an auth slice**, carrying no signal that it had done so. That row would be reviewing an elevation factor, not a withdrawal path.
3. **THAT IS THIS ROW'S OWN SUBJECT ARRIVING FROM THE OTHER SIDE.** The branch is named for an adapter nobody installed. An install nobody notices is the same defect with the sign flipped, and it is the worse one, because the first is visible as a 503 and the second is visible as a payout.

**THE GATE IS NOT WEAKENED TO REACH THE ROUTE.** Nothing here relaxes `required`, and no second refusal is added either: C-27 is the authentication boundary and this module has always deferred to it.

### 5. What actually refuses, re-derived, and it is one deployable over

**THE APPROVAL EDGE HAS A DRIVER, A LEDGER BUILDER, A POSTING SITE AND A MANIFEST LINE. IT HAS NO IO ADAPTER AND NO CLOCK.**

- `UNWIRED_WITHDRAWAL_APPROVAL_IO` is the **only** `WithdrawalApprovalSweepIo` in the tree and refuses every call.
- The job is registered in `apps/worker/src/schedule.ts` with `disposition: 'unscheduled'`.
- `apps/worker/src/index.ts` states the condition in its own words: the installation **MUST NOT BE DISPATCHED BEFORE A PAYMENT RAIL EXISTS**, because past `approved` the only arrow is `transferring`, `packages/rail` opens no socket, and `0072`'s `WD-C2` refuses `approved --> cancelled` at the database. **A wired deployment would extinguish a wallet claim into a state with no exit and no cancel.**

**THE RAIL IS FOUNDER-OWED AND IS NOT A SLICE.** So this port waits on exactly the condition its driver waits on, and no engineering session supplies it.

**WHAT A WIRED API WOULD DO ON ITS OWN, IF C-27 EVER OPENED**, stated because it is the honest version of "the creation writes no money": it would create a `requested` or `cooling` row, debit nothing, post nothing, and hold there indefinitely, while `gateNoInFlight` refused that identity's every later withdrawal until they cancelled. **That is a promise Merit cannot keep, told on the screen that says a trader's money is leaving.** A 503 says Merit cannot do this today, which is true.

### 5a. The rail trap, put as three questions after dispatch and answered at the migrations

**A dispatcher addition arrived after this row's work was complete**, naming a hazard it was right to name: with no rail the approval sweep stays unscheduled, so **what happens to a withdrawal an installed door accepts?** Its standing note read that *"the door debits a wallet into `approved`, which has no exit and no cancel"*, and asked that this be verified against the migrations rather than trusted. **It was, and the standing note is wrong about the mechanism.** The conclusion it protects is untouched.

**Q1. DOES `POST /wallet/withdrawals` DEBIT OR HOLD THE WALLET AT REQUEST TIME? NO.** The adapter performs exactly five operations and they are all named: `lockScope()`, one `insert('payoutDestinations')`, one `insert('walletWithdrawals')`, and the two `updateAt('walletWithdrawals')` calls the approval and cancellation edges use. **There is no `insert('walletEntries')` anywhere under `apps/api/src`** -- every occurrence of that key in the deployable is a read or a row-narrowing helper -- and the withdrawal module imports nothing from `@merit/ledger` and posts no ledger transaction. **A created withdrawal moves no money and extinguishes no claim.**

**Q2. WHAT ADVANCES THE ROW, AND WHERE IS THE DEBIT? `apps/worker/src/withdrawals/approval-sweep.ts`, AND THE DEBIT IS THERE RATHER THAN HERE.** Its approval arm runs `updateAt('walletWithdrawals')`, then `io.ledger.postLt06(...)`, then `insert('walletEntries', walletDebitValues(...))`, **all in one transaction with the `approved` transition**. That is `INV-M20-01`'s requirement that every wallet debit be checked against the live position inside the same transaction, and it is why `apps/worker/src/index.ts` calls that job **the first writer of a `wallet_entries` row in this application**. Outside tests the only other writer of a `wallet_withdrawals` row is `apps/worker/src/sweeps/expiry.ts`, which writes the freeze trio and `updated_at` and never `status`.

**Q3. CAN THE TRADER GET IT BACK? FROM THE STATES THIS DOOR CREATES, YES.** `0072`'s `WD-C2` refuses a cancellation only when `OLD.status NOT IN ('requested', 'cooling')`. `CreatedStatus` is exactly `'requested' | 'cooling'`, and `POST /wallet/withdrawals/:withdrawalId/cancel` is served by the same backend, so **every row this door can create sits on the cancellable side of that predicate**. The state with no exit and no cancel is `approved`, and **this door cannot create it**.

**SO THE STRANDING SCENARIO DOES NOT EXIST ON THE REQUEST PATH**, and the hazard as posed is discharged. **THAT DOES NOT MAKE THE INSTALL SAFE, AND THE REASON IS SECTIONS 4 AND 5 RATHER THAN THIS ONE.** What an installed door would produce is a `requested` or `cooling` row that **nothing in this estate can advance**, on a route **no caller can reach** because of `C-27`. The trader can cancel it, and until they do, `gateNoInFlight` refuses their every later withdrawal behind a screen saying one is in flight.

**AND THE ASYMMETRY THE ADDITION ITSELF ARGUES IS WHAT KEEPS THE PORT UNINSTALLED.** *"An unbuilt endpoint is recoverable"*: an uninstalled port is one line away from installed, and a founder overturning section 4 pays that line. **An installed cash door that no request can reach is not reviewable**, because nothing exercises it until an unrelated auth row makes it live. **Leaving it uninstalled preserves both readings; installing forecloses the one this entry is asking to be read.**

**NOTHING HERE SCHEDULES THE APPROVAL SWEEP AND NO RAIL ADAPTER WAS WRITTEN.** Both were named out of fence and both are untouched.
