## ADR-366: the admin wallet port has FIVE members and the entry that blocks it names THREE, the write surface is TWO members rather than one because both appends go through the door nobody counted, and against the unwired default exactly one member is ever consulted (2026-09-06, status: proposed)

**`useAdminWalletBackend` (`apps/api/src/routes/admin-wallet.ts:744`) installs the backend for the surface on which a human being at Merit reads and adjusts a trader's wallet.** An adjustment is a credit or a debit nobody transacted for, so it is the most dangerous admin write in this tree. The row was dispatched to rule the port rather than to repair a sentence.

**THE RULING IS THAT THE PORT REFUSES COMPLETELY AND THAT THE ENTRY DESCRIBING WHY IS INCOMPLETE IN A WAY THAT MATTERS.** No write path is reachable, no figure is quoted and nothing is recorded that a later reader could take as an approved adjustment; all three are asserted as cases against the real default rather than argued. What is wrong is the census: the port declares five members, the `BLOCKED` entry carries blockers for three, and the member it does not name is the one BOTH of this module's appends travel through.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `366`, branch `claude/the-admin-wallet-backend`, session **561**.
- **THE DELIVERABLE IS A RULING AND A SUITE. NO PORT IS WIRED, NO DOOR IS OPENED, NO MIGRATION NUMBER IS TAKEN OR RESERVED, AND NO FILE UNDER ANY `src/` IS CHANGED.** `git diff origin/main -- apps/api/src` is **EMPTY** and `git diff --stat origin/main -- packages/db/migrations scripts/db` is **EMPTY**.
- **MONEY PATH, `E2` READ OWED.** Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**
- **A DISPATCH PROMPT IS NOT A SOURCE.** Two of its premises did not survive contact with the tree and both are recorded in the direction that cuts against this row's convenience: section 9 finds the `BLOCKED` reason accurate in every clause it states, and section 8 finds the contradiction the row was told to check for **already closed**, by an `accepted` ADR, sixteen days before this wave opened.

### 4. The reads and the writes, separated member by member

**THEY ARE SEPARATED BECAUSE THEY HAVE DIFFERENT RISK AND DIFFERENT BLOCKERS**, and an entry treating them as one thing is the defect [ADR-358](ADR-358.md) kept finding.

| Member | Kind | What it does |
|---|---|---|
| `principal` | **READ** | resolves the operator behind the request, or `null` |
| `now` | **READ** | the clock, read once, by the reconciliation route |
| `reconcile` | **READ** | the whole reconciliation projection, no transaction and no side effect |
| `writeCorrection` | **WRITE** | the adjustment, its posting and its wallet entry |
| `operator` | **GATEWAY, and it is write-capable** | opens the unit of work and yields the `AdminWalletTx` that carries `insert` |

**`operator` IS THE ROW THAT MATTERS AND IT IS NEITHER A READ NOR A WRITE.** Calling it a read because its signature says `fn` is how a census loses an append. The handle it yields carries `lockAt`, `rowAt` and `rowsWhere`, which read, **and `insert`, which writes**, and this module makes exactly two `tx.insert` calls:

```
tx.insert('adminActions', ...)        writeAuditRow (`admin-wallet.ts:1447`), before every append
tx.insert('walletSpendLimits', ...)   the spend-limit endpoint's whole write
```

**SO THE SPEND-LIMIT ENDPOINT'S WRITE DOES NOT TOUCH `writeCorrection` AT ALL.** A slice that solved `principal`, `writeCorrection` and `reconcile` and stopped would still write nothing, because it would hold no `operator`; and a slice that solved `principal` and `operator` alone would have a **fully working spend-limit endpoint** and a correction that still refuses. **Those are two different deployments and the entry describes neither.**

**AND A SPEND LIMIT IS NOT A MINOR WRITE.** `wallet_spend_limits` is what a trader may spend; `daily_cents: 0` is a writable value meaning no wallet spend at all. A census that files this port's write risk entirely under `writeCorrection` has filed the reversible-looking half of the surface under the irreversible half's blockers and lost it.

### 7. The three refusal properties, as cases rather than as prose

**(a) NO PATH QUOTES A FIGURE A READER COULD TAKE AS A BALANCE OR AN AMOUNT.** Asserted on every route: the response document's key set is exactly `type`, `title`, `status`, `code`, `instance` and **no sixth**, which forecloses `detail`, the member every quoted figure in this module travels in. Beyond that, no digit appears anywhere in the document except in `status` (a status code) and `instance` (the framework's request counter), and none of `cents`, `balance`, `amount`, `wallet` or `adjustment` appears at all.

**AND THAT CASE IS NOT VACUOUS, WHICH IS ASSERTED IN THE OTHER DIRECTION.** This module really does have a refusal that quotes a balance: `INSUFFICIENT_FUNDS_STATUS` (`apps/api/src/routes/admin-wallet.ts:371`) carries a `detail` reading *"This correction debits N cents against a balance of M"*. A case drives a wired backend into it and asserts the frozen balance appears in the document. **So the property proved above is a property of the unwired PATH and not of a module with no figure to quote.**

**(b) NO PATH WRITES A LEDGER ENTRY, AN ADJUSTMENT, OR ANY WALLET STATE.** Asserted structurally rather than by counting rows in a recorder that was never handed one. A wrapper delegating every member to `UNWIRED_ADMIN_WALLET_BACKEND` records which members a request consults; on all three routes the trace is exactly `['principal']`. **`operator` is the only member that yields an `AdminWalletTx` and it is never called**, so no transaction is opened, no `insert` is reachable, and `writeCorrection` is never entered.

**(c) NO PATH RECORDS SOMETHING A LATER READER WOULD TREAT AS AN ADJUSTMENT HAVING BEEN APPROVED.** The record that would say so is the `admin_actions` row: `action: 'wallet_entry.correct'`, `initiative: 'operational'`, and an `evidence_refs` entry of kind `second_approver` carrying a name. It is written by `writeAuditRow` (`apps/api/src/routes/admin-wallet.ts:1447`) through `tx.insert`, so it is behind `operator` and falls with (b). **The only thing this deployment records about such a request is a log line**, whose text names the port member and reaches no reader of the wallet.

**THE STOP CONDITION THE DISPATCH SET WAS NOT MET.** No write path is reachable against the unwired default. **It was measured rather than assumed**, and seed 7 of section 11 is the proof that the case fires: making the unwired `principal` resolve a principal instead of rejecting turns `operator` into a consulted member and reddens it.

### 13. Where this entry is most likely wrong

- **THE CLASSIFICATION OF `operator` AS A GATEWAY IS A JUDGEMENT AND THE OTHER FOUR ARE NOT.** A reader may reasonably say a member that opens a transaction is a write, full stop, in which case the write surface is two and the reading is unchanged; or that it is neither and the port has three reads, one write and one door. **What is not a judgement is that both appends go through it**, and that is what the case asserts.
- **THE 503 SENTENCE AT `AdminWalletUnwired` WAS NOT EDITED AND SOMEBODY MAY THINK IT SHOULD BE.** It is accurate about the class and misleading about the deployment. **Repairing it is a one-line `src/` change on the money path and this row had no other reason to open the file**, which is the disposition [ADR-362](ADR-362.md) took on the equivalent docblock in `checkout.ts`.
- **NOTHING IN THIS MODULE GATES ON `identities.status`.** Section 8 rules that `INV-M20-06` does not govern an admin correction, and that ruling is about which invariant applies rather than about whether a correction against a `closed` identity should be refused. **If a founder reads that as a hole, the place to look is section 8's last paragraph**, and no gate was invented for it here.
- **THE SUITE PROVES WHAT THIS PROCESS DOES.** It proves nothing about a deployment holding a PARTIAL backend, which is a different value and answers differently. Section 5 is the argument that no deployment can reach that state today, and it is a reading of source rather than of a running system.

### 14. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS RULING 4 AND 5 TOGETHER: whether the spend-limit endpoint and the correction endpoint should be allowed to become installable separately.** They are behind different blocker sets today by accident rather than by decision. A slice that lands `principal` and the operator door gets a **fully working spend-limit endpoint** on the same commit, with the correction still refusing. **That may be exactly right**, because a spend limit is reversible by a later effective-dated row and a correction is not; but nothing in this tree has ruled it, and the entry that describes the port's blockers does not currently let a reader see the choice exists.
