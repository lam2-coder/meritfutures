## ADR-228: The dual-control threshold is `500000` integer cents, it needed a ceiling before it needed a value, and it is undischarged on the path the question named  (2026-08-29, status: proposed)

**The founder answered a question about payouts and the only column that can hold the answer is not on any payout path.** `dual_control_threshold_cents` exists on exactly one table in this estate, [`account_adjustments`](../../packages/db/migrations/0038_account_adjustments.sql), which is the ADMIN adjustment table. `grep -c 'dual_control\|dualControl'` over [`payouts.ts`](../../apps/api/src/routes/payouts.ts), [`admin-payouts.ts`](../../apps/api/src/routes/admin-payouts.ts), [`wallet-withdrawals.ts`](../../apps/api/src/routes/wallet-withdrawals.ts) and [`wallet.ts`](../../apps/api/src/routes/wallet.ts) returns **0, 0, 0 and 0**, and neither [`0010_payouts.sql`](../../packages/db/migrations/0010_payouts.sql) nor [`0011_wallet.sql`](../../packages/db/migrations/0011_wallet.sql) declares a dual-control column of any kind. **The number lands where it can land, and section 5 says plainly that the control the question described does not exist.**

**And the number was the smaller half of the problem.** [`0038:191`](../../packages/db/migrations/0038_account_adjustments.sql) declares the threshold **PER ROW** under `CHECK (dual_control_threshold_cents > 0)`, so the writer of an adjustment chooses the line its own amount is measured against. A row naming `9223372036854775807` satisfies `account_adjustments_dual_control_above_threshold` at any amount a `bigint` can hold, with no approval row. **That was executed, not argued**: against the merged schema on PostgreSQL 16.13, a **$1,000,000** credit with no approval cleared every `CHECK` and stopped only at a foreign key deliberately falsified to reach them (section 3). [`0068`](../../packages/db/migrations/0068_dual_control_threshold_ceiling.sql) is the bound.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `228`, session **418**, dispatched as `claude/dual-control-threshold-is-answered`. **Migration `0068` was reserved REQUIRED and is TAKEN**; nothing returns to the pool. The row's premises were re-derived at their own files before a line changed and **all of them hold**; two of its conjectures resolved in the direction the row called the sharpest (section 8).

- **MONEY PATH. `E2` READ IS OWED AND NOTHING HERE DISCHARGES IT.** [`0068`](../../packages/db/migrations/0068_dual_control_threshold_ceiling.sql) carries an `E2 READ: MONEY PATH` header. This entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing**, and the approval block names four things this entry cannot decide.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the attack commits, that the ceiling refuses it, that the original constraint fires once the threshold is honest, and that a stricter threshold is still permitted is **MEASURED**, live, in section 3. That nothing writes `account_adjustments`, that no payout or withdrawal route carries dual control, and that no configuration table exists among the 115 tables is **DERIVED** by search, at the scope each claim names. What is **JUDGED** is that the bound belongs in DDL rather than in the route (section 4.3), that it is a ceiling rather than an equality (section 4.2), and that the mismatch between the question's reasoning and the column's is worth reporting rather than smoothing (section 6).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim below was read at its own file.

**A threshold whose reasoning is lost is a threshold the next session moves**, so both halves are recorded, verbatim, here and in [`0068`](../../packages/db/migrations/0068_dual_control_threshold_ceiling.sql) and beside the constant itself.

>
> "above what payout amount should a second human have to approve it"

> **ANSWER**, 2026-08-29: **`$5,000`, which is `500000` INTEGER CENTS.**

### 3. Measured, against a running database

**Scope of this section:** all 64 migration files applied forward-only into an empty database under `ON_ERROR_STOP=1` on **PostgreSQL 16.13**, giving **115 tables**. `CHECK` constraints are evaluated at tuple insert and foreign keys are `AFTER ROW` triggers, so a row carrying unresolvable FK uuids reaches **every** `CHECK` first: **a foreign-key error is the signal that all checks passed.**

#### 3.1 Nothing writes the table, so the constraint has never run in production shape

`ADMIN_WALLET_TABLES` excludes `accountAdjustments` **deliberately** ([`admin-wallet.ts:471`](../../apps/api/src/routes/admin-wallet.ts)), and that exclusion is asserted rather than assumed at [`admin-wallet.test.ts:109`](../../apps/api/test/admin-wallet.test.ts). `writeCorrection` is a refused port. **`account_adjustments_dual_control_above_threshold` has never been evaluated against a row in any deployment**, so nothing about it had ever been tested by use.

#### 3.2 The attack, and the four cases

| Case | Amount, threshold, approval | Result |
|---|---|---|
| **A. THE ATTACK** | `100000000`, `9223372036854775807`, none | **REFUSED** by `account_adjustments_dual_control_threshold_ceiling` |
| **B. The same amount, honest threshold** | `100000000`, `500000`, none | **REFUSED** by `account_adjustments_dual_control_above_threshold` |
| **C. A sub-threshold credit** | `499999`, `500000`, none | **PERMITTED**, reaches the foreign key |
| **D. A STRICTER threshold** | `100`, `10000`, none | **PERMITTED**, reaches the foreign key |

**And the case that is the whole reason this entry exists.** With `account_adjustments_dual_control_threshold_ceiling` dropped, which is **exactly `origin/main`**, case A was re-run:

```
ERROR: insert or update on table "account_adjustments"
       violates foreign key constraint "account_adjustments_identity_id_fkey"
```

**A $1,000,000 credit with no approval row cleared every `CHECK` on the table.** It stopped on the identity uuid, which was random because this probe had no identity graph. **Against a real identity it commits.** `0038`'s own comment calls that constraint one that "CANNOT BE WRITTEN AROUND"; it can, from the one direction the comment does not look, which is not evading the comparison but choosing its right-hand side.

Case D matters as much as case A and is easier to overlook: **the ceiling must not stop a writer being stricter than the firm's number**, and it does not.

### 4. The ruling

#### 4.1 Where the value comes from: a constant, and the column RECORDS rather than SOURCES it

**`DUAL_CONTROL_THRESHOLD_CENTS = 500_000n`**, at [`admin-wallet.ts`](../../apps/api/src/routes/admin-wallet.ts), with the question recorded beside it. **Two measurements decide the shape rather than convenience.** No configuration table exists among the **115** tables this estate declares, and no config reader exists in this deployable. The precedent is one route over: `MINIMUM_WITHDRAWAL_CENTS = 10_000n` ([`wallet-withdrawals.ts`](../../apps/api/src/routes/wallet-withdrawals.ts)), which records that it is "the contract's constant transcribed and NOT a parameter this file chose". **This is the founder's number transcribed**, which is why it does not fall to [ADR-139](ADR-139.md) clause 3's and [ADR-158](ADR-158.md) clause 6's refusal to invent a number on the cash door. That refusal stands and is untouched.

**The column is not a second source.** [`0038:279`](../../packages/db/migrations/0038_account_adjustments.sql) makes it "the threshold IN FORCE when the row was written, not the current one". **Refused: a plan version.** An adjustment may name no account at all (`account_id uuid NULL`), so there is no plan version to read it from even in principle, and a threshold that differed per trader would not be a threshold on Merit's own authority.

#### 4.2 It is a DEFAULT and never a CEILING the caller may raise, and the refusal is in DDL

**Ruled: a caller may never supply the threshold.** [`WalletCorrectionBody`](../../apps/api/src/routes/admin-wallet.ts) carries no such field and `WalletCorrectionDraft` gains none; the writer reads the constant. **The refusal is [`0068`](../../packages/db/migrations/0068_dual_control_threshold_ceiling.sql)'s `account_adjustments_dual_control_threshold_ceiling`, `<= 500000`, and not that sentence, because a comment is not a control.**

**A CEILING AND DELIBERATELY NOT AN EQUALITY, and the reason is the column's own purpose.** `= 500000` is the tighter constraint and kills the trap in both directions, and it is **refused**: a `CHECK` constrains every row, historical rows included, so an equality would make the entire history unrepresentable the first time the threshold moved. Rows written at `500000` would violate a re-issued `= 300000`, and the remedy would be a growing `IN (...)` list or dropping the control. **An equality defends this column by destroying the property [`0038:279`](../../packages/db/migrations/0038_account_adjustments.sql) created it for.**

**The ceiling makes the asymmetry structural.** A writer may name a **lower** threshold, which can only require **more** approvals; it may not name a higher one, which can only require fewer. **Tightening is free and loosening is a migration**, which is the ceremony the loosening direction deserves and the tightening direction does not.

#### 4.3 In DDL rather than in the route, on the threat model's own terms

[ADR-067](ADR-067.md) section 5 is explicit that at launch scale this is "compromise resistance, not insider resistance". **A refusal in application code is a refusal a compromised application session is on the wrong side of.** A `CHECK` is not: raising this ceiling needs deploy access to the database, which is a different credential from the one that reaches the route. **That asymmetry is the control**, and it is the reason this is not simply a validation in the handler.

`0038` is merged and is **superseded by addition, never edited** (constitution `E2`), which is [`0028`](../../packages/db/migrations/0028_supersede_plan_version_immutability.sql)'s mechanism on this estate. `0038` is byte for byte unchanged.

### 5. THE PAYOUT PATH, ANSWERED WITH CITATIONS, AND THE ANSWER IS THAT THE FOUNDER'S THRESHOLD IS UNDISCHARGED THERE

**Scope of this search:** every file under `apps/api/src/routes/`, every migration under `packages/db/migrations/`, and `docs/plans/M05`, `M06` and `M20`.

**`dual_control_threshold_cents` is the only amount-denominated dual-control threshold in the estate.** Exactly two files name it: `0038`, which declares it, and `0068`, which bounds it. **Every other dual control in this tree is unconditional** and triggers on a payload hash or on membership of [ADR-010](ADR-010.md)'s sensitive set, never on an amount.

**The near-miss a reader will make, named so nobody makes it.** [`wallet-withdrawals.ts:1501`](../../apps/api/src/routes/wallet-withdrawals.ts) declares `required: 'passkey or dual_channel'`. **`dual_channel` is a step-up AUTH FACTOR for the SAME human. It is not a second human**, and the word "dual" is the only thing it shares with dual control.

**So the sentence this entry exists to make.** The founder was asked "above what payout amount should a second human have to approve it". **No payout route in this tree asks a second human to approve anything, at any amount.** The number they gave is now in force on the admin adjustment path, where it is the size of the loss one compromised owner session can cause without a second key, and it is **UNDISCHARGED** on the path the question described. **Closing that is not this fence's** and it is not a small slice: `payout_requests` and `wallet_withdrawals` have no column to hold an approval, so it is a migration, a route, and a ruling on whether a trader's own withdrawal should ever wait on an operator.

### 6. The reasoning the founder was shown is not the reasoning this column carries, and that is reported rather than smoothed

**Both halves of the framing offered with the question are true and one of them is vacuous.** The `$5,000` option was described as catching the unusual payouts "without adding friction to normal trader withdrawals". **`account_adjustments` adds friction to no trader withdrawal at any value, `1` cent included**, because no trader withdrawal writes a row of it and none can (section 5). The reassurance was true and it was true of every possible answer.

**What the number actually sets is [ADR-067](ADR-067.md) section 5's quantity**: "the size of the loss one compromised owner session can cause without a second key", and that entry says it "should be set low and read as that number". **`OQ-F6-01` recommended `10000` cents**, tied to the wallet withdrawal minimum ([M20:30](../plans/M20-wallet.md)) so that "every adjustment large enough to be withdrawn on its own needs the second key".

**`500000` IS FIFTY TIMES THAT RECOMMENDATION, AND IT IS THE FOUNDER'S ANSWER.** This entry lands it and does not argue it down. What it will not do is let the 50x pass unrecorded, because the recommendation and the answer were reasoned from different questions: one about an admin's unilateral authority, one about trader friction that this column does not create. **The tie to the withdrawal minimum is what the answer gives up**: at `500000`, an adjustment can credit a wallet **fifty times** the amount that can be withdrawn on its own before a second key is needed.

**And [ADR-067](ADR-067.md) `OQ-F6-02` is still open and is now 50x wider per credit.** The `CHECK` is per row and nothing sums repeated sub-threshold credits. That entry's stated launch mitigation was "a low threshold plus the `admin_actions` trail"; **the threshold is no longer low, so half of that mitigation is gone** and the aggregation gap is the approval block's second item.

### 7. What this entry does NOT do, stated so nobody reads coverage into a green suite

1. **It makes no payout dual controlled.** Section 5.
2. **It does not exercise the constraint through a writer**, because there is no writer. The probes in section 3 drive the database directly.
3. **It does not close `OQ-F6-02`**, the sub-threshold aggregation gap.
4. **It supplies no `dual_control_approvals` row.** Header item 3 of [`admin-wallet.ts`](../../apps/api/src/routes/admin-wallet.ts) remains unrepaired; what changed is that the missing piece is now **one** thing rather than two, and the remaining one is the approval row and not the number.
5. **It sets no precedent for putting a launch candidate in DDL.** The standing parameter-status ruling keeps plan parameters in `plan_version_sizes`. This is not a plan parameter: it bounds an ADMIN's own authority, it is denominated in the firm's loss, and no plan version scopes it.

### 8. Found rather than dispatched

1. **The corpus had already recommended a number and the dispatch did not name it.** [ADR-067](ADR-067.md) `OQ-F6-01`, `10000` cents. An entry that landed `500000` without finding it would have silently overruled a recommendation nobody knew was there.
2. **`0038`'s own comment overclaims.** "THE DUAL-CONTROL CONTROL CANNOT BE WRITTEN AROUND" was false when it was written, in the direction the sentence does not look. **The comment is not edited**, because `0038` is merged; `0068` makes it true instead.
3. **`admin-wallet.ts` carried three sentences that stopped being true** the moment the founder answered, each asserting the threshold has no source. All three are repaired in place, and each records what it used to say, because a deleted sentence is how the claim comes back.
4. **The migration allocation table's own rule contradicts the dispatch.** [ALLOCATION](ALLOCATION.md) says a number is claimed "BEFORE the file is written, in its own commit"; row `228` says "in the same commit that writes it". **The table's rule was followed**, being the stricter of the two and the one `CI-06h` was built around. Reported rather than resolved quietly.
