## ADR-230: The `pair` class gets a WRITE door and keeps its read refusal, the narrowness is a stamp rather than a check, and the route it was built for still does not serve  (2026-08-29, status: proposed)

**`POST /checkout` is how Merit takes money and it answers 503.** [`wiring.test.ts`](../../apps/api/test/wiring.test.ts)'s `BLOCKED` entry for `useCheckoutBackend` named two obstructions and led with this one: `CheckoutTx.insertAttribution` writes `attributions`, which is scope class `pair` ([ADR-106](ADR-106.md)), and **no authority in `packages/db` admitted a request handler writing that class.** A `pair` key is a member of neither `ScopedTableKey` nor `FirmTableKey`, so the only door was `systemDb(reason)`, whose vocabulary is `'nightly-batch' | 'operator-console'`, and a checkout request handler is neither word.

**This entry builds the door and it is narrower than a table list.** `PairRule` gains a REQUIRED `writer` field naming which of the two identity columns a party-writer must be, or naming nobody, each with its own reason. `ScopedTx.insertAsParty` inserts one row of a table whose rule says `by: 'party'`, **STAMPING the identity the handle carries into that column and REFUSING a caller that names it, in either spelling.** So "a handler party to pair A cannot write a row for pair B" is not a validation this door performs: **there is no parameter through which the writer's own column could be supplied.**

**ADR-106's ruling is untouched, because ADR-106 is a ruling about a READ.** Its whole ground is disclosure: every row a disjunction returns carries the other party's identity uuid out of a `NOT NULL` column. **This door builds no `RETURNING` clause and returns `void`**, so the ground is not outweighed here, it is ABSENT, which is the shape [ADR-191](ADR-191.md) already used to admit `either` to a key set `pair` is excluded from. `scopePredicate` still throws on every `pair` key, no key changed key sets, and nothing became readable.

**AND THE ROUTE STILL DOES NOT SERVE, WHICH IS THE HALF WORTH READING.** Section 6 is the written account the dispatch asked for as its alternative stop condition. The `BLOCKED` entry named two obstructions and there are four; this entry discharges the first and **finds two the entry never carried**, one of which refuses every checkout of every payment method rather than one arm.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `230`, session **420**, dispatched as `claude/checkout-goes-live`. The row reserved migration `0069` conditionally, *"if the authority needs one"*. **IT DOES NOT AND `0069` IS NOT TAKEN**; section 4.4 says why, and the number returns to the pool untouched.

- **MONEY PATH. `E2` READ IS OWED AND NOTHING HERE DISCHARGES IT.** This entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.** The subject is the one control Appendix `D2`'s audit called fully discharged, so section 5 states what this widening does and does not touch of that discharge.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the stamp binds the handle's identity, that both spellings of the writer column throw before any statement is sent, that a second handle writes a different row, and that a caller-wins spread or a deleted refusal makes the narrowness assertion fail is **MEASURED**, in `packages/db/test/pair-write-door.test.ts` and in the two seeded defects of section 3.4. That five `CheckoutTx` methods read `firm` tables, that two more reach a row `owned` by the affiliate, and that `SystemReason` still has two members is **DERIVED** by reading each declaration at its own file, at the scope each claim names. What is **JUDGED** is that a write is a different question from a read (section 4.1), that the counterparty is not this door's to validate (section 4.3), and that the firm read is not this session's to answer (section 7).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim below was read at its own file on this tree.

### 1. The question that had no answer, and the one it is not

**M08 section 3.1 rules that attribution resolution *"HAPPENS AT CHECKOUT START, in the same step that pins the plan version"* and that *"IT HAPPENS ONCE"*.** So one `attributions` row is written inside one buyer's checkout transaction, by that buyer's request, and by nothing else in the estate.

[ADR-106](ADR-106.md) had already ruled that such a row is scoped to NEITHER party. **That ruling is about what a query RETURNS**, and its argument is quoted rather than summarised, from [`scope.ts`](../../packages/db/src/scope.ts)'s own `PairRule` docblock:

> The reason is not that no predicate exists -- `columnA = $1 OR columnB = $1` returns precisely the rows that are this person's and no others -- it is that every row it returns carries the OTHER party's identity uuid in a `NOT NULL` column.

**Nothing in that sentence is about an INSERT**, and the file said so without noticing: [ADR-112](ADR-112.md) section 10 records that giving the accessor an ADDRESS did not move the AUTHORITY, and [`checkout.ts`](../../apps/api/src/routes/checkout.ts)'s header called the result *"a wall that is still standing"* and left `insertAttribution` a port *"until somebody takes it"*.

### 3. What was built

#### 3.1 The ruling lives in the registry, one entry per table, each with a reason

`PairRule.writer` is a two-arm discriminated union and it is **REQUIRED**, so a `pair` table registered after this entry answers the question or does not compile. That is this file's own totality rule, which it already applies to the class of every table: *"a table added to `schema.ts` without a rule here does not compile"*.

| Table | `writer.by` | Why, in one line (the registry carries the argument) |
|---|---|---|
| `identity_links` | **`nobody`** | An edge is MERIT'S assertion about two people, produced by M07's detectors with `evidence jsonb NOT NULL` beside it. A party who could write one could assert an edge to anybody |
| `dedupe_matches` | **`nobody`** | [ADR-022](ADR-022.md) makes a dedupe hit a HARD LINK THAT AUTO-ENFORCES, so the row bans an account before a human has looked. A subject who could write their own could write it at a strength that clears |
| `attributions` | **`party`, `buyer_identity_id`** | The buyer's own act creates the row, once, at checkout start. The affiliate is asleep, and an affiliate who could write it could mint a referral over somebody else's purchase |

**`by: 'nobody'` is the DEFAULT ANSWER and it is written out rather than implied**, because a field whose absence means "no" is a field a later author forgets to think about.

#### 3.2 The door is a stamp, and the narrowness is structural

`pairInsertStatement` ([`scoped-db.ts:2142`](../../packages/db/src/scoped-db.ts)) is reached through `ScopedTx.insertAsParty` ([`scoped-db.ts:2335`](../../packages/db/src/scoped-db.ts)) over `PartyWritableTableKey` ([`scoped-db.ts:2126`](../../packages/db/src/scoped-db.ts)). In order:

1. The rule is read WIDENED, so the class and the `writer` guards are written against the REGISTRY rather than against a type narrowed at a literal key. That is `insertUnderStatement`'s stated construction and its stated compiler error.
2. A non-`pair` class, and a `pair` rule saying `by: 'nobody'`, both **throw**.
3. A `writer.column` that is neither declared identity column **throws**, because a stamp into a third column is an identity written where the registry declares none.
4. The caller naming the writer column, in **either** spelling, **throws** before any statement is built.
5. The counterparty is **required**, in the Drizzle property spelling only, and may not be null: a pair row with one party is not a pair, and both columns are `uuid NOT NULL REFERENCES identities(id)` in the DDL.
6. The insert is built with the writer column stamped LAST, and with **no `RETURNING`**.

**`PartyWritableTableKey` IS DERIVED FROM THE REGISTRY AND NOT AN `Extract` DOWN TO ONE MEMBER**, which is the opposite of `ParentedTableKey`'s choice and is made on the same reasoning. That type is a hand-written list because `DerivedTableKey` contains `ledger_entries`, so the CLASS is not the ruling there. **Here the ruling IS per table and it is in the registry**, so an `Extract` would be a second statement of a decision already written once, which is the drift `packages/db` exists to keep to one.

#### 3.3 The narrowness assertion, written as the row worded it

`packages/db/test/pair-write-door.test.ts` is **16 cases** and proves the property from three directions, because one assertion of it would be an assertion about a VALUE and the property is about a SHAPE:

1. **THE STAMP.** Every statement the door builds binds the handle's own identity into the writer column, on every party-writable table.
2. **THE REFUSAL.** Both spellings of the writer column throw, and **nothing is sent** when they do: a refusal that threw after the INSERT would be a refusal that wrote the row.
3. **THE ABSENCE.** `scopePredicate` still throws for every `pair` key, no `pair` key is in `ScopedTableKey`, and the door emits no `RETURNING`.

**A CONTROL CASE IS RUN BESIDE THE NEGATIVE**, because a door that refused everything would pass every assertion above: the same call on a second identity is asserted to bind the second identity and NOT the first.

**AND THE SELF-DEAL ROW IS ASSERTED WRITABLE.** `attributions_literal_self_deal_is_void` permits the two columns to name one person on a voided row, and SD-M8-05's argument is that *"the self-deal check must record WHAT IT FOUND, not only its verdict, or an argument about a voided commission has no evidence on either side."* A door refusing a counterparty equal to the writer would make that evidence unwritable, so the permission is asserted rather than left to be a side effect.

#### 3.4 Two seeded defects, watched firing

| Seeded defect | Result |
|---|---|
| The caller's values spread AFTER the stamp, so a supplied buyer wins | **`a handler party to pair A cannot write a row for pair B` FAILS** |
| The writer-column refusal loop short-circuited to `continue` | **The same case FAILS** |

Both were restored from a byte copy and the suite returned to 16 passing.

**A THIRD REFUSAL IS A COMPILE ERROR AND VITEST CANNOT SEE IT, SO IT WAS FALSIFIED SEPARATELY.** The test file carries `// @ts-expect-error` on `const notAMember: PartyWritableTableKey = 'accounts'`. Changing that literal to `'attributions'` makes `tsc` report **`TS2578: Unused '@ts-expect-error' directive`**, which is the directive proving it is live. The key type widening past the ruling is therefore a build failure and not a test failure.

### 4. What was refused

#### 4.1 A scoped READ of a `pair` table

**Not proposed, not built, and the refusal is re-stated in three places rather than assumed to be remembered.** ADR-106's ground stands whole. What this entry says is that the ground is about a return value and an INSERT has none.

#### 4.2 A `RETURNING` clause

**The obvious convenience and it is refused.** `insert` and `insertUnder` return their rows; this returns `void`. **It is what makes ADR-106's ground ABSENT rather than merely outweighed**, and the one caller it was built for wants nothing back: `CheckoutTx.insertAttribution` is `Promise<void>` in its own port.

#### 4.3 A guard on the counterparty

**The door proves WHO IS WRITING and never who is being written about**, and this is stated rather than left to be discovered. Two reasons. The counterparty is a value the caller already held before it opened the transaction: on `attributions` it comes out of a coupon the buyer typed or a click token the buyer presented. And a guard refusing a counterparty EQUAL to the writer would destroy SD-M8-05's evidence, per section 3.3.

#### 4.4 A migration

**`0069` was reserved conditionally and is NOT taken.** The authority is a TYPE and not a table: no column, constraint, index or grant changes. `0026_roles_and_grants.sql:75` grants `merit_app` `SELECT, INSERT, UPDATE, DELETE` on all tables and its append-only `REVOKE` list at `:88` does not name `attributions`, so the role could always insert the row and what was missing was the accessor. **A `REVOKE UPDATE, DELETE ON attributions` is arguably owed** on the same append-only reading -- one attribution per purchase, resolved once -- and it is **named here rather than taken**, because it is a decision about the table and not about this door.

#### 4.5 A `SystemReason` member, an `apps/api` `system(reason, fn)` door, a `SqlExecutorReason` member, a cast past a key type

**None of the four.** Section 7.

### 5. What this does to Appendix `D2`, which is the control this widens

**`D2-3` is the row [the controls audit](../reviews/2026-08-29-d2-controls-audit.md) calls *"FULLY DISCHARGED, and it is the strongest row in the audit"***, and its evidence is `scopedDb`'s export plus two independent lint legs. **Nothing in this entry touches any of the three.** `client()` stays unexported, `merit/no-raw-db-client` is unchanged, the semgrep rule is unchanged, and no caller outside `packages/db` gains a way to reach the database that is not a door.

**What it DOES change is what one door can write, and that is worth saying plainly rather than burying**: a scoped handle can now insert into a table it could not before. The reasons that makes the control no weaker are the whole of section 3, and the shortest of them is that **the widening carries no parameter**. Every other write on `ScopedTx` takes values that decide which row is touched; this one decides the tenancy column itself, from the handle, and refuses to be told.

#### 6.2 A row the buyer must see that belongs to the affiliate

`clickByToken` ([`:753`](../../apps/api/src/routes/checkout.ts)) returns a `ClickRef` whose `affiliate` is an `AffiliateRef` carrying `affiliates.identity_id`, and `couponByCode` returns the same shape ([`:457`](../../apps/api/src/routes/checkout.ts)) because `coupons.affiliate_id` names one. **`affiliates` is `owned` on `identity_id`** ([`scope.ts:1093`](../../packages/db/src/scope.ts)) and **`affiliate_clicks` is `derived` through it** ([`scope.ts:1109`](../../packages/db/src/scope.ts)), whose own reason says it in capitals: *"A CLICK BELONGS TO THE AFFILIATE AND NOT TO THE PERSON WHO CLICKED."*

**So a BUYER-scoped read of either returns the empty set**, for every buyer who is not themselves the affiliate, and `resolveAttribution` then folds every referral as `no_code_and_no_click`. **That is a wrong answer that RETURNS ROWS**, which is the exact failure mode [`scope.ts`](../../packages/db/src/scope.ts)'s opening paragraph exists to make unavailable, and it is the one obstruction here that **needs a ruling rather than a door**: the buyer legitimately must learn one fact about another identity, and no class in this vocabulary says so.

- **Approval:** `___________________________` (UNSIGNED. **MONEY PATH, `E2` READ OWED** on this ruling. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS WHETHER THE BUYER IS THE RIGHT WRITER, AND IT IS THE ONE JUDGEMENT HERE THAT COULD BE WRONG.** Section 3.1 says the buyer authors the row because the buyer's act creates it and the affiliate is asleep. The alternative reading is that **nobody** authors it and the row is Merit's own record of a commercial fact, in which case the honest door is not on `ScopedTx` at all but a one-verb handle like `EstablishmentTx`, taking both identities and reachable from one caller. **That would be stricter and it would also be a bigger slice**, because it needs its own brand, its own `transaction` overload, and its own line in `apps/api/src/db.ts`. This entry took the narrower change to the existing surface; the stricter alternative is real and is named rather than dismissed.

  **THE SECOND IS THE FIRM READ, AND IT IS NOW BLOCKING TWO MONEY ROUTES.** Section 6.1. `usePayoutBackend` and `useCheckoutBackend` are both refused by the same shape: a port that runs every method on one transaction, at one identity, needing a row that belongs to nobody. **The candidate answer is small and it is not obviously safe**: give `ScopedTx` a read over `FirmTableKey` only, on the ground that `firmDb()` already takes NO reason because no identity is at risk in those rows, so a scoped handle reading them grants nothing `firmDb()` does not already grant unconditionally. **This entry did not take it**, deliberately, because it is a second widening of the estate's central control inside a session dispatched for one, and the objection worth weighing is that it puts the whole catalogue one method call from every request handler. **It needs its own session and its own entry**, and until it has one, both revenue routes stay at 503.

  **THE THIRD NEEDS A RULING AND NOT A DOOR, WHICH IS WHY IT IS THE HARDEST.** Section 6.2. The buyer must learn `affiliates.identity_id` for a coupon they typed, and that row is somebody else's. **No class in the six-member vocabulary describes "one identity may read one column of another identity's row because the first identity named it"**, and inventing one is exactly the kind of widening that is worse than the 503 it removes. The likely shape is a projection rather than a class -- a narrow reader returning an `AffiliateRef` and nothing else -- but that is a design and this entry does not make it.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The door has no caller, so nothing has exercised it against a real database.** Every assertion in section 3 reads SQL that was built and never sent; `ci.yml`'s `integration` job has no Postgres, which is `write-accessor.test.ts`'s own stated limit and is inherited here rather than solved. **What that cannot catch is a `NOT NULL` this door does not know about**: if `attributions` gains a required column, the first real insert fails at the database and no test in this repository turns red first. The mitigating fact is that the failure direction is a refused write and never a wrong row.
