### 3. THE LOCK, DECIDED. The payout path LOCKS, and the lock is a PORT MEMBER and not a line inside `transact`

[ADR-291](ADR-291.md) built `transact` taking no lock, **reported that rather than deciding it**, and registered it as slice 6's question. Row `293` required it be decided in writing, either way, **with the read-then-write this branch actually performs as the evidence.** Deciding it does not need the code to land: the read-then-write is a property of the path, and it is readable today.

#### 3.1 The read-then-write is REAL, and slice 6 is what creates it

[ADR-291](ADR-291.md)'s stated reason for not locking was that *"nothing this transaction currently does reads-then-writes"*. **That was true when it was written and slice 6 is precisely what makes it false.** Before slice 6 no member of `PayoutTx` wrote anything.

**AND THE READ-THEN-WRITE IS NOT INCIDENTAL. IT IS `G-NO-IN-FLIGHT`, WHICH IS A LIABILITY CONTROL THAT THE ROUTE ITSELF CALLS ONE.**

| Step | Line |
|---|---|
| The in-flight fact is READ, through `subject()` into the evaluation | `const subject = await tx.subject(accountId);` [`payouts.ts:1137`](../../apps/api/src/routes/payouts.ts), folded at [`:1143`](../../apps/api/src/routes/payouts.ts) |
| It is DECIDED in memory | `if (!evaluation.noPayoutInFlight.pass) return refuse('conflict', 'Conflict', 409, ...)` [`payouts.ts:1152-1153`](../../apps/api/src/routes/payouts.ts), commented *"It is a liability control and not a convenience"* at [`:1151`](../../apps/api/src/routes/payouts.ts) |
| And the row is WRITTEN against that decision | `await tx.insertPayoutRequest(row);` [`payouts.ts:1201`](../../apps/api/src/routes/payouts.ts) |

**THE CLAMP IS THE SECOND ONE AND IT IS THE MONEY ONE.** `approved_cents` is `min(requested, withdrawable, cap)` computed off `subject.state` and written as `approvedCents`, so two transactions reading one balance both write approvals against it.

#### 3.2 The identical shape one door over is LOCKED, and that file says why in its own words

[`wallet-withdrawals.ts`](../../apps/api/src/routes/wallet-withdrawals.ts) carries the same gate under the same name:

- `gateNoInFlight` is documented **"FOUR STATUSES, FILTERED IN MEMORY, AND UNDER `lockScope()`. See ... this file's header for why the lock is what makes the check a control."** ([`:1415-1419`](../../apps/api/src/routes/wallet-withdrawals.ts))
- That header states it directly: **"ONE IN FLIGHT" IS DECIDED UNDER `lockScope()`** ([`:125`](../../apps/api/src/routes/wallet-withdrawals.ts))
- And `decideWithdrawal` takes the lock as its **first statement**, above every gate: `await tx.lockScope();` ([`:1490`](../../apps/api/src/routes/wallet-withdrawals.ts)), under the docblock **"THE LOCK IS FIRST AND EVERY GATE BELOW IS DECIDED UNDER IT. A gate evaluated before the lock is a gate evaluated against a state another transaction can still change."** ([`:1465-1467`](../../apps/api/src/routes/wallet-withdrawals.ts))

**A payout is not a weaker case than a wallet withdrawal. It is the same case with the firm's split on the other leg.**

#### 3.3 The database's unique index is a BACKSTOP and it is NOT the control

`CREATE UNIQUE INDEX payout_requests_no_in_flight_uq ON payout_requests (account_id) WHERE status IN ('approved', 'frozen');` ([`0010_payouts.sql:200-201`](../../packages/db/migrations/0010_payouts.sql)), written under the heading **"G-NO-IN-FLIGHT, ENFORCED IN THE DATABASE"** and the reason **"because the engine is not the only writer"**.

**IT IS REAL AND IT IS NOT SUFFICIENT, FOR TWO SEPARATE REASONS.**

**First, it converts a specified refusal into an internal error.** The contract answers `G-NO-IN-FLIGHT` `409 conflict` with a named message ([`payouts.ts:1153`](../../apps/api/src/routes/payouts.ts)). Unlocked, the losing transaction of a race reaches the insert and receives a unique violation, which is not a `PayoutBackendUnwired`, is not caught by `unwiredOrThrow`, and is therefore a **500** on a request the contract says is a clean 409. **That is [SECURITY](../architecture/SECURITY.md) section 4 item 9's own sentence, "columns that record a control are not the control", applied to an index**: the index records the outcome and the lock is what makes the gate a gate.

**Second, the index is PER ACCOUNT and the exposure question is PER IDENTITY.** [`0010_payouts.sql:45-49`](../../packages/db/migrations/0010_payouts.sql) denormalises `identity_id` onto the row and says why in the migration's own comment: *"the question 'how much is this human extracting right now' cannot be a join if it is being asked inside the race it is protecting against."* **Two accounts of one identity pass a per-account unique index simultaneously.** `lockScope()` locks the handle's own identity row and **takes no argument at all** ([`scoped-db.ts:3634-3640`](../../packages/db/src/scoped-db.ts)), which is exactly the granularity that sentence describes and the only one in this package that matches it.

#### 3.4 WHERE IT GOES: on `PayoutTx`, called by `decidePayout`. NOT inside `transact`

**AND THIS IS THE HALF THAT REQUIRED RE-DERIVATION, BECAUSE THE SENTENCE EVERY DOCUMENT REPEATS IS IMPRECISE.** [ADR-291](ADR-291.md), [`payout-backend.ts:165`](../../apps/api/src/payout-backend.ts) and row `293` all say *"`databaseWithdrawalBackend` calls `tx.lockScope()` first"*. **It does not.** Read at source, `databaseWithdrawalBackend.transact` takes no lock: it **exposes** the member, `lockScope: async () => { await tx.lockScope(); }` ([`:1121-1123`](../../apps/api/src/routes/wallet-withdrawals.ts)), `WithdrawalTx` **declares** `lockScope(): Promise<void>` ([`:947`](../../apps/api/src/routes/wallet-withdrawals.ts)), and the **decision function** calls it ([`:1490`](../../apps/api/src/routes/wallet-withdrawals.ts)). **`checkout.ts` is the second, independent instance of the same arrangement**: the port declares `lockScope(): Promise<void>` ([`:958`](../../apps/api/src/routes/checkout.ts)) under the docblock at [`:952`](../../apps/api/src/routes/checkout.ts) *"IT TAKES NO ARGUMENT, AND THAT IS THE WHOLE OF ITS SAFETY"*, and the handler calls it ([`:2121`](../../apps/api/src/routes/checkout.ts)).

**SO THE PRECEDENT IS UNANIMOUS AND IT IS THE OPPOSITE OF THE SENTENCE: NO ADAPTER IN THIS TREE LOCKS INSIDE `transact`.** Two do it as a port member called by the decision function, and there is no third arrangement to follow.

**AND THE ARGUMENT AGAINST HIDING IT IN `transact` IS [ADR-291](ADR-291.md)'s OWN, ONE MEMBER OVER.** That entry refused to memoise `identityStatus` because a cache *"would make the order an accident of which member ran first"*, when `ADR-140`'s ordering is `INV-M5-23`'s placement argument. **A lock taken inside `transact` is the same defect with the money on the other side**: the ordering that makes the gate a control would be invisible at the only place a reader checks orderings, which is the ordered function the contract's section 6 sentence is transcribed into. `decideWithdrawal` puts the lock in that function, in one line, with the reason above it.

**AND IT GOES FIRST, ABOVE THE IDENTITY GATE**, on `decideWithdrawal`'s placement ([`:1490`](../../apps/api/src/routes/wallet-withdrawals.ts), above `gateIdentityStatus` at [`:1493`](../../apps/api/src/routes/wallet-withdrawals.ts)). **This does not disturb `ADR-140`.** That ruling orders the identity-status refusal ahead of everything read **about the account**; `lockScope()` reads nothing about the account, takes no address, and locks the caller's own identity row. Placing it first additionally puts `identityStatus()`'s own read of `identities` under the lock, which is strictly the safer of the two orders.

#### 3.5 The ruling, stated so slices 4, 5 and 7 inherit a decision rather than a silence

1. **The payout path TAKES the per-identity lock.** The read-then-write is real, it is `G-NO-IN-FLIGHT` and the clamp, and the identical shape one door over is locked with the reason written above it.
2. **`PayoutTx` GAINS a `lockScope(): Promise<void>` member**, worded on `WithdrawalTx`'s and checkout's, both of which take no argument.
3. **`postgresPayoutBackend` implements it by delegating to `handle.lockScope()`**, which is the whole body, exactly as [`wallet-withdrawals.ts:1121-1123`](../../apps/api/src/routes/wallet-withdrawals.ts) does.
4. **`decidePayout` calls it as its FIRST statement**, above `gateIdentityStatus`.
5. **`transact` STILL TAKES NO LOCK**, and that is now a decision rather than a report.

**WHAT THIS COSTS, STATED RATHER THAN MINIMISED.** Every payout request takes a row lock on the caller's identity for the life of its transaction, including requests that are about to be refused. **`decideWithdrawal` pays exactly this cost deliberately** and its docblock is the argument: a gate evaluated before the lock is evaluated against a state another transaction can still change. **The alternative was measured and refused**: locking only around the insert would leave the gate decided outside the lock, which is the arrangement the index already fails to rescue in section 3.3.

**AND IT IS NOT BUILDABLE IN THIS ROW EITHER**, for section 2's reason: clauses 2 and 4 are lines of [`routes/payouts.ts`](../../apps/api/src/routes/payouts.ts). **It is a ruling, and it is owed to the same row.**
