## ADR-079: the consistency period is bounded against the ANCHOR, not against the row's own trading day  (2026-08-22, status: proposed)

**No frozen document is amended by this ruling. [`0015_rule_states.sql`](../../packages/db/migrations/0015_rule_states.sql) compares `consistency_period_start_day` against the wrong operand, and this ADR decides what it should have compared it against instead. It is money path: the constraint refuses to write state rows the engine is specified to produce, so the signature is the founder's.**

- **Origin:** [session 129](../sessions/2026-08-22-session-129.md) observed the rejection on its own row 0 while asserting `GS-071` at scale. [Session 132](../sessions/2026-08-22-session-132.md) re-derived it against the tree, **refuted that session's second finding** (the `0015:208` high-water bound, already repaired by [`0037`](../../packages/db/migrations/0037_supersede_rule_states_high_water_bounds_balance.sql) under [ADR-053](ADR-053.md) five days earlier) and reduced this to one application rather than two.

- **Context:** [`0015:193`](../../packages/db/migrations/0015_rule_states.sql) carries

  ```sql
  CONSTRAINT rule_states_consistency_period_started CHECK (
    consistency_period_start_day IS NULL
    OR consistency_period_start_day <= trading_day
  )
  ```

  under the comment *"SD-07. A consistency period that has started is not in the future."* **[`progression.ts:339`](../../packages/rules-engine/src/day/progression.ts) writes `consistencyPeriodStartDay: nextDay.day.tradingDay` on the eval-pass row**, so that row carries `trading_day` = the pass day and `consistency_period_start_day` = the day after it.

---

### 1. It is not an edge case, and it was executed rather than argued

**Every account that passes an evaluation writes this row.** `0001` to `0045` applied forward-only into an empty PostgreSQL 16.13 under `ON_ERROR_STOP=1`, then [session 129](../sessions/2026-08-22-session-129.md)'s row 0 inserted verbatim:

```
ERROR:  new row for relation "rule_states" violates check constraint
        "rule_states_consistency_period_started"
DETAIL:  Failing row contains (1, 11400000-0000-0000-0000-000000000079, 2026-01-01,
         funded, 4750000, f, 4750000, 5000000, 5000000, 0, 0, 0, 0, 0, 2026-01-02,
         0, null, null, f, {}, {}, \x13bb4ef8f18145650451bbbaff49aaaeb6755322fba8512b955093254b9004..., probe-0, ...)
```

**The engine is right and three primary sources say so.** [M01:563](../plans/M01-rules-engine.md) states `R-47` as *"`consistencyPeriodStartDay` = **the next trading day after** `payoutAnchorDay`"*; the pseudocode at [M01:737](../plans/M01-rules-engine.md) comments the same line `// R-47, strict`; and `AS-12` at [M01:987](../plans/M01-rules-engine.md) says the period is *"trading days **strictly after** the anchor"* and *"the eval pass day is excluded"*. **No rule moves. The constraint does.**

### 1.1 Why nobody saw it, and one correction to the brief this session was dispatched from

**The settlement row never tripped it.** On a settlement the anchor is the **basis** day, which [`0010:63`](../../packages/db/migrations/0010_payouts.sql) defines as *"The LAST CLOSED DAY the decision used"*, and the row is written for the **effective** day, which [`0010:97`](../../packages/db/migrations/0010_payouts.sql) defines as *"the FIRST TRADING DAY WHOSE OPENING BALANCE REFLECTS THE WITHDRAWAL"*. So `nextTradingDayAfter(basis) <= effective` and the old predicate held.

**The brief said settlement rows "get equality". They satisfy it by `<=`, and the difference is worth recording because a mechanism stated loosely in a brief is how a later session cites it as fact.** Equality holds only when the effective day is the very next trading day. **`GS-068` is the case where it is not**: basis `2026-11-25`, effective `2026-11-27`, with Thanksgiving `2026-11-26` carrying no session between them. On a longer transfer window the stored start sits strictly before `trading_day`.

**So every case anybody thought to write was a case the constraint was right about**, which is `0037`'s finding one screen up in the same table, and no gate could see this one because `CI-03` never touches a database.

### 2. The ruling

**`0015`'s constraint is superseded by [`0046`](../../packages/db/migrations/0046_supersede_rule_states_consistency_period_started.sql), and the replacement compares against the anchor:**

```sql
CONSTRAINT rule_states_consistency_period_after_anchor CHECK (
  consistency_period_start_day IS NULL
  OR payout_anchor_day IS NULL
  OR consistency_period_start_day > payout_anchor_day
)
```

`0015` is merged and is never edited (constitution [E2](../../MERIT_BUILD_MASTER_PROMPT.md)), so it is superseded rather than repaired.

**The defect is not a direction, it is a REFERENCE POINT.** `R-47` defines the period start against the **anchor**; `0015` bounded it against the row's own `trading_day`. That is why a correct engine produced a row a correct-looking constraint refused, and it is why the replacement is not the old predicate with a qualifier bolted on. **The new predicate asserts `R-47`'s own strictness against the day `R-47` actually names**, which is the bar [ADR-053](ADR-053.md) section 3(b) set when it refused a predicate that was merely derivable: this one is stated, in the rule, in the words *"strictly after"*.

**It is also exactly the invariant `AS-12` is an attack on.** If the basis day were included in the new period, *"the very day that funded a payout counts against the next cycle … and it looks like the consistency rule working rather than a bug."*

**The name is not reused.** [ADR-053](ADR-053.md) and `0036` retired a name rather than redefining it so that a reader who greps it finds nothing instead of a statement whose meaning changed underneath them. **The reason is stronger here than in either precedent: the other operand changed.** A reader who greps `rule_states_consistency_period_started` must not find a constraint that compares a different pair of columns.

---

### 3. What this deliberately stops asserting, which is the half worth the founder's attention

**Four losses, stated rather than discovered later.**

- **Nothing in the schema now bounds `consistency_period_start_day` against the row's own `trading_day`, in either direction.** A period start years in the future is accepted on every row.
- **Before the first settlement the constraint asserts nothing at all.** `payout_anchor_day IS NULL` is exactly `payouts_settled_count = 0` by `rule_states_settlements_imply_anchors` ([`0015:188`](../../packages/db/migrations/0015_rule_states.sql)), so **the eval-pass row that motivated this entire ruling is EXEMPT from its replacement.** It inserts clean at `0046` because the constraint is silent, not because the constraint permits it. Section 4 is what makes that distinction testable rather than asserted.
- **The true bound is not expressible as a `CHECK`.** It is `period_start <= nextTradingDayAfter(trading_day)`, and `nextTradingDayAfter` is a lookup into `trading_calendar`; **a `CHECK` cannot read another table.** That is the same wall ADR-053 hit when the freeze it wanted turned out to be a two-row property.
- **What holds the eval-pass shape instead is the fixture and property layer**, `GS-068` and `RE-P-18`. **The schema is not a second opinion on that row**, and this is stated so the next reader does not treat it as one.

**Four stronger or simpler designs were considered and each is refused for a stated reason.**

**(a) Drop the constraint outright.** Refused: `R-47`'s strictness is real, stated and expressible, and discarding it repeats ADR-053(c)'s error of throwing away a true statement because a false one sat next to it.

**(b) Keep a `trading_day` bound with a slack constant**, `period_start <= trading_day + N`. Refused twice over: `N` is invented, and [ADR-042](ADR-042.md)'s date-unit shape check forbids interval arithmetic against a `date` column. The next trading day after a Friday is three calendar days later and after a holiday cluster it is more, so no constant is both safe and meaningful.

**(c) Scope the old predicate to `phase = 'eval'`.** **Refused as vacuous, and this is the most instructive of the four.** [`advance.ts:120`](../../packages/rules-engine/src/day/advance.ts) sets `consistencyPeriodStartDay: null` for the whole eval phase, so the `IS NULL` disjunct already passes every eval row. **The constraint would cover nothing while looking like a control**, which is worse than no constraint, because the next reader would count it as coverage.

**(d) A trigger consulting `trading_calendar`.** Refused for `0036`'s stated reason, that a trigger can be disabled and fires per row rather than per constraint, and for a second reason of its own: it would have to identify the reset row, **no column marks one**, and deriving a discriminator from `traded_days_count = 0` is precisely the move ADR-053 section 3(b) refused.

---

### 4. The predicate is two-valued because of guards it writes, which is ADR-053's hazard inverted

**A `CHECK` that evaluates to NULL PASSES in PostgreSQL.** ADR-053's predicate was two-valued because of three `NOT NULL`s it never mentioned, and its probe asserted them from the catalogue for that reason. **Here both compared columns are `NULL`able** — confirmed from `information_schema` on the running database — **so the two `IS NULL` guards written into the predicate are what make it two-valued.**

The hazard runs the other way and the probe asserts the other fact: **if a later migration makes either column `NOT NULL`, a guard here becomes dead code**, and the next reader should be told by a failing probe rather than by inspection.

---

### 5. The probe watches the new constraint REFUSE, and that is not the same test as watching the old row insert

**This is the assertion the first draft of this entry was missing, and it is the one that matters most.**

Section 3 establishes that the eval-pass row is exempt from the replacement. **So "the row inserts clean at `0046`" is satisfied by a constraint that refuses nothing, ever.** A `CHECK` that has only ever been watched not-applying is a `CHECK` nobody has tested, and it would have shipped that way.

[`probe_consistency_period_after_anchor.sql`](../../scripts/db/probe_consistency_period_after_anchor.sql) therefore asserts in **three** directions, leading with the success cases because the defect being repaired was a constraint refusing a legitimate row and no inventory of rejections can see one. Run at `0046`:

```
SUCCESS 1: the eval-pass row is writable (session 129 row 0, trading_day 2026-01-01 period_start 2026-01-02)
SUCCESS 2: a settled row whose period starts the next trading day after the anchor is writable (anchor 2026-11-25, start 2026-11-27)
SUCCESS 3: an ordinary funded day after the settlement is writable (start 2026-11-27 before trading_day 2026-12-04)
REJECTION 1: a period starting ON the anchor is refused by rule_states_consistency_period_after_anchor, (AS-12, R-47 is strict)
REJECTION 2: a period starting BEFORE the anchor is refused by rule_states_consistency_period_after_anchor
REJECTION 3: the retired name is absent from the catalogue
REJECTION 4: both guarded columns are nullable, so neither IS NULL guard is dead
REJECTION 5: the predicate still compares against payout_anchor_day
```

and the same file run against a database at `0045`:

```
ERROR:  PROBE FAILED: the eval-pass row is unwritable, the period bound has been re-pointed at trading_day
exit: 3
```

**`REJECTION 1` and `REJECTION 2` assert the CONSTRAINT NAME rather than a bare `check_violation`**, via `GET STACKED DIAGNOSTICS`. The bare condition is satisfied by any constraint on the table refusing the row, so a probe catching it would report these cases green on a row rejected by `rule_states_settlements_imply_anchors` or by the win-day bound — a rejection that proves nothing about the constraint under test.

### 6. Consequences

- **[`0046`](../../packages/db/migrations/0046_supersede_rule_states_consistency_period_started.sql) drops `rule_states_consistency_period_started` and adds `rule_states_consistency_period_after_anchor`.** The retired name is **gone from the catalogue** rather than quietly redefined, asserted by `REJECTION 3`.
- **The column and constraint `COMMENT`s are re-stated in `0046`.** A `COMMENT` is replaceable metadata rather than migration text, so `0015` is untouched on disk and still says what it said the day it merged. Its `--` comment above the constraint can never be edited (E2) and still reads *"a consistency period that has started is not in the future"*, which is the sentence that was wrong.
- **[`probe_consistency_period_after_anchor.sql`](../../scripts/db/probe_consistency_period_after_anchor.sql) is wired into the migrations job and pinned in `CI-06h`'s required list, in one commit.** `CI-06s` asserts both directions and `DELTA_MANIFEST` section 18 records that a probe wired and left unpinned has happened three times.
- **[`DATA_MODEL`'s `rule_states` entry](../architecture/data-model/rule_states.md) carries the constraint by name** in its `Constraints:` line, so the retired name is replaced there in the same branch rather than left pointing at a constraint the database no longer has.
- **No engine change and no fixture change.** `packages/rules-engine` is untouched. `GS-068` and `RE-P-18` are already correct; it is the schema that could not hold the row.
- **No `SD-nn` and no `CI-06` letter.** `0047` stays free.

- **Founder approval: PENDING.** **Unsigned by design rather than by omission.** This supersedes a `CHECK` on a merged money-path table, so it is not taken on a session's authority ([E2](../../MERIT_BUILD_MASTER_PROMPT.md), [ADR-003](ADR-003.md)).

  **One checkable clause, carrying the refusal direction rather than only the insert:** *the probe inserts the eval-pass row clean at `0046`, is refused at `0045` naming `rule_states_consistency_period_started`, and at `0046` a post-settlement row whose period starts on or before its anchor is refused naming `rule_states_consistency_period_after_anchor`.* **Cost if wrong: a merged money-table constraint is superseded for a case that does not occur, and replaced by one that refuses nothing.**

  **Every load-bearing claim above was executed or read at its source in this session**, per the [CLAUDE.md](../../CLAUDE.md) caution that the reconciliation session's worst errors were failures to check a claim against a primary source. Both database states were run rather than predicted, on PostgreSQL 16.13, with all 46 migrations applying forward-only into an empty database. The mandated grep for a superseding migration was run before any `0015` constraint was cited: `rule_states_consistency_period_started` is defined once, at `0015:193`, and nothing supersedes it. **Session 129's second finding is NOT reproduced here**, because `0037` repaired it on 2026-08-17 and session 132 established that.

  **[ADR-053](ADR-053.md) recorded a merge-before-signature as a process failure and ruled that money-path migrations wait for the read.** This branch waits.
