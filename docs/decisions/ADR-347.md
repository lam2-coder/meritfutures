### 2. Ruling 1: where the limit belongs, and what is honestly buildable here

**[SECURITY](../architecture/SECURITY.md) `C-07` rows rate limits as "edge and app".** Both halves are owed. **Only the app half is in this repository, and the entry says so rather than implying the row is discharged.**

#### 2.1 The wall this tree already reached once, from the other side

[`auth-backend.ts`](../../apps/api/src/auth-backend.ts) states, in a paragraph headed *"THE ONE THAT IS DELIBERATELY ABSENT IS THE PER-IP LIMIT"*, that API_CONTRACT rows `POST /auth/otp` as `5/hour/IP, 5/hour/email` and **only the second half is enforced**, because [`server.ts:170`](../../apps/api/src/server.ts) builds the instance as `Fastify({ logger: options.logger ?? false })` and **configures no `trustProxy` anywhere**, so `request.ip` is the IMMEDIATE PEER. Behind an edge that is one address for every trader at once.

**THIS ROW TAKES THE OPPOSITE DECISION ON THE IDENTICAL FACT, AND THE DIFFERENCE IS THE NUMBER RATHER THAN THE ADDRESS.** The OTP limit is fixed in prose at five per hour, so one shared bucket would have been five requests per hour for the whole product: unusable, and correctly refused. **The certificate limits are DATA the deployment sets**, by both section 11 rows' own words (*"the limits are data rather than prose"*), so a deployment behind an edge sizes them for what its origin actually sees, or moves the control to the edge and says so. What is refused is inventing a number in the source and calling one bucket a per-IP limit.

#### 2.2 What the app half is worth, stated where it is paid

**TODAY IT IS A REAL PER-CALLER LIMIT.** [INFRA](../architecture/INFRA.md) proposes Cloudflare as [ADR-007](ADR-007.md) and **nothing in this repository configures an edge**, so the peer is the caller.

**THE DAY AN ORIGIN SITS BEHIND A PROXY, THE SAME COUNTER BECOMES A GLOBAL LIMIT WITH A PER-IP NAME**, and **no check in this repository can see an edge appear in front of it**. There is no tripwire available: an edge is a deployment fact, not a file. So the limitation is WRITTEN, at four sites, rather than watched, and the cost is stated instead of discovered. **A reader who wants a mechanical control here should build the edge half, not a check.**

**AND THE EDGE HALF IS NOT MERELY THE SAME COUNTER SOMEWHERE ELSE.** A limit that only exists in application code is defeated by anything that does not reach the application, and by anything that reaches N replicas instead of one. Both are the edge's job, both are named in the module, and neither is closed here.

### 3. Ruling 2: per-ASN is not per-IP, and it is refused rather than faked

**API_CONTRACT section 11's verify row is per IP and per ASN**, and `M11:246` counter 3 names the ASN dimension for this endpoint specifically: *"one code verified by thousands of distinct sources is `AS-M11-04`'s enumeration signature"*.

**AN ASN IS NOT OBSERVABLE FROM A SOCKET.** Resolving one needs a mapping from address to autonomous system, which is a DATA SOURCE. **This tree has none and cannot get one**, measured four ways:

1. **`apps/api/package.json` declares ONE runtime dependency, `fastify`.** Every other entry is a workspace package, and none of them carries a routing table. Adding a third-party one is a `VG-12` admission and is not this row's subject.
2. **`certificate_verifications` HAS NO COLUMN FOR IT.** [`0025_reserved_sequence.sql`](../../packages/db/migrations/0025_reserved_sequence.sql) declares `ip_hash bytea NULL` and `user_agent_class text NULL` and nothing else about a source. Adding one is a migration, and this row reserves no migration number.
3. **THE EGRESS IS REFUSED, AND IT WAS RUN RATHER THAN ASSUMED.** Three public ASN endpoints, each `curl` through the configured proxy: `https://ip-api.com/...`, `https://api.iptoasn.com/...` and `https://download.maxmind.com/`. **All three: `curl: (56) CONNECT tunnel failed, response 403`, HTTP code `000`.**
4. **AND A LOOKUP PER REQUEST WOULD BE THE WRONG SHAPE EVEN IF IT RESOLVED**, because it would put a third-party network call on the critical path of the endpoint whose whole problem is that it is expensive.

**SO PER-ASN IS OWED, WITH ITS BLOCKER NAMED, AND NOTHING IN THE TREE PRETENDS OTHERWISE.** A "per ASN" counter computed from anything this process holds would be the per-IP counter under a second name, and **a second name on one counter is worse than the missing counter**: it reports a dimension nobody is counting, which is the shape [ADR-235](ADR-235.md) section 5 ruling 3 refused when it declined to trade the entropy against the limit.

**WHAT IS BUILT INSTEAD, PER ROUTE, IS EXACTLY WHAT EACH ROW SAYS AND NOTHING MORE.**

| Row | Section 11's words | Built |
|---|---|---|
| `GET /verify/:code` | *"Public, and per IP and per ASN **rather than** per `code`"* | per IP. **NO per-code counter**, because the row removes that dimension on purpose: *"one hot card served to many viewers is legitimate"* |
| `GET /certificates/:code/image.png` | *"Per IP and **per `code`**"* | per IP **and** per `code`, because *"an enumeration campaign and a single hot card look identical when only the IP is counted"* |

### 4. Ruling 3: what a refusal returns, and that an absent configuration refuses

#### 4.1 The refusal

**`429`, `application/problem+json`, `code: "rate_limited"`, `title: "Rate limited"`, and a `Retry-After` naming the close of the current window in whole seconds, never below one.**

**NONE OF THAT IS THIS ROW'S VOCABULARY.** [`server.ts`](../../apps/api/src/server.ts)'s `STATUS_CODE` already maps `429` to `rate_limited` and its `TITLE` already carries `Rate limited`; [ADR-235](ADR-235.md) section 5 ruling 2 recorded that both existed and that *"nothing on this route reaches them"*. This is the reach. `Retry-After` follows `POST /auth/otp`'s and `POST /checkout`'s precedent for the identical answer, including the *"at least one second"* floor, because a `Retry-After: 0` reads as "immediately".

**NOTHING SAYS WHICH DIMENSION REFUSED.** Section 2's problem document carries no free text on these rows, and telling a caller whether the address or the code exhausted the budget tells an enumerator which knob to turn. The dimension is a log field.

**AND THE REFUSAL DISCLOSES NOTHING ABOUT MERIT'S BOOK ON THE VERIFY ROW**, which is what lets it sit ahead of the constant-time floor. The decision there reads the ADDRESS and never the token, so a `429` is identical for a code that resolves and one that names no row; [ADR-170](ADR-170.md) section 4.2's floor governs the paths that DO read a code and none of them is reached. The image row sits OUTSIDE `INV-M11-05`'s constant-time clause by API_CONTRACT section 6.3's own words, so its per-code dimension raises no clock question.

#### 4.2 An absent configuration is a refusal

**[ADR-226](ADR-226.md) RULED THAT AN ABSENT TURNSTILE SECRET IS A REFUSAL AND NOT A DISABLED CONTROL. [ADR-240](ADR-240.md) applied the rule to a threshold. THIS IS THE THIRD TIME AND IT IS THE FIRST WHERE THE THING BEING SWITCHED OFF IS A LIMIT**, which is the case where *disabled* and *unlimited* are the same word and where a permissive default is therefore invisible.

**NO NUMBER IN THE MODULE IS A LIMIT.** Five variables, all required, all valued nowhere in this repository ([ADR-012](ADR-012.md)):

| Variable | What it sets |
|---|---|
| `MERIT_VERIFY_RATE_LIMIT_WINDOW_SECONDS` | the verify row's window |
| `MERIT_VERIFY_RATE_LIMIT_PER_IP` | requests per window per observed address |
| `MERIT_CERTIFICATE_IMAGE_RATE_LIMIT_WINDOW_SECONDS` | the image row's window |
| `MERIT_CERTIFICATE_IMAGE_RATE_LIMIT_PER_IP` | requests per window per observed address |
| `MERIT_CERTIFICATE_IMAGE_RATE_LIMIT_PER_CODE` | requests per window per `code` |

**ONE WINDOW PER ROUTE AND NOT ONE SHARED WINDOW**, because section 11 states every other limit in that contract as a RATE (`5/hour/IP`, `600/minute/IP`) and a rate is a count and a window together; two routes sharing one window would make one row's number mean something the other row never said. **Both dimensions of the image row share ITS window**, on the same reading one level down: `per IP and per code` is one rate expressed over two keys.

**THE POLICY IS PARSED AND NOT COERCED**, on `environmentVerifyPresentation`'s stated reason: `Number('')` is `0` and `Number(undefined)` is `NaN`, so an absent variable and a nonsense one must arrive as ONE refusal. **NO UPPER BOUND IS INVENTED**, because no approved document gives one and a ceiling written here would be the module deciding a limit it just said it does not set.

**THE POLICY IS READ ON EVERY REQUEST rather than once at construction**, on `VerifySource.presentation`'s rule: a configuration validated lazily, or on a path only some callers take, answers differently for different callers.

**AND THE PORT'S OWN DEFAULT REFUSES TOO.** `UNWIRED_CERTIFICATE_RATE_LIMITER` throws, so a process that never ran the wiring slice answers `503` on both rows exactly as it does for auth. A default that admitted would let such a process serve the most expensive unauthenticated handler in the tree unmetered while every other port around it refused, which is a control nobody notices is missing.

### 5. Why the counter is in memory, which is the one place this entry declines the tree's own precedent

**THE OBVIOUS ALTERNATIVE IS THE OTP SEND BUDGET'S SHAPE**: count the window off the table the route already writes, exactly as `requestOtp` counts `otp_challenges` inside `db.firm`. `certificate_verifications` is scope class `firm`, is already written on every fetch by both rows, and carries `certificate_verifications_time_idx`. **It is the right instinct and it cannot be made correct here without a migration.**

**`certificate_verifications.result` IS `CHECK (result IN ('valid', 'unknown', 'revoked', 'deferred'))` AND HAS NO MEMBER FOR A REFUSED REQUEST.** A query-based limiter therefore has two options and both are defects:

1. **LEAVE THE REFUSAL UNRECORDED**, which makes the limiter **self-blinding**: past the threshold nothing is counted, the window drains, and a sustained attacker gets a duty cycle instead of a refusal.
2. **RECORD IT AS `unknown`**, which injects a lie into the exact signal `AS-M11-04` counter 3 reads, *"a high distinct-code rate with a near-total unknown rate"*.

Adding a fifth member is a migration. [ADR-235](ADR-235.md) section 6.1 already ruled that a bound in DDL is a migration and refused to widen a fence to reach one; **this row reserves no migration number either, and takes the same answer.**

**A COUNTER IN MEMORY COUNTS EVERY REQUEST INCLUDING THE ONES IT REFUSES**, needs no column and no vocabulary, and is what an application-layer limiter is. **Its costs are stated rather than hidden**, in the module and here:

- **IT IS PER PROCESS.** N replicas serve N times the configured limit. A shared counter is the edge's job and is the same owed item as section 2.
- **ITS KEY SPACE IS BOUNDED PER WINDOW AND NOT ABSOLUTELY.** The map holds at most the distinct keys seen inside one window and is DROPPED WHOLE when the window rolls. **It is deliberately not capped**: a limiter that refuses everybody once its bookkeeping is full is a denial-of-service switch an attacker flips on purpose, which is a worse failure than the memory.
- **THE WINDOW IS FIXED AND NOT SLIDING**, so a caller who spends the whole allowance at the end of one window and again at the start of the next sends twice the limit across the boundary. A sliding window is the same unbounded key space with a per-key timestamp list, and the burst it removes is one window wide. **The window is the deployment's number, so a deployment that cares about the boundary shortens it.**

**AND THE DETECTOR NOW SEES LESS THAN THE LIMITER DOES, WHICH IS A COST THIS ROW CREATES AND MUST NOT LEAVE UNSAID.** `certificate_verifications` records every request the limiter ADMITS and none that it refuses, so past the threshold the table shows a rate CAPPED at the limit rather than the true one. The enumeration signature still fires up to the cap and the `429`s are in the access log. **Closing the gap is the fifth `result` member, owed with the migration it costs.**
