## ADR-257: four fields arrive at two slots, `ok` is the engine's and is not recomputed, and the field with nowhere to go is integer cents (2026-08-29, status: proposed)

**Row `257` sent one session at the last supplier on `useAdminWriteBackend` that is not behind the SSO purchase: the projection of `ValidationResult` onto `PlanValidation`, which the entry had named and which nothing in this tree performed. THE PROJECTION IS BUILT. What it cannot carry is the ruling, and the field it cannot carry is `sizeCents`, which is INTEGER CENTS on a plan an operator is about to publish.**

**THE LOSS IS ARITHMETIC AND NOT AN OVERSIGHT.** A `CvViolation` declares four fields. One entry of `PlanValidation.errors` declares two. Two slots do not hold four facts, so every possible projection loses two of them and the only question is which. **AND THE LOSS IS NOT REMOVABLE BY WIDENING THE PORT**: [API_CONTRACT](../architecture/API_CONTRACT.md) section 2 freezes the problem envelope at `errors?: Array<{ path: string; message: string }>`, so a widened `PlanValidation` would move the same loss one line later. **The loss is forced by a frozen document, so it is REPORTED at section 5 and the document is not moved.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `257`, session **448**, dispatched as `claude/two-shapes-for-one-verdict`.

- **MONEY PATH: this is the projection an operator's plan decision is read through.** The [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) read is **OWED** on this diff and is not discharged by this entry. Ships `proposed` with an **UNSIGNED** approval line. **NO MIGRATION NUMBER AND NO `RI-` NUMBER ARE TAKEN, RESERVED OR SPENT.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That two `plan_version_sizes` rows carrying the same defect produce two violations equal in `id`, in `path` and in `detail` and differing in `sizeCents` alone is **MEASURED**, by running `validatePlan` over them. That `ValidationResult.ok` is false on a plan whose nineteen `CV-nn` rules all pass is **MEASURED**, on a plan built for the purpose. That the `ok` the route is contractually promising is the engine's is **DERIVED**, at [`0004_catalog.sql:188`](../../packages/db/migrations/0004_catalog.sql) and `FM-07`. What is **JUDGED** is that the materialization findings are folded into `errors` rather than dropped beside a false `ok` (section 4), and that `sizeCents` is REFUSED a home in `message` rather than given one (section 4).

- **THE PORT IS NOT WIRED AND THE WIRED COUNT DOES NOT MOVE.** `useAdminWriteBackend` stays `BLOCKED` on `principal(request)`, which is behind the SSO purchase and was never this row's to move.

### 2. The arithmetic, which is the whole shape of the problem

`CvViolation` ([`types.ts:667`](../../packages/rules-engine/src/types.ts)) and `MaterializationFinding` are the same four fields:

| Field | What it is | Where it can go |
|---|---|---|
| `id` | `CV-01` to `CV-19`, or `MZ-lock-flag`, `MZ-per-phase`, `MZ-cap-ordinals`. Two closed vocabularies with disjoint prefixes | `code` |
| `detail` | The engine's own sentence, carrying the value it found | `message` |
| `path` | *"Where it was found, so the publish error names the field and not the rule alone"*, in the field's own words | **nowhere** |
| `sizeCents` | *"`size_cents` of the row it was found on, or `null` for a rules-only finding"* | **nowhere** |

**`path` IS NOT A SUBSTITUTE FOR `sizeCents` AND `sizeCents` IS NOT A SUBSTITUTE FOR `path`.** `path` names a FIELD (`drawdown_cents`, `phase_funded.split_bp`) and is identical across every size row that trips the same rule; `sizeCents` names the ROW and is identical across every rule that trips on the same row. The pair is an address and neither half is one.

**AND `sizeCents` IS THE ONLY ROW ADDRESS THERE IS.** `validatePlan` takes `sizes: readonly PlanVersionSizeRow[]` and reports per row; no violation carries an ordinal, an index or a `plan_version_sizes` primary key. Measured: two rows differing only in `size_cents`, both with `drawdown_cents` at zero, produce

```
{ id: 'CV-02', path: 'drawdown_cents', detail: 'drawdown_cents is 0', sizeCents:  5000000n }
{ id: 'CV-02', path: 'drawdown_cents', detail: 'drawdown_cents is 0', sizeCents: 10000000n }
```

which project to two entries that are **equal**, not degraded and not approximated. `test/admin-write-plan-validation.test.ts` asserts that equality directly.

### 3. THE FIRST RULING: `ok` is the engine's, carried without arithmetic

**The row called this the second trap and it is the one with a wrong answer available on both sides.**

`ValidationResult.ok` is `errors.length === 0 && materialization.length === 0`. A projection that recomputed `ok` from the `CV-nn` list alone would say `true` on a plan version whose `plan_version_sizes` rows disagree with the parent `rules` jsonb. **That is ruled at a primary source and the source is a migration.** [`0004_catalog.sql:188`](../../packages/db/migrations/0004_catalog.sql), in the block declaring the materialized column itself:

> The publish path writes both, and CV-publish validation asserts the materialized flag matches the parent's jsonb.

The failure mode is named where the finding type is declared: **`FM-07`**, *"Plan config published with impossible values ... Accounts permanently ineligible while looking healthy, or a gate that does nothing."* A size row that disagrees with its rules is a plan whose published text and executed arithmetic are two different plans, and `copy_blocks` publishes the first while the engine runs the second.

**THE OTHER DIRECTION IS CHECKED AND IS NOT A COST.** The row warned that taking the engine's `ok` could fail a plan the contract intends to pass. It does not: [API_CONTRACT](../architecture/API_CONTRACT.md)'s publish row states that the endpoint *"Materializes `plan_version_sizes` in the same transaction"*, so the contract's own sentence about this endpoint is that the two agree, and a version where they disagree is not a version that document intends to publish. **Nothing in the corpus says a materialization disagreement is publishable.**

**SO `ok` IS CARRIED THROUGH UNTOUCHED**, and the projection performs no boolean arithmetic at all. `ValidationResult.ok`'s own declaration gives the reason in one line: it is *"carried so a caller cannot publish by checking the wrong list"*, and a projection that recomputed it would be exactly that caller.

### 4. THE SECOND RULING: what the projection carries, what it drops, and what it refuses

[`projectPlanValidation`](../../apps/api/src/routes/admin-writes.ts) is total, pure, and shorter than the block above it that explains it.

**1. THE MATERIALIZATION FINDINGS ARE FOLDED INTO `errors`.** They BLOCK, they are the same four fields, and `MZ-` and `CV-` are disjoint prefixes so nothing is confused by their sharing a list. **The reason it is a ruling rather than a convenience is the handler.** [`admin-writes.ts`](../../apps/api/src/routes/admin-writes.ts) maps `validation.errors` into the problem document with `validation.errors.map((error) => ({ path: error.code, message: error.message }))`, so a projection that dropped them would answer `validation_failed` with an **EMPTY `errors[]`**: a refusal an operator cannot act on, on the one endpoint where the remedy is editing the thing that was refused. Measured, on a plan whose eval and funded daily loss limits differ: `errors` empty, `materialization` one finding, `ok` false.

**2. `diffs` ARE DROPPED AND MUST NOT BE FOLDED.** `PublishDiff` never blocks; `PW-02b` and `PW-04` fire on plans that publish. A `PW-` value inside `errors` would make an advisory indistinguishable from a reason a publish failed, to any caller that reads the list rather than the flag, and it would break the agreement between `ok` and `errors.length === 0` that item 1 exists to establish. **What that costs is real and is reported at section 5 finding 3: `PW-01` to `PW-04` reach nobody on this endpoint.**

**3. `message` IS `detail`, BYTE FOR BYTE, AND NOTHING IS APPENDED TO IT.** The row named this trap and the refusal is asserted rather than intended: the projected document is searched for the two size values and neither appears.

**THE ALTERNATIVE WAS AVAILABLE AND IS REFUSED ON THREE GROUNDS.** `sizeCents` could have been written into `message`, or encoded into a structured `code` such as `sizes[5000000].drawdown_cents`. Both were considered and both are refused:

- **Money in this corpus is an integer field and never a substring.** `INV-02` is *"all money is `bigint` integer cents AT EVERY BOUNDARY"* and [API_CONTRACT](../architecture/API_CONTRACT.md) section 1 is *"`*_cents` are JSON integers"*. A cents value recoverable only by parsing prose is not integer cents at a boundary; it is prose that happens to contain digits.
- **It would not be readable by the caller it is for.** The consumer is the operator console, which must show WHICH size row to repair. A console cannot branch on a regex over a sentence the engine is free to reword.
- **It would hide the finding rather than fix it.** A `message` that carries the number lets the next reader conclude the projection is lossless, which is the exact failure the row's first trap describes.

**4. `path` AND `sizeCents` ARE LOST, AND THE LOSS FAILS CLOSED.** This is the half that decides whether the projection may ship at all. **`ok` survives intact, so every plan the engine refuses is still refused and no plan publishes that should not.** What is lost is an operator's ability to tell which of a version's size rows is broken: the refusal is correct and under-informative. **A publish blocked for an unclear reason costs a session; a publish allowed for a wrong reason costs a plan in front of buyers.** The projection is built because the loss is on the first side of that line, and the loss is reported because being on the safe side of a line is not the same as being right.

### 5. THREE FINDINGS ABOUT `API_CONTRACT`, REPORTED AND NOT APPLIED

**None of the three is repaired here.** Each would move a line in a frozen document, this row grants that only with an ADR clause naming which line moves, and **all three reach every endpoint rather than this one**, so a repair scoped to a publish handler would be the wrong shape of repair. They are stated so that whoever holds a row over that document holds them too.

**FINDING 1. THE PROBLEM ENVELOPE CANNOT CARRY MONEY, AND ONE VALIDATOR IN THIS TREE PRODUCES MONEY.** Section 2 declares `errors?: Array<{ path: string; message: string }>` with the comment *"validation failures only"*. `validatePlan` is the only validator in the corpus whose findings carry a cents value, and that value is the row address. **The envelope is two fields wide and the finding is four fields wide, so widening `PlanValidation` moves the loss and does not remove it.** What a repair would look like is one optional member on the `errors[]` element, integer cents, absent on every other endpoint. It is not taken here.

**FINDING 2. THE `path` SLOT ON THIS ENDPOINT WILL CARRY A RULE ID AND NOT A PATH.** The handler writes `path: error.code`, so a `validation_failed` from a publish carries `CV-09` in the field section 2 documents as *"`errors[]` lists paths"* and `CvViolation.path` describes as *"where it was found, so the publish error names the field and not the rule alone"*. **The wire has ONE addressing slot and the engine produces TWO addressing facts**, so the handler's choice is forced by the same arithmetic as everything else in this entry, and this session does not change it: the `id` is the closed, stable vocabulary a client can branch on, and `path` is not unique across size rows. **The mapping line is left exactly as committed** because changing what a caller is served is a contract decision and not a handler's.

**FINDING 3. THE PUBLISH ROW NAMES TWO ERRORS AND THE HANDLER RAISES A THIRD.** [API_CONTRACT](../architecture/API_CONTRACT.md)'s `POST /admin/plans/versions/:versionId/publish` names `precondition_failed` and `conflict`. It does not name `validation_failed`, which is what the handler answers both for a malformed body and for a `CV-nn` violation, and which other rows in the same document do name explicitly where it applies. **And the code may be the wrong one on the CV path rather than merely unlisted:** section 2 defines `validation_failed` as *"Body or query failed schema validation"*, and on a CV violation the body is well formed and the STORED DRAFT is what cannot publish. That is a 422-shaped condition in a document that already reserves six 422 codes for exactly that distinction. **Reported. It is a ruling about a frozen endpoint row and it needs a founder, not a session with a projection to write.**

### 9. Where this session is most likely wrong

**THE `ok` RULING RESTS ON A MIGRATION COMMENT AND ON A FAILURE-MODE NAME, NOT ON AN ENDPOINT RULING.** [`0004_catalog.sql:188`](../../packages/db/migrations/0004_catalog.sql) says CV-publish validation asserts the flag matches, and `FM-07` says what a mismatch costs. **Neither says the word `ok`, and no approved document states in one place that a materialization finding refuses a publish.** The engine states it, at [`validate.ts:674`](../../packages/rules-engine/src/plan/validate.ts), and this entry takes the engine at its word on the ground that the engine's reading is the one the migration comment describes. A founder who reads `0004`'s sentence as describing the SIZE-MATERIALIZATION step of the same transaction rather than a gate before it would rule the other way, and the projection's one line would change.

**AND THE JUDGEMENT THAT THE LOSS FAILS CLOSED IS ABOUT THE WHOLE PUBLISH PATH AND IS ARGUED, NOT EXECUTED.** It rests on `ok` being the only value the handler branches on, which is read from the handler and is true today. **It would stop being true the moment anything downstream read `errors` to decide something**, and nothing mechanical in this tree would notice. That is the strongest argument for not shipping the projection at all, and it is recorded here rather than resolved.

**THE PROJECTION IS NEVER CALLED IN THIS TREE.** No wiring slice exists, so every case here drives it directly. What is NOT executed is the composition a deployment would write, and in particular that `validatePlan`'s `rules: unknown` and `sizes: readonly unknown[]` can be narrowed to `PlanRulesJson` and `PlanVersionSizeRow[]` at the wiring site without a cast that hides a shape error. **The port takes `unknown` and something has to make it concrete, and this entry does not say what.**
