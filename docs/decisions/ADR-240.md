## ADR-240: a horizon a deployment sets is configuration and a signing key this deployable would hold is not, so one of three ports is wired and the other two have their absences measured (2026-08-29, status: proposed)

**Row `240` sent one session at three ports whose remaining obstruction was believed to be deployment configuration, on the standing rule that [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md) established: a port may be wired when its only remaining gap is something the deployment supplies, because an adapter that refuses `unconfigured` is a live control rather than a stub. The premise held for one of the three and did not hold for the other two, and which is which is the whole of this entry.**

**`setEconomicCalendarSource` is WIRED.** Its remaining ground was a staleness horizon that lives with the alarm, which is a threshold a deployment sets. It has a name now, [`MERIT_ECONOMIC_CALENDAR_HORIZON_TRADING_DAYS`](../../apps/api/src/routes/economic-calendar.ts), valued nowhere in this repository, and an absent one answers 503 for every request identically rather than publishing a freshness verdict nobody decided.

**`useCertificateBackend` and `useCertificateImageSource` are NOT wired, and the reason is not that the work was larger than expected.** Neither is waiting on a secret. `image_url` is *"signed, time-limited"* and the endpoint it would address accepts no query for a signature to ride on, so no variable in any vault closes it; `CertificateImageSource` waits on a card renderer, and no deployment supplies a renderer by setting a variable. Both entries are narrowed and both absences are made **executable** rather than left as sentences in a test file.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `240`, session **430**, dispatched as `claude/the-ports-that-wait-on-configuration`. The row is **CONDITIONAL** on ruling, and it is taken.

- **NOT THE MONEY PATH.** No ledger account, no balance, no payout, no migration and no reserved number. `E2` is not owed. Ships `proposed` with an **UNSIGNED** approval line.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the wired adapter refuses an absent, blank, fractional, zero and negative horizon, that it opens no door when unconfigured, that the horizon is what decides `stale` and not the rows, that the stored trading day is carried across rather than built from the instant, and that `CertificateCard` and `image/png` each appear in exactly one shipped source file is **MEASURED**, by executing it. That `verify_url`'s old ground is discharged and that the image row admits no query is **DERIVED**, at the file and line each claim names. What is **JUDGED** is that a count of sessions is the right shape for the staleness comparison (section 3), that an unwired port is a 503 and not a 500 (section 4), and that a URL signing key does not belong in `apps/api` (section 5).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every citation in row `240` was re-derived, and two of them did not survive: section 2 carries both.

### 3. The ruling on `setEconomicCalendarSource`, and why [ADR-146](ADR-146.md) clause 4 survives it

[ADR-146](ADR-146.md) clause 4 reads: *"A ROUTE READS NO CLOCK TO DECIDE FRESHNESS, AND THE FRESHNESS FACT ARRIVES AS DATA."* Its stated ground is a vocabulary error and not a prohibition on clocks: *"the comparison `coverage_end_day` sits on one side of is a TRADING day, so a route reaching for `new Date()` would produce a UTC date and compare two different vocabularies."* Its second sentence names who answers instead: *"the deployment where the calendar and the horizon both live, and not the route file."*

> **1. THE HORIZON IS AN ENVIRONMENT VARIABLE, NAMED HERE AND VALUED NOWHERE.** `MERIT_ECONOMIC_CALENDAR_HORIZON_TRADING_DAYS`. [ADR-146](ADR-146.md) clause 7 refused to invent the horizon's VALUE and found none anywhere in the corpus; that refusal is untouched, because no number lands in this repository. What lands is the name a deployment sets it under, which is the shape [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md) both used for a credential and this entry uses for a threshold.
>
> **2. THE UNIT IS TRADING DAYS AND THE NAME CARRIES IT.** `..._HORIZON_DAYS` would have been [ADR-146](ADR-146.md)'s own defect in a variable name: a deployment setting a number would have no way to know whether it had bought calendar days or sessions, and the two differ by every weekend and every holiday in the window.
>
> **3. `stale` IS A COUNT OF SESSIONS AND NEVER A DATE COMPARISON.** The adapter counts the `trading_calendar` rows whose session has **not yet opened** at the instant of the read and whose `trading_day` is at or before `covered_through_day`, and compares that count with the horizon. `session_open_at` is a `timestamptz` and so is the clock; `trading_day` is a day and so is `coverage_end_day`. **No value ever crosses between the two vocabularies**, so the failure clause 4 forbids has no site at which to happen.
>
> **4. AN ABSENT HORIZON IS `unconfigured` AND FAILS CLOSED WITH A 503.** There is deliberately no default. Both defaults are wrong in a way a deployment cannot see: a `false` is [`DEP-M4-09`](../plans/M04-trader-portal.md)'s confident failure published to a trader, and a `true` is a permanent alarm a deployment cannot switch off by configuring the thing it forgot.
>
> **5. THE PANEL AND THE ALARM READ ONE NAME.** [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md)'s Tier-1 row asserts the same comparison from the alarm's side. [INFRA](../architecture/INFRA.md) section 8 rows the variable beside that alarm and states that both are set to the same value, because two values would be a panel and an alarm disagreeing about one calendar.

**Clause 3 is the judgement and the alternative is what makes it one.** The obvious implementation resolves *"today's trading day"* by containment, `session_open_at <= now <= session_close_at`, and then compares two days. **That shape has no answer at 03:00 on a Saturday**, and a dashboard panel is asked the question at 03:00 on a Saturday. Choosing between *"the last session that closed"* and *"the next session that opens"* is a ruling about what an operator and a trader see out of hours, which no approved document makes and which this fence had no business making. **A count of sessions still ahead is defined at every instant**, needs no holiday branch because [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql) made a holiday's `session_open_at` NULL and `NULL >= $1` is not true, and degrades in the safe direction: a `trading_calendar` that is itself exhausted counts few sessions ahead and the panel says stale, which is the honest answer when the sessions cannot be counted.

**What the adapter reads, and through which door.** Three tables, all scope class `firm` in [`packages/db/src/scope.ts`](../../packages/db/src/scope.ts), in one `db.firm` transaction: `economic_calendar_current` for the occurrences, `economic_calendar_loads` for `covered_through_day`, and `trading_calendar` for the count. The view and never the base table, because [`0039`](../../packages/db/migrations/0039_economic_calendar.sql) calls the view *"the only definition of that anywhere"* and an adapter over `economic_calendar` would re-derive the maximum revision in TypeScript, which is `FM-M7-08`'s second source of truth. **The occurrence read is bounded by `atLeast(now)` on `scheduled_release_at`**, which is [`0039`](../../packages/db/migrations/0039_economic_calendar.sql)'s own `economic_calendar_release_idx`, *"the panel's read: upcoming releases by instant"*, and is an instant compared with an instant.

**The maximum over `coverage_end_day` is lexicographic and that is sound where sorting instants is not.** [ADR-146](ADR-146.md) finding 8: a zero-padded ISO **day** has one spelling and an RFC 3339 **instant** does not, which is why `renderEconomicCalendar` still refuses to sort rows.

### 4. An unwired port is a 503 and never a 500, which this route had backwards

`routes/economic-calendar.ts` threw `EconomicCalendarError` when no source was wired, and that class becomes a 500 through `server.ts`'s error handler. Its own header explains why every case of that class is a 500: *"EVERY CASE IS A DEFECT RATHER THAN A REQUEST THE CALLER GOT WRONG."* **An unwired port is not a defect.** It is a deployment nobody finished, which is the sentence `VerifySourceUnwired`, `CertificateBackendUnwired` and `CertificateImageUnwired` each already carry on their own ports.

> **6. `EconomicCalendarUnwired` AND `EconomicCalendarUnconfigured` ARE TWO CLASSES AND ONE STATUS CODE.** Both answer 503. They are separated for the same reason [`turnstile.ts`](../../apps/api/src/turnstile.ts) keeps three refusals apart while telling the caller one thing: an operator needs to know whether a line is missing from `start.ts` or a variable is missing from a vault, and a caller must not be told either. The refusal carries no detail, on [API_CONTRACT](../architecture/API_CONTRACT.md) section 2's rule that a problem document never leaks internals.
>
> **7. AN `EconomicCalendarError` IS STILL A 500 AND THE SUITE ASSERTS BOTH DIRECTIONS.** A tier of four, two rows for one occurrence, a `*_day` carrying an instant: each is a row somebody wrote wrongly and this endpoint takes no input, so a caller can cause none of them. A 503 there would send an operator to look at a vault for a bug in a loader. **A separation asserted in one direction only is a rename.**

### 5. The trap, ruled: a signing key is not a Turnstile secret, and this one is not even a secret this deployable could use

Row `240` named the trap and asked for a ruling rather than a wave. Here it is, in the order the facts arrived.

**FIRST, THE TWO KEYS ARE DIFFERENT KEYS AND ONLY ONE OF THEM EXISTS.** `certificates` carries `signature bytea NOT NULL` and `signing_key_id text NOT NULL` ([`0020_public_surface.sql`](../../packages/db/migrations/0020_public_surface.sql)), and that is the **CLAIM** signature: [M11](../plans/M11-certificates-social-proof.md) section 3.2 has the issuer, which runs in the **worker**, ask a Vault to sign the canonical claims and store what comes back. `INV-M11-06` is its rotation property and M11 section 3.3 is its rotation state machine. **`apps/api` already reads that signature out of a column and has never held the key that made it**, which is the correct posture and is not what `image_url` asks for. The URL signature is a second key, for a second purpose: time-limited access to bytes.

**SECOND, THE SIGNATURE HAS NOWHERE TO RIDE ON THE URL THIS REPOSITORY SERVES.** [API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3 states of `GET /certificates/:code/image.png`: *"Auth: none. Request: the path token only, no query, no body."* A signed, time-limited URL carries at minimum a signature and an expiry, and the path has no slot for either. `imageHandler` reads `request.params` and never `request.query`, and [`certificate-links.test.ts`](../../apps/api/test/certificate-links.test.ts) asserts that structurally **and** behaviourally: the same code fetched with signature-shaped query parameters is answered identically to one fetched bare. **So an `image_url` pointing at that row is unsigned however it is dressed**, and a deployment handed a key would have nowhere to spend it.

**THIRD, A KEY HELD HERE WOULD BE THE WRONG SHAPE OF RISK AND THE ROW IS RIGHT TO SAY SO.** A Turnstile secret is sent to the party that does the work and verifies the answer; Merit's process holds a credential it cannot misuse on its own. A **URL signing key is held and USED by this process**, and `apps/api` is the internet-facing surface with the largest reachable code path in the estate, serving the trader API and the operator API off one codebase. What that would cost, stated rather than waved past: **key storage** in a process that also terminates unauthenticated public requests; **key rotation** on a calendar M11 section 3.3 wrote for the claim signer and not for this; and a **blast radius** in which an application compromise mints valid card URLs for every code in the book, including codes the compromise learned by enumeration.

> **8. THE URL SIGNER DOES NOT BELONG IN `apps/api`, AND IT BELONGS WITH WHATEVER VERIFIES IT.** A signed URL is verified by the server that serves the bytes. [INFRA](../architecture/INFRA.md) section 2 already rows both candidates: **S3-compatible object storage**, whose presigner is the store's own and whose key never enters an application process, and **Cloudflare at the edge**, whose signed-URL verification is an edge rule. Either puts the key with the verifier, which is where a key that authorises access to an object belongs.
>
> **9. AND THAT IS NOT ENOUGH TO WIRE THIS PORT, WHICH IS THE HONEST HALF.** [`routes/account-reads.ts`](../../apps/api/src/routes/account-reads.ts)'s `CERTIFICATE_BLOCKER` reached the same finding independently on the `/certificate` row and states the count: *"the card renderer, the CDN origin and the URL signer are all M11 and none exists"*, and `certificates` carries no image location column, *"so there is not even a stored value to sign"*. **A variable named here would close the ORIGIN and neither of the other two.** So `useCertificateBackend` is not the shape [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md) wired, and it is not wired on their precedent.
>
> **10. NO NAME IS TAKEN FOR THE ORIGIN, AND THE REASON IS `useCheckoutAdapters`' STATED RULE.** A variable whose only consumer refuses is a name nothing reads, and calling a setter that installs a supplier which always throws would raise the wired count and serve nothing. The origin's name is owed to the slice that has a card to point it at.

### 6. `useCertificateImageSource`, and the absence made executable

The entry already said the right thing: the answer this port owes is **bytes**, and [`certificates.ts`](../../apps/api/src/routes/certificates.ts)'s own header says the renderer *"is not in this repository"*. **That is a claim about what this repository does NOT contain, which is the class of claim [ADR-235](ADR-235.md) found had been read for weeks as a description of a deployment, and session 426's landmine states in one line: a comment cannot fail.**

So it is measured. Over every `src` directory of every member of `apps/` and `packages/`, which is every directory in this repository holding shipped application source: **`CertificateCard` is named in one file and that file is the port's own declaration**, and **`image/png` is named in one file and it is the route that LABELS bytes it was handed**. `assertPng` there refuses bytes carrying no PNG signature, which is a validator and is the opposite of a producer. [`certificate-links.test.ts`](../../apps/api/test/certificate-links.test.ts) executes both counts, and asserts first that the sweep reaches source at all, so an empty answer is not an empty search.

> **11. THE DAY A RENDERER LANDS, THAT CASE GOES RED AND THE ENTRY EXPIRES.** This is `RI-22` leg 3's shape at test scale: assert over what the tree produces rather than over the prose describing it.
>
> **12. ONE HALF OF THE CARD IS CONFIGURATION AND THE OTHER IS NOT, AND THAT IS WHY THE PORT STAYS BLOCKED.** `CertificateCard.cache_max_age_seconds` is *"config rather than a number stated here"* ([API_CONTRACT](../architecture/API_CONTRACT.md) section 6.3), so a deployment supplies it. The `bytes` beside it are a renderer, which no deployment supplies by setting a variable. **A port with one configurable half and one absent half is not a port that configuration closes**, and naming the first while the second has no producer would be clause 10's defect a second time.

### 10. Consequences

- **The dashboard's economic calendar panel serves real rows from a real deployment for the first time**, and the freshness fact beside them is decided against a threshold somebody set rather than against nothing.
- **A deployment that forgets the horizon finds out immediately and loudly**, at a 503 on one endpoint, rather than at a trader reading a confident empty panel.
- **The panel and the alarm now share one name**, so the two cannot drift into disagreeing about one calendar without somebody changing two values.
- **The wired count moves from seven to eight and the blocked list from seventeen to sixteen**, and `wiring.test.ts` asserts the numbers rather than logging them.
- **Two blocked entries stop resting on unexecuted claims.** The next session dispatched at either meets a test that will have failed the day the obstruction lifted.
- **The certificate card's home is now a named question rather than an assumed one.** Whoever takes M11's card slice starts from clause 8 instead of from a signing key in an API process.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST IS WHETHER A COUNT OF SESSIONS IS THE STALENESS COMPARISON YOU MEANT.** [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md) says the coverage day *"still runs ahead of today by the configured horizon"*, and section 3 clause 3 implements *"ahead"* as a count of sessions rather than as a difference between two days. The two agree on an ordinary Tuesday and disagree across a long weekend, which is exactly the window in which a stale calendar is most likely and least noticed. **If you meant calendar days, the variable's name is wrong and so is the comparison**, and both change together in one file.

  **THE SECOND IS THAT THE PANEL AND THE ALARM ARE ONE NAME AND TWO PROCESSES.** Clause 5 asserts they must be set to the same value and nothing in this repository can check it: the alarm is not in this tree. **A deployment that sets one and not the other gets a panel and a pager disagreeing about the same calendar**, and the failure is silent in the direction that matters, because the panel would say fresh while nothing paged. A check that reads both is owed to whoever builds the alarm.

  **THE THIRD IS WHERE THE CARD LIVES, WHICH THIS ENTRY DELIBERATELY DOES NOT DECIDE.** Section 5 rules the signer out of `apps/api` and names two candidates, and it stops there. **The decision that follows is not a technical one**: a card served from an object store is a file that exists after revocation until its URL expires, and `INV-M11-08` makes the re-render the only path by which a revocation reaches an image already in circulation. **A presigned object URL and a live re-rendering endpoint are two different revocation stories**, and the second is the one the corpus is written against.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The adapter has never met a database.** Every case here runs against a fixture that answers by table key, which proves which door was opened, which tables were named and what the filters carried, and proves nothing about whether `rowsWhere` on a `DISTINCT ON` view behaves as the transcription says. `packages/db`'s own suite covers the predicate and `ADR-120`'s approval clause runs the other half against a real PostgreSQL; **this entry has run neither against `economic_calendar_current`**, and a view is the one relation kind where the accessor has the least prior traffic.
