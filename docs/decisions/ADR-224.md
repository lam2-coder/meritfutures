## ADR-224: `.env` is ignored by a three-line rule and the rule is asserted by running git, because an entry anybody can delete is not a control and the gate that claimed to verify it reads no gitignore  (2026-08-29, status: proposed)

**THE CONSTITUTION ASKED FOR THIS BY NAME AND NOTHING HAD DISCHARGED IT.** [`MERIT_BUILD_MASTER_PROMPT.md:384`](../../MERIT_BUILD_MASTER_PROMPT.md), Appendix E's Moltbook row, demands *"`.env` never in git (verified by CI, not trust)"*. The parenthetical is the whole clause and it is the half that was missing: there was no entry to trust and no verification either.

### 2. The pattern set, derived spelling by spelling

**Three patterns, and each one exists because the other two do not cover it.** Git's rule is that a pattern carrying no slash matches by BASENAME at any depth, and that the last matching pattern in a file decides.

| Pattern | What it covers, and the spelling that forces it to exist |
|---|---|
| `.env` | The plain file at any depth: the root `.env`, `apps/api/.env`, `packages/db/.env`. **A leading-slash `/.env` would be root-only**, which is the spelling that leaves a per-package file uncovered, and `apps/api/.env` is precisely the file a developer creates when a package needs its own connection string |
| `.env.*` | The suffix family at any depth: `.env.local`, `.env.production`, `.env.test`, `apps/api/.env.local`, and the two-suffix `.env.production.local` the Next.js and dotenv conventions both document. **It is a separate pattern because `.env` does not match `.env.local`**, which is the trap the row named: a set that looks complete covers the file nobody creates and misses the five people actually write. **And `*.env` covers neither**, since it requires a name before the dot |
| `!.env.example` | Re-includes the one file that is a TEMPLATE. It is a negation, so it must come after the two patterns it carves out of, and it matches by basename too, so `apps/api/.env.example` is re-included as well as the root one |

**MEASURED, not reasoned.** Against the three lines as landed, `git check-ignore --no-index -v -n` answers: `.env` ignored by `.env`, `apps/api/.env.local` ignored by `.env.*`, `.env.example` matched by `!.env.example` and therefore NOT ignored, `.envrc` matched by nothing. That transcript is section 5's fourth block in inverted form and it is the acceptance direction the suite asserts.

### 3. `.env.example` is the exception, and it is the ONLY one

**A committed template carries variable NAMES and never values.** Without it, every developer reconstructs the variable list from a stack trace, which is how a `.env` gets written from guesswork in the first place. It is a real and common exception and this entry takes it deliberately rather than inheriting it.

**THE EXCEPTION SET HAS EXACTLY ONE MEMBER AND THAT IS THE RULING.** `.env.sample` and `.env.template` are equally common spellings and both are REFUSED. The argument is not tidiness: **every additional spelling admitted here is another name under which somebody can commit a real value and be told by `.gitignore` that it was fine.** One spelling is one thing a reviewer has to recognise. Three is a set nobody holds in their head, and the failure is silent in the dangerous direction.

**NO `.env.example` IS CREATED BY THIS ENTRY**, and no file of any `.env` spelling is. The negation declares the exception; it does not require the file to exist, and `git check-ignore` answers about a path whether or not anything is there. The row forbids creating one and nothing here needs it.

#### 3.1 `.envrc` is deliberately OUTSIDE the rule

**It is direnv's file and direnv is used by nothing in this repository.** Scope of the search: the whole tree excluding `node_modules` and `.git`; `grep -rn "direnv\|envrc"` returns nothing outside `.gitignore`'s own comment and `RI-21` itself. It is also a shell SCRIPT rather than a value file, so the naming convention this rule is about does not reach it.

**The reason it is asserted rather than merely left out** is that an omission and a decision look identical in a `.gitignore`. `RI-21` asserts `.envrc` is NOT ignored, so the next reader finds a decision with an entry beside it rather than a hole. **If direnv is ever adopted, this section is where the pattern set is re-argued**, and the check goes red on the day the rule changes without it.

### 4. **THE CHECK IS THE DELIVERABLE AND THE `.gitignore` LINE IS NOT**

**An entry anybody can delete with no gate noticing is the exact defect this entry exists to end.** The three lines landed in `.gitignore` are one careless edit from gone, and the sentence in `INFRA` would go on asserting them.

**AND A GREP FOR `.env` IN `.gitignore` IS NOT A TEST THAT `.env` IS IGNORED.** That is the whole reason an `RI-nn` was spent rather than a line added. Two cases settle it, both seeded in the suite:

1. **A subdirectory `.gitignore` re-includes the path while the root entry is still there word for word.** `apps/api/.gitignore` holding `!.env.local` leaves `apps/api/.env.local` unignored, and a grep over the root file finds `.env.*` and reports success. This case is [`repo-invariants.test.ts:2577`](../../packages/tooling/test/repo-invariants.test.ts) and it is the argument in one test.
2. **A `*` catch-all makes every subject ignored for a reason that is not this rule**, would read green after the `.env` entries were deleted, and takes the corpus with it.

**SO `RI-21` ASKS GIT.** [`repo-invariants.mjs:4710`](../../packages/tooling/checks/repo-invariants.mjs) runs `git check-ignore --no-index -v -n --stdin` over the paths in `ENV_IGNORE_SUBJECTS` ([`:4568`](../../packages/tooling/checks/repo-invariants.mjs)), **fourteen of them, nine that must be ignored and five that must not**, and each row carries the spelling it is there for. `-v` returns the matching SOURCE and PATTERN, which is what lets the check refuse a match that did not come from this repository's own `.gitignore`: a developer's global excludes file or a `.git/info/exclude` is not in any clone but one, and a pattern that does not name `env` is not the rule this entry states.

**A NEGATION IS A MATCH THAT MEANS NOT-IGNORED**, and reading "a rule matched" as "ignored" would invert exactly the exception section 3 carves out. `git check-ignore -v` reports `!.env.example` as the deciding rule for `.env.example`, and the check reads the leading `!`.

#### 4.1 Leg 2, because an ignore rule does not reach a tracked file

**Git applies `.gitignore` to UNTRACKED paths only.** A `.env` committed before the rule landed stays in the tree, stays in every clone and stays in the history, and leg 1 goes on reporting that the rule holds, which it does. **The rule holding is not the property anybody wants.**

Leg 2 is one `git ls-files` ([`repo-invariants.mjs:4818`](../../packages/tooling/checks/repo-invariants.mjs)) and it reports any tracked path whose basename is `.env` or begins `.env.`, with `.env.example` alone admitted. **Measured on this branch: zero such paths, so this leg is green on landing and its finding text has been watched firing in the suite** ([`repo-invariants.test.ts:2604`](../../packages/tooling/test/repo-invariants.test.ts), which stages an EMPTY file in a temporary work tree and never in this repository).

**`--no-index` on leg 1 is deliberate and the two legs are why.** Without it, git reports a tracked path as not-ignored, and a committed `.env.example` would satisfy leg 1's "must not be ignored" assertion for entirely the wrong reason. Leg 1 is about PATTERNS; leg 2 asks the tracking question on its own.

### 6. What is refused

- **A SECRETS-SCANNING LEG OF ANY KIND**, which the row names as the trap. `RI-21` reads no file content anywhere. `CI-05` already runs gitleaks twice, semgrep, `pnpm audit` and syft/grype, and section 1 measured **0** `continue-on-error` across all four workflows. **The property `RI-21` owns is the one none of those five reads: what git will do with a path that does not exist yet.**
- **A NEW CI STAGE, AND ANY EDIT TO `.github/workflows/**` AT ALL.** The row admits the workflow *"if the check needs a stage"* and it does not: `RI-21` is a row of `CHECKS`, so [`ci.yml:173`](../../.github/workflows/ci.yml)'s repository-invariants step in `CI-01` runs it on the day it lands, with no edit anywhere. **A fence condition that is not met is not an invitation.**
- **`.env.sample` and `.env.template`** as further exceptions, on section 3's argument.
- **`.envrc`**, on section 3.1's, and it is asserted rather than omitted.
- **A pattern over `secrets.txt`, `credentials.json` or `env.production` without a leading dot.** They are outside the naming convention this rule is about, and a rule that reaches for them is a rule whose population nobody can state.
- **Creating a `.env`, a `.env.example` or any file of that family**, and writing any real value anywhere. The suite's leg 2 case stages an EMPTY file in a temporary directory outside this repository.
- **Grepping `.gitignore` for a string**, which is section 4 and is the reason the number was spent.
- **`MERIT_BUILD_MASTER_PROMPT.md`**, which is frozen. Its Moltbook clause is quoted and not edited.

### 8. Where this entry is most likely wrong

**The population is a list of spellings and the world is not.** `RI-21` asserts fourteen paths. A file named `env.production`, `.env-local` with a hyphen, or `config/secrets.env` is outside both the check and the `.gitignore` rule it asserts, and neither would be caught by anything here. **That is a deliberate scope and not an oversight**, because the alternative is a pattern wide enough to swallow source files, which seed 4 shows the check refusing. But it means the honest claim is *"the dotenv naming convention is ignored"* and never *"a secret cannot be committed"*, and section 9's approval block asks the founder to read it that way.
