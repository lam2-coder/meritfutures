### 2. The vendor. Postmark, and the two criteria that decide it

Four criteria, from the row: **deliverability, price transparency, whether a key can be scoped to sending alone, and whether a sandbox exists that costs nothing.** Two candidates were weighed seriously.

**THE CHANNEL THAT SIGNS A TRADER IN IS EMAIL, SO THE VENDOR THAT MATTERS IS A MAIL VENDOR.** `verifyOtp` refuses the `sms` channel outright, so an SMS vendor would deliver codes nothing here can consume. That is section 6 and it is why this section weighs mail and not messaging.

| | **Amazon SES** | **Postmark (taken)** |
|---|---|---|
| **Integration cost in THIS tree** | SigV4 request signing. That is either `@aws-sdk/client-ses` or a hand-rolled signer on the sign-in path | **One `fetch`.** A JSON `POST` with the token in a header, which is `turnstile.ts`'s call shape with a different body |
| **Key scoped to sending** | Tightest in principle: an IAM policy can be `ses:SendEmail` on one identity ARN | **Tight in practice with no policy to write.** A *server* token sends from one server and cannot manage the account, the domains or the other servers; the account token that can is a different credential this deployment is never given |
| **Deliverability** | Shared pools, reputation the sender builds; DKIM and SPF are the operator's either way | **Transactional-only pools.** The vendor refuses bulk mail on the streams a code goes out on, so Merit's sign-in code does not share IP reputation with anybody's newsletter |
| **Sandbox that costs nothing** | Yes: new accounts start sandboxed and send only to verified addresses | Yes: a test token that accepts requests and delivers nothing. **Neither is used by this repository's suite**, which injects `fetch` instead |
| **Published per-send price** | Published per thousand | Published per volume plan |

**THE DEPENDENCY IS WHAT DECIDES IT AND THE ARGUMENT IS ALREADY IN THIS FILE'S NEIGHBOUR.** [`auth-backend.ts:925`](../../apps/api/src/auth-backend.ts)'s `NO_WEBAUTHN` refuses a ceremony because *"admitting one is a `VG-12` decision with an entry of its own, not a line in a wiring slice"*. An AWS SDK on the sign-in path is exactly that shape, and hand-rolling a request signer is worse: a signing bug fails as a 403 from a vendor rather than as a compile error, on the money path, in a slice whose objective is delivery. **A send that is one `fetch` is a send whose whole surface is readable in one screen**, and that is the property this codebase optimises for everywhere else.

**WHAT IT COSTS PER SEND IS NOT WRITTEN HERE AND THE ABSENCE IS THE RULING.** The row's own trap says a price that cannot be cited to the vendor's published table is a number to leave as config with the absence stated, and **this entry states it: no figure from either vendor's price table is transcribed into this repository.** For the email branch that costs nothing, because the email branch charges no budget (section 3). For SMS it is [`MERIT_OTP_SMS_PRICE_CENTS`](../../apps/api/src/otp-delivery.ts), named and unset.

### 3. The price. It is config, it is integer cents, and absent it the branch refuses

**THE EMAIL BRANCH CHARGES NOTHING, AND THAT IS THE SCHEMA'S DESIGN RATHER THAN AN OMISSION THIS ENTRY TOOK ADVANTAGE OF.** `otp_send_budget` admits four scope kinds and none of them is an address; its cost half is `global` because *"Merit's SMS bill is one number"*; and API_CONTRACT section 11 gives the email row velocity and no budget. **A handler that charged `spend_cents` for an email would be inventing a row shape the table does not have.** So the second half of `NO_DELIVERY` survives exactly where it was written, on the SMS branch, and section 6 is what holds that branch closed.

**THE PRICE IS AN ENVIRONMENT VARIABLE AND NEVER A CONSTANT IN A FILE**, for the reason a constant is wrong rather than merely unfashionable: a per-message price varies by destination country, by carrier surcharge and by contract, so a figure compiled in is wrong for every destination but one **and** stale the day the vendor's table moves. It is [`resolveOtpSmsPriceCents`](../../apps/api/src/otp-delivery.ts) at [`otp-delivery.ts:315`](../../apps/api/src/otp-delivery.ts), and it is total over what a deployment can put in the variable.

**WHEN IT IS ABSENT, THE BRANCH REFUSES. IT IS NEVER A ZERO.** This is ADR-226's ruling arriving on the money half: *"a secret absent from one environment must not be the way the control switches itself off in another"*. A default of zero would be a **cost breaker that counts every send as free and therefore never trips**, which is a fail-open control reporting green.

**THE VALUE IS INTEGER CENTS AND A DECIMAL POINT IS REFUSED RATHER THAN ROUNDED.** [`0029:412`](../../packages/db/migrations/0029_phone_identity_and_auth.sql) declares `spend_cents bigint`, and the constitution puts money in integer cents with no floats on a financial path. A real per-message price is a fraction of a cent, so **something must round, and the ruling is that it is not a parser**:

- **Truncating is catastrophic and silent.** `Number('0.79')` succeeds; taking it to `0` disarms the breaker while every gate stays green.
- **Rounding is a decision about money.** It belongs to whoever sets the variable, once, visibly, in the variable, rather than to a line of code nobody reads.
- **AND THE DIRECTION IS UP.** Over-stating trips the breaker early and `otp_send_budget` **degrades rather than stopping** (`0029` header item 2), so an early trip defers a verification to the `pre_funded` gate. Under-stating pays an unbounded bill. **The bounded failure is the one to choose and the schema is what makes it bounded.**

`resolveOtpSmsPriceCents` therefore refuses `0.79`, `.5`, `1.0`, `1e2`, `0x10`, `-1`, `0` and anything past `Number.MAX_SAFE_INTEGER`, and admits whole digits with surrounding whitespace trimmed. Each of those is a case in [`otp-delivery.test.ts`](../../apps/api/test/otp-delivery.test.ts).

### 4. Fail closed, and the failure modes that are told apart for the operator alone

Four outcomes; **`sent` is the only one that admits.**

| Outcome | What it means | What the caller gets |
|---|---|---|
| `sent` | the vendor took the message, and its own reference is in the log | `202` |
| `rejected` | the vendor read the message and would not take it | **503** |
| `unconfigured` | no token, no sender address, or no sender for that channel | **503** |
| `unavailable` | the call did not complete, or came back unreadable | **503** |

**ALL THREE REFUSALS ARRIVE AS ONE STATUS, AND THAT IS THE ONE PLACE THIS DIFFERS FROM ADR-226.** Turnstile's `failed` is a `403` because the caller holds the token and can solve the challenge again. A **rejected destination** is different: API_CONTRACT [`:93`](../architecture/API_CONTRACT.md) says `POST /auth/otp` *"deliberately does not reveal whether the destination exists"*, and an answer that differed for a refused address would disclose through the status what the body withholds. **What the split buys is a log line an operator can act on**, and [`deliveryRefused`](../../apps/api/src/auth-backend.ts) at [`auth-backend.ts:992`](../../apps/api/src/auth-backend.ts) is where the three become one status with three different reasons.

**THE REFUSAL TYPE IS DERIVED AND NOT RESTATED.** `type OtpDeliveryRefusal = Exclude<OtpDeliveryOutcome, { readonly outcome: 'sent' }>` at [`auth-backend.ts:989`](../../apps/api/src/auth-backend.ts), read by a `switch` with no `default`. **`strict` plus `noImplicitReturns` turn a fifth outcome member into a `tsc` error rather than into a case this file silently treats as one of the others**, which is exactly what ADR-226 built one file over and is the reason it is copied rather than re-invented.

**AN ABSENT CREDENTIAL IS A REFUSAL AND NEVER A PRETEND SEND.** The answer that is available and is refused is *"no token, no mail, answer 202 anyway"*, which is the sentence `NO_DELIVERY` existed to keep this file from writing: **a handler that answers `sent: true` having sent nothing is a worse answer than 503**, because a trader waits for a code that is not coming and every gate stays green.

**THE DEADLINE IS 5s AND THERE IS NO RETRY.** `TURNSTILE_TIMEOUT_MS` is `3_000` at [`turnstile.ts:135`](../../apps/api/src/turnstile.ts) for an anycast edge answering a form post; this is a regional API accepting a message into a queue, so it gets more room. **No retry is a stronger rule here than it was there**: a repeated verification costs a packet, where a repeated send is a second billed message and a second copy of a live code in somebody's inbox, and **a request that timed out may well have been accepted**. That refusal can therefore under-report a delivery, and the cost is accepted rather than hidden: a trader may read a 503 while the code arrives. They ask for another, which is an inconvenience; the failure in the other direction is the one this entry exists to remove.

### 5. `requestOtp`, and not one number in it is this file's choice

The order refuses before anything costs: **channel, then key, then velocity and the row in one firm transaction, then the send.**

**THE KEY IS RESOLVED BEFORE A ROW IS WRITTEN.** A challenge whose `code_hash` was taken under no admitted key is a challenge nothing can ever verify, so `resolveOtpMacKeys` refusing has to land ahead of the write. **And the CURRENT key issues while the retiring one only verifies**: issuing under a retiring key would extend its life by a full TTL past the rotation that retired it. Both are cases in [`auth-backend.test.ts`](../../apps/api/test/auth-backend.test.ts).

**THE THREE NUMBERS ARE TRANSCRIBED WITH THEIR CITATIONS, ON `OTP_MAX_ATTEMPTS`' PRECEDENT IN THE SAME FILE.**

| Constant | Value | Where it comes from |
|---|---|---|
| `OTP_CODE_DIGITS` | 6 | `otpCodeDigest`'s own docblock prices HMAC-SHA-256 against *"a six-digit code is 10^6 candidates"*, and [ADR-197](ADR-197.md) section 3 rules the construction on that arithmetic |
| `OTP_TTL_MINUTES` | 10 | [`0002:313`](../../packages/db/migrations/0002_identity.sql), `expires_at ... -- short TTL, 10 minutes`, which the rotation story already leans on |
| `OTP_EMAIL_SENDS_PER_WINDOW` | 5 per hour | [API_CONTRACT `:1462`](../architecture/API_CONTRACT.md), *"5/hour/IP, 5/hour/email"*, second half |

**THE VELOCITY IS COUNTED OFF `otp_challenges` AND THE SCHEMA SAYS SO RATHER THAN THIS ENTRY DECIDING IT.** [`0029:539`](../../packages/db/migrations/0029_phone_identity_and_auth.sql) calls `otp_challenges_destination_created_idx` *"the per-number velocity read, which is what `otp_send_budget`'s 'phone' scope is counted from"*, and declares it **the SMS sibling of** `otp_challenges_email_created_idx (email_normalized, created_at DESC)` from [`0002:325`](../../packages/db/migrations/0002_identity.sql). **The index for this exact read exists and was built for it.** Every row in the window counts, consumed and expired alike: this is a budget on **sending**, and a code that was used is still a code that was sent.

**THE PER-IP HALF IS DELIBERATELY NOT ENFORCED HERE AND THAT IS THE LANDMINE THIS SLICE ALMOST WALKED INTO.** [`server.ts:170`](../../apps/api/src/server.ts) builds the instance as `Fastify({ logger: options.logger ?? false })` and configures no `trustProxy`, so `request.ip` is the **immediate peer**. Behind Cloudflare that is one edge address for every trader at once, and *five per hour counted on it is five per hour for the whole product*. [INFRA `:27`](../architecture/INFRA.md) puts rate limiting at the edge, which is the one place the address is the trader's. **This is ADR-226's `remoteip` refusal arriving as a counter instead of as a field**, and it would have passed every test in this repository while locking out production.

**THE ROW IS WRITTEN BEFORE THE SEND.** The two orders fail differently and only one fails safe. Sending first risks a delivered code with no row to answer it, which is a person holding a valid-looking code that can never verify. Writing first risks at worst a row nobody was sent, which expires in ten minutes and costs one of that address's own velocity slots. **[ADR-126](ADR-126.md) priced this same trade one method over and took the same side**: *"paid in an inconvenience rather than in a row"*.

**`Retry-After` IS DERIVED FROM THE OLDEST ROW IN THE WINDOW**, because that is when a slot actually frees. `routes/auth.ts` says the same of the SMS branch: *"the number is the budget row's, never this file's"*. Whole seconds, rounded up, floored at one.

**THE COUNT AND THE INSERT ARE NOT ATOMIC ACROSS CONCURRENT REQUESTS, AND THE OVERSHOOT IS STATED RATHER THAN IMPLIED.** Two requests for one address that read the same count both insert, so the limit is a budget that converges rather than a barrier that cannot be crossed; the overshoot is bounded by the number of requests in flight at once for a single address. **`0029`'s own header routes the burst arm elsewhere**: *"Sub-minute velocity belongs at the edge, where it can refuse a send before one is paid for"* ([`0029:382`](../../packages/db/migrations/0029_phone_identity_and_auth.sql)).

**THE SENDER'S DEFAULT IS THE REAL VENDOR AND NOT AN UNWIRED SENTINEL**, at [`auth-backend.ts:1055`](../../apps/api/src/auth-backend.ts). That is `routes/auth.ts`'s ruling on the Turnstile verifier applied to the other outbound call on this route: **a capability that is live only when a wiring slice remembers it is a defect one layer out**, and `start.ts` is outside this fence. It still fails closed with no token, so there is no configuration in which the default sends nothing and says otherwise.

### 8. What a green suite does not prove

**NOTHING HERE HAS EVER SENT A MESSAGE.** Every case injects a `fetch` or a fake sender, deliberately: **a suite that could reach a vendor is a suite that can spend money.** What is exercised is this file's request shape, its deadline, and its total reading of an answer it does not control. **What is not exercised is the vendor's actual behaviour**, and the first real send will be the first time anything in this repository learns whether the account, the domain signature and the sender address agree.

**NO DEPLOYMENT IN THIS REPOSITORY HOLDS THE TOKEN**, so a deployment today answers 503 on `POST /auth/otp`. That is the control working rather than the gap surviving, and it is also why **an end-to-end sign-in has not been observed by anybody.**

**AND THE ROUND TRIP IS PROVED WHERE IT CAN BE.** The strongest case in this slice takes the digest written into `otp_challenges.code_hash` and checks it against the code handed to the sender, through `otpCodeMatches` itself. A suite asserting *"a row was written"* and *"a message was sent"* separately would pass over a handler that stored one code and sent another, and that is the defect a person would meet as *"the code you sent me does not work"*.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS THE VENDOR, BECAUSE IT IS THE ONLY DECISION HERE THAT COSTS MONEY OUTSIDE THIS REPOSITORY.** Section 2 takes Postmark over Amazon SES on the ground that SES is a dependency admission and Postmark is one `fetch`. **The counter-position is real**: a founder already inside AWS pays one bill, gets one identity system, and may hold an account today. **If that is the case, say so and the adapter is a second file on the same port** -- the whole point of `OtpSender` being a port is that the vendor is one object, and `requestOtp` never learns which one it holds. **What must not happen is both**, because two senders is two reputations and two things to rotate.

  **THE SECOND IS THE PER-SEND PRICE, AND IT IS A QUESTION ABOUT SMS RATHER THAN ABOUT CODE.** Section 3 rules that the value is integer cents, rounded UP by whoever sets it, and that its absence refuses. **What this entry cannot know is what Merit will actually be charged**, because that is a contract with a vendor nobody has signed. **The two-minute version of this decision is: when an SMS vendor is taken, read their table for the destinations Merit actually sells to, round up to whole cents, and set the variable.** A price that is right for the United States and wrong for the countries the ladder sells into is the failure mode, and `scope_kind = 'country'` exists in `otp_send_budget` precisely because the founder's own schema anticipated it.

  **THE THIRD IS THE FIVE-PER-HOUR-PER-ADDRESS LIMIT, WHICH IS THE ONE NUMBER HERE A REAL TRADER WILL MEET.** It is API_CONTRACT's own prose and this entry transcribed rather than chose it, but **prose written before anybody had sent an email is not the same thing as a limit somebody has watched work.** Five codes an hour is generous against an attacker and thin against a person whose first two went to spam. **If it is wrong it is wrong in the direction of locking out the very first traders**, who are the ones with no deliverability history, and the repair is one constant and one citation.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **Section 5's per-IP argument rests on `trustProxy` being unconfigured today.** If a later session configures it for a rate limiter or for logging, `request.ip` becomes the client address, the reason for leaving the per-IP half at the edge evaporates, **and nothing in the suite will notice** -- because the tests assert the behaviour and not the reason for it. That is ADR-226's own named weakness arriving on a second control, which is itself worth a founder's attention: **two entries one wave apart both rest on one unconfigured Fastify option.**

  **AND ONE OBJECTION WORTH TWO MINUTES, because it is the strongest thing on the other side.** A reader could say this entry took a vendor decision the founder should have taken, on criteria a founder holds better information about. **The honest answer is that the row instructed exactly this** -- *"pick one and wire it behind config, so only a key is owed later"* -- **and that the port is what makes the decision cheap to reverse.** Replacing Postmark with SES is one file implementing `OtpSender` and one default changed; nothing in `auth-backend.ts`, in `routes/auth.ts` or in the schema knows which vendor it holds. **The expensive half was never the vendor. It was that nothing at all delivered a code, and that half does not have to be paid twice.**
