## ADR-304: a commission is not the firm's, and it is not a seventh scope class away either. `affiliate_commissions` is ONE COLUMN away, the column is the one the other three tables on this rail already carry, and `0078` is RESERVED AND NOT WRITTEN (2026-08-30, status: proposed)

**[ADR-253](ADR-253.md) ruled that this table is not one registration away but a SEVENTH SCOPE CLASS away, stated the argument FOR that class in its section 6, and left the question open on the ground that a class is a slice with a row of its own. Row `304` is that row. THE ANSWER IS NO. The vocabulary is not what is missing. What is missing is `affiliate_id uuid NOT NULL REFERENCES affiliates(id)`, which `affiliate_creatives`, `affiliate_clicks` and `affiliate_statements` each declare, on which all three are registered `derived` via `affiliates` WITH NO RULING AT ALL, and which `affiliate_commissions` is the only table on this rail to lack.**

**`firm` IS REFUSED AND IT WAS NAMED BEFORE IT WAS MET.** The row named it as the trap; [ADR-253](ADR-253.md) section 2 clause 7 named it before that. It is refused here for the reason both give and it is not re-argued: a commission is what Merit OWES a named affiliate, `firmDb()` takes no reason on [ADR-102](ADR-102.md) clause 5's ground that no identity is at risk, and here one is. **Nothing below reaches for it and nothing below needs it.**

**AND THE SEVENTH CLASS IS REFUSED ON GROUNDS THAT ARE NOT `firm`'s.** It would key an affiliate's money to `attributions.affiliate_identity_id`, which [`0012`](../../packages/db/migrations/0012_disputes_and_affiliate_settlement.sql) declares a SNAPSHOT AT THE MOMENT OF PURCHASE in its own comment, *"because ... an affiliate can be reassigned or an identity merged afterwards"* -- while the rail that PAYS the commission keys on the affiliate row as it stands now. **The class and the payment agree until exactly the two events the column was frozen for, and then they disagree**, which is a wrong tenancy answer behind a door that RETURNS ROWS. Section 3.

**AND IT WOULD NOT HAVE UNBLOCKED WHAT IT WAS PROPOSED TO UNBLOCK.** `GET /affiliate/stats` has TWO obstructions and every entry in this tree names one. `conversions_30d` is a count of attributed sales, the only relation recording one is `attributions`, and `attributions` is `pair`: excluded from `ScopedTableKey`, excluded from `FirmTableKey`, and `scopePredicate` throws on it. **No seventh class fixes that and no eighth would either**, because ADR-106's exclusion is a ruling about what a ROW read returns and a count returns no row. Section 5.

**NO MIGRATION IS WRITTEN AND NO FILE `0078_*.sql` EXISTS.** The number is RESERVED in [ALLOCATION](ALLOCATION.md) with the three things its writing row owes, and it returns to the pool unspent if it is never taken, which is `0062`'s and `0074`'s move. **`0077` is [ADR-297](ADR-297.md)'s and was not touched.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `304`, session **493**, branch `claude/a-commission-is-not-the-firms`. **[ADR-253](ADR-253.md) section 6's open question, and `useAffiliateDeps`' third and last obstruction.**

- **MONEY PATH BY SUBJECT AND NOT BY DIFF.** `affiliate_commissions.amount_cents` is `bigint NOT NULL CHECK (amount_cents <> 0)` and is SIGNED, and a wrong tenancy rule on it shows one affiliate what another is owed. **No executable money line lands here**: no migration, no DDL, no `schema.ts` declaration, no registration, no ledger account, no arithmetic over cents, and no float anywhere. What changes under `apps/api/src` is the text of one refusal, which continues to refuse, and what changes in `packages/db/src` is one paragraph of a header comment that has been stale since the ruling it says is owed was made.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That `affiliate_creatives`, `affiliate_clicks` and `affiliate_statements` each declare exactly one `affiliate_id uuid NOT NULL REFERENCES affiliates(id)` while `affiliate_commissions` declares none, that `attributions` declares BOTH `affiliate_id` and `affiliate_identity_id` and both are `NOT NULL`, that `affiliate_commissions.attribution_id` is the ONLY foreign key in the whole migration set whose parent is registered `pair`, that `affiliates` carries four of `AffiliateStats`' nine fields and no conversion counter, that `purchases.affiliate_id` is NULLABLE on a table registered `owned` on the BUYER, and that no file in any `src/` tree in this repository names this table outside a comment, is **MEASURED**, by executing it. That `conversions_30d` can only be counted over `attributions` is **DERIVED**, from the migration set's relations and from `attributions_affiliate_idx`'s own shape. What is **JUDGED** is that a commission belongs to the affiliate row as it stands rather than to the identity frozen into the attribution (section 3), and that a permanent vocabulary member is the wrong price for a defect one column repairs (section 4).

- **A DISPATCH PROMPT IS NOT A SOURCE, AND NEITHER IS AN ADR.** Every citation row `304` carried was re-derived, including the ones it flagged as already verified. **All of them hold.** Two claims that came through [ADR-253](ADR-253.md) and through the module header are wider than the tree supports and section 9 carries both.

### 1. The question, exactly, and what it is not

**ADR-253 SECTION 6 LEFT ONE QUESTION AND IT IS THE WHOLE OF THIS ROW.** Its words: the seventh class *"would be a rule that derives through a `pair` parent and NAMES which of the two columns the child belongs to"*, the argument for it *"is real and is recorded rather than buried"*, and it is not taken there **for two reasons neither of which is that the argument fails** -- the fence, and the precedent that a class is a slice.

**SO THIS ENTRY MAY NOT ANSWER BY REPEATING EITHER REASON.** A row dispatched to rule on a class cannot rule that a class is a slice; that is the thing it was given a slice to do. What it can do is meet the argument, and the argument does fail, on three grounds ADR-253 did not have in front of it.

**WHAT THIS ENTRY IS NOT.** It is not a registration: `packages/db/src/scope.ts`'s `SCOPE_RULES` and `TABLES` are not edited and `packages/db/src/schema.ts` declares nothing new. It is not a migration: no `0078_*.sql` exists. It is not a wiring: `useAffiliateDeps` still holds `productionAffiliateDeps` and **the wired count does not move**.

### 3. The seventh class, met rather than deferred, and REFUSED

**THE CLASS ADR-253 SKETCHED, WRITTEN OUT SO IT IS REFUSED RATHER THAN PARAPHRASED.** A rule naming a `pair` via table, the local column addressing it, and WHICH of the parent's two identity columns the child belongs to. On this table: `via: 'attributions'`, `localColumn: 'attribution_id'`, `leg: 'affiliate_identity_id'`. The predicate is an `EXISTS` over the parent matching the id and the leg, it terminates immediately because the leg IS an identity column, and it discloses no buyer: a commission row carries no identity column at all, so ADR-106's ground -- that a returned row hands the reader the other party's uuid out of a `NOT NULL` column -- is ABSENT here rather than outweighed, exactly as ADR-253 says.

**THAT MUCH OF ADR-253 SECTION 6 IS CORRECT AND IS NOT DISPUTED.** The class would work. It is refused because of what it would be TRUE OF.

#### 3.1 It keys money to a column the DDL declares to be a historical snapshot

**`attributions` CARRIES TWO ROUTES TO THE AFFILIATE AND THEY ARE NOT THE SAME ROUTE.** [`0012:79`](../../packages/db/migrations/0012_disputes_and_affiliate_settlement.sql) is `affiliate_id uuid NOT NULL REFERENCES affiliates(id) ON DELETE RESTRICT` and [`0012:100`](../../packages/db/migrations/0012_disputes_and_affiliate_settlement.sql) is `affiliate_identity_id uuid NOT NULL REFERENCES identities(id) ON DELETE RESTRICT`. **The migration says in its own comment which of the two is a fact of record and why:**

> *"Both identities are stored rather than joined, because the check is a statement about the two of them AT THE MOMENT OF PURCHASE, and an affiliate can be reassigned or an identity merged afterwards."*

**SO `affiliate_identity_id` IS DELIBERATELY FROZEN, AND THE SEVENTH CLASS WOULD MAKE A FROZEN COLUMN THE TENANCY OF LIVE MONEY.** Every other relation on the settlement rail keys on the affiliate row as it stands: `affiliate_statements` is `derived` via `affiliates`, `affiliates.balance_cents bigint NOT NULL` carries the running debt including clawbacks and is `owned`, and `affiliate_commissions.paid_in_statement_id` points AT the statement, so the row that pays a commission already answers "whose money is this" with the current owner.

**THE TWO ANSWERS AGREE UNTIL EXACTLY THE TWO EVENTS `0012` FROZE THE COLUMN FOR, AND THEN THEY DISAGREE IN BOTH DIRECTIONS.** After a reassignment or a hard merge, the identity named on the attribution reads commission rows they are not paid, and the identity holding the affiliate row is paid a statement whose line items they cannot read. **That is not a smaller version of the `firm` mistake, it is the same shape**: a wrong tenancy answer behind a door that RETURNS ROWS rather than behind one that refuses, which is ADR-253's own test for what makes an available class a lie.

**AND A CLASS NAMING A LEG MUST NAME WHICH, WHICH IS A SECOND HAZARD ON THE SAME LINE.** `buyer_identity_id` is the other leg, is equally available, compiles equally well, and would return every commission Merit owes to the BUYER whose purchase earned it. There is no mechanical check that could tell the two apart: both are `uuid NOT NULL REFERENCES identities(id)` on the same row, and the enumeration in `affiliate-commissions-unregistrable.test.ts` asserts precisely that they are a pair. **A vocabulary member whose correctness rests entirely on a string literal being the right one of two is a member this registry's opening paragraph exists to refuse.**

#### 3.2 The class would be true of exactly one row in the migration set, and the DDL is why

**MEASURED, OVER EVERY `CREATE TABLE` IN THE SET: `affiliate_commissions.attribution_id` IS THE ONLY FOREIGN KEY IN THIS SCHEMA WHOSE PARENT IS A RELATION REGISTERED `pair`.** Nothing references `identity_links`, nothing references `dedupe_matches`, nothing references `identity_merges`, and `attributions` has exactly one child. The case asserts this by name, so a second child arrives in a diff and re-opens the question rather than being absorbed by a class already written.

**SINGLE MEMBERSHIP IS NOT ITSELF A REFUSAL AND THIS ENTRY DOES NOT PRETEND OTHERWISE.** [ADR-191](ADR-191.md) added `either` for `events` and `events` is still its only member. **What separates the two cases is whether DDL could have answered instead.** `events` carries `identity_id uuid NULL` beside `account_id uuid NULL` with no CHECK tying them, and that nullability IS the table: one row is identity-level, the next is account-level, a third is neither, and no column that could be added makes those one shape. **A class was the only expression available.** Here a column that three sibling tables already carry expresses it in a vocabulary that already exists, which is the difference between a missing member and a missing column.

#### 3.3 It does not unblock the endpoint it was proposed to unblock

Section 5. `stats` waits on `conversions_30d` as well, that number is a count over a `pair` relation, and no member of a scope vocabulary can make a `pair` row scoped-readable without overturning ADR-106 itself.

### 4. The ruling: it is a COLUMN away, and `0078` is reserved for it

**THE THREE OTHER TABLES ON THIS RAIL ARE REGISTERED, ARE REGISTERED IDENTICALLY, AND WERE REGISTERED WITHOUT A RULING BETWEEN THEM.**

| Relation | Column, as the DDL declares it | Rule |
|---|---|---|
| `affiliate_creatives` ([`0005:106`](../../packages/db/migrations/0005_affiliate_program.sql)) | `affiliate_id uuid NOT NULL REFERENCES affiliates(id) ON DELETE RESTRICT` | `derived` via `affiliates`, `hop` |
| `affiliate_clicks` ([`0005:158`](../../packages/db/migrations/0005_affiliate_program.sql)) | the same declaration | `derived` via `affiliates`, `hop` |
| `affiliate_statements` ([`0012:136`](../../packages/db/migrations/0012_disputes_and_affiliate_settlement.sql)) | the same declaration | `derived` via `affiliates`, `hop` |
| **`affiliate_commissions`** ([`0012:159`](../../packages/db/migrations/0012_disputes_and_affiliate_settlement.sql)) | **none** | **unregistrable** |

`affiliate_statements`' own `why` says what that shape costs to register, in the registry's own words: *"THIS IS THE THIRD TABLE ON EXACTLY THE SHAPE `affiliate_creatives` AND `affiliate_clicks` WERE REGISTERED ON, and it is registered without a ruling for that reason."* **The fourth table on this rail is unregistrable, and the only structural difference between it and the three is one column.** The scope question here is a property of the column set and not of the vocabulary, so the honest repair is the column.

**A COMMISSION BELONGS TO THE AFFILIATE ROW, AND THAT IS THE JUDGEMENT THIS ENTRY MAKES RATHER THAN MEASURES.** It is what the statement that pays it belongs to, it is what the balance that carries the clawback belongs to, and it is what `affiliates.commission_bp` -- the rate the amount was computed at -- belongs to. **A commission is money Merit owes an affiliate, and `affiliates` is the row that says who that is today.**

#### What `0078` owes, so it is not written thin

**1. THE COLUMN.** `affiliate_id uuid NOT NULL REFERENCES affiliates(id) ON DELETE RESTRICT`, which is the three siblings' declaration character for character.

**2. THE AGREEMENT CONSTRAINT, AND IT IS NOT OPTIONAL.** A denormalized tenancy column that can disagree with its parent is a commission paid to the wrong affiliate, and the objection that a derivation cannot drift is the seventh class's strongest remaining argument. **It is closable by the database rather than by care**: a `UNIQUE (id, affiliate_id)` on `attributions` -- redundant for uniqueness against the primary key, and existing precisely so a composite edge can name it -- and then `FOREIGN KEY (attribution_id, affiliate_id) REFERENCES attributions (id, affiliate_id)` on `affiliate_commissions`. **The idiom is already in this estate**: `reserve_coverage_snapshots_anchor_fk` is a composite foreign key in [`0049`](../../packages/db/migrations/0049_reserve_coverage_snapshots.sql). Under it, a commission whose affiliate disagrees with its attribution's affiliate cannot be inserted at all.

**3. NO BACKFILL, NO DEFAULT, AND THE MEASUREMENT THAT MAKES THAT SAFE.** **Nothing in this repository writes an `affiliate_commissions` row.** Measured over every `.ts` file under `apps/*/src` and `packages/*/src` with comments stripped: the table's name occurs in comments and in refusal strings and nowhere else, and [`packages/affiliate/src/attribution.ts`](../../packages/affiliate/src/attribution.ts) says so itself, that P3 *"writes the attribution and no commission"* and the commission clock is P5's and unbuilt. So a `NOT NULL` column with **no `DEFAULT`** is addable to an empty table with no data migration, and a default here would be a wrong affiliate waiting for the first writer that forgets the column.

**4. THE READ SHAPE.** The three figures `stats` needs are per-affiliate sums partitioned by `status`, so `(affiliate_id, status)` is the index the reading row will want. `0012` already declares four indexes on this table and none of them is keyed on an affiliate, because until this column exists there is nothing to key on.

**5. AND THE REGISTRATION IS THE SAME COMMIT'S OR THE NEXT ROW'S, NEVER EARLIER.** The `schema.ts` declaration and the `derived` rule name a column, and the suite reads the DDL rather than the transcription, so a registration landing before `0078` names a column that does not exist. **The order is: migration, then declaration, then rule.** Whether that is one row or two is the dispatcher's, and this entry states only that it cannot be inverted.

**WHAT THE REGISTRATION THEN COSTS IS NOTHING, WHICH IS THE POINT.** `derived` via `affiliates` on `affiliate_id`, `traversal: 'hop'` because `affiliates.id` is that table's primary key and the reference is single-valued, terminating one hop out at an `owned` rule with `nullable: false`. No new class, no change to `scopePredicate`, no change to `ScopedTableKey`, no change to any totality assertion, and no judgement that the three siblings did not already carry.

#### The condition that survives the ruling, stated here because it is where the next session will look

**ADR-253 SECTION 6'S STANDING CONDITION ATTACHES TO ROW-LEVEL READABILITY BY ANY ROUTE, NOT TO THE CLASS, AND THIS RULING DOES NOT DISCHARGE IT.** Its words: an affiliate who can read commission rows *"learns HOW MANY attributions they have and can address each one, and if any door ever resolves an `attributions` row from its id for a party, the uuid stops being opaque and ADR-106's ground returns one hop out."* **A `derived` rule returns the same rows the seventh class would have, carrying the same `attribution_id`.** The condition therefore holds against `0078` exactly as it held against the class, and it holds today: the one door in this estate that resolves anything about an attribution is `attributionAffiliate`, which takes an `affiliateId` and returns one bit ([ADR-262](ADR-262.md)), and nothing anywhere resolves an `attributions` row from its id for a party. **The registering row inherits that condition and should say so in its own `why`.**

### 5. The finding row `304` did not carry: `stats` has TWO obstructions and every entry in this tree names one

**`AffiliateStats` IS NINE FIELDS AND THEY DO NOT HAVE ONE SOURCE.** [API_CONTRACT section 7](../architecture/API_CONTRACT.md):

| Field | Source | Reachable today |
|---|---|---|
| `code`, `commission_bp`, `status`, `chargeback_rate_bp` | `affiliates`, all four declared columns of [`0005`](../../packages/db/migrations/0005_affiliate_program.sql) | **YES.** `owned` on `identity_id` |
| `clicks_30d` | a count over `affiliate_clicks`, whose `affiliate_clicks_affiliate_time_idx (affiliate_id, clicked_at DESC)` is that count's own shape | **YES.** `derived` via `affiliates` |
| `earned_cents_lifetime`, `payable_cents`, `paid_cents_lifetime` | sums over `affiliate_commissions` | **NO.** This entry's subject, and `0078` |
| `conversions_30d` | a count of attributed sales, and the only relation recording one is `attributions` | **NO, AND NOT FOR THIS ENTRY'S REASON** |

**THE SECOND OBSTRUCTION IS `attributions` AND IT IS A `pair` TABLE.** It is excluded from `ScopedTableKey`, excluded from `FirmTableKey`, and `scopePredicate` throws on it by name. `attributions_affiliate_idx (affiliate_id, created_at DESC)` is exactly the shape of "this affiliate's conversions in the last 30 days", which is the DDL agreeing that this is where the number lives.

**THE ALTERNATIVE SOURCE WAS MEASURED AND IT IS ON THE WRONG SIDE OF THE TENANCY.** [`0006:122`](../../packages/db/migrations/0006_commerce.sql) declares `purchases.affiliate_id uuid NULL REFERENCES affiliates(id)`, so a second relation does record which affiliate was on a sale. `purchases` is registered `owned` on `identity_id`, and that identity is **the BUYER's**. An affiliate's scoped read of `purchases` returns the affiliate's own purchases and never their referrals', so the column counts the wrong population through the only door that table has. It is also NULLABLE, which is [ADR-101](ADR-101.md) clause 2's refusal on top.

**AND NO SCOPE CLASS FIXES IT, WHICH IS WHY THIS BELONGS IN THIS ENTRY RATHER THAN IN A LATER ONE.** ADR-106 excludes `pair` because a returned ROW hands a reader the other party's identity uuid out of a `NOT NULL` column. **A count returns no row.** So the construction that serves `conversions_30d` is the one this estate already has twice and already wrote the argument for: a NAMED DOOR that computes inside the caller's own transaction and hands back one scalar. `attributionAffiliate` reads an `owned` row unscoped and returns a bit ([ADR-262](ADR-262.md)); `ScopedTx.effectiveAccountCap()` reads a `firm` row unscoped and returns an integer ([ADR-265](ADR-265.md)), whose own words are that *"the narrowing lives in the RESULT rather than in the predicate, and no key changed key sets"*.

**THAT DOOR NEEDS NO REGISTRY CHANGE AT ALL AND NO DDL.** `attributions` is already a `TableKey`. **`conversions_30d` is therefore the cheapest of the three pieces of work `stats` is waiting on, and it is the one no entry in this tree had identified as work.**

**IT IS DELIBERATELY NOT BUILT HERE.** [ADR-003](ADR-003.md) strict is one objective per money-path session and the objective is the class question; a door is a slice, on [ADR-191](ADR-191.md)'s and ADR-253's own rule about what a session may take as a side effect of the thing it was sent to rule. It is named, sized and owed a row.

### 7. The control

[`packages/db/test/affiliate-commissions-is-a-column-away.test.ts`](../../packages/db/test/affiliate-commissions-is-a-column-away.test.ts), and it is a sibling of ADR-253's enumeration rather than a replacement for it: **that file asserts the six refusals and this one asserts the measurements the ruling on top of them rests on.** Both read the migrations, for the reason ADR-253 gives -- the subject is a table `schema.ts` does not contain, so there is no transcription to compare against.

> **THE RAIL'S SHAPE**, asserted in one case in both directions: the three siblings each declare exactly one `affiliate_id` edge to `affiliates`, NOT NULL, and each is registered `derived` via `affiliates` on it; `affiliate_commissions` declares no column referencing `affiliates` at all. **This is the whole ground of section 4 and it goes red the moment either half moves**, including on the day `0078` lands, which is correct: the entry that lands it is the entry that repoints this case.
>
> **THE TWO ROUTES ON THE PARENT**, asserted by name and by nullability, plus `0012`'s own sentence about reassignment and merge read out of the migration text rather than paraphrased. Section 3.1 is an argument about which of two columns is a fact of record, and the migration is the only thing entitled to settle that.
>
> **THE ONLY CHILD OF A `pair` PARENT IN THE WHOLE MIGRATION SET**, enumerated over every `CREATE TABLE` and every foreign key in it, and asserted as a one-element list containing this exact column. **This is the case with teeth, and the walk is WATCHED FINDING SOMETHING rather than asserted to have them.** No migration is seeded to do it: the walk is parameterised by which relations count as the parent, the real question is asked with the registry's own `pair` predicate, and a second case asks the identical walk a question with a known answer -- treating `affiliate_statements` as the parent -- and gets back the edge that reaches it. So a second child of a real `pair` relation is FOUND rather than passed over, and the day one lands this case names it in a diff instead of a class quietly acquiring a second member.

### 8. The repair, and it is asserted over what a caller is served

**`COMMISSIONS_UNREACHABLE` IS THE SENTENCE A LATER SESSION MEETS WHEN IT ASKS WHY `stats` REFUSES, AND IT IS WRONG IN TWO PLACES.** It says the table *"is a seventh class away, and ADR-253 declines to write one to make a registration compile"* -- and this entry rules that it is not a class away. It names `affiliate_commissions` as the obstruction, and there are two. **A refusal is the one place a later session reads to find out what to build**, which is ADR-253 section 5's own ground for repairing `STATEMENTS_UNREACHABLE`, and a refusal that sends a session to write a scope class is worse than one that says nothing.

Both are repaired, in the constant and in [the module header's finding 1](../../apps/api/src/routes/affiliate.ts). **The retired sentences are kept in place saying what was ruled rather than deleted**, on `RI-14`'s rule that a false sentence removed leaves nothing for the next reader to check.

**THE ASSERTION IS OVER WHAT A CALLER IS SERVED AND NOT OVER THE FILE**, which is the same choice ADR-253 section 5 made and for the same reason: an assertion over source text would forbid a docblock that quotes what was corrected, and could be satisfied by deleting the record instead of the defect.
