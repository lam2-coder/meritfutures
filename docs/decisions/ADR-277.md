## ADR-277: the worker's guard asked the right question of the wrong table, and the repair is a refusal plus a type, because the sharper half of the defect was on the branch that looked safe  (2026-08-30, status: proposed)

**Row `277` asked whether `calendarCarriesDay`'s row-existence test and `trading_calendar_loads` coverage coincide by construction, and said in terms that a documentation defect would be a complete outcome. THEY DO NOT COINCIDE, THE WRONG-ANSWER PATH IS REAL, AND IT IS ON BOTH BRANCHES.** Nothing in the schema ties a `trading_calendar` row to a load: [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql) declares no foreign key between the two tables, and [`0048:186`](../../packages/db/migrations/0048_audited_writes_on_append_only_tables.sql) rules in terms that CALENDAR-C3's retroactivity test is the FOLD EXTENT and explicitly **NOT** the coverage window, so a calendar row may be inserted for a day no load ever declared.

**AND THE ROW READ THE TWO BRANCHES THE WRONG WAY ROUND, WHICH IS THIS ENTRY'S ONE CORRECTION TO IT.** The row called the explicit-day branch "the sharper half, because it looks like it checks and does not". It is the milder half. On the estate [ADR-273](ADR-273.md) finding 1 actually names, a calendar loaded through June and a job run in August, **every day the implicit fold can return is INSIDE coverage**, so a coverage test alone would have passed it. What is wrong there is that the calendar is EXHAUSTED: the fold returns the last day Merit KNOWS ABOUT and calls it the last day CLOSED, and `0032`'s header calls that "the single most silent failure available to this table". The repair therefore needed a fact the row did not name, and it is the one the payout door already proves.

- **MONEY PATH. This is the path that WRITES `rule_states`, which is the payout basis.** The [**`E2`**](../../MERIT_BUILD_MASTER_PROMPT.md) read is **OWED**. Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.** It inherits the `E2` debt on [ADR-268](ADR-268.md), which built the door this entry transcribes, and on [ADR-273](ADR-273.md), whose finding 1 is this entry's subject.

### 2. THE RULING

> **1. THE PREMISE IS REAL AND IT IS A WRONG-ANSWER PATH RATHER THAN A DOCUMENTATION DEFECT.** A `trading_calendar` row states that Merit knows what a day IS. A `trading_calendar_loads` interval states that somebody LOADED it. Nothing in the schema makes the first imply the second, and `0048` header item 7 rules out the only mechanism that could have: it names the coverage-window test and REFUSES it, on the grounds that loading a year writes one load row and then inserts roughly 250 days inside it. Section 3.
>
> **2. THE REPAIR IS A REFUSAL ON BOTH BRANCHES AND NEVER A DEFAULT, AND IT IS `lastClosedTradingDayStatement`'s RULE TRANSCRIBED RATHER THAN A NEW ONE.** The implicit branch proves three facts, which are that a session has closed, that a session ahead of `now()` exists, and that ONE load spans both days ([`scoped-db.ts:3105-3113`](../../packages/db/src/scoped-db.ts)). The named branch proves two, which are that the calendar carries the day and that one load covers it, and it deliberately does NOT ask the third: `RB-01` re-runs a night that failed, so the day is named precisely because it is behind.
>
> **3. WHAT HOLDS IT IS A TYPE AND NOT A HABIT, WHICH IS [ADR-273](ADR-273.md) RULING 1 APPLIED WHERE THAT ENTRY COULD NOT REACH.** Both readers return a `TradingDayAnchor` declaring `tradingDay` on the `anchored` arm ALONE ([`adapter.ts:463`](../../apps/worker/src/batch/adapter.ts)), so a caller that skips the verdict does not compile. **AND IT GOES ONE STEP FURTHER THAN `apps/api`:** the coverage-blind fold is not module-private with one caller, it is **gone from the exported surface entirely**, so there is no second caller to bound and no count to keep true.
>
> **4. THE TWO TABLES ARE READ IN ONE TRANSACTION.** `WorkerDb.batch` opens a transaction per call, and `trading_calendar` is the one table in this estate the corpus built a CORRECTION mechanism for, so two calls are two snapshots between which a row can legitimately move. A basis day chosen from a calendar the transaction that checked coverage never read is the verdict `scoped-db.ts` refuses to produce on the payout door, and this job writes its answer into `rule_states`.
>
> **5. NO DOOR WIDENED, NO KEY SET MOVED, NO MIGRATION WRITTEN, NO GATE WEAKENED.** `SystemTx.rows` already serves every `TableKey`. `packages/db/**` is untouched.
>
> **6. `RI-30` IS NOT MINTED AND THE NUMBER IS RETURNED.** Section 5.
>
> **7. TWO FILES OUTSIDE THE FENCE MOVED, BOTH ARE DEFECT REGISTERS THAT PIN THE DEFECT, AND THE DEPARTURE IS REPORTED RATHER THAN PERFORMED QUIETLY.** Section 6.

### 3. The premise, established from the schema and the loader rather than from the refusal string

**THE REFUSAL, QUOTED.** On the parent commit `resolveTradingDay` threw, for a day the calendar has no row for, that *"A day the calendar does not carry is a day outside coverage, and folding it would raise a coverage miss on every account rather than closing anything"*, and the function it called was `calendarCarriesDay`, whose whole body was `tx.rowsWhere('tradingCalendar', { tradingDay: day })` and a length test. **The sentence is about `trading_calendar_loads` and the query is about `trading_calendar`.**

**FOUR FACTS SETTLE WHETHER THAT MATTERS, AND EACH IS READ AT ITS SOURCE.**

| Asked | Read at |
| --- | --- |
| Does `trading_calendar` declare a foreign key to the loads table, or the reverse | **NEITHER.** `0032` creates both tables and the only FK between the family is `trading_calendar_revisions.trading_day` to `trading_calendar` ([`0032:194`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql)) |
| Does any trigger tie a calendar INSERT to a load | **NO, AND THE ONE THAT COULD HAVE, DOES NOT ON PURPOSE.** `0048` part 5 adds `trading_calendar_retroactive_insert_recorded`, and header item 7 states that its test is `NEW.trading_day <= the greatest trading day in fills, daily_marks and rule_states` and that the coverage test *"is not"* the right one ([`0048:186`](../../packages/db/migrations/0048_audited_writes_on_append_only_tables.sql)) |
| Which direction does the DDL commit to | **ONE ONLY.** *"A day inside these bounds with no trading_calendar row is a bug in the load. A day OUTSIDE them is unknown"* ([`0032:313`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql)). It says nothing about a calendar row outside every load, which is the direction that folds |
| Does a loader make them coincide in practice | **THERE IS NO LOADER.** [`packages/db/src/seed/calendars/README.md:18`](../../packages/db/src/seed/calendars/README.md): *"The loader is **not** here yet. It is S-E4"*. `generate.mjs` produces the source file and writes no row. So nothing at all currently constrains the pair, and a future loader that writes both would still leave the backfill path of `0048` free to insert a calendar row alone |

**SO THE ROW-EXISTENCE TEST AND THE COVERAGE TEST ARE DIFFERENT QUESTIONS, AND THE ANSWER TO THE ROW IS THAT THIS IS NOT A DOCUMENTATION DEFECT.**

**AND THE IMPLICIT BRANCH IS WORSE, WHICH IS WHERE THE ROW HAD IT BACKWARDS.** `readLastClosedTradingDay` selects a day off a `trading_calendar` row, so it can never return a day the calendar lacks; on a perfectly loaded estate its answer is always inside coverage. What breaks it is the estate [ADR-273](ADR-273.md) section 9 names: a calendar loaded through June, read in August. The fold returns `2026-06-30`, which IS covered, and calls it the last closed day. **A coverage test on the returned day alone would have passed that estate**, which is why ruling 2 takes all three of the door's facts and not just the coverage one. The distinguishing fact is fact 2, that a session ahead of `now()` exists: without it, an exhausted calendar and an unbroken holiday are the same reading, and `0032`'s header already says that is the worst thing this table can do quietly.

**WHY THE COMPARISON IS STRING ORDERING AND CONSTRUCTS NO `Date`.** A `YYYY-MM-DD` is fixed width and zero padded, so lexicographic order is chronological. ### 8. Where this entry is most likely wrong

**RULING 2 MAKES THE IMPLICIT BRANCH STRICTER THAN THE ROW ASKED FOR.** The row said the repair is a refusal on an uncovered day. Fact 2, that a session ahead of `now()` must exist, is not a coverage read, and a reviewer may hold that transcribing the whole door rather than only its coverage clause exceeded the mandate. **The defence is that the coverage clause alone does not repair the estate `ADR-273` finding 1 names**, which section 3 measures; but a reviewer who wants the smaller change should say so, and the smaller change is one deleted branch.

They prove the adapter asks for one unit of work; they prove nothing about isolation level, and `apps/worker/src/db.ts`'s own header draws that line for every case in this deployable.
