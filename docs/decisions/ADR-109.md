## ADR-109: the accessor cannot name a row, so the idempotency store is a port and the raw body is a parser  (2026-08-26, status: proposed)

**An idempotency layer's whole job is to find ONE ROW by its key and stamp THAT ROW with a response. A webhook receiver's is to claim ONE event id. Nothing in [`packages/db`](../../packages/db/src/scoped-db.ts) can name a row at any authority, and the door everybody reaches for first -- a third `SystemReason` member -- would not change that.** This entry rules that the missing construction is a PREDICATE rather than an AUTHORITY, that the unowned replay is a second TYPE rather than a nullable field, and that API_CONTRACT section 10's "verified BEFORE parsing" is a content-type parser rather than anything a handler can do.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-k` row and section 15's prompt, session **219**. **MONEY PATH**, [ADR-003](ADR-003.md) strict. The number was RESERVED before dispatch and is not this session's to choose.

- **Context:** the dispatch's own amendment predicted one hole (`idempotency_keys` is `owned` on a NULLABLE column, so a webhook with no identity has no accessor) and asked for it to be verified rather than believed. Verifying it found a wider one, and found that the remedy the same dispatch prescribed is unavailable. [Session 222](../sessions/2026-08-26-session-222.md) hit the identical wall from `apps/worker` one day earlier and reported it; this entry is the ruling that report asked for, arriving from the second caller rather than the first.

### 2. THE RULING

> **1. THE MISSING CONSTRUCTION IS A PREDICATE, NOT AN AUTHORITY.** `SystemReason` does not gain a third member. Every method on all three transaction handles narrows by tenancy or by nothing, so a caller that must name ONE ROW is refused identically at every authority, and admitting `'request-handler'` would buy a door that still writes the whole table. **Widening the reason vocabulary to solve a predicate problem is the change that looks like a fix and is not one**, and it would spend exactly the admission [ADR-096](ADR-096.md) section 5 refused, for a defect it does not touch.
>
> **2. THE ACCESSOR NEEDS A KEYED READ AND A KEYED WRITE, AND THAT IS A `packages/db` RULING WHICH IS THE FOUNDER'S.** [Session 222](../sessions/2026-08-26-session-222.md) reported it from the provisioning saga, session 219 reports it from the idempotency layer and the webhook re-drive, and the three needs are one need. **This entry does not design it**: the shape decides whether "reach the database and choose a scope are the SAME ACT" survives, and a construction that admits an arbitrary predicate at a call site is [ADR-008](ADR-008.md)'s guarantee handed back.
>
> **3. UNTIL IT LANDS, THE STORE IS A PORT AND NO IMPLEMENTATION OF IT IS WRITTEN.** [`apps/api/src/idempotency.ts`](../../apps/api/src/idempotency.ts) declares `IdempotencyStore` with three methods, **every one of which takes the scope and the key**, so an implementation must name a row and cannot be written by accident against a handle that cannot. **`apps/api` gains no `@merit/db` dependency in this session**, which keeps the absence a fact somebody can grep rather than a comment.
>
> **4. THE UNOWNED REPLAY IS A SECOND TYPE AND NOT A NULLABLE FIELD.** `IdentityScope` and `UnownedScope` are distinct and the union is discriminated. Section 4 is the argument, and it is the schema's own: `idempotency_keys_identity_idx` is PARTIAL on `identity_id IS NOT NULL`, so the database already holds two populations.
>
> **5. A RECEIVER THAT CANNOT UPDATE A ROW MUST APPLY BEFORE IT CLAIMS.** [`webhooks-psp.ts`](../../apps/api/src/routes/webhooks-psp.ts) applies the business effect, then INSERTs the row carrying the result, then ROLLS BACK if `psp_webhook_events_provider_event_uq` refused the claim. **This is not a workaround for item 3, it is better than the alternative**: insert-then-apply-then-stamp needs an `UPDATE` and leaves a window in which a crash commits a claim for an effect that never happened.
>
> **6. THE RAW BODY IS A ROUTE-SCOPED CONTENT-TYPE PARSER AND NEVER A RE-SERIALISATION.** `RouteDefinition` should gain a way to say a route is served raw, and `compose` should register those routes inside their own encapsulated context carrying the buffer parser. **Registering it on the root instance is refused**: a Fastify content-type parser is per encapsulation context, so a root registration takes JSON parsing away from every route that lands later. Until the seam exists, `rawBodyOf` REFUSES a parsed body, and the route answers 500 rather than verifying a document the provider did not sign.
>
> **7. A HANDLER MAY NEVER RECOVER THE BYTES BY RE-ENCODING `request.body`.** Two JSON texts that parse equal serialise differently, so a re-encoded body is a DIFFERENT DOCUMENT and its MAC will not verify. The failure is a `401` for every legitimate webhook, with no line of code looking wrong. **This is the one clause in this entry that is a prohibition rather than a plan**, and the suite watches a correctly signed payload being refused after a pretty-printing round trip.

### 3. Clause 1's arithmetic, because "add a reason" is what everybody tries first

The amendment that dispatched this session offered three shapes and named the first: *"either `SystemReason` admits a third member and the ADR says what makes that member legitimate rather than a hole"*. **The honest answer is that the member would be legitimate and would not work.**

| Door | Reaches `idempotency_keys`? | Can name one row? |
|---|---|---|
| `scopedDb(id)` / `scopedTx` | **Yes**, it is `owned` | **No.** Tenancy predicate only |
| `firmDb()` / `firmTx` | **No**, `FirmTableKey` excludes `owned` | **No.** No predicate at all |
| `systemDb(reason)` / `systemTx` | **Yes**, generic over `TableKey` | **No.** No predicate at all |
| `systemDb('request-handler')`, hypothetically | Yes | **No.** Identical to the row above |
| `sqlExecutor(reason)` | Yes, it is raw SQL | **Yes** -- and the vocabulary is one member and it is not this |

**Four of the five rows fail on the same column**, which is why the ruling is about that column. The fifth is the door [ADR-102](ADR-102.md) built deliberately narrow, and prying it open for a request handler is a larger admission than the one this entry declines to make: `executeSql` on an open transaction routes around every control in that file at once.

### 4. Clause 4, and why a nullable field is the shape the schema refuses

`scope.ts`'s own `why` for this table states the mechanism: *"NULLABLE IS HOW THE UNOWNED REPLAY IS EXCLUDED, and SQL does the excluding: a key replayed by an unauthenticated caller carries no identity and no correct one, so `identity_id = $1` drops it without a second predicate because NULL never equals anything."* The DDL agrees in its own index, which is partial on `identity_id IS NOT NULL`.

**So the two populations are already separate at the storage layer, and the question this entry answers is whether the LAYER should hide that.** It should not, for a reason that is checkable rather than aesthetic: a store implemented against `{ identityId?: string }` has ONE code path, and the path that is correct for an identity (`WHERE key = $1 AND identity_id = $2`) is silently wrong for the unowned row, because `identity_id = NULL` matches nothing. The bug is a row that can be written and never read, on the exact table whose purpose is to be read on the second delivery. **A discriminated union makes that a switch somebody has to complete.**

**WHAT THIS COSTS is one thing and it is stated rather than left to be discovered:** a caller that genuinely does not know whether it has an identity has to decide before it calls, and there is no `maybeScope(id?)` helper. That is the point. `POST /auth/otp` runs at required factor `none` and is unowned; `POST /checkout` requires a session and is not; **an endpoint that cannot say which it is has a bug upstream of this layer.**

### 5. Clause 6, measured rather than reasoned

API_CONTRACT section 10 states the ordering in capitals and [`packages/psp`](../../packages/psp/src/webhook.ts) makes it a module boundary: `PspAdapter.verifyWebhook` is the only function in this workspace that returns a parsed webhook body, and `apps/api` never calls `JSON.parse`. **That defends the ORDER and it does not defend the BYTES**, and the bytes are what a framework takes away.

| What was probed, against fastify 5.12.1 in `apps/api` | Result |
|---|---|
| Default `application/json` parser | `request.body` is a plain `Object`; `request.raw.readable` is `false`, so the stream is spent |
| An unregistered content type | `415 FST_ERR_CTP_INVALID_MEDIA_TYPE`, before the handler |
| `addContentTypeParser('application/json', { parseAs: 'buffer' })` | `request.body` is the exact bytes, `'{"a":1,  "b":  2}'` recovered with both spaces |
| The same parser registered AFTER the route | **Still applies.** Parsers resolve per request, not at registration |

The last row is what makes clause 6's seam small: `compose` can register a raw-served route and its parser in either order, and a wiring session does not have to reorder `buildServer`.

### 6. A landmine this entry names and does not repair

**`idempotency_keys.key` is the PRIMARY KEY and it carries no identity.** With an endpoint prefix and nothing else, identity A holding `/checkout:tok_1` blocks identity B's `/checkout:tok_1`.

**It is a DENIAL and not a DISCLOSURE**, and the difference is the scope predicate doing its job: B's scoped `find` returns nothing, so B never receives A's stored response even when the bodies are identical. What B gets is a refused insert. **`beginIdempotent` reports that as its own outcome, `key_held_elsewhere`, rather than guessing**, because this layer genuinely cannot tell a foreign holder from a row it is racing, and answering either way would be an invention. Both answer `409 conflict`.

**The repair is a migration and this session is forbidden one**, so it is reported: the primary key would have to be `(key, identity_id)` with a partial unique index for the NULL arm, or the identity would have to join the prefix. Clients generate opaque tokens, so the collision is unlikely and it is not impossible, and an unlikely cross-tenant denial on the checkout path is worth a number rather than a shrug.

### 7. What this entry does NOT rule, named rather than implied

- **The shape of the keyed accessor.** Clause 2 says it is needed and says why this session must not design it in passing.
- **Whether `apps/api` gets `@merit/db`.** It does not here. The wiring is a session with a migration-adjacent read of its own.
- **Rate limiting the refusal write.** API_CONTRACT section 11 says webhooks are *"not rate limited; protected by signature verification"*, which is true of the business path and **is not true of the `signature_verified = false` insert**: that write happens for a caller who proved nothing. [`unverifiedEventId`](../../apps/api/src/routes/webhooks-psp.ts) makes retries of ONE payload collide on the unique index, so a redelivering attacker writes one row; **a caller that varies the body still writes one row per body**, and bounding that is somebody's.
- **The re-drive of a deferred event.** `psp_webhook_events_deferred_idx` is its index and `defer_attempts` is its counter, and both belong to the batch. The receiver writes `0` and never increments, because it is the first arrival and not a re-drive.
- **Whether `CI-06/vg-inventory`'s arrival probe should distinguish a USE from a MENTION.** `VG-3` and `VG-6` wait on the artifact *"`scopedDb` named under `apps/api/src`"*, and the probe is `\bscopedDb\b` over every `.ts` file in that directory. **A comment explaining that the accessor CANNOT be used names it too**, and this session's first draft of [`idempotency.ts`](../../apps/api/src/idempotency.ts) turned the gate red on prose: `29 of 30`, both rows reported as ARRIVED, on a deployable with no session, no identity and no read. [`gates.mjs`](../../scripts/corpus/gates.mjs) and [STRATEGY](../testing/STRATEGY.md) are both outside this fence and **neither is edited**: the identifier is described rather than spelled, with the reason written at the site, and the artifact has genuinely not arrived. **The probe is a proxy and this is the shape of proxy that fails on a document rather than on a fact**, which is the same class as the `fastify-plugin` substring its own comment was hardened against, one level up.

- **What a `payment.succeeded` MEANS.** `PspEventApplier` is a port with no implementation. `POST /checkout` (session 220) writes the `purchases` row this receiver's applier will resolve against, and there is no vendor adapter for either provider: `packages/psp` ships two fakes and shipping a real one is a procurement decision nobody has taken.

### 8. Consequences

- **Session 220 inherits clause 2 with a third caller attached.** `POST /checkout` presents an `Idempotency-Key` that API_CONTRACT section 1 makes REQUIRED, and the layer it presents it to cannot store the response. [Session 216](../sessions/2026-08-25-session-216.md) already reported that a checkout handler is neither of `systemDb`'s two reasons; this adds that even the reason it is not would not help it.
- **`0048` stays free.** No migration is written and none is numbered.
- **The route is registered and answers 503.** A live public deployment serves `POST /api/v1/webhooks/psp/:provider` and reports the dependency as absent, which is section 2's `service_unavailable`. A missing route would answer 404 and read as a contract Merit never wrote.
- **Nothing in `packages/db` moves**, and `git status --porcelain packages/db` reports zero on the branch that carries this entry.
