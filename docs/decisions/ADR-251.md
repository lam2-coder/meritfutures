## ADR-251: an instant is not a trading day, the gap was narrower than the sentence, and the port that named it asked a three-armed question with one arm (2026-08-29, status: proposed)

**Row `251` sent one session at the smallest of `useAdminWriteBackend`'s three suppliers and asked one question first: is it buildable. It is. `@merit/rules-engine` now maps an instant to an exchange trading day by CONTAINMENT over `trading_calendar`'s stored session bounds and `trading_calendar_loads`' coverage, it answers UNKNOWN where the estate loaded nothing, and it never computes a day from a clock. The clause the entry carried is not narrowed, it is FALSE, and it is removed.**

**WHAT REPLACES IT IS SMALLER AND IS NOT A MISSING FUNCTION.** `AdminWriteBackend.tradingDay(): string` has one arm. The resolver answers three, because [ADR-042](ADR-042.md) F-4 requires `outside_coverage` to be distinguishable from `not_a_session`. And no ruling in this corpus says which day an operator close takes when the instant is in no session, while `accounts_terminal_has_close_date` requires `closed_on` on every `closed_admin` row. **A DECISION IS OWED AND A FUNCTION IS NOT.**

**THE PORT IS NOT WIRED AND THE WIRED COUNT DID NOT MOVE.** `useAdminWriteBackend` stays blocked on `principal(request)`, which is behind the C-08 SSO purchase, and on a `ValidationResult` projection nothing in this tree performs. The entry is narrowed from three clauses to two and every one of them is executed rather than restated.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `251`, session **441**, dispatched as `claude/an-instant-is-not-a-trading-day`. **RESERVED, REQUIRED**, and taken.

- **MONEY PATH BY CONSEQUENCE, `E2` READ OWED.** A trading day is the unit every rule in the engine is measured over. No migration number and no `RI-` number were taken, no DDL was written, and no money value is computed here. Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the resolver returns the row's day and not the instant's UTC date, that it answers three ways, that it refuses the data a containment lookup could not answer over, and that the port still throws, is **MEASURED**, by executing it, and by executing three seeded paper-overs and watching each go red. That both calendar tables are `firm`, that `apps/api` declares the engine and holds `db.firm`, and that the worker never reads `trading_calendar_loads`, is **DERIVED** at the file and line each claim names. ### 3. What was built, and the five refusals inside it

`packages/rules-engine/src/calendar.ts` gains `buildSessionCalendar` and `tradingDayAt`, plus the types they need, and `src/index.ts` gains the export lines.

**THE FENCE NAMED `calendar.ts` AND NOT `index.ts`, AND THE SECOND FILE IS DECLARED HERE RATHER THAN TAKEN QUIETLY.** `packages/rules-engine/package.json` declares `"exports": { ".": "./src/index.ts" }` and **no subpath**, so a function added to `calendar.ts` and not named in the barrel is a function no workspace caller can reach: dead code with a docblock, and a row whose whole premise is that `apps/api` should be able to reach it. **The diff to `index.ts` is export statements and a comment and nothing else.** It is recorded as a fence question rather than a fence widening because the alternative reading, that the grant covers a file no caller can import, makes the grant self-defeating; **if the founder reads it the other way, the export lines are the diff to revert and the function stays where it is.**

**AND `packages/db/src/**` WAS PERMITTED "only if a read helper is genuinely owed (declare it)". IT IS NOT OWED AND NOTHING WAS TAKEN THERE.** `FirmTx` already reads both tables through the keyed accessor and `liability.ts` performs exactly that read in this same deployable, so a helper would be a second way to do a thing this deployable already does.

#### Clause 1. It answers by CONTAINMENT, and containment is the corpus's own definition

[ADR-146](ADR-146.md) section 3's worked example is the specification: `2026-03-03T23:30:00Z` is 17:30 CT, inside the session that opened at 17:00 CT on `2026-03-03`, and **that session's trading day is `2026-03-04`**. The instant's UTC date is the other day. So the answer is the row whose `[session_open_at, session_close_at]` holds the instant, which is `R-01`'s own shape, and every comparison is instant against instant.

#### Clause 2. It consults BOTH tables, because one of them cannot say "I do not know"

Coverage is stated in DAYS and the question is asked about an INSTANT, so **deciding "is this instant inside coverage" by comparing it against `coverage_start_day` would need a date for the instant**, which is the one derivation [ADR-146](ADR-146.md) clause 1 forbids. The session bounds are already instants, so a covered interval's reach in instants is the earliest open and the latest close among the sessions it holds, and the comparison stays honest.

**THE THREE ANSWERS ARE `CalendarLookup`'s, ONE VOCABULARY OVER.** A day, `not_a_session` for an instant inside a loaded span that no session contains, and `outside_coverage` for an instant the estate loaded nothing around. Collapsing the last two is [ADR-042](ADR-042.md) F-4's silent failure: "an exhausted calendar is indistinguishable from an unbroken holiday ... and NOTHING RAISES".

#### Clause 3. It lives in `calendar.ts` and it is a SECOND VALUE, and both halves of that are judgements

The fence permitted `calendar.ts` or one new module beside it. **It is `calendar.ts`**, because the distinction the whole function turns on, `not_a_session` against `outside_coverage`, is already written there once, and splitting it would put two halves of one ruling in two files where they can drift.

**AND `CalendarDay` DOES NOT GAIN SESSION INSTANTS**, which was the available shortcut. `0032` header item 4 refused the symbol dimension because it "changes the engine's calendar contract, and makes the calendar's grain differ from the grain every counter is defined at"; instants on `CalendarDay` do the same thing from the other side. Every rule that folds over a slice counts in DAYS. **No rule folds over a `SessionCalendar` and nothing in the engine reaches one.**

#### Clause 4. Coverage FILTERS rather than refuses, and this is where it parts from `buildCalendarSlice`

`buildCalendarSlice` throws on a day outside its declared coverage. This constructor drops one instead, and the two are right for different reasons: **there the caller declares its own coverage, so a day outside it is the caller contradicting itself, while here coverage is a SECOND TABLE's fact and a calendar loaded further than its loads is an ordinary estate state.** `liability.ts` rules exactly this pair of tables: "coverage is the authority on what may be answered, so the walk stops at `coveredThroughDay` whatever rows happen to sit past it."

**IT ALSO MAKES F-4's OWN BRANCH FALL OUT RATHER THAN BE WRITTEN.** An estate with a full `trading_calendar` and no `trading_calendar_loads` row places no session at all, so every instant answers `outside_coverage`, which is `anchorCalendar`'s "an estate that has days and no record of having loaded them is entitled to answer for none of them".

#### Clause 5. Two adjacent loads leave the gap between them UNKNOWN, and that is stated rather than hidden

Loads covering `..06-30` and `07-01..` are not merged, because merging them on a date successor is the date arithmetic `R-02` forbids and `liability.ts` refuses by name. The consequence is that the overnight gap between June's last close and July's first open falls in neither span and answers `outside_coverage` where a human would say `not_a_session`.

**THIS ERRS TOWARDS THE ANSWER THAT REFUSES.** It never returns a day it cannot read off a row. The remedy is a load that overlaps by a day, which is a fact that row would state, and `liability.ts` already names overlapping as the intended practice.

#### The refusals the constructor makes

**OVERLAP IS THE LOAD-BEARING ONE.** Containment is an ANSWER only while at most one session holds an instant; two overlapping rows make one moment two trading days and a scan returns whichever it reached first, silently. `P1-SE` states the property this relies on: "The next session opens at 17:00 CT regardless, so no overlap is created and no fill is orphaned." Beside it: days strictly ascending, `close > open` on `0032`'s `trading_calendar_session_ordered`, whole millisecond bounds, and a backwards coverage interval.

**AND `trading_calendar_holiday_has_no_session` IS A TYPE RATHER THAN A CHECK.** `SessionDay` is a discriminated union on `is_holiday`, so **a holiday carrying a session cannot be spelled**. That is `0032` F-1's defect refused at the type level: `R-01` is a containment lookup, so a fabricated holiday interval is an interval a fill can fall inside, and it is an interval this function would place an instant in.

**THE INSTANT IS WHOLE EPOCH MILLISECONDS AND NEVER A `Date`.** `merit/engine-purity` bans the constructor and `no-restricted-globals` bans the bare global. A number is data the caller supplies, and `Date.parse` at the call site is `liability.ts`'s `instantMs` idiom.
