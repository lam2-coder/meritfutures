**IT IS ALSO THE FIRST TIME EITHER OF THE TWO ENTRIES WAITING ON THIS NUMBER HAS BEEN NARROWED RATHER THAN RESTATED**, and the narrowing produced the finding: the two refusals were one finding for exactly as long as neither number had a source, and they stopped being one finding here.

### 2. THE RULING

> **1. `firm_parameters` IS BUILT, IT IS REGISTERED `firm`, AND ITS VOCABULARY IS CLOSED AT THE DATABASE WITH A NAMED `CHECK`.** [`0074_firm_parameters.sql`](../../packages/db/migrations/0074_firm_parameters.sql) creates it on [`price_floors`](../architecture/data-model/price_floors.md)' shape: grain `(parameter, effective_from)`, superseded by a new row rather than updated, carrying a written reason and an approver. `firm_parameters_vocabulary_is_closed` admits exactly one member, `base_account_cap`. A second member is an ADR plus a superseding migration and never an edit, on [`0073`](../../packages/db/migrations/0073_operator_directory.sql)'s precedent for `operators.role` and [ADR-126](ADR-126.md)'s for `SystemReason`.
>
> **2. THE COLUMN TYPE IS THE SECOND CLOSURE AND IT IS THE ONE A `CHECK` CANNOT PROVIDE.** The table declares ONE value column and it is `integer`. There is no `text_value`, no `cents_value` and no `jsonb_value` beside it, so a firm parameter that is not an integer belongs in a table of its own. **A `CHECK` closes what may be NAMED; a second value column widens what may be STORED while leaving that `CHECK` untouched**, and that is the shape a settings bag actually arrives in.
>
> **3. THE CAP'S DOMAIN BELONGS TO THE PARAMETER AND NOT TO THE COLUMN.** `firm_parameters_base_account_cap_is_positive` is `parameter <> 'base_account_cap' OR integer_value > 0`, so a later member with a different domain gets its own disjunct rather than arriving by loosening the cap's bound. `identities.max_accounts_override` carries `CHECK (> 0)` and the base and the exception agree on their domain.
>
> **4. `approved_by` IS A FOREIGN KEY INTO `operators(actor)`, WHICH THIS TABLE'S OWN PRECEDENT DOES NOT CARRY.** `price_floors.approved_by` is bare `text` on `0002`'s actor idiom because no operator directory existed when `0024` was written. `0073` built one **one migration ago**, so a cap approved by a name in no directory is UNWRITABLE rather than merely undesirable. `ON UPDATE RESTRICT` and `ON DELETE RESTRICT` in both directions, on `0073`'s own ruling: an approval is a historical fact and not a pointer at whoever holds the seat today.
>
> **5. THE TABLE SHIPS EMPTY, AND AN ABSENT ROW IS NO CAP RATHER THAN AN UNLIMITED ONE.** No seed, no DDL default, no fallback, and nothing under any `src/` writes a row. A cap is a launch candidate re-confirmed at launch as a config row and never a constant, so a number written here would be a number this session invented. **THE RULED READING OF THE ABSENCE IS THE HALF THAT MATTERS**: folding an absent row into an unlimited cap, or skipping the comparison when the read returns nothing, is a control that answers yes to everybody on the endpoint that sells accounts. **The slice that writes the read owes a REFUSAL there before it owes anything else**, and this entry writes that obligation into the docblock the implementer will open rather than into a comment nobody has to pass.
>
> **6. `useCheckoutBackend`'s CAP CLAUSE IS NARROWED AND NOT DISCHARGED, AND WHAT REMAINS IS A DOOR RATHER THAN A COLUMN.** `accountCap()` is a method of `CheckoutTx`, which is a SCOPED transaction, and a scoped transaction refuses every `firm` key outside `CATALOG_TABLE_KEYS` -- five members, and this key is deliberately not one of them. **The read cannot simply move outside the transaction**, because `INV-M3-15` requires the restriction check at the same point in the transaction as the cap and `gateIdentity` performs both in one call. `refuseUncatalogued` states the admission argument in its own message and **this table satisfies it exactly**; making that argument is a diff on `packages/db` with an ADR attached, `scoped-db.ts` is outside this fence, and **this entry does not make it**.
>
> **7. THE TWO ENTRIES ARE NO LONGER ONE FINDING, AND THAT IS THIS SESSION'S FINDING.** `databaseAuthBackend` holds an `ApiDb`, `ApiDb.firm` reaches every `FirmTableKey`, and `firmParameters` is one as of this branch. **So `readMe` needs no catalogue admission at all and `accountCap()` does.** What the two still share is the empty table and nothing else. An entry that kept calling them identical would send a session to clear one and find the other standing, which is the failure mode `useCheckoutBackend`'s own block has recorded twice.
>
> **8. NEITHER PORT IS WIRED, NO SETTER IS CALLED, AND NO GATE WAS WEAKENED TO PASS IT.** `useCheckoutBackend` is not called, `useAuthBackend` is not called, `start.ts` is untouched, and both routes still answer 503. Three shipped assertions went RED on this branch and **all three were repaired by making them ask a narrower question rather than a looser one**. Section 9.

### 3. Ruling 1 and 2, and the shape argument the row asked for by name

**THE ROW NAMED THE FAILURE MODE BEFORE THE TABLE EXISTED**: *"a firm parameter table is exactly the thing that grows into a settings bag nobody can reason about."* That is correct, and the two candidate shapes answer it differently.

| Shape | What it costs | What it buys |
|---|---|---|
| **A single-purpose table**, `account_caps(cap_accounts, effective_from, ...)` | A new table per parameter, and the corpus has **many** launch-candidate parameters left to place | Nothing to close, because there is no vocabulary. The settings bag is refused by construction |
| **A keyed parameter table with a closed `CHECK`** | The vocabulary is a thing that can be widened, so it has to be watched | ADR-238 ruling 3's own words, *"a firm parameter row on `price_floors`' shape"*. `price_floors` IS a keyed parameter table, and its key is `product_ref` |

**THE SECOND IS TAKEN, AND THE REASON IS THAT THE PRECEDENT ADR-238 NAMED IS ALREADY THE SECOND SHAPE.** `price_floors` is one row per `(product_ref, effective_from)` and nobody calls it a settings bag, because a floor is one kind of number and the key selects which product's. This table is one kind of number and the key selects which parameter's. **The difference between the two tables is that `price_floors.product_ref` is bare text with no `CHECK` on either side of the clamp, which its own registry rule records as a weakness**, and this table closes what its precedent left open.

**AND THE CLOSURE IS TWO CLOSURES, WHICH IS THE PART THE ROW'S SENTENCE DOES NOT REACH.** A `CHECK` over `parameter` decides which names may be written. It says nothing about the SHAPE of what is stored, and the settings bag does not usually arrive as a fifth member of an enum: it arrives as a `text_value` column beside the integer one, added by a session that needed somewhere to put a string, passing every existing constraint untouched. **So the table declares one value column and its type is part of the vocabulary.** A firm parameter that is not an integer has nowhere to go here, and giving it one is visible in a diff as a new column rather than as a new row.

### 4. Ruling 4, and where this table is tighter than the precedent it copies

**`price_floors.approved_by text NOT NULL` IS AN APPROVER RATHER THAN A `users` ROW, ON `0002`'s ACTOR IDIOM.** That was the only shape available in `0024`: no table in this schema held an operator, which is the absence [ADR-237](ADR-237.md) measured and `0073` closed **one migration before this one**.

**SO THE PRECEDENT IS FOLLOWED IN SHAPE AND IMPROVED IN ONE PLACE, AND THE IMPROVEMENT IS AVAILABLE ONLY BECAUSE OF WHEN THIS FILE LANDED.** `0073` made `admin_actions.actor` resolve; this file makes `firm_parameters.approved_by` resolve, which is the same control applied to the row that SETS a limit instead of to the row that RECORDS an act. **A cap approved by nobody is now unwritable**, and that matters here for a reason ADR-238 ruling 4 already gave: *"a purchase refused by a number no row records is a refusal nobody can reconstruct"*. A number recorded with an approver nobody can name is the same defect one column over.

**THE COST IS STATED RATHER THAN HIDDEN: THE FIRST CAP CANNOT BE WRITTEN UNTIL THE FIRST OPERATOR IS.** `operators` has no writer in this repository either, so the two empty tables are now ordered. That is correct rather than awkward -- a cap has to be approved by somebody who exists -- and it is why section 10 names the operator writer as the first of the two things standing between this row and a number.

**`0024` IS MERGED AND IS NOT EDITED.** `price_floors.approved_by` keeps its bare `text` type. Repairing it is a supersession with its own argument and its own session, and it is registered in section 10 rather than taken here.

### 5. Ruling 5, and the trap the row named first

**THE ROW PUT THIS TRAP AHEAD OF THE SHAPE TRAP AND IT WAS RIGHT TO.** *"The override exists and the base does not, so the available shortcut is to read an absent override as an absent cap or as an unlimited one. Both are a control that answers yes to everybody, on the endpoint that sells accounts."*

**BUILDING THE TABLE DOES NOT REMOVE THAT TRAP. IT MOVES IT ONE STEP LATER AND MAKES IT LOOK MORE REASONABLE**, which is worse. Before this file, an implementer had no row at all and had to notice they were inventing a number. After it, an implementer has a door, a query, and an empty result set, and `?? Infinity` reads like defensive programming rather than like a cap being switched off.

**SO THE OBLIGATION IS WRITTEN WHERE THE IMPLEMENTER WILL BE STANDING**, in `AccountCapRow.maxAccounts`' own docblock and in `firm_parameters`' own `COMMENT ON TABLE`, rather than only here. Neither is a control and this entry does not pretend otherwise: **a comment cannot fail.** What CAN fail is asserted instead -- that no migration seeds a row, that `integer_value` carries no DDL default in the SQL or in the Drizzle transcription, and that the refusal sentence is present in the docblock a future diff would have to delete on purpose.

**AND THE ONE CONTROL THAT WOULD ACTUALLY BIND IS NAMED AND REFUSED.** A `NOT NULL` cap column on `identities` with a DDL default would make an absent cap unrepresentable. ADR-238 ruling 3 refuses it and this entry does not reopen it: **a DDL default is a constant**, changing the platform cap would become a migration plus a backfill of every identity row, and it erases the distinction between the base and the exception that `max_accounts_override`'s own name carries.

### 6. Ruling 6, and why the catalogue admission is a different session's

**THE CLAUSE THIS ENTRY NARROWS HAS SAID "NO COLUMN" SINCE IT WAS WRITTEN. IT NOW SAYS "NO DOOR", AND THAT IS A SMALLER THING TO BE MISSING.**

`accountCap()` is a `CheckoutTx` method. `CheckoutTx` is served by a scoped transaction, `ScopedTx` refuses every `firm` key, and [ADR-233](ADR-233.md) built exactly one way through: `CATALOG_TABLE_KEYS`, a closed list of five, reached by `catalogRows`, `catalogRowsWhere` and `catalogRowAt`. **`refuseUncatalogued`'s message states the admission test and this table meets it in terms**: *"ADR-233 admits a `firm` table here because a request handler holding an identity must read it INSIDE its own transaction, and never because the row belongs to nobody, which is already true of every `firm` table in the registry."*

**THE ALTERNATIVE THAT NEEDS NO ADMISSION IS THE ONE TO CHECK FIRST, AND IT FAILS ON AN INVARIANT RATHER THAN ON TASTE.** The route could read the cap through `db.firm` before opening the transaction, as `CheckoutEnrichment.contracts` already reads `integration_contracts`. `INV-M3-15` requires the restriction check at the same point in the transaction as the cap, `gateIdentity` performs both in one call, and ADR-238 ruling 2 keeps that ordering deliberately. **A cap read before the transaction opens is a cap that may have been superseded by the time the purchase commits**, which is a supersession-dated table's characteristic failure and the reason the row is dated at all.

**SO THE ADMISSION IS THE RIGHT MOVE AND IT IS NOT THIS ENTRY'S**, because `packages/db/src/scoped-db.ts` is outside row `252`'s fence, because the fence says the registration and nothing else, and because admitting a sixth member to a list ADR-233 closed is that ruling's own vocabulary moving. It is one line of list plus an argument, it is sized in section 10, and **taking it here would have been the widest possible reading of a fence that names two files by path.**
