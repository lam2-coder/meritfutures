### 5. The cause, re-derived at source rather than taken from a sibling entry

**THE CONSTRAINT IS WHERE [ADR-428](ADR-428.md) SAYS IT IS**, at [`packages/db/migrations/0073_operator_directory.sql:274-277`](../../packages/db/migrations/0073_operator_directory.sql), read on this tree:

```sql
ALTER TABLE admin_actions
  ADD CONSTRAINT admin_actions_actor_is_an_operator
    FOREIGN KEY (actor) REFERENCES operators(actor)
    ON UPDATE RESTRICT ON DELETE RESTRICT;
```

**RED 1 IS THE SAME CONSTRAINT AND IT DOES NOT SAY SO IN ITS OWN OUTPUT, SO IT WAS PROVED RATHER THAN INFERRED.** Its assertion reads only `expected 400 to be 200` at [`admin-writes.test.ts:921`](../../apps/api/test/admin-writes.test.ts). Three things were checked, and together they close it:

- **THE ROUTE TURNS `23503` INTO EXACTLY THAT `400`.** [`apps/api/src/routes/admin-writes.ts:858-862`](../../apps/api/src/routes/admin-writes.ts) maps SQLSTATE `23503` to `validation_failed` at status **400**, with the constraint name carried into `detail`. **So a foreign-key refusal in this module is indistinguishable from a validation refusal at the status code, which is why RED 1 could not name its own cause.**
- **THE STATEMENT THE ROUTE ISSUES WAS RUN DIRECTLY AND THE KEY IS WHAT REFUSED IT.** `INSERT INTO admin_actions (actor, ..., reason, ...) VALUES ('sso:owner@merit', ..., 'a reason', ...)` against this schema returns *ERROR: insert or update on table "admin_actions" violates foreign key constraint "admin_actions_actor_is_an_operator"*, `DETAIL: Key (actor)=(sso:owner@merit) is not present in table "operators"`.
- **AND THE SAME STATEMENT LANDS ONCE THE DIRECTORY ROW EXISTS.** `INSERT INTO operators (actor, role, display_name) VALUES ('sso:owner@merit','owner','Probe')` followed by the identical `admin_actions` insert returns `INSERT 0 1` twice.

**THE SQLSTATE ORDERING [ADR-428](ADR-428.md) USED TO EXPLAIN WHY THREE CASES STILL PASS WAS RE-MEASURED AND HOLDS.** The same insert with `reason` OMITTED and the same unknown actor is refused by *null value in column "reason" of relation "admin_actions" violates not-null constraint*, and never reaches the referential trigger. **Postgres checks `NOT NULL` before it fires a foreign key, so each of the three passing cases raises its own violation one layer shallower than the constraint that was actually broken, and collects the `400` its assertion wanted for the wrong reason.**

**[ADR-237](ADR-237.md)'s TWO CLAIMS WERE CHECKED AT ITS OWN WORDS AND AT THE FILES IT NAMES, AND BOTH HOLD.** [`ADR-237.md:167`](ADR-237.md) reads *"`CI-06h` went RED on the first push and the constraint is what failed"*, and [`ADR-237.md:183`](ADR-237.md) rules *"The repair is the fixture and never the constraint. IT WAS "SCHEMA CHANGES ARE CHECKED AGAINST THEIR `.sql` CALLERS."** `CI-06h` is a `psql` job: every step in it is a `psql` invocation, a `.sql` probe or a `.mjs` assertion, and its `env:` block at [`corpus.yml:176-180`](../../.github/workflows/corpus.yml) is `PGHOST`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` and nothing else. **`0073` broke three callers of one constraint. The two written in SQL went red within the hour and were repaired the same day, [`ADR-237.md:167`](ADR-237.md). The one written in TypeScript went red in a language the only database-bearing job cannot execute, and no human and no gate was ever going to see it.**

**AND THE SILENCE HAD A SECOND LAYER THAT IS WORTH NAMING SEPARATELY, BECAUSE IT IS THE ONE A READER WILL UNDERESTIMATE.** The block did not fail. **It did not run**, so it reported as a SKIP, and a skip is green. [`admin-writes.test.ts:16-17`](../../apps/api/test/admin-writes.test.ts) says the cases *"SKIP LOUDLY when there is none"*, and loudness is a property of a log nobody reads on a green run. **A skipped case and a passing case are the same colour at the top of a CI page, and the count that distinguishes them, `10 skipped`, is stated by no gate in this repository** -- `grep -rn "10 skipped"` over `scripts/`, `packages/tooling/`, `.github/` and `docs/STATE.md` returns nothing. **So the number that would have carried the warning is not bound to anything either.**

**THE THIRD LAYER IS THE RECORD, AND IT IS THE ONE THIS REPOSITORY HAS THE MOST MACHINERY FOR AND STILL MISSED.** [`admin-writes.test.ts:21-22`](../../apps/api/test/admin-writes.test.ts) states a real measurement, *"run by hand for session 257 against PostgreSQL 16.13 with all 47 migrations applied"*. **It was true when written and it is a claim with no expiry date on it**, and 28 migrations later it still reads exactly as confident as it did on day one. **A hand-run is a measurement that ages into a false statement without anybody editing it**, and this corpus has a gate class for derivable counts, `CI-06/derivable-counts`, precisely because typed figures rot. **A dated hand-run is a typed figure about the world rather than about the tree, and no `<!--gen:-->` span can derive it.**

**THIS ROW MINTS NO INVARIANT FOR ANY OF THE THREE AND THE RESTRAINT IS DELIBERATE**, on [ADR-428](ADR-428.md) section 12 item 3's own ground, which this row read and agrees with rather than re-arguing: the honest control for *a TypeScript caller of the schema went stale* is **a job that runs those callers against the schema**, and a static check approximating it would be a check that passes while the property it names is false. **That is the failure this corpus has paid for more often than any other, and a ninth instance of it bought under time pressure is worse than the hole reported plainly.** Section 11 is what this row would wire instead, and it is not wired.
