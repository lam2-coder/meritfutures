## ADR-359: certificate revocation CANNOT be served by this deployment and the route that reaches for it refuses correctly, writing nothing and inventing nothing; the refusal is loud in the one channel that matters and DELIBERATELY MUTE on the wire, and until this row nothing executed was holding that channel open (2026-09-06, status: proposed)

**A live request reaches the unwired default, and that is the fact that separates this port from every dead one beside it.** `useCertificateRevokeBackend` is declared at [`admin-certificates.ts:400`](../../apps/api/src/routes/admin-certificates.ts) and no file under any `src/` calls it, while `currentCertificateRevokeBackend()` **is** called, at `:676`, on the first line of the handler `toAdminCertificateRoutes` registers. So `POST /admin/certificates/:id/revoke` is a registered, reachable route standing on a backend nobody installed.

**THE SERIOUS FINDING WOULD HAVE BEEN A SILENT SUCCESS AND THERE IS NONE.** It was checked first, and the measurement is section 3: the request is refused, nothing is written, no plausible value is invented, and the process never reaches the transaction opener at all.

**WHAT THIS ROW ADDS IS THE HALF THE STATUS CODE CANNOT CARRY.** The refusal presents on the wire as `401 unauthenticated`, byte-identical to the document a genuinely anonymous caller gets, on [ADR-192](ADR-192.md) clause 2's disclosure rule. The handler's own comment says the discrimination *"is in the log"*. **That sentence was the whole control and no executed assertion was holding it**, so a refactor that dropped one `request.log.error` would have left this deployment with **no channel at all** distinguishing "this deployment cannot revoke" from "your credentials were rejected", and every case in the suite would have stayed green. Four cases now hold it.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `359`, branch `claude/a-revoke-nobody-installed`, session **554**.
- **THE DELIVERABLE IS A RULING PLUS FOUR EXECUTED ASSERTIONS AND NO WIRING.** No backend is installed here, and section 5 is the argument for why installing one here would have been reaching across three fences at once.
- **MONEY PATH BY CONSEQUENCE, `E2` READ OWED.** Nothing here is a migration, a route or an arithmetic. But a certificate is a trader's public proof of a paid outcome, and `AS-M11-05` is written about the act of withdrawing one. Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**
- **NO MIGRATION WAS TAKEN AND NONE IS NEEDED.** `git diff --stat origin/main -- packages/db/migrations scripts/db` is **EMPTY**. The schema this route needs is merged: `0020` carries all three revocation columns and the constraint that binds them.
- **A DISPATCH PROMPT IS NOT A SOURCE.** Every figure below is a command this session ran against its own tree. The dispatch named three claims. **All three reproduce**, and two things the tree says around them do not, which is section 7.

### 2. THE RULING

**RULED: certificate revocation CANNOT be served by this deployment, and the blocker is three obstructions rather than one missing call.** Section 5 names each at `file:line`. None of the three is a shape this row may decide.

**RULED: what a request to the revoke route does today is CORRECT and is not changed here.** It refuses, it writes nothing, it invents no `revoked_at`, no revocation class and no reason. **The route is left registered.** A registered route that refuses is a route whose absence is visible; an unregistered one is a 404 indistinguishable from a typo.

**RULED: the refusal's SHAPE is `refuses cleanly`, and it is the good shape rather than the dangerous one.** The dangerous shape this wave has found repeatedly is an unwired port returning a plausible value, which a caller cannot tell from a real answer. `UNWIRED_ADMIN_CERTIFICATE_BACKEND` has **no live arm at all**: all four members refuse and each names itself.

**RULED: the wire-level muteness is CORRECT and STAYS**, on [ADR-192](ADR-192.md) clause 2, and the log is therefore load-bearing. **So the log line is a control and is now held by an executed assertion rather than by a comment.** That is the only thing this row changes about the tree.

### 3. What a request does today, read from route to default rather than inferred

The path is four statements and it was walked, not guessed.

1. [`admin-certificates.ts:676`](../../apps/api/src/routes/admin-certificates.ts) `const active = currentCertificateRevokeBackend();` returns `UNWIRED_ADMIN_CERTIFICATE_BACKEND` (`:397` is the module-scope initialiser and nothing under `src/` reassigns it).
2. `:689` `await active.principal(request)` is the **first** member touched. The default's `principal` is `() => Promise.reject(new AdminCertificateUnwired('principal'))` (`:388`).
3. `:691` catches it, `:692` logs it at **error** level, `:693-696` answers `401 unauthenticated`.
4. `active.operator(...)`, which is the only thing that opens a transaction, is **never reached**.

| question the dispatch asked first | measured answer |
|---|---|
| does it 500? | **No.** `AdminCertificateUnwired` is caught on both legs. The outer catch re-throws only what is neither a `Refusal` nor an unwired/unconfigured error, so a 500 here would be a real defect and never this |
| does it silently succeed? | **No, and it cannot.** The refusal is raised one statement before the transaction opener. `wire`'s recorder observes an empty call list |
| does it refuse cleanly? | **Yes**, and the status is **401, not the 503 the class's own docblock advertises** |

**THE 503 DID NOT GO AWAY; IT MOVED BEHIND THE 401, AND WITH THE FULL DEFAULT INSTALLED IT IS UNREACHABLE.** `:366`'s docblock reads *"Answered as 503, never 500"*, and that is true of `operator`, `now` and `presentation` and **false of `principal`**, because `principal` is the member reached first and its refusal is answered 401 by design. The 503 branch at `:738` is live only for a **partially** installed backend. That is not a contradiction to repair by editing the docblock: the sentence is about the class and the class does answer 503 on three of its four members. It is recorded here because a reader who greps for `503` and finds that comment will predict the wrong status for the deployment as it actually stands.

**AND THE CLOCK REFUSES BEFORE THE AUDIT ROW.** `ctx.backend.now()` is read at `:821`, one statement ahead of `insert('adminActions', ...)` at `:836`. `admin_actions` is append-only under `0026` and its retention is forever, so **an audit row explaining a mutation that never happened is a record no later read can withdraw**. The ordering is the control and it is now asserted.

### 4. What it costs today, and the harm named in the direction it actually runs

**The dispatch named two harms worth naming explicitly. Measured, ONE of them cannot arise here and the other is the whole cost.**

**"A revocation that reports success without persisting" CANNOT ARISE.** Section 3 is the measurement: no success is reported, and the transaction opener is not reached.

**"A revoked certificate that is still honoured" CANNOT ARISE EITHER, AND THE REASON IS WORSE THAN THE HARM.** The read side is complete and correct: [`verify.ts:460`](../../apps/api/src/routes/verify.ts) is `if (row.revokedAt !== null) return 'revoked';`, and `GET /verify/:code` renders section 6.3's `revoked` block off it. **A revocation would be honoured the instant one existed. None can exist.**

```
$ grep -rn "'certificates'" --include=*.ts apps/ packages/ | grep -v /test/
```

resolves to **one write site in the entire tree**: `lockAt` at `:798` and `updateAt` at `:861-862`, both in this handler. `verify.ts:789` and `certificate-image-source.ts:262` are reads through `db.publicLookup`; `certificates.ts:911` is a scoped read; `auth-backend.ts`' two `revokedAt` writes are on `sessions` and are a different table.

**SO THE COST IS EXACTLY THIS: an enforcement decision Merit makes about a real trader has no mechanism to reach the public page, and the page will keep printing the claim.** That is `AS-M11-05`'s subject arriving as an absence rather than as a wrong value. It is a **fail-closed** absence, which is the right direction, and it is total.

### 5. Why the backend cannot be served, cited at `file:line`

Three obstructions. **Each was re-measured on this head. None of the three is this row's to decide, and no two of them lift together.**

**OBSTRUCTION 1, an identity provider this repository cannot install.** `principal(request)` ([`admin-certificates.ts:353`](../../apps/api/src/routes/admin-certificates.ts)) resolves only through `AdminSessionSource`, whose setter is `setAdminSessionSource` ([`admin-reads.ts:242`](../../apps/api/src/routes/admin-reads.ts)) and which `start.ts` does not call. [`operator-identity.ts:65`](../../apps/api/src/operator-identity.ts) says so in its own words. Under [ADR-237](ADR-237.md) this is now **one** named thing rather than two: the operator directory is in this database and the assertion verifier, C-08's hardware-key SSO, is not.

**OBSTRUCTION 2, a door that does not exist, and it is a circularity rather than a missing call.** `AdminCertificateTx` runs `lockAt`, `insert` and `updateAt` on **one** transaction ([`:326-332`](../../apps/api/src/routes/admin-certificates.ts)), across two tables of **opposite scope class**:

| table | class | where |
|---|---|---|
| `certificates` | `owned` on `identity_id` | [`packages/db/src/scope.ts:969-970`](../../packages/db/src/scope.ts) |
| `adminActions` | `firm` | [`packages/db/src/scope.ts:1119`](../../packages/db/src/scope.ts) |

`db.firm('certificates')` does not compile, because `FirmTableKey` is every key whose class is `firm` ([`scope.ts:1614-1616`](../../packages/db/src/scope.ts)), and [`certificates.ts:878`](../../apps/api/src/routes/certificates.ts) states the same refusal independently. `db.scoped` needs an identity, and **this route cannot know it until it has read the row**: `:id` is `certificates.id` and the identity is a column of the row the door would be opened to read. [ADR-231](ADR-231.md)'s `db.publicLookup` does not reach it either, on the address rather than on the permission: that door is **read only** and its vocabulary is `certificates` by `code`, while this route locks and updates and addresses by `id`, which `0020` keeps distinct on purpose so the public token can be rotated after an incident.

**So the audit half has a door and the subject half does not**, which is the one-live-arm-beside-refusing-arms shape `wiring.test.ts` refuses on `usePayoutBackend`'s stated rule.

**OBSTRUCTION 3, configuration rather than a door, and it is a founder question.** `presentation()` ([`:363`](../../apps/api/src/routes/admin-certificates.ts)) is `GET /verify/:code`'s copy, and the `account_enforced` sentence is **`OQ-M11-02`, still open** ([`M11:364`](../plans/M11-certificates-social-proof.md), *"a legal and brand question"*). **No wording is invented here.** A deployment that answered with copy this row made up would be publishing a legal statement about a named person that counsel never saw.

### 6. Whether the refusal is loud enough: it has two channels and only one of them speaks

**THE ANSWER IS SPLIT, AND SAYING SO IS THE POINT OF THE SECTION.**

| channel | what it carries today |
|---|---|
| **the wire** | `401 unauthenticated`, **indistinguishable** from the document a genuinely anonymous caller gets. Same `type`, `title`, `status` and `code`; only `instance`, the request id, differs |
| **the log** | `request.log.error({ err }, ...)` at `:692`, carrying the error itself, whose message names the refusing member **and** names `useCertificateRevokeBackend` as the thing that would install one |

**The wire muteness is deliberate and correct.** The handler's own comment argues it: whether this process holds a backend is a fact about the deployment, an unauthenticated caller may not have it, and answering 503 would tell them the endpoint exists and that its backend is the only thing missing, which is the disclosure the 401-before-403 branch refuses one statement later.

**THE CONSEQUENCE IS THE FINDING.** Because the wire says nothing, **the log is not a diagnostic convenience; it is the only place the fact exists.** And it is worse than that for the person most likely to hit it: an operator with valid credentials gets 401 too, because `principal` refuses before it consults any session. **The wire tells them their credentials are wrong.** The true answer, that this deployment installed no revoke backend, is reachable only by someone reading the process log.

**Nothing executed was holding that line.** Deleting `:692` left the suite green. Four cases now hold both halves, in [`test/admin-certificates.test.ts`](../../apps/api/test/admin-certificates.test.ts), each falsified in both directions (section 9):

1. the unwired 401 and the anonymous 401 are the same document but for `instance`, so adding a `detail` naming the port **re-argues** the disclosure instead of drifting through it
2. the log is reached, exactly once, carrying the error rather than a rewritten string, and its message names `AdminCertificateBackend.principal` and `useCertificateRevokeBackend`
3. all four default members refuse and each names itself, so there is no live arm
4. an unwired clock refuses before the audit insert

**THIS ROW DOES NOT MAKE THE WIRE LOUDER.** Doing so would overturn ADR-192 clause 2 in a test file. Whether it should be overturned is section 8's first question.

### 8. Open questions, recorded as the founder's with options and no values

**NO RETENTION WINDOW, NO REVOCATION REASON VOCABULARY AND NO GRACE PERIOD IS INVENTED HERE.** The corpus states none, and each would be a promise to a real trader.

**OQ-1. Should the wire stay mute?** ADR-192 clause 2 says yes and this row does not disturb it. The options are (a) leave it, and accept that an operator's first signal is a wrong-credentials answer; (b) discriminate **after** authentication only, which needs `principal` to be servable and so is blocked behind obstruction 1 anyway; (c) add an unauthenticated health surface that reports which ports are uncomposed, which is a new disclosure decision and not a tweak. **No option is taken here.**

**OQ-2. Should a deployment that cannot revoke refuse to START?** Today it starts and serves a route that always refuses. The options are (a) leave it, on the ground that a running deployment missing one operator endpoint is better than no deployment; (b) fail closed at boot, which makes the absence impossible to miss and makes every other endpoint hostage to this one; (c) declare it in a startup report that names uncomposed ports without blocking. **This is a founder call about operational posture and no code here assumes an answer.**

**OQ-3. Which obstruction is meant to lift first?** They are independent and the order is a sequencing decision. Obstruction 3 is the cheapest and is `OQ-M11-02`, a question already open and already the founder's. Obstruction 1 is C-08 and is the largest. **Obstruction 2 is the only one that is a design question inside this repository**, and it is whether a route that must touch an `owned` table and a `firm` table on one transaction gets a named door, as `effectiveAccountCap` did, or whether the audit row moves off the transaction, which would cost the `before` triple's atomicity.
