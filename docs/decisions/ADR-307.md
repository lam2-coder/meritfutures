## ADR-307: the pin that fixed one `qs` advisory is the vehicle of the next two, and `CI-05` has been red on every branch since (2026-09-03, status: proposed)

**`CI-05 security static` is red on `main` and on every open pull request, and it is not any of their diffs.** `pnpm audit --audit-level=moderate` reports two moderate advisories against `qs`, reached transitively through `packages/rules-engine > @stryker-mutator/core > typed-rest-client > qs`. The package is pinned to `6.15.3` by this repository's ONE `pnpm.overrides` entry, and **`6.15.3` is inside both new advisories' vulnerable ranges**. The override that closed GHSA-q8mj-m7cp-5q26 is what now holds the tree open to GHSA-x5fp-wj9c-mxmx and GHSA-4mjr-xmp4-gh2g.

**THE FIX IS ONE CHARACTER-RANGE AND THE READING IS THE POINT.** The pin moves `6.15.3` to `6.16.0`. What is worth recording is not the number but the shape: **a version pin written as the remedy for one advisory is a standing bet that no future advisory covers the version it names**, and that bet lost here within days. The `//pnpm.overrides` note in `package.json` argued for `6.15.3` in the advisory's own words and, once the new advisories published, became a live sentence recommending a vulnerable version. It is rewritten to carry the history rather than only the current number.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `307`, branch `claude/the-pin-is-the-vulnerability`. **NON-MONEY.** No `src/` line, no migration, no test, no gate, no workflow. The diff is `package.json`, `pnpm-lock.yaml`, this ADR and the registries.

- **NO GATE IS WEAKENED, AND THE ALTERNATIVE THAT WOULD HAVE WEAKENED ONE IS NAMED AND REFUSED.** `--audit-level=high` would make both advisories invisible without removing either package, which is weakening a gate to pass it. The existing note in `package.json` already refused exactly that move for the first advisory, on the same rule that refused a `.gitleaksignore` fingerprint. **This row keeps that refusal and does not re-argue it.**

- **NOTHING IS SIGNED.** `status: proposed`, approval line UNSIGNED.

### 1. The failure, re-derived at source rather than read off CI

`main`'s last green `CI-05` ran on 2026-09-01 at 22:06Z, and nothing has been pushed to `main` since. **That green is not evidence about today**: `pnpm audit` queries a live advisory database, so a newly published advisory turns the check red with no commit and no push. The base branch looks green in history and is red in fact.

### 2. What the exposure actually is, stated so it is not overstated

**`@stryker-mutator/core` is a `devDependency` of `packages/rules-engine` and of nothing else.** That is deliberate and it is [ADR-127](ADR-127.md)'s delegated `VG-12` grant: `package.json`'s own note reads *"STRYKER LIVES HERE AND NOWHERE ELSE"*, and it is not a root declaration precisely so that a package cannot run it by accident.

**So nothing Merit ships reaches this code path.** The exposure is CI runners and developer machines, not production, and no deployable's dependency graph contains `qs` by this route. **This is stated to size the row honestly and NOT as a reason to leave it**: the check is a merge blocker on every branch, and a repository whose security gate is permanently red has no security gate.

### 3. Why the pin moves rather than the package

Three moves would clear the check and only one is honest.

| Move | Effect | Verdict |
|---|---|---|
| **Raise `--audit-level` to `high`** | Both advisories stop being reported. Neither package changes | **REFUSED.** Weakening a gate to pass it. `package.json`'s own note already refused this once |
| **Drop `@stryker-mutator/core`** | Removes the path entirely | **REFUSED AND IT IS NOT THIS ROW'S TO TAKE.** Mutation testing on the engine is [STRATEGY](../testing/STRATEGY.md) section 2's ruling, admitted under [ADR-127](ADR-127.md)'s `VG-12` grant. Retiring it is a founder ruling, not a security patch |
| **Move the pin to `6.16.0`** | Removes the vulnerable package. Path-scoped, so no direct dependant of `qs` is decided for | **TAKEN** |

### 4. The general fact this row exists to record

**A version pin is a remedy with an expiry date that nobody writes down.** `6.15.3` was correct when it was chosen and became the vulnerability itself when two further advisories published against the range containing it. The tree carried a live, confident, well-argued sentence in `package.json` recommending that exact version, and that sentence was false from the moment the advisories landed.

**This is the same defect class the corpus has now found in three places in two days**: [ADR-298](ADR-298.md)'s stale citations, [ADR-303](ADR-303.md) section 7's five sentences that a typed return made false, and this. In each, a claim that was true when written outlived the fact it described, and in each **no check could see it**, because the claim is English prose about a fact held somewhere else.

**No `RI-nn` is minted for it here and the reason is that a line reader cannot hold the property.** "No sentence recommends a version an advisory covers" needs the live advisory database, which is `CI-05`'s job and is already run. The control that catches this is the one that already fired: `CI-05` went red the day the advisory published. **What failed was not the control but the reading of it** — a red security check on a stale base was available to be mistaken for a red check on the branch under review.

### 5. What is NOT taken

- **THE TWO HALVES OF `CI-05` DO NOT DISAGREE ABOUT "CURRENT", AND THIS ENTRY CHECKED RATHER THAN ASSUMED.** A draft of this section claimed they did, on `ci.yml:158`'s workflow-level `GRYPE_DB_AUTO_UPDATE: 'false'` beside `pnpm audit`'s live database. **The claim was false and the source says so in its own comment.** `ci.yml:533` is a dedicated `VG-12 vulnerability database` step that sets the variable to `'true'` and runs `grype db update`; auto-update is off for the SCAN only, so a scan cannot silently re-download and inherit the unbounded wait the split exists to remove. Both halves read a database refreshed on the run. **It is recorded because the wrong reading is the natural one** — a workflow-level `false` looks like a pinned database until you read the step that overrides it — and because an ADR that asserted a security check was internally inconsistent would have been believed.
- **No other override is added and none is reviewed.** There is exactly one and it stays exactly one.
- **Node 20 deprecation warnings** appear in every `CI-05` log (`actions/checkout@v4`, `actions/setup-node@v4` forced onto Node 24). Noted, not this row's.

### 6. Approval

This is a **non-money** row. What is owed is a read of section 3's refusals — specifically that dropping `@stryker-mutator/core` was refused as a founder ruling rather than taken as a convenience, and that raising `--audit-level` was refused as weakening a gate to pass it — and of section 4, which is the only part of this row that is not a dependency bump.

**What a founder read adds and this entry cannot.**

**THE FIRST THING TO DECIDE IS WHETHER `@stryker-mutator/core` STAYS.** This row refused to drop it, on the ground that mutation testing on the engine is [STRATEGY](../testing/STRATEGY.md) section 2's ruling admitted under [ADR-127](ADR-127.md)'s `VG-12` grant, and a security patch is not the place to retire a testing ruling. **That refusal is the right call for a session and the wrong one for a founder to leave unmade**, because the package is now the sole reason a transitive `qs` pin exists at all, and the pin has moved twice in two advisories. A founder who is willing to lose mutation testing removes the whole path and this override with it; a founder who is not accepts that the pin will move again.

**THE SECOND IS SECTION 4'S DECISION NOT TO MINT AN `RI-nn`.** The reasoning is that a line reader cannot hold "no sentence recommends a version an advisory covers" without the live advisory database, which `CI-05` already carries. That is sound as far as it goes, and it leaves the actual failure uncontrolled: **what broke was the reading of a red check, not the check.** Whether that deserves a gate of its own — something that refuses to let a red `CI-05` be attributed to a base branch without the attribution being demonstrated — is a founder's call about how much process a misreading is worth, and this entry declines to make it.

**NOTHING ELSE HERE IS A JUDGEMENT.** The version bump itself is forced: `6.15.3` is inside the range of both live advisories and `6.16.0` is outside them, verified by `pnpm audit --audit-level=moderate` exiting 0 on this branch where it exits 1 on `main`.
