### 3. `approved_at` is suppressed on one status, and that is `F6` rather than a preference

**THE COLUMN CAN LIE ON EXACTLY ONE STATUS AND [ADR-290](ADR-290.md) FINDING `F6` SAID SO BEFORE THIS ROW EXISTED.** `payout_requests.approved_at` is `timestamptz NOT NULL DEFAULT now()` ([`0010:89`](../../packages/db/migrations/0010_payouts.sql)) and [`0031`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql) relaxed nothing, by its own stated design: adding columns is what *"keeps every existing NOT NULL and every existing CHECK on this table intact"*. **So a held row carries a non-null `approved_at` whose value is the insert time and not an approval time.**

[API_CONTRACT:515](../architecture/API_CONTRACT.md) types it `string | null` and says *"null while held: the hold is PRE-approval"*, and the declaration's own docblock repeats it: a client that types it non-null *"renders an epoch date on the one state that most needs to render correctly."* **`listPayouts` therefore serves `null` when `status = 'held_pending_review'` and the column everywhere else.** The suite's fixture carries a real `Date` in that column precisely so a straight read would pass a weaker assertion, and removing the suppression was seeded and watched failing.

**THE `hold` BLOCK IS READ TWO SIDED, MATCHING THE CONSTRAINT'S OWN SHAPE.** `payout_requests_hold_is_complete` is a biconditional, so a row carrying a hold column off `held_pending_review` is refused as loudly as a held row missing one. **Serving one direction only would publish a hold the database has already erased.** Three of the five hold columns are read and two are not: `hold_flag_id` and `hold_reason` have no slot on `PayoutHold`, and [API_CONTRACT](../architecture/API_CONTRACT.md) is why rather than an oversight, the trader being shown *the fact, the ToS clause and the date it resolves*, never the evidence and never the detector.

**AND `settled_at` IS CHECKED PRESENT ON `settled`**, which is `payout_requests_settled_has_days` ([`0010:152-157`](../../packages/db/migrations/0010_payouts.sql)) read in the one direction it actually runs. It is an implication and not a biconditional, so the reverse is not asserted.

**EVERY REFUSAL ON THIS PATH IS A `PayoutRowError` AND THEREFORE A 500**, not a `PayoutBackendUnwired`. That is this module's existing ruling applied one member over: an unbuilt member is retryable and a row whose columns disagree with the schema that wrote them is not, and a retryable status would tell a trader to retry what no retry can fix. **Money goes through `centsOf` and then `centsToJson`**, so a column that did not arrive as a `bigint` is refused rather than coerced and a value past `Number.MAX_SAFE_INTEGER` throws rather than serialising wrong. **There is no `Number()` anywhere on this path.**
