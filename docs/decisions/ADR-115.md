## ADR-115: enrichment observes, and the two places observe mode could quietly become enforcement are closed by shape rather than by discipline  (2026-08-26, status: proposed)

**[ADR-023](ADR-023.md) settles what this slice is for and this entry settles three things it does not reach. It rules that observe mode writes NO `risk_flags` row and that the score therefore has no persisted column, which is reported rather than repaired; that the non-blocking direction is a TYPE and not a promise, because `observeEnrichment` returns `Promise<void>` and never throws; and that the signal write is a READ then an ADDRESSED WRITE, because `identity_signals` carries its natural key as a `CREATE UNIQUE INDEX` that the transcription does not declare, so a blind insert would raise `23505` on the ordinary repeat-purchase path and roll a purchase back.** No vendor is named, no migration is written, no threshold exists and `0048` stays free.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-p` row and section 15's prompt, session **223**. The number was RESERVED BEFORE DISPATCH and reserved **conditionally**: [ALLOCATION](ALLOCATION.md) row 115 says an entry is expected "only if the vendor port or the scoring shape needs one". **The scoring shape needed one, and clause 1 is why.**

- **Context:** [ADR-023](ADR-023.md) is accepted and is not reopened. The vendor is **bought and not built**, the adapter is **vendor-agnostic**, the rollout is **graduated**, and step 1 is observe mode: *"Signals recorded, scored, and reported; nothing is blocked. The purpose is to learn the distribution on Merit's own traffic."* [M03 section 7.9](../plans/M03-billing-checkout.md) specifies the call and its failure behaviour, [M07](../plans/M07-risk-abuse.md)'s `D-15` is what the signals feed, and the procurement condition in section 7.9.1 is **not** reopened here. What this entry rules is the shape of the transcription, which the ruling does not fix and which decides in three places whether observe mode stays observe mode.

- **MONEY PATH by position**, and it decides nothing: it runs inside checkout's transaction. The `E2` line-by-line read on everything this lands is **owed and is the founder's**.

**Claim 4's cost, stated plainly, because it is the one that would have shipped.** A blind `insert` on every finding is the obvious transcription, it passes every type check, it passes a suite that observes each identity once, and it fails in production on **the second purchase by any returning trader** with a duplicate key. Inside checkout's transaction that error is not a lost signal: Postgres puts the transaction into the aborted state at the failing statement and turns its `COMMIT` into a `ROLLBACK`, so **the purchase is refused**. That is enrichment blocking a checkout through the database rather than through a decision, which is exactly what [ADR-023](ADR-023.md)'s step 1 forecloses, and no reviewer reading the diff for "does this decide anything" would see it.

### 2. THE RULING

#### Clause 1. Observe mode writes NO `risk_flags` row, and the score has NO persisted column

**The score is computed, carried in the reported outcome, and stored nowhere.** No `risk_flags` row, no `severity`, no mapping from one to the other anywhere in `packages/enrichment`.

Three reasons, in the order they bind:

1. **`D-12` already ruled this shape** (claim 3). A detector that observes without accusing produces a watched set rather than a flag. Observe mode accuses nobody by construction, so the flag table is the wrong table and not merely a premature one.
2. **Writing a severity would be acquiring authority over money LEAVING while claiming none over money arriving** (claims 1 and 2). `risk_flags.source` is reserved `'vendor:<name>'` in its own DDL comment "so a QuantSentry-class detector plugs in without a migration", and that invitation is real; taking it up with a number nobody has tuned, in a band `G-HOLD-REQUIRED` reads, would hold real traders' payouts on a signal whose distribution is the thing this mode exists to learn.
3. **A flag per checkout is a queue nobody works.** `status` defaults to `'open'` and `SD-M7-02` gives the high band a clock. Observe mode runs on every purchase.

**THE CONSEQUENCE IS A GAP AND IT IS REPORTED RATHER THAN PAPERED OVER.** There is no column in the 47 migrations for an observe-mode enrichment score. The nearest available surface is `identity_signals.value_preview`, and it is the wrong one: the DDL calls it "a non-identifying display fragment for admin ... deliberately not enough to reconstruct what it previews", which is a preview of the VALUE and not a reading about it. Writing a band there would make the column mean two things and would put a score into the graph's node table where `D-16` would find it.

**So the score is REPORTED and not STORED, and persisting it is a migration a later session owes.** What that migration should carry is stated here so the next session does not re-derive it: one row per assessment, the score in **integer basis points on `identity_links.confidence_bp`'s 0 to 10000 scale** ([`0002_identity.sql:163`](../../packages/db/migrations/0002_identity.sql)), the reading counts beside it so a score standing on one facet is distinguishable from one standing on five, and **no `severity` column**, because a table that had one would answer clause 1 the other way by default.

#### Clause 2. The non-blocking direction is a TYPE, and the failure directions are a `catch`

**`observeEnrichment` returns `Promise<void>` and never throws.** Both halves are load bearing and neither is a preference.

- **`Promise<void>`** means a call site has nothing to branch on. "An enrichment outcome changes what checkout returns" stops being a code path somebody must avoid writing and becomes a shape that does not exist. This is [ADR-105](ADR-105.md)'s second rule for the payment port ("nothing in the interface returns a decision") tightened one notch, because a payment port at least reports what the provider said.
- **Never throwing** is the same ruling against a subtler shape. A throw inside checkout's transaction is a `ROLLBACK`, so a propagating enrichment failure is **enforcement by exception**, and enforcement by exception is a **silent** decline: the customer is refused and told nothing. [ADR-023](ADR-023.md) forbids a silent decline even in step 3, where declining is permitted at all.

**The reporter's own throw is caught for the same reason one layer out.** An observability call that can abort a purchase is the identical defect wearing a different hat.

**AND THE `catch` HIDES NOTHING ON THE ONE PATH WHERE THAT WOULD MATTER.** If a write this package issues fails, the caller's transaction is **already** aborted before the catch runs; the `COMMIT` is already a `ROLLBACK` and swallowing the error changes only that checkout is not ALSO handed a second exception from a path that decides nothing. The outcome is reported as `record_failed` so the failure is visible rather than absent.

#### Clause 3. The signal write is a READ then an ADDRESSED WRITE, and the residual is named rather than closed

Per claim 4, a repeat observation is `rowsWhere({ kind, valueHash })` followed by `updateAt({ id }, ...)`. `{ kind, valueHash }` is refused by `refuseUnaddressed` and `{ id }` is the only address the table has.

**THE RESIDUAL, STATED IN FULL.** Two checkouts by ONE identity, in flight at the same moment, presenting the same enrichment reference, can both read no row and both insert. The loser gets `23505` and its purchase rolls back. It is narrow, it is real, and it is not closed here.

**Two constructions would close it and BOTH are diffs on [`packages/db/src/scoped-db.ts`](../../packages/db/src/scoped-db.ts), which is outside this session's fence.** They are named so the next session chooses rather than rediscovers:

| Construction | What it buys | What it costs |
|---|---|---|
| **An `ON CONFLICT` upsert on the accessor** | The race disappears. One statement, no read, no lost increment | It needs a conflict TARGET, and the only correct target here is the `uniqueIndex` `uniqueKeys()` deliberately does not read. So it lands with a decision about whether an index may be a target, which is a wider ruling than one caller |
| **A savepoint** | A failing write stops poisoning the caller's transaction, which helps every caller and not only this one | [ADR-102](ADR-102.md) foreclosed nested transactions on the ground that "a primitive admitted before a caller exists is a primitive nobody can remove". **A caller exists now**, and this is that report |

**A third repair is cheaper than both and is not a substitute for either:** declaring the natural key in [`schema.ts`](../../packages/db/src/schema.ts), which would make `{ kind, valueHash }` addressable and turn the read-then-write from forced into merely cautious. [Session 227](../sessions/2026-08-26-session-227.md) already reported that **34 unique keys the DDL declares are absent from the transcription**, and this is one caller feeling one of them. The suite pins the fact, so the day it changes a test says so.

#### Clause 4. No enabled contract row means NO CALL AT ALL, and the row is installed disabled

Per claim 5. The package DECLARES the row and installs it with `enabled: false`, and `approved_by` and `approved_at` are **required parameters with no default**, because there is no approver a source file could invent that would be true. Enabling it is a separate act and a separate diff.

**The absence of a contract is also the strongest non-blocking case in the slice**: no row, no call, no disclosure, no signal, and a checkout that commits exactly as it would have.

**THE DISCLOSURE RECORD IS WRITTEN WHENEVER THE SUBJECT LEFT MERIT, INCLUDING ON A TIMEOUT.** `integration_dispatches` answers "what did we send about this person", which "a privacy deletion request and a vendor breach ask ... IDENTICAL", and a vendor that received a buyer's email and then failed to answer received it exactly as much as one that answered. `idempotency_key` is the purchase id, so `integration_dispatches_idempotency_uq` makes **one enrichment disclosure per purchase** a fact rather than a convention: a retried payment attempt is a new session against the same purchase ([M03 section 3.2](../plans/M03-billing-checkout.md)), and asking the vendor twice about one purchase would be two disclosures of one person for one event.

#### Clause 5. The budget is 800 integer milliseconds and it is a package constant

`ENRICHMENT_TIMEOUT_MS = 800`, exported rather than passed, so the number is read in one place by whoever is answering how long a purchase may wait on a fraud signal.

**THE RACE IS AGAINST THE PROMISE AND NOT AGAINST THE ADAPTER'S GOOD BEHAVIOUR.** An `AbortSignal` is passed so an adapter CAN drop its socket and nothing depends on it doing so, which is the only honest posture when the thing on the other end is a third party. The abandoned call is given its rejection handler at the moment it is made, so a failure arriving after the request is gone settles a promise nobody awaits instead of becoming an unhandled rejection, which in Node is a process exit.

**When it fires:** nothing from the vendor is recorded because there is nothing to record; the dispatch row is written; the outcome is reported as `timed_out`; and the function resolves, so the purchase commits.

**800 IS A LATENCY BUDGET AND NOT A TUNED PARAMETER**, and the distinction matters because [ADR-023](ADR-023.md) forbids the second kind here. It bounds how long a transaction may stay open; it does not decide anything about a buyer, and moving it changes no outcome for anybody.

### 3. What this entry deliberately does NOT rule

- **It does not name a vendor and does not reopen the procurement.** [M03 section 7.9.1](../plans/M03-billing-checkout.md) makes portability history a condition of acceptance and that is untouched.
- **It does not set a threshold**, because [ADR-023](ADR-023.md) rules thresholds "tuned on beta data, never on the vendor's defaults" and there is no beta data. **`ageDays` is recorded and NOT scored** for the same reason: turning an age into a risk reading needs a curve, and a curve invented here would be an untuned parameter sitting in a scored path looking exactly like a tuned one.
- **It does not answer `OQ-M3-03`**, and clause 1 is written so that answering it either way remains available.
- **It does not design step 3.** A soft decline plus a review queue is a different slice and it will need this entry's clause 1 reopened, deliberately, by somebody who has the distribution in front of them.
- **It writes no migration.** `0048` stays free.

**Four seeds turn one assertion red and that is reported rather than rounded up.** Each is a single-property control whose whole cover is one test, which is the honest description of a source-reading gate.

### 5. The approval line, UNSIGNED

> **An enrichment call that times out, errors or returns a maximal risk score leaves the checkout COMMITTED and reports the outcome, watched in all three directions.**

**Watched.** `packages/enrichment/test/observe.test.ts`, and each direction asserts BOTH halves of "committed": that `observeEnrichment` resolved, and that it resolved to `undefined`.

```
$ pnpm vitest run --project unit packages/enrichment
  Test Files  5 passed (5)
       Tests  83 passed (83)
```

**Cost if wrong:** observe mode silently becomes enforcement by outage, which is the silent decline [ADR-023](ADR-023.md)'s step 3 forbids even when enforcement IS enabled. **The `E2` line-by-line read is owed on every line this lands and is the founder's.**

**What a founder read adds and this entry cannot.** Three of the decisions here are judgements rather than derivations. **That observe mode persists NOTHING** (clause 1) refuses the invitation `risk_flags.source` writes into its own DDL comment, and the entry's own reason is that taking it up would acquire authority over money leaving while claiming none over money arriving, on a band `G-HOLD-REQUIRED` reads. The cost is stated and is real: the distribution this mode exists to learn is reported and then gone, and the migration that would keep it is specified here and owed by nobody. **That the residual race in clause 3 is NAMED and NOT CLOSED** ships a known duplicate-key path on the money path: two checkouts by one identity, in flight together, and the loser's purchase rolls back. Both closures are diffs on a file outside this fence and the entry says which, so the judgement is whether a money-path slice may land carrying a race it can describe exactly. **That 800 milliseconds is a latency budget rather than a tuned parameter** is the distinction ADR-023 forbids collapsing, and it holds only while nothing downstream reads the timeout as a signal about a buyer.
