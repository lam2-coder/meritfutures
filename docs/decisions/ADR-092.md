## ADR-092: `schema.ts` and `scope.ts` are transcribed ONCE PER MODULE, the owner is the TABLE rather than the module, and the queue is the TYPE CHECKER rather than a document  (2026-08-24, status: accepted)

**[P4](../plans/P4-portal-and-site.md) section 10 item 1 calls this *"the single decision that most changes how many of the remaining phases can run concurrently"* and refuses to take it. This entry takes it. A RULING ONLY: no transcription, no table added, and no change of any kind to `packages/db`.**

**The three readings P4 names differ in how they SLICE the work and not at all in how much of it can RUN AT ONCE. All three permit exactly ONE concurrent transcribing session, because all three treat the pair as a resource to be held.** That is the finding, and it is why the ruling is a reading plus two specifications rather than a choice among three.

- **Origin:** [session 172](../sessions/2026-08-24-session-172.md)'s [P4](../plans/P4-portal-and-site.md), section 10 item 1, itself standing on fourteen module measurements run in parallel on 2026-08-24 ([sessions 157 to 170](../sessions/README.md)), each fenced to one module and blind to the other thirteen. **Ten of the fourteen independently proposed the same slice on the same pair of files.**

- **Context:** [`schema.ts`](../../packages/db/src/schema.ts) transcribes **7 tables of 111** and [`scope.ts`](../../packages/db/src/scope.ts) writes a rule for each of the seven, both figures reported as-is by [ADR-084](ADR-084.md) on purpose. [P4](../plans/P4-portal-and-site.md) measured **98 of 100 schema deltas landed against 7 of 111 tables reachable**, schedules thirteen tables and **cannot schedule the other 91**.

---

### 1. All three readings permit ONE concurrent session, and the number is the whole question

**P4 states the cost in one sentence and it is correct**: `schema.ts` and `scope.ts` are one pair of files, so every session that transcribes into them is serial with every other. P4 wave 1 is already serial on `schema.ts` for exactly this reason ([P4](../plans/P4-portal-and-site.md) section 8: *"`P4-a` then `P4-b`, strictly serial"*).

**Counted for each reading, which is the comparison P4 asks for and does not make:**

| Reading | Concurrent transcribing sessions | Sessions to reach 111 | What bounds it |
|---|---|---|---|
| **1. Once for the estate** | **1** during, unbounded after | **1** | One session writes 111 tenancy rules on the money path. Section 7.1 |
| **2. Once per phase** | **1** | one or more per phase | [DELIVERY_PLAN](../DELIVERY_PLAN.md)'s phases are sequential, and P4 already splits its own into two serial slices. Section 7.2 |
| **3. Once per module, owner and queue, taken literally** | **1** | **22** | A queue is depth one by definition, and section 3 measures that the owner does not partition |
| **3 AS RULED HERE** | **N, bounded by table-set disjointness and NOT by the file** | 22, concurrent wherever the sets are disjoint | Section 5's one line |

**A reading that is elegant and serialises the whole estate is worse than one that is ugly and does not.** Reading 1 is the elegant one and it buys a single session that two other rules forbid. Reading 3 taken literally is the ugly one and it buys the same number: **one**.

---

### 2. The ruling

**The unit of work is the MODULE'S TABLE SET.** Reading 3. It is the shape ten of the fourteen measurements implicitly assumed, and it is the only one of the three whose unit matches where the knowledge lives: a scope rule states how a row reaches an identity, and that argument is made in the module plan that owns the table's behaviour.

**P4 leaves *owner* and *queue* undefined and this entry defines both, because each was doing the serialising.**

> **1. THE OWNER IS THE TABLE, NOT THE MODULE. A table is registered ONCE, by the first session that needs it, and the registration is not re-argued.** A later module that reads the same table finds it present and its slice is that much smaller. **The `why` field states the TABLE's tenancy and never the reader's use**, so it does not matter which module's session writes it.
>
> **2. THE QUEUE IS THE TYPE CHECKER, NOT A DOCUMENT.** There is no roster, no holder, no ticket. **A session computes its own slice from the tree** by reading `TABLE_KEYS`, and dispatches concurrently with any other whose remaining table set is disjoint. Every way two concurrent registrations can go wrong on this pair is already a compile error, **with exactly one exception, and section 5 closes it.**

**Both halves are load bearing. Either alone still serialises**: a per-module owner with a real queue is one session at a time, and a compiler-checked queue with per-module ownership deadlocks on the 54 tables more than one module claims.

---

### 3. The owner cannot be the module, and it is measured rather than argued

**Module plans do not partition the 111 tables. They cover them, with heavy overlap and with gaps.**

Run here over all 47 migrations and all 22 `M*.md` plan documents, whole-word match:

| Tables named by | Count |
|---|---|
| **more than one module plan** | **54 of 111** |
| exactly one module plan | 53 |
| **no module plan at all** | **4** (`payment_disputes`, `affiliate_statements`, `ledger_halts`, `identity_signal_weights`) |
| four or more module plans | 23 |

**`accounts` is named by 21 of the 22 plan documents and `identities` by 16.** `purchases` by 11, `plan_versions` by 9. **A rule that assigns a table to "its module" has no answer for `accounts` and no answer for the four that belong to nobody.**

**AND THE COLLISION IS NOT HYPOTHETICAL. IT ALREADY HAPPENED, INSIDE THE MEASUREMENT WAVE, ON FOUR TABLES.**

[Session 159](../sessions/2026-08-24-session-159.md)'s `M5-1` claims seven tables including `wallet_withdrawals`, `wallet_entries`, `wallet_spend_limits` and `wallet_dormancy`. [Session 169](../sessions/2026-08-24-session-169.md)'s `M20-a` claims **those same four** and nothing else. **159 saw it from its side** and wrote the collision down (*"`M5-1`, and any M20 slice adding a wallet table"*). **169 declared the opposite**, that `schema.ts` and `scope.ts` are *"M20-a's alone"*. Two sessions, one table set, and a per-module owner cannot say which is right because **both are right about their own plan**.

**Under this ruling the four tables have one registration and it belongs to whichever session merges first.** The other rebases four rows out. That is a loud cost paid once, not a design question.

**Two more per-table questions exist and they are named rather than ruled**, because each is a table's own tenancy and neither is this entry's: [`identity_links`](../../packages/db/migrations) carries **two** identity columns against an `owned` rule that names one ([session 161](../sessions/2026-08-24-session-161.md)), and `attributions` carries `buyer_identity_id` **and** `affiliate_identity_id`, both `NOT NULL REFERENCES identities(id)` ([session 162](../sessions/2026-08-24-session-162.md)). **That these are per-TABLE rulings and not per-module ones is itself an argument for the ruling above.**

### 4. The queue can be the type checker, and the four hazards were SEEDED AND WATCHED rather than predicted

**Four sessions in the wave assert that this pair is [P3](../plans/P3-ledger-billing-identity.md)'s `pnpm-lock.yaml` finding on another file**, and [P4](../plans/P4-portal-and-site.md) section 9 adopts it: *"the two files move together or the workspace does not compile. Treat them as ONE unit of contention."*

**THE FIRST HALF IS TRUE AND THE ANALOGY IS FALSE, AND THE DIFFERENCE IS THE WHOLE RULING.** A keep-both merge of a lockfile produces a **plausible wrong file that nothing checks**. A keep-both merge of this pair produces a **compile error**. Both are "serial" in the sense that a merge needs a human; only one of them is serial in the sense that costs a cycle.

Every row below was executed in a throwaway git worktree at `f6b0d5c` with `tsc --noEmit` and `vitest run packages/db/test/scoped-db.test.ts`. **`packages/db` on this branch is unchanged, and `git status --porcelain packages/db` reports zero.**

| Seeded concurrent-merge hazard | Result |
|---|---|
| **Two branches declare the same table in [`schema.ts`](../../packages/db/src/schema.ts)** | **`TS2451: Cannot redeclare block-scoped variable 'liabilitySnapshots'`** |
| **Two branches add the same key to `TABLES`** | **`TS1117: An object literal cannot have multiple properties with the same name`** |
| **A table declared in `schema.ts` and never registered** | **`tsc` exit 0, suite unchanged at 26**, and the call site is refused: **`TS2345: Argument of type '"probeUnregistered"' is not assignable to parameter of type 'ScopedTableKey'`** |
| **Two branches add DISJOINT tables and the merge is attempted** | **Textual conflict in all three files**, `schema.ts`, `scope.ts` and `scoped-db.test.ts`. Loud, and every keep-both resolution is verified by `tsc` |
| **A REGISTERED table omitted from `DDL_NAMES`** | **`tsc` exit 0 and the suite GREEN at 25 tests where the baseline is 26.** Section 5 |

**The fourth row is the one the lockfile analogy gets wrong.** Two branches adding disjoint tables **do** conflict, in three files. They conflict **textually**, which git reports, and the resolution is verified by a type checker rather than trusted. **A conflict a machine finds and a machine checks is a rebase. A conflict nothing finds is the lockfile.**

### 5. ONE hazard is silent, it is the entire cost of this ruling, and it is one line

**[`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts) states one table-to-SQL-name map TWICE.**

| Site | Declared as | Total over `TableKey`? |
|---|---|---|
| `SQL_NAME`, [`:256`](../../packages/db/test/scoped-db.test.ts) | `Readonly<Record<TableKey, string>>` | **YES.** Omitting a table does not compile |
| `DDL_NAMES`, [`:394`](../../packages/db/test/scoped-db.test.ts) | `ReadonlyArray<readonly [TableKey, string]>` | **NO.** An array. Omitting a table compiles and passes |

**Both hold the same seven pairs today.** `DDL_NAMES` is what drives the per-table drift assertion, the mechanical check [ADR-084](ADR-084.md) section 1 installed **in place of a superseded ADR-008 consequence**, and the assertion for a table not in the list simply does not exist.

**Executed:** delete `['liabilitySnapshots', 'liability_snapshots']` from `DDL_NAMES`, change nothing else. `tsc --noEmit` exits **0**. The suite passes at **25 tests where the baseline is 26**. `liability_snapshots` is still in `TABLES`, still in `SCOPE_RULES`, still scoped, and **its drift assertion is gone, the test count went DOWN, and nothing said so.**

**That is what a keep-both merge on this pair looks like when the resolver keeps both sides of `TABLES` and one side of `DDL_NAMES`**, and it is the only resolution of the four in section 4 that is green and wrong.

> **THE REMEDY IS ONE LINE AND IT IS THE PRECONDITION THIS RULING CARRIES: `DDL_NAMES` must be derived from `SQL_NAME` or declared total over `TableKey` the way `SQL_NAME` and `SCOPE_RULES` already are.** Two hand-maintained statements of one map is precisely the drift class [`schema.ts`](../../packages/db/src/schema.ts)'s own header and `packages/db/tsconfig.json`'s `checkJs` comment say this package exists to remove, and it is sitting inside the suite that guards against it.

**Written as a precondition and not performed here, because this entry holds no part of `packages/db`.** It is small, it is mechanical, and it belongs to the next session that opens `scoped-db.test.ts`, which by [P4](../plans/P4-portal-and-site.md) section 8 is `P4-a`. **Concurrent transcription is safe once it lands and is one loud conflict short of safe before it.**

**The constitution's own preference decides the shape**: *"Prefer a new CI gate over a bigger model whenever the error is checkable."* This error is checkable by a mapped type, which is cheaper than a gate.

### 6. [ADR-084](ADR-084.md)'s property is preserved, and strengthened rather than merely untouched

**The property**: `SCOPE_RULES` is declared against a mapped type over `TableKey`, so an unregistered table is a compile error at the call site rather than an unscoped read.

**Nothing in this ruling touches it.** `TABLES` stays the hand-written object at [`scope.ts:40`](../../packages/db/src/scope.ts), `TableKey` stays `keyof typeof TABLES`, and the `satisfies` clause stays at [`:154`](../../packages/db/src/scope.ts). Row three of section 4 is that property watched working: a `pgTable` added to `schema.ts` and never registered compiles, changes no test, and **is refused at the call site with `TS2345` naming `ScopedTableKey`**.

**It is strengthened in one place.** Section 5 makes a third per-table list total, so after it lands the ONLY way to register a table is to write it into four places that all refuse to compile without each other. **A reading that broke this property would be decisive against itself, and this one adds to it.**

**The property is also what makes concurrency safe, which is worth saying because it reads as the opposite.** A total mapped type is a **merge-time verifier**: it checks the merged whole, not either branch. Two branches each internally complete produce a merged file that compiles **because** the clause is total. **`satisfies` is not what serialises this pair. It is what would let it be concurrent.**

### 7. The two readings this rules out, and why each fails on something other than taste

#### 7.1 Once for the estate: forbidden by two rules and not executable today

- **[ADR-003](../../CLAUDE.md) forbids it.** A scope rule is money path: [P4](../plans/P4-portal-and-site.md) marks `P4-a` and `P4-b` **YES** on the strength of [session 159](../sessions/2026-08-24-session-159.md)'s reasoning, that *"a scope rule is where 'forgot to scope' stops being available"*. **One session writing 111 tenancy rules is one money-path diff of 111 objectives**, which is the regime's central prohibition rather than a stylistic preference.
- **[E2](../../MERIT_BUILD_MASTER_PROMPT.md) forbids it in practice.** Seven money-path files are already merged on delegated authority awaiting the founder's line-by-line read. **A single pull request carrying 111 hand-argued tenancy rules makes that debt unpayable**, not merely larger.
- **[ADR-084](ADR-084.md) section 7 is the argument on correctness, and it is the strongest of the three.** That session's first suite passed **all 22 assertions** against a rule scoping `accounts` by `user_id` instead of `identity_id`, because the expectation was taken from the rule. **The defence that caught it was a person who knew the table.** A session transcribing 111 tables knows the seven it read. Auto-derivation is not the fallback either: ADR-084 section 4 measured that a mechanical FK walk returns 25 tables and is **confidently wrong on at least three**, each producing a scoped query that returns rows for the wrong identity with no error anywhere.
- **It is not executable today in any case.** Two of the 111 have no class in the four-class vocabulary (section 3), and **twelve carry a later column change** the drift assertion cannot currently read ([P4](../plans/P4-portal-and-site.md) section 5.4). A single estate-wide session runs into both on its way through.

#### 7.2 Once per phase: the unit is wrong and it buys nothing

- **Concurrency is 1.** [DELIVERY_PLAN](../DELIVERY_PLAN.md)'s phases are sequential, and within one phase [P4](../plans/P4-portal-and-site.md) already splits its thirteen tables into two slices it calls strictly serial. **Reading 2 is reading 3 with a coarser unit and the same ceiling.**
- **A phase is a scheduling unit and tenancy is a property of a table.** P4 takes `plan_versions`, which nine module plans name. The rule survives; the `why` gets argued from the marketing site's use of the table rather than from the table.
- **It cannot schedule what has no plan.** 91 tables are unscheduled and most belong to phases that do not exist as documents. **Reading 2 has nowhere to put them**, which is the same reason [P4](../plans/P4-portal-and-site.md) could name this item and not resolve it.

### 8. What this changes in [P4](../plans/P4-portal-and-site.md), stated and deliberately LEFT

**[P4](../plans/P4-portal-and-site.md) is outside this session's fence and a plan's wave structure is not a ruling session's to rewrite.** Named here so it is not discovered:

1. **Section 9's `schema.ts` / `scope.ts` row resolves.** Its *"Across phases: unresolved, and it is section 10's first item"* is answered by section 2 above.
2. **`P4-a` and `P4-b` may no longer need to be strictly serial.** Their table sets are disjoint (`plan_versions`, `rule_states`, `sessions` against ten others), and **P4's own section 8 measures `P4-b`'s ten as clean of later column changes**, so `P4-b` does not depend on `P4-a`'s drift ruling. Under this ruling they are concurrent with one loud conflict, once section 5's line lands. **`P4-a` still goes first if the two are run in sequence**, because it carries the drift ruling and section 5's precondition.
3. **Section 6's row *"The estate-wide transcription: the other 91 belong to the phases that read them"* is superseded in its second clause.** They belong to the modules that read them, registered per table, first writer wins.
4. **Ten of the ten measured transcription slices may be dispatched concurrently**, with exactly one intersecting pair (`M5-1` and `M20-a`, four wallet tables) whose second merger rebases four rows out.

**Whoever holds [P4](../plans/P4-portal-and-site.md) next makes these four edits. This entry makes none of them.**

### 9. Consequences

- **There is no roster and no holder, and that is the point.** A dispatching session computes its slice from `TABLE_KEYS` on the tree it opened. **A coordination document would be a fifth statement of a set the compiler already knows**, and it would go stale between the read and the merge exactly as the wave's fourteen fences did.
- **A session cannot know its own slice size before it runs**, because a sibling may register a shared table first. **This is stated as a cost rather than solved**: a slice of "M17's four tables, minus whatever is already registered" is a fence a session can hold and cannot pre-count. Reporting "I registered 2 of my 4, the other two were already there" is the honest form.
- **Every new table remains a diff on `scope.ts` forever**, unchanged from [ADR-084](ADR-084.md). **That is the cost and it is still the point.**
- **The four tables no module plan names** (`payment_disputes`, `affiliate_statements`, `ledger_halts`, `identity_signal_weights`) **have no session that would reach them under any of the three readings**, and this ruling does not give them one. They are unregistered, therefore unreachable, therefore safe, and they are named here so their absence is a record rather than a gap.
- **`packages/db/test/scoped-db.test.ts` becomes the pair's third file for fencing purposes**, and every transcription fence must hold it. [P4](../plans/P4-portal-and-site.md) already does this for `P4-a` and `P4-b`; ten of the fourteen measurement slices do too.
- **This entry rules NOTHING about the write accessor.** `ScopedDb` is `__brand`, `identityId` and `rows()`. Registering a table makes it readable and nothing else, which is the same boundary [P4](../plans/P4-portal-and-site.md) section 6 draws.

### 10. Alternatives considered

- **A holder document, one row per table, claimed before a session runs.** Rejected, and it is the tempting one because [ALLOCATION](ALLOCATION.md) works exactly this way for ADR numbers. **An ADR number has no representation in the tree and a registered table has one**: `TABLE_KEYS` is the registry, derived, and a second hand-maintained copy of it is section 5's defect deliberately re-committed. [ADR-034](ADR-034.md) deleted a State column for this reason and [ADR-065](ADR-065.md) T3 found it growing back as a second row.
- **Alphabetise `TABLES` and `SCOPE_RULES` so concurrent inserts land in different hunks.** Rejected. It converts some loud conflicts into clean merges, which is a **worse** outcome: the conflict is the notification. It also does nothing for the one silent hazard, which is an omission rather than a collision.
- **One file per table under `packages/db/src/schema/`.** Rejected on [ADR-043](ADR-043.md)'s own line, quoted by [ALLOCATION](ALLOCATION.md): a table split into a file per row is not a table. It would also break `TableKey` being `keyof typeof TABLES` without adding a barrel file that reintroduces the same contention.
- **Generate `scope.ts` from the DDL.** Rejected by [ADR-084](ADR-084.md) section 4, measured: the derivation returns 25 and is wrong on three, each wrong answer being a query that returns rows for the wrong identity. **The registry is declared and never derived**, and that sentence is the file's first line.
- **Rule reading 3 and stop, leaving owner and queue as P4 wrote them.** Rejected because section 1 counts it: the literal reading permits one concurrent session, which is what the ruling was asked to change.
