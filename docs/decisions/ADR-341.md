## ADR-341: the one integer that blocks the portal is one of three, the cap's value is founder-owed and its row is not landable by this repository at all, so `GET /me` keeps its refusal and the refusal is corrected instead (2026-09-05, status: proposed)

**THE DISPATCH'S FINDING REPRODUCES AND ITS HEADLINE DOES NOT.** `GET /me` is the trader portal's first call on every page load, `readMe` is refused in `apps/api/src/auth-backend.ts`, and the reason it gives is exactly true: `Me.max_accounts` has a source, has a reader, and has no row. **What is not true is that the cap is the last thing between that method and a response.** Two more fields of `Me` have a reachable row and no reader, and the row the cap needs cannot be written by anything in this tree even if a founder rules the number tomorrow.

**SO NOTHING IS WIRED AND THE ENTRY IS CORRECTED, WHICH IS THE CHEAPER OF THE TWO OUTCOMES BY A LARGE MARGIN.** A session that had taken the dispatch at its word would have written a cap row, found `GET /me` still refusing, and left the next session a discharged blocker beside an endpoint that still answers 503. That is the shape [`checkout-backend-blockers.test.ts`](../../apps/api/test/checkout-backend-blockers.test.ts) was created by, one port over, and it happened twice there before anybody wrote it down.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `341`, branch `claude/one-integer-blocks-the-portal`, session **530**.
- **NOT THE MONEY PATH BY FILE AND ADJACENT BY SUBJECT.** `git diff --stat origin/main -- packages/db scripts/db` is **EMPTY**, measured at the moment this line was written. **NO MIGRATION NUMBER IS TAKEN, RESERVED OR SPENT**, no SQL is written, no SQL is edited, no `SD-nn`, no `U-nn`, no `CV-nn`, no route behaviour changes and no response shape moves. The subject is the number that decides who may buy an account, so an **`E2` READ IS OWED** and four are inherited: [ADR-238](ADR-238.md), [ADR-252](ADR-252.md), [ADR-265](ADR-265.md) and [ADR-284](ADR-284.md), all `proposed` and all UNSIGNED.

### 2. The cap's value is founder-owed, and the derivation is the finding rather than the claim

**THE CORPUS STATES THREE NUMBERS AND NONE OF THEM IS THE ONE THIS ROW WOULD WRITE.**

| Where | What it states |
|---|---|
| Constitution 0.4 | Core EOD *"Max 10 accounts"*, Rapid *"Max 5"*, Direct *"Max 5"* |
| [M01](../plans/M01-rules-engine.md) appendix A.1, A.2, A.3 | `Maximum accounts per entity` at **10**, **5** and **5**, identical across every size, each sourced to constitution 0.4 |
| [data-model](../architecture/data-model/README.md) section 11 | the value lives at `plan_versions.rules.limits.max_accounts_per_entity`, per plan version, with no `CV-nn` and no database constraint |

**AND [ADR-238](ADR-238.md) RULING 1 REFUSES ALL THREE WAYS OF READING A PER-PLAN NUMBER AS THE PER-IDENTITY BASE**, because the cap is enforced against an identity's total live accounts across every plan (constitution B1, `INV-M3-08`, `GS-094`). **The purchased version makes the effective cap the maximum over every published version, so a buyer picks their own cap by picking a plan.** That is the whole reason a firm parameter exists, and it is also why the number a careless session would reach for is the worst of the three: **`GS-094`'s own scenario says "cap of 10", and 10 is Core EOD's plan number, which is precisely the maximum-over-versions reading the ruling names first.** A row written from it would be that refused reading, stored, approved by nobody, and quoted back to a buyer in a `409`.

**SO THERE IS NO FIRM-WIDE BASE IN THE CORPUS AND THIS ROW DOES NOT INVENT ONE.** `0074_firm_parameters.sql` already said the same sentence about itself in its own header: *"a number written here today would be a number this session invented"*. **THE VALUE IS FOUNDER-OWED AND IT IS THE BLOCKER.**

### 3. And the row is not landable by this repository even once the number is ruled, which nothing had said

**[ADR-284](ADR-284.md) BUILT A WRITE CONTROL AFTER THE BLOCKER TEXT WAS WRITTEN, AND THE BLOCKER TEXT WAS NEVER UPDATED.** `0076_firm_parameter_write_control.sql` makes a `firm_parameters` row require, at the database:

1. a `dual_control_approvals` row whose digest matches the payload (`firm_parameters_dual_control_is_real`),
2. **two distinct `owner` operators**, the operator of record and the second person who checks them, because API_CONTRACT section 8 bounds `ops` to *"no config or role changes"*,
3. an `admin_actions` row (`firm_parameters_change_is_audited`),

and `0076`'s own header **refuses to seed the operator that would satisfy any of it**: *"a real operator's identifiers are not this repository's to hold"* ([ADR-012](ADR-012.md)), and *"an invented one is a row somebody would have to remember to delete"*. It goes further and says a deployment that already wrote a cap by hand **fails this migration on purpose**.

**THE CONSEQUENCE IS A CORRECTION TO HOW THIS WORK IS DISPATCHED AND NOT ONLY TO THIS ENTRY.** The cap row is not a seed migration waiting on a number. **It is a deploy-time act through the dual-control path, and the founder owes two things rather than one: the value, and the operator directory the approval names.** A future row dispatched to "write the cap once the number is ruled" will find no migration it is allowed to write.

### 4. `Me.kyc.placement` has no reader, and the reason is an absent adapter rather than an absent decision

**THE CONTRACT MAKES IT NON-NULLABLE.** API_CONTRACT section 3 declares `kyc: { state: ...; placement: string; verified_at: string | null }`. `verified_at` beside it is nullable and an identity with no verification simply has none; **`placement` is a bare `string`, so an unverified trader still needs one and the response cannot omit it.**

**AND AN IDENTITY WITH NO VERIFICATION HAS NO FIRED TRIGGER TO REPORT.** `kyc_verifications.placement` records *"the trigger that FIRED, not the set that was configured"*, and [ADR-264](ADR-264.md) already exercised an identity with no `kyc_verifications` rows against a live fold, so the empty chain is a real and common state rather than an edge.

**THE ONE SETTLED FILL IS ALREADY WRITTEN AND IT IS NOT REACHABLE FROM HERE.** `pendingTrigger` in [`routes/kyc.ts`](../../apps/api/src/routes/kyc.ts) answers the earliest **unreached** member of the trader's own pinned trigger set, which its docblock argues is *"the moment they will actually be asked, drawn from the configuration that governs them"*. It is computed from the seven `KycGateFacts` a `KycBackend` measures, and **this deployable has no database `KycBackend` at all**: `productionKycDeps.backend` is `UNWIRED_KYC_BACKEND` and no `databaseKyc` factory exists for a wiring slice to install.

**SO WRITING A SECOND FILL INSIDE `auth-backend.ts` IS REFUSED, AND NOT ON SIZE.** `effectiveTriggers` applies the firing order and `INV-M19-02`'s imposed member, and `kyc.ts` says in its own words that a second ordering there *"would be a second statement of one ruling"*. The same sentence binds a third statement written one directory up, in the file least likely to be read beside the first. **This is the same class of hazard ADR-092 section 5 names on the money path, arriving on a read.**

### 5. `Me.accounts_count` has one reader and no producer, and what it needs is a ruling

**THE FIELD IS NOT HARD, IT IS UNRULED**, and those are different absences with the same symptom. `accounts` is `owned` on `identity_id`, so a count over the scoped rows is one statement. **What nobody has written down is WHICH accounts count.**

`account_status` (`0001`) declares **seven** members: `provisioning_pending`, `active`, `breached`, `expired`, `closed_admin`, `closed_chargeback`, `graduated`. **The corpus never says which of them are live for cap purposes.** `AccountCapRow.liveAccounts` is declared *"Live accounts this IDENTITY holds"* in [`routes/checkout.ts`](../../apps/api/src/routes/checkout.ts) and **nothing in this tree produces the number**; the field is declared, compared twice, and never written. **[ADR-238](ADR-238.md)'s own approval block registered exactly this and it is still true:** *"no implementation of `accountCap` exists to confirm it"*.

**TWO MEMBERS ARE WHERE A READER WOULD DISAGREE AND THEY ARE NAMED RATHER THAN GUESSED.** `graduated` is an account that reached the live ladder's end, and `provisioning_pending` is an account that has been sold and not yet created. **[ADR-260](ADR-260.md) already refused to widen an engine union to make a map total rather than deciding what a half-provisioned account is worth to a rule**, and the same refusal binds a cap the account is counted against: a session that folded either member in or out would be deciding, in a projection nobody reads twice, how much exposure one buyer may accumulate.

### 6. What is landed, and why the correction is the deliverable

**THE BLOCKER TEXT IS CORRECTED AND THE CORRECTED SENTENCE IS KEPT BESIDE ITS CORRECTION.** That is `RI-14`'s property applied to an entry `RI-14` does not read: the clause that misled is *"every other field of `Me` is reachable through the scoped door"*, it is **TRUE about the door** (`users`, `accounts`, `kycVerifications`, `identityPhones`, `affiliates` and `identityRestrictionEpisodes` are all `owned`, `identities` is `root`), and deleting it would leave the next reader free to write it again. **It stays, and REACHABLE IS NOT RESOLVABLE stays beside it.**

**AND THE THREE ABSENCES ARE RUN RATHER THAN DESCRIBED.** [`apps/api/test/me-blockers.test.ts`](../../apps/api/test/me-blockers.test.ts) is thirteen cases, each reading the file its clause is a fact about, and two of them EXECUTE a value rather than reading text: the port's refusal, asserted to open no door, and the identity of the installed `KycBackend`. **The day any of the three closes, the case for it turns red and the session that closed it is the one holding the entry**, which is `wiring.test.ts`'s liability-that-expires idiom applied one level down, at a METHOD rather than at a port.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING OWED IS THE NUMBER, AND IT IS THE ONLY THING ON THIS PAGE NO ENGINEERING SESSION CAN SUPPLY.** How many live accounts may one resolved identity hold across every plan? The corpus offers 10, 5 and 5 and each belongs to a plan; the base belongs to the firm. **A second thing is owed with it and is easy to miss: the operator directory.** `0076` will not accept a cap approved by a name in no directory, and it refuses to seed one, so the number and the two `owner` operators who approve it arrive together or not at all.

  **THE SECOND QUESTION IS WHETHER SECTION 5's ANSWER IS A RULING OR A LOOKUP.** I have said `accounts_count` needs a ruling because `account_status` has seven members and no document says which are live. A founder may reasonably answer that it is obvious: everything except the three closed states. **I did not take that answer because `provisioning_pending` and `graduated` are not obvious in the same direction** and because the number bounds exposure. **If it is a lookup, this section is a ceremony around a five-minute decision and should be read as one.**

  **THE THIRD IS WHETHER CORRECTING AN ENTRY IS A DELIVERABLE.** This row produces no wired method and no served endpoint. Its output is a more accurate refusal and thirteen cases that keep it accurate. **The argument for it is that the alternative was measured and is worse**: a cap row landed against a blocker that named one absence would have left `GET /me` refusing with a discharged reason on it, and that exact failure has happened twice on `useCheckoutBackend`. **The argument against it is that a founder dispatched this row to unblock a portal and it is being handed a longer list.**

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **My claim that nothing writes a `firm_parameters` or an `operators` row rests on a regex over two `src` trees at one instant**, and a writer built out of a computed table key would pass it. I believe there is none because `packages/db`'s keyed accessor takes the key as a literal in every call site in this tree, but I did not prove that, and it is the weakest assertion in [`me-blockers.test.ts`](../../apps/api/test/me-blockers.test.ts). **The second weakest is section 4's reading of `placement`.** I have taken "non-nullable in the contract" as binding on a response nobody serves yet, and a founder could rule that the field is nullable in practice and that the frozen declaration is the thing that is wrong. **That would discharge section 4 entirely and it is a ruling I am not entitled to take.**
