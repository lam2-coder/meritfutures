### 3. THE RULING

#### Clause 1. A wallet-funded purchase is a purchase with no processor, and the columns are ABSENT rather than unknown

`psp` is *"which MID took it"* ([DATA_MODEL `purchases`](../architecture/data-model/purchases.md)) and `psp_reference` is that processor's own reference for the payment. On the wallet path no MID took it and no processor issued a reference, because no processor was called: `payment_method = 'wallet'` requires `wallet_debit_cents = amount_paid_cents` (`purchases_wallet_leg_matches_method`), so the whole price is paid by an `LT-08` posting inside the checkout transaction, and [`checkout.ts`](../../apps/api/src/routes/checkout.ts)'s wallet arm never reaches `cardLegOf` at all.

**The alternative is the one the schema currently forces and it is worse than the defect.** Writing `'psp_a'` and a minted string onto a row that reached no processor is the state `FM-M3-01` pages on wearing a wallet purchase's clothes, and it is precisely what `SD-M3-06` exists to make unrepresentable: *"without an explicit method the wallet path is indistinguishable from a PSP purchase whose webhook never arrived"*. Finding 1 measured that row **ACCEPTED** today. So both columns become nullable.

**`0006`'s CHECK on `psp` survives and is not restated.** `purchases_psp_check` is a separate constraint from the NOT NULL, confirmed at the catalogue after `0081` applies, so it goes on refusing any string outside `('psp_a','psp_b')` for every row that names one. It admits NULL because `NULL IN (...)` is NULL and a CHECK that evaluates to NULL admits the row, which is the identical composition [ADR-322](ADR-322.md) relies on for `wallet_entries.provenance`. **The processor vocabulary is therefore still written down exactly once**, in `0006`, which is [ADR-216](ADR-216.md)'s refused copy.

#### Clause 2. The constraint is a total `CASE` keyed on `payment_method`, and both alternatives are strictly weaker

```sql
ALTER TABLE purchases
  ADD CONSTRAINT purchases_processor_columns_follow_method CHECK (
    CASE payment_method
      WHEN 'psp'    THEN psp IS NOT NULL AND psp_reference IS NOT NULL
      WHEN 'mixed'  THEN psp IS NOT NULL AND psp_reference IS NOT NULL
      WHEN 'wallet' THEN psp IS NULL     AND psp_reference IS NULL
      ELSE false
    END
  );
```

**`payment_method` IS THE DISCRIMINATOR, and the dispatch asked which is better.** The alternative is to key on the presence of the columns, `CHECK ((psp IS NULL) = (psp_reference IS NULL))`, which states only that the two AGREE. That is strictly weaker in both directions and it admits the two rows this repair exists to refuse: a `payment_method = 'wallet'` row naming `psp_a` and a minted reference, which is the row measured ACCEPTED in finding 1; and a `payment_method = 'psp'` row naming no processor, a purchase that claims a card took it and records none. **Keying on the method refuses both AND implies the agreement**, because every branch names both columns, so the presence-keyed spelling buys nothing the method-keyed one does not already have.

**It is also the table's own idiom rather than a new one.** `purchases_wallet_leg_matches_method` ([`0006:190`](../../packages/db/migrations/0006_commerce.sql)) already keys the wallet CENTS on `payment_method`; this keys the wallet PROCESSOR COLUMNS on the same discriminator, and [DATA_MODEL](../architecture/data-model/purchases.md)'s note that the wallet constraints *"together make a wallet purchase that looks like a stalled PSP purchase **unrepresentable**"* is what they are together for.

**A TOTAL `CASE` AND NOT A DISJUNCTION, WHICH IS [ADR-322](ADR-322.md)'s FINDING APPLIED RATHER THAN REDISCOVERED.** The natural spelling is a disjunction over columns that are now NULLABLE, and any branch reading a NULL column can evaluate to NULL: `NULL OR FALSE` is NULL and **a CHECK that returns NULL ADMITS THE ROW**. Every branch above returns `IS NULL` or `IS NOT NULL`, which are total, so no branch can return NULL and no row is admitted by vacuity. `REJECTION 3` in the probe is what would go red if somebody ever simplified it back.

**`ELSE false` is not reachable today and is not decoration.** `payment_method`'s own CHECK closes it at three members; a fourth added by a later migration is refused here until somebody rules whether that method calls a processor, rather than admitted by falling off the end of the `CASE` as NULL.

#### Clause 3. The idempotency anchor stays exactly as `0006` built it, and NULL distinctness is the right answer rather than a tolerated one

`purchases_psp_reference_uq ON purchases (psp, psp_reference)` is now a unique index over two nullable columns. In PostgreSQL a btree unique index treats NULLs as **DISTINCT** unless built `NULLS NOT DISTINCT`, so `(NULL, NULL)` collides with nothing, including with another wallet row.

**THAT IS CORRECT, AND THE REASON IS ASSERTED RATHER THAN ASSUMED.** The anchor defeats a duplicate WEBHOOK (finding 7), and a webhook is a processor's statement about a payment. **A wallet purchase reached no processor, so no processor can ever make a statement about it and there is no delivery to deduplicate.** M03's matcher looks the row up by `(psp, psp_reference)` with a `psp` drawn from the closed vocabulary, and SQL equality with NULL is never true, so **wallet rows are invisible to that matcher by construction**, which is exactly what they should be. Their own idempotency is `INV-M3-13`: the row is `'paid'` in the transaction that creates it, so there is no second arrival at all.

**A PARTIAL INDEX WAS CONSIDERED AND REFUSED, and the dispatch asked for the reason.** `CREATE UNIQUE INDEX ... WHERE psp IS NOT NULL` admits and refuses **exactly** the same rows as the index already on the table: a row with a NULL `psp` is unconstrained under the partial index because it is not in it, and unconstrained under the full index because its key is distinct from every other. So it is a pure RESTATEMENT of clause 2's CHECK, in a second vocabulary, with nothing keeping the two in step, which is [ADR-216](ADR-216.md)'s refused copy again. Its cost is not zero either: it means dropping and recreating the one object `0006` names as the anchor, and a `CREATE INDEX` that lost the word `UNIQUE` in that rewrite behaves identically to the anchor until the first duplicate webhook arrives.

**What the partial index WOULD have bought is named rather than waved away, and it is bought another way.** It would be immune to a later `NULLS NOT DISTINCT` rebuild of this index, which would permit exactly ONE wallet purchase in the entire table and fail on the second, silently. That hazard is real, so `ACCEPTANCE 2` in [`probe_purchase_processor_columns.sql`](../../scripts/db/probe_purchase_processor_columns.sql) writes a SECOND wallet purchase and requires it to commit, and `REJECTION 8` reads `pg_index.indnullsnotdistinct`, `indisunique` and `indpred` from the catalogue. **An assertion catches the `NOT NULL` coming back as well, which a partial index would not.** What `0081` adds instead of an index is a `COMMENT ON INDEX` that says all of this at the object.

#### Clause 4. `'mixed'` names a processor, and that is a ruling this file had to make

A total `CASE` has to answer for all three members. `ELSE false` on `'mixed'` would make the method unwritable, which is a NEW refusal the defect does not force and which would foreclose the ruling [`checkout.ts`](../../apps/api/src/routes/checkout.ts) item 5 says is owed. **The answer follows from the cents constraint rather than from taste**: `purchases_wallet_leg_matches_method` requires `wallet_debit_cents < amount_paid_cents` under `'mixed'`, so there is a card remainder, so a processor took part of it and issued a reference for that part. `'mixed'` is grouped with `'psp'`.

It is written as its own `WHEN` branch with the same body rather than folded into one `IN`, so the ruling is visible at the member it rules. Nothing writes a `'mixed'` purchase today: `checkout.ts`'s `refuseMixed` declines the method by name.

### 5. What this means for `checkout.ts`, in one paragraph

### Approval

**Status: `proposed`. The approval line is UNSIGNED and merging is not signing.** No `status` field anywhere moves and nothing is marked `accepted`. **`E2` READ OWED**, and one is inherited: [ADR-322](ADR-322.md) is `proposed` and UNSIGNED, is this branch's base, and is the entry this one reuses the `CASE`-not-disjunction finding from.

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO CHECK IS THE ONE NO GATE CAN: THAT A WALLET-FUNDED PURCHASE SHOULD LEAVE THE PROCESSOR COLUMNS EMPTY RATHER THAN SAY SOMETHING.** Every gate in this diff can tell you the constraint refuses what it must and admits what it must. **None of them can tell you that a reconciliation between Merit's books and a processor's settlement report should simply not see these rows.** That is what clause 1 means operationally, and it is the kind of thing a founder overrules. The counter-case is real: an operator asking "what did we sell yesterday" against `(psp, psp_reference)` now gets an answer that silently omits every wallet sale, and the money is real money even though no card touched it. This ruling says the discriminator for that query is `payment_method` and always was, and `purchases_wallet_leg_matches_method` already assumed as much. **If you would rather a wallet row carried a Merit-minted reference in some third namespace, say so now**: that is a different column, not a different CHECK, and it gets an order of magnitude more expensive after the first checkout backend is installed.

  **THE SECOND IS CLAUSE 3, AND IT IS THE CLOSEST CALL IN THE FILE.** The webhook idempotency anchor is now a unique index over two nullable columns, and the thing that makes wallet rows not collide with each other is PostgreSQL's default that NULLs are distinct. **That is a load-bearing property of a money-path object being carried by a default nobody wrote down**, and the honest description of what this entry did is: it declined to state the rule in the index, on the grounds that a partial index would be a second copy of the CHECK, and bought an assertion instead. `ACCEPTANCE 2` and `REJECTION 8` are that assertion. **A reader who thinks the anchor should say `WHERE psp IS NOT NULL` in its own definition is not wrong**, and the cost of ruling the other way is one more migration that drops and recreates the index, not a rewrite of this one. It is worth a minute because the failure mode of getting it wrong is silent and total: a `NULLS NOT DISTINCT` rebuild caps Merit at one wallet-funded purchase for all time.

  **THE THIRD IS CLAUSE 4, WHICH DECIDES SOMETHING ABOUT A FEATURE NOBODY HAS BUILT.** `'mixed'` is refused by `checkout.ts` and has no code path, and this constraint nonetheless rules that a mixed purchase must name a processor. The reasoning is mechanical rather than aesthetic, `purchases_wallet_leg_matches_method` leaves a card remainder under `'mixed'`, but a total `CASE` forced an answer and this is it. **If the eventual mixed design wants to record the card leg somewhere other than these two columns, this constraint is in its way** and the session that builds it will meet a refusal rather than a blank column. Ruling it the other way now is a smaller change than ruling it later.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** Finding 5 says nothing writes a `purchases` row, which is what lets this constraint be made exact with no backfill and no migration risk. **It is also what means nobody has ever exercised any constraint on this table outside a probe.** If a checkout backend is installed and the first real wallet purchase is refused, the cause will be a column this constraint requires that the handler does not set, and the only place that would have been caught earlier is a probe written from the handler's own insert rather than from the DDL. This file's probe was written from the DDL.
