## ADR-231: The public lookup door, and the enumeration control it rests on is asserted by the corpus and enforced by nothing  (2026-08-29, status: proposed)

**`GET /verify/:code` is the page a funded trader shows the world and it answered `503`, because the scope system had no word for what it does.** [`certificates`](../../packages/db/migrations/0020_public_surface.sql) is scope class `owned` on `identity_id` ([`scope.ts:858`](../../packages/db/src/scope.ts)), and the route is unauthenticated: `db.scoped` has no identity to open with, and `db.firm` refuses the key at compile time because `FirmTableKey` is every key whose class is `firm` ([`scope.ts:1473`](../../packages/db/src/scope.ts)). **That is not a defect in the registry.** The class answers WHO OWNS A ROW and it answers it correctly; what did not exist is a separate answer to WHAT AN UNAUTHENTICATED CALLER MAY ADDRESS A ROW BY.

**The ruling is a fifth door with a `(table, column)` vocabulary**, taken on [`resolutionDb`](../../packages/db/src/scoped-db.ts)'s own shape one door along. `PUBLIC_LOOKUP_ADDRESS` is `{ certificates: ['code'] }` ([`scoped-db.ts:1697`](../../packages/db/src/scoped-db.ts)); the handle is read only, non-transactional, one row, one table, one column, its brand disjoint from the other four, and it has no `transaction` overload, so a caller who has proved nothing reaches no write at any authority. **The route serves a real row today.**

**And the finding is worth more than the route.** The vocabulary's safety is one sentence: a member of that list asserts that the named column CANNOT BE GUESSED. `INV-M11-05` fixes `certificates.code` at *"128 bits of entropy, no sequence"* ([M11:54](../plans/M11-certificates-social-proof.md)), and **nothing in this repository enforces it or ever could today**: the column is `text NOT NULL` with no length bound and no alphabet bound ([`0020:125`](../../packages/db/migrations/0020_public_surface.sql)), the table's three `CHECK` constraints are about payout kind, revocation completeness and deferral, and **nothing in this tree issues a certificate at all**, so there is no minter to hold the invariant instead. Section 6.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `231`, session **421**, dispatched as `claude/verify-goes-live`. **NO MIGRATION NUMBER WAS RESERVED AND NONE IS TAKEN**, which is section 6.4's whole difficulty.

- **NOT THE MONEY PATH, AND IT IS A PUBLIC ORACLE OVER MERIT'S OWN PAYOUT BOOK.** Ships `proposed` with an **UNSIGNED** approval line. `E2` is not owed on a read that moves no money; the approval block names three things this entry cannot decide, and the first of them is section 6.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the door reaches `certificates` by `code` and refuses every other table and column, that the route answers `200` with a real row over the real adapter, and that seven seeded defects turn it red is **MEASURED**, in section 7. That nothing issues a certificate, that no rate limiter exists in this tree, and that `certificates.code` carries no DDL bound is **DERIVED** by search, at the scope each claim names. What is **JUDGED** is that the vocabulary belongs beside `RESOLUTION_ADDRESS` rather than on the scope registry (section 4.2), that resolving the identity from the code is worse rather than cheaper (section 4.3), and that an unkeyed digest is the right choice for `code_hash` exactly as long as section 6 is wrong (section 5.2).

### 2. The ruling

**A fifth door, `db.publicLookup`.** Read only, non-transactional, one row of one table at one declared column.

| | |
|---|---|
| **The vocabulary** | `PUBLIC_LOOKUP_ADDRESS = { certificates: ['code'] }` ([`scoped-db.ts:1697`](../../packages/db/src/scoped-db.ts)) |
| **The type** | `PubliclyLookedUpTableKey` ([`:1688`](../../packages/db/src/scoped-db.ts)). A table outside it is `TS2345`; a column outside it is `TS2353` |
| **The run-time guard** | `refusePublicAddress` refuses an undeclared TABLE by name, a column outside the list by name, and an address that omits the declared column. The fold to `schema.ts` then proves the database bounds it to one row |
| **The handle** | `PublicLookupDb` ([`:1766`](../../packages/db/src/scoped-db.ts)), brand disjoint from `ScopedDb`, `SystemDb`, `FirmDb` and `ResolutionDb` |
| **What it cannot do** | There is no `transaction(publicLookupDb(), ...)` overload, so it composes into nothing and writes nothing |

**The scope registry is untouched.** `certificates` is still `owned` and still owned by the trader whose row it is. **This matters for a second reason and it is stated here rather than left to be inferred:** [`scope.ts`](../../packages/db/src/scope.ts) is also session **420**'s file, for the `pair` write `POST /checkout` needs. **The two doors were ruled separately and this one needed no line of that file**, which is a consequence of putting the vocabulary beside `RESOLUTION_ADDRESS` rather than on the registry and is one of the reasons section 4.2 chose that.

### 3. The transcription repair the door found

**`{ code }` was not an address the accessor would accept, and the reason was a spelling.** [`0020:177`](../../packages/db/migrations/0020_public_surface.sql) declares the key as a separate `CREATE UNIQUE INDEX certificates_code_uq ON certificates (code)`, and `uniqueKeys()` reads `schema.ts` through drizzle's `getTableConfig`, which sees an inline `.unique()`, a table-level `primaryKey`, a table-level unique constraint, and **not** a separately declared index. So `certificates.code` sat in the set [`keyed-accessor.test.ts`](../../packages/db/test/keyed-accessor.test.ts) already measures as *"the keys the migrations declare and `schema.ts` does not"*, and `refuseUnaddressed` refused `{ code }` as a predicate that *"can match more than one row"*.

**The database has bounded it to one row since `0020`. Only the transcription did not say so.** `schema.ts` now carries `.unique('certificates_code_uq')`, which that suite's first case checks against the migrations in the direction that matters: a key `schema.ts` claims must be a real one. **No migration was written and none was needed**; nothing in this workspace generates SQL from `schema.ts` and `drizzle-kit generate` is permanently foreclosed.

### 4. What was refused

#### 4.1 A `db.public` that took a table list and not a column list

**`certificates` declares TWO unique keys and only one of them may be public.** [`0020`](../../packages/db/migrations/0020_public_surface.sql) keeps `code` distinct from `id` *"so the public token can be ROTATED AFTER AN INCIDENT"*, and a door that admitted `id` would hand a holder who kept the immutable key a way to correlate the certificate after the token they were told to forget had changed. **That is `RESOLUTION_ADDRESS`'s own objection to `users.id` arriving one table along**, and it is why the vocabulary is two-part. Watched: `past('certificates', { id })` throws, and the case asserts in the same breath that `id` IS a unique key, so the refusal is the vocabulary's and not the fold's.

#### 4.2 A per-table opt-in declared on the scope registry beside the class

**Refused on three grounds.**

1. **It answers a different question.** `SCOPE_RULES` says who owns a row. A public-readability flag says what a stranger may address it by. One table with two vocabularies is how the next reader takes the class as licence.
2. **A flag is the wrong shape**, by 4.1: the useful unit is the COLUMN, and a class-adjacent flag naturally reads as a property of the table.
3. **Blast radius.** `SCOPE_RULES` is read by `FirmTableKey`, `PairTableKey` and `ScopedTableKey`, so a mistake there is estate-wide, and the registry is under concurrent edit by session **420**. Section 2.

#### 4.3 Resolving the identity FROM the code and then opening `db.scoped`

**The dispatch called this the least new machinery and it is not less machinery at all.** To learn `identity_id` from a code you must read `certificates` addressed by `code` for a caller with no identity, which is exactly the read that had no door. **So this design needs everything above, plus a second round trip.** What the second trip buys is the objection:

- **`db.scoped(identityId)` is an authority over EVERY `owned` and `derived` table that identity has** at seven verbs, `payout_requests`, `accounts`, `wallet_entries` and `kyc_verifications` among them. Handing it to an unauthenticated handler in exchange for one column of one row it already held makes the blast radius of any future edit in that handler the trader's whole book. `db.publicLookup` reaches one table at one column, forever, by type.
- **"The code is what authorises" is not a property it buys.** In the door as built, the code is literally the entire predicate: there is no tenancy conjunct and no second address.
- **It gives `null` two meanings.** No row with that code, or a row whose identity did not match the scope opened with it. `INV-M11-03`'s `unknown` is a claim about Merit's book and needs exactly one.
- **It puts a second round trip inside `INV-M11-05`'s constant-time floor**, widening the variance the floor has to dominate for nothing.

**Watched:** the adapter case asserts the recorded call list contains no `scoped` door and that no call carries an `identityId`, so this design failing back in is a red test naming it.

#### 4.4 A shape check on `:code` in the handler

**Already ruled and not reopened.** [`verify.ts`](../../apps/api/src/routes/verify.ts)'s handler docblock and ADR-170 foreclosure 3: a token of the wrong length or alphabet answers `unknown` at the same floor, because a check that short-circuited ahead of the lookup would hand an attacker the token's alphabet and length for free. **It was re-examined rather than assumed, since the floor would in fact dominate a refusal placed inside the lookup**, and it is still refused: it defends nothing, because an attacker guessing short codes learns nothing either way, and it would read as an answer to section 6 while changing no code that gets minted.

### 5. The three arms, as built

#### 5.1 `lookup`, through the new door

`db.publicLookup(px => px.rowAt('certificates', { code }))`. The row comes back WHOLE, `revoked_reason` and `identity_id` included, because a door cannot project and a projection is a statement about what one caller renders. **The withholding is `toVerifyRow`'s and it is structural**: the response is rebuilt field by field, so a column added to that table tomorrow cannot ride out onto the public page. The `undefined`/`null` translation is the adapter's, because the handler's `null` is `INV-M11-03`'s claim about Merit's book.

#### 5.2 `record`, through the firm door, and the digest is this entry's choice

`db.firm(tx => tx.insert('certificateVerifications', ...))`. [`0025`](../../packages/db/migrations/0025_reserved_sequence.sql) requires `code_hash` and `ip_hash` to be digests and **names no algorithm**, so one had to be chosen here. **SHA-256, unkeyed**, on [`idempotency.ts`](../../apps/api/src/idempotency.ts)'s precedent, because a second algorithm in one deployable is a vocabulary nothing shares.

**It is unkeyed where [`auth-backend.ts`](../../apps/api/src/auth-backend.ts)'s OTP digest is HMAC, and the difference is the input.** That digest keys because an OTP is six digits and a dump of unkeyed digests is a rainbow table; this one is taken over a token `INV-M11-05` fixes at 128 bits, where a preimage search is the same search as guessing the code. **THAT ARGUMENT IS EXACTLY AS STRONG AS SECTION 6 SAYS IT IS.** `0025`'s own reason for hashing is that storing codes in the clear *"would make this table a list of valid tokens for anyone who reached it"*, and against a walkable code space an unkeyed digest is that list with one step added. **A keyed digest is the remedy if section 6 resolves the wrong way, and it is named here rather than taken, because keying it today would add a required secret and a second unconfigured-refusal path to defend a property that is either fine or broken at the mint.**

`ip_hash` is `NULL` and never a digest of the empty string when the address was not observed, because one shared bucket for every such row is worse than a null in a table whose signal is a rate across sources. `user_agent_class` is not sent at all: the column's comment is *"a class, never the string"* and no approved document enumerates the classes.

#### 5.3 `presentation`, from the environment, with nothing defaulted

Seven variables, `MERIT_VERIFY_STATEMENT_*` (five), `MERIT_VERIFY_DISCLOSURE` and `MERIT_VERIFY_FLOOR_MS` ([`verify.ts:684`](../../apps/api/src/routes/verify.ts)). **Seven and not one JSON blob**, so a deployment that forgot the `account_enforced` sentence is told which sentence it forgot. **An unset variable is a refusal and never a default**, which is ADR-226's shape for an absent Turnstile secret; the refusal is read BEFORE the lookup, so it is identical for every code and holds no information about any of them.

**`INV-M11-03`'s unknown wording is NOT among them.** It is fixed in the module, so no deployment can override *"no certificate with this code"* into *"this is fake"*. **No upper bound is invented on the floor**: ADR-170 section 4.2 rules it a MEASURED p99 the deployment owes, and a ceiling written here would be this route choosing a latency budget the corpus has not chosen. The measurement remains owed.

### 6. THE FINDING: the enumeration control is asserted by the corpus and enforced by nothing

#### 6.1 What the corpus commits to

`INV-M11-05`: *"Certificate codes are unguessable ... 128 bits of entropy, no sequence"* ([M11:54](../plans/M11-certificates-social-proof.md)). M11 section 9: *"128 bits of entropy, no sequence, no structure ... The code space is not walkable, which makes the attack infeasible rather than merely rate limited"* ([M11:246](../plans/M11-certificates-social-proof.md)). [`API_CONTRACT:1473`](../architecture/API_CONTRACT.md) puts it beyond doubt for this endpoint: *"The catalog's 600/minute/IP is an enumeration budget on a 128-bit token and is deliberately not inherited here"*. **The entropy is the primary control and the corpus says so.**

#### 6.2 What this tree enforces, derived by search over `apps`, `packages`, `e2e` and `scripts`

| Leg of the control | State |
|---|---|
| **Entropy of the code** | **NOT ENFORCED ANYWHERE.** `certificates.code` is `text NOT NULL` ([`0020:125`](../../packages/db/migrations/0020_public_surface.sql)) with one unique index and no `CHECK`. The table declares three `CHECK` constraints and none names `code`. A row with `code = '1'` inserts today |
| **A minter** | **DOES NOT EXIST.** `grep -rIn "insert('certificates'\|INSERT INTO certificates"` over those four directories returns **nothing, exit 1**, and so does a search for `certificateCode`, `certificate_code`, `mintCode` and `issueCertificate`. **Nothing in this repository issues a certificate**, so there is nowhere the 128 bits could be being applied |
| **The rate limit** | **DOES NOT EXIST.** [`API_CONTRACT:1473`](../architecture/API_CONTRACT.md) rows it per IP and per ASN and says the limits are *"data rather than prose"*. `grep -rIn "fastify-rate-limit\|rateLimit(\|RateLimiter\|tokenBucket\|leakyBucket"` over `apps` and `packages` returns **one hit, an unrelated identity-signal fixture**. `apps/api` declares exactly one runtime dependency, `fastify` |
| **The anomaly signal** | **LIVE AS OF THIS ENTRY.** Every lookup writes `certificate_verifications`, including the unknown and the malformed, and a rejected write fails the request rather than serving it unmetered. **It is the first of the three legs to become real** |

**Two live files describe the first leg as a property this system has.** [`certificates.ts:154`](../../apps/api/src/routes/certificates.ts): *"The enumeration control here is three things: the 128-bit code with no sequence"*. [`verify.ts`](../../apps/api/src/routes/verify.ts)'s header: *"a 128-bit guess that hit"*. **Neither sentence is false about the specification and both read as facts about the deployment.**

#### 6.3 What that means for the route this entry ships

**The route is safe to serve now, and the reason is not reassuring: there is nothing to enumerate.** No certificate exists in any deployment of this tree, because nothing issues one. **What must not happen is that the issuer lands without the mint**, at which point a walkable code space would put Merit's whole payout book behind a public endpoint with no rate limit and only an after-the-fact anomaly counter, which is `AS-M11-04` and `FM-M11-04` exactly as written.

**The ORDER is the ruling this entry can make and does:** the slice that first writes a `certificates` row owes the 128-bit mint in the same slice, and the DDL bound owes a migration whoever gets there first.

#### 6.4 Why the fix is not in this pull request, said plainly

**The dispatch asked for it here and the fence does not carry it, and the fence wins.** Row `231`'s fence is `packages/db/src/**` and `packages/db/test/**`; unlike rows `230` and `232` it does **not** name `packages/db/migrations/**` and it reserves no migration number. A `CHECK` on `certificates.code` is a migration. **Widening a fence to finish is the move this session was told not to make**, and taking an unreserved number is the collision [ADR-034](ADR-034.md) exists to prevent. The other named fix, a rate limit, is a slice of its own: nothing in this tree limits anything, and the corpus wants it keyed per ASN.

**What IS in this pull request is the gap pinned as a red light.** [`public-lookup.test.ts`](../../packages/db/test/public-lookup.test.ts)'s last case reads `0020` and asserts that `code` is `text NOT NULL` under a unique index, that the table's three `CHECK` constraints are the three that exist, and that neither a `length(code)` bound nor a `code ~` alphabet bound is among them. **The day a migration adds one, that case goes red and sends the reader here.** It is [`wiring.test.ts`](../../apps/api/test/wiring.test.ts)'s liability-that-expires shape applied to a column.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS SECTION 6, AND IT IS WORTH MORE THAN THE ROUTE.** The corpus says certificate codes carry 128 bits of entropy and that the entropy is the primary enumeration control, and this tree enforces that nowhere: no DDL bound on the column, no minter, no issuer, and no rate limit either. **Today that is harmless, because no certificate exists.** The decision is what must be true before the first one does, and this entry's answer is that the issuance slice owes the mint in the same slice and a migration owes the column a `CHECK`. **If you would rather the `CHECK` land first, on its own, before anything can write a weak code**, that is a small session and it is the safer order; this one could not take it, because row `231` reserved no migration number and widening a fence to finish is the move it forbade.

  **THE SECOND IS WHETHER A `(table, column)` ALLOW-LIST IS THE VOCABULARY YOU WANT THE ESTATE TO HAVE.** It is now a second closed list beside `RESOLUTION_ADDRESS`, and both grant a read to a caller who has proved nothing. **What makes them safe is different in each case and the difference is worth holding**: the resolution door is safe because a caller learns only whether an address exists, and this one is safe only because the address IS a secret. **A future member added to this list by someone who read the shape and not the reason is the failure mode**, which is why the docblock states the assertion a member owes and why the suite fails on the vocabulary changing at all.

  **THE THIRD IS THE ONE THING HERE THAT IS PURELY THIS ENTRY'S TASTE.** `code_hash` is an UNKEYED SHA-256 (section 5.2), and its whole justification is the 128 bits section 6 says nothing enforces. **If section 6 resolves the wrong way, that table becomes a rainbow-table target**, and the remedy is an HMAC under a deployment secret, which costs a required variable and a second refusal path. **It is named rather than taken because keying it today defends a property that is either fine or broken at the mint**, and the mint is where the decision actually belongs.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The door is narrow by type and wide by row.** `rowAt` returns every column of `certificates`, `identity_id` and the internal `revoked_reason` included, and the only thing between those and the public page is `toVerifyRow` rebuilding the response field by field. **A door that could project would be strictly better and it is not what was built**, because a projection is a statement about what one caller renders and would have to be re-argued at every future member of the vocabulary. The residual risk is real and it is one file wide: an edit to `verify.ts` that spread the row instead of rebuilding it would publish a trader's identity uuid, and the suite asserts against exactly that on a revoked row.
