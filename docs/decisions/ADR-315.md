## ADR-315: a handle that names nothing. The sweep's adapter sentence named a member `ExpiryTx` does not have, and the member is unreachable rather than merely unwanted  (2026-09-04, status: proposed)

**The hourly expiry sweep's I/O boundary specified its own ledger adapter, in the docblock directly above the port that declares it, as `postTransaction(tx.ledger, await readChart(tx.ledger), lt01(values))`. `tx.ledger` named nothing.** `ExpiryTx` ([`ports.ts:157`](../../apps/worker/src/sweeps/ports.ts)) declares `rowsWhere`, `lockAt` and `updateAt` and no ledger handle, and `EXPIRY_TABLES` ([`ports.ts:83`](../../apps/worker/src/sweeps/ports.ts)) is `['payoutRequests', 'walletWithdrawals']`, which excludes both ledger keys **deliberately** and says so ([`ports.ts:76-78`](../../apps/worker/src/sweeps/ports.ts)). **So the file said two things and neither was reachable from the other**, and a session sent at `postLt01` would have met the disagreement before it wrote a line.

**THE SENTENCE IS RULED WRONG AND THE PORT IS RULED RIGHT.** The three members stand, `EXPIRY_TABLES` is unchanged, and the `LedgerTx` stays in the wiring, recovered by the IDENTITY of the `ExpiryTx` `postLt01` is handed rather than read off it as a member. **The member is not refused on taste. It is unreachable**, for three reasons stated in section 3, and the first of them is that this file cannot NAME `LedgerTx` at all.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `315`, branch `claude/a-handle-that-names-nothing`. [ADR-305](ADR-305.md) section 7 slice 3, its `F3`.

- **MONEY PATH, `E2` READ OWED.** The diff moves no executable line: what lands under `apps/worker/src` is a docblock, and what lands under `apps/worker/test` is five cases. **No cents are arithmetic'd anywhere in this row, no migration is written, no number is reserved, no `RI-nn` is minted, and no `package.json` is edited.** What it decides is the shape a posting on the release path will take, which is why it is read as money path anyway.

- **NOTHING IS WIRED AND THE WIRED COUNT DOES NOT MOVE.** `postLt01` still has no adapter; it is [ADR-305](ADR-305.md) section 7 slice 6 that builds one, and that slice is blocked on this row and on slice 2, which is not in this wave.

### 2. The constraint, which is why a second handle is not the answer

[ADR-006](ADR-006.md) requires the posting to commit in the **same transaction** as the state change that caused it. `packages/ledger` relies on that rather than restating it, which is why `postTransaction` ([`post.ts:126`](../../packages/ledger/src/post.ts)) takes the caller's open transaction as its first argument with no overload that omits it. And `0057`'s `DEFERRED` note puts the same sentence in the schema's own words at [`:104`](../../packages/db/migrations/0057_terminal_withdrawal_obligation.sql): *"ADR-006's consequence: a posting commits in the SAME transaction as the state change that caused it."*

**[ADR-305](ADR-305.md) cites that sentence as `0057`'s header item 3 and it is not in the header.** It is item 3 of that file's *SEVEN THINGS THAT NEED THE LINE-BY-LINE READ*, which is a `DEFERRED` note about a constraint trigger. **The sentence is real and the pointer to it was loose**, so this entry cites where it actually found it.

**So a second handle opened beside the sweep's transaction is refused before any design question is reached**, and this entry does not reopen it.

### 3. Why the `ledger` member is unreachable, and not merely unwanted

**REASON 1. THIS FILE CANNOT NAME `LedgerTx`.** `sweeps/ports.ts` declares its whole outside world structurally and imports nothing, and `apps/worker/package.json` declares no `@merit/ledger`. That absence is not incidental: [`ledger-posting-authority.test.ts:175`](../../apps/api/test/ledger-posting-authority.test.ts) asserts `expect(WORKER_MANIFEST).not.toContain('@merit/ledger')`, and this row does not move it. **So `ledger: LedgerTx` cannot be written here. It could only be RESTATED here.**

**REASON 2. RESTATING IT PUTS BOTH EXCLUDED KEYS BACK INSIDE THIS FILE.** `LedgerTx` ([`tx.ts:82`](../../packages/ledger/src/tx.ts)) is `rows(key: LedgerReadKey)` and `insert(key: LedgerWriteKey, values)`; `LedgerReadKey` ([`tx.ts:63`](../../packages/ledger/src/tx.ts)) is `'ledgerAccounts' | 'ledgerHalts'` and `LedgerWriteKey` ([`tx.ts:64`](../../packages/ledger/src/tx.ts)) is `'ledgerTransactions' | 'ledgerEntries'`. **Those are exactly the two keys `EXPIRY_TABLES` excludes.** A restatement writes them into the port as an `insert` key union, which puts `tx.ledger.insert('ledgerEntries', ...)` one call away in `expiry.ts`: a single-sided entry written past `assertBalanced` ([`posting.ts:273`](../../packages/ledger/src/posting.ts)), past `LEDGER-C1`'s sign check, and past `assertNoLiveHalt` ([`post.ts:166`](../../packages/ledger/src/post.ts)). **That is the exclusion's own sentence becoming false**, and it would also be a third statement of one shape, which `LedgerTx` already pays for once and names as [ADR-092](ADR-092.md) section 5's hazard ([`tx.ts:24`](../../packages/ledger/src/tx.ts)).

**REASON 3. IT BREAKS THE HEADER'S ASSIGNABILITY CLAIM.** [`ports.ts:19-21`](../../apps/worker/src/sweeps/ports.ts) states that `SystemTx` is assignable to `ExpiryTx` with no import in either direction, and it is: `SystemTx` ([`scoped-db.ts:3709`](../../packages/db/src/scoped-db.ts)) declares `rowsWhere`, `lockAt` and `updateAt` generic over `TableKey`. **It declares no `ledger` property.** A `ledger` member therefore ends that assignability and forces the wiring to build an adapter object it does not otherwise need.

**NONE OF THE THREE IS AN OBJECTION TO `AdminPayoutTx.ledger`** ([`admin-payouts.ts:369`](../../apps/api/src/routes/admin-payouts.ts)), which is a live `readonly ledger: LedgerTx` on the money path and stays one. That file imports `@merit/ledger`, composes the posting itself and names the accounts; this one refuses all three by design. **The precedent is real and it is a precedent for a different file.**

### 4. The shape the wiring will actually take

`ExpirySweepIo.ledger` is a member of the object built ONCE, before any transaction opens, so a per-transaction closure is not available to it: the only per-transaction thing `postLt01` receives is the `ExpiryTx`. With a member ruled out, what is left is identity.

```
const ledgerOf = new WeakMap<object, LedgerTx>();

transact: (fn) => LIVE_DB.batch((tx) => { ledgerOf.set(tx, tx); return fn(tx); }),
ledger:   { postLt01: async (tx, values) => {
             const ledger = ledgerOf.get(tx);
             if (ledger === undefined) throw new ExpirySweepUnwired('ledger.postLt01');
             await postTransaction(ledger, await readChart(ledger), lt01(values));
           } },
```

**`ledgerOf.set(tx, tx)` is the whole of it, and it is not a trick.** `LIVE_DB.batch` ([`db.ts:150`](../../apps/worker/src/db.ts)) hands out a `SystemTx`, which satisfies `ExpiryTx` and satisfies `LedgerTx`, so the wiring is recording the handle it opened under itself and reading it back as the narrower of the two views. **There is ONE transaction, no cast, and no second handle**, which is section 2's constraint met rather than restated.

**RECOGNITION BY IDENTITY IS THIS FILE'S OWN CITED IDIOM.** [`ports.ts:95-97`](../../apps/worker/src/sweeps/ports.ts) already relies on it for filter terms, and the thing it relies on is `TERMS` ([`scoped-db.ts:723`](../../packages/db/src/scoped-db.ts)), a module-private `WeakSet` that recognises a term by identity *"precisely so a caller cannot hand-roll one"*. **The same property is what makes the refusal correct here**: a fake `ExpiryTx` the wiring did not open has no ledger authority, and `postLt01` must refuse it rather than post through a handle whose authority it cannot know.

**A MODULE-LEVEL "CURRENT TRANSACTION" SLOT IS REFUSED BY NAME.** `runExpirySweep` opens several transactions in sequence and one per released row, so a single mutable slot is wrong the first time two are live, and a `WeakMap` keyed on the handle `postLt01` is actually given cannot be.

### 5. What the exclusion protects, and what this ruling costs

**THE EXCLUSION IS UNCHANGED AND ITS SENTENCE STAYS TRUE.** `EXPIRY_TABLES` gains no member, no accessor on `ExpiryTx` reaches a ledger key, and after this row no ledger key appears in the port's code at all. That last part is now checked rather than promised: the suite strips comments and asserts that none of `ledgerTransactions`, `ledgerEntries`, `ledgerAccounts` or `ledgerHalts` is named in `sweeps/ports.ts`, so the paragraph EXPLAINING the exclusion can stay writable and cannot be the thing that breaks it.

**WHAT IT COSTS IS A COUPLING THE TYPE CHECKER CANNOT SEE.** `postLt01`'s `tx` parameter no longer carries its own evidence that a ledger handle exists for it; the wiring's map does, and the failure mode is a runtime refusal rather than a compile error. **This entry states that cost rather than burying it.** The refusal is loud and is the same one the rest of this port already raises, which is the disposition `UNWIRED_EXPIRY_SWEEP_IO` was built on: a sweep that returned a plausible value would be a fixture paying real traders.

### 6. Alternatives considered

| Alternative | Why not |
|---|---|
| **`ExpiryTx` gains `ledger: LedgerTx`** | Section 3, all three reasons. The decisive one is that the exclusion's own sentence, *"nothing here can write a ledger row by naming a key"*, becomes false the moment the member exists, and the row that dispatched this slice required it restated and **still holding** |
| **A narrower `ledger` member that cannot `insert`** | `postTransaction` ([`post.ts:126`](../../packages/ledger/src/post.ts)) takes a whole `LedgerTx`. Anything that can serve it can write a ledger row by naming a key, so there is no narrowing that keeps the sentence true and still posts |
| **Change `postLt01`'s signature** | It is read as text by [`ledger-posting-authority.test.ts:188`](../../apps/api/test/ledger-posting-authority.test.ts), which is outside this row's fence, and the sweep's own call site is in `expiry.ts`, also outside it. **Reported rather than taken** |
| **Cast the `ExpiryTx` to a `LedgerTx` in the adapter** | It is a `SystemTx` at runtime, so the cast would work and it is refused anyway: [`ports.ts:23-26`](../../apps/worker/src/sweeps/ports.ts) rules that nothing here casts past a key type, and a handle cast is the same act on a wider object |
| **Open a second transaction for the posting** | [ADR-006](ADR-006.md) and `0057`'s `DEFERRED` note at [`:104`](../../packages/db/migrations/0057_terminal_withdrawal_obligation.sql). Not negotiable and not reopened |

### 9. Approval

**What a founder read adds and this entry cannot.**

**THE THING TO DECIDE IS WHETHER A COUPLING THE COMPILER CANNOT SEE IS THE RIGHT PRICE FOR A SENTENCE STAYING TRUE.** This entry chose to keep `ExpiryTx` at three members and to let the wiring hold the ledger handle in a `WeakMap`, so that `EXPIRY_TABLES`'s stated protection survives word for word and `expiry.ts` never gets within reach of a ledger key. **The alternative reading is that `AdminPayoutTx.ledger` already lives on the money path with the same exposure, that a `ledger` member is honest about a dependency this job genuinely has, and that a type the checker enforces beats a map the checker cannot see.** Read that way, the right move is to add the member and AMEND the exclusion's sentence to say what it would then protect, which is the narrower and still valuable claim that no ledger key is reachable through the sweep's own table accessors. **Both readings end with one transaction and one posting. They differ on whether the sweep is allowed to be able to write a ledger row at all**, and a founder who thinks the answer is "yes, and say so plainly" should send the next session to reverse this and rewrite [`ports.ts:76-78`](../../apps/worker/src/sweeps/ports.ts) rather than leave the two standing together.

**THE SECOND IS THE FAILURE MODE THIS SHAPE CREATES AND THE MEMBER WOULD NOT.** `postLt01` handed an `ExpiryTx` the wiring did not open refuses at run time where the member would have refused at compile time. **On this job that is defensible and it is not free**: the sweep runs unattended on a clock, and the refusal surfaces as a rolled-back release, a held payout and a nightly assertion, rather than as a red build. Section 5 states the cost rather than hiding it, and the reason it is acceptable is that it is the same refusal the whole port already makes; the reason it is a cost is that a compile error would have been better.

**THE THIRD IS THAT THIS ROW REPAIRED A CITATION INSIDE ANOTHER SESSION'S LANDED ENTRY.** [ADR-172](ADR-172.md) finding 16 quoted a sentence this row deleted, from a pointer that was already wrong. The repair is narrow and is recorded in section 7, and **a founder may prefer that a landed entry's evidence never be edited by a later row at all**, in which case the remedy is a note in the later entry and a permanently stale quote in the earlier one. This entry took the reading that a quote nobody can check is worse.
