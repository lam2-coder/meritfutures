## ADR-128: the audited write, and the table `OI-01` has been waiting on  (2026-08-27, status: proposed)

**Five open items close here in two forward-only migrations, and the split into two is the first thing this entry rules.** `OI-03`, `OI-04`, `OI-12` and `OI-13` are one idea stated four ways: **a write that changes what the database already said goes through a path that records who and why, or it does not commit.** `OI-01` is a different thing, a table the approved design named and the fold did not build, and the remedy it waits on is a **founder choice between two named designs** rather than a gap with one obvious closure.

- **Origin:** the migration cluster, session **240**. The number was **RESERVED BEFORE DISPATCH and REQUIRED** ([ALLOCATION](ALLOCATION.md) row 128): _"Five open items, one forward-only migration, one number. A migration is never edited once merged, only superseded ([E2](../../MERIT_BUILD_MASTER_PROMPT.md)), so five sessions claiming five numbers for one coherent change is the shape this reservation exists to prevent."_

- **Migration numbers taken: `0048` and `0049`, both claimed in this commit.** The reservation asked for one and invited a split with a reason. The reason is in section 1.

## 1. Two migrations, and the reason is the founder's read rather than tidiness

**Folding `OI-01` into `0048` would mean that a founder who prefers the other design rejects three `SECURITY DEFINER` paths and a calendar guard along with it.** [`0033`](../../packages/db/migrations/0033_trading_calendar_revision_required.sql) already writes for exactly this case, in its own header: _"Reject this half if the founder reads the ruling narrowly; `CALENDAR-C1`'s image half stands without it."_ A separate file is the stronger form of the same courtesy, and it costs nothing that supersession does not already pay: a guard is superseded per object, not per file.

| Migration | Items | Why these belong together |
|---|---|---|
| [`0048`](../../packages/db/migrations/0048_audited_writes_on_append_only_tables.sql) | `OI-04`, `OI-12`, `OI-13`, and the DDL half of `OI-03` | The audited write. `OI-04` and `OI-13` are the paths; `OI-12` is the write that had no path |
| [`0049`](../../packages/db/migrations/0049_reserve_coverage_snapshots.sql) | `OI-01` | A missing table, ruled by a choice between two named designs |

**`OI-03` takes no migration number at all**, because it needs no DDL: its own words ask for a check that reads the revoke list **against the document**, and a `.sql` file cannot read markdown.

## 2. `OI-03`, and the drift was not a prediction

**The item reads:** _"`0026`'s append-only revoke list is a list, and a list drifts. Eighteen tables are named there against DATA_MODEL section 1's Mutability set. The CI check must assert the revoke list against the document rather than trusting either."_

**It had already happened three times when this session read it.** [DATA_MODEL section 1](../architecture/data-model/README.md) carried **three** copies of its Mutability bullet, left by three keep-both merges:

| Copy | What it claimed |
|---|---|
| 1 | "twenty-three tables", four migrations, naming `0026`, `0032`, `0039`, `0040` |
| 2 | "twenty-two tables", three migrations, naming `0026`, `0032`, `0039`, `0038` |
| 3 | "twenty-two tables", three migrations, naming `0026`, `0032`, `0039`, `0042` |

**The installed set was twenty-five**, read from `has_table_privilege` against a schema built from empty. **Every gate was green throughout**, and the reason each one missed it is worth stating rather than assuming: `CI-06u` looks for duplicated **passages** and these three had diverged; `CI-06i` reads table **names** and not privileges; and nothing in the repository read the database's grants at all. **A migration that forgot its `REVOKE` would have been invisible in exactly the same way**, which is the failure this item is actually about.

**The remedy is [`scripts/db/assert_append_only_grants.mjs`](../../scripts/db/assert_append_only_grants.mjs)**, which reads the fenced block in DATA_MODEL section 1 and the installed privileges and fails **in both directions**. The three paragraphs become one, and the list becomes a block a parser can survive.

**A table is append-only exactly when `merit_app` holds neither `UPDATE` nor `DELETE` on it.** One question covers both halves of `0026`'s promise, because `merit_app` inherits everything granted to `PUBLIC`: a revoke binding only the application role leaves the table off the derived list and is reported. `impersonation_sessions` is what proves the definition is not a tautology: `0042` revokes `DELETE` and **keeps `UPDATE`** deliberately, and it is on neither side of the comparison.

### Inverting `0026`'s default privileges was considered and is NOT taken

`0026:174` grants `merit_app` full DML on every table a later migration creates, so **every append-only table has to remember to revoke**, and that is the root of the drift rather than a symptom of it. `ALTER DEFAULT PRIVILEGES ... REVOKE UPDATE, DELETE` would invert the failure mode from "forgot to revoke, silently mutable" to "forgot to grant, breaks immediately", which is strictly stronger.

**It is not taken, for three reasons and the founder may overrule any of them.** It reverses a decision `0026` states and reasons in its own comment. [`0045`](../../packages/db/migrations/0045_simulation_runs.sql) already writes against the current default in a comment that would become false. And a future migration's author would meet a failure whose cause is in a file they never read, where the check gives the same protection with a message that names the fix. **`OI-03` asks for a check.**

## 3. `OI-04` and `OI-13`, and the defect underneath them

**`0026` named three functions that do not exist** and said where they belong: _"performed by `SECURITY DEFINER` functions owned by `merit_migrator` rather than by widening the grant ... each arrives in the same pull request as its negative-authz test (VG-5, DATA_MODEL section 14)."_ [`0048`](../../packages/db/migrations/0048_audited_writes_on_append_only_tables.sql) creates them and [`scripts/db/probe_audited_writes.sql`](../../scripts/db/probe_audited_writes.sql) is that test.

| Function | Writes | Requires |
|---|---|---|
| `supersede_daily_mark` | `daily_marks.superseded_by` | Same account-day, both marks live |
| `suppress_identity_link` | the four `SD-M7-04` dispute columns | A non-blank author and a non-blank note, edge not already suppressed |
| `rewrite_rule_state` | every `rule_states` column except its identity and its birth | A `B.4` step 3 `admin_actions` approval, and a moved version-like input |

### Three things the register rows do not say, found by writing the code

1. **`identity_links` is four columns and not one.** `OI-04` calls it "a single-column update". `suppressed` is the operative field and `identity_links_suppression_has_author` makes `suppressed_by` mandatory, so `disputed_at`, `dispute_note`, `suppressed` and `suppressed_by` move together or the write is not a dispute resolution. **The row is imprecise rather than wrong** and it is corrected in place.
2. **`merit_migrator` held nothing at all.** `0026` creates the role and grants it no privilege, because DDL is held by ownership. A `SECURITY DEFINER` function owned by it therefore fails with `relation "daily_marks" does not exist`, which reads like a missing table and is a missing `USAGE ON SCHEMA public`. It then fails again with `permission denied for table daily_marks` under a column-scoped `UPDATE` grant alone, because the `WHERE` clause reads `id` and `SELECT` was never granted. **Both were produced by executing them.**
3. **The ruled mark correction was not performable at all.** Section 4.

### `rewrite_rule_state` requires a version-like input to have moved, and that clause is a READING

Every other assertion in the three functions is a transcription of a sentence somebody already wrote. This one is not. `B.4` step 1 scopes divergence detection by `engine_version` and says rows from an older version are _"out of scope until step 4 rewrites them"_, and [ADR-047](ADR-047.md) rules the calendar revision the engine's **second version-like input** whose step 4 rewrite _"restamps the watermark"_. So a rewrite moving neither is not step 4; it is an `UPDATE` to an append-only table with an approval stapled to it. **Reject this clause if `B.4` is read narrowly.** The other five assertions stand without it, and `SUCCESS 8` and `REJECTION 10` in the probe are the pair that make it testable in both directions.

### What `rewrite_rule_state` deliberately does NOT assert

`B.4` step 3 says the approval _"is an `admin_actions` row with the report's digest"_, so requiring the row is transcription. **What the row's `action` string should say, and under which key the digest lives, is not in the corpus**, and a contract invented in a function body is a second contract nobody wrote down ([`0033`](../../packages/db/migrations/0033_trading_calendar_revision_required.sql) header item 5). The function asserts the row exists and its reason is non-blank. M01's replay job specifies the rest when it is built.

## 4. A defect in a merged money-path migration, found by writing a fixture

**The ruled mark correction is refused by the database in both directions and there is no third order.** [`0014`](../../packages/db/migrations/0014_marks.sql) states it: _"A CORRECTION PRODUCES A NEW MARK ROW AND POINTS THE OLD ONE HERE. Never an UPDATE."_ So does `0026`. Executed against PostgreSQL 16:

| Order | Result |
|---|---|
| Insert the replacement, then point the old row at it | `duplicate key value violates unique constraint "daily_marks_live_per_account_day_uq"`. The partial unique index is on `superseded_by IS NULL`, so for the instant before the old row is pointed away the account-day carries **two live marks** |
| Point the old row first, then insert the replacement | `insert or update on table "daily_marks" violates foreign key constraint`. `superseded_by` references `daily_marks(id)` and cannot name a row that does not exist yet |

**`daily_marks_no_self_supersede` closes the self-reference, and pointing the old mark at an unrelated row to free the index is the exact thing the function refuses.** So **the mechanism behind the never-claw-back promise** (DATA_MODEL section 16 ruling 2, `B4 #5`) **has never been executable.** It was never noticed because `daily_marks` has zero rows and no correction has ever been attempted, which is the same reason [ADR-035](ADR-035.md)'s trigger and `EC-157`'s constraint each survived for months.

**The ruling: defer the uniqueness, do not weaken it.** A partial `UNIQUE INDEX` cannot be deferred, because only a constraint can be deferred and a unique constraint cannot be partial. An `EXCLUDE` constraint can be both, so `0048` replaces the index with `EXCLUDE USING btree (account_id WITH =, trading_day WITH =) WHERE (superseded_by IS NULL) DEFERRABLE INITIALLY DEFERRED`: **the identical predicate over the identical btree, under the name every document cites.** What changes is **when** it is checked, which is `0027`, `0033` and `CALENDAR-C1`'s argument arriving on a third guard: a correction is one **transaction**, and requiring an order inside it is a contract written in an index and nowhere else.

**The cost is stated rather than discovered.** Between the `INSERT` and the `UPDATE`, inside that one transaction and visible to nothing outside it, the account-day carries two live marks. A query issued by that same transaction in between would see both. **The alternative is that the ruled correction cannot happen.** `REJECTION 6b` in the probe is what holds the guarantee at commit, and it checks the exception **class**, because the class moved from `unique_violation` to `exclusion_violation` and a handler written against the old one would catch nothing while reporting green.

## 5. `OI-12`, and the obvious guard is the wrong guard

**The item, in `0035`'s words:** _"an `INSERT` writes no revision row and moves no watermark. For a future day that is correct. For a day backfilled inside an existing coverage window it is not: the day sequence moves retroactively and every stamped row still claims a watermark that looks current."_

**`CALENDAR-C3` refuses a retroactive `trading_calendar` `INSERT` that leaves no record.** Three parts of it are decisions rather than transcription.

**The retroactivity test is the fold extent, not the coverage window.** The item's own phrase "inside an existing coverage window" reads as a lookup into `trading_calendar_loads`. It is not: an ordinary forward load writes a coverage row for a year and then inserts every day inside it, so the coverage reading would demand a revision row for **all 250 of them**, which is the one case `OI-12` says is already correct. What makes a day retroactive is that the engine has already folded past it, so the test is `NEW.trading_day <= greatest(max(trading_day))` over `fills`, `daily_marks` and `rule_states`. Those are **P1 S-E section 4's ruled partition**, the same three tables `CALENDAR-C1` counts over, and widening them stays a founder's call ([ADR-045](ADR-045.md)'s own sentence, kept).

**The prior image of a day that did not exist is the absence, and it is not a fabrication.** `trading_calendar_revisions_prior_row_is_a_row` requires the four keys to be **present** and says nothing about their values, and `is_holiday` is `NOT NULL` on every real calendar row, so `"is_holiday": null` can only mean "no row existed". That is `F-4`'s own vocabulary. It is also what stops the guard being satisfied by pointing at some earlier correction's revision row for the same day, which `REJECTION 13` watches.

**`incident_ref` is required unconditionally, because no existing constraint reaches this case.** `dependent_row_count` counts rows on the day **itself**, and a day that was never a trading day legitimately has none, so `trading_calendar_revisions_incident_named_when_dependent` sees a zero and lets `incident_ref` stay null. The harm from a backfill is on every day **after** it.

### `CALENDAR-C3` is immediate, and `0032`'s foreign key becomes deferrable so that it can be

**This pairing was arrived at by watching the alternative fail.** The guard has to ask its question **at the moment the day is inserted**. Written as a deferred constraint trigger it asks at commit instead, and then **one transaction that seeds a calendar and then writes marks against it refuses itself.** That is not hypothetical: it is what [`probe_calendar_revision_required.sql`](../../scripts/db/probe_calendar_revision_required.sql)'s own fixture does, and **running every existing probe against the new schema** (DELTA_MANIFEST section 18's rule) is what found it, on the first run, before any of it was written down as safe.

An immediate trigger needs the revision row to exist when the calendar row lands, so `trading_calendar_revisions_trading_day_fkey` is superseded as `DEFERRABLE INITIALLY DEFERRED`, keeping its name and `ON DELETE RESTRICT`. A revision naming a day that never arrives still fails, at commit rather than at the statement. **Nothing becomes writable that was not.**

**The cost is an order, and it is stated rather than silent**, which is the distinction `0033` header item 5 draws when it objects to "a second contract nobody wrote down": a backfill records the absence and then adds the day, and `CALENDAR-C3`'s message says so in the sentence a reader meets when they get it wrong.

## 6. `OI-01`, and only three of its five fields needed a table

**The recommendation implemented is not this session's.** [`liability_snapshots.md`](../architecture/data-model/liability_snapshots.md) has carried it, with its three reasons in order of weight, since the reconciliation: _"give them their own table rather than widening this one."_ This entry proposes adopting it, and the approval line is unsigned.

| Field | Disposition |
|---|---|
| `reserve_cents`, `cvar99_cents`, `rcr_bp` | [`reserve_coverage_snapshots`](../architecture/data-model/reserve_coverage_snapshots.md), a separate table |
| `funded_accounts` | `liability_snapshots`, by `ALTER TABLE`. It is not reserve coverage: it is the count behind `P-M6-01`'s own sum, and API_CONTRACT renders it beside `as_of` and `open_liability_cents` |
| `per_plan` | **Nothing.** It was never orphaned |

**`per_plan` had a home for thirty-three migrations and `OI-01` kept counting it.** API_CONTRACT's `per_plan` is loss ratio, threshold, `sales_paused` and CUSUM per plan, and [`0016`](../../packages/db/migrations/0016_treasury_controls.sql) built `plan_breaker_state` with `plan_id`, `evaluated_on`, `ratio_bp`, `threshold_bp`, `min_sample` and a state whose values include `paused`. **This is [ADR-117](ADR-117.md)'s blind spot in its plainest form**: the register's own entry was stale and nothing could tell it.

**`rcr_bp` is a `GENERATED` column, which answers the third reason rather than accepting it.** That reason is _"a ratio stored beside its own numerator invites recomputation drift"_. A ratio the database computes cannot disagree with the two numbers stored beside it. It is integer arithmetic on `bigint` cents, so no float enters the reserve path, and truncation runs toward zero, which lowers the ratio and arms the breaker marginally sooner rather than later.

**`NULLIF` in that expression is load-bearing and was proven by execution.** A `GENERATED` column is computed **before** the row's `CHECK` constraints are evaluated: with a plain `/ cvar99_cents`, a zero denominator raises a bare `division by zero` and `reserve_coverage_snapshots_cvar99_is_positive` never fires at all. A zero CVaR99 is not infinite coverage, it is a floor nobody computed, and the operator has to be told which of those happened.

**`RESERVE-C1` is what makes carrying both a reference and a copy honest.** `INV-M5-11` says the reserve is reported against a **live** rail balance, so the row names the `treasury_balances` row it read and attestation staleness (`P-M6-07`) is a join; [ADR-047](ADR-047.md) rules that a reference beats a copied value. But a snapshot holding only a pointer is not a snapshot, so `reserve_cents` is stored too and a trigger asserts at write time that the copy **is** the referenced balance. **Reject `RESERVE-C1` if the pointer alone is preferred**; the table stands without it and loses its self-containment. **The limit is stated**: `treasury_balances` is not append-only, so a later correction to an attestation can move a balance this table has already cited, and this trigger fires on `INSERT` and cannot see it. Making `treasury_balances` append-only is a separate ruling and is not taken here.

## 8. What this entry does not do

- **It does not invert `0026`'s default privileges.** Section 2.
- **It does not make `treasury_balances` append-only.** Section 6.
- **It does not create an un-suppress path for `identity_links`.** `SD-M7-04` rules the suppression and rules nothing about reversing it, and a reversal no document asks for is a power invented in a migration.
- **It does not widen `CALENDAR-C3`'s partition** beyond the three tables P1 S-E section 4 names, on ADR-045's standing sentence.
- **It does not specify the replay job's `admin_actions` vocabulary.** Section 3.
- **It does not extend `CI-06w` to the `OI` table**, which [ALLOCATION](ALLOCATION.md) names as the check that would have caught session 120. `scripts/corpus/` was outside this session's fence except for `CI-06h`'s needle list, and that widening is declared in the pull request rather than taken quietly.

**What a founder read adds and this entry cannot.** This entry names four of its own decisions as the founder's and the block collects them so a read starts from the questions rather than from the DDL. **`OI-01`'s design is a CHOICE between two named designs**, which is why section 1 splits the work into two migrations: so that preferring the other design rejects one file rather than three `SECURITY DEFINER` paths and a calendar guard along with it. **`rewrite_rule_state`'s version-like-input clause is a READING and the entry says to reject it if `B.4` is read narrowly**; every other assertion in the three functions transcribes a sentence somebody already wrote, and this one does not. **Replacing the partial unique index with a deferrable `EXCLUDE`** buys a correction that the database refused in both directions and costs a window, inside one transaction and visible only to it, where an account-day carries two live marks; the alternative is that the ruled correction cannot happen at all. **`RESERVE-C1` is offered for rejection in the same way**: reject it if the pointer alone is preferred, and the table stands without it and loses its self-containment. Section 2's refusal to invert `0026`'s default privileges is the fifth, and it is the one the entry itself calls strictly stronger while declining to take it.
