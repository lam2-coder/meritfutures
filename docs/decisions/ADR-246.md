## ADR-246: three certificate ports are two questions, the card is one deliverable and not three, and a port whose own message promised a 503 was answering 500 (2026-08-29, status: proposed)

**Row `246` sent one session to read `useCertificateBackend`, `useCertificateImageSource` and `useCertificateRevokeBackend` as a set for the first time, and to answer one narrow question: what is left of the first two once [ADR-240](ADR-240.md) has ruled the signing key out of this deployable and [ADR-231](ADR-231.md) has built the public door. The answer is that both wait on the same single absent artefact, that no part of it is configuration, and that a third refusal in this deployable waits on it too. The set splits two and one.**

**NEITHER PORT IS WIRED AND NO ENVIRONMENT VARIABLE IS NAMED**, which is [ADR-240](ADR-240.md)'s clause 10 unchanged. What is added is that the two are ONE piece of work rather than two, said with a measurement: `certificates` carries seventeen columns, none of them an image location, and no migration in the set of 67 alters the table.

**AND THE SET READING FOUND A DEFECT THE PORTS WERE HIDING FROM EACH OTHER.** `CertificateBackendUnwired`'s own message says `GET /certificates` answers **503**, and it is raised by both arms of the port; the list handler guarded only the read, so a refusal from the signer answered **500**. It is repaired here on [ADR-240](ADR-240.md) section 4's standing ruling, watched red before green.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `246`, session **436**, dispatched as `claude/the-certificate-ports`. The row is **CONDITIONAL** on ruling, and it is taken.

- **NOT THE MONEY PATH.** No ledger account, no balance, no payout, no migration and no reserved number. `E2` is not owed. Ships `proposed` with an **UNSIGNED** approval line.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the list route answered 500 on the signer arm and answers 503 now, that a half-wired backend answers by the state of the caller's own rows, that `certificates`' column set holds no image location and that no migration alters it, and that the three `BLOCKED` entries split two-and-one on the renderer and the resolver, is **MEASURED**, by executing it. That both database arms of `useCertificateImageSource` are already written elsewhere in this deployable, and that `CertificateLinks` has no nullable half so one refusing field refuses the whole response, is **DERIVED** at the file and line each claim names. What is **JUDGED** is that the card is one deliverable rather than three absences (section 2), that the state-dependence of a half-wiring is a stronger refusal than its status code (section 4), and that repairing the status code does not make a half-wiring more permissible (section 4 clause 5).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every citation carried by the three entries was re-derived. **Two did not survive** and section 5 carries both.

### 2. The ruling: the card is one deliverable, and it is not in this deployable

[ADR-240](ADR-240.md) clause 8 ruled the URL signing key out of `apps/api` and named where it belongs: the object store, whose presigner is the store's own, or the edge, whose signed-URL verification is an edge rule. **That ruling is read FORWARD here and is not re-opened.** Row `246` named overturning it as the trap and there is nothing to overturn: the ruling is right and this entry's own finding is that it did not go far enough, in the safe direction.

> **1. A SIGNER SIGNS AN ADDRESS, AN ADDRESS ADDRESSES AN OBJECT, AND THERE IS NO OBJECT.** [ADR-240](ADR-240.md) established that a key held here would have nowhere to spend itself. This entry adds the step behind it: even a key held in the right place would sign a URL for a card no producer in this repository renders. **`CertificateCard` is named in one file and it is the port's own declaration**, which [`certificate-links.test.ts`](../../apps/api/test/certificate-links.test.ts) already executes.
>
> **2. THE CARD IS ONE DELIVERABLE AND THE TWO PORTS ARE ITS TWO SIDES.** `useCertificateBackend` owes an `image_url` that addresses the card; `useCertificateImageSource` owes the card's bytes ([`certificates.ts:958`](../../apps/api/src/routes/certificates.ts), reached through [`certificates.ts:976`](../../apps/api/src/routes/certificates.ts)). **A renderer plus somewhere for its output to live closes both, and nothing smaller closes either.** The two entries therefore expire together or not at all, and a session dispatched at either is dispatched at the card.
>
> **3. AND A THIRD REFUSAL IN THIS DEPLOYABLE IS ON THE SAME ABSENCE.** `databaseAccountReads.readCertificate` is **installed** and refuses by name; its `CERTIFICATE_BLOCKER` ([`account-reads.ts:878`](../../apps/api/src/routes/account-reads.ts)) reached this finding independently on the `/certificate` row. **So the card is worth measuring once, not three times**, and this is the first entry to say so because it is the first to read the ports together.
>
> **4. THE TABLE HOLDS NO ADDRESS FOR IT EITHER, AND THAT IS MEASURED RATHER THAN QUOTED.** `certificates` carries **seventeen** columns and none is an image location, and **no migration in the set of 67 alters the table**. [`0020_public_surface.sql`](../../packages/db/migrations/0020_public_surface.sql) states the reason one line above its own DDL: *"THE CARD IS A RENDERING; THE CERTIFICATE IS THE ROW."* The row exists. The rendering does not. [`certificate-ports.test.ts`](../../apps/api/test/certificate-ports.test.ts) names the column set rather than counting it, so a column added tomorrow fails with its own name in the diff.
>
> **5. WHERE IT BELONGS, STATED AS AN ANSWER RATHER THAN AS A REFUSAL.** The renderer belongs with the **issuer**, which [M11](../plans/M11-certificates-social-proof.md) section 3.2 puts in the **worker** and which already talks to a Vault for the claim signature; the card's bytes belong in the **object store**, and the address and its signature belong with whatever serves those bytes, which is [ADR-240](ADR-240.md) clause 8's ruling unchanged. **`apps/api` renders nothing and signs nothing; it addresses.** That is the posture this deployable already holds for the claim signature, which it reads out of a column and has never held the key for.

**WHAT THIS ENTRY DOES NOT DECIDE IS WHETHER THE ADDRESS IS STORED.** A presigned URL is minted per request and need not be persisted, so `certificates` may or may not owe an image-location column. Section 4 clause 4 measures that it has none today; it does not rule that it should gain one. That is the card slice's, with a migration number of its own if it needs one.

### 3. What is NOT wired, and why naming a variable would still be wrong

**NO PORT IS WIRED AND NO ENVIRONMENT VARIABLE IS NAMED.** [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md)'s precedent is that a port may be wired when its only remaining gap is something a deployment supplies. **A renderer is not such a gap**, and this entry re-confirms rather than re-argues it.

`verify_url` remains the interesting half and it remains closed for a reason that is about the OTHER field. `CertificateLinks` ([`certificates.ts:378`](../../apps/api/src/routes/certificates.ts)) has **no nullable member**, and `projectCertificate` puts both fields through `assertUrl`. So the discharged half buys nothing alone: **one refusing field refuses the whole response**, and an origin variable named here would be [ADR-240](ADR-240.md) clause 10's defect a second time.

### 4. The defect the set reading found, and the one it refuses to let the repair hide

**`CertificateBackendUnwired` IS RAISED BY BOTH ARMS AND ITS MESSAGE SPEAKS FOR BOTH**: *"so `GET /certificates` answers 503 rather than an empty list. An empty list is a trader being told they have no certificates."* The list handler guarded `readCertificates` inside a `try` and called `renderCertificates` **after** the `catch`, so a refusal raised by `links` was an unhandled error and [`server.ts`](../../apps/api/src/server.ts) answered **500**.

**WATCHED FAILING BEFORE IT PASSED**, on the real tree, with no source modified to produce the red:

```
FAIL apps/api/test/certificate-ports.test.ts >
  a refusal from the `links` arm is a 503 and not a 500
AssertionError: expected { status: 500, code: 'internal_error' }
              to strictly equal { status: 503, code: 'service_unavailable' }
```

> **6. AN UNWIRED PORT IS A 503 AND NEVER A 500, AND THIS IS [ADR-240](ADR-240.md) SECTION 4 APPLIED RATHER THAN EXTENDED.** That entry ruled the identical shape one wave ago on [`economic-calendar.ts`](../../apps/api/src/routes/economic-calendar.ts): an unwired port is *"a deployment nobody finished"* and not a defect, and a 500 sends an operator to hunt for a bug when what is missing is a line in [`start.ts`](../../apps/api/src/start.ts). **`certificates.ts` is a file [ADR-240](ADR-240.md) read closely and did not repair**, which is worth recording: reading a file for one question does not find the defects belonging to another.
>
> **7. THE REPAIR IS THE SMALLEST ONE THAT MAKES THE SENTENCE TRUE.** The render moves inside the region that already catches `CertificateBackendUnwired`. Nothing else is caught that was not caught before: a `CertificateRowError` from a malformed row is still a 500, because that IS a defect.

**AND THE STATUS CODE IS NOT THE REASON THE PORT STAYS UNWIRED, WHICH IS THE HALF THAT MATTERS MORE.** `projectCertificate` never calls `links` for a deferred row, which is [ADR-168](ADR-168.md) foreclosure 4 enforced structurally rather than by a trailing conditional. So a backend with a live read and a refusing signer behaves like this, executed:

| The caller's certificates | The deployment answers |
|---|---|
| all deferred | **200**, with real rows |
| one issued | **503** after the repair, **500** before it |

> **8. A REFUSAL DECIDED BY THE STATE OF THE CALLER'S OWN ROWS IS REFUSED WHATEVER STATUS CODE IT CARRIES.** Two callers, one deployment, one difference: a column on a row each of them owns. [`verify.ts`](../../apps/api/src/routes/verify.ts)' `readPresentation` refuses the same shape in its own words, calling a lazily-read copy table *"a hit-versus-miss oracle built out of a configuration error"*. **This is that, built out of a half-wiring**, and it is an independent ground: it would stand even if the card landed tomorrow and only the origin were missing.
>
> **9. SO THE REPAIR IS NOT A STEP TOWARDS WIRING THIS PORT AND MUST NOT BE READ AS ONE.** It is stated here because the opposite reading is available: a 503 looks like an ordinary unwired port where a 500 shouts, so tidying the code could be read as making a half-wiring easier to ship unnoticed. **That is why clause 8 is executed rather than written into a comment.** The test that asserts the 503 sits beside the test that asserts the answer is state-dependent, and a session that half-wires this port fails the second one.

### 6. What this entry does NOT rule

- **It does not overturn [ADR-240](ADR-240.md).** Section 5's ruling that the URL signing key does not belong in `apps/api` is read forward and strengthened, not re-opened. **No signing key, no bucket, no hostname and no secret is written into this repository** ([ADR-012](ADR-012.md)).
- **It does not touch [API_CONTRACT](../architecture/API_CONTRACT.md).** The tension between section 6's *"signed, time-limited"* `image_url` and section 6.3's *"no query"* image row is still reported and still unrepaired.
- **It does not reach `useCertificateRevokeBackend`.** That port is behind the SSO purchase and no admin identity is invented to get past it. Its entry gains one sentence recording that the card does not release it.
- **It names no environment variable and wires no port.** The wired count in [`wiring.test.ts`](../../apps/api/test/wiring.test.ts) is unchanged.
- **It reserves no migration number and takes none**, and it does not rule whether the card's address belongs in a column.
- **It does not decide where the card is stored or which vendor serves it.** [ADR-240](ADR-240.md) clause 8 named the two candidates and that is still where the question sits.

### 9. Consequences

- **A session dispatched at either remaining certificate port now arrives at one question instead of two**, and the question is where the card is rendered and where it lives rather than which variable is missing.
- **The trader-facing certificate surface refuses honestly on both arms of its port**, so an operator reading a 503 knows a line is missing from `start.ts` and is not sent hunting for a defect.
- **The half-wiring that would raise the wired count by one is now a failing test rather than a warning in a comment**, and it fails on the ground that survives the card landing.
- **`certificates`' column set is asserted by name**, so the day the card gains a home in the table, three documents that say it has none go red together.
- **The three-port set is recorded as two-and-one**, so the next reader does not have to re-derive that the revoke port is a different question.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST IS WHETHER THE CARD IS THE WORKER'S OR THE EDGE'S, AND THIS ENTRY ONLY NARROWS IT.** Section 2 clause 5 puts the renderer with the issuer, in the worker, on the ground that the issuer already exists there and already talks to a Vault. **The alternative is a live re-rendering endpoint**, and [ADR-240](ADR-240.md)'s own founder block named why that is not a detail: `INV-M11-08` makes the re-render the only path by which a revocation reaches an image already in circulation, so **a card written once into an object store is a file that keeps asserting a revoked claim until its URL expires**. A worker that renders on issue and a service that renders on fetch are two different revocation stories, and the corpus is written against the second. **This entry deliberately does not choose**, and the choice changes what M11's card slice builds.

  **THE SECOND IS WHETHER REPAIRING THE 503 WAS THE RIGHT MOVE AT ALL.** Section 4 clause 9 states the case against it plainly: a 500 is loud and a 503 is expected, so the repair makes a half-wired deployment quieter. The reasoning taken is that [ADR-240](ADR-240.md) section 4 already ruled the general question and a route may not answer a different code from the one its own error class promises. **If you would rather this route stayed loud, the repair reverts in one commit** and the executed state-dependence case stands either way.

  **THE THIRD IS THAT THE STATE-DEPENDENCE CASE IS A FENCE THIS ENTRY BUILT AND NOBODY ASKED FOR.** No approved document says a port must refuse uniformly across callers. **`usePayoutBackend`'s one-live-arm rule is the nearest thing and it is a rule about ARMS, not about callers**, and this entry reads it across to a per-row property. If that reading is wrong, a future session with a real reason to serve deferred-only traders meets a test it must argue with rather than a comment it can weigh.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The claim that the two ports are ONE deliverable rests on the card being one artefact**, and nothing here proves that the bytes `useCertificateImageSource` serves and the object `image_url` addresses are the same object. **They may be two**: a live-rendered response on this deployable's own row and a stored card in an object store are both consistent with every approved sentence read here. If they are two, the two entries do not expire together and section 2 clause 2 is the sentence that falls.
