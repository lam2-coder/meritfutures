### 2. What the table actually claims, derived rather than assumed

**THE DISPATCH ASKED FOR THIS DERIVATION BEFORE A LINE OF THE CHECK, AND IT CHANGED THE CHECK.** A naive one-row-per-`lands`-heading reader is wrong in both directions and would have produced a false answer either way.

**THE TABLE'S KEY IS A SECTION NUMBER, AND A ROW MAY KEY A RANGE.** Its first row is `1 to 13`, one row claiming thirteen numbers. So a row count is not a claim count: **28 rows claim 39 numbers.** That is very likely where the dispatch's 19 came from, a count taken over some narrower slice of the region; whatever it was, a count of rows answers a question nobody asks of this table.

**A LANDING RECORD IS NOT THE UNIT EITHER, IN EITHER DIRECTION.** Sections `1` to `13`, `15`, `16` and `22` take numbers and record no migration landing at all; section `16` is this table itself. And `## 14.` heads **three** sections for three separate landings on **one** claimed number, which the `14` row records in its own words as *"CLAIMED THREE TIMES ... allocated three times"*. A reader demanding one row per landing heading would report the `14` row as two rows short of a table that is complete.

**A LETTERED HEADING TAKES NO NUMBER, AND THAT IS THE TABLE'S OWN WRITTEN RULE** rather than this check's taste: *"A lettered section deliberately claims no number, so the sequence this table allocates is undisturbed by either, and adding rows for them would make the table's own key ambiguous between a number and a name."* `4a`, `4b` and `4c` head **six** sections between them and none of them is owed a row.

**SO THE COMPARISON IS THE SET OF NUMBERS ON `## <n>.` HEADINGS AGAINST THE SET THE KEY COLUMN CLAIMS.** Measured on `f93a0cdd`:

| Measured | Value |
|---|---|
| `## ` headings in the file | **56**, of which **50** are numeric and **6** are lettered |
| distinct numbers those 50 headings take | **47**. `14` is taken three times and `21` twice |
| rows in the `### Section numbers` region keyed by a number | **28**, one of which keys the range `1 to 13` |
| distinct numbers those 28 rows claim | **39** |
| **numbers taken by a heading and claimed by no row** | **8**: `24`, `26`, `28`, `29`, `30`, `32`, `33`, `34` |
| numbers claimed by a row and taken by no heading | **0** |

**`27` IS THE DIFFERENCE BETWEEN NAMING A GAP AND MEASURING ONE, AND IT IS WHY THE ANSWER IS EIGHT AND NOT NINE.** `27` heads no section in this file, so nothing claims it and the table owes it no row. **The `31` row states that precisely**, *"and `27` has no section at all"*. The `45` and `48` rows compressed the same set to *"26 to 30"*, which reads as five numbers where four are owed. Three consecutive rows carried the imprecise form forward; the check is what stops the next one.

### 3. Why this is a fourth leg of `RI-37` and not a new invariant

**THE STRONGEST ARGUMENT IS NOT THE GENERAL PREFERENCE AND IT IS NOT THE SHARED FILE.** It is that `RI-37` already issues this instruction and cannot see whether it was followed. Leg 1's finding text, written by [ADR-334](ADR-334.md), ends:

> Write the section, claim its number in section 16's section-number table, and MEASURE it rather than reconstructing it from the ADR

**A check that tells a session to do three things and verifies one of them is a check with a hole in the middle of its own sentence.** Leg 4 closes it, and the finding text needed no edit.

**THE SUPPORTING ARGUMENTS, EACH CHECKED RATHER THAN ASSERTED.** `RI-37` already reads `packages/db/DELTA_MANIFEST.md` and already walks every `## ` line of it, so leg 4 adds a second pass over lines already in memory and no second file. Its stated subject is the completeness of that document's records, and *"this heading's number is in the register"* is the same class as *"this migration's number is in the manifest"*. And row `330`'s precedent extended `RI-35` rather than minting a number for a sibling assertion.

**THE ARGUMENT AGAINST, NAMED RATHER THAN LEFT FOR A READER TO FIND.** The two legs read DIFFERENT registries: legs 1 to 3 compare a directory to a document, leg 4 compares a document to itself. **A reader could reasonably call that two invariants sharing a file.** The title now has to carry both clauses and it is longer for it. What settles it is the instruction above: the two are not siblings, one is the other's unverified half.

**THE TITLE WIDENED AND `RI-29` DID ITS JOB BEFORE THE REGISTER ROW WAS TOUCHED.** In the same run that first showed leg 4 red, `RI-29` reported [`ALLOCATION.md:638`](ALLOCATION.md) *"states what `RI-37` asserts without carrying the title the live `CHECKS` array holds"* and quoted the new title back. ### 4. How the check tolerates the recorded collision, by a written rule and not a special case

**THIS IS THE TRAP THE ROW WAS DISPATCHED WITH AND IT IS SELF-REFERENTIAL: SECTION 16'S TABLE IS ABOUT NUMBERS AND ITS OWN HISTORY IS A COLLISION.** [`DELTA_MANIFEST.md:732`](../../packages/db/DELTA_MANIFEST.md) rules it in terms:

> **Neither is renumbered, and that is a ruling rather than an omission.** Both `OI-06`s are cited from module plans, STATE, a migration header and a session log; renumbering either breaks every citation of whichever one moves ... **The collision is left in place and the table allocates forward.**

**THE SAME RULING GOVERNS THE SECTION-NUMBER HALF, WHERE THE LIVE INSTANCE SITS**: two rows claim `21`, `## 21.` heads two sections, and `## 14.` heads three on one row.

**THE RULE IS THAT THE KEY COLUMN IS READ AS A SET AND MULTIPLICITY IS NOT READ.** If a collision is left in place and the table allocates forward, then two rows carrying one number claim ONE number, and the question this leg asks, *is this number claimed*, has one answer whether it is claimed once or twice. **The tolerance is a consequence of the rule the file already wrote, not an exception carved for `21`.** The heading side is a set for the identical reason: `## 14.` heading three sections is three landings on one allocation, and the `14` row is a complete record of it.

**THE COST IS STATED RATHER THAN HIDDEN, AND IT IS THE HALF THAT KEEPS THIS FROM CONCEALING A FUTURE COLLISION.** This leg can no more report a FUTURE duplicate row than the recorded one. **It does not silently absorb that job.** Duplicate rows in an allocation table are `OI-11`, which is open in this very table, states the defect in its own words, *"`allocated()` accumulates claims into a `Set`, so the two adjacent rows both claiming `0034` produced one member and twelve gates passed"*, and names its own blocker. A check claiming a property it does not test is worse than one that says which property is somebody else's.

**AND THE TOLERANCE IS NOT A HOLE, WHICH IS EXECUTED RATHER THAN ARGUED** (section 6). Taking ONE of the two `21` rows away leaves the check green; taking BOTH away is exactly one finding. The number must still be claimed by something.

### 7. The repair, and the standing rule it had to amend to be allowed to happen

**THE TABLE'S STANDING RULE FORBIDS EXACTLY WHAT THIS ROW DOES**: *"a row written on somebody else's behalf is a claim nobody made"*. Six rows invoked it to decline. **The rule is kept and its SCOPE is written down** ([ADR-065](ADR-065.md) T3, amended in place above the table):

- **A row for a section that does not yet exist is a CLAIM** about an allocation nobody has made. Only its author may write it, because only its author knows what the number is for. That is the whole content of the original rule and it is untouched.
- **A row for a section ALREADY IN THIS FILE, under a merged heading any reader can open, is a TRANSCRIPTION.** The claim was made, by the heading, when it landed. What is missing is the register entry, not the decision. Every one of the eight rows names the session, the migration and the ADR **read off the section's own opening line**, and every one of them can be checked against the heading beside it.
