### 2. THE RULING

> **1. THE BASE ACCOUNT CAP IS THE FIRM'S NUMBER, AND `plan_versions.rules.limits.max_accounts_per_entity` CANNOT SERVE IT IN ANY OF THE THREE FORMS AVAILABLE.** The cap is enforced against an identity's TOTAL live accounts across every plan (constitution B1, `INV-M3-08`, `GS-094`, and `AccountCapRow.liveAccounts`' own declaration), and the parameter is stored PER PLAN VERSION with no `CV-nn`, no database constraint and no requirement that two published versions agree. **Reading the purchased version makes an identity's effective cap the MAXIMUM over every published version**, so a buyer chooses their own cap by choosing a plan. **Reading the pinned version on the reset path reads a row that may have been retired years earlier**, which is `B4 #12`'s provable-rules-at-the-time property arriving where it does harm. **Requiring every published version to agree** is a firm parameter wearing a plan's costume, and no `CHECK` can express it because a `CHECK` cannot read another row. All three are refused.
>
> **2. `accountCap()` KEEPS ITS NO-PLAN SHAPE, AND ITS POSITION AS THE FIRST CALL OF BOTH HANDLERS IS CORRECT RATHER THAN AN ORDERING ACCIDENT.** A method that took a plan version would be the port asking a per-identity question of a per-plan-version number, which clause 1 refuses. The ordering also carries `INV-M3-15`, which requires the restriction check at the same point in the transaction as the cap, and `gateIdentity` performs both in one call.
>
> **3. THE HOME IS A `firm` PARAMETER ROW ON `price_floors`' SHAPE, AND THIS ENTRY NAMES IT WITHOUT BUILDING IT.** Effective dated, superseded by a new row rather than updated, carrying its approver, with `identities.max_accounts_override` folded over it exactly as the column's name already says. **Building it is a migration plus a registration in [`packages/db/src/schema.ts`](../../packages/db/src/schema.ts) and [`packages/db/src/scope.ts`](../../packages/db/src/scope.ts), both of which are session 427's this wave**, and the row's fence says STOP AND REPORT rather than edit. **NO MIGRATION NUMBER IS TAKEN**, because a number reserved for a file this session cannot write is a hole in [ALLOCATION](ALLOCATION.md) with nobody to fill it.
>
> **4. THE CAP IS NOT AN ENVIRONMENT VARIABLE AND THE `turnstile.ts` PRECEDENT DOES NOT REACH IT.** [ADR-226](ADR-226.md) and [ADR-229](ADR-229.md) admit a deployment-supplied value where the value is a SECRET the repository must not hold. A cap is a business parameter that decides who is refused a purchase, it is quoted back to the buyer in the refusal body, and an operator has to be able to see it, change it and be recorded as having changed it. **A purchase refused by a number no row records is a refusal nobody can reconstruct.** The corpus already rules the general form: *"There is no plan parameter anywhere in application code"*, and a value read from `process.env` is application code with an indirection.
>
> **5. THE CROSS-IDENTITY READ IS REFUSED A SECOND TIME, AND NOT ON [ADR-233](ADR-233.md)'s GROUND.** That entry admitted a `firm` read because a `firm` row belongs to NOBODY, so there was nothing to disclose and nothing to weigh. **`affiliates` and `affiliate_clicks` belong to somebody**, so the objection that was ABSENT there is fully PRESENT here and the argument does not transfer. Section 5 says what makes the case different in the one direction that matters, and refuses it anyway.
>
> **6. WHAT THE PORT MUST DO INSTEAD IS A STAMP AND NOT A READ.** The buyer's handler does not need to LEARN the affiliate's identity. It needs `attributions.affiliate_identity_id` written and it needs ONE BIT for the literal self-deal void. **That is [ADR-230](ADR-230.md)'s `insertAsParty` construction applied to the counterparty**: `packages/db` resolves the affiliate from the code or the token INSIDE the transaction, stamps the uuid into the row, and returns the handler a boolean rather than an identity. **This entry does not build it**, because it needs `AffiliateRef` to stop carrying `identityId` and `packages/affiliate` is outside this fence.
>
> **7. THE LEDGER ARM IS NOT THIS SESSION'S, [ADR-165](ADR-165.md)'s GROUND HOLDS, AND [ADR-176](ADR-176.md)'s REMEDY DOES NOT TRANSFER.** `SystemReason` gains no member here. What this entry adds is the half ADR-165 did not reach: ADR-176 cleared the identical obstruction for `LT-01` by DELETING `PayoutTx.ledger` and posting later at a system authority, and **`LT-08` cannot follow, because [M20](../plans/M20-wallet.md) pins it to the purchase transaction by name and `DEP-M20-02` states the consequence of moving it.** The remaining work is a ruling in `packages/ledger` and `packages/db` whose subject it is.
>
> **8. THE PORT STAYS BLOCKED AND ITS ENTRY IS REWRITTEN FOR ACCURACY RATHER THAN NARROWED.** All three clauses survive their rulings, so the entry names three things exactly as it did. **What changes is that each clause now carries its ruling and each is ASSERTED** by [`test/checkout-backend-blockers.test.ts`](../../apps/api/test/checkout-backend-blockers.test.ts) rather than only written, which is the control this entry values most: a clause that goes stale now turns a case red instead of waiting four restatements for a reader.

### 3. Ruling 1, and why the parameter's home is the finding rather than its absence

**THE TWO HALVES OF THE CAP ARE NOT IN DISPUTE AND THEY DO NOT FIT TOGETHER.**

| | Where the corpus puts it | What the corpus does with it |
|---|---|---|
| **The enforcement** | Constitution B1: *"Aggregations the business runs on are identity-level: total accounts (cap enforcement)"* | `INV-M3-08`: *"Account caps are enforced per resolved identity, never per email or per user"*. `GS-094`: *"cap of 10: the eleventh purchase is refused"*. `B4 #17`: a merge puts *"the merged entity over its account cap"*, one number belonging to one entity |
| **The parameter** | [data-model/README](../architecture/data-model/README.md) section 11, inside the `plan_versions.rules` jsonb, as `limits.max_accounts_per_entity` | [plan-config audit](../reviews/2026-08-20-plan-config-audit.md) finding C: one of two parameters *"with neither a database constraint nor an application check"*, deliberately invisible to `validatePlan` |

**SO ONE NUMBER PER PUBLISHED PLAN VERSION IS COMPARED AGAINST ONE COUNT PER IDENTITY, AND THE COUNT SPANS EVERY PLAN.** `AccountCapRow.liveAccounts` is declared *"Live accounts this IDENTITY holds"* and is read by a method that takes no plan. That is not a shape somebody chose carelessly; it is the shape the constitution requires. **The parameter is the half that does not fit.**

**THE THREE AVAILABLE READINGS, EACH REFUSED FOR A REASON THAT IS NOT THE OTHERS'.**

| Reading | Why it is refused |
|---|---|
| **The purchased version's number** | An identity's effective cap becomes the MAXIMUM over every published version, because a buyer at the cap on one plan buys the plan with the larger number. `B4 #21` requires that *"caps must bound worst-case extraction to the computed ceiling"*, and this computes the ceiling from a number the adversary selects |
| **The pinned version's number, on the reset path** | An account is pinned to the version it was sold under, permanently and provably (`B4 #12`, and `0004_catalog.sql`'s own header). A reset therefore reads a RETIRED row, so two identities holding identical accounts are capped differently by which year they bought in |
| **A value every published version must agree on** | This is a firm parameter stored in a per-plan blob. A cross-row agreement is not expressible as a `CHECK`, which `0004_catalog.sql` already records about a different leaf of the same jsonb: a conditional not-null *"cannot be a CHECK over the parent's `rules` jsonb"*, so `SD-10` materialized the leaf onto a column instead. Materializing this one does not help, because the disagreement is between ROWS rather than between a row and its parent |

**THE THIRD READING IS THE ONE WORTH REJECTING SLOWLY, BECAUSE IT ALMOST WORKS AND IT IS WHAT A CAREFUL SESSION WOULD REACH FOR.** Enforce agreement at publish, in `POST /admin/plans/:id/versions`, and then read any version's number. **It fails on the reset path and it fails in the direction that costs money**, because a retired version was published before the agreement rule existed and no later publish can reach back to it. It also concedes the whole point: a parameter every version must agree on is not a plan parameter, and storing it per version is then a replication with a validator bolted on rather than a design.

### 4. Ruling 3, and the shape is taken from a table that already exists

**`price_floors` IS THE PRECEDENT AND IT IS AN EXACT ONE.** Its registry rule reads: *"THE HARD STOP UNDER STACKING ARITHMETIC, AND IT IS THE FIRM'S NUMBER. The table declares no foreign key at all, carries no identity column, and there is no correct one, because a floor that differed per trader would not be a floor."* Its grain is `(product_ref, effective_from)`, so a change is a new row rather than an update, and `approved_by text NOT NULL` records who authorised it on `0002`'s actor idiom.

**A CAP THAT DECIDES WHO IS REFUSED A PURCHASE IS THE SAME CLASS OF NUMBER AS A FLOOR THAT DECIDES WHAT A PRICE MAY NOT GO BELOW.** It is the firm's, it is versioned, it is approved by a person, and its history has to be quotable, because `INV-M3-08`'s refusal is a `409` a buyer will ask about. `wallet_spend_limits` is the same idiom one class over: *"supersession is a new row rather than an update, so a limit dated in the future has not arrived and does not bind yet"*.

**THE ALTERNATIVE THAT NEEDS NO NEW TABLE IS NAMED AND REFUSED.** `identities.max_accounts_override` could be made `NOT NULL` with a DDL default, which puts the whole cap on a row `accountCap()` already reads. **It is refused because a DDL default is a constant**, and the corpus is explicit that these values are *"a launch candidate re-confirmed at launch, never a constant"*; because changing the platform cap would then be a migration plus a backfill of every identity row; and because it erases the distinction between the base and the exception that the column's own name carries.

**WHY THE ROW IS NOT BUILT HERE, STATED AS A FENCE RATHER THAN AS A DIFFICULTY.** A new `firm` table is a migration, a Drizzle declaration in [`schema.ts`](../../packages/db/src/schema.ts) and a classification in [`scope.ts`](../../packages/db/src/scope.ts). **Both files are session 427's this wave and the row that dispatched this session says STOP AND REPORT rather than edit.** A column added to an existing table needs `schema.ts` for the same reason. **So the cap is RULED and NOT BUILT, and no migration number is taken**, because [ALLOCATION](ALLOCATION.md)'s own record of what a premature reservation costs is four paragraphs long and this entry is not adding a fifth.

### 5. Ruling 5 and 6, the cross-identity read, and what makes this case different in the one direction that matters

**[ADR-233](ADR-233.md) SECTION 5 ALREADY REFUSED THIS AND THE ROW WAS RIGHT TO WARN AGAINST REUSING ITS ARGUMENT.** That section's ground is that a `firm` row belongs to nobody. **These rows belong to somebody**, so the ground is unavailable and a reader who reaches for it has made a mistake. This section says what IS different, and then refuses anyway.

**WHAT IS GENUINELY DIFFERENT: THE BUYER IS NOT A STRANGER TO THIS ROW.** [ADR-008](ADR-008.md) filters an `owned` read because the row is somebody else's and the caller has no relation to it. A buyer presenting a coupon code or a click token holds a token the affiliate GAVE THEM, and the row they would reach is the one that token names and no other. **That is a real distinction and it is why this question was worth asking twice.** [ADR-230](ADR-230.md) leaned on it explicitly, declining to validate `insertAsParty`'s counterparty on the ground that *"the identity it names is one the caller already held"*.

**AND IT IS NOT ENOUGH, FOR THREE REASONS THAT DO NOT DEPEND ON EACH OTHER.**

1. **A TOKEN IS NOT AN AUTHORISATION.** `affiliate_clicks_token_uq` makes the token name one row, and nothing about holding it says the affiliate consented to being identified to the holder. A click token is picked up by following a link, which anybody can do to anybody's link.
2. **THE HANDLER WOULD LEARN A UUID IT HAS NO USE FOR.** The checkout response carries no affiliate field. The identity is wanted for one column and one comparison, and every door in `packages/db` returns WHOLE ROWS, which [ADR-231](ADR-231.md)'s own approval block names as where it is most likely wrong. **Granting a whole-row read to serve one column and one bit is the widest possible answer to the narrowest possible question.**
3. **THE REGISTRY HAS NOWHERE TO WRITE THE EXCEPTION.** `OwnedRule` carries `class`, `column`, `nullable` and `why`. A per-table grant saying which columns of another identity's row a buyer may see is a field that does not exist, and ADR-233 refused to invent it from inside a fence that was not its subject. That is still true.

**SO THE REMEDY IS A STAMP AND NOT A READ, WHICH IS THE PART ADR-233 REGISTERED AND DID NOT NAME.** The handler needs two things and neither is an identity:

| What the handler needs | How it gets it without a cross-identity read |
|---|---|
| `attributions.affiliate_identity_id` on the row it writes | **`packages/db` stamps it.** `insertAsParty` already stamps the BUYER from the handle and refuses a caller naming it. The counterparty is resolvable from `coupons.affiliate_id` or `affiliate_clicks.affiliate_id` inside the same transaction, so the uuid never crosses into `apps/api` at all |
| The literal self-deal bit, for `attributions_literal_self_deal_is_void` | **A boolean on the resolved reference.** *"Is this affiliate the caller"* discloses nothing the caller does not already hold: a buyer using their own code knows it is theirs, and a buyer using somebody else's learns only that it is not theirs, which names nobody |

**THIS ALSO CLOSES THE CONTRADICTION ADR-233 SECTION 5 REGISTERED AND COULD NOT REPAIR.** That section found that `insertAsParty` on `attributions` **has no possible caller**, because ADR-230 justified taking the counterparty from the caller on a premise no door satisfies. **The stamp satisfies it by removing the premise**: the counterparty stops coming from the caller.

**IT IS NOT BUILT HERE AND THE FENCE IS THE REASON, NOT THE SIZE.** `AffiliateRef` carries `identityId` ([`packages/affiliate/src/attribution.ts:139`](../../packages/affiliate/src/attribution.ts)) and `attribute` compares it against the buyer's ([`:369`](../../packages/affiliate/src/attribution.ts)). Both must change for the bit to replace the uuid, and `packages/affiliate` is outside this entry's fence. **The successor slice is a ruling on `packages/db` plus a shape change in `packages/affiliate` plus a port change here, and it is one session's subject rather than three sessions' side effect.**

### 6. Ruling 7, the ledger arm, and the argument [ADR-165](ADR-165.md) did not have to make

**[ADR-165](ADR-165.md) CLAUSE 3 IS UNTOUCHED AND IS RE-DERIVED RATHER THAN CITED.** `SystemReason` is exactly `'nightly-batch' | 'operator-console'` at [`scoped-db.ts:267`](../../packages/db/src/scoped-db.ts), and that clause's reason is general: *"the vocabulary that moves is the TABLE and never the REASON"* ([ADR-126](ADR-126.md)). A checkout is neither word.

**AND THE THREE OTHER DOORS ARE FORECLOSED FOR REASONS THAT ARE NOT THE REASON WORD.** [`packages/ledger/src/tx.ts`](../../packages/ledger/src/tx.ts) states them and this entry checked each: a double-entry posting touches two parties by construction, so no single-identity handle writes both; `FirmTx` cannot serve it because `ledger_transactions` and `ledger_entries` are both `derived` rather than `firm`; and **[ADR-233](ADR-233.md)'s catalogue door cannot serve it either**, because that door reads `firm` rows and has no write verb at all. `ApiDb` declares `scoped`, `firm`, `resolution`, `establishment`, `publicLookup` and `transaction`, and none of them yields a `SystemTx`.

**WHAT THIS ENTRY ADDS IS THE ARGUMENT ADR-165 NEVER HAD TO MAKE, BECAUSE ADR-176 DID NOT EXIST YET.** [ADR-176](ADR-176.md) cleared this exact obstruction on the payout route by **deleting the handle**: `PayoutTx.ledger` is gone, the `LT-01` posting happens at a system authority, and the request path records the approval and stores the client's key for the door that posts it. **A session reading only ADR-165 would reach for that remedy here and it is foreclosed.**

| | `LT-01`, the payout | `LT-08`, the checkout wallet leg |
|---|---|---|
| What the corpus requires of the posting's timing | Nothing that binds it to the request | [M20](../plans/M20-wallet.md): *"LT-08 posted in the same transaction as the purchase"*, and `DEP-M20-02`: *"M3 resolves target-account ownership server side and posts LT-08 in the purchase transaction"* |
| What moving it costs | An idempotency key and a door | `DEP-M20-02`'s own consequence column: *"`INV-M20-02` fails, and the wallet becomes a transfer instrument"* (`AS-M20-06`) |

**SO THE ARM IS NOT THIS SESSION'S AND SAYING SO IS THE RESULT RATHER THAN A SHORTFALL.** The next move is a ruling on how a two-party posting is authorised from a request path, in `packages/ledger` and `packages/db`, by a session whose subject that is. **Nothing here widens `SystemReason`, invents a door, or moves the posting.**

### 7. Ruling 8, and why a partial wiring is refused rather than overlooked

**THE CARD ARM COULD BE MADE TO LOOK LIVE TODAY AND MUST NOT BE.** `CheckoutTx.ledger` is nullable and the wallet arm answers 503 when it is `null`, so a backend could be installed that serves `payment_method: 'psp'` and refuses the other two. **That is `usePayoutBackend`'s stated rule met exactly**: it puts a live-looking route in front of the arm that moves wallet value, on an endpoint whose contract accepts three payment methods.

**AND IT WOULD NOT EVEN REACH THAT FAR, WHICH IS THE CHEAPER OBJECTION.** `accountCap()` is unconditional on both paths, so a backend built today refuses every request of every payment method on its first line. **That raises the wired count and serves nothing**, which is the shape `useCheckoutAdapters`' entry already rules *"not a wiring"*, and which [ADR-233](ADR-233.md) section 6.3 refused for this same port one day ago.

### 12. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS RULING 1, BECAUSE IT MOVES A FROZEN DOCUMENT.** `limits.max_accounts_per_entity` sits in the `plan_versions.rules` example in a document that is `approved`, and this entry says that home is wrong for the enforcement the constitution requires. **If you disagree, the alternative is not "leave it there": it is to change the ENFORCEMENT to per plan**, which means an identity may hold the cap on every plan you publish, and `GS-094`'s eleventh purchase becomes the eleventh purchase of that plan. That is a coherent product and it is a different one. **Nothing can be built until one of the two moves.**

  **THE SECOND IS WHETHER THE CAP IS A NUMBER AN OPERATOR CHANGES.** Ruling 3 assumes yes, and buys a table, an approver column and an effective date for it. If the answer is that the cap changes once a year by migration, the cheaper `identities.max_accounts` default this entry refuses in section 4 becomes defensible and the slice shrinks a lot.

  **THE THIRD IS RULING 6's DISCLOSURE ARGUMENT**, which is the one place here a reasonable person lands elsewhere. This entry says the handler may learn *"is this affiliate you"* and may not learn *"who is this affiliate"*. **A stricter reading says the bit is also a disclosure**, because a buyer who tries a coupon code and gets a self-deal void has confirmed the code belongs to an identity they control, which matters if identities can be merged after the fact. **That is a narrow case and it is real**, and if you take the stricter reading then attribution cannot be resolved in the request path at all and the whole fold moves to a job, which is a much bigger slice.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **Ruling 1's central claim rests on `liveAccounts` being an identity-wide count, and no implementation of `accountCap` exists to confirm it.** The field's declaration says *"Live accounts this IDENTITY holds"* and the constitution says cap enforcement is an identity-level aggregation, and both are prose. **If the intended count was per plan all along, ruling 1 is wrong in its entirety and the purchased version's number is simply correct.** No test in this branch can settle that, because the thing that would settle it is the adapter this port does not have.
