## ADR-073: A gate-inventory row closes when it is implemented or carries a dated activation condition, `CI-09` ships one leg of four, and `VG-11` is struck from `CI-07`  (2026-08-20, status: accepted)

**`OI-26` is the finding that [STRATEGY section 4.1](../testing/STRATEGY.md) rows ten pipeline stages and Actions runs five of them.** The finding is correct. This ADR rules what follows from it, which is not a queue of workflows: it states when a row of that inventory is **closed**, so that "the inventory is complete" becomes a property a gate can read rather than a claim a session can make.

**Every number below was measured on this tree rather than carried from the plan that commissioned this ruling, and two of the plan's own lines did not survive that.** They are section 1.

## 2. The ruling

> **A row of [STRATEGY section 4.1](../testing/STRATEGY.md) is CLOSED when one of three things is true of it, and a row that is none of the three is a finding.**

| | Disposition | What the row must carry | What makes it checkable |
|---|---|---|---|
| **(a)** | **Implemented** | The workflow file and the **job name** that runs it | Both resolve on disk. A job name is a string in a file, not a claim about a run |
| **(b)** | **Waiting**, with a **dated activation condition naming the artifact** | A date and **one artifact**, stated as a path or as a manifest key | The artifact's presence is a command. **The condition is two-sided**: while the artifact is absent the row is closed, and **the day it arrives the row is a finding until the stage is written** |
| **(c)** | **Discharged outside Actions** | The register that carries the obligation | The register resolves and rows the work. This exists for `CI-10` and section 4 is the whole of its scope |

**(b)'s second sentence is the entire value of the ruling and the reason it is not a note in a document.** A "deferred" row decays into a row nobody rereads. A row whose condition is read by a gate cannot: it converts the arrival of a `build` script from something a person has to notice into something CI reports on the commit that adds it.

**Three limits, stated here rather than discovered by the session that builds the gate.**

- **This ADR rules on the STAGE row and not on the `VG` row.** A stage can be implemented while a gate assigned to it is not: `VG-5` is assigned to `CI-06`, `CI-06` runs, and `VG-5` is not wired. Section 4.2's twelve rows are **not** in this ruling's scope, and section 8 is what follows from that.
- **An implemented row is not thereby a row that proves what it claims.** `CI-02`'s own [STRATEGY](../testing/STRATEGY.md) row promises the `PT-nn` and `Mxx-*-nn` suites and the tree has neither. Disposition (a) asserts that a job exists, never that its contents cell is true, and that boundary is the same one `CI-06r` and `CI-06q` each state about themselves.
- **One artifact per condition.** A condition naming two artifacts cannot fail cleanly, because the gate cannot say which half arrived.

## 3. The alternative, argued: write `CI-07` now

**This is the option to defeat, because it is the one that looks like progress.** A `CI-07` job can be written today. It would install, run a bundle grep against `apps/*/dist`, find no directory, and either skip or fail.

**The prompt offers two citations for rejecting it. One is being stretched and survives the stretch; the other names the wrong harness. The line that actually settles it is in the tree and neither citation is it.**

| Citation | What it says where it lives | Does it reach `CI-07` |
|---|---|---|
| [STRATEGY section 4](../testing/STRATEGY.md): *"a gate added as advisory is a gate that stays advisory"* | It is the second half of a sentence about **extending the inventory**: *"the rule for extending it is that a new gate arrives with its blocking level decided, because..."* It governs the **blocking level** at the moment a gate is added | **Only through one added step, and the step holds.** A stage whose artifact does not exist can only skip, and a stage that always skips is an advisory whatever its `if:` says. **Stretched, and it survives being stretched** |
| [`falsify.mjs`](../../scripts/corpus/falsify.mjs) makes a gate that cannot pass the tree an ERROR | True, and of the wrong population. `falsify.mjs` runs the **`GATES` in [`gates.mjs`](../../scripts/corpus/gates.mjs)**, which are the `CI-06` corpus checks. Pipeline stages are falsified by [`falsify-ci.mjs`](../../scripts/ci/falsify-ci.mjs), which **has no clean phase at all**, by explicit design: *"THE CLEAN DIRECTION IS THE STAGE ITSELF"* | **No.** `CI-07` is a stage, so the harness cited never runs it clean and cannot report it. **Stretched, and it does not survive** |
| [`repo-invariants.mjs`](../../packages/tooling/checks/repo-invariants.mjs) rule 2: *"A CHECK THAT CANNOT RUN IS NOT A CHECK THAT PASSED. Any check that cannot reach its inputs throws, which is a non-zero exit, not a skip"* | Stated as one of the two rules that file and `gates.mjs` are both written under, and **inherited verbatim** by [`falsify-ci.mjs`](../../scripts/ci/falsify-ci.mjs): *"A MISSING TOOL IS AN ERROR, NOT A SKIP"* | **Yes, and it closes both branches.** The skip branch is forbidden by name. The fail-forever branch is forbidden by [STRATEGY section 1](../testing/STRATEGY.md): *"A test suite whose failures are not trusted is worse than a smaller suite whose failures are, because the first one trains its own reader to click through red"* |

> **RULED: `CI-07` is not written now.** Not because writing it is premature, but because the tree already forbids both shapes it could take, and it forbids them in a file that runs on every push.

**The honest cost of the ruling, stated so it is not discovered later.** Disposition (b) buys nothing on the day it is taken. What it buys is the day the artifact arrives, and if `CI-06/gate-inventory` is never built, this ADR is prose. **The ruling is worth exactly what that gate is worth**, and that is why section 6 states what the gate must read rather than leaving the shape to the session that writes it.

## 5. `CI-09`'s scope: one leg is built and three take conditions

**The referring plan says three of `CI-09`'s four legs "have a subject" and concludes that `CI-09` is built. The first half is true and the second does not follow, because HAVING A SUBJECT AND HAVING AN INPUT ARE DIFFERENT THINGS.** The replay self-audit is the leg where they come apart, and it comes apart quietly.

| Leg | Subject | Input | Ruled |
|---|---|---|---|
| **Simulation harness** | [`packages/harness`](../../packages/harness/README.md), 4,382 lines over nine source files and seven suites, exporting `runHarness` and `runSweep`, folding the real engine | **Needs none.** Pure compute from a seed, and [`rng.ts`](../../packages/rithmic/src/simulator/rng.ts)'s keyed determinism is what makes a nightly run reproducible | **BUILT** |
| **Replay self-audit** | [`replay.ts`](../../apps/worker/src/batch/replay.ts), 409 lines, exporting `runReplayAudit` | **Absent.** It takes `BatchPorts` and reads `accountsWithStoredState`, `storedRuleStates` and `accountDaysFrom` from a database. **There is no seeded demo world**: [`packages/db/src/seed/`](../../packages/db/src/seed/calendars/README.md) holds calendar source files and nothing else, and [INFRA](../architecture/INFRA.md)'s demo seed is described as a plan | **(b) Waiting, 2026-08-20**, on a demo-world seed script |
| **Stryker on the engine** | [`packages/rules-engine`](../../packages/rules-engine/README.md). A genuine target: `RI-01` holds its manifest free of workspace dependencies in all four fields and `RI-07` holds its module graph free of Node builtins, which is what makes mutants meaningful there and nowhere else | **Needs a new dependency**, and that is a `VG-12` admission. Section 6 | **(b) Waiting, 2026-08-20**, on the `VG-12` admission |
| **Detector canary** | **None.** `canary` appears in no `.ts` file in the tree. `INV-M7-07` and the `M7-S-nn` suites are [M07](../plans/M07-risk-abuse.md)'s | Absent with the subject | **(b) Waiting, 2026-08-20**, on M07's detector code |

**The replay leg is the one that would have been built on the plan's reading, and what it would have produced is worth spelling out.** `runReplayAudit` throws `ReplayAuditRefusal` when `storedRows > 0 && inScope === 0`, and that guard is `OI-14`'s, added because *"a refusal that returns a report can be read like a clean one."* **With zero stored rows the guard does not fire.** The nightly would report `accountsAudited: 0`, `diverged: 0` and exit green, every night, over nothing. That is `OI-14`'s own defect reproduced one level up, in the place its guard cannot see.

> **So the obligation travels with the condition rather than being lost with it: when the replay leg is built, it refuses on `accountsAudited === 0`.** A leg whose activation condition is a seeded world must assert that the world is there.

**One correction to the referring plan's arithmetic, which changes nothing and would otherwise be copied.** WAVE-04 section 3 gives `packages/rules-engine` as **10,264 source lines**. The tree gives **5,732** across 17 files under `src/`, and **20,995** including `test/`. Neither is 10,264 and the figure reproduces nothing. It is not load bearing: the argument for Stryker on the engine is the purity boundary, not the size.

**And `CI-09` built with one leg still discharges what the plan wanted from it.** Session 106's landmine is that `packages/harness` *"exists with its own tests; nothing calls it"*, which this session confirmed: no file outside the package imports `@merit/harness`. **The simulation-harness leg is the consumer**, and it is the leg that needs neither a database nor an admission.

## 6. Stryker, `VG-12`, and what `OQ-TS-02` is left holding

**The admission is not spent here, and the reason is not cost.** `VG-12`'s mechanical half is wired; its **human** half is not a thing this session or the next one can perform. [Session 23](../sessions/2026-08-15-session-23.md) records why: *"a job can see the dependency surface changed and cannot see that a human agreed"*, so the approval lives in `.github/CODEOWNERS` plus a branch-protection setting, and **that session's blocker is still open**: *"One founder action: turn on Require review from Code Owners for `main`."*

> **RULED: Stryker is an activation condition and not a purchase.** A session that installs it would be granting itself the admission the gate exists to withhold, on a branch where the enforcing setting may still be off.

**`OQ-TS-02` asks whether Stryker's mutation score is ever a gate or only a trend. This ADR does NOT settle it, and it narrows it in a way the founder should have before answering.**

`RI-02` asserts that **no coverage threshold exists anywhere in the tree**, scanning every `.js`, `.mjs`, `.cjs`, `.ts`, `.mts`, `.cts`, `.json`, `.yaml` and `.yml` file, and one of its needles is `/thresholds\s*:/i`. Stryker's configuration carries a `thresholds` block. Checked rather than assumed:

| Config form | Text | `RI-02` |
|---|---|---|
| `stryker.conf.mjs` or `.js` | `thresholds: { high: 80, low: 60, break: null },` | **MATCH.** A finding at `CI-01`, which blocks merge |
| `stryker.conf.json` | `"thresholds": { "high": 80, "low": 60, "break": null }` | **No match.** The `"` between the key and the colon defeats the needle |

**So the tree already forbids one spelling of a Stryker threshold and permits the other, and neither outcome is a ruling anybody made.** `RI-02`'s own `covers` line is honest that it is *"a SPELLING check in both directions"*, so this is the stated limitation firing rather than a bug. **What the founder is being handed is a sharper question than the one `OQ-TS-02` asks**: not only whether the score is a gate, but whether `RI-02`'s vocabulary should reach a mutation threshold at all, given that its argument (*line coverage measures how much code was executed, which is the one quality signal generated tests inflate for free*) is an argument about coverage and **not** about mutation score, which is the one metric generated tests do not inflate for free.

**`OQ-TS-02` therefore stays open, and it is now blocking nothing**, because the leg it governs is behind an admission that has not been spent.

## 7. `VG-11`, assigned to two stages in one document

**[STRATEGY](../testing/STRATEGY.md) rows `VG-11` twice and the two rows disagree.** Section 4.1 lists it in `CI-07`'s contents; section 4.2 rows it as `CI-02`, blocking merge. One is wrong.

**Where the error came from, which is checkable rather than inferred.** [INFRA](../architecture/INFRA.md)'s gate graph chains `G2 -> G10 -> G11 -> D10`. `CI-07`'s contents cell reads *"VG-2, VG-10, VG-11, D0-10"*: **the same four identifiers in the same order.** The contents cell is a transcription of that chain, and the chain is the half of INFRA that contradicts INFRA's own table one screen below it.

**Three independent reasons the section 4.2 row is the correct one.**

| | Evidence |
|---|---|
| **The implementation is stated identically in three documents and it is not a build check** | [VIBE_FAILURE_POSTMORTEMS](../../research/VIBE_FAILURE_POSTMORTEMS.md), which is where the `VG` series is defined, rows *"VG-11 strip upload metadata | **upload-path unit test** | CI"*. [INFRA](../architecture/INFRA.md)'s table rows *"unit test on the upload path"*. STRATEGY 4.2 rows *"unit test on the upload path"*. **A unit test is `CI-02`'s contents.** A bundle grep, a live bucket-policy probe and a request against production config are the other three, and none of them is a unit test |
| **The blocking levels are incompatible** | All three documents give `VG-11` the level **merge**. `CI-07`'s other three occupants block **deploy**, and INFRA's graph puts the whole `BUILD` chain **downstream of `MERGE`**. **A gate that blocks merge cannot be implemented by a stage that runs after merge** |
| **`VG-11` needs source and the stage's input is an artifact** | `CI-07`'s row is qualified *"against the production build"*. Stripping metadata on upload is a property of a code path, provable with no build at all, which is why it is the one member of that list not waiting on the artifact `CI-07` is waiting on |

> **RULED: the section 4.2 row stands. `CI-07`'s contents cell is the losing row and `VG-11` is struck from it.** `CI-07` gates `VG-2`, `VG-10` and `D0-10`.

**Two consequences that are not repaired here, both because the files are outside this session's fence, and both recorded so they are not rediscovered.**

- **[INFRA](../architecture/INFRA.md) contradicts itself in the same way and is the origin.** Its graph places `G11` after `MERGE` while its table blocks merge on it. The repair is to the graph.
- **[STATE](../STATE.md) carries the losing assignment**, in the `VG-1 to VG-12` row of the P1 table: *"VG-2, VG-10 and VG-11 to CI-07"*. Under this ruling `VG-11` is assigned to a stage that **does** exist, so the count in that row is unaffected and only the reason changes: `VG-11` is unwired **inside a running stage**, which is `VG-5`'s case rather than `VG-2`'s.

## 8. What this ADR does not do, and P1 is still not closed

**`OI-26` opened on the sentence "P1's definition of done is the full gate inventory". That sentence is not what [DELIVERY_PLAN section 4](../DELIVERY_PLAN.md) says**, and the difference decides whether this ADR closes anything.

| P1's | DELIVERY_PLAN's words |
|---|---|
| **Contents** | *"Monorepo scaffold, the reconciled schema and migrations, TradingCalendar as data, CI with the full STRATEGY gate inventory including VG-12 and the corpus-integrity checks"* |
| **Definition of done** | *"Every VG gate wired and failing correctly on a seeded violation. VG-12 is not deferred"* |

> **The gate inventory is P1's CONTENTS. Its DEFINITION OF DONE is the twelve `VG` gates, and [STATE](../STATE.md) measures that at THREE OF TWELVE.**

**So closing all ten rows of section 4.1 advances the contents half and does not close P1.** This ADR rules the stage rows; it rules nothing about `VG-2`, `VG-3`, `VG-5`, `VG-6`, `VG-9`, `VG-10` or `VG-11`, six of which are unwired because their stage does not run and one of which (`VG-5`) is unwired inside a stage that does.

**That is a second ruling waiting to be asked for and this ADR deliberately does not take it.** Extending disposition (b) to section 4.2's twelve rows is the obvious next move and it is a different question: a `VG` row's condition is its **stage**, which makes the conditions chain, and a chained condition is a shape nobody has ruled. **It is named here so the next session proposes it rather than assuming this one covered it.**

**It also does not write a gate.** `CI-06/gate-inventory` is a later session's, and what it must read is stated in section 2 so that session does not have to infer the parse: for every row of section 4.1, exactly one disposition; every job named by (a) resolving in the workflow file named beside it; every artifact named by (b) resolving to **absent**; and the register named by (c) resolving. **The third of those four is the assertion that does the work**, and it is the one an implementer is most likely to leave out, because it is the only one that fails on good news.

- **Alternatives considered.**

  - **Write `CI-07`, `CI-08` and `CI-09` now, as the finding's plain reading suggests.** Rejected in section 3. The decisive citation is `repo-invariants.mjs` rule 2 rather than either of the two the referral offered, and one of those two does not reach a pipeline stage at all.
  - **Write `CI-07` and `CI-08` as skipped jobs, so the rows are literally implemented.** Rejected as the same thing wearing the disposition it is trying to earn. A job whose every step is `if: false` satisfies (a) by a parse and satisfies nothing else, and it is strictly worse than (b) because it removes the day the condition would have fired.
  - **Leave the open rows as prose, marked "deferred", with no dated artifact.** Rejected: it is what the rows carry today. The reason `CI-07` sat unnoticed since P1 was declared closed is that nothing could read its state, and a marker no gate reads is the same marker.
  - **Delete `CI-07` and `CI-08` from the inventory until their artifacts exist.** Rejected on the stronger version of the same argument. The rows carry the `VG` assignments for `VG-2`, `VG-10` and `D0-10`; deleting them would delete the record that those gates are assigned somewhere, and STATE's *"the other nine are not late, they are assigned to stages that do not exist"* would stop being checkable against anything.
  - **Build all four `CI-09` legs, treating "has a subject" as sufficient.** Rejected in section 5: the replay leg would report a clean audit over zero accounts, nightly, which is `OI-14`'s defect one level above the guard that catches it.
  - **Spend the `VG-12` admission on Stryker here, since the engine is the one valid target.** Rejected in section 6: the admission's human half cannot be performed by a session, and session 23's founder action to enforce it is still open.
  - **Rule `OQ-TS-02` closed while holding the file.** Rejected. `RI-02` already decides one spelling of it mechanically and the other by omission, and a ruling written on top of an accident is worse than an open question.
  - **Rule that `VG-11` belongs to `CI-07`, repairing section 4.2 instead.** Rejected on three independent grounds in section 7. It is the reading the identical ordering in INFRA's graph invites, which is why the provenance is recorded rather than only the verdict.

- **Consequences:**

  - **[STRATEGY section 4.1](../testing/STRATEGY.md) gains a `Closure` column and every one of its ten rows carries a disposition.** No row is added: the four `CI-06` slug gates are a later session's and take slugs under [ADR-065](ADR-065.md), not rows here.
  - **`CI-07`'s contents cell loses `VG-11`.** Section 4.2 is untouched.
  - **`CI-04` is given a condition although the referring prompt named only three rows.** Stated plainly because it is a widening: applying the rule to three of four open rows would hand `CI-06/gate-inventory` a table it must reject on the day it first runs.
  - **`CI-09` is built with one leg of four**, which is smaller than the plan assumed and is the whole of what the tree supports. It gives `packages/harness` the consumer it has never had.
  - **Four activation conditions now fail on good news**: a `build` script, an installed Playwright, a Neon branch, a demo-world seed, plus the `VG-12` admission and M07's detector code inside `CI-09`. **Each is a commit somebody would otherwise land without noticing the row it reopens.**
  - **`OQ-TS-02` stays open and stops blocking.** `OQ-TS-01` and `OQ-TS-03` are untouched.
  - **P1 does not close on this ADR.** Its definition of done is the twelve `VG` gates and three are wired. Section 8 names the ruling that would be needed and does not take it.
  - **No gate, no workflow and no script changed in this session.** The ruling is read by two later sessions and neither of them is this one.

- **Founder approval: GRANTED 2026-08-21.** Given as an **explicit delegated approval**, not as a line-by-line read; [E2](../../MERIT_BUILD_MASTER_PROMPT.md) reserves that read for the money path and this entry is not on it. Section 1's correction and section 8's boundary were read first, as the entry asked.

  **This signature was owed rather than optional, and the reason is that the ruling was already load bearing.** Session 121 built `CI-06/gate-inventory` against these dispositions and it runs on `main` today, which means **a blocking gate was enforcing an unsigned proposal**. That session named the position rather than resolving it, correctly: *"this gate now blocks merge on it; that is the founder's to resolve, not this session's."* A gate that enforces a ruling nobody signed is the same defect as a ruling nobody enforces, one direction over.

  **Two things the implementation proved about the ruling, and both survived.** `CI-09` was built on exactly the leg section 5 rules `BUILT` and no other, and section 4's four open rows were readable as written: `CI-04` still waits on a Neon branch no session can produce, and the gate asserts the CONDITION is present and dated rather than that the artifact exists. **The distinction section 4 draws is the one a gate can actually check**, which is the test this entry needed to pass.

  **Section 8's boundary is unmoved by this signature.** Extending disposition (b) to section 4.2's twelve `VG` rows is a second ruling, their conditions **chain**, and no entry has ruled that shape. It is named here and stays unowned.
