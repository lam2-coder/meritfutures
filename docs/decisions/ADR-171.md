## ADR-171: the third door is REFUSED, and the reason is a measurement rather than the argument it was allocated against: it unblocks none of the five ports (2026-08-28, status: proposed)

**[ALLOCATION](ALLOCATION.md) row `171` reserved this number REQUIRED under the heading _"ONE RULING UNBLOCKS FIVE PORTS"_, and named the five: `setAdminReadSource`, `setAdminSessionSource`, `useAdminPayoutBackend`, `useAdminWalletBackend` and `useAdminWriteBackend`, each said to wait on `systemDb('operator-console')`, which [`apps/api/src/db.ts`](../../apps/api/src/db.ts) declines to declare under [ADR-120](ADR-120.md) clause 3.** This entry read the five ports at their own declarations before ruling on the door, and **the premise does not survive the reading**. Four of the five wait first on a RESOLVED OPERATOR PRINCIPAL, which no door onto the trader database can produce because **the operator directory is not in this database**; the fifth says in its own header that what it is missing _"is not an authority, it is a shape"_. **The door is refused, ADR-120 clause 3 stands, and the wired count stays at 6 of 21** -- not because a third door would be unsafe in the abstract, but because opening it today moves nothing and hands every adapter in the deployable an unscoped read and write over every identity's rows.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `171`, session **306**, dispatched as `claude/operator-door`. The number was RESERVED before dispatch and the reservation names it **REQUIRED**, so the row is amended in place ([ADR-065](ADR-065.md) T3, `CI-06f`). **NOT MONEY BY FILE**: no migration, no `SD-nn`, no `packages/db` change, no route, no gate, no handler logic. **Money by what it governs**: two of the five ports are the money path, and the thing being ruled on is which authority the deployable serving the whole public trader surface may open a connection at.

- **Context:** [Session 302](../sessions/2026-08-27-session-302.md) built [`apps/api/test/wiring.test.ts`](../../apps/api/test/wiring.test.ts), measured `apps/api` at 6 of 21 backend ports, and wrote the sentence this session was dispatched against: _"five of the fourteen remaining ports are one ruling and not five slices."_ That sentence was written from the ports' BLOCKED reasons. This session read the ports.

- **[ADR-165](ADR-165.md) closed the vocabulary question the day before.** `SystemReason` is `'nightly-batch' | 'operator-console'` ([`scoped-db.ts:197`](../../packages/db/src/scoped-db.ts)), it already carries the operator word, and that entry ruled it gains no member. **So no widening was ever needed and none is taken here.** The question was only ever whether `ApiDb` declares a third door onto a word that already exists.

### 2. THE RULING

> **1. [`apps/api/src/db.ts`](../../apps/api/src/db.ts) DECLARES NO THIRD DOOR AND [ADR-120](ADR-120.md) CLAUSE 3 STANDS UNAMENDED.** `scoped(identityId, fn)` and `firm(fn)`, and no `operator(fn)` beside them. That clause's alternatives list refused _"a `system(reason, fn)` door in `db.ts` FOR LATER"_ and this entry finds that the offer on the table today is exactly that one.
>
> **2. THE REASON IT STANDS IS A MEASUREMENT AND NOT A RESTATEMENT OF THE ARGUMENT IT WAS ALLOCATED AGAINST. THE DOOR UNBLOCKS ZERO OF THE FIVE.** Section 4 walks each port to its own declaration. `setAdminSessionSource` is the SSO port itself and no database door can serve it; `setAdminReadSource` is blocked on a read shape and says so; the three write backends each require `principal(request)`, which reduces to `setAdminSessionSource`, and each carries at least one further blocker of its own. **A door whose whole justification is five callers, and which has none, is a primitive admitted before a caller exists** ([`job-queue.ts`](../../packages/queue/src/job-queue.ts)'s rule, cited by ADR-120 clause 3 for this exact refusal).
>
> **3. THE BLAST RADIUS IS THE ARGUMENT THAT WOULD HOLD EVEN IF THE COUNT WERE FIVE, AND IT IS SPECIFIC RATHER THAN GENERAL. `ApiDb` IS A PARAMETER AND NOT AN IMPORT.** Every adapter in this deployable is `databaseX(db: ApiDb)` and every one is handed `LIVE_DB` by [`start.ts`](../../apps/api/src/start.ts). So a third method on `ApiDb` is not a capability the admin adapters acquire; it is a capability **`databaseAuthBackend` acquires**, in the file whose entire design is that it cannot have one. Section 5 is that argument and it is the strongest thing in this entry.
>
> **4. THE ONE-FILE, TWO-DOOR CONVENTION BECOMES AN ASSERTION, WHICH IS THE MECHANICAL FORECLOSURE A REFUSAL OWES.** [`apps/api/test/db.test.ts`](../../apps/api/test/db.test.ts) pins the door count and their names, pins the value imports `db.ts` takes from the accessor so that `systemDb` arriving is a red suite rather than a diff somebody has to notice, and asserts that exactly one file under `apps/api/src` imports `@merit/db`. **[ADR-165](ADR-165.md) section 10 finding 5 named this repair, called it six lines, and named this fence as the one that could make it.**
>
> **5. THE `BLOCKED` REASONS ARE CORRECTED AND THE TRIPLE DOES NOT MOVE.** `{ declared: 21, wired: 6, blocked: 15 }` is unchanged. Five reasons are rewritten to name the blocker each port actually has, one of them because it was measurably FALSE (finding 10) and one because it told the reader a door would reach an operator session (finding 4). **A reason that misnames the obstruction is worse than a short one, because it retires the question in the wrong direction**, and it is what produced this session's own dispatch.
>
> **6. WHAT WOULD CHANGE THIS RULING IS WRITTEN AS A CONDITION AND NOT LEFT TO THE NEXT SESSION'S JUDGEMENT.** Section 9. The door is takeable by the slice that lands an `AdminSessionSource` a deployment can install, because that slice is the first one for which the door has a caller that reaches a row.

### 3. Clause 1, and the question the dispatch put in three parts

The dispatch asked the entry to answer three things if it opened the door. **They are answered here in the refusal**, because an entry that refuses without answering them has not shown its work.

**(a) WHAT AN OPERATOR-CONSOLE HANDLER MAY REACH THAT A TRADER HANDLER MAY NOT.** Everything, and that is not a figure of speech. `scoped(identityId, fn)` composes a tenancy predicate onto every read and stamps the identity onto every insert; `firm(fn)` takes `FirmTableKey` and a `firm` row belongs to nobody by construction. `SystemTx` is declared over `TableKey` -- every key in the registry, `owned`, `derived`, `pair`, `root` and `firm` alike -- with `insert`, `updateAt` and `deleteAt` on it and no predicate anywhere except the address the caller writes ([`scoped-db.ts:1798-1831`](../../packages/db/src/scoped-db.ts)). **The two existing doors are narrowings of the estate; the third is the estate.** What makes it safe in `apps/worker` is that the deployable has no caller to resolve and no request to serve ([ADR-165](ADR-165.md) clause 2); neither of those is true here.

**(b) WHO RESOLVES THE OPERATOR'S PRINCIPAL, AND HOW THE DOOR KNOWS IT.** **Nobody in this repository, and that is the finding rather than a gap this entry works around.** The dispatch's own framing is right and is the reason the door fails: the door must not open before the principal resolves, or it is an unauthenticated system handle in a request path. The resolution is `AdminSessionSource.lookup(token)`, whose supplier is the admin identity provider behind `ADMIN_ORIGIN` (finding 5), and **the database holds no operator, no role and no operator session to resolve against** (finding 4). So the ordering constraint the dispatch names cannot be satisfied by anything in this tree: there is no resolution for the door to come after.

**(c) WHAT IT FORECLOSES.** Section 6. A convention that says "reach for `scoped` unless you cannot" is the convention every future handler is one deadline away from reading the other way, and clause 4 replaces the part of it that is checkable with a check.

### 5. Clause 3, and the file a third door would actually change

**THE DOOR WOULD BE OPENED FOR THE ADMIN CONSOLE AND SPENT IN THE AUTH SURFACE, AND THIS IS A DERIVATION RATHER THAN A WORRY.**

[ADR-120](ADR-120.md)'s headline finding is `B1`: **a pre-identity read has no door at any authority.** `users.email` is `citext NOT NULL UNIQUE` and `users` is scope class `owned` on `identity_id`, so resolving an address to a person requires already knowing the person. The refusal is written in one constant so twelve error messages cannot drift apart, and it names the exact escape it is refusing ([`auth-backend.ts:290-296`](../../apps/api/src/auth-backend.ts)):

> _"`firmDb()` refuses an `owned` key and `systemDb`'s reason vocabulary is `nightly-batch | operator-console`, **which a request handler is not in**."_

**`databaseAuthBackend` TAKES AN `ApiDb`** ([`auth-backend.ts:347`](../../apps/api/src/auth-backend.ts)). It is handed `LIVE_DB` by [`start.ts`](../../apps/api/src/start.ts), the same value every other adapter is handed. **So the day `ApiDb` declares `operator(fn)`, `db.operator(tx => tx.rowAt('users', { email }))` is in scope inside that file**, and `B1` -- the single most-wanted missing construction in this deployable, blocking `verifyOtp`, which the entry that found it calls _"the corpus's most load-bearing endpoint"_ -- falls to one line, at the reason word `'operator-console'`, inside a handler serving an anonymous request.

**THAT IS NOT A SLIPPERY SLOPE, IT IS THE FIRST STEP OF ONE, AND IT IS AVAILABLE ON THE DAY THE DOOR LANDS.** Twelve of `AuthBackend`'s sixteen methods refuse today and several refuse on `B1` alone. A door opened for an admin console nobody can authenticate into would be, from the first hour, the shortest path past the refusal that entry was written to record. **`SystemReason` is a closed vocabulary precisely so that "forgot to scope" becomes "wrote the word system"** ([ADR-084](ADR-084.md) section 5, quoted by [ADR-165](ADR-165.md) section 5). Putting the word behind a method on the object every adapter already holds is the inverse of that design: it makes the unscoped authority the thing a caller reaches by ACCIDENT rather than by writing a word somebody reviews.

**THE NARROWER DOOR WAS CONSIDERED AND IT DOES NOT SURVIVE THE SAME TEST.** A door typed over a union of the admin tables rather than over `SystemTx` -- `operator<T>(fn: (tx: AdminTx) => Promise<T>)` for some narrow `AdminTx` -- keeps `users` out of reach and would defeat the paragraph above. It is refused on a different ground: **there is no admin table set to narrow to.** The three write ports declare three different narrow handles (`AdminWriteTx` over ten keys, `AdminPayoutTx`, `AdminWalletTx`), each narrowed at the PORT, and a fourth narrowing in `db.ts` would be a fourth list of tables maintained beside three that already exist -- `RI-04`'s two-lists defect at arity four. **The narrowing belongs where it already is**, and the adapters that would apply it cannot be constructed.

### 6. Clause 4, and the mechanical rule that replaces a convention

**A REFUSAL THAT LEAVES ONLY A PARAGRAPH BEHIND IS A REFUSAL WITH A HALF-LIFE.** [`db.ts`](../../apps/api/src/db.ts)'s header is the record of ADR-120 clause 3 and it is prose; the next session dispatched at a count can read it, disagree, and add a method, and every gate in this repository stays green. **`apps/worker` does not have that problem and `apps/api` did**, which is what [ADR-165](ADR-165.md) section 10 finding 5 recorded and rowed as owed.

[`apps/api/test/db.test.ts`](../../apps/api/test/db.test.ts) asserts three properties, and the header states what each one covers and what none of them do:

1. **THE DOOR COUNT AND THEIR NAMES.** `Object.keys(LIVE_DB)` is `['scoped', 'firm']`, with the arity of each pinned beside it. `LIVE_DB` is typed `ApiDb`, so a third method on the interface must appear here or the file does not compile: **the interface is checked through its one implementation** rather than by parsing the type.
2. **THE VALUE IMPORTS `db.ts` TAKES FROM THE ACCESSOR**, as an exact list: `firmDb`, `scopedDb`, `transaction`. `systemDb` arriving is a failing case naming this entry, and since case 3 makes `db.ts` the only file that may import the accessor at all, the two together are the mechanical form of "this deployable cannot reach `'operator-console'`". **It is asserted over the IMPORT and never over the string**, on [ADR-165](ADR-165.md) section 9's measured lesson: six files under `apps/api/src` name `systemDb` in prose to say that they do not reach it, and a substring check would count each of those as a violation of the property it is describing.
3. **THE ACQUISITION POINT, WHICH IS WHERE A HANDLE IS OBTAINED AND NOT WHERE THE PACKAGE IS NAMED.** This is the case that was written as ADR-165 finding 5 words it -- _"exactly one file under `src` imports the accessor"_ -- and **it failed on its first run.** `routes/account-reads.ts` imports `atMost`. So the case pins a MAP of file to the value names it takes off the accessor, and asserts separately, first and with its own message, that **no file but `src/db.ts` takes any of `firmDb`, `scopedDb`, `systemDb` or `transaction`**: the four exports that yield a handle. The map is the broader net and the handle list is the property `db.ts`'s header is actually about.

**THAT FAILURE IS THE ARGUMENT FOR THE FILE AND IT IS BETTER THAN THE ARGUMENT THIS ENTRY WAS GOING TO MAKE.** The convention had already drifted, in a route module that landed months of sessions after the header describing it, and every gate in this repository was green over it. **The prose was describing the tree as it was when the prose was written**, which is the failure mode a control exists to make impossible and a convention cannot.

**WHAT IT PROVES NOTHING ABOUT, WRITTEN IN THE FILE RATHER THAN LEFT TO BE ASSUMED.** Not whether a composed predicate reaches one row or many, which is `packages/db`'s and is asserted in [`packages/db/test/keyed-accessor.test.ts`](../../packages/db/test/keyed-accessor.test.ts). Not whether `SystemReason` still has two members, which [`packages/ledger/test/accessor-bind.test.ts`](../../packages/ledger/test/accessor-bind.test.ts) already parses out of `scoped-db.ts` and which a second copy here would duplicate. Not the MANIFEST half, which is `RI-08`'s and whose own header rules that _"Two lists is the defect; one list read twice is the fix."_

**AND IT DOES NOT STOP THE DOOR.** A session that decides to open one edits three lines in a test file alongside the door itself. **That is the point rather than a weakness**: the check cannot make the decision, it can only make the decision visible to whoever reviews the diff, which is precisely what a paragraph in a header does not do.

### 9. What would change this ruling, as a condition

**THE DOOR IS NOT REFUSED FOREVER AND THE ENTRY SHOULD NOT PRETEND OTHERWISE.** The condition is stated so that the session that meets it does not have to re-derive this reading:
