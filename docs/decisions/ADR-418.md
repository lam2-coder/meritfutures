### 3. Is `replay-adapter.test.ts` really the only consumer? Derived at source, and the answer has two halves

The dispatch forbade inheriting this claim from ADR-414 or from itself. It was derived twice, because a "consumer" of a file is not one population.

#### 3.1 The module graph, resolved rather than grepped

A grep for the path finds prose. What the retirement question needs is the set of files whose import, export, `require` or dynamic `import` SPECIFIER RESOLVES to this module, so the instrument resolves each relative specifier against the importing file's directory and compares it to the target, trying the bare path and the `.ts`, `.tsx`, `.mts`, `.js` and `/index.ts` extensions the resolver would.

**Over the `771` tracked `.ts`, `.tsx`, `.mts`, `.js`, `.mjs` and `.cjs` files in this tree, there is exactly ONE.**

| consumer | shape | what it takes |
|---|---|---|
| `apps/worker/test/replay-adapter.test.ts` | a dynamic `import` by relative path, inside case 4.2 | `EVENT_NAMES` |

**A PACKAGE-NAME SPELLING WAS CHECKED SEPARATELY AND THERE IS NONE.** No file in this tree carries an import-shaped `@merit/api` specifier, and `tsconfig.base.json` declares no `paths` aliases, so there is no second address this module could be reached by. **ADR-414 SECTION 6's FIGURE IS CORRECT AND IT REPRODUCES EXACTLY.**

#### 3.2 And the file has a dependant that is not in the module graph at all

**AN IMPORT IS NOT THE ONLY WAY TO DEPEND ON A FILE, AND THE DEPENDANT THAT DECIDES THIS ROW IS A PATH STRING IN A CHECK.** These are the sites that name the path in a way that a deletion breaks, derived by reading each one rather than by counting matches:

| site | what it does with the path | whose |
|---|---|---|

| `packages/tooling/test/absence-claims.test.ts`, its `OLD_PATH` constant | reads the file to assert the anchor occurs once at each of the two addresses | **row 417's** |
| `apps/api/test/event-placement.test.ts`, its `OLD_PATH` constant | five reads across three cases, the narrow-surface assertion among them | **this row's** |

**THAT IS THE FINDING UNDER ADR-414 SECTION 6.** Its consumer figure is true; its conclusion, that *"retiring the pair is a coherent slice for a row holding both sides"*, is false, because the second half of the retirement is not an `apps/**` edit at all.

### 5. Which file carries the anchored sentence, established from the register

The dispatch required this be settled from `RI-35`'s register rather than from either file's own prose, because the prose is what is in dispute.

| file | carries the anchor | claimed the binding, before this row | is the bound copy |

### 6. The case, and the RED watched before it

**THE MARKER IS THE INSTRUMENT BECAUSE THE PROSE IS WHAT DRIFTED.** Two headers can both assert a binding in good faith; only one can carry a token a runner counts.

The case added to `apps/api/test/event-placement.test.ts` derives the bound path OUT OF THE REGISTER, by finding the claim's anchor string and reading the `site` field immediately above it, then asserts three things: that the anchor occurs exactly once in each of the two files, that exactly one of them carries the marker, and that the one that does is the path the register named.

**IT WAS WATCHED RED BEFORE THE PROSE WAS WRITTEN.** The case landed first, against the unrepaired tree, and failed with the marker absent from both files:

```
FAIL  apps/api/test/event-placement.test.ts > the relocation, and the bindings that moved with it
      > exactly one of the two copies of the anchored sentence claims to be the bound one
AssertionError: expected [] to deeply equal [ 'apps/api/src/events.ts' ]

```

**IT FAILS ON GOOD NEWS AND IT FAILS ON THE BAD KIND TOO.** Two claimants is the state ADR-415 found; zero is the state where nobody can tell which copy leg 1 reads; and the day the `site` moves, this case reddens at the marker while the case above it reddens at the register, so neither half can move alone and leave a green suite.

### 10. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.** [ADR-410](ADR-410.md), [ADR-414](ADR-414.md) and [ADR-415](ADR-415.md), whose findings this row answers, are each `proposed` and unsigned on this row's base.

- **What a founder read adds and this entry cannot.**

  **THE FIRST DECISION IS WHETHER "ONLY CONSUMER" IS A QUESTION THE PROGRAMME KNOWS HOW TO ASK.** Three consecutive rows have now reasoned about this module's dependants and all three counted imports. The dependant that actually decides its fate is a string in a register, and nothing in the tree connects the two: a reader of `apps/api/src/events.ts` before this commit had no way to learn that a check in another package would fail if the file were removed. **A founder should decide whether a file bound by a register ought to say so at the file**, which is what this row did by hand and what nothing enforces.

  **THE SECOND IS WHETHER A THREE-FENCE REPAIR SHOULD EVER BE DISPATCHED AS THREE ROWS.** ADR-415 priced this fence at three files and named two of them `apps/**`. This row was granted those two and not the third, so the wave has now spent three rows on one deletion and has not taken it. **That is not a failure of any row**, and every one of them was right to refuse. It is a question about how the wave is cut, and the evidence is that a fence drawn by directory cannot express a binding that runs between directories.

  **THE THIRD IS THE ONE WITH THE SHORTEST FUSE.** The producer's header carried a sentence claiming a check watched it, for the whole life of two waves, while that check read a different file. Nothing was red. **A founder should decide whether an anchored sentence ought to be unique in the TREE rather than unique in the FILE**, because the state this row found is a check silently watching the wrong copy of its own sentence, and the only reason it was ever noticed is that a human-written entry told a later row to go and read both files.
