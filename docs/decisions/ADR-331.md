## ADR-331: the executor that lost the rows. `pg` answers a multi-statement plan with one result per statement, the accessor read `.rows` off the array, and the flattening lands on the side that destroyed it  (2026-09-05, status: proposed)

**[ADR-327](ADR-327.md) section 9 finding 1 measured a defect and left it, saying *"the row that writes the queue's ONE DOOR owes this, and it is recorded here so that session does not spend a day on a `filter` of `undefined`"*.** This entry is that repair, taken as its own row rather than as a means inside the door's. It reproduces the defect against a real database before changing a line, fixes it on the side pg-boss's own adapters fix it on, **refuses to widen `SqlExecutorReason`**, and measures a SECOND blocker on the same construction that finding 1 did not name: every plan the vendor wraps in `locked()` carries its own `BEGIN` and `COMMIT`, so a supervisor built on a caller's open transaction commits it. **The half worth reading is section 5**, because it is the half that decides what the next row has to build.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `331`, branch `claude/an-executor-that-loses-the-rows`, session **522**. [ADR-327](ADR-327.md) section 9 finding 1, on [ADR-165](ADR-165.md)'s ONE DOOR and [ADR-084](ADR-084.md)'s pool.

- **MONEY PATH BY FILE.** [`packages/db/src/scoped-db.ts`](../../packages/db/src/scoped-db.ts) is the accessor every money read and write goes through, and this diff changes what one of its functions returns. **FOUNDER `E2` READ OWED**, and five reads are inherited ([ADR-327](ADR-327.md), [ADR-328](ADR-328.md), [ADR-329](ADR-329.md), [ADR-330](ADR-330.md) and [ADR-303](ADR-303.md)'s repaired citation), all `proposed` and all UNSIGNED.

### 2. THE REPRODUCTION

#### 2.1 How it was taken

`0001`..`0082` applied forward-only from empty under `ON_ERROR_STOP=1` against **PostgreSQL 16.13**, which is the estate [ADR-327](ADR-327.md) section 3.1 measured its grant on. **118 tables in `public` and 12 in `pgboss`.** Every statement ran under `SET LOCAL ROLE merit_app`, taken on the transaction's own connection through the executor under test, so nothing reached the database with more authority than the application has. The queue was constructed by [`pgBossQueue`](../../packages/queue/src/pg-boss-queue.ts) and driven through `start()`, `declareQueue`, an `enqueue` inside a caller's open transaction, and a wait long enough for one supervise pass, with `pgboss.queue.maintain_on` and `monitor_on` set to `NULL` first so that neither phase was skipped on a lease its own first iteration had taken. **That trap is [ADR-327](ADR-327.md) section 3.3's and it was cleared rather than rediscovered.**

#### 2.2 What `pg` actually returns, which is the whole defect in one line

The plan is pg-boss's own, rendered by its `locked()` helper at `pg-boss/dist/plans.js:2374` over `transaction()` at `:2364`:

```
BEGIN;
SET LOCAL lock_timeout = 30000;
SET LOCAL idle_in_transaction_session_timeout = 30000;
SELECT pg_advisory_xact_lock(('x' || encode(sha224(...), 'hex'))::bit(64)::bigint);
SELECT 1 AS a;
COMMIT;
```

Run on a `pg` connection as `merit_app`, verbatim from the transcript:

```
--- A. pg returned: Array.isArray = true , length = 6
--- A. `.rows` on that array is: undefined
--- A. per-statement rows: [[],[],[],[{"pg_advisory_xact_lock":""}],[{"a":1}],[]]
--- B. sqlExecutorOn returned: {}
--- B. `.rows` is undefined
```

**SIX STATEMENTS, SIX RESULTS, AND THE ROWS THE CALLER WANTED IN ELEMENT FOUR WITH EMPTY ARRAYS EITHER SIDE.** `.rows` on an array is `undefined`, so the accessor answered `{ rows: undefined }`, which `JSON.stringify` prints as `{}` because the property is present and undefined. **That is not the type the function declares.** `SqlExecutor.executeSql` is `Promise<{ rows: unknown[] }>` at [`scoped-db.ts:3516`](../../packages/db/src/scoped-db.ts), and a wrong answer past a type is worse than a throw: the caller has no reason to check.

**AND THE PAYLOAD IS IN THE MIDDLE, WHICH IS WHY ONLY A FLATTEN IS CORRECT.** An executor that returned the LAST result would have returned the `COMMIT`'s empty array and passed a naive test. pg-boss's own PGlite adapter says the same thing in its own words at `dist/adapters/pglite.js`: flatten *"so a RETURNING in the middle isn't lost behind a trailing COMMIT"*.

#### 2.3 The supervisor, dying exactly where finding 1 said it would

```
--- C. start()
--- C. declareQueue()
--- C. enqueue()
--- C. enqueue returned: a job id
--- C. leases cleared; waiting 65s for one supervise pass
--- C. failures observed: 1
--- C. TypeError: Cannot read properties of undefined (reading 'filter')
               at #monitor (.../pg-boss@12.28.0/node_modules/pg-boss/dist/boss.js:187:45)
--- C. statements seen: 73
```

**73 STATEMENTS RAN AND THE FIRST FAILURE WAS THE ONE FINDING 1 PREDICTED.** Line 187 of that file is `const warnings = rowsCacheStats.filter(...)`, fed by `cacheQueueStats`, which is a `locked()` plan. [ADR-327](ADR-327.md) recorded the line as `185`; **on the pg-boss@12.28.0 installed in this tree it is `187`**, and the difference is reported rather than smoothed over. The failure arrives as an unhandled `error` event, because [`pgBossQueue`](../../packages/queue/src/pg-boss-queue.ts) publishes five methods and none of them is an emitter, so a caller cannot subscribe to it: **the supervise pass aborts and nothing in the process is told.**

**`enqueue` WAS UNAFFECTED, WHICH FINDING 1 ALSO SAID.** It returned a job id in the same run. The reason is not luck: an enqueue passes `values`, `pg` takes the extended protocol for a parameterised call, and the extended protocol cannot carry a second statement at all. **So the one path this function's one admitted reason exists for is the one path the defect could never reach**, and that is why it survived a whole row after being measured.

### 3. Which side flattens, and why it is this one

**THE DISPATCH ASKED FOR A DECISION AND NOT A PATCH, SO HERE IS THE EVIDENCE IT WAS TAKEN ON, ALL OF IT READ OUT OF THE INSTALLED PACKAGE.**

| Read at | What it says |
|---|---|
| `pg-boss/dist/types.d.ts:18` | `IDatabase.executeSql` is declared `Promise<{ rows: any[] }>`. **The contract the library asks an adapter for is the NORMALISED one**, a single object, not the driver's answer |
| `pg-boss/dist/tools.js:10` | `unwrapSQLResult`, which flattens a `Result[]` by concatenating each element's `rows` and passes a single result through |
| `pg-boss/dist/db.js:39` | its own built-in driver returns `pool.query(...)` **verbatim**, array and all |
| `pg-boss/dist/boss.js:76` | so the supervisor unwraps on the way in, which is what makes the built-in driver legal |
| `adapters/knex.js:16`, `adapters/drizzle.js:30` | both call `unwrapSQLResult` themselves |
| `adapters/pglite.js:24` | flattens by hand, `flatMap(r => r.rows ?? [])`, and its comment says it *"mirrors how pg-boss unwraps the array that node-postgres returns"* |
| `adapters/kysely.js:10`, `adapters/prisma.js:6` | normalise to `{ rows }` over drivers that never produce the array |

**FIVE ADAPTERS OUT OF FIVE NORMALISE, AND THE ONLY THING THAT HANDS THE ARRAY BACK IS THE DRIVER ITSELF.** `sqlExecutorOn` is an adapter of exactly that kind: it takes `pg` and answers `{ rows }`. **So the flattening belongs here, and the argument is not aesthetic.** By the time `pgBossQueue` receives `{ rows: undefined }` the array is gone. Information destroyed at the driver boundary can only be preserved at the driver boundary, and no wrapper at the construction site can recover what was already thrown away.

**THE ALTERNATIVE WAS CONSIDERED AND IT COSTS THE INTERFACE.** A transparent executor, returning `pg`'s result unchanged, works too: pg-boss unwraps in the supervisor and every direct `.rows` reader in `manager.js`, `contractor.js` and `navigator.js` is single-statement. But it requires `JobTransaction.executeSql` to admit `Result[]`, which puts **`pg`'s result shape inside the vendor-neutral interface [ADR-006](ADR-006.md) made a review criterion**. [`job-queue.ts`](../../packages/queue/src/job-queue.ts) calls that type *"the narrowest thing a Postgres-backed queue can be handed"*; widening it to name a driver is the opposite of what it is for, and a BullMQ adapter would then have to satisfy a type describing node-postgres.

**AND `unwrapSQLResult` IS NOT IMPORTED, WHICH IS A CONSTRAINT RATHER THAN A PREFERENCE.** It is not on pg-boss's public entry point: `dist/index.js` exports the class, the plan builders and the five adapters, and not this. Reaching it means a deep import, and `packages/db` naming the vendor at all would break the containment [`surface.test.ts`](../../packages/queue/test/surface.test.ts) asserts over the whole tree, that **exactly one module imports `pg-boss`**. So the semantics are reproduced in six lines and **bound rather than copied**: section 7's third case reads the installed library and the accessor together, so a vendor that changed its answer turns a Merit case red.

### 5. The second blocker, measured, which finding 1 did not name

**`sqlExecutorOn` COULD NOT CONSTRUCT `pgBossQueue` EVEN WITH THE ROWS REPAIRED, AND THE REASON IS TRANSACTION CONTROL RATHER THAN RESULT SHAPE.**

`locked()` renders `BEGIN; ...; COMMIT;` (`plans.js:2364`). Handed a caller's OPEN transaction, that `BEGIN` is a no-op with a warning and that `COMMIT` **commits the caller's transaction**. Measured on the same estate, after the fix, with the in-transaction test comparing `now()` against the statement clock:

```
--- E. before the plan: {"second_statement_of_a_transaction":true}
--- E. after one `locked()` plan: {"second_statement_of_a_transaction":false}
```

**ONE PLAN AND THE CALLER'S TRANSACTION IS GONE.** `declareQueue` is such a plan, so it is reached at construction rather than at some later maintenance pass. That is [ADR-006](ADR-006.md)'s central consequence, *"enqueue participates in the same transaction as the state change that caused it"*, destroyed one statement into the thing meant to serve it.

**SO THE CONSTRUCTOR EXECUTOR HAS TO BE POOL-SHAPED: ONE CONNECTION PER STATEMENT, WHICH IS WHAT THE VENDOR'S OWN DRIVER IS** (`db.js:39` is `this.pool.query(text, values)`). It also has to outlive any one transaction, because pg-boss holds the handle for the life of the boss and polls on it. **And `apps/worker` cannot build one for itself**: `merit/no-raw-db-client` (VG-4) bans `pg` outside `packages/db`, and [ADR-084](ADR-084.md) section 9 keeps `client()` unexported permanently. **The door has to come from `packages/db` or it cannot exist**, which is what makes it a ruling rather than a chore.

**THE PROOF THAT THE FIX IS SUFFICIENT FOR THAT SHAPE WAS TAKEN ON A RIG AND IS LABELLED ONE.** A pool-shaped executor carrying the SAME six lines of normalisation, `SET ROLE merit_app` on each connection, was handed to `pgBossQueue` and driven end to end. This is the shape `packages/db` owes, written in a probe rather than shipped, on the same footing as [ADR-327](ADR-327.md) section 3.1's rig.

### 11. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

**What a founder read adds and this entry cannot.**

**THE FIRST THING TO DECIDE IS SECTION 4, BECAUSE IT IS THE ONLY JUDGEMENT HERE AND NO GATE CAN MAKE IT.** Every check in this row answers "does the executor return what the driver gave it". **None of them answers "should a third row exist before anything can enqueue a job"**, and that is the question. This entry refuses to widen a closed vocabulary on the money accessor and refuses to publish a pool-shaped raw-SQL door, on the ground that both belong to a session whose subject they are. The cost is real and it is not hypothetical: [ADR-327](ADR-327.md) granted the privileges, this row repairs the executor, and **a deployable still cannot construct the queue**, which will read to some as three sessions of discipline buying one working file. A founder who wants the door and its reason folded into the next row rather than into a row of their own is asking for a faster process than [ADR-165](ADR-165.md) describes, and that entry's own section 6 says what the slower one costs: session 222 built an entire provisioning saga against ports rather than take one manifest line.

**THE SECOND IS WHETHER THE FLATTENING BELONGS IN `packages/db` AT ALL, GIVEN THAT NOTHING IN THIS TREE CAN YET REACH IT.** Section 2.3 measures that `enqueue`, the only path this function's one reason exists for, cannot produce a multi-statement string: it always passes `values` and the extended protocol forbids it. **So the six lines added here are unreachable by every caller that exists today**, and a reader is entitled to call that speculative work on the money path, which Appendix F2 names as a tell. The answer this entry gives is that the function DECLARED `{ rows: unknown[] }` and returned `{ rows: undefined }`, which is a lie in a type on the accessor every money read goes through, and that a lie is worth repairing on the day it is found rather than on the day it is reached. **Whether that is the right standard for a file under `E2` is a judgement about how much unreached code belongs on a money path, and it is a founder's to make.**

**THE THIRD IS SECTION 7, WHICH IS THE UNCOMFORTABLE ONE.** The suite was green against a defect that had been measured, written into an approval block, quoted in three shipped files and named as owed. **Nothing in the repository could turn red about it**, because the only model of the driver in the tests had one mode and it was the mode that worked. That is the self-grading trap in C10's own words wearing a different costume: the fixture and the implementation shared an assumption, so the coverage was real and the model was not. **A founder should ask whether the two cases added here are enough**, given that the answer they model was read off a real database once, in a probe that is not in the suite, because `CI-04`'s second leg is still a dated condition.
