## ADR-102: the accessor learns to WRITE inside a transaction it also produces, and a third door serves the rows that belong to nobody  (2026-08-25, status: proposed)

**[ADR-008](ADR-008.md) scoped the accessor to bound a BOLA failure on the READ side, and [ADR-084](ADR-084.md) built it. Neither ruled on a write, and the write has the same failure mode with worse consequences: a read that returns the wrong rows is a leak, and a row written under the wrong identity is a corruption no later read can tell apart from an honest one.** This entry rules the write path, the transaction primitive `packages/queue` has been waiting for since [session 147](../sessions/2026-08-24-session-147.md), and what a caller with no identity reads a `firm` table through.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-f` row and section 15's prompt, session **213**. Section 6 of that plan found that the axis P3's six modules collide on is the write accessor and not the routes: **ten slices are behind this one and nothing was in front of it.**

- **Context:** `ScopedDb` and `SystemDb` each carried `__brand`, an identity or a reason, and `rows()`. Nothing else. [`index.ts`](../../packages/db/src/index.ts) exported no writer and no transaction, and [ADR-084](ADR-084.md) section 9 rules `client()` unexported **permanently**.

### 2. THE RULING

> **1. `scopedDb(id)` AND `systemDb(reason)` DO NOT MOVE. THEY STAY READ ONLY.** A write is reached only through `transaction(handle, fn)`, which takes one of the three read handles and hands the callback the same authority with the write methods attached. **There is no non-transactional write and there is no ambient default.**
>
> **2. AN UPDATE AND A DELETE CARRY THE PREDICATE THE MATCHING READ CARRIES.** Not a predicate written for the write side: the same `scopePredicate(key, identityId)`, over the whole of `ScopedTableKey` including `derived`, whose `EXISTS` is as correct in a `WHERE` clause as it is in a read.
>
> **3. AN INSERT HAS NO WHERE CLAUSE, SO THE IDENTITY IS WRITTEN, AND ONLY `owned` HAS SOMEWHERE TO WRITE IT.** The scoped writer's insert accepts `OwnedTableKey` and nothing else, and it stamps the tenancy column from the handle. **`root` and `derived` inserts are compile errors**, for two different reasons stated in section 4.
>
> **4. THE TENANCY COLUMN IS NEVER THE CALLER'S TO NAME**, in an insert's values or in an update's `SET`, in either spelling, on every class that has one. For `derived` the tenancy column is the FOREIGN KEY the rule traverses, and moving it is the re-parenting this ruling would otherwise leave open.
>
> **5. `SystemReason` STAYS AT TWO MEMBERS AND A THIRD, NARROWER DOOR IS ADDED.** `firmDb()` serves `FirmTableKey` and takes **no reason**, because the question a reason answers -- *why are you reading rows that are not yours?* -- does not arise about a row that is nobody's. A `ScopedTableKey` passed to it is a compile error.
>
> **6. THE TRANSACTION IS THE ONLY PRODUCER OF A `JobTransaction`,** and the raw executor is `sqlExecutor(reason)` from a closed one-member vocabulary rather than a property on the handle. **Neither `packages/db` nor `packages/queue` imports the other**; the two shapes are bound by an assertion that READS `job-queue.ts`.
>
> **7. THE READ INTERFACES ARE UNCHANGED AND THAT IS A RULING, NOT A CONVENIENCE.** Section 6 is why: a required method on `ScopedDb` would have made `CI-01`'s brand seed pass on the wrong evidence.

### 3. Which of the three failure classes this write path can suffer, asked because the dispatch asked it

**[ADR-101](ADR-101.md) refuses two of three failure classes on the READ side and names the third as open. The same three questions asked of the write path give three different answers, and one of them is worse than the read's.**

| Class | On the read side | On the write side |
|---|---|---|
| **1. A rule that answers a DIFFERENT question from the row's own identity column** | Refused by ADR-101 clause 1 | **CANNOT ARISE, and it is the type that says so.** The write path never chooses a predicate: `update` and `delete` call `scopePredicate` and an assertion compares the rendered `WHERE` of all 57 scoped writes against the rendered read predicate, table by table. There is no second place a rule could be written differently |
| **2. A nullable edge, so the rule is silent on the rows where it is absent** | Refused by ADR-101 clause 2 | **INHERITED WHOLE AND NOT MADE WORSE.** A write carrying a rule that drops rows updates or deletes FEWER rows than it should, which is a failed write rather than a wrong one. It is the one direction where the write is the safer half |
| **3. A `semi-join` on a reverse edge whose relation is not TOTAL** | **NOT refused.** ADR-101 section 7 reproduces it and says no assertion over these migrations can see it | **NOT refused, and it is WORSE HERE.** `ledger_transactions` is the registry's only `semi-join` and rests on this property today. A read through it returns a subset; a DELETE through it deletes a subset and leaves the rest, which is a partially applied write with no error anywhere. **This entry does not close it and it inherits it in the direction that destroys** |
| **4. RE-PARENTING. A row moved to another identity by a `SET`** | **Does not exist on the read side at all** | **REFUSED, by clause 4.** This is the one failure class that is the write path's own, and the only one this entry invents a control for. It is least visible on `derived`, where the column being moved is a foreign key and looks like data |

**So: one class the write path cannot suffer, one it inherits harmlessly, one it inherits and makes worse, and one that is its own and is refused.** The honest coverage is three of four, and the uncovered one is [ADR-101](ADR-101.md)'s and not this entry's to close: the remedy that entry names is an attestation on reverse-edge rules, which edits `ledgerTransactions`' row in [`scope.ts`](../../packages/db/src/scope.ts) and is outside this fence.

### 4. Clause 1: the write path, and the two inserts that are compile errors

**`update` and `delete` serve the whole of `ScopedTableKey` and `insert` serves `OwnedTableKey`. The asymmetry is the whole design and it is one sentence: an UPDATE and a DELETE have a `WHERE` clause and an INSERT does not.**

- **`root` is refused because inserting into `identities` CREATES an identity.** A handle already bound to one has no correct row to write there, and the row it would write is either a duplicate of itself or a different person.
- **`derived` is refused because the row carries no tenancy column, so there is nothing to stamp.** The tenancy is the parent's, and the accessor cannot establish that the parent belongs to this identity without reading it.

**THE CONSTRUCTION THAT WOULD SERVE `derived` IS NAMED AND NOT BUILT.** `INSERT INTO t (...) SELECT ... WHERE EXISTS (<the parent's scope predicate>)` inserts zero rows when the parent is not this identity's, atomically, with no read-then-write race. It is correct and it is roughly forty lines. It is refused here on [`job-queue.ts:88-91`](../../packages/queue/src/job-queue.ts)'s own rule, which this file borrows twice: *"a primitive admitted before a caller exists is a primitive nobody can remove."* **The two callers that will need it are named in section 8 rather than guessed at**, and a zero-row insert that raises rather than returning quietly is a decision the first of them should make with its own semantics in hand.

**THE RE-PARENTING REFUSAL IS THE PART A REVIEWER SHOULD LOOK AT HARDEST.** The predicate matched the row as it stood. A `SET` that moves the tenancy column hands the row to somebody else **after** the predicate has already agreed to it, and on a `derived` table the column being moved is a foreign key: `ledger_entries.ledger_account_id` re-pointed at another identity's ledger account is a row that leaves this identity's scope and enters theirs, with every check in this package green. `tenancyColumn(key)` returns `rule.column` for `root` and `owned` and **`rule.localColumn` for `derived`**, and the guard refuses both the SQL spelling and the Drizzle property spelling, because the values object is keyed by the second and the registry names the first.

**THE GUARD IS A THROW AND NOT A TYPE, and the reason is not the same as [ADR-101](ADR-101.md) section 6's.** There the predicate was a fact about the DDL that `tsc` cannot read. Here the fact is available to the type system and the encoding is expensive rather than impossible: it means deriving the Drizzle property name from `TABLES[K]`'s column map inside a conditional type, over ninety-two tables, at every call site. **The offending key is a string at the moment it is passed, so a runtime sees it perfectly**, and the suite watches it throwing on all 37 `owned` tables in both spellings and on all 57 scoped tables for the `SET`. ADR-084's `firm` refusal went the other way for the opposite reason: a table KEY is a literal type and no runtime sees it until the query runs.

### 5. Clause 2: the transaction, and the `JobTransaction` nothing could produce

**`transaction(handle, fn)` takes the handle that says whose rows may be reached and returns the same authority with writes attached.** That is [ADR-008](ADR-008.md)'s *"reach the database and choose a scope are the SAME ACT"* extended to the side that writes: the write path cannot be entered without having first chosen a scope.

**THERE IS NO `scopedDb(id).insert(...)`, AND THAT IS `job-queue.ts`'s RULING APPLIED TO THE ACCESSOR RATHER THAN A NEW ONE.** That file's header states it about itself: *"THE AWKWARD ONE TO WRITE IS THE NON-TRANSACTIONAL ONE... There is no `enqueueNow`, no optional transaction and no ambient default: a caller with no state change to join opens a transaction around the single insert, which is one line and is correct."* [ADR-006](ADR-006.md)'s central consequence is that enqueue participates in the same transaction as the state change that caused it, and a write reachable outside a transaction makes that consequence optional at every call site that forgets it. `INV-M3-13`'s wallet leg and [M08](../plans/M08-affiliate-system.md) section 3.1's attribution both commit inside checkout's transaction, so this is the clause the most later code depends on.

**`BEGIN` / `COMMIT` / `ROLLBACK` ARE ISSUED ON THE CONNECTION RATHER THAN THROUGH DRIZZLE'S `db.transaction`, and the reason is `executeSql`.** `JobTransaction.executeSql(text, values)` is `pg`'s own call shape with `$n` placeholders, which is what pg-boss generates. Routing it through Drizzle means splitting somebody else's SQL on `$n` and rebuilding it as template chunks, and that text transform breaks the first time a dollar-quoted string or a literal `$1` inside a text value goes through it. **One connection, one transaction, and the two views of it created in one place.** The pass-through is asserted byte-exact against a recording connection, with `$$not a placeholder$$` in the seeded text.

**THE POOL IS RECOVERED WITH A CHECK AND NOT WITH A CAST.** `drizzle(pool, ...)` attaches `$client` to the handle it returns and [`client.ts:58`](../../packages/db/src/client.ts) declares its return type as plain `NodePgDatabase<typeof schema>`, which erases it. **`client.ts` is outside this session's fence**, so `poolFromClient()` proves the property at runtime and the suite watches it succeed, and a Drizzle upgrade that moved it fails there rather than at the first transaction in production. `pg` is imported for its TYPES ONLY, which erases, so `client.ts` remains the only file in the workspace that imports it at runtime.

**THE ESCAPE HATCH IS NAMED RATHER THAN CARRIED.** A handle with `executeSql` on it runs arbitrary SQL on the transaction's connection, which is every control in this file routed around by a caller who already holds a legitimate handle. So it is not a method: it is `sqlExecutor(reason)` over a closed one-member vocabulary, on `SystemReason`'s exact precedent, so that *"ran raw SQL"* is a diff a reviewer reads. **This closes the accidental door and not the deliberate one**, which is the limit `job-queue.ts` states about `JobTransaction` and `STRATEGY` section 4.2 states about `VG-4`, in the same words, and it is stated here rather than left to be discovered.

**NEITHER PACKAGE IMPORTS THE OTHER AND THE BIND IS AN ASSERTION.** `packages/db` declares no `@merit/queue` dependency, [`packages/queue/package.json:13`](../../packages/queue/package.json) says in its own `//` key that `@merit/db`'s absence *"is the design rather than an omission"*, and **`package.json` is outside this fence besides**. So `SqlExecutor` restates `JobTransaction`'s shape, which is [ADR-092](ADR-092.md) section 5's two-statements-of-one-fact hazard, and it is closed the only way it can be from here: the suite READS `packages/queue/src/job-queue.ts` and compares the two interface bodies, and separately asserts that `enqueue` still takes the transaction first with no overload that omits it. **That is [ADR-101](ADR-101.md)'s instrument pointed at a sibling package instead of at the migrations.**

**THERE IS NO NESTED TRANSACTION.** A savepoint is a primitive no caller has asked for, and the transaction handles carry no `transaction` method, which the suite asserts on all three.

### 6. Why the read interfaces did not move, which is a finding rather than a design note

**A required method added to `ScopedDb` would have broken [ADR-084](ADR-084.md)'s second watched refusal without turning anything red.**

`CI-01/scope-system-db-not-assignable` seeds a value declaring exactly `__brand`, `reason`, `identityId` and `rows()`, assigns it to a `ScopedDb`, and demands the needle `__brand` in the compiler's output. [`falsify-ci.mjs:689-694`](../../scripts/ci/falsify-ci.mjs) says why in its own comment: without `identityId` present TypeScript reports *"Property 'identityId' is missing"*, **which passes a naive needle while proving the wrong thing.** Add `insert`, `update`, `delete` or `transaction` to `ScopedDb` and TypeScript reports four missing properties instead, the needle stops matching, and **the case fails loudly** -- or, had the needle been the bare exit code, it would have passed on evidence about the wrong incompatibility.

**`scripts/ci/falsify-ci.mjs` is outside this session's fence**, and [ADR-084](ADR-084.md) section 10 is the precedent for widening onto it. **This session did not need to, because the design that keeps the seed honest is also the better design**, and the causation runs in that order rather than the other one: the fence made the constraint visible, the constraint was checked, and `job-queue.ts` had already ruled the same question for the same reason. `node scripts/ci/falsify-ci.mjs CI-01` reports **12 of 12** on this branch, with both scope cases found on `ScopedTableKey` and on `__brand` exactly as before.

**The suite carries a regression guard for it**, in the package that owns the shape rather than in the file this session may not touch: three tests assert that `scopedDb(...)` carries exactly `__brand`, `identityId` and `rows`, that `systemDb(...)` carries exactly `__brand`, `reason` and `rows`, and that no read handle carries `insert`, `update`, `delete`, `sqlExecutor` or `transaction`.

### 7. Clause 3: the reader with no identity, priced the way ADR-096 section 5 priced the one it refused

**[ADR-096](ADR-096.md) is the precedent and it went the other way.** It refused a third `SystemReason` for `apps/site` and ruled the site *"not a reader of this database at all"*, reading over HTTP instead. **That remedy is unavailable here**, because under that same entry `apps/api` is the process the site reads THROUGH: if `apps/api` cannot reach a `firm` table then nothing can.

**THE FINDING THAT DECIDES IT IS THAT ONE DOOR WAS SERVING TWO DIFFERENT ACTS.** `systemDb(reason).rows(key)` is generic over `TableKey`, so it serves *"EVERYBODY's rows, read without their identity"* -- which is what `'nightly-batch'` and `'operator-console'` do -- and also *"NOBODY's rows"*, which is what reading `coupons` is. **Only the first has an identity at risk.** So the vocabulary stays at two members and a narrower door is added rather than the list being widened.

**Reading 1, a third `SystemReason` member, priced:**

- **It would have made the vocabulary's own argument false in its own file.** [`scoped-db.ts:25-28`](../../packages/db/src/scoped-db.ts) says the reason for a reason is that *"the legitimate unscoped readers are a list somebody has to join"*. Every request handler in `apps/api` is a legitimate reader of `plan_versions`, so a list whose third member is `'request-handler'` is a list nobody has to justify joining. **That is [ADR-096](ADR-096.md) section 5's own argument against the member it refused, and it applies here unchanged.**
- **It would have widened the two accepted members rather than added to them.** A caller holding `systemDb('request-handler')` can read `accounts`, `wallet_entries` and `payout_requests` firm-wide, because `SystemReason` does not narrow the key type and never has. **The reason names the caller and the key type names the reach, and they are not connected.**
- **It buys nothing the narrower door does not.** Every table clause 3 exists for is `firm`.

**Reading 2, letting `apps/api` read `firm` tables through `scopedDb`, is not expressible** and is refused for [ADR-096](ADR-096.md) section 6's reason: what a session under a deadline writes instead is a cast, and `firm` keys are excluded from `ScopedTableKey` precisely so that cast has to be written by hand.

**Reading 3 is taken: `firmDb()`, `FirmTableKey` only, no reason.** A caller that wants an unscoped read of a SCOPED table still writes the word system, and now that word means only what [ADR-084](ADR-084.md) accepted it for.

**WHAT IT COSTS, STATED AGAINST THE ENTRY RATHER THAN AROUND IT.** The `firm` classification now decides read AND write authorization for 35 tables **with no word written at the call site**. Before this entry a mis-classified `firm` table was behind a two-member vocabulary; now it is behind nothing but the classification. **And [ADR-101](ADR-101.md) section 8 records a live defect in that classification's only mechanical check**: the assertion `no firm table carries a column referencing identities` reads the `CREATE TABLE` and misses `admin_actions.on_behalf_of_identity_id`, which [`0043`](../../packages/db/migrations/0043_admin_attributed_actions.sql) adds by `ALTER`, and which is the only one of the 35 firm tables that reaches `identities` directly. **That table is `firm` correctly and the check is blind anyway, so the estate has no mechanical guarantee that the next one will be.** Repairing it is a ruling about what the `firm` class PROMISES, it turns the assertion red on a correctly-classified row, and it edits [`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts), which five concurrent sessions hold. **It is inherited, named, and not repaired here.**

**IT ALSO MAKES [ADR-096](ADR-096.md) SECTION 9's MEASURED HOLE CHEAPER TO FALL INTO.** That entry measured that adding `"@merit/db": "workspace:*"` to `apps/site/package.json` and seeding a firm-wide read leaves `tsc`, `eslint`, `check:invariants` and `gates` all green, and named `RI-08` as the remedy. `RI-08` is still unwritten. **A site that linked the package could previously only reach a `firm` table by writing `systemDb('operator-console')` on a marketing page, and can now write `firmDb()`.** Both are one line; the second is shorter and reads like nothing. **This entry does not widen the hole and it does lower the wall inside it**, and `RI-08` is worth more after this entry than before it.

### 8. What this FORECLOSES, which is the part every later slice inherits

**Ten slices write through whatever this lands. Each of these becomes expensive on the day somebody wants it.**

1. **A write outside a transaction is unavailable, permanently, and single-statement writes pay for it.** Every `INSERT` of one row opens a transaction. That is one line at the call site and a round trip on the wire, and it is the cost `job-queue.ts` already accepted for `enqueue`. **Undoing it means adding a method to `ScopedDb`, which is the change section 6 says breaks `CI-01`'s brand seed.**
2. **An INSERT into a `derived` table is a compile error and stays one until somebody builds `INSERT ... SELECT`.** `P3-i` ([session 216](../sessions/README.md)) inserts `ledger_entries` and `P3-l` (session 222) inserts `provisioning_queue`. **Neither is blocked**: a double-entry posting touches two identities' accounts by construction, so it is a firm-class act and `systemTx` serves it, and the provisioning saga runs on a job with no session. **But both must say which they are, and that is the point.**
3. **The two-word system vocabulary now authorizes WRITING every row in the estate and not only reading them.** `'nightly-batch'` needs it and a batch that cannot write is not a batch. **`'operator-console'` is the one that costs**: an operator handle reaches every row with one word, and nothing in this package distinguishes the liability dashboard it was accepted for from an operator deleting `ledger_entries`. **Narrowing it later means splitting the vocabulary and touching both call sites.**
4. **`firmDb()` has no reason and adding one later is a breaking change at every call site.** The argument for having none is that no identity is at risk; the day a `firm` table turns out to hold something identity-shaped, the fix is a per-table re-classification and not a reason.
5. **Nested transactions are foreclosed.** No savepoint, no partial rollback inside a callback. A saga that wants to compensate one step without abandoning the transaction cannot, and `P3-l`'s compensation path is the first place that could bite.
6. **`sqlExecutor` is one member wide.** A second consumer of raw SQL is a diff on [`scoped-db.ts`](../../packages/db/src/scoped-db.ts) forever, which is [ADR-084](ADR-084.md)'s *"every new table is a diff on `scope.ts`, forever. That is the cost and it is the point"* applied to a second list.
7. **`SqlExecutor` restates `JobTransaction`.** The bind is an assertion over source text, so a rename in `packages/queue` fails a test in `packages/db` and the two must move together. **The alternative was a dependency edge and `packages/queue` has ruled against having one.**
8. **The pool is reached through Drizzle's `$client`.** A Drizzle upgrade that removes it breaks every write in the estate at once, and the check that catches it is a unit test rather than a type.

### 11. Alternatives considered

- **Write methods on `ScopedDb` itself.** Refused on section 6 and on `job-queue.ts`'s own ruling. It is the shape a reader expects and it makes the non-transactional write the easy one, which is the bug ADR-006 chose Postgres to remove.
- **A third `SystemReason` member.** Refused on section 7, on [ADR-096](ADR-096.md)'s own argument, and on the finding that a reason does not narrow the key type.
- **`firmDb(reason)` with its own vocabulary.** Refused: there is nothing to justify. A reason that answers no question is the eighth `why` field [ADR-101](ADR-101.md) section 3 describes.
- **Exporting `client()` so `packages/queue` could take a real handle.** Foreclosed permanently by [ADR-084](ADR-084.md) section 9, and it is the reading that reverses [ADR-008](ADR-008.md).
- **`executeSql` as a plain method on the transaction handle.** Refused: it is the accessor routed around by anyone holding a legitimate handle, and a name is cheap.
- **Rewriting `$n` placeholders into Drizzle chunks so Drizzle's own `transaction()` could be used.** Refused on section 5: a text transform over a vendor's generated SQL breaks on a dollar-quoted string, and the failure would be a mangled `INSERT` inside a money transaction.
- **A `values` type that omits the tenancy column at compile time.** Refused on cost rather than on principle (section 4), and the runtime guard is watched on 94 table-and-spelling combinations.
- **Widening onto [`falsify-ci.mjs`](../../scripts/ci/falsify-ci.mjs) to add four new compile-refusal cases.** **Refused: the fence is absolute** ([P3 wave 3](../plans/P3-wave3-modules.md) section 13 rules 6 and 13). All four were watched failing to compile in this session with the output quoted in section 9, and **making them permanent is a follow-on with a one-file fence**, named in section 12.

### 12. Consequences

- **Ten slices can start.** `P3-i`, `P3-j`, `P3-k`, `P3-l`, `P3-n`, `P3-o` and `P3-p` all write, and none of them could.
- **`packages/queue` has a producer.** [ADR-006](ADR-006.md)'s transactional-enqueue criterion becomes gradeable for the first time, and `P3-l` is the first caller it will be graded against.
- **Four compile-time refusals exist and NONE of them is permanently watched.** They are `firmDb` on a scoped key, the scoped insert on a `derived` key, the scoped insert on `root`, and the three new brands. **`falsify-ci.mjs` is where they belong and it is outside this fence.** The follow-on is four case objects on the pattern [ADR-084](ADR-084.md) already set, taking `CI-01` from 12 to 16, and it needs an `ALLOCATION` row and nothing else.
- **The accessor now has three doors and a reviewer has to know which one a diff opened.** `scopedDb` reaches one identity, `systemDb` reaches everybody, `firmDb` reaches nobody. That is more surface than [ADR-084](ADR-084.md) signed, and the argument for it is that the three acts were always three and one door was serving them.
- **`packages/db` and `packages/queue` are now coupled by an assertion instead of by a dependency**, which is a shape worth naming because a third package will want the same trick and it is not free: the assertion is textual and a reformat of the other file breaks it.
- **The estate is strictly better than before this entry and it is not safe.** [ADR-101](ADR-101.md)'s third failure class is live, reaches the write path, and destroys rather than leaks; the `firm` class carries more weight than its only check can bear; and no write in this estate has ever been executed against a database. **Those are four different statements and none of them cancels the others.**
