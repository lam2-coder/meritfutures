### 3. Why the codec is a transcription and not a decision

**NOTHING IN THE MODULE CHOOSES A SHAPE.** `PlanRulesJson` was transcribed from DATA_MODEL section 11 key for key in [`types.ts`](../../packages/rules-engine/src/types.ts), which says so in its own header, and this file reads that type's keys and no others. Where the two existing decoders and the type agree, the module agrees with them; where the document is silent, it refuses.

**THE ROUND TRIP IS AGAINST A TRANSCRIPTION THIS SESSION DID NOT WRITE**, which is the property that makes the suite more than a function checking itself. `published-plans-in-code.ts` holds Appendix A's three plans as `PlanRulesJson` values, written by a session that had not seen a decoder. Every case renders one of them into JSON, reads it back, and compares; and the case that matters is the next one, because a decoder can be `toEqual`-green on a document and still resolve differently. **`resolvePlan(decode(stored(rules)), size)` is compared with `resolvePlan(rules, size)` for all three plans**, and `ResolvedPlan` is where the cents a payout is decided against actually live.

**THE JSON LEG IS NEVER SKIPPED**, on [ADR-250](ADR-250.md) section 3's reason: an object copy carries the `bigint` no `jsonb` column can hold, and a suite that skipped `JSON.parse` would be green on a rendering the store cannot produce.

**AND KEY ORDER IS READ BY NOTHING.** `jsonb` sorts keys by length and then bytewise, so what Postgres returns is not what was written. The suite re-sorts a document into that order at every level and decodes it again.

**THE ENCODE DIRECTION IS DELIBERATELY ABSENT AND THAT IS WHERE THIS DIFFERS FROM [ADR-250](ADR-250.md) A SECOND TIME.** `gates-codec.ts` exports both directions because the worker WRITES `rule_states.engine_gates` through `RuleStateWriterIo`. **Nothing in this repository writes `plan_versions.rules` from a `PlanRulesJson`**: the publish path validates a document somebody authored. An encoder here would be a second statement of the shape with no caller to keep it honest.

### 4. The row's real open question, ruled

The row said a decoder at READ *"either re-runs that validation, trusts the publish gate, or refuses"*. **THE FIRST ARM DOES NOT EXIST AND THE REASON IS A SIGNATURE.**

**`validatePlan` TAKES THE DECODED TYPE.** [`plan/validate.ts:660`](../../packages/rules-engine/src/plan/validate.ts) declares `validatePlan(rules: PlanRulesJson, sizes: readonly PlanVersionSizeRow[]): ValidationResult`. So "re-run the validation instead of decoding" is not a choice between two designs: decoding is strictly PRIOR to it, and this module is that step. A session that read the row's three arms as three designs would have spent its budget looking for a way to call a function that needs the value it was trying to build.

**AND IT CANNOT BE RUN AT READ EVEN AFTER DECODING, BECAUSE IT NEEDS EVERY SIZE OF THE VERSION.** `validate.ts`'s own header: *"A VALIDATOR HANDED ONE SIZE AT A TIME COULD NOT SEE THE PLAN. CV-11 and CV-12 are inequalities across the jsonb and one size row; every size must satisfy them independently, and the 150K row failing while 25K passes is a version that must not publish."* A payout read holds the account's ONE pinned size. **A `validatePlan` call there would return an `ok` about a different question from the one the publish gate answered, and an `ok` nobody may rely on is worse on a money path than no call at all.**

**SO THE RULING IS: TRUST THE PUBLISH GATE FOR THE NINETEEN, REFUSE STRUCTURALLY, AND NAME THE UNCHECKED SET.**

**THE READ-TIME FLOOR IS NOT NOTHING AND IT IS NOT THIS MODULE'S.** `resolvePlan` already refuses five rules across six throws, and they are precisely the ones whose violation would otherwise produce a WRONG `ResolvedPlan` rather than a refused one:

| Refused at | Rule | What it would otherwise be |
| --- | --- | --- |
| [`resolve.ts:64`](../../packages/rules-engine/src/plan/resolve.ts) | `CV-01` | `intraday_trailing` quietly mapped onto `trailing_eod`, which `R-17` forbids by name |
| `:102` | `SD-10` | a permanent floor lock at a bound nobody published |
| `:130` | `CV-06` | a consistency gate enabled with no share to compare against |
| `:145`, `:151` | `CV-16` | a loss limit outside the vocabulary, or one with no cents |
| `:243` | `CV-03` | a profit target of zero, which passes on the account's first day |

**WHAT IS NOT RE-CHECKED AT READ, SAID OUT LOUD.** `CV-02`, `CV-04`, `CV-05`, `CV-07` to `CV-15`, `CV-17` to `CV-19`, and the three `MZ-` materialization findings. A `plan_versions` row published before any of those existed decodes here and resolves. **The sharpest of them is `CV-13`**, which bounds `split_bp` at 10,000: a stale row carrying `20000` decodes, resolves, and would pay a trader twice the plan. **That case is written into the suite as a PASSING assertion rather than left implicit**, so the ruling is executable and a founder who wants it changed can see exactly which case to move.

**WHY NOT RESTATE THEM HERE ANYWAY.** Because nineteen rules stated a second time on the money path with nothing comparing the two statements is `FM-16` nineteen times, in the same file that exists to close one instance of it. If a founder wants a read-time bound on `split_bp`, **the right shape is a `CHECK` on the store or a widening of `resolvePlan`'s own refusals, not a second validator in a decoder.** Section 9.

**SO WHAT `plan` WAITS ON IS NAMED AND SMALLER, AND IT IS THE ROW THAT SHOULD FOLLOW.** All four case assertions above run in link 7 on every `CI-01`, so this paragraph is a predicate rather than a sentence.
