## ADR-045: A `trading_calendar` correction that leaves no prior image is refused by the database  (2026-08-16, status: accepted)

**This closes `OI-06` as raised by the session that wrote [`0032`](../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql). [ADR-042](ADR-042.md) F-2 ruled the table; it did not rule what obliges anybody to write to it. The founder has now ruled that.**

- **Context:** [ADR-042](ADR-042.md) F-2 created `trading_calendar_revisions` because `INV-04`, "replaying every mark from day one reproduces stored state byte-identically", was defined against a value that can move underneath it. **The table exists and nothing in the database requires a single row of it.** `0032` installs no trigger, the loader writes the prior image because its own code says so, and a hand-run `UPDATE` against the calendar on a Sunday afternoon leaves no image at all. **F-2 landed as a table nobody is obliged to write to**, which is the same object as a golden test that was never wired: it looks like a control in every document that cites it.

  **The exposure is not theoretical and it is not small.** `trading_calendar` decides what a trading day IS, and every counter the engine keeps is counted in trading days. A corrected row with no image makes the nightly self-audit page with **no way to distinguish a calendar correction from an engine regression**, which is precisely the failure F-2 was written to end.

  **`0032` deliberately did not add the trigger**, and it said so in its own header and in `OI-06`: [ADR-042](ADR-042.md) is silent, [CLAUDE.md](../../CLAUDE.md) says silence means propose an ADR and proceed on approval, and a money-path trigger is not a thing a session adds on its own authority. **That restraint is what this ADR is answering, and it was the right call**: the session that would have added it quietly is the session that also proved the weak reading of F-1 wrong by executing it, and only one of those two is a session's to decide.

### The ruling

**Founder ruling, 2026-08-16.**

> **Add the trigger, in `0027`'s idiom, superseding and never editing.**

**`0033` is that trigger and it is [`0027`](../../packages/db/migrations/0027_triggers_invariants.sql)'s idiom exactly: it ASSERTS, it does not WRITE.** Every guard in `0027` raises on a transaction that is already wrong; not one of them repairs anything. A trigger that wrote the prior image itself would have to invent an `actor` and a `reason`, and **a reason nobody gave is the thing `trading_calendar_revisions.reason` exists to refuse**: the column is `NOT NULL` and non-blank because a prior image with no reason records that the calendar moved and not that anybody decided it should. A trigger cannot decide it. So the database's answer to a correction with no reason is to reject the correction, not to write a reason of its own.

| Guard | What it refuses |
|---|---|
| **`CALENDAR-C1`** | An `UPDATE` to `trading_calendar` that commits without a `trading_calendar_revisions` row carrying **that row's prior image**, `to_jsonb(OLD)`, compared as `jsonb` rather than as text |
| **`CALENDAR-C1`, the counted half** | A prior image whose `dependent_row_count` is not the number the database itself counts across `fills`, `daily_marks` and `rule_states` for that day |
| **`CALENDAR-C2`** | A `DELETE` from `trading_calendar`, and a `TRUNCATE` of it |

**`CALENDAR-C1` is a deferred constraint trigger, for the same reason `0027`'s zero-sum and `STAT-C1` triggers are deferred**: the image and the update arrive in one transaction in an order the database has no business dictating. A non-deferred `AFTER UPDATE` trigger would silently require the loader to write the image first, which is a second contract nobody wrote down. Deferring makes the assertion a statement about the **transaction**, which is the unit the correction actually is.

### The counted half, which is one assertion more than the ruling names

**Ruled as part of it, and stated separately because it is separately rejectable.** `dependent_row_count` was self-reported by the loader. The `CHECK` that makes an incident an incident, `trading_calendar_revisions_incident_named_when_dependent`, reads that number and nothing else, so **writing `0` skipped the incident requirement entirely** on a day a hundred marks depended on. An audit control whose input is supplied by the party being audited is a form, not a control.

**So the trigger recounts.** It is the same three tables [P1 S-E section 4](../plans/P1-SE-trading-calendar.md) partitions on, and no more: `reconciliations` and `ingest_files` also carry a `trading_day` and are deliberately **not** counted, because the ruled partition names three tables and widening it is a founder's call rather than a migration's.

**The cost is stated rather than discovered.** Two transactions racing, one inserting a fill for day D while the other corrects day D, can make the loader's count and the trigger's count disagree, and the correction is then refused. That is fail-closed in the direction the corpus already chose everywhere else on this table: **a fill arriving for a day being corrected is itself the incident**, and the error names both numbers so the operator can see which way it moved.

### `CALENDAR-C2`, and why a delete is not a smaller version of an update

**A `DELETE` leaves no prior image, and `DELETE` followed by `INSERT` is an `UPDATE` with the control removed.** Adding `CALENDAR-C1` without `CALENDAR-C2` would have produced a guard whose bypass is one extra statement.

**The protection that exists today is real and inverted.** `trading_calendar_revisions.trading_day` is `ON DELETE RESTRICT`, so **a day that has already been corrected cannot be deleted, and a day nobody has ever touched can be.** The rows the audit trail protects are exactly the rows that already have one.

**`TRUNCATE` is named because `TRUNCATE` is the documented way past a row trigger.** It fires no row triggers at all, and the corpus has already found two guards that passed by not looking (`array_length` on an empty array, the positional NO-FLOATS block). A statement-level `BEFORE TRUNCATE` trigger closes it, and it binds the table owner, which a `REVOKE` does not.

**The escape hatch exists and it is auditable, which is what makes an outright refusal acceptable.** A day that should not have been transcribed is corrected by marking it `is_holiday` with no session, which is a positive fact, leaves a prior image, and is refused if it leaves none. **Nothing about the calendar needs a row to vanish**, and the one operation that would make a row vanish is the one operation that can leave no trace of what it said.

- **Consequences:** `0033` carries all three guards, with an `E2 READ: MONEY PATH` header, and **supersedes without editing**: `0027`, `0032` and `0004` are untouched on disk. Every guard is probed against a real database by [`scripts/db/probe_calendar_revision_required.sql`](../../scripts/db/probe_calendar_revision_required.sql), wired into the `migrations` job and **pinned by `CI-06h`**, so deleting the step is itself a gate failure; `OI-07` closed by being pinned rather than by the file existing, and this one arrives already pinned. **The loader S-E4 writes must write the image in the same transaction as the correction**, and its `dependent_row_count` must be the count rather than an estimate; both are now enforced rather than documented. **The trigger count moves from 6 to 9**, which is a generated span in [STATE](../STATE.md) and [INDEX](../INDEX.md) and is regenerated rather than stated here.

- **Alternatives considered:** **a trigger that WRITES the prior image itself** (rejected above: it must invent `actor` and `reason`, and a fabricated reason is worse than a refused update, since it makes the audit trail read as though somebody decided something); **the same trigger reading `actor` and `reason` out of session `GUC`s** (rejected: it moves the contract from the schema into `SET LOCAL` calls nobody can grep for, and an unset `GUC` either raises, which is this design with more moving parts, or defaults, which is the fabricated reason again); **a non-deferred `AFTER UPDATE` trigger** (rejected: it dictates the write order inside the transaction, and that order is an implementation detail of a loader that does not exist yet); **`REVOKE UPDATE, DELETE` on `trading_calendar`** (rejected: the table is correctable by ruling, so revoking `UPDATE` outright forbids the correction the ADR-042 F-2 machinery is built to record, and a revoke does not bind the owner); **leaving `dependent_row_count` self-reported** (rejected above); **counting `reconciliations` and `ingest_files` in the dependency set** (rejected: the ruled partition names three tables, and this migration implements the ruling rather than extending it); **a `CHECK` instead of a trigger** (rejected: a `CHECK` cannot see another table, which is why every cross-table invariant in this schema is a trigger in `0027`).
