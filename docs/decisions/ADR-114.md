## ADR-114: the composite trigger set fires on funnel order because every condition is monotone, and the KYC webhook's contractual anchor names no table  (2026-08-26, status: proposed)

**[ADR-021](ADR-021.md) ruled placement a composite trigger set firing at whichever member is reached FIRST, and the FREEZE gate ruled the set. Neither ruling could see the two places the set meets a tree that has moved since.** This entry rules that a tie inside one evaluation is broken by FUNNEL ORDER and that the tie-break is sound only because every condition in the set is MONOTONE; that the KYC webhook's contractual idempotency anchor names no table in the estate and names a pair that is not a unique key and must never become one, so its store is a PORT; and that one ordering rule is implemented twice because a type forecloses reuse, bound by a suite that reads the other implementation.

- **Origin:** [P3 wave 3](../plans/P3-wave3-modules.md) section 9's `P3-o` row and section 15's prompt, session **221**. **MONEY PATH**, [ADR-003](ADR-003.md) strict. The number was RESERVED before dispatch and **CONDITIONALLY**: [ALLOCATION](ALLOCATION.md)'s row says an entry is expected "only where the trigger set meets the accessor or the port meets a vendor". Both happened, and a third thing happened that neither clause predicted.

- **Context:** the placement decision is settled and is not reopened here. [ADR-021](ADR-021.md) took it, M19 section 1.2.1 records the FREEZE ruling `{second_distinct_account_purchase, pre_funded}` with the earliest firing, and [`0003_kyc.sql:71-72`](../../packages/db/migrations/0003_kyc.sql) writes the frozen array into the migration's own comment. What was open is everything between that ruling and a running endpoint.

### 2. THE RULING

> **1. A TIE INSIDE ONE EVALUATION IS BROKEN BY FUNNEL ORDER, AND FUNNEL ORDER IS THE VOCABULARY'S OWN ORDER WITH `direct_purchase` MOVED TO THE FRONT.** `kyc_verifications.placement` is `NOT NULL` under a CHECK, so exactly one of the reached set is written. The corpus writes the vocabulary three times and all three agree; `direct_purchase` is the one member whose list position disagrees with its moment, because the CHECK groups it with the configured placements while INV-M19-02 puts it at PURCHASE.
>
> **2. THE TIE-BREAK IS SOUND ONLY BECAUSE EVERY CONDITION IS MONOTONE, AND THAT IS A CLAUSE RATHER THAN A REMARK.** A purchase count never falls, a second concurrent account having existed is not undone by closing one, and an evaluation pass is latched. Under monotone conditions the earliest-reached trigger of a SNAPSHOT is the earliest-in-TIME trigger. **A non-monotone trigger added later makes "earliest fires" false with no type and no example assertion moving**, so the property is asserted over 500 generated cases rather than argued.
>
> **3. `kyc.triggers` GAINS ITS TYPE AND ITS READER IN `packages/kyc`, NOT IN THE RULES ENGINE, AND THE READER REFUSES RATHER THAN DEFAULTS.** M01 section 1.2 puts KYC outside the engine's type by ruling and this entry does not move that. Five shapes are refused: a non-array, an empty array, an unknown member, a repeated member, `direct_purchase` (not configurable, INV-M19-02) and `payout_request` alone (invalid as a sole trigger, ADR-021). **A reader that filled in a missing key would BE the hardcode INV-M19-01 exists to lock out.**
>
> **4. THE KYC WEBHOOK'S STORE IS A PORT WITH NO IMPLEMENTATION, AND THE MISSING THING IS A TABLE RATHER THAN AN AUTHORITY.** Findings 2, 3 and 4. `productionDeps` resolves nothing; the route is registered because the contract row exists. **No migration is written here and `0048` stays free.**
>
> **5. ONE ORDERING RULE IS IMPLEMENTED TWICE AND THE TWO ARE BOUND BY A SUITE THAT READS THE OTHER.** Finding 5 forecloses reuse. [`packages/kyc/test/webhook-bind.test.ts`](../../packages/kyc/test/webhook-bind.test.ts) reads `packages/psp/src/webhook.ts`, compares the refusal vocabulary member for member and the ordering steps position for position, **inside the verify function's own body rather than over the file**, because every step is also named in a doc comment higher up.
>
> **6. MERIT NEVER PROXIES A DOCUMENT, AND THE INVARIANT IS ENFORCED IN TWO PLACES BECAUSE ONE OF THEM CANNOT SEE INSIDE A JSONB BLOB.** The port has no method returning a document and no field one could be assigned to. The receiver SCREENS a verified payload before anything stores it, **REFUSES rather than redacts**, and records **key paths and never values**.

### 3. Clause 1 and 2 in full: what "earliest" means when two triggers are true at once

**ADR-021's phrase is *"whichever of the configured triggers is reached FIRST"*, and a gate evaluated at a moment sees a set of facts rather than a history.** Two configured triggers can be true at the same evaluation, and the row admits one value.

**The tie-break is not invented here. It is read off the corpus, three times, and the three agree**: ADR-021's own table, [M19 section 1.2.1](../plans/M19-kyc-identity.md)'s table, and [`0003_kyc.sql:77-85`](../../packages/db/migrations/0003_kyc.sql)'s CHECK list all write the vocabulary in the order a trader reaches the moments. `direct_purchase` is moved to the front and nothing else moves.

**The second-order property is the one that matters and it has to be stated because a type cannot carry it.** Recording the earliest trigger of a snapshot is only the same thing as recording the earliest trigger in time if the conditions never go back. They do not:

| Trigger | Input | Why it cannot un-fire |
|---|---|---|
| `first_purchase`, `second_purchase_any` | purchase count | Purchases are rows; the count only rises |
| `second_distinct_account_purchase` | **high-water** distinct concurrent accounts | Deliberately a high-water count and not a live one. A fleet operator who closes an account **has still been a second-account holder**, and a live count would let the fleet trigger un-fire, which is the exact evasion the trigger exists to catch |
| `eval_pass` / `pre_funded` | evaluation passed | Latched |
| `direct_purchase` | the pinned plan's shape plus a purchase | The plan version is pinned; INV-M19-02 makes it unconfigurable |
| `payout_request` | a payout was requested | A request is a row |

**The high-water reading of the second-account count is a ruling and not an implementation detail**, and it is the one line of this entry most likely to be quietly reversed by somebody writing the query, because "how many accounts does this trader have" is the natural thing to ask and it is the wrong question.

**What this forecloses:** a trigger whose condition can become false again cannot join this set without re-opening clause 2. Naming it here is cheaper than discovering it from a funnel that reports the wrong trigger, because **funnel data is not reconstructible after the fact** (INV-M19-11 says so in its own words).

### 4. Where the port meets a vendor: two verifiers, and what would make it one

**API_CONTRACT section 10 states ONE rule for every inbound webhook and this workspace now implements it twice.** Finding 5 is why: the first implementation is branded to the payment provider set, and the brand is not decoration. `purchases.psp` carries a CHECK; `kyc_verifications.provider` does not (finding 6), and the difference is exactly the difference between a set Merit has closed and a choice Merit has not made.

**So `KycProvider.provider` is a `string`.** A closed union here would be **choosing a vendor in a type**, and ADR-021 makes that choice a DISCLOSURE event: the selected provider is named in the privacy policy at selection time. The untrusted `:provider` path parameter is resolved to a 404 instead, which is where an untrusted path parameter belongs.

**WHAT WOULD END THE DUPLICATION IS A THIRD PACKAGE NEITHER PROVIDER SET BRANDS**, holding the ordering, the header reading, the MAC decoding and the refusal vocabulary, with the provider identity a parameter. **It is not created here, and the reason is finding 7 rather than taste**: a new package that `apps/api` consumes forces an edit to `apps/api/package.json` and `pnpm-lock.yaml`, and section 6 is what that costs while three sessions run concurrently. Lifting it is a slice with two consumers already written, which is the cheapest moment to do it and is not this moment.

**Until then the binding suite is the control**, and it is `packages/ledger`'s remedy for the same hazard: when a package cannot import the statement it must agree with, its suite reads it.

### 5. Where the trigger set meets the accessor: the anchor names nothing

**API_CONTRACT section 10's table gives this endpoint an idempotency anchor and the estate has no table for it.** Findings 2, 3 and 4, in the order they bite:

1. **There is nowhere to write the claim.** The only inbound-webhook table belongs to the payment rail.
2. **Even given a table, the pair the contract names cannot address a row on the table that exists.** `(provider, provider_applicant_id)` is not unique on `kyc_verifications` and **must not be made unique**, because SD-M19-01 makes a re-verification a new row against the same applicant. This is the first place in the corpus where [ADR-112](ADR-112.md)'s address refusal is **correct on a table nobody had checked**, rather than a transcription gap: the DDL agrees with `schema.ts` here, and both agree that the pair names many rows.
3. **And no authority admits the caller.** A webhook has no identity, `kyc_verifications` is `owned`, and the system reasons are two.

**The consequence is stated as code rather than as a comment.** `KycWebhookStore` is a port, `productionDeps.store` is `null`, and a deployment that cannot store a payload **does not verify one**: section 10 requires the raw payload stored, and a receiver that verified and then discarded would answer 200 for an event nobody can re-drive.

**One vocabulary decision is taken here so that the migration which finally lands does not have to invent it.** `KycProcessingResult` is `psp_webhook_events.processing_result`'s four CHECK values plus **`rejected_document`**, which has no counterpart on the payment rail because a payment provider has no document to send. **When that table is created, that member is a CHECK value somebody must decide on, and this is where it was decided.**

### 6. The two files outside the fence, and the collision reported rather than resolved

**`apps/api/package.json` gains one line and `pnpm-lock.yaml` gains eighteen, every one of them an importer block and none of them a `packages:` entry, so [VG-12](../../research/VIBE_FAILURE_POSTMORTEMS.md) is asked to admit nothing.** [Session 219](../sessions/2026-08-26-session-219.md) took the identical pair for `@merit/psp` and measured it the same way.

**The pair is forced rather than chosen** (finding 7), and the alternative was considered and rejected: putting the port in the route module would have kept the fence intact and put the trigger evaluator somewhere `apps/worker` cannot reach it, because [ADR-100](ADR-100.md) ruling 2 forbids anything outside `apps/api/src/routes/` from importing anything inside it. **`pre_funded` fires at `phase.passed`, which is the worker's moment.** A trigger evaluator only one of the two callers can import is half a deliverable.

**THE COLLISION IS REPORTED AND NOT RESOLVED.** Session 220 creates `packages/affiliate` and session 223 creates `packages/enrichment`, both consumed by `apps/api`, and **neither slice's fence holds `apps/api/package.json` or `pnpm-lock.yaml` either**. Three concurrent branches add one line each to the same dependency block. It is a one-line textual conflict on merge rather than a design conflict, and it is **the serialization [ADR-100](ADR-100.md) bought the ROUTES out of, unbought for the manifest**: the same argument that made the module list a directory listing applies to a dependency list that every new package edits, and nobody has made it yet.

### 7. What this entry does NOT do

**It does not re-decide placement.** ADR-021 and the FREEZE gate did, and this entry transcribes them.

**It writes no migration, allocates no migration number, touches no `packages/db` file and registers no scope rule.** `0048` stays free.

**It rules nothing about dedupe, sanctions or re-verification.** `dedupe_matches` is [session 168](../sessions/2026-08-24-session-168.md)'s `M19-8`, `sanctions_screenings` is M19 section 3.4, and `POST /kyc/reverify` is M19's. `POST /kyc/session` REFUSES an expired verification with a `409` naming re-verification rather than writing an `initial` row that would break the supersession chain INV-M19-06 exists to keep.

**It selects no vendor and touches no privacy policy.** ADR-021 makes provider selection a disclosure event.

**It does not add the two API_CONTRACT section 12 rows these endpoints owe.** That document is outside this session's fence, `CI-06k` reads the document and no source file, and the debt is recorded here and in the session entry rather than taken. [Session 218](../sessions/2026-08-26-session-218.md) recorded the identical debt for `POST /phone/change/:id/cancel`, which makes this the second one waiting on the same edit.

### 8. Approval line

**UNSIGNED. One checkable clause, carrying the direction it fails in.**

> Verification fires at each configured trigger and at the EARLIEST of them, watched against a fixture where both `second_distinct_account_purchase` and `pre_funded` become true in either order and in the same evaluation, with the same trigger named in all three; a second verification of the same applicant writes a NEW row rather than updating one; and no document-bearing key in a verified webhook payload reaches any store.

**Cost if wrong:** P3's fourth done-clause, *"verification firing at each configured trigger"*, is asserted by nothing, and the corpus-coverage figure the post-beta adjudication is settled on is computed over a funnel that recorded the wrong trigger. **Funnel data cannot be reconstructed afterwards**, which INV-M19-11 states as the reason the column exists.

**Founder approval: PENDING.** MONEY PATH: the [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) line-by-line read is owed on every line this entry lands and this branch does not merge before it.

**What a founder read adds and this entry cannot.** Three of the decisions here are judgements rather than derivations. **That a tie is broken by funnel order with `direct_purchase` moved to the front** (clause 1) reads ADR-021's *"reached FIRST"* as an order the corpus never wrote down as an order, and the one member that moves is the one whose list position disagrees with its moment. **That the second-account condition is a HIGH-WATER count** (section 3) is the line this entry itself names as most likely to be quietly reversed, because *"how many accounts does this trader have"* is the natural query and it lets a fleet operator un-fire the trigger by closing an account. **That the KYC webhook's store is a port with no implementation, so a deployment that cannot store a payload does not verify one** (clause 4) prefers a route that refuses to a route that verifies and discards, and the cost is that the endpoint the contract declares answers nothing until a table nobody has written exists. Section 5's `rejected_document` is a fourth thing to read before signing: a CHECK value is decided here for a table that does not exist, so the migration that finally lands inherits a vocabulary rather than choosing one.
