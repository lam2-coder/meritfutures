**THAT SHAPE IS THE WHOLE DELIVERABLE AND IT IS DELIBERATE.** The port stays **BLOCKED**, the wired count does **NOT** move, and every unimplemented member **refuses visibly** rather than answering wrongly. **TEN WIRED OF TWENTY-FOUR DECLARED WITH FOURTEEN BLOCKED, BEFORE AND AFTER** ([`wiring.test.ts`](../../apps/api/test/wiring.test.ts), the count assertion), because `wired` is the set of ports `start.ts` CALLS and `start.ts` is untouched.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `291`, session **482**, branch `claude/the-first-real-payout-backend`. **NO MIGRATION NUMBER IS TAKEN OR RESERVED** and `packages/db/migrations/**` is untouched. **NO `RI-nn` WAS MINTED** and `RI-32`, which row `291` reserved to this session by name, **IS LEFT FREE**; section 8 says why.

- **MONEY PATH. The [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) read is OWED AND HAS NOT HAPPENED.** Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.** It inherits `E2` debt on [ADR-287](ADR-287.md), [ADR-285](ADR-285.md), [ADR-283](ADR-283.md), [ADR-281](ADR-281.md), [ADR-268](ADR-268.md), [ADR-264](ADR-264.md), [ADR-260](ADR-260.md) and [ADR-233](ADR-233.md), every one of which is `proposed` and UNSIGNED.

- **NOTHING IS WIRED AND THAT IS THE HARD PROHIBITION THIS ROW CARRIED.** `start.ts` does not call `usePayoutBackend`, installing the backend is [ADR-287](ADR-287.md) slice 9 behind a founder `E2` read, and a session that wired it early would have moved a count nobody verified.

- **TWO SIBLING ROWS ARE IN FLIGHT AND NEITHER IS TOUCHED HERE.** Row `289` (session 480) owns the `eligibility_snapshot_id` ruling and row `290` (session 481) owns the `failure_note` and `timeline` ruling. Slices 6 and 7 are blocked on them; this slice depends on neither and waited for neither.

### 1. The re-derivation row `291` required, and its verdict

**Row `291` required `identityStatus`'s EXISTS classification to be re-derived against the primary source before anything was built on it, and said that a contradiction would be the deliverable.** There is no contradiction. [ADR-287](ADR-287.md) section 2 holds in all three of its legs, each read at the file rather than carried:

| The claim | Re-derived at | Verdict |
|---|---|---|
| The enum has three members | `CREATE TYPE identity_status AS ENUM ('active', 'restricted', 'closed')`, [`0001_extensions_and_enums.sql:27`](../../packages/db/migrations/0001_extensions_and_enums.sql) | **HOLDS** |
| The column exists and is not null | `status identity_status NOT NULL DEFAULT 'active'`, [`0002_identity.sql:42`](../../packages/db/migrations/0002_identity.sql) | **HOLDS** |
| `identities` is reachable on a scoped handle | `identities` is scope class `root` on `id` in `SCOPE_RULES` ([`scope.ts`](../../packages/db/src/scope.ts)) and `ScopedTableKey` excludes only `FirmTableKey` and `PairTableKey` | **HOLDS** |
| The type transcribes the column | `IdentityStatus` is `'active' \| 'restricted' \| 'closed'` ([`routes/payouts.ts`](../../apps/api/src/routes/payouts.ts)) | **HOLDS** |

**AND ONE LEG WAS CHECKED THAT [ADR-287](ADR-287.md) DID NOT STATE, BECAUSE AN ENUM IS A THING A LATER MIGRATION CAN WIDEN.** A recursive read of `packages/db/migrations` for `ALTER TYPE identity_status` and for `ALTER TABLE identities` touching `status` returns **NOTHING**. The three members are the three members on the merged tree, so the decoder's list and the column's CHECK are one fact and not two.

**THE SIGNATURE'S RULING IS PRESERVED RATHER THAN RESTATED.** `identityStatus()` takes no account, because the refusal is a fact about the human evaluated before anything about the account is read, and `decidePayout` calls it first. The implementation reads **PER CALL AND MEMOISES NOTHING**: [ADR-287](ADR-287.md) section 2 warns that an adapter reading the identity row lazily inside `subject()` and caching it would satisfy the type and break [ADR-140](ADR-140.md)'s ordering, which is `INV-M5-23`'s placement argument. A cache would make that order an accident of which member ran first, and `payout-backend.test.ts` asserts two calls are two reads so a later slice cannot add one quietly.

### 2. `transact`, which is the load-bearing decision in this session

**Row `291` said its shape is what slices 4 to 7 inherit, so every property below is stated as a decision rather than left as code.**

```
transact: (session, fn) => db.scoped(session.identityId, (handle) => { ...; return fn(tx); })
```

**THE EXISTING SCOPED-DOOR IDIOM IS USED AND NO NEW ONE IS INVENTED.** `db.scoped` is `ApiDb`'s first door ([`apps/api/src/db.ts`](../../apps/api/src/db.ts)), and `databaseWithdrawalBackend` ([`routes/wallet-withdrawals.ts`](../../apps/api/src/routes/wallet-withdrawals.ts)) is the precedent this file follows line for line: the same port shape, the same door, the same `tx.rows('identities')` read, the same exactly-one-row refusal.

**FIVE PROPERTIES, AND EACH ONE IS A CHOICE THE NEXT SLICE INHERITS:**

1. **THE IDENTITY IS BOUND ONCE, FROM THE SESSION.** That is why `PayoutTx` carries no identity parameter, in the port's own words. A member taking an account id can be handed one the caller does not own, and a scoped read of a foreign account's rows is EMPTY, which is how `subject()` returning `null` becomes API_CONTRACT section 1's 404 rather than a 403 that confirms the account exists.

2. **IT COMMITS ONLY IF `fn` RETURNS, AND THIS FILE ADDS NO SECOND COMMIT RULE.** `db.scoped` is `transaction(scopedDb(identityId), fn)`, which issues `BEGIN`, `ROLLBACK`s on a throw without letting a failed rollback replace the error that caused it, and `COMMIT`s on the one path where `fn` returned ([`packages/db/src/scoped-db.ts`](../../packages/db/src/scoped-db.ts)). Re-derived at the function rather than assumed from the port's docblock. The suite asserts a throw from `fn` propagates unchanged, because an adapter converting a throw into a value would commit a transaction whose caller failed.

3. **NO SECOND UUID PREDICATE.** `db.scoped` refuses a non-uuid before the accessor with `DbDoorError`, "rather than passing it through to a predicate that would match no row and read like an empty account". A check here would be that fact stated twice on the money path.

4. **NO LOCK IS TAKEN, AND IT IS REPORTED RATHER THAN DECIDED.** `databaseWithdrawalBackend` calls `tx.lockScope()` FIRST, because its handler reads a balance and then writes against it. Nothing on this transaction reads-then-writes yet, `PayoutTx` declares no `lockScope` member to call, and a lock installed here would be a serialization policy for slices 4 to 7 chosen by the slice that could not see their reads. **It is registered as slice 6's question in section 7 finding F3**, and the suite asserts the current call list so that adding one is a visible decision rather than a silent line.

5. **THE HANDLE DOES NOT ESCAPE, AND IT IS HELD BY SHAPE RATHER THAN BY A RUNTIME FLAG.** `transact` takes the unit of work instead of handing a `PayoutTx` back, which is `ApiDb`'s own stated property ("a transaction cannot outlive the function that opened it and no caller has a `commit` to forget") extended one layer out. A validity flag flipped after `fn` settles was considered and REFUSED: it would be a second mechanism for a property the signature already carries, and `db.ts` says in its own words that this is "a property of every call site rather than of this signature".

### 4. Two refusal vocabularies, and the difference is the status code

**THIS IS THE ONE GENUINELY NEW RULING IN THIS FILE AND IT IS SMALL, SO IT IS STATED PLAINLY RATHER THAN LEFT IN A DOCBLOCK.**

`PayoutBackendUnwired` becomes **503**, which API_CONTRACT section 2 defines as a dependency that is down and safe to retry. An unbuilt member is exactly that.

`PayoutRowError` is **DELIBERATELY NOT** a `PayoutBackendUnwired`, so `unwiredOrThrow` rethrows it and the route answers **500**. This is `RuleStateUnreadable`'s ruling applied one door over, in the words `wiring.test.ts`'s own entry already carries: a row whose columns disagree with the schema that wrote them is an internal error, and a retryable status would tell a trader to retry what no retry can fix.

**NO SYNTHESISED DEFAULT ON EITHER PATH, AND THE FOURTH-MEMBER CASE IS THE ONE THIS MODULE EXISTS TO GET RIGHT.** A status outside the enum's three members RAISES. It never falls back to `restricted`, which would deny a trader on a value nobody wrote, and never to `active`, which would open the money door on one. [ADR-041](ADR-041.md) refused a fourth member and [ADR-140](ADR-140.md)'s predicate is `= 'active'` precisely so a fourth arriving later fails CLOSED, and closed here means raising rather than choosing. **NO CAST ONTO AN UNVALIDATED ROW**: the accessor hands back `unknown`, `asRow` narrows it with a shape test that throws, and `member` refuses a value outside a closed list.

**AND ZERO ROWS IS NOT A REFUSAL TO HAND THE TRADER EITHER.** `identities` is `root` on `id`, so the predicate is the caller's own row and the answer is exactly one. Zero is Merit's records disagreeing with the session it just authenticated, which is not the trader's fault and is not a status.

### 5. Money, secrets and the standing prohibitions

- **NO FLOAT TOUCHES THIS PATH, INCLUDING IN A FIXTURE.** This slice reads no money column at all: the only column it reads is `identities.status`, which is an enum. The one numeric literal in the suite is an HTTP status code.

- **NO GATE WAS WEAKENED AND NO FENCE WAS WIDENED.** They are the same move.

### 7. What this session found rather than built

**F1. `idempotency` COULD ANSWER TODAY AND IS DELIBERATELY LEFT REFUSING.** `databaseIdempotencyStore` exists at [`src/idempotency-store.ts:144`](../../apps/api/src/idempotency-store.ts), has its own suite, and would satisfy the field on this tree with one line. **It is not installed, and the authority is `usePayoutBackend`'s own closing sentence**: installing `listPayouts` and `idempotency` beside a `transact` whose `subject` rejects would put a live-looking route in front of the arm that approves payouts. **A partial backend refuses AS A WHOLE or it is a fixture serving real traffic.** This is the member row `291` predicted a session would be tempted to fill, and it is written here rather than taken. Slice 9 installs it, with the rest.

**F2. THE `PayoutTx` CENSUS WAS BLIND TO AN IMPLEMENTATION CARRYING NO TYPE ANNOTATION.** Section 6. Recorded as a landmine because the failure mode is silent and general: any future adapter satisfying a port by contextual typing alone is invisible to a census keyed on `: PortName`, and the census reports PASS over it. **The durable repair is not this file's**: it is either a census that reads the module list rather than a token, or a standing convention that a port implementation carries its annotation. The convention is followed here and stated at the site; the census is unchanged in method.

**F3. THE LOCK IS SLICE 6's QUESTION AND IT IS OPEN.** Section 2 property 4. When `insertPayoutRequest` lands, the transaction reads an eligibility basis and then writes a `payout_requests` row against it, and `payout_requests_no_in_flight_uq` is the constraint that would arbitrate a concurrent second request. Whether that is served by the unique index alone, as `databaseIdempotencyStore` is served by its primary key, or needs `tx.lockScope()` the way the withdrawal path does, is a decision that belongs to the slice that can see the write. **This slice does not pre-empt it and does not leave it undiscovered.**

**F4. `PayoutRowError` IS A NEW ERROR CLASS ON THE PAYOUT PATH AND THE ROUTE DOES NOT KNOW IT BY NAME.** It is caught by nothing and becomes a 500, which is the intent (section 4). Registered because the route's catch is a list of classes and a later slice may reasonably decide a malformed identity row deserves its own handling. **It must not be made a `PayoutBackendUnwired` to achieve that**, because that would make an internal fault retryable.

### 8. `RI-32` IS NOT MINTED, AND IT IS LEFT FREE

**Row `291` reserved `RI-32` to this session BY NAME and conditioned it: "only if the work needs one".** It does not, and the reasoning is written out rather than left as an omission, because a reserved number quietly unused reads like a number forgotten.

**THE THREE CANDIDATES WERE ENUMERATED AND EACH IS ALREADY SERVED:**

1. **"`start.ts` does not call `usePayoutBackend`"** is the property this row most needed held. It is **already** a live assertion in two places: `wiring.test.ts` derives the wired set from `start.ts` itself and pins the count, and `rule-state-producibility.test.ts` asserts the call's absence directly. A third statement would be `FM-16` on the money path, which is the defect this repository names most often.
2. **"No unimplemented member answers plausibly"** is BEHAVIOUR and not repository structure. A static check cannot see what a member returns; `payout-backend.test.ts` drives all five and watches each reject. An invariant here would be a weaker copy of a test that already exists.
3. **"No cast onto an unvalidated row in the new module"** is not mechanical. `asRow`'s own `as Record<string, unknown>` is the legitimate narrowing every module in this tree performs after a shape test, so a token-level ban would fire on the correct code and a nuanced one is not a static check.

**SO `RI-32` STAYS FREE AND IS THE NEXT AVAILABLE INVARIANT NUMBER.** No seed-and-watch transcript appears in this file, because minting nothing means there was nothing to watch fail, and a transcript of an invariant that does not exist would be the theatre the ritual exists to prevent.

### 10. Approval

**Status `proposed`. The approval line below is UNSIGNED, and merging is not signing.**

This is a **BUILD** row on the **money path**, so unlike [ADR-287](ADR-287.md) there is a diff to read line by line, and that read is **OWED AND HAS NOT HAPPENED**. It is one new module of about two hundred and forty lines, one new suite, and two edits to existing suites.

- **Decision:** `postgresPayoutBackend` implements **`transact`** and **`identityStatus()`** and **nothing else**. Its other five members reject with `PayoutBackendUnwired`. The port stays BLOCKED, `start.ts` is untouched, and the wired count does not move.
- **Consequences:** [ADR-287](ADR-287.md) slices 4 to 7 now have a transaction to build on and inherit the five properties in section 2. `usePayoutBackend`'s clause FIVE narrows for the first time and names five members rather than a port. `RI-32` is left free.

**WHAT A FOUNDER READ ADDS AND THIS ENTRY CANNOT.**

**THE FIRST THING TO READ IS SECTION 2, BECAUSE IT IS WHAT SLICES 4 TO 7 CANNOT CHEAPLY CHANGE.** Five properties are decided there and the fifth is the one most worth disagreeing with: the handle's non-escape is held by SHAPE, on `db.ts`'s own argument, and a reader who wants a runtime guard on the money path would be overruling a convention rather than fixing an oversight.

**THE SECOND IS `idempotency`, WHICH IS A REFUSAL THIS SESSION CHOSE.** It could answer today. It is left refusing on `wiring.test.ts`'s closing ruling, and that ruling is one sentence in a test file rather than an ADR. **If the founder reads the partial-backend argument differently, F1 is a one-line change and this is the moment to say so**, because slice 9 will otherwise install it under a count that moves.

**THE THIRD IS WHETHER SECTION 4's 500 IS RIGHT.** A malformed `identities` row answering 500 rather than 503 is deliberate and follows `RuleStateUnreadable`, but it is a trader on the payout door seeing an internal error, and the alternative reading is that any failure on this route should be retryable. **This entry takes the first and states it as a decision rather than a transcription.**

**AND ONE THING THIS ENTRY IS NOT A JUDGEMENT ABOUT.** Section 1 is a FINDING and not a preference: every leg is a citation, and the re-derivation can be refuted by opening the migration rather than by disagreeing. Row `291` said a contradiction there would be the deliverable and would stop the session. There was none.
