### 2. Why a sibling entry's MEASUREMENT can be wrong and not only its summary

The dispatch asked for this to be re-counted on the grounds that [ADR-416](ADR-416.md) counted callers for [ADR-303](ADR-303.md) limit 4 and got it wrong, which [ADR-421](ADR-421.md) proved. **This row is the second instance of the same failure and it has a sharper shape than the first.**

[ADR-413](ADR-413.md) wrote "nine docblocks" from a reading of the directory. It is right about the number of MODULES and wrong about the noun. Three entries then carried the phrase forward verbatim without opening the directory, and each of the three added weight to it: [ADR-416](ADR-416.md) said the sentence now carried more because `pinned-plan.ts` had come to depend on a `SystemTx` satisfying `CatalogReadTx`, and [ADR-421](ADR-421.md) said it was load-bearing a second time because it is the seam a narrowing would break. **Both of those observations are correct. Both were made about a sentence nobody had re-read.**

**AND THE COPYING HID THE PART THAT MATTERED.** The gap the four entries were pointing at, in substance, is the admin liability read. The sentence they used to point at it names `AdminSourceTx`, which does not have `LiabilityTx` as a member. So for four entries the words said one thing, the intent meant another, and the words were the half that got carried.

### 4. Which handles were already controlled, and the instrument that answered it

**A GREP FOR AN ASSIGNMENT WAS WRITTEN FIRST AND IS NOT WHAT THIS SECTION RESTS ON.** It finds the assignments, but it cannot tell whether a given handle is reached by one, because `AdminSourceTx` is an intersection and an assignment to it silently binds five arms that are never named at the site.

**SO EACH HANDLE WAS BROKEN IN TURN AND `tsc` WAS ASKED WHO NOTICED.** [ADR-418](ADR-418.md)'s instrument: measure a property by performing the change. A method no `SystemTx` carries was appended to one interface, the whole deployable was typechecked, the file was restored, and the errors were read. **The first pass of this was WRONG and is recorded rather than quietly corrected**: it counted any error at all, which counts every hand-written fake that implements the interface, and it reported all ten handles as controlled. The second pass counts only errors naming `SystemTx`, which is the property in question.

### 5. The obstruction four entries deferred on, re-tested

[ADR-413](ADR-413.md) item 4 states it in one sentence:

> the binding site would be a file that names `@merit/db`, and [ADR-171](ADR-171.md) clause 1 rules there is no system door here to bind against.

and section 5 of that entry expands it: *"`apps/api/src/db.ts` is the one file that may name `@merit/db` and declares no `system` door for it to bind against."*

**IT IS SOUND FOR `apps/api/src` AND IT WAS NEVER TESTED AGAINST `apps/api/test`, WHICH IS WHERE THE WITNESS BELONGS.** Three separate reasons, and any one of them is enough.

**(a) THE ONE-FILE RULE IS ABOUT `src`, AND ABOUT HANDLES RATHER THAN NAMES.** [ADR-171](ADR-171.md) clause 4 put the convention into `apps/api/test/db.test.ts`, and that file's own header records that "one file imports `@merit/db`" is **false in this tree and was false before this file existed**. What it pins is a map from file to which VALUE each takes off the accessor. It says nothing whatever about `test/`, where many files already name the accessor; this row derived that count and does not transcribe it into the suite.

**(b) A TYPE BUYS NO CAPABILITY, AND THE FILE HOLDING THE CONTROL SAYS SO IN ITS OWN WORDS.** `db.test.ts` again:

> A type-only import is deliberately not pinned, because a type buys no capability -- `import type { SystemTx }` cannot open anything, and a case that failed on one would be asserting a house style rather than an authority.

**That sentence names this row's instrument by name, and it was written by the entry that created the obstruction's other half.**

**(c) THE BINDING WAS ALREADY TAKEN, TWICE, AND ONE OF THEM IS INSIDE `src`.** `apps/api/test/admin-source-pinned-plan.test.ts` imports `SystemTx` from `@merit/db` and binds it to a supplier by type, which [ADR-416](ADR-416.md) landed. And `apps/api/src/admin-source/pinned-plan.ts` carries `import type { CatalogReadTx } from '@merit/db'`, **a type-only import from the accessor inside `apps/api/src/admin-source/` itself**. So the sentence "`db.ts` is the one file that may name `@merit/db`" was already not describing the tree on the day [ADR-413](ADR-413.md) wrote it, and [ADR-416](ADR-416.md) made it less true two files further in without either entry noticing.

**NOTHING HERE WEAKENS [ADR-171](ADR-171.md) CLAUSE 1 AND NOTHING HERE ASKS FOR A DOOR.** No third door is declared, no value of type `SystemTx` is constructed, `apps/api/src/db.ts` is not in the diff, and the wired triple does not move. **A door and a type are different purchases and the deferral conflated them**: the door is an authority a running process acquires, and the witness is a sentence `tsc` refuses to compile. This row buys the second and asks for none of the first.
