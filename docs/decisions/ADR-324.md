**A refusal is the one place a later session reads to find out what to build, so a refusal quoting a discharged obstruction sends that session to do work already done.** [ADR-253](ADR-253.md) section 5 repaired exactly that on `affiliate_statements`; [ADR-304](ADR-304.md) section 8 repaired it again on `affiliate_commissions` and wrote the assertions that were supposed to end it. **This row is the third occurrence, at the site of the second, and the assertions did not fire.**

**WHAT HAPPENED.** [`0078_affiliate_commission_owner.sql`](../../packages/db/migrations/0078_affiliate_commission_owner.sql) merged ([ADR-321](ADR-321.md), on ADR-304 section 4). **THE RULING IS IN TWO PARTS AND THE SECOND IS THE POINT OF THE ROW.** The message is rewritten to say what is true now. And the assertions on it are rewritten to COMPUTE their expectations from `scope.ts`, `schema.ts`, the migration directory and the `ScopedTx` interface body, and to require the served message to agree with what they find in BOTH directions. **A test that pins prose goes stale in silence; a test that derives goes red.**

**THE METHOD IS STILL UNWIRED AND THIS ROW DID NOT WIRE IT.** `unwired('stats', COMMISSIONS_UNREACHABLE)` is untouched, no adapter is written, no counting door is built, `scopePredicate` and the six scope classes are not edited, and **no SQL is written and no migration is touched**.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `324`, session **515**, dispatched as `claude/a-refusal-that-outlived-its-reason`. **NOT A MIGRATION AND NOT A MONEY MOVE, BUT AN `E2` READ IS OWED ANYWAY: it changes what an operator is told when a money route refuses.** Three reads are inherited, all `proposed` and all UNSIGNED: [ADR-321](ADR-321.md), [ADR-322](ADR-322.md) and [ADR-323](ADR-323.md).

### 3. THE RULING, part one: what the message says now

**The shape is `TWO obstructions, one discharged, one live`, and neither half is deleted.**

1. **The commissions half says what closed it.** `affiliate_commissions` is DECLARED in `schema.ts` and REGISTERED `derived` via `affiliates` on `affiliate_id` in `scope.ts`, so the three money figures of `AffiliateStats` have a scoped door and wait on an adapter alone. The message names the column the DDL declares, names the three sibling tables it matches, and names `0078` as WRITTEN.
2. **The class question is recorded as SETTLED rather than dropped.** The answer is `derived` and not `firm`, **and the sentence saying why `firm` would have been wrong is kept**: it is available, it passes every mechanical check in this repository, and it is FALSE, because a commission is what Merit owes a named affiliate. That mistake is still reachable by a session that wants a one-line registration, and the only place it is named is here.
3. **The second obstruction is carried over unchanged in substance and strengthened by one sentence.** `conversions_30d` is a count over `attributions`, which is `pair`: excluded from `ScopedTableKey` AND from `FirmTableKey`, so `scopePredicate` throws on it, and NO scope class fixes that, because the exclusion ADR-106 wrote is a ruling about what a ROW read returns while a count returns no row. What serves it is a NAMED DOOR returning one integer, ADR-262's and ADR-265's construction, needing no registry change and no DDL. **The added sentence is that no migration reaches it either, so `0078` neither helped it nor could have** -- which is the specific wrong inference the old message's shape invited.
4. **The four-step closing sentence is updated rather than replaced.** It read *"this method waits on a migration, a registration, a counting door and then an adapter, in that order"*. It now reads that it waited on those four, **THE FIRST TWO HAVE LANDED**, and what is left is the counting door and then the adapter, and no further ruling. The order is preserved because the order is the useful part.

**The docblock above the constant keeps every retired sentence, per `RI-14`'s rule and this file's own habit**, and adds what is new: that nothing went red, and why.

**The module header's item 1 carried the same `0078 is RESERVED ... and is NOT WRITTEN` clause a second time**, which is the exact duplication ADR-253 section 5 found on `affiliate_statements`. It is repaired in the same commit and its old wording is quoted rather than deleted.

### 4. THE RULING, part two: which assertions are DERIVED, and which stay TEXTUAL

**The file's own boundary is unchanged and it is what made the repair non-obvious.** [`affiliate-stats-obstructions.test.ts`](../../apps/api/test/affiliate-stats-obstructions.test.ts) asserts over what a caller is SERVED and not over the source file, on ADR-253 section 5's reason: an assertion over source text would forbid the docblock that quotes what was corrected, and could be satisfied by deleting the record instead of the defect. **The repair keeps the SUBJECT the served message and moves only the EXPECTATION into the tree.**

**Derived, each from a named file, each asserted in both directions:**

| The expectation | Derived from | Goes red when |
|---|---|---|
| whether the message may say `UNREGISTERED`, and which class it must name | the registry rule parsed out of [`scope.ts`](../../packages/db/src/scope.ts), including its `via` and `localColumn` | the table is registered, unregistered, or registered under a different class, `via` or column |
| whether the message may say `undeclared in schema.ts` | the `pgTable('affiliate_commissions', {...})` body in [`schema.ts`](../../packages/db/src/schema.ts) | the owner column is added or removed |
| which migration number the message must name, and that it may not say `NOT WRITTEN` | the migration directory, filtered to files declaring `ALTER TABLE affiliate_commissions ADD COLUMN affiliate_id` | the file is written, removed, renumbered or superseded by a second one |
| the column DDL the message quotes | the `ADD COLUMN` line of that migration, with the `ON DELETE` tail stripped | the DDL spells the column differently from the refusal |
| the scope class the message attributes to `attributions`, and whether it may claim no class reaches it | the `attributions` rule in [`scope.ts`](../../packages/db/src/scope.ts) | `attributions` moves off `pair` |

| that every `ADR-nnn` the message cites exists | `docs/decisions/` | a cited entry is renumbered or was never written |
| the list of clauses the tree has RETIRED, asserted absent from **all six** messages | the first three rows of this table, assembled at run time | a retired clause reappears at any of the six sites, not only at `stats` |

**The last row is the one that would have caught this defect.** It builds its list of forbidden phrases from the tree rather than from a reader's judgement, so on a tree where the clauses are still true the list is empty and the case is vacuous BY CONSTRUCTION; on this tree it is non-empty and the case asserts it, and that non-emptiness is itself asserted.

**Textual, and named as such rather than left to look derived:**

- **`firm` is available, passes every mechanical check, and is FALSE because a commission is what Merit owes a named affiliate.** Nothing in the tree computes it. `scope.ts` records the answer (`derived`) and never the refuted alternative, which is the point of the sentence. The derivable HALF is asserted beside it: `firm` is a class this registry really has, so the mistake is available rather than hypothetical.
- **ADR-106's exclusion is a ruling about what a ROW read returns while a count returns no row.** This is the reason `pair` cannot be fixed by any class. It is an ADR's reasoning; the tree carries its consequence, not its argument.
- **A NAMED DOOR returning one integer is the right construction for the count.** ADR-262 and ADR-265 built two; that they are the right precedent for a third is a judgement. That they EXIST is derived, by the ADR-existence case and by the `effectiveAccountCap` non-vacuity check.
- **The five other refusals' phrases.** Untouched by this row, and left textual because moving them is a different fence.

**Every derivation is guarded for non-vacuity in its own describe block**: the registry parser reads a known class and reads nothing for a name that is not registered, the schema parser finds the table body and a known column inside it and the empty string for a table that does not exist, the migration directory is read and holds more than fifty files, and `ScopedTx` is read as an interface body with `effectiveAccountCap` in it. **A parser that silently matched nothing would make half the cases pass by accident, which is this row's own defect one layer down.**

### Approval

The approval line is UNSIGNED and merging is not signing.** No `status` field anywhere moves and nothing is marked `accepted`. **`E2` READ OWED**, and three are inherited: [ADR-321](ADR-321.md), [ADR-322](ADR-322.md) and [ADR-323](ADR-323.md) are all `proposed` and UNSIGNED, and the first is the migration this entry is about.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO CHECK IS THE ONE NO GATE CAN: THAT THIS IS WHAT AN OPERATOR SHOULD BE TOLD WHEN THE ROUTE REFUSES.** Every case in this diff can tell you the message agrees with the registry, the schema and the migration directory. **None of them can tell you the message is USEFUL to the person holding the 503.** Read the message end to end as that person. It now leads with an obstruction that is DISCHARGED, and spends four sentences on it before reaching the one that is still refusing. That ordering is deliberate, because the discharged half is what a reader arriving from the old message will be looking for, and it is exactly the ordering a founder might overrule: the alternative is to lead with the counting door and put the history behind it.

  **THE SECOND IS WHETHER `firm` SHOULD STILL BE NAMED AT ALL.** The class question is settled and the registry records `derived`. This entry nonetheless keeps the sentence saying `firm` is available, passes every mechanical check, and is FALSE. **The argument for keeping it is that the mistake is still one line away for a session that wants a quick registration, and this refusal is the only place in the tree that says why it is wrong.** The argument against is that a settled question restated in a live refusal is one more sentence that can go stale, which is the defect this very row exists to repair. It is a judgement about how much history a refusal should carry and it is not mechanically decidable.

  **THE THIRD IS THE ONE I WOULD MOST WANT OVERRULED IF IT IS WRONG: WHAT `E2` MEANS FOR A ROW THAT MOVES NO MONEY.** Nothing here writes SQL, moves a cent or changes a route's behaviour; the endpoint answered 503 before and answers 503 now with the same class. **But the diff changes the sentence a human reads when Merit refuses to show an affiliate what it owes them**, and this row exists because the last version of that sentence was wrong for a wave and no control noticed. If refusal text is inside `E2`, this class of row needs the founder read every time and the queue is longer than it looks. If it is not, then the repair mechanism has to be entirely mechanical, and section 4's table is the whole of the control.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** **The derivations bind the message to the tree, and a message can agree with the tree and still be false about the WORLD.** The clearest case is the counting door: the derivation asks whether `ScopedTx` declares a member matching `/conversion/i`, so a door named `attributedSaleCount` would satisfy the tree and leave this refusal claiming the work is not done. **The name is a guess about a file nobody has written yet, and that is the weakest link in section 4's table.** The direction of the error is safe -- it fails to notice work that landed, rather than claiming work that did not -- and it is the same direction as the defect this row is repairing, which is why it is stated here rather than inside the table where it would read as measured.
