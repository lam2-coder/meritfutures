### 3. Why the status is 503 and why no code is invented

**API_CONTRACT section 2's table is CLOSED and this fence does not carry that document.** `gateIdentityStatus` in this same file already met that boundary and recorded the cost rather than smoothing it: *"a sixth spelling would be a ruling this session did not take; the `detail` carries the fact the code cannot."* `sendTurnstileRefusal` (`routes/auth.ts`) says the same in its own words: *"NO NEW CANONICAL CODE. Section 2's table is closed."*

**`service_unavailable` IS THE ROW OF THAT TABLE THIS ANSWER BELONGS TO.** Section 2 defines it as *"Dependency down (PSP, Rise), safe to retry"*. The nightly fold is a dependency of this answer; [ADR-241](ADR-241.md) ruled its schedule EXTERNAL and registered it in `CRON_INVENTORY`, so it is a dependency that lives outside this repository exactly as the two named vendors do. **The retry half of that row is what decides it**: once the day is folded, the same request is answerable.

**THE FOUR ALTERNATIVES ARE REFUSED, EACH FOR A DIFFERENT REASON.**

> **`payout_not_eligible` 422 is refused because its body would be a lie in a shape the client trusts.** Section 6 requires that code to carry the FULL gate breakdown, and there is no evaluation here, so every cell would read pass. That is [ADR-140](ADR-140.md)'s own finding one door up, where a refusal shaped as `payout_not_eligible` *"would carry a breakdown in which EVERY GATE PASSES"*, and it is why the identity term is a named refusal instead. **A trader is not ineligible because Merit has not run a batch.**
>
> **`conflict` 409 and `precondition_failed` 412 are refused because both say the CLIENT acted.** 409 is *"already claimed, already exists"* and 412 is *"Client acted on stale state"*. This caller did nothing; the state that is stale is Merit's.
>
> **`internal_error` 500 is what this arm exists to remove.** `rule-state-reader.ts` rules the distinction in terms: an absence and a malformed row *"are different operational days and the first one is not an error in the estate at all"*.

**NO `Retry-After`.** RFC 9110 permits one on a 503, and this deployment has no honest value for it: the schedule is [ADR-241](ADR-241.md)'s external fact. A number here would be this repository asserting an operator fact it does not hold, which is the shape [ADR-264](ADR-264.md) refused when it declined to claim a scheduled run had happened.

**THE `detail` IS GENERIC AND THE OPERATOR'S DISCRIMINATOR GOES TO THE LOG.** Section 2 requires that `detail` *"never leaks internals or other users' data"*, and `AuthBackendUnwired` (`routes/auth.ts`) already rules exactly this split for the two absences that share this status: *"Both are `503 service_unavailable` to a client and they are different facts to an operator, so the reason travels with the error ... THE REASON NEVER REACHES THE RESPONSE."* The account, the day and the table name are logged at **WARN** rather than at ERROR, on the reader's own sentence above; the body carries no account id, no trading day and no table name, and the suite asserts all three absences.

### 4. What the arm does NOT do

**IT DOES NOT SYNTHESISE A STATE, AND THAT IS THE WHOLE POINT OF THE ROW.** `stateNotFolded` takes a `RuleStateAbsent` and returns a problem document. It constructs no `RuleState`, calls no fold, and reads nothing. `rule-state-producibility.test.ts` link 7 asserts that this route contains no `RuleState` construction, so the property is a predicate rather than a promise.

**IT DOES NOT CATCH `RuleStateUnreadable`, AND THE OMISSION IS THE RULING.** A row whose columns disagree with the schema that wrote them is an internal error in the estate, and answering it with a retryable status would tell a trader to retry something no retry can fix and would tell an operator nothing is wrong. That case is asserted at `500` beside the two at `503`, so a later widening of the guard turns the suite red rather than quietly making every fault on this route look like a schedule.

**IT IS NOT FOLDED INTO `unwiredOrThrow`.** The idempotency store cannot raise a `RuleStateAbsent`, so a shared helper would claim a path that does not exist and would need a coverage escape to ship. The arm sits at the one call site the throw can reach.

**AND THE RETHROW IS UNCHANGED.** An `unwiredOrThrow` that stopped rethrowing would answer every internal fault on this route with a retryable 503, which is the opposite defect and a larger one.

### 5. The constraint the arm creates, which is ruling 4 and was not in the row

**A 503 AND A 404 ARE DISTINGUISHABLE, SO THE ORDER IN WHICH A BACKEND READS IS NOW LOAD BEARING.**

`PayoutTx.subject` returns `PayoutSubject | null`, and `null` is API_CONTRACT section 1's 404 for *"a resource the caller does not own"*, which exists so that this API does not confirm the existence of other people's resources. The reads on that transaction are SCOPED, so a foreign account's `rule_states` rows are not merely absent from the caller's view, they are indistinguishable from an account whose day has not been folded: an empty list is `RuleStateAbsent`.

**SO AN IMPLEMENTATION THAT READ THE STATE BEFORE IT RESOLVED THE ACCOUNT WOULD HAND A PROBER A 503 FOR EVERY ACCOUNT OF EVERY OTHER IDENTITY**, where the contract requires 404. Before this diff that failure was invisible, because both answers were the same 500.

**THE REMEDY IS A REQUIREMENT ON `subject()` AND IT IS WRITTEN WHERE AN IMPLEMENTER WILL MEET IT**, in that method's own docblock and in `PayoutSubject.state`'s: the ownership answer comes FIRST, and `RuleStateAbsent` may escape only for an account this handle can already see. **IT IS NOT ENFORCED HERE AND THAT IS STATED RATHER THAN HIDDEN**: nothing in this tree implements `PayoutTx`, so there is no call order to check, and a route cannot observe the order of reads inside a port it does not own. The requirement is registered in `usePayoutBackend`'s entry as well, so the row that finally implements the port meets it in the file that lists what the port waits on.

### 7. What was found under the arm, reported and not repaired

**AN UNSTAMPED REFUSAL LEAVES THE IDEMPOTENCY KEY CLAIMED FOREVER, SO A RETRY WITH THE SAME KEY IS A `409` AND NOT THE VERDICT THE FOLD HAS SINCE PRODUCED.**

This was found by writing the wrong assertion. The case originally read *"a retry after the fold gets a real answer"* and expected `200`; it measured `409`. `beginIdempotent` claims the key before the handler runs, a refusal is deliberately never stamped (`RefusalThrown`'s own comment says why), and `classify` calls a claimed row with a null response `in_flight`, which `problemForOutcome` answers `409 conflict`.

**THAT IS TRUE OF EVERY REFUSAL THIS ROUTE MAKES AND IS NOT CREATED HERE.** `identity_restricted`, `not_found`, `conflict` and `payout_not_eligible` all leave the same claimed row. **It matters more here than on any of them**, because this is the only refusal on this route that is MERIT'S rather than the caller's: the others are fixed by the caller changing something, which naturally comes with a new key, and this one is fixed by Merit running a batch, after which the caller's instinct is to resend exactly what they sent.

**SO THE `detail` NAMES THE HEADER AND THE CONTRACT IS NOT MOVED.** `apps/api/src/idempotency.ts` is outside this fence, the rule reaches every endpoint that claims a key, and a change there is a ruling about the whole idempotency layer rather than about a payout. The measurement is written into the suite as a passing case in both directions: the same key answers `409 conflict`, and a NEW key answers `200` with an approval. **The 409 is also what proves the 503 was not stamped**, because a stamped one would replay `503` verbatim there.

**AND ONE SENTENCE IN `payouts.ts` IS INCOMPLETE RATHER THAN FALSE.** The `RefusalThrown` catch says stamping *"would make a trader who fixed the cause and retried with the same key read their own old refusal back"*, which is true of stamping and says nothing about what NOT stamping does. The consequence is now written on `stateNotFolded`, which is where the reader who needs it is standing.

### 9. Where this entry is most likely wrong

**RULING 2 IS THE ONE TO ARGUE WITH.** `service_unavailable` is now the answer for THREE different things on this route: a deployment with no backend installed, a backend that cannot express a method, and a fold that has not run. A client cannot tell them apart from the code, and only the third carries a `detail`. **The defence is that API_CONTRACT section 2's table is closed, that a route may not amend a frozen contract, and that the operator's discriminator belongs in the log on `AuthBackendUnwired`'s own ruling. The counter is that "closed" is a property of a document an ADR can move, and that a `state_not_folded` code would be worth one line of section 2.** If a founder wants that code, this entry has the argument for it already assembled and the fence to write it is `API_CONTRACT.md` plus this route; nothing here would be reverted, only renamed.

**RULING 4 IS A REQUIREMENT WITH NO ENFORCEMENT, AND THAT IS THE WEAKEST THING IN THIS DIFF.** The ordering constraint on `subject()` is written in two docblocks and one entry, and a docblock cannot fail. Nothing implements `PayoutTx`, so there is nothing to check today; the row at `287` that finally writes one is where this becomes a live hazard, and it will meet the requirement in prose rather than in a gate. **The honest position is that this diff makes an existing information-disclosure risk VISIBLE rather than introducing it**, because a state-first implementation was always going to be wrong, but it does move the two answers from identical to distinguishable.

**AND THE ARM IS EXERCISED ONLY THROUGH A FAKE.** No backend exists, so what is measured is that the route converts a thrown `RuleStateAbsent` into a 503. That the deployment's real reader raises the same class on the same day is `ADR-264`'s measurement and not this one's, and it is inherited rather than re-executed: no PostgreSQL was built in this session.
