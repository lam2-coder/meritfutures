## ADR-214: a reason's existence claim DOES reach schema objects, and because no runner can tell a column name from prose, the reason supplies the command that settles it  (2026-08-29, status: proposed)

**The artifact every build session reads to learn what is still owed spent a night telling them the opposite of the tree.** [`apps/api/test/wiring.test.ts`](../../apps/api/test/wiring.test.ts)'s `usePayoutBackend` entry read *"A `RuleState` NO MIGRATION IN THIS TREE CAN STORE"*, that *"`0015_rule_states.sql` declares NONE of the three"*, and that a recursive grep for lifetime_settled over the migrations directory returned nothing at all. [`0065:101`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql), [`:107`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql) and [`:118`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql) had landed all three columns, session **400** had landed the writer, and the entry's own cited grep returns **7** lines.

**No gate could see it, and that is this entry's real subject.** [`RI-14`](../../packages/tooling/checks/repo-invariants.mjs) is *"No reason claims a named thing does not exist while the tree exports it"* and it reads **EXPORTS**. A migration COLUMN is not an export. So the one class of claim this file makes most often about the database sat outside every check in the tree. **That is not a bug in `RI-14`; it is a boundary nobody had drawn.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `214`, session **404**, dispatched as `claude/blocked-map-is-not-checked`. **Every premise in the row was re-derived at its source and every one held.** **No migration number, no `SD-nn`, no `GS-nnn` was taken.**

- **NOT A MONEY PATH CHANGE.** No door, no port, no adapter, no scope class, no interface member, no migration. `usePayoutBackend` is **not** wired and section 4 says what still blocks it, re-derived on this tree rather than inherited.

- **Ships `proposed` with an UNSIGNED approval line.** Merging is not signing.

### 1. THE RULING

> **1. YES. A REASON'S EXISTENCE CLAIM REACHES SCHEMA OBJECTS.** A column, a constraint, an index or a view is a thing the tree either has or does not have, exactly as an export is, and a reason asserting its absence is making the same kind of claim `RI-14` was written for. **The boundary that let this through was accidental, not principled.**
>
> **2. AND NO RUNNER CAN TELL A COLUMN NAME FROM PROSE. THAT WAS MEASURED, NOT ASSUMED.** Section 2 runs four candidates over this tree. The discriminator everybody reaches for first -- absence phrasing plus a name the migrations declare -- moves **26** sites across 280 shipped `.ts` files, of which **ONE** is a real defect and **25** are honest sentences: `events` is absent from a REGISTRY, `name` from a RESPONSE, `route` is a file stem. **The word "absent" does not mean "not in the schema", and no rule over English recovers that.** A rule that turns honest sentences red is worse than one that misses a case.
>
> **3. SO THE BURDEN MOVES TO THE SENTENCE MAKING THE CLAIM. A REASON THAT WANTS TO ASSERT A SCHEMA FACT QUOTES THE COMMAND THAT SETTLES IT, AND THE RUNNER RUNS THE COMMAND.** [`RI-20`](../../packages/tooling/checks/repo-invariants.mjs) executes a backticked command beside a stated result and fails the reason when the result is not what it says. **This is not a name matcher and must never become one.** It moves **1** site on `origin/main` -- the defect -- and turns **0** honest sentences red, because a sentence not quoting a command is not making a claim this check reads. **The cost lands on the author who wants the strong claim rather than on every author who does not.**
>
> **4. NOTHING EXECUTES THROUGH A SHELL, AND ONLY `grep` EXECUTES AT ALL.** The command is tokenised by the check and run with `execFileSync`. A shell metacharacter, a glob character, an absolute path or a `..` segment makes the claim **UNSETTLEABLE**, which is a finding. A command that is not `grep` is a finding. **Both are findings rather than skips on purpose: a check a later author evades by writing `rg` is not a check.** Widening the vocabulary is a ruling, not an edit.
>
> **5. `RI-20` GETS NO REFUTED-CLAIM ESCAPE, AND [ADR-212](ADR-212.md) IS WHY.** `RI-14` lets a block quote a false sentence when it marks it as history, and that is right: **a false sentence deleted leaves nothing for the next reader to check.** It is right *because a name is inert*. A command is not. ADR-212 already ruled that a `file:line` pointer quoted as HISTORY must not wear the shape that says follow me; **a command quoted as history is written out of command grammar for the identical reason.** The repaired header block does exactly that, and `RI-20` caught the first draft of it, which did not.
>
> **6. `RI-15`'s DECLARATION READER GAINS THE TWO `ALTER TABLE` SHAPES, AND THAT IS THE SAME BLINDNESS ONE CHECK OVER.** Its five shapes had no `ADD COLUMN` and no `ADD CONSTRAINT`. A merged migration is never edited, only superseded (constitution `E2`), so **every column added to a table after its `CREATE` arrives that way**, and the whole of that half of the schema was UNCITABLE: a reason pointing at `0065:101` for `lifetime_settled_cents` was told the line declares nothing. **Measured at 0 sites moved and 1,088 schema objects made citable.**
>
> **7. THE MAP IS REPAIRED AGAINST THE TREE, AND WHAT COULD NOT BE REPAIRED IS REGISTERED RATHER THAN REACHED FOR.** Three reasons were false and are rewritten with the retired sentence quoted; six citations were drifted and are repointed. Two false sentences live in handler files outside this fence and are named in section 5.

### 3. `RI-20` WAS WATCHED FAILING, INCLUDING ON THE REAL TREE

**The most valuable run happened before a line of the map was repaired.** `RI-20` was written, added to `CHECKS`, and executed against the unmodified working tree:

```
FAIL   RI-20  A reason that quotes a command and states its result is run, and the result is what it says  (1)
       apps/api/test/wiring.test.ts:219: the reason says `grep -rn lifetime_settled

```

**Then it caught the repair's own first draft.** The header block rewritten above the entry quoted the false sentence verbatim, in live backtick-plus-result grammar, and `RI-20` failed it. **That is clause 5 being discovered rather than assumed**, and the sentence now reads *"a recursive grep for lifetime_settled over the migrations directory returned nothing at all"* -- the same claim, out of the shape that says run me.

**Nine seeded cases in [`repo-invariants.test.ts`](../../packages/tooling/test/repo-invariants.test.ts) hold it**, each restored by the suite's own temp-tree discipline: a false null claim, a false COUNT, a non-`grep` command, a shell-metacharacter payload (which also asserts no file was created, so the injection direction is tested rather than described), a path that has moved, the rename guard, the asserting-nothing throw, **the ACCEPTANCE direction** -- a probe that only ever attempts forbidden things passes against a guard that rejects everything -- and **the stated limit**, that the check reads the COUNT of matching lines and never their content, so a sentence naming the wrong pattern passes. That last case exists because a `covers` line claiming a limit nobody exercised is a claim nobody checked.

### 4. WHAT STILL BLOCKS `usePayoutBackend`, RE-DERIVED ON THIS TREE RATHER THAN INHERITED

**The dispatch's instruction was to say precisely what remains rather than inherit a sentence, because inheriting sentences is the defect this session exists to fix.** Every line below was opened at its source in this session.

1. **THE STATE HALF IS SPENT.** `RuleState` requires `lifetimeSettledCents`, `breached` and `breachKind` ([`types.ts:1004`, `:1009`, `:1010`](../../packages/rules-engine/src/types.ts)). [`0065:101`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql) declares `lifetime_settled_cents`, [`:107`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql) `breached`, [`:118`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql) `breach_kind`, and [`:126`](../../packages/db/migrations/0065_rule_state_lifetime_and_breach.sql)'s `rule_states_breach_kind_is_a_breach_kind` enumerates every member of `BreachKind` ([`types.ts:789`](../../packages/rules-engine/src/types.ts)) in its `IN` list. Session 400 landed the writer, so `RULE_STATE_WRITE_COLUMNS` ([`state-writer.ts:232`](../../apps/worker/src/batch/state-writer.ts)) carries them. **The grep the entry quoted returns 7 lines and `RI-20` now runs it on every CI-01.**

   **AND THE PER-FILE CLAIM WAS A GRAIN ERROR WORTH NAMING SEPARATELY.** *"`0015_rule_states.sql` declares NONE of the three"* was true when written and is **still true today**. It was the wrong question. A merged migration is never edited, only superseded (constitution `E2`), so **what a TABLE can store is never a fact about one file.** An entry asking a per-file question about a per-table fact is stale the moment the next `ALTER TABLE` lands, by construction -- which is also why clause 6 above had to teach `RI-15` to read `ADD COLUMN` before this entry could even cite its own evidence.

2. **A `firm` READ INSIDE A PORT THAT RUNS EVERY METHOD ON ONE TRANSACTION.** `PayoutTx.subject` returns `PayoutSubject` ([`payouts.ts:329`](../../apps/api/src/routes/payouts.ts)) whose `plan` ([`:332`](../../apps/api/src/routes/payouts.ts)) is a `ResolvedPlan`. `planVersions` ([`scope.ts:702`](../../packages/db/src/scope.ts)) and `planVersionSizes` ([`scope.ts:707`](../../packages/db/src/scope.ts)) are both scope class `firm`, and `ScopedTableKey` is `Exclude<TableKey, FirmTableKey | PairTableKey>` ([`scope.ts:1423`](../../packages/db/src/scope.ts)), so no `ScopedTx` read reaches either. **[ADR-211](ADR-211.md) clause 2 ruled the remedy and nothing has applied it**: two transactions, scoped first, the catalogue read a SECOND PORT beside `PayoutTx` rather than a member of it. That is a change to `routes/payouts.ts`.

3. **[ADR-213](ADR-213.md)'s `0066` SPENT THE MUTABILITY HALF OF ADR-211 CLAUSE 3 AND ONLY THAT HALF.** [`0066:212`](../../packages/db/migrations/0066_published_size_grid_immutable.sql) creates `plan_version_sizes_published_immutable` beside [`0027:260`](../../packages/db/migrations/0027_triggers_invariants.sql)'s `plan_versions_published_immutable`, so both halves of a `ResolvedPlan` are pinned and the crossing ADR-211 clause 2 designed **is safe**. It is still **not built**. Clause 3 refused the port because nothing pinned the numbers; that reason is gone and clause 2's unapplied remedy is what stands in its place.

4. **NOTHING IN THIS TREE IMPLEMENTS `PayoutTx`.** Derived at reporting time: no `implements PayoutTx`, no factory returning one.

5. **AND A FALSE CLAIM SITS INSIDE THE PORT ITSELF, UNREPAIRED.** [`routes/payouts.ts:438-439`](../../apps/api/src/routes/payouts.ts) states *"no member of this interface that a scoped door cannot serve"* while `subject()` returns a `ResolvedPlan` no scoped door reaches. **Session 401 registered it, ADR-213 section 8 registered it again, and this entry registers it a third time.** It is a handler file outside three consecutive fences.

**So the honest statement is: one of four grounds is cleared, the port stays at 503, and no port was wired by this session.**

### 6. WHAT THIS ENTRY DOES NOT RULE, so the gap is a decision rather than an oversight

1. **It does not widen `RI-20` past `grep`.** Section 2 measured nothing that needed `rg`, `psql`, `node` or `git`. **A `psql` claim is the interesting one and it is deliberately not taken**: half the map's strongest evidence is executed against a live PostgreSQL, and a check that ran one would need a database in CI-01, which is CI-03's stage and not this one.
2. **It does not reach `docs/`.** Section 2 states the exemption that would need and whose check it belongs to.
3. **It does not rule that a reason MUST quote a command to claim a schema fact.** `RI-20` checks the claims that are made; it does not require them. **A reason can still assert a schema absence in bare prose and no gate will read it** -- that is the residual hole, it is stated rather than hidden, and section 2 measured why closing it costs 25 honest sentences.
4. **It does not touch `RI-14`.** Its narrowness was measured to be right, twice.

### 9. Approval

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS CLAUSE 3, BECAUSE IT PUTS A COST ON HONESTY AND A DISCOUNT ON SILENCE.** `RI-20` reads only reasons that quote a command. **A reason that says "no migration declares this" in bare prose is unchecked, and a reason that proves the same thing with a grep is checked forever.** Section 6 item 3 states that hole plainly. The alternative is C3 -- read the prose -- and section 2 measured what that costs: **25 honest sentences turned red to catch one defect**, in a repository whose house style is to explain absences at length. **This entry took the narrow rule on that measurement, and a founder who would rather have the false positives and the arguments they start should say so**, because the seeds and the shapes for C3 are in this entry and rebuilding them is an hour, not a session.

  **THE SECOND IS WHETHER A CHECK SHOULD EXECUTE ANYTHING AT ALL.** `RI-20` runs a subprocess out of text in a comment. Clause 4 constrains it to `grep`, with no shell, no glob, no absolute path and no `..`, and the injection direction is a seeded case that asserts no file appeared. **It is still a category this repository's checks had never entered**, and the honest statement of the risk is that the constraint list is a denylist of characters rather than a proof. **A founder who wants that boundary held differently has two options and both are worse in a way worth knowing**: dropping execution leaves the defect exactly where it was, and moving the check to CI-03 beside the database work buys a stronger sandbox at the cost of not running on the stage that reads this file.

  **THE THIRD IS THE EXACT COUNT IN THE REPAIRED ENTRY.** The map now says the grep *"returns 7 lines"*, and `RI-20` checks the number. **A later migration that mentions `lifetime_settled` for any reason turns that entry red**, in a session that has nothing to do with `usePayoutBackend`. That is deliberate -- the sentence's claim about the tree really did change, and the failure names the real number -- but it is a cost paid by whoever is unlucky. **The alternative is a `returns nothing` / `returns at least one` pair, which never goes stale and never says how much.** This entry chose the precise claim because the vague one is how the original sentence survived; a founder who thinks a build session should never be stopped by an unrelated file's grep count should say so now, while it is one number and not a convention.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left to be found.** **Clause 5 refuses `RI-20` a refuted-claim escape, and that asks every future author to notice a rule that is not written where they are working.** Somebody repairing this map in six months will quote the false sentence the natural way, see a red check, and have to find clause 5 to learn why. **The alternative -- an escape marker like `RI-14`'s -- is the thing that makes the check worthless**, because the marker sits in the same block as the live claim and would exempt both; that is not a hypothetical, it is what the first draft of the repaired entry did. **The bet is that a loud failure with a pointer beats a quiet exemption**, and it is a bet about people rather than about code, which is the kind this entry is least qualified to make.
