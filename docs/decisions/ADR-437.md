### 4. What a narrowed write RETURN would be claiming, and whether the schema is evidence for it

**FIRST, THE STRUCTURAL HALF, AND IT IS BETTER THAN [ADR-426](ADR-426.md) SECTION 12 ITEM 3's SENTENCE SUGGESTS.** That entry says *"a write returns what the database made of what was sent, which is not the same claim as a read"*. Read as a claim about SHAPE, that is wrong and this row checked it rather than inheriting it: [`scoped-db.ts:4110`](../../packages/db/src/scoped-db.ts) is `unscopedInsertStatement(source, key, values).returning()`, and [`:539`](../../packages/db/src/scoped-db.ts) builds that statement with no projection and no alias, so `RETURNING` with no argument yields the table's own select model. **`DeclaredRow<K>` describes an inserted row exactly as well as it describes a selected one, and `schema.ts` is exactly as much evidence for the one as for the other.**

**SO THE SENTENCE IS RIGHT ABOUT SOMETHING ELSE, AND SAYING WHICH IS THE POINT OF THIS SECTION.** A narrowed return type would claim *"each element has the columns `schema.ts` transcribes for K, at the types it transcribes"*. It would NOT claim the thing a caller actually wants from a write's return, which is a RELATION between what was sent and what came back. Defaults fired, a generated column computed, a trigger rewrote a value, a `CHECK` was satisfied: none of that is in the shape, and all of it is what makes an inserted row interesting. **A type over a write's return is a true statement about the least interesting property of that value.**

**AND ON THIS FAMILY IT IS A TRUE STATEMENT NOBODY READS.** [`evaluate.ts:841`](../../apps/worker/src/breaker/evaluate.ts) is `await tx.insert('planBreakerState', toBreakerStateRow(decision));`. **The value is discarded.** [ADR-421](ADR-421.md) section 9 reason 2 says *"zero errors is zero readers"* and [ADR-430](ADR-430.md) section 4 observed it from the inside, where a mapping taking `unknown` absorbed the narrowing. **Here it is stronger and simpler: there is no mapping on the return because there is no value taken.** Case `10.2` asserts it rather than leaving it to be re-derived.

### 7. The refusal, and its four reasons in the order they carry weight

**THE WRITE PATH IS NOT NARROWED BY THIS ROW, ON EITHER QUESTION.**

1. **NO RULING AUTHORISES IT, AND THAT WAS CHECKED AT SOURCE RATHER THAN INFERRED.** [ADR-303](ADR-303.md) limit 4 names four verbs and every one of them is a READ: [`scoped-db.ts:3461`](../../packages/db/src/scoped-db.ts) writes them out as *"`rows`, `rowsWhere`, `rowAt`, `lockAt` and every `FirmTx` and `SystemTx` read still return `unknown`"*, and [`limit-4-census.test.ts:63`](../../packages/db/test/limit-4-census.test.ts) is the same four as a literal. **`insert` is not limit 4's and no other ruling in this tree names the write path.** [ADR-430](ADR-430.md) section 12 item 4 and [ADR-426](ADR-426.md) section 12 item 3 both call it a different question and neither answers it. **There is nothing here to spend.**
2. **THE ADMISSION RULE CANNOT BE SATISFIED, AND IT IS THE RULE ALL THREE PRECEDENTS HONOURED.** [ADR-421](ADR-421.md) section 9 states it: a row that *"can therefore show a hand-written mapping DELETED in the same commit"*. On the return there is nothing to delete, section 6.1. On the values there is exactly one mapping, [`evaluate.ts:504`](../../apps/worker/src/breaker/evaluate.ts)'s `toBreakerStateRow`, **and it is the kind of mapping [ADR-303](ADR-303.md) limit 2 rules is KEPT**: [`scoped-db.ts:3449`](../../packages/db/src/scoped-db.ts) reads *"IT IS NOT A DECODER. It SHRINKS one. A driver-side caller still writes a field mapping onto the engine's own row type, once per caller, which is an accepted `FM-16`."* Narrowing the values parameter would TYPE that mapping, not delete it. **A row that reported it as a deletion would be reporting a rename.**
3. **THE RETURN BUYS NOTHING AND THE MEASUREMENT IS NOT AMBIGUOUS**, section 6.1. Zero errors in any `src/` file in any package, because the one call site discards the value.
4. **AND THE VALUES NARROWING WOULD REST ON THE ONE TRANSCRIBED FACT NOTHING COMPARES**, section 5. Type and nullability are compared over the whole registered population; DEFAULT is not compared anywhere, and DEFAULT is the fact a write type uniquely depends on. **A read type never says a column may be absent and a write type says it about every defaulted column.**

**WHAT WOULD MAKE IT TAKEABLE, STATED SO THE NEXT ROW DOES NOT RE-DERIVE IT.** A ruling that names the write path, on the model of [ADR-303](ADR-303.md) limit 4 naming four read verbs; a family whose consumer READS what `insert` returns, so the admission rule has a mapping to delete; and, before any values narrowing anywhere, **a check that compares a `schema.ts` default against the DDL**, which is the one leg of the transcription this estate has never taken. **The third is worth more than the other two and is not this row's to build.**

### 8. The money finding, taken because this is the money path's neighbourhood

**THE MONEY RULE DOES NOT STOP THE NARROWING AND IT IS THE REASON EVERY RUNTIME REFUSAL STAYS REGARDLESS.** The dispatch's rule is that a narrowing letting a non-integer reach a `*_cents` column outranks the narrowing. **It was tested rather than assumed, and it does not fire.**

**EVERY `*_cents` COLUMN IN THIS SCHEMA IS `bigint` WITH `mode: 'bigint'`, DERIVED BY WALKING THE DECLARATIONS.** A TypeScript `bigint` cannot hold `1.5`, so a values type derived from `schema.ts` refuses a float on a money column at compile time. The one apparent exception is `payoutCapScheduleCents` at [`schema.ts:452`](../../packages/db/src/schema.ts), which is `jsonb` on BOTH sides and is [ADR-303](ADR-303.md) limit 3's known blob rather than a scalar money column.

**AND THE COMPARISON THIS TREE DOES NOT MAKE WAS MADE ONCE BY HAND, FOR THE MONEY POPULATION ONLY.** Every `*_cents` column name in `schema.ts` was matched against its declaration in the migration set and **every one agrees: `bigint` on the transcription and `bigint` in the DDL.** That agreement is one reading taken on one afternoon by one row. It is not a check, and section 5's table is where the checks are.

**WHAT DOES FIRE IS THE DEFAULT, AND IT IS THE REASON THIS SECTION EXISTS.** `$inferInsert` marks a column OPTIONAL wherever `schema.ts` records a default or an identity. **337 columns in this schema carry one, and 12 of them are `*_cents` columns.** Each of those twelve would be omittable from a narrowed write on the strength of a `DEFAULT` nobody compares against the DDL, and the value the database then chooses for that money column is chosen by a clause the type asserts exists. **A narrowing sold as making money safer would be resting, on twelve money columns, on the only fact in the transcription that has never been checked.**

**NONE OF THE TWELVE IS ON THIS FAMILY'S WRITABLE TABLE, AND THAT IS ASSERTED RATHER THAN NOTED.** `plan_breaker_state.numerator_cents` and `.denominator_cents` are `bigint` with `mode: 'bigint'`, `NOT NULL`, and carry no default, on the transcription AND in [`0016`](../../packages/db/migrations/0016_treasury_controls.sql). **Case `10.3` is that comparison, run on every suite run.** So if a later row does take the values narrowing on this family, the two money columns are REQUIRED rather than omittable, and the day somebody adds a `DEFAULT` to either one the case goes red and the write-path question has to be asked again.

**NOT ONE `throw` WAS DELETED AND NOT ONE REFUSAL WAS RETIRED**, because nothing in this row's diff touches `evaluate.ts` at all. `throw new BreakerRowError(` occurs **10** times in that file on the base tree and **10** times on this branch; `throw ` occurs **11** and **11**.
