### 3. What the seed module actually is, read in full

**THE DISPATCH ASKED WHETHER THERE IS A LOADER AT ALL OR ONLY DATA PLUS A SHAPE TEST. IT IS THE SECOND, AND THE FILES SAY SO ABOUT THEMSELVES BEFORE ANY CHECK DOES.**

`generate.mjs`'s own header, quoted verbatim:

> `WHAT THIS FILE IS NOT: it is not the loader. It opens no database connection, imports no client, writes no row, and imports pg nowhere. The same division calendars/generate.mjs states about itself, one seed over.`

The detector README says the same in its own words: *"The loader is **not** here."*

**AND UNTIL THIS ROW, NOTHING CHECKED EITHER SENTENCE.** The division was a convention held by whoever remembered it, which is the exact shape this corpus keeps paying for.

**DERIVED RATHER THAN READ OFF THE PROSE.** Every `import` in every module under `packages/db/src/seed` resolves to a `node:` builtin, and there are only two such modules, one per seed:

| Module | Specifiers it imports |
|---|---|
| `packages/db/src/seed/detectors/generate.mjs` | `node:crypto`, `node:fs`, `node:path` |
| `packages/db/src/seed/calendars/generate.mjs` | `node:crypto`, `node:fs`, `node:path` |

The generator's exported surface is a parser, a citation checker, a builder and a serialiser. Its `main` takes `--out` and `--check` and writes a JSON file. **There is no function in it that could be handed a connection.**

**WHAT CALLS IT.** Nothing under any `src/` reads the generated artifact. Two files under `apps/worker/src/detectors` name `m07-detectors-v1.rows.json`, `fills.ts` and `canary.ts`, and **both mentions are comments**: a search for a read or an import of that path across every `src/` directory in the workspace returns nothing. Every executing reader is a test. **[ADR-409](ADR-409.md)'s blocker 2 reproduces exactly.**

**SO THE ANSWER TO "WHAT WOULD HAVE TO BE TRUE FOR A DEPLOYMENT TO RUN IT" IS THAT A DEPLOYMENT COULD NOT RUN IT AT ALL**, because the artifact is data and the module beside it cannot write a row. That is not a gap in `P7-d`. `P7-d`'s row in [P7](../plans/P7-risk-and-abuse.md) section 8 names its deliverables as `packages/db/src/seed/detectors/**`, the test, `STATE` and `sessions/`, and **names no loader**. The slice delivered what it was given.

| Clause | Checked how | Result |
|---|---|---|

The detector registry is the second kind. **Hand-writing eighteen rows into a migration would also throw away the one property the seed was built for**: every value carries the `M07` line it was read from, and a migration cannot re-derive a citation on the day `M07` moves.

**THE CONVENTION THEREFORE POINTS AT A DIRECTORY THIS ROW OWNS**, which is the fact that made the rest of this document necessary rather than optional.

### 5. The schema is not what stands in the way, and this is the expensive wrong turn foreclosed

**A ROW THAT READ "the table is empty" AND REACHED FOR A MIGRATION NUMBER WOULD BE TAKING ONE FOR NOTHING**, and a migration is the one artifact this corpus can never edit back. Both halves were derived from the merged SQL.

| Question | Source | Answer |
|---|---|---|
| Does the table exist | `0008_risk.sql` creates `detector_definitions` with `(detector, version)` as its primary key, `parameters jsonb NOT NULL`, `description`, `effective_from`, `effective_to`, `is_sensitive boolean NOT NULL DEFAULT true` | **YES, since `0008`** |
| Does it carry every column a generated row holds | The first suite in `packages/db/test/seed-detectors.test.ts` asserts exactly that, and it is green | **YES** |

**NOTHING IN THIS SECTION IS AN ARGUMENT FOR WRITING THE LOADER.** It removes one candidate blocker and leaves section 6's.

### 6. What actually stops it, and it is not scoped to this seed

**THERE IS NO DEPLOYMENT.** Derived from the workflows rather than asserted: `.github/workflows/` holds `ci.yml`, `corpus.yml`, `golden.yml` and `nightly.yml`, and **not one of them deploys anything**. The only place any migration is ever applied is `corpus.yml`'s `migrations` job, gate `CI-06h`, which stands up a `postgres:16` **service container** on the runner, applies `packages/db/migrations/*.sql` forward-only from empty under `ON_ERROR_STOP`, asserts the object counts, and is torn down with the job.

**SO `detector_definitions` IS NOT EMPTY IN A DEPLOYMENT. IT IS EMPTY BECAUSE THERE IS NO DEPLOYMENT FOR IT TO BE EMPTY IN**, and every other table in this estate is in the same condition. The corpus says so about itself in many places and in its own words: *"no deployment has ever served this field"*, *"No deployment of Merit can post a ledger entry today"*.

**THIS IS WHY THE LOADER WAS NOT WRITTEN, AND THE REASON IS NOT THE FENCE.** The fence permits it. The convention puts it inside the fence. The schema is ready for it. **What is missing is a caller, and behind the caller an environment.**

| What a loader would need | Where it lives | Verdict |
|---|---|---|
| A module under `packages/db/src/seed/` | **INSIDE this row's fence** | buildable |
| An import of `firmDb` and `transaction` | `packages/db/src/scoped-db.ts`, reachable by relative path from inside the package | **needs no barrel edit**, so this row's hard limit on `packages/db/src/index.ts` is not what refuses it |
| A call site | **OUTSIDE this fence**, and there is no candidate: no deployable start path, no workflow step, no script | **A FINDING** |
| An environment for that call site to run in | nowhere in this repository | **A FINDING** |

**THE DISPATCH RULED THIS CASE IN ADVANCE**: a call site outside `packages/db/src/seed/**` is a finding with its measurement rather than an edit to take. It is a finding, and section 6's second row is why the finding is stronger than the dispatch anticipated. **A loader written here would be a module with no caller, in a repository with no environment, for a slice no plan allocates.** [ADR-409](ADR-409.md) refused an adjacent build one row earlier on the sentence this row adopts: *an install nothing can exercise is an install nothing falsifies.*

**AND THE SLICE GENUINELY DOES NOT EXIST.** `P7`'s slice table allocates `P7-a` through `P7-m` and **none of them is a detector loader**. The only loader slice in the corpus is `S-E4`, it is the calendar's, it is scoped **money path, fresh session** with six proofs and a committed probe file beside it, and it is still unwritten because the calendar transcription it depends on is blocked on the founder. **The blocker `S-E4` itself waited on is gone**: `OI-06 (calendar prior image)` was ruled and closed on 2026-08-16 by [ADR-045](ADR-045.md). So a loader is not blocked by an open ruling. It is unscheduled.

**Eleven of eighteen, and the same eleven [ADR-409](ADR-409.md) section 5 names.** The figure is additionally pinned inside the seed's own test against the generator's own `counts` block, so it is derived twice by two mechanisms.

**THE SECOND WAS DERIVED BY EXECUTION.** The detector census composes the three module lists and runs every detector through the real `runDetectors` against the real seed rows. `apps/worker/src/detectors` exports three lists holding **3**, **4** and **7** detectors, which is **fourteen**, and the census asserts that the number which run is `IMPLEMENTED.length - 1`. Run on this tree: `pnpm vitest run apps/worker/test/detector-census.test.ts` reports **17 passed**. **Thirteen of fourteen decline against a fully loaded registry, and `D-02` is the one that runs.**

**SO THE ENTRY SAYS WHICH, AS THE DISPATCH ASKED.** **LOADING THE REGISTRY IS NECESSARY AND IT IS NOT SUFFICIENT.** With the table loaded and nothing else changed, a scheduled run would find one detector that works and thirteen that report a parameter they do not have. **AND THE ORDER MATTERS MORE THAN EITHER FIGURE.** [ADR-409](ADR-409.md) established that the thirteen do not decline for one reason: two carry no such parameter at all, which is a seed repair; two decline on an unmet input; and `D-14` was handed its number in a controlled mutation and declined anyway because it also needs a severity band, which is a money decision. **This row re-derived the figures and did not re-derive that partition**, which is section 5 of that document and stands.

### 12. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.** The `proposed` and unsigned backlog stands and this row settles none of it. [ADR-409](ADR-409.md), whose findings this row re-derived and extends, is itself `proposed` and unsigned on this row's own base.

  **What a founder read adds and this entry cannot.**

  **THE DECISION THIS ROW IS ASKING FOR IS WHETHER A SEED LOADER IS WORTH BUILDING AT ALL YET, AND IT IS ONE DECISION COVERING TWO SEEDS.** [ADR-409](ADR-409.md) put the same question and called it the cheapest of the three things on its page. This row measured the price and disagrees about the shape rather than the cost. **A loader is cheap. A caller is not, because there is nothing to call it from**: no workflow in this repository deploys, and the only database any migration has ever touched is a service container that is destroyed when the job ends. **So the question is not "write the loader"; it is "does Merit want a deployment path", and the loader is the first thing that would need one.** A founder asked only about the loader would be pricing the smaller half.

  **THE SECOND THING TO DECIDE IS WHETHER THAT LOADER IS ONE MODULE OR TWO.** The convention puts both at `packages/db/src/seed/`, both seeds are in the same condition, and `S-E4` is already specified with six proofs and a probe file. **A detector loader written without reference to `S-E4` would be the second half of a slice nobody merged the first half of.** This row would give one session both, on `S-E4`'s scope, rather than a detector-shaped module that the calendar then needs again.

  **AND THE THIRD IS THE ONE THAT COSTS MONEY IF IT IS GOT WRONG.** Loading the registry does not turn detection on. Thirteen of the fourteen detectors that exist decline against a fully loaded table, and clearing them needs `OQ-M7-02` answered per detector, plus a severity band per condition, and severity decides who gets held. **A plan that treats "seed the registry" as the item between Merit and working abuse detection is off by two decisions of different kinds**, and only one of them is a number.

  **WHAT THIS ROW WOULD SAY IF IT COULD KEEP ONE SENTENCE.** The seed is finished, it is cited line by line to `M07`, and it has been correct and unused since 2026-08-27. **Nothing is wrong with it.** What is missing is everything downstream of it, and the smallest honest description of that is that this repository has never written a row to a database that outlived a CI job.
