## ADR-349: the detector runner gets four of its five ports and the fifth is shown to be unreachable rather than unwritten, the dispatched claim that an adapter was the only blocker is re-derived and found to be one of three, and the job stays unscheduled with all three named (2026-09-05, status: proposed)

**THE DISPATCH SAID THE DETECTORS ARE BUILT, TESTED AND NEVER RUN, BLOCKED ONLY ON AN ADAPTER.** The first three quarters of that reproduce exactly. **THE WORD "ONLY" DOES NOT, AND THAT IS THIS ROW.**

`DetectorRunnerIo` has **five** members. `apps/worker/src/detectors/adapter.ts` serves **four** of them over [ADR-165](ADR-165.md)'s one door. Two further blockers sit behind that one: `detector_definitions` has no producer, and eleven of the eighteen seeded registry rows state no number.

### 2. THE HEADLINE FINDING: the adapter was never the only blocker, and there are three

`DetectorRunnerIo` declares `transact`, `terms`, `events`, `now` and `nonce`. Four are served by this row. **Here is what stands between the fifth and a run, and what stands behind it.**

**BLOCKER 1: THE EVENT SINK, AND IT IS THREE REFUSALS RATHER THAN ONE.**

1. **NO SINK IS REACHABLE.** `TRANSACTION_EVENT_WRITER` in `apps/api/src/events.ts` is the workspace's only composed event writer. `RI-04` forbids the import, `node-linker=isolated` makes an undeclared bare specifier resolve at neither run time nor build time, and `test/event-sink.test.ts` section 3 asserts that no relative specifier under `apps/worker/src` escapes this deployable. **This is not a file somebody forgot to write.**
2. **`detector.run_degraded` HAS NO REGISTRY ROW ANYWHERE.** `docs/architecture/EVENTS.md` section 8 does not carry it; [M07](../plans/M07-risk-abuse.md) section 5 carries it marked NEW. [ADR-159](ADR-159.md) clause 1 makes the registry the authority for a name, so `buildEvent` would refuse it at the NAME. Amending a frozen document is an ADR and is not inside this fence.
3. **`detector.run_completed` IS ACCEPTED BY NAME AND WOULD BE REFUSED AT THE SUBJECT.** [ADR-205](ADR-205.md) clause 1 added `detector_run_id` to that row and the producer's `subjectField` reads it; `runner.ts`'s payload does not carry it. `test/event-sink.test.ts` section 4b pins that absence as a live clearing condition, and this row does not clear it, because the payload is `runner.ts`'s and clearing it is that pin's own row.

**AND THE REFUSAL IS NOT QUIET, WHICH IS WHY IT IS THE DEFAULT.** `runOne` inserts the run row, inserts the flags, inserts the groups and then calls `emitRunEvents`, all inside one `io.transact`, and `emitRunEvents` is called on every run rather than only on a degraded one. A rejecting `emit` therefore rolls the whole thing back. `runOne` catches it, and the outcome comes back `recorded: false` with the detector in `DetectorRunReport.unrecorded`. **A deployment holding `postgresDetectorRunnerIo(LIVE_DB)` writes zero `detector_runs` rows.** `test/detector-adapter.test.ts` section 2 asserts exactly that, and it is the case this row was dispatched to write.

**BLOCKER 2: `detector_definitions` HAS NO PRODUCER.** `readDefinition` refuses a detector with no current registry row, on `INV-M7-04`, and points at `packages/db/src/seed/detectors/` as what fills the table. That directory holds a README, a generator, a source JSON and a rows JSON. **Nothing under any `src/` reads any of them.** Derived by walking `apps/` and `packages/` for the seed's filename with comments stripped: **zero non-test readers**. So a fully wired runner against a real database raises `DetectorUnregistered` for every detector and records eighteen `failed` runs.

**BLOCKER 3: ELEVEN OF THE EIGHTEEN SEEDED ROWS STATE NO NUMBER.** Derived from the rows file with the generator's own `hasAStatedNumber` predicate transcribed, and cross-checked against the file's declared `counts`: **18 rows, 7 with at least one stated number, 11 with none, 18 sensitive.** `OQ-M7-02` is the founder's and unanswered. A detector reading `{state: 'unstated', value: null}` raises `DetectorDeclined`, which the runner records as `failed`.

**SO THE ROW STAYS `unscheduled` AND NOW NAMES ALL THREE.** This is the breaker's row's shape one entry down the same array: *"Two blockers, and the second is not an adapter."* Here there are three and only the first is.

### 3. Ruling 1: what a detection writes, and whether anything reads it

**WHAT IT WRITES IS UNCHANGED BY THIS ROW AND IS RESTATED SO THE NEXT QUESTION IS ASKABLE.** One `risk_flags` row per real finding, at `open`, at `internal`, carrying `identity_id`, an optional `account_id`, a `flag_type`, a `severity`, an `evidence` object that may not be empty (`INV-M7-03`), `first_detected_on`, and `detector_run_id` pointing at the run that caused it. `DetectorFinding` has **no `status` field and must never have one** (`INV-M7-02`), so `enforced` is not a value a detector avoids, it is a word with nowhere to go.

**NOTHING READS IT, AND THIS ROW DOES NOT CHANGE THAT.** `GET /admin/flags` reaches `AdminReadSource.listFlags`, which `apps/api/src/admin-source/flags.ts` implements in full, including `AS-M7-03` clause 3's corroboration ordering. **That implementation is composed by `composeImplementedAdminReads`, and no module under any `src/` calls it.** Derived by walking `apps/api/src` with comments stripped: **one occurrence, which is the declaration itself.** So the queue's data source exists, is written, is tested, and is wired to nothing, exactly as the runner was.

**THIS ROW DOES NOT CHANGE WHAT `GET /admin/flags` COULD SERVE, AND SAYING SO PLAINLY IS THE RULING.** The route's blocker is one deployable over and is a composition line, not an adapter. What this row changes is the other end: before it, a flag could not be written by anything; after it, a flag still cannot be written, because the sink refuses inside the transaction that would have written it. **A raised flag currently has no reader AND no writer, and the two absences are independent.** Wiring either one alone leaves the pair useless, and that is the sentence a founder should read before deciding whether either is worth a row.

### 4. Ruling 2: the adapter is written and the job is NOT scheduled

**WRITING AN ADAPTER MAKES A JOB RUNNABLE; A CLOCK MAKES IT RUN.** [ADR-165](ADR-165.md) clause 5's rule that the row which writes a door is not the row which wires a job is taken here in its strongest form, because in this case the two are separated by more than convention.

**IT IS NOT SCHEDULED, AND THE FIRST REASON IS THAT IT WOULD DO NOTHING.** Section 2's blocker 1 means every run is `unrecorded`. A clock in front of that is a process that starts, reads, computes, throws its whole answer away and exits, and `CRON_INVENTORY`'s dead-man switch for this row alarms on a run's ABSENCE, so the estate would be paged nightly by a job that was running. **THAT IS STRICTLY WORSE THAN THE JOB NOT EXISTING**, because it is a page whose cause is invisible from the page.

**THE SECOND REASON IS THE ONE THAT WOULD STILL HOLD IF THE FIRST LIFTED.** A detector run that fires against production data has consequences for real traders. `M07` section 3.3 makes severity contextual and a money decision every time it is written; 4 and 5 is the band `G-HOLD-REQUIRED` reads to hold a payout for 48 hours under [ADR-040](ADR-040.md). **A first run against the real estate should be a decision somebody takes with a date on it, not a consequence of an adapter landing.**

**WHAT WOULD HAVE TO BE TRUE BEFORE A CLOCK IS ARGUABLE**, listed so the next row does not have to re-derive it: a reachable event sink or a ruled change to when the runner emits; a `detector_definitions` producer; `OQ-M7-02` answered and the numbers seeded; and a reader for what is raised. **That is four things and this row does one of them.**

### 5. Ruling 3: no threshold is invented, and the boundary is where a false positive would enter

**NOT ONE NUMBER IN THIS DIFF IS A THRESHOLD.** The adapter reads no `detector_definitions` row on its own account, holds no constant a detector compares against, and has no argument a caller could pass a threshold in. Every number a detector runs on comes from the registry, which is `INV-M7-04`'s whole point: *"Why did this not fire in March" must be answerable from data, and it cannot be if parameters live only in code.*

**WHAT IS OWED IS NAMED RATHER THAN GUESSED.** `OQ-M7-02` (the eleven rows' thresholds) and `OQ-M7-03` (`sla_hours`) are the founder's and are unanswered. This row invents neither.

**AND THE ESTATE IS PROTECTED FROM THE `sla_hours` GAP TODAY BY THREE INDEPENDENT REFUSALS, WHICH WERE MEASURED RATHER THAN ASSUMED.** `sla_hours` is unstated in every seeded row, and `risk_flags_high_severity_has_sla` requires a clock at severity 4 and 5, so: `detectors/fills.ts` **caps** a wanted 4 or 5 down to 3 and copies the reason into the evidence; `detectors/identity.ts` raises `DetectorDeclined` rather than computing one; `detectors/graph.ts` refuses through `refuseUnclockedSeverity`. **So no flag any in-tree detector can raise today reaches the band that holds a payout.** `test/detector-adapter.test.ts` asserts it on the flags a real firing run produces, rather than restating it.

**THE ONE PLACE A FALSE POSITIVE COULD ENTER THROUGH THIS DIFF IS THE BOUNDARY CAST, AND IT IS GUARDED TWICE.** `DetectorTx.rowsWhere` takes an untyped filter because a detector composes its window from registry parameters at run time; `SystemTx.rowsWhere` takes a typed one. The cast between them is the only one in this deployable past a key type. A compile-time conditional makes both detector table unions a `tsc` error unless the accessor still carries a key of each name, **watched going red by adding a bogus member**, and a run-time membership check refuses a key the port did not declare before it reaches the door. The COLUMN names are the accessor's to check and it throws on one that is not a column; that throw lands in `attemptScan`'s catch and is recorded as a `failed` run, which is asserted rather than assumed.

### 6. The falsification, and why the silent case is the one that matters

Section 5 of `test/detector-adapter.test.ts` drives the **real** `D-01` detector through the **real** adapter over a recording door, twice, with the same registry row and the same code, differing only in the seeded rows.

| Case | Seeded | Result |
|---|---|---|
| **Fires** | Two accounts, one symbol, one side, four fills each at the same instants | Status `ok`, run recorded, **two** `risk_flags` rows at `copy_cluster`, `open`, `internal`, each joined to the run id, each with non-empty evidence, **each below severity 4 and carrying no `sla_due_at`** |
| **Silent** | The same two accounts, same symbol, same side, every fill an hour or two from the other account's | Status `ok`, run recorded, `rows_scanned` non-zero, **zero** real flags, canary found, `degraded` empty |

**TWO FLAGS AND NOT ONE, AND THE PAIR IS THE FINDING RATHER THAN A DUPLICATE.** A copy cluster is an accusation about a RELATIONSHIP and the runner has no evidence which side led, so both identities are named. Asserting one would have been asserting that a detector picks a culprit.

**THE SILENT CASE WAS WATCHED FAILING.** With `window_seconds` widened from 2 to 7200 in the registry row and nothing else changed, the hours-apart fills become a cluster and the case goes red on `expect(quiet.realFlags).toEqual([])`. **That is the whole argument for the case existing**: a detector wired with the wrong threshold restricts traders who did nothing, and a firing case alone passes over a detector that fires on everything.

**AND THE SILENCE IS A DETECTOR THAT WORKED RATHER THAN ONE THAT STOPPED LOOKING**, which is `GS-122` and is asserted beside it: the canary was seeded and found, `synthetic_found` equals `synthetic_expected`, and `rows_scanned` is the real row count. `AS-M7-05`'s sentence is *"`detector_runs` records `status: ok`, `rows_scanned: 0`, `flags_raised: 0` and that is indistinguishable from a genuinely quiet night"*. The quiet case here records a non-zero scan and a found canary, so it is distinguishable, which is the property the whole module exists for.

### 8. `src/db.ts` grew a value, and it is not a second door

`ADR-157`'s three read terms are minted by `packages/db` and `isFilterTerm` reads WeakSet membership rather than shape, so a hand-rolled term is a jsonb VALUE to the accessor and narrows nothing. An adapter that wanted to hand a detector those constructors therefore had two ways to get them, and one was to import the accessor in a second file, which `test/db.test.ts` pins at exactly one.

**SO `WORKER_TERMS` IS ON `src/db.ts`, AND `ADR-165` CLAUSE 2 COUNTS DOORS ONTO TABLES.** A term reaches no table. It names no key, carries no scope predicate, has no `rows` and no `insert`, and `transaction()` has no overload that takes one. It is strictly smaller than the pool-shaped executor that file already carries: that hands out arbitrary SQL on the money database, and this hands out the ability to say `<=`, `>=` and `IS NULL` on a read the caller could already make with `=`. **THERE IS NO `isNotNull` AND THE ABSENCE IS UPSTREAM**: `ADR-157` refuses it by name, this file mints nothing, and the vocabulary cannot become four without the accessor growing a fourth first.
