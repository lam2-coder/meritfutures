## ADR-241: the worker is a one-shot job whose exit code is its only signal, the schedule is external, and the first `BatchPorts` value over Postgres serves four of ten methods and refuses six by name  (2026-08-29, status: proposed)

**[ALLOCATION](ALLOCATION.md) row `241` dispatched this session to make the worker deployable actually run its job, and named three things so that none could be quietly skipped: an entrypoint that invokes `main`, a `BatchPorts` adapter over Postgres, and something that schedules it.** All three landed. **A fourth thing was required and is the one this entry argues hardest for: the process must FAIL LOUDLY**, because the defect being repaired is not that the worker did nothing, it is that a worker doing nothing was indistinguishable from a worker working.

- **Origin:** row `241`, session **431**, branch `claude/the-worker-runs-a-job`. **MONEY PATH BY CONSEQUENCE**: nothing evaluates a trader until this runs, so no trader is funded and none is paid. [**`E2`**](../../MERIT_BUILD_MASTER_PROMPT.md) **READ IS OWED.** The entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **NO MIGRATION WAS TAKEN.** Row `241` reserved `0074` conditionally, against the case that this work needed DDL. **It did not.** Every table this session reads is registered in [`scope.ts`](../../packages/db/src/scope.ts) already, every column it reads is declared already, and nothing here writes a schema object. **`0074` returns to the pool** and the row records it, which is the mechanism working rather than a number spent to look busy.

- **WHAT IS MEASURED AND WHAT IS JUDGED**, separated before the argument starts. That the deployable exited 0 having done nothing is **MEASURED**, twice, in section 1. That it now exits non-zero on a failed batch is **MEASURED**, by a test that spawns a process and reads its status. The accounting of four served ports and six refusing is **DERIVED**, method by method, in section 4. What is **JUDGED** is that the schedule belongs outside the process (section 3), that concurrency stays at one (section 4.3), and that a partial adapter that refuses is better than a complete one that guesses (section 4.1).

### 1. The defect, re-derived rather than carried

The dispatch supplied the measurement and required it to be reproduced before a line changed. It reproduces.

```
$ grep -c "^main();\|^await main();\|void main()" apps/worker/src/index.ts
0

$ pnpm --filter @merit/worker start
> @merit/worker@0.0.0 start /home/user/meritfutures/apps/worker
> node --experimental-strip-types src/index.ts

EXIT=0
```

`apps/worker/package.json` started the deployable on `src/index.ts`, which is the package's `exports` target. That module declared `export function main(): void` whose body was a `console.log` listing everything the module does not do, and **nothing called it**. So the process loaded a barrel of re-exports, bound the name, and exited.

**A PROCESS THAT EXITS 0 HAVING DONE NOTHING IS WORSE THAN ONE THAT CRASHES.** [`CRON_INVENTORY`](../ops/runbooks/CRON_INVENTORY.md) opens on the failure one layer up: *"A scheduled job that stops being scheduled is invisible."* This was the same failure one layer down. Every dead-man switch in that register watches for a completion signal to be ABSENT; a deployment reporting success is a deployment those switches read as healthy.

**And the consequence was the whole estate rather than one job.** [ADR-239](ADR-239.md) put it plainly and this session confirms it: the provisioning saga, the expiry sweep, the detector runner, the breaker evaluator, the two digest producers and the nightly batch are all downstream of one uncalled function. **If this estate has ever been thought of as partly running, it was not running at all.**

### 2. The entrypoint, and why nothing catches

[`apps/worker/src/start.ts`](../../apps/worker/src/start.ts) is one statement.

```ts
await main().finally(closeWorkerDb);
```

**A SEPARATE FILE RATHER THAN AN ENTRY-POINT GUARD**, which is [`apps/api/src/start.ts`](../../apps/api/src/start.ts)'s ruling transcribed rather than re-argued: importing `index.ts` must have no effect, and the usual guard comparing `import.meta.filename` with `process.argv[1]` is a run-time string comparison that is right until something invokes the file by a symlink and invisible when it silently stops matching. `pnpm start` names this file, this file calls `main`, and the barrel stays a module that exports.

**THERE IS NO `try` AND THAT ABSENCE IS THE WHOLE CONTROL.** A rejected top-level `await` in an ES module makes Node report the error and exit non-zero. A supervisor's only signal is the exit code, so every `catch` that logged and fell through would rebuild the defect in a new costume: a batch visibly broken in a log nobody reads and invisibly fine to the thing that pages. **The trap the row named is that a job which cannot fail loudly is the defect being fixed, wearing different clothes, and the answer to a trap phrased that way is a predicate rather than a promise.**

**THE PREDICATE WATCHES A PROCESS.** [`apps/worker/test/entrypoint.test.ts`](../../apps/worker/test/entrypoint.test.ts) spawns real processes with `spawnSync` and reads `status`:

| case | what runs | status |
|---|---|---|
| the real entry point, `DATABASE_URL` unset | `src/start.ts` | **non-zero**, and stderr names `DATABASE_URL` |
| a job that cannot resolve its day | `main` over a stub door with an empty calendar | **non-zero**, `WorkerJobRefusal` |
| **a port that refuses mid-batch** | `main` over a stub door with one marked account | **non-zero**, `BatchPortUnwired`, `loadAccountDay` |
| a completed run over an empty book | `main` over a stub door with a closed session | **0**, and it prints its report |

**A TEST THAT IMPORTED `main` AND ASSERTED ON A REJECTED PROMISE WOULD HAVE PROVED THAT A FUNCTION THROWS**, which was never in doubt, **and would have said nothing about what a supervisor sees.** The third row is the case an operator will actually meet, and it is the one that would have been easiest to leave unwritten.

**THE TEST THAT STOOD IN THIS DEPLOYABLE'S SUITE WAS THE DEFECT IN TEST FORM.** `test/service.test.ts` read `expect(() => main()).not.toThrow()` under the name *"the deployable starts"*, and it was green for the entire period in which the deployable started and did nothing. It is replaced rather than repaired.

**THE POOL IS RELEASED AND THAT IS NOT A DETAIL.** `pg` holds the event loop open, so a one-shot job that did not close its pool would succeed and then hang, which a supervisor reads as a job still running and a dead-man switch reads as a job that never finished. `closeWorkerDb` is a new export on [`src/db.ts`](../../apps/worker/src/db.ts), on that file's own reasoning: it is process lifecycle rather than a unit of work, so it sits beside the door and not on it. `Promise.prototype.finally` rejects with the original reason, so releasing the pool cannot turn a failed batch into a green one.

### 3. THE RULING ON THE SCHEDULE: EXTERNAL

**The row required this to be ruled and said which way it must not be fudged: a timer inside a process that nothing restarts is not a schedule.**

**RULED: the worker's nightly batch is a ONE-SHOT PROCESS. It runs once, reports, and exits. The schedule lives OUTSIDE it, in the platform scheduler, and is registered in [`CRON_INVENTORY`](../ops/runbooks/CRON_INVENTORY.md)'s scheduled-work table.**

The argument is not preference and it is not infrastructure taste. **An in-process timer and a loud failure are mutually exclusive.**

| | in-process timer | external schedule |
|---|---|---|
| the failure signal | a log line, inside a process that stays up | **the exit code** |
| a batch that throws | the process either dies, losing every later run, or swallows it and stays green | the run fails, the next run is unaffected |
| a process that wedges | invisible: it is still up | the run does not complete and the dead-man switch fires |
| what a supervisor restarts | a service that may have stopped scheduling internally hours ago | nothing to restart; the scheduler starts the next one |

**A LONG-LIVED PROCESS HAS NO EXIT CODE TO FAIL WITH.** That is the whole of it. This session's entire subject is that a status of 0 from a process that did nothing is unreadable, and an in-process timer would make every future run unreadable in exactly the same way: the only status such a process ever leaves is the status of its LAST moment, which says nothing about the two hundred nightly folds before it. **Choosing the timer would be choosing, deliberately, the shape whose failure mode this entry exists to remove.**

**THE SECOND REASON IS THAT THE REGISTER ALREADY WORKS THIS WAY.** `CRON_INVENTORY`'s rule is *"a job in this table without a dead-man switch is a job that does not exist"*, and every switch in it is phrased as the ABSENCE of a completion signal by an expected-by time. That phrasing presumes discrete runs with discrete completions. A timer inside a service produces neither.

**WHAT IS NOT RULED HERE, said so the ruling is not read wider than it is.** Which platform scheduler, and its cron expression, are **deployment facts and are not written down in this repository** ([ADR-012](ADR-012.md)). The register says the job runs after ingest and is expected by 06:00 CT; what enters the scheduler's configuration is an operator's, in the same way a `DATABASE_URL` is. **This entry rules the SHAPE and not the setting.**

**AND `@merit/queue` IS NOT THE ANSWER TO THIS QUESTION, which is worth stating because it looks like it should be.** [ADR-086](ADR-086.md) landed the `JobQueue` interface and `pgBossQueue`; what has never landed is the job store, because pg-boss's schema is in no migration and `pgBossQueue` is configured `migrate: false` precisely so that gap fails loudly rather than being closed by a library running DDL on the money database at boot. **A queue is how a job is HANDED OFF, not how it is STARTED on a clock**, and the nightly batch has no producer to hand it off from. So the manifest line that header has asked for since session 147 is still owed, still by a different session, and this entry does not spend it.

### 4. The adapter, method by method

[`postgresBatchPorts`](../../apps/worker/src/batch/adapter.ts) is **the first `BatchPorts` value constructed under any `src/` in this workspace**, which `apps/api/test/rule-state-producibility.test.ts` has been running as a measurement and which returned zero until this session.

| port | here | blocker if it refuses |
|---|---|---|
| `calendarWatermark` | **SERVED**. the maximum `trading_calendar_revisions.id`, or `null` | |
| `calendarSlice` | **SERVED**. `trading_calendar` as an [ADR-049](ADR-049.md) value | |
| `accountsWithLiveMark` | **SERVED**. the day's `daily_marks`, superseded rows dropped | |
| `accountsWithStoredState` | **SERVED**. every `rule_states.account_id` | |
| `loadAccountDay` | **REFUSES** | six fields beyond the account id, and `prior` needs the codec |
| `accountDaysFrom` | **REFUSES** | the same, per account across its whole history |
| `storedRuleStates` | **REFUSES** | `engine_gates` has a ruled encoding and no decoder |
| `writeRuleState` | **COMPOSED, ONE LEG SHORT** | the encoder half of the same codec |
| `raiseReconciliation` | **REFUSES** | no event writer exists in this deployable |
| `raiseDivergence` | **REFUSES** | the same |

#### 4.1 Why a refusing adapter is the right artifact and not a smaller one

**`databaseAccountReads` serves one of four and `databaseAuthBackend` four of sixteen.** In every case in this tree the refusal carries the blocker rather than a shrug, and the reason is always the same: **a fixture serving real traffic is worse than a 503.** Here it is worse than that. `runNightlyBatch` counts a `written` outcome per account that did not throw, so a port returning a plausible value produces a report saying the book gained rows on a night it gained none, and `INV-04`'s replay audit then reads an empty table as an estate with nothing to audit.

**Each refusal is a `BatchPortUnwired` naming the method and the slice that clears it**, because the first question anybody asks a red batch is what to build next.

#### 4.2 The three blockers, each with a home

1. **The `engine_gates` codec.** [ADR-206](ADR-206.md) ruled the encoding on 2026-08-29 and [`rule_states.md`](../architecture/data-model/rule_states.md) reproduces it. What is owed is a module. **Its home is `packages/rules-engine` and NOT this deployable**, on [ADR-239](ADR-239.md) slice A's reasoning: `readLiability` in `apps/api` needs the same decoder and cannot import `apps/worker`, so an encoder here and a decoder there is `FM-16`, two statements of one predicate with nothing comparing them. **That home is outside this session's fence and the fence was not widened to finish**, which is the same move as weakening a gate to pass it.
2. **The `AccountDay` loader.** Six fields: a `ResolvedPlan` from the account's PINNED `plan_versions.rules` and its `plan_version_sizes` row; a `prior` `RuleState` read back through the codec above; the day's live `DailyMark`; the settlements whose effective trading day is this day; `accounts.opened_on`; and `R-40`'s five context facts across KYC, freezes, reconciliation, in-flight payouts and account status. **Every one is a reading of a table, and a reading a port GUESSED at would produce a money row nobody could tell from a correct one.** Section 6 sizes it.
3. **An event sink.** `raiseReconciliation` and `raiseDivergence` are events. `TRANSACTION_EVENT_WRITER` in `apps/api/src/events.ts` is the only composed writer in the tree, `apps/worker`'s manifest declares `@merit/db` and `@merit/rules-engine` and nothing else, and under `node-linker=isolated` an undeclared import does not resolve at all. `EVENTS.md` names `replay.divergence_detected` one of the two events that must never be quiet, so **a channel that swallowed a finding here would be exactly the quiet this deployable exists to end.**

#### 4.3 Concurrency is 1, and it is a ruling rather than a default

`Appendix B.5` permits worker concurrency and `FM-10` states what must exist before it is safe: *"settlement webhook and nightly batch race on the same account -> anchors advanced twice, or once with the wrong values"*, with the control being that **the batch takes a per-account advisory lock**. [`nightly.ts`](../../apps/worker/src/batch/nightly.ts) says the adapter owes that lock in terms. **This adapter does not hold it**, because `SystemTx.lockAt` locks a ROW and `FM-10`'s lock is on the ACCOUNT, taken around the whole fold rather than around the insert.

**RULED: `BATCH_CONCURRENCY` is 1 until that lock exists, and it is a constant rather than an environment variable, so no deployment can raise it past a control that has not been built.** One account in flight is **not** the lock. It is the difference between a race and a queue, and the constant moves when the lock lands and not before.

#### 4.4 Two properties of the calendar read, because both are decisions

**A holiday is inside `coverage` and is not in `days`.** `types.ts` is explicit that *"a day INSIDE coverage that is not in `days` is positively not a trading day, and a day OUTSIDE coverage is UNKNOWN"*, and those two answers are the ones [ADR-042](ADR-042.md) `F-4` and `0032` exist to keep apart. A holiday row is Merit knowing the day and knowing it carries no session, so it bounds the window it sits inside and appears in no session list.

**`sequence` is dense over SESSIONS and not over calendar rows**, because `R-37` counts a cadence gap by subtracting sequences and the gap it wants is in trading days. `packages/harness`'s `toCalendarSlice` names the line that would change *"for a calendar with holidays in it"*. This is that calendar and this is that line.

### 5. THE FIRST RUN AGAINST AN EMPTY DATABASE

**The row named this as its second trap and it is right to: `runNightlyBatch` reads the calendar watermark BEFORE anything else, and a job pointed at a fresh database on a stale watermark is a different kind of bad day.** The behaviour is stated here rather than discovered on a night nobody is watching.

**RULED AND BUILT: every refusal that can be made about the RUN is made ABOVE the watermark read.** `main` resolves the trading day and the engine version first, so a job that cannot say which day it is closing never opens a transaction at all.

| database state | what happens | what is written |
|---|---|---|
| **no `trading_calendar` rows at all** | no session has closed, so no day resolves. `WorkerJobRefusal` on `tradingDay`, **before the watermark read**, exit non-zero | **nothing** |
| a calendar, no `trading_calendar_revisions` | the watermark is `null`, **which is CORRECT and is not "unknown"**: the calendar genuinely has never been corrected, and `ports.ts` fixes that reading | rows stamped `null`, correctly |
| a calendar and no `daily_marks` | zero accounts considered. The run **completes**, prints `written: 0` beside `accountsConsidered: 0`, exits 0 | **nothing** |
| a calendar and any marked account | the fold is reached, `loadAccountDay` refuses, exit non-zero | **nothing** |
| `MERIT_ENGINE_VERSION` unset | `WorkerJobRefusal`, before any read | **nothing** |

**THE STALE-WATERMARK BAD DAY IS NOT REACHABLE FROM AN EMPTY DATABASE, and the reason is that `null` is a fact here rather than a missing value.** On a fresh database `trading_calendar_revisions` is empty, so the watermark is `null` and every row stamped with it truthfully records a pristine calendar. There is no carried value and no default: the only way to stamp a row with a watermark it did not read would be to read the watermark AFTER the slice, which is the ordering [`0035`](../../packages/db/migrations/0035_rule_states_calendar_revision.sql)'s header refuses and which `nightly.ts` marks load bearing in a comment above the two lines.

**AND NO FIRST RUN IS DESTRUCTIVE, which is a property of the schema rather than of this job's care.** `rule_states` is insert-only: `0015` states that a rule state is never superseded and `0026` revoked `UPDATE, DELETE` on the table from `merit_app` and from PUBLIC. `state-writer.ts` therefore publishes a `RuleStateTx` with `insert` and nothing else, and this adapter has no other write. **The worst a first run can do is write correct rows or write none.**

**THE DAY IS READ FROM THE CALENDAR AND IS NEVER DERIVED FROM A CLOCK.** [ADR-146](ADR-146.md) clause 4 forbids a UTC calendar date derived from an instant meeting an exchange CT trading day. `readLastClosedTradingDay` compares an instant only with an instant, `session_close_at <= now`, and READS the trading day off the row that comparison selected. That is `databaseEconomicCalendar`'s idiom in `apps/api`, which counts sessions that have not yet opened and compares a count with a horizon. `MERIT_BATCH_TRADING_DAY` overrides it, which `RB-01` needs to re-run a night that failed, and **an override the calendar does not carry is refused rather than folded**, because a day outside coverage would raise a coverage miss on every account rather than closing anything.

### 6. What is owed, sized so the next session does not start from scratch

**SLICE A: the `engine_gates` codec.** `packages/rules-engine`, both directions, over `ENGINE_GATE_LEAVES`' twenty-five dotted paths. Unchanged from [ADR-239](ADR-239.md) section 6 and unclaimed. It clears `storedRuleStates`, the write port's remaining leg, and `readLiability` in `apps/api` at the same time.

**SLICE B2: the `AccountDay` loader.** The largest of what remains, and it is **money path in the strongest sense**: it decides what the engine is fed. Six fields, section 4.2. It should be **planned before it is written**, because two of the six are readings that no primary source in this tree states end to end: which `plan_version_sizes` row an account's size names, and how `R-40`'s five context facts are each resolved from their tables. **A session that writes it without ruling those two first will invent them.**

**SLICE C: the event sink.** `raiseReconciliation` and `raiseDivergence`, and the manifest line that lets this deployable reach a writer. It is the smallest of the three and it is the one that turns a refusing batch into a batch that reports.

**AND ONE THING THIS ENTRY DOES NOT SCHEDULE.** Five other jobs in `CRON_INVENTORY` are built and unwired: the detector runner, the expiry sweep, the two digest producers, the breaker evaluation and the statistics run. **Each needs its own entrypoint decision and its own row**, and this session deliberately did not invent a job registry or a `MERIT_WORKER_JOB` selector to hold them, because a registry nobody ruled is a vocabulary this deployable would then have to live with. The pattern is now on disk once and it is cheap to follow.

### 7. Where this entry is most likely wrong

**Named rather than left for a reader to find.**

**THE EXTERNAL-SCHEDULE RULING ASSUMES THE PLATFORM HAS A SCHEDULER THAT RUNS A PROCESS TO COMPLETION AND READS ITS EXIT CODE.** That is true of every cron-shaped scheduler and it is what `INFRA`'s Railway service model implies, but **this session did not verify it against the deployment**, because the deployment is not in this repository. If the platform can only keep a service up and cannot run a job to completion, the ruling still holds and the shape that satisfies it is a thin supervisor that invokes this process, **not** a timer moved inside it. **The thing that must not happen is the timer.**

**AND THE ADAPTER'S WHOLE-TABLE READS ARE HONEST AND NOT FREE.** `SystemTx` narrows by equality or by a `FilterTerm`, and the three term constructors live in `@merit/db`, which only `src/db.ts` may name in this deployable. So `superseded_by IS NULL` is applied in this process rather than in the query. For the calendar that is right. **For `accountsWithStoredState` it is not**: it is `B.1`'s *"every account that has ever existed"* and it reads the whole of `rule_states` to project one column. It is stated at its own site, nothing calls it yet, and the repair is a read on `packages/db` rather than a filter here.

### 9. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.**

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS SECTION 3.** An external schedule means this repository does not contain the thing that starts the nightly batch: a cron expression in a platform console does, and it can be deleted by somebody who does not know what it was for. The alternative puts the timer where the code review can see it and costs the exit code, which is the only signal a supervisor has. **This entry chose readability of failure over visibility of configuration, and the register plus its dead-man switch is what carries the other half.**

  **THE SECOND IS SECTION 4.1.** Four of ten ports are served and six refuse. That is a deployable which, pointed at the production database tonight, would exit non-zero every night until three more slices land. **That is louder than what it replaces and it is not quieter than what a complete-looking adapter would be**, which would fold traders against invented inputs. If a red nightly batch every night is unacceptable operationally before those slices land, the answer is to not schedule it yet rather than to make it quiet, and that is an operator's call rather than this entry's.

  **THE THIRD IS SECTION 4.3.** Concurrency at one means the nightly fold is serial across the whole book. At the current book that is nothing; at a book of thousands it is the run's wall clock. **The lock is what buys the parallelism back, and it is a slice nobody has claimed.**
