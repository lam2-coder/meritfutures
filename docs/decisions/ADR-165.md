## ADR-165: `apps/worker` is admitted to the trader database, the reason it runs at existed before the door did, and the deployable takes ONE door because a scheduled job has nobody to resolve  (2026-08-27, status: proposed)

**[ADR-117](ADR-117.md) ruling 3 made `DB_ADMITTED` an EMPTY list on the argument that a one-line manifest edit is *"reviewed by whoever reviews manifests rather than by whoever reviews queries"*, and [ADR-120](ADR-120.md) added the first name to it with the rule that a slice may take an admission only where the admission is that slice's SUBJECT.** This entry adds the second. It rules that `apps/worker` is admitted; that the deployable takes exactly ONE door, `systemDb('nightly-batch')`, because a scheduled job has no caller to resolve and `scope.ts` leaves no other handle generic over the classes a detector run reads; that `SystemReason` gains no member; and that `RI-08`'s list is amended rather than a thirteenth invariant minted. **The half worth reading is section 6**, which names which deployables may reach the trader database after this and which may not, because the value of this slice is not the code it lands.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `165`, session **292**, dispatched as `claude/p7a-worker-db` against [P7](../plans/P7-risk-and-abuse.md) section 8's `P7-a` row. The number was RESERVED before dispatch and the reservation names it **REQUIRED**. **NOT MONEY BY FILE**: no migration, no `SD-nn`, no `packages/db` change, no route, no gate. **Money by what it governs**, which is the only sense in which a line naming which processes may open a connection to the trader database is not money.

- **Context:** [P7 section 3.2](../plans/P7-risk-and-abuse.md) is the finding this entry closes: [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md) rows detector runs as scheduled work, scheduled work is `apps/worker`'s, and *"the detector runner reads `fills`, `daily_marks`, `identity_links` and `identity_signals` from a deployable that cannot declare the accessor at all."* That plan's own dispatch order states what this slice is for in one sentence: **its value is that the question "may a scheduled job read the trader database" gets answered in the file whose subject it is, before a detector slice answers it in a manifest diff.**

- **Session 279 was dispatched for this slice and its work is unrecoverable**, its container having had no push credential. Nothing landed, so nothing here is a re-tread of a diff on disk; the reservation row was untouched on `main` and this session started from it.

### 2. THE RULING

> **1. `@merit/worker` IS ADMITTED TO `DB_ADMITTED`, AND WHAT MAKES THAT CORRECT HERE IS THE SAME THING THAT MADE [ADR-120](ADR-120.md) CORRECT: IT IS THIS ENTRY'S SUBJECT.** [ADR-117](ADR-117.md) ruling 4's test is not weakened, not met by a better need, and not met by a bigger one. It is met by a session whose OBJECT is the authority change, reserved by name in [ALLOCATION](ALLOCATION.md) row `165` before it ran. `RI-08`'s two throws are untouched, `acquires` is untouched, and the `guarded.length === 0` refusal is the assertion that matters most now that the list holds two.
>
> **2. THE DEPLOYABLE TAKES ONE DOOR AND THERE IS NO SECOND.** [`apps/worker/src/db.ts`](../../apps/worker/src/db.ts) opens `batch(fn)` over `systemDb('nightly-batch')` and declares **no `scoped`, no `firm`, and no reason parameter.** The absence of a reason parameter is what forecloses `'operator-console'` from this deployable BY CONSTRUCTION rather than by convention: there is no argument position a caller could put it in. Finding 7 is why the one door is not a preference: for a `pair` table `systemDb(reason)` is *"the only door left"* in `scope.ts`'s own words, and `identity_links` is the second table `P7` section 3.2 names.
>
> **3. `SystemReason` IS NOT WIDENED AND NO THIRD MEMBER IS TAKEN FOR THE DETECTOR SERVICE.** `'nightly-batch'` already names what a detector run, a fold, a sweep and a nightly assertion each are, and a member minted for a service rather than for a KIND of access is the vocabulary joining itself, which is [ADR-096](ADR-096.md) clause 3's argument applied one deployable over. **[ADR-126](ADR-126.md) is the general form and it is followed rather than restated: the vocabulary that moves is the TABLE and never the REASON.**
>
> **4. `RI-08`'s LIST IS AMENDED AND NO INVARIANT IS MINTED.** The admission is a diff to `DB_ADMITTED`, which is `RI-08`'s subject, and a second check over the same property would be the two-lists defect that file's own `RI-04` header names. **`RI-13` is the next free invariant number and this entry leaves it free.**
>
> **5. AFTER THIS ENTRY, TWO WORKSPACE PACKAGES MAY REACH THE TRADER DATABASE AND EVERY OTHER ONE MAY NOT.** Section 6 enumerates the outside by name and gives, for each, the reason that is not this list. **A slice that finds it needs one of those names STOPS and reports it**, and the admission is taken by a session whose whole subject is the authority change. That is the procedure, it is not a preference, and five sessions have now followed it.
>
> **6. THE ADMISSION IS NOT A CAPABILITY GRANT AND THE DISTINCTION IS THE WHOLE DESIGN.** This list grants the ability to NAME `@merit/db`. `scopedDb` still needs an identity, `systemDb` still needs one of two reasons, `firmDb` still refuses every `owned` key, [ADR-112](ADR-112.md)'s addressed write still refuses an address that names no unique key, and [ADR-157](ADR-157.md)'s terms are still admitted on the read path only. Those are the controls on the USE, at the type level, and this entry moves none of them.

### 3. Clause 1, and the fifth decline

**THE ADMISSION IS NOT A BETTER-ARGUED VERSION OF ONE THAT WAS DECLINED. IT IS A DIFFERENT ACT**, and `apps/worker` is the second deployable to demonstrate the same thing.

[ADR-120](ADR-120.md) section 3 recorded two declines, sessions 218 and 220, each blocked *"by the shape of their own dispatch: the admission was a MEANS in a slice whose END was something else."* **Finding 5 adds three more, all inside this deployable, spread across three sessions and a year of file headers.** Session 147 named the remedy in advance and called it *"the session that brings the first job with it"*. Session 222 reached the line from the provisioning saga, wrote *"THIS SESSION IS THAT SESSION AND THE MANIFEST IS OUTSIDE ITS FENCE"*, built the whole saga against ports instead, and reported the wiring in a pull-request body.

**Five declines across two deployables is what a control that works looks like from the inside.** Every one of them named the same remedy and none of them took it, which is the only evidence available that a list whose entire enforcement is *"somebody has to write a reason here"* is enforcing anything at all.

**SO THE TEST IS NOT WHETHER THE NEED IS REAL AND IT IS NOT WHETHER IT IS BIG.** The need was real in session 147 and it was real in session 222. The test is whether the need is the SUBJECT, and the reason that test is the right one is that a control whose design is *"adding a name here is the admission decision"* is defeated the first time the decision is taken by somebody who was thinking about a saga.

### 4. Clause 2, and why one door is a measurement rather than a taste

**THE DETECTOR RUNNER'S READ SET SPANS FOUR SCOPE CLASSES IN ONE JOB.** [P7 section 3.2](../plans/P7-risk-and-abuse.md) names `fills`, `daily_marks`, `identity_links` and `identity_signals`; the runner writes `detector_runs`. Read out of [`scope.ts`](../../packages/db/src/scope.ts) rather than assumed:

| Table | Class | `scopedDb` | `firmDb` | `systemDb(reason)` |
|---|---|---|---|---|
| `fills` | `derived` | reaches it | **refuses** | reaches it |
| `daily_marks` | `derived` | reaches it | **refuses** | reaches it |
| `identity_signals` | `owned` | reaches it | **refuses** | reaches it |
| **`identity_links`** | **`pair`** | **refuses** | **refuses** | reaches it |
| `detector_runs` | `firm` | **refuses** | reaches it | reaches it |

**No two doors cover the set and one does.** `scopedDb` is declared over `ScopedTableKey`, which is `Exclude<TableKey, FirmTableKey | PairTableKey>`; `firmDb` is declared over `FirmTableKey`; `systemDb(reason)` is declared over `TableKey`. `scope.ts` states the consequence at `PairTableKey` in its own words, and it was written about a different caller: *"REFUSED BY BOTH NARROW DOORS AND SERVED BY THE ONE THAT TAKES A REASON ... `systemDb(reason)` is generic over `TableKey` and is the only door left."*

**So the one-door design is not a minimalism.** A `firm` door would reach a strict subset (finding 8). A `scoped` door would reach four of the five and would need an `IdentityId` cast with nothing legitimate to cast (finding 9): `apps/api` casts an identity a handler RESOLVED from a session token, and the only thing a batch could cast is a uuid it read out of a row, which is an identity nobody authenticated and a predicate that would then be checked against the row it came from.

**AND THE REASON IS SPENT AT THE CALL SITE RATHER THAN ACCEPTED AS AN ARGUMENT.** That is the one design decision here that is a choice rather than a consequence, and it is made in the safe direction: `systemDb(reason)` with a parameter would have been shorter and would have put `'operator-console'` one string literal away from a scheduled job. `apps/api/src/db.ts` reaches the same conclusion from the other side and writes *"a door declared here is a door somebody uses"*; this file makes the same sentence true of an ARGUMENT.

### 5. Clause 3, and the member that was not minted

**THE TEMPTING LINE IS `'detector-service'` AND IT IS TEMPTING FOR A GOOD REASON.** A `detector_runs` row records which detector ran under which parameters, `INV-M7-04` makes that recording the thing that answers *"why did this not fire in March"*, and a reason string that named the detector service would put that fact one more place.

**IT IS REFUSED BECAUSE `SystemReason` DOES NOT NAME SERVICES, IT NAMES KINDS OF ACCESS.** `'nightly-batch'` is *"a job that partitions across every account"* and `'operator-console'` is *"a human looking at the estate"*. A detector run is the first of those exactly: it partitions across every account, it runs because a clock said so, and it has no caller. **A third member would not carry information the first two lack; it would carry information about WHO is running, which is what `detector_runs` is for and what a scope vocabulary is not.**

**AND THE COST OF THE ALTERNATIVE IS ALREADY MEASURED.** [ADR-109](ADR-109.md) clause 1 refused to widen this same vocabulary to solve *"what turned out to be a predicate problem"*, and [ADR-157](ADR-157.md) held it at two members while widening the accessor in three other directions on the same day. A vocabulary that grows once per deployable is a boolean written in words, and the whole reason it is a closed list is [ADR-084](ADR-084.md) section 5's sentence: *"forgot to scope" becomes "wrote the word system"*.

**AND THE PROCEDURE HAS A COST THAT IS PAID DELIBERATELY.** Session 222 built an entire provisioning saga against ports rather than take this line, and that saga still has no adapter. **That is the control working, not the control failing.** A list that is cheap to join is not a list.

### 7. What this admission does NOT unblock, which is every wave-2 slice

**THE HONEST STATEMENT IS THAT NO DETECTOR BECOMES WRITABLE TODAY AND THIS ENTRY IS NOT WHAT WAS BLOCKING THEM.**

[P7 section 3.1](../plans/P7-risk-and-abuse.md) names the real blocker and [ADR-157](ADR-157.md) section 5 answered it in the negative: *"not one of the four detectors it names is served by a scalar aggregate"*, so the accessor was deliberately widened by a range term, a null term and a row lock and NOT by an aggregate, on the argument that admitting one would have spent the widening and left P7 blocked on the JOIN it is actually blocked on. **`D-01` is a self-join on `fills` inside a two second window. `D-02` is a rolling correlation over twenty trading days. `D-03` is a variance of sums across a discovered group.** None of the three is an equality conjunction over one table, with or without this entry.

**So the three things `P7` waits on are unchanged in number and one of them is now closed.** The read shape is still owed and it is `packages/db`'s to rule, not this deployable's. The fixture format is still [ADR-125](ADR-125.md)'s and blocks all three of P7's done-gates. **What closes here is only the third: the deployable can now name the accessor, so when the read shape arrives there is somewhere for the adapter to go.** A reader looking for a detector after this merge will not find one, and that is the design rather than an omission.

### 9. What was watched failing, and the direction this leaves open

**THE ADMISSION ITSELF, WATCHED IN BOTH DIRECTIONS.** With the manifest line added and `DB_ADMITTED` unchanged, `node packages/tooling/checks/repo-invariants.mjs` exits **1** at **11 of 12** with `FAIL RI-08` naming `apps/worker/package.json: dependencies.@merit/db`. With the name admitted it exits **0** at **12 of 12** and `RI-08`'s computed title reads **2**. **A control nobody has seen fail is not known to be a control**, and this one was seen failing on the exact package it was about to admit.

**FOUR SEEDS ON THE NEW SUITE, EACH REVERTED FROM A BYTE-IDENTICAL COPY.**

| Seed | Caught by |
|---|---|
| `WORKER_REASON` set to `'operator-console'` | the reason case, on both the positive and the negative expectation |
| A second door, `system(reason, fn)`, added to `LIVE_DB` | the door-count case |

**THE THIRD CASE WAS WRITTEN WRONG FIRST AND THE TREE SAID SO.** It tested whether a file CONTAINED the accessor's name and failed on [`src/provisioning/ports.ts`](../../apps/worker/src/provisioning/ports.ts), whose header names `@merit/db` in order to state that it does not import it. A prose mention of a package a file deliberately does not reach is the opposite of the property being asserted, so the instrument is the import statement. **That is recorded because a substring test would have passed the day it was written and failed on the first file that documented its own restraint.**

**THE DIRECTION NOTHING CATCHES, STATED PLAINLY.** `RI-08` reads `DB_ADMITTED` as data, so a third name added to the array with a comment and no entry passes every gate in this repository. **The control on that is this document and the review that reads it, and there is no mechanical version.** A check that demanded an ADR link per element would be a check on a comment, which is prose control over prose. Recorded as the standing limit rather than closed.
