## ADR-219: the portal's first write verb, and the CSRF control it does not mint because the one the corpus already has is on the wrong side of a fence  (2026-08-29, status: proposed)

**`ApiClient` had exactly one member and every trader write in Merit was unreachable behind it.** [`apps/portal/src/http/client.ts`](../../apps/portal/src/http/client.ts) declared an interface whose only method was `get`, so the application could not express a `POST` at all: sign-in, checkout, the payout request, `KYC` and the phone change were each blocked on the same missing line. Three screens declined to add it and each said why at the point it declined. **This entry is the fourth encounter and it takes the ruling.**

**A WRITE IS NOT A READ WITH A DIFFERENT STRING IN `method`, WHICH IS WHY THREE SCREENS WERE RIGHT TO DECLINE.** It carries a request body, it is the only place a `CSRF` posture can be argued, it is the only place an `Idempotency-Key` can be sent or withheld, and it is the first thing in this application that can RECEIVE a `Set-Cookie` it has no way to deliver. Four clauses below, and nothing else moves.

**NO PAGE CALLS `post` IN THE COMMIT THAT ADDS IT.** [ADR-003](ADR-003.md) gives a money-path session one objective and this one is the transport; [ADR-190](ADR-190.md) rules a control that answers wrongly worse than one that honestly refuses, and a screen that starts posting on a posture nobody has read is that control.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `219`, session **409**, dispatched as `claude/portal-first-write-verb`. The row is **RESERVED, REQUIRED**, and the number is spent: the corpus is silent on the first of the three questions in the place the row looked, and it is NOT silent in the place the row did not look, which is the first finding below.

- **MONEY PATH ADJACENT, and the adjacency is total rather than partial.** No migration, no ledger, no engine and no `apps/api` line is touched, and `apps/api` is byte for byte unchanged. But `POST /accounts/:accountId/payout`, `POST /wallet/withdrawals` and `POST /checkout` all ride on this function when a segment wires one, and the `Idempotency-Key` clause is the difference between a replay and a second payment. **The `E2` read is owed on [`client.ts`](../../apps/portal/src/http/client.ts) and on [`http-client.test.ts`](../../apps/portal/test/http-client.test.ts).** This entry ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** The route and method counts in section 2, the origin topology in section 3, the three `Set-Cookie` emitters and the two `204`s in section 4, the eleven stale prose sites in section 7 and every count in section 8 are **MEASURED** over the tree at the moment of writing. That `SameSite=Lax` leaves the same-site case open is **DERIVED** from the cookie's attributes and `INFRA`'s origin table together. What is **JUDGED** is that this client mints no token (clause 1), that the caller owns the idempotency key (clause 3), and that `ApiSuccess` does not gain a status in this slice (clause 5).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim below was read at its own file. **Three of the row's premises did not survive and they are in section 1.**

### 3. Clause 1: the CSRF posture. **NO TOKEN IS MINTED HERE**

**THE OBLIGATION IS REAL AND IT IS `apps/api`'s.** Section 1 establishes that the constitution rules `CSRF on cookie mutations`. This entry does not weaken that and does not discharge it. Three measurements say the discharge cannot happen in this file.

**ONE. NOTHING ON THE SERVER READS A TOKEN.** `grep -rni csrf apps/api packages` returns nothing. A header sent from here would be an unread header, and an unread header on a money path is worse than no header at all: it is a control the next reader counts. There is also no token for the client to send. The session cookie is `httpOnly`, so page script cannot read it; `API_CONTRACT` declares no endpoint that issues a token; and inventing a value would be a second copy of a decision `apps/api` has not made.

**TWO. THE REQUEST THIS CLIENT MAKES IS NOT THE REQUEST CSRF DEFENDS AGAINST.** A cross-site request forgery is a request the VICTIM'S BROWSER is tricked into issuing with its own cookies attached. Section 2 of `client.ts` established, on three measurements, that the browser never calls this API at all: the portal's SERVER holds the inbound `Cookie` header and forwards exactly one name from it. This `fetch` runs in Node, the cookie is attached by hand rather than by a cookie jar, and **no page anywhere can cause it to be issued**. [ADR-095](ADR-095.md) ruling 3 and [ADR-138](ADR-138.md) section 3 refuse a Server Action in this deployable OUTRIGHT and `RI-11` reads every compiled file under `apps/` for one. **The portal exposes no browser-reachable write endpoint for a forged form to target.**

**THREE. FOR THE CROSS-SITE CASE THE COOKIE IS ALREADY THE CONTROL.** [`auth.ts:589`](../../apps/api/src/routes/auth.ts) sets `merit_session` with `HttpOnly; Secure; SameSite=Lax`, which is `API_CONTRACT:19`'s attribute list written out. A `Lax` cookie is not attached to a cross-site `POST` at all, so an attacker page on `evil.com` posting to `/api/v1/checkout` arrives with no session and is a `401`. **A token for that case would be a second copy of a protection the cookie already gives**, which is the shape this corpus has spent a week finding.

#### 3.1 What `Lax` does not cover, which is the half the ruling turns on

**`SameSite` IS SITE-SCOPED AND MERIT'S TRADER SURFACES SHARE A SITE.** [`INFRA`](../architecture/INFRA.md) section 2.1 rows `site` on **`meritfutures.com`**, `portal` on **`app.meritfutures.com`**, and `api` on **`app.meritfutures.com`, under `/api/v1`**. `meritfutures.com` and `app.meritfutures.com` have the same registrable domain, so a request issued by a page on the marketing origin to the API is **same-site**, `Lax` permits it, and the host-only `merit_session` cookie is sent because the destination host matches.

**SO AN INJECTION ON THE MARKETING SITE IS A FULLY AUTHENTICATED WRITE AGAINST A TRADER'S MONEY, AND `Lax` DOES NOTHING ABOUT IT.** That is what `Lax` does not cover, and it is the ground a control has to be ruled on rather than the ground the row expected.

**THE CORPUS ALREADY REASONS THIS WAY ONE ORIGIN OVER, WHICH IS WHY THIS READS AS AN OVERSIGHT RATHER THAN A TRADE.** `INFRA` section 3 hard rule 3 puts the admin console and `api-admin` on `ADMIN_ORIGIN`, *"a separate apex domain"* ([ADR-012](ADR-012.md)), and says in terms that *"cookie scope, CORS, and the CSP never span the two origins, so an XSS on the portal cannot reach the admin surface even in principle"*. **The operator surfaces were separated at the site boundary on purpose. The trader surfaces were not**, and `Lax` is the only thing standing where the separation would have been.

The other two limits are named so nobody has to rediscover them. `Lax` permits a **top-level GET navigation**, which is harmless only while every mutation is a `POST`, and section 2 measures that it is. And it is no defence against **script running on the origin itself**, where `httpOnly` is the control and a token in a script-readable cookie would be no control at all.

#### 3.2 What is registered rather than ruled

**The shape of the API-side control is `apps/api`'s ruling and this entry does not pick one**, because a client that starts sending a header before the server decides which header it reads has made the decision by shipping. The two candidates are named so the next fence-holder does not start from nothing:

| Candidate | What it costs, and the thing to check first |
|---|---|
| **An `Origin` header check on unsafe methods** | Cheapest, and it fits this deployment's shape: the only legitimate caller is the portal's SERVER, whose `fetch` sends no `Origin` at all, so "refuse when an `Origin` is present and is not allowlisted" admits the real caller and refuses the marketing origin. **Check first that no browser ever calls the API directly**, which is true today and would stop being true the day a browser-side client is admitted |
| **A minted token** | The textbook answer and the more expensive one here. It needs an issuing endpoint `API_CONTRACT` does not have, a place to hold the value that page script can read, and a matching client change. **It also cannot be reached by the portal's server-side call as currently designed** |

**A THIRD OPTION IS THE ONE NOBODY HAS COSTED**: moving the marketing site off the trader surfaces' registrable domain, which is what `ADMIN_ORIGIN` already does for the operator half and which would make `Lax` sufficient by construction. It is an infrastructure ruling rather than a code one and it is nobody's fence today.

### 4. Clause 2: the unsafe-method cookie policy, against `C-02` as written

**OUTBOUND: NOTHING CHANGES, AND THAT IS A RULING RATHER THAN AN ABSENCE OF ONE.** A write forwards exactly one named cookie, never `request.headers.cookie` wholesale, and asks for no `credentials` mode. Section 2 of `client.ts` gave three measurements for that policy and **not one of them turns on the method**: the API sends no CORS header, the cookie is `httpOnly`, and a wholesale relay would hand another deployable every cookie the portal's own origin has accumulated. `C-02` rules nothing about unsafe methods separately.

**`C-02` IS ALSO WEAKER THAN THE SENTENCE THAT CITED IT.** It says *"SameSite"* and names no mode. `Lax` is `API_CONTRACT:19`'s and `auth.ts:589`'s. Reading the mode back out of `C-02` is reading a document for a word it does not contain, and section 1 records it because the next session will be pointed at `C-02` the same way.

**INBOUND IS THE HALF ONLY A WRITE HAS, AND IT IS A DEAD END THAT HAD TO BE SAID OUT LOUD.** Three registered `POST`s answer with a `Set-Cookie`: [`auth.ts:1033`](../../apps/api/src/routes/auth.ts) and [`auth.ts:1088`](../../apps/api/src/routes/auth.ts) establish a session and [`auth.ts:1098`](../../apps/api/src/routes/auth.ts) clears one. **This client receives all three on a server-side `Response` and delivers none of them**, and that is not a gap it can close:

- `next@16.3.2` raises `ReadonlyRequestCookiesError`, *"Cookies can only be modified in a Server Action or Route Handler"*, which is the pinned package's own message.
- [ADR-138](ADR-138.md) section 3 with `RI-11` refuse a Server Action in this deployable **outright**.
- A portal-owned Route Handler on a path `API_CONTRACT` does not specify is the one door [ADR-095](ADR-095.md) ruling 3 leaves standing, **and nobody has ruled on it**.

**SO `post` IS NECESSARY AND NOT SUFFICIENT FOR SIGN-IN.** [Session 408](../sessions/2026-08-29-session-408.md) found that the served set already admits no complete sign-in, because `requestOtp` is blocked on `NO_DELIVERY` and both passkey ceremonies on `NO_WEBAUTHN`. **This is a second and independent reason and it is on the portal's side of the fence**, so it outlives delivery landing: a deployment that could send a code still could not keep the session the API handed back.

### 5. Clause 3: idempotency. The caller's key, never this file's

**WHAT THE CLIENT SENDS:** the caller's string, verbatim, in `Idempotency-Key`, when the caller supplies one, and **no header at all** when the caller passes `null`. The header name is lower case because the reader already is: [`affiliate.ts:807`](../../apps/api/src/routes/affiliate.ts) reads `headers['idempotency-key']`, and the portal test asserts against that file rather than copying the string.

**WHO GENERATES IT: THE CALLER, AND A TRANSPORT THAT MINTED ONE WOULD DEFEAT THE MECHANISM RATHER THAN IMPLEMENT IT.** [`API_CONTRACT:23`](../architecture/API_CONTRACT.md) is the whole argument: *"replaying a key with an identical body returns the original response verbatim; replaying with a different body returns `409 idempotency_key_reuse`"*. A replay is a SECOND CALL. A client that minted a fresh key per call would send a different key on the retry, which the contract's own sentence makes a second payout rather than a replay of the first. `INV-M5-06` states the identical rule one leg over, for the API's call to the transfer rail, in the form that makes the direction unmissable: *"the same `idempotency_key` on every attempt, generated **before** the first send and persisted in the same transaction"* ([`M05:85`](../plans/M05-payout-system.md)). **Before the first send is before this function is entered.**

**THE FIELD IS REQUIRED AND `null` MUST BE WRITTEN OUT.** `API_CONTRACT:23` requires a key on `POST /checkout`, `POST /accounts/:id/payout`, `POST /accounts/:id/reset` and `POST /wallet/withdrawals`, and accepts one everywhere else. **This file holds no list of those four, on purpose.** Three of them carry a path parameter, so a check here would need a pattern table, which is a third copy of a contract fact whose enforcement already lives in the handler; the portal is not the idempotency control for the same reason `INV-M4-06` makes it not the authorization control. **What an OPTIONAL field would buy is a silent default**, and a payout that omitted its key by omission rather than by decision is exactly the failure the key exists to prevent. A required `string | null` puts the decision at the call site, in the diff, beside the path, which is `submits_to`'s idiom on three screens already.

**WHAT IS CHECKED HERE IS THE SHAPE AND NOTHING ELSE.** A key carrying `CR`, `LF`, `NUL` or a leading or trailing space is refused before it reaches a socket, because a header value is this layer's business and a header this file composes by hand is a header this file can be made to inject into.

### 6. Clause 4: the `204`. And clause 5: the one thing this result type still cannot say

**A `204` IS A SUCCESS WITH `body: null`.** `response.ok` is true for it, so without an arm the shared mapping would hand `response.json()` an empty stream and **render a successful logout as `server_error`**. Two registered routes answer `204`, and **the second of them is the one the very next slice will want**: `POST /auth/logout` ([`auth.ts:1100`](../../apps/api/src/routes/auth.ts)) and `POST /sessions/:id/revoke` ([`auth.ts:1176`](../../apps/api/src/routes/auth.ts)), which is the route the security screen has been rendering a disabled control for since [ADR-162](ADR-162.md). **Without this arm, a revoke that SUCCEEDED would render as an outage on the screen where a trader is throwing an attacker out**, which is `ADR-190`'s wrong answer arriving through a success. It is keyed on the STATUS and never on an empty payload: a status is a statement the server made, while an empty body on a `200` is a server that answered wrongly, which is `client.ts` section 3's existing reading and does not move. **The read path is untouched by this arm**, and the asymmetry is asserted rather than left implicit.

- **Approval:** `___________________________` (UNSIGNED. **Merging is not signing.**)

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO DECIDE IS SECTION 3.1, BECAUSE IT IS A LIVE SECURITY GAP AND NOT A TRANSPORT QUESTION.** `meritfutures.com` and `app.meritfutures.com` are the same site, so `SameSite=Lax` does not stop the marketing origin from issuing an authenticated write against a trader's money, and the constitution's `CSRF on cookie mutations` has no implementation anywhere in the tree. **It is checkable in two minutes**: read `INFRA` section 2.1's origin table and `auth.ts:589`, and ask whether anything else stands between a script on the marketing site and `POST /wallet/withdrawals`. **This entry believes nothing does, and it cannot fix it**, because the fix is in `apps/api` or in the infrastructure and this fence is neither. **The judgement worth a founder's disagreement is the ORDER**: this entry treats the missing server-side control as more urgent than the missing client-side token, on the ground that a token nothing checks is not a control.   **THE SECOND IS CLAUSE 3, BECAUSE IT IS THE CLAUSE THAT CAN LOSE MONEY IF IT IS WRONG.** The client mints no idempotency key and requires the caller to write `null` out. **That is right if and only if every future caller actually generates its key before the first attempt and holds it across retries**, and this file cannot make anybody do that: `post({ idempotencyKey: crypto.randomUUID() })` at a call site type-checks, reads as careful, and is `FM-M5-03` exactly. **What would close it is a rule at the call sites rather than in the transport**, and the candidates are a lint rule refusing a freshly generated value in that position, or a required-key list this entry deliberately refused to hold. **If the founder wants the transport to hold the list after all, say so now**: it is four patterns and it is much cheaper before there is a caller than after there are nineteen.
