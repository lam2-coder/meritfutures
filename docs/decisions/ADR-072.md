## ADR-072: A golden fixture is writable when three checkable conditions hold, and every registry row without one carries a stated blocker from a closed vocabulary  (2026-08-20, status: accepted)

**40 fixtures stand against <!--gen:gs_count-->316<!--/gen--> registered scenarios and the reason for each of the 276 absences lives nowhere.** [Section 33.4](../testing/golden-scenarios/33-ownership-index-and-coverage-reconciliation.md) records **three** deliberate absences in prose, each written so it reads as a decision rather than a gap. That is the right idea at three rows. **This entry is the same idea at 276**, moved out of prose and into a column, because **a blocker nobody wrote down is indistinguishable from a fixture nobody got to**, which is how 276 came to be quoted as a queue.

- **Context:** The subtraction is arithmetic and the queue it implies is not. [WAVE-04 section 2](../plans/WAVE-04-fixture-backlog-and-gate-inventory.md) partitions the 276 and its partition is the input this entry checked rather than copied. The checking is section 3 and it did not survive: **the plan's partition is drawn on whether the code exists, and the condition that actually binds is whether the format can state the assertion.** The plan says so itself, one paragraph above the partition, and then partitions the other way.

  **The reason each absence exists is not unrecorded everywhere.** [`fixtures/README`](../../packages/rules-engine/fixtures/README.md) carries a held-back table that covers every M1-owned scenario, re-derived against primary sources, and it is the best record in the tree. **It is also prose, hand-maintained, and stale in at least four rows**: GS-053, GS-060, GS-067 and GS-068 appear on held-back rows while their fixtures sit on disk, and the GS-059 row still names `L-11` as its binding clause after `L-11` was lifted. It covers M1 and says nothing about the other 243. **That is the argument for a column rather than against the record**: the same defect this entry exists to fix is visible in the best hand-maintained instance of it.

- **Decision:** three conditions, one status column, one closed vocabulary, and a citation on every blocked row.

### 1. What makes a fixture WRITABLE

**Three conditions, all checkable rather than judgeable, and a fixture is writable exactly when all three hold.**

| | Condition | How it is checked, without a reading |
|---|---|---|
| **W1** | The code the assertion runs against exists **and is reachable from the loader**, which imports `@merit/rules-engine`'s public entry point and nothing else | Read the imports of [`golden-loader/src`](../../packages/golden-loader/README.md). A symbol in `apps/worker` or `packages/rithmic` fails W1 whether or not it is implemented |
| **W2** | The fixture format can state **both** the input and the expectation: a plan record, a calendar, an ordered day stream, a settlement list, and one expected end state | Read `SETTLEMENT_KEYS`, `EXPECTATION_KEYS` and the `L-nn` refusals in [`loader.ts`](../../packages/golden-loader/src/loader.ts), and the `RuleState` fields in [`types.ts`](../../packages/rules-engine/src/types.ts). A field the type does not carry cannot be pinned |
| **W3** | No open question holds the expected end state undecided | The scenario's row, and the open item it names in [STATE](../STATE.md) |

**"The engine has not implemented the rule yet" is NOT one of the three, and that is [ADR-048](ADR-048.md) working.** A fixture citing an undeclared rule loads, derives inverted, and flips on its own when the rule lands. **So W1 is almost never the binding condition on an M1 row, and W2 almost always is.** The partition in section 3 is what that sentence costs when it is written down and then not used.

### 2. Every row without a fixture carries a STATED BLOCKER, from a closed vocabulary

**The vocabulary is six terms and it is closed.** A term names **which condition fails and by what mechanism**. It does not name the fix: `format-cannot-express` is a statement about the format as it stands, never a proposal that the format should grow.

| Term | Condition | What must be true of the row |
|---|---|---|
| `open-question` | W3 | A named `OI-nn` or `OQ-nn` holds the expected end state, and the item is open |
| `vendor-call` | W3 | The owning module plan is not `approved` and is held pending the Rithmic vendor call |
| `outside-loader-boundary` | W1 | The code the assertion runs against **exists** and lives outside `@merit/rules-engine` |
| `no-plan-record-value` | W2 | The expectation needs a configuration value **no plan document states**, so writing it would invent one, which `TR-01` forbids |
| `format-cannot-express` | W2 | A fixture format exists for the owning module and cannot state this input or this expectation |
| `no-fixture-format` | W2 | **No fixture format exists for the owning module at all** |

**`no-module-code` was offered by the plan and is deliberately NOT in the vocabulary.** For the 229 rows it would have covered, the module's code being absent is true and is not the binding half: the fixture format is `packages/rules-engine/fixtures/GS-NNN-*.yaml`, a day stream folded through the engine, M1-shaped in every field, so **a module whose code landed tomorrow would still have nowhere to write**. A vocabulary term that names the half which clears first would turn the table back into the queue this entry exists to stop.

**When more than one condition fails, the row carries the blocker that WOULD STILL HOLD IF EVERY OTHER WERE CLEARED.** That is the rule, it is checkable per row, and it is the property that makes the column a queue: a blocker naming something that can be cleared while the row stays unwritable is a promise the table cannot keep.

**A BLOCKER WITH NO CITATION IS THE FINDING.** Every blocked row carries a citation that supports its blocker, naming the file and the fact. A row whose reason cannot be cited is not a blocked row; it is a row nobody has looked at, and the two have been indistinguishable for 276 rows.

**The artifact is [section 39](../testing/golden-scenarios/39-fixture-status-and-blockers.md)**, one table, 316 rows, in numeric order, with a status on every row and a blocker and a citation on every row that has no fixture.

### 3. The plan's partition, checked rather than copied, and it does not hold

**Two of its five counts agree and three do not.** The table derives them; the derivation is section 39 and the commands are in the pull request.

| WAVE-04 section 2 | Section 39 derives | |
|---|---|---|
| 40 written | **40** | agrees, and both were checked by listing the directory |
| **16 writable today** | **2** | **does not agree.** `GS-059` and `GS-080` |
| 14 needing one ruling | **31 M1 rows blocked**, of which 22 are `format-cannot-express` | does not agree |
| 3 held on an open question | **2**, `GS-004` and `GS-031` on `OI-16` | does not agree |
| 243 with no code | **243**, as 14 `vendor-call` and 229 `no-fixture-format` | agrees on the count, and names the format rather than the code as the binding half |

**The fourteen that moved are all one mistake and it is W1 against W2.** The plan reaches its sixteen by finding the code: *"`R-43` and `R-44` are declared and live in `payout/clamp.ts`"*, *"`R-46` to `R-50` are declared and live in `payout/settle.ts`"*, *"`advanceDay` is the fold `CI-03` runs."* **Every one of those is true, and every one of them is a W1 finding on rows that fail W2.** The golden stage folds `advanceDay` and diffs a `RuleState`; `approved_cents`, `clamp_reason`, `trader_cents` and `firm_cents` live on `PayoutEvaluation`, which no fixture in this format ever sees. `GS-026` to `GS-029` and `GS-241` pin exactly those fields. `GS-047` needs one day applied twice and `L-10` refuses it. `GS-035` needs a clock and `INV-01` forbids one. `GS-079` needs a `daily_loss_limit` all three plan records carry as `null`.

**This is not a correction of a careless plan.** WAVE-04 section 2 states the governing sentence correctly and in bold: *"the M1 backlog is bounded by W2 and W3, not by W1."* It then partitions on W1. **A condition stated and not used is the failure mode this entry's three-condition form is meant to remove**, which is the strongest argument available that the form is worth having.

### 4. Section 33.3's row, and what it answers

**Settled here because it is a reading of a frozen document rather than an edit to one.** [Section 33.3](../testing/golden-scenarios/33-ownership-index-and-coverage-reconciliation.md) rows *"Section 5.2's minimum of 40 golden files | <!--gen:gs_count-->316<!--/gen--> defined | yes."*

**The row answers a different question from the one its own label asks.** Every other row of 33.3 maps a **source battery** to the scenarios that carry it, and its `Complete` cell answers *"did this battery land in the registry?"* The 40-golden-files row is not a battery. **It is a floor on ARTIFACTS**, and the cell answers the registry-completeness question the other rows ask, which is the wrong one for it.

**The constitution's minimum is on FILES, and it is met on files.** [Section 5.2](../../MERIT_BUILD_MASTER_PROMPT.md) reads *"hand-built scenario fixtures (>=40) ... Stored as YAML -> expected end-state JSON. CI runs all."* A scenario that is defined and unwritten is not stored as YAML and CI does not run it. **40 `.yaml` and 40 `.expected.json` are on disk, so the minimum is met exactly, with zero margin, on the count that is not in the cell.**

**The definitions count does not bear on it in either direction.** 316 is the registry, it exceeds 40 for reasons that have nothing to do with fixtures being written, and **the row would read `yes` at four files.** The cell is true and it is not evidence. **Section 39 is where the number that would fail is now visible**, and the 40 is one written row away from being a claim the corpus can no longer make.

- **Alternatives considered:**

  - **Leave the reason in prose, which is what 33.4 does.** Rejected, and the rejection is the entry. Prose scales to three absences and stops there: 33.4 covers 3 of 276, [`fixtures/README`](../../packages/rules-engine/fixtures/README.md)'s held-back table covers M1 and is stale in four rows, and neither is queryable. **A reason that cannot be listed cannot be counted, and a backlog that cannot be counted gets quoted at its subtraction**, which is 276 and is wrong by every measure this entry took.
  - **An open vocabulary, one phrase per row.** Rejected. It is prose with a column's punctuation: no two rows would agree on wording, and the count by blocker, which is the number that tells a wave what to schedule, could not be taken at all.
  - **Record only the M1 rows, since every fixture on disk is M1's.** Rejected. The 243 are the majority of the claim and their blocker is the one most often misread: naming `no-fixture-format` on all 229 is what stops a future wave queueing 229 fixture sessions for work that has no file to go in.
  - **Drop `vendor-call` and fold M2 into `no-fixture-format`.** Considered seriously, because the format objection does survive the vendor call. Rejected on a checkable distinction: **`M02` is the one module plan of twenty-one that is not `approved`**, so its scenarios' expected end states rest on a specification still at `review` under [ADR-005](ADR-005.md). That is a W3 hold and it outranks a W2 one.
  - **Add a term for the multi-account rows (`GS-052`, `GS-062`).** Rejected as over-fitting. The condition that fails is W2 and `format-cannot-express` states it; the citation carries that it is **not fixable by a format change**, because the engine is per account by design.

- **Consequences:**

  - **The three fixture sessions of this wave are queued against rows that are not writable.** `W2` is given six and one of them (`GS-080`) is writable; `W3` is given six and none is; `W4` is given four and one (`GS-059`) is. **Fourteen of the sixteen fail W2 today.** This entry does not rewrite those prompts and does not touch a fixture; it names the collision, and the pull request names it again, because a session that discovers this at its own bench has already spent its context.
  - **The real available work is two fixtures, and the fourteen are rulings.** That is a smaller wave and a truer one. `format-cannot-express` at 22 M1 rows is the largest single queue in the corpus and it is one question asked twenty-two times: **what does a fixture look like when the assertion is not one account's end state?**
  - **`CI-06/fixture-inventory` gets a subject.** [WAVE-04 section 6](../plans/WAVE-04-fixture-backlog-and-gate-inventory.md) reserves the slug for `W8`. Section 39's table is what such a gate reads: status against the directory, and a citation on every blocked row. **This entry does not write that gate.**
  - **Section 33.3's row is not edited**, because 33 is outside this session's fence and the reading is recorded here instead. **The row stays true and stays uninformative**, and section 39 carries the number that moves.
  - **The status column dates.** A fixture landing turns a `writable` row `written`, and a lifted `L-nn` turns a `blocked` row `writable` with nothing to warn a reader. That is the argument for the gate rather than against the table, and it is why every blocked row cites a file a gate can read rather than a session that once looked.

- **Founder approval: GRANTED 2026-08-21.** Given as an **explicit delegated approval**, not as a line-by-line read; [E2](../../MERIT_BUILD_MASTER_PROMPT.md) reserves that read for the money path and this entry is not on it.

  **The clause this entry asked to be read before signing has since been TESTED, which is why it is signed rather than argued.** Consequence 1 predicted, per session, which of the sixteen queued fixtures were writable: `W2` one of six (`GS-080`), `W3` none of six, `W4` one of four (`GS-059`). All three sessions ran. **`W2` wrote exactly `GS-080`. `W3` wrote nothing. Both are exact.**

  **`W4` is where the ruling was wrong, and it was wrong in the safe direction.** It wrote `GS-059` **and `GS-049`**, two of four against one predicted, so *"fourteen of the sixteen fail `W2` today"* is really thirteen. **A ruling that stops a wave was off by one fixture, and the error left MORE work available rather than less.** The cost the approval clause named, *"a wave stopped for nothing"*, did not occur: fifteen of the sixteen rows behaved as ruled, and the wave that replaced the fixture queue produced [ADR-073](ADR-073.md), [ADR-074](ADR-074.md) and three `CI-06` gates.

  **Two things this signature does not settle**, both already in flight. Section 39's table has drifted against the directory: `CI-06/fixture-inventory`'s first run found **43 `.yaml` on disk against 40 `written` rows**, with `GS-049`'s row still reading `blocked / format-cannot-express` for a fixture that exists. That is `X2`'s repair, and the gate has those rows REGISTERED rather than exempted. And the counts in section 3 date from before those three fixtures landed: **they are the reading of 2026-08-20 and the table is the live record**, which is the argument section 5's last consequence already makes against itself.
