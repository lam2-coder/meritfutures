## ADR-216: `rule_states.phase` moves onto `account_phase`, and the argument against a `CHECK` is a copy count nobody had taken  (2026-08-29, status: proposed)

**The defect was live in the merged schema and it is closed by [`0067`](../../packages/db/migrations/0067_rule_state_phase_vocabulary.sql).** [`0001:45`](../../packages/db/migrations/0001_extensions_and_enums.sql) declares `account_phase` as **exactly** the engine's four `Phase` members, and it did so before any other table in this estate existed. **[Session 398](../sessions/2026-08-29-session-398.md) found this and reported it rather than taking it**, under [ADR-003](ADR-003.md), and said in terms that it is cheaper before rows land than after. It was right about the price, and section 4 measures which way the price runs, because it is not symmetric between the two candidate answers.

### 1. What the column is for, and why `text` was never neutral here

`rule_states` is one row per account per trading day and it is what the nightly replay audit compares a recomputed state against. `RuleState.phase` is typed `Phase` at [`types.ts:920`](../../packages/rules-engine/src/types.ts), a closed union of four declared at [`types.ts:787`](../../packages/rules-engine/src/types.ts). `phase` is **input 3** of `ADR-026` `C-07`'s nineteen hash inputs, which is stated in `0015`'s own header at [`0015:144`](../../packages/db/migrations/0015_rule_states.sql).

**A column that admits any string on the table replay compares against is not a cosmetic gap.** A phase that differs from the engine's by a letter hashes differently, so it makes replay diverge on an account whose state was never wrong, and the divergence names a column rather than a rule. `0067` closes it before the first row rather than after, which is the same argument [ADR-047](ADR-047.md) makes from the other direction about the cost of a hash change once rows accumulate.

### 2. What `rule_states` and `account_phase` actually carried, measured live

`0001` through `0066` applied forward-only into an empty database under `ON_ERROR_STOP=1` on **PostgreSQL 16.13**, read at `pg_attribute`, `pg_constraint`, `pg_enum` and `pg_type` rather than by grep:

```
rule_states.phase                                text, NOT NULL
constraints on rule_states naming phase          0
rule_states rows                                 0
account_phase labels, in enumsortorder           eval, funded, closed, graduated
table columns of type account_phase              accounts.phase, and that is all
enum types in schema public                      13, every one created in 0001
```

**Both halves of the reservation hold and one of them is stronger than it was written.** `account_phase` is not merely a superset the engine happens to fit inside: it is the engine union member for member **and in the same order**, which matters because an enum's declaration order is its sort order.

**THE TABLE HOLDS ZERO ROWS AND NO WRITER EXISTS.** `B5` term 1, a `writeRuleState` implementation, is still owed. That is what makes `0067` free today and it is checked rather than assumed (section 5).

**AND READING THE ROWS FOUND THE GAP WIDER THAN THE RESERVATION SAID.** [`0007:192-193`](../../packages/db/migrations/0007_accounts.sql) declares `account_status_history.from_phase` and `to_phase` as bare `text NULL` with no `CHECK`, beside `from_status` and `to_status` which are bare `text` against `account_status`, on a table whose parent `accounts` is declared against both types. That is `0007`'s and is registered in section 8 rather than repaired.

### 4. THE TYPE THAT ALREADY EXISTS, NOT A `CHECK`, AND THIS IS NOT `ADR-207`'S CONCLUSION COPIED

[ADR-207](ADR-207.md) section 4 chose a `CHECK` over a new `ENUM` for `breach_kind` on three measured reasons. **The reservation asked which transfer. Two of the three do not survive the move, and the third survives as a fact and dies as a reason.**

**REASON 1 -- "every one of the thirteen is created in `0001` and no migration since has added one" -- DOES NOT TRANSFER.** It is a reason against **CREATING** a type, and what made it decisive for `breach_kind` is that an enum there would have been the first new estate vocabulary and therefore a ruling nobody had taken. `account_phase` already exists. Measured: **13 enum types before `0067` and 13 after, 65 labels before and 65 after.** Nobody has to rule where new vocabularies live, because no vocabulary is created. **Adding no new type is not the same as using an existing one**, and reason 1 speaks only to the first.

**REASON 2 -- "this table already stores an engine union as bare `text` (`phase`), so an enum for `breach_kind` would make the table internally inconsistent" -- INVERTS, BECAUSE ITS PREMISE IS THE DEFECT THIS ENTRY REPAIRS.** `ADR-207` wrote that reason while `rule_states.phase` was unconstrained, and it is `rule_states.phase` being unconstrained that this slice exists to end. **A reason that cites a gap as its justification cannot survive the gap's repair with its sign unchanged.** What survives is the requirement underneath it -- the table should not hold one engine union as a type and another as bare text -- and section 7 states honestly that `0067` leaves that requirement unsatisfied in the other direction, rather than pretending it does not.

**REASON 3 -- "a `CHECK` narrows by `DROP` and re-`ADD` under one name, which is `E2`'s own mechanism, while an enum value can be added and can never be removed" -- TRANSFERS AS A FACT AND FAILS AS A REASON HERE.** Both halves were executed rather than recalled, on 16.13:

```
ALTER TYPE account_phase DROP VALUE 'graduated';
  ERROR:  syntax error at or near "VALUE"

BEGIN; ALTER TYPE account_phase ADD VALUE 'probationary';
       SELECT 'probationary'::account_phase;
  ERROR:  unsafe use of new value "probationary" of enum type account_phase

BEGIN; ALTER TABLE rule_states ADD CONSTRAINT tmp_c CHECK (...);
       ALTER TABLE rule_states DROP CONSTRAINT tmp_c;
       ALTER TABLE rule_states ADD CONSTRAINT tmp_c CHECK (...);
  ALTER TABLE / ALTER TABLE / ALTER TABLE
```

**The fact is stronger than `ADR-207` states it.** `DROP VALUE` is a **syntax error** and not a permission failure: the grammar has no such production, so there is no privilege that would make it work. And widening costs two migrations in an estate where one file is one transaction, because a value added inside a transaction cannot be used in it.

**IT FAILS AS A REASON BECAUSE BOTH COSTS ARE ALREADY BORNE.** `accounts.phase` has been `account_phase` since `0001`. If the engine ever removes a `Phase` member, `account_phase` must be recreated and `accounts.phase` rewritten **whether or not `rule_states.phase` ever joined it**; if the engine adds one, the two-migration dance is owed already. **`rule_states.phase` joining adds ONE MORE COLUMN to a rewrite that has to happen anyway, and does not add the rewrite.** The marginal irreversibility is zero. **That is what `breach_kind` had no counterpart to**, and it is exactly the asymmetry the reservation said the answer is not automatic about.

**AND A `CHECK` BUYS A NARROWABILITY THAT IS NOT A BENEFIT HERE.** It would let `rule_states.phase` narrow **independently of `accounts.phase`**. Two columns holding the same engine union, free to move apart, is not a feature; it is the drift this migration exists to stop.

#### THE REASON `ADR-207` COULD NOT REACH: THE COPY COUNT

`Phase`'s four members are written out **literally six times** in this repository, with **no comparator between any two of them**:

| # | Site |
|---|---|
| 1 | [`packages/rules-engine/src/types.ts:787`](../../packages/rules-engine/src/types.ts) -- `export type Phase` |
| 2 | [`0001_extensions_and_enums.sql:45`](../../packages/db/migrations/0001_extensions_and_enums.sql) -- `CREATE TYPE account_phase` |
| 3 | [`packages/db/src/schema.ts:163`](../../packages/db/src/schema.ts) -- `pgEnum('account_phase', ...)` |

| 5 | `apps/api/src/routes/accounts.ts:748` -- `const PHASES` |
| 6 | `apps/portal/src/api/types.ts:123` -- an inline union |

**`breach_kind` had TWO copies and `ADR-207` paid for the second with a comparator, calling the copy `FM-16` and saying this corpus has found it four times. A `CHECK` here would have been a SEVENTH copy of four members that already have six and none.**

`ALTER COLUMN ... TYPE account_phase` writes the type's **NAME** and not its members. **So this column's vocabulary is copy 2 by construction rather than by assertion, and there is nothing new for a comparator to defend.** That is not an aesthetic preference. It is the difference between a fact stated once and a fact stated twice, and this corpus has a name for the second.

**WHAT THIS ENTRY PAYS INSTEAD.** [`rule-state-phase-vocabulary.test.ts`](../../packages/db/test/rule-state-phase-vocabulary.test.ts) binds copies 1, 2 and 3 -- which nothing did before today -- deriving all three and carrying none, comparing member for member **and in order**, and throwing rather than passing vacuously if any parse returns nothing. Copies 4, 5 and 6 are in `apps/**` and are reported (section 8).

#### AND THE PRICE OF DEFERRING IS NOT SYMMETRIC

A `CHECK` added after rows land can be added `NOT VALID` and validated later without an exclusive-lock rewrite. **A column type change cannot**: `ALTER COLUMN ... TYPE` takes `ACCESS EXCLUSIVE` and rewrites the whole table. **So the answer this entry takes is precisely the one whose price rises fastest, and it is taken on the day the table holds zero rows.** Session 398's "cheaper before rows land than after" is true of both answers and *much* truer of this one.

### 6. THE FOLD'S THIRD MEMBER, WHICH THE SUITE DEMANDED BEFORE THE MIGRATION WAS BELIEVED

**`packages/db/test/scoped-db.test.ts` went RED on this migration, and the control that did it says in its own comment that this was its purpose.** `ADR-094` and [ADR-103](ADR-103.md) close the fold's `ALTER COLUMN` sub-vocabulary at ONE shape, `DROP NOT NULL`, with a default of FAIL, on `ADR-094` item 3's rule against writing a rule for a shape with zero instances. Its inventory assertion reads:

> *"The day a fourth one lands -- a `SET DATA TYPE`, a `SET NOT NULL`, or a `DROP NOT NULL` on a third table -- this is RED and the next session reads the ruling before writing a regex."*

**`0067` is that day and this is that session, and the ruling was read before the regex was written.**

**CLAUSE 5 OF THIS ENTRY ADDS THE FOLD'S THIRD MEMBER, THE WAY `ADR-103` ADDED ITS SECOND: THE COMPARISON FIRST, THE VOCABULARY SECOND.** `retypedColumns` reads `ALTER COLUMN <name> TYPE` and its synonym `SET DATA TYPE` as one member, requires **every** top-level clause to match, requires the type to look like a type, and returns `null` on anything else. `withType` applies it to the folded definition and **throws on the two ways of applying nothing** -- a definition whose own type reads empty, and a retype to the type the column already has -- on `withoutNotNull`'s own argument that a fold applying nothing agrees with a transcription it never checked. `SET NOT NULL`, `SET DEFAULT` and `DROP DEFAULT` still have zero instances and stay refused.

**A NEW ASSERTION HOLDS THAT EXACTLY ONE OF THE TWO READERS CLAIMS EACH STATEMENT.** A reader widened until it matched everything would satisfy the inventory assertion while folding `DROP NOT NULL` as a retype to the type `NULL`, and every comparison downstream would then read a definition nobody wrote. Seed 11 is that case, watched failing.

**THE ALTERNATIVE WAS TO LET A TEST PICK THE SCHEMA.** A `CHECK` needs no fold change, because `ADD CONSTRAINT` touches no column. **Refusing the type change on that ground would have been choosing the weaker schema guarantee to avoid extending a parser, which is weakening a gate to pass it in the exact shape [`DISPATCH_PROTOCOL`](../DISPATCH_PROTOCOL.md) section 3 names.** The vocabulary was closed because there had been nothing to rule on. The moment there is an instance, a rule for it is written against something, which is `ADR-094` item 3 satisfied rather than circumvented.

**AND THIS MEMBER RUNS ON A REGISTERED TABLE ON THE DAY IT LANDS, WHICH `ADR-103`'S DID NOT.** That member shipped with no registered carrier -- `otp_challenges` and `trading_calendar` were the only two and neither was registered -- and session 214 had to find the gap for `ADR-106` to close. `rule_states` has been registered since `ADR-094`, so the per-table TYPE-and-NULLABILITY comparison reads this column against the transcription immediately, with no second entry needed.
