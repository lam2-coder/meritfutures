### 2. THE RULING

**Clause 1. AN UNWIRED SESSION SOURCE RESOLVES TO `unknown` AND NEVER THROWS.** `adminHandler` asks whether a source is installed before it asks a source anything, so a caller presenting a cookie to a deployment that recognises no token is answered **401 `unauthenticated`**, identically to a caller presenting nothing. The ground is [ADR-192](ADR-192.md) clause 2's, unaltered: **a deployment that cannot authenticate anyone has authenticated nobody**, which is true of every caller and discloses nothing. `unknown` is not a convenience value; it is the only lookup such a deployment can honestly make, and it is the arm an unrecognised token already took.

**Clause 2. AN UNWIRED READ SOURCE ANSWERS 503, BEHIND THE AUTHORIZATION AND NEVER IN FRONT OF IT.** The refusal is reached only after `authorizeAdmin` returned `allowed`, so the caller reading it is an authenticated operator holding a role the endpoint admits, and telling them their own console's read port is uncomposed discloses nothing to anybody not entitled to know it. `service_unavailable` is built as a **handler code** at the call site, exactly as `admin-writes.ts`, `admin-wallet.ts`, `admin-payouts.ts` and `admin-certificates.ts` build it. **`server.ts` is byte for byte unchanged**, which is [ADR-192](ADR-192.md) clause 4 kept rather than reopened.

**Clause 3. THIS CLOSES [ADR-190](ADR-190.md) ITEM 2 FOR `admin-reads.ts`, WHICH IS WHERE [ADR-192](ADR-192.md) LEFT IT OPEN.** That item registered one class carrying two facts with one status between them. [ADR-192](ADR-192.md) section 3 recorded in terms that it _"remains open for `admin-reads.ts` alone, where the mixing is"_. **The two wiring sites leave `AdminReadError` and no fifth class is minted**: derived at the moment of reporting, that class has **20** throw sites in this module and **0** of them are about wiring, where before this entry it had 22 of which 2 were. Its 500 is now right for every site it has.

**Clause 4. NO `OperatorAssertionVerifier` IS WRITTEN, AND THE REASON IS NOT DEFERRAL.** Section 3.

**Clause 5. `readLiability` AND `exportEvidence` ARE LEFT OWED**, in those words, and the route's refusal is explicit. Section 4.

**Clause 7. THE VERIFIER SLICE AS THE DISPATCHER DESCRIBED IT IS ALREADY LANDED, AND WHAT IS OWED IS ITS CALLER.** The decision offered a test: *"if that slice is writable without the identity-provider purchase, it is genuinely yours"*, and named it as `refusingAssertionVerifier` answering `unconfigured` when any of the three variables is absent, `unconfigured` being a 503 rather than a silent pass. **THAT FUNCTION EXISTS, IN FULL, AND HAS SINCE `ADR-237`.** [`operator-identity.ts:212`](../../apps/api/src/operator-identity.ts) returns `unconfigured` naming exactly which variables are missing and `unavailable` when all three are set, so **neither arm can be made to pass by an environment file**, and [`test/operator-identity.test.ts`](../../apps/api/test/operator-identity.test.ts) exercises both. **So there is no slice to write there.** What is missing is the half the decision's own test excludes: a verifier that actually checks an assertion, which requires the assertion format, which is the purchase. **It is NAMED OWED WITH ITS BLOCKER** (section 3, five items, item 5 being the one that cannot be inferred), and the second thing owed is smaller and worth naming separately: **nothing turns `unconfigured` into a 503, because nothing calls the verifier at all.** `refusingAssertionVerifier` and `operatorFromAssertion` have **zero callers** outside their own suite, derived at the moment of reporting. The caller is a login route minting an `operator_sessions` row, and it needs a verified assertion first.

**Clause 6. NO AUTHORIZATION REQUIREMENT IS RELAXED AND NO GATE IS WEAKENED.** `authorizeAdmin` and `resolveAdminRole` are untouched. Every caller refused before this entry is refused after it. What changed is which refusal, never whether one happens. **Five test cases moved and not one was skipped, disabled or deleted**; each is amended in place with the claim it replaced quoted beside it under `RI-14`, and three cases were added.

### 3. Clause 4, and what an `OperatorAssertionVerifier` would actually have to verify

**THE ROW ASKED FOR THIS TO BE ARGUED RATHER THAN ASSUMED, AND THE ARGUMENT IS THAT THE CORPUS HAS ALREADY ANSWERED IT AND THE ANSWER IS A PURCHASE ORDER.** Read off the primary sources rather than reasoned toward:

| Source                                                            | What it commits to                                                                                                                                        |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`SECURITY`](../architecture/SECURITY.md) C-08                    | _"RBAC on admin, admin on a separate origin, IP allowlist, hardware-key SSO"_, and the row itself now says the SSO half _"is OWED and the seam is named"_ |
| [`SECURITY`](../architecture/SECURITY.md) threat row S            | _"Phished admin credential"_ is controlled by **hardware-key SSO (phishing-resistant)** and by nothing else                                               |
| [`API_CONTRACT`](../architecture/API_CONTRACT.md) section 8       | the role set is **closed** at `owner`, `ops`, `readonly`                                                                                                  |
| [`operator-identity.ts`](../../apps/api/src/operator-identity.ts) | three variables named and never valued, and `refusingAssertionVerifier` failing closed in both arms                                                       |

**SO A VERIFIER THAT SATISFIED THIS REPOSITORY WOULD HAVE TO ESTABLISH FIVE THINGS**, and they are written out because the fifth is the one a plausible implementation silently drops:

1. the assertion is signed by a key currently published at `MERIT_ADMIN_IDP_JWKS_URL`;
2. its issuer is exactly `MERIT_ADMIN_IDP_ISSUER`, because an assertion from another provider is another provider's;
3. its audience is exactly `MERIT_ADMIN_IDP_AUDIENCE`, because an assertion the same provider minted for a different relying party is the confused-deputy shape and needs no attacker inside Merit;
4. it is unexpired, and its `assertionId` has not been seen before, which is what `operator_sessions.idp_assertion_id` exists to hold;
5. **the authentication behind it was actually phishing-resistant**, evidenced by a claim the provider asserts, and not assumed from the fact that a provider was configured.

**ITEM 5 IS WHY THIS IS NOT A SMALL FUNCTION AND IS NOT WRITEABLE HERE.** Items 1 to 4 are a JWT library and a cache. Item 5 is the entire content of C-08: a verifier that checks 1 to 4 and skips 5 **passes every test anybody would write for it and satisfies none of the control**, because the threat model's answer to a phished admin credential is the hardware key and not the signature over it. Which claim carries that evidence, and what values of it count, is a fact about the provider Merit buys. **It cannot be derived, defaulted, or guessed, and a guess would be indistinguishable from a correct implementation until the day it mattered.**

**AND ITEM 4 HAS A SECOND BLOCKER THAT IS NOT THE PROVIDER.** A verified assertion becomes a session by writing an `operator_sessions` row, and **nothing in this repository can write one**. Merit is passwordless by [ADR-039](ADR-039.md), `0002:280` states it in the schema, and [ADR-237](ADR-237.md) section 8 ruled that building a session source over an empty table would answer every real operator 401 on a door that is not shut against them.

**THIS ENTRY DOES NOT DISTURB THAT RULING AND IS NOT AN EXCEPTION TO IT.** [ADR-237](ADR-237.md) refused to make the route **look live**. Clause 1 makes an unwired deployment answer the refusal it was already giving to the caller who sent nothing. **Nothing is wired, nothing looks live, and one number changes.**

**WHAT IS LEFT OWED, NAMED SO THE NEXT SLICE INHERITS A LIST AND NOT A FEELING:** the identity-provider purchase; an `OperatorAssertionVerifier` implementing items 1 to 5 against it; a directory write that provisions an `operators` row; a login route that turns a `verified` assertion into an `operator_sessions` row; and the `systemDb('operator-console')` door.

**THIS PARAGRAPH ENDED WITH A CLAUSE THAT IS WRONG AND IT IS CORRECTED HERE RATHER THAN QUIETLY DROPPED (`RI-14`).** It read: _"and the `systemDb('operator-console')` door, which [ADR-171](ADR-171.md) section 9 makes takeable at that point and not before"_, written as though the door were owed by all five items alike. **THE DOOR IS OWED BY THE READ SOURCE AND IS NOT OWED BY THE SESSION SOURCE**, and the discriminator is the scope registry rather than a judgement. `operators` and `operatorSessions` are both **class `firm`** ([`scope.ts:1596`](../../packages/db/src/scope.ts), [`:1600`](../../packages/db/src/scope.ts)), so both are members of `FirmTableKey` and **`ApiDb.firm()` reaches them today**, with no new door, no `SystemReason`, and nothing for [ADR-171](ADR-171.md) clause 1 to refuse. `AdminSessionSource.lookup` reads exactly those two relations and `resolveOperatorSession` is already its verdict, written and tested. **The read source is the one that needs the door**, because `AdminSourceTx` spans accounts, events, flags, the identity graph and search, and those are `owned` keys the firm door refuses by construction.

**SO A DATABASE-BACKED `AdminSessionSource` IS BUILDABLE TODAY AND IS STILL REFUSED, ON A NARROWER GROUND THAN THE ONE THIS ENTRY FIRST GAVE.** It is not blocked; it is declined. Nothing can write an `operator_sessions` row, so it would answer `unknown` to every token, which is **byte for byte what clause 1 now answers with nothing installed at all**. [ADR-237](ADR-237.md) section 8 refused it because the 401 would misreport an unfinished deployment, and clause 1 has since made that 401 the answer either way, so **that objection is spent and a new one has to carry the refusal or it falls**. It does: wiring it buys **no observable change** and costs a real transaction against `operators` and `operator_sessions` **on every unauthenticated probe of the admin surface**, which is a database round trip an anonymous caller gets to schedule. It would also move the wiring triple to `wired: 11` and report as progress a port whose table cannot be filled. **A ROW THAT WIRES IT SHOULD SAY WHICH OF THOSE TWO IT IS BUYING**, because it is not buying a working console.

### 4. Clause 5, and why a partial liability figure is worse than a refusal

**THE ROW ASKED WHETHER TO COMPOSE `readLiability` AND `exportEvidence` HERE, AND THE ANSWER IS NO, AND THEY ARE LEFT OWED.** Saying it in those words is the row's own requirement and it is met here rather than paraphrased.

**THE FIRST REASON IS THE ONE THE ROW NAMED AND IT IS SUFFICIENT.** A liability figure that quietly returns part of its leaf paths is a number an operator acts on, and no field of the wire type can carry the fact that it is partial: `EligibleNext7d` declares `total_cents`, `account_count` and `by_day[]` and **not one measured term**. **A number that is silently incomplete is worse than an honest refusal on a screen whose purpose is to size an obligation.**

**THE SECOND REASON MAKES THE FIRST MOOT AND IS WHY THIS IS A REFUSAL RATHER THAN A DEFERRAL.** Composing anything onto `AdminReadSource` requires an `AdminSourceBackend`, whose one method yields an `AdminSourceTx`, for which `systemDb('operator-console')` is the only supplier in the accessor. `ApiDb` declares **five** doors (`scoped`, `firm`, `resolution`, `establishment`, `publicLookup`) and none of them is it, [ADR-171](ADR-171.md) clause 1 refuses to add it, and section 9 conditions it on the `AdminSessionSource` section 3 just refused. **The composition is not being declined on taste; there is nothing to compose it onto.**

**AND OPENING THE DOOR ANYWAY WAS CONSIDERED AND IS REFUSED WITH THE ARGUMENT.** It is mechanical, it would typecheck, and it would move the wiring triple. It would also publish a live system handle reaching every account in the database, inside a deployable where **no operator can authenticate**, in exchange for zero observable behaviour. **That is a security regression bought with wiring theatre**, and a triple that moved would report it as progress.

**ONE CORRECTION THE REFUSAL DOES NOT EXCUSE.** The row said `readEvidence` is _"likewise uncomposed"_. **The port method is `exportEvidence`, and it IS composed**: `adminReadSourceParts` supplies it from `createEvidenceExporter`. What is missing is the **install**, which is the same door. So the port stands at **six of seven methods with producers** and not five, and `readLiability` is the one name missing from `IMPLEMENTED_ADMIN_READS` and from the parts.
