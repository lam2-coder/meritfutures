## ADR-198: a `_cents` value inside `events.payload` is a DECIMAL STRING  (2026-08-28, status: proposed)

**[Session 366](../sessions/2026-08-28-session-366.md) wrote the first real `events` row this system has ever recorded and found that three of the eight names it can produce fail at the DRIVER**, with `TypeError: Do not know how to serialize a BigInt`. `events.payload` is [`jsonb NOT NULL`](../../packages/db/migrations/0017_events_and_audit.sql) at `0017:50`, drizzle's jsonb mapping is `JSON.stringify`, and `JSON.stringify` refuses a `bigint` outright; meanwhile [`assertPayloadRules`](../../apps/api/src/events.ts) REFUSES a `_cents` value that is not a `bigint`, because [`Cents`](../../packages/rules-engine/src/types.ts) is `bigint` at `types.ts:38` and a `number` reaching a financial path may already have lost digits. **Each rule is correct alone and their conjunction is empty**, so every money payload in the catalogue is unwritable and **33 of the 102 readable catalogue rows carry a `_cents` field**. **This entry gives the format the writer has been refusing for want of.**

- **Origin:** [ALLOCATION](ALLOCATION.md) row `198`, session **370**, dispatched as `claude/event-payload-serialisation`. The reservation is amended in place under [ADR-065](ADR-065.md) T3. **`ADR-198` was RESERVED BEFORE DISPATCH** and no number was chosen here.

- **MONEY PATH.** This format is what every `_cents` value this system will ever record looks like in the column that is append-only and retained forever. **NO MIGRATION IS TAKEN AND NONE WAS RESERVED**: `jsonb` already holds whatever this entry chooses, and changing the column type would edit a merged migration, which constitution `E2` forbids absolutely. No `SystemReason` member, no `SqlExecutorReason` member, no `pg` import, no cast past a key type, no ledger account named, no door widened, no gate weakened.

- **THE ENTRY SHIPS `proposed` WITH AN UNSIGNED APPROVAL LINE.** What is **derived** is the collision, the four counts in section 2, the precedent census in section 6, and the magnitude arithmetic in section 3. What is **judged** is clause 1 itself -- decimal string over the three alternatives -- and section 5's refusal to extend the conditional encoding this tree already implements one deployable over. Section 12 is that question.

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim below was read at its own file. **One of the dispatch's premises did not survive and it is section 6**, and a second count in a file inside this fence was found off by one and repaired, which is section 11.

### 1. THE RULING

> **1. A `_cents` FIELD IN AN `events.payload` IS A JSON STRING HOLDING THE DECIMAL INTEGER NUMBER OF CENTS.** Not a JSON number. The canonical form is an optional leading `-`, then either `0` or a nonzero digit followed by any digits: `/^(0|-?[1-9][0-9]*)$/`. No `+`, no leading zeros, no `-0`, no decimal point, no exponent, no thousands separator, no whitespace, and never the empty string. `"150000"` is a hundred and fifty thousand cents. **The format is EXACT over every integer and has no ceiling.**
>
> **2. `null` STAYS `null`.** A `_cents` field the catalogue marks optional and a producer leaves empty reaches the column as JSON `null` and not as `"0"` or `""`. `assertPayloadRules` already admits a null `_cents`, and encoding an absence as a number would make "no figure" and "zero cents" the same row forever.
>
> **3. THE ENCODING HAPPENS AT THE WRITER AND THE DOMAIN FORM STAYS `bigint` UP TO IT.** `assertPayloadRules` is UNTOUCHED and still refuses a `_cents` value that is not a `bigint`, so a producer hands the sink `bigint` cents exactly as it does today and the string exists only from the moment the row becomes storage. Section 7 is why this is the writer's and not `buildEvent`'s.
>
> **4. THE INVERSE IS `BigInt(s)` AND THE CORPUS HOLDS EXACTLY ONE IMPLEMENTATION OF EACH DIRECTION.** [`centsToPayload`](../../apps/api/src/events.ts) and [`centsFromPayload`](../../apps/api/src/events.ts) in `apps/api/src/events.ts`. A reader that spells its own parse is a second implementation of a format in a forever-retained column, which is the defect [ADR-159](ADR-159.md) clause 1 refuses one level up.
>
> **5. `_bp` IS UNCHANGED AND STAYS A JSON INTEGER.** [`BasisPoints`](../../packages/rules-engine/src/types.ts) is `number`, `assertPayloadRules` already requires a safe integer, and a ratio in basis points has no magnitude problem. **This entry rules on `_cents` and on nothing else in the payload.**
>
> **6. A `bigint` REACHING THE WRITER UNDER A KEY THAT DOES NOT END `_cents` IS STILL REFUSED.** [EVENTS](../architecture/EVENTS.md) section 1 declares a format for `_cents` fields and declares none for anything else, so a `bigint` anywhere else in a payload is a field whose wire shape no document states, and the writer says so by path instead of inventing one. The refusal survives this entry; what changes is its subject and its message.
>
> **7. NO UPPER BOUND IS IMPOSED ON THE VALUE.** A decimal string is lossless over every integer, so a bound would refuse a value the system had already computed and would LOSE THE EVENT rather than lose the digits, on `assertTenanted`'s reasoning that a refusal inside the caller's transaction rolls the fact back with it. The one existing bound in this tree, [`centsToJson`](../../apps/api/src/routes/catalog.ts) at `catalog.ts:515`, is the HTTP wire's and exists because the format there is a JSON integer; it is not this entry's and is not extended to this column.
>
> **8. `schema_version` DOES NOT MOVE AND STAYS `1`.** EVENTS section 1 keeps two shapes readable forever "because consumers include a 2031 audit reading a 2027 row". **That rule protects readers of rows that EXIST, and no row of any of the 33 money names has ever been written**: all three of the money names this tree can produce fail at the driver today, measured live and re-derived in section 10. There is no earlier shape, so there is nothing to keep readable.

### 3. Why a JSON number loses, and the magnitude argument is NOT the reason

**THE CEILING IS REAL ARITHMETIC AND A THEORETICAL LIMIT, AND SAYING SO IS THE POINT.** `Number.MAX_SAFE_INTEGER` is `9,007,199,254,740,991` cents, which is `$90,071,992,547,409.91`. The largest per-account money figure the corpus parameterises is the payout cap at the largest size, **450,000c** ([`M01:1215`](../plans/M01-rules-engine.md)), and [ADR-024](ADR-024.md) shortened the ladder to **5**, so one account's lifetime payout commitment is bounded near `2,250,000c`. The largest firm-level figure any payload carries is `remaining_ladder_exposure_cents`, defined at [`0009:181`](../../packages/db/migrations/0009_ledger.sql) as `sum((ladder - payouts_settled) * cap)`; reaching 2^53 through it needs on the order of **four billion funded accounts at the largest plan**. **The 2^53 ceiling is therefore theoretical for every figure this system can produce**, [`catalog.ts:515`](../../apps/api/src/routes/catalog.ts) is right that "at 2^53 cents that is ninety trillion dollars and will not happen", and **this entry does not rest on magnitude.**

**WHAT DECIDES IT IS THE TYPE A CONSUMER HOLDS, FOREVER.** `JSON.parse` yields a JavaScript `number` for a JSON number, and a `number` is an IEEE-754 double. So a JSON number would guarantee that **every JavaScript reader of this table holds money as a double**, which is the one type `assertPayloadRules` refuses on the way IN, for the reason it gives. That check is decidable at the writer because the value arrives as a `bigint`; it becomes **undecidable at every reader forever**, because nothing looking at a JSON number can tell a value that is exact from a value that lost digits. A string parses to `bigint` and the check stays decidable at every consumer, including the 2031 audit EVENTS section 1 names. [ADR-104](ADR-104.md) clause 5 already "refuses a `number` for money at runtime as well as at compile time", quoted at [`ADR-158:56`](ADR-158.md), and this is that refusal reaching the one surface it had not yet reached.

**AND PRODUCING THE NUMBER IS ITSELF THE COERCION THE TREE REFUSES.** There is no way to put a `bigint` into `JSON.stringify` output as a number token; it requires `Number(value)` first. That is precisely the cast `assertPayloadRules` declines to accept from a caller because "coercing it would store the loss". A writer performing it on the caller's behalf would be the same coercion moved one file down.

**WHAT A JSON NUMBER WOULD HAVE BOUGHT, stated rather than skipped.** It is the shape [API_CONTRACT section 1](../architecture/API_CONTRACT.md) already states for the HTTP wire at `API_CONTRACT.md:31` -- "`*_cents` are JSON integers. `*_bp` are JSON integers. No floats, no formatted strings" -- so the event feed and the API would have read alike, and Metabase would need no cast. **That is a real cost of this ruling and section 9 carries it.** It does not outweigh a forever-retained column handing every reader the refused type.

### 4. Why a typed envelope loses, priced rather than assumed away

The shape is `"approved_cents": { "unit": "cents", "value": "150000" }`, or the same with a numeric `value`.

**WHAT IT BUYS.** A reader who does not know this corpus's key convention learns the unit from the value itself, and a future unit that is not cents (a foreign currency, a fractional tick) would have somewhere to go without a new key suffix.

**WHAT IT COSTS, and the first cost is the one that decides it.**

1. **THE UNIT IS ALREADY IN THE KEY, so the envelope states one fact twice.** EVENTS section 1 puts "integer cents in `_cents` fields", which is the same declaration the envelope would carry, and **two statements of one fact can disagree**. Nothing on the row would say which wins when a key ending `_cents` carries `{"unit": "bp"}`, and the append-only table cannot be repaired after the first producer spells it wrong. A format whose redundancy has no tiebreak is worse than one with none.
2. **IT RE-SPECIFIES 33 CATALOGUE ROWS TO BUY THAT.** Every payload literal in EVENTS that prints a `_cents` field becomes false, the fenced `jsonc` block at [`EVENTS.md:224`](../architecture/EVENTS.md) included, whose line is `"approved_cents": 150000`. A decimal string changes the same 33 rows' TYPE and leaves their SHAPE intact, which is the smaller edit to a frozen document and the smaller thing for a reader to relearn.
3. **IT IS THE LARGEST OF THE FOUR ON a table retained forever.** Three JSON tokens and two keys per money field, on the row EVENTS calls "the single most audited event in the system", which carries six of them.
4. **A FOREIGN CURRENCY IS NOT THIS CORPUS'S PROBLEM TODAY**, and no document states one. Buying an extension point for a case no corpus row names, at the price of the three costs above, is the trade this entry declines. **If a currency arrives, `_cents` is wrong as a KEY as well as as a value, and the envelope would not have saved the rename.**

### 5. The fourth option, which the dispatch did not name and which this tree already implements

**THE CONDITIONAL ENCODING EXISTS, IN THIS REPOSITORY, OVER A `jsonb` COLUMN, AND IT WAS FOUND BY SEARCHING RATHER THAN GIVEN.** [`asJsonNumber`](../../apps/worker/src/detectors/graph.ts) at `graph.ts:394` converts a `bigint` "to a `number` when it is exactly representable and to a DECIMAL STRING when it is not", over `risk_flags.evidence`, which is the same `jsonb` problem one deployable over. Its header states the same finding this entry states: "a `bigint` CANNOT BE `JSON.stringify`d AND `evidence` IS `jsonb`". **It is exact, it is precedent, and it is the option a session that only read the dispatch would never have priced.**

**IT LOSES ON ONE PROPERTY AND THAT PROPERTY IS DECISIVE FOR THIS COLUMN.**

**THE TYPE VARIES WITH THE VALUE, so the rare branch is the untested branch, and it first runs on the largest figure the system has ever computed.** Section 3's arithmetic says every value this system can actually produce is under 2^53. So a consumer written against real data sees `number` and only ever `number`; the string branch is code that no fixture, no suite and no deployment ever executes, and the day it does execute is the day a figure crossed ninety trillion dollars, which is the single row where being wrong costs most. A uniform string has no rare branch because every row exercises the only branch there is.

**AND IT CANNOT BE VERSIONED.** EVENTS section 1 makes a payload's shape a function of `schema_version` and requires both shapes to stay readable. **A magnitude-conditional type makes shape a function of the VALUE**, which no version number can express: a consumer that reads `schema_version` still does not know what it is about to parse, and the versioning rule the catalogue is built on has nothing to say about it.

**`asJsonNumber` IS NOT OVERTURNED HERE AND IS NOT TOUCHED.** It lives in `apps/worker`, it serves `risk_flags.evidence`, and that column is not EVENTS' to rule on. **The two `jsonb` columns now answer the same question differently, and that is registered in section 11 as an open item rather than repaired inside this fence**, on the standing rule that a slice reports rather than widens. A session that unifies them should read this section first, because the argument above is a reason the two answers may legitimately differ: an evidence object is read by an investigator looking at one flag, and an event payload is read by machines for decades.

### 6. The dispatch's premise that a decimal string is a format no document states is FALSE

The dispatch and [session 366](../sessions/2026-08-28-session-366.md) both say a JSON string "is a format no document in this corpus states, so every reader of the feed acquires an undeclared parse". **Three prior rulings state it, and one of them is about a `bigint` reaching a `jsonb` column.**

| Where | What it already states |
|---|---|
| [ADR-158](ADR-158.md) clause 3, at `ADR-158:54` | "`entry_id` is a DECIMAL STRING, and it is the first non-uuid identifier this contract carries". `wallet_entries.id` is a `bigint` identity and the field "is a string of decimal digits, a client must not parse it" |
| [API_CONTRACT](../architecture/API_CONTRACT.md) at `:681` | "**`entry_id` is a STRING and it is the only identifier in this document that is not a uuid** ... a `bigint` on the wire as a JSON `number` is the defect [ADR-122](ADR-122.md) refuses in the digest for the same reason: it admits a value above `Number.MAX_SAFE_INTEGER` that has already lost digits by the time anything reads it" |
| [`graph.ts:394`](../../apps/worker/src/detectors/graph.ts) | a `bigint` reaching a `jsonb` column becomes "a DECIMAL STRING when it is not" exactly representable |

**SO THE COST THE DISPATCH PRICED AS "AN UNDECLARED PARSE" IS SMALLER THAN IT LOOKED, AND THE ARGUMENT FOR THE NUMBER WAS CORRESPONDINGLY WEAKER.** A decimal string for a 64-bit integer is this corpus's established answer wherever the value crosses into JSON, and this entry extends the answer rather than minting one. **What is still owed is the DECLARATION**, because the three above are about `entry_id` and about `evidence` and none of them is about `events.payload`, and EVENTS is where a reader of the feed looks. Section 9 is that amendment.

**The premise this refutes is the fourteenth a session has checked and found false**, and it is recorded here rather than in a pull-request body because it changed which option won.

### 7. Why the encoding is the WRITER's and not `buildEvent`'s

**THE LIMIT BELONGS TO THE COLUMN AND NOT TO THE EVENT**, which is session 366's argument for putting the refusal there and it carries unchanged to the encoding.

| Candidate | Disposition |
|---|---|
| `assertPayloadRules` | It is the DOMAIN rule and it is a gate. Teaching it to accept a canonical string would admit at the producer the type it exists to refuse, which is weakening a gate to pass it |
| `buildEvent` | The envelope would leave the producer already encoded, so `EventSink` over a writer that does not serialise -- the shape every suite in this tree uses -- would see strings where the producer wrote `bigint`s. A case asserts today that the envelope reaches such a sink unchanged, and it should keep being true |
| **`TRANSACTION_EVENT_WRITER`** | **Taken.** It is the only file that knows the destination is `jsonb`, it already holds the refusal, and everything above it keeps the domain type |

**SO THE ORDER IS: `assertPayloadRules` requires `bigint` at the producer, the writer encodes `_cents` to a string, and the writer then refuses any `bigint` that survives.** The third step is clause 6 and it is why the encoding cannot silently swallow a money value under a key nobody declared.

### 8. What a consumer must do, stated because it is the cost this entry chose

A consumer reading `events.payload`:

- **In JavaScript**, `BigInt(payload.approved_cents)` for a `_cents` field, which is `centsFromPayload`. `Number(...)` on it is the defect and is what a `_cents` key is a warning about.
- **In SQL**, `(payload ->> 'approved_cents')::bigint`. This is exact and it is what a JSON number would have needed anyway, because `->>` returns text either way; **the cast is not a new cost of this ruling**, only a newly obvious one.
- **In Metabase and BI**, the same cast. A `jsonb` string in a chart without one renders lexicographically, which sorts `"9"` above `"10"`. **That is the sharpest practical cost of this ruling and it is named here rather than discovered on a dashboard.**

### 12. The question, plainly

**THAT THE JSON NUMBER LOSES IS DERIVED. THAT THE UNIFORM STRING BEATS THE CONDITIONAL IS JUDGED, AND IT IS THE ONE LINE TO READ SLOWLY.**

The conditional is exact, it is already in this tree, and it renders every real figure as a number, which is friendlier to every consumer this system will actually have. **This entry refuses it on a property that will never be exercised**: that the string branch is untested until the worst possible row. A founder who reads that as buying insurance against an impossible event, at the price of a cast in every dashboard query and a parse in every reader, is holding a defensible position and should overturn clause 1 in favour of `asJsonNumber`'s shape, which would also make the two `jsonb` columns agree.

**The cost of this entry being wrong is a cast in BI and a lexicographic sort somebody hits once.** **The cost of the other error is a union type in an append-only column retained forever, whose second arm first executes on the largest number the firm has ever computed.** The column cannot be repaired afterwards, and that asymmetry is why the ruling went the way it did.
