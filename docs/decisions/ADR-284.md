## ADR-284: the cap's missing row is a missing WRITER, the writer is an operator act on a config number, and so the control lands before the row does  (2026-08-30, status: proposed)

**[ADR-252](ADR-252.md) built the cap's row and [ADR-265](ADR-265.md) built its door, and both entries closed saying the same sentence: what is left is an EMPTY TABLE.** This entry is the third narrowing of that clause and the first one that is a piece of PRODUCT rather than a ruling about a read. A row needs somebody to write it, and the somebody is an operator, and an operator act on a config number is the exact act constitution Appendix D4 and [ADR-010](ADR-010.md) name.

**SO THE ORDER IS THE FINDING. The control lands BEFORE the row does.** A session that wrote the first cap by hand and left the control to the admin route would have created the number this repository is least able to explain: a limit on the firm's exposure, in force, approved by nobody, with no audit row and no second person. `0076_firm_parameter_write_control.sql` makes that row unwritable. It seeds nothing, names no operator and invents no number.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `284`, session **475**, branch `claude/a-cap-with-a-door-and-no-row`. **Migration `0076` IS TAKEN AND SPENT**, under the row's own condition that it be taken if and only if a row-writer genuinely needs one; section 2 ruling 1 is the measured reason it does. `RI-33` was reserved to this row and is **NOT TAKEN**: section 9.2 says why, and it is a fence reason rather than a judgement that no invariant would help. **THE FENCE WAS EXTENDED TO `packages/db/test/**` BY THE DISPATCHER AFTER THIS SESSION REPORTED IT SHORT**, and to nothing else; section 9 is the ruling that extension asked for.

- **MONEY ADJACENT. `POST /checkout` is the endpoint that SELLS ACCOUNTS and this is the number its first line reads.** `E2` READ OWED, **and three are inherited**, because [ADR-252](ADR-252.md), [ADR-265](ADR-265.md) and [ADR-237](ADR-237.md) are all `proposed` and UNSIGNED and this entry rests on all three. It ships `proposed` with an UNSIGNED approval line, and merging is not signing. **No `status` field anywhere moves and nothing is marked `accepted`.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That `firm_parameters` declared no `uuid` column while `admin_actions.subject_id` is `uuid NOT NULL`, that `dual_control_approvals` carried no foreign key on either of its two names, that `merit_app` holds `UPDATE` and `DELETE` on `firm_parameters`, and that every part of `0076` permits what it must and refuses what it must, are **MEASURED** against a PostgreSQL 16.13 instance carrying the whole set applied forward-only from empty (section 7). What is **DERIVED** is that the port does not become wireable and the wired count does not move (section 5). What is **JUDGED** is that a `base_account_cap` write is inside [ADR-010](ADR-010.md)'s sensitive set (section 3), that the control is table wide rather than per parameter (ruling 3), that both hands must be `owner` (ruling 5), that the delay window is owed rather than invented (ruling 7), and that the vocabulary sweep guards a VALUE SURFACE rather than the `ALTER` statement (ruling 10, section 9).

- **A DISPATCH PROMPT IS NOT A SOURCE.** The row supplied four citations and all four were re-derived at this commit before a line was written. **All four held.** Section 1.

### 2. THE RULING

**Ruling 1. A ROW-WRITER GENUINELY NEEDS A MIGRATION, AND THE REASON IS A HARD BLOCKER RATHER THAN A PREFERENCE.** `admin_actions.subject_id` is `uuid NOT NULL` (`0017:79`) and `dual_control_approvals.subject_id` is `uuid NOT NULL` (`0016:229`). `firm_parameters` declared **SIX columns and not one of them a `uuid`**, read out of `information_schema.columns` rather than out of the file. So **the audit row API_CONTRACT section 8 requires of every admin mutation cannot name a cap row at all**, and neither can an approval of one. That is `0048` item 0's shape exactly: a ruled act that is not performable against the merged schema, unnoticed because the table has zero rows. It was found by writing the insert.

**Ruling 2. A `firm_parameters` WRITE IS INSIDE [ADR-010](ADR-010.md)'s SENSITIVE SET.** Section 3 is the argument. Constitution D4 requires dual control plus a delay window on *"any config edit touching cap/split/gap"*, and this is a config edit touching a cap. It is RULED here rather than inherited, because the alternative reading is available and section 3 states it.

**Ruling 3. THE CONTROL IS TABLE WIDE AND NAMES NO PARAMETER.** `firm_parameters_vocabulary_is_closed` admits ONE member, and `0074` rules that a second one is *"an ADR plus a superseding migration"*. So *"every write to this table is dual controlled"* and *"every cap edit is dual controlled"* are the same set today, and the ADR that widens the vocabulary is the document that decides whether a new member carries this control. **A per-parameter exemption written now would be a control with a hole shaped like a parameter nobody has proposed.** It also keeps `0076` free of the string `base_account_cap` on any declaring line, which is what `checkout-backend-blockers.test.ts` asserts of the whole migration set.

**Ruling 4. THE APPROVAL PINS THE PAYLOAD, AND THIS IS THE FIRST TIME `payload_hash` HAS A READER.** `0016` added the column with its own reason: *"An approval that does not pin the payload approves whatever the request happens to say when it executes, which is a control that can be edited after it is passed."* `0070` deliberately left it unread, because *"the bytes an operator approved are an admin request body and a withdrawal row is not one"*. **Here the row IS the payload.** A cap change has no prior state to approve, so what the second person checks is the number, the date and the written reason, and `firm_parameter_payload_digest` is those fields written out canonically. **Length prefixed, so the encoding is injective**, and the timestamp is rendered in UTC rather than cast, because a `timestamptz` cast to `text` renders in the SESSION's TimeZone and the same row would digest differently for two operators in two places.

**Ruling 5. BOTH HANDS ARE ACTIVE `owner` OPERATORS.** [API_CONTRACT section 8](../architecture/API_CONTRACT.md) bounds `ops` to *"read plus account actions, no config or role changes"*, and [ADR-010](ADR-010.md) names the credential in the same word: *"A second `owner` credential must exist before the first sensitive config edit."* So `owner` on the operator of record AND on the second person, because a checker without the authority to make the change is not a check on it. `status = 'active'` on both, because `0073` declares that column to be *"whether they may act today, which is not whether they exist"* and an operator row can never be deleted once it has acted, so suspension is the only offboarding there is.

**Ruling 6. `dual_control_approvals` GETS ITS TWO REFERENTS, AND WITHOUT THEM RULING 5 IS THEATRE ON ITS OWN TERMS.** Read out of `pg_constraint`: three foreign keys in this schema reference `operators` and **none of them is on `dual_control_approvals`**. `dual_control_approvals_second_person` requires only that the approver's string DIFFER from the requester's, so before this file the second person could be any string, including a string naming nobody. This is `0073`'s own finding about `0017:77`, standing one table over, on the table that IS the dual control. `0074` already resolves `firm_parameters.approved_by` into `operators`, so the REQUESTER was real by composition and **the CHECKER was not, and the checker is the entire control.**

**Ruling 7. THE DELAY WINDOW IS OWED AND IS NOT INVENTED.** D4 and [ADR-010](ADR-010.md) both require *"dual control plus a delay window"* and **neither states a duration**; [SECURITY C-10](../architecture/SECURITY.md) restates the pair without one. The only duration nearby is the 48 hour cooling on a payout DESTINATION change, a different control on a different act. A number written here would be a number this session invented, which is `0074`'s own refusal about the cap and `0073`'s about the operator-session lifetime ceiling, arriving a third time. **What is installed instead is the half that needs no number**: `FP-DC7` refuses a row dated before its own approval, so a backdated cap cannot silently rewrite what was in force while a purchase was being refused. It is not the delay window and `0076` says so in its own comment, which a case now pins.

**Ruling 8. `0074`'s SUPERSESSION PROMISE IS ENFORCED RATHER THAN WRITTEN.** That file says a change is a new row and never an UPDATE, *"so the number in force on the day a purchase was refused stays readable after the number has moved"*, and `merit_app` holds `UPDATE` and `DELETE` on the table. **DELETE is the hole that matters and it is the quiet one**: an UPDATE that moved the number already fails `FP-DC5` because the digest stops matching, while a DELETE fails nothing and removing the current row makes an older, higher cap current again, with no new row, no approval and no audit trail.

**Ruling 10. THE VOCABULARY SWEEP GUARDS A VALUE SURFACE AND NOT THE `ALTER` STATEMENT.** Section 9, and it is the ruling the fence extension asked for rather than a permission it granted. Both readings are stated, one is taken from the file's own header, and every case that moved ends STRONGER on the axis it guards, each strengthening watched RED under a seed.

**Ruling 9. THE OPERATOR ROUTE IS FOUNDER OWED AND IS NOT STUBBED.** Section 5. No identity provider is stubbed, no admin session is invented, and no hostname, bucket, key or secret is written ([ADR-012](ADR-012.md)). Merit stays passwordless ([ADR-039](ADR-039.md), `0002:280`) and nothing in this diff can mint a session.

### 3. Ruling 2, and the reading it refuses

**THE AVAILABLE READING IS THAT "cap" IN D4 MEANS THE PAYOUT CAP, AND IT IS NOT SILly.** The constitution's own use of the word is the liability triple: *"Caps + consistency + cadence gaps + an 8-payout live-graduation ladder are the liability architecture"*, and *"cap per request (min payout $100); split applied at ledger level"*. Cap, split and gap are three PLAN parameters about how money leaves. `base_account_cap` is a different number: how many live accounts one identity may hold across every plan. Under that reading, a cap raise here would need an audit row and no second person, and [M09](../plans/M09-marketing-site.md) section 3's own precedent would apply, which says in terms that adding something to [ADR-010](ADR-010.md)'s closed set *"is an amendment to that ADR and not an application of it"*.

**IT IS REFUSED, AND THE REASON IS WHAT D4 IS PROTECTING RATHER THAN WHICH NOUN IT USED.** [M14](../plans/M14-loyalty-retention.md) section 6 and [M17](../plans/M17-offers-engine.md) section 5 both say why cap, split and gap are the named three: they are *"the parameters through which economic sabotage is silent"*. `0074`'s own header says the same sentence about this number without knowing it was making this argument: *"A number that decides who may buy an account is the number that decides how much of the firm's tail risk a single buyer may accumulate, so a reviewer reading this file is reading a limit on exposure rather than a settings table."* **A raise here is the anti-fleet control loosened**, and a fleet of correlated accounts under one buyer is the failure mode [M19](../plans/M19-kyc-identity.md) buys biometric dedupe for and [M07](../plans/M07-risk-abuse.md) builds an identity graph for. **One owned admin session that can raise it alone is [M06](../plans/M06-admin-ops-console.md) `FM-M6-05` with the mitigation removed.**

**AND THE ASYMMETRY IS TOTAL, WHICH IS WHY THIS IS RULED RATHER THAN DEFERRED.** If this ruling is wrong, an operator action nobody performs yet costs a second key it did not need. If the other reading is wrong, one compromised session raises the firm's exposure ceiling and the audit trail reads as a settings change. **A control installed on an empty table costs nothing and a control retrofitted after the first row costs the row.**

**WHAT IS NOT RULED HERE, AND IT IS THE FOUNDER'S.** Whether `base_account_cap` joins the SET [ADR-010](ADR-010.md) enumerates, as a written amendment to that ADR's text, is a question about that document. This entry rules the CONTROL onto this table and records the amendment as owed. `0076` is correct under either resolution: nothing in it edits [ADR-010](ADR-010.md), and if the founder rules the account cap outside the set, the file becomes a control that is stricter than required rather than a control that is wrong.

**ONE THING THE RULING DELIBERATELY DOES NOT DO: IT DOES NOT EXEMPT A LOWERING.** The tempting shape is *"dual control on a raise, one hand on a cut"*, on `0070`'s threshold-ceiling asymmetry. It is refused because a conditional control needs a comparison against the row currently in force, on a supersession-dated table where *"currently in force"* is itself the read this estate has one door for, and because the incident tool for a compromised buyer is `identities.status` and an account freeze ([M05](../plans/M05-payout-system.md) section 6 rules a freeze explicitly OUTSIDE dual control), not the firm's base number. **A control with a direction is a control with a case analysis, and the availability argument it would buy is already answered by [SECURITY](../architecture/SECURITY.md) section 8.1's break-glass.**

### 4. What the writer looks like, end to end

**FOUR ROWS AND TWO TRANSACTIONS, and the first transaction is the second person.**

| Step | Row | Who |
|---|---|---|
| 1 | `operators`, two rows, `role = 'owner'` | The bootstrap. Section 6 |
| 2 | `dual_control_approvals`, `status = 'pending'`, `subject_kind = 'firm_parameter'`, `subject_id` the cap row's future `id`, `payload_hash` the canonical digest of the change | The operator proposing the number |
| 3 | the same row moved to `approved` | THE SECOND PERSON, and `dual_control_approvals_second_person` is what makes them a second one |
| 4 | `firm_parameters` and `admin_actions`, in ONE transaction | The proposing operator, whose name is the row's `approved_by` and the audit row's `actor` |

**THE `id` IS CHOSEN BY THE WRITER AND NOT BY THE DATABASE.** The approval names the row before the row exists, which is what pinning a payload means. `0076` declares a `gen_random_uuid()` default anyway, and it is a convenience for a scratch database rather than the path: a row that takes the default cites an approval that names a different subject and is refused by `FP-DC2`.

**THE AUDIT ROW'S `initiative` IS `operational`.** `0043`'s closed vocabulary is `enforcement | trader_request | operational`, and a firm parameter change is neither an enforcement act against a trader nor a trader's request. Derived by writing the row: `admin_actions.initiative` is `NOT NULL` and the first attempt at this fixture failed on it.

**THE TWO TRIGGERS ARE `DEFERRABLE INITIALLY DEFERRED`**, on `0070`'s and `0048`'s shape, so the order of the two inserts inside step 4 is the writer's business rather than a contract written in a trigger.

### 6. The operator bootstrap, ruled and not performed

**THE FIRST `operators` ROW CANNOT BE CREATED BY AN AUTHENTICATED OPERATOR**, which is the ordinary bootstrap and is not special to Merit. `0073` already anticipates the state: `idp_issuer` and `idp_subject` are nullable and a NULL pair is *"a row provisioned before the provider has ever seen that person"*, so the directory can be filled before the identity provider exists.

**RULED: THE FIRST OPERATORS ARE A DEPLOY-TIME ACT AND NOT A ROUTE.** That is `0070`'s own asymmetry in its own words: *"deploy access rather than the route access [ADR-067](ADR-067.md) section 5 assumes compromised, and that asymmetry is the control."* Whoever holds migration access already holds everything a route could grant.

**AND NO OPERATOR IS SEEDED HERE.** A real operator's identifiers are not this repository's to hold ([ADR-012](ADR-012.md)), and an invented one is a row somebody has to remember to delete, on a table whose rows can never be deleted once they have acted. **So a deployment produced by this tree still cannot write a cap, and that is correct rather than a defect**, for the same reason `0074` shipping empty is correct.

### 9. Ruling 10: the vocabulary sweep guards a VALUE SURFACE, and the case is narrowed only because it is strengthened

**THE FENCE WAS SHORT AND THE DISPATCHER EXTENDED IT TO `packages/db/test/**` AND NOTHING ELSE.** Row `284` named the migration and not the tests that assert about the table the migration alters, and four cases were reported RED before the extension rather than repaired past it. The extension came with a condition, and this section is the ruling it asked for.

**TWO READINGS WERE LIVE AND ONE IS TAKEN. Ruling 10: the property is the VALUE SURFACE, the title overreached, and `0076` widens nothing the case exists to guard.**

**The source settles it, and it says so twice.** [`firm-parameter-vocabulary.test.ts`](../../packages/db/test/firm-parameter-vocabulary.test.ts)'s own header states the closure as a PAIR: *"A CHECK closes which parameters may be NAMED. It says nothing about what may be STORED, and a `text_value` column landing beside `integer_value` would be the settings bag arriving under a constraint that still passes."* And the case's own comment gives the same reason in the same words: *"a column added by an `ALTER` would widen what may be STORED without touching the CHECK that says what may be NAMED."* `0074` completes it, ruling that the value TYPE is itself part of the vocabulary: *"a parameter that is not an integer belongs in a table of its own"*.

**`0076` adds a `uuid` handle and a `uuid` approval citation.** Neither can hold a parameter's value, `integer_value` is still the only column that can, and `firm_parameters_vocabulary_is_closed` is untouched. **The form was a proxy for the property and the property is intact.**

**WHAT WAS REJECTED, AND WHY.** The other reading is that the table is closed to every `ALTER` absolutely, and that `0076`'s columns belong somewhere else. It is refused because the only other home is a side table joined on `(parameter, effective_from)`, and that is a WEAKER control: `dual_control_approval_id` would stop being `NOT NULL` on the row that needs it, so a cap row could exist with no authorisation and presence would rest on a trigger somebody can drop, where today it rests on a column somebody cannot. `0070` put the citation ON the row for the same reason, and `0074` put `approved_by` there too. **A control moved off the row to keep a test's form is a gate weakened to pass it wearing the opposite costume.**

**AND A NARROWING IS ONLY LEGITIMATE IF THE CASE ENDS STRONGER ON ITS OWN AXIS, SO BOTH CASES DO.**

| Case | Was | Is | Watched |
|---|---|---|---|
| *"no migration alters `firm_parameters` at all"* | BANNED the statement and CLASSIFIED nothing, so the first legitimate `ALTER` left deleting the case as the only move | reads **every column any migration adds, over the whole set, and refuses any type that could carry a value**. `text_value text`, `cents_value bigint` and `jsonb_value jsonb` are red by TYPE, whatever they are named | **RED under two seeds**: `ADD COLUMN text_value text` and `ADD COLUMN budget bigint`, the second named so that nothing but its type condemns it. Both named themselves in the failure |
| *"no other migration widens the vocabulary, BY CONSTRAINT NAME"* | read MENTIONS over whole files, so a later migration EXPLAINING the closure turned it red while widening nothing, and it was BLIND to a widening that never types the old constraint's name | reads **DECLARING lines**, `COMMENT ON` skipped whole, and is **name-blind**: a second membership list over `parameter` is caught wherever it appears | **RED under a seeded `ADD CONSTRAINT firm_parameters_vocabulary_v2 CHECK (parameter IN (...))`, and the OLD form was measured GREEN on that same seed.** The strengthening is the difference between those two runs |
| *"the Drizzle declaration transcribes the same six"* | compared against a six-name LITERAL, which was `0074`'s `CREATE TABLE` written out a second time and stopped being the installed table the moment a second migration declared a column | derives the installed set from the **whole migration set** | **RED under a seeded parser break**: it is the sentinel for the `ADD COLUMN` sweep, because a parser that stops matching reports NO widening, which is the silent direction |

**THE MENTION-COUNTING REPAIR IS NOT NEW HERE AND THAT IS THE POINT.** `checkout-backend-blockers.test.ts` made the identical repair on `max_accounts`, in this repository, and recorded its reason: *"A count of MENTIONS was never the claim."* The scanner is transcribed from that file rather than invented, and it is a scanner rather than a `.replace()` over a comment regex, so `RI-30`'s second leg is untouched: that invariant is about the JavaScript stripper in `packages/tooling`, and SQL comments are `--`.

### 9.1 The fourth case was a pre-existing leak, and this diff only exposed it
