### 3. What `DetectorRunnerIo` requires, member by member

The interface is declared in [`apps/worker/src/detectors/ports.ts`](../../apps/worker/src/detectors/ports.ts) and has five members. Each was traced to whatever serves it.

| Member | What it must supply | Producer today |
|---|---|---|
| `transact` | The unit of work a run reads and writes in, taking the callback rather than handing back a handle | **`postgresDetectorTransact`**, over `LIVE_DB.batch` at `systemDb('nightly-batch')` |
| `terms` | `ADR-157`'s three read-path constructors, injected because a term is only a term if `packages/db` minted it | **The accessor's own `atMost`, `atLeast` and `isNull`**, reached by name through the one door |
| `now` | The run's only clock, from which `started_at`, `finished_at` and every `sla_due_at` derive | **The process clock** |
| `nonce` | One value per run, from a source with real entropy, so a memorised battery cannot pass | **`postgresDetectorNonce`**, over `randomUUID` |
| `events` | The sink that commits `detector.run_degraded` with the run row that is degraded, or neither | **NONE. This is the whole gap.** |

**FOUR OF THE FIVE ARE SERVED, AND THEY ARE SERVED BY REAL CODE RATHER THAN BY A PLAN.** `postgresDetectorRunnerIo` in [`apps/worker/src/detectors/adapter.ts`](../../apps/worker/src/detectors/adapter.ts) composes them and is exported through the barrel. **The sentence in the dispatch that the runner "does not run" is therefore too strong as stated**, and the accurate sentence is the one section 6 derives: it runs, and everything it does is thrown away.

**THE UNWIRED DEFAULT'S RECORDED REASON, QUOTED VERBATIM** from `DetectorRunnerUnwired` in `ports.ts`:

> `DetectorRunnerIo.${what} cannot be served by this deployment: no adapter is installed. The detector runner refuses rather than returning a plausible value, because an empty report is indistinguishable from a clean night and that is exactly the failure AS-M7-05 names.`

**AND THAT REASON IS NOW PARTLY OUT OF DATE IN ITS OWN TERMS.** It says *no adapter is installed*. An adapter IS installed, for four members, and `UNWIRED_DETECTOR_RUNNER_IO` is no longer the only inhabitant of its type. The value is still correct as the default for a deployment that composed nothing; the words describe a tree that has moved. **It is reported here and not edited**, because `ports.ts` is inside this row's fence but rewriting a live refusal message to be prettier is not what the row was dispatched to do, and `RI-14`'s discipline is to keep a sentence beside its correction rather than to quietly restate it.

### 4. The three blockers, each checked at its own source

The authoritative statement is the detector row in [`apps/worker/src/schedule.ts`](../../apps/worker/src/schedule.ts), which is nobody's this wave and was read and not written. It names three. **All three were re-derived rather than accepted.**

| Blocker | Checked how | Verdict |
|---|---|---|
| **(1) No event sink is reachable from `apps/worker` at all** | `TRANSACTION_EVENT_WRITER` was located: it is in [`apps/api/src/events.ts`](../../apps/api/src/events.ts) and nowhere else. `RI-04` is live and held in this row's own baseline | **HOLDS** |
| **(1a) `detector.run_degraded` is a row in no version of the catalogue** | Searched [`docs/architecture/EVENTS.md`](../architecture/EVENTS.md) for the name | **HOLDS. Absent.** |
| **(1b) `detector.run_completed`'s payload is one field short** | `emitRunEvents` in [`runner.ts`](../../apps/worker/src/detectors/runner.ts) builds a payload carrying `detector`, `detector_version`, `trading_day`, `rows_scanned`, `flags_raised` and `duration_ms`, and **not** `detector_run_id`, which the catalogue row names | **HOLDS** |
| **(2) `detector_definitions` has no producer** | No `.ts` under any `src/` reads the seed. Every reader of `m07-detectors-v1.rows.json` in this workspace is a test | **HOLDS** |
| **(3) Eleven of the eighteen seeded rows state no number** | Derived from the seed by counting rows carrying no parameter whose `state` is `stated` and whose value is numeric | **HOLDS, exactly eleven.** Its second clause does not. Section 5 |

**BLOCKER (2) IS WORSE THAN THE ROW SAYS AND THE DIFFERENCE IS WHO OWNS IT.** The row attributes the gap to the detector seed. **Neither seed in this workspace has a loader.** `packages/db/src/seed/calendars` and `packages/db/src/seed/detectors` are both generators that write a `rows.json`, and nothing anywhere applies either one to a database. So the missing producer is not `P7-d` having left something out; it is a shared, unowned gap that the detector runner is merely the first job to need. **That is a finding for whoever owns seeding and it is not taken here**, because `packages/db/src/seed/**` is nobody's this wave.

**BLOCKER (1b) IS THE ONLY ONE WITH A LEG INSIDE THIS ROW'S FENCE, AND IT IS STILL NOT TAKEN.** Adding `detector_run_id` to the payload is a change to `runner.ts`, which is this row's file. **It is refused for two reasons and the second is the load-bearing one.** First, `apps/worker/test/event-sink.test.ts` pins the field's absence and that file is outside this fence, so the edit would land a test failure in somebody else's file. Second, and decisively, **clearing (1b) clears nothing**: blockers (1) and (1a) both stand, no sink is reachable, and a payload made correct for a producer that cannot be called is a change nothing can exercise.

What did not exist anywhere is a check that reads the three modules together, so the summary sentence one file over could generalise past its evidence and no runner could contradict it. **That is the expiry shape this programme keeps paying for: a true clause and an over-general one in the same sentence, with only the true half testable.**

**AND ANSWERING THE FOUNDER'S QUESTION WOULD NOT CLEAR ALL THIRTEEN.** Two of the thirteen decline because their registry row carries no such parameter at all, which is a seed repair rather than an answer: `D-04` and `D-05`. ### 6. The sentence that matters most, and it is not in any disposition

Sections 3 and 5 together produce a fact that no record in this tree states:

> **`D-02` runs today, finds its own canary, and writes nothing.**

Under the sink `postgresDetectorRunnerIo` installs when `src/` calls it the way `src/` calls it, `runner.ts` emits inside the write transaction and emits unconditionally. The refusal rolls back the `detector_runs` row inserted before it. Run against the composed default, **every one of the fourteen comes back `unrecorded`, the one that works included.**

**THAT IS WHY BLOCKER (3) BEING PARTLY EXPIRED MOVES NOTHING.** The disposition `unscheduled` is correct, and it is correct for blockers (1) and (2), which stand without qualification. Had blocker (3) been the only one, this row would have found a schedulable job. It was not, and the honest report is that the third blocker is weaker than recorded and the first two carry the disposition on their own.

**ONE FILE: [`apps/worker/test/detector-census.test.ts`](../../apps/worker/test/detector-census.test.ts). NO SOURCE FILE WAS TOUCHED.**

### 12. Approval

**Status `proposed`. The approval line below is UNSIGNED and merging is not signing.** Inherited as well as owed: the `proposed` and unsigned backlog stands, two rows run beside this one holding `407` and `408`, and this row settles neither.

  **What a founder read adds and this entry cannot.**

  **AND THE THING THIS ROW WOULD SAY IF IT COULD ONLY KEEP ONE SENTENCE.** `D-02` works. It runs against its real registry row, it finds its own canary, and under the value this deployment actually installs it writes nothing at all. **The estate has one working detector and no way to learn that it worked.** Whether that is worth a sink and a loader is a founder's call and not a row's.
