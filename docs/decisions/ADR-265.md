## ADR-265: the cap gets a door that hands out one number, the catalogue admission its own sizing called for is refused because it would have built the trap, and the two ports become one finding again  (2026-08-30, status: proposed)

**[ADR-238](ADR-238.md) ruling 1 ruled the base account cap the FIRM'S number. [ADR-252](ADR-252.md) built its row and wired no reader, and left both entries waiting on it saying the same thing in different words: the number NOW HAS A COLUMN AND STILL HAS NO DOOR.** This entry is the door. It is one clause of a two-clause blocker on the endpoint that takes money, and it is the cheapest thing that was left on it.

**THE SIZED REMAINDER WAS WRONG AND THAT IS THIS SESSION'S FINDING.** ADR-252 section 10 sized the whole of what remained as *"the `CATALOG_TABLE_KEYS` admission, one member plus ADR-233's argument, in `packages/db/src/scoped-db.ts`"*, and named it *"the whole remainder of `useCheckoutBackend`'s clause 1"*. **The admission is refused here rather than taken, and the reason is the trap the dispatching row named first**: a catalogue read hands out ROWS, and a caller holding rows does the effective dating and folds `identities.max_accounts_override` itself. Taking the sized remainder would have built the control that gets forgotten.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `265`, session **456**, branch `claude/a-column-with-no-door`. **NO MIGRATION NUMBER IS TAKEN OR RESERVED**, and none is needed: `0074` is the highest, the directory was read at the moment of branching, and `0075` is still next. **No `packages/db/migrations` file is added, edited or read for anything but its text.**

- **MONEY PATH. `POST /checkout` is how money enters the firm and this is the number its first line reads.** `E2` READ OWED, **and two are inherited**, because [ADR-252](ADR-252.md) and [ADR-238](ADR-238.md) are both `proposed` and UNSIGNED and this entry rests on both. It ships `proposed` with an UNSIGNED approval line, and merging is not signing. **No `status` field anywhere moves and nothing is marked `accepted`.**

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED.** That the door builds the statement `0074`'s own index comment rules (the parameter named, `effective_from <= now()`, `ORDER BY effective_from DESC`, `LIMIT 1`), that it sends two statements and no join, that the base is read FIRST and the identity SECOND, that an absent base row throws with the identity unread, that the override wins in BOTH directions, and that `CATALOG_TABLE_KEYS` is unchanged at five members with this key not among them, are **MEASURED** by [`packages/db/test/account-cap-door.test.ts`](../../packages/db/test/account-cap-door.test.ts), watched RED on the unmodified tree and watched firing under six seeded defects. What is **JUDGED** is the refusal of the catalogue admission (section 3), the unconditional refusal ahead of the override read (section 4), and the return type being `number` rather than `number | null` (section 4).

### 2. THE RULING

> **1. THE DOOR IS `ScopedTx.effectiveAccountCap()`, IT TAKES NO ARGUMENT, AND IT RETURNS ONE INTEGER.** The base is `firm_parameters.base_account_cap` read as the latest row whose `effective_from` has arrived; the exception is `identities.max_accounts_override` on the handle's own row; **both are resolved INSIDE `packages/db` and the caller receives the resolved number.** It takes no argument on `lockScope`'s reason: there is no address a caller could point at somebody else's cap.
>
> **2. THE `CATALOG_TABLE_KEYS` ADMISSION [ADR-252](ADR-252.md) SIZED AS THE REMAINDER IS REFUSED, NOT DEFERRED, AND THE LIST IS STILL FIVE MEMBERS.** `refuseUncatalogued`'s admission test is MET by this table, so the objection is not that the argument fails. It is that a catalogue read is the WRONG SHAPE for this number, in three ways that each independently decide it. Section 3.
>
> **3. THE OVERRIDE WINS IN BOTH DIRECTIONS AND NEITHER `Math.max` NOR `Math.min` IS CORRECT.** `0002:47` names *"grandfathered merges (B4 #17), where an identity is over cap through no purchase of its own"*, which needs a LARGER number, and an identity under review needs a smaller one. **A door that clamped either way would silently decline to apply half the exceptions an operator writes**, and the clamp is the shape a careful session reaches for.
>
> **4. AN ABSENT BASE ROW THROWS, AND IT THROWS BEFORE THE IDENTITY IS READ.** The ORDER is the control rather than a consequence of it: an override carries no approver and no written reason, `firm_parameters` carries both by construction (`approved_by` is a foreign key into `operators`), and **a door that read the identity first and fell back to the exception would promote a per-entity exception into the firm's number on exactly the deployment nobody configured.** A deployment that has not set the firm's number has not authorised selling accounts to anybody, including the ones an operator wrote an exception for.
>
> **5. THE RETURN TYPE IS `number` AND THAT IS A CONTROL RATHER THAN A SIGNATURE.** `number | null` is a value `?? Infinity` can be written against in one character, and `Infinity` is the answer this whole line of entries exists to refuse. **There is no absent value here for anybody to fold**, and there is no second field for a caller to hold the base in beside the resolved number.
>
> **6. `ORDER BY` AND `LIMIT` ARRIVE THE WAY `FOR UPDATE` DID.** [ADR-112](ADR-112.md) foreclosure 3 named four constructions with no shape in this accessor and this is the first read that needs two of them. They are taken inside a NAMED statement builder with no caller-supplied option, exactly as `lockingSelectStatement` took `FOR UPDATE`, so the accessor gains one read that orders rather than a general `orderBy`, and the foreclosure holds for every other caller.
>
> **7. THE TWO ENTRIES ARE ONE FINDING AGAIN, AND THE SYMMETRY WITH [ADR-252](ADR-252.md) RULING 7 IS THE POINT.** That entry found the two refusals had STOPPED being one finding, because `accountCap()` needed a catalogue admission and `readMe` did not. **The difference between them was the CONSTRUCTION half, and there is now one construction serving both.** What is left of either is the empty table. Section 5.
>
> **8. NEITHER PORT IS WIRED, NO SETTER IS CALLED, NO MIGRATION IS WRITTEN AND NO GATE WAS WEAKENED TO PASS IT.** `useCheckoutBackend` is narrowed for the second time in a week and keeps its `LT-08` clause; the `readMe` refusal is narrowed for the second time and keeps the empty table. `start.ts` is untouched. One shipped assertion and one shipped invariant went RED on this branch and **both were repaired by asking a narrower question rather than a looser one.** Section 7.

### 3. Ruling 2, and why the sized remainder would have built the trap

**THE ROW PUT THE FOLD TRAP FIRST AND IT DECIDES THIS SECTION.** *"A reader that returns the override when it exists and the base otherwise is correct. One that returns the base and lets a caller remember the override is a control that will be forgotten exactly once."*

**A `CATALOG_TABLE_KEYS` ADMISSION IS EXACTLY THE SECOND READER.** `catalogRowsWhere('firmParameters', { parameter: 'base_account_cap' })` hands the handler rows of one table, and every remaining step is then the handler's. Three consequences, each of which alone settles it:

| | What the admission gives the caller | What the named door gives them |
|---|---|---|
| **The fold** | The BASE. `identities.max_accounts_override` is a second read on a second table that the caller has to remember, in two callers, forever | One integer, with the exception already applied |
| **The dating** | EVERY row `firm_parameters` has ever held for this parameter, superseded ones included, because [ADR-112](ADR-112.md) foreclosure 3 records that `ORDER BY` and `LIMIT` have no shape in this accessor. The caller picks one | The latest row whose `effective_from` has arrived, built once |
| **The scope of the grant** | THE WHOLE TABLE, FOREVER. `firm_parameters` is a VOCABULARY: it admits one member today and a later ADR may admit others, and a key in that list is a read of all of them by anybody holding a scoped transaction | One parameter, named in the door, returned as a count |

**SO THE ADMISSION IS REFUSED AND THIS IS [ADR-262](ADR-262.md)'s CONSTRUCTION APPLIED TO A `firm` TABLE.** That entry discharged the cross-identity read *"without a read grant"*: `attributionAffiliate` reads an `owned` row unscoped and returns a bit, and the narrowing lives in the RESULT rather than in the predicate. **This reads a `firm` row unscoped and returns an integer.** No key changed key sets, `refuseUncatalogued` is untouched, and `CATALOG_TABLE_KEYS` is the same five members it has held since [ADR-233](ADR-233.md).

**THE ARGUMENT A DOOR OWES IS NOT "THE ANSWER IS SMALL", AND `scoped-db.ts`'s OWN HEADER SAYS SO**: *"it is that ONE handler on ONE path needs this answer inside its own transaction"*. `INV-M3-15` is that argument in the corpus's own words. It requires the restriction check at the same point in the transaction as the cap, `gateIdentity` performs both in one call, and **a cap read through `ApiDb.firm` before the transaction opens is a cap that may have been superseded by the time the purchase commits**, which is a supersession dated table's characteristic failure and the reason `firm_parameters` is dated at all.

**WHAT THIS COSTS, STATED RATHER THAN HIDDEN.** A named door per question does not scale the way a list does: the second firm parameter a scoped transaction needs will be a second door and a second argument, and a session that wants six of them should reopen the admission with that as its evidence rather than treat this entry as forbidding it. **What this entry refuses is the admission AS THE ANSWER TO THIS NUMBER**, because this number is two rows on two tables and a catalogue key can only ever hand over one of them.

### 4. Ruling 3, 4 and 5, and the traps the row named in the order it named them

**THE FOLD.** `identities.max_accounts_override` is `integer NULL CHECK (> 0)` and its name is the whole design: it OVERRIDES. The available shortcut is a clamp, and it is available in both spellings. `Math.max(base, override)` reads as "an exception can only ever be generous", which is what a reviewer expects an exception to be and is not what the column is: **`0002:47` names the grandfathered merge, and nothing anywhere in the corpus says an operator may not write a smaller number for an identity under review.** `Math.min` reads as "the firm's cap is a ceiling nobody exceeds", which deletes B4 #17's case entirely. The door applies the override, and the case asserting the SMALLER direction is the one that catches both.

**THE ABSENCE.** [ADR-252](ADR-252.md) ruling 5 said the slice writing this read *"owes a REFUSAL there before it owes anything else"*, and it said the trap gets WORSE once the table exists: *"an implementer has a door, a query, and an empty result set, and `?? Infinity` reads like defensive programming rather than like a cap being switched off."* Three things answer that here and none of them is a comment:

1. **THE THROW**, rather than a `null` or a sentinel. A refusal a caller can reach for a default in is a refusal with a default.
2. **THE RETURN TYPE `number`**, so no call site has an absent value to fold. This is the same move `AffiliateRef` made one entry ago: **the property is structural rather than careful, because there is nothing on the shape to put the wrong answer in.**
3. **THE ORDER**, which is the half a reviewer would not think to ask for. The base is read first and the identity is not read at all when it is missing, so the refusal cannot be answered by an exception. **A door that read both and then decided would produce a deployment where an operator-written override is the only cap in force and nobody approved the number it is an exception to.**

**AND THE THROW FAILS CLOSED IN THE DIRECTION THAT MATTERS.** Inside the checkout transaction it rolls back and nothing is written, so a deployment with no cap sells no accounts. That is the correct answer to *"the firm has not said how many accounts one identity may hold"*.

### 5. Ruling 7, and the finding only reading both entries together produces

**[ADR-252](ADR-252.md) RULING 7 IS THE MOST INTERESTING SENTENCE EITHER ENTRY HAS PRODUCED AND THIS ENTRY REVERSES IT WITHOUT CONTRADICTING IT.**

| | `useCheckoutBackend`, `accountCap()` | `databaseAuthBackend`, `readMe` |
|---|---|---|
| Before `0074` | The number had no column anywhere | The number had no source anywhere |
| After `0074` ([ADR-252](ADR-252.md) ruling 7) | A catalogue admission, **plus** a row | A row |
| After this entry | **A row** | **A row** |

**THE DIFFERENCE BETWEEN THEM WAS ALWAYS THE DOOR, AND THERE IS NOW ONE DOOR.** ADR-252 was right that the two refusals had stopped being identical, and it was right for the reason it gave: one read ran inside a transaction bound by an invariant and the other did not. **That distinction was about the CONSTRUCTION each needed, and this entry builds a construction that serves both** -- because `readMe` assembles every other field of `Me` through the same scoped door, so a method on `ScopedTx` is reachable from both callers without either of them changing authority.

**SO THE TWO ENTRIES ARE ONE FINDING AGAIN AND THE FINDING IS THE EMPTY TABLE.** That is a smaller and more honest statement than either has carried: nothing under any `src/` writes a `firm_parameters` row, nothing writes the `operators` row its `approved_by` references, and the two empty tables are ORDERED, so the first cap cannot be written until the first operator is.

**ONE ASYMMETRY SURVIVES AND IT IS RECORDED RATHER THAN SMOOTHED.** The emptiness costs the two ports different things. A cap that refuses a purchase fails closed on an endpoint that already answers 503. **`GET /me` serves a trader their own account, and a `Me` that cannot be assembled without a row nobody has written makes the WHOLE response unavailable rather than one field of it.** That is why `readMe` is narrowed and not discharged even though its construction half is gone: wiring it would be a worse endpoint than not wiring it.

### 6. Ruling 6, and one thing TypeScript would not let the guard say

**THE DOOR ASSERTS ITS OWN REGISTRY READINGS**, on `attributionAffiliateStatement`'s idiom: it reads `firm_parameters` UNFILTERED and `identities` SCOPED, and if either registration moves, the read is the wrong read rather than a failing one.

**AND THE OBVIOUS WAY TO WRITE THAT GUARD DOES NOT COMPILE, WHICH IS WORTH RECORDING BECAUSE THE REASON IS INSTRUCTIVE.** `SCOPE_RULES` is `as const`, so `SCOPE_RULES.firmParameters` has the singleton type `{ class: 'firm' }`, and a direct assignment is narrowed to it: a guard reading `rule.class !== 'firm'` then has type `never` inside its own branch and the compiler refuses the message that names what the class became. `attributionAffiliateStatement` compiles only because its guard has a second disjunct.

**THE GUARD IS ABOUT THE FUTURE RATHER THAN ABOUT THIS COMPILE, AND THAT IS THE SENTENCE THE INDIRECTION EXISTS TO CARRY.** A registration is a line a later session edits; the day one moves, this door reads unfiltered where a tenancy column now exists, **and that recompiles clean.** `registeredRule(key)` reads the rule as a `ScopeRule` so the runtime check survives, with the reason written above it.

### 11. Landmines for the next session

- **A NAMED SECTION HEADING CAN HIJACK A NEARBY CITATION.** `RI-15` resolves a name to the nearest occurrence, so a comment that NAMES a declaration between a citation and its target makes the citation unrepairable at the obvious line and produces two different failure messages for the same pointer. Repoint at the declaration itself, not at the number the first message quotes.
- **`prettier --write` MOVES EVERY POINTER BELOW ITS FIRST REFLOW.** Run `format:check` BEFORE deriving citations, not after. This is the third session to pay for the same ordering.
- **ASSIGNMENT NARROWING MAKES A REGISTRY GUARD UNCOMPILABLE, NOT UNNECESSARY.** Section 6. The temptation is to delete the guard because "TypeScript says it cannot happen"; TypeScript is describing the registry as it is compiled today and the guard is about the day somebody edits it.
- **DRIZZLE'S COLUMN MAPPER COERCES BEFORE ANY GUARD IN THIS TREE RUNS.** A case asserting that a wrongly typed value is refused may be passing on the mapper rather than on the check it names. Section 7 event 4.
- **`pnpm run verify` AND `falsify.mjs` WERE NOT RUN**: the row forbids the first by name and the second mutates the working tree.
- **DEPENDENCIES ARE NOT INSTALLED IN A FRESH CONTAINER** (`pnpm install` first), and **`pnpm vitest` IS NOT A SCRIPT IN THIS WORKSPACE** (`npx vitest run`).
