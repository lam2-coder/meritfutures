## ADR-297: a column that cannot be null, and the null is not the defect. `payout_requests.approved_at` holds the REQUEST instant on every row, it is the only one of four state timestamps not bound to its state, and the repair is a SUPERSESSION whose number is RESERVED AND NOT WRITTEN  (2026-08-30, status: proposed)

**The dispatch's three premises were re-derived at source before anything was built on them, and ALL THREE HOLD, byte for byte.** [`0010_payouts.sql:89`](../../packages/db/migrations/0010_payouts.sql) is `approved_at timestamptz NOT NULL DEFAULT now(),`; [`payouts.ts:267`](../../apps/api/src/routes/payouts.ts) is `readonly approved_at: string | null;`; [`payouts.ts:256`](../../apps/api/src/routes/payouts.ts) says *"`approved_at` IS NULLABLE AND THAT IS THE HOLD'S WHOLE SHAPE IN ONE FIELD."* **So the one field a client uses to tell a held payout from an approved one is backed by a column that can never be null and defaults to `now()`.**

**THE RULING IS THE THIRD SHAPE: A SUPERSEDING MIGRATION. `0077` IS RESERVED IN [ALLOCATION](ALLOCATION.md) AND NOT WRITTEN.** The wire type does not move and the projection does not derive the null from `status`. Both are refused in writing, in sections 5 and 6, with the trader-visible consequence of each stated.

**AND THE DEFECT IS ONE LAYER DEEPER THAN THE NULLABILITY, WHICH IS WHY THE READ-SIDE REPAIR CANNOT REACH IT.** `approved_at` is `NOT NULL DEFAULT now()` and **no writer in this repository ever sets or updates it**, so on every row it holds **the INSERT instant**, which is the REQUEST instant. `created_at` ([`0010:123`](../../packages/db/migrations/0010_payouts.sql)) is `timestamptz NOT NULL DEFAULT now()` on the same table with the same default and the same absence of a writer. **The two columns are byte-identical on every row this schema can produce, and one of them is named for a decision the other is named for the absence of.**

**THE COLUMN WAS CORRECT WHEN IT WAS WRITTEN AND [ADR-040](ADR-040.md) FALSIFIED IT WITHOUT TOUCHING IT.** When `0010` landed, `[*] --> approved` was the only entry edge, approval was the same transaction as the request ([ADR-019](ADR-019.md), [M05 section 1.1](../plans/M05-payout-system.md)), and `DEFAULT now()` was the approval instant because the request instant and the approval instant were the same instant. ADR-040 added a second entry edge, `[*] --> held_pending_review`, on which they are not.

- **Origin:** [ALLOCATION](ALLOCATION.md) row `297`, session **487**, branch `claude/a-column-that-cannot-be-null`. **[ADR-287](ADR-287.md) section 7, slice 7's blocker.** **RULING ONLY: NO `src/` LINE, NO MIGRATION WRITTEN, NO TEST CHANGED, NO `RI-nn` MINTED.** `apps/api/src/**` and `packages/db/**` are out of fence and were read only.

- **MONEY PATH, and the [`E2`](../../MERIT_BUILD_MASTER_PROMPT.md) read is OWED.** Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **`API_CONTRACT` DOES NOT MOVE, AND THE FENCE'S PERMISSION FOR IT RESOLVES TO "NO".** The row's fence admits [API_CONTRACT](../architecture/API_CONTRACT.md) *"for this field only and only if the ruling is that the contract moves"*. **The ruling is that the SCHEMA moves.** [`API_CONTRACT:516`](../architecture/API_CONTRACT.md)'s `approved_at: string | null // null while held: the hold is PRE-approval` and [`:530`](../architecture/API_CONTRACT.md)'s paragraph are **correct as written and are vindicated rather than amended**. The defect was never in the contract, and this row edits no byte of it.

- **NOTHING IS WIRED AND NO COUNT MOVES: TEN WIRED OF TWENTY-FOUR DECLARED, FOURTEEN BLOCKED.** `start.ts` is untouched and `usePayoutBackend` is still one of the fourteen ([`wiring.test.ts:561`](../../apps/api/test/wiring.test.ts)).

### 2. WHAT THE COLUMN ACTUALLY HOLDS, WHICH IS NOT WHAT IT IS NAMED

**`DEFAULT now()` plus no writer, anywhere, ever, means the column holds the INSERT instant on every row.** `payout_requests` carries a second column with exactly that definition and exactly that absence of a writer:

| Column | Declared | Default | Ever written by any deployable? |
|---|---|---|---|
| `approved_at` | [`0010:89`](../../packages/db/migrations/0010_payouts.sql) | `NOT NULL DEFAULT now()` | **NO** |
| `created_at` | [`0010:123`](../../packages/db/migrations/0010_payouts.sql) | `NOT NULL DEFAULT now()` | **NO** |

**So `approved_at` is a second copy of `created_at` under a name that claims a decision the row has not necessarily made.** That is the defect stated exactly. It is not that the column cannot be null; it is that the column answers a different question from the one its name asks, and the nullability is merely the place where the difference becomes visible.

**AND IT IS THE ONLY ONE OF FOUR STATE TIMESTAMPS OF WHICH THAT IS TRUE.** `payout_requests` records the entry instant of four of its five states. Three are `NULL` and bound to their state by a CHECK. One is neither:

| State | Timestamp | Nullable | Bound to its state |
|---|---|---|---|
| `approved` | `approved_at` [`0010:89`](../../packages/db/migrations/0010_payouts.sql) | **NO** | **NO CONSTRAINT ANYWHERE** |
| `settled` | `settled_at` [`0010:90`](../../packages/db/migrations/0010_payouts.sql) | YES | `payout_requests_settled_has_days` [`0010:152-157`](../../packages/db/migrations/0010_payouts.sql) |
| `frozen` | `frozen_at` [`0010:105`](../../packages/db/migrations/0010_payouts.sql) | YES | `payout_requests_freeze_is_complete` [`0010:141-149`](../../packages/db/migrations/0010_payouts.sql) |
| `held_pending_review` | `held_at` [`0031:47`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql) | YES | `payout_requests_hold_is_complete` [`0031:62-72`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql) |

**`approved_at` IS THE OUTLIER ON ITS OWN TABLE, AND THE REPAIR IS TO MAKE IT MATCH ITS THREE SIBLINGS.** That is not a preference imported from outside: it is `0010`'s and `0031`'s own established shape for a state-entry timestamp, applied to the one column that was written before the state it names had a second way in.

**AND THE CORPUS CONFIRMED THAT SHAPE TWICE MORE, AFTER `0010`, ON TWO OTHER TABLES.** [`0070:153`](../../packages/db/migrations/0070_withdrawal_approval_and_dual_control.sql) gives `wallet_withdrawals` an `approved_at timestamptz NULL` with [`:200-203`](../../packages/db/migrations/0070_withdrawal_approval_and_dual_control.sql)'s `wallet_withdrawals_approved_has_timestamp` splitting the states before approval from those after; [`0016:235`](../../packages/db/migrations/0016_treasury_controls.sql) gives `dual_control_approvals` an `approved_at timestamptz NULL` with [`:255-257`](../../packages/db/migrations/0016_treasury_controls.sql)'s biconditional on `status = 'approved'`. **Two later migrations, two other tables, one shape, and `0010:89` is the only approval timestamp in this schema that does not have it.**

### 3. WHERE THE COLUMN LIES, DERIVED FROM THE MACHINE RATHER THAN FROM THE ONE STATE THE DISPATCH NAMED

[STATE_MACHINES:80-89](../architecture/STATE_MACHINES.md) draws two entry edges and seven transitions. Walking every path a row can take:

| Path a row can take | `approved_at` holds | Is it the approval instant? |
|---|---|---|
| **`held_pending_review`**, entered at request time | the request instant | **NO. NOTHING WAS APPROVED.** |
| **`approved`** via `[*] -->`, approved directly | the request instant | **YES.** They are one instant ([ADR-019](ADR-019.md)) |
| **`approved`** via `G-HOLD-RELEASED`, a released hold | the request instant | **NO. The approval is up to 48 hours later** |
| **`settled`** reached through a direct approval | the request instant | **YES** |
| **`settled`** reached through a released hold | the request instant | **NO** |
| **`frozen`** via `G-FREEZE-DURING-FLIGHT` | inherits either | **DEPENDS ON A PATH THE ROW DOES NOT RECORD** |
| **`failed`** via `G-HOLD-ENFORCED`, an enforced hold | the request instant | **NO. NOTHING WAS EVER APPROVED** |
| **`failed`** via `G-FREEZE-ENFORCED`, an enforced freeze | inherits either | **DEPENDS ON A PATH THE ROW DOES NOT RECORD** |

**SO THE COLUMN LIES ON FOUR OF THE EIGHT PATHS AND `status` DISCRIMINATES ONLY ONE OF THEM.** This is the finding that decides the ruling, and it is why the read-side repair of section 6 cannot be the answer.

**THE ROW CANNOT TELL YOU WHICH PATH IT TOOK, AND THAT IS A CONSTRAINT WORKING AS DESIGNED RATHER THAN A GAP.** `payout_requests_hold_is_complete` ([`0031:62-72`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql)) is a biconditional on `status = 'held_pending_review'`, so **all five hold columns are NULL the instant the row leaves that state**. A released hold in `approved` and a request approved directly are byte-identical rows. [ADR-290](ADR-290.md) finding `F5` states the same mechanism from the trader's side: *"A trader held for forty hours and then paid sees a payout indistinguishable from one that was never held."*

**AND ON THE AUTO-RELEASED ARM THE TRUE APPROVAL INSTANT IS RECORDED NOWHERE AT ALL.** [`admin-payouts.ts:151-153`](../../apps/api/src/routes/admin-payouts.ts) says the operator release leaves it in `admin_actions.created_at`, *"durably and append-only"*. **The expiry sweep leaves no such row, deliberately**: [`expiry.ts:190-192`](../../apps/worker/src/sweeps/expiry.ts) refuses one because *"an expiry is nobody's decision"*, and `hold_expires_at`, which would have carried the instant, is NULLed by the same biconditional on the way out. The event that would carry it, `payout.hold_released`, has no producer in this tree ([ADR-290](ADR-290.md) section 3.4). **So a hold released by the clock loses its approval instant irrecoverably, today, by construction.**

### 4. THE TWO MERGED FILES THAT ALREADY MET THIS, AND WHAT THEY DID AND DID NOT RULE

**THIS DEFECT IS NOT NEW AND THIS ROW IS ITS FOURTH SIGHTING.** It is [ADR-158](ADR-158.md) finding 15, restated as that entry's owed item 1 at [`:155`](ADR-158.md): *"a false approval time on the one state where the trader is being told nothing has been approved."* ADR-158 refused to repair it inside its fence at [`:133`](ADR-158.md) and named the two shapes: *"either a superseding migration or a second edit to `GET /payouts`, and both are outside this fence."* [ADR-290](ADR-290.md) finding `F6` is the third sighting and recorded it rather than fixing it, for the same fence reason. **This row is the first with the standing to decide, and the dispatch's three shapes are ADR-158's two plus the one nobody had proposed.**

**TWO DEPLOYABLES ON `main` REFUSE TO WRITE THE COLUMN AND BOTH SAY THE REPAIR IS A MIGRATION'S.** [`admin-payouts.ts:143-153`](../../apps/api/src/routes/admin-payouts.ts):

> `approved_at` IS LEFT AS IT STANDS AND THE FINDING IS INHERITED, NOT REPAIRED. [...] This endpoint holds the true approval instant and still does not write it, because writing it would DESTROY the request instant irrecoverably to correct a value ADR-158 has already dispositioned [...] Overwriting is the lossy direction and the repair is a superseding migration's.

[`expiry.ts:203-205`](../../apps/worker/src/sweeps/expiry.ts) inherits that reason verbatim.

**THEIR REFUSAL IS CORRECT, IT IS EVIDENCE FOR THIS RULING RATHER THAN AGAINST IT, AND ITS PREMISE EVAPORATES THE DAY `0077` LANDS.** They refuse because the column arrives PRE-FILLED with a value that is the only surviving record of the request instant, so writing the approval instant over it destroys a fact. **Under `0077` the column is NULL while held, `created_at` holds the request instant durably, and the release write destroys nothing.** The objection is an artifact of the defective column and not a standing argument, which is exactly why repairing the column is what unblocks the write those two files declined.

**AND NEITHER FILE RULED THE PROJECTION, BECAUSE NEITHER PROJECTS TO A TRADER.** Their sentence *"the repair is a superseding migration's"* is about the WRITE. It is quoted here so that slice 7's implementer, who will find it, reads it as the disposition of a write rather than as a licence to read the column raw.

### 5. SHAPE 1 REFUSED: THE WIRE TYPE MOVES

**Refused.** `approved_at` would stop being nullable and the hold's shape would be carried elsewhere.

**IT DOES NOT REMOVE THE LIE. IT REMOVES THE ABILITY TO EXPRESS THE TRUTH.** A non-null wire field must be filled on a held row, and the only value the row has is the request instant, which is the false approval time. This shape takes the one field that can currently say *"nothing was approved"* and requires it to say something else.

**THE HOLD'S SHAPE IS ALREADY CARRIED TWICE OVER AND DOES NOT NEED THIS FIELD.** `hold: PayoutHold | null` ([`payouts.ts:269`](../../apps/api/src/routes/payouts.ts), [API_CONTRACT:518-522](../architecture/API_CONTRACT.md)) is present exactly on `held_pending_review`, and `payout_requests_hold_is_complete` is a biconditional on that same status, so the wire's null arm and the database's constraint agree with nobody deciding anything. `status` itself carries the member. **So the premise of `payouts.ts:256`, that the nullability is the hold's WHOLE shape, is generous to itself; the hold has two other tellers.** That does not rescue this shape, because the field would still be publishing a false instant.

**THE FROZEN CONTRACT WOULD HAVE TO BE AMENDED AGAINST A SENTENCE THAT IS TRUE.** [`API_CONTRACT:516`](../architecture/API_CONTRACT.md) and [`:530`](../architecture/API_CONTRACT.md) state the nullability and the reason for it, and both are correct. **Narrowing a frozen type to accommodate a defective column inverts the direction of repair.**

**AND FOUR PORTAL FILES ALREADY HANDLE THE HONEST CASE CORRECTLY.** [`view.ts:104`](../../apps/portal/src/app/payouts/view.ts), [`wire.ts:91`](../../apps/portal/src/app/payouts/wire.ts) and [`source.ts:191`](../../apps/portal/src/app/payouts/source.ts) all type it nullable, and [`sections.ts:316`](../../apps/portal/src/app/payouts/sections.ts) renders `NOT_REPORTED` on null. **This shape would break a rendering path that is already right.**

**TRADER-VISIBLE CONSEQUENCE: a held trader is shown an approval time for an approval that has not happened, with no way for any client to detect it.** This is the worst of the three and it is the only one that makes the tree worse than it is today.

### 6. SHAPE 2 REFUSED: THE PROJECTION DERIVES THE NULL FROM `status`

**Refused, and this is the refusal worth arguing with, because it is what [ADR-290](ADR-290.md) `F6` recommended** in the words *"`listPayouts` must therefore SUPPRESS `approved_at` when `status = 'held_pending_review'`"*. **That instruction is necessary and it is not sufficient, and section 3 is why.**

**`status` DISCRIMINATES ONE OF THE FOUR LYING PATHS.** Suppressing on `held_pending_review` repairs the held row and leaves a **released hold sitting in `approved` publishing the request instant as its approval time**, wrong by up to 48 hours, on a row no projection can distinguish from a direct approval. It leaves both `failed` arms unrepaired and indistinguishable from each other. **A rule that fixes one of four cases and reads as though it fixed the field is a partial repair that reads as a complete one.**

**THIS CORPUS HAS ALREADY RULED THAT EXACT SHAPE, ONE FIELD OVER, AND REFUSED IT.** [ADR-290](ADR-290.md) section 3.2 refused folding the surviving timestamps into `timeline` because two of the four are NULLed on exit: *"A partial history that reads as a complete one is worse than an empty one."* **The fold ADR-290 refused and the suppression ADR-290's own F6 recommended are the same move on the same table against the same two constraints.** F6 is narrower than its own neighbouring section, and this row overturns it rather than inheriting it.

**IT ALSO REPAIRS ONE READER OUT OF FIVE.** The column is read by [`admin-payouts.ts`](../../apps/api/src/routes/admin-payouts.ts), [`expiry.ts`](../../apps/worker/src/sweeps/expiry.ts), [`account.ts:575`](../../apps/api/src/admin-source/account.ts), the portal's four files, and `listPayouts` when it exists. **A rule living in one projection is a rule every other reader must independently remember**, and the register of this corpus's own defects is largely a register of facts stated in more than one place that then disagreed.

**AND IT WOULD BE THE THING THAT STOPS `0077` EVER BEING WRITTEN.** A read-side suppression makes `GET /payouts` look correct, which removes the visible symptom that is the only pressure toward repairing the column. That is the precise mechanism [ADR-158](ADR-158.md) named and lost to twice already.

**TRADER-VISIBLE CONSEQUENCE: a trader held for forty hours and then paid is shown an approval time forty hours before the approval, on a row that renders as though nothing unusual happened.** Strictly better than shape 1 and strictly worse than shape 3.

### 7. THE RULING. SHAPE 3: `0077` SUPERSEDES THE COLUMN, AND IT IS SPECIFIED HERE AND NOT WRITTEN

**`payout_requests.approved_at` BECOMES NULLABLE, LOSES ITS DEFAULT, AND IS BOUND TO ITS STATE BY A CHECK, ON THE MODEL ITS OWN THREE SIBLING TIMESTAMPS AND TWO LATER MIGRATIONS ALREADY USE.** `0010` is **NOT EDITED**. This is an addition from outside it, which is [`0070:151`](../../packages/db/migrations/0070_withdrawal_approval_and_dual_control.sql)'s own idiom: *"`0011` IS UNTOUCHED. This is an addition from outside it, not an edit of it."*

**A MIGRATION NUMBER IS RESERVED IN [ALLOCATION](ALLOCATION.md) AND NO FILE IS WRITTEN. `0077` IS THE NUMBER.** Constitution `E2`: a merged migration is never edited, only superseded, and the supersession is a founder read before it is a session's transcription.

**The shape owed, stated so the row that writes it does not re-derive it:**

```
ALTER TABLE payout_requests
  ALTER COLUMN approved_at DROP NOT NULL,
  ALTER COLUMN approved_at DROP DEFAULT;

ALTER TABLE payout_requests
  ADD CONSTRAINT payout_requests_approved_has_timestamp CHECK (
    status = 'held_pending_review' OR approved_at IS NOT NULL
  );
```

**The CHECK is a one-sided implication and NOT a biconditional, and the asymmetry is deliberate.** `held_pending_review` is the only state that is unambiguously pre-approval ([STATE_MACHINES:103](../architecture/STATE_MACHINES.md): *"`held_pending_review` sits BEFORE approval and is not reachable from any other state"*). Every other member of `payout_status` is at or past approval on every path that reaches it, so every other member requires the timestamp. **It is `0070`'s `wallet_withdrawals_approved_has_timestamp` transposed**, whose own comment states the same split: *"cancelled is reachable only from requested and cooling, both BEFORE approval, and failed is reachable only from transferring, which is after it."*

**FOUR THINGS THE ROW THAT WRITES `0077` MUST DECIDE, NAMED HERE RATHER THAN DISCOVERED:**

1. **The release paths must then WRITE the column**, and this ruling is what makes that write lossless. [`admin-payouts.ts`](../../apps/api/src/routes/admin-payouts.ts) holds the true instant and declines to write it today only because the write would destroy the request instant. Under `0077` it destroys nothing, and **the CHECK makes the omission a `23514` rather than a silent falsehood**, which is the same mechanism [`expiry.ts:491`](../../apps/worker/src/sweeps/expiry.ts) already relies on for the hold columns. **That edit is in neither this fence nor `0077`'s, and it must land in the same wave**, because a release that does not write the column becomes unperformable the moment the CHECK exists.
2. **The index at [`0010:212-213`](../../packages/db/migrations/0010_payouts.sql)**, `payout_requests_identity_approved_idx ON payout_requests (identity_id, approved_at DESC)`, spans a column that becomes nullable. Postgres sorts `DESC` with `NULLS FIRST` by default, so **every held request would sort to the top of a trader's payout list**. Whether that is the wanted ordering or wants an explicit `NULLS LAST` is a decision, and it is the kind that is invisible until a trader with a held payout loads a page.
3. **`0031`'s stated argument must be met head on, because it argues the other way and it is on the record.** [`0031:40-44`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql): *"A superseding migration that relaxes NOT NULL on the money table has a far wider blast radius than one that only adds, and storing the full decision costs nothing."* **That argument is sound and it does not reach this column.** `0031` was choosing whether a held row could store the MONEY, and it verified that it could: `approved_cents`, the split, the ordinal and the pinned plan version are all computed at request time, so nothing needed relaxing. **`approved_at` is the one column on that table whose value does not exist at request time**, and `0031`'s own principle, store what is computed and defer only what is not, is therefore an argument FOR relaxing it. **`0031` relaxed nothing because it read `approved_at` as a money column rather than as the fourth state timestamp.**
4. **The blast radius is ZERO today and it grows monotonically from the day slice 6 lands.** `usePayoutBackend` is `BLOCKED` and **nothing in any `src/` tree inserts a `payout_requests` row**: every occurrence of `payoutRequests` across `apps/*/src` and `packages/*/src` is a `rowAt`, `rowsWhere` or `lockAt`, and there is no `insert`. **The table is empty in every environment, so the supersession needs no backfill and breaks no writer, because there is no writer.** The first committed row ends that forever, and it is the strongest reason this ruling should not wait.

### 8. WHAT SLICE 7 DOES NOW, AND THE ONE ORDERING CONSTRAINT

**[ADR-287](ADR-287.md) SLICE 7 IS UNBLOCKED. `listPayouts` READS THE COLUMN STRAIGHT, WITH NO STATUS GUARD.**

```
approved_at: row.approvedAt === null ? null : row.approvedAt.toISOString(),
```

**That is correct under `0077` because the database guarantees the null, and it is correct BEFORE `0077` because no reachable row can make it false.** The proof of the second half is narrow and it is stated rather than assumed: the only paths on which the column lies run through `held_pending_review`, that state is entered at request time or not at all, the only thing that could enter it is the hold branch of `insertPayoutRequest()`, and **[ADR-287](ADR-287.md) slice 8 rules that branch UNSCHEDULABLE** because `HoldFlag.tosClause` has no value space until counsel drafts one. **No held row can exist, so no lying row can exist.**

**SLICE 7 MUST NOT CARRY THE SUPPRESSION `F6` PROPOSED**, and that is a consequence rather than a preference: a guard on `held_pending_review` would be a read-side workaround for a schema defect this row rules must be repaired at the schema, it would repair one of four paths, and per section 6 it is the thing that stops the repair being made.

**THE ORDERING CONSTRAINT IS ONE SENTENCE AND IT IS THE WHOLE RESIDUAL RISK OF THIS RULING: `0077` MUST LAND BEFORE SLICE 8.** Until a held row can exist the straight read cannot lie; the moment one can, it does. **Slice 8's stop condition gains `0077` as a precondition**, alongside the clause vocabulary it already waits on, and since slice 8 waits on counsel while `0077` waits only on a founder read, the ordering is the one this tree would reach anyway.
