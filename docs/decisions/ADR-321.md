## ADR-321: a commission is not the firm's, and now it is not anonymous either. `0078` adds the one column three sibling tables already carry, a composite foreign key makes the denormalized affiliate unable to disagree with its parent, and the registration follows the column rather than the other way round (2026-09-05, status: proposed)

**[ADR-304](ADR-304.md) ruled that `affiliate_commissions` is ONE COLUMN away rather than a seventh scope class away, reserved `0078` for that column, and deliberately did not write it. This row writes it.** [`0078_affiliate_commission_owner.sql`](../../packages/db/migrations/0078_affiliate_commission_owner.sql) adds `affiliate_id uuid NOT NULL REFERENCES affiliates(id) ON DELETE RESTRICT`, the agreement constraint that makes it sound, and the index the three per-affiliate sums read. `packages/db/src/schema.ts` then declares the table and `packages/db/src/scope.ts` registers it `derived` via `affiliates`, in that order and never another.

**MONEY PATH. `E2` READ OWED.** `affiliate_commissions.amount_cents` is signed money Merit owes a named affiliate, and until this file the table named no affiliate. Nothing here moves a cent and nothing here writes a row; what it decides is WHOSE money every future row is.

**NO CLASS IS ADDED, NO CLASS IS CHANGED, AND NOTHING ADR-304 RULED IS RE-ARGUED.** The vocabulary is still six. `scopePredicate` is untouched, `ScopedTableKey` gains a member by construction rather than by edit, and no totality assertion moves. **`firm` IS STILL REFUSED** on ADR-304's ground and [ADR-102](ADR-102.md) clause 5's, and it is not re-litigated here.

### 2. The three parts, and each is separately rejectable

Written as parts on `0048`'s, `0033`'s and `0076`'s precedent. Rejecting one leaves the others standing.

**1. THE COLUMN, `NOT NULL`, WITH NO `DEFAULT`.** The three siblings' declaration character for character. A default here is a **wrong affiliate waiting for the first writer that forgets the column**, and a wrong affiliate is silent where a `NOT NULL` is loud.

**2. THE AGREEMENT CONSTRAINT, AND IT IS NOT OPTIONAL.** Part 1 alone denormalizes a tenancy: the same fact now sits on two rows. Two rows that can disagree about who is owed money is **a commission paid to the wrong affiliate**, and that objection was the seventh class's strongest remaining argument. It is closed by the database rather than by care: `UNIQUE (id, affiliate_id)` on `attributions`, redundant for uniqueness against its primary key and existing precisely so a composite edge can name it, then `FOREIGN KEY (attribution_id, affiliate_id) REFERENCES attributions (id, affiliate_id) ON DELETE RESTRICT` on `affiliate_commissions`. **The idiom is copied and not invented**: `reserve_coverage_snapshots_anchor_fk` ([`0049`](../../packages/db/migrations/0049_reserve_coverage_snapshots.sql)) is this estate's other composite foreign key, and a second spelling of one construction is how two constructions come to exist.

**3. THE READ SHAPE.** `affiliate_commissions_affiliate_status_idx (affiliate_id, status)`. `GET /affiliate/stats` renders `earned_cents_lifetime`, `payable_cents` and `paid_cents_lifetime` ([API_CONTRACT section 7](../architecture/API_CONTRACT.md)), which are three sums over this table for one affiliate partitioned by `status`. `0012` declares four indexes here and **none is keyed on an affiliate**, because until the column existed there was nothing to key on.

---

### 3. The constraint constrains BOTH rows, which is why it is a foreign key and not a `CHECK`

**A `CHECK` cannot see another table and a trigger on the child sees only writes to the child.** The composite foreign key refuses disagreement from **three directions**, and all three are executed in [`probe_affiliate_commission_owner.sql`](../../scripts/db/probe_affiliate_commission_owner.sql):

| Direction | The write | Result |
|---|---|---|
| the child, at INSERT | a commission on affiliate A's attribution naming affiliate B | **refused** by `affiliate_commissions_attribution_owner_fk` |
| the child, at UPDATE, as `merit_app` | moving an existing commission to affiliate B | **refused** by the same constraint, by name |
| **the parent** | `UPDATE attributions SET affiliate_id = B` while A's commission cites the pair | **refused** by the same constraint |

**The third is the one nothing else would have caught.** [`0012`](../../packages/db/migrations/0012_disputes_and_affiliate_settlement.sql)'s own comment says an affiliate **can be reassigned**, so the parent moving under a correct child is a documented possibility on this exact table rather than a hypothetical.

### 5. The order, and it could not be inverted

ADR-304 section 4 clause 5 rules it and this row is its first instance. **Migration, then declaration, then rule.** The `schema.ts` transcription and the `derived` rule both name `affiliate_id`, and `scoped-db.test.ts` compares the transcription against the migrations rather than against itself, so a registration landing before `0078` names a column that does not exist and is asserted against nothing.

**THE REGISTRATION COSTS NOTHING, WHICH IS THE POINT ADR-304 MADE.** `derived` via `affiliates` on `affiliate_id`, `traversal: 'hop'`, terminating one hop out at an `owned` rule with `nullable: false`. No new class, no change to `scopePredicate`, no change to any totality assertion, and no judgement the three siblings did not already carry.

### 6. The standing condition is inherited, is stated in the rule's own `why`, and is NOT discharged

**[ADR-253](ADR-253.md) section 6's condition attaches to ROW-LEVEL READABILITY BY ANY ROUTE and not to the class that was refused.** Its words: an affiliate who can read commission rows *"learns HOW MANY attributions they have and can address each one, and if any door ever resolves an `attributions` row from its id for a party, the uuid stops being opaque and [ADR-106](ADR-106.md)'s ground returns one hop out."*

**A `derived` rule returns the same rows the seventh class would have, carrying the same `attribution_id`.** So the condition holds against `0078` exactly as it held against the class. It holds **today**: the one door in this estate that resolves anything about an attribution is `attributionAffiliate`, which takes an `affiliateId` and returns one bit ([ADR-262](ADR-262.md)), and nothing anywhere resolves an `attributions` row from its id for a party. **The day something does, this rule is what has to be re-argued**, and the sentence saying so is in `SCOPE_RULES.affiliateCommissions.why` rather than only here, asserted by a case in [`affiliate-commissions-is-a-column-away.test.ts`](../../packages/db/test/affiliate-commissions-is-a-column-away.test.ts) — because a condition recorded only in an ADR is a condition the next reader of `scope.ts` never sees.

### 7. The finding this row did not expect: the file written to go red on success did not go red

[`affiliate-commissions-is-a-column-away.test.ts`](../../packages/db/test/affiliate-commissions-is-a-column-away.test.ts)'s own header predicted which case `0078` would turn red: *"AND ONE CASE IS WRITTEN TO GO RED ON SUCCESS. `the rail's shape` asserts that this table declares NO edge to `affiliates`. When `0078` lands it will, and this case fails."*

**IT DID NOT FAIL.** Every parser in that file reads a `CREATE TABLE` body, `0012` is merged, and constitution `E2` makes its body permanent — **so the column ADR-304 ruled owed could only ever arrive as an `ADD COLUMN` from outside it, which the file could not see.** The case that went red was `neither 0078 nor 0077 is written`, which reads the directory. Watched at **1 failed of 17** before a line was moved.

**THE SAME BLINDNESS WAS LIVE IN A GENERAL ASSERTION AND THAT ONE IS A DEFECT.** `every derived rule names a foreign key the DDL actually declares` ([`scoped-db.test.ts`](../../packages/db/test/scoped-db.test.ts)) read `ddlColumnDefs` — the `CREATE TABLE` body — while `derivedEdge` twenty cases below already read `foldTableDefs`. It had never mattered, because every `derived` rule registered before this one names a column its own `CREATE TABLE` declares. **`affiliate_commissions.affiliate_id` is the first that does not**, and the assertion failed on a correct rule at `affiliate_commissions.affiliate_id: expected undefined to be defined`. It now reads the fold, which is ADR-094's rule (*a table is read AS OF THE LAST MIGRATION*) arriving on an assertion nobody had moved. **The `firm` assertion two cases below is still blind in the same way**, which [ADR-101](ADR-101.md) section 8 already records as a finding about what the `firm` class promises; it is left where that entry put it.

**BOTH TEST FILES NOW FOLD**, and both keep the CREATE-only reading as a second assertion, because *"the subject's `CREATE TABLE` declares no edge to `affiliates`"* is a permanent fact that a supersession quietly rewriting `0012` would turn red.

### 9. What this row deliberately does not do

1. **IT WRITES NO ROW.** No commission, no attribution, no affiliate. The commission clock is P5's and is unbuilt; this row makes its first row writable and correct.
2. **IT DOES NOT EDIT `0012`.** Constitution `E2`. The supersession is **by addition from outside**, which is `0028`'s, `0048`'s, `0068`'s, `0070`'s, `0072`'s, `0073`'s and `0076`'s mechanism on this estate.
3. **IT DOES NOT DROP `affiliate_commissions_attribution_idx`.** `0012` declares it and the composite key does not make it redundant to a planner reading the attribution alone. Dropping an index a merged migration declared is a supersession this row does not take.
4. **IT CHANGES NO GRANT.** `0026:174` already grants `merit_app` DML here; whether this table belongs in the append-only set is `OI-03`'s question against a document this row does not hold.
5. **IT WIRES NO ADAPTER.** `GET /affiliate/stats` is **not** served by this row. Three of its nine fields now have a door; `conversions_30d` is still a count over a `pair` relation that no scope class reaches, and ADR-304 section 5 sizes the named counting door that serves it. **A session reading only the first half would think the endpoint is one adapter away and it is not.**
6. **IT REPAIRS NO REFUSAL STRING IN `apps/api`.** See section 10.

### Approval

**Status: `proposed`. The approval line is UNSIGNED and merging is not signing.** No `status` field anywhere moves and nothing is marked `accepted`. **`E2` READ OWED**, and it is inherited as well as owed: [ADR-304](ADR-304.md) and [ADR-253](ADR-253.md) are both `proposed` and UNSIGNED, and this entry rests on the first of the two.

  **What a founder read adds and this entry cannot.**

  **THE FIRST THING TO CHECK IS THE ONE NO GATE CAN: THAT A COMMISSION BELONGS TO THE `affiliates` ROW AND NOT TO THE ATTRIBUTION'S FROZEN IDENTITY.** Every check in this diff can tell you the column exists, is `NOT NULL`, and cannot disagree with its parent. **None of them can tell you that `affiliates` is the right parent.** ADR-304 section 4 makes that judgement in one sentence and this file executes it: a commission is what the statement that pays it belongs to, what the balance carrying the clawback belongs to, and what `affiliates.commission_bp` — the rate the amount was computed at — belongs to. The alternative on the row is `attributions.affiliate_identity_id`, which `0012` freezes at the moment of purchase, and the difference only ever shows itself on a reassigned affiliate or a merged identity, which is exactly the case nobody will be watching. **If you rule the other way, `0078` is superseded and not edited, and the supersession is a new number.**

  **THE SECOND IS WHETHER THE DENORMALIZATION SHOULD EXIST AT ALL.** The column stores a fact the database can already derive by joining `attributions`. This entry takes the denormalization because it is what the three siblings do, because a scope rule must name ONE column of THIS row, and because the composite key makes drift unwritable — but a reviewer could reasonably say that a `derived` rule two hops out through `attributions` would have been the honest shape and that ADR-106 is what forbids it rather than the schema. **That is a judgement about which of two costs is smaller and it is not derivable.** It is worth a minute because the answer is permanent: `E2` makes a merged column impossible to remove.

  **THE THIRD IS SECTION 10, AND IT IS THE PART A READ CHANGES.** This row knowingly leaves a shipped refusal string saying four false things, with green tests asserting each of them. The argument for leaving it is the fence; the argument against it is that Merit has now recorded this exact defect three times and built a test file specifically to catch it. **If you rule that the fence should have stretched, the repair is one row and should be dispatched immediately**, and this paragraph is the record that the choice was made rather than missed.

  **WHERE THIS ENTRY IS MOST LIKELY WRONG, named rather than left for a reader to find.** The claim that nothing writes `affiliate_commissions` is a claim about **this tree on this day**, and it is what makes a `NOT NULL` column with no default safe. It was re-measured rather than inherited, and it stops being true the moment the P5 commission clock lands. **If `0078` and that slice are ever in flight together, the slice writes the column or the migration fails, and no gate in this repository would tell either session about the other.**
