## ADR-264: the fold was run rather than reasoned about, the row it wrote is read back by `apps/api`, and what stands between the payout port and 200 is now a deployment and one read on the wrong door  (2026-08-30, status: proposed)

**[ALLOCATION](ALLOCATION.md) row `264` sent this session at the two halves `usePayoutBackend`'s fifteenth reason named: something must RUN the fold so a `rule_states` row exists, and `apps/api` must READ that row back into a `RuleState`.** Both are settled here. **Neither settles the port**, and the reason it does not is a different kind of thing from every reason this entry has carried for sixteen revisions.

- **Origin:** row `264`, session **455**, branch `claude/one-row-from-a-verdict`. **NO MIGRATION IS WRITTEN, RESERVED OR SPENT.** The highest is `0074` and it stays there; `git diff origin/main -- packages/db/migrations` is empty on this branch.

- **MONEY PATH: this is the value `evaluatePayout` folds into the verdict on the door where money leaves the firm.** A field defaulted in the reader is a gate that never fires. The [**`E2`**](../../MERIT_BUILD_MASTER_PROMPT.md) read is **OWED** on this diff. Ships `proposed` with an **UNSIGNED** approval line. **Merging is not signing.**

- **AND IT INHERITS FOUR `E2` DEBTS AS WELL AS OWING ONE.** [ADR-241](ADR-241.md), [ADR-250](ADR-250.md), [ADR-258](ADR-258.md) and [ADR-260](ADR-260.md) are each `proposed` and UNSIGNED, and the measurement in section 2 stands on all four: 241 made the process run, 250 wrote the codec, 258 and 260 resolved the six `AccountDay` fields. **A founder who moves any of them moves the run this entry measured.**

- **`usePayoutBackend` IS NOT WIRED AND THE ROW REQUIRED THAT BE SAID EXPLICITLY RATHER THAN QUIETLY.** [`apps/api/src/start.ts`](../../apps/api/src/start.ts) is untouched, `usePayoutBackend` is called by nothing under any `src/`, the payout routes still answer 503, and **the wired count does not move.** Section 5 says which half refuses and why, and it is not the half this row expected.

- **WHAT IS MEASURED, WHAT IS DERIVED, AND WHAT IS JUDGED**, separated before the argument starts. That the nightly fold WRITES a `rule_states` row end to end on a seeded database is **MEASURED**, in section 2, by running it. That the reader rebuilds the same state the writer folded is **MEASURED**, by `SD-08`'s digest, in section 4. That `tradingCalendar` is unreadable on a payout transaction is **DERIVED**, from two closed lists, in section 5. What is **JUDGED** is that an absent row is a refusal and never a default verdict (section 3), that the reader is pure and the caller reads the rows (section 3), and that the second transcription is registered rather than moved (section 6).

- **A DISPATCH PROMPT IS NOT A SOURCE.** Every claim the row carried was re-derived on this tree before a line was written. **One of them did not hold and it is the row's own second sentence**: section 2.

### 1. The question the row asked first, and why it was the right one to ask first

The row said, in terms: *does the fold, end to end on a seeded database, actually WRITE a `rule_states` row today? `ADR-260` says it completes. **Completing and persisting are different claims and this row does not assume the second.***

That distinction is the whole of section 2 and it was worth making. `ADR-260` section 5's claim is about `loadAccountDay` resolving six fields of six, and `runNightlyBatch` calling five methods that all answer. **Neither sentence is a claim that a row lands in a table.** Between the fold and a stored row stand `writeRuleStateVia`, `encodeEngineGates`, a `bytea` a trigger checks is thirty-two bytes, an insert-only table whose `UPDATE` and `DELETE` were revoked by `0026`, and nine other constraints. A session that had read those files and reported "the fold writes a row" would have been reporting a chain of inferences, and this port has been wrong four times about exactly that shape of claim.

### 3. THE READER, AND THE TWO RULINGS INSIDE IT

[`apps/api/src/rule-state-reader.ts`](../../apps/api/src/rule-state-reader.ts). **Two functions, two error classes, and no third outcome anywhere in the module.**

`readRuleState(value, at)` rebuilds the engine's `RuleState` from one row. `ruleStateOn(rows, accountId, tradingDay)` selects the row for one day out of the rows the caller read, and refuses.

#### RULING 1: it is PURE, and the split is `resolveExternalGates`'s split unchanged

Nothing in the module opens a transaction, names a table key or reaches `@merit/db`. **The CALLER reads the rows on the handle it already holds and what it gets back is the NARROWING.** `ruleStates` is registered `derived` via `accounts` ([`scope.ts`](../../packages/db/src/scope.ts)), so a payout transaction reaches those rows one hop out and this field implies no second door.

That is [ADR-260](ADR-260.md) ruling 1 applied one field over, and the reason is stronger here than it was there: **a reader that opened its own transaction would be a second snapshot**, and a payout evaluated across two snapshots can read a state written after the account row it is being folded against.

#### RULING 2: AN ABSENT ROW IS A REFUSAL AND IT IS NEVER A DEFAULT VERDICT

**This is the trap the row named, it is the one this port has refused four times, and it is why the module has two error classes and no fallback arm.**

`rule_states` holds no row for an account-day until a nightly fold has closed that day. A reader that answered such a day with a zeroed state, with a carried-forward state, or with the latest row it could find would put a **confident** payout verdict in front of a trader on inputs nobody computed. `R-41` conjoins the context gates as vetoes and `evaluatePayout` reads the rest of this value for the engine gates, so every field of a fabricated state is a gate that never fires. **A wrong answer that returns 200 is worse than an honest 503.**

`RuleStateAbsent` is a distinct class from `RuleStateUnreadable` **because the operational days are different**: an absence is a fold that has not run, and a malformed row is a database question. Neither is a state.

**AND `R-06` IS WHY THE DAY IS AN ARGUMENT RATHER THAN AN ORDERING.** *"No endpoint may evaluate eligibility against anything other than the last closed day, whatever the batch is doing at the time."* A reader that fell back to the most recent row it could find would answer a payout request out of a state computed before the nights in between, **which reads as a working endpoint and pays against a floor that has moved.** There is no `latest` function in the module and `rule-state-producibility.test.ts` link 6 sweeps for one.

**NOTHING DEFAULTS.** Twenty-two fields, and every read throws where a `??` would have been. A cents column that arrives as a `number` is REFUSED rather than coerced, on `INV-02`: a `number` here has already passed through a conversion this module did not make, and past 2^53 it has already lost digits. `0065`'s `breached = (breach_kind IS NOT NULL)` pairing is checked on the way past and refused rather than repaired, because a `null` kind on a breached row tells a consumer about a drawdown type that never happened.

**THREE COLUMNS ARE NOT READ.** `context_gates` is `INV-23`'s half that never enters the replayed state, `state_hash` is computed FROM a state rather than carried by one, and `calendar_revision_id` is [ADR-047](ADR-047.md)'s stamp on the row. A `RuleState` has no field for any of the three, and a case in the suite damages all three and watches the digest still close.

### 4. THE ASSERTION, WATCHED RED BEFORE GREEN, AND THE THING IT COMPARES

[`apps/api/test/rule-state-reader.test.ts`](../../apps/api/test/rule-state-reader.test.ts), thirteen cases. **The row in section 2 is the fixture, column for column, as `SystemTx.rowsWhere('ruleStates', ...)` returned it**, and `FOLDED_STATE_HASH` is what `rule_states.state_hash` holds for it.

**THE ONE CASE THIS FILE EXISTS FOR IS A DIGEST COMPARISON AND NOT A FIELD COMPARISON.**

`SD-08`'s hash is computed by `apps/worker` from the `RuleState` the engine folded, BEFORE the row is written, over nineteen columns and twenty-five gate leaves in [ADR-026](ADR-026.md) C-07's order. So re-hashing the state THIS reader rebuilds and comparing the thirty-two bytes **compares the writer's transcription with the reader's, through a value neither of them can adjust.** The engine is the only implementation of the digest ([ADR-081](ADR-081.md) moved it out of `apps/worker`) and `@merit/rules-engine` is a declared dependency of `apps/api`, so the comparator needs no cross-deployable import at all.

**RED BEFORE GREEN, BOTH WATCHED AND BOTH RECORDED.**

| # | State of the tree | Result |
|---|---|---|
| 1 | the suite written, `apps/api/src/rule-state-reader.ts` absent | **RED.** `Cannot find module '../src/rule-state-reader.ts'`, 1 failed suite, no tests |
| 2 | the module written | **GREEN.** 13 passed |
| 3 | the module perturbed: `balanceCents` read, then `+ 1` cent | **RED.** the digest reads `9e8b0a45891d4744...` against the stored `68d7303f2d7282a3...`, 3 failed |
| 4 | perturbation reverted from a byte copy | **GREEN.** 13 passed |

**Case 3 is the one that matters and it is why the comparator is not decoration.** One cent, on one field, out of twenty-two, moves the whole digest. A suite that compared the rebuilt state field by field against a literal would have been comparing this session's transcription with this session's other transcription.

**THE OTHER TWELVE CASES ARE THE REFUSALS**, and each is executed rather than asserted about: every NOT NULL column deleted in turn and watched refusing (eighteen of them), the three NULLABLE columns watched reading `null` so that case is not vacuous, a `phase` of `provisioning_pending` refused, a cents column arriving as a `number` refused, both halves of the `0065` breach pairing refused and the correct pair watched reading, a gate leaf removed from the bag and watched failing in the ENGINE's decoder, an absent row raising `RuleStateAbsent` with the account and day on it, **a row for a NEIGHBOURING day raising the same refusal** (`R-06`), two rows for one day refused rather than one being chosen, and a row belonging to another account refused.

### 5. WHETHER THE PORT IS WIREABLE. IT IS NOT, AND THE HALF THAT REFUSES IS NEW

**The row asked for this explicitly and it gets an explicit answer: `usePayoutBackend` DOES NOT BECOME WIREABLE, and nothing in this diff installs a backend.**

**WHAT CHANGED IS THE CHARACTER OF THE REMAINDER, AND IT IS WORTH THE PARAGRAPH.** Sixteen revisions of this reason have each named something nobody had BUILT: a job nothing called, an adapter that refused, a codec nobody had written, a resolver nobody had written, a reader nobody had written. **Every one of those is now built.** What stands is two things, and neither is a capability:

**FIRST, NO DEPLOYMENT HAS RUN THE JOB.** [ADR-241](ADR-241.md) ruled the schedule EXTERNAL and registered it in [`CRON_INVENTORY`](../ops/runbooks/CRON_INVENTORY.md), on the argument that a long-lived process has no exit code to fail with. **That ruling is honoured here and no in-process timer was built**, which the row named as its second trap. The consequence is that whether a row exists in a real database is an operator fact this repository cannot assert, and section 2 measured the capability rather than the deployment.

**SECOND, AND IT IS THE FINDING: THE DAY IS UNREADABLE ON THE TRANSACTION THAT READS THE STATE.** `R-06` permits exactly one day, so `subject()` must select the stored row BY DAY. The calendar that says which day that is is `tradingCalendar`, whose scope class is `firm`, and [ADR-233](ADR-233.md)'s `CATALOG_TABLE_KEYS` is a **closed list of five** -- `coupons`, `geoRestrictions`, `midHealth`, `planVersions`, `planVersionSizes` -- which does not include it. `ScopedTableKey` is `Exclude<TableKey, FirmTableKey | PairTableKey>`, so `rows`, `rowsWhere` and `rowAt` cannot be handed that key either. **A `ScopedTx` cannot read the trading calendar at all.**

**THE READ EXISTS IN THIS DEPLOYABLE, ON A DIFFERENT DOOR, WHICH IS WHY THIS IS A SECOND TRANSACTION RATHER THAN A MISSING CAPABILITY.** `databaseEconomicCalendar` ([`routes/economic-calendar.ts`](../../apps/api/src/routes/economic-calendar.ts)) reads `tradingCalendar` through `ApiDb.firm`. So what `subject()` needs is one of exactly two things:

1. **[ADR-211](ADR-211.md) clause 2's TWO-TRANSACTION REMEDY**, needed again on the CALENDAR half after [ADR-233](ADR-233.md) removed the need for it on the CATALOGUE half. Nobody has ruled it acceptable on this path, and the entry that removed it elsewhere removed it on the ground that one transaction is better.
2. **A SIXTH CATALOGUED KEY**, which `refuseUncatalogued`'s own message describes as *"a diff on packages/db with an argument attached"*.

**NEITHER IS TAKEN AND THE REASON IS THE FENCE.** Row `264` fences `apps/api/src/routes/payouts.ts`, `apps/api/src/start.ts`, one reader module, `apps/worker/src/batch/**`, the two suites, `CRON_INVENTORY` and this entry. **`packages/db` is not in it**, and widening a fence to finish is the same move as weakening a gate to pass it. **The finding is registered, sized, and the next row can take it in either direction.**

**THIS CLAUSE HAD NEVER BEEN NAMED ON THIS PORT**, which is the fifth time this entry has produced that sentence and the reason `rule-state-producibility.test.ts` exists: a reason naming the second-cheapest blocker retires the question for every reader after it. It is link 6 there, derived from both closed lists on every `CI-01` pass.

**AND THE OTHER FIVE MEMBERS OF `PayoutBackend` ARE NOT CLAIMED TO BE READY.** This entry establishes `PayoutSubject.state`. `identityStatus`, `holdFlag`, `insertPayoutRequest`, `listPayouts` and `idempotency` were not built, not audited end to end, and are not what section 5 is about; the port's reason names `listPayouts` and `idempotency` as constructible today and this session did not re-derive that.

### 6. THE SECOND TRANSCRIPTION, REGISTERED RATHER THAN MOVED

**`toRuleState` in [`apps/worker/src/batch/adapter.ts`](../../apps/worker/src/batch/adapter.ts) and `readRuleState` in `apps/api` read the same twenty-two values off the same row.** `apps/api` cannot import `apps/worker`. **That is `FM-16` by name: two statements of one predicate.**

**ITS HOME IS `packages/rules-engine`, BESIDE `gates-codec.ts`, ON [ADR-239](ADR-239.md) SLICE A's ARGUMENT UNCHANGED** -- both deployables need the one rebuilding, neither can import the other, and that package declares no workspace dependency at all, so it is the only place both arrows already point. **That package is not in this row's fence**, and this is `adapter.ts`'s own precedent for the second `plan_versions.rules` decoder, registered there and not taken.

**WHAT `FM-16` ACTUALLY COSTS IS "WITH NOTHING COMPARING THEM", AND THAT HALF IS PAID.** Section 4's digest is a comparator between the two transcriptions that runs on every `CI-01` pass, over a value neither of them can adjust. **A shared module would make the two agree by construction and would prove nothing about whether the STORED row survives the trip**, which is the property that actually matters on a money path and the one no amount of code sharing supplies. So the finding is real and the exposure is smaller than the shape suggests; the merge is owed and it is not urgent.

**WHAT IS OWED, SIZED.** One module in `packages/rules-engine` taking a `Record<string, unknown>` and returning a `RuleState`, both call sites repointed, and the digest comparator kept. It is small, it is `FM-16`, and it should be one row.

### 8. Where this entry is most likely wrong

**Named rather than left for a reader to find.**

**THE SEED IS ONE ACCOUNT ON ONE DAY IN PHASE `eval`, AND THAT IS THE NARROWEST BOOK A FOLD CAN HAVE.** It exercises `prior: null`, an empty KYC chain, no settlements, no payout requests and a pristine calendar. **A funded account with a stored prior, a settled payout and a corrected calendar is a different path through `resolveAccountDay` and this session did not run it.** What the measurement establishes is that the chain from `daily_marks` to a stored row is unbroken, not that every branch inside it is. **The digest in section 4 is over the row that path produced**, so a defect on a branch nothing traversed is invisible to both halves of this entry.

**THE READER'S SELECTION CONTRACT ASSUMES THE CALLER KNOWS THE LAST CLOSED DAY, AND SECTION 5 IS THAT NO CALLER ON THIS TRANSACTION DOES.** So `ruleStateOn` ships with a correct signature and no correct caller. That is deliberate -- the alternative was a `latest` arm that would have been wrong forever -- but it means the one function on this path that could still be designed wrong has not met its call site.

**THE `FM-16` JUDGEMENT IN SECTION 6 IS A JUDGEMENT.** A reviewer may hold that a second transcription of a money-path row should not have been written at all while its home was out of fence, and that the row should have stopped and reported instead. The counter is that the comparator makes this pair strictly better observed than a shared module would be, and that the reader is the deliverable the row asked for. **It is one module either way and the merge is cheap.**

**AND THE `state_hash` FIXTURE IS A CONSTANT IN A SUITE.** It came out of PostgreSQL and nothing in `CI-01` re-derives it from a database. If the engine's serialization changes, that case goes red and the correct repair is to re-run section 2 rather than to update the constant. **A session that updated the constant to make the suite pass would have deleted the comparator**, and this paragraph is the only thing standing in its way.
