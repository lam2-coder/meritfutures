### 5. THE RULING. A short position is a HOLD, and it is this row's one judgement

**[ADR-316](ADR-316.md) SECTION 3.5 IS EXPLICIT THAT THIS IS OWED AND THAT IT IS THE SLICE'S:** *"`decideApproval` HAS NO SUCH TERM ... The function is sound as written, because `driveApprovals` posts nothing and therefore debits nothing, and it is not sufficient for a driver that does."* `APPROVAL_HOLDS` has no member naming a short position and `insufficient_funds` ([`wallet-withdrawals.ts`](../../apps/api/src/routes/wallet-withdrawals.ts)) is a request-time HTTP refusal that is not this. **That entry made a RECOMMENDATION and refused to rule it, naming the counter-argument.** This row rules it.

**THE RULING: a position that will not cover the debit is a HOLD, named `insufficient_position`, minted in `apps/worker` and evaluated LAST. The row stays open and the next run retries. It is never a cancellation and never a refusal.**

**FOUR REASONS, AND THE THIRD IS THE ONE THAT DECIDED IT.**

1. **THE MONEY IS MONEY THE TRADER SPENT.** The only way the position falls between request and approval is a debit, and the only debit this schema has beside this one is `LT-08`, the wallet-funded purchase. **That is the trader buying something with their own balance**, and closing their withdrawal over it is Merit deciding what they should have spent it on.
2. **A HOLD IS "NOT YET" AND A CANCELLATION IS "NO".** `APPROVAL_HOLDS`' own docblock rules the distinction: *"A guard that does not hold is 'not yet' rather than 'no'"*. A cancellation is a denial, and the constitution's third product constraint is **zero denials, ever**, with abuse handled at detection time and never at request time.
3. **THE COUNTER-ARGUMENT IS ANSWERED BY `0072` AND THIS IS WHAT SETTLED IT.** [ADR-316](ADR-316.md) refused to rule because *"a hold that never clears sits inside `G-NO-IN-FLIGHT` forever and the counter-argument is real."* **It is real and it is not fatal, because the trader's own exit is still open.** [`0072:211-218`](../../packages/db/migrations/0072_terminal_withdrawal_transitions.sql) raises `WD-C2` only when `NEW.status = 'cancelled' AND OLD.status NOT IN ('requested', 'cooling')`, and it says why in its own words: *"`G-TRADER-CANCELS` is drawn from requested and from cooling and from nowhere else, both BEFORE approval."* **A held row is `requested` or `cooling`, so the trader can take it back whenever they choose.** The lockout is not indefinite; it is under the trader's own hand, which is the one hand that should hold it. **The same sentence is false one arrow later**, which is exactly [ADR-305](ADR-305.md) section 5's finding and is why slice 9 is blocked.
4. **THE DATABASE IS THE BACKSTOP AND NOT THE CONTROL.** `balance_after_cents >= 0` ([`0011:90`](../../packages/db/migrations/0011_wallet.sql)) is `INV-M20-01`'s DDL half. The term refuses the row before the arithmetic is done, so a `23514` from Postgres on this path means this file is wrong rather than that the database saved it. **This driver is the first writer in the application to exercise that CHECK at all**, which section 6 measures.

**IT IS EVALUATED LAST, AFTER THE SEVEN, AND THE REASON IS `decideApproval`'s OWN.** That function puts dual control last because it is the only term whose answer changes when a second person acts. **The position is the only term whose answer changes when NOBODY acts**, so reporting `insufficient_position` above a standing identity refusal would tell a trader to wait for money when what actually blocks them is a restricted identity.

**`>` AND NOT `>=`.** A withdrawal that empties the wallet exactly is a wallet emptied and not an overdraft, and `balance_after_cents >= 0` admits the zero row it produces. Two cases sit either side of the boundary.

**AND THE POSITION IS THREADED THROUGH THE LOOP RATHER THAN RE-READ.** An identity with two approvable withdrawals must see the first debit before deciding the second, and re-reading `wallet_entries` inside the loop would read rows this transaction has not committed. Two cases assert the running balance walking down.

**`APPROVAL_HOLDS` IN `apps/api` IS NOT WIDENED**, which keeps [ADR-316](ADR-316.md) section 9's claim true. The name is minted in `MACHINE_APPROVAL_HOLDS` in `apps/worker`, which is that entry's own ruling that *"the driver states its own machine arm"*.
