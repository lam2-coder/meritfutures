### 4. Why a pinned list is the vacuous answer, stated as the argument that chose the design

The dispatch is explicit that a green check which cannot fail is worse than none, because it retires the question falsely. **The obvious implementation is exactly that check**, and it is worth writing down why, because it is the version a later row would otherwise re-invent.

Pin `updateStatementOn`'s three names. Now run the motivating failure: somebody adds `refuseCurrencyColumn`, puts it in `scopedInsertStatement`, and does not put it in the update builder. **The update builder's list is still the same three. The pin is still satisfied. The check is green and the money-path builder is missing a rule that another builder has.** That is item 5's sentence word for word, and the obvious check does not see it.

So the assertion is over the MATRIX and it is four legs:

- **Leg A, the guard roster is closed.** Every `refuse*` declared in `scoped-db.ts` is pinned. A rule that ARRIVES is named the moment it is declared, before anybody asks where it was placed.
- **Leg B, the write-builder roster is closed.** Every function that constructs a write is pinned. A NEW builder carrying no guards at all is item 5's failure arriving one level up, and leg B is the only leg that sees it.
- **Leg C, the matrix is pinned**, per builder, together with the count of refusals that builder throws INLINE rather than through a named guard. **The throw count is not decoration**: a fourth rule can arrive as a bare `throw new Error(...)` in a builder's body, which legs A and D cannot see by construction, and the count is what sees it. Editing an existing message does not move it; adding a refusal does.
- **Leg D, every empty cell is declared**, with a reason, classed `SETTLED` or `OPEN`.

**LEG D IS THE ONE THAT ANSWERS THE MOTIVATING FAILURE AND LEGS A TO C ARE WHAT MAKE ITS INPUTS TRUSTWORTHY.** Under leg C alone an author who adds a guard to one builder updates one cell and is finished. Under leg D that same edit turns every OTHER builder's cell for the new guard into an undeclared absence, and the author has to write down, per builder, why the rule does not apply there. **Section 7 case 1 is that sequence executed, and the check names all five other builders including `updateStatementOn`.**

### 5. What this check cannot do, stated here rather than discovered later

**IT DOES NOT ADJUDICATE AN ABSENCE.** Leg D requires a reason to EXIST. It cannot tell a correct reason from a plausible one, and a cell classed `OPEN` keeps the check green **on purpose**, because a check that went red on the tree it ships with is a check somebody deletes in the first week. What this converts is an unwritten convention into a written one with a tripwire on it. **That is the whole of the claim and it is deliberately smaller than "the guard set is correct".**

**IT READS NAMES AND NOT BEHAVIOUR.** A guard is a function whose name matches `refuse[A-Z]`. That convention is real and file-wide, nine declarations with no exceptions on this base, but it IS a convention, and a refusal added under another name is invisible to legs A and D. **Leg C's inline-throw count covers one half of that hole and not the other**: a refusal written inline is counted, and a refusal written as a helper called `checkCurrency` is not. **Naming that limit is cheaper than pretending the check is a semantic analysis**, and the honest price of closing it is a rule that no function in this file may throw except one matching the convention, which is a lint rule and not this row's.

**IT IS COUPLED TO NAMES, AND DELIBERATELY NOT TO LINE NUMBERS OR ORDERING.** [ADR-450](ADR-450.md) refused a control partly because it would break on every refactor. That objection was tested here rather than assumed: the matcher searches a whole function body for a call by name, so moving a guard within a builder, reordering the three, reformatting the chain or reflowing the file leaves it green. **What turns it red is a change to WHICH builder calls WHICH guard**, which is the change it exists to see.

### 6. The finding: one absence with no reason, measured rather than asserted

`insertUnderStatement` at [`:2181`](../../packages/db/src/scoped-db.ts) builds `source.insert(table).values(values).returning()` from a caller-supplied `values` object and calls **none** of the three write guards. Its three absences are not alike.

1. **`refuseTenancyColumn` is SETTLED and the source argues it beside the code.** A `derived` row REACHES its identity through the parent edge, which `tenancyColumns` at [`:407`](../../packages/db/src/scoped-db.ts) returns as that row's tenancy column, and PROVING that parent is the whole contract of this builder. The file says it at `:2224`: *"`refuseTenancyColumn` refuses both spellings on the paths that stamp; this one requires one and refuses the other."* **Calling the guard here would refuse every insert the builder exists to make.** `pairInsertStatement`'s absence of the same guard is settled the same way and argued in the same voice at its own site.
2. **`refuseGeneratedColumn` is OPEN and already priced.** [ADR-448](ADR-448.md) section 8 item 3 owns it, for all four insert builders, and this row does not reopen it.
3. **`refuseTermInValues` is OPEN AND NOTHING ANYWHERE HAS EVER SAID WHY.** Every other builder that takes a values object calls it. This one does not, and `grep -in term` over the whole of its body returns nothing.

**THE EXPOSURE IS MEASURED AND IT IS NARROW, WHICH IS SAID PLAINLY RATHER THAN DRESSED UP.** `insertUnder` has **one** live producer in the tree, [`auth-backend.ts:1092`](../../apps/api/src/auth-backend.ts), and its key type `ParentedTableKey` at [`:2149`](../../packages/db/src/scoped-db.ts) is `Extract<DerivedTableKey, 'sessions'>`, a closed list of one. **`sessions` is not a money table and no caller passes a term today, so no live defect is demonstrated and none is claimed.** What is claimed is narrower and is the point of the row: this is a values-object builder missing a values-object guard for no recorded reason, it is precisely the shape item 5 says nobody is watching, and until this check existed nothing in the tree would have mentioned it.

**IT IS NOT REPAIRED HERE AND THE REASON IS THE CONSTRAINT, NOT THE APPETITE.** `refuseTermInValues` returns `void`, so placing it in that builder means INSERTING a line at roughly `:2194`, and **172 of this file's cited lines sit below that point**. The repair that moves nothing is the one `refuseGeneratedColumn` already demonstrates: an expression-shaped variant returning the values it cleared, substituted into the existing `.values(...)` argument at `:2282`. **Price: that variant, its four other call sites left on the void spelling or migrated with them, and a row that owns this file.** The absence is declared `OPEN` in the check, so the debt is carried in something that runs rather than in prose.
