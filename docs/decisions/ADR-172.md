### 2. THE RULING

> **Clause 1. THE TWO FINDINGS ARE TWO QUESTIONS AND NOT ONE SEAM. This number takes finding 1.**
>
> The reservation's premise was that both are *"about how a request handler obtains a transaction-scoped dependency it cannot construct itself"*. **Finding 2 is not, because `WithdrawalTx` has no such dependency**: finding 13 shows `POST /wallet/withdrawals` posts nothing and declares no `ledger` member, so its backend was never waiting on a handle it could not construct. It was waiting on an implementation, and finding 7 shows the implementation exists. **The seam was single in the dispatch and is double in the tree.**

> **Clause 2. `PayoutTx.ledger` IS THE DEFECT, AND THE MISSING DOOR IS NOT.**
>
> The question *"how does a request handler obtain a `LedgerTx`"* **has no good answer and should not be given one.** A door in `apps/api/src/db.ts` that returned a handle satisfying `LedgerTx` would be `systemDb` under another name: finding 5's vocabulary is closed, and the only handle that satisfies the interface is generic over **every table in the estate** (`insert<K extends TableKey>`). Admitting it to a request handler hands the trader surface authority over every row Merit holds, which is the hazard [ADR-102](ADR-102.md) section 8 foreclosure 2 and [ADR-165](ADR-165.md) both refused. **The refusal is upheld and this entry adds no fourth door.**
>
> **So the correct repair is on the PORT and not on the accessor: `PayoutTx` must not carry a `LedgerTx`.** The request path RECORDS the approval; the posting is performed at a system authority.

> **Clause 3. THE POSTING MOVES OFF THE REQUEST PATH, ON THREE PRECEDENTS THE TREE ALREADY SET.**
>
> This is not a new architecture, it is the one already in force everywhere else the same posting is reachable:
>
> * **The worker already posts**, at `systemDb('nightly-batch')` (finding 16).
> * **The operator console already posts**, `admin-payouts.ts`'s release arm at `systemDb('operator-console')`.
> * **The cash door already declined to post on its own request path**, deliberately and in writing, for this exact reason (finding 13).
>
> `payouts.ts` is the ONLY one of the four that tries to post from a request handler, and it is the only one that cannot be constructed. **That correlation is the finding.**

> **Clause 4. THE `INV-M5-06` KEY DISCIPLINE IS PRESERVED BY CONSTRUCTION AND THAT IS WHY THIS RULING IS SAFE.**
>
> Finding 15: all three doors build `` `${PAYOUT_ENDPOINT} ${idempotencyKey}` `` **from the request row's own stored key**, and `ledger_transactions.idempotency_key` is `text NOT NULL UNIQUE`. The key is therefore a property of the APPROVAL and not of the DOOR. Removing the request-path posting removes one of three doors that mint the identical string; **it cannot produce a second posting, and the database, not application memory, is what refuses one.**

> **Clause 5. `useWithdrawalBackend` STAYS BLOCKED, AND ITS RECORDED REASON IS REPLACED RATHER THAN DELETED.**
>
> The store exists, so the written reason is false. **The port is still not wireable, and the true reason is worse than the false one.** Findings 13 and 14: a wired endpoint writes a `requested` or `cooling` row, **nothing in this tree ever advances it**, and `requested` and `cooling` are both in `OPEN_WITHDRAWAL_STATUSES`, so `gateNoInFlight` refuses that identity's every later withdrawal.
>
> **Wiring it would convert an honest 503 into a permanent, silent, per-trader lockout** behind a screen that says a withdrawal is in flight. The dispatch's own constraint decides this: *"the failure direction must be refusal rather than duplication"*. **Both options refuse; only one of them refuses reversibly.** The 503 is the reversible refusal and it is kept.
