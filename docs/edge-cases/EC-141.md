## EC-141: Two approved documents disagree on where a golden file's expectation lives  (2026-08-15, module: M1, status: specced)
- Scenario: [STRATEGY section 2](../testing/STRATEGY.md) and [GOLDEN_SCENARIOS section 2](../testing/GOLDEN_SCENARIOS.md) both rule the fixture format as **"YAML plus an expected end-state JSON sibling"**, and GOLDEN_SCENARIOS section 2's printed example shows the expectation as an **inline `expect:` block in the YAML**. Both documents are approved and frozen, and a fixture author reading either one alone writes a valid-looking file the other rules out. The failure is not that a fixture fails to load, which would be cheap and loud. It is the two shapes that pass: a fixture carrying **both**, where a loader silently picks one and the reader cannot see which, and a fixture carrying only the inline block, where a loader that reads siblings finds none, applies a default, and the scenario goes green against an expectation nobody wrote. **A golden file is a specification, so an ambiguity about where its expectation lives is an ambiguity about what it specifies**, and this class resolves by whoever writes the next loader rather than once.
- Correct behavior: **The sibling is the physical layout and `expect` is the logical block it holds. The `.expected.json` sibling IS that block, serialized as JSON.** That reading keeps both approved sentences true without amending either, which is why it is the one taken: an ADR amending a frozen document to remove an ambiguity that a reading already removes is a cost with no purchase. Enforced by `L-05` in [`packages/golden-loader/src/loader.ts`](../../packages/golden-loader/src/loader.ts): **a fixture YAML carrying an `expect` key fails to load, naming the rule**, because the one shape neither reading permits is a fixture with two homes for one truth, and a loader choosing between them on a reader's behalf is the silent half of this entry. The sibling's key set is closed (`end_state`, `events`, `pins`, `note`) so a stray key is refused rather than ignored, and `L-06` refuses a sibling with no `pins`. **The ruling is reversible and the reversal is one rule wide:** if the founder reads it the other way, `L-05` inverts to refuse the sibling and the fixture files move their expectation inline. Nothing else in the loader depends on the direction, and that is deliberate, so the reversal costs an edit rather than a redesign. Recorded here rather than in a session note because an ambiguity between two frozen documents is discovered by every reader independently, and an entry is what makes the second reader's discovery a lookup.
- Golden scenario ref: **none owned**, which is the honest answer rather than an omission and uses CI-06e's documented sentinel so the exception is reported rather than silent. This is a property of the fixture FORMAT rather than of an engine behavior, so a scenario asserting it would be a golden file about golden files, and the registry would gain an identifier that pins no rule. It is covered by `L-05`'s seeded violation in [`packages/golden-loader/test/loader.test.ts`](../../packages/golden-loader/test/loader.test.ts), which asserts the rule id that comes back, and by the assertion that the untouched fixture tree loads clean.
