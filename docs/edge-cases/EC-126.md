## EC-126: The verification provider becomes a payout dependency  (2026-08-14, module: M19, status: specced)
- Scenario: M19 sits upstream of provisioning, funded trading, and the wallet's external withdrawal leg, so a provider outage has a blast radius that looks from outside exactly like the failure constitution 0 calls fatal. The dangerous part is not the outage but the naive gate: "verify KYC is current before paying" reads naturally as a provider call, and under a re-verification regime there is already a code path that talks to the provider on a sensitive action, so an outage would stop payouts for identities verified months ago. The second-order version is a multi-day outage under pre-funded leaving passers unable to be funded, which is a queue of people who did the hard part, and is the moment somebody suggests "let them trade and verify later".
- Correct behavior: **Verification is a state Merit holds, not a question Merit asks.** G-ELIGIBLE reads `kyc_verifications.state = verified` from Merit's own database and no payout path calls the provider, ever. A re-verification trigger **queues a new check without revoking the existing status**: the identity stays verified and the *gated action*, such as a destination change, is what blocks, keeping the ATO control tight while ordinary payouts flow. Provisioning queues honestly with a visible state, a pre-written comms template naming the dependency, and a next-update time rather than a slipping ETA. **"Trade now, verify later" is refused in advance, in writing**, because it is exactly what an outage produces and it converts a bounded delay into an unverified funded account. A second provider is post-v1 and is not the answer here.
- Golden scenario ref: GS-213.
