## EC-098: A backdated correction changes a statistic already published  (2026-08-14, module: M12, status: specced)
- Scenario: B4 #5 pins the backdated fill correction and the never-claw-back rule, but not that a correction to a closed trading day changes a number Merit already published. An account that passed now did not, and a trailing window that closed six weeks ago is wrong. Silently recomputing makes the published series editable, which destroys the evidentiary value of publishing it and is undetectable to anyone who did not save the old page. Never correcting leaves a known-wrong number. Correcting only when it helps is indefensible and is what everyone will assume happened unless the policy is fixed in advance. The version that will actually occur is subtler: most corrections are immaterial, and "sensible standard applied case by case, after seeing the delta" is exactly how a materiality policy becomes a selection mechanism, with the first hard case arriving under pressure.
- Correct behavior: Published values are **immutable**; a correction produces a new row with `restatement_of` set and the superseded value stays visible with a restatement note naming the cause. **Materiality is a published threshold per statistic, fixed in advance** (proposed 0.5 percentage points for rates, 1 percent of value for money figures), so restating is arithmetic rather than judgment; below the threshold the recomputation is still recorded in the method changelog, so nothing is invisible even when nothing is restated. Recomputation uses the **definition version in force when the original was published**, never the current one, or a restatement would silently mix a data correction with a methodology change. Every restatement alerts, because a rising restatement rate means the ingest pipeline has a problem the statistics surface noticed first.
- Golden scenario ref: GS-167.
