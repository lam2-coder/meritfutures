## EC-146: A control a database can only half-enforce reads as fully enforced in every document that cites it  (2026-08-16, module: M19, status: specced)
- Scenario: [ADR-039](../decisions/ADR-039.md) (c) requires that a phone change notify **the prior number and email**, which is `INV-M16-03`'s account-takeover countermeasure applied to a number. `phone_change_requests_applied_is_complete` makes `prior_notified_at` a precondition of reaching `applied`, and that **reads as enforcement** to every subsequent reader. It is not, and the gap is structural rather than a coding slip. **A database can only assert that a timestamp exists.** Worse, the sending path may have nothing to send to: there is **no plaintext telephone number in any migration**. `identity_phones.phone_hash`, `phone_change_requests.new_phone_hash`, `otp_challenges.destination_hash` and `contact_channels.value_hash` are all one-way, and `identity_phones.phone_preview` is deliberately "enough to recognise, not enough to reconstruct". Both `0019` and the [`contact_channels`](../architecture/data-model/contact_channels.md) design record say the value is hashed because **"the sending path holds the address"** — and the sending path is [M10](../plans/M10-integrations.md), which holds nothing by design, with `AS-M10-06` part 3 forbidding a vendor from holding it either. **So a handler with no address to send to and a NOT NULL-shaped obligation will fill the column, the constraint will pass, and the anti-takeover control will read as enforced in every document and in every test that inspects the row, while never having sent anything.** Challenge-response flows are unaffected, because there the trader types the number into the request; every message **Merit itself initiates** to a prior destination is the exposed class. The email side has the same gap on prior addresses and not on current ones, since `users.email` is plaintext but is one column on one row that a change overwrites.
- Correct behavior: **`SD-M16-06` made the countermeasure representable and not sendable, and the difference is the whole entry.** Storage-enforceable is not send-enforceable, and the two must never be conflated by a reader of the constraint. Two things follow and the first is a rule about evidence rather than about storage. **A notification obligation is discharged by a dispatch record, never by a timestamp**: `prior_notified_at` is set from an `integration_dispatches` row addressed to the prior channel, so the artifact that proves the send is the artifact that permits the state change, and a handler with no address produces no dispatch and therefore cannot advance the request. **GS-265 pins exactly this and is written to fail against the timestamp alone**, which is the only form of the assertion the `CHECK` cannot make. Second, **the address question is open and is named rather than assumed**: `OQ-M10-06` records that nothing in the schema holds an address the dispatcher can send to, and it is a founder ruling because the alternatives (a reversibly encrypted column under a dedicated key, or a vendor-held token) are a privacy decision and not an implementation detail. **This corpus has no gate that can tell a storage-enforceable control from a send-enforceable one**, which is stated here so the next reader does not infer enforcement from the constraint's shape.
- Golden scenario ref: GS-264, GS-265
