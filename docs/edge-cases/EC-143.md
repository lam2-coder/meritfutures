## EC-143: A recycled phone number convicts the innocent person who inherits it  (2026-08-16, module: M19, status: specced)
- Scenario: There is no adversary in the first half of this entry, which is what makes it the phone analogue of [AS-M19-04 and AS-M19-05](../plans/M19-kyc-identity.md): the harm falls entirely on somebody who did nothing. A fleet operator is restricted, and their verified number sits in `identity_phones` hard-linked to a banned identity, retained forever and correctly so, because it is fraud history. Months later the carrier reclaims the number and reassigns it, **which is ordinary carrier behaviour in every market Merit operates in and is not an edge case**. A new customer buys it, registers honestly, verifies it, and the strongest identity signal in the system now says they are a banned fleet operator. **Both obvious implementations are wrong and they are wrong in opposite directions.** Refusing at the door is one line, `phone_hash UNIQUE`, and it puts the innocent owner into a support ticket **before** any check that could rescue them has run, on a refusal that cannot explain itself: saying "that number belongs to another account" discloses the prior holder, which AS-M19-05 counter 4 forbids, so the honest refusal is an unexplained one. Binding silently hands them a ban they cannot see the reason for.
- Correct behavior: **Bind the graph, queue the human, then let evidence break the link.** Verification **completes** (`INV-M19-13`): the edge is written at the hard-link confidence ceiling, a **severity-5 flag opens against both identities**, and no state changes automatically. `identity_phones_live_number_idx` is deliberately **not unique**, and that missing index is the counter, because it is what buys the time for the check to run. The portability check then runs on evidence amendment 3 already paid for (`INV-M19-14`): if `last_ported_at` falls **after** the prior holder's restriction date this is not the same graph node, the prior row is **released** rather than superseded, and `identity_phones_release_is_evidenced` refuses a release that asserts this without showing it. A released row frees `identity_phones_live_per_identity_uq`, so the new customer verifies normally and **no operator unpicks anything by hand**. **Neither person is ever told about the other.** Two residuals are recorded rather than closed. **A number reassigned with no portability record leaves the guard with no input**, and that case ends where every unresolvable identity case in M19 ends, in a review queue with nothing enforced; `DEP-M19-09` makes portability history a **disqualifying** vendor criterion precisely because this is the corpus without it. And **the guard is a link-breaker, so it can be invoked on purpose**: an operator who understands it can cycle numbers to launder the graph one edge at a time. Three things bound that and none is the guard itself, a release is evidenced or it does not happen, every release is a permanent row so serial recycling is a countable pattern, and the phone is one node in a scored graph rather than a verdict.
- Golden scenario ref: GS-262, GS-263
