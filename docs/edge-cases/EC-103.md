## EC-103: The retention feature contends with the payout path for one database  (2026-08-14, module: M13, status: specced)
- Scenario: Analytics is by a wide margin the heaviest read workload in the estate: a funded trader with a year of history pulls tens of thousands of fills and the interesting queries aggregate across all of them. ADR-006 and ADR-007 deliberately put jobs, marks, fills, and the ledger in one Postgres instance so restore and backup are one procedure, which means an analytics query and a payout request contend for the same resources. The timing is the attack even with no attacker: traders open analytics after the session closes and around the daily reset, which is when the nightly batch runs and when M05 FM-M5-12's promo-day payout spike lands. The constitution's target is payout request p95 under 500ms, and the module most likely to break it is the one nobody classified as a money path. A trader with ten accounts refreshing during a wave is a denial of service with an innocent explanation, and a competitor who works this out has a very cheap way to make Merit's payouts slow on the day it hurts most.
- Correct behavior: **Precompute** the expensive shapes once per account per closed day in the nightly batch, so the common page load is a single-row read rather than an aggregation. Run analytics reads against the read replica or a role with hard connection and statement-timeout caps, so the worst case is slow analytics rather than slow payouts. Cursor paginate everywhere with a hard cap on the widest window a single request may ask for. And make it a **named gate**: load test analytics at realistic concurrency **while** the payout load test runs, asserting the payout p95 target still holds, because testing them separately proves nothing about the only interaction that matters.
- Golden scenario ref: GS-178.
