## EC-086: The support console is a read of the identity graph without the admin origin's controls  (2026-08-14, module: M10, status: specced)
- Scenario: The admin console sits behind a separate apex domain, an IP allowlist, hardware-key SSO, and RBAC (ADR-012, C-08). The support sidebar reads much of the same data through a service credential, from a self-hosted Chatwoot instance, over the public internet, for an agent authenticated by Chatwoot rather than by Merit. Exploited directly by a compromised agent account, and realistically by dossier item 9's social engineering: a caller who gets an agent to open a conversation "for" a trader has Merit's own tool display that trader's context, and everything read back is authoritative because it came from Merit.
- Correct behavior: The control sits in the data, not in the agent, because support staff are hired to be helpful under time pressure and will be. **The client never names the trader**: the sidebar passes the conversation's contact reference and the server resolves it, so there is no parameter in which to name an unassigned identity. Fields are role scoped and minimized to account status, plan, phase, gate progress, and ticket context, explicitly excluding the identity graph, linked accounts, payout destinations, flags, and KYC detail; anything beyond the default is a separately audited escalation. Every read writes `support_context_views` with the field list, and **per-agent breadth** (distinct identities per hour) is alerted, because that is the shape both compromise and a social-engineering campaign make. **Support cannot mutate identity, destination, or KYC state at all**, as a code-level absence rather than a permission setting.
- Golden scenario ref: GS-149.
