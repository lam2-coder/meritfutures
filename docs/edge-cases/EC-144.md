## EC-144: The one abuse that pays the attacker, funded by an exemption written for somebody else  (2026-08-16, module: M16, status: specced)
- Scenario: SMS pumping, also sold as artificially inflated traffic. The attacker controls, or revenue-shares with whoever controls, a block of premium-rate numbers, points Merit's registration form at them and drives volume. **Every OTP Merit sends is revenue to them and a line item to Merit.** No account is taken over and nothing is stolen in the sense the rest of M16 is written about. **It lands here through a classification error rather than a coding one.** `INV-M16-11` exempts the `security` class from rate limiting for an excellent reason, that a quota which can drop a freeze notice will drop one on the day it matters. Registration OTP looks **exactly** like a security message: it is about authentication, it is time-critical, and dropping it breaks a real customer's signup, so it would be classified `security` by any careful person applying this module's own four classes. **That classification is the vulnerability.** And the attack has a property nothing else in the corpus has: every other abuse costs the adversary something to attempt, while **pumping pays**, so there is no volume at which they stop voluntarily and no threshold below which the attempt is uneconomic.
- Correct behavior: **The exemption is post-identity, and the split is the invariant** (`INV-M16-12`). `INV-M16-11` is **CONFIRMED and not amended**, in those words: the security and money classes stay exempt for exactly the reason written beside them. What changes is that a **fifth class exists which is neither of them**. `INV-M16-11` was written for an authenticated recipient at an address Merit already verified, where an exemption costs Merit a message it wanted to send anyway; registration OTP is the opposite on both counts, so **an exemption there is not a promise to a customer, it is a blank cheque written to a stranger**. `notification_kinds.class` gains `pre_identity_auth`, which carries per-number, per-IP and per-country velocity plus the cost breaker of EC-142. **The enforcement is structural rather than configured**: `rate_limit_exempt` is `GENERATED ALWAYS AS (class IN ('security','money')) STORED`, on `mutable`'s precedent from `SD-M16-01` and for the identical reason, because as an ordinary boolean **one careless seed row marking the registration-OTP kind exempt restores pumping and nothing objects**. Generated, the two facts cannot disagree at all. `CI-06k` asserts the same thing from the tree, so a later migration widening that expression fails a gate rather than a reading. The existing `mutable` column then gives the right answer for the new class **without being touched**: `pre_identity_auth` is not silenceable, so nobody may opt out of the OTP proving they own the number they are registering.
- Golden scenario ref: GS-270
