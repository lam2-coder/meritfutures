## EC-150: A clock in the schema with nothing scheduled to reach it  (2026-08-16, module: M05, status: specced)
- Scenario: [ADR-040](../decisions/ADR-040.md) makes the auto-release **the load-bearing control** of the whole enforcement window: it is the only thing standing between a bounded hold and an indefinite one. The hold is therefore expressed the way every control in this corpus is expressed, as columns and a constraint. [`0031`](../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql) adds `hold_expires_at`, makes it mandatory whenever the status is `held_pending_review` through `payout_requests_hold_is_complete`, and indexes it for the sweep. **Every one of those artifacts reads as the control, and not one of them is it.** The control is a job somewhere else reaching the clock, and the schema cannot express that a job exists. **A hold with a mandatory expiry and no releaser is indistinguishable, from inside the database, from a hold that releases**: the column is populated, the constraint passes, the index is used, the row is correct, and the trader is never paid. It fails no test, because there is no test a schema can fail by omission, and it fails no review, because the reviewer is reading the migration and the releaser is not in it.
- Correct behavior: **Every `*_expires_at` column in the migration set is dispositioned in [CRON_INVENTORY](../ops/runbooks/CRON_INVENTORY.md)**, either against the release job that reaches it or on a written exemption list stating why no job is needed, and `CI-06l` asserts exactly that from the tree with no database. The disposition is **exactly one of the two**, because two dispositions for one clock resolve in whichever direction the reader already believed. **The discriminator for an exemption is which way a missing job fails**: a clock that releases something held must be reached, because nothing reaching it leaves a trader waiting on Merit indefinitely; a clock read as a predicate where the row is used needs no job, because expiry takes effect with no write and there is nothing to stall. The list **fails in both directions**, in the [NO-FLOATS list](../../scripts/db/assert_no_floats.sql)'s idiom: an unlisted column is the obvious failure, and **a stale entry for a renamed column is how an allowlist silently grants more than it names**, since the row stays, the list still looks complete, and the column under its new spelling is covered by nothing. The hold joins the **existing** hourly freeze-expiry sweep rather than getting a second job, on ADR-040's one-job-one-row-one-switch rule: a second sweep is a second thing to stall.
- Golden scenario ref: GS-275, GS-276
