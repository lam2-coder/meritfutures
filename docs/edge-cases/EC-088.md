## EC-088: An error handler copies crown-jewel data into the least controlled system in the estate  (2026-08-14, module: M10, status: specced)
- Scenario: An unhandled exception on the payout path is captured with frame locals, which include the eligibility snapshot, the clamped amount, the identity, and the destination reference, plus the request body on a serialization error. That payload lands in an error-tracking vendor with different retention, a different access model, more humans, and no relationship to the `scopedDb` discipline. The standard defense, a scrubber with a denylist of key names such as password, token, and card, is blind here by construction: the payout path contains none of those words and every field on it is sensitive.
- Correct behavior: **Invert the polarity to deny-by-default on money paths.** Errors raised inside the payout, ledger, KYC, and identity-resolution paths serialize an allowlisted context only: route, release, error class, request id, and account id. No frame locals, no request body, no headers. The allowlist is the same `integration_contracts` mechanism every other integration uses, so there is one queryable place answering what may reach the vendor. A **canary token seeded into a synthetic exception on a schedule** tests the negative, which is otherwise untestable: the canary appearing vendor-side proves the scrubber regressed. And `GET /admin/identities/:id/disclosures` answers the question the scenario creates, so a vendor incident has a bounded, evidenced scope rather than being reportable as unbounded.
- Golden scenario ref: GS-152.
