## 39. Fixture status and blockers

**One row per registered scenario, and the reason lives in a column rather than in prose.** [ADR-072](../../decisions/ADR-072.md) is the ruling: a fixture is writable when three checkable conditions hold, and **every row without a fixture carries a stated blocker from a closed vocabulary with a citation that supports it**. [Section 33.4](33-ownership-index-and-coverage-reconciliation.md) is the same idea at three rows; this is it at <!--gen:fixture_backlog_rows-->316<!--/gen-->.

**`status` is derived from the directory and not from this file.** `written` means a `GS-NNN-*.yaml` and its `.expected.json` sibling are on disk in [`packages/rules-engine/fixtures`](../../../packages/rules-engine/fixtures/README.md). `writable` means the assertion can be written today, and since [ADR-076](../../decisions/ADR-076.md) it names WHERE. `covered-elsewhere` means it is already written and RUNS, in a suite the citation names. `blocked` means at least one of `ADR-072`'s conditions fails, and the `blocker` names **the one that would still hold if every other were cleared**.

### `covered-elsewhere`, and the word that carries it is EXECUTED

[ADR-076 section 1](../../decisions/ADR-076.md) is the ruling and this is its rule in its own terms: **a registry row is discharged when its assertion is EXECUTED somewhere a gate can read, not when a file appears in [`packages/rules-engine/fixtures`](../../../packages/rules-engine/fixtures/README.md).** So a row is `covered-elsewhere` when **both** of these hold, and neither alone is enough:

1. the scenario has **no golden fixture**, and
2. a named suite outside that directory **runs an assertion for it**, in an ordinary `pnpm exec vitest run`, and the case is reported as a PASS.

A row in this status carries **no blocker**, because nothing is blocked. It is a status and not a seventh blocker term for a checkable reason: a blocker names which of `W1`, `W2`, `W3` fails, and on these rows none has.

**THREE THINGS LOOK LIKE COVERAGE AND ARE NOT, and the reason this list is here rather than in the ruling is that all three are true of a row this document nearly moved.**

- **A path that resolves is not a running assertion.** A file exists whether or not anything in it executes.
- **A file that contains the `GS-nnn` is not a running assertion.** Those ids were written into the suites by [session 123](../../sessions/2026-08-21-session-123.md) as comments, on purpose, so a gate could find them. A comment is a claim about a file, and a refactor can leave one behind.
- **A `describe` that names the row is not a running assertion when the block is skipped.** `describe.skipIf(condition)` with the condition false reports a named skip, never enters its body, and leaves every grep in the tree passing.

**The third was not hypothetical, it was `GS-072`.** [ADR-076 section 6](../../decisions/ADR-076.md) counted it among seven rows moving to this status while its cited block was `describe.skipIf(!replayExists)` over a false condition: a named skip whose body threw. **Six rows moved and not seven**, and the difference was one run of the suite. **The test for this status is therefore watched rather than read**: the citation is checked by executing it and seeing a PASS, not by opening the file.

**So the row satisfies section 1's governing rule and fails the gate that implements it.** `CI-06/fixture-inventory` assertion 6 refuses a citation that names the row ONLY from inside a disabled construct **or the comment run above one**, and `describe.skipIf` is in `TEST_DISABLERS` whatever its condition evaluates to. `GS-072` is named at [`:332` and `:341`](../../../scripts/demo/test/replay-determinism.property.test.ts), both in that comment run. **The gate is not wrong and is not relaxed**: it rules its own limit in its own text, *"IT IS A STATIC PARSE AND NOT A VITEST RUN ... **The row therefore stays `blocked` and the discharge is OWED**, with the repair named rather than performed: the id wants naming once outside the block, in a file [session 249](../../sessions/2026-08-27-session-249.md) did not hold. **What moved is the reason.** It is no longer *"the assertion runs nowhere"*, which was true and has stopped being true; it is that the only reader a gate has cannot tell.

### `GS-049` carries a disposition and not only a status, and this is it

**One fixture discharges the row and the row is NOT split.** [Its registry row](04-gs-030-to-gs-051-the-appendix-b4-battery.md) names three probe shapes and adds *"runs as a property suite as well as a fixture"*. **What is not in the stream is the third probe's LENGTH**, twelve flat days against the row's hundred, and the reason it is not a residual is arithmetic rather than effort: **a sibling pins one `end_state`, and the end state after twelve flat days and after one hundred is the same state, field for field**, because a flat day moves no balance, no floor and neither counter. A longer grind buys a golden file a longer `events` list and nothing else. The trajectory in between is what a property suite asserts, and the row itself names one.

**One thing was checked rather than accepted, and it did not hold.** The sibling names *"`RE-P-01`, `RE-P-03` and `RE-P-04`"* as where that trajectory is asserted. `RE-P-01` executes, at [`floor-monotonicity.property.test.ts:259`](../../../packages/rules-engine/test/floor-monotonicity.property.test.ts). `RE-P-03`'s content executes as `PT-02`, at [`win-days-monotonicity.property.test.ts:153`](../../../packages/rules-engine/test/win-days-monotonicity.property.test.ts). **`RE-P-04` executes nowhere in this tree**: no property suite asserts that `tradedDaysCount` is non-decreasing, which is [M01](../../plans/M01-rules-engine.md)'s `INV-09`. So the floor and the win-day count have the length and **the traded-day count does not**.

**That is a residual on `RE-P-04` and it is not a residual on this row.** The fixture pins `traded_days_count: 9` across the grind, so a counter that moved on a zero-fill day fails there; what is missing is the generated-sequence form, whose owner is the property suite and not a golden file. **The row moves to `written` on the directory**, per [ADR-072](../../decisions/ADR-072.md)'s rule that the status is a fact about the directory, and the missing `RE-P-04` suite is named here so it is not discovered a third time.
