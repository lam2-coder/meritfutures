Retention: forever.
Design note for the founder: `eligibility_snapshot` is a `jsonb` column rather than a separate table because it is written exactly once, always read with its parent, and must never drift from it. A join here would add a way for the proof and the decision to disagree.
**Why `SD-05`'s ordinal index is partial.** A failed transfer must not consume a ladder rung or advance the cap schedule (EC-037). With a total unique index a failure would burn the ordinal and the retry would need a new one, which silently shortens a finite ladder (5 / 5 / 4).
**Why the `SD-09` predicate is the dangerous half, and why the two indexes sit adjacent.** The partial unique enforces G-NO-IN-FLIGHT in the database because the engine is not the only writer (FM-11, EC-040, GS-052). If `transferring` had stayed in the predicate after [ADR-028](../../decisions/ADR-028.md) retired the value, the index would still exist, still be valid, and enforce **nothing**, because no row would ever match, and no test would fail. **A predicate fixed in one of two places is a uniqueness guarantee that holds on Tuesdays**, so both are written in one file, adjacent, with the same predicate, precisely so a future change to one is visibly a change to one of two. **[`0031`](../../../packages/db/migrations/0031_payout_hold_and_identity_restriction.sql) is that change and it moves both, adjacent, under their existing names**: a held request is **outstanding**, and had the predicate stayed at `('approved','frozen')` a trader could hold one request and file a second against the same account. That is the `C-02` defect from the other direction, and it is probed rather than reasoned about ([`probe_payout_hold.sql`](../../../scripts/db/probe_payout_hold.sql)).

**`held_pending_review` is not `frozen` under a second name, and the discriminator is the ledger.** Both states carry a cited flag, both expire, both block settlement. They diverge on the only question that decides behaviour: a **frozen** request has LT-01 posted and `trader_wallet` credited, so the money is already the trader's and enforcement means LT-03 `payout_reversal`; a **held** request has **nothing posted**, so release means *approve and pay* and enforcement means *close the request, with nothing to reverse*. A held request is entered **before** approval and stores the full evaluated decision, which is why `0031` relaxes no `NOT NULL` and no existing CHECK on this table.

**Why the hold trio survives its own release, and the freeze trio does not.** `payout_requests_freeze_is_complete` couples its trio to the status in both directions, so a released freeze must clear its columns and the row keeps no evidence it was ever frozen. That is merged and is not edited. `payout_requests_hold_is_complete` is written the other way on the new columns: an **open** hold must be complete, and a **released** one keeps its trio, so "Merit held this payout and paid it at the SLA" is provable **from the row**. This is [ADR-041](../../decisions/ADR-041.md)'s own argument for the restriction being an episode row: a record erased by the act of ending is unprovable at exactly the moment it is contested. The one combination that stays unrepresentable either way is a hold with a flag and no clock, or a clock and no flag.

**`payout_requests_account_ordinal_uq` is unchanged, and that is correct.** A held request holds its ordinal while held; enforcement sends it to `failed`, which releases the rung (EC-037). `payout_requests_freeze_is_complete` and `payout_requests_reflection_needs_settlement` are likewise unchanged: a held row leaves the three freeze columns null and satisfies the first branch of the one, and is `balance_reflection_status = 'pending'`, which the other permits.
