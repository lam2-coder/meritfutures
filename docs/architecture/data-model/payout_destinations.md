### payout_destinations
**`OI-06 (payout destinations)`**, [ADR-169](../../decisions/ADR-169.md), [`0051`](../../../packages/db/migrations/0051_payout_destinations.sql). **The destination namespace, given a table for the first time.** `C-11`'s and `C-24`'s 48 hour cooling window had no storage anywhere in the schema: `destination_ref` on [`payout_transfers`](payout_transfers.md) (`0010:243`) and [`wallet_withdrawals`](wallet_withdrawals.md) (`0011:132`) is the destination **of a transfer**, and nothing recorded that a destination changed or when. `G-DESTINATION-COOLING` ([STATE_MACHINES section 3.2](../STATE_MACHINES.md)) reads this table.

| Column | Type | Constraints | Why |
|---|---|---|---|
| `identity_id` | uuid | not null, fk `identities(id)` on delete restrict, pk | **The person, never the account.** The external leg carries no `account_id` for the same reason (`SD-M5-06`: the money is the person's by the time it is here). It is also what lets the **affiliate rail share the namespace**: `affiliates.identity_id` (`0005`) makes an affiliate an identity, so `C-24` needs no discriminator and no second table ([ADR-017](../../decisions/ADR-017.md): one rail, one destination table) |
| `destination_ref` | text | not null, `<> ''`, pk | The **provider-side** destination id, never bank details. Merit does not hold them, which is `0010`'s point and stays true here. **Byte-exact, not `citext`**: an opaque provider id may legitimately be case-sensitive, and folding case would collide two genuinely different destinations onto one row, handing the second a window it never earned |
| `first_seen_at` | timestamptz | not null default now() | When this destination first appeared for this identity. **The destination's own clock**, so a reconciliation that discovers one from an older `payout_transfers` row can state the earlier truth. **Immutable after insert** by `PAYOUT-DEST-C1` |
| `cooling_until` | timestamptz | **not null** | **THE CONTROL, and the `NOT NULL` is the whole of it.** See below |
| `created_at` | timestamptz | not null default now() | The **row's** clock beside the destination's. Equal to `first_seen_at` on every row a live registration writes; different on exactly the rows a backfill or reconciliation writes, which are the rows an incident is argued from |

Primary key: `payout_destinations_pkey (identity_id, destination_ref)`.
Constraints: `payout_destinations_cooling_follows_first_seen` (`cooling_until > first_seen_at`), `payout_destinations_ref_is_present` (`destination_ref <> ''`), and the `PAYOUT-DEST-C1` trigger `payout_destinations_window_only_grows`.
Indexes: **none beyond the primary key**, and that is a decision. See below.
Retention: forever (security record). **Not deletable by `merit_app`**, by `REVOKE DELETE ... FROM merit_app, PUBLIC` in `0051`. Not readable by `merit_analytics`, `merit_dispatcher` or `merit_live`.

**`cooling_until NOT NULL` is the amendment this record exists to carry, and the recommendation does not contain it.** [DELTA_MANIFEST](../../../packages/db/DELTA_MANIFEST.md)'s `OI-06` row recommends a registry *"carrying `first_seen_at` and `cooling_until`"* and says nothing about nullability. Under `timestamptz NULL` an `INSERT` that omits the column writes a destination that is **usable the instant it exists**: the gate reads `cooling_until > now()`, a NULL compares to nothing, the predicate is not true, and the withdrawal is not cooled. That is a fail-**open** on precisely the row an attacker who has just added their own destination has caused to be written. Under `NOT NULL` that row cannot exist. It is [SECURITY](../SECURITY.md) section 4 item 9's transferable lesson applied before rather than after: *"columns that record a control are not the control."*

**The duration is not in this table and that is [ADR-037](../../decisions/ADR-037.md)'s rule.** 48 hours is a launch candidate that lives in config, so what the database asserts is the **ordering** (`cooling_until > first_seen_at`) and never the length, which is exactly the split `0029` made for the phone ceremony's `withdrawal_hold_until`. **The window is nevertheless STORED rather than computed from `first_seen_at` plus today's configured duration**, and that is the one place this table deliberately accepts a second derivable-looking value: a cooling window is a **promise made at a moment**, so a config change from 48 hours to 72 would otherwise retroactively re-cool every destination ever registered, and a change the other way would retroactively release them. [`reserve_coverage_snapshots`](reserve_coverage_snapshots.md)'s `GENERATED` remedy for the same hazard is structurally unavailable here, for [session 281](../../sessions/2026-08-27-session-281.md)'s reason on a different table: a generated column is a row-local expression and the duration is not in the row.

**The first destination an identity ever registers is cooled too.** `C-11` and [SECURITY](../SECURITY.md) section 4 item 1 both say a **change** triggers cooling, and a first destination is not a change. But that document's own threat row is *"attacker with a stolen session requests a payout to their own destination"*, beaten by *"the 48 hour destination-cooling window (C-11)"*, and on an identity that has never withdrawn there is nothing to change from -- so a first-destination exemption is a hole that opens on every account that has not yet used the rail, which at launch is all of them. `NOT NULL` is what implements the fail-closed reading: every row carries a window because no row can be written without one, so *"is this a change?"* is never a question a handler gets to answer wrongly.

**`PAYOUT-DEST-C1`: the window may only grow, and the row's identity is fixed.** `UPDATE` has to exist, because [STATE_MACHINES section 6](../STATE_MACHINES.md) glosses the gate as *"destination changed **inside** the 48 hour cooling window"*, so a running window can be extended and an extension is an `UPDATE`. **The append-only alternative was refused on a measured ground rather than on taste**: with more than one row per `(identity, destination)` the gate's read becomes `max(cooling_until)`, and [ADR-157](../../decisions/ADR-157.md) **refused the scalar aggregate on the accessor** -- so an append-only registry would put `P5-h`'s gate outside the one door `P5-a` landed, blocking the slice this table exists to unblock. The trigger is what makes the grant safe: the only `UPDATE` anybody wants to make wrongly is one that **shortens** the window, and a PostgreSQL grant cannot tell a lengthening from a shortening. `identity_id`, `destination_ref` and `first_seen_at` are immutable in the same guard because they fail the same way -- each is an `UPDATE` that launders a new destination through a row that already had standing. An **equal** write is permitted, so a re-registration inside a still-longer window is a no-op rather than an error, which removes a read-then-decide race.

**The reader's obligation, which this table's shape makes load-bearing.** An **absent row** means *"register it and cool it"*, never *"not cooling"*. That is what keeps the byte-exact `destination_ref` fail-closed: a ref differing only in case finds no row, and the registration path then arms a window for it. The gate is `P5-h`'s and the obligation is recorded here because `0051`'s choice of `text` over `citext` is what creates it.

**Why the grants are a fourth shape.** [`0032`](../../../packages/db/migrations/0032_trading_calendar_holidays_coverage_revisions.sql), [`0039`](../../../packages/db/migrations/0039_economic_calendar.sql) and [`0049`](../../../packages/db/migrations/0049_reserve_coverage_snapshots.sql) each revoke `UPDATE, DELETE` because each implements an append-only table; [`0050`](../../../packages/db/migrations/0050_live_cache_and_role.sql) revokes `ALL` because its sentence is about reading. This table is neither. It must be **readable** by `merit_app` (both payout legs and the affiliate rail run there) and **updatable** for the re-arm. What may never happen is that a row **vanishes**: the row is the memory of the window, and a `DELETE` followed by a re-`INSERT` is a fresh `first_seen_at`, a fresh window, and no trace that the destination was ever here before. So `SELECT`, `INSERT` and `UPDATE` survive and `DELETE` goes, against `0026`'s `ALTER DEFAULT PRIVILEGES`.

**No index beyond the primary key, and the reader that would want one is named.** The gate's read is a single `(identity_id, destination_ref)` lookup, which the primary key serves exactly. `0029`'s partial `phone_change_requests_live_hold_idx` has no analogue **because of** the `NOT NULL`: that index exists to skip rows whose hold column is NULL and this table has none. [M07](../../plans/M07-risk-abuse.md)'s `D-09` destination-concentration detector reads `destination_ref` **across** identities, which the composite key's second column does not serve -- and `D-09` is specified against `payout_transfers`, the detector does not exist, and `P7` owns detectors. An index whose query nobody has written is a guess at its shape that a sacred file can never take back.

**What `0051` deliberately does not create.** No `provider` column: `destination_ref` is a provider-side id, but `wallet_withdrawals` carries no provider at all, so `P5-h` would have to supply a hardcoded `'rise'` to form the key, which is the literal-in-the-gate drift `E2` exists to catch. The day a second rail lands, the namespace needs a ruling and a **superseding** migration. No `verified_at` and no `notified_at`: `C-11`'s re-verification lives in [`kyc_verifications`](kyc_verifications.md) and the notification in `0034`'s contact tables, and a second copy of a fact is a second thing that can disagree with it. No `updated_at`: nothing in the fifty merged migrations maintains one, so every such column is a value a handler is trusted to write, and `cooling_until` moving forward under `PAYOUT-DEST-C1` is the record of the re-arm. No `DELETE`-refusing trigger, although [`0033`](../../../packages/db/migrations/0033_trading_calendar_revision_required.sql)'s `CALENDAR-C2` has the precedent and states why a revoke is weaker (*"a revoke does not bind the table owner and a trigger does"*): that guard is affordable on `trading_calendar` because a ruled correction path leaves every legitimate need another door, and this table has no ruled procedure for a row written in error. Named, and deliberately unspent.
